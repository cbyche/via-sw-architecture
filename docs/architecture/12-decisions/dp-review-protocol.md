# DP 공통 검토 절차

> 적용 범위: 새 VIA 핵심 DP 후보의 상세 논의와 A/B 정의.
>
> 각 후보는 이 절차로 검토한다. 기존 후보의 적합성, QA 우열, 구현 가능성을 이미 입증했다는 뜻은 아니다. 후보 목록은 [VIA 핵심 Architecture Decision 후보](./core-dp-discovery.md)에 있다.

> **v2 · 2026-09-24:** 초기 12개와 새 DP-13에 전체 적용한 보완 규칙을 §7.7~7.9에 기록했다. 상세 보고서보다 먼저 읽을 문서는 [최종 요약 보고서](./dp-executive-summary.md), 적용 결과와 검증 기록은 [전체 검토 종합](./dp-review-synthesis.md)이다.

**각 DP 페이지는 그 자체로 하나의 완성된 보고서여야 한다.** 해당 내용을 처음 보는 SW Architect 심사관이 이전 대화나 다른 DP를 읽지 않아도 문제, 대안, 구조 차이, 비교 근거와 판단을 순서대로 이해할 수 있어야 한다. 이 원칙은 검토 항목 충족과 별도의 필수 완료 기준이다.

## 1. 모든 A/B가 만족해야 할 원칙

**두 대안은 동일한 결정 범위에서 상호 배타적(mutually exclusive)이어야 하며, 각각을 최선으로 구성하여 서로에게 steelman 대안이 되어야 한다.**

여기서 steelman은 같은 기능·제약·자원 조건에서 유능한 설계자가 실제로 채택할 만한 강한 설계를 뜻한다. A를 선호하더라도 B의 장점을 가장 잘 살린 형태로 구성하고, B를 선호하더라도 A에 같은 기준을 적용한다.

두 대안을 합친 hybrid가 양쪽 장점을 실질적으로 취할 수 있다면 기존 A/B 비교를 그대로 진행하지 않는다. **그 hybrid를 새로운 A로 삼고, 이에 대등하면서도 같은 결정 범위에서 상호 배타적인 B를 다시 도출한다.** 새 B가 성립하지 않으면 DP를 재정의·분할·통합하거나 제외한다. 두 칸을 채우기 위해 약한 B를 만들지 않는다.

trade-off는 구조에서 나와야 한다. cache, 로그, 재시도, 검증 또는 정상적인 최적화를 한쪽에서 금지하여 차이를 만들지 않는다.

## 2. 상호 배타성을 어떻게 확인하는가

먼저 결정 범위를 고정한다. 같은 시스템 안에서도 요청 종류나 상태 종류가 다르면 서로 다른 구조를 사용할 수 있기 때문이다.

| 반드시 명시할 항목 | 답해야 할 질문 |
| --- | --- |
| 대상 | 어떤 요청, 상태, 계약 또는 실행 코드를 비교하는가? |
| 적용 조건 | 정상 시, 장애 시, fallback 시에도 어떤 범위까지 이 결정이 유지되는가? |
| A의 결정 규칙 | 누가 최종 확정하는가? 무엇이 기준 기록인가? 어떤 경계를 반드시 통과하는가? |
| B의 결정 규칙 | 위의 같은 질문에 A와 양립할 수 없는 어떤 답을 하는가? |
| 대안 식별 조건 | 실제 설계를 보고 A인지 B인지 구분할 수 있는 규칙은 무엇인가? |
| 동시 채택 시도 | A와 B를 함께 적용하면 어디에서 충돌하며, 해결하려면 어떤 새 책임·정책이 필요한가? |

같은 조건의 설계가 A와 B 양쪽 정의에 모두 들어가면 정의가 겹친다. 서로 다른 요청에 A와 B를 적용할 수 있다면 요청별 선택 정책과 그 권한도 검토한다. 정상 시 A, 장애 시 B로 전환한다면 전환 조건, 진행 중 상태와 최종 권한 인계까지 하나의 대안에 포함한다.

공통 구현 기술을 사용하는 것과 같은 구조 결정을 동시에 채택하는 것은 구분한다. 예를 들어 현재 상태 저장 방식도 로그를 남길 수 있고, 이벤트 이력 방식도 현재 상태 snapshot을 저장할 수 있다. 두 방식의 차이는 저장 파일 두 종류의 존재 여부보다 **상태가 불일치했을 때 어떤 기록을 기준으로 복구하는가**에서 확인해야 한다.

각 상세 문서에는 다음 문장을 구체적인 내용으로 완성한다.

> 이 DP의 대상은 ___이다. A는 ___를 최종 기준으로 삼고, B는 ___를 최종 기준으로 삼는다. 같은 조건에서 두 규칙을 동시에 적용하면 ___가 충돌한다. 이를 결합하려면 ___라는 추가 결정을 내려야 한다.

## 3. Hybrid를 먼저 구성해 보는 절차

A/B 초안을 만든 직후, 양쪽의 장점을 결합한 가장 설득력 있는 hybrid를 적는다. 단순히 “혼합 가능”이라고 기록하지 않고 누가 선택·중재하며 상태와 장애를 어떻게 처리하는지 설명한다.

| 결합 시도에서 발견한 것 | 처리 |
| --- | --- |
| 기존 A 또는 B의 최종 권한을 유지한 채 snapshot·cache·buffer 같은 보완책을 추가할 수 있음 | 해당 대안의 steelman에 포함한다. 적용 가능한 공통 보완책은 반대안에도 허용한 뒤 trade-off를 다시 본다. |
| 요청·단계·상태별 분담을 통해 양쪽의 핵심 장점을 취할 수 있음 | hybrid를 새 A로 구성한다. 선택 정책·중재·상태 연결 비용까지 포함하고, 상호 배타적인 강한 B를 새로 도출한다. |
| 권한 위치와 Process 배치처럼 서로 독립적인 결정을 한 A/B에 묶었음 | 결정 축을 분리한다. 서로 다른 DP의 선택을 조합할 수 있다는 이유로 하나의 DP 안에서 대립시키지 않는다. |
| 결합하면 요구사항 위반이나 권한 충돌이 발생함 | 충돌 지점과 이를 제거할 수 없는 이유를 구체적으로 기록한다. “복잡해진다”만으로 배제하지 않는다. |

hybrid의 비용도 비교 대상이다. 두 경로 유지, 선택 오류, 상태 동기화, version 호환, 장애 복구와 로그 연결을 포함한다. 그 비용이 어느 QA에 영향을 주는지 설명하고, 측정 근거가 없으면 예상이라고 표시한다.

hybrid 외에도 유력한 제3의 구조가 있으면 검토 기록에 남긴다. 더 강한 대안을 누락한 채 기존 두 안만 비교하지 않는다. 최종 A/B로 좁힌 이유와 제외한 구조의 이유를 남긴다.

## 4. Steelman을 어떻게 확인하는가

A와 B 각각에 다음 내용을 작성한다.

1. **채택 이유:** 어떤 실제 사용자 상황과 운영 조건에서 이 안을 합리적으로 선택하는가?
2. **완성된 설계:** 정상 응답뿐 아니라 취소·정정, 늦은 결과, 장애·재연결, 데이터 이행과 실행 기록을 누가 책임지는가?
3. **최선의 보완:** 상대안의 장점을 가져올 수 있는 최적화와 보완책을 적용했는가? 못 가져온다면 어떤 구조적 이유 때문인가?
4. **남는 약점:** 보완 후에도 남는 비용과 QA상의 불리함은 무엇인가?
5. **성립 조건:** 필요한 Model·Agent 기능과 target PC 자원 조건이 실제로 제공되는가? 미확인이라면 무엇을 확인해야 하는가?

같은 개발 성숙도, 자원 한도, 외부 기능과 합리적인 최적화 기회를 적용한다. 두 안의 코드 줄 수나 내부 호출 수를 억지로 같게 만들지는 않는다. 구조에서 발생하는 호출·상태·자원 차이는 평가에 남긴다.

한쪽에만 공통 기능, 검증, retry 또는 로그를 빼서 만들었던 장점은 인정하지 않는다. 선택안의 약점 보완을 측정 이후로 미루지 않고, 양쪽의 가능한 보완책을 후보 정의 단계에서 먼저 검토한다. 보완이 대안의 최종 권한이나 기준 기록을 바꾸면 새로운 후보 version으로 취급한다.

## 5. 함께 빠뜨리면 안 되는 기준

| 기준 | 확인할 내용 | 잘못된 비교의 예 |
| --- | --- | --- |
| 같은 제품 문제 | 같은 사용자 목표·필수 기능·완료 조건·권한과 정보 시점을 제공 | A는 취소를 지원하고 B는 지원하지 않는데 응답시간만 비교 |
| 한 가지 구조 결정 | 독립적으로 바꿀 수 있는 선택을 묶지 않음. 불가피하게 묶이면 그 이유를 명시 | 공통 Gateway 여부에 별도 Process와 다른 Model까지 함께 변경 |
| 실제로 바꿀 수 있는 책임 | VIA가 소유하는 책임과 외부 dependency의 제공 기능을 구분 | B를 위해 Agent에 존재하지 않는 복합 업무 기능이 있다고 가정 |
| 전체 수명과 장애 | 동시 요청, 지연·중복·역순 event, 부분 실패, 중단, 재연결·재시작을 양쪽에서 설명 | 정상 시에는 빠르지만 늦은 결과가 취소한 Task를 되살림 |
| QA의 구조적 인과 | 구조 차이 → 처리·변경·장애 경로 차이 → 단일 QA metric 차이를 연결 | 상태 소유자를 나눴다는 이유만으로 Process 장애도 격리된다고 주장 |
| 비용의 완전한 귀속 | 추가 Component, cache, 저장소, adapter, Model, 계측과 복구 비용을 실제 책임 경계에 따라 기록 | 공통 서비스 비용을 감추거나 Agent로 옮긴 시간을 VIA 성능 개선으로 주장 |
| 다른 DP와의 의존 | 선행 가정, 고정할 선택과 결론이 뒤집힐 조건을 명시 | 뒤 DP를 결정한 후 앞 DP의 A/B가 같은 기능을 제공할 수 없게 됨 |
| 비교 가능한 근거 | 같은 endpoint·단위·분모·evidence 수준으로 비교하고 실패·timeout도 포함 | Agent 실행을 제외한 QA-01과 Agent 없이 직접 처리하는 QA-02를 동일 구간처럼 비교 |
| 변경 비용과 가역성 | A→B와 B→A의 계약·데이터·배포 이행 범위, 호환과 복구 방법을 설명 | 기존 데이터 이행을 무시하고 “설정으로 언제든 전환 가능”이라고 주장 |
| 결론의 유효 범위 | 동점·미측정·한쪽 지배·조건부 우열과 재검토 조건을 허용 | 초기 후보 수를 모두 유지하거나 모든 DP에서 큰 점수 차이가 나야 한다고 전제 |

변경 비용을 QA-21~23의 평균 변경 요소 수와 임의로 합치지 않는다. [Architecture Element 정의](../10-element-definition.md)에 맞춘 구조 변경량과 이행 작업·불확실성을 구분해 기록한다.

필수 조건 위반은 QA 점수로 상쇄하지 않는다. 기존 [Quality Model](../08-quality-attributes/quality-model.md)의 잘못된 대상 Action, 중복 Action, 무효 승인 사용, 무단 접근·노출 금지 조건을 양쪽에 동일하게 적용한다. 모든 요청을 거절해서 조건을 만족한 후보는 기능 적합성에서 탈락한다.

## 6. 모든 DP를 논의할 동일한 순서

상세 검토 전에 전체 후보의 상호 배타성·hybrid 가능성·중복·선행 의존을 한 번 예비 점검한다. 이 결과로 논의 순서를 조정한다. 아래 표는 **작성자가 설계를 검토하는 순서와 산출물 기준**이다. 심사관에게 보여줄 완성 보고서의 읽기 순서는 6.2를 따른다. 검토 중의 시행착오를 그대로 보고서 목차로 옮기지 않는다.

| 순서 | 논의할 내용 | 반드시 남길 결과 |
| --- | --- | --- |
| 1 | 왜 지금 결정해야 하는가 | 발표용 배경 인트로 1페이지와 Mermaid 그림: 대표 사용자 상황, 실제 난제, 중요성·필요성, 고민할 지점과 한 문장 결정 질문 |
| 2 | 무엇을 결정하는가 | 한 문장 질문, 대상·적용 조건·제외 범위, 양쪽의 동일 기능·필수 조건 |
| 3 | 어떤 대안을 검토했는가 | A/B 초안, hybrid와 유력한 제3안, 결합·분할·제외 이유 |
| 4 | 양쪽을 충분히 강하게 만들었는가 | 각 안의 채택 이유, 필요한 외부 기능, 허용된 보완책과 보완 후 남는 약점 |
| 5 | 최종 A/B가 상호 배타적인가 | 같은 범위의 서로 양립할 수 없는 결정 규칙, 동시 채택 시 충돌 설명 |
| 6 | 실제 구조가 어떻게 달라지는가 | 같은 시야·표현 수준의 A/B Mermaid 구조 그림과 차이 요약: 공통·변경 Component·Interface·State·Deployment, 권한·소유자·의존 방향과 변경 비용 |
| 7 | 전체 수명에서 작동하는가 | 정상·동시 실행·제어·부분 실패·재연결·복구 흐름과 사용자에게 보이는 결과 |
| 8 | 사고실험에서 어떤 안이 얼마나 유리한가 | 전체 QA 비교표: 예상 우세·차이 크기·판단 확실성·구조적 이유·성립 조건, 주 비교 후보/회귀/해당 없음 분류 |
| 9 | 다른 결정에 의존하는가 | 다른 DP의 고정 조건, 서로 조합할 수 없는 선택, 필요한 제한 교차 비교 |
| 10 | 어떻게 공정하게 확인하는가 | 동일 workload·dependency·자원·계측 조건, 증거 수준, 동점·실패 처리와 사전 평가 규칙 |
| 11 | 언제 결론을 바꿔야 하는가 | 가정 변화, 반대 방향 결과, 이행·되돌리기 조건, 영향받는 다른 DP |
| 12 | 이 DP를 유지할 수 있는가 | 유지 / 재정의 / 분할 / 통합 / 제외 / 근거 부족에 따른 보류 및 이유 |

3~5에서 A/B가 성립하지 않으면 먼저 재구성하고 나서 상세 구조와 QA 표를 작성한다. 12의 “유지”는 비교할 DP로서 적합하다는 뜻이다. A나 B의 승자를 선택했다는 뜻은 아니다.

### 6.1 배경 인트로와 A/B 그림은 필수 산출물

각 DP의 상세 설명은 발표에 옮길 수 있는 **배경 인트로 1페이지**로 시작한다. 대표 사용자 상황과 그림으로 왜 중요하고 필요한지, 어떤 요구 사이에서 고민해야 하는지를 설명한 뒤 한 문장 결정 질문으로 끝낸다. A/B 상세 설명 전에 이 페이지를 배치한다.

A와 B에는 각각 **Mermaid 구조 그림**을 둔다. 동일한 VIA 전체 또는 확대 영역을 같은 이름·표현 수준으로 그리고, 공통 부분과 바뀌는 책임·권한·상태·계약·Process 경계를 명시적으로 구분한다. 각 그림 아래에는 핵심 구조 차이를 한 문장으로 설명하고, 두 그림 직후에는 공통/변경 사항 비교표를 붙인다. 비동기·상태·복구 순서가 핵심이면 같은 시나리오의 sequence 또는 state diagram을 추가한다.

그림의 범례, 논리 경계와 Process 경계의 구분, 발표용 배치와 축약 예시는 [DP 배경과 A/B 구조 그림 작성 기준](./dp-diagram-guide.md)에 있다. 작성 시 이 기준을 함께 적용한다.

### 6.2 독립된 완성 보고서의 읽기 순서

아래 목차를 각 DP 페이지에 적용한다. 문서의 길이보다 독자가 앞 내용만으로 다음 내용을 이해할 수 있는지가 기준이다. 인트로 1페이지는 보고서의 도입부이며, 보고서 전체를 한 장으로 압축하라는 뜻이 아니다.

| 순서 | 보고서에 보여줄 내용 | 독자가 여기까지 읽으면 이해할 것 |
| --- | --- | --- |
| 1 | DP ID·직관적인 이름·문서 상태·한 문장 요지 | 무엇을 검토하는 문서이고, 대안 검토·사고실험·측정·최종 결정 중 어디까지 진행했는가 |
| 2 | 그림을 포함한 배경 인트로 | VIA에서 사용자가 겪는 상황, 왜 중요한 문제인지, 왜 구조 결정을 해야 하는지 |
| 3 | 결정 질문과 공통 조건 | 같은 문제를 푸는 A/B의 비교 대상, 반드시 제공할 기능, 외부 기능·자원 가정과 제외 범위 |
| 4 | 대안 A의 설명과 Mermaid 구조 그림 | A의 핵심 원리, 전체 VIA 내 위치, 책임·권한·계약·상태, 대표 요청과 관련 실패 처리 |
| 5 | 대안 B의 설명과 Mermaid 구조 그림 | 같은 상황에서 B가 어떻게 작동하며, A와 어디가 같고 다른가 |
| 6 | 구조 차이와 A/B 구성의 타당성 | 한눈에 보는 공통/변경 비교, 양쪽 steelman, 상호 배타성, hybrid·제3안의 처리 이유 |
| 7 | 전체 QA 사고실험 비교표와 근거 | 어떤 안이 얼마나 우세하거나 비슷할 것으로 예상되는지, 이유·조건·불확실성은 무엇인지 |
| 8 | 검증 방법과 근거 수준 | 예상을 무엇으로 확인할지, 실제 결과가 있다면 무엇을 실행·관찰했는지, 예상과 결과는 어떻게 다른지 |
| 9 | 다른 DP와의 관계 및 변경 비용 | 어떤 선택을 고정했는지, 결론이 뒤집힐 조건, 계약·데이터·배포 이행의 영향 |
| 10 | 현재 판단과 다음 조치 | DP 유지·재구성·보류 여부, 대안 추천이 가능한 범위와 남는 약점, 무엇을 확인하면 결론을 바꿀지 |

A/B는 같은 항목과 같은 수준으로 설명한다. 양쪽의 장점과 약점, 정상 동작과 관련 실패 처리를 각각 이해할 수 있어야 한다. 설명에 필요한 sequence 또는 state diagram은 해당 대안 바로 뒤에 둔다. 별도 부록을 봐야 핵심 동작을 알 수 있는 구성은 피한다.

현재 단계에서 실측이 없다면 8에 검증 계획과 미측정 상태를 적는다. 10의 현재 판단도 설계·사고실험이 뒷받침하는 범위까지만 적는다. **완성된 보고서란 논의와 근거가 빠짐없이 연결된 문서이며, 미확인 사항을 숨기거나 최종 승자를 반드시 선언한 문서가 아니다.**

### 6.3 처음 읽는 심사관을 위한 작성 규칙

- **필요한 시스템 설명을 안에 둔다.** 해당 DP에 필요한 VIA의 역할, 주변 Component와 외부 dependency의 책임을 짧게 설명한다. 전체 시스템 문서를 복사할 필요는 없지만 핵심 경계를 외부 링크로만 대신하지 않는다.
- **용어를 쓰기 전에 풀어 쓴다.** 새로운 약어와 프로젝트 전용 용어는 첫 등장 위치에서 설명한다. 긴 사전을 먼저 암기하게 하지 않는다. QA·다른 DP를 참조할 때 ID와 직관적인 이름을 함께 쓴다.
- **하나의 대표 상황을 끝까지 연결한다.** 배경의 사용자 상황을 A/B 동작과 구조 비교에서도 사용한다. 새로운 장애·변경 상황이 필요하면 왜 추가했는지 설명한다.
- **절 사이에 논리적 연결을 둔다.** 어떤 문제 때문에 이 결정 질문이 나왔고, 어떤 구조 차이 때문에 이 QA를 비교하는지 문장으로 연결한다. 표와 그림을 나열하는 것으로 설명을 대신하지 않는다.
- **그림은 본문과 같은 대안을 설명한다.** 이름·책임·version을 맞추고 그림 앞에는 볼 지점, 뒤에는 핵심 차이와 의미를 적는다. 공통 부분과 변경 부분을 독자가 추측하게 하지 않는다.
- **조건을 주장 가까이에 둔다.** 가정·예상·실측을 구분하고, 특정 조건에서만 성립하는 우세를 일반적인 우세처럼 쓰지 않는다. 필요한 제약을 문서 끝의 주석에만 두지 않는다.
- **다른 문서는 검증을 위한 참조로 사용한다.** 결정에 필요한 요구사항·QA metric·고정한 다른 DP 선택은 이 문서에도 요약한다. 링크는 상세 계약과 출처를 확인하는 데 사용한다.
- **검토 이력은 본문 뒤로 보낸다.** 최종 비교안에 도달한 핵심 이유는 본문에 남기되, 폐기한 문구와 반복 수정 과정이 설명 흐름을 끊지 않도록 별도 이력으로 정리한다.

### 6.4 독립 보고서 읽기 검토

완료 전에 이전 대화와 다른 문서를 보지 않는다는 조건으로 처음부터 끝까지 읽는다. 아래 질문의 답이 해당 위치에서 이미 제시되어 있는지 확인한다.

1. 인트로를 읽고 사용자 상황, 중요성·필요성과 결정 질문을 설명할 수 있는가?
2. A/B를 읽기 전에 비교 범위와 공통 조건, 필요한 용어를 이해했는가?
3. 두 그림을 보고 VIA의 어느 부분이 같고, 어느 권한·상태·계약·실행 경계가 달라지는지 말할 수 있는가?
4. 왜 두 안이 각각 합리적이고, 왜 단순 hybrid로 선택을 피할 수 없는지 이해했는가?
5. 각 QA의 우세 예상이 앞에서 설명한 구조로부터 자연스럽게 이어지는가?
6. 예상과 실제 근거를 구분하고, 현재 판단의 한계와 다음 조치를 설명할 수 있는가?
7. 핵심 논리를 이해하려고 뒤 절을 먼저 보거나 다른 문서를 열거나 이미 지난 절로 돌아가야 하는 곳은 없는가?

어느 질문에 답하기 어려우면 설명 순서·이름·그림·전제 배치를 고친다. 설명자가 옆에서 보충해야만 이해되는 문서는 완료로 표시하지 않는다. 이 읽기 검토와 diagram 렌더링 검토는 링크·용어 자동 검사와 별도로 기록한다.

## 7. QA trade-off 표 작성 규칙

**각 DP 상세 문서에 전체 QA를 한눈에 비교하는 사고실험 표를 반드시 포함한다.** 양쪽 steelman과 상호 배타성을 확인한 A/B를 대상으로, 어떤 안이 얼마나 우세할지 또는 비슷할지를 예측한다. 각 QA는 기존의 단일 대표 metric을 그대로 사용한다.

### 7.1 사고실험 진행 방법

먼저 표 위에 DP와 A/B version, 대상 사용자 상황, 다른 DP의 고정 선택, Model·Agent 기능, workload·자원 조건을 적는다. 조건이 미정이면 사용한 가정을 명시한다.

같은 사용자 입력과 외부 사건을 A/B에 각각 넣었다고 가정하고 다음을 따라간다.

1. 누가 판단·확정하고, 어떤 Component와 계약을 거쳐 언제 사용자에게 결과가 전달되는가?
2. 동시 요청, 지연·중복·역순 결과, 취소·정정과 관련 장애가 발생하면 무엇이 달라지는가?
3. Model·Agent·Context·State 또는 실험·로그 요구가 바뀌면 어떤 설계 요소를 바꾸어야 하는가?
4. 양쪽에 합리적인 보완책을 적용한 뒤에도 어떤 시간·정확성·변경 범위·장애 영향·메모리·노출·기록 차이가 남는가?

각 QA에 관련된 상황을 사용하고, 그 QA의 기존 집계 방식으로 예상 대표값에 어떤 영향이 생길지 설명한다. 한쪽에 유리한 사례 하나만으로 전체 workload의 우열을 단정하지 않는다. 예상 방향이 조건마다 바뀌면 조건별로 설명한다.

### 7.2 예상 우세와 차이의 크기

표의 예상 판정에는 다음 표현을 사용한다. 이는 **측정 전 정성적 예상**이며 실제 수치·점수·확정된 승패가 아니다.

| 예상 판정 | 의미 |
| --- | --- |
| A 크게 우세 / B 크게 우세 | 해당 QA의 지배적인 비용이나 실패 경로가 구조적으로 달라져, 대표 사용자 상황에서 큰 차이가 날 것으로 예상 |
| A 우세 / B 우세 | 대표 상황에서 의미 있는 차이가 예상되지만, 지배적인 비용·실패 경로 전체가 달라지는 정도는 아님 |
| A 조금 우세 / B 조금 우세 | 방향은 예상할 수 있으나 전체 metric에 미치는 영향은 작을 것으로 예상 |
| 비슷 | 비교 가능한 경로·책임과 보완책을 살펴본 결과, 실질적인 차이가 작거나 없을 것으로 예상 |
| 조건에 따라 다름 | 명시한 조건에 따라 우세 방향이 바뀜. 같은 행에 조건별 방향과 크기를 적음 |
| 판단 근거 부족 | 방향 또는 차이의 크기를 뒷받침할 근거가 부족함. 아는 범위와 부족한 정보를 적음 |
| 직접 비교 불가 | 양쪽의 해당 경로·endpoint·분모가 같지 않음. 각각의 적용 여부와 이유를 적음 |
| 해당 없음 | 비교 범위에 해당 QA의 대상이 양쪽 모두 존재하지 않음 |

“비슷”은 “아직 모름”과 다르다. 실제 차이가 없다고 입증한 것도 아니다. 한쪽에만 해당 QA 경로가 없다면 “직접 비교 불가”로 남기며, 빠진 쪽을 0점이나 최고점으로 채우지 않는다.

차이의 크기와 판단 확실성도 구분한다. 확실성은 **높음 / 중간 / 낮음**으로 적는다. 높음은 고정된 구조·계약에서 이유를 직접 설명할 수 있는 경우, 중간은 명시한 workload·dependency 가정에 좌우되는 경우, 낮음은 미확인 기능·구현·Model 동작에 크게 좌우되는 경우다. 큰 차이를 예상해도 확실성은 낮을 수 있다. 확실성이 높아도 실측을 대체하지 않는다.

“크게 우세”에는 왜 작은 차이가 아니라 큰 차이인지 추가 근거가 필요하다. 임의로 10%, 2배, 5점 같은 숫자를 붙이지 않는다. 구조로 계산할 수 있는 값은 전제와 계산을 공개하고 설계 추정으로 표시한다. 이 표현들은 서열 비교용이며, 숫자로 바꿔 QA 간 합계나 승리 개수를 계산하지 않는다.

평가 역할은 주 비교 지표 후보 / 회귀 확인 / 해당 없음 중 하나와 이유로 기록한다. 상세 표에서는 ‘핵심·trade-off·보조’를 주 비교 후보의 세부 역할로, ‘필수·변경·관측·자원 회귀’를 회귀 확인의 세부 역할로 쓸 수 있다. 보조라고 적었다고 primary driver로 확정된 것은 아니다. 직접 비교가 어려운 QA는 대안별 적용 여부를 명시하고 공통 비교 조건을 먼저 해결한다. 같은 metric의 실제 경로가 존재하지만 이 DP가 바꾸지 않는 경우, 예상 판정은 “비슷”으로 기록할 수 있고 실제 평가에서는 회귀 확인으로 관리한다.

표 아래에는 A를 선택할 이유, B를 선택할 이유, 결론을 가장 크게 바꿀 미확인 가정과 먼저 확인할 항목을 짧게 적는다. 표만으로 숫자 투표를 하거나 최종 승자를 확정하지 않는다.

### 7.4 행별 근거와 후속 측정

표에 다 담기 어려운 내용은 해당 QA 바로 아래의 설명으로 연결한다. 각 행의 근거에는 다음 항목이 있어야 한다.

| 항목 | 적을 내용 |
| --- | --- |
| QA ID·이름·단일 metric | 카탈로그 정의와 연결. ID만 보고 다른 문서로 돌아가야 하지 않도록 이름을 함께 씀 |
| 역할 | 주 비교 지표 후보 / 회귀 확인 / 해당 없음과 그 이유 |
| A와 B의 예상 차이 | 어느 조건에서 어느 쪽이 얼마나 유리할 수 있는지, 또는 비슷함·판단 부족·직접 비교 불가 |
| 구조적 이유 | 바뀐 책임·계약·상태·배치에서 metric까지 이어지는 원인 |
| 보완 후에도 남는가 | 양쪽에 합리적 최적화를 적용해도 차이가 남는 이유 |
| 반증과 근거 | 어떤 결과이면 예상을 철회할지, 무엇으로 관찰할지, 현재는 가설·추정·실측 중 무엇인지 |

논의 단계에서는 수치 점수나 측정된 우열을 만들지 않는다. 측정 전에는 적용 QA, 목표·점수 경계, workload, 실패 처리, 의미 있는 차이와 동점 판정 규칙을 동결한다. 이후 실제 구조적 차이가 확인된 QA만 [Evaluation Method](./evaluation-method.md)의 사전 기준에 따라 주 비교 지표로 확정한다. 특정 개수를 채우기 위해 QA를 추가하지 않는다.

QA-11과 QA-12~15는 통합 결과와 원인 설명의 관계이므로 같은 성공을 독립 점수처럼 중복 합산하지 않는다. 반드시 지켜야 하는 조건, target 미달과 증거 부족도 함께 보고한다. 어느 쪽이 더 좋은지 종합할 우선순위나 가중치가 필요하면 결과를 보기 전에 정하며, 미정이면 조건별 trade-off까지만 결론낸다.

제품 내부 로그 자체를 비교하는 DP에서는 독립적인 평가 관측으로 로그 누락 여부를 확인할 계획도 필요하다. 후보가 남긴 로그만을 정답으로 삼아 그 로그의 완전성을 판정하지 않는다. 실제 fixture·반복 수·계측 계약은 [Measurement Guide](../11-measurement/README.md)에 따라 후속 동결한다.

후속 측정에서는 이 사고실험 표의 version을 보존하고, 같은 QA 행에 실제 A/B metric, 측정 판정과 예상 일치·불일치 이유를 연결한다. 예상을 결과에 맞춰 덮어쓰지 않는다. 반대 결과나 비슷한 결과도 그대로 기록한다.

### 7.5 사고실험 근거의 엄격성

예상표의 판정은 아래 내용을 담은 사고실험 기록과 연결한다. “경계가 적으니 빠르다”, “통합했으니 정확하다” 같은 일반론만으로 우세를 채우지 않는다.

1. **출발점 구분:** 현재 계약에서 확인한 사실, 후보 설계로 정한 사항, 확인되지 않은 가정을 분리하고 출처 절을 적는다.
2. **동일 사건 추적:** 같은 입력·외부 사건을 A/B에 넣고 판단·호출·상태 갱신·출력을 단계별로 따라간다. 각 단계가 어떤 QA 구간에 포함되는지 확인한다.
3. **차이 도출:** 공통 비용을 제외한 추가·제거·변경 경로를 적는다. 수식이나 요소 수를 쓰면 변수·대상·집계 단위를 정의하고, 모르는 값을 임의 상수로 채우지 않는다.
4. **반대안의 최선 적용:** cache·batch·Model 공유·adapter·부분 재시도 등 적용 가능한 보완을 양쪽에 허용하고도 남는 차이인지 확인한다.
5. **반례와 민감도:** 우세가 사라지거나 뒤집히는 workload·장애·dependency 조건을 적는다. 범위 내의 타당한 반례가 해결되지 않으면 판정을 조건부 또는 판단 근거 부족으로 내린다.
6. **대표 metric까지 연결:** 일부 경로의 개선이 가장 느린 case의 p95, 전체 run 비율 또는 전체 change pack 평균까지 바꾸는지 확인한다. 한 경로의 예시를 전체 QA 결과로 확대하지 않는다.

각 기록에는 짧은 식별자와 설명 제목을 두고 QA 행에서 연결한다. 근거의 확실성이 예상표의 표현보다 약하면 표를 낮춘다. 구조적으로 중요한 결정이어도 양쪽 steelman을 적용한 뒤 충분한 QA trade-off가 남지 않으면 그 사실을 적고 Core DP 유지 여부를 재검토한다.

### 7.6 첫 적용에서 확인한 비교 왜곡 방지 항목

[DP-01 사고실험](./via-dp-01-direct-handling.md)에서 다음 점검을 추가했다. 다른 DP에도 같은 원칙을 적용하되 기존 QA 정의를 변경하지 않는다.

- **경로·분모 이동:** A/B 선택으로 요청이 다른 QA 경로에 들어가거나 Task 자체가 없어지면 서로 다른 대표값을 직접 비교하지 않는다. 적용 불가를 0시간·성공 표본으로 채우지 않는다.
- **비용의 외부 이동:** 외부 Agent 시간·메모리·변경 책임이 VIA의 측정 경계 밖으로 이동한 것과 사용자 전체 비용이 줄어든 것을 구별한다.
- **metric의 실제 의미:** 요청 영향 범위는 변경 요소 수가 아니고, 총 노출량은 초과 노출이 아니며, 필수 의존 실패는 불필요한 장애 전파가 아니다. 지표 이름만으로 인과를 추정하지 않는다.
- **계약상 가능성과 결과의 차이:** 강한 양쪽 설계가 같은 정확성·관측 계약을 만족할 수 있다는 사실만으로 실측 동점을 확정하지 않는다. 오류 빈도·변경 ledger·자원 수명이 없으면 차이 크기를 미정으로 남긴다.
- **판정 분리:** 구조 결정의 유효성, QA trade-off의 충분성, 문서의 읽기 완결성, 후보 명세·검증 완료를 각각 보고한다. 한 항목의 통과를 다른 항목의 통과로 대신하지 않는다.

### 7.7 전체 적용에서 추가한 왜곡 방지 규칙

| 점검 | 적용 규칙 | 대표 적용 |
| --- | --- | --- |
| 기능 적합성 먼저 | 필요한 native 시각·정정·node 제어 기능이 없으면 후보 성립 문제다. 시험기가 누락 정보를 무료로 주거나, 불가능한 B를 낮은 정확성 점수로 비교하지 않는다. | DP-03/07 |

‘A 우세 가능 · 중~큼, 조건 X’ 같은 표기는 §7.2의 조건부 방향과 정성적 크기를 함께 쓴 것이다. X에서 달라지는 경로를 설명하되 전체 대표값에서도 그 크기가 확인되었다는 뜻으로 쓰지 않는다. 실제 대표값의 크기를 모르면 본문과 결론에 반드시 그 한계를 적는다.

### 7.8 핵심 DP와 나머지 구조 결정을 구별한다

모든 중요한 결정을 같은 수준의 A/B 평가 대상으로 만들지 않는다. 전체 적용 결과는 다음 네 분류로 정리한다.

| 분류 | 필요한 근거 | 처리 |
| --- | --- | --- |
| 우선 핵심 검증 후보 | 합리적 steelman과 배타성이 있고, 동일 기능의 명시적 사건에서 서로 반대 방향인 QA 비용·효과가 구조로 설명됨 | 먼저 검증 명세를 준비한다. 크기·대표성·target·승자는 여전히 미확정이다. |
| 조건부 핵심 후보 | 구조 차이는 유효하나 실제 critical path·변경 집합에서 충분한 양방향 효과가 남는지 미확인 | 결론을 가를 구체 조건을 적는다. 조건을 해소해도 차이가 약하면 보조 결정으로 낮춘다. |
| 선행 범위·기능 적합성 결정 | 제품 책임이나 외부 기능을 정해야 비교 가능한 모집단이 성립함 | 범위·지원 profile을 먼저 정리한다. 비교 불가능한 metric을 억지로 같은 표본으로 바꾸지 않는다. |
| 보조 설계 결정 | 구조적으로 중요하지만 반대 방향의 QA 이점이 약하거나 지배 관계 가능성이 있음 | 명시적 계약으로 유지하고 다른 DP 비교의 고정 조건으로 사용한다. 주 평가표의 수를 채우지 않는다. |

위 분류는 심사·측정 통과나 ADR 승인을 뜻하지 않는다. 가능한 차이 하나를 찾는 것과 이 제품의 대표 QA를 크게 바꾸는 것은 다르다. 관측 가능한 반례·승격/강등 조건을 남기고, 심사 발표에서도 조건부 후보를 확정 핵심 목록처럼 합쳐 소개하지 않는다.

### 7.9 전체 문제와 신규 후보를 한 번 더 확인한다

모든 보고서를 작성한 뒤 UC-01~18, 24개 M/A/C 변경과 5개 E 변경, 전체 19개 QA를 다시 연결한다. coverage는 관련 책임·검증 위치가 있다는 뜻이며 기능 구현·정확성 입증이 아니다. 같은 QA가 여러 DP에 연결되어도 자동으로 ASR이 되지 않는다.

신규 DP는 기존 요구에서 나온 미해결 구조 질문이어야 한다. 독립적인 권한·상태·계약·Process·dependency 축인지, 기존 DP의 보완책이나 파라미터인지 먼저 검사한다. 정상적인 배타적 steelman A/B와 양방향 QA 가설이 성립할 때만 ID를 추가한다. 그렇지 않으면 기존 DP의 공통 조건·미확인 사항으로 연결한다. 이번에는 정상 과부하의 자원 점유 권한을 다루는 DP-13을 추가했다.

ID는 검토 우선순위가 아니라 지속적인 식별자다. 범위를 재정의하거나 A/B 이름을 바꾸면 이전 의미와 새 의미를 매핑하고 version을 기록한다. 특히 기존 ADR의 A/B 문자와 새 VIA-DP의 A/B 문자를 그대로 대응시키지 않는다. 이미 공개된 v1 예상은 Git의 해당 commit으로 보존하며, 측정 이후 수정으로 원래 가설을 덮어쓰지 않는다.

## 8. 완료와 재검토 관리

각 DP에 검토 version, 공통 조건, 결정 규칙, 후보 A/B version, 관련 QA·다른 DP, 미확인 가정과 판정 근거를 남긴다. 상호 배타성, hybrid 검토, steelman, 배경 인트로와 그림, A/B 구조 그림과 차이 요약, 전체 QA 사고실험 비교표와 공정한 검증 경로가 설명되어야 상세 정의를 완료로 표시한다. 그림의 렌더링 가독성과 6.4의 독립 보고서 읽기 검토도 통과해야 한다. 판단 근거 부족인 행에는 부족한 정보와 후속 확인 방법을 남긴다.

새로운 hybrid, 외부 기능의 부재, 선행 DP 변경 또는 공통 조건 변경이 발견되면 영향을 받는 후보와 QA만 연결을 따라 다시 연다. A/B의 결정 규칙이 바뀌면 새 version으로 기록하고, 이전 예상·결과를 새 후보의 근거로 그대로 사용하지 않는다. 공통 절차 변경은 전체 후보에 영향 점검을 한 번 수행한다.

모든 후보 검토 후 남은 DP의 중복, 전체 문제 coverage와 조합 가능성을 다시 확인하여 최종 목록을 정한다. 서로 충돌하는 선택들의 개별 승자를 단순 결합하지 않는다. 근거가 부족하면 보류할 수 있으며, 반복 작업을 피하기 위해 불확실성을 숨기지는 않는다.
