> 상태: **사용자 피드백 반영 / 구조 제안은 합의 전 / 구현·측정 없음**

## 1. 합의한 행동과 아직 제안인 구조

| 항목 | 상태 |
| --- | --- |
| 제한된 조회 후에도 지칭 후보가 둘 이상이면 질문 | 사용자 합의 |
| 새 발화 시 같은 Conversation의 미전송 요청 보류 | 사용자 합의; 실제 전송과의 경쟁 경계는 본문 §11 |
| 한정된 자료 설명·요약은 VIA, 조사·업무 계획·실행은 Agent | 사용자 합의; semantic LLM이 의미상 handling을 제안 |
| 화면 상세 표시, 사용자 발화 중 음성 알림 금지, 종료 뒤 음성 핵심 요약 | 사용자 지정 |
| 중단 뒤 재개 의도가 불명확할 때만 확인 | 사용자 합의; Request Interpreter가 새 입력의 재개·정정·전환 의미를 판단 |
| S2S 직접 응답 최소화 | 사용자 지정; 맥락 없이 자체 지식으로 답할 수 있는 명백한 독립 질문만 허용, 나머지는 VIA 해석 |
| 단기·중기·장기 기억과 저장 방식의 분리 | 설계 진행을 사용자에게 위임받음; 수명·승격·삭제의 세부안은 검토 중 |
| 독립 업무는 별도 Task, 한 업무의 단계는 한 Agent에 통째로 위임 | 사용자 합의; 같은 Agent가 여러 Task를 담당해도 identity는 분리 |

## 2. S2S 직접 응답은 명백한 자체 지식 질문에 한정한다

**사용자 지정 방향:** S2S의 자율 판단 범위를 최소화한다. 첫 질문이라도 “광합성이 뭐야?”처럼 현재 문장과 자체 지식만으로 답할 수 있는 명백한 독립 질문이면 직접 답할 수 있다. 반대로 “두 번째 걸 쉽게 설명해줘”는 이전 답변의 대상 해석이 필요하므로 VIA Core가 처리한다. 첫 질문/후속 질문이라는 순서 자체를 routing 기준으로 쓰지 않는다.

S2S에 Task·자료·기억 해석, Context 검색, 업무 planning·tool loop를 붙이지 않는다. 앞서 제안한 풍부한 대화 view를 이용한 후속 대화 fast path와 Interaction Guard 확장안은 채택하지 않는다. VIA가 확정한 내용을 S2S로 음성화하는 것은 계속 가능하며, 이는 S2S가 요청 의미를 자율적으로 확정하는 직접 응답과 다르다.

| 입력 | 목표 경로 |
| --- | --- |
| “광합성이 뭐야?” 같은 독립 자체 지식 질문 | 최소 admission을 통과하면 S2S 직접 응답; 첫 질문도 허용 |
| “두 번째 것은?”, “이 오류는 왜 나?” | Request Interpreter가 대화·화면과 결합해 해석 |
| “지금 날씨는?”, 개인 자료 질문 | VIA가 필요한 현재/개인 근거를 조회·해석하거나 위임 |
| “요약해서 메일로 보내줘”, “아까 일 취소해” | VIA가 목표·Task·제약을 확정한 뒤 Agent 위임·제어 |

**아직 닫아야 할 설계:** ‘명백한 독립 질문’임을 판정하는 최소 admission 계약. 새 범용 classifier나 S2S agent runtime을 두지 않고 같은 S2S의 제한된 direct/Core 제안과 host의 제외 조건 검사를 결합하는 안을 검토한다. 이 제안은 요청 전체의 referent·Task·계획을 S2S에서 만드는 계약이 아니다. 정보가 부족하거나 모델이 제한된 인계 출력을 지원하지 않으면 Core로 보낸다. 좁은 허용 범위에 대한 예시·제외 조건·지원 모델 계약은 추가로 구체화한다.

Controller는 Request identity와 현재 입력·권한·출력 세대 및 알려진 대기 질문·정정 여부를 확인한다. 이 host 검사는 semantic LLM 재호출과 다르다. 단어 규칙이나 S2S의 자신감만으로 숨은 맥락 의존성을 전부 판별한다고 주장하지 않는다. 허용되지 않은 speculative 답변은 재생하지 않는다. 판단 실패가 남는다는 사실과 매번 Core로 전환할 때의 지연 비용도 보존한다.

## 3. 모델 요구를 누가 확인하는가

사용자가 지금 모델 API나 구현 방법을 해결해야 하는 것은 아니다. Architecture 작업에서는 에이전트가 필요한 연동 계약, host에서 해결하는 부분, 모델 의존 부분, 미지원 시 동작을 정리한다. 특정 dependency가 정해지면 공식 문서·공개 예제로 지원 여부를 조사하고, 실행 환경이 제공되는 범위에서 실제 입출력을 확인한다. 문서 확인과 실제 실행 관측은 구분한다.

| 요구 | VIA가 설계할 부분 | 실제 dependency 확인이 필요한 부분 |
| --- | --- | --- |
| 생성 중 음성 보류·즉시 중단 | 자체 playback buffer·release·epoch·로컬 stop | audio stream 획득, 생성 취소·session 제어 지원 |
| 말과 당시 화면 연결 | OS capture·timestamp·timeline·gap 처리 | transcript와 acoustic 시점 대응을 얻을 수 있는지 |
| 상세 Text와 Voice 요약 | 공통 사실·채널별 view·실제 전달 기록 | 지정한 Voice 요약의 의미 보존, text/audio 대응 |
| 최소 S2S 직접 응답 | 좁은 허용 범위·host 제외 조건·Core fallback | 단순 direct/Core 인계 출력과 실제 판정 품질 |
| 이미지 화면의 이해 | 화면 근거와 UI 정보의 선택·제공 계약 | 공유 semantic LLM이 필요한 시각 입력을 처리하는지 |

사용자가 공유 on-device Omni, 약 10B Thinker 개발 목표, fine-tuned Qwen3-Omni-30B-A3B-Instruct reference를 지정했다. 모델팀에 요구할 계약도 이 Architecture에서 정하며 별도 ASR을 필요한 구조에 포함할 수 있다. [공유 Omni 설계](./shared-omni-runtime.md)에 입력 보호·역할 분리·자원 경합과 모델/runtime/host 책임을 구체화했다. 사용자에게 API 설계를 떠넘기지 않는다. 실측에는 향후 승인된 실행 환경·모델 접근이 필요하며 지금 완료했다고 주장하지 않는다. [모델 기능 확인 원장](./model-capability-review.md)에 공식 문서 확인과 실제 실행 상태를 분리해 기록한다.

## 4. 복합 요청의 실패는 두 수준으로 나눈다

기준은 문장 길이나 “그리고”의 개수가 아니라 **사용자의 독립 목표인지, 한 목표를 수행하는 내부 계획인지**다.

| 상황 | VIA | Downstream Agent |
| --- | --- | --- |
| “이 문단 요약하고 오후 일정 알려줘” | 명시된 독립 요청과 각각의 결과·실패 관리; 한쪽 실패가 다른 쪽을 막지 않음 | Agent 위임이 필요한 항목이 있을 때만 해당 업무 수행 |
| “자료를 요약한 뒤 그 요약을 메일로 보내줘” | 자료·수신자·제약·완료 조건을 한 Task로 묶어 Agent에 통째로 위임 | 요약·발송의 내부 순서·의존·재시도·부분 실패를 처리 |
| “경쟁사를 조사해서 보고서를 만들어줘” | 하나의 목표·제약·완료 조건으로 위임하고 부분/최종 상태 연결 | 조사 순서, 검색 도구, source 실패 대처, 보고서 작성과 저장 |
| “보고서와 일정 등록을 각각 해줘” 중 보고서 실패 | 일정과 무관하면 일정 결과 유지; 전체 성공이라고 보고하지 않음 | 각 업무 내부의 실패 원인·복구 가능성·실제 완료 범위 제공 |

“요약해서 발송”은 하나의 사용자 업무이며, “조사해서 보고서 작성”과 같은 위임 경로를 사용한다. VIA가 요약 Request와 발송 Request로 자동 분해하지 않는다. 단독으로 요청한 자료 요약은 VIA 직접 처리일 수 있지만 외부 실행을 위한 업무 내부 단계라면 Agent에 포함한다.

독립된 지속 업무 두 개는 VIA Task도 두 개다. 같은 Agent를 선택해도 각각의 상태·취소·질문·완료를 연결할 identity를 유지한다. Agent가 이를 구분할 계약을 제공하지 않으면 하나의 불투명한 실행으로 합치지 않는다. 일회성 직접 응답은 여전히 Request만으로 충분하며 모든 독립 질문에 장기 Task를 강제하지 않는다.

VIA Request Graph는 독립 목표와 사용자가 명시한 목표 사이 관계만 표현한다. 한 업무 내부의 요약→발송 같은 단계 graph는 Agent 책임이다. 별도 목표·담당 경계 때문에 실제로 Task 사이 결과 인계가 필요한 경우에만 Controller가 선행 결과 version과 후속 admission을 연결한다. 한 Agent가 업무 전체를 처리할 수 없다는 이유만으로 VIA가 임의로 내부 계획을 짜지 않는다. 전체 수행 가능한 Agent를 찾거나 지원 한계를 알리고 필요한 사용자 선택을 구한다.

Agent가 실패했다고 VIA가 내부 plan을 새로 짜거나 전체 업무를 무조건 재실행하지 않는다. 실패·완료 범위·artifact version·접수 상태를 확인하고 사용자에게 다음 선택을 연결한다. 확인되지 않은 외부 상태는 확인 불가이며, 내부 retry와 외부 재위임을 동시에 시도해 중복 실행하지 않는다. 사용자 명시 all-or-nothing 요구가 있을 때는 실행 전 지원 여부를 확인하고, 여러 Agent의 Action을 VIA가 원자적으로 rollback할 수 있다고 약속하지 않는다.

## 5. 기억은 의미 수명과 저장 방식을 분리한다

단기·중기·장기는 “언제 어떤 의미로 재사용할 것인가”이고 RAM·파일·DB는 “어디에 어떤 내구성으로 저장할 것인가”다. 중기 기억도 재시작을 견디려면 디스크에 저장할 수 있다. 파일 DB 자체를 장기 기억과 동일시하지 않는다.

| 계층 제안 | 예시 | 소유권·저장·수명 |
| --- | --- | --- |
| 단기 작업 Context | 현재 발화, 당시 화면, 선택, 이번 해석에 필요한 원문 | IM evidence buffer·Controller workspace·Context cache; RAM 중심, 요청이 쓰는 evidence만 정책 범위에서 pin·필요 시 내구화 |
| 중기 Conversation·Task 작업집합 | 최근 대화 요약, 확정 대상, 미해결 질문, 진행 업무와 결과 참조 | Context Manager가 원래 owner 기록에서 파생 view 생성; 필요 시 지속 저장하고 source revision으로 재구성 |
| 장기 User Memory | 사용자가 허용한 답변 선호·지속 사실 | Context Manager owner, State Store 내구 기록; 확인·변경·삭제 가능; 현재 지시가 우선 |
| 원본 업무·응답·복구 기록 | Task/Execution, command, 질문, 결과·전달 기록 | Controller·Task·Gateway·Response 각각의 권위; 기억 요약 계층과 별개, cache 만료로 삭제하지 않음 |

저장 주안은 local embedded DB로 구조화 상태·참조·삭제 revision을 관리하고, 허용된 큰 evidence는 별도 파일로 두되 수명·참조를 함께 관리하는 것이다. 특정 DB 제품은 아직 선택하지 않는다. DB와 파일 사이 crash로 생기는 orphan·누락의 복구 계약도 필요하다. 추가 embedding 모델이나 vector DB를 자동 도입하지 않는다.

요약에는 출처·version·범위·누락을 남긴다. 정확한 대상 ID·수치·제약·권한·업무 상태는 typed record와 필요한 원문을 유지하고, 요약이 부정·조건·정정을 지우면 원문으로 돌아간다. 원문이 삭제되거나 보관기간이 끝나면 복원한 척하지 않고 파생 요약도 해당 삭제 범위에 맞춰 갱신·폐기한다. 대화 요약을 자동 장기 선호로 승격하지 않는다. 백그라운드 요약이 필요하면 같은 semantic LLM의 제한된 예산을 쓰며 새 입력을 막지 않도록 관리한다.

아직 정할 제품 정책은 raw audio·screen 저장 기본값, Conversation·evidence 보관기간, 사용자 동의에 따른 기억 승격 범위, 백업·외부 provider 삭제 범위다. 이는 보관 기술만으로 결정할 수 없다.
