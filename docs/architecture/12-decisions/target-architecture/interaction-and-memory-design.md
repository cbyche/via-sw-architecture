> 상태: **사용자 피드백 반영 / 구조 제안은 합의 전 / 구현·측정 없음**

## 1. 합의한 행동과 아직 제안인 구조

| 항목 | 상태 |

## 2. S2S를 위한 맥락과 제한된 직접 응답

Interaction Manager에 제어 기능을 넣는 방향은 타당하지만 “작은 코드 모듈이 모든 문장의 의미를 정확히 분류한다”는 가정을 두지 않는다. 말할 차례·중단·revision·허용 범위 검사는 host, 맥락 안의 발화 의미 판단은 모델이 담당한다. 추가 분류 모델은 두지 않는다.

현재 검토할 주 제안은 **맥락을 가진 S2S + 제한된 응답 범위 + 필요한 요청만 Core 해석**이다. 정확성을 이미 확보한 경로가 아니라 실현 가능성과 범위를 닫아야 하는 제안이다.

| 주체 | 제안 책임 |
| --- | --- |
| Context Manager | 최근 실제 대화, 확정 대상·topic, 관련 Task·대기 질문, 적용 가능한 선호를 작은 view로 구성; 출처·revision·누락 표시 |
| Request Controller | 사용할 view·응답 범위·정책 revision 관리; Request identity와 최종 direct admission 유지 |
| Interaction Manager 내부 Interaction Guard 제안 | S2S에 유효 view 연결, 입력·화면·출력 세대 변경 감지, 알려진 배제 조건이면 Core 인계; 의미 확정 권한 없음 |
| 같은 S2S 모델 | 같은 응답 호출에서 `DIRECT_PROPOSAL` 또는 `NEEDS_CORE` 제안; scope 안의 응답을 생성 |
| Response Manager | 허용한 응답의 상세/음성 view·publication·차례 관리; IM이 실제 재생 |

`Interaction Guard`는 아직 확정 Component나 구현이 아니며 전체 구조 그림에 별도 box로 추가하지 않는다. 기존 Timeline & Buffer·Turn-Taking Control과의 내부 분리는 계약을 확정하며 정리한다. 매 요청 Controller의 짧은 host 검증은 유지할 수 있다. Controller·Interpreter는 논리 Component이지 각각 원격 서비스가 아니므로 상자 수를 모델 호출 수나 네트워크 왕복 수로 간주하지 않는다. 줄이려는 주 비용은 추가 semantic inference와 큰 Context 구성·조회다.

예를 들어 VIA가 이미 “TCP와 UDP의 차이를 설명 중”이라는 맥락을 갖고 실제 앞 답변이 제공된 상태에서 사용자가 “두 번째 걸 더 쉽게 설명해줘”라고 한다. S2S가 UDP 설명을 제안하고 현재 view·입력·출력 revision이 유효하면 semantic LLM의 같은 해석 반복을 생략하는 경로를 검토한다. 반대로 “그 설명으로 파일 만들어줘”, “화면의 이 오류는?”, “아까 업무 취소해”는 Core로 보낸다. 최신 정보·개인 자료 조회·업무 실행은 직접 범위를 벗어난다.

이 후속 설명 경로는 현재 본문 §8의 좁은 self-contained 질문 범위를 넓히는 **검토 제안**이다. 초기 권고는 Core가 확인한 topic의 후속 대화부터 이 경로를 허용하고, 새로운 자유 질문은 semantic 해석으로 연결하는 것이다. 첫 질문까지 S2S가 스스로 식별하도록 넓히는 것은 별도 검토 대상이며, 이 권고도 사용자 합의 전이다. 작업 관련 화면이 있다는 사실만으로 항상 Core로 보내면 fast path가 거의 없어지고, 화면 존재를 무시하면 지칭 누락이 생길 수 있다는 trade-off도 남는다.

방어 조건은 다음과 같다.

- view는 전체 대화의 완전한 대체물이 아니다. 미해결 대상·대기 질문·정정·Context gap·오래된 revision이면 Core 확인 경로를 사용한다.
- S2S의 높은 confidence나 “직접 답변 가능” 자기 선언만으로 허용하지 않는다. Host는 revision·scope·출력 소유권 등을 검사하지만 숨은 의미 의존성을 전부 검출할 수는 없다.
- direct admission 기록 뒤에도 barge-in·정정·권한 철회로 release를 무효화한다. 알려진 변경이 늦게 도착하는 비용과 위험은 남는다.
- Core로 보낼 입력·당시 evidence를 보존하고 speculative 음성을 사용자에게 먼저 재생하지 않는다.
- 모델이 route 제안·text/audio 결합·host 보류 계약을 제공하지 않으면 이를 가진 척하지 않는다. 동일 semantic LLM 확인 경로를 사용하거나 직접 범위를 줄인다.
- 매 요청이 결국 Core로 넘어가거나 입력 view·S2S 판정 비용이 이득을 없애면 구조를 단순화한다. 비동기 사후 검사만으로 이미 발화한 오류를 예방했다고 주장하지 않는다.

## 3. 모델 요구를 누가 확인하는가

사용자가 지금 모델 API나 구현 방법을 해결해야 하는 것은 아니다. Architecture 작업에서는 에이전트가 필요한 연동 계약, host에서 해결하는 부분, 모델 의존 부분, 미지원 시 동작을 정리한다. 특정 dependency가 정해지면 공식 문서·공개 예제로 지원 여부를 조사하고, 실행 환경이 제공되는 범위에서 실제 입출력을 확인한다. 문서 확인과 실제 실행 관측은 구분한다.

| 요구 | VIA가 설계할 부분 | 실제 dependency 확인이 필요한 부분 |
| --- | --- | --- |
| 생성 중 음성 보류·즉시 중단 | 자체 playback buffer·release·epoch·로컬 stop | audio stream 획득, 생성 취소·session 제어 지원 |
| 말과 당시 화면 연결 | OS capture·timestamp·timeline·gap 처리 | transcript와 acoustic 시점 대응을 얻을 수 있는지 |
| 상세 Text와 Voice 요약 | 공통 사실·채널별 view·실제 전달 기록 | 지정한 Voice 요약의 의미 보존, text/audio 대응 |
| 조건부 S2S 직접 응답 | versioned view·scope·admission·Core fallback | Context 주입과 route/응답 계약의 실제 지원·판정 품질 |
| 이미지 화면의 이해 | 화면 근거와 UI 정보의 선택·제공 계약 | 공유 semantic LLM이 필요한 시각 입력을 처리하는지 |

사용자 입력이 필요한 것은 이미 고정된 모델·PC·local/cloud 제약이 있는 경우 그 조건, 그리고 지원 불가 시 허용할 제품 동작의 변경이다. 고정 조건이 없다면 현 단계에 임의 모델을 선정하거나 실험용 자격증명을 요구하지 않는다. 실측에는 향후 승인된 실행 환경·모델 접근이 필요하며 지금 완료했다고 주장하지 않는다.

## 4. 복합 요청의 실패는 두 수준으로 나눈다

기준은 문장 길이나 “그리고”의 개수가 아니라 **사용자의 독립 목표인지, 한 목표를 수행하는 내부 계획인지**다.

| 상황 | VIA | Downstream Agent |
| --- | --- | --- |
| “이 문단 요약하고 오후 일정 알려줘” | 명시된 독립 요청과 각각의 결과·실패 관리; 한쪽 실패가 다른 쪽을 막지 않음 | Agent 위임이 필요한 항목이 있을 때만 해당 업무 수행 |
| “자료를 요약한 뒤 그 요약을 메일로 보내줘” | source·요약 version·수신자·의존 관계 보존; 요약 실패 시 발송 보류 | 실제 발송과 그 업무의 재시도·도구 처리 |
| “경쟁사를 조사해서 보고서를 만들어줘” | 하나의 목표·제약·완료 조건으로 위임하고 부분/최종 상태 연결 | 조사 순서, 검색 도구, source 실패 대처, 보고서 작성과 저장 |
| “보고서와 일정 등록을 각각 해줘” 중 보고서 실패 | 일정과 무관하면 일정 결과 유지; 전체 성공이라고 보고하지 않음 | 각 업무 내부의 실패 원인·복구 가능성·실제 완료 범위 제공 |

한 Agent가 종속된 요청 묶음을 온전히 수행할 수 있으면 사용자 관계를 그대로 전달하고 그 Agent가 실행 의존성을 관리할 수 있다. VIA는 계약된 결과·경계만 추적하며 내부 단계별 command를 중복 발행하지 않는다. 여러 Agent 또는 VIA 직접 처리와 Agent를 잇는 의존은 Controller의 Request Graph가 관리한다. 선택 단위·묶음 경계의 세부는 제안이다.

Agent가 실패했다고 VIA가 내부 plan을 새로 짜거나 전체 업무를 무조건 재실행하지 않는다. 실패·완료 범위·artifact version·접수 상태를 확인하고 사용자에게 다음 선택을 연결한다. 확인되지 않은 외부 상태는 확인 불가이며, 내부 retry와 외부 재위임을 동시에 시도해 중복 실행하지 않는다. 사용자 명시 all-or-nothing 요구가 있을 때는 실행 전 지원 여부를 확인하고, 여러 Agent의 Action을 VIA가 원자적으로 rollback할 수 있다고 약속하지 않는다.

## 5. 기억은 의미 수명과 저장 방식을 분리한다

단기·중기·장기는 “언제 어떤 의미로 재사용할 것인가”이고 RAM·파일·DB는 “어디에 어떤 내구성으로 저장할 것인가”다. 중기 기억도 재시작을 견디려면 디스크에 저장할 수 있다. 파일 DB 자체를 장기 기억과 동일시하지 않는다.

| 계층 제안 | 예시 | 소유권·저장·수명 |
| --- | --- | --- |
| 단기 작업 Context | 현재 발화, 당시 화면, 선택, 이번 해석에 필요한 원문 | IM evidence buffer·Controller workspace·Context cache; RAM 중심, 요청이 쓰는 evidence만 정책 범위에서 pin·필요 시 내구화 |
| 중기 Conversation·Task 작업집합 | 최근 대화 요약, 확정 대상, 미해결 질문, 진행 업무와 결과 참조 | Context Manager가 원래 owner 기록에서 파생 view 생성; 필요 시 지속 저장하고 source revision으로 재구성 |
| 장기 User Memory | 사용자가 허용한 답변 선호·지속 사실 | Context Manager owner, State Store 내구 기록; 확인·변경·삭제 가능; 현재 지시가 우선 |
| 원본 업무·응답·복구 기록 | Task/Execution, command, 질문, 결과·전달 기록 | Controller·Task·Gateway·Response 각각의 권위; 기억 요약 계층과 별개, cache 만료로 삭제하지 않음 |

저장 주안은 local embedded DB로 구조화 상태·참조·삭제 revision을 관리하고, 허용된 큰 evidence는 별도 파일로 두되 수명·참조를 함께 관리하는 것이다. 특정 DB 제품은 아직 선택하지 않는다. DB와 파일 사이 crash로 생기는 orphan·누락의 복구 계약도 필요하다. 추가 embedding 모델이나 vector DB를 자동 도입하지 않는다.

요약에는 출처·version·범위·누락을 남긴다. 정확한 대상 ID·수치·제약·권한·업무 상태는 typed record와 필요한 원문을 유지하고, 요약이 부정·조건·정정을 지우면 원문으로 돌아간다. 원문이 삭제되거나 보관기간이 끝나면 복원한 척하지 않고 파생 요약도 해당 삭제 범위에 맞춰 갱신·폐기한다. 대화 요약을 자동 장기 선호로 승격하지 않는다. 백그라운드 요약이 필요하면 같은 semantic LLM의 제한된 예산을 쓰며 새 입력을 막지 않도록 관리한다.

아직 정할 제품 정책은 raw audio·screen 저장 기본값, Conversation·evidence 보관기간, 사용자 동의에 따른 기억 승격 범위, 백업·외부 provider 삭제 범위다. 이는 보관 기술만으로 결정할 수 없다.
