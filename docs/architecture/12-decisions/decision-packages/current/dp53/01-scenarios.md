# DP53 상황과 완료 조건

[진입점](README.md) / [실행 설계](02-execution-design.md) / [구조 선택](03-structural-choices.md)

## 1. 문제와 가정

사용자는 문서를 읽고 해석하는 중에도 요청을 바꾼다. 이전 판본의 읽기, 모델 호출, Agent 전송과 음성 생성이 서로 다른 단계에 있고, 이전 결과가 새 결과보다 늦게 도착할 수 있다. 업무 ID를 정확히 알아도 revision 검사와 상태 변경 사이, 검사와 실제 송신 사이에 경합이 남는다.

| 구분 | 이번 탐색 조건 |
| --- | --- |
| 고정 | 같은 업무 T를 수정한다는 연결은 정확하다. 무관한 업무 U는 계속 진행한다. 음성 입력은 정정 처리와 분리해 계속 수신한다. |
| 자료 가정 | 지정 문서 D의 판본 D@17을 읽을 수 있다. 읽기 범위와 누락 여부가 결과에 포함된다. 파일명만으로 판본 동일성을 인정하지 않는다. |
| 의미 의존성 | 해석기는 입력/기준 snapshot을 받아 변경 제안을 반환한다. 기준 판본, 입력 식별자와 아직 해소하지 못한 조건을 반환하며 직접 상태를 변경하지 않는다. |
| 실행 가정 | Rust async 형태로 설명하되 제품 런타임 확정은 아니다. 개발 호스트는 macOS, Windows I/O와 음성 API는 대상 환경의 제약 조사다. |
| 확인 필요 | 모델 호출의 실제 중단과 자원 반환, Agent의 수정/취소/조회/중복 방지/명령 순서 지원, 최대 동시 부하 |
| 책임 경계 | 발표자료 생성과 새로운 발표 구성 계획은 Downstream Agent 업무다. 기존 결론의 범위가 정해진 발췌/설명과 구별한다. |

"만들지는 말고 먼저 구성만 설명"은 파일 생성 권한 철회와 현재 결과 요구 변경을 포함한다. Agent가 preview-only 수정 계약을 지원하는지는 확인해야 한다. VIA가 범용 발표 계획 엔진으로 바뀌었다고 가정하지 않는다.

## 2. 대표 사건 원장

숫자는 사건 순서이며 시간/성능 수치가 아니다. 각 분기에서 같은 입력과 외부 상태를 두 구조에 적용한다.

| 순서 | 입력 또는 외부 사건 | 내부 처리 | 사용자가 확인할 결과 |
| --- | --- | --- | --- |
| 1 | "이 문서로 발표자료 만들어줘" | 확정 입력에서 r1 채택. D@17 읽기 J1, 해석 J2와 준비 실행 시작 | 확인된 처리 방향. Agent 접수 전에는 접수했다고 하지 않음 |
| 2 | "아, 전체 말고 결론만. 다섯 장으로" 시작 | 현재 음성 중단, 같은 대화의 미전송 admission hold. 입력 자체는 계속 수신 | 구판 음성 중단. 이 시점만으로 Agent 업무 취소 완료를 주장하지 않음 |
| 3 | 위 입력 해석 완료 | r2 채택. 구판 확정 권한 회수, 필요 연산 준비와 이전 실행 수거 | 결론만/다섯 장 변경 반영 |
| 4 | J2의 r1 결과가 늦게 반환 | usage와 종료를 수거하되 r1 위임 제안은 채택 거부 | 구판 요청이 현재 상태를 덮지 않음 |
| 5 | r2 명령 C2가 전송 대기 또는 Dispatching | 대기 중이면 철회 가능. Dispatching이면 접수/미전송/불명을 구분 | 실제 확인된 상태 |
| 6 | "잠깐, 만들지는 말고 먼저 구성만 설명해줘" | r3 채택. C2 대기 철회 또는 외부 실행 X2 수정/취소 조정 | 현재 생성 금지 요구와 이전 실행의 남은 상태 |
| 7 | X2가 완료/취소 접수/취소 완료/불명 중 하나를 반환 | X2 실제 상태 기록. r3 완료로 덮어쓰지 않음 | 이미 만들어진 결과가 있으면 사실과 현재 요청 상태를 함께 안내 |
| 8 | 구판 음성 생성 완료 후 재생 시도 | response 판본과 출력 epoch가 맞지 않으면 거부 | 구판 "만들겠습니다"가 다시 재생되지 않음 |

성공은 최신 요구의 처리를 이어가고 구판 결과가 새 실행/응답/현재 요청을 덮지 않는 것이다. 외부 취소 불가 또는 불명 안내는 필요한 실패 처리이며, 원래 목표를 성공 완료한 것과 같지 않다.

## 3. 변형과 기대 상태

| ID | 같은 조건으로 검토할 사건 | 필요한 처리와 관측 |
| --- | --- | --- |
| S01 | 정정 없이 정상 완료 | 하나의 최신 판본으로 결과 채택, 접수/완료와 표시/청취 상태 분리 |
| S02 | 한 발화에서 해석 시작 후 "아니, 결론만" | provisional 입력 판본 갱신, 초기 해석 무효화. 발화 종료/확정 전 외부 실행 허가 없음. 새 입력을 들어보기도 전에 정정을 예측했다고 하지 않음 |
| S03 | 별도 후속 발화가 이전 요청 변경 | 새로운 입력 이력과 보완 관계 보존. 업무 T의 실행만 교체하고 U의 연산을 취소하지 않음 |
| S04 | sender가 자원 대기 중일 때 변경 | 명령은 Pending 유지. 정정 commit 뒤 sender의 claim 거절, 실제 송신 없음 |
| S05 | Dispatching 확정 뒤 첫 write 전/후 변경 | 가능하면 중단하되 미전송 증명 없으면 Unknown 가능성 유지. 로컬 transaction을 원격 접수와 동일시하지 않음 |
| S06 | Agent 접수 후 변경 | 실행 ID와 제어 command ID를 연결. 수정 지원 시 수정, 취소 접수와 적용 완료 구분. 모호한 상태에서 새 생성 업무 중복 시작 금지 |
| S07 | 모델 호출 취소 후 정상 결과 반환 | callback과 비용 수거, 자원 실제 반환 후 슬롯 해제, 구판 채택 차단 |
| S08 | 음성 생성 완료/재생 전 변경 | 대기 PCM 거부/해제. 이미 장치에 제출한 범위는 stop/flush와 receipt로 별도 기록 |
| S09 | 같은 판본 재시도 중 이전 attempt 반환 | revision 같아도 attempt가 다르면 과거 실행은 채택 불가 |
| S10 | 짧은 간격의 반복 정정, 취소 불가능 연산 누적 | 입력 기록 보존. 모델/읽기 시작은 슬롯으로 제한. 현재 실행 예약은 최신 필요 상태로 병합, 이전 원문 삭제 금지 |
| S11 | 정정 commit 직후 프로세스 종료 | 저장된 current version/실행 필요/command 상태 복원. handle은 복원하지 않음. 외부 Dispatching을 무조건 재전송하지 않음 |
| S12 | 같은 파일명에서 자료 판본 또는 접근 허용 변경 | 내용 cache/진행 중 연산 동일성 재검사, 권한 철회 시 새 소비자 연결 금지 |
| S13 | 이전 Agent 완료와 취소 완료 응답 역순 | 실행별 source 순서 또는 조회로 정리. 생성된 artifact를 구판이라는 이유만으로 숨기지 않음 |
| S14 | 재생 중 무관한 업무 U의 입력/결과 | 재생 중단은 현재 출력에 적용. T/U의 내용 판본과 실행 취소를 일괄 변경하지 않음 |

## 4. 보장 경계

물리적 발화 시작, 입력 감지, admission hold 적용은 같은 시각이 아니다. hold 전에 이미 Dispatching을 확정한 경우 외부 제어 경로로 처리한다. "사용자가 말한 순간 모든 외부 실행이 멈춘다"는 보장은 만들지 않는다.

같은 대화의 해석 전 미전송 보류는 [참조 제어 계약](../../../target-architecture/control-and-lifecycle.md)의 동작을 이번 공통 조건으로 사용한다. 해석 후 대상이 T로 확정되면 U는 재검증하여 해제한다. U의 이미 진행 중 업무, 다른 대화의 실행과 입력 수신은 중단하지 않는다. 공유 자원 경합으로 U가 기다릴 가능성까지 없다고 주장하지 않는다.

입력 포화에서는 raw audio 보관을 무한 확장하지 않는다. 근거 계층의 제한과 gap 표시를 사용하고 유실된 발화를 성공 수신으로 처리하지 않는다. 제어 상태 반영이 지연/실패하면 미전송 허가를 닫고 오류를 표시하며 기존 Agent 관측과 local stop을 유지한다.
