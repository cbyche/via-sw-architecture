# DP52 구현 수준 설계 탐색

2026-10-23 / 설계 제안 / 실제 구현과 측정 없음

## 1. 대표 상황에서 시작한다

사용자가 하나의 음성 연결에서 출장 일정과 발표자료 작성을 번갈아 요청한다. 사용자는 업무 창이나 Agent thread를 선택하지 않는다. 같은 Agent가 별도 실행 E1과 E2를 제공한다고 가정하며, 다른 Agent인 경우도 같은 식별 계약을 사용한다. API가 독립 실행을 지원하는지는 아직 확인하지 않았다.

| 순서 | 사용자 입력 또는 외부 사건 | VIA 내부 처리 | 사용자 결과 |
| --- | --- | --- | --- |
| 1 | U1: 출장 일정 정리해줘 | U1 보존, 새 업무 T1 생성, 실행 E1 연결 | 출장 업무 접수 |
| 2 | U2: 그리고 이 보고서로 발표자료 만들어줘 | U2 보존, 별도 업무 T2 생성, 실행 E2 연결 | 발표자료 업무 접수 |
| 3 | E1: 수요일 오전과 오후 중 언제 출발할까요? | T1/E1에 질문 Q1 등록 | 질문은 아직 음성 미전달일 수 있음 |
| 4 | U3: 출장은 수요일 출발로 바꿔줘 | T1의 수정 요청으로 연결 | 수정 접수와 실제 변경 완료 구분 |
| 5 | E2 진행 상황 도착 | T2/E2 상태 갱신 | 확인된 진행 상황 유지 |
| 6 | U4: 발표자료는 어디까지 됐어? | T2에 연결, 현재 상태 또는 새 조회 사용 | 발표자료 상태 응답 |
| 7 | 여전히 유효한 Q1이 음성으로 전달됨 | Q1의 실제 전달 범위 기록 | 출장 시간 질문을 들음 |
| 8 | U5: 오후로 해줘 | 당시 전달 근거로 T1/E1/Q1 연결, 유효성 재검사, 답변 적용 | 출장 질문 답변 접수 |
| 9 | E2 결과와 E1 답변 수신 확인이 역순 도착 | 실행별로 상태와 결과 연결 | 업무가 섞이지 않음 |

Q1이 4번 수정 때문에 철회되는 경우에는 7번 전달을 허용하지 않는다. Q1의 내용이 달라지면 새 question revision을 사용한다. 질문의 정확한 만료와 재사용 조건은 Agent capability 확인 사항이다. 정상 표는 Q1이 계속 유효한 분기다.

소프트웨어의 재생 범위 관측은 사용자의 인지 여부를 보장하지 않는다. 여기서 실제 전달은 출력 측이 제공하는 관측 사실과 불명 상태를 뜻한다. 합성 완료, 재생 큐 삽입, 화면 표시와 음성 출력은 서로 다른 상태다.

## 2. 모델이 맞혀도 남는 실패

1. U5를 해석하는 동안 Q1이 철회되어도 예전 질문에 답변을 보낼 수 있다.
2. T1의 실행이 E1에서 E3으로 바뀌면 `current_run` 조회만으로 Q1 답변을 E3에 잘못 보낼 수 있다.
3. 연결 저장과 업무 적용 사이에 종료되면 입력이 사라질 수 있다.
4. 업무 적용 후 확인이 유실되면 같은 입력을 다시 적용할 수 있다.
5. 사용자 답변을 기다리는 함수가 공통 입력 루프를 점유하면 다른 업무도 멈춘다.
6. 가장 최근 생성된 질문과 마지막으로 제시된 질문을 같게 취급하면 짧은 답변의 근거가 바뀐다.

모델은 입력 및 주어진 상태에 대한 연결 제안을 반환한다. 모델이 저장소를 직접 변경하거나 실행을 시작하지 않는다. 현재성 검사, 소유권과 재시도는 VIA 코드 책임이다. 모델의 지능이나 프롬프트 차이로 아래 구조의 우열을 만들지 않는다.

## 3. 실제 객체와 상태 소유권

아래 내부 모듈명은 이번 구현 제안이다. 기존 Reference Architecture의 Component를 새로 선택하거나 개명한 것이 아니다.

| 소유 책임 | 내부 데이터 | 생성과 변경 주체 | 수명 |
| --- | --- | --- | --- |
| Request Controller의 입력 보관 모듈 | InputRecord, 입력 revision, 해석 attempt, 입력별 적용 상태 | 입력 수신과 판단 반환 처리 | 연결 전후 원본을 유지, 임시 해석 자료는 호출 종료 후 해제 |
| Request Controller의 연결 처리 모듈 | AssociationSnapshot, ReadSet, 선택한 plan, 입력과 업무 연결 | 판단 시작과 검증 및 확정 절차 | snapshot은 호출 수명, 채택 기록은 복구 가능한 기록 |
| Task Manager의 업무 상태 모듈 | WorkSession, 업무별 대화 참조, 실행과 질문 | 업무 전이 함수 또는 업무별 실행체 | Voice 연결보다 길며 완료 후 메모리 상주를 해제할 수 있음 |
| Agent Gateway | 외부 식별 대응, inbox, 전송 시도와 결과 | provider adapter와 송수신 worker | 실행 종료 뒤 늦은 이벤트 식별 기간까지 유지 |
| Response Manager | Presentation, 채널별 전달 사실과 범위 | 출력 측 관측 이벤트 | 질문의 생성 상태와 독립적으로 유지 |
| State Store | 원자 저장, 유일 제약, outbox, receipt | 의미 소유자의 검증된 변경 요청 | 프로세스 재시작을 넘는 복구 기준 |

업무별 세션은 TaskId로 식별하는 VIA 상태 묶음이다. Agent thread, 모델 session, OS thread와 동일하지 않다. 같은 Task에 여러 Execution을 연결할 수 있고, 같은 Agent가 여러 Task의 Execution을 가질 수 있다. 새 음성 연결은 기존 Conversation을 참조할 뿐 업무나 실행을 새로 만들지 않는다.

### 미정 입력과 대화 기록

미정 입력은 Conversation의 입력 보관함에 남는다. 마지막 활성 업무에 먼저 삽입하지 않는다. 연결되면 Task의 대화 이력에 입력 참조를 추가하며 원문을 Task마다 복사하지 않는다. 한 입력의 복수 업무 지시는 동일 입력을 참조하는 복수 operation으로 표현한다. 직접 응답은 Task 없이도 입력과 응답 기록을 유지한다.

`WaitingForClarification`은 해당 입력의 대기다. 호출 stack, DB lock이나 모델 실행 자원을 잡은 채 사용자 답을 기다리지 않는다. 앞선 U1의 연결이 아직 미정이면 후속 입력이 `EarlierInput(U1)`을 참조할 수 있다. 의존 관계를 저장하고 반환하며, U1 연결이 끝나면 해당 입력만 다시 준비한다. timeout이면 입력을 보류하고 알리며 조용히 삭제하지 않는다. 보관 기간과 원본 삭제 정책은 별도 제품 binding이 필요하다.

### 실행과 질문 식별

외부 대응은 `(provider, account, remote_session, remote_run) → ExecutionId → TaskId`를 유지한다. 명령 전송 전에 VIA ExecutionId와 idempotency key를 예약한다. 외부 ID 반환 전 이벤트가 올 수 있으므로 client correlation 지원을 확인한다. 연결할 수 없는 이벤트는 격리하고 최근 업무로 추측 적용하지 않는다.

질문은 `(ExecutionId, QuestionId, question_revision)`으로 식별한다. task의 현재 실행을 조회해 과거 질문 답변의 실행을 바꾸지 않는다. Agent가 독립 실행 식별을 지원하지 않으면 별도 provider session을 사용할 수 있는지 확인한다. 그것도 불가능하면 해당 Agent의 admission 직렬화 또는 다른 지원 경로가 필요하다. 이 경우 기능 및 대기 비용을 공개한다.

## 4. 판단 중 변하는 상태

공통 입력 경로는 `입력 보존 → snapshot 준비 → 모델 await → 현재성 검증 → 적용 확정`이다. snapshot과 검증용 ticket은 함께 생성한다. 모델에는 읽기 전용 view를 주고, VIA는 별도 ReadSet을 유지한다. 모델이 ReadSet을 생성하거나 검증하게 하지 않는다.

| 변경 | 필요한 처리 |
| --- | --- |
| 무관한 T2 진행률 변경 | T1 답변 재판단 사유가 아님 |
| T1 질문 철회 또는 내용 변경 | Q1 답변 적용 거절 |
| T1 실행 교체 | 정확한 실행과 질문의 현재 유효성 재검사 |
| 입력 전사 revision 변경 | 확정 전 이전 attempt 결과 폐기 |
| 앞선 입력의 새 업무 생성 | 관련 candidate directory와 의존 관계 재검증 |
| 발화 뒤 다른 질문 전달 | 발화 당시 전달 이력의 의미를 최신 질문으로 치환하지 않음 |

Task의 `link_revision`은 연결 의미에 영향을 주는 실행, 질문, 업무 식별 상태가 바뀔 때 올린다. 진행률은 별도 판본이다. 후보 검색의 누락 검증에는 조회한 행의 revision뿐 아니라 조회 범위의 membership revision도 필요하다. 그렇지 않으면 판단 중 새 후보가 추가되는 경우를 놓친다. 지나치게 넓은 전역 revision은 무관한 변경으로 재시도를 늘리므로 조회 범위를 기록한다. 두 구현에 같은 검증 범위를 적용한다.

질문 답변은 두 시점을 검사한다. `ExposureCut`은 사용자 발화 당시 확인 가능한 제시 범위이고, 현재 질문 revision은 지금 답변을 적용할 수 있는 조건이다. 이력이 늦게 도착하면 출력 측 순서 번호와 watermark로 빠진 범위를 확인한다. 완전성을 확인하지 못하면 해당 답변을 보류하거나 명시 확인으로 보낸다. `Displayed`만으로 음성 전달을 확정하지 않는다. 화면 질문에 대한 명시적 UI 답변은 별도 interaction ID를 제공할 수 있다.

확정 전 입력 revision 변경은 재판단 대상이다. 확정된 plan 또는 예약된 ticket의 payload는 바꾸지 않는다. 채택 뒤 원 InputRecord를 수정하지 않고 새 InputId와 원 입력을 가리키는 supersedes 참조를 생성한다. 이후 정정은 선행 적용 여부를 확인하는 별도 요청으로 연결한다. 변경된 payload를 같은 idempotency key로 재전송하지 않는다. 정정 시점의 미전송 보류와 외부 취소는 DP53에 전달할 계약이며 여기서 재설계하지 않는다.

## 5. 코드를 따라가며 드러난 확정 방식

### 5.1 연결과 업무 변경을 한 저장 트랜잭션으로 확정

Request Controller의 연결 전이와 Task Manager의 업무 전이를 같은 Unit of Work에서 호출한다. 각 모듈은 자신의 의미 규칙을 가진다. 임의 테이블 수정 권한을 모든 호출자에게 열지 않는다.

한 transaction 안에서 입력 revision 및 attempt 검증, 후보와 질문 현재성 검사, Task 생성 또는 연결, 질문 답변 적용, 대화 참조, 적용 receipt와 외부 명령 outbox를 저장한다. 실패하면 전부 rollback한다. commit이 로컬 적용의 선형화 지점이다.

모델과 Agent 네트워크 await는 transaction 밖이다. 사용자 답변 대기는 열린 질문 레코드로 표현한다. 공통 DB writer를 쓰더라도 외부 업무가 끝날 때까지 기다리지 않으므로 출장 대기가 발표자료 조회를 막지 않는다. Agent 이벤트도 같은 업무 전이 API를 통과한다.

SQLite를 사용하면 짧은 쓰기는 직렬화된다. 전용 DB thread에 요청을 넘기고 async 호출자가 결과를 await하는 구현이 가능하다. WAL을 켜거나 connection을 늘려 여러 writer의 동시 쓰기가 가능하다고 주장하지 않는다. DB 지연이 커지면 공통 처리 경로가 영향을 받는 비용은 남는다.

### 5.2 업무별 상태 소유자에게 영속 ticket을 넘겨 적용 확인

Task Manager 내부 업무별 async 실행체가 WorkSession과 해당 업무 이벤트 순서를 소유하게 만들면, 공통 입력 처리기는 업무 상태를 직접 변경할 수 없다. 다음 전달 프로토콜이 필요해진다.

`입력 plan과 대상 예약 → 영속 ApplyTicket → 업무 소유자 검증 → 업무 상태와 ApplyReceipt commit → 입력 측 receipt 반영`

업무 측 receipt commit이 로컬 적용의 선형화 지점이다. 공통 입력 상태는 `Reserved → Applied`로 후속 수렴한다. `Reserved`의 응답이 없다고 다른 Task로 재연결하면 안 된다. 이미 적용되었을 수 있기 때문이다. 같은 LinkId를 조회하거나 재전달하며 업무 측은 저장된 결과를 반환한다. 명시적인 미적용 거절을 확인한 operation만 재판단할 수 있다.

기본안에서는 Task 소유자가 업무 상태와 라우팅용 summary를 같은 저장 transaction에 기록한다. 공통 snapshot은 그 저장된 summary를 읽는다. 비동기 cache만 보고 후보를 고르는 방식을 기본안에 몰래 추가하지 않는다. 예약 시 directory ReadSet을 검사하고 실제 적용 시 업무 소유자가 현재 질문과 실행을 다시 검사한다.

실행체는 업무마다 OS thread를 만드는 방식이 아니다. 같은 process의 async task로 시작할 수 있다. DB commit을 기다리는 동안 해당 업무의 전이는 직렬이지만 다른 업무 실행체는 진행할 수 있다. 같은 DB를 사용하면 쓰기 직렬화는 여전히 남는다. 재기동 또는 메모리 해제 후 재생성에는 owner epoch를 사용해 예전 실행체의 저장을 거절한다.

이 구조의 이익 후보는 업무별 상태의 독점 소유, 독립적인 활성화 및 해제, 특정 업무 처리 지연의 분리다. 비용은 ticket 및 receipt, 중간 상태 조회, 전송 재시도와 복합 입력의 부분 적용이다. 단순히 actor라고 부르는 것으로 정확성, 성능 또는 장애 격리를 주장하지 않는다.

### 5.3 실제 차이와 독립 선택

두 번째 구현에서도 입력과 업무 상태를 같은 transaction으로 직접 확정하면 첫 번째 구현에 가까워진다. 채널 사용 자체는 주요 구조 차이가 아니다. 저장 경계, 쓰기 권한과 복구 기준이 바뀌어야 한다.

SQLite 대 다른 저장 엔진, mutex 대 channel, 모델 호출 병렬 수, 후보 점수 임계값, 질문 선택 프롬프트는 각각 별도 선택이다. 이를 한꺼번에 바꾸어 이번 확정 방식의 손익으로 합산하지 않는다. 대화 전체를 순차 처리하며 Agent 종료를 기다리는 구현은 공통 요구를 깨므로 강한 비교안으로 채택하지 않았다.

## 6. 큐, 대기와 자원 해제

| 항목 | 제안 계약 |
| --- | --- |
| 오디오 callback | DB 및 업무 큐 send를 기다리지 않음. DP51의 입력 경로에서 이미 확보한 입력 참조를 비실시간 수신 경로가 보존 |
| 미정 입력 | 영속 보관 후 해석 작업 수용. 수용량 부족을 조용한 입력 삭제로 처리하지 않음 |
| 해석 queue | InputId와 attempt를 전달. in-flight 수와 payload byte 상한을 별도로 제한 |
| 업무 mailbox | ticket와 이벤트 참조만 전달. 원음과 전체 대화 사본을 넣지 않음 |
| Agent progress | 독립 완전 snapshot이면 최신 값으로 합칠 수 있음. 순차 delta이면 누락 및 gap 처리 없이 합치지 않음 |
| 질문, 완료, 답변 | 임의 drop 금지. 영속 inbox와 수신 확인 또는 재조회 지원 필요 |
| 포화 | 가득 찬 업무에 대한 ticket만 대기. 공통 dispatcher가 해당 send를 await하며 다른 업무 전송을 막지 않음 |
| 모델 자원 | 실제 호출 때 확보, 반환 또는 실제 취소 종료 시 해제. 사용자 답변 대기 중 KV 유지와 가중치 복제 강제 없음 |
| 업무 메모리 | 처리 중 message와 영속 미확인 변경이 없고 checkpoint 완료 시 해제 가능. wake 등록과 owner epoch 필요 |
| 종료 | 신규 admission 종료, 수신 중인 항목 보존, 적용 또는 영속 재시도 상태 확인 후 handle 해제 |

`max_pending_inputs`, `max_inflight_resolutions`, `max_task_mailbox_items`, `max_payload_bytes`, 영속 backlog byte 예산과 retry deadline은 제품 Resource Profile에 binding해야 한다. 값은 이번 문서에서 만들지 않는다. 무제한 queue나 무제한 spawn은 어느 기본안에서도 허용하지 않는다. DB 및 저장 장치 포화 시 원본 보존을 보장할 수 없으면 그 범위를 사용자에게 알리고 새 처리 수용을 제한한다.

입력 텍스트와 불변 snapshot은 process 안에서 Arc로 공유할 수 있고, 큰 evidence는 소유자 참조로 전달한다. 직렬화 및 model request 생성 시 필요한 복사 비용은 남는다. process 분리를 별도로 선택하면 Arc가 IPC 공유를 제공한다고 해석하지 않는다.

## 7. 손익과 현재 판단

| 관점 | 한 transaction 확정 | 업무 소유자 적용 확인 |
| --- | --- | --- |
| 지연 | 짧은 commit 뒤 연결 상태 확정 | 예약, queue, 적용 receipt와 후속 반영 경로 추가 |
| 겹침 | 외부 대기는 공유 writer를 점유하지 않음. DB 정체는 공통 영향 | 업무별 handler 정체 분리 가능. 공통 DB와 runtime 정체는 남음 |
| 메모리 | 상태와 호출 snapshot 중심 | mailbox, ticket, receipt 및 반영 대기 상태 추가 |
| 변경 | 교차 불변식을 한 transaction에서 검토하기 쉬움 | 업무 전이를 캡슐화하나 전달 및 복구 계약 변경 비용 추가 |
| 신뢰성 | 입력과 업무 적용 사이 불일치 구간 없음 | 중간 상태를 receipt로 복원해야 함 |
| 모델 비용 | 같은 의미 판단이면 기본 비용 같음 | stale 재판단이 늘어날 때 추가 비용 가능, 자동 절감 없음 |
| 연결 정확성 | 공통 검증을 올바르게 구현하면 같은 결과 | 공통 검증을 올바르게 구현하면 같은 결과 |

QA01은 NORMAL의 실제 첫 실질 음성, WAIT는 별도 보고이고 QA03은 전체 목표의 VIA 처리 경로다. 로컬 commit 시간을 이 지표 전체로 대신하지 않는다. QA04는 공통 8개 변경 과제의 실제 운영 모듈 변화가 있어야 수치화한다. QA05는 재시도와 폐기 호출까지 포함하고 QA06은 전체 제품 RAM이다. QA02와 QA08의 직접 차별화는 현재 근거가 없다.

QA07은 최초 업무 연결과 사용자 지정 순서의 정확도다. 질문 전달, 중복 방지와 receipt 복구 전체를 새로운 QA07 의미로 넣지 않는다. 두 구현이 같은 올바른 판단을 보존하면 QA07 우위는 미확정이다. 관련성만으로 차별화 coverage를 채우지 않는다. 기존 정의, 목표와 모집단은 변경하지 않는다.

우선 상세화할 구현은 한 transaction 확정이다. 한 PC에서 교차 상태를 일관되게 저장하고 외부 대기와 분리하는 데 필요한 중간 상태가 적다. 이는 작성자 판단이며 사용자 선택이 아니다. 업무 소유자 방식이 정상 사용에서 지연 분리나 상주 메모리 해제에 실질 이익을 주고 추가 복구 비용을 상쇄하면 재검토한다. 첫 방식에서도 업무별 handler를 순수 함수로 분리하고 idle 상태를 해제할 수 있으므로 그런 개선 가능성을 제거해 후자의 이익을 만들지 않는다.

현재는 의미 있는 구현 선택 지점을 찾았지만 주요 DP에 필요한 복수 QA의 강한 차이를 입증하지 않았다. 미확인 값을 숫자로 채우지 않는다. 구체 사건과 반증 조건은 [사건별 검토](review.md), 호출 및 저장 스케치는 [코드](code-sketch.md)를 따른다.
