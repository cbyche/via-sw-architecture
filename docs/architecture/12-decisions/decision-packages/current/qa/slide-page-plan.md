## 공통 편집과 판정 규칙

- 슬라이드 오른쪽 점수표는 **6점 ●●●부터 0점 ○○○ 순서**로 배치한다. 아래 표도 같은 순서다.
- 목표 충족은 1~6점이며 0점은 목표 미달이다. 실측 표에서는 미관측을 숫자 점수로 바꾸지 않는다. 현재 사고 실험 표는 예상 원값을 숫자 구간에 대입한 예상 점수이며, 사용자 지시대로 기능 실패에 시간 벌점을 적용하지 않는다.
- 모든 수치 예시는 **설명용 가상값**이다. 점수 간격은 비교 표현 규칙이며 출처가 모든 구간을 정한 것은 아니다.
- COMMON-28-v1 전체를 5회 실행하고 QA별 관측을 추출한다. QA04/08의 개발 변경과 QA07의 무부하 대조는 연결된 별도 평가다.
- 예상 DP 손익은 발표자 노트에 둔다. 실측 우열이나 최종 A/B 선택으로 표현하지 않는다.

## QA02 지칭 대상 식별 정확도

### 화면 본문

| 분류 | Title | Scenario |
| --- | --- | --- |
| Accuracy | **지칭 대상 식별 정확도** | 시스템은 사용자가 화면이나 과거 이력을 지칭할 때 **의도한 대상 집합을 누락이나 추가 없이 정확하게 식별해야 한다.**<br>**[지칭 대상 집합 일치율 ≥ 93%]**<br>※ 측정 조건: 공통 28개 중 지칭 판단 44건 × 5회 / 정답 대상 집합 전체 일치<br>※ 목표 근거: ReALM-3B 화면 지칭 93.0%의 집합 완전 일치 성능 참조 |

**사용자가 가리키거나 다시 언급한 대상을 정확히 골라 재설명과 오작업을 줄인다.**

- **목표 93%:** ReALM-3B 화면 지칭의 대상 집합 완전 일치율 93.0%를 기술 참조 목표로 채택한다.
- **판정 단위:** 원본과 범위 및 필요한 버전까지 대상 집합 전체가 같아야 성공이다. 연구와 VIA의 처리 범위 차이는 발표자 노트에 둔다.

**측정 산식**

```text
a = 100 × 전체 대상 집합이 일치한 판정 수 / 220
대상: 지칭 판단 44개 × 5회 / 실제 모호한 입력 4건은 사전 제외
```

**설명용 예시:** 정답 `{매출표 A, 비용 그래프 B}`에 `{A,B}`는 성공. `{A}`와 `{A,B,C}`는 실패 220회 중 205회 전체 집합 일치 → **약 93.18% → 1점 ◐○○**. 217~219회면 5점이며 220회면 6점

### 점수표

| 점수 | 표시 | 기준: a [%] |
| ---: | --- | --- |
| 6 | ●●● | a = 100% |
| 5 | ●●◐ | 98.6% ≤ a < 100% |
| 4 | ●●○ | 97.2% ≤ a < 98.6% |
| 3 | ●◐○ | 95.8% ≤ a < 97.2% |
| 2 | ●○○ | 94.4% ≤ a < 95.8% |
| 1 | ◐○○ | 93% ≤ a < 94.4% |
| 0 | ○○○ | 0% ≤ a < 93% |

**구간 도출:** 93%를 1점 하한으로 두고 (100−93)/5 = 1.4%p씩 나눈다. 6점은 100%일 때만 부여한다. 220개 중 205~207개 일치가 1점이며 220개가 6점이다.

**출처 각주:** [Apple ReALM, SIGDIAL 2024 §3과 Table 3](https://aclanthology.org/2024.sigdial-1.5.pdf). 자료 확인일 2026-10-14.

### 발표자 노트

**발표자 노트:** 화면과 대화의 지칭을 해석하고 전체 대상 집합이 같아야 성공이라는 공통점을 먼저 설명한다. 단 ReALM은 질의별 집합이고 VIA는 표현별 집합과 revision이므로 평가 단위와 처리 범위는 다르다. 화면 최고 성능 93.0%를 두 DP의 기술 참조 최소 목표로 선택했다. ReALM의 대화 97.9%와 평균내지 않는다. 후보 수집과 과거 원본 검색 및 범위와 버전의 처리가 VIA에서는 더 넓으므로 관련 연구의 성능을 적용한 요구이지 동일 시험의 비열등성 증거가 아니다. 마우스 연구와 근거 없는 downstream 복구율은 사용하지 않는다.

**자료:** [정의와 점수 및 DP 예상](qa02-referent-accuracy.md) / [연구 과제 조건과 통계 한계 및 잘못된 복구 산식](research-notes/qa02-accuracy-research.md).

**DP 설명:** **DP-47과 DP-45는 현재 화면과 과거 자료에서 같은 대상 집합을 고르는 문제를 다루므로 같은 성공 판정을 적용한다.** 공통 적용 자체는 양안 차이의 증거가 아님

## QA04 변경 범위

### 화면 본문

| 분류 | Title | Scenario |
| --- | --- | --- |
| Maintainability | **변경 범위** | 시스템은 기능을 추가하거나 VIA가 주고받는 데이터 형식을 바꿀 때 **수정해야 하는 Rust 모듈 수를 작게 유지해야 한다.**<br>**[변경 과제당 평균 변경 Rust 모듈 수 ≤ 3개]**<br>※ 측정 조건: 공통 기능의 형식 변경 3건 + 기능 확장 3건 / 변경 모듈 수와 28개 기능 회귀<br>※ 목표 근거: ARGO PR 145건 평균 5.4개 × 60% = 3.24개 → 3개 |

**기능을 바꿀 때 여러 개발자의 코드와 담당 영역까지 수정이 퍼지는 부담을 줄인다.**

- **목표 3개:** 사용자 제공 ARGO PR 145건 평균 5.4개 × (1−40%) = 3.24개보다 엄격한 3개를 채택한다. 실제 요구 개선 폭은 약 44.4%다.
- **모듈 단위:** package / crate target / 완전한 mod 경로로 식별하는 운영 Rust 모듈이다. 파일 수나 기능 책임 상자 수가 아니다.

**측정 산식**

```text
x = (C01 변경 모듈 수 + … + C06 변경 모듈 수) / 6
각 변경은 같은 시작 코드에서 독립 수행 / 단위: 개
```

**설명용 예시:** 6개 변경의 수정 모듈 수 `2, 2, 3, 4, 3, 4` → 합계 18 / 6 = **평균 3개 → 1점 ◐○○**. 실제 mod 트리에서 수정된 노드만 센다.

### 점수표

| 점수 | 표시 | 기준: x [개] |
| ---: | --- | --- |
| 6 | ●●● | x ≤ 1 |
| 5 | ●●◐ | 1 < x ≤ 1.4 |
| 4 | ●●○ | 1.4 < x ≤ 1.8 |
| 3 | ●◐○ | 1.8 < x ≤ 2.2 |
| 2 | ●○○ | 2.2 < x ≤ 2.6 |
| 1 | ◐○○ | 2.6 < x ≤ 3 |
| 0 | ○○○ | x > 3 |

**구간 도출:** 목표 평균 3개와 변경을 한 모듈에 모은 평균 1개 사이를 (3−1)/5 = 0.4개씩 분할한다. 평균값이므로 소수 경계를 사용한다.

**출처 각주:** [사용자 제공 ARGO 집계와 적용 조건](targets-source-qa04-argo.md) / [Rust 모듈 정의와 계수 예시](targets-source-qa04.md). 자료 확인일 2026-10-14.

### 발표자 노트

**발표자 노트:** 파일 수와 module 수는 다르다. prompt와 schema 및 설정 변경도 담당 운영 모듈에 귀속하고 테스트 전용 변경은 제외한다. 부모 모듈은 실제 수정됐을 때만 센다. AI 코딩 병행 수정의 부담은 사용자 경험에서 나온 요구이고 모듈 수는 변경 파급의 구조 지표다. 이 값만으로 전체 개발시간이나 충돌 건수를 증명하지 않는다. “형식 변경은 1개와 기능 확장은 5개”라는 이전 가정은 사용하지 않는다.

**자료:** [모듈 정의와 변경 과제 및 점수표](qa04-change-scope.md) / [조사 근거와 Rust 설명](research-notes/qa04-change-research.md) / [ARGO 수치와 계산](targets-source-qa04-argo.md) / [모듈 계수 예시](targets-source-qa04.md).

```text
C = (28개 전체 묶음 총비용 1 + … + 총비용 5) / 5

```

**설명용 예시:** 한 묶음의 준비 $0.08 + 의미 $0.45 + 음성 $1.12 + 갱신과 재시도 $0.15 = $1.80. 5회가 모두 같다면 **평균 $1.80 → 3점 ●◐○**.

### 발표자 노트

**발표자 노트:** 월 $20와 20근무일 및 하루 40요청 가정은 폐기했다. 28개는 공통 대표 시나리오 묶음이다. 입력량과 추론 포함 출력량은 각 사건의 견적 규격이다. 실제 후보의 호출 수와 출력량을 강제하지 않는다. 추론과 음성 및 cache의 실제 청구 bucket을 사용한다. 가격은 확보했지만 필요한 정보를 담은 payload와 기능 달성을 검증하지 않았다.

**발표자 추가 노트:** Realtime 190개 Response는 매번 명시적 입력을 지정한다. 원본 맥락은 Luna에 제공한다. 음성은 481초 입력과 545초 생성 출력으로 견적을 냈고 음성과 함께 생성되는 텍스트도 포함한다. 음성 토큰 환산은 근사치이며 실제 청구는 provider usage로 확인한다.

**자료:** [활동과 원장 및 점수표](qa05-model-cost.md) / [공식 단가와 수정된 견적 및 누락 방지 항목](research-notes/qa05-cost-research.md).

| Resource Efficiency | **최대 RAM 사용량** | 시스템은 삼성 노트북의 다른 앱과 함께 실행될 수 있도록 **사용 중 VIA의 실제 RAM 최고량을 제한해야 한다.**<br>**[VIA 전체 RAM 관측 최고량 ≤ 512 MB]**<br>※ 측정 조건: 공통 28개 전체 × 5회 / Windows 11과 클라우드 모델 / 전체 VIA의 동시 RAM 최고량<br>※ 목표 근거: PC 플랫폼 및 기술기획 측 시스템 요구사항 512 MB / 과제에서 사용자 지정 |

**기본 탑재 VIA가 사용자의 다른 앱이 쓸 RAM을 과도하게 차지하지 않게 한다.**

- **목표 512 MB:** 기본 탑재 VIA의 RAM 부담을 제한하기 위한 PC 플랫폼 및 기술기획 측 시스템 요구사항이다. 과제에서 사용자가 지정했다.
- **측정 범위:** 전체 VIA의 같은 시점 RAM을 합치고 공유 페이지는 한 번만 센다. 앱 시작과 초기 준비 및 후속 처리까지 포함한다.

**측정 산식**

```text
M = max(5회 전체 실행의 같은 시점 VIA RAM 바이트 합계) / 1,000,000
512 MB = 512,000,000바이트 / 서로 다른 시점의 프로세스 피크를 더하지 않음
```

**설명용 예시:** 시점 t1의 전체 RAM 380 MB → 시점 t2의 전체 RAM 400 MB. 5회 전체에서도 400 MB가 최고라면 **358.4 < 400 ≤ 409.6 → 3점 ●◐○**. 프로세스별 개별 최고값의 합을 사용하지 않는다.

### 점수표

| 점수 | 표시 | 기준: M [MB] |
| ---: | --- | --- |
| 6 | ●●● | 0 ≤ M ≤ 256 |
| 5 | ●●◐ | 256 < M ≤ 307.2 |
| 4 | ●●○ | 307.2 < M ≤ 358.4 |
| 3 | ●◐○ | 358.4 < M ≤ 409.6 |
| 2 | ●○○ | 409.6 < M ≤ 460.8 |
| 1 | ◐○○ | 460.8 < M ≤ 512 |
| 0 | ○○○ | M > 512 |

**구간 도출:** 요구 상한 512 MB와 예산의 절반 256 MB 사이를 (512−256)/5 = 51.2 MB씩 나눈다. 256 MB는 개선 등급의 기준이며 별도 조직 요구나 구현 최소량이 아니다.

### 발표자 노트

**발표자 노트:** 512 MB는 512,000,000바이트이며 488.28125 MiB다. 사용자 지시로 과제에 지정한 시스템 요구사항이고 실제 삼성 내부 승인 문서를 별도로 확인한 것은 아니다. 이전 512MiB 참조와 RAM-v1의 철회 이력은 유지한다. Windows 전체 RAM 계측은 공유 페이지와 그래픽 버퍼의 귀속 및 표본 누락을 검증해야 한다. 전용 RAM만 측정한 값을 전체 RAM으로 채점하지 않는다. 현재 대상은 클라우드 모델 조건이며 로컬 모델을 쓰면 가중치와 실행 상태도 포함한다.
