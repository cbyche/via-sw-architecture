# 독립 측정 리뷰 1차

> **이관한 원전 이력:** 본문의 현재·최신·실측 전·검토 완료는 원래 날짜와 대상 범위의 기록이다. 현재 네 DP의 정본 상태와 결과는 [QA 기준 안내](../README.md) 및 [공통 QA v3](../../evaluation/common-qa-v3/README.md)에서 확인한다. 이 기록을 최신 실측 또는 현재 설계 승인으로 계승하지 않는다.


> 2026-10-14 / 리뷰어 `review_measurement` / 초안 작성에 참여하지 않은 독립 검토 / 구현·모델 호출·측정 없음

## 결론

**P1 없음. P2 5건을 발견했고 검토 도중 2건(M-04·05)의 보완을 재확인했다. M-01~03은 후속 재검토가 필요하다.** QA1의 텍스트 표시 경계, 의미 없는 접수 신호 제외, 음성 차례 대기 분리는 일관된다. 문헌의 지침과 작성자가 정한 수치·평균·점수 구간도 구별했다. 아래 결함은 실제 계산 또는 발표에서 해석이 달라질 수 있는 부분이다. 발견 당시와 보완 후의 상태를 나누어 기록한다.

## M-01 · P2 — `+∞` 실패가 있는 QA1에는 유한 평균 비교식을 적용할 수 없다

- **위치:** [QA1 §5와 §10](../qa01-first-response-latency.md), 검토 시점 73~75행 및 153~154행.
- **문제:** 미응답 한 건이면 대표값을 `+∞`로 정하지만, 차이 판정은 `100ms 또는 느린 안 평균의 10% 중 큰 값`과 bootstrap 구간을 적용한다. 한 안이 실패하면 실용 차이 기준도 무한대가 되며 양안이 실패하면 차이 `∞−∞`는 정의되지 않는다. 현재 문장은 양안 실패만 별도로 언급하여 한 안 실패의 처리도 불명확하다.
- **최소 수정:** 시간 우열·bootstrap·실용 차이는 양안의 전체 대표 표본이 유한하고 공통 기능 조건을 만족할 때만 계산한다고 명시한다. 한 안 또는 두 안의 실패는 실패 원장과 0점을 보존하되 `유효한 시간 비교 불가`로 보고한다. 정상 안이 기능 조건을 만족했다는 사실과 시간 차이의 입증을 구별한다. 성공 표본 평균은 계속 진단으로만 남긴다.
- **제품 결정과의 구별:** 실패에 `+∞` 판정값을 쓰는 엄격함 자체는 명시된 평가 제안이다. 여기서 지적하는 것은 그 제안의 채택 여부가 아니라 뒤 비교식의 미정의 분기다.

## M-02 · P2 — QA2 예시가 명시한 평가 단위를 바꾼다

- **위치:** [QA2 §2와 §9](../qa02-referent-accuracy.md), 검토 시점 27행 및 158~178행.
- **문제:** 본문은 지칭 표현 하나와 revision을 한 판정으로 정하고 서로 다른 표현의 집합을 합치지 않는다고 한다. 그런데 “처음 표는 그대로 두고 그래프는 아래 것만” 예시는 표 유지와 그래프 정정의 두 binding을 `{표 A, 그래프 D}` 하나의 판정으로 합친다. 이 방식은 100개 판정의 분모와 부분 정정의 점수를 바꿀 수 있다.
- **최소 수정:** 예시를 한 지칭 표현이 복수 대상을 가리키는 장면으로 바꾸거나, 현재 예시를 표 표현 `G1={A}`와 그래프 표현 `G2={D}`의 두 판정으로 분리한다. 슬라이드 문구도 같은 단위를 유지한다. 평가 단위를 Request 전체로 바꾸려면 별도 정의 개정이 필요하므로 예시만 고치는 편이 작다.

## M-03 · P2 — QA3 인과 그래프에 목표 입력 전 작업시간이 들어갈 수 있다

- **위치:** [QA3 §2와 §4](../qa03-via-processing-time.md), 검토 시점 27~29행, 74~97행.
- **문제:** 시작점은 최초 입력 종료지만, 산식은 자원 선행 작업의 실제 duration을 그대로 더하며 다른 목표의 경합 작업도 포함한다. `t0=-4초`에 시작해 현재 목표의 입력 `0초` 이후 `1초`까지 자원을 점유한 이전 작업과, `1~2초`의 현재 목표 작업을 연결하면 현 산식으로 5+1=6초가 될 수 있다. 현재 목표가 입력된 뒤 실제 경과는 2초이고 제외할 외부 구간도 없다. 목표 전 준비 비용을 비용·메모리로 분리한다는 §5와도 충돌한다.
- **최소 수정:** 목표별 귀속 그래프를 입력 `t0`에서 절단한다. 입력 전에 완료된 작업은 시각 0의 기성 상태로 두고, 입력을 가로지르는 경합 작업은 `t0` 이후 잔여 구간만 넣는다. root·release 시각과 자원 edge의 처리 원칙을 명시하고 위 2초 예시를 추가한다. 외부 시간을 제거하기 전에 정상 duration 그래프로 재구성한 완료 시각이 실제 완료 시각과 관측 오차 안에서 일치하는지도 검증 조건에 둔다.
- **추가 명료화:** 이 값은 외부 업무 시간을 제거한 처리 경로 길이다. 병렬 처리 예시의 4.8초가 실제 wall-clock에 순증한 시간이라는 뜻은 아니다. 발표의 “VIA 자체가 더하는 시간”은 “외부 업무 시간을 제외한 VIA 처리 경로의 시간”으로 쓰면 이 의미가 더 분명하다.

## M-04 · P2 — QA9의 좋은 평균 점수로 필수 음성 누락이 가려질 수 있다

- **위치:** [QA9 §6](../qa09-audio-delivery-lag.md), 검토 시점 114~116행 및 §8의 120회 구성.
- **문제:** 음성 미전달을 5,000ms로 두면 119건이 100ms이고 1건이 미전달인 경우 평균은 약 140.8ms로 5점이다. 잘못된 요약은 회귀 위반이라고 하지만 필수 음성 미전달에 대해서는 그와 별개의 기능 실패 판정이 명시되어 있지 않다. “음성을 끝없이 미뤄도 좋은 평가를 받는 빈틈을 막는다”는 목적을 평균만으로는 충족하지 못한다.
- **최소 수정:** 상한 적용 평균과 점수는 유지할 수 있다. 다만 `필수 음성 1건 이상 미전달 = 공통 기능 회귀 실패`를 독립 조건으로 명시하고, 원값·점수 옆에 항상 표시한다. 실패가 있는 안을 “음성 전달 요구 충족”이나 유효한 지연 우세로 선언하지 않는다. 점수를 새 복합 지표로 바꿀 필요는 없다.
- **검토 중 보완 재확인 — 해결:** 최신 §6은 필수 음성 미전달을 `+∞` 판정·전체 0점으로 바꾸고 원시 관측 시간과 `AUDIO_NOT_DELIVERED`를 보존한다. 위의 119+1 반례로도 성공 점수를 얻지 못한다. 잘못된 의미의 음성도 유한 지연만으로 성공하지 못한다고 명시했다. 최초 검토 때부터 `t_adopted`의 첫 내용 채택을 시작으로 읽었으며, 최신 본문에서도 이 경계가 유지됨을 확인했다.

## M-05 · P2 — Windows 소프트웨어 loopback을 실제 음향 출력으로 오인할 수 있다

- **위치:** [QA9 §3와 §8](../qa09-audio-delivery-lag.md), 검토 시점 47행 및 133~139행.
- **문제:** 종료점은 실제 들리는 첫 sample인데 PoC는 종류를 구별하지 않고 Windows audio 출력과 loopback onset을 연결한다. WASAPI loopback은 하드웨어 지원에 따라 audio engine 출력 stream을 capture buffer로 복사할 수 있다. 이 시각이 DAC·장치·스피커를 지난 실제 음향 시작과 같다는 보장은 없다. callback과 loopback을 대조해도 남은 장치 지연을 입증하지는 못한다.
- **확인한 공식 근거:** [Microsoft Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)은 하드웨어 loopback pin과 audio-engine stream 복사를 구별한다. [Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)는 application 제출과 실제 스피커 출력 사이의 render latency를 별도로 정의한다.
- **최소 수정:** 실제 acoustic onset은 보정한 외부 마이크 또는 적절한 물리 loopback 경로로 검증하도록 하고 capture·device 지연 및 관측 오차를 기록한다. WASAPI/system-mix loopback만 쓴 최소 PoC는 소프트웨어 출력 proxy로 명명하고 실제 청취 지연으로 보고하지 않는다. 현재 fixture 기반 PoC를 제품 전체 음향 시험으로 확대할 필요는 없다.
- **검토 중 보완 재확인 — 해결:** 최신 §8은 WASAPI software loopback과 실제 장치 출력을 구별하고 보정한 acoustic microphone 또는 출력단 analog loopback 및 오차 기록을 요구한다. software capture/callback만 있으면 proxy로 보고하고 실제 음성 목표 달성으로 채점하지 않는다고 적었다. 이는 제안한 경계 혼동을 해소한다. 실제 장비 보정은 추후 PoC에서 검증할 사항이다.

## 결함으로 분류하지 않은 제품·평가 결정

- QA1 평균 1초는 HCI 지침을 적용한 설계 목표이며 개별 요청 또는 음성 청취 1초 보장이 아니다. 문서가 이 차이와 꼬리 지연 반례를 이미 명시했다.
- QA2의 98%는 50건당 오류 1건이라는 제안 예산이다. 제품 근거를 사용자와 확정할 필요는 있으나 문헌으로 거짓 정당화하지는 않았다. 20개 사례 5회 반복을 독립 100개 상황으로 일반화하지 않는 설명도 적절하다.
- QA3 5초와 QA9 500ms는 설계 예산이다. 지금의 출처가 이 수치를 실험적으로 증명하지 않았다는 점을 각 문서가 밝혔다. 이 수치의 제품 수용은 문서 버그 수정과 별도의 결정이다.
- QA1의 DP44 우세는 약한 가설이며 QA1×DP42는 동점 예상이다. 현재 패키지로 1순위 QA의 3~4개 DP 차별화가 입증됐다고 말할 수 없다. 이는 실제 선택·후속 검증의 남은 문제이며 지표를 변형해 해결할 결함이 아니다.
- QA1과 QA3은 초기 구간과 전체 경로의 관계이며 합산하지 않는다고 적었다. QA9도 회귀 축으로 구별하여 중복 가중을 피했다.
