# QA01 / QA03 목표 근거 독립 교차 검토

> **이관한 원전 이력:** 본문의 현재·최신·실측 전·검토 완료는 원래 날짜와 대상 범위의 기록이다. 현재 네 DP의 정본 상태와 결과는 [QA 기준 안내](../README.md) 및 [공통 QA v3](../../evaluation/common-qa-v3/README.md)에서 확인한다. 이 기록을 최신 실측 또는 현재 설계 승인으로 계승하지 않는다.


> 2026-10-14 / 검토자: QA05와 QA06 작성 담당 에이전트 / QA01과 QA03 작성에는 참여하지 않음
>
> 범위: 문서와 외부 출처 및 가상 계산의 검토. 실행 코드, 실제 Windows 표시 계측, 모델 실행, PoC 결과와 통계적 성능 보장을 검증한 기록은 아니다.

## 1. 검토 대상과 결론

- [QA01 첫 응답 지연시간 v2](../qa01-first-response-latency.md) 전체
- [QA03 VIA 처리시간 v2](../qa03-via-processing-time.md) 전체
- [목표 수치 도출 논리](../target-rationale.md)의 QA01과 QA03 및 공통 변경 규칙

**최초 검토 결과: P1 없음. 수치 도출 설명의 P2 1건. 수정 재확인 후 미해결 P1/P2 없음.** 두 상세안에서 출처에 없는 실험값이나 stakeholder 합의를 발견하지 않았다. 1초와 5초를 외부 지침에서 가져온 부분과 이를 VIA 제품 목표 및 대표 시험 최대값에 적용한 판단을 구분한다. 평균에서 최대값으로 바꾼 산식, 예시, 실패 처리와 차이 판단은 일관적이다.

P2는 요약 문서의 5초 경계 설명이다. 상세 QA03의 산식이나 목표 숫자를 다시 바꾸라는 발견 사항은 아니다. 검토자가 대상 문서를 직접 고치지 않고 작성 담당자에게 전달했다.

## 2. 발견 사항

### LAT-01 — P2: 요약 문서가 5초를 설명하면서 5~10초 구간의 상단을 가리킴

**위치:** [목표 수치 도출 논리 §4](../target-rationale.md#4-qa03-왜-5초인가), 최초 검토 시 54행.

**검토 당시 표현:** `Long wait` 2~5초와 `Captive` 5~10초를 나열한 직후 “후자의 대기 범주를 넘어가는 부담을 만들지 않도록 5초”라고 설명한다.

**문제:** “후자”는 바로 앞의 5~10초 구간이다. 그 구간을 넘지 않는다는 설명은 상단 10초를 가리킬 수 있으므로 목표 5초의 직접 도출 논리와 맞지 않는다. 사용자가 가장 중요하게 요구한 “왜 그 숫자인가”에 관한 요약 문장이므로 수정이 필요하다.

**구체적 수정안:** “VIA 자체 처리가 Windows의 `Long wait` 상단을 넘지 않도록 **5초를 처리 상한으로 채택한다**.” 또는 같은 의미로 5초가 `Captive`의 시작 경계임을 직접 설명한다. 5초를 빠른 응답이나 자연스러운 무응답 시간으로 표현하지 않는 현 단서는 유지한다.

**해결 확인 기준:** 요약의 근거 문장이 2~5초 구간의 상단 또는 다음 구간의 시작을 명확히 지칭하고 상세 QA03 §7과 같은 의미가 되면 닫을 수 있다. 목표 5초와 DAG 계산 방식의 변경은 요구하지 않는다.

| 입력 이전 비용 | 목표 시작 이전에 끝난 작업은 제외하고 시작 전부터 점유 중인 자원은 시작 이후 잔여 구간만 포함함. 선행 준비 비용은 QA05에 남김 |

## 6. 결함과 구별해 유지할 한계

1. **1초와 5초는 출처가 있는 제품 목표 제안이다.** 원문이 VIA의 모든 요청에 그 숫자를 법칙처럼 지정하지 않는다. 제품 요구의 선택이라는 현재 표현을 발표에서도 유지해야 한다.
2. **대표 시험 최대값은 미래 모든 요청의 최악 시간 보장이 아니다.** 입력 길이, 장치, 부하, 모델, 네트워크 조건과 표본 수를 고정하고 그 조건에 한해 비교해야 한다. 문서는 이미 이 범위를 제한한다.
3. **QA03의 귀속 처리 5초는 UX 지침을 내부 책임 경로에 적용한 설계 요구다.** 실제 사용자가 느끼는 총 대기가 만족스러워졌다는 실증 결과로 바꾸면 안 된다. 원시 전체 대기시간은 함께 남겨야 한다.
4. **목표를 만족할 수 있는지는 아직 측정하지 않았다.** 특히 클라우드 모델 및 실제 UI 표시를 포함한 최대 1초 달성 가능성은 문헌만으로 확인되지 않는다. 현재 문서는 달성 사실을 주장하지 않는다.
5. **구조상 기대와 최댓값의 우열은 별개다.** DP45의 사전 관계 준비가 반복 응답을 줄여도 미생산 및 갱신 사례가 전체 최대값을 결정할 수 있다. 최대값 사건을 추적한다는 현 절차를 그대로 실행해야 한다.

이 한계들은 숫자를 공란으로 돌려야 한다는 의미가 아니다. 출처와 제품 요구 및 실측 결과를 구분한 상태에서 1초와 5초를 검토 가능한 목표로 제안할 수 있다.

## 7. 수정 확인 이력

- 최초 검토: `LAT-01` P2 1건을 작성 담당자에게 전달했다.
- 작성 담당자가 요약 문장을 “Long wait의 상단을 넘어 Captive 구간의 대기를 추가하지 않도록 5초”로 수정했다. 2026-10-14 검토자가 실제 파일을 다시 읽어 숫자 5초와 경계 설명이 일치함을 확인했다. **`LAT-01` 해결.**
- QA03의 음성 표는 “완료 조건에 포함하지 않음”과 “streaming 재생은 준비 완료 전에 시작할 수 있음”을 함께 명시한다. 실제 재생이 반드시 완료점 뒤라는 해석을 만들지 않으며 §2의 streaming 허용과 일치함을 재확인했다.
- `git diff --check`를 수행했고 형식 오류가 없었다. 이 확인은 문서 whitespace 검사이며 PoC 검증이 아니다.
- 최종 판정: 검토 범위 내 미해결 P1/P2 없음. §6의 적용 한계는 그대로 남는다.
