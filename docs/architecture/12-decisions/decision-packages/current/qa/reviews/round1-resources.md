## 1. 범위와 결론

검토 범위는 QA04~09 상세 문서와 패키지 README의 요약·대응표다. 프로젝트 경계와 이전 QA 계약 및 실제 사건 경계 계약을 먼저 확인했다. 기존 기준선과 새 후보의 번호를 구분하고 작성자 예산을 미승인이라는 이유만으로 결함 처리하지 않았다.

**P1 없음. 수정이 필요한 P2는 2건이다.** 두 건 모두 요약표가 상세 명세의 현재 정의·판정과 달라지는 통합 문제다. QA04~09의 점수 구간과 예시 계산에서 공백·중복·잘못된 채점은 발견하지 못했다. 리뷰 시점의 발견 사항이며 아래 수정 확인 전에는 해결됐다고 간주하지 않는다.

## 2. 수정이 필요한 발견 사항

### RES-01 — P2: QA09 시작점을 요약표가 텍스트 표시로 바꾼다

- 위치: [당시 패키지 README §3](../history/source-package-overview-20261015.md#3-추가-후보와-권고)의 QA09 행. 검토 당시 46행.
- 현재 요약: `텍스트 표시 후 재생 가능한 시간 중 평균 음성 시작 대기`.
- 상세 계약: [QA09 §3](../qa09-audio-delivery-lag.md#3-산식과-사건-경계)는 `t_adopted`부터 eligible 구간을 합산하며 UI 표시를 기다린 뒤 시계를 시작하지 않는다고 명시한다.
- 영향: 응답 내용 채택 후 UI 표시가 300ms 늦으면 요약표로 구현한 평가자는 그 300ms를 음성 지연에서 제외한다. UI가 느린 구조에 유리해질 수 있고 발표와 PoC가 서로 다른 지표를 사용한다.
- 요청 수정: 요약도 **응답 내용 채택 후 재생 가능한 구간의 평균 음성 시작 대기**로 맞춘다. 다른 인덱스·발표용 문구에서 텍스트 표시를 시작점으로 쓰는 곳도 함께 확인한다.
- 해결 확인: README와 QA09의 시작점이 모두 실제 내용 채택이며 UI 표시·summary ready·PCM ready가 시작점이 아닌지 확인한다.

### RES-02 — P2: QA08의 DP44 예상 우열이 상세안과 반대다

- 위치: [당시 패키지 README §4 대응표](../history/source-package-overview-20261015.md#4-qadp-대응과-예상-우열)의 `08 병행 변경 중복 × DP-44` 셀. 검토 당시 63행.
- 현재 요약: `B 약`.
- 상세 판정: [QA08 §6](../qa08-parallel-change-overlap.md#6-dp의-예상-우열과-판정)는 강한 A의 분리 handler와 B의 공통 게시·결합을 고려하여 **실용적 동점 예상 / 커버리지에 세지 않음**으로 결론낸다.
- 영향: 사용자가 대응표만 보면 상세 검토에서 철회한 B 이익이 아직 유효한 가설인 것으로 이해한다. 약한 QA–DP 연결을 남겨 커버리지를 과장할 위험이 있다.
- 요청 수정: 대응표를 `=`로 맞추고 QA08 이름도 상세 문서의 `병행 수정 중복`과 통일하면 좋다. 새로운 B 우위 주장을 채택하려면 먼저 실제 독립 변경 집합으로 근거를 추가해야 한다.
- 해결 확인: QA08 본문·인덱스·최종 대응표가 같은 판정을 사용하며 현재 핵심 커버리지에 포함하지 않는지 확인한다.

### 점수와 산술 확인

QA04~09 각 일곱 구간은 유효한 비음수 값 영역을 빠짐없이 덮고 경계의 등호가 겹치지 않는다. 목표 경계에서 모두 1점이며 최상위 경계 이하에 6점을 부여한다. QA08은 0만 6점이고 양수 1/6까지 5점이다. 반올림 전 값으로 판정하도록 했다.

계산을 별도 재확인했다.

- QA04 목표: `(3×1+3×5)/6 = 3`.
- QA05 목표: `$20/(20×40)×20 = $0.50`. 예시 합계 `$0.04+$0.21+$0.17+$0.03 = $0.45`이므로 2점이다.
- QA06 frame payload: `118.65234375MiB`. 내부 예산 소계는 1,792MiB다. 가상 동시 합계 900MiB는 6점이다.
- QA07 예시 150ms는 2점이다.
- QA08 예시 `1+0+1+0+0+1`을 여섯 쌍으로 나누면 0.5개이며 3점이다.
- QA09 예시 `2.3−2.0=0.3초`는 3점이다.

유한 구간 확인과 실패 규칙 검토를 구별했다. `NOT_RUN`, `INCOMPLETE_*`는 수치 0점으로 표시하지 않으며 실제 필수 응답 실패의 별도 0점 규칙은 명시되어 있다.

## 4. 낮은 우선순위 보완 제안

QA07의 `i`가 LI-01~04 네 사례인지 각 사례×겹침 시점의 12개 cell인지 한 줄로 고정하면 좋다. 반복 평균의 차이에 `max(0, ·)`를 적용하므로, 겹침 시점 간 평균을 먼저 내는 것과 각 시점의 증가분을 먼저 자르는 것은 같지 않다. 예를 들어 세 시점의 차이가 −100/0/+100ms이면 전자는 0이고 후자는 약33.3ms다. 실행 전에 **12개 case cell 각각에서 20회 평균 차이를 계산한 뒤 12개를 평균**하거나 **네 사례마다 모든 시점을 먼저 평균**하는 중 하나를 명시해야 한다. 현재 문서의 대표 사례 수 해석을 더 좁히기 위한 보완이며 본 리뷰의 P2 두 건과 별도로 기록한다.

## 6. 검증 한계와 재검토 요청

실제 Rust module registry·diff, provider billing ledger, Windows 공유 allocation 중복 제거와 audio loopback은 아직 없다. 공식 API 설명이 특정 미래 계측 구현의 정확성을 증명하지 않는다. 점수의 산술 타당성과 비교 절차를 검토했으며 3개·$0.50·4GiB·200/500ms가 제품에 최적인지나 실제 달성 가능한지는 검증하지 않았다.

RES-01과 RES-02를 수정한 뒤 수정된 README와 연결 명세를 다시 읽어 재검토 결과를 별도 기록한다. 낮은 우선순위 QA07 집계 보완도 실행 명세가 동결되기 전에는 반영하는 편이 안전하다.
