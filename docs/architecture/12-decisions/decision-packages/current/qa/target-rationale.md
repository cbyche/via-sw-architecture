## 2. QA01: 왜 1초인가

**사용자는 입력이 어떻게 이해됐는지 확인하고 생각과 행동을 이어갈 수 있어야 한다.**

- [Nielsen, Response Times: The 3 Important Limits, 1993](https://www.nngroup.com/articles/response-times-3-important-limits/)은 약 1초를 사용자의 사고 흐름 유지에 관한 UI 응답 지침으로 설명한다.
- [Microsoft Windows 응답성 지침, 2026-03-18 갱신](https://learn.microsoft.com/en-us/windows/apps/develop/performance/responsive)은 `Pause` 0.5~1초를 지연은 있지만 응답성이 유지되는 범위로 설명한다.
- VIA의 종료점은 해당 요청이나 업무 화면에 **첫 완결된 내용이 보이는 때**다. 이 UI 동작에 위 지침을 적용하여 **1초 이하**를 요구한다.

2026-10-15 사용자 지시에 따라 공통 600건의 산술평균으로 판정한다. 오답도 실제 시간을 포함한다. 평균 1초가 개별 응답 1초를 보장하지 않으며 외부 HCI 지침이 이 집계 방법을 입증한 것은 아니다.

**심사 답변:** “생각과 행동의 흐름을 유지할 UI 반응 수준을 외부 HCI 지침에서 가져왔습니다. 인사나 로딩 표시를 제외한 첫 내용 표시를 1초 안에 제공하도록 요구합니다.”

**예시:** 발화 종료 0초 → ‘네’ 표시 0.1초 → 채택한 비교 수행 안내 0.8초 → Agent 전송 1.3초 → 음성 요약 재생 2.5초라면 해당 사건은 0.8초다. Agent 위임 완료나 음성 차례를 첫 표시의 종료점으로 사용하지 않는다.

## 3. QA02: 왜 93%인가

**화면과 대화 속 표현이 가리키는 대상 집합을 찾는 연구를 수치 참조로 삼는다.** 마우스로 표시된 표적을 누르는 운동 과제의 98.7%를 옮긴 이전 논리는 철회했다.

[Apple ReALM, SIGDIAL 2024](https://aclanthology.org/2024.sigdial-1.5.pdf)은 화면과 이전 대화에서 사용자가 가리키는 대상을 해석한다. §3은 예측 대상 집합과 정답 집합이 전부 일치해야 성공으로 센다. Table 3에서 ReALM-3B는 **화면 93.0%와 대화 97.9%**를 보였다. 화면 결과 중 가장 높은 전용 해석 모델의 93.0%를 관련 기술 참조로 선택하고 두 DP의 공통 최소 목표를 **93%**로 제안한다. 화면과 대화 점수를 평균내지 않는다.

**적용 한계:** 집합 완전 일치 원리는 같지만 ReALM은 질의별 집합이고 VIA는 지칭 표현별 집합과 revision이므로 평가 단위도 다르다. ReALM은 상위 처리에서 찾은 후보 항목과 유형 및 위치를 입력으로 받는다. VIA는 화면 증거 수집과 포인터 시간 관계 및 범위와 부분 정정까지 처리해야 한다. DP-45의 과거 원본 조회와 버전 해석도 논문의 앞선 대화 항목보다 넓다. 연구의 일부 복수 정답은 모호한 표현의 가능 후보 집합이다. VIA의 동시에 의도한 복수 대상과 완전히 같은 구성은 아니다.

**심사 답변:** “화면과 대화의 지칭 대상을 찾는 ReALM과 같은 집합 완전 일치 판정을 사용합니다. 해당 연구의 최고 화면 성능 93.0%를 기술 참조로 잡아 VIA에도 93% 이상을 요구합니다. 연구가 VIA 전체나 사용자 만족을 검증했다고 주장하지는 않습니다.”

**예시:** 정답 `{표 A, 그래프 B}`에 `{표 A}`나 `{표 A, 그래프 C}`는 실패다. 220판정 중 205개가 전체 정답 집합과 같으면 약 93.18%로 1점이다. 동일 사례 반복은 독립 사용자 모집단의 신뢰구간을 입증하지 않는다. 일반 Agent benchmark의 성공률을 VIA 실패의 복구율로 바꾸어 99%를 만들지 않는다. [출처 조건과 제외한 수치](research-notes/qa02-accuracy-research.md)

## 4. QA03: 왜 5초인가

**VIA는 일의 실행을 연결하는 인터페이스이므로 자체 처리가 장시간 대기를 만들어서는 안 된다.**

[Microsoft Windows 지침](https://learn.microsoft.com/en-us/windows/apps/develop/performance/responsive)은 `Long wait`를 **2~5초**, 불가피하게 길고 복잡한 상황의 `Captive`를 **5~10초**로 분류한다. VIA의 해석과 상태 연결 및 응답 준비가 Long wait의 상단을 넘어 Captive 구간의 대기를 추가하지 않도록 **5초를 자체 처리의 상한**으로 채택한다. 이 값이 자연스럽거나 빠른 대화라는 뜻은 아니다. 첫 내용 반응은 QA01에서 1초를 요구한다.

입력부터 모든 VIA 처리와 상세 텍스트 표시 및 음성 요약 준비까지의 완료 경로에서 외부 Agent의 도메인 작업과 사용자 대기 시간을 제거한다. 76목표를 5회 수행한 귀속 처리시간의 **산술평균**을 평가한다. 외부 업무가 없는 직접 응답은 실제 완료 지연과 일치한다. 위임 업무에서는 전체 대기에서 VIA가 소유한 처리 경로의 예산이다.

**심사 답변:** “해석 단계에 임의 시간을 배분해서 5초를 만든 것이 아닙니다. Windows가 구별하는 장시간 대기의 경계 5초를 가져와 VIA 자체 처리의 한계로 적용했습니다. 외부 업무까지 5초에 완료한다는 주장은 하지 않습니다.”

**예시:** VIA 1.2초 → 외부 작업 8초와 VIA 준비 3초가 병렬 → VIA 0.6초라면 실제 완료는 9.8초다. 외부 작업을 0초로 둔 VIA 경로는 `1.2 + max(0,3) + 0.6 = 4.8초`다. 이를 실제 경과시간에서 단순히 8초 빼서 1.8초로 보고하지 않는다.

## 5. QA04: 왜 평균 3개 모듈인가

**기존 Agent 개발에서 발생한 변경 파급을 줄인다는 요구다.** 사용자가 제공한 ARGO 집계는 기능 추가와 데이터 형식 변경 PR 145건에서 평균 수정 모듈 수 **5.4개**다. 사용자가 정한 40% 개선 목표를 적용하면 `5.4 × 0.60 = 3.24개`이며 제시된 최종 상한 **3개**를 채택한다. [ARGO 근거 기록](targets-source-qa04-argo.md)

3개는 5.4개 대비 약 **44.4% 감소**이므로 40% 개선을 충족하는 더 엄격한 목표다. 평균이 정수여야 해서 반올림한 것이 아니다. 40%는 사용자가 지정한 개선 요구이며 논문이 제시한 보편적 개선율이 아니다.

**출처 상태:** PR 145건을 이 작업에서 직접 열어 분석하지 않았다. 사용자 제공 내부 집계라는 상태를 표시한다. 향후 실제 개선율을 검증할 때는 대상 PR 목록과 집계 기간 및 모듈 정의를 확보해 VIA의 Rust 운영 모듈 기준과 비교 가능성을 확인해야 한다. 기존 VIA의 1개와 3개 변경 사례는 계수 방법 예시로만 남긴다.

**심사 답변:** “기존 ARGO의 145건 평균 5.4개를 기준으로 변경 파급을 40% 이상 줄이려는 요구입니다. 계산값 3.24보다 엄격한 평균 3개를 상한으로 정했습니다.”

**예시:** 변경 6건에서 `2,2,3,4,3,4`개를 수정했다면 평균 3개다. 이는 설명용 숫자이며 실제 후보의 측정값이 아니다.

## 6. QA05: 왜 공통 묶음당 $2.55인가

**같은 대표 시나리오 전체를 범용 API 구성의 참조 원가 이내로 제공한다는 요구다.** 공통 28개에는 사용자 입력 84건과 Agent 사건 36건이 있다. 음성 입력 81건과 의무 음성 응답 109건 및 의미 처리 120건을 각 입력의 규격으로 다시 합산했다. 이전 20요청 견적을 비례 환산하지 않았다.

| 항목 | 공통 원장에 따른 참조 조건 | 금액 |

## 7. QA06: 왜 512 MB인가

**과제의 PC 플랫폼 및 기술기획 측이 VIA에 부여한 RAM 상한을 준수한다.** 2026-10-15 사용자가 기본 탑재 VIA의 최대 RAM 사용량을 **512 MB 이하**로 지정하고 이 역할들의 시스템 요구사항으로 기록하도록 했다. 직접 출처는 이 사용자 지시이며 실제 조직의 별도 요구사항 문서나 승인 회의록을 확인한 것은 아니다. [SR-PC-MEM-01 출처와 범위](targets-source-qa06-platform.md)

이 값은 동종 제품의 사용량이나 Windows의 공통 앱 한도에서 도출한 숫자가 아니다. 다른 앱과 공존하기 위해 프로젝트가 정한 자원 제약이다. 부분 기능 수치를 합산했던 기존 512MiB 논리는 철회 이력으로 유지한다. **512 MB는 512,000,000바이트이며 512MiB와 다르다.**

**측정:** Windows 11에서 공통 28개 전체 묶음을 5회 수행하며 앱 시작부터 후속 처리 종료까지 VIA 전체의 같은 시점 RAM을 공유 중복 없이 합한 최고량을 사용한다. 전용 영역만 측정한 결과로 목표 충족을 주장할 수 없다. 전체 RAM의 계측 구현은 검증 전이다.

**점수 도출:** 1점의 상한은 요구값 512 MB다. 예산의 절반인 256 MB 이하를 6점으로 놓고 그 사이를 `(512−256)/5 = 51.2 MB`씩 나눈다. 절반과 균등 간격은 개선 여유를 표현하는 채점 규칙이며 요구 조직이 준 추가 수치가 아니다.

**심사 답변:** “기본 탑재 VIA가 사용할 수 있는 최대 RAM을 과제의 PC 플랫폼 및 기술기획 측 시스템 요구사항으로 512 MB로 정했습니다. 사용 중 전체 VIA의 동시 RAM 최고량으로 준수 여부를 판단합니다.” 출처를 묻는 경우 사용자 지정 프로젝트 요구이며 실제 삼성 내부 승인 문서를 확인한 것은 아니라고 구분한다.

**설명용 예시:** 같은 시점의 합계가 380 MB와 400 MB이고 전체 5회에서도 400 MB가 최고라면 **3점**이다. 서로 다른 시점의 프로세스 최고값을 더한 420 MB를 사용하지 않는다. 실제 제품 측정값은 아니다.

## 8. 변경과 평가 규칙

- QA01/03은 사용자 정정에 따라 평균과 오답 실제 시간으로 개정했다. 목표와 수치 배점은 유지하며 이전 최대값 점수는 옮기지 않는다.
- QA02는 부적절한 마우스 참조 99%를 철회하고 ReALM 참조 93%로 바꿨다. 44개 지칭을 반복한 220판정은 독립 사용자 220명의 증거가 아니다.
- QA04는 기존 1개와 5개 가정을 폐기한 상태를 유지한다. 평균 3개의 직접 근거는 사용자 제공 ARGO 집계와 개선 요구다.
- QA05는 공통 28개 묶음의 내용과 가격표를 버전으로 고정해야 한다. 다른 활동량이나 단가에 같은 금액을 자동 재사용하지 않는다.
- QA06의 이전 확보량 1GiB는 재사용하지 않는다. 512MiB 목표와 RAM-v1 점수도 철회했다. 새 요구는 **512 MB**이며 출처와 단위 및 RAM-v3-MB 점수를 별도로 관리한다.
- 현재 아홉 QA의 점수표에서 0점은 목표 미달이며 1~6점은 목표 충족과 개선 여유다. 중간 경계는 비교 표현 규칙이며 논문이 정한 합격선으로 제시하지 않는다.
- 목표에 맞춰 측정값이나 실패를 고치지 않는다. 실제 수치가 예상과 다르면 경계와 구현의 대등성을 검토하고 정당한 결과를 보존한다.
