# QA07 — 요청 의미 해석 정확도

2026-10-22 / `QA07-REQ-v1.1` / **상세 명세와 목표 및 점수의 사용자 검토용 제안 / 미측정**

**용어와 모집단 설명 정정:** TreeDST는 대화 이해 평가 데이터셋이다. 80건은 모든 QA의 공통 입력 수가 아니라 이전 COMMON-28에서 도출한 QA07 평가 후보 수다. 나머지 80건의 전체 의미가 명확하다는 검증은 아직 없다. 현재 공통 v4의 입력 24건과 구별한다. 목표와 점수 구간, 과거 결과는 이번 설명 정정으로 바꾸지 않는다.

## 1. 핵심 설명

**사용자 입력에 포함된 각 요청에 대해 무엇을 해 달라는지, 어떤 자료나 항목에 적용하는지, 어떤 제한을 지켜야 하는지, 다른 요청이나 이전 요청을 어떻게 이어받거나 바꾸는지를 처음 확정할 때 정확히 해석했는지 평가한다.**

| 항목 | 내용 |
| --- | --- |
| QA 이름 | 요청 의미 해석 정확도 |
| 한 줄 정의 | 사용자 입력의 필수 요청 의미 전체를 최초 확정에서 올바르게 해석하는 능력 |
| 단일 지표 | **입력별 필수 요청 의미 전체 일치율(%)** |
| 목표 제안 | **90% 이상** |
| 목표 근거 | 대화 의미 해석 연구의 TreeDST 전체 프로그램 exact match **90.8%**를 기술 참조로 삼아 정수 백분율의 초기 개발 목표 **90%**로 제안. 0.8%p 내림은 작성자의 목표 설정 규칙이며 연구 결론이 아님 |
| 평가 단위 | 사용자 입력 하나와 사전 등록한 의미 평가 revision 하나 |
| 성공 조건 | 필수 의미가 모두 정답과 동등하며 의미를 바꾸는 추가 해석도 없음 |
| 평가 입력 | 현재 공통 v4는 **24개 사용자 입력**으로 QA07 정답을 준비했으나 후보 출력이 없어 미산출. 별도로 제안했던 COMMON-28 파생안은 **84입력−사전 모호 입력 4건=80개 평가 후보**이며 전체 의미의 평가 가능성 검토 전 |
| 반복과 목표 계산 예 | COMMON-28 파생안을 채택한다면 80×5=400판정에서 360건 성공이 90%. 현재 v4의 분모나 이미 실시한 공통 평가 횟수가 아님 |
| 관측 경계 | VIA가 의미를 처음 확정한 기록. 모델의 잠정 출력, Agent 업무 완료나 음성 전달 완료가 아님 |
| 상태 | 정의는 기존 사용자 지침. 목표, 점수, 모집단과 세부 실행 절차는 이번 제안이며 실행 동결과 측정은 별도 |

“아까 두 견적을 설치비는 제외하고 비교해줘. 보고서 작성은 계속하고.”에서는 **견적 식별, 비교 작업, 설치비 제외, 보고서 유지까지 전부 맞아야 한 건 성공**이다. 실제 비교 내용의 전문성이나 보고서 작성 결과의 품질은 Downstream Agent의 업무 품질로 구별한다.

## 2. 왜 의미 전체를 한 번에 평가하는가

“설치비 제외” 하나를 놓쳐도 잘못된 비교가 되고 “보고서는 계속”을 놓치면 원치 않은 취소나 변경으로 이어질 수 있다. 따라서 항목별 정답률을 평균하지 않고 **입력 하나에 성공 1 또는 실패 0**을 부여한다.

```text
G_i = 입력/revision i의 평가자 전용 정답 의미
P_i = 같은 입력/revision에 대해 VIA가 처음 확정한 의미
K_i = 그 입력에서 확인할 필수 의미 항목과 관계

I_i = 1  (K_i의 모든 의미가 동등하고 의미를 바꾸는 추가 해석이 없음)
      0  (오류 / 누락 / 불필요한 추가 / 기한 내 확정 없음)

QA07 = 100 × Σ I_i / N
N = 사전 등록한 유효 평가 입력/revision과 반복의 전체 수
```

내부 호출, 검색, 후보 확장, 재시도와 분할된 Request 수는 N을 늘리지 않는다. 하나의 입력이 세 업무를 요구해도 한 건이며 세 업무와 관계를 모두 확인한다. 실패 원인은 여러 개 기록할 수 있지만 실패 횟수는 하나다. N=0이나 계측 불능은 0%가 아니다.

### 2.1 정답에 포함할 의미

입력과 허용된 문맥에서 요구하는 항목을 실행 전에 지정한다. 모든 입력에 모든 항목이 나타나는 것은 아니다. 아래 표현은 평가에서 확인할 의미이며 특정 내부 JSON이나 새로운 Component를 강제하지 않는다.

[저장소 용어](../../../../02-terms.md)에 따라 **사용자 입력(User Turn)**은 한 번의 발화 또는 Text 전송, **사용자 요청(User Request)**은 그 입력에 담긴 질문이나 지시, **VIA Request**는 이를 처리하도록 구분한 논리 단위, **VIA Task**는 여러 요청에 걸쳐 지속적으로 추적하는 사용자 업무 목표다. 아래에서 요청한 처리를 막연히 “작업”이라 부르거나 모든 요청을 VIA Task라고 부르지 않는다.

| 사용할 명칭 | 정확히 판정할 내용 | 예와 판정 경계 |
| --- | --- | --- |
| **요청한 처리** | 각 사용자 요청이 요구하는 행위와 산출물. 설명/비교/조회/파일 작성/수정/취소/승인/거부 등을 구별 | “두 견적을 비교”는 비교 요청. 각각 요약하는 것으로 바꾸면 오류. 이를 수행할 도구나 도메인 계획은 평가 밖 |
| **처리 대상과 적용 범위** | 처리를 적용할 자료/항목의 식별자, 필요한 판본, 문서 구간/셀 범위/대상 집합과 역할 | “이 두 견적”은 Q1/Q2, “이 문단만”은 지정 문단 범위. 원본과 비교본의 역할도 보존. 사용자 입력에서 대상이 새 결과물이라면 생성할 결과물 종류/이름을 판정하며 존재하지 않는 파일 ID는 요구하지 않음 |
| **요청의 제한사항** | 사용할 자료, 계산/비교 기준, 포함/제외, 기간/금액/수량, 출력 형식과 전달 허용 범위를 제한하는 명시 내용 또는 유효한 문맥상 요구 | “설치비 제외”, “본문만 사용”, “두 장의 PDF”, “외부 전달 금지”. 실제 접근 차단/송신 성공과는 구별 |
| **실행 순서, 결과 의존과 실행 조건** | 여러 요청을 독립적으로 처리할 수 있는지, 어느 요청 뒤에 수행하는지, 앞 요청 결과가 다음 입력인지, 어떤 조건에서만 실행하는지 | “만든 뒤 이름 변경”은 선후 관계. “검색 결과로 요약 작성”은 데이터 의존. “계약서가 있으면 요약”은 조건부 실행. Agent가 스스로 세우는 도구 실행 순서가 아님 |
| **이전 요청/응답 또는 VIA Task와의 연결** | 어느 이전 요청, 실제 전달 응답이나 Task를 참조하는지 식별하고, 후속 질문/수정/상태 조회/취소/유지인지 또는 독립된 새 요청인지 구별 | “아까 설명의 두 번째 항목”은 이전 응답 참조이고 Task가 없어도 됨. “그 보고서만 취소”는 기존 보고서 Task 식별과 취소. “그 결과로 새 발표 작성”은 기존 결과를 참조하는 새 업무 |
| **정정할 내용과 유지할 내용** | 정정 발화가 앞서 확정된 요청의 어느 내용을 바꾸며 무엇을 그대로 두는지 | “납기만 다시 비교하고 설치비 제외는 유지”는 비교 항목 변경과 제외 기준 유지. 별도 업무의 취소로 확장하지 않음 |
| **사용자가 지정한 수행자와 수신자** | 사용자가 명시한 Agent 또는 결과를 받을 사람/채널의 식별과 역할 | “그 자료를 만든 Agent에게 맡겨”의 작성 Agent, “민수에게 보내”의 수신자. 지정이 없을 때의 자동 Agent 추천 우열은 평가 밖 |

“조건” 한 단어에 제한사항과 실행 조건을 섞지 않는다. **“설치비 제외”는 비교 기준의 제한사항, “계약서가 있을 때만 실행”은 실행 조건**이다. “결론을 먼저 보여줘”는 결과의 표시 형식이고 “파일을 만든 다음 발송”은 실행 순서다. 한 문장이 여러 항목을 동시에 지정할 수 있으며 이 분류를 독립 점수로 합산하지 않는다.

예를 들어 “아까 두 견적을 설치비는 제외하고 비교해줘. 보고서 작성은 계속하고.”의 정답은 다음과 같다.

- 비교 요청: 이전 대화에서 지정한 견적 Q1/Q2를 비교하고, 비교 금액에서 설치비를 제외한다.
- 유지 지시: 현재 작성 중인 보고서의 VIA Task T-report를 식별하고 그 업무를 취소하거나 변경하지 않는다.
- 두 지시의 관계: 보고서 완료를 비교의 선행조건으로 요구하지 않는다. 이 입력에는 실행 순서를 새로 지정한 내용이 없다.

따라서 “다섯 단어에 해당하는 값이 들어 있다”가 아니라 **입력이 요구한 위 의미를 전부 맞혔는가**를 판정한다.

사용자 지정 Agent의 의미 해석은 포함하지만 지정이 없는 경우의 최적 Agent 순위나 도메인 계획은 포함하지 않는다. “보내지 마”의 의미는 포함하되 실제 송신 차단, 접근 권한 강제와 도구 실행 성공은 별도 기능 계약이다. 직접 답변도 요청한 질문, 대상과 형식을 평가하며 답변의 사실 정확성 전체를 QA07에 넣지 않는다.

### 2.2 같은 의미를 판정하는 규칙

- 표현이나 내부 ID가 달라도 같은 의미면 성공이다. 후보 출력을 공통 의미 표현으로 옮기는 adapter와 원본 ID 대응을 먼저 검토한다. adapter가 빠진 조건을 정답에서 보충해서는 안 된다.
- 대상 집합과 순서 없는 제외 집합은 순서와 중복 표기를 무시한다. 작업의 선후 관계, 조건 적용 범위와 입력/출력 역할은 보존한다. 독립 작업은 나열 순서를 바꿔도 된다.
- “설치비를 빼고”와 “설치비 제외” 같은 동의 표현, 단위, 날짜의 허용 정규화는 사전에 정한다. 결과를 보고 특정 대안만 통과하도록 바꾸지 않는다.
- 새로운 작업, 대상, 필수 조건이나 금지를 추가로 확정하면 실패다. 설명 문구와 trace ID처럼 의미를 바꾸지 않는 부가 정보는 무시한다. 특정 도구나 Component 이름을 정답으로 요구하지 않는다.
- 비교용 object의 key 순서는 무관하다. 누락, `null`, `false`, 숫자 `0`은 서로 다르며 number의 `1`과 `1.0`은 같다. 문자열은 허용한 정규화 외에는 대소문자를 구분한다. 등록되지 않은 배열은 임의 정렬하지 않는다.
- 자유문장 등 자동 비교 불가 항목은 후보 이름을 가린 두 평가자가 원본과 판정표로 확인한다. 불일치와 조정 이유를 남긴다. 모델 judge 하나의 유사도 점수를 정답으로 대체하지 않는다.

v3의 집합/순서/타입 구별 원칙을 유지하면서 향후 실제 출력의 의미 정규화 절차를 구체화한 제안이다. 기존 v3 object와 정답은 변경하지 않는다.

## 3. 최초 확정과 정정의 경계

### 3.1 무엇을 확정으로 보는가

해당 대안의 채택 책임자가 실제 처리 기준으로 수용한 의미를 관측한다. 의미 commit보다 먼저 확정 내용으로 사용자에게 게시하거나 실행 경로에 넘겼다면 그 앞선 사용을 기록한다. 내부에서 “잠정”이라 이름 붙여도 실제 채택을 감추지 않는다.

| 사건 | QA07에서의 취급 |
| --- | --- |
| 모델이 후보나 문장 일부를 생성 | 잠정 결과. 확정 전 내부 수정은 실패가 아님 |
| “확인 중입니다” 접수 표시 | 전체 의미 확정이 아님 |
| 일부 작업만 먼저 확정하여 안내 | 부분 확정과 시각 보존. 전체 성공을 미리 부여하지 않음 |
| 필수 의미 전체를 처음 확정 | 최초 확정 결과를 정답과 대조 |
| 먼저 확정한 잘못된 부분을 나중에 수정 | 소급 성공 금지. 부분별 최초 채택 이력도 대조 |
| 의미는 맞았으나 이후 인계에서 조건 누락 | QA07 성공 유지. 인계 실패를 별도 보고 |

부분 확정을 지원하면 먼저 올바르게 채택한 부분과 나중에 추가한 의미를 연결하여 전체 완성 시점에 판정한다. 잘못된 확정을 덮어쓴 마지막 snapshot만 보고 성공 처리하지 않는다. 이력이나 전체 확정 경계를 관측할 수 없으면 해당 실행은 미인증이다. 실제 채택 전까지의 추가 조회와 재해석은 허용한다.

### 3.2 revision과 분모

- 한 발화 안의 “이 문단, 아니 저 문단”은 최종 입력 의미 한 건이다. 중간 ASR 전사마다 표본을 만들지 않는다. 입력 도중 실제 잘못 확정한 내용은 조기 확정 오류로 보존하고 이후 정답으로 지우지 않는다.
- 뒤의 새 발화가 이전 요청을 고치면 새 입력/revision의 별도 판정이다. 이전 오류를 유지하고 새 판정에서는 바꾼 부분과 유지 조건을 함께 본다.
- 명확화 답변은 기존 질문에 연결한 별도 입력이다. 앞선 모호한 입력을 나중에 얻은 정보로 소급 채점하지 않는다.
- Agent 진행, 질문, 결과 사건은 문맥과 회귀 입력이며 사용자 입력 분모에 더하지 않는다. 그 질문에 대한 사용자 답은 포함할 수 있다.
- 후속 정정으로 이전 판단이 필요 없어지는 시험은 입력 schedule과 필수 채택 여부를 실행 전에 정한다. 후보가 느려서 채택하지 못했다는 이유로 사후 제외하지 않는다. 완료가 요구되지 않는 중간 판본은 별도 회귀로 사전 등록한다.

## 4. 측정 모집단과 절차

### 4.1 공통 입력에서 도출한 모집단 제안

**현재 공통 평가와 이전 파생 제안을 구별한다.** [v4 공통 계약](../evaluation/common-qa-v4/01-common-contract.md)은 동일한 24입력에 QA01, QA03, QA05, QA06과 QA07을 적용하고, QA02는 그 안의 33지칭 표현, QA04는 연결된 6개 변경 과제를 사용한다. QA07은 24개 정답만 준비됐으며 실제 최초 채택 출력이 없어 미산출이다. 이 24건에 아래 80×5를 합하거나 같은 분모라고 설명하지 않는다.

`QA07-REQ-POP-v1`은 [COMMON-28-v1](../scenarios/common-28-v1/common-scenarios.md)의 **84개 사용자 입력**에서 시작한다. 원전에 모호하다고 표시된 `S06-U02`, `S09-U01`, `S20-U01`, `S26-U05`의 4건은 별도 확인 회귀로 두고 **나머지 80건을 정량 평가 후보**로 제안한다. [평가 계획](qa07-evaluation-plan.md)에 시나리오별 수량과 의미 판정 범위를 기록했다.

**80은 QA01~06이 모두 사용하던 공통 분모가 아니다.** QA01~06의 이전 설계가 공통으로 참조한 것은 28개 시나리오의 원전이며 각 QA의 관측 단위와 수량은 달랐다. 84−4는 이번 QA07 상세화에서 작성자가 새로 도출한 후보 수다. 네 건을 제외했다는 사실만으로 나머지 입력의 모든 의미가 명확하다고 검증된 것은 아니므로 기존 “명확한 입력 80건” 표현을 정정한다. 실제 WAV, 화면, 전달 이력과 전체 정답을 검토해야 실행 가능성과 분모를 확정할 수 있다. 원전 COMMON-28이나 기존 v3를 수정하지 않는다.

이 파생안을 채택한다면 각 에피소드를 같은 초기 상태에서 5회 반복하여 400건을 판정하는 계획이다. 에피소드 안의 후속 입력과 이력은 이어 간다. 5회는 이전 계획의 반복 규격을 빌린 제안이며 현재 v4의 반복 횟수나 실행 결과가 아니다. 언어, Text/Voice와 자료 난이도를 고정하고 한국어 VIA 결과를 영어 연구와 같은 모집단으로 취급하지 않는다.

### 4.2 실행 순서

1. **정답 준비:** 입력/revision, 원본과 알려진 Task 상태, 필수 의미, 허용 표현과 금지된 추가 의미를 원장에 기록한다. 정답과 오답 예를 두 사람이 검토하고 후보 입력에서 분리한다.
2. **동일 조건 고정:** 모델과 버전, 권한, 원본 이력, 입력 시각, 실제 전달 상태, 총 호출/자원 예산과 제한시간을 동일하게 적용한다. 화면 후보나 과거 관계의 정답을 미리 제공하지 않는다.
3. **실제 해석 경로 관측:** 근거 취득, 준비, 조회, 생산, 해석, 확장과 채택을 해당 구조대로 실행한다. 평가자 정답을 후보 출력으로 복사하지 않는다.
4. **최초 채택 수집:** 입력/revision, attempt, 근거 판본, 부분/전체 채택 내용과 시각, UI 게시 및 전달 참조를 남긴다. 이후 정정 이력도 보존한다.
5. **의미 비교:** 동결한 adapter와 규칙으로 비교하고 자동 판정 불가 항목은 익명 검토한다. 원인별 진단은 남기되 부분 점수를 주지 않는다.
6. **전수 집계:** 성공, 오류, 무응답, timeout, 후보 장애와 계측 불능을 구분한다. 모든 예정 입력과 반복을 보고하며 대안 실행 순서를 교차한다.
7. **함께 보고:** 성공 수/N, 반올림 전 일치율, 점수, 시나리오별 오류와 같은 입력의 대안 간 불일치를 제시한다. QA01/03 시간, QA05 비용과 QA06 RAM은 기존 정의로 따로 보고한다.

### 4.3 제한시간과 실패 처리

완료 상한은 **실제 발화 종료 또는 Text 제출 후 30초**로 제안한다. 늦은 ASR 완료나 내부 queue 수신으로 시작을 미루지 않는다. 기존 QA02 상한과 맞춘 시험 규격이며 사용자 반응 목표가 아니다. 첫 부분 안내의 QA01과 전체 의미 확정의 QA07 시각은 구별한다.

| 상황 | 처리 |
| --- | --- |
| §2.1에서 정한 필수 의미 중 하나라도 틀림 | 0. 원인과 최초 잘못된 채택 보존 |
| 명확한 입력을 해석하지 못해 불필요한 확인을 확정 | 0. 평가자가 새 힌트를 주어 성공으로 바꾸지 않음 |
| 기한 내 전체 의미 없음, 모델 오류 또는 후보 crash | 0. 실패도 N에 포함 |
| 원본 접근 불가지만 요청 자체는 명확 | 요청 의미는 평가. 자료를 읽었거나 업무를 끝냈다고 가정하지 않음 |
| 근거로 필수 의미를 정할 수 없는 사전 등록 입력 | 정량 제외. 확인 질문과 잘못된 단정을 기능 회귀로 전수 보고 |
| 시험 장치가 공통 입력을 잘못 전달 | 영향받은 모든 대안의 같은 사례/반복을 무효 처리하고 원인과 재실행 보존 |
| 채택 여부조차 알 수 없는 계측 누락 | `UNOBSERVABLE`. 후보의 0점/성공으로 변환하지 않으며 전체 점수 확정 불가 |

중단되어 미실행한 입력을 제거해 완주 결과를 만들지 않는다. 예정 분모, 관측 성공/실패와 미확인 건수를 함께 보고한다. 관측분 비율은 부분 결과로만 표시한다. 시간과 비용에는 정확도 벌점을 더하지 않고 실제 관측값을 보존한다.

timeout 감소로 일치율이 높아진 경우와, 기한 안에 채택한 의미의 오류가 줄어든 경우를 원인별로 구별한다. 둘 다 전체 지표에 포함되지만 전자를 의미 모델 자체의 이해 능력 향상이라고 설명하지 않는다. 입력 의미는 명확하지만 별도 접근 동의나 실행 승인이 필요한 정상 질문은 불필요한 명확화 오류가 아니다.

## 5. 목표 90%의 근거와 한계

### 5.1 참조한 기술 과제

**TreeDST는 Tree-based Dialog State Tracking의 약자로, 대화가 이어질 때마다 사용자의 현재 요청을 구조화된 의미로 기록하고 이를 예측하도록 만든 데이터셋**이다. Apple 연구진의 [EMNLP 2020 논문](https://aclanthology.org/2020.emnlp-main.651/)과 [공식 저장소](https://github.com/apple-aiml-research/ml-tree-dst)에 공개되어 있다. 10개 영역의 27,280개 대화에 사용자 대화 상태와 시스템 응답 행위의 정답을 붙였다. 컴퓨터가 만든 대화 흐름을 사람이 자연스럽게 표현한 자료이며 Siri 실사용 대화 로그가 아니다.

설명용 예로 “내일 3시에 민수와 회의 잡아줘” 다음에 “4시로 바꿔”라고 하면, 기존 일정 생성 요청의 시간을 4시로 바꾸면서 날짜와 참석자는 유지하는 의미를 예측하는 종류의 평가다. 이 예문은 이해를 돕기 위한 한국어 예시이며 데이터셋 원문 인용은 아니다. TreeDST는 모델 이름이나 VIA 시험 입력 목록이 아니다.

[Zhou 등, ACL 2022, §5와 Table 1](https://aclanthology.org/2022.acl-long.110.pdf)은 문맥을 사용하는 대화 발화를 의미 프로그램으로 해석하고 전체 exact match를 보고한다. FULLTOGRAPH의 validation 정확도는 **TreeDST 90.8%, SMCalFlow 80.7%**다. [공식 코드의 checkpoint 표](https://github.com/microsoft/online-semantic-parsing-for-latency-reduction)에서도 확인된다. 전체 발화를 받은 offline parser 수치이며 조기 실행 정확도나 VIA 실측이 아니다.

요청 구조 전체를 판정한다는 점에서 지칭 집합이나 intent 분류 단독 정확도보다 직접적인 참조다. 다만 프로그램 구조 일치와 VIA의 의미 동등성은 동일 시험이 아니다. 연구의 한 턴 문맥은 VIA의 화면 취득, 한국어 음성, 여러 Task의 수정과 장기 이력 전체를 검증하지 않는다.

### 5.2 외부 사실에서 VIA 목표로 옮기는 판단

| 단계 | 근거 또는 판단 |
| --- | --- |
| 사용자 요구 | 요청한 처리, 처리 대상과 적용 범위, 제한사항과 이전 요청/응답 또는 Task와의 연결까지 올바르게 이해 |
| 지표 선택 | 입력별 전체 충족이라는 사용자 정의. 항목 평균이나 Agent 성공률로 대체하지 않음 |
| 기술 참조 | 문맥 기반 전체 의미 해석에서 TreeDST 90.8%라는 공개 결과 |
| 작성자 제안 | 약 90% 수준을 초기 개발 목표로 사용. **정수 백분율로 내림하여 90%** 제안. 완화 폭 0.8%p |
| 근거 한계 | 내림과 허용 폭의 외부 사용성 근거는 없음. VIA의 추가 난이도를 0.8%p로 보정한 계산도 아님 |
| 자체 확인 | 동결한 VIA 입력과 최초 확정 결과로 목표 확인. 적용 자료가 바뀌면 비교 가능성 재검토 |

**90%는 관련 기술 수준을 참고한 초기 개발 목표이며 보편적 사용자 허용 오류율이 아니다.** 같은 연구의 SMCalFlow 80.7%도 함께 공개하여 과제와 표현에 따른 차이를 드러낸다. 두 값을 평균내거나 높은 값만으로 VIA의 달성을 단정하지 않는다. 최신 최고 성능을 조사해 확정했다는 주장도 아니다.

90.8%를 그대로 목표로 둘 수도 있으나 VIA 독립 데이터와 사용자 오류 허용 연구가 없는 상태에서 소수점 한 자리의 요구 정밀도가 정당화되지는 않는다. 이번에는 정수 목표 90%를 제안한다. 95%나 99%를 필수 목표로 정할 직접 근거는 확보하지 못했다. 더 높은 사용자 요구나 자체 증거가 생기면 이유와 새 판본을 남겨 모든 대안에 동일하게 개정한다. 낮은 실측값이 나왔다는 이유만으로 목표를 낮추지는 않는다.

### 5.3 전용하지 않은 수치와 통계 해석

- QA02의 ReALM 93%는 지칭 집합이므로 복사하지 않는다. 항목별 정답률을 곱해 전체 정확도를 만들지 않는다. 오류 독립성의 근거가 없다.
- [Desai와 Aly, Findings ACL 2021, Table 3](https://aclanthology.org/2021.findings-acl.5.pdf)의 TOPv2 test exact match는 **87.52%**다. 같은 논문의 confidence estimator F1은 의미 해석 exact match와 다르다. 과제 차이를 확인하는 자료이며 90%의 산술 도출식이 아니다.
- 360/400 성공은 해당 시험의 90%다. [NIST TN 2045](https://www.nist.gov/publications/confirming-performance-threshold-binary-experimental-response)에 따른 모집단 성능 보장은 별도의 표본 수와 수용 기준 설계가 필요하다.
- 후속 입력과 5회 반복은 서로 관련된다. 400개를 독립 시행으로 가정한 좁은 신뢰구간을 제시하지 않는다. 제품 일반화에는 독립 에피소드 표집과 별도 수용 계획이 필요하다.

출처 위치, 수치와 원문 조건, 적용 판단은 [조사 기록](research-notes/qa07-meaning-research.md)에 남겼다.

## 6. 0~6점 제안 — `QA07-REQ-score-v1`

90%부터 100%까지를 **2%p의 다섯 구간과 오류 없는 최고 등급**으로 나눈다. 중간 점수는 표시 규칙이며 논문이 2%p마다 같은 사용자 가치 차이를 검증한 것이 아니다.

| 점수 | 원형 표시 | 일치율 a의 범위 | 400판정에서 성공 수 | 의미 |
| ---: | --- | --- | --- | --- |
| 0 | ○○○ | 0% ≤ a < 90% | 0~359 | 목표 미달 |
| 1 | ◐○○ | 90% ≤ a < 92% | 360~367 | 목표 충족 |
| 2 | ●○○ | 92% ≤ a < 94% | 368~375 | 오류 감소 |
| 3 | ●◐○ | 94% ≤ a < 96% | 376~383 | 오류 감소 |
| 4 | ●●○ | 96% ≤ a < 98% | 384~391 | 오류 감소 |
| 5 | ●●◐ | 98% ≤ a < 100% | 392~399 | 오류 감소 |
| 6 | ●●● | a = 100% | 400 | 평가 표본에서 오류 없음 |

반올림 전 원값으로 채점한다. 367/400=91.75%는 표시를 92%로 반올림해도 1점이다. N이 달라져도 같은 비율 구간을 사용하되 모집단 판본을 밝히고 다른 모집단과 직접 순위 비교하지 않는다. 미측정, 계측 불능, 비적용은 0점이 아니다. 가중 총점이나 새 우선순위를 도입하지 않는다.

| 견적 A/B 비교, 설치비 제외, 보고서 유지까지 맞음 | 성공 | 성공 | 전체 일치 |
| A/B는 맞지만 설치비 제외 누락 | 성공 | 실패 | 조건 오류 |
| A/B는 맞지만 보고서도 취소 | 성공 | 실패 | 기존 업무 관계 오류 |
| A/C를 비교 대상으로 채택 | 실패 | 실패 | 같은 대상 오류가 두 지표에 반영 |
| 대상을 맞췄지만 비교 대신 각각 요약 | 성공 | 실패 | 작업 오류 |
| 만든 다음 이름 변경할 일을 역순으로 해석 | 대상이 맞으면 성공 | 실패 | 순서 오류 |
| 처음 의미는 맞았지만 인계에서 조건 누락 | 성공 | 성공 유지 | 인계 실패를 별도로 보고 |
| 처음 조건 누락 확정 후 자기 수정으로 복구 | 대상이 맞으면 성공 | 실패 유지 | 최초 실패를 소급하지 않음 |
| 실제 모호한 “응”에 질문 대상 확인 | 사전 제외 | 사전 제외 | 확인 회귀의 성공이며 정량 성공을 추가하지 않음 |

QA02는 표현/revision, QA07은 입력/revision이 분모다. 한 입력에 지칭 두 개와 독립 조건 세 개가 있을 수 있다. 같은 대상 오류를 두 독립 개선 효과로 합산하거나 비율을 곱하지 않는다. 목표 숫자만 보고 어느 쪽이 더 쉬운 요구라고 단정할 수 없다.

## 8. 현재 네 DP와 예상 차이

아래는 구조와 관측 경로의 검토이며 새로운 A/B 선택이나 실측 우열이 아니다. DP별로 다른 정확도 지표를 만들지 않는다.

| DP | QA07을 바꿀 수 있는 경로와 양방향 가설 | 현 단계 판단과 반증 조건 |
| --- | --- | --- |
| [DP2 의미 해석 실행](../dp02/design.md) | 대화 실행 A의 문맥 연속성은 유지 조건 누락을 줄일 수 있음. 공통/요청별 실행 B는 업무 혼입을 줄일 수 있지만 분리와 재결합에서 조건 누락 가능 | 직접 평가 경로 있음, 우열 미확정. 최초 의미가 같으면 정확도 차이 가설은 성립하지 않음 |
| [DP3 화면/음성 지칭](../dp03/cpu-runtime-architecture.md) | 원본 해석 A와 시각 후보 생산/결합 B-R1/R2/R3가 대상, 역할과 제외의 최종 의미에 영향. 전문 후보가 누락을 줄일 수 있으나 A도 원본 보완 가능 | QA02와 겹친 오류를 별도 설명. 배치 차이만으로 우위가 생기지 않으며 원본 보완 후 같은 의미면 동점 |
| [DP5 위임용 메모리](../dp05/design.md) | A는 현재 의도에 필요한 관계를 해석, B는 사전 관계를 적용하고 원본 보완. A의 검색 누락과 B의 관계 오류/노후화, B의 반복 관계 재사용이 서로 다른 경로 | 직접 평가 경로 있음, 우열 미확정. 공급 자료만 평가하지 않고 최종 의미까지 확인. 보완 후 같으면 정확도 차이 없음 |
| [DP44 음성 실행/전달](../dp44/design.md) | 최초 의미 이후 음성 준비 수명은 기본적으로 QA07 밖. 실제 들은 내용이 후속 입력의 의미 문맥이 되는 경로는 별도 | 고정 정답 Delivery fixture는 차별화 근거 아님. 실제 전달 이력을 사용하는 후속 해석이 달라지는 경우에만 검증 가능 |

관련 입력은 공통 목록에서 구조의 영향 경로로 먼저 정하여 모든 대안에 동일하게 적용한다. coverage를 채우려고 동점을 차이로 바꾸지 않는다. 기본안과 tactic을 구별하고 QA01/03의 속도 개선을 정확도 향상으로 대신 설명하지 않는다.

## 9. 최소 검증과 남은 준비

| 단계 | 수행할 내용 | 주장 범위 |
| --- | --- | --- |
| 판정기 확인 | 동의 표현, 제외/순서/역할 오류, 최초 오답 후 정정, timeout의 고정 출력 대조 | 규칙과 adapter의 정합성. 모델 정확도 아님 |
| 실제 모델 PoC | 관련 DP의 실제 근거 취득부터 최초 의미 채택까지 같은 입력과 예산으로 실행 | 지정 모델과 fixture 및 proxy 경계의 결과 |
| 공통 회귀 | 80입력과 확인 필요 4입력, 각 5회 및 별도 필수 기능 변형 | 대표 묶음의 정확도와 실패 |
| 제품 검증 | 실제 화면/음성/전달 이력, 독립 사용 사례와 장치 환경 | 해당 표집과 제품 경로의 근거 |

아직 준비할 것은 입력별 전체 의미 oracle, 원본 WAV/화면과 전달 이력의 검증, 대안별 채택 adapter와 실행 manifest다. 이번 작업은 평가 설계를 문서화한 것으로 모델 실행이나 실제 측정을 수행하지 않았다. 기존 결과를 새 목표로 사후 채점하지 않는다. 정적 문서 검사 통과는 정확도 검증이 아니다.

## 11. 검토 질문과 답변

| 질문 | 답변 |
| --- | --- |
| 왜 QA02 외에 필요한가 | 대상이 맞아도 작업, 조건, 순서와 업무 연결이 틀릴 수 있다. 대상 오류 중복은 인정한다. |
| 왜 90%인가 | 공개된 문맥 기반 전체 해석 90.8%를 참조한 초기 목표다. 정수 내림은 작성자 판단이며 사용자 오류 허용 연구의 결론이 아니다. |
| 더 어려운 연구 결과는 왜 함께 제시하는가 | SMCalFlow 80.7%와 TOPv2 87.52%는 과제에 따른 차이와 VIA 달성 가능성의 불확실성을 보여 준다. |
| 조건이 많으면 불리하지 않은가 | 완전 일치가 어려워진다. 복합성별 진단을 공개하되 항목 평균으로 바꾸지 않는다. |
| 질문해서 정답을 얻으면 성공인가 | 정보가 부족한 입력은 별도 회귀다. 명확한 입력에 새 힌트를 주어 최초 오류를 복구하지 않는다. |
| 400건이면 충분한가 | 기능 목록과 반복 규격에서 나온 수이며 독립 표본 크기나 제품 성능 보장이 아니다. |
| 오해했지만 Agent가 올바르게 처리하면 성공인가 | 최초 의미 확정 실패를 유지한다. Downstream 복구를 소급하여 더하지 않는다. |
| 기존 합성값에 점수를 바로 붙이는가 | 아니다. 새 평가의 모집단과 실제 관측 조건을 충족해야 한다. |
