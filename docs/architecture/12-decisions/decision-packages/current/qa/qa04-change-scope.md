## 1. 정의와 대표 지표

**VIA의 기능·정책이나 외부 연동 형식을 변경할 때, 해당 변경을 완료하기 위해 수정해야 하는 운영 소프트웨어 모듈의 범위를 최소화해야 한다.**

쉽게 설명하면 **“같은 기능을 바꾸는 데 제품 코드의 몇 개 모듈을 손봐야 하는가?”**다. 구현 언어, 그림의 상자 수, 담당자 수로 의미를 바꾸지 않는다.

| 항목 | 현재 규격 |
| --- | --- |
| 요구사항명 | 기능 및 연동 변경의 파급 범위 |
| 대표 숫자 | **변경 과제당 평균 변경 운영 모듈 수 X**, 개/과제 |
| 변경 대상 | Q4-C01~Q4-C08 여덟 과제. 데이터 형식 변경 2개와 기능/정책 확장 6개 |
| 집계 범위 | 제품에 포함되어 직접 관리하는 Rust, Python 등 모든 언어의 운영 모듈. 해당 모듈 소유 prompt/schema/config와 필요한 이관 코드 포함 |
| 시작 기준 | 변경 전 코드·의존성·모듈 목록과 동작을 고정한 기준 버전 |
| 종료 기준 | 변경 후 수용 조건과 기존 기능 회귀가 충족된 최종 patch |
| 목표 | **평균 3개 이하 제안 유지**. ARGO 근거와 새 언어/모집단의 비교 가능성은 실행 전에 확인 |
| 점수 | 기존 수치 경계 유지, 새 적용 판본 CHG-v4. 검증된 새 평균에만 적용 |
| 본문 | 전체 평균 X 하나와 목표/점수 및 근거 상태 |
| 부록 | 과제별 수정 모듈, 직접 수정 이유, 기존/신규 구분, 계약·상태 이관, 회귀 결과 |

이번 구체화는 변경 시험의 요구를 정한다. 아래 기능을 현재 제품의 필수 기능으로 새로 채택하거나 실제 구현을 시작한 것이 아니다. 어떤 방안이 이미 변경 후 동작을 지원한다면 증거를 확인해 0개로 기록한다. 없는 기능을 있다고 가정하거나 필요한 기능의 결함 수정을 새 확장 비용으로 세지 않는다.

## 2. 어떤 변경을 평가하는가

아래 표는 직관적인 요약이며 정확한 입력, 전후 조건과 제외 범위는 [변경 과제 정본](change-scenarios.md)에 있다.

| ID | 변경 대상 | 변경 전 → 변경 후 | 바뀌지 않아야 하는 것 |
| --- | --- | --- | --- |
| Q4-C01 | 모델이 주고받는 데이터 형식 | 기존 요청/응답/사용량 형식 → 필드 이름·중첩 구조가 다른 동등한 형식 | 요청 의미, 응답 내용, 취소 결과, 사용량 |
| Q4-C02 | Agent가 주고받는 데이터 형식 | 기존 요청/취소/접수 형식 → 필드 이름·중첩 구조가 다른 동등한 형식 | 업무 ID, 실제 접수/취소 상태, 중복 방지 |
| Q4-C03 | 화면에서 차트 관계 읽기 | 대상만 가리킴 → 범례가 가리키는 계열과 해당 그래프 범위까지 연결 | 기존 표·버튼·문단 지칭 |
| Q4-C04 | 요청별 임시 자료 보관 | 공통 보관 규칙 → 요청별로 종료 시 폐기 또는 제한 시간 동안 재사용 | 다른 유효 요청의 자료, 최소 상태 기록과 전달 이력 |
| Q4-C05 | 기억한 선호의 적용 기한 | 변경/삭제 전까지 적용 → 지정 기한까지만 적용 | 기한 없는 선호, 기한 이전 정상 적용 |
| Q4-C06 | 응답 일부 수정 | 응답 전체 교체 → 지정 문단과 그 문단의 대기 음성만 교체 | 다른 문단, 다른 업무와 이미 전달한 사실 |
| Q4-C07 | 선택 문장 다시 읽기 | 응답 단위 읽기/중단 후 계속 읽기 → 선택한 문장만 다시 읽고 기존 위치로 복귀 | 원래 읽기 진행 위치, 내용 판본과 접근권한 |
| Q4-C08 | 정보 일부 사용 철회 | 자료 전체 사용 철회 → 지정 구간만 사용 철회 | 나머지 허용 구간과 무관한 자료의 사용 |

Q4-C01/02는 어댑터에서 끝날 수 있는 대조 과제다. 동점이어도 제거하지 않는다. 나머지 과제는 상태·판본·처리 수명과 데이터 관계의 변경을 확인한다. 수정 모듈 수를 먼저 정하지 않으며 DP별 예상 우위도 미리 부여하지 않는다.

## 3. 운영 모듈 집계

<a id="3-rust-모듈을-어떻게-세는가"></a>
Rust에 한정했던 이전 규칙을 운영 코드 전체로 확장한다. **소스·공개 경계·상태 소유에 대응하는 실제 모듈**을 세며 책임 상자를 임의로 가상 분할하지 않는다.

| 대상 | 고유 ID와 집계 |
| --- | --- |
| Rust | package / crate-target / 정규 모듈 경로. 파일 수와 구별 |
| Python | 배포 패키지 / 정규 import 모듈 경로. 패키지 초기화 코드도 실제 수정될 때 포함 |
| 그 밖의 언어/독립 실행 코드 | 실제 소스 단위와 외부 경계에 대응하는 모듈 ID를 사전 등록 |
| prompt/schema/config/모델 manifest | 사전 등록한 운영 소유 모듈 1개. 소비자가 실제 수정되면 그 모듈도 포함 |
| 의존성/build/배포 설정 | 소유 root 또는 build/배포 모듈을 사전 등록하고 실제 수정 시 포함 |
| 자동 생성 코드 | 수정한 원본 schema/generator 소유 모듈을 포함. 결정적 재생성만으로 수를 늘리지 않되 수동 수정 어댑터는 포함 |
| 테스트/주석/포맷만 변경 | 운영 모듈 수에서는 제외. 필수 회귀는 완료 조건이고 테스트 변경 내역은 부록 |
| 외부 라이브러리/모델 가중치 | 사용한다는 이유만으로 외부 내부 모듈을 세지 않음. 변경한 제품 측 adapter/설정/manifest는 포함. 모델 학습은 범위 밖 |

각 모듈의 소스, 공개 함수/자료형, 상태, 의존성과 자산 소유를 registry로 고정한다. 부모가 실제 수정되지 않으면 자식 변경만으로 부모를 추가하지 않는다. 같은 모듈에서 함수 여러 개를 고쳐도 한 번이다. 필요한 신규/삭제 모듈도 한 개씩 포함하고 기존 수정과 별도 열로 설명한다. 단순 이동은 전후 ID를 연결해 한 모듈로 센다. 실질 분할/병합은 실제 변경 모듈 집합을 기록한다.

양안의 분해 수준을 검토하되 억지로 같은 개수로 맞추지 않는다. 평가용 거대 모듈 합치기, 얇은 모듈 쪼개기, 변경을 외부 스크립트나 prompt로 숨기기를 허용하지 않는다. 운영 모듈 수는 개발 공수나 충돌 수의 직접 측정값이 아니다.

## 4. 평균과 공통 모집단

```text
M_i = Q4-Ci를 완료하기 위해 수정/추가/삭제한 고유 운영 모듈 집합
X = (|M_1| + |M_2| + ... + |M_8|) / 8
```

모든 비교 구성에 같은 여덟 요구를 적용한다. DP 하나만 바꾸고 나머지 기반은 동일하게 둔다. 직접 관련 없는 과제도 공통 제품 평균에는 유지하며, 결과를 보고 유리한 과제만 선택하지 않는다. 관련 경로별 내역은 부록에서 설명하고 별도 대표 점수로 만들지 않는다.

각 변경은 같은 변경 전 버전에서 독립 수행한다. Q4-C01의 변경을 다음 과제의 준비물로 누적하지 않는다. 같은 모듈이 서로 다른 두 과제에서 바뀌면 각 과제에서 한 번씩 센다. 이미 지원하는 기능은 수용 시험으로 입증한 뒤 0개로 기록한다. 미완료/미구현/미관측을 0개로 처리하지 않는다.

여덟 과제 중 하나라도 완료 조건이나 증거가 없으면 전체 X와 점수를 확정하지 않는다. 관측된 부분 집합과 미완료 이유를 남긴다. 새 범위의 구현 patch 없이 작성한 수는 DESIGN_CHANGE_REVIEW이며, 실제 patch와 회귀 결과가 있는 경우만 IMPLEMENTED_CHANGE_REVIEW다.

## 5. 목표와 출처

사용자가 제공한 ARGO 기능 추가/형식 변경 PR 145건의 평균 5.4개에서 40% 감소하면 3.24개다. 이를 더 엄격한 평균 3개 목표로 정했던 [목표 도출](targets-source-qa04-argo.md)을 유지한다.

현재 확장은 Rust뿐 아니라 제품의 모든 언어를 포함하고 변경 과제를 여덟 개로 바꾼다. **3개는 목표 제안으로 유지하며, 새 단위의 측정 결과로 ARGO 대비 44.4% 개선을 자동 주장하지 않는다.** 실제 비교에는 원자료의 모듈 정의와 PR/독립 변경 단위, 변경 유형의 동등성을 확인해야 한다. 이전 여섯 과제 평균은 새 여덟 과제 평균이 아니다.

SEI의 [Modifiability Tactics](https://www.sei.cmu.edu/library/modifiability-tactics/)는 결합도·응집도와 변경 비용의 관계를 설명한다. 이 자료에서 3개 또는 특정 DP 우위를 도출하지 않는다. [기존 조사](research-notes/qa04-change-research.md)는 당시의 Rust/여섯 과제 범위로 읽는다.

## 6. 0~6점 — CHG-v4

목표 3개와 우수선 1개 사이를 0.4개씩 나눈 수치 경계는 유지한다. 적용 모집단과 언어 범위가 바뀌어 판본을 분리했다. 미측정과 미완료에는 점수를 부여하지 않는다.

| 점수 | 원형 표시 | 평균 변경 모듈 수 x |
| ---: | --- | --- |
| 0 | ○○○ | x > 3 |
| 1 | ◐○○ | 2.6 < x ≤ 3 |
| 2 | ●○○ | 2.2 < x ≤ 2.6 |
| 3 | ●◐○ | 1.8 < x ≤ 2.2 |
| 4 | ●●○ | 1.4 < x ≤ 1.8 |
| 5 | ●●◐ | 1 < x ≤ 1.4 |
| 6 | ●●● | 0 ≤ x ≤ 1 |

반올림 전 평균에 적용한다. 한 과제의 모듈 1개 차이는 전체 평균 1/8개 차이다. 별점 차이가 나도록 구간이나 분모를 바꾸지 않는다.

## 7. 측정 절차와 이관

1. 여덟 과제 각각의 변경 전후 동작을 baseline에서 확인하고 공통 수용 fixture를 확정한다.
2. 후보별 모듈/자산 소유표와 동일 build/feature 조건을 고정한다.
3. 각 과제를 독립 patch로 완성하고 해당 수용 시험과 기존 기능 회귀를 수행한다.
4. 실제 변경 모듈과 각 수정 이유, 신규/삭제, 계약·상태 이관 및 검증 증거를 대조한다.
5. 여덟 과제의 집계가 완비된 경우 대표 평균 X 하나를 보고하고 세부는 부록으로 제공한다.

현재는 정의와 변경 대상의 구체화 완료이며 실제 patch/측정은 없다. 공통 평가 v3~v6의 기존 C01~C06 및 concept:: 값은 보존한다. 수치 담당은 새 ID에 사례를 매핑하고 실제 근거 상태를 구별해야 하며 기존 평균/별점을 이름만 바꿔 복사하지 않는다.
