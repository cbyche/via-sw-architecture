## 1. 제안과 판정

**응답 내용을 채택한 뒤 사용자가 들을 수 있는 시간 동안 음성 요약이 얼마나 더 늦어지는지 평가한다.** 사용자 발화와 이미 재생 중인 응답 때문에 말할 수 없는 시간은 원시 대기에 남기되 이 추가 지연에서 제외한다. UI 표시나 음성 준비 완료를 기다린 뒤 시계를 시작하지 않는다.

필요한 품질이지만 현행 네 DP의 두 안은 같은 음성 준비, 현재성 확인, 실제 재생 경계를 사용한다. **현재는 필수 회귀 검증으로 두고 핵심 trade-off 커버리지에 세지 않는다.** 음성 경로의 공통 성능을 DP-44 B의 독점 이익으로 붙이지 않는다.

| 항목 | 명세 |
| --- | --- |
| 이름 | **음성 전달 지연** |
| 한 문장 정의 | 올바른 응답 내용이 채택된 뒤 음성을 전달할 수 있는 시간 중 해당 요약이 실제로 시작될 때까지 누적된 대기 |
| 단일 지표 | **평균 음성 전달 지연(ms)** |
| 평가 단위 | 음성 요약이 필요한 사전 지정 Response 1개 |
| 좋은 방향 | 작을수록 좋음 |
| 목표 제안 | **500ms 이하** |
| 핵심 사용자 가치 | 화면에 답을 남긴 뒤 말할 수 있을 때 음성 대화도 이어감 |
| 현재 권고 | QA1의 텍스트 종료점을 보완하는 필수 회귀 검증 |

## 2. 재생 가능 시간을 먼저 정의한다

평가자가 다음 조건을 만족하는 시간 구간을 `eligible`로 기록한다.

1. Voice 기능과 장치가 사용 가능하다.
2. 사용자가 말하는 중이 아니다.
3. 공통 차례 규칙에서 앞서 전달할 기존 응답이 끝났다.
4. 해당 Response가 철회, 대체되지 않았고 현재 권한에서 전달할 수 있다.

모델 호출 중, TTS 미완료, 내부 queue 대기, 여유 worker 없음 또는 후보의 준비 미완료는 재생 불가능한 외부 조건이 아니다. **그 시간은 eligible 대기로 센다.** 후보가 `준비 안 됨`이라는 상태를 붙여 지연을 없앨 수 없게 한다.

eligible 판정은 후보가 보고한 ready flag가 아니라 evaluator의 공통 발화, 차례, revision, 권한 원장으로 결정한다. 권한은 실제로 유효하지만 후보의 재확인이 늦은 시간도 포함한다. 실제 권한 철회는 분모의 해당 응답을 임의 삭제하는 이유가 아니라 사전에 정한 취소 oracle로 판정한다.

사용자 발화 schedule, 이미 진행하던 응답의 실제 음성 fixture와 차례 정책은 양안에 같다. 한쪽이 이전 요약을 길게 만들어 다음 응답의 제외 시간을 늘리지 않도록 전달 의미와 허용 요약 범위도 같게 둔다. 예비 PoC에서는 고정된 이전 음성 클립으로 이를 검증한다.

## 3. 산식과 사건 경계

```text
t_adopted(i) = 실제 출력할 첫 올바른 응답 내용과 source revision이 채택된 시점
t_audio(i) = 같은 Response 요약의 첫 내용 음성이 실제 출력된 시점
eligible(t) = 앞 절의 공통 조건을 만족하면 1, 아니면 0
D(i) = ∫[t_adopted(i), t_audio(i)] eligible(t) dt
QA09 = Σ D(i) / 음성 전달이 필요한 사전 지정 Response 수
```

첫 음성의 내용이 대상, 상태, 결론에 맞는지 전체 요약으로 판정한다. 알림음, filler, 무음 packet, 첫 PCM buffer 생성 또는 playback queue 삽입은 음성 시작이 아니다. 실제 Windows 출력에서 들리는 의미 있는 음성의 첫 sample을 관측한다.

`t_adopted`는 처리할 의도만 막연히 정한 시각이 아니라 실제로 안내할 답변, 대상, 상태, source revision이 채택된 시각이다. 첫 내용 단위가 먼저 정해지면 상세 전체가 완성될 때까지 늦추지 않는다. 음성 요약 문장이나 PCM이 준비된 시각도 아니다. 요약과 TTS 준비가 늦은 시간을 포함한다. 실제 텍스트 표시 시각은 별도로 보존하며 UI가 늦다고 음성 지연이 짧아지지 않는다.

**한 번의 `max(t_adopted, t_first_eligible)`만 빼는 산식은 쓰지 않는다.** 준비 중 사용자가 다시 말하면 여러 개의 eligible 구간이 생길 수 있기 때문이다. 제외 구간의 합집합과 실제 시작까지의 누적 가능한 시간을 계산한다. 겹친 제외 구간을 두 번 빼지 않는다.

이 QA는 최초 입력부터 실제 청취까지의 총 대기를 대표하지 않는다. 다음 원값을 함께 보존한다.

- 입력 또는 Agent 사건부터 실제 음성 시작까지의 전체 wall time
- 응답 내용 채택 이후 사용자 발화 대기와 이전 응답 차례 대기
- 요약 준비 완료, 첫 PCM 준비, 실제 audio onset
- 재생 중단과 최종 실제 전달 구간

## 4. 평가 모집단과 의미 판정

[COMMON-28-v1](../scenarios/common-28-v1/common-scenarios.md)의 **의무 음성 요약 109건 × 5회 = 545개 전달 지연**을 사용한다. 직접 응답과 수행 안내 및 Agent 질문과 결과 및 정정과 재연결을 같은 목록에서 관측한다. 별도 여섯 사례와 20회 반복안은 폐기했다.

120개 지정 응답 중 Voice OFF의 4건과 진행 UI 표시 7건은 공통 출력 정책상 음성 의무가 없으므로 사전에 제외한다. JSON에 응답마다 `voice_required`와 제외 이유를 기록했다. 후보가 느린 응답을 사후에 취소해 분모를 줄일 수 없다.

S20의 복수 질문과 S21의 고정 이전 음성 중단 및 S23의 다른 응답 중 결과 도착과 S24의 Voice 전환에서 재생 가능한 구간을 확인한다. 입력과 고정 이전 클립 및 Task와 요약의 의미 범위는 양안 동일하다. 준비 완료와 재생 차례를 혼동하지 않고 공통 발화/차례 원장으로 eligible을 산출한다.

## 5. 목표와 명확한 근거

**평균 500ms 이하**를 음성 전달 추가 예산으로 제안한다.

| 세부 설계 예산 | 제안 |
| --- | ---: |
| 이미 채택된 응답에서 짧은 요약을 준비하는 추가 시간 | 200ms |
| 같은 요약의 첫 음성 chunk 준비 | 200ms |
| 현재성 확인, 출력 queue, 장치의 실제 재생 시작 | 100ms |
| 합계 | **500ms** |

이 분해는 직렬 상한 배분을 이용한 **설계 예산**이다. 실제 streaming과 중첩 작업은 종료점을 당길 수 있지만 시간을 더해 실측값을 만들지는 않는다. 모델이나 네트워크가 200ms를 만족한다는 측정 증거가 있다는 뜻도 아니다. 목표를 제시하고 실제 가능한지 후속 PoC에서 확인한다.

| 출처 | 확인한 사실 | 수치 도출에 사용할 범위 |
| --- | --- | --- |
| [Microsoft — Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio) | application buffer 이후 audio engine, driver, hardware를 거쳐 실제 출력되며 장치가 지원하는 buffer 크기가 다름 | PCM 준비와 실제 들리는 시작을 구별하는 근거. 모든 Windows PC에서 100ms를 보장하는 출처는 아님 |
| [기존 실제 사건 경계 계약](../../../../11-measurement/event-boundary-contract.md) | 실제 audible sample과 software enqueue를 구별하고 UI/audio proxy 범위를 명시 | 관측 원칙 재사용. 기존 음성 QA의 집계와 목표를 그대로 계승하지 않음 |
| [출력 방식 사용자 합의](../../03-03-qa-dp-evaluation-plan.md) | 상세 텍스트와 요약 음성을 제공하며 음성은 들을 수 있을 때 전달 | eligible 대기를 별도로 볼 요구 근거 |

출처 확인일은 2026-10-14다. **500ms를 사람이 자연스러운 대화로 느끼는 보편적 임계값이라고 설명하지 않는다.** 응답 내용 채택 이후의 음성 추가 대기를 관리하는 제품 예산 제안이다. 짧은 이름은 유지하되 발표 정의에서 재생 불가능 구간을 제외한다고 반드시 밝힌다.

## 6. 0~6점 구간

`x`는 반올림 전 평균 음성 전달 지연이다. 목표 충족은 1점 이상이다.

| 점수 | 표시 | 구간 |
| ---: | --- | --- |
| 0 | ○○○ | `x > 500ms` |
| 1 | ◐○○ | `400 < x ≤ 500ms` |
| 2 | ●○○ | `300 < x ≤ 400ms` |
| 3 | ●◐○ | `200 < x ≤ 300ms` |
| 4 | ●●○ | `150 < x ≤ 200ms` |
| 5 | ●●◐ | `100 < x ≤ 150ms` |
| 6 | ●●● | `0 ≤ x ≤ 100ms` |

500ms는 전체 추가 예산, 100ms는 이미 준비된 요약에서 출력 경로 예산만 남은 우수 수준이다. 중간 경계는 개선 여유를 나타내는 설계 등급이다. 음성 생성이 텍스트 준비와 겹치면 최상위 구간에 들어갈 수 있으며, 아직 생성되지 않은 음성을 준비됐다고 가정해서는 안 된다.

음성 미전달은 사전에 정한 eligible 누적 관측 제한 **5초**에 도달하면 해당 필수 응답의 판정값을 `+∞`로 두며 전체 QA09의 점수는 **0점**이다. 실제 무한 시간을 관측했다는 뜻이 아니라 필수 음성을 전달하지 못한 실행의 실패 판정이다. 5,000ms라는 작은 유한값으로 잘라 여러 빠른 사례와 평균내지 않는다. 원시 기록에는 실제 관측 종료, eligible 누적 시간과 `AUDIO_NOT_DELIVERED`를 남긴다. 미전달을 분모에서 제거하지 않는다.

잘못된 요약이 먼저 나왔다면 오류 기록을 남기고 올바른 요약 시작까지 측정한다. 뒤에 고쳤어도 이미 전달한 잘못된 상태나 대상은 회귀 위반으로 남는다. 유한 지연 원값이 있어도 필수 의미 조건을 어긴 실행은 성공 점수로 인정하지 않는다.

장치 자체를 관측하지 못한 실행은 `관측 불능`이며 0점이나 성공으로 바꾸지 않는다. 시험 환경에서 eligible 구간이 충분하지 않았던 경우는 환경 미충족으로 재실행하고 해당 실패 시도를 원장에 남긴다. Voice OFF 조건은 사전 모집단 밖이며 0ms로 섞지 않는다.

## 7. DP별 예상과 선택

| DP | 사전 예상 | 발표용 한 문장 | 커버리지 |
| --- | --- | --- | --- |
| 44 | **실용적 동점 예상** | **두 안이 같은 음성 준비와 최종 재생 경로를 사용하므로 응답 내용 채택 이후 음성 전달의 독립 우위는 기대하지 않는다.** | 세지 않음 |
| 42 | **실용적 동점 예상** | **채택된 응답의 음성 전달은 대화 쪽에서 끝나므로 업무 서비스를 나눈 이익을 이 지표에 붙이지 않는다.** | 세지 않음 |
| 47 | 비교 제외 | 지칭 해석 전 비용은 첫 응답, VIA 처리시간에서 평가하고 응답 채택 뒤 음성 비용으로 다시 세지 않음 | 세지 않음 |
| 45 | 비교 제외 | 과거 근거 조회를 다시 하도록 만들지 않은 공통 요약 경로를 사용 | 세지 않음 |

44의 특정 실행 연결이 준비 완료 이후 재생 시작을 실제로 지연시키면 차이는 기록한다. 그러나 설명의 편의를 위해 A만 전체 음성 생성 완료를 기다리게 하거나 B만 streaming을 허용하지 않는다. 같은 provider와 audio 준비 정책, 재생 순서에서 남는 지연만 비교한다.

**결론은 필수 회귀 검증 유지다.** 사용자가 음성을 기다릴 수 있는 제품 기능을 보호하는 목적이 분명하며 현재 네 DP의 차이를 늘리기 위한 추가 핵심 QA로는 부적합하다.

## 8. 최소 PoC

실제 Response identity와 revision, 실제 UI 표시, 요약 준비 경로, Windows audio 출력 및 실제 음성 onset을 연결한다. Downstream Agent의 실제 업무는 고정 질문, 결과 fixture로 대체할 수 있다. 말할 수 있는 구간은 동일 사용자 음성 입력과 이전 출력 클립에서 판정한다.

**WASAPI software loopback과 실제 장치 출력은 다르다.** [Microsoft Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)은 audio engine의 stream을 복사하는 경로도 설명한다. 실제 audible endpoint 채점에는 보정한 acoustic microphone 또는 출력단을 관측하는 analog loopback을 사용하고 녹음 clock, 장치 경로, 전파 오차를 기록한다. WASAPI capture나 render callback만 구현했다면 audio engine까지의 proxy 측정으로 표시하며 실제 음성 시작 목표를 달성했다고 채점하지 않는다.

예비 구조 시험에서 TTS를 고정 음성 chunk stream으로 대체하면 **실행 연결과 출력 지연의 PoC**로 보고한다. 모델의 실제 요약, TTS 지연이나 품질을 입증한 것으로 표시하지 않는다. 첫 음성 chunk를 처음부터 제공해 전체 음성 준비 지연을 측정한 것처럼 보고하지 않는다.

**최소 기록:** `response_id, request_id, task_id, revision, response_content_adopted, text_content_presented, summary_ready, first_pcm_ready, eligible_intervals, actual_audio_onset, actual_delivered_range, invalidated_at, timeout, source_text_ref, audio_ref, observation_error_ms, evidence_class`.

공통 목록의 109개 의무 음성 응답을 5회씩 같은 환경에서 관측한다. callback 시간과 실제 출력 관측 시간의 차이를 검증하고 software loopback만으로 end-to-end이라고 부르지 않는다. 시험 시작 전 음성 endpoint, 장치, buffer, provider 조건과 calibration을 기록한다. 이 문서는 PoC 설계이며 지금 구현이나 모델 호출을 승인, 수행한 기록이 아니다.

## 9. 발표 한 장 카드

| 칸 | 사용할 문구 |
| --- | --- |
| 제목 | **말할 수 있게 된 뒤 음성이 얼마나 더 늦어지는가** |
| 정의, 지표 | 응답 내용 채택 뒤 재생 가능한 구간에서 실제 요약 음성이 시작되기까지의 누적 시간 평균 |
| 목표, 근거 | **500ms 이하** — 요약 200 + 첫 음성 200 + 출력 100ms의 설계 예산 |
| 예시 | 응답 채택 0.7초 → 텍스트 0.8초 → 사용자 발화 종료 2.0초 → 음성 시작 2.3초: **300ms**, **3점 ●◐○** |
| 점수 | `>500 / ≤500 / ≤400 / ≤300 / ≤200 / ≤150 / ≤100ms`이면 0~6점 |
| DP 관계 | 현재 공통 음성 경로의 회귀 검증이며 A/B 차별화 축으로 세지 않음 |
| 현재 결론 | **QA1을 텍스트로 측정해도 음성 전달을 빠뜨리지 않도록 유지** |

예시는 가상값이며 0.7~2.0초 구간이 실제 사용자 발화로 차단됐다고 가정한다. 입력 사건이 0초였다면 전체 실제 청취 대기는 2.3초라는 원값도 함께 남긴다.
