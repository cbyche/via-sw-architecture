## 1. 발표에 사용할 핵심 설명

**외부 업무와 사용자 대기를 제외하고 VIA가 목표 완료까지 처리한 경로 시간의 산술평균을 평가한다.**

| 항목 | 제안 |
| --- | --- |
| QA 이름 | **VIA 처리시간** |
| 한 문장 정의 | 사용자의 한 목표를 완료하는 과정에서 외부 Agent 업무와 사용자 대기를 제외한 VIA 처리 경로의 소요시간 |
| 단일 지표 | **평균 VIA 귀속 처리시간(초)** / 대표 시험 집합의 산술평균 |
| 목표 제안 | **대표 시험의 평균 5초 이하** |
| 목표 근거 | **Microsoft Windows의 장시간 대기 구간 경계인 5초**를 VIA 자체 처리의 상한으로 적용 |
| 주된 비교 DP | DP-42는 분명한 차이 가설. DP-44는 약한 방향 가설로 검증 필요 |
| 보완 연결 | DP-47과 DP-45도 같은 완료 경계로 측정 가능한 비교 축 |

**첫 응답 지연시간**은 구체적인 첫 안내를 사용자가 볼 때 끝난다. 이 QA는 그 뒤의 위임, 질문 연결, 정정과 최종 결과 정리를 포함해 해당 목표에서 VIA가 해야 할 처리를 모두 마쳤을 때 끝난다. 두 시간을 합산하지 않는다. 같은 요청의 첫 부분과 전체 과정이라는 관계이며 동일한 이익을 두 번 더해 종합점수를 만들지 않는다.

## 2. 한 목표의 시작과 완료를 고정한다

### 시작점

- 음성 목표는 **최초 요청의 실제 발화 종료**다. VAD 판정 / 전사 확정은 VIA 구간에 포함한다.
- 텍스트 목표는 **사용자 제출 시점**이다.
- 후속 정정이나 취소가 독립 평가 목표이면 그 입력을 새 시작점으로 삼는다. 원래 업무와 중복 집계하지 않도록 평가 원장에서 명시한다.
- 사용자 입력 없이 도착한 Agent 알림 자체는 새로운 사용자 목표로 세지 않는다. 첫 응답 지연시간이나 지정된 원래 목표의 후속 처리에 포함한다.

### 완료점

시간 종료점은 다음 처리 단계가 끝난 시점이다. **결과의 정답 여부는 시간 종료 조건이 아니다.** 잘못된 대상이나 상태로 종료했어도 실제 경로 시간을 사용하고 오류를 별도 기록한다. 아래의 의미상 완료 기준은 기능 판정용이며 오답 시간을 늘리는 조건으로 사용하지 않는다. 각 fixture에는 정확히 어느 사실이 필요한지 평가 전에 적는다.

1. 정해진 목표의 VIA 상태와 Request/Task 관계가 확정됐다.
2. 외부 전달이 필요한 경우 해당 목표가 요구한 Agent 접수 / 결과 / 제어 사실을 확인했다.
3. 사용자가 확인할 **필수 상세 텍스트가 해당 Request/Task UI에 모두 표시**됐다.
4. 음성 안내 대상이면 **해당 요약의 전체 음성 데이터와 출력 참조가 준비**됐다. 실제 청취와 음성 재생 차례까지 기다리지는 않는다.

4번은 사용자가 정한 “상세 텍스트 + 들을 수 있을 때 음성 요약”을 QA 3에서 다루기 위한 **새 측정 경계 제안**이다. 전체 음성이 준비될 때까지 재생을 막는 실행 정책은 아니며 streaming 재생을 허용한다. 음성을 영원히 생성하지 않고 텍스트만 빨리 끝내는 구현을 완료로 인정하지 않는다. 음성의 실제 재생 / 현재성 / 누락 여부는 별도 공통 기능 검증과 원시 기록으로 확인한다. 재생 직전 필요한 후속 검증을 생략해도 된다는 뜻은 아니다.

| 목표 유형 | 정해진 완료 사실 | 완료로 볼 수 없는 것 |
| --- | --- | --- |
| 자료 직접 설명 | 요구한 설명의 상세 텍스트 표시와 음성 요약 준비 | 첫 문장만 표시하거나 답 대신 접수 인사 |
| 문서 작성 위임 | Agent 결과를 확인하고 올바른 Task에 연결한 최종 안내 / 자료 참조 표시와 요약 준비 | “작성하겠습니다”라는 첫 안내나 명령 전송만 완료 |
| 현재 업무 상태 확인 | 확인된 현재 상태의 상세 텍스트 표시와 요약 준비 | 캐시에 남은 과거 상태를 현재 상태로 단정 |
| 기존 요청 정정 / 취소 | 해당 제어의 실제 확인 상태와 이후 관계를 확정하고 표시 / 요약 준비 | 취소 요청 접수를 실제 취소 완료로 표현 |
| 확인 질문이 필요한 목표 | 정해진 사용자 답변을 받은 뒤 원래 목표의 완료 조건 달성 | 확인 질문을 했다는 이유만으로 원래 목표를 완료 |
| 권한 거부 / 결과 미확인 안내 | fixture가 요구한 정당한 종료 / 보류 사실과 후속 행동 표시 / 요약 준비 | 원래 성공 가능한 목표를 빠르게 포기 |

정정으로 대체된 이전 revision은 이미 수행한 처리와 폐기를 기록하되 미생성 음성 나머지를 새로 준비할 의무는 없다. 최종 revision의 상태와 상세 내용 및 전체 요약 준비를 완료 조건으로 사용한다.

외부 Agent의 업무 품질 자체는 평가하지 않는다. 공통 stub이 제공한 결과를 VIA가 올바르게 연결 / 전달하는지 확인한다. 장기 업무의 모든 가능한 미래 사건을 끝없이 기다리는 것이 아니라 **fixture에 정한 한 목표**의 완료점을 관측한다.

## 3. 포함 / 제외 경계

| 구간 | 처리 |
| --- | --- |
| VIA 코드, 저장, 상태 확정, UI 처리, 재검증, 재시도 | 포함 |
| VIA가 호출한 음성 / 의미 모델의 전송 / 추론 / 응답과 quota 대기 | 포함 — cloud에 있다고 외부 업무로 제외하지 않음 |
| VIA의 조회 / 검색 / 원본 읽기와 Context 구성 | 포함 |
| 서비스 간 RPC, 직렬화, receipt 반영, 내부 queue와 자원 경합 | 포함 |
| 목표 완료 전에 필요한 음성 요약 생성 | 포함 |
| Downstream Agent 내부의 업무 reasoning / 계획 / 도구 실행 | 제외 |
| 사용자에게 질문한 뒤 답변을 기다리는 시간과 답변 자체의 발화 길이 | 제외 |
| 사용자 입력 종료 판단과 전사 확정 | 포함 |
| 준비된 음성을 들을 차례와 이미 준비된 음성의 재생 길이 | 완료 조건에서 제외. 같은 목표의 후속 확인 입력이 청취 완료 뒤 제공될 때도 순수 재생과 차례 대기 node는 0초. 요약과 TTS 생성 및 내부 출력 준비는 포함 |

Agent 전송 네트워크와 접수 확인 프로토콜은 VIA 연동 경로이므로 포함한다. Agent가 명령을 소비할 수 있게 된 뒤 내부 업무 결과를 제공할 때까지를 외부 업무로 분류한다. Agent가 내부 대기를 구분해 제공하지 못하면 해당 경계의 불확실성을 기록하며 VIA 내부 시간을 임의로 빼지 않는다.

## 4. 단일 산식과 병렬 처리

외부 대기를 실제 경과시간에서 단순히 빼면 병행 처리 시간을 놓칠 수 있다. **인과 그래프에서 외부 대기만 제거한 완료 경로 길이**를 계산한다.

```text
각 목표 i의 실제 실행 그래프 G_i:
  node = 실제 작업 또는 대기
  edge = 선행 결과, resource 순서, 상태/receipt 등 실제 의존

d'(v) = 0              외부 Agent 업무, 사용자 대기 / 발화, 순수 청취 / 재생 차례 대기
        실제 duration  VIA 처리 / 모델 / 연동 / 내부 대기

finish(v) = d'(v) + max(finish(parent(v)))
T_i = 공통 완료점까지의 가장 긴 의존 경로 길이

평균 VIA 귀속 처리시간 T = (T_1 + … + T_N) / N
```

**직렬 작업은 더하고 병렬 작업은 늦게 끝나는 경로를 따른다.** DAG 계산은 실제 외부 시간을 0으로 만들고 인과 / 자원 순서를 보존한 귀속 분석이다. Agent가 현실에서 0초에 끝나는 새 시스템의 성능을 예측하는 시뮬레이션이 아니며, CPU 사용시간의 합도 아니다.

### 내부 대기를 이중으로 세지 않는 규칙

- 외부 응답을 기다린 같은 시간을 `외부 업무`와 `VIA queue 대기`로 동시에 기록하지 않는다.
- resource를 앞 작업이 사용해서 생긴 대기는 그 선행 작업의 완료 edge로 표현한다. 그 시간을 다시 같은 길이의 대기 node로 더하지 않는다.
- 준비된 작업이 VIA 정책 / scheduler 때문에 추가로 시작되지 않은 시간은 별도 내부 대기 node로 남긴다.
- 다른 목표의 작업이 현재 목표를 지연시켰다면 그 자원 순서를 포함한다. 관련 배경 작업을 숨겨 빠른 값으로 만들지 않는다.
- **그래프는 현재 목표의 `t0`에서 절단한다.** 입력 전에 끝난 작업은 초기 상태로만 참조하며 소요시간을 더하지 않는다. `t0` 전에 시작해 이후까지 자원을 점유한 작업은 `t0` 이후의 잔여 구간만 넣는다. 예를 들어 배경 job이 `t0−4초`부터 `t0+1초`까지 자원을 사용했다면 현재 목표의 경합 선행 구간은 5초가 아니라 **1초**다. 입력 전 비용은 QA05의 활동 비용에 남긴다.
- 원인과 경계를 복원할 수 없는 gap은 외부 시간이라고 가정해 제외하지 않는다. trace 미완전으로 표시하고 원시 wall-clock과 함께 보존한다.
- 실제 시작 / 종료, source 시각과 VIA 수신 시각, parent/resource owner를 모두 남긴다. 서로 다른 시계는 오차를 보정하고 남은 오차를 기록한다.
- 외부 duration을 0으로 바꾸기 **전**의 그래프가 실제 완료 시각을 관측 오차 범위에서 재구성하는지 확인한다. 그렇지 않으면 계측 복원이 불완전하므로 누락을 기록한다. 오답 여부 때문에 시간을 바꾸지는 않는다. 외부 시간을 제거한 뒤의 값은 실제 wall-clock에 순증한 지연의 인과 효과를 추정한 값이 아니다.

### 병렬 계산을 이해하는 가상 예시

```text
VIA 입력 / 위임 처리 1.2초
  ├─ 외부 Agent 업무 8.0초
  └─ VIA의 필요한 병행 처리 3.0초
둘 다 완료 후 VIA 최종 표시 / 요약 준비 0.6초

실제 경과시간 = 1.2 + max(8.0, 3.0) + 0.6 = 9.8초
VIA 귀속시간 = 1.2 + max(0.0, 3.0) + 0.6 = 4.8초
```

`9.8 − 8.0 = 1.8초`로 계산하면 실제 수행한 VIA의 병행 경로 3초가 사라진다. 이 사례의 QA 3 값은 **4.8초**다. 실행 경로가 단순 직렬일 때만 `전체 − 외부`와 같아진다. 위 수치는 측정 결과가 아닌 설명용 값이다.

## 5. 대표 평가 집합과 측정 절차

**공통 28개 시나리오의 사용자 완료 목표 76개 × 5회 = 380개 완료 경로**를 사용한다. [COMMON-28-v1](../scenarios/common-28-v1/common-scenarios.md)의 G-ID마다 최초 입력과 함께 완료해야 할 후속 입력 및 Agent 사건과 완료 조건을 지정했다. 확인 답변이나 같은 목표의 정정을 별도 목표로 부풀리지 않는다. 사용자 입력 없이 오는 Agent 사건은 기존 목표에 연결하거나 QA01 관측으로 관리한다.

직접 응답과 조회, 위임과 복합 의존 및 질문/답변과 정정/취소, 채널 전환 및 정당한 거부/실패 안내를 같은 목록에서 관측한다. 최초 12목표 별도 표는 폐기했다. 위 76개는 전체 회귀 목표다. DP-RELATED-v2에서는 구조가 관여하는 목표만 같은 비중으로 평균내고 무관한 목표는 제외한다. 선택한 목표의 후속 정정과 Agent 처리 전체는 인과 경로에 남긴다.

### 측정 순서

1. 목표별 최초 입력과 필수 완료 사실, 예상 외부 사건, 포함 / 제외 owner를 등록한다.
2. 필요한 과거 자료와 cache를 동일한 사용자 활동으로 준비한다. 준비 비용은 비용 / 메모리 축에 남기며 목표 도착 이후의 준비 / 갱신 지연은 이 QA에 포함한다.
3. A/B 각각 같은 목표와 외부 stub을 실행하고 순서를 교차한다. 구조적 중간 왕복이나 모델 호출을 양안 동일한 한 개의 고정 지연으로 대체하지 않는다.
4. 실제 wall-clock과 인과 graph를 수집한다. 의미상 올바른 완료 여부도 별도로 기록하되 시간 종료나 점수의 조건으로 사용하지 않는다.
5. 외부 / 사용자 시간만 0으로 바꿔 목표별 귀속시간을 계산한다. 병행 경로의 기대값과 trace 재현을 확인한다.
6. 같은 관련 목표 집합의 실제 처리시간 산술평균을 구한다. 전체 회귀를 수행할 때의 수량은 380개다. 오답 / 잘못된 상태 종료도 포함하고 오류는 별도 기록한다. 정답이 나오기까지 기다린 시간이나 실패 벌점을 대신 넣지 않는다.

## 6. 오답과 미관측의 처리

**오답과 잘못된 상태 종료도 그때까지 실제 수행한 VIA 경로 시간을 그대로 포함한다.** 성공 표본만 평균내지 않으며 `+∞`, timeout 대체값, 강제 0점 등 실패 벌점은 사용하지 않는다. 오류는 별도 기능 / 정확도 기록이다.

공통 목록의 마지막 필수 source 이후 60초는 시험 운영용 관측 한도다. 처리 종료 자체가 없으면 `NOT_OBSERVED`로 남기며 그 한도를 처리시간으로 만들어 넣지 않는다. 관측분 평균과 미관측 건수를 구분하고 전체 380건 평균이라고 잘못 보고하지 않는다. 이번 사고 실험은 등록한 관련 목표 모두 처리가 종료된다는 가정으로 점추정한다.

## 7. 목표 5초의 도출과 근거 수준

### 제품 요구에서 숫자까지

**VIA 자체의 요청 해석과 업무 연결 및 결과 전달이 길고 복잡한 작업을 하나 더 기다리는 부담이 되어서는 안 된다.** 사용자와 CTO/담당임원은 빠른 상호작용을 요구하고 PC 플랫폼 및 제품 통합 담당자는 제품 사용 중 VIA가 만드는 지연을 제한할 필요가 있다. 이 관점에서 외부 업무를 제외한 VIA 처리에 상한을 제안한다. stakeholder가 5초에 이미 합의했다고 주장하지 않는다.

[Microsoft, Improve the responsiveness of your Windows app](https://learn.microsoft.com/en-us/windows/apps/develop/performance/responsive)은 Windows의 주요 상호작용을 분류하고 각 종류에 목표를 정하도록 안내한다. 2026-03-18 갱신본의 해당 분류는 다음과 같다.

| Windows 분류 | 지연 범위 | 원문의 사용자 경험 설명 |
| --- | --- | --- |
| `Long wait` | 2~5초 | 응답성이 좋다고 느끼지 않는 긴 대기 |
| `Captive` | 5~10초 | 피하기 어려운 길고 복잡한 작업에 허용하는 대기 |
| `Long-running` | 10~30초 이상 | 사용자가 다른 일을 할 가능성을 고려해야 하는 작업 |

**도출:** 외부 Agent의 도메인 업무를 제외한 VIA 자체 처리만으로 `Captive` 구간까지 넘어가지 않도록 **평균 5초를 목표선**으로 채택한다. 첫 내용은 QA01에서 1초 안에 표시하도록 요구하고 이 QA는 나머지 상세 표시와 음성 요약 준비까지 포함한 완료 경로를 제한한다. 5초가 자연스러운 무응답 대기라는 뜻은 아니다. 2026-10-15 사용자 지시에 따라 380개 목표의 산술평균에 5초를 적용한다. 외부 지침은 이 평균 집계나 오답 포함 규칙의 실증 근거가 아니다.

기존의 해석 1.5초와 근거 1초 등을 더한 내부 예산표는 목표의 근거에서 제거했다. 여기서는 외부 상호작용 기준에서 숫자를 가져오고 구조가 그 값을 만족하는지 평가한다. **5초를 VIA 책임에 적용한다는 결정은 제품 요구 제안이며 Microsoft가 VIA의 내부 시간에 5초를 지정했다는 뜻은 아니다.**

### 직접 답변과 업무 위임의 차이

| 목표 | QA03 값과 사용자가 기다린 시간의 관계 | 이 목표로 주장하는 내용 |
| --- | --- | --- |
| 외부 업무와 추가 사용자 입력이 없는 직접 답변 | 같은 시작과 완료 경계에서 귀속 경로가 실제 VIA 완료 경과시간에 대응 | 이 조건의 대표 시험에서 첫 요청부터 상세 표시와 음성 요약 준비까지 평균 5초 |
| 외부 Agent에 맡긴 업무 | 외부 업무의 duration을 0으로 바꾼 인과 경로를 계산하므로 실제 총 대기와 다름 | 외부 업무가 길더라도 VIA 자체 처리의 상한을 별도로 적용 |
| 질문과 답변 또는 여러 단계가 있는 목표 | 해당 목표의 VIA 처리 경로를 누적하되 외부 업무와 사용자 대기만 제외 | 단계마다 5초를 따로 주지 않고 한 목표 전체의 VIA 경로를 평균 5초로 제한 |

이 측정은 실행된 인과 경로의 귀속 분석이다. 현실의 총 대기에서 VIA 때문에 순증한 시간의 인과 효과를 추정한 값은 아니다. 사용자 전체 대기시간과 음성의 실제 전달 상태는 원시 증거에 함께 남긴다. Agent가 포함된 요청도 총 5초 안에 끝난다고 발표하지 않는다.

## 8. 0~6점 구간 — `QA-C03-score-v3`

5초가 목표 충족선이고 1초가 높은 개선 수준이다. 그 사이를 0.8초 간격으로 나눈다. **중간 구간과 1초의 전체 처리 우수선은 설계상 표시 규칙**이다. 첫 응답의 HCI 1초 근거를 전체 목표 완료시간에 그대로 적용한 것이 아니다.

| 점수 | 원형 표시 | 평균 귀속시간 t의 범위 | 의미 |
| ---: | --- | --- | --- |
| 0 | ○○○ | t > 5초 | 평균 목표 미달 |
| 1 | ◐○○ | 4.2초 < t ≤ 5초 | 목표 충족 |
| 2 | ●○○ | 3.4초 < t ≤ 4.2초 | 처리 여유 확보 |
| 3 | ●◐○ | 2.6초 < t ≤ 3.4초 | 처리 여유 확보 |
| 4 | ●●○ | 1.8초 < t ≤ 2.6초 | 처리 여유 확보 |
| 5 | ●●◐ | 1초 < t ≤ 1.8초 | 처리 여유 확보 |
| 6 | ●●● | 0초 ≤ t ≤ 1초 | 높은 개선 수준 |

v3는 기존 수치 구간을 유지하며 오답을 포함한 전체 처리시간의 산술평균을 채점한다. 이전 최대값 점수를 재사용하지 않는다.

반올림 전 값으로 채점한다. 미측정은 미측정이고 음수는 계측 오류다. 같은 목표 집합에 같은 구간을 적용하며 A/B 점수 차이를 만들기 위해 DP별로 구간을 좁히지 않는다. 예비 PoC에서 점수가 같은 경우 원값과 불확실성을 먼저 보고, 세분화가 필요한 객관적 이유가 있을 때만 판본을 바꾼다.

## 9. DP별 예상 결론과 한 문장 이유

아래는 §5의 정상 목표 집합을 대상으로 한 **PoC 전 예측**이다. 전체 Architecture 선택이나 측정된 순위는 아니다. v3에서는 모든 목표에 같은 비중을 적용한 평균으로 비교한다. [점추정 자료](history/qa-dp-thought-experiment.md)에 실제 숫자와 가정을 기록한다.

| DP | 예상 결론 | 발표용 한 문장 구조 설명 | 현재 커버리지 판단 |
| --- | --- | --- | --- |
| **42** | **A 우세 예상** | **A는 대화와 업무의 관련 상태를 한 번에 확정하므로 서비스 사이의 명령 / 접수 확인 왕복을 줄인다.** | 구조 경로가 명확한 주된 차이 가설 |
| **44** | **B가 짧아지는 방향을 예상하지만 약한 가설** | **B는 완료 결과가 다음 단계로 직접 전달되므로 중앙에 회수해 다시 배정하는 단계를 줄인다.** | 중요할 만큼의 시간 차이 근거가 부족하므로 아직 핵심 커버리지로 세지 않음 |
| **47** | **A 우세 예상** | **A는 원본에서 지칭 결과를 직접 만들므로 후보 생산 이후 결합을 기다리는 의존 단계를 줄인다.** | 주표 외 보완 가능한 차이 가설 |
| **45** | **B 우세 예상** | **B는 반복 사용되는 과거 관계를 미리 준비하므로 요청 처리 중 근거를 다시 구성하는 경로를 줄인다.** | 주표 외 보완 가능한 차이 가설. 유효 관계 반복 사용의 실제 비중 확인 필요 |

### 42의 주장은 어디까지 분명한가

모듈화된 통합 A도 비동기 worker와 독립 논리 상태를 갖는다. A가 업무 때문에 대화 전체를 막는 약한 구현을 비교하지 않는다. A/B 모두 외부 Agent의 확정 사실을 기다려야 한다. 예상 차이는 **VIA 내부에서 관련 상태를 확정하는 경로**에 있다. 외부 업무시간을 줄였다고 주장하지 않는다.

### 44를 강한 커버리지로 확정하지 않는 이유

44A는 짧은 dispatcher와 우선순위 mailbox, 병렬 worker를 허용한다. B의 직접 전달은 중앙 재배정을 줄일 수 있지만 typed channel, join과 credit 대기도 생긴다. 같은 thread pool과 같은 모델 부하에서는 차이가 매우 작을 수 있다. 모델 추론시간이 큰 경로에 중앙 왕복 몇 회가 있다는 것만으로 체감 차이를 단정할 수 없다.

**현재 판단은 “B 방향을 먼저 검증하되 핵심 QA 연결은 아직 입증되지 않았다”이다.** 이것은 A/B 사이에서 결정을 못 내린다는 뜻이 아니라 현재 설계의 이 축을 **차이가 분명한 평가축으로 승인하지 않는 결론**이다. 실제 차이가 없으면 44의 다른 QA 축이나 비교 구도를 보완해야 한다.

### 47 / 45로 연결을 확장할 때의 조건

47A도 여러 모델 호출과 재판단을 할 수 있다. B의 생산자 병행을 막거나 매 frame 추론을 강제하지 않는다. 생산→결합의 선후 관계가 동일한 완료 목표에서 얼마를 더하는지 확인한다.

45A의 원본 / 관계 cache와 부분 갱신을 유지한다. B에만 이미 준비된 정답 관계를 공급하지 않는다. 양안에 동일한 COMMON-28-v1을 적용하며 실제 준비 활동 이후 최초 / 반복 / 원본 변경 / 새 관계의 동일 사건을 사용한다. B의 전체 우세 예측을 검증하려면 관계 반복 사용이 실제로 현재 처리 경로를 줄여야 한다. 본 QA는 요청 도착 이전 준비 비용을 시간에 더하지 않으므로 그 비용은 **모델 비용 / 메모리 축에서 반드시 함께 공개**한다.

## 10. 최소 PoC 범위와 차이 인정

| 항목 | 범위 |
| --- | --- |
| 42에서 구현 | 실제 local 상태 확정, A의 공동 확정, B의 독립 명령 / receipt / event 반영과 UI 완료 경로 |
| 44에서 구현 | 중앙 회수 / 후속 배정과 stage 직접 연결, 실제 queue / cancel / join / credit 경로 |
| 공통 모델 | 동일 모델 / 입출력 계약. 호출이 차이 원인이 아니면 같은 지연 profile을 사용할 수 있으나 결과명을 모사 의존 PoC로 표시 |
| 외부 Agent | 접수 / 질문 / 완료 / 취소를 같은 시점에 제공하는 유한 stub. 도메인 업무 구현은 필요 없음 |
| UI와 음성 | 상세 텍스트 실제 표시 계측, 음성 요약 전체 준비 계측. 생략하면 사용자 출력 완료시간을 측정했다고 하지 않음 |
| 남길 증거 | 목표 / 입력 / 완료 oracle, trace DAG, 원래 wall-clock, 제외 node, 계산 결과, 오류 / 취소 / late completion |
| 이번 문서의 상태 | **PoC 설계 제안. 구현 / 모델 호출 / 측정 없음** |

DP 비교는 등록한 관련 경로의 산술평균과 원값을 보고하고, 전체 회귀의 380개 평균과 구별한다. 향후 실용 차이 제안은 오차를 고려한 평균 차이 0.5초이며 5회 묶음에서도 방향을 확인한다. 통계적 확증이나 모든 요청의 최대시간을 보장하지 않는다. 오답은 실제 시간으로 포함하고 미관측은 별도 표시한다. 이번에는 PoC나 모델 실행을 하지 않는다.

## 11. 발표 한 장 원고

- **정의:** 외부 업무와 사용자 대기를 제외한 VIA의 목표 처리 경로 시간
- **지표:** 외부 Agent 업무와 사용자 대기를 제외한 목표별 완료 경로의 산술평균
- **목표:** 대표 시험의 평균 5초 이하 — Microsoft Windows의 장시간 대기 구간 경계 적용
- **측정:** 실제 인과 순서를 보존하고 제외 구간만 0으로 계산. 내부 queue / 모델 / RPC / UI / 음성 준비 포함
- **예시:** `VIA 1.2 + max(Agent 8, VIA 3) + VIA 0.6`의 VIA 귀속은 4.8초. 가상 시험 4.8 / 3.2 / 2.1 / 4.0초의 **평균 3.525초 → 2점 ●○○**
- **연결:** DP-42 A는 공동 확정으로 서비스 왕복을 줄임. DP-44의 직접 stage 연결 효과는 아직 약한 가설
- **각주:** 외부 업무를 포함한 총 대기는 별도 표시. 5초는 Windows 지침을 VIA 책임에 적용한 제품 요구 제안이며 미측정.

## 12. 문서 검수 기록

- 첫 응답과 목표 전체 완료의 경계를 분리했다.
- cloud 모델 시간을 Agent 업무시간으로 제외하지 않았다.
- 음성 재생을 강제 endpoint로 삼지 않으면서 요약 생성은 완료 전에 포함했다.
- 병렬 VIA 작업을 단순 외부시간 차감으로 잃는 예시를 추가했다.
- 오답도 실제 처리시간으로 평균에 포함하며 미관측은 별도로 기록하고 시간 벌점을 만들지 않는다.
- 5초 목표의 외부 출처와 VIA 적용 판단을 구별하고 기존 내부 예산 분할을 제거했다.
- v3에서 사용자 지시에 따라 산술평균과 오답 실제 시간으로 정정하고 이전 v2를 archive에 보존했다.
- 0.8초 점수 간격과 0.5초 실용 차이는 연구가 정한 값이 아닌 평가 규칙임을 밝혔다.
- 44의 약한 차이를 확인된 커버리지로 세지 않았다.
- 제3자 검토 결과와 보완 이력은 패키지 통합 검토 문서에 연결한다. 이 절은 작성자 검수이며 독립 검토 완료가 아니다.
