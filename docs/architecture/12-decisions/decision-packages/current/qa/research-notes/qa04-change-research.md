## 1. 사용자가 제공한 협업 문제

사용자는 여러 개발자가 각각 AI 코딩을 사용하면서 변경이 넓게 퍼져 충돌과 통합 비용이 늘고 다른 담당 영역을 수정하기 주저하는 경험을 설명했다. 이것이 변경 범위를 품질 후보로 다루는 직접 요구다.

변경 모듈 수는 수정과 검토의 범위를 나타낸다. 작업시간은 모델과 도구 및 개발자 숙련에 더 영향을 받으므로 구조 대안 비교의 주지표로 채택하지 않았다. 모듈 수가 곧 인건비나 실제 Git 충돌 횟수라고 주장하지 않는다.

## 2. Rust의 집계 단위

| 자료 | 확인한 구분 | 적용 |
| --- | --- | --- |
| [Rust Reference: Modules](https://doc.rust-lang.org/reference/items/modules.html) | `mod`는 함수와 자료형 등 item의 이름과 공개 경계를 구성하며 중첩 가능 | 고유 논리 모듈 경로를 센다. 한 파일에 여러 모듈이 있을 수 있음 |
| [Rust Book: Packages and Crates](https://doc.rust-lang.org/book/ch07-01-packages-and-crates.html) | crate는 컴파일 단위이고 package는 Cargo 관리 단위 | crate나 파일 및 실행 프로세스 수와 모듈 수를 혼동하지 않음 |

식별자는 package와 crate target 및 완전한 module path를 조합한다. 운영 코드를 수정하거나 추가하거나 삭제한 고유 모듈을 센다. 자식만 수정했다고 부모를 자동 가산하지 않는다. 부모의 import나 mod 선언 및 공개 연결이 실제 바뀌면 부모도 센다. 소유 prompt와 schema 및 config 변경은 소유 모듈로 추적하며 테스트 전용 수정은 제외한다. 상세 예외와 완료 조건은 현재 QA04 명세를 따른다.

## 3. 목표 3개의 직접 근거: 사용자 제공 ARGO 분석

사용자는 이전 Agent 개발 과제 **ARGO의 기능 추가와 데이터 형식 변경 PR 145건에서 평균 5.4개 모듈을 수정했다**는 집계를 제공하고 **40% 이상 개선**을 요구했다. [ARGO 목표 근거 기록](../targets-source-qa04-argo.md)에 제공된 수치와 산식 및 증빙 조건을 보존한다.

| 항목 | 수치와 의미 |
| --- | --- |
| 기존 평균 | **5.4개/PR**, 사용자 제공 145건의 집계 |
| 개선 요구 | **40% 이상 감소**, 사용자 지정 목표 |
| 40% 감소 시 상한 | `5.4 × 0.60 = 3.24개` |
| VIA 운영 목표 | **변경 과제당 평균 3개 이하** |
| 3개 달성 시 표시값 대비 감소율 | `(5.4 − 3) / 5.4 ≈ 44.4%` |

평균은 소수로 측정할 수 있다. 3개는 정수로만 측정해야 해서 생긴 값이 아니라 **40% 개선 요구를 만족하는 더 엄격하고 간명한 목표**로 선택한 값이다. 40%는 외부 논문의 보편 임계가 아니며 3개를 정확히 40% 감소라고 쓰지 않는다.

### 자료 출처와 감사 범위

현재 확인 가능한 근거는 사용자가 제공한 집계와 개선 요구다. 이번 문서 작성 과정에서 ARGO PR 145건을 직접 열어 분석하거나 사용자 집계를 독립 재현하지 않았다. 평균 5.4는 제공된 표시값이며 이를 곱해 PR별 값이나 원시 정수 총합을 만들어 넣지 않는다.

실제 개선율을 입증할 때는 다음을 대조해야 한다.

- ARGO의 분석 기간과 PR 목록 및 기능 추가와 형식 변경의 분류
- 하나의 PR에 여러 변경이 섞이거나 하나의 변경이 여러 PR로 나뉜 경우의 처리
- ARGO의 모듈 식별 기준과 VIA의 운영 Rust 모듈 기준
- 테스트 전용 변경과 자동 생성 코드 및 설정 변경의 포함 범위
- PR별 변경 모듈 집합과 반올림 전 평균

이 확인 전에도 사용자 제공 기준과 개선 요구를 **목표 설정 근거**로 사용할 수 있다. 다만 VIA의 대표 여섯 변경을 측정해 평균 3개가 나왔다는 이유만으로 ARGO의 전체 변경 분포 대비 실제 유지관리 비용이나 충돌이 44.4% 줄었다고 주장하지 않는다. 모듈 수의 실제 개선율에도 집계 단위와 변경 집단의 비교 가능성이 필요하다.

## 4. 외부 연구가 뒷받침하는 범위

| 출처와 위치 | 확인한 내용 | 채택 범위 |
| --- | --- | --- |
| [CMU/SEI-2002-TR-025, Illuminating the Fundamental Contributors to Software Architecture Quality](https://www.sei.cmu.edu/documents/689/2002_005_001_14063.pdf) / §3.1~3.2 | 변경 모듈 수를 modifiability 시나리오의 response measure로 사용. 의존성에서 수정 파급을 설명 | 지표의 타당성 근거. 난이도 가중치와 모듈 목표 개수를 혼동하지 않음 |
| [Modern Code Review: A Case Study at Google, ICSE-SEIP 2018](https://storage.googleapis.com/gweb-research2023-media/pubtools/4476.pdf) / §5.2와 §7.1 | 약 900만 리뷰에서 35% 이상이 한 파일 변경이고 약 90%가 10개 미만 파일 변경. 작은 변경과 가벼운 검토 관행 설명 | 국소 변경의 협업 이점에 대한 보조 자료. 파일 수와 reviewer 수를 Rust 모듈 3개로 환산하지 않음 |
| [Understanding predictive factors for merge conflicts, 2020](https://www.sciencedirect.com/science/article/pii/S095058492030001X) | 더 많은 변경 파일과 개발자 및 commit이 관련된 큰 contribution에서 충돌 관련성을 보고 | 넓은 변경 파급을 줄이려는 방향의 근거. AI 코딩 자체나 3모듈 임계의 검증은 아님 |

외부 자료는 변경 범위 제한의 필요성과 지표 선택을 뒷받침한다. **숫자 3의 직접 근거는 ARGO의 사용자 제공 기준값과 개선 요구다.** 다른 코드 benchmark의 파일 수나 함수 수를 Rust 모듈 수로 바꾸지 않는다.

## 5. 실제 VIA 수정 두 건: 계수 방법의 예시

원본 `/Users/changbae/Workspace/via`의 HEAD `b6032a4c472e18ec216b3e8592346ab269495342`에서 읽은 Git 이력과 `mod` 선언을 대조한 기록이다. 이 두 사례는 실제 모듈을 세는 방법의 예시로 유지한다.

| commit | 독립 변경 | 운영 모듈 |
| --- | --- | --- |
| `06bfa51bc6373d206f46c4f0ab01bcf5d6b05ab6` | Agent의 재할당 포트를 실제 실행 인자에 반영 | `via-backends / lib / crate::openclaw`, `via-backends / lib / crate::runtime`, `via-process / lib / crate::spawn`: **3개** |
| `6d984b635d755ec03e8d00a0b970ebeff61044aa` | 첫 음성 입력에서 엔진 연결을 시작하고 보관 입력을 전달 | `via-app / lib / crate::realtime::connection`: **1개** |

첫 사례의 gateway 파일은 테스트 assertion만 바뀌어 제외했고 integration test와 문서도 제외했다. 두 번째 사례의 wire payload 시험과 내부 테스트도 운영 모듈로 추가하지 않았다. 파일별 집계와 재현 명령은 [Git 수정 근거](../targets-source-qa04.md)에 보존했다.

두 사례 중 큰 값 3을 대표 변경의 평균 상한으로 삼았던 이전 도출 방식은 현재 근거로 사용하지 않는다. 1개와 3개 사례의 평균이나 상단으로 ARGO 145건의 집계를 대신하지 않는다. [이전 조사 문서](../../../../../../archive/qa-targets-before-task-aligned-revision-20261014/research-notes/qa04-change-research.md)와 [이전 QA04](../../../../../../archive/qa-targets-before-task-aligned-revision-20261014/qa04-change-scope.md)는 수정 이력으로 보존한다.

## 6. 폐기한 산식과 설명

- “데이터 형식 변경은 1개이고 기능 확장은 5개”: 실제 필요한 수정 목록에서 도출하지 않아 폐기했다.
- “주담당 1개와 관련 2개이므로 3개”: 원하는 숫자를 다시 나눈 것이므로 사용하지 않는다.
- “실제 두 수정 중 큰 값 3이 전체 변경의 평균 목표”: 관측 사례가 대표하지 않는 분포까지 확장했으므로 현재 목표 근거에서 제외했다.
- “파일 수가 적을수록 좋으니 Rust 모듈도 3개”: 집계 단위와 수치 도출이 달라 사용하지 않는다.
- “3개는 5.4개보다 정확히 40% 작다”: 40% 감소는 3.24개이고 3개는 약 44.4% 감소이므로 잘못된 설명이다.

## 7. 발표와 실제 변경 검증

**발표 핵심:** “ARGO의 기능 추가와 데이터 형식 변경 PR 145건에서 평균 5.4개 모듈을 수정했습니다. 변경 파급을 40% 이상 줄이기 위해 VIA는 평균 3개 이하를 목표로 합니다.” 발표에서는 사용자 제공 내부 집계라는 출처를 함께 표시한다.

| 심사 질문 | 답변 |
| --- | --- |
| 3개라는 숫자는 어디에서 나왔는가 | 사용자 제공 ARGO 평균 5.4개에 40% 개선 요구를 적용한 3.24개보다 엄격하게 3개를 선택했다. |
| 145건을 직접 감사했는가 | 아니다. 현재는 사용자 제공 집계이며 PR 목록과 모듈 식별 기준을 첨부해야 독립 재현할 수 있다. |
| 형식 변경과 기능 확장의 수정 수를 정해 둔 것인가 | 아니다. 완료 조건을 만족하는 실제 변경 모듈을 세며 유형별 수정 수를 사전 배정하지 않는다. |
| 3개면 개발시간이나 충돌도 같은 비율로 감소하는가 | 아니다. 수정 범위가 지표이며 실제 시간과 충돌은 별도 결과다. |
| 이전 VIA의 1개와 3개 사례는 무엇을 보여주는가 | 파일 수와 실제 운영 모듈 수를 구별해 집계하는 방법을 보여준다. 현재 목표값의 직접 근거는 아니다. |

현재 C01~C06은 데이터 형식 변화 3건과 기능 확장 3건이다. 실제 후보에 적용한 patch가 없으므로 어느 안이 평균 3개를 만족했는지는 미측정이다. 각 변경을 같은 코드 버전에서 독립 수행하고 완료 여부를 확인해야 한다. 모듈 경계는 변경 전에 고정하며 거대한 모듈로 합쳐 숫자만 낮추거나 필요한 prompt와 설정 변경을 빼지 않는다.

`CHG-v3`의 1점은 `2.6 < 평균 ≤ 3`이고 최고 6점은 `평균 ≤ 1`이다. 중간 0.4개 간격은 비교 표현 규칙이며 연구가 검증한 협업 부담의 임계값이 아니다. 원값은 여섯 변경 모듈 수 합을 6으로 나누어 보존한다. 현재 점수 구간은 이전과 같아도 근거 판본은 달라졌으므로 과거 도출 논리와 혼용하지 않는다.
