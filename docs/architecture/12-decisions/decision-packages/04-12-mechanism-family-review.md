# Stage 4 재발굴 — 반론, 품질 영향과 판정

> 상태: **작성자 자기 반론 및 문서 대조 / 사용자 검토용** / 2026-10-02
> 입력: [계열 분류와 발굴](./04-10-mechanism-family-discovery.md), [실행과 상태](./04-11-mechanism-family-proposals.md).
> 독립 리뷰, 구현 검증, 모델 capability 확인 및 측정 결과가 아니다. 기존 04-09의 리뷰 결과를 이 두 대안에 재사용하지 않는다.

## 1. 먼저 제기한 반론과 처리

| 작성 중 제기한 반론 | 확인 및 문서 반영 | 남은 판단 |
| --- | --- | --- |
| T에 추가 조회 loop를 넣으면 C-대화 아닌가? | 그 형태는 S-01의 확장이다. C-대화는 Agent 결과, 답변과 정정 이후의 의미상 다음 처리도 모델에 넘기는 경우로 좁혔다. 04-11 §2.2~2.5에 상태 원본과 재개 차이 명시 | 구조 차이 설명은 개선됐지만, 같은 품질 이익에 그 전체 교체가 꼭 필요한지는 미입증 |
| T도 선행 결과 뒤 RESOLVING으로 돌아갈 수 있지 않은가? | target의 WAIT_DEPENDENCY 전이를 다시 대조했다. 04-11 §2.1과 정상 흐름에 기존 재해석 능력을 명시. 후속 사건의 모델 판단 자체를 C만의 기능으로 쓰지 않음 | C의 독점적인 기능 이익은 아직 입증되지 않았으며 기존 graph 확장 반론이 더욱 중요 |
| Request Graph에 모델 재판단 노드만 추가하면 되지 않는가? | 가장 강한 국소 전환 반론으로 남겼다. 선택적 노드와 기존 receipt로 같은 이익을 얻으면 별도 대화 실행 원본이 불필요하다고 명시 | **열림.** C-대화를 강한 대안이나 선발 후보 확정으로 표시하지 않음 |
| C-대화가 모델에게 승인과 취소까지 맡기는가? | 즉시 hold, 질문 expiry, 실제 사용 권한, 전송 및 게시 검사는 Interaction Guard와 기존 owner의 코드에 남겼다. source-confirmed Task 사실도 유지 | 코드 검증이 의미 정확성을 전부 보장하지 않는 한계는 남음 |
| 로그를 남기기만 하면 정확히 복구되는가? | UNKNOWN 전송의 외부 조회가 먼저이고, 이어갈 의미상 동작은 모델이 다시 판단한다. 동일 기록의 다른 판단, 후속 누락과 표현만 바뀐 중복 목표를 미확인으로 기록 | 확인 가능한 복구까지 매번 사용자에게 떠넘기는 것은 정상 지원으로 세지 않음 |
| T도 비동기이고 connector 장애는 이미 격리하지 않는가? | C-독립의 이익을 단순 Agent/connector 실패에서 제거했다. 공유 Core owner/저장 실패에 대한 독립 실행만 남겼다 | 실제 단일 사용자 PC에서의 이익 크기 미확인 |
| C-독립의 전송 직전 권한 조회로 충분하지 않은가? | 조회와 전송 사이 철회 경합을 명시했다. 짧은 증표와 사후 보상도 즉시 차단의 대체가 아님 | 공통 순서 권위나 준비/확정 조정이 필요하고 독립성 비용을 다시 평가해야 함 |
| 독립 메시지의 빠른 진행과 동기 조정의 정확성을 동시에 장점으로 쓰지 않았는가? | 단순 비동기 형태는 B-06/08 부분 지원으로 기록. 엄격한 보완은 미완성 검토 방향으로 분리하고 같은 방안의 장점으로 합치지 않음 | C-독립 보류 |
| 진행 중 작업을 끝내면 전환이 쉬워지지 않는가? | 두 방향 모두 drain 후 사라지는 live migration 비용과 남는 진행/확정 의미 변경을 분리 | 데이터 이전비만으로 주요 자격을 주장하지 않음 |
| 기존 여섯 문서 작성비 때문에 유지하는가? | S-01~06의 주요 자격을 다시 판정. 문서와 기능 검토는 남기되 기존 리뷰 완료를 구조적 중요성 근거에서 제외 | 새 DP 수에 맞추거나 기존 번호와 일대일 대응하지 않음 |

## 2. 기능 지원과 손실

아래 `설계상 유지`는 계약을 보존한 제안이라는 뜻이며 구현 성공이 아니다. `미확인`은 지원 또는 동등으로 계산하지 않는다. T도 구현과 모델 능력이 측정된 안은 아니며 reviewed 설계 기준이다. 전체 요구 목록은 [02-00](./02-00-requirements-and-choices.md)과 [고정 UC](../../05-representative-use-cases.md)를 그대로 사용한다.

| 요구 묶음 | C-대화 | C-독립의 비동기 형태 | 손실/사용자 우회 |
| --- | --- | --- | --- |
| Voice/Text, 당시 화면 근거, 자체 지식 직접 S2S, 한정 자료 설명 | 공통 입력 및 S2S 설계상 유지. 근거 조회/설명의 의미 정확성 미확인 | 동일 입력과 모델 경로 설계상 유지 | 관측하지 않은 화면이나 source를 두 구조 모두 복원할 수 없음. 재지칭을 성공과 동등하게 세지 않음 |
| 불완전 요청, 정정, 여러 질문과 업무의 관계 | 사건별 판단으로 지원하려는 설계. 오결합과 후속 누락의 실제 지원 미확인 | 원장별 현재 상태가 달라지는 동안 질문 표시/상태 연결이 부분적 | 모호하면 질문, 누락은 미완료와 재시도. 추가 설명/재선택은 V-02와 시간 비용 |
| 독립 Task, 선행 결과 뒤 후속, Agent capability와 실제 상태 | Task/Execution identity와 capability 유지. 의미상 후속 재개의 정확성 미확인 | 내구 메시지로 지원하려는 설계. 원장 중단 중 접수와 실제 실행 상태를 구별 | 외부 UNKNOWN을 새 실행으로 대체하지 않음. 확인 불가와 지원 불가는 공통 실패 동작 |
| 새 발화의 로컬 stop, 미전송 hold, 실제 취소 결과 | stop와 hold 코드 경로 유지. 자연어 대상 판별 미확인 | 로컬 stop 유지. 대화 원장의 hold 확정 후 다른 원장 전송을 즉시 막는 기능은 **부분 지원** | 메시지 지연 사이 이미 나간 일은 취소 불가할 수 있음. 사용자가 사전에 취소해야 한다는 안내는 요구 충족 대체가 아님 |
| Text 기록, Voice 핵심, 실제 전달 범위 | Response Manager와 Interaction Manager의 전달 계약 유지 | 원장 간 적용 대기 추가. 전달 receipt의 의미 유지 | 모델 설명 실패는 확인된 상태 또는 원문 제공. 자료 설명 실패를 접수 멘트로 성공 처리하지 않음 |
| 권한 철회, 삭제한 기억의 신규 사용 차단 | 공유 epoch 검사 유지. Conversation Agent 기록/문맥 무효화 추가 필요 | owner별 적용 ACK 전의 신규 사용 차단은 **부분 지원**. 엄격한 보완은 미완성 | `적용 중` 표시가 즉시 차단과 동등하지 않음. 철회 후 노출은 사후 정정으로 없앨 수 없음 |
| 채널 종료/재시작 이후 확인 가능한 업무와 요청 복구 | 외부 Task 사실은 기존 계약 유지. 미완료 대화 목표 재판단은 **미확인** | 원장별 복구와 Agent 조회 이후 조정. 일관된 재개와 barrier 종료 조건은 **미확인** | 사용자가 요청을 다시 설명하는 우회 비용과 복구 실패를 남김. 모든 상황을 UNKNOWN으로 끝내면 요구 미충족 |
| 단일 Omni, 역할 격리, 의미 추론 중 새 음성 인식 | 같은 weights/ASR 경로 유지. 추가 loop 부하 아래 진행성은 미확인 | 같은 weights/ASR 경로 유지. process/메시지 부하 아래 진행성 미확인 | 더 많은 자원을 쓰는 사실을 제외하지 않으며 입력 유실은 실패 |

## 3. 두 구체 대안의 V-01~13 검토

품질 의미와 우선순위의 원본은 [03-00 §2](./03-00-quality-scenarios.md#2-어떤-품질을-보고-있는가)다. 아래는 **T 대비 인과 가설**이다. 수치, 별점, 가중 총점이나 실측 우위가 아니다. V-04/05에서 Agent 내부 실행과 사용자의 답변 대기는 외부 조건으로 구별하며 VIA 준비, 모델/자원 대기, 조정, 재처리와 전달은 포함한다. 두 부특성이 묶인 관점도 각각 설명한다.

| 공통 관점 | C-대화 | C-독립 |
| --- | --- | --- |
| V-01 기능 정확성 | 새 사건과 의미 관계를 함께 판단해 고정 계약에서 누락한 연결을 찾을 가능성. 반대로 이미 확정한 의도를 다시 해석하고 후속을 누락할 위험. 코드의 형식/권한 검증으로 정답 보장 불가. 실제 차이 미확인 | source-confirmed Task 사실은 유지. 서로 다른 owner의 적용 시점으로 hold/철회 경합 증가. 단순 형태의 오전송 위험은 구체 반례이며 빠른 성공으로 계산 불가 |
| V-02 기능 적절성 | 필요한 근거를 순서대로 얻어 재설명을 줄일 가능성. 불필요한 탐색과 이미 답한 질문 반복 가능성도 있음. 기존 재판단 노드로 같은 효과를 얻는지 확인 필요 | 일부 owner 장애 중 무관한 접수/조회가 계속되면 사용자 재입력 부담 감소 가능. 다만 부분 접수, 적용 중 철회와 불일치 질문이 조작/재확인 부담을 늘림 |
| V-03 기능 완전성 | 고정 요구를 모두 기준으로 유지. 지속 목적의 재개, 중복 방지와 모델 판단 capability는 미확인. 기존 T의 graph 기능을 없앤 손실을 유연성으로 덮지 않음 | 비동기 형태의 B-06/08 부분 지원과 정상 원장만 진행하는 한계를 §2에 명시. 엄격 보완의 기능을 구현된 지원으로 합치지 않음 |
| V-04 상호작용 반응성 | 적합한 다음 응답을 일찍 제안할 여지와 반복 모델 호출 지연이 함께 있음. 로컬 stop/hold는 공유하므로 그 자체 개선 주장은 없음 | 로컬 stop은 동일. 메시지 적용까지 hold/질문 종료/철회 효과가 늦어질 수 있음. 공통 순서 보완 시 왕복 및 장애 대기가 추가됨 |
| V-05 VIA 귀속 요청 완료 시간 | 형식 변환/재질문을 줄이는 경우 이익 가능. 결과 도착 후 모델의 다음 판단이 추가되므로 이미 정해진 후속의 해제는 T보다 늦어질 수 있음. 외부 업무 시간을 줄였다고 주장하지 않음 | 건강한 경로에서는 여러 원장 확정과 메시지 적용 비용 추가. 일부 Core owner 장애 중 무관한 처리 지연을 줄일 가능성. target도 이미 병렬 비동기이므로 평상시 병렬성 우위는 입증되지 않음 |
| V-06 자원 활용성과 수용량 | 사건 이력, 처리 원장, 문맥 재구성 및 반복 추론 비용. 추가 weights는 없음. 긴 이력이 KV/추론 예산과 동시 session 수를 제한할 수 있으며 최대 수용량 미확인 | 추가 process, 원장, inbox/outbox 중복과 조정 기록 비용. 공통 CPU/메모리/저장 장치 병목은 남음. 장애 중 backlog 한도가 수용량을 제한 |
| V-07 결함 허용성과 복구성 | Task 사실과 사용 권한은 코드 경로 유지. 모델 중단 중 다음 의미상 진행은 멈춤. receipt로 이미 처리한 사실을 보존해도 같은 다음 판단을 재현한다는 보장은 없음 | 내부 owner 장애를 격리할 가능성. 전체 PC/디스크 장애 격리는 아님. 독립 원장 간 불완전 관계와 UNKNOWN 결정의 복구 경우가 늘고, 엄격 조정은 관련 owner 장애에 다시 묶임 |
| V-08 변경 용이성과 모듈성 | 새 대화 변형을 모델 계약/prompt로 흡수할 가능성. 대신 모델 변경이 요청 연결, 다음 처리와 설명에 넓게 영향을 줌. 도구 schema, 원장과 guard의 공동 version 관리 필요 | owner 내부 변경은 국소화할 수 있음. owner 간 메시지 의미/버전, barrier 변경은 호환 기간과 여러 복구 경로를 함께 수정해야 함. 공유 transaction 결합 감소가 변경비 감소와 항상 같지는 않음 |
| V-09 분석 및 시험 용이성 | 원인 분석에는 판단 입력, 제안, 거절과 실제 receipt의 연결이 필요. 내부 사고 저장은 요구하지 않음. 시험은 동일 사건에서 다른 다음 동작을 제안하는 경우까지 판정해야 하므로 결정적 코드 재개보다 복잡 | 원인 분석에 원장별 확정/적용 순서와 correlation이 필요. 전역 clock 하나로 확정 순서를 추정하지 않음. 시험에 메시지 중복/역순, 원장별 crash와 부분 확정을 통제해야 함 |
| V-10 기밀성 | actual read/provide/publish 검사 유지. 장기 대화 입력과 KV가 정보 노출면을 넓힐 수 있어 삭제 의존성 및 재구성 필터 필요. 같은 모델 사용은 권한 공유가 아님 | 정책 복제와 철회 적용 지연이 신규 사용 위험을 만듦. 별도 process/DB라는 이유로 보호 향상을 주장할 수 없음. 즉시 차단 회복 비용을 별도 기록 |
| V-11 상호운용성과 공존성 | 상호운용: Agent canonical 계약은 유지하나 사건별 제안과 tool receipt를 모델 adapter가 지원해야 함. 공존: 반복 추론이 다른 PC 앱과의 연산/메모리 경합을 늘릴 수 있음 | 상호운용: 외부 Agent capability는 같은 기준. 내부 메시지 버전과 부분 상태 호환 부담 추가. 공존: process와 저장 I/O가 늘어 다른 앱 경합 가능 |
| V-12 조작 용이성과 사용자 오류 방지 | 기존 Task/질문 ID, 실제 제시 focus와 승인 digest 유지. 모델이 설명이나 후속 대상 선택을 틀리면 혼동 가능. 추가 확인이 필요한 경우 비용을 남김 | `접수`, `Agent 접수`, `철회 적용 중`, `확인됨`을 구별해야 함. 다른 원장의 오래된 질문 표시가 오류를 유발할 수 있어 terminal 시 전송 거절과 UI 갱신 필요 |
| V-13 설치 용이성 | 새 모델 weights 설치는 없음. 실행 계약, prompt, 도구 schema와 원장의 호환 배포/rollback 필요. 이를 설치 용이성 향상이라고 주장할 근거 없음 | 여러 process 및 원장 version의 설치, 갱신 순서, 제거/부분 실패 정리 부담 증가. 독립 갱신이 실제 이익이 되는 빈도는 미확인 |

어느 관점도 연결 여부만으로 점수를 부여하지 않았다. 후보별 로컬 진단이 필요해도 같은 QA의 정의, metric, 모집단과 방법을 바꿀 수 없다. 실제 검증은 공통 계약과 권한이 마련된 이후의 작업이다.

## 4. 전환 비용을 분리한 판정

| 구분 | C-대화 | C-독립 |
| --- | --- | --- |
| 새 기능 자체 개발 | model tool loop, 사건 입력 구성, 중복 목표 검사, 반복 제한. 이 개발량만으로 주요 구조 자격을 주장하지 않음 | 메시지 전달, retry, inbox/outbox, 상태 표시. 메시지 기술 도입량만으로 자격을 주장하지 않음 |
| 운영 중 이전 | 활성 graph/질문과 사건 기록 사이 이어갈 상태 변환. 기존 요청을 끝내거나 과도기 T 처리기로 남기면 감소 | 원장 분할/통합, 진행 command와 applied revision 이전. drain 및 새 요청부터 적용하면 감소 |
| 남는 핵심 설계 교체 | 의미상 후속 실행과 복구를 graph 전이에서 모델의 사건별 판단으로 옮길 경우 진행 원본과 계약 변화. **기존 graph 재판단 노드로 같은 효과를 낼 수 있다는 반론 미해결** | 여러 owner의 원자 확정을 독립 확정 후 조정으로 바꾸면 guard/command/권한/질문의 경합 및 복구 프로토콜 변화. 명확한 차이이나 정확성 손실을 막을 추가 설계가 필요 |
| T가 유리한 조건 | 명시적 관계와 bounded 해석으로 충분한 대화 범위를 지원하고 예측 가능한 후속/복구가 중요 | 단일 PC에서 짧은 local transaction으로 정확성과 응답성이 충분하고 공동 장애가 감수 가능 |
| C가 유리할 조건 | 고정 계약에 걸리는 중요한 의미 관계가 실제로 많고 사건별 판단이 사용자 재작업을 줄이며 추가 추론/복구 비용을 감수 가능 | 내부 owner의 독립 장애/변경 중 무관한 업무를 계속할 가치가 높고 엄격 조정의 비용까지 감수 가능 |
| 주장의 반증 | 기존 T의 작은 확장으로 같은 이익을 얻음, 후속 누락/반복과 추가 VIA 대기가 이익을 상쇄, 실제 부족한 대화 범위가 없음 | target의 기존 격리로 문제 충분히 해결, 엄격 hold/철회 조정이 독립성 이익을 제거, 추가 메모리/조정 부담이 더 중요 |
| 현재 판정 | **다른 계열 가능성 검토 중. 우선 사용자 검토 방향. 강한 후보 확정 아님** | **보류. 구조 차이만으로 선발하지 않음** |

특정 feature가 있느냐보다 전체 진행과 확정 원리가 달라지는지 살폈다. 동시에 원리를 다르게 그렸다는 사실만으로 선택할 필요가 있다고 결론내리지 않았다. 이번 탐색은 주요 DP 후보를 확정하지 못했다.

## 5. 검증 범위와 다음 체크포인트

작성자 대조는 target의 실제 Component 책임, 기존 비동기와 transaction 경계, 고정 요구 B-01~09, P-01~16과 V-01~13을 기준으로 했다. 외부 source의 구현이나 특정 framework의 capability를 검증한 작업은 아니다. 전환 공수와 품질 효과의 수치는 산출하지 않았다.

문서 검사는 실행 후 [00-workplan](./00-workplan.md)의 현재 실행 기록에 남긴다. 자동 검사는 링크, 용어, QA catalog와 기존 그림의 생성물 일치를 확인할 뿐 대안의 구조적 중요성이나 모델 기능을 증명하지 않는다. 이번에는 비교 그림을 새로 만들지 않았다. 아직 자격이 열린 후보를 상세 도식의 완성도로 포장하지 않기 위해 먼저 흐름과 계약을 검토했다.

**이번 사용자 보고는 여기까지다:** 원칙을 먼저 GitHub에 게시했고, 기존 계열을 분류했으며, 두 방향의 정상/정정/철회/실패/재시작과 싼 양방향 전환을 검토했다. C-대화의 구조적 필요성은 미결, C-독립은 보류라는 결론을 그대로 보고한다. Stage 4 전체 완료, Stage 5 착수나 DP 선발을 선언하지 않는다.

다음 사용자 검토에서 우선 확인할 자료는 04-11 §2.5의 **기존 Request Graph에 모델 재판단 노드를 추가하는 가장 싼 반론**이다. 이것으로 같은 품질 이익을 얻는다면 C-대화도 계열 내부 선택으로 내리고 새로운 해결 원리를 탐색해야 한다. 이 반론을 사용자에게 해결하도록 떠넘기지 않으며, 후속 작업에서는 구체적인 대화 사례와 양쪽 상태 전이를 더 대조할 출발점으로 사용한다.
