# QA01~06 목표 수치 도출 논리

> 2026-10-14 / 제품 요구 제안 / 출처 확인 및 문서 검토 / 구현과 PoC 측정 전

**목표는 구현에 필요한 시간을 나눠 정하는 값이 아니라 사용자나 제품이 요구하는 수준이다.** 이 문서는 확인한 외부 사실과 VIA에 적용하는 제품 판단을 연결한다. 실제 stakeholder 합의나 VIA 실측 결과가 없는 부분을 이미 합의했거나 달성한 것으로 표현하지 않는다.

읽는 순서는 이 문서 → [발표용 표](./quality-requirements-table.md#presentation-table) → 각 QA 상세안이다. [패키지 README](./README.md#4-qadp-대응과-예상-우열)에서 QA와 DP의 대응 및 예상 손익을 함께 확인한다. QA07~09는 별도 보조 후보로 유지하며 이번 목표 근거 재작성은 핵심 여섯 QA를 대상으로 한다.

## 2. QA01: 왜 1초인가

**사용자는 입력이 어떻게 이해됐는지 확인하고 생각과 행동을 이어갈 수 있어야 한다.**

- [Nielsen, Response Times: The 3 Important Limits, 1993](https://www.nngroup.com/articles/response-times-3-important-limits/)은 약 1초를 사용자의 사고 흐름 유지에 관한 UI 응답 지침으로 설명한다.
- [Microsoft Windows 응답성 지침, 2026-03-18 갱신](https://learn.microsoft.com/en-us/windows/apps/develop/performance/responsive)은 `Pause` 0.5~1초를 지연은 있지만 응답성이 유지되는 범위로 설명한다.
- VIA의 종료점은 해당 요청이나 업무 화면에 **첫 완결된 정답 내용이 보이는 때**다. 이 UI 동작에 위 지침을 적용하여 **1초 이하**를 요구한다.

평균 1초는 20초 걸린 한 사건을 수십 개의 빠른 사건으로 가릴 수 있다. 따라서 대표 사례 30개와 반복 3회의 **최대값**으로 판정한다. 한정된 시험에서 관측한 최대값이며 모든 미래 요청의 수학적 최악 시간을 보장하는 것은 아니다.

**심사 답변:** “생각과 행동의 흐름을 유지할 UI 반응 수준을 외부 HCI 지침에서 가져왔습니다. 인사나 로딩 표시를 제외한 첫 내용 표시를 1초 안에 제공하도록 요구합니다.”

**예시:** 발화 종료 0초 → ‘네’ 표시 0.1초 → 채택한 비교 수행 안내 0.8초 → Agent 전송 1.3초 → 음성 요약 재생 2.5초라면 해당 사건은 0.8초다. Agent 위임 완료나 음성 차례를 첫 표시의 종료점으로 사용하지 않는다.

## 3. QA02: 왜 93%인가

**화면과 대화 속 표현이 가리키는 대상 집합을 찾는 연구를 수치 참조로 삼는다.** 마우스로 표시된 표적을 누르는 운동 과제의 98.7%를 옮긴 이전 논리는 철회했다.

[Apple ReALM, SIGDIAL 2024](https://aclanthology.org/2024.sigdial-1.5.pdf)은 화면과 이전 대화에서 사용자가 가리키는 대상을 해석한다. §3은 예측 대상 집합과 정답 집합이 전부 일치해야 성공으로 센다. Table 3에서 ReALM-3B는 **화면 93.0%와 대화 97.9%**를 보였다. 화면 결과 중 가장 높은 전용 해석 모델의 93.0%를 관련 기술 참조로 선택하고 두 DP의 공통 최소 목표를 **93%**로 제안한다. 화면과 대화 점수를 평균내지 않는다.

**적용 한계:** 집합 완전 일치 원리는 같지만 ReALM은 질의별 집합이고 VIA는 지칭 표현별 집합과 revision이므로 평가 단위도 다르다. ReALM은 상위 처리에서 찾은 후보 항목과 유형 및 위치를 입력으로 받는다. VIA는 화면 증거 수집과 포인터 시간 관계 및 범위와 부분 정정까지 처리해야 한다. DP-45의 과거 원본 조회와 버전 해석도 논문의 앞선 대화 항목보다 넓다. 연구의 일부 복수 정답은 모호한 표현의 가능 후보 집합이다. VIA의 동시에 의도한 복수 대상과 완전히 같은 구성은 아니다.

**심사 답변:** “화면과 대화의 지칭 대상을 찾는 ReALM과 같은 집합 완전 일치 판정을 사용합니다. 해당 연구의 최고 화면 성능 93.0%를 기술 참조로 잡아 VIA에도 93% 이상을 요구합니다. 연구가 VIA 전체나 사용자 만족을 검증했다고 주장하지는 않습니다.”

**예시:** 정답 `{표 A, 그래프 B}`에 `{표 A}`나 `{표 A, 그래프 C}`는 실패다. 100판정 중 93개가 전체 정답 집합과 같으면 93%로 1점이다. 동일 사례 반복은 독립 사용자 모집단의 신뢰구간을 입증하지 않는다. 일반 Agent benchmark의 성공률을 VIA 실패의 복구율로 바꾸어 99%를 만들지 않는다. [출처 조건과 제외한 수치](./research-notes/qa02-accuracy-research.md)

## 4. QA03: 왜 5초인가

**VIA는 일의 실행을 연결하는 인터페이스이므로 자체 처리가 장시간 대기를 만들어서는 안 된다.**

[Microsoft Windows 지침](https://learn.microsoft.com/en-us/windows/apps/develop/performance/responsive)은 `Long wait`를 **2~5초**, 불가피하게 길고 복잡한 상황의 `Captive`를 **5~10초**로 분류한다. VIA의 해석과 상태 연결 및 응답 준비가 Long wait의 상단을 넘어 Captive 구간의 대기를 추가하지 않도록 **5초를 자체 처리의 상한**으로 채택한다. 이 값이 자연스럽거나 빠른 대화라는 뜻은 아니다. 첫 내용 반응은 QA01에서 1초를 요구한다.

입력부터 모든 VIA 처리와 상세 텍스트 표시 및 음성 요약 준비까지의 완료 경로에서 외부 Agent의 도메인 작업과 사용자 대기 시간을 제거한다. 12목표를 5회 수행한 귀속 처리시간의 **최대값**을 평가한다. 외부 업무가 없는 직접 응답은 실제 완료 지연과 일치한다. 위임 업무에서는 전체 대기에서 VIA가 소유한 처리 경로의 예산이다.

**심사 답변:** “해석 단계에 임의 시간을 배분해서 5초를 만든 것이 아닙니다. Windows가 구별하는 장시간 대기의 경계 5초를 가져와 VIA 자체 처리의 한계로 적용했습니다. 외부 업무까지 5초에 완료한다는 주장은 하지 않습니다.”

**예시:** VIA 1.2초 → 외부 작업 8초와 VIA 준비 3초가 병렬 → VIA 0.6초라면 실제 완료는 9.8초다. 외부 작업을 0초로 둔 VIA 경로는 `1.2 + max(0,3) + 0.6 = 4.8초`다. 이를 실제 경과시간에서 단순히 8초 빼서 1.8초로 보고하지 않는다.

## 5. QA04: 왜 평균 3개 모듈인가

**기존 Agent 개발에서 발생한 변경 파급을 줄인다는 요구다.** 사용자가 제공한 ARGO 집계는 기능 추가와 데이터 형식 변경 PR 145건에서 평균 수정 모듈 수 **5.4개**다. 사용자가 정한 40% 개선 목표를 적용하면 `5.4 × 0.60 = 3.24개`이며 제시된 최종 상한 **3개**를 채택한다. [ARGO 근거 기록](./targets-source-qa04-argo.md)

3개는 5.4개 대비 약 **44.4% 감소**이므로 40% 개선을 충족하는 더 엄격한 목표다. 평균이 정수여야 해서 반올림한 것이 아니다. 40%는 사용자가 지정한 개선 요구이며 논문이 제시한 보편적 개선율이 아니다.

**출처 상태:** PR 145건을 이 작업에서 직접 열어 분석하지 않았다. 사용자 제공 내부 집계라는 상태를 표시한다. 향후 실제 개선율을 검증할 때는 대상 PR 목록과 집계 기간 및 모듈 정의를 확보해 VIA의 Rust 운영 모듈 기준과 비교 가능성을 확인해야 한다. 기존 VIA의 1개와 3개 변경 사례는 계수 방법 예시로만 남긴다.

**심사 답변:** “기존 ARGO의 145건 평균 5.4개를 기준으로 변경 파급을 40% 이상 줄이려는 요구입니다. 계산값 3.24보다 엄격한 평균 3개를 상한으로 정했습니다.”

**예시:** 변경 6건에서 `2,2,3,4,3,4`개를 수정했다면 평균 3개다. 이는 설명용 숫자이며 실제 후보의 측정값이 아니다.

## 6. QA05: 왜 활동당 $0.71인가

**정의한 사용자 활동을 범용 API 구성의 참조 원가 이내로 제공한다는 요구다.** 음성 모델은 사용자가 지정한 `gpt-realtime`이며 기존 Luna 백엔드는 유지한다. [사용자 활동 20건](./user-activity-20.md)은 화면 6건과 과거 6건 및 업무 제어 4건과 직접 질의 4건에 Agent 사건 6건을 더한 입력 명세다. 고객의 하루 이용량이나 월 구독료가 아니다.

| 항목 | 참조 조건 | 금액 |
| --- | --- | ---: |
| Realtime 텍스트 입력 | 제어 46,000토큰 + 채택 응답 13,000토큰. $4/100만 토큰 | $0.2360 |
| Realtime 텍스트 출력 | 원 발화 전달 2,000토큰 + 음성의 텍스트 1,300토큰. $16/100만 토큰 | $0.0528 |
| Realtime 음성 입력 | 120초 × 약 10토큰/초. $32/100만 토큰 | $0.0384 |
| Realtime 음성 출력 | 130초 × 약 20토큰/초. $64/100만 토큰 | $0.1664 |
| Luna 텍스트와 화면 입력 및 출력 | 기존 26회 × 20,000입력/추론 포함 총 청구 출력 500과 화면 90장 | $0.2131 |
| **합계와 목표** | **$0.7067 → 센트 단위 올림** | **$0.71** |

[gpt-realtime 공식 단가](https://developers.openai.com/api/docs/models/gpt-realtime)와 [음성 환산 규칙](https://developers.openai.com/api/docs/guides/voice-latency-cost?voice-api=realtime)을 사용한다. Realtime은 모든 Response에 대화 밖 출력 설정과 명시적 입력을 함께 사용하며 원본 의미 맥락은 Luna에 제공한다. 자동 응답과 별도 전사 모델을 추가하지 않은 참조 구성이다. [상세 계산과 입력 가정](./qa05-model-cost.md)

**심사 답변:** “화면과 과거 내용의 질의를 포함한 20요청을 음성과 의미 API로 제공하는 참조 견적이 $0.7067입니다. 이를 기준으로 자체 VIA의 모델 원가를 $0.71 이내로 관리하려는 제안입니다.”

**검증 한계:** 단가는 공식 자료이나 토큰 수와 음성 길이는 미실행 견적 규격이다. 기능 동등성이나 실제 청구 상한을 입증하지 않는다. 준비와 재시도 및 누적 이력과 마지막 요청 이후 청구는 실제 후보 비용에 모두 포함한다. 필요한 입력이 견적 규격을 넘으면 결과 비교 전에 참조도 개정한다.

## 7. QA06: 기존 512MiB를 철회한 이유

**동종 제품의 공개 RAM 수치로 방어할 수 없었다.** PowerToys는 명령 실행 UI이고 Vosk와 Orca는 인식과 합성의 부분 기능이다. 이들의 수치를 나열해 VIA의 통합 기능에 허용할 RAM을 정하는 논리를 철회한다.

기능 비교 제품은 **Windows Copilot Voice와 Vision**이다. 공식 설명에서 Windows의 음성 대화와 화면 공유 기능은 확인했지만 같은 사용자 활동의 전체 RAM 최고량이나 앱에 적용하는 공식 한도는 찾지 못했다. ChatGPT Windows와 삼성 Galaxy Book의 Bixby에서도 해당 수치를 확보하지 못했다. [제품별 확인 자료와 제외한 수치](./research-notes/qa06-memory-research.md)

따라서 QA06은 **`TARGET_EVIDENCE_UNRESOLVED`**다. 근거 있는 절대 목표를 요구받았지만 현재 조사로 그 부분을 완성하지 못했다. 임의의 새 MiB와 점수를 넣지 않는다. 512MiB와 RAM-v1 점수는 철회 이력으로 남긴다.

**정의와 측정할 일은 명확히 한다.** Windows 11에서 화면 6건과 과거 6건 및 업무 제어 4건과 직접 질의 4건에 Agent 사건 6건이 겹치는 [활동](./user-activity-20.md)을 5회 수행한다. 앱 시작부터 후속 처리 종료까지 전체 VIA의 같은 시점 RAM을 공유 중복 없이 합한 최고량이다. 계측 구현도 미검증이다.

**남은 근거:** 같은 삼성 노트북에서 동종 제품의 공통 기능을 측정하고 VIA의 추가 기능과 다른 앱의 공존 영향을 확인해야 방어 가능한 제품 상한을 정할 수 있다. 이 문서 수정에서 그 측정을 수행하지 않았다.

**예시:** 같은 시점의 합계가 380MiB와 400MiB였다면 최고량은 400MiB다. 서로 다른 시점의 프로세스 최고값을 더해 420MiB로 보고하지 않으며 현재 점수로 변환하지 않는다.

## 8. 변경과 평가 규칙

- QA01과 QA03의 평균을 최대값으로 바꿨으므로 기존 평균 결과와 점수를 그대로 옮기지 않는다. DP의 재사용 평균 이익만으로 최대값 이익을 주장하지 않는다.
- QA02는 부적절한 마우스 참조 99%를 철회하고 ReALM 참조 93%로 바꿨다. 반복 fixture 100판정은 독립 사용자 100명의 증거가 아니다.
- QA04는 기존 1개와 5개 가정을 폐기한 상태를 유지한다. 평균 3개의 직접 근거는 사용자 제공 ARGO 집계와 개선 요구다.
- QA05는 정의한 20요청 활동의 내용과 가격표를 버전으로 고정해야 한다. 다른 활동량이나 단가에 같은 금액을 자동 재사용하지 않는다.
- QA06의 이전 확보량 1GiB는 재사용하지 않는다. 512MiB 목표와 RAM-v1 점수도 철회했다.
- QA06을 제외한 현재 점수표에서 0점은 목표 미달이며 1~6점은 목표 충족과 개선 여유다. 중간 경계는 비교 표현 규칙이며 논문이 정한 합격선으로 제시하지 않는다.
- 목표에 맞춰 측정값이나 실패를 고치지 않는다. 실제 수치가 예상과 다르면 경계와 구현의 대등성을 검토하고 정당한 결과를 보존한다.
