## 1. 발표에서 설명할 한 문장

**입력이나 업무 사건이 발생한 뒤 그 내용을 반영한 첫 응답이 화면에 표시되기까지 걸린 시간의 최대값을 평가한다.**

| 항목 | 제안 |
| --- | --- |
| QA 이름 | 첫 응답 지연시간 |
| 단일 지표 | 최대 첫 응답 지연시간 `L` / 대표 시험 집합의 최대값 / 초 / 작을수록 좋음 |
| 목표 | `L ≤ 1.00초` |
| 측정 시작 | 실제 사용자 발화 종료 또는 텍스트 제출 또는 외부 업무 사건의 최초 소비 가능 시점 |
| 측정 종료 | 해당 Request/Task UI에 첫 완결된 정답 내용 단위가 실제 표시된 시점 |
| 제외하는 응답 | 인사, 알림음, spinner, 빈 카드, 의미 없는 첫 토큰, 미채택 계획, 사실과 다른 완료 안내 |
| 연결 | 44의 주된 검토 축. 47과 45에도 동일 의미로 적용. 42는 동점 예상으로 핵심 연결에서 제외 |

이 QA는 **사용자가 화면에서 요청의 해석이나 처리 내용을 확인할 수 있게 되는 대기**다. 화면을 보지 않는 사용자가 음성을 실제로 들은 시각이나 업무가 완전히 끝난 시각을 뜻하지 않는다. 두 상황은 [QA09](./qa09-audio-delivery-lag.md)와 [QA03](./qa03-via-processing-time.md)에서 각각 다룬다.

## 2. 왜 1순위인가

VIA는 말과 화면으로 요청하고 업무가 진행되는 동안 다시 개입할 수 있게 하는 interaction software다. 첫 내용 응답이 늦으면 사용자는 자신의 말이 해석됐는지 알기 어렵고 반복 요청하거나 기다리게 된다. 반면 첫 안내만 빠르고 뒤 처리가 느린 문제는 QA03이 평가한다. 빠른 오답을 우수한 응답으로 인정하지 않기 위해 이 QA의 종료점도 정답 조건을 만족해야 한다.

**1순위의 근거는 사용자 가치다. 네 DP에서 자동으로 가장 큰 차이가 난다는 뜻은 아니다.** 현행 44는 실행 연결을 직접 바꾸므로 이 QA를 주된 목표로 삼을 수 있으나 강한 A와 B의 실질적 차이는 아직 입증되지 않았다. 그 약점을 1순위라는 이름으로 덮지 않는다.

## 3. 첫 응답으로 인정하는 내용

문자열 일치 대신 사전에 적은 의미 판정표로 평가한다. 각 사례에는 `event_id`, 관련 Request/Task와 revision, 정답 대상과 범위, 실제 처리 단계, 필요한 확인 사항을 기록한다.

| 종류 | 인정 조건 | 예시 |
| --- | --- | --- |
| 구체적 수행 안내 | 대상과 범위 및 수행할 내용이 실제로 채택됨 | “선택한 매출표와 비용 그래프를 비교하겠습니다.” |
| 직접 답변 | 질문의 핵심에 해당하는 첫 완결된 내용이 맞음 | “선택한 셀의 합계는 120입니다.” |
| 확인 질문 | 원본만으로 해결할 수 없는 모호함을 구체적으로 좁힘 | “위 그래프와 아래 그래프 중 어느 것을 말씀하셨나요?” |
| 업무 상태 | 확인된 상태와 해당 업무를 정확히 연결함 | “보고서 업무에서 자료 접근 권한을 요청했습니다.” |
| 업무 결과 | 확인된 결과의 첫 내용을 해당 업무에 정확히 연결함 | “보고서가 완성됐고 결과 파일은 R7입니다.” |

`이것을 처리하겠습니다`처럼 미해결 지칭을 되풀이하거나 `네`, `알겠습니다`, `처리 중입니다`만 표시하면 인정하지 않는다. 명확한 요청에 불필요한 확인 질문을 하거나 처리 능력이 있는데 근거 없이 거절하는 것도 인정하지 않는다. 카드에 보이는 선택 강조와 문장을 함께 읽으면 대상을 유일하게 확인할 수 있는 경우는 문장에 긴 고유 ID를 나열할 필요가 없다. 그 강조 영역도 표시 증거에 포함한다.

**위임은 선행조건이 아니다.** 채택한 수행 안내는 Agent 전송 전에 표시할 수 있다. `요청을 보냈습니다`, `Agent가 접수했습니다`, `완료했습니다`는 각각 전송, 확인된 접수, 확인된 완료 이후에만 맞는 내용이다. VIA가 이해한 작업 연결을 도메인 작업 완료로 바꾸어 안내해서는 안 된다.

streaming 출력은 첫 토큰에서 시계를 멈추지 않는다. 예를 들어 “매출표와…”만 보이면 미완결이고 “매출표와 비용 그래프를 비교하겠습니다.”까지 보이면 완결이다. 정답 의미가 완성된 첫 프레임을 종료점으로 한다. 접속 뒤 나올 부정이나 조건을 생략하면 의미가 바뀌는 조각은 완결로 인정하지 않는다.

### 정정과 오답의 처리

- 입력 revision마다 별도 평가 사건을 정한다. 수정 전 요청의 응답을 새 정정의 응답으로 재사용하지 않는다.
- 이미 보인 오답을 0.4초에 철회하고 1.2초에 처음 정답을 보였다면 지연 원값은 1.2초다. 앞선 오답 기록과 기능 검증 실패는 그대로 남긴다. 뒤 정답이 앞 오답을 지우지 않는다.
- 새 입력으로 정상 폐기된 이전 후보는 정답 응답 의무가 있는 평가 사건과 구별한다. 어떤 사건의 응답 의무가 사라지는지는 fixture의 사전 상태 전이로 정한다. 후보가 임의로 폐기했다고 분모에서 빼지 않는다.
- 여러 상태 사건을 하나의 카드 갱신으로 합쳐도 각각의 지정 사건이 요구한 내용과 현재성을 만족하는지 판정한다. 후보가 잘게 쪼갠 알림 수로 분모를 늘리지 않는다.

## 4. 시계의 시작과 끝

| 입력 | `t0` | 포함하는 대기 |
| --- | --- | --- |
| 음성 | 녹음된 발화의 실제 마지막 음성 sample 시각 | endpoint 판단, 전사 확정, 입력 전송과 해석 및 UI 표시까지 |
| 텍스트 | UI의 제출 동작 시각 | 입력 수용, 해석, 채택 및 UI 표시까지 |
| Agent 사건 | 시험용 외부 Agent source interface에서 사건을 처음 제공할 수 있게 된 시각 | polling 발견, 전달, 원본 상태 확인, 대화 연결과 UI 표시까지 |

사용자가 중간에 쉬었다가 계속 말하는 구간을 발화 종료로 잘못 잘라 시간을 줄이지 않는다. 음성 fixture는 입력 시작 / 실제 종료와 정정 관계를 사전 표기한다. 새 사용자의 발화가 계속되는 중에도 다른 업무의 확인된 사건은 텍스트로 표시할 수 있다.

`t1`은 지정 응답 영역의 **실제 표시 프레임**이다. 문자열 생성 완료, response queue 삽입, UI API 호출 반환, DOM/state 변경만으로 실제 표시를 대신하지 않는다. 계측에는 표시 프레임과 응답 ID/revision을 연결하는 receipt와 화면 기록을 남긴다. 한정된 PoC에서는 Windows UI 하나와 재생 fixture로 충분하다. 표시까지 구현하지 않은 실행망 측정은 내부 지연 진단으로만 보고한다.

Agent fixture와 VIA를 같은 호스트의 monotonic clock에 놓는 것을 최소 PoC의 기본으로 제안한다. 실제 원격 Agent를 쓰면 clock 동기화 오차와 송신측 timestamp의 의미를 함께 증명해야 한다. 증명하지 못하면 로컬 수신 시간을 원래 시작점인 것처럼 사용하지 않는다. 화면 표시 관측과 clock의 지연값 오차 상한을 후보별로 기록한다. 10ms는 제안하는 계측 해상도이지 실제 오차가 더 큰 장치에도 적용하는 고정 면책값이 아니다. 오차 상한을 정할 수 없으면 UI 원값을 참고용으로 남기고 대안의 시간 차이는 판정 보류한다.

**음성 요약의 재생 대기는 이 시계의 종료 조건이 아니다.** 텍스트는 상세 내용을 해당 UI에 남기고 음성은 사용자가 들을 수 있을 때 요약한다. 음성 준비 / 실제 전달과 stale 요약 차단은 별도 검증을 유지한다. 빠른 텍스트만 만들고 음성을 생략하는 후보는 공통 기능을 충족한 대안이 아니다.

## 5. 산식과 실패

사전 지정된 응답 의무 사건과 반복을 모두 포함한 `N`개에 대해 `l_i = t1_i − t0_i`, **`L = max(l_1, …, l_N)`**이다. 같은 사례는 양안에 같은 횟수로 들어간다. 수치는 반올림 전에 계산하며 단위는 초다. 사전 처리로 음수 지연이 생기는 것을 막기 위해 의미 채택 이전에 표시한 잠정 내용은 종료점으로 인정하지 않는다. 정당한 선행 준비는 허용하되 확정 입력에 대한 최종 채택과 표시를 확인한다.

**관측 상한 제안은 사건당 30초다.** 이는 사용자 허용시간이나 목표가 아니라 시험 종료 규칙이다. 30초까지 정답 표시가 없으면 해당 `l_i = +∞` 판정값을 사용하며 최대값 `L = +∞`와 0점을 기록한다. 실제 무한 대기를 관측했다는 뜻은 아니다. 실패가 있는 실행의 성공 표본 평균과 최대값은 진단으로 별도 표시하고 전체 시험 집합의 최대값으로 대체하지 않는다. 실패 표본을 버리거나 임의의 유한 시간으로 바꾸지 않는다. 30초 이후의 늦은 응답도 기록하되 해당 실행을 소급 합격시키지 않는다.

이 엄격한 규칙은 **필수 사례에 대한 응답을 빠뜨리지 않는 후보끼리 지연을 비교한다**는 평가 제안이다. 한 번의 실패로 시간 점수가 0이 되는 비용을 의도적으로 수용한다. 평균과 실패율을 가중 결합한 지표는 만들지 않는다. QA02의 정확도 표본과 같은 모집단을 강제하지 않으며 성능 비교의 실패 사실을 정확도 결과에서도 숨기지 않는다.

응답내용 판정에 이견이 있으면 근거 프레임과 사전 oracle을 두 검토자가 확인한다. 합의하지 못한 표본은 임의로 성공이나 실패로 정하지 않고 해당 비교를 `판정 보류`로 보고한다. 계측 누락도 후보의 빠른 성공으로 간주하지 않으며 원인을 보존한 뒤 양안의 대응 표본을 재측정한다. 미측정 / 증거 부족은 0점이 아니다.

평균으로 합격을 정하면 긴 대기를 빠른 사례로 상쇄할 수 있다. 예를 들어 29건이 0.2초이고 1건이 20초이면 평균은 0.86초지만 **이번 지표는 최대 20초이므로 0점**이다. 유형별 원값과 분포, 평균, 1초 초과 사건 수는 진단으로 함께 공개한다.

최대값은 **정한 장치와 부하 및 시험 집합에서 관측한 상한**이다. 실제 모든 사용자와 모든 미래 요청의 최악 시간을 증명한 값이 아니다. 시험 사례나 반복 수가 달라지면 최대값의 비교 조건도 달라지므로 같은 모집단과 반복 수를 유지한다. 실제로 발생한 느린 사례를 이상치라는 이유로 삭제하지 않는다. 계측 오류를 증명한 경우에만 양안의 대응 시험을 다시 수행하고 이전 기록을 남긴다.

## 6. 목표 1초의 근거

### 사용자 요구에서 숫자까지

**사용자는 자신의 말이 어떻게 이해됐는지 확인하고 다음 생각과 행동을 이어갈 수 있어야 한다.** 이 요구는 사용자와 CTO/담당임원의 빠른 대화 및 올바른 요청 이해 요구에서 나온다. 아래 수치는 그 요구를 만족시키기 위해 제안하는 제품 기준이며 stakeholder가 숫자까지 합의했다는 기록은 아니다.

| 단계 | 근거와 판단 |
| --- | --- |
| 사용자 경험의 기준 | Nielsen(1993)은 약 1초를 지연을 느끼면서도 사고 흐름을 이어갈 수 있는 UI 응답 지침으로 제시한다. |
| Windows 적용의 확인 | Microsoft의 현재 Windows 성능 지침도 `Pause`를 0.5~1초로 분류하며 응답성이 유지되는 범위로 설명한다. |
| VIA의 측정 경계 | 첫 완결된 정답 내용이 Request/Task 화면에 표시되는 시간을 잰다. Agent 업무의 완료나 음성 재생을 1초 안에 끝내라는 요구가 아니다. |
| 제품 목표 | 대표 시험의 모든 지정 사건이 이 기준을 만족하도록 **최대 첫 응답 지연시간 1초 이하**를 제안한다. |

숫자 1초를 먼저 정한 뒤 모델과 코드에 나눈 것이 아니다. **화면에서 생각과 행동을 이어가는 데 필요한 외부 UI 지침을 VIA의 첫 내용 표시 요구에 적용했다.** 평균으로는 개별 사건의 긴 대기를 숨길 수 있으므로 시험 집합의 최대값으로 판정한다. 실제 구현의 달성 여부는 아직 측정하지 않았다.

### 출처와 적용 범위

## 7. 0~6점 — `QA-C01-score-v2`

| 점수 | 원형 | 최대 `L` / 초 |
| --- | --- | --- |
| 0 | ○○○ | `L > 1.00` 또는 필수 사건 미응답으로 `L = +∞` |
| 1 | ◐○○ | `0.84 < L ≤ 1.00` |
| 2 | ●○○ | `0.68 < L ≤ 0.84` |
| 3 | ●◐○ | `0.52 < L ≤ 0.68` |
| 4 | ●●○ | `0.36 < L ≤ 0.52` |
| 5 | ●●◐ | `0.20 < L ≤ 0.36` |
| 6 | ●●● | `0 ≤ L ≤ 0.20` |

0.2초는 1초보다 80% 짧은 도전 수준으로 제안한다. 0.2~1.0초 사이의 0.16초 간격은 개선 정도를 표시하는 평가 규칙이며 각 경계가 별도 연구에서 도출됐다는 뜻이 아니다. v1의 수치 경계를 유지하되 최대값을 채점하는 v2로 변경했다. 과거 평균 점수를 그대로 이전하지 않는다.

음수는 계측 또는 계약 오류로 채점하지 않는다. 점수는 시험 집합의 최대값을 요약하며 기능 위반을 숨기는 종합 성적이 아니다. 원값이 달라도 같은 점수일 수 있다. 점수 차이가 없다고 원값 차이를 지우거나 점수 차이를 만들기 위해 경계를 바꾸지 않는다.

## 8. 이해 예시

**가상 예시이며 측정값이 아니다.** 사용자는 선택한 매출표와 비용 그래프의 비교를 요청했다.

```text
0.0초  사용자 발화 종료                      ← 시작
0.1초  “네” 표시                            (제외)
0.8초  “매출표와 비용 그래프를 비교하겠습니다.” 표시 ← 첫 정답 내용
1.3초  Agent에 요청 전송
2.5초  앞 발화가 끝나 음성 요약 재생
```

이 사건의 지연은 **0.8초**다. 사례 한 건을 전체 시험의 최대값인 것처럼 채점하지 않는다. 별도 4건으로 구성된 가상 시험 집합의 지연이 `0.8, 0.6, 1.0, 0.8초`이면 **최대값은 1.0초이고 1점 ◐○○**이다. 평균 0.8초는 진단값이며 채점에 사용하지 않는다. Agent 전송 1.3초와 음성 시작 2.5초는 이 QA의 종료점이 아니다.

## 10. 최소 PoC와 차이 판정

1. 각 DP의 두 경로와 같은 UI 한 개를 만든다. 입력 replay, Task 사건 fixture, 모델 adapter와 음성 output stub을 공통 사용한다. 내용 정답을 미리 주는 stub은 실행망 지연만 검증한다. 47의 해석 차이까지 주장하려면 실제 두 해석 경로와 같은 모델 조건이 필요하다.
2. A/B는 같은 원본, 동일 모델 / 가격표 / 호출 제한과 주변 기능을 사용한다. 호출 수, 의존 단계, cache/생산물은 구조가 결정한 대로 다르게 허용한다. 그 비용을 숨기지 않는다.
3. 사건 순서를 고정하고 A/B 실행 순서를 균형 배치한다. 사례30개 × 반복3회를 제안한다. 추가 반복이 필요하면 양안 전체에 적용하고 유리한 반복만 남기지 않는다.
4. `case_id`, `event_id`, `request/task_id`, `revision`, `t0`, 내용 채택, 각 await/queue 구간, 모델 call, UI enqueue, 실제 frame/receipt, oracle 판정, timeout, 앞선 오답, 음성 준비/가능/재생을 기록한다.
5. 전체 90건의 최대값과 그 값을 만든 사건을 공개한다. 작성자 제안의 실용 차이 기준 `δ`는 **100ms 또는 느린 안 최대값의 10% 중 큰 값**이다. 이는 1초 목표의 10% 이상을 구별하려는 비교 규칙이며 HCI의 확정 체감 차이가 아니다. 관측 최대값 차이 `Δ = L_slow − L_fast`에서 양안의 보수적 결합 오차 상한 `U = u_A + u_B`를 뺀 값이 `δ` 이상이어야 한다. `u_A`와 `u_B`에는 각 안의 모든 표본에 적용되는 최대 계측 오차를 사용한다. 120ms 차이에 양안 오차가 각각 100ms라면 우세로 판정하지 않는다.
6. 반복별 30건의 최대값 세 쌍에서도 같은 우열 방향이 나타나야 '대표 시험에서 차이 확인'으로 표시한다. 전체 최대값의 차이와 세 번의 방향 확인은 제한된 PoC의 재현성 규칙이며 모집단 최대값의 신뢰구간이나 통계적 확증이 아니다. 최대값을 만든 사건과 그 원인을 추적한다. 평균용 bootstrap 절차를 최대값의 신뢰구간으로 재사용하지 않는다.
7. 위 비교는 **양안의 모든 지정 사건이 유한한 정답 응답시간을 가진 경우에만** 적용한다. 한쪽이라도 `+∞`이면 최대값 차이나 비율을 계산하지 않는다. 해당 안의 점수는 0점이며 응답 의무 충족 여부를 별도로 비교한다. 이를 유한한 속도 차이의 커버리지로 세지 않는다. 양안이 유한하지만 비교 기준을 통과하지 못하면 '차이 미확인'으로 판정한다. 현 문서는 실행이나 달성된 점수를 보고하지 않는다.

stub의 고정 지연을 대안마다 임의로 다르게 주어 예상 결과를 만들어서는 안 된다. 입력해석 공통 stub으로 44를 살펴보는 결과와 실제 클라우드 모델을 포함한 사용자 체감 결과는 별도 실험 수준으로 표시한다. 최소 PoC의 숫자를 제품 전체 / 모든 Windows 앱의 성능으로 확대하지 않는다.

## 11. 발표 한 장에 넣을 문안

> **첫 응답 지연시간**<br>
> 요청이나 업무 사건 이후 첫 내용 응답이 해당 UI에 표시될 때까지 걸린 시간의 최대값<br>
> **목표: 대표 시험의 최대 1초 이내** — Nielsen(1993)의 1초 지침과 Microsoft Windows 응답성 구간 적용<br>
> 음성은 실제 발화 종료부터 측정. 단순 인사와 spinner 제외. 구체적 수행 안내는 Agent 전송 전에도 인정.<br>
> **예시:** “네”는 제외하고 구체적 수행 안내까지 0.8초. 가상 시험 0.8 / 0.6 / 1.0 / 0.8초의 최대는 1.0초 → 1점.<br>
> **점수:** 1초 초과 0점 / 1초 이내 1~6점 / 0.2초 이내 6점<br>
