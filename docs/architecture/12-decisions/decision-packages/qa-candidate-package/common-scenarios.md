# QA 공통 대표 시나리오와 관측 목록

> **COMMON-28-v1 / 2026-10-14 / 문서상 평가 구성 완료 / 구현과 측정 전**
> 현재 후보 QA01~QA09의 공통 평가 입력 정의다. 기존 ASR ID와 측정 계약을 변경하지 않는다. 아래 N과 관측 ID 및 반복 횟수는 이 판본의 문서 기준으로 정했다. WAV와 화면 파일 및 Windows 계측 구현과 실행 manifest의 검증은 후속 PoC 준비이며 이 문서의 실제 측정 완료를 뜻하지 않는다.

## 1. 하나의 공통 목록에서 측정한다

**28개 대표 시나리오를 같은 조건에서 각각 5회 실행하고 각 QA의 관측값을 같은 실행 기록에서 계산한다.** QA02는 그 안의 지칭 판단을 사용하고 QA09는 사전에 음성 전달을 요구한 응답만 사용한다. QA04와 QA08은 이 기능에 연결된 개발 변경 과제다. QA07의 무부하 실행은 네 공통 시나리오에서 무관한 배경 사건만 제거한 대조 실행이다.

28은 사용 빈도나 통계적 최소 표본 수가 아니다. 기존 [18개 UC와 94개 필수 변형](../../../05-representative-use-cases.md)을 대조해 지칭 근거와 실행 경로 및 상태 변화가 다른 대표 에피소드를 분리한 **기능 커버리지에 따른 시험 규격**이다. 예를 들어 사전 선택과 발화 중 지시 및 실제 모호함은 서로 다른 실패 원인을 가지므로 별도 시나리오로 둔다. 한 에피소드의 후속 질문이나 정정은 그 안의 입력으로 센다. 같은 장면의 문장만 바꿔 N을 늘리지 않았다.

정량 비교를 제품의 모든 변형 시험과 혼동하지 않는다. 추가 **F01~F18은 공통 시나리오에서 파생한 기능 회귀 변형**이며 어떤 UC를 보완하는지 아래에 명시했다. 정량 시험 28개에 포함하지 않고 비용과 지연 점수의 분모도 늘리지 않는다. 필수 기능을 삭제하거나 이 회귀에서 실패한 안은 28개 대표 시험의 좋은 수치만으로 기능을 충족했다고 주장할 수 없다.

**기록 원본:** [common-scenarios.json](./common-scenarios.json). 시나리오와 관측 ID 및 견적 필드는 이 파일에서 관리한다. 본문의 등록 표와 [비용 재견적](./common-model-cost-quote.md)은 같은 원본에서 계산한다. JSON은 설계 원장으로 정답을 포함하므로 후보에 통째로 입력하지 않는다. 실행 fixture를 만들 때 사용자에게서 온 입력과 공개 원본을 평가자 전용 정답 및 목표와 분리한다.

- **시나리오:** 시작 상태와 입력 및 사건 흐름과 완료 조건을 가진 에피소드 S01~S28.
- **응답 사건:** U는 사용자 입력, A는 사용자에게 전달해야 하는 Agent 사건이다. 네트워크 receipt나 내부 단계 완료는 새로운 응답 사건으로 세지 않는다. 각 사건의 첫 응답은 하나만 판정한다.
- **완료 목표:** G는 사용자 목표다. 확인 답변과 같은 목표의 수정 및 Agent 결과는 같은 G에 연결하며 별도 새 목표로 세지 않는다. 독립적인 조회나 새 업무는 새 G다. 한 복합 목표의 여러 하위 업무는 모두 끝나야 해당 G가 완료된다.
- **지칭 판단:** B는 한 표현이 가리키는 대상 집합이다. 집합에 대상 세 개가 있어도 판단 한 건이다. 한 발화의 서로 다른 두 표현은 두 건이다. 발화 도중 폐기된 잠정 지칭은 독립 정답으로 세지 않고 최종 revision만 판정한다.
- **반복:** 5회는 같은 기능 상황에서 결과의 반복 일관성을 확인하기 위한 PoC 규격이다. 독립 사용자 5명이나 성공률의 통계적 보증으로 해석하지 않는다. 최대값은 이 고정 시험의 관측 최대값이다.

QA02는 S06-U02와 S09-U01 및 S20-U01과 S26-U05의 실제 모호한 입력을 대상 집합 일치율에 넣지 않는다. 이 네 입력은 확인 질문을 해야 하며 QA01과 QA03 및 기능 판정에는 남긴다. 확인 후 정답을 결정할 수 있는 지칭은 해당 B에 별도로 포함한다. 실패나 잘못된 대상을 사후에 모호함으로 바꾸어 분모에서 제거할 수 없다.

## 3. 공통 실행 조건

### 3.1 초기 상태와 비용 범위

- Windows 11에서 이 후보 패키지의 클라우드 음성 및 의미 모델 조건을 사용한다. 양안의 CPU와 RAM 및 전체 worker 예산과 모델 및 네트워크 조건을 동일하게 둔다. 실제 장비와 OS build 및 모델 snapshot은 실행 manifest에 기록하고 다른 조건의 결과를 같은 표에 섞지 않는다. 참조 Architecture의 on-device 모델 메모리 달성값으로 전용하지 않는다.
- 각 S를 시작할 때 **원본 이력 200턴과 완료 Task 20개 및 최대 5개 진행 Task**를 같은 snapshot으로 복원한다. S에서 쓰는 H와 자료 및 Task ID는 이 원본에 포함한다. 각 시나리오의 진행 Task는 필요한 수만 활성화하고 나머지는 완료 상태로 둔다. 숨은 정답 관계나 생성된 요약은 초기 입력으로 주지 않는다.
- 시나리오별 앱 시작 전부터 비용 원장과 RAM 관측을 연다. S21의 8초와 S23의 5초 이전 음성 클립은 초기 원본 fixture이므로 새 생성 비용은 없으며 RAM과 재생 점유에는 포함한다. A의 cache와 B의 파생 생산을 포함한 준비가 실제로 수행되면 모두 센다. 원본을 읽고 같은 source 입력을 제공하기 시작한 시각에서 5초 후 첫 입력을 시작한다. 앱이나 파생 준비가 늦어도 원천 입력 시각을 늦추지 않는다. 특정 안의 파생 생산 완료를 기다려 주지 않는다. 5초 안에 준비되지 않은 작업은 입력과 겹치는 경합으로 남긴다.
- S 내부의 이력과 유효 cache는 유지한다. 다음 S와 다음 반복에는 같은 원본 snapshot에서 새로 시작한다. 따라서 이 시험은 하루 종일 누적된 steady-state 사용량이 아니며 **같은 시작 상태에서의 대표 에피소드 묶음**이다. S11은 그 내부에 실제 반복 조회를 넣어 재사용 경로도 포함한다.
- 원본 화면은 2880×1800이고 시나리오별 선택과 포인터 및 화면 변화 원본을 제공한다. 화면 근거 보존 범위는 최대 15장이다. 양안 모두 압축과 crop 및 같은 범위의 추가 읽기를 허용한다. 참조 견적의 이미지 수는 후보의 읽기 횟수 제한이나 정답 crop 제공이 아니다.
- 초기 준비와 원본 변경 및 재시도와 미사용 생산 및 폐기한 음성까지 실제 청구를 전부 포함한다. 28개 S의 비용을 더한 값이 한 묶음 비용이다. RAM은 28개 피크의 합이 아니라 앱 시작부터 후속 종료까지의 **동시 사용량 최고치**다.

### 3.2 사건의 시각과 완료 의존

- U의 시작 시각부터 원장에 지정한 길이로 발화한다. 음성 지연 시작점은 파일 끝의 무음이 아니라 주석한 실제 발화 종료다. Text는 지정한 제출 순간을 사용한다. 길이는 현재 입력 규격이며 녹음된 실측 길이라는 주장이 아니다.
- 일반 후속 입력은 직전 지정 응답의 상세 표시와 필수 음성 재생 완료 후 2초에 시작한다. 사용자가 보아야 할 확인 질문이나 결과가 오기 전에 답하는 잘못된 시험을 피한다. 30초까지 해당 응답이 없으면 실패를 남기고 정해진 30초 시점을 다음 입력의 기준으로 사용한다. 빠진 응답을 새로 성공 처리하지 않는다.
- Agent 기술 접수는 올바른 ingress 이후 100ms, 업무 결과는 해당 논리 동작을 실행할 수 있게 된 뒤 8초를 기본 외부 profile로 둔다. 이 값은 외부 Agent 성능의 측정값이 아니라 양안에 동일한 시험 입력이다. 단일 Agent가 복합 요청 전체를 받으면 각 동작의 명세가 같은 ingress에서 전달된 것으로 본다. 순서나 데이터 의존이 있는 동작은 `max(명세 전달 시각, 선행 결과 시각)`부터 시작하며 독립 동작은 다른 동작을 기다리지 않는다. 여러 실행으로 나누는 구조도 같은 논리 의존을 적용한다. S17의 기존 업무 완료와 취소는 각 사건 행의 별도 trigger를 따른다. VIA가 추가한 실행 의존은 QA03에 포함한다.
- 같은 Task의 진행 직후 완료가 오면 최신 완료 카드가 앞선 진행 응답 의무도 충족할 수 있다. 각 사건의 QA01 시작은 각각의 source 시각이며 종료는 그 카드가 실제 표시된 시각이다. 낡은 진행 상태를 현재 상태로 다시 표시하지 않는다. 사용자 요청이나 승인 질문 및 서로 다른 Task의 결과를 이 규칙으로 생략할 수 없다.
- 별도 trigger가 있으면 해당 행이 우선한다. **상대 시각과 시간 간격 및 겹침까지 같은 규칙**을 적용한다. S05/S11/S18/S19의 무관한 BG 진행과 결과는 첫 사용자 발화 종료 -100ms와 +100ms에 제공한다. 사건을 VIA가 수신한 시각으로 원천 시각을 바꾸지 않는다.
- S22의 완료/취소 교차는 T3 완료 사실을 사용자 취소 발화 종료 +100ms에 제공한다. 실제 취소 ingress가 앞서면 완료 직전 취소가 접수된 경우로, 늦으면 이미 완료된 경우로 기록하되 T3의 외부 확정 결과는 완료다. 동일 외부 완료 시각을 유지하며 후보의 미래 ingress에서 거꾸로 시간을 계산하지 않는다.
- 등록 표의 명시적 순서는 ID 발급 순서이며 절대 시각 정렬이 아니다. 특히 뒤에 적힌 BG 사건은 지정 trigger에 따라 먼저 발생할 수 있다. 실행기는 trigger의 원천 사건을 기준으로 재생한다.

### 3.3 목표와 관측 종료 및 실패

- 각 G는 등록한 관련 입력과 Agent 사건의 유효한 최종 revision에 필요한 상태와 상세 Text 및 필수 전체 음성 준비를 완료해야 끝난다. 정정으로 폐기된 구버전의 미생성 음성 나머지를 계속 만들 의무는 없다. 이미 수행한 구버전 처리는 QA03 경로와 비용 원장에 남긴다. 접수와 중간 진행만으로 최종 목표를 완료하지 않는다. 정당한 거부나 취소 미확인이 목표인 경우 그 사실을 정확히 안내하는 것이 완료 조건이다. 실제 업무 성공과는 별도 상태로 보존한다.
- QA03은 같은 G에서 외부 Agent 업무와 사용자 대기 및 후속 발화만 0으로 둔 인과 경로 길이다. 같은 목표의 확인 답변을 받기 위해 실제로 들은 음성의 순수 재생 길이와 차례 대기도 0으로 둔다. 요약과 TTS 생성 및 내부 출력 준비는 VIA 처리에 남긴다. 최초 입력 이전의 작업은 초기 상태이며 이후까지 남은 점유만 포함한다. VIA 모델과 조회 및 재시도와 내부 경합은 제외하지 않는다.
- 30초 내 첫 올바른 응답이 없으면 QA01은 +∞로 기록한다. G의 마지막 필수 외부 사실 또는 입력이 제공된 뒤 60초에도 완료되지 않으면 QA03은 +∞다. 입력이 끝나기 전에 타임아웃을 앞당겨 실패 비용을 숨기지 않는다.
- 모든 입력과 의무 외부 사건 제공이 끝난 기준 시각을 `t_final_source`로 둔다. 이후 **60초까지 필요한 처리와 준비를 관측하고 미완료면 실패로 남겨 취소를 요청**한다. 이후 **120초까지 종료와 늦은 청구를 수집**한다. 120초에도 정산이 안 되면 비용은 `INCOMPLETE_COST`다. 필요한 기능을 취소했다가 늦게 정산됐다는 이유로 성공으로 바꾸지 않는다.
- 후보의 실패로 후속 입력이나 source trigger가 영원히 발생하지 않으면 해당 anchor의 30초 deadline을 실패 시각으로 기록하고 원장에 명시된 후속 입력을 제공한다. 필요한 ingress가 없는 경우 Agent가 성공 결과를 대신 만들지 않는다. 의존하는 목표도 미완료로 남긴다.
- 실패한 시나리오와 반복은 원장에서 삭제하지 않는다. 기능 미완료를 저비용이나 저메모리 성공으로 채점하지 않는다. 계측 누락은 0값이 아닌 관측 불능이다.

### 3.4 음성 응답과 반복 순서

- Voice ON의 사용자 요청과 확인 질문 및 최종 결과는 짧은 음성 요약을 전달한다. 진행 사실은 Task UI에 표시하고 같은 Task의 최종 결과만 음성으로 요약한다. Voice OFF의 4개 응답과 진행 표시 7개는 사전에 QA09 분모에서 제외한다. 제외 이유는 각 응답에 기록한다.
- 음성 요약은 참조 견적에서 각 5초 생성으로 둔다. 실제 재생 길이와 생성 길이를 별도 기록한다. 중단으로 들려주지 못해도 생성되어 청구된 음성은 QA05에 남는다. 5초에 필요한 핵심을 담는 WAV를 제작할 때 검증하고 부족하면 결과 전에 입력 판본과 견적을 함께 개정한다.
- 사용자 발화와 고정 이전 음성 클립의 차례를 공통 원장으로 관리한다. 동시에 도착한 서로 다른 Task 응답은 source 시각과 ID 순으로 말하되 현재 발화는 우선한다. 후보가 준비가 안 됐다는 이유로 재생 불가능 시간을 늘릴 수 없다. 구형 응답을 일부러 오래 읽어 다음 응답 지연을 숨기지 않는다.
- 각 S의 5회 paired 실행에서 A/B 순서는 AB, BA, AB, BA, AB다. 홀수 반복으로 한 쪽이 먼저 시작하는 횟수가 하나 더 있음을 공개한다. 실행마다 같은 초기화와 부하를 적용하며 OS 상태와 온도 및 네트워크 이상을 기록한다. 유리한 반복을 골라 삭제하지 않는다. 5회로 통계적 유의성이나 실사용 상한을 증명하지 않는다.

C01~C06을 같은 시작 코드에서 각각 독립 수행한다. 변경 후의 위 표 수용 조건과 **S01~S28 전체의 기존 기능 회귀**를 확인한다. 변경 과제는 코드 diff 한 건으로 세며 5회 runtime 반복을 5개의 변경으로 세지 않는다. QA08은 QA04의 같은 변경 집합을 CO-01~CO-06의 기존 독립 쌍으로 조합한다.

QA07은 S05/S11/S18/S19의 첫 U를 각각 5회 비교한다. 부하 있음은 정량 목록의 실행을 재사용한다. 부하 없음은 같은 초기 정보와 foreground 입력에서 BG의 진행과 결과 및 그 처리만 제거한다. BG는 다른 Task이며 현재 질문의 정답과 지칭 및 권한이나 완료 목표에 필요한 근거가 아니다. 이 독립성 조건을 어기면 무부하 대조로 인정하지 않는다. 두 조건의 평균 차이에서 음수를 0으로 둔 네 값을 평균한다. 추가 무부하 실행은 QA05/06 전체 묶음에 합산하지 않는다. 두 조건의 foreground 완료를 확인하고 부하 있음 조건에서는 BG 처리 완료와 유실도 확인한다.

## 7. DP 공통 적용과 PoC 범위

- DP44/47/45/42의 각 두 안에 **같은 COMMON-28-v1**을 적용한다. 한 DP만 잘 나오는 S를 골라 대표값을 바꾸지 않는다. 각 S의 관련 DP는 인과 경로를 검토하기 위한 표시이며 그 DP에서 다른 S를 빼라는 지시가 아니다.
- 다른 영역은 양안이 같은 고정 주변부를 사용한다. 특정 구조의 모델 호출 수와 cache hit를 강제하지 않는다. 준비와 후보 확장 및 후속 상태 확정까지 실제 차이가 나타나도록 관측한다.
- QA01/03의 최대값이 비교 DP가 바꾸지 않는 공통 경로에서 나오면 대표값은 동점일 수 있다. 영향을 받은 경로의 개선은 진단값으로 보여주고 임의 제외로 trade-off를 만들지 않는다.
- PoC는 전체 제품 구현을 요구하지 않는다. 한 DP의 실제 구조와 공통 입출력 및 원장을 연결하고 외부 Agent 업무는 동일한 고정 source로 모사할 수 있다. 단, 일부 S만 실행한 결과를 28개 전체 QA 수치로 부르지 않는다. 모델이나 UI/음성 장치를 대체했다면 mock/proxy 범위를 표시한다.
- 현재 완료 범위는 **시나리오 구성과 입력 문안 및 관측 ID와 수량과 반복 규칙과 표 반영**이다. 실제 자료 asset의 hash와 tokenizer 검증 및 Windows 측정은 수행하지 않았다. QA06의 절대 목표 근거 부족은 시나리오를 완성한 것으로 해결되지 않는다.
