# QA 후보 07. 부하 추가 지연

> **공통 평가 구성:** [COMMON-28-v1](./common-scenarios.md)의 28개 대표 시나리오를 동일 조건에서 5회 실행한다. 관측 ID와 건수 및 제외 조건을 공통 목록에서 관리한다. 현재 문서상 입력 구성은 완료됐으며 실제 자료 제작과 구현 및 측정은 별도다.

> 발표 준비: [QA07 한 장 설명 페이지](./slide-page-plan.md#qa07) / 기존 추가 후보의 목표 근거와 상태를 유지한다.

> 2026-10-14 / 작성자 검토안 / **예비 후보: 핵심 승격 보류** / 미구현·미측정
>
> 이 번호는 이번 후보 묶음의 식별자이며 기존 ASR-QA ID를 바꾸지 않는다. [중심 계획](../03-03-qa-dp-evaluation-plan.md)과 [추가 후보 판정](./additional-candidates.md)을 함께 읽는다. 목표와 점수는 평가 전 제안이다.

## 1. 제안과 판정

**다른 업무의 사건이 몰려도 지금 대화하는 요청이 얼마나 더 늦어지는지 평가한다.** 첫 응답 지연이 절대적인 기다림이라면 이 후보는 다른 업무가 더한 기다림이다.

같은 정의로 DP-44와 DP-42를 비교할 수 있다. 그러나 현재 강한 A는 두 DP 모두 비동기 처리와 제한된 worker를 사용할 수 있다. B의 구조만 보고 간섭이 작다고 단정할 근거는 부족하다. **현재는 두 DP 모두 실용적 동점이 기본 예상이며 QA1의 부하 진단으로 사용한다. 핵심 QA 수나 커버리지를 채우는 용도로 승격하지 않는다.**

| 항목 | 명세 |
| --- | --- |
| 이름 | **부하 추가 지연** |
| 한 문장 정의 | 다른 Task의 사건 처리로 인해 현재 사용자 요청의 첫 응답이 추가로 늦어진 시간 |
| 단일 지표 | **평균 부하 추가 지연(ms)** |
| 좋은 방향 | 작을수록 좋음 |
| 평가 단위 | 동일 foreground 입력의 부하 없음/있음 실행 쌍 |
| 목표 제안 | **200ms 이하** |
| 사용자 가치 | 다른 일을 맡겨 둔 상태에서도 현재 대화를 비슷한 속도로 이어감 |
| 현재 권고 | QA1의 보조 진단. 독립 차별성이 확인된 뒤에만 핵심 후보로 재검토 |

## 2. 지표와 산식

평가 cell `i`는 **공통 S05/S11/S18/S19의 첫 사용자 요청 4개** 중 하나다. 같은 cell의 foreground 요청과 응답 판정은 부하 없음/있음 두 조건에서 동일하다. 각 조건을 공통 5회 반복한 평균을 먼저 계산한다.

```text
L_idle(i)   = 부하 없는 조건에서의 첫 응답 지연 평균
L_loaded(i) = 다른 Task 사건이 함께 있는 조건에서의 첫 응답 지연 평균
D(i)        = max(0, L_loaded(i) - L_idle(i))
QA07        = Σ D(i) / 4
```

각 조건의 첫 응답 시작 / 종료점은 [QA1](./qa01-first-response-latency.md)의 정의를 그대로 쓴다. 끝점은 첫 내용 단위가 Request/Task UI에 실제 표시된 때이며 오답도 실제 시간을 사용한다. 음성 차례 대기, 모델의 첫 토큰, queue 삽입을 끝점으로 바꾸지 않는다. 유한한 평균 산식은 양 조건의 필수 foreground 응답이 모두 관측됐을 때 적용한다.

각 cell의 반복 평균을 뺀 뒤 증가분만 집계하고 네 cell을 같은 비중으로 평균낸다. 음수 차이는 원값에 남기지만 다른 cell의 악화를 상쇄하지 않는다. 이 0 하한은 잡음에도 작은 양의 값을 만들 수 있으므로 예비 실행에서 반복 분산을 확인한다. 개별 반복의 양수 차이를 먼저 잘라 평균내는 계산도 사용하지 않는다.

### 왜 절대 응답시간과 다른가

| 설명용 가상값 | 부하 없음 | 부하 있음 | 추가 지연 |
| --- | ---: | ---: | ---: |
| 구조 X | 400ms | 650ms | 250ms |
| 구조 Y | 650ms | 700ms | 50ms |

X의 절대 응답은 더 빠르지만 Y의 부하 간섭은 더 작다. 두 값을 모두 볼 이유는 있다. 다만 QA1이 이미 같은 부하 사례를 충분히 포함한다면 이 후보를 독립 핵심 QA로 올려 **같은 지연 효과를 반복 강조할 필요는 없다.** 이 후보의 작은 값만으로 좋은 사용자 경험이라고 결론내리지 않는다.

## 3. 비교 모집단

[COMMON-28-v1](./common-scenarios.md)의 네 시나리오에 이미 무관한 BG Task의 진행과 결과를 넣었다. 현재 요청의 발화 종료 -100ms에 진행, +100ms에 결과를 source에서 제공한다.

| 공통 S | 현재 요청 | 부하 없음 조건의 변경 |
| --- | --- | --- |
| S05 | 말하면서 두 그래프 지칭 | BG 진행과 결과 및 그 처리만 제거 |
| S11 | 과거 비교 결과 재참조 | 같은 원본 이력에서 BG 사건만 제거 |
| S18 | 기존 보고서 상태 확인 | TA 상태와 정답을 유지하고 BG 사건만 제거 |
| S19 | 무관한 일반 지식 질문 | 사용자 입력을 유지하고 BG 사건만 제거 |

부하 있음 4×5건은 공통 실행 기록을 재사용하고 무부하 4×5건만 추가한다. 총 20개의 대응 쌍이며 추가 무부하 실행은 QA05/06의 묶음 비용이나 RAM에 합산하지 않는다. BG는 foreground 지칭이나 질문 및 권한과 목표에 필요한 근거가 아니다. 이를 제거해 정답이 바뀌면 유효한 대조 시험이 아니다. BG의 유실이나 무기한 지연으로 빠른 값을 만들면 기능 실패로 남긴다.

DP-44는 같은 Task 소유·저장 경계 아래 중앙 continuation과 stage 연결만 바꾼다. DP-42는 동일한 실행 연결을 고정하고 대화/업무의 확정·전달 경계만 바꾼다. CPU, 전체 worker 예산, 모델 수용량, 저장 내구 조건과 foreground 우선 정책은 같다. 독립 서비스마다 같은 수의 worker를 줘 B의 총 자원을 늘리지 않는다.

## 4. 목표 수치의 도출과 근거

**목표는 평균 200ms 이하로 제안한다.** 계산은 다음과 같다.

```text
첫 응답 목표 후보             1,000ms
단일 foreground 처리 설계 예산   800ms
동시 업무 간섭에 남기는 예산      200ms
```

1,000ms는 QA1에서 별도로 검토하는 HCI 응답 목표 후보에 연결한다. **800/200 분배는 VIA의 설계 예산 제안이지 인간 실험에서 발견한 임계값이 아니다.** QA1 목표 또는 실측 가능한 단일 요청 예산이 달라지면 함께 재검토한다. 200ms를 자연 대화의 발화 간격에서 가져왔다고 설명하지 않는다.

| 근거 | 확인한 사실 | 여기서 사용할 범위 |
| --- | --- | --- |
| [Google SRE — Handling Overload](https://sre.google/sre-book/handling-overload/) | 요청 수만으로 자원 부하를 설명하기 어렵고 자원 제한과 요청 중요도를 고려해야 함 | 사건 수뿐 아니라 payload·CPU·저장·model 조건을 고정할 이유. 200ms의 출처는 아님 |
| [Tokio — cooperative task yielding](https://tokio.rs/blog/2020-04-preemption) | 실행 중인 async 작업이 다른 작업의 실행 기회와 지연에 영향을 줄 수 있음 | 실행 조직과 scheduler 조건을 확인할 이유. 중앙 dispatcher가 반드시 느리다는 근거는 아님 |
| [Tokio — spawn_blocking](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html) | blocking/긴 계산을 별도 작업 경로에서 처리하는 지원이 있음 | 강한 A에도 적절한 worker를 허용해야 할 근거 |
| [현재 QA 계획](../03-03-qa-dp-evaluation-plan.md) | 첫 응답과 전체 처리시간은 분리하며 교차 사건을 다뤄야 함 | 절대 지연과 추가 지연을 구별할 내부 요구 |

출처 확인일은 2026-10-14다. CPU 부하를 제거한 mock만 실행했다면 실제 PC의 부하 간섭을 검증했다고 주장하지 않는다.

## 5. 0~6점 구간 제안

`x`는 반올림 전 평균 부하 추가 지연이다. 1점 이상이 목표 충족이며 원값을 함께 표시한다. 미측정과 관측 실패는 0점 수치로 대신하지 않는다.

| 점수 | 표시 | 구간 |
| ---: | --- | --- |
| 0 | ○○○ | `x > 200ms` |
| 1 | ◐○○ | `150 < x ≤ 200ms` |
| 2 | ●○○ | `100 < x ≤ 150ms` |
| 3 | ●◐○ | `75 < x ≤ 100ms` |
| 4 | ●●○ | `50 < x ≤ 75ms` |
| 5 | ●●◐ | `25 < x ≤ 50ms` |
| 6 | ●●● | `0 ≤ x ≤ 25ms` |

200ms는 목표 예산, 25ms는 목표의 1/8 수준을 보여주는 최상위 설계 구간이다. 중간 구간은 성능 여유를 읽기 위한 등급화이며 사용자 체감이 이 경계에서 급변한다는 연구 결과가 아니다.

처음부터 느린 구조가 낮은 추가 지연으로 고득점할 수 있다. **QA1의 절대 지연 목표를 함께 제시하고 이 점수로 QA1 실패를 상쇄하지 않는다.** 기능 실패, 유실, 무한 대기 또는 측정 불능이 있으면 점수와 별도로 실패 상태를 표시한다.

## 6. 네 DP의 예상 판정

| DP | 대표 범위의 사전 예상 | 발표에 쓸 한 문장 | 현재 커버리지 |
| --- | --- | --- | --- |
| 44 | **실용적 동점 예상** | **두 안 모두 짧은 비동기 처리와 제한된 worker를 사용하므로 실행 연결 방식만으로 부하 간섭의 우위를 기대하기 어렵다.** | 세지 않음 |
| 42 | **실용적 동점 예상** | **통합 Core도 업무 작업을 분리 실행할 수 있으므로 서비스 분리만으로 현재 요청의 대기가 줄어들지는 않는다.** | 세지 않음 |
| 47 | 비교 제외 | 같은 입력 해석의 처리량 차이는 QA1·QA3·QA5에서 먼저 평가 | 세지 않음 |
| 45 | 비교 제외 | 이력 생산의 background 비용은 QA1 부하 사례와 QA5·QA6에 우선 반영 | 세지 않음 |

이는 **측정 전 선택 판단**이다. 동점이라는 결과를 측정했다고 표현하지 않는다. 어느 한쪽에 실제 공유 lock·수용량 경합·commit 경합이 남아 200ms 예산을 의미 있게 소비하는 것이 확인되면 차이 후보로 재검토한다. 희귀 crash나 재시작을 정상 부하 사례로 바꿔 넣지 않는다.

## 7. 한정 PoC와 실패 처리

**구현할 범위:** 실제 실행 연결, 실제 Task 사건 적용과 UI 표시, 실제 local queue·worker·저장 경로. 외부 Agent는 같은 시각에 고정 사건을 내는 fixture로 대신할 수 있다. 모델은 양안에 같은 기록 응답을 재생하는 기계적 실험과 실제 호출 실험을 구별한다.

**실행 단위:** 공통 시나리오 4개 × 부하 유무 × 각 5회. A/B 순서는 교차하고 같은 seed, 입력, 사전 상태와 model replay 지연을 사용한다. warm-up은 양안 동일하게 하고 warm-up 사건은 평가 사례에 섞지 않는다. 실제 실행은 아직 승인·수행하지 않았다.

**실패 규칙:**

- idle은 성공했지만 loaded의 필수 첫 내용이 공통 제한시간 안에 나오지 않으면 `QA07=+∞`라는 실패 판정값과 **0점**을 기록한다. 이는 실제 무한 대기를 관측했다는 뜻이 아니라, 필수 응답 없는 실행을 작은 추가 지연으로 채점하지 않는 규칙이다. 실제 관측 종료시각과 timeout을 원장에 남긴다.
- idle 조건도 실패한 사례는 낮은 증가분으로 양호 판정하지 않는다. 전체 QA07을 `기준 실행 실패 — 우열 판정 불가`로 표시하고 실패 원값을 보존한다.
- background 사건을 유실하거나 끝없이 미뤄 얻은 낮은 foreground 지연은 유효하지 않다. 모든 필수 사건은 동일 drain 구간 안에 현재 원본에 반영되어야 한다. 그 기능 조건이 실패하면 지연 원값은 보존하되 평가 상태는 `FAIL`이며 선택용 점수는 0점이다. 유실을 정상 부하 감소로 세지 않는다.
- foreground와 같은 Task를 바꾸는 사건을 몰래 background에 넣어 다른 의미 문제를 만들지 않는다.
- proxy UI callback이면 실제 화면 표시와 구별해 결과에 표시한다.

**최소 원장:** `case_id, pair_id, alternative, seed, event_source_time, payload_hash, foreground_start, correct_content_presented, idle_or_loaded, queue_wait, worker_budget, store_commit, timeout, lost_event_count, drain_complete, trace_ref`.

**우열 확인:** 원값 차이 50ms 이상을 초기 실용 차이 후보로 둔다. 반복 오차보다 큰지 함께 확인한다. 50ms는 목표 간섭 예산 200ms의 1/4이라는 설계 판정값이며 HCI 최소인지차라고 부르지 않는다. 이 수준의 구조 차이가 없으면 동점으로 남기고 핵심 커버리지에 넣지 않는다.

## 8. 발표 한 장 카드

| 칸 | 사용할 문구 |
| --- | --- |
| 제목 | **다른 업무가 지금 대화를 얼마나 늦추는가** |
| 정의·지표 | 같은 요청의 부하 없음/있음 응답시간 차이의 평균 |
| 목표·근거 | **200ms 이하** — 첫 응답 1초 설계 예산 중 동시 업무 간섭에 0.2초 배정 |
| 예시 | 혼자 처리 600ms → 다른 업무와 처리 750ms → 추가 지연 **150ms**, **2점 ●○○** |
| 점수 | `>200 / ≤200 / ≤150 / ≤100 / ≤75 / ≤50 / ≤25ms` 순으로 0~6점 |
| DP 관계 | 44·42의 정상 사용 간섭을 확인하되 현재는 동점 예상 |
| 현재 결론 | **핵심 QA에 추가하지 않고 QA1의 부하 진단으로 유지** |

예시는 가상값이다. 직관적인 결론은 현재 구조만으로 자동 간섭 이익을 주장할 수 없다는 것이며, 후보 문서의 완성이 실측 우위의 완성을 뜻하지 않는다.
