# QA03 VIA 처리시간 조사 부록

> 조사 확인일 2026-10-14 / [현재 QA03 명세](../qa03-via-processing-time.md)

## 1. 목표 근거를 다시 찾은 이유

이전의 해석 1.5초와 근거 보완 1초 및 연결 0.5초와 응답 준비 1.5초 및 여유 0.5초는 이미 고른 5초를 내부에 배분한 것이었다. 사용자나 제품이 왜 5초를 요구하는지 설명하지 못하므로 목표의 근거에서 제거했다.

VIA는 입력을 이해하고 외부 업무를 연결하며 결과를 전달하는 인터페이스다. 외부의 실제 작업과 사용자의 답변을 기다린 시간을 제외한 **VIA 자체 완료 경로가 장시간 대기를 추가하지 않도록 한다**는 요구를 먼저 두었다.

## 2. 직접 참조한 Windows 기준

[Microsoft의 응답성 지침](https://learn.microsoft.com/en-us/windows/apps/develop/performance/responsive)은 다음 구간을 구별한다. 확인한 페이지의 갱신일은 2026-03-18이다.

| 구간 | 시간 | 원문의 의미를 요약한 설명 | VIA에 사용하는 방식 |
| --- | --- | --- | --- |
| Pause | 0.5~1초 | 빠르지는 않지만 응답성이 유지됨 | 첫 내용 표시 QA01의 참조 |
| Wait | 1~3초 | 수행할 일 때문에 대기함 | 전체 처리에서도 더 좋은 수준을 설명하는 참고 |
| Long wait | 2~5초 | 더 이상 응답성이 있다고 느끼기 어려움 | 자체 완료 경로가 넘어가지 않을 상단 5초 채택 |
| Captive | 5~10초 | 불가피하게 길고 복잡한 경우의 대기 | VIA 자체 처리가 이 수준의 대기를 추가하지 않도록 제한 |
| Long-running | 10~30초 이상 | 사용자가 다른 일을 할 수 있는 장시간 처리 | 외부 업무의 총 소요시간과 VIA 내부 부담을 구별할 배경 |

구간은 일부 겹치며 엄밀히 분리된 인간 반응의 실험 임계가 아니다. **5초는 Long wait의 상단**이다. Captive의 상단은 10초이므로 “Captive의 상단을 피하기 위해 5초”라고 설명하면 틀린다. 이 문구는 교차 리뷰에서 정정했다.

## 3. 5초를 적용하는 정확한 범위

직접 답변에서는 입력 종료부터 상태 확정과 필수 상세 텍스트 표시 및 음성 요약 전체 준비까지의 실제 경로가 대응한다. 위임 업무에서는 외부 실행 시간을 0으로 바꾼 **원래 실행 의존 그래프의 VIA 경로**를 계산한다.

- 포함: VIA 코드와 저장, VIA가 부른 클라우드 모델, 전송과 내부 큐, 필요한 원본 조회, Agent 접수 확인 경로, 최종 표시와 요약 준비.
- 제외: Downstream Agent 내부의 업무 수행, 사용자 답변을 기다리는 시간과 그 발화 길이.
- 음성 출력 차례와 이미 준비된 음성의 재생 길이는 완료 조건에 넣지 않는다. 실제 전달은 QA09에서 확인한다.
- 외부 시간을 제거한 값은 실제 사용자 총 대기나 VIA 도입으로 순증한 지연의 인과 추정값이 아니다.

## 4. 병렬 예시를 발표 자료에 남긴다

```text
VIA 입력과 위임 1.2초
  ├ 외부 Agent 업무 8.0초
  └ VIA의 필요한 병행 준비 3.0초
두 경로가 끝난 후 VIA 표시와 요약 준비 0.6초

실제 완료 = 1.2 + max(8.0, 3.0) + 0.6 = 9.8초
VIA 귀속 = 1.2 + max(0.0, 3.0) + 0.6 = 4.8초
```

단순히 `9.8 − 8.0 = 1.8초`로 보고하면 외부 업무와 겹쳐 수행한 VIA 준비 경로를 빠뜨린다. 위 값은 설명용 가상 예시다. 여러 시험을 채점할 때는 공통 28개 시나리오에서 도출한 76개 완료 목표와 5회 반복의 최대값을 사용한다.

## 5. 계산에서 발견한 함정

1. 외부 duration을 0으로 만들기 전 그래프가 실제 완료시각을 재구성해야 한다. 재구성되지 않으면 의존 누락이나 대기 중복을 먼저 고친다.
2. 선행 작업이 자원을 사용한 시간을 edge로 이미 반영했다면 동일한 queue 대기를 node로 다시 더하지 않는다.
3. 입력 전에 시작한 배경 작업은 현재 목표의 입력 이후 잔여 점유만 포함한다. 입력 4초 전부터 1초 뒤까지 점유했다면 현재 목표에는 1초가 해당한다.
4. VIA 클라우드 모델 호출을 외부 업무로 빼지 않는다. 모델이 원격에 있다는 사실과 책임 경계는 다르다.
5. 계측 누락은 0초가 아니다. 실패와 불완전 trace를 별도로 남긴다. 제한시간과 무응답 판정은 상세 명세를 따른다.
6. 평균에서 최대값으로 바꾼 것은 새 평가 판본이다. 고정 시험의 최대값을 모든 실제 사용의 보장으로 확대하지 않는다.

## 6. 심사 답변과 발표 구성

**주요 답변:** “Windows의 장시간 대기 구분에서 5초를 가져와 VIA 자체 완료 경로의 상한으로 적용했습니다. 빠르고 자연스러운 첫 반응은 QA01의 1초로 보장하도록 요구하고 그 뒤 내부 처리가 불필요하게 길어지는 문제를 별도로 평가합니다.”

“왜 3초가 아닌가”에는 5초가 우수 수준이 아니라 허용 상한이고 짧을수록 같은 점수표에서 더 높은 점수를 받는다고 설명한다. 5초를 자연스러운 대화의 실험 임계라고 말하지 않는다. 목표를 현재 모델의 실측 성능에서 역산하지도 않았다.

한 장에는 Windows 구간의 5초 경계와 위 병렬 타임라인을 함께 둔다. 지표와 점수는 현재 명세를 참조하고 DP-42의 공동 확정과 서비스 간 receipt 연결의 차이를 구조 원인 한 문장으로 덧붙인다. 실제 최대 경로 차이는 PoC 전 가설이다.
