# QA 후보 08. 병행 수정 중복

> 발표 준비: [QA08 한 장 설명 페이지](./slide-page-plan.md#qa08) / 기존 추가 후보의 목표 근거와 상태를 유지한다.

> 2026-10-14 / 작성자 검토안 / **예비 후보: QA4 보조 지표로 우선 사용** / 미구현 / 미측정
>
> 이 번호는 이번 후보 묶음의 식별자다. 기존 ASR-QA ID를 변경하지 않는다. [중심 계획](../03-03-qa-dp-evaluation-plan.md)의 AI 코딩 협업 요구와 Rust 모듈 정의를 따른다.

## 1. 제안과 판정

**서로 다른 기능을 고치는 두 개발자가 같은 모듈을 얼마나 함께 수정해야 하는지 평가한다.** 사용자는 AI 코딩을 활용하는 병행 개발에서 수정 영역이 겹쳐 협의와 충돌 정리가 늘어나는 경험을 제시했다. 변경 모듈 수가 같은 두 구조에서도 특정 모듈에 변경이 집중되는 정도는 다를 수 있다.

이 후보는 현재 여섯 QA 외에 남길 가치가 있다. 그러나 공통 모듈 수정이 곧 Git 충돌이라는 뜻은 아니며 실제 통합 시간도 측정하지 않는다. **우선 QA4 변경 범위를 보완하는 예비 후보로 유지하고 실제 변경 집합에서 두 DP 이상의 차이가 확인될 때만 핵심 후보로 올린다.**

| 항목 | 명세 |
| --- | --- |
| 이름 | **병행 수정 중복** |
| 한 문장 정의 | 독립적인 두 기능 변경을 병행할 때 양쪽이 함께 수정해야 하는 구현 모듈의 범위 |
| 단일 지표 | **변경 쌍당 평균 공통 수정 모듈 수** |
| 평가 단위 | 변경 전의 같은 코드 버전에서 각각 수행하는 독립 변경 과제 2개의 쌍 |
| 좋은 방향 | 작을수록 좋음 |
| 목표 제안 | **1개/쌍 이하** |
| 요구 근거 | 여러 개발자의 AI 코딩으로 수정 영역이 겹칠 때 조율 부담이 커졌다는 사용자 팀의 경험 |
| 현재 권고 | QA4 보조 지표로 유지. 핵심 6개를 자동으로 7개로 늘리지 않음 |

## 2. 지표와 집계 단위

```text
M(c) = 변경 과제 c에 수정 / 추가 / 삭제한 고유 운영 Rust 모듈의 집합
O(p) = |M(p.left) ∩ M(p.right)|
QA08 = Σ O(p) / 평가 전에 정한 독립 변경 쌍 수
```

양쪽 변경은 변경 전의 같은 코드 버전에서 독립적으로 시작한다. 먼저 한 변경을 통합한 뒤 두 번째를 구현하면 변경 전의 같은 코드 버전의 중복을 재는 시험이 아니다. 결과가 좋은 쌍만 고르지 않고 모든 사전 지정 쌍을 같은 비중으로 집계한다.

모듈 ID는 [QA4 §3](./qa04-change-scope.md#3-rust-모듈을-어떻게-세는가)의 `package / crate-target / fully-qualified-module-path`를 그대로 사용한다. inline module, crate root, 추가 / 삭제와 소유 prompt/schema/config의 처리도 QA4와 같게 유지한다. `.rs` 파일 수, 함수 수, 개발자 수 또는 추상 책임 수로 바꾸지 않는다. 단순 이름 변경은 baseline ID에 연결한다. 한 파일 안의 서로 다른 inline module 수정은 파일 공유만으로 같은 모듈이 되지 않는다.

### QA4와 구별되는 이유

아래는 **설명용 가상 코드 구조**다.

| 구조 | 변경 C1 | 변경 C2 | 과제당 변경 모듈 평균 | 두 과제의 공통 수정 |
| --- | --- | --- | ---: | ---: |
| X | `{a,b,c}` | `{a,d,e}` | 3개 | 1개 |
| Y | `{a,b,c}` | `{d,e,f}` | 3개 | 0개 |

QA4는 X와 Y가 같다. QA08은 Y의 병행 수정 중복이 더 작다. 반대로 거대한 모듈 하나에 모든 변경을 몰면 QA4가 작아 보여도 QA08은 계속 같은 모듈을 가리킨다. **분해 왜곡을 잡는 보조 설명으로도 유용하다.**

## 3. 대표 변경 쌍

변경 과제의 입력 / 완료 조건은 [QA4의 C01~C06](./qa04-change-scope.md#4-지표와-공통-변경-모집단)을 그대로 사용하고, 이 후보에서는 **어떤 두 변경을 병행할 것인지**만 추가한다. 새 변경 pack으로 QA4와 다른 문제를 측정하지 않는다. 구현 전에 두 과제를 별개 팀원이 독립적으로 완료할 수 있는지 검토한다.

| 쌍 | 왼쪽 변경 | 오른쪽 변경 | 독립성 기준 |
| --- | --- | --- | --- |
| CO-01 | C01 모델 요청과 응답 데이터 형식 변경 | C02 Agent 요청과 접수 확인 데이터 형식 변경 | 서로 다른 외부 protocol의 별도 개정 |
| CO-02 | C01 모델 요청과 응답 데이터 형식 변경 | C03 화면과 과거 자료의 좌표 및 시각과 버전 표현 변경 | 모델 호출과 자료 취득 protocol의 별도 개정 |
| CO-03 | C02 Agent 요청과 접수 확인 데이터 형식 변경 | C03 화면과 과거 자료의 좌표 및 시각과 버전 표현 변경 | 업무 전달과 근거 취득 protocol의 별도 개정 |
| CO-04 | C04 Agent 중간 답변을 section별 정정으로 확장 | C05 실제 전달 구간과 원본 대응 목록 반환 확장 | 현재 결과 정정과 과거 설명 조회의 별도 기능 확장 |

| CO-06 | C05 실제 전달 구간과 원본 대응 목록 반환 확장 | C06 source extent별 동의 철회로 확장 | 조회 결과 설명력과 사용 허용 범위의 별도 요구 |

양쪽 과제는 최종적으로 함께 성립해야 한다. 예를 들어 CO-06에서 새 반환 목록이 철회 구간을 노출해서는 안 된다. 이미 현재성 / 동의 철회 기능이 있다는 이유로 삭제한 뒤 다시 구현하지 않는다. 각 요구의 변경 전/후는 QA4에서 먼저 고정한다.

현재 제안은 네 DP 모두 C01~C06과 위 여섯 쌍을 사용한다. 각각 다른 DP 부분은 공통 코드 버전으로 고정한다. 외부 wire 대조 쌍 세 개를 결과가 같다는 이유로 삭제하지 않는다. 이후 pack 개정이 필요하면 사전 버전 변경으로 처리하고 이전 결과와 구별한다. 숫자를 DP 간에 합산하지 않는다. 두 과제의 요구 자체가 상충하는 쌍을 발견하면 구조의 문제가 아니므로 본 평가 전에 완료 조건을 바로잡는다.

## 4. 목표 1개의 도출

**평균 1개/쌍 이하**는 아래 협업 예산으로 제안한다.

1. 병행하는 두 변경이 각각의 담당 모듈에서 대부분 완료되도록 한다.
2. 공통 계약이나 연결 모듈을 조정할 필요는 인정한다.
3. 대표 변경 쌍 하나당 공통 수정 영역을 평균 1개 이내로 관리한다.

이 값은 팀이 수용할 협업 범위를 표현하는 **작성자 설계 예산**이다. 사용자가 평균 1개를 승인했다거나 AI 코딩 업계의 표준이라고 주장하지 않는다. 실제 팀의 담당 경계와 대표 변경 로그를 확보하면 이 예산을 검증한다. 현재 요구 근거는 병행 수정의 부담이라는 사용자 경험이며, 숫자 1은 그 요구를 측정 가능하게 바꾸는 제안이다.

| 출처 | 확인한 사실 | 적용 한계 |
| --- | --- | --- |
| [Rust Reference — Modules](https://doc.rust-lang.org/reference/items/modules.html) | `mod`는 crate의 모듈 트리에 항목을 만들며 외부 파일과 논리 모듈 경로는 구별됨 | 고유 구현 모듈 식별의 근거. 수정 중복 목표를 제공하지 않음 |
| [GitHub — Merge conflicts](https://docs.github.com/en/pull-requests/reference/merge-conflicts) | 같은 줄의 경쟁 변경과 수정/삭제가 충돌 원인이며 서로 다른 줄 / 파일은 자동 병합 가능 | 모듈 중복을 실제 Git 충돌 횟수라고 부르면 안 되는 근거 |
| [현재 논의의 팀 경험](../03-03-qa-dp-evaluation-plan.md#ai-코딩-협업과-변경-범위) | AI 코딩 병행 작업의 변경 충돌, 통합 부담과 다른 담당 영역 수정에 대한 주저함 | 이 팀의 요구. 모든 AI 개발팀으로 일반화하지 않음 |

출처 확인일은 2026-10-14다. 이 자료들에서 모듈 중복 1개가 특정 man-month나 비용을 뜻한다는 주장을 도출하지 않는다.

## 5. 0~6점 구간

`x`는 반올림 전 변경 쌍당 평균 공통 수정 모듈 수다. 6개 대표 쌍에서 공통 수정의 총합이 0 / 1 / 2 / 3 / 4 / 5~6개인 경우를 읽기 쉽게 구분한다.

| 점수 | 표시 | 구간 |
| ---: | --- | --- |
| 0 | ○○○ | `x > 1` |
| 1 | ◐○○ | `4/6 < x ≤ 1` |
| 2 | ●○○ | `3/6 < x ≤ 4/6` |
| 3 | ●◐○ | `2/6 < x ≤ 3/6` |
| 4 | ●●○ | `1/6 < x ≤ 2/6` |
| 5 | ●●◐ | `0 < x ≤ 1/6` |
| 6 | ●●● | `x = 0` |

이 구간은 목표 1개와 6개 변경 쌍의 정수 계수 해상도에서 도출한 설계 규칙이다. 사람이 0.5개와 0.67개에서 협업 부담을 다르게 느낀다는 심리 실험은 아니다. 소수 표시를 반올림해 구간을 넘기지 않고 실제 정수 합과 분모로 채점한다.

독립 변경 하나가 완료되지 않았으면 그 쌍을 0개로 세지 않는다. `변경 미완료`를 표시하고 실행 전의 설계 예측만 있다면 `설계 영향 분석`으로 보고한다. 실측 변경 / 빌드 / 행동 검증이 없는데 실측 점수를 부여하지 않는다.

## 6. DP의 예상 우열과 판정

| DP | 현재 판정 | 직관적인 한 문장 | 핵심 커버리지 |
| --- | --- | --- | --- |
| 44 | **실용적 동점 예상** | **A의 분리된 handler와 B의 공통 게시 / 결합 규칙을 함께 고려하면 실행 연결의 분산만으로 병행 수정 중복이 줄지는 않는다.** | 세지 않음 |
| 45 | **A 우세 가설은 남기되 검증 전 핵심 제외** | **A는 원본별 읽기 계약을 개별적으로 바꾸므로 공통 파생 관계의 schema와 게시 계약을 함께 수정할 필요가 적다.** | 세지 않음 |
| 42 | **실용적 동점 예상** | **강한 통합안도 대화와 업무의 내부 모듈을 분리하므로 서비스 경계만으로 코드 수정의 겹침이 줄지는 않는다.** | 세지 않음 |
| 47 | 보조 검토 | 원본 adapter 변화와 중간 후보 계약 변화의 실제 diff가 필요하며 현재는 문서의 상자 수로 판정하지 않음 | 세지 않음 |

44의 A에는 handler 분리와 자료 기반 등록을 허용한다. B의 전체 flow wiring도 실제 수정되면 센다. 45의 B에는 producer별 adapter와 schema versioning을 허용하고 A의 공통 Context Composer가 실제로 바뀌면 센다. 이 보완 뒤에도 두 DP에서 가설 차이가 남을 때만 독립 핵심 후보로 고려한다.

**현재 결론은 승격 보류다.** 그 이유는 어느 상황인지 몰라서 결정을 못 하는 것이 아니라, 이 지표의 값이 실제 Rust 변경 집합에 의존하고 해당 코드가 아직 없기 때문이다. 핵심 6개와 같은 수준의 확정 우열로 발표하지 않는다.

## 7. 범위를 한정한 PoC

제품 전체를 만들 필요는 없다. QA4와 같은 최소 실행 골격에 필요한 type, port, 모듈 연결과 실제 운영 자산을 작성한 뒤 각 변경을 독립 patch로 구현한다. 기능 완료 조건은 짧은 통합 test와 계약 검증으로 확인한다. 테스트 전용 파일의 수정은 집계하지 않는다.

1. 양안의 module manifest와 change pack을 먼저 고정한다.
2. 각 변경을 동일 baseline에서 독립 구현한다. 다른 변경의 개선을 먼저 가져오지 않는다.
3. 실제 diff를 module path와 소유 자산으로 매핑한다.
4. 변경마다 요구를 만족했는지 확인한다.
5. 미리 정한 쌍의 교집합을 계산한다.
6. 코드 수준 충돌이 있었는지는 별도 원장에 남긴다. 자동 병합 성공을 의미적 통합 성공과 같게 보지 않는다.

AI coding 도구를 쓰면 같은 모델 / 버전과 도구 접근 범위, 구현 요구와 검증 범위를 기록한다. 다른 스타일로 임의 재작성한 모듈을 최소 변경인 것처럼 세지 않는다. 코드 패치가 필요한 범위인지 독립 리뷰로 확인한다. 인간 또는 AI가 과제마다 작업한 시간은 보조 메모이며 QA08 산식에 넣지 않는다.

**최소 원장:** `baseline_commit, alternative, change_id, requirement, completion_check, module_manifest_ref, changed_module_ids, source_diff, owned_asset_diff, pair_id, intersection_ids, overlap_count, actual_merge_conflict, reviewer, evidence_class`.

**실패 처리:** 미완료 과제, 허용 기능 삭제, 한쪽만 거대 모듈 재구성, 생성 코드 중복 집계, 소유 자산 누락을 발견하면 해당 분석을 수정한다. 수정 전 원장을 보존한다. 차이가 총 1개 중복 모듈뿐이면 실제 요구로 인한 차이인지 먼저 확인하고 단순 파일 배치 차이를 구조적 우위로 과장하지 않는다.

## 8. 발표 한 장 카드

| 칸 | 사용할 문구 |
| --- | --- |
| 제목 | **둘이 다른 기능을 고칠 때 같은 곳을 얼마나 건드리는가** |
| 정의 / 지표 | 독립 변경 두 개가 함께 수정하는 Rust 모듈 수의 평균 |
| 목표 / 근거 | **1개/쌍 이하** — 공통 조정 영역을 한 곳 이내로 관리하려는 협업 예산 |
