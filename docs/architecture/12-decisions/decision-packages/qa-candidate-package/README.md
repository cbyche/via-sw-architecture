# VIA QA 후보 상세안과 DP 구성 판정

> 2026-10-14 / 작성자 제안 / 독립 검토와 보완 완료 / 사용자 승인·PoC 측정·대안 선정 전

**기존 6개 QA와 추가 3개 후보를 같은 형식으로 정리한다.** 각 문서에 정의, 하나의 지표, 목표 수치의 도출, 점수, 이해 예시, DP별 예상과 최소 PoC를 둔다. 현재 논의의 중심은 [QA·DP 평가 계획](../03-03-qa-dp-evaluation-plan.md)이며 이 폴더는 그 상세 명세다.

**[품질 요구사항 표와 발표용 요약](./quality-requirements-table.md):** 대화에서 제공한 QA 9개 표와 중요도·난이도 판단 근거를 보존했다. 같은 파일의 [발표용 축약 표](./quality-requirements-table.md#presentation-table)는 Scenario를 정의·목표·측정 조건·목표 근거 각 한 줄로 정리한다.

## 1. 먼저 읽을 결론

1. **첫 응답 지연시간을 1순위로 유지한다.** 실제 발화 종료·입력 제출·업무 사건 발생부터 첫 정답 내용이 해당 UI에 표시될 때까지를 잰다. 위임 전의 구체적 수행 안내는 인정하고 인사·spinner는 제외한다. 음성은 사용자가 들을 수 있을 때 따로 전달한다.
2. **지칭 대상 집합 일치율은 47과 45에 같은 의미로 적용할 수 있다.** 하지만 같은 지표로 측정 가능하다는 것과 두 안의 정확도 차이가 있다는 것은 별개다. 강한 B의 원본 보존과 보완 경로까지 인정하면 정확도 차이를 미리 확신할 근거는 약하다.
3. **숫자의 근거는 모두 공개하되 근거의 종류를 구별한다.** HCI 지침, 공식 API 의미, 팀의 협업 요구와 작성자 제품 예산을 섞지 않는다. 연구가 VIA의 98%·3개·$0.50·4GiB를 정해 준 것은 아니다.
4. **현재 네 DP와 여섯 QA의 조합이 양성과정의 선정 조건을 충족한다고 결론낼 수 없다.** 44의 속도 차이는 약하고 47은 B의 뚜렷한 이익이 부족하며 42는 정상 사용에서 세 번째 비교 축과 B의 이익이 부족하다. 추가 후보를 정의해도 그 빈칸이 자동으로 채워지지 않는다.

이 결론은 DP를 폐기하거나 대안을 선정하는 결정이 아니다. 먼저 명확한 QA를 완성한 뒤 실제 구조가 어떤 손익을 만드는지 검토한 결과다. 다음 단계는 **현재 비교안의 이익을 강화할 수 있는지 검토하고 최소 경로로 차이 가설을 확인하는 것**이다. 전체 제품 구현이나 큰 모델 실험부터 시작할 근거는 없다.

## 2. 기존 여섯 QA의 제안 순서

`후보 QA01~09`는 이 패키지에서 읽는 순서다. 기존 `ASR-QA-*`나 `QA-09/19/29/39`를 재번호하지 않는다. 아래 수치는 **목표 제안**이며 측정 결과가 아니다.

| 순위 | QA / 상세 명세 | 단일 지표 | 목표 | 숫자의 직접 근거 |
| --- | --- | --- | --- | --- |
| 1 | [첫 응답 지연시간](./qa01-first-response-latency.md) | 평균 첫 응답 지연시간 | **1초 이하** | HCI의 약 1초 UI 지침을 평균 목표로 적용한 설계 판단 |
| 2 | [지칭 대상 식별 정확도](./qa02-referent-accuracy.md) | 지칭 대상 집합 일치율 | **98% 이상** | 50건당 오류 1건 이하의 제품 예산 제안 |
| 3 | [VIA 처리시간](./qa03-via-processing-time.md) | 평균 VIA 귀속 처리시간 | **5초 이하** | 의미·근거·상태·응답 준비·내부 대기를 배분한 처리 예산 |
| 4 | [변경 범위](./qa04-change-scope.md) | 변경 과제당 평균 변경 Rust 모듈 수 | **3개 이하** | 단순 연동 3건×1개와 의미 변경 3건×5개의 협업 예산 |
| 5 | [모델 사용 비용](./qa05-model-cost.md) | 20요청 활동당 평균 총 모델 비용 | **$0.50 이하** | 월 $20와 월20일·일40요청의 사업 예산 가정 |
| 6 | [최대 로컬 메모리](./qa06-local-memory.md) | VIA 전체 동시 최대 commit | **4,096MiB 이하** | 32GiB급 장치 계획에서 VIA에 배정한 commit 예산 |

**우선순위의 이유:** 사용자가 대화를 이어갈 첫 반응 → 잘못 지정한 대상 때문에 다시 설명해야 하는 부담 → 첫 안내 뒤에도 남는 전체 처리 부담 → AI 코딩 병행 개발의 변경 파급 → 운영 비용 → 로컬 자원 공존 순서다. 필수 기능·권한·최소 장치 조건을 만족하는 대안 사이에서 사용하는 순서이며 낮은 순위의 큰 손실을 무시하는 규칙은 아니다.

| --- | --- |
| QA01 | 기존 ASR-QA-02 응답성의 경계 재검토. 텍스트 첫 내용 표시로 구체화했으므로 기존 음성·중단 집계 결과와 호환되지 않음 |

| QA03 | 기존 ASR-QA-03 VIA 귀속 시간의 시작·종료·겹침 규칙 재검토 |
| QA04 | 기존 ASR-QA-05 변경 용이성. 책임 단위에서 실제 Rust 모듈 수로 바뀌므로 이전 수치 재사용 불가 |

## 4. QA–DP 대응과 예상 우열

**실측 확인은 전부 0개다.** 아래는 문서상 대표 사례에 대한 사전 예측이다. `A/B`는 방향이 있는 가설, `약`은 실용 차이 근거가 특히 부족함, `=`는 실용적 동점 예상, `진단`은 추가 확인 범위다. 동점과 약한 방향을 확정 커버리지로 세지 않는다.

| QA | DP-44 | DP-47 | DP-45 | DP-42 |
| --- | --- | --- | --- | --- |
| 01 첫 응답 | **B 약** | **A** | **B** | **=** |
| 02 지칭 정확도 | = | **= / 차이 탐색** | **A 약** | = |
| 03 VIA 처리시간 | **B 약** | A 보완 | B 보완 | **A** |
| 04 변경 범위 | **A** | A 보완 | **A** | = |
| 05 모델 비용 | = | **A** | **A 약** | = |
| 06 최대 메모리 | A 진단 | **A 약** | A 진단 | **A** |
| 07 부하 추가 지연 | = | 진단 | 진단 | = |
| 08 병행 수정 중복 | = | 진단 | A 약 | = |
| 09 음성 전달 지연 | = | 공통 검증 | 공통 검증 | = |

주요 선택 축을 굵게 표시했으며 실제로 영향을 받는 추가 축도 숨기지 않는다. 표의 방향보다 각 QA 문서의 **대표 모집단·강한 대안·한 문장 구조 설명**이 우선한다. QA마다 평가 질문이 다르므로 latency 사건 집합, 변경 과제 집합, 비용 활동을 같은 분모에 억지로 합치지 않는다. 같은 QA를 DP별로 다른 뜻으로 재정의하지 않는다.

### DP별 구조 설명과 구성 판정

| 제안 DP 순위 | 발표에서 말할 핵심 손익 | 현재 판정 |
| --- | --- | --- |
| **1. 44** | B는 완료에서 다음 처리를 직접 시작할 수 있고 A는 교차 경로의 진행 규칙을 중앙에서 바꾸기 쉽다. | 응답 대기 대 변경 범위의 방향은 설명 가능. A도 짧은 async dispatcher여서 시간 차이가 핵심 수준인지 불확실 |
| **2. 47** | A는 원본을 함께 판단하고 B는 후보·근거·revision을 나누어 유지하며 결합한다. | A의 시간·비용 이익은 가설로 남지만 B의 정확도 이익은 자동 성립하지 않음. 현재 여섯 QA에서 균형 있는 trade-off 부족 |
| **3. 45** | B는 게시 관계를 읽어 요청 때의 조합을 줄이고 A는 필요 없는 선행 생산과 새 관계 계약의 변경을 줄인다. | 첫 반응 대 변경·전체 비용의 trade-off가 가장 설명하기 쉬움. A cache와 B backfill 비용을 포함해 확인 필요 |
| **4. 42** | A는 로컬 상태를 함께 확정하고 B는 서비스별 확정과 receipt로 연결한다. | A의 처리시간·메모리 이익 가설은 있으나 B의 중요한 정상 사용 이익과 세 번째 차이 축 부족 |

**순위의 근거:** 44는 상시 입력과 업무 사건을 대화에 연결하는 실행을 직접 다룬다. 47은 말과 화면 지칭이라는 VIA의 핵심 기능이다. 45는 과거 설명과 업무를 재사용하는 편의다. 42는 그 상태들의 수명을 연결하는 기반이다. 이는 **사용자 문제의 우선순위 제안**이다. 심사에 적합한 비교안으로 완성됐다는 점수나 A/B 승패와 혼동하지 않는다.

### 양성과정 조건별 결론

| 사용자 조건 | 현 상태 |
| --- | --- |
| 명확한 단일 지표의 QA 4~6개 | 기존 여섯 개 상세 명세 제안 완료. 추가 세 개는 후보·회귀용 |
| QA마다 최소 2개 DP에서 차이 | 02의 정확도와 06의 메모리는 두 연결의 실용 차이 근거 부족. 다른 항목도 실측 전 |
| DP마다 3~4개 QA의 차이 | 42는 특히 부족. 44는 시간 두 축과 변경 범위의 차이 강도 검토 필요 |
| 1순위 QA가 1순위 DP의 주된 목표 | 44와 첫 응답의 문제 관계는 적합. 실제 대안 차이는 약한 가설 |
| 1순위 QA가 최소3개 DP에서 차이 | 47·45의 방향과 44의 약한 가설. 현재 ‘3개 확보’라고 발표하면 과장 |
| 서로 좋은 점이 다른 대안을 비교 | 45는 설명 가능. 44는 조건부 가설. 47·42는 B의 이익 보강 필요 |

**추천:** QA 정의와 목표안을 먼저 사용자 검토본으로 채택하고, 44의 시간 차이와 47·42의 B 이익을 짧은 설계 재검토의 우선 과제로 둔다. 그 검토에서도 같은 결론이면 DP 한두 개의 비교 주제를 바꾸는 것이 점수나 모집단을 꾸미는 것보다 타당하다. 현재 문서에서는 DP를 변경하지 않는다.

## 5. 근거를 읽는 법

| 근거 수준 | 해당 예 | 말할 수 있는 것 |
| --- | --- | --- |
| 공식 정의·관측 계약 | Rust module, Windows commit, 모델 usage bucket | 무엇을 어떻게 세는지 |
| 사용자 경험 지침·연구 | UI 약1초 지침, 인간 턴 교환과 VR 음성 Agent 연구 | 응답 대기를 중요하게 다루는 이유와 목표 제안의 출발점 |
| 팀에서 직접 나온 요구 | AI 코딩 병행 변경·충돌·담당 경계 경험 | 변경 파급과 중복을 평가할 이유 |
| 작성자 요구 예산 | 오류1/50, 평균3모듈, 월$20, commit4GiB, 음성0.5초 | 목표 숫자의 재현 가능한 산식. 사용자 승인 요구나 실증 최적값은 아님 |
| 구조 검토 | 실행 의존, 원본/파생 상태, 확정과 전달 경계 | PoC 전에 설명할 예상 우열과 반증 조건 |
| PoC 증거 | 아직 없음 | 현 문서로 달성 수치나 실제 우승자를 주장할 수 없음 |

모든 QA의 **숫자 출처를 추적 가능하게 만드는 것**과 모든 숫자가 논문으로 입증된 것은 다르다. 사업·장치·협업 예산은 그 결정을 내리는 이해관계자가 확정해야 한다. 현재는 구체적인 제안을 완성해 검토 가능하게 한 단계다.

## 6. 공통 점수와 실패 규칙

| 점수 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 표시 | ○○○ | ◐○○ | ●○○ | ●◐○ | ●●○ | ●●◐ | ●●● |

0점은 목표 미달, 1~6점은 목표 충족과 개선 여유다. 같은 QA의 두 안에는 같은 점수 함수를 적용한다. 원값과 실패를 함께 표시하며 원값이 같은 경우 서로 다른 점수를 주지 않는다. 점수를 가중 합산해 상위 QA 손실을 가리지 않는다.

- **미측정·계측 누락·미완료 변경**은 0점과 구별한다. 수행한 필수 응답 시험에서 제한시간 내 응답하지 않은 실패는 해당 시간 QA의 명시 규칙을 따른다.
- 문헌은 중간 점수 경계를 정해주지 않는다. 각 QA 문서는 목표와 최고 수준 및 중간 구간의 설계 원리를 별도로 적는다.
- 예비 PoC 후 본 비교 전에 해상도를 보정할 수 있다. 본 비교 뒤 바꾸면 원래 구간과 점수, 변경 이유와 양안 재채점 결과를 모두 보존한다.
- 허용 범위·산식·모집단을 바꾸면 단순 재채점이 아니라 새 평가 버전이다. 기존 결과를 새 지표로 이름만 바꾸지 않는다.
- 적은 표본에서 일부 점수가 나오지 않는 것은 정상이다. 점수를 채우려고 같은 사례를 복제하지 않는다.

## 7. 다음 실행의 순서와 범위

1. **명세 검토:** QA1의 UI 종료점, QA3의 외부 시간 제거, Rust 모듈 단위와 목표 예산을 함께 검토한다.
2. **DP 손익 보강 검토:** 44의 임계 경로와 47·42의 B가 주는 사용자 이익을 다시 확인한다. 문제와 QA 의미는 고정하고 대안의 실질 메커니즘을 확인한다.
3. **최소 PoC 준비:** 구현할 비교 경로, 공통 주변부, fixture, 모델·Windows profile, 원시 trace와 동일 조건을 확정한다. 각 QA 문서의 수량은 실행 전 제안이다.
4. **예상과 측정 비교:** 먼저 사전 우열과 한 문장 원인을 고정하고 실제 원값을 측정한다. 반대 결과가 나오면 측정 경계·구현 대등성을 확인하고 정당한 결과를 보존한다.
5. **채점과 발표:** 동일 구간으로 원값을 채점하고 각 QA의 한 장 설명과 DP의 trade-off 표에 연결한다. 합격선과 실용 차이 기준을 구별한다.

현재 작업은 1의 상세안과 2의 검토 쟁점을 준비한 것이다. 제품 구현, 모델 실행, Windows 계측, 측정 동결, 대안 선정이나 원격 게시를 수행한 상태로 표현하지 않는다.
