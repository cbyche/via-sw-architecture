# VIA 품질 요구사항 표와 발표용 요약

> 2026-10-14 / QA01~QA09 검토안 / 목표 수치와 중요도·난이도는 제안 / 미측정

사용자가 제공한 품질 요구사항 레퍼런스의 `ID / 분류 / Title / Scenario / 중요도·난이도` 형식으로 정리한다. [대화에서 제공한 상세 표](#detailed-table)와 판단 근거를 그대로 보존하고 같은 파일에 [발표용 축약 표](#presentation-table)를 제공한다. 대화의 로컬 파일 링크는 GitHub에서 열 수 있는 상대경로로 바꿨다.

QA01~QA09는 [QA 후보 패키지](./README.md)의 식별자다. 기존 ASR 번호를 변경하지 않는다. 각 QA의 측정 경계·예외·점수·DP 관계는 연결된 상세 명세를 따른다.

## 1. 대화에서 제공한 상세 표

첨부 표의 **ID / 분류 / Title / Scenario / 중요도·난이도** 구성을 따랐습니다. Scenario에는 **요구사항 문장 → 정량 목표 → 측정 조건 → 목표 근거**를 넣었습니다.

목표 수치는 기존 문서의 **검토용 제안값**입니다. 중요도·난이도는 이번에 제안하는 등급이며 **H=높음 / M=보통 / L=낮음**입니다.

| **[QA07](./qa07-load-interference.md)** | Performance<br>성능 | **부하 추가 지연** | 시스템은 다른 업무의 사건을 함께 처리할 때 **현재 사용자 요청의 첫 응답에 추가되는 지연을 작게 유지해야 한다.**<br><br>**[평균 부하 추가 지연 ≤ 200ms]**<br><br>**측정 조건:** 동일 요청의 부하 없음·있음 조건을 비교한다. 대표 사례 4개와 사건 겹침 시점 3개의 **12개 조합**을 조건별 20회 반복한다. 조합마다 `부하 있음 평균 − 부하 없음 평균`을 계산하고 음수는 0으로 처리한 뒤 12개 값을 평균낸다. 첫 응답의 경계는 QA01과 같다. 다른 업무의 사건을 유실하거나 무기한 미뤄 지연을 줄인 경우는 인정하지 않는다.<br><br>**목표 근거:** 첫 응답 **1,000ms** 예산 중 단일 요청 처리에 **800ms**와 동시 업무 간섭에 **200ms**를 배정했다. | **M / H** |
| **[QA08](./qa08-parallel-change-overlap.md)** | Maintainability<br>변경 용이성 | **병행 수정 중복** | 시스템은 독립적인 두 기능 변경을 병행할 때 **양쪽에서 함께 수정해야 하는 모듈의 범위를 작게 유지해야 한다.**<br><br>**[변경 쌍당 평균 공통 수정 모듈 수 ≤ 1개]**<br><br>**측정 조건:** QA04의 변경 과제 6개로 사전에 정한 독립 변경 쌍 6개를 평가한다. 두 변경을 같은 기준선에서 각각 수행한 뒤 **변경 모듈 집합의 교집합 크기**를 계산하고 평균낸다. 모듈 정의와 운영 자산의 집계 규칙은 QA04와 동일하다. 실제 Git 충돌 횟수나 통합 작업시간으로 해석하지 않는다.<br><br>**목표 근거:** 각 변경은 담당 영역에서 완료하고 공통 계약이나 연결부의 조정은 **쌍당 평균 1개 모듈 이내**로 제한하려는 팀 협업 예산이다. | **M / M** |
| **[QA09](./qa09-audio-delivery-lag.md)** | Performance<br>성능 | **음성 전달 지연** | 시스템은 채택한 응답의 음성 요약을 **사용자가 들을 수 있는 시간에 신속하게 전달해야 한다.**<br><br>**[평균 음성 전달 지연 ≤ 500ms]**<br><br>**측정 조건:** 대표 사례 6개를 20회 반복한다. **올바른 응답 내용을 채택한 시점부터 해당 요약의 첫 내용 음성이 실제 출력될 때까지 재생 가능한 시간만 누적**한다. 사용자 발화·앞선 응답 재생 등으로 말할 수 없는 시간은 제외한다. 요약 생성·TTS·내부 큐·출력 장치 대기는 포함한다. 텍스트 표시나 음성 준비 완료 시점부터 측정을 시작하지 않는다.<br><br>**목표 근거:** 짧은 요약 준비 **200ms** + 첫 음성 생성 **200ms** + 현재성 확인·출력 큐·장치 재생 시작 **100ms**의 추가 전달 예산이다. | **H / H** |

### 1.2 중요도와 난이도 판단 근거

**중요도는 목표 미달이 사용자와 개발·운영에 미치는 영향**을 기준으로 했습니다. **난이도는 목표를 달성하기 위해 필요한 구조적 조정의 복잡성**을 기준으로 한 사전 판단입니다.

| QA | 중요도 판단 이유 | 난이도 판단 이유 |
|---|---|---|
| **QA01** | 첫 응답이 늦으면 사용자가 대화가 이어지고 있는지 확인하기 어렵다. **VIA의 핵심 사용 경험**이다. | 입력 종료 판단부터 해석·내용 채택·실제 표시까지 여러 경로를 평균 1초 안에 연결해야 한다. |
| **QA02** | 지칭 오류는 잘못된 자료 처리와 사용자의 재설명으로 이어진다. **말과 화면을 이해하는 기능의 핵심**이다. | 화면 변화·복수 대상·부분 정정·과거 버전을 함께 구별해야 한다. |
| **QA03** | 첫 안내 이후에도 처리가 길어지면 사용자는 업무가 진행되지 않는다고 느낀다. | 해석·근거 보완·상태 확정·Agent 연결·최종 응답 준비의 전체 경로를 줄여야 한다. |
| **QA04** | AI 코딩 병행 개발에서 수정 영역의 확산은 협의와 통합 부담을 키운다는 **팀의 직접적인 요구**가 있다. | 정정·조회·권한 계약의 확장이 여러 상태와 소비 경로로 퍼지는 것을 제한해야 한다. |
| **QA05** | 반복 사용에 따른 모델 비용이 서비스 운영 부담으로 누적된다. | 입력량·재사용·생산 시점·재시도 정책을 조정하되 응답 품질과 필요한 처리를 유지해야 한다. |
| **QA06** | VIA가 사용자 업무 앱과 PC 자원을 함께 사용해야 한다. | 원본 버퍼·사본·캐시·후보 상태의 크기와 수명을 관리해야 한다. 현재 후보 문서의 클라우드 모델 구성을 기준으로 판단했다. |
| **QA07** | 여러 업무를 맡긴 상태의 대화 경험을 확인한다. 절대 응답 지연은 QA01에서도 다루므로 보완 항목으로 둔다. | 작업 간 CPU·모델·저장 경합을 제어하면서 다른 업무의 처리도 유지해야 한다. |
| **QA08** | 변경 범위가 같더라도 수정 영역이 겹치면 병행 개발의 조율 부담이 커질 수 있다. | 담당 모듈과 공통 계약의 경계를 조정해야 하며 QA04의 변경 집합을 활용해 평가할 수 있다. |
| **QA09** | 음성 전달이 늦거나 빠지면 화면을 보지 않는 사용자는 대화를 이어가기 어렵다. **음성 서비스의 필수 품질**이다. | 요약·음성 생성·실제 출력을 연결하면서 사용자 발화와 응답 차례 및 최신 내용을 함께 지켜야 한다. |

### 1.3 표를 해석할 때 유지할 조건

- **평균 목표와 개별 사례 보장은 다릅니다.** 실패나 느린 사례를 숨기지 않고 원값과 함께 확인합니다.
- QA05·QA06의 공통 활동은 **이력 200턴·완료 업무 20개·진행 업무 5개**에서 시작하며 원본 변경 2건과 Agent 사건 6건을 포함합니다. 초기 준비부터 후속 작업까지 관측합니다.
- **QA01~QA06은 핵심 검토 대상**입니다. QA07은 QA01의 부하 진단이며 QA08은 QA04의 협업 보조 지표입니다. QA09는 필수 음성 검증 항목입니다. **중요도가 높다는 사실만으로 DP의 두 방안을 구별하는 핵심 평가축이 되는 것은 아닙니다.**
- 여기의 **H/M/L은 중요도·난이도 평가**입니다. 이후 PoC 결과에 부여할 **0~6점 성능 점수와는 별개**입니다.

## 2. 발표용 축약 표

각 Scenario는 **정의 한 줄 → 목표 한 줄 → ※ 측정 조건 한 줄 → ※ 목표 근거 한 줄**로 구성한다. 목표와 H/M/L은 검토안이며 QA별 상세 규칙은 ID의 링크에서 확인한다.

| ID | 분류 | Title | Scenario | 중요도 / 난이도 |
|---|---|---|---|---|
| [QA01](./qa01-first-response-latency.md) | Performance | **첫 응답 지연시간** | 시스템은 사용자 요청이나 업무 사건에 대한 **구체적인 첫 응답을 신속하게 화면에 표시해야 한다.**<br>**[평균 첫 응답 지연시간 ≤ 1초]**<br>※ 측정 조건: 발화 종료·입력 제출·Agent 원천 제공 → 첫 정답 내용 표시 / 30사례 × 3회<br>※ 목표 근거: HCI의 약 1초 UI 응답 지침을 평균 목표로 적용 | **H / H** |
| [QA02](./qa02-referent-accuracy.md) | Accuracy | **지칭 대상 식별 정확도** | 시스템은 사용자가 화면이나 과거 이력을 지칭할 때 **의도한 대상 집합을 누락이나 추가 없이 정확하게 식별해야 한다.**<br>**[지칭 대상 집합 일치율 ≥ 98%]**<br>※ 측정 조건: 화면·과거 지칭 각 20개 × 5회 / 식별 가능한 대상 집합의 완전 일치<br>※ 목표 근거: 지칭 50건당 식별 오류 1건 수준 이하의 제품 오류 예산 | **H / H** |
| [QA03](./qa03-via-processing-time.md) | Performance | **VIA 처리시간** | 시스템은 사용자 목표를 완료하는 과정에서 **VIA가 담당하는 처리의 소요시간을 최소화해야 한다.**<br>**[평균 VIA 귀속 처리시간 ≤ 5초]**<br>※ 측정 조건: 12목표 × 5회 / 외부 업무·사용자 대기·발화를 제외한 완료 경로<br>※ 목표 근거: 해석 1.5 + 근거 1 + 연결 0.5 + 응답 준비 1.5 + 여유 0.5 = 5초 | **H / H** |
| [QA04](./qa04-change-scope.md) | Maintainability | **변경 범위** | 시스템은 기능이나 연동 계약을 변경할 때 **수정이 필요한 Rust 모듈의 범위를 작게 유지해야 한다.**<br>**[변경 과제당 평균 변경 모듈 수 ≤ 3개]**<br>※ 측정 조건: 동일 기준선의 변경 6건 / 수정·추가·삭제한 고유 운영 Rust 모듈 수<br>※ 목표 근거: (연동 3건 × 1개 + 의미 변경 3건 × 5개) ÷ 6 = 평균 3개 | **H / H** |
| [QA05](./qa05-model-cost.md) | Cost Efficiency | **모델 사용 비용** | 시스템은 동일한 사용자 활동을 처리하는 데 필요한 **음성·의미 모델의 총사용 비용을 최소화해야 한다.**<br>**[20요청 활동당 평균 총 모델 비용 ≤ $0.50]**<br>※ 측정 조건: 20요청 활동 5회 / 준비·음성·갱신·재시도·폐기를 포함한 전체 청구량<br>※ 목표 근거: 월 예산 $20 ÷ (20일 × 일 40요청) × 20요청 = $0.50 | **M / M** |
| [QA06](./qa06-local-memory.md) | Resource Efficiency | **최대 로컬 메모리** | 시스템은 다른 PC 업무와 함께 실행할 수 있도록 **로컬에서 동시에 확보하는 메모리의 최대량을 제한해야 한다.**<br>**[VIA 전체 동시 최대 commit 메모리 ≤ 4,096MiB]**<br>※ 측정 조건: Windows·클라우드 모델 / 20요청 활동 5회 / 전체 VIA의 동시 commit 최대값<br>※ 목표 근거: 32GiB급 PC 예산 배분 — OS 8 + 업무 16 + VIA 4 + 여유 4GiB | **M / M** |
| [QA07](./qa07-load-interference.md) | Performance | **부하 추가 지연** | 시스템은 다른 업무의 사건을 함께 처리할 때 **현재 사용자 요청의 첫 응답에 추가되는 지연을 작게 유지해야 한다.**<br>**[평균 부하 추가 지연 ≤ 200ms]**<br>※ 측정 조건: 4사례 × 3시점 × 조건별 20회 / 부하 유무의 평균 차이 중 증가분 집계<br>※ 목표 근거: 첫 응답 1,000ms − 단일 요청 처리 800ms = 간섭 예산 200ms | **M / H** |
| [QA08](./qa08-parallel-change-overlap.md) | Maintainability | **병행 수정 중복** | 시스템은 독립적인 두 기능 변경을 병행할 때 **양쪽에서 함께 수정해야 하는 모듈의 범위를 작게 유지해야 한다.**<br>**[변경 쌍당 평균 공통 수정 모듈 수 ≤ 1개]**<br>※ 측정 조건: 독립 변경 6쌍 / 같은 기준선에서 각각 변경한 Rust 모듈 집합의 교집합<br>※ 목표 근거: 공통 계약·연결부의 조정을 변경 쌍당 평균 1개로 제한하는 협업 예산 | **M / M** |
| [QA09](./qa09-audio-delivery-lag.md) | Performance | **음성 전달 지연** | 시스템은 채택한 응답의 음성 요약을 **사용자가 들을 수 있는 시간에 신속하게 전달해야 한다.**<br>**[평균 음성 전달 지연 ≤ 500ms]**<br>※ 측정 조건: 6사례 × 20회 / 내용 채택 → 실제 음성 시작 중 재생 가능한 시간만 누적<br>※ 목표 근거: 요약 준비 200ms + 첫 음성 생성 200ms + 출력 100ms = 500ms | **H / H** |

발표 표 아래에는 다음 두 문장을 공통 각주로 둔다.

- 목표 수치와 중요도·난이도는 제안값이며 실제 성능 평가는 PoC에서 수행한다.
- QA01~QA06은 핵심 검토 대상이며 QA07·QA08은 보조 지표와 QA09는 필수 음성 검증 항목이다.

측정 상세와 실패 처리, 목표 산식의 가정, 0~6점 구간, 예시와 QA–DP 관계는 각 QA 상세 명세와 [패키지 대응표](./README.md#4-qadp-대응과-예상-우열)로 연결한다.
