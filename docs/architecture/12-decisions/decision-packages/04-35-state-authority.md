# 04-35. 대화와 업무 상태의 원본 — 현재 상태와 확정 사건

> 사용자 검토: 35에 유지, 40번대 승격하지 않음 / 2026-10-05 / [가이드](./04-30-comparison-guide.md) / 이전: [음성 처리](./04-34-incremental-voice.md) / 다음: [권한 격리](./04-36-capability-isolation.md)

**A는 저장된 현재 상태를 읽어 이어가고, B는 확정된 사건을 적용해 현재 상태를 만들어 이어간다.** A도 감사 이력과 미완료 전송을 기록한다. B의 차이는 기록량이 아니라 사건이 상태의 원본이라는 점이다.

**메인 그림에서 볼 차이:** 같은 질문 답변과 업무 조건 변경을 A는 현재 값으로 확정하고, B는 의미 사건으로 확정해 현재 값을 계산한다. 정상 상태 생산과 조회를 먼저 보고, B의 재구성 경로가 어떤 추가 능력과 유지 부담을 만드는지 비교한다. 단순 재시작은 B만의 이익이 아니다.

읽는 순서는 **사용자 상황 → 구조도 → 같은 사례의 흐름 → 품질 손익 → 가장 싼 전환 반론**이다. 그림 없이 읽을 때도 §3의 생산 책임과 §4의 사건 표로 같은 결론에 도달하도록 작성했다.

| 먼저 알아둘 말 | 쉬운 뜻 |
| --- | --- |
| 사건 원본 | 질문 답변 확정이나 Agent 접수 확인처럼 이미 일어난 의미 있는 변경의 기록 |
| projection과 replay | projection은 사건으로 계산한 조회 상태, replay는 같은 계산을 다시 수행하는 복구 |

## 0. 사용자 검토 결론과 다시 읽을 때의 핵심 (2026-10-05)

**35는 현재 번호의 구조 검토 자료로 유지하고 40번대 유력 Decision Point 후보로 올리지 않는다.** 사용자는 A/B가 구조적으로 다르다는 점은 인정하지만, 이 차이가 현재 VIA의 중요한 품질속성에 큰 영향을 미치는 주요 결정은 아니라는 결론을 내렸다. 이는 A 또는 B의 채택도, 측정으로 차이가 작다고 입증했다는 뜻도 아니다. 상태 저장 기능의 필요성과 이 비교를 주요 발표 결정으로 선정할 가치는 구별한다.

### 0.1 A는 최종 상태만, B는 모든 history를 남기는가?

그 구분은 아니다. **A도 필요한 변경 이력을 충분히 남길 수 있다. 차이는 현재 상태를 무엇으로부터 확정하는가다.** 여기서 ‘현재 상태’는 업무가 끝났을 때의 최종 결과만이 아니라, 진행 중인 질문, 업무 조건, 미완료 명령과 접수 상태까지 포함한다.

같은 보고서 T1의 기간을 사용자가 ‘상반기’에서 ‘3분기’로 정정했다고 하자. 두 안 모두 공통 의미 해석과 현재 유효성 검사를 거친 뒤 정정을 채택한다. 아래 값은 동작 설명용이며 새 schema의 선정이 아니다.

| 확인할 것 | A: 현재 상태가 원본 | B: 확정 사건이 원본 |
| --- | --- | --- |
| 이번 정정 때 확정할 기록 | T1의 현재 기간을 `3분기`로 변경. `상반기 → 3분기`라는 감사 기록도 함께 남길 수 있음 | `T1 기간을 3분기로 변경하기로 확정`한 사건을 기록하고, 코드로 현재 기간 `3분기`를 계산해 함께 저장 |
| 다음 요청이 읽는 것 | 저장된 T1의 현재 기간 `3분기` | 이미 계산해 저장한 T1의 현재 기간 `3분기` |
| 이력의 역할 | 현재 값이 된 경위를 설명하고 진단/검증을 보조 | 현재 값을 생산하고 필요 시 다시 계산하는 권위 원본 |
| 현재 값과 이력이 어긋날 때 | 이력이 자동으로 현재 값을 덮는 원본은 아님. 검증과 복구 절차로 원인을 조사 | 원본 사건이 온전한지 확인한 뒤 그 사건에서 파생 상태를 재구성 |
| 사용자에게 돌아오는 결과 | 확인된 정정 상태를 안내. Agent 반영 여부는 실제 접수/결과로 구별 | 같은 결과와 같은 외부 확인 필요 |

A의 이력도 상태 재구성에 충분할 수 있다. 필요한 분석이나 복구가 그 이력으로 해결되면 B의 추가 가치는 줄어든다. 그 이력을 정상 갱신과 복구의 최종 근거로 삼고 현재 상태를 항상 그로부터 생산하도록 바꾸면 B 계열로 옮겨간다. 따라서 ‘history가 있다’만으로 B라고 부르지 않는다.

B도 모든 원문 발화, 화면과 외부 상황을 영구 저장하지 않는다. 설계한 확정 사건과 허용된 자료만 보존하며, 기록하지 않았거나 삭제한 사실을 replay로 되살릴 수 없다.

### 0.2 미리 정리하는 A와 나중에 해석하는 B인가? LLM이 기록하는가?

**두 안 모두 변경을 저장할 때 현재 상태를 만든다.** B가 상황을 통째로 보관했다가 다음 요청 때 LLM으로 다시 해석하는 구조는 아니다. B도 정상 조회마다 전체 history를 재생하지 않고 저장된 조회 상태를 읽는다.

- 공통 의미 해석에서는 Omni가 사용자의 발화를 어떤 질문/업무에 연결할지와 변경 의미를 제안할 수 있다. 기록 방식의 선택 때문에 별도 LLM을 추가하지 않는다.
- A는 검증된 변경 값을 코드로 저장한다. B는 검증된 변경을 형식이 정해진 사건으로 기록하고, reducer라는 코드로 현재 상태를 계산한다. 자유 형식 LLM 요약이 사건 원본을 대신하지 않는다.
- 외부 Agent의 접수처럼 이미 구조화된 사실은 의미 해석 LLM 없이도 기록할 수 있다. 사건 재생 역시 LLM 호출, 외부 명령 재실행 또는 음성 재생이 아니다.
- 전송 준비와 외부 접수는 두 안 모두 별도 사실이다. 사건이 많아도 받지 못한 접수 확인을 추측할 수 없다.

### 0.3 실제 차이를 인정하면서도 승격하지 않는 이유

| 품질 | 구조에서 기대할 수 있는 차이 | 현재 VIA에서 주요 선택 근거로 삼지 않는 이유 |
| --- | --- | --- |
| V-01/02/03 정확성, 적절성, 완전성 | 상태 생산 오류와 복구 가능한 관계의 범위가 달라질 여지 | 말뜻/대상/Task를 해석하는 능력은 공통이다. A도 내구 기록, 감사 이력과 복구를 지원하며 정상 기능의 큰 우열은 확인되지 않음 |
| V-04/05 반응성과 VIA 완료 시간, V-06 자원 | B의 사건/조회 상태 갱신과 재생 관리에 추가 비용 가능 | A의 감사 비용도 포함해야 한다. 실제 응답 시간이나 수용량에 큰 차이가 난다는 근거는 없음 |
| V-08 변경과 모듈성 | B는 보존된 사건으로 조회 형태를 추가하기 쉬울 수 있음 | A에도 조회 view와 모듈화를 허용한다. Agent 기술/계약 변경이 자동으로 사건 재구성의 이익이 되지 않으며 B에는 옛 사건 의미의 호환 부담도 있음 |
| V-07 복구, V-09 분석과 시험 | B는 온전한 사건으로 파생 상태를 재구성하고 상태 전이를 재현 가능 | 가장 분명한 조건부 이익이지만, 현재 요구에서 반복 활용할 중요도와 강한 A 대비 추가 가치가 주요 DP 승격을 뒷받침하지 못함 |

이 판단은 효과가 전혀 없다는 주장이 아니다. **실제 다른 저장 구조라는 사실만으로 VIA의 중요한 설계 결정이 되는 것은 아니라는 선별 결론**이다. 드문 재시작/자료 변환 사례나 일반적인 event sourcing의 장점을 늘어놓아 승격 근거를 대신하지 않는다. 기존 구현 사례의 존재도 현실성의 참고일 뿐 VIA의 효과 증명은 아니다.

### 0.4 이 문서를 남기는 목적

A/B의 원본, 정상 쓰기/조회, 복구/삭제 계약과 비용을 나중의 상세 설계 참고로 보존한다. 사건 재구성을 일상적으로 활용해야 하는 제품 요구나 강한 A로 충족하기 어려운 중요한 품질 근거가 새로 생기면 재검토할 수 있다. **지금 새 A/B를 찾거나 B의 우위를 입증해야 하는 미완료 과제로 남기지 않는다.** 아래 그림과 발표 대본은 기존 비교를 설명하는 자료이며, 그림의 완성도나 이전 작성자 평가가 이번 사용자 결론을 대체하지 않는다.

## 1. 왜 VIA에서 중요한가

보고서 업무 T1이 “기간은?”이라는 질문 Q7을 기다린다. 사용자가 “상반기로 해줘”라고 답하면 VIA는 Q7의 답변, T1의 조건과 답변을 전달할 명령 c9를 일관되게 저장해야 한다. c9가 준비된 것, Agent가 실제 접수한 것, 사용자가 진행 안내를 실제로 받은 것은 서로 다른 사실이다. 이는 매일의 정상 대화와 업무 갱신에서 필요한 상태 운영이다.

이후 자료 형식이나 조회 구조가 바뀌거나 VIA가 재시작해도 같은 관계를 이어가야 한다. 재시작 사례만으로 두 구조의 필요성을 판단하지 않는다. 정상 처리에서 무엇을 원본으로 확정하고 이후 조회와 재구성이 어디에 의존하는지 비교한다.

UC-06/10/13/15/18의 연속성을 지키는 문제다. VIA만의 고유 기능은 아니므로 기능 해석/지칭보다 우선순위는 낮다. 다만 오래 이어지는 Conversation과 여러 Task의 관계를 책임지는 VIA에서는 잘못된 복구가 실제 사용자 업무에 영향을 준다.

## 2. SW Architecture에서 무엇이 어려운가

프로그램 종료 직전의 값을 저장하는 것만으로 “답변 확정”, “전송 준비”, “Agent 접수”, “사용자에게 실제 전달”을 모두 알 수 없다. 외부 Agent의 접수는 local DB와 하나의 transaction으로 확정할 수도 없다. 더구나 새 버전에서 상태 형식이 바뀌면 과거 질문/전달 관계를 어떤 의미로 읽을지 정해야 한다.

**현재의 상태를 권위 있는 원본으로 갱신할 것인가, 확정된 사건을 원본으로 남기고 현재 상태를 그 사건으로 만들 것인가**가 결정이다. 사건 이력은 debug log가 아니라 `어떤 질문의 답을 어떤 버전에서 확정했다`와 같은 의미 있는 변경 기록이다. 같은 정상 기능을 유지하면서 쓰기, 상태 생성과 복구의 중심이 달라진다.

## 3. 공통 범위와 두 구조

Request Controller는 요청 의미, Task Manager는 업무/실행 연결, Agent Gateway는 전송, Response Manager는 전달 상태를 소유한다. State Store는 이 owner들이 만든 변경을 local transaction으로 원자 확정한다. **outbox**는 외부로 보낼 의도를 내구 저장한 원장이고, **inbox**는 받은 외부 사건의 중복을 구별하는 원장이다. 둘 다 양안에 있다.

### A. 현재 상태를 원본으로 저장

각 owner가 새 상태와 미완료 intent를 만든다. State Store는 질문, Task, 전송 및 전달 record를 함께 변경한다. 정상 읽기와 재시작은 이 현재 record를 믿는다. 감사 이력, backup과 미완료 전송 기록도 둘 수 있다. A를 이력이 전혀 없는 안으로 만들지 않는다.

상태 schema가 바뀌면 현재 값을 새 형식으로 변환한다. 과거 원인 조사에 필요한 정보가 이미 기록돼 있으면 활용할 수 있지만, 모든 과거 상태를 의미 전이로 재생할 것을 기본 계약으로 삼지 않는다.

### B. 확정 사건을 원본으로 저장하고 상태를 계산

각 owner가 현재 유효 조건을 확인하고 `질문 답변 확정`, `명령 전송 준비`, `외부 접수 확인`, `응답 실제 전달` 같은 **domain event**를 만든다. State Store의 **Journal Append Module**이 사건 묶음을 append하고 **Projection Module**이 같은 transaction에서 현재 조회 상태를 만든다.

projection은 사건으로 계산한 현재 값이다. 계산 함수인 **reducer**는 이미 확정된 사실만 적용하는 코드이며 모델을 다시 호출하지 않는다. **Checkpoint Module**은 검증한 중간 상태와 마지막 사건 위치를 저장하여 처음부터 모두 읽는 비용을 줄인다. checkpoint도 사건 의미와 삭제 정책에 맞는지 검증해야 한다.

정상 읽기는 journal 위치와 일치하는 projection을 사용한다. 재시작 시 유효 checkpoint와 이후 사건을 재생해 상태를 만들며, 새로운 조회 형태도 필요한 사실이 보존돼 있으면 같은 사건에서 구성할 수 있다. replay는 전송 intent의 상태를 복원할 뿐 외부 전송이나 음성 재생을 직접 실행하지 않는다.

메인 그림의 두 producer는 이번 답변의 의미와 Task 변경을 만드는 대표 owner다. Agent Gateway의 접수와 Response Manager의 실제 전달 기록에도 같은 원본 원칙을 적용한다. State Store가 의미를 다시 해석하거나 Task 관계를 스스로 선택하지 않는다. 그림의 반환 화살표는 대표 owner를 향한 정상 조회이며 다른 owner도 자기 상태를 읽는다. 별도 process나 분산 DB를 추가하는 선택이 아니다.

### 그림을 보며 말할 발표 대본

**① 상단의 같은 사용자 상황을 가리키며**

“보고서 업무가 기간을 물었고, 사용자는 상반기로 하라고 답했습니다. 두 안 모두 질문을 답변 완료로 바꾸고, 업무 조건과 Agent에 전달할 명령을 저장해야 합니다. 전달할 명령을 저장했다는 것과 Agent가 실제로 받았다는 것은 구분합니다. 사용자가 얻는 정상 결과는 같습니다.”

**② A의 두 owner에서 파란 원통까지 따라가며**

“A에서는 요청과 업무의 소유자가 변경할 현재 값을 만듭니다. State Store는 질문, 업무, 미완료 명령과 감사 이력을 함께 확정합니다. 이후에는 이 현재 기록을 읽어 계속 처리합니다. 감사 기록과 backup, 상태 변환도 허용하므로 A가 과거를 전혀 모르는 구조는 아닙니다.”

**③ B의 사건 원장, Projection Module, 현재 상태를 차례로 가리키며**

“B에서는 같은 소유자가 ‘Q7의 답변이 상반기로 확정됐다’, ‘c9 전송을 준비했다’라는 사건을 만듭니다. 사건이 원본이고 현재 상태는 그 사건을 적용한 계산 결과입니다. 이 계산은 모델 추론이 아니라 코드입니다. 이 비교에서는 사건과 현재 상태를 같은 transaction에 저장하므로 조회 지연이 필연이라는 전제도 없습니다.”

**④ B 아래쪽의 다시 계산하는 점선을 따라가며**

“이 구조에서는 보존된 사건으로 상태를 다시 만들거나 다른 조회 형태를 구성할 수 있습니다. 다만 필요한 사실을 기록해 두었어야 합니다. 재생한다고 없던 Agent 접수 사실이 생기거나 외부 명령이 다시 실행되는 것은 아닙니다. A의 감사 기록으로 필요한 분석이 충분하다면 이 추가 능력의 가치는 작습니다.”

**⑤ 하단의 선택 이유와 대가를 가리키며**

“현재 상태 운영과 필요한 감사 조회가 중심이면 A가 단순합니다. 상태 재구성과 원인 검증, 조회 구조 변경을 반복해서 활용한다면 B를 검토할 이유가 있습니다. 대신 사건의 옛 의미를 계속 지원하고 삭제와 재생을 관리해야 합니다. B가 의미를 더 정확하게 이해한다거나 더 빠르다고 주장하는 비교는 아닙니다. 현재 VIA에서는 이 추가 능력이 중요한 품질에 큰 영향을 미치는 주요 결정이라고 보지 않아 35의 검토 자료로 남깁니다.”

[편집용 draw.io](./diagrams/choice35-structure.drawio) / [발표용 PNG](./diagrams/choice35-structure.png). 메인 그림의 실선은 정상 변경과 기록, 점선은 조회 반환 또는 명시된 재구성이다. 네모에는 Component/Module 이름, 원통에는 상태 이름을 표시한다. §4의 긴 사건도는 동일 원칙의 장애 추적용 보충 자료이며 발표 설명의 전제는 아니다.

### 3.1 감사 기록을 가진 A와도 비교가 성립하는가

메인 그림에서 A도 **현재 상태/inbox/outbox와 감사 기록을 같은 transaction에 저장**한다. backup과 외부 접수 조회를 갖춘다. B는 감사 기록의 존재가 아니라 **확정 사건을 읽어 현재 상태를 계산하는 경로**가 정상 쓰기/읽기와 복구의 바탕이라는 점이 다르다.

| VIA에서 확인할 상황 | A로 충분한 경우 | B의 추가 가치를 검토할 경우 |
| --- | --- | --- |
| c9 전송 후 접수 확인 전 종료 | 현재 미완료 원장과 외부 조회로 복구 | B도 같은 외부 조회가 필요. 이 사례만으로 B 필요성 없음 |
| 답변이 어느 질문에 연결됐는지 조사 | 질문/답변/실제 게시 버전을 감사 기록에 남기면 추적 가능 | 확정 전이 전체로 과거 시점의 의미 상태까지 다시 구성할 필요 |
| 조회 상태 생성 코드 결함 수정 | 현재 상태 검증/변환과 backup으로 필요한 복구 달성 | 원본 사건이 온전하고 새 계산으로 파생 view를 재생성할 운영 가치 |
| 개인 자료 삭제 | 현재/파생 사본과 backup 수명 관리 | 사건 payload, checkpoint, view까지 삭제/무효화해 재생으로 부활 방지 |

확정 경위의 진단과 재연결은 VIA의 기존 기능 범위다. **모든 과거 상태의 무제한 재구성이 필수라는 새 요구는 만들지 않는다.** 현재 복구와 충분한 감사 이력으로 해결되면 A를 우선할 이유가 있다. B는 반복적인 상태 재구성/수정의 운영 가치가 사건 schema/삭제/재생 비용보다 클 때 선택한다. 사건 데이터 자체가 틀리면 replay도 잘못된 상태를 만들며 외부 결과를 발명할 수 없다.

### 3.2 정상 변경에서 실제로 교체되는 책임

공통 해석은 Q7과 T1의 관계 및 “상반기”라는 값을 제안하고 현재 질문, Task와 권한 버전을 확인한다. 의미 판단 방법 자체는 35의 선택이 아니다. 아래 예시는 설명용 필드이며 구현 schema를 선정하지 않는다.

| 단계와 생산자 | A의 상태 변경 계약 | B의 사건 생산과 상태 계산 계약 |
| --- | --- | --- |
| Request Controller | `Q7.answer=상반기`, `Q7.status=answered` 등의 변경 값과 예상 버전 | `AnswerAccepted(Q7, T1, 상반기, expected_version)` 사건 제안 |
| Task Manager | T1의 기간 및 기존 실행에 연결된 `c9=pending` 변경 값. 지원되지 않는 외부 수정은 임의 실행하지 않음 | T1 조건 변경과 `CommandPrepared(c9, T1, answer_ref)` 사건 제안. 같은 외부 지원 검사 |
| State Store | 소유자들의 변경 묶음, inbox/outbox 및 감사 이력을 원자 확정 | 사건 묶음 append와 결정적 projection, 사건 위치 및 inbox/outbox를 원자 확정. 실패하면 전체 미확정 |
| 정상 조회 | 각 owner가 현재 기록을 읽는다. 감사 기록은 진단용이며 현재 값과 불일치할 때 자동으로 원본이 되지 않음 | 각 owner가 원장 위치에 맞는 projection을 읽는다. 정상 조회마다 전체 사건을 재생하지 않음 |
| Agent Gateway | c9 전송 후 실제 접수를 확인하면 접수 상태 변경을 제안 | 같은 확인 후 접수 사건을 제안. 전송 준비 사건만으로 접수를 만들지 않음 |
| Response Manager | 실제 표시/음성 전달 반환에 따라 전달 상태 변경을 제안 | 같은 반환으로 전달 사건을 제안. 사용자에게 보냈다는 계획과 실제 전달을 구별 |

A도 갱신 함수를 공통화하고 여러 관계를 한 번에 검증할 수 있다. B의 reducer와 유사한 코드를 A에 재사용할 수 있다는 사실을 부정하지 않는다. 구조 차이는 함수 유무가 아니라 **정상 쓰기가 무엇을 권위 원본으로 확정하고 조회, 재구성, schema 변경과 삭제가 어느 기록에 의존하는가**다. 양안 모두 version 충돌은 재검사하고, 현재 동의 철회는 저장 및 외부 제공 전에 반영한다.

### 3.3 B의 추가 능력을 실제 VIA 요구에 대입한 결과

| 기존 요구와 검토할 능력 | 강한 A의 가장 싼 대응 | B에서 달라지는 점 | 현재 판단 |
| --- | --- | --- | --- |
| UC-06/10: 어느 질문의 답이 어떤 업무 조건이 됐는가 | 질문/답변/Task/버전의 감사 기록 조회 | 같은 확정 사건으로 관계와 전이를 다시 계산 | 일반 경위 설명만으로 B 필요성을 입증하지 못함 |
| UC-10/13/15: 대화의 질문 상태, Task 진행 상태, 실제 전달 상태를 서로 다른 조회 형태로 제공 | 현재 관계를 join하거나 조회용 view/cache 추가 | 보존 사건을 입력으로 새로운 projection 구성, 기존 사건 생산 계약을 유지할 수 있음 | 여러 조회가 있다는 사실만으로는 부족. 기존 상태/감사로 원하는 조회를 만들 수 없거나 변경 작업이 반복해서 더 클 때 조건부 이익 |
| UC-18: 조회 상태 계산 결함을 고치고 관계 재구성 | 현재 상태 검증, 감사 원장 참조, 변환과 backup | 원본 사건이 맞으면 수정한 계산으로 파생 상태 재생성 | 실제 능력 차이가 있으나 드문 장애 하나를 주력 선택 근거로 삼지 않음 |
| 상태 생산/조회 로직을 반복 검증 | 감사 기록과 fixture로 필요한 사례 구성 | 보존된 의미 전이로 상태 계산을 재현하고 비교 | V-09의 조건부 운영 이익. 모델 의미 판단이나 외부 실행 전체의 재현은 아님 |

**작성자 판단:** 현재 고정 요구에는 “모든 과거 상태를 반복 재구성해야 한다”는 조건이 없다. 강한 A에 감사와 조회 view를 더하는 경로가 많은 요구를 충족한다. 따라서 B의 반복 활용 빈도나 변경 비용 우위를 확보했다고 보고하지 않는다. 보강 결과는 B를 무조건 추천하는 결론이 아니라, 현재 운영 중심이면 A, 기록된 사건의 재사용이 지속적인 개발/운영 수단이면 B라는 선택 기준을 구체화한 것이다.

B의 비용도 정상 경로에 있다. event와 projection을 함께 갱신하고, 사건 reader와 계산 코드의 호환, checkpoint 유효성 및 삭제 후 재생 차단을 관리한다. A도 감사와 내구 원장을 쓰므로 B의 추가 비용을 전체 기록량으로 부풀리지 않는다. V-08은 조회 형태 변경과 사건 의미 변경을 나누어 평가하며, 의미 변경이 잦으면 B의 장기 호환 부담이 더 클 수 있다.

메인 정상 사례에 접수 확인 전 종료를 추가한 추적이다. 두 안 모두 이 문제를 풀어야 하며, 이 사건도의 성공 결과를 B의 독점 이익으로 세지 않는다.

## 6. 실패, 삭제와 지원 한계

| 사건 | A | B |
| --- | --- | --- |
| commit 전/후 crash | 원자 transaction의 결과와 미완료 intent로 구별 | 동일, journal/projection 위치를 함께 확정하지 못하면 실행 차단 |
| 접수 ACK 유실 | 외부 조회/idempotency capability에 따라 확인, 불명 유지 | 동일. replay가 외부 사실을 만들 수 없음 |
| 상태 schema 변경 | 현재 record migration | event reader/reducer와 checkpoint 호환 또는 명시 변환 필요 |
| 원문 삭제 | 현재 tombstone과 파생 자료 사용 차단/정리 | 민감 payload는 삭제 가능한 참조로 분리. 삭제 후 재생에 없는 원문을 요구하지 않게 event 의미 설계 |
| journal/current 손상 | backup/검증과 외부 조회, 복원 불가 범위 표시 | 권위 journal 손상은 projection만으로 과거 사건을 재창조하지 않음. 검증된 복원점 사용 |

두 안 모두 요구된 정상 복구를 지원하려 한다. B의 replay도 삭제된 내용, 기록하지 않은 원인, 외부에서만 발생한 사실을 복원하지 못한다. 복원 불가를 성공으로 세지 않는다.

| V-01 정확성 | 현재 상태/관계의 원자 갱신, migration 오류 위험 | 사건과 view 일치 검사, 잘못된 event 의미/reducer는 오류를 반복 생산 |
| V-02 적절성 | 정상 이어가기와 감사 조회로 필요한 사용자 부담을 줄임 | A가 복원하지 못한 관계를 실제로 재구성할 때만 재설명 감소 가설. 일반적 우세는 미확인 |
| V-03 완전성 | 같은 정상 기능과 복구 목표 | 같은 요구, 보존하지 않은/삭제된 사실 복원은 미지원 |
| V-04 반응성 | 직접 write/read 및 감사 기록 비용 | 같은 transaction의 append+projection 비용. 정상 조회는 projection 사용; 실제 시간 차이 미측정 |
| V-05 VIA 완료 시간 | 일반 요청은 단순, migration/복구에 필요한 조회 | 정상 write 비용과 재구성 시간, Agent 시간 이익은 없음 |
| V-06 자원과 수용량 | 현재 상태/필요 원장/backup 크기 | journal/checkpoint/view 저장, replay CPU와 backlog 수용량 부담 |
| V-07 결함과 복구 | 현재 상태 복원 및 외부 재조정 | view 재구성 가능, 원본 journal 손상/reader 실패는 새 중요 장애 |
| V-08 변경과 모듈성 | 현재 schema와 migration 변경 | view 변경은 분리 가능, event 의미와 옛 reader 장기 호환 비용 |
| V-09 분석과 시험 | 감사 범위 내 원인 추적과 crash 시험 | 전이 재생 가능, 잘못된 순서/중복/삭제 이후 replay 시험 필요 |
| V-10 기밀성 | 현재/backup의 민감 자료 정리 | 사건/복제 view/checkpoint의 민감 payload 정리 경로 확대 |
| V-11 연동과 공존 | 연동: 같은 Agent 사실 계약 / 공존: 현재 IO | 연동: 외부 동일 / 공존: append와 replay IO/CPU 경합 |
| V-12 조작과 오류 방지 | 확인된 상태와 불명 상태 구별 | 동일. 재생된 상태를 새로 수행한 업무처럼 알리지 않음 |
| V-13 설치 | 현재 schema migration 및 복구 도구 | reader/reducer/checkpoint의 호환 배포와 제거 시 보존 정책 필요 |

## 8. 싼 추가와 전환의 판단

**A에 로그만 추가하면?** 변경된 row와 debug 문자열만으로 B의 의미 사건, 결정적 상태 생성과 옛 의미 호환이 생기지 않는다. 이미 완전한 사건과 replay를 갖춘 A라면 차이가 작아지는 것이 맞다. 그 경우를 일반 A의 기본값으로 숨기거나, 반대로 재사용할 이력을 무시하지 않는다.

| 비용 | A → B | B → A |
| --- | --- | --- |
| 기능 개발 | event/reducer/checkpoint와 삭제 연동 | 현재 상태 운영/검증 경로 |
| 상태 이행 | 현재 record를 시작 snapshot으로 가져올 수 있음. 과거 사건을 소급 발명하지 않음 | 검증된 최신 projection을 초기 current record로 사용 |
| 핵심 재설계 | owner의 쓰기 결과를 상태 값에서 의미 전이로 변경. 정상 읽기/복구/schema/삭제가 그 사건을 원본으로 소비 | reducer를 현재 갱신 함수로 재사용 가능. journal 의존 복구/검증을 해제하고 current record를 권위로 전환 |

역전환은 더 쉬울 수 있다. 진행 작업을 끝내도 앞으로의 쓰기/상태 생성 의미 변경은 남지만, 이력 재생 기능을 포기하는 비용을 대규모 개발로 과장하지 않는다. A와 완전한 event 원본을 병행하면 두 기록 불일치의 권위와 원자 갱신을 정해야 한다. 단순 감사 log만 필요한 제품에는 B가 과하다.

**가장 싼 혼합:** A의 현재 상태를 계속 원본으로 두고 필요한 의미 감사 기록과 조회 view를 추가한다. 경위 설명과 현재 조회 요구가 이 범위에서 충족되면 이를 우선 검토한다. 과거 사건이 정상 상태 생성과 복구의 최종 근거가 되도록 전환하면 B 계열이며, 양쪽을 독립 원본으로 유지하면 불일치 해결 책임이 추가된다. 감사 기록을 소비하는 보조 기능 하나를 넣었다는 이유만으로 B로 분류하지 않는다.

## 9. 판단

**2026-10-05 사용자 결론: 구조 차이는 인정하되 VIA의 중요한 품질에 미치는 영향이 주요 후보 승격을 뒷받침하지 않아 35에 유지한다. 40번대로 올리지 않는다.** §0의 동작 설명과 판단 근거를 현재 결론으로 읽는다. 아래 조건부 선택 이유는 상세 설계 참고이며 A/B 승자나 승격 대기 과제가 아니다.

**실제 상태 운영 구조의 비교지만, B의 선택 필요성은 조건부이며 기능 주제보다 후순위다.** 원본이 다르면 정상 writer, 상태 생성, 변경과 복구가 함께 바뀐다. A는 현재 원장/backup으로 충분한 경우, B는 확정 경위와 view 재구성이 중요한 경우에 선택 이유가 있다. 작은 감사 기록으로 필요한 복구/진단을 모두 충족하면 B의 이익은 약해진다.

[Microsoft Event Sourcing 설명](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)은 사건 원본과 상태 재구성의 원리 참고다. VIA에 특정 DB나 패턴을 선정한 근거가 아니다. 쓰기/삭제/재생 시간과 실제 복구율은 아직 측정하지 않았다.
