## 최신 산출물: 여섯 QA와 추가 세 후보

**[QA 후보 상세안과 DP 구성 판정](./qa-candidate-package/README.md)**에서 먼저 전체 결론을 읽는다. 아홉 후보의 정의와 측정안 및 예시와 DP 예상 및 최소 PoC를 정리했다. **아홉 후보 모두 목표 수치와 0~6점 표를 갖췄다.** QA06은 2026-10-15 사용자가 지정한 **512 MB** 시스템 요구사항과 RAM-v3-MB를 적용한다. 다른 목표는 검토안이고 전부 미측정이다. 독립 리뷰와 보완 기록도 패키지에 연결한다.

**2026-10-14 발표용 표 정리:** 사용자가 요청한 [품질 요구사항 표와 발표용 요약](./qa-candidate-package/quality-requirements-table.md)에 대화의 상세 Scenario를 보존하고 중요도 / 난이도 판단 근거를 보완했다. 중요도 / 난이도는 `H(10) / H(9)`처럼 표시하며 1~4=L / 5~7=M / 8~10=H다. 중요도 근거에는 사용자가 지정한 stakeholder 8개 역할의 요구를 연결했다. 같은 파일의 [축약 표](./qa-candidate-package/quality-requirements-table.md#presentation-table)는 첨부 레퍼런스처럼 Scenario를 정의 한 줄 / 목표 한 줄 / ※ 측정 조건 한 줄 / ※ 목표 근거 한 줄로 구성한다. 1~10점은 사전 중요도 / 난이도 제안이며 PoC의 0~6점과 구별한다. 중요도는 기존 QA 순서에 맞춘 평가 우선도다. QA09의 기존 H는 M(5)로 조정했으며 필수 음성 검증 지위는 유지한다. 이때의 요청은 표 문서화와 GitHub 게시였다. 이후 사용자 피드백에 따른 QA06 개정은 다음 문단을 따른다.

**2026-10-14 사용자 지적에 따른 수치 개정:** [목표 논리](./qa-candidate-package/target-rationale.md)의 현재 제안은 QA01 평균 1초 / QA02 ReALM 참조 93% / QA03 평균 5초 / QA04 ARGO 평균 5.4개 대비 40% 이상 개선한 평균 3개 / QA05 gpt-realtime과 Luna의 견적 $2.54604에 따른 $2.55이다. QA06은 부적합 기능 참조에서 정한 512MiB와 점수를 철회했다. 동종 제품에서 목표 수치를 확보하지 못했던 조사 이력은 보존한다. **후속 갱신: 2026-10-15 사용자 지정 [512 MB 시스템 요구사항](./qa-candidate-package/targets-source-qa06-platform.md)과 RAM-v3-MB 점수를 적용했다.** 계측 구현은 검증 전이며 아홉 QA 모두 미측정이다. [공통 시나리오 명세](./qa-candidate-package/common-scenarios.md)와 [개정 전 기록](../../../archive/qa-targets-before-task-aligned-revision-20261014/README.md)을 연결한다.

핵심 결과는 **명확한 QA를 정의하는 것만으로 네 DP의 trade-off 요건이 충족되지는 않는다**는 점이다. 특히 강한 B의 보완 경로를 인정한 47의 정확도, 44의 짧은 비동기 조정과 직접 stage 연결의 실용적 속도 차이, 42의 정상 사용 B 이익은 근거가 부족하다. 추가 QA로 빈칸을 인위적으로 채우지 않는다. 아래 초기 제안에서 바뀐 예상은 상세안과 최신 대응표를 따른다. 기존 03-02와 과거 결과는 보존한다.

## 기록과 근거의 관리

**이 문서가 현재 QA와 DP를 함께 검토하는 중심 문서다.** 매 논의가 끝나면 사용자 합의, 작성자 제안, 미해결 질문과 변경 이유를 갱신한다. [작업 계획](./00-workplan.md#qa-dp-selection-contract-20261014)은 진행 요약과 재개 위치를 제공하고 이 문서로 연결한다. 작업 계획의 이전 상세 논의는 당시 제안 이력으로 보존한다.

연결 단위는 **사용자 문제 → QA와 단일 지표 → 목표 수치와 도출 근거 → 0~6점 기준 → DP의 구조 차이와 예상 우열 → 동일 조건의 PoC → 원값과 검증 범위 → 점수와 trade-off 판단 → 최종 선택 이유**다. 각 결과와 발표 주장에는 사용한 정의 버전과 근거 경로를 남긴다. 정의나 사례가 바뀌면 이전 결과를 새 지표의 결과로 바꾸지 않고 재평가 필요성을 표시한다.

[03-02의 기존 QA와 P21](./03-02-quality-attribute-definitions.md), 이전 DP-41 실행과 결과는 당시 계약의 근거로 보존한다. 이 문서는 기존 측정 계약이나 결과를 덮어쓰지 않는다. 구현 / 실험은 별도 승인 후 진행한다.

## 합의한 선정 기준과 현재 상태

- 핵심 QA는 4~6개, 핵심 DP는 약 4개로 구성한다.
- 각 QA는 하나의 명확한 품질과 지표를 가지며 여러 DP에서도 같은 측정 의미를 유지한다.
- 각 DP에서 3~4개 QA의 두 방안 간 성능 차이와 trade-off를 평가한다.
- 각 QA는 최소 2개 DP에서 차이를 확인해야 한다. 1순위 QA는 1순위 DP의 주된 목표이며 4개 DP 모두, 차선으로 3개 DP에서 차이를 설명해야 한다.
- 관련성, 측정 가능성, 동점은 확인된 trade-off 커버리지로 세지 않는다. 실측 전의 연결은 차이 가설로 표시한다.
- 실제 구조 차이를 설명하는 강한 대안을 비교한다. cache, 병렬 처리와 부분 갱신을 제거해 차이를 만들지 않는다.

사용자는 **첫 응답 지연시간**이라는 이름과 요청 내용을 반영하지 않는 접수 신호를 제외하는 방향에 동의했다. 응답은 Request 또는 Task별 UI의 상세 텍스트와 사용자가 들을 수 있을 때 제공하는 음성 요약으로 구성한다고 명시했다. 실제 음성 재생은 사용자 발화나 이전 응답 때문에 대기할 수 있으므로 핵심 지표의 종료점으로 부적절하다고 지적했다. 아래의 텍스트 표시 종료점은 이 방향을 반영한 작성자 제안이다.

지칭 대상 집합 일치율의 47/45 공통 적용과 실제 Rust 모듈 수의 집계 규칙을 상세안에 정의했다. 전체 순서와 평가 조건은 작성자 초안이며 **이번 사용자 검토를 반영한 목표와 점수의 제안이며 실제 제품 승인과 PoC는 별도**이다. 우선순위 1번은 기존 ASR-QA-01 번호와 구별한다.

## QA와 DP의 우선순위 제안

명칭은 관찰할 대상을 짧게 드러내고 정의와 측정 경계에서 범위를 고정한다. 모든 경계를 짧은 이름 하나에 담지는 않는다. 아래 명칭은 검토안이며 기존 ASR ID를 재번호하지 않는다.

| 제안 순위 | QA 이름 | 대표 지표 | 우선순위 근거 |
| --- | --- | --- | --- |
| 1 | 첫 응답 지연시간 | 평균 첫 응답 지연시간 | 대화를 주고받는 경험과 입력 / 업무 사건에 대한 체감 대기를 좌우한다. |
| 2 | 지칭 대상 식별 정확도 | 지칭 대상 집합 일치율 | 말과 화면 또는 과거 맥락으로 지정한 대상을 다시 설명할 필요를 줄인다. |

DP 순서 제안은 **44 → 47 → 45 → 42**다. 44는 사용자 입력과 업무 사건의 대화 실행을 직접 다룬다. 47은 화면을 말로 지정하는 기능의 반응과 정확성을 좌우한다. 45는 과거 이력 재사용의 반응 / 정확성 / 비용에 영향을 준다. 42는 대화와 업무의 독립적인 수명을 연결하는 기반이며 분리안의 정상 사용 이익을 더 검증해야 한다. 이는 대안의 승패나 구현 순서가 아니다.

필수 기능과 합의한 최소 품질 / 장치 조건을 충족하는 대안 사이에서 우선순위를 적용한다. 빠른 오답이나 저비용 미처리를 이익으로 세지 않는다. 미세한 상위 차이로 큰 하위 손실을 자동 정당화하지 않는다.

## 첫 응답 지연시간 검토안

### 이름과 평가 대상

QA 이름은 사용자 동의를 받은 **첫 응답 지연시간**이며 대표 지표 제안은 **평균 첫 응답 지연시간**이다.

**정의 제안:** 사용자 입력 또는 Agent 사건 이후 해당 요청이나 업무에 대한 첫 내용 응답이 Request 또는 Task별 UI에 표시될 때까지 걸리는 시간.

사용자가 동의한 대로 `네`, 알림음, 단독 `처리 중입니다`와 같은 접수 신호는 제외한다. 응답은 요청 또는 업무의 구체적 내용을 전달해야 한다. 실제 출력 문장이 길거나 상세 결과가 streaming으로 추가되더라도 첫 완결된 내용 단위가 표시된 시점으로 평가한다. 빈 카드, 제목만 있는 자리표시자 또는 의미를 확정할 수 없는 첫 토큰은 응답이 아니다.

**사용자가 정한 출력 방식:** 텍스트는 Request 또는 Task별 UI에 상세 내용과 처리 상태를 남겨 사용자가 확인할 수 있게 한다. 음성은 그 응답을 요약해 사용자가 들을 수 있을 때 전달한다. 텍스트 표시와 음성 재생은 같은 응답 / 버전 / 업무를 참조하되 재생 대기를 이유로 텍스트를 막지 않는다. 실제 사용자 청취를 이 지표만으로 입증하지 않으며 음성 요약 생성과 실제 전달은 별도로 검증한다.

### 관측 경계

| 사건 | 시작점 | 응답으로 인정하는 내용 |
| --- | --- | --- |
| 사용자 음성 요청 / 정정 | 실제 발화 종료 | 요청에 대한 답변, 식별한 대상 / 범위와 채택한 수행 내용, 사실에 맞는 상태, 또는 필요한 정보를 특정한 확인 질문 |
| 사용자 텍스트 요청 / 정정 | 사용자가 입력을 제출한 시점 | 위와 동일 |
| Agent 질문 / 상태 / 결과 | Agent source interface에서 사건이 소비 가능해진 최초 시점 | 해당 업무와 연결된 질문, 확인된 상태 또는 결과 |

음성 입력은 실제 발화 종료 이후 VAD 판정과 전사 확정 시간을 포함한다. Agent 사건은 VIA 수신 이전의 발견 / 전달 지연을 숨기지 않는다. 다른 사용자 발화와 사건이 겹쳐도 텍스트 응답 경로를 진행한다. 요청 자체의 해석이 아직 미확정이면 근거 없는 실행 내용을 미리 표시하지 않는다.

**종료점 제안:** 해당 Request 또는 Task의 UI에 첫 내용 단위가 실제 표시된 시점이다. 음성 재생 여부와 무관하게 동일한 경계를 쓴다. 상세 응답 전체나 TTS 생성 완료까지 기다리지 않는다. 메모리에 문자열이 준비되거나 UI queue에 넣은 시각은 실제 표시와 구별하며 UI 처리 / 렌더 대기는 이 지표에 포함한다. 사용자가 실제 읽은 순간을 측정하는 것은 아니다. 화면을 보지 않는 상황의 음성 체감 대기를 텍스트 지연으로 대체해 설명하지 않는다.

사례별 응답 판정표에는 요청 정보, 올바른 대상 / 범위, 안내할 수 있는 실제 처리 단계와 모호할 때 필요한 질문을 적는다. 정확한 문장을 강제하지 않고 의미가 같은 표현을 허용한다. 진행 안내, 결과와 확인 질문의 의미가 판별되는 첫 단위를 기준으로 한다. 접수 / 수행 결정 / 전송 / 외부 접수 / 업무 완료는 서로 다른 단계다.

**위임 전 응답:** `선택한 매출표와 비용 그래프를 비교하겠습니다`는 대상 / 범위와 수행 내용이 실제로 채택됐다면 Agent 전송 전에도 첫 응답이 될 수 있다. 단순히 식별되지 않은 `이것`을 반복하거나 미채택 모델 제안을 확정 계획으로 표시하는 것은 제외한다. VIA의 역할은 사용자 요청의 이해 / 처리 연결이며 Downstream Agent의 도메인 계획 / 실행을 미리 완료한 것으로 표현하지 않는다. `완료했습니다`는 해당 동작의 완료가 확인된 때만 사용한다.

**설명용 가상 타임라인:** 입력 종료 0초 → `네` 표시 0.1초 → 구체적인 비교 수행 안내 표시 0.8초 → Agent 전송 1.3초 → 음성 요약 재생 2.5초라면 첫 응답 지연은 0.8초다. 이는 실제 측정값이나 목표값이 아니다. 첫 응답을 Agent 위임 완료와 묶지 않는다. 불필요한 확인 질문도 구체적 내용이면 시간에 포함하고 기능 오류를 별도 기록한다.

측정 단위는 사전 지정한 입력 사건이다. 2026-10-15 사용자 지시에 따라 QA01은 600개 실제 응답시간, QA03은 380개 실제 VIA 처리시간의 산술평균이다. 오답도 그대로 포함하며 정답이 나올 때까지 기다리거나 실패 벌점을 넣지 않는다. 미관측은 별도 표기한다. 목표와 수치 배점 경계는 유지한다.

음성은 요약 준비, 재생 가능 조건의 충족, 재생 시작과 실제 전달을 별도 기록한다. 사용자 발화나 이전 응답 때문에 기다린 구간과 준비 이후 불필요한 실행 지연을 구별한다. 오래된 안내를 나중에 그대로 읽지 않도록 사용 직전에 요청 / 업무 / 응답 버전을 확인한다. 음성 누락이나 무한 대기를 허용해 텍스트 지표만 좋게 만들지 않는다. 끼어들기 중단도 별도 검증한다. 이 제안은 기존 [사건 경계 계약](../../11-measurement/event-boundary-contract.md)의 실제 관측 원칙을 사용하지만 이전 음성 종료점과 QA 집계를 그대로 계승하지 않는다.

| --- | --- | --- |
| 44 | 중앙 완료 회수 / 후속 지시 대 단계별 활성화 / 결합 / 대기 | 강한 A의 짧은 dispatcher와 비동기 처리가 B와 동등하거나 추가 결합 비용보다 작음 |

같은 첫 응답의 사용자 목표와 판정 경계를 유지한 채 구조가 그 지연에 영향을 주는지 확인한다. DP별로 임의의 내부 완료시각을 종료점으로 선택하지 않는다.

## 목표 수치와 도출 근거

**모든 QA에는 목표 수치와 명확한 근거를 함께 둔다.** 지표, 단위, 적용 모집단, 목표값, 출처 또는 사업 / 장치 요구, VIA에 적용하는 계산 / 추론, 한계, 0~6점 경계를 한 묶음으로 관리한다. 문헌의 수치를 복사하거나 이전 P21 목표를 새 지표에 그대로 적용하지 않는다.

| QA | 확보한 근거와 도출 방식 |
| --- | --- |
| 첫 응답 지연시간 | Nielsen(1993)과 Microsoft Windows의 약 1초 UI 지침을 첫 완결 내용 표시 평균 목표에 적용 |
| 지칭 대상 식별 정확도 | ReALM-3B 화면 지칭 집합 완전 일치율 93.0%를 관련 기술의 공통 최소 목표로 채택 |
| VIA 처리시간 | Windows Long wait 상단 5초를 VIA 자체 완료 경로의 평균 시간으로 적용 |
| 변경 범위 | 사용자 제공 ARGO PR 145건 평균 5.4개에서 40% 감소한 3.24개보다 엄격한 평균 3개 채택 |
| 모델 사용 비용 | 공통 28개 묶음의 gpt-realtime 및 Luna 참조 견적 $2.54604를 센트 단위로 올려 $2.55 제안 |
| 최대 RAM 사용량 | 사용자 지정 PC 플랫폼 및 기술기획 측 시스템 요구사항 **512 MB**. 이전 512MiB 참조는 철회 이력으로 유지 |

연구로 도출할 수 있는 수치와 팀 / 제품이 정해야 하는 요구 예산을 구분한다. 평균, 개별 사건 상한과 성공률은 서로 다른 통계이므로 출처가 개별 지연을 설명한다면 평균 목표의 직접 검증 근거라고 주장하지 않는다.

### 첫 응답 목표의 근거 조사

| 출처 | 확인한 내용 | VIA 적용과 한계 |
| --- | --- | --- |
| [Nielsen 1993 Response Times](https://www.nngroup.com/articles/response-times-3-important-limits/) | 약 0.1초는 즉각적인 UI 반응 감각, 약 1초는 사고 흐름을 유지하는 지침으로 설명 | 텍스트 첫 내용 표시의 1초 목표 후보를 뒷받침하는 HCI 지침. VIA 음성 대화 실험이나 실제 모든 요청의 성공 보장은 아님 |
| [Miller 1968](https://doi.org/10.1145/1476589.1476628) | 응답 대상과 사용자 목적에 따라 적절한 응답시간을 구별해야 한다는 문제 제기 | 무엇이 첫 응답인지와 관측 경계를 먼저 정할 근거. 초록만으로 VIA의 특정 초 단위를 도출하지 않음 |
| [Stivers 외 2009](https://pubmed.ncbi.nlm.nih.gov/19553212/) | 10개 언어의 자연 대화에서 발화 겹침과 턴 사이 침묵을 줄이는 경향을 관찰 | 음성 대기와 턴 조절의 중요성을 설명하는 근거. 인간 간 발화 간격을 텍스트 UI 표시의 합격선에 직접 대입하지 않음 |

현재 상세안은 **대표 시험의 평균 첫 내용 표시 1초 이하**다. 공통 120사건 × 5회의 600개 값을 모두 포함한다. 오답도 실제 시간을 사용한다. 외부 UI 지침은 숫자의 참조이며 평균 집계는 사용자 정정이다. 개별 요청 1초 보장이 아니다. 0.2초 우수선과 0.16초 간격은 유지한다.

## 원형 점수 체계

사용자가 지칭한 기존 체계는 [발표 점수 설명](../../../presentations_files/dp-comparison/v4/README.md)과 [QA 목표 근거 및 7단계 등급](../../../presentations_files/quality-metrics.md)에서 확인했다. 세 원으로 표시하며 빈 원은 0점, 반원은 1점, 채운 원은 2점이다.

| 점수 | 표시 |
| --- | --- |
| 0 | ○○○ |
| 1 | ◐○○ |
| 2 | ●○○ |
| 3 | ●◐○ |
| 4 | ●●○ |
| 5 | ●●◐ |
| 6 | ●●● |

QA별 원값을 하나의 단조로운 0~6점 함수로 변환한다. 같은 QA의 같은 정의 / 모집단에는 DP와 대안에 관계없이 같은 구간을 적용한다. 시간 / 비용 / 메모리 / 변경 수는 낮을수록, 지칭 정확도는 높을수록 점수가 높다. 반올림 전 원값으로 채점하고 값 / 단위 / 목표 / 범위 / 실패를 점수와 함께 표시한다. 미측정은 0점 대신 미측정으로 표시하며 QA 점수를 가중 합산하지 않는다.

기존에는 0점이 대표 목표 미달이고 1~6점은 목표 충족과 개선 여유를 나타냈다. 이 표시 의미는 재사용 출발점이며 새 QA별 목표와 최상위 구간 및 중간 경계는 근거를 확인해 정한다. 모든 중간 경계가 HCI 실험으로 도출된 값인 것처럼 설명하지 않는다. 목표/우수 수준의 근거와 그 사이를 등급화한 설계 규칙을 구분한다.

**점수 구간 보정:** 예비 PoC에서 범위 / 측정 해상도와 실제 차이를 확인한 뒤 본 비교 전에 구간을 보정할 수 있다. 본 비교 결과 뒤 보정이 필요하면 원값과 이전 구간을 보존하고 변경 이유 / 시점 / 새 구간을 기록해 양안에 동일하게 재채점한다. 원값의 우열은 단조 점수로 뒤집지 않는다. 선호안만 유리하게 하거나 DP마다 다른 구간으로 바꾸지 않으며 새 점수만 제시해 결과를 미리 정한 것처럼 보이게 하지 않는다. 정의 / 모집단이 바뀌면 재채점만으로 호환된 결과를 만들지 않는다.

## 구조적 예상과 PoC 검증

PoC는 비교하려는 구조와 차이 가설을 검증할 최소 구현이다. 제품의 모든 기능 / 앱 / 장애 조건을 완성하는 단계가 아니다. 각 PoC에 구현한 경로, 공통으로 고정한 주변 기능, 모사한 외부 조건과 주장할 수 있는 범위를 적는다. 차이를 만드는 실행 의존 / 상태 / 모델 호출을 고정 가산값으로 대신하지 않는다. UI 표시를 계측하지 않고 게시 준비까지만 모사했다면 실제 사용자 UI 지연으로 보고하지 않는다.

**PoC 전:** VIA의 주요 사례와 평가 비중을 먼저 정하고 그 범위 전체에 대해 A 우세 또는 B 우세라는 예상 결론을 제시한다. 발표에는 **우세안 + 실제 구조 차이 + 해당 QA에 미치는 효과**를 한 문장으로 적는다. 장면별 조건을 계속 나열하며 결론을 유보하는 형식은 사용하지 않는다. 실제 측정 전이라는 상태는 유지하며 구조 이름이나 모듈 수만으로 우위를 주장하지 않는다.

부수적인 상황과 반증 조건은 상세 검토에 보존한다. 대표 범위 밖 상황을 질문받으면 검증 범위를 정확히 설명하고 실제 미검토 사항은 인정한다. 이미 검토한 불리한 결과를 미검토라고 말하지 않는다. 대표 범위에서도 의미 있는 차이를 예상할 근거가 없으면 동점으로 판단해 핵심 trade-off 축에서 제외하거나 비교 구도를 재검토한다. 결론을 분명히 하는 것과 차이를 만들어 내는 것은 구별한다.

**한 문장 작성 예시:** `반복 이력 조회에서는 B가 필요한 관계를 미리 만들어 두므로 요청 때마다 관계를 구성하는 시간을 줄인다.` 이는 해당 대표 범위를 선정했을 때 사용할 구조 설명의 형식 예시이며 DP-45 전체의 실측 결론은 아니다. 선정한 대표 범위는 발표 공통 전제로 한 번 밝히고 QA별 한 문장에 예외를 길게 붙이지 않는다. 저비용 cache 등 실제 강한 대안과 비교해 이 구조 차이가 남는지는 PoC 전에 확인한다.

**PoC 후:** 같은 조건에서 예상이 맞는지 확인하고 원값을 확정된 점수 구간으로 채점한다. 예상과 다르면 우선 측정 경계 / 구현 대등성 / 시나리오 / 병목을 확인한다. 확인 후에도 반대 결과가 남으면 그 조건과 원인을 보존한다. 직관적인 손익이 뚜렷한 DP를 선정하는 것과 결과를 직관에 맞게 조정하는 것은 구분한다.

### 첫 응답 지연의 장면별 탐색 이력

아래는 대표 범위를 정하기 전의 탐색 기록이다. 최종 발표용 결론표는 주요 사례와 비중을 정한 뒤 DP별 예상 우열 하나와 한 문장 이유로 별도 정리한다.

| DP와 장면 | 우선 예상 | 구조적 이유와 확인할 조건 |
| --- | --- | --- |
| 44 단순 입력과 적은 동시 사건 | A 유리 가능 | 중앙의 짧은 비동기 조정에 비해 B의 단계 연결 / 결합 관리가 추가될 수 있음 |
| 44 여러 후속 실행과 입력의 교차 | B 개선 가능성은 있으나 약한 가설 | 직접 활성화가 중앙 재배정을 줄일 수 있지만 A도 비동기이며 B의 결합 / 버퍼 대기가 남음. 음성 차례 대기를 첫 텍스트 지연 이익으로 넣지 않음 |
| 47 원본 근거를 처음 해석하는 단순 요청 | A 유리 가능 | 원본 공동 해석에 비해 B는 후보 생산 뒤 결합이 필요할 수 있음. 모델 입력 크기 / 생산 병행 / 호출 전략에 따라 역전 가능 |
| 47 일부 후보를 재사용하는 정정 | 고정 우열 없음 | B의 재사용 이익과 생산자 왕복을 비교하며 A의 국소 patch와 cache도 허용 |
| 45 유효한 공통 관계를 반복 조회 | B 유리 가능 | 요청 중 원본 결합 / 관계 생산을 생략하는 범위에서 빠름. A의 동등한 warm cache로 차이가 사라질 수 있음 |
| 45 새로운 관계나 갱신 직후 조회 | A 유리 가능 | B의 게시 / 갱신 대기가 추가되는 조건. A의 검색 / 결합 비용이 크면 역전 가능 |
| 42 위임 전에 수행 내용을 안내 | 우열 미확정 | 양안 모두 업무 접수 왕복 전에 대화 쪽에서 안내할 수 있음. 전체 왕복 차이는 주로 VIA 처리시간에서 평가 |

이 표는 예측이며 측정값이나 점수가 아니다. 새 응답 경계에서 모든 DP의 첫 응답 차이가 뚜렷하다고 주장하지 않는다.

## QA별 한 장 설명과 이해 예시

각 QA는 아래 내용을 발표 한 장에 담을 수 있는 설명 명세로 완성한다. 먼저 정의와 수치를 합의하고 실제 PPTX 제작 때 이 명세를 사용한다.

| 항목 | 반드시 설명할 내용 |
| --- | --- |
| 이름과 정의 | 무엇을 평가하는지 한 문장 |
| 지표와 선택 이유 | 단일 지표와 단위, 이 지표가 품질을 나타내는 이유 |
| 측정 방법 | 시작 / 종료점 또는 평가 단위와 산식, 포함 / 제외 범위 |
| 목표와 근거 | 목표 수치, 출처 또는 요구 예산, VIA에 적용한 도출 과정 |
| 점수 | 0~6점 경계와 원형 표시, 목표 충족 구간 |
| 이해 예시 | 하나의 장면과 입력 / 처리 / 측정값을 짧게 보여주는 타임라인이나 계산 |
| 연결 DP | 해당 QA를 비교할 DP와 차이의 구조적 원인 |

**아래 값은 모두 설명용 가상값이며 목표 / 예상 성능 / 측정 결과가 아니다.** 실제 발표에서도 예시임을 표시한다. 점수 구간을 정한 뒤 각 예시의 점수까지 연결한다.

| QA | 발표용 이해 예시 초안 |
| --- | --- |
| 첫 응답 지연시간 | 입력 종료 0.0초 → 접수 인사 0.1초 → 구체적인 수행 안내 표시 0.8초 → Agent 전송 1.3초 → 음성 요약 2.5초. 측정값은 0.8초다. |
| 지칭 대상 식별 정확도 | 사용자가 지정한 집합이 `{표 A, 그래프 B}`인데 결과가 `{표 A, 그래프 C}`면 그 평가 건은 불일치다. 대상 하나가 맞았다고 해당 건을 절반 정답으로 세지 않는다. |
| VIA 처리시간 | 다른 대기 / 겹침이 없는 직렬 예시에서 VIA 처리 1.2초 → 외부 Agent 실행 8초 → VIA 결과 전달 처리 0.6초라면 VIA 귀속은 1.8초다. |
| 변경 범위 | 하나의 기능 변경에 실제 Rust 모듈 3개를 수정했다면 3개로 센다. 한 모듈 안에서 함수를 여러 개 바꾸어도 그 모듈은 한 번 센다. |
| 모델 사용 비용 | 같은 활동 묶음에 요청 처리 $0.03 + 사전 생산 $0.02 + 폐기 / 재시도 $0.01이면 총 $0.06이다. 사용된 최종 응답의 호출만 세지 않는다. |
| 최대 RAM 사용량 | 공유 영역이 없다는 단순 예시에서 같은 순간의 VIA 프로세스 RAM이 200MiB와 180MiB면 전체는 380MiB다. 각 시점의 전체 합 중 최고량을 찾는다. |

첫 응답 예시는 위임 전의 구체적인 수행 안내가 첫 응답이며 음성 재생 대기는 분리된다는 설명과 함께 보존한다.

## AI 코딩 협업과 변경 범위

### 사용자 경험과 평가 목적

사용자는 여러 개발자가 각자 AI 코딩을 활용하면서 변경 충돌과 통합 / 수정 작업이 반복되고, 변경 범위가 넓을수록 담당 개발자가 다른 영역을 수정해도 되는지 판단하기 어려웠다고 설명했다. 이는 이 팀의 요구 근거로 기록한다. 모든 조직이 수동 구현을 하지 않는다거나 AI 코딩이 항상 충돌을 늘린다는 일반 사실로 확대하지 않는다.

**설계안의 변경 파급을 비교하는 목적에는 평균 변경 모듈 수가 개발 인력 / 시간보다 적합하다는 판단이다.** 인력 / 시간은 도구, 개발자 숙련, 프롬프트, 병행 작업과 검증 과정의 영향을 함께 받는다. 변경 모듈 수는 같은 기능 변경이 구현 구조의 얼마나 넓은 영역을 건드리는지 관찰한다. 여러 담당 영역으로 수정이 퍼질수록 협의 / 검토 / 통합 범위가 커질 수 있다는 점이 선택 이유다.

단, 변경 모듈 수는 충돌 횟수나 유지관리 비용 자체가 아니다. 여러 독립 모듈의 수정은 충돌하지 않을 수 있고 공유 모듈 하나에 변경이 집중되면 충돌이 클 수 있다. 모듈 안 변경 규모와 API 파급도 다르다. 실제 일정 / 자원 계획에서는 시간 자료가 여전히 필요하다.

심사 설명은 **AI 코딩을 활용하는 병행 개발 환경에서 같은 기능 변경의 수정 파급과 협업 범위 확대를 줄이기 위해 실제 변경 모듈 수를 평가한다**로 제한한다. 충돌 감소를 직접 입증했다고 표현하지 않는다. PoC에서 검증하려면 담당 영역과 동시 수정 모듈의 겹침, 실제 충돌 / 통합 사례를 보조 증거로 남기며 다른 점수와 합성하지 않는다.

### 모듈 집계 기준

[Rust 공식 모듈 설명](https://doc.rust-lang.org/book/ch07-02-defining-modules-to-control-scope-and-privacy.html)에 따른 crate root와 `mod`의 운영 모듈 경로를 식별 단위로 한다. crate 식별자와 모듈 경로, 소스와 소유 prompt/schema/config, API, 의존을 평가 전에 정한다. Rust 모듈은 파일 / crate / process와 각각 다르다.

같은 변경 과제에 수정 / 추가 / 삭제한 고유 운영 모듈을 각각 한 번 세고 과제별 수의 평균을 사용한다. 자식 수정만으로 부모를 자동 가산하지 않으며 부모 자신의 API나 연결 코드가 바뀌면 센다. 테스트 전용 변경, 주석 / 포맷과 생성 결과 재출력은 제외한다. 수작업 생성 원본과 실제 구현 자산은 소유 모듈로 추적한다. 단순 이동 / 개명은 동일 모듈의 이력으로 연결한다.

양안의 모듈 구성을 같게 만들거나 추상 책임 수로 다시 합치지 않는다. 분해 수준을 사전 검토하고 전체 규모와 실제 diff를 함께 제시해 거대 모듈 집중이나 한쪽만 미세 분할하는 왜곡을 막는다. 실제 모듈 수가 같으면 동점이다. 현재 활성 경로에서 Rust 구현은 확인되지 않았으므로 구현 전에는 설계 기반 변경 영향 분석이며 코드 변경 / 검증을 수행한 뒤 실측으로 보고한다.
