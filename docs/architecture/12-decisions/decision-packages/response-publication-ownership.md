# 직접 답변과 업무 알림의 전달을 한곳에서 관리할 것인가

> 상태: **우선 검토 후보 / 사용자 선정 전** · [목록](./README.md)

**질문:** 서로 다른 경로에서 만들어진 답변의 Text·Voice·알림 전달을 공통 Component가 관리할 것인가, 응답 종류별 Component로 나눌 것인가?

> **발표 구성:** 배경 1장 → 설계 비교 1장. 아래 배경 문구와 도식 구성은 슬라이드 제작용 원고이며 새 배경 그림이나 발표 파일을 생성한 것은 아니다. 사례는 고정 UC를 설명하기 위한 예시이고, 발생 빈도·수치·대안의 우위를 측정한 결과가 아니다.

## 1. 배경 페이지 — 왜 중요한 Architecture 문제인가

### 문제가 드러나는 사용자 상황

VIA가 화면의 표를 설명하는 중에 보고서 완료와 다른 업무의 승인 질문이 도착한다. 사용자가 끼어들면 음성은 즉시 멈춰야 하고, 결과와 질문은 화면에 남아야 한다. 이후 “방금 말한 것”이 생성만 된 문장을 가리키는 것으로 처리되어서도 안 된다.

문제는 어떤 알림을 먼저 읽을지의 순서만이 아니다. **응답 구성·게시·실제 전달 상태를 누가 소유하고, 여러 응답 경로가 어떻게 하나의 출력 장치를 공유하는가**가 핵심이다.

### 이 과제에서 왜 중요한가

VIA는 직접 답변과 여러 Agent의 진행·질문·결과를 사용자가 접하는 하나의 대화로 연결해야 한다. 외부 Agent가 업무를 정확히 끝내더라도 결과를 엉뚱한 대화에 알리거나, 승인 질문을 놓치거나, 사용자가 말하는 중에 음성으로 끼어들면 VIA의 핵심 역할은 실패한다. 따라서 응답 전달은 업무 처리 뒤에 붙는 화면 기능이 아니라 **업무 상태를 사용자의 다음 행동으로 연결하는 책임**이다.

전달 기록은 다음 입력의 근거이기도 하다. “방금 말한 두 번째로 해줘”를 해석하려면 생성된 답변 전체와 실제 표시된 내용, 실제로 들려준 범위를 구분해야 한다. 전달 책임을 잘못 나누면 출력의 문제를 넘어 후속 지칭·승인·업무 연결까지 잘못될 수 있다. 이는 문서에 정의된 위험 경로이며, 실제 발생률을 측정한 주장은 아니다.

### Architecture적으로 어려운 이유

| 동시에 만족해야 할 요구 | 구조적으로 부딪히는 지점 | 단순 처리로 남는 문제 |
| --- | --- | --- |
| 직접 답변과 업무별 알림은 독립적으로 만들어진다 / 사용자는 한 번에 하나의 Voice만 듣는다 | 여러 생산 경로와 하나의 출력 장치를 연결하는 조정 권한 | 각 경로가 별도 queue만 가지면 서로의 발화·중단 상태를 알 수 없음 |
| Text 상세는 즉시 남긴다 / Voice는 차례를 기다리고 요약될 수 있다 | 하나의 응답 identity 아래 채널별로 다른 진행 상태 | 단일 `전달 완료` 값으로 표시와 청취를 함께 표현할 수 없음 |
| 사용자가 끼어들면 즉시 멈춘다 / 질문·완료·실패는 이후에도 보존한다 | 장치의 즉시 stop과 내구 publication 원장의 수명이 다름 | 중단을 응답 삭제로 취급하거나, 옛 packet이 재생을 다시 시작할 수 있음 |
| 재시작 후 이어간다 / 이미 들려준 음성은 확실하지 않으면 반복하지 않는다 | 물리적 재생과 receipt 저장은 한 DB transaction으로 묶이지 않음 | 기록만 보고 전부 재생하면 중복, 전부 완료로 보면 미전달을 숨김 |

이 선택은 알림 우선순위를 정하는 것보다 앞선 문제다. 우선순위가 같아도 **누가 publication·채널 상태·복구 원장을 소유하고, 어떤 계약으로 출력 차례를 조정하는가**에 따라 변경 범위와 정합성 책임이 달라진다. 공통 owner는 이 의미를 한곳에 모으지만 모든 응답 기능의 변경을 함께 받아야 한다. 종류별 owner는 독립성을 얻는 대신 공통 출력 조정과 전달 이력 결합이 필요하다.

### 배경 슬라이드 1장에 사용할 내용

**제목:** 여러 응답 경로를 하나의 대화와 실제 전달 이력으로 연결해야 한다.

| 배치 | 슬라이드에 남길 핵심 문구 | 함께 보여줄 도식 |
| --- | --- | --- |
| 왼쪽 — 과제 환경 | 직접 답변·완료·승인 질문이 비동기로 도착한다 | 직접 답변 / 업무 A 완료 / 업무 B 승인 질문의 세 입력을 공통 사용자 창구로 연결 |
| 가운데 — 사용자 경험 | 화면에는 상세, 음성에는 핵심. 사용자 발화가 시작되면 즉시 중단한다 | 같은 응답의 Text 표시와 Voice 대기·부분 재생을 두 lane으로 표시하고 끼어들기 사건을 겹침 |
| 오른쪽 — 어려움의 원인 | 생성됨 ≠ 표시됨 ≠ 들려줌. 후속 지칭은 실제 전달 범위를 사용한다 | 음성 앞부분만 전달된 지점 뒤에 “방금 말한 것”을 배치; 전달 불명 구간은 별도 표시 |

**하단 Challenge:** 독립적으로 생성되는 응답을 단일 발화·즉시 중단·내구 기록과 연결하려면, 응답 게시와 출력 조정의 책임을 어디에 두어야 하는가?

**발표자 설명:** “이 과제에서 응답은 답변 문자열 하나가 아닙니다. 화면에 남긴 상세와 음성으로 들려준 요약의 상태가 다르고, 사용자는 그 일부를 듣고 바로 다음 지시를 합니다. 그래서 단순한 알림 queue만으로는 충분하지 않습니다. 게시·청취 기록을 공통으로 소유할지, 응답 종류별로 소유하면서 장치 조정을 공유할지가 다음 페이지의 선택입니다.”

**배경 근거:** [UC-07 후속 업무](../../05-representative-use-cases.md#uc-07), [UC-11 중단·정정](../../05-representative-use-cases.md#uc-11), [UC-13 비동기 알림](../../05-representative-use-cases.md#uc-13), [전체 구조 §13](../target-architecture/architecture.md#13-응답-전달), [제어 계약 §6~7](../target-architecture/control-and-lifecycle.md#6-출력과-대화-차례).

## 2. 설계 비교 페이지 — 응답 종류별 분리와 공통 출력 조정의 책임 배치

**배경에서 이어받는 질문:** 문서 첫머리의 구조적 질문을 같은 사용자 목표·조건에서 비교한다. 먼저 책임 경계, 다음 상태와 계약, 마지막 이점·비용의 순서로 설명한다.

### 두 방안

**방안 1 — 공통 Response Manager.** Request Controller가 admission한 직접 답변·질문·업무 결과를 Response Manager가 공통 publication·채널별 전달 상태로 관리한다. Interaction Manager는 표시·재생·local stop과 receipt를 제공한다.

**방안 2 — 응답 종류별 Component.** 대안 전용 Direct Response Delivery는 직접 답변·VIA clarification을, Task Notification Delivery는 Agent 진행·결과·질문을 구성·게시한다. 각각 publication 원장을 소유한다. Interaction Manager의 공통 출력 계약을 확장해 하나의 Voice lease·output epoch와 응답 간 arbitration을 관리한다. Request Controller의 게시 admission은 두 경로 모두 유지한다.

[draw.io 편집 원본](./diagrams/response-publication-ownership.drawio) · [표기 규칙](./diagrams/README.md)

### 그림에서 확인할 흐름과 구조 차이

① 허용된 응답이 종류별 구성·게시 검사를 거쳐 ② 발화 후보와 release/cancel로 이어지고, 실제 I/O의 receipt가 원장에 돌아온다. 방안 1은 Response Manager 안에서 공통 대기열과 전달 기록을 조정한다. 방안 2는 두 publication owner의 후보를 Interaction Manager의 확대된 arbiter가 조정한다. 파란 원장은 이 소유권 분리를 보여준다. 장치 입출력은 검정 공통 부분이며, 실제 receipt를 만든다는 이유로 publication 원장의 owner가 되지는 않는다.

| 구조 차이 | 방안 1 | 방안 2 |
| --- | --- | --- |
| Component | 하나의 Response Manager | 두 대안 전용 전달 Component로 분리 |
| publication 원장 | 공통 owner | 응답 종류별 owner; 공통 ID·version·receipt 계약 |
| 출력 차례 조정 | Response Manager의 대기열 + Interaction Manager의 현장 검사 | Interaction Manager의 공통 arbiter + 종류별 내구 대기열 |
| 전달 이력 조회 | Response Manager의 read port | 두 read port를 요청/응답 identity로 결합 |

### 어느 쪽이 설득력 있는가

방안 1은 실제 게시·중단·전달 불명을 한 계약으로 관리하고 응답 간 차례를 조정하기 좋다. 대신 직접 응답과 업무 알림의 요구가 한 Component의 변경으로 모인다. 공통 관리가 모든 응답을 한 직렬 처리로 막는 구조일 필요는 없다.

방안 2는 대화형 설명과 업무 알림의 표현·전달 기능이 서로 다르게 발전할 때 유리할 수 있다. shared library로 publication ID·receipt 처리를 재사용하고 공통 arbiter로 음성 중첩을 막을 수 있다. 대신 원장과 복구 흐름이 분산되고, “이미 들려준 내용”을 확인할 조회·조정 계약이 늘어난다.

### 설계 비교 페이지 발표 설명

**그림에서 짚을 순서:** 공통 Response Manager와 두 종류별 publication owner의 파란 경계를 먼저 비교한다. 이어 각 원장에 누가 쓰는지, 두 경로가 Interaction Manager의 한 출력 arbiter로 어떻게 모이는지 설명한다.

**발표자 설명:** “배경에서 본 전달 상태의 차이를 1안은 공통 owner 안에서 조정하고, 2안은 종류별 owner와 공통 arbiter 사이의 계약으로 조정합니다. 2안도 음성을 제멋대로 재생하는 구조는 아닙니다. 종류별 기능 변경이 독립적인 이점과, 전달 이력·복구를 다시 결합하는 부담 중 무엇이 더 중요한지 검토해야 합니다.”

## 3. 자체 검토와 남은 질문

- 사용자 발화 중 알림 금지, Text 상세/Voice 요약, 좁은 S2S 직접 응답, 실제 전달 기록은 양쪽 모두 유지한다.
- local barge-in은 두 방안 모두 Interaction Manager에서 즉시 수행한다. 응답 Component의 승인 응답을 기다리지 않는다.
- 대안의 두 Component가 같은 공유 Omni를 사용한다. 모델을 각각 적재하거나 새 TTS를 추가하지 않는다.
- **후보로 남길 이유:** 공통 Component의 분리와 publication 상태 소유권 이동, Interaction Manager의 계약 확대가 그림에 드러난다. 알림 우선순위만 바꾸는 후보와 구분된다.
- 공통 arbiter·shared library를 허용한 대안에서도 원장·복구 중복이 큰지, 공통 Response Manager가 서로 다른 기능의 변경을 과도하게 묶는지가 논점이다. 결과는 아직 없다.
