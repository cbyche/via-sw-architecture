## 1. 이 문서로 무엇을 알아볼 수 있는가

VIA는 사용자의 말을 듣고 화면과 대화 맥락을 함께 이해하는 PC 소프트웨어다. 간단한 설명은 직접 답하고, 보고서 작성이나 메일 발송처럼 실제 업무가 필요한 요청은 외부 Agent에 맡긴다. 업무가 진행되는 동안에도 새 질문과 정정을 받고, 나중에 도착한 결과를 원래 대화에 연결해야 한다.

이 일을 구현하는 SW 구조는 하나만 있는 것이 아니다. 한 처리자가 전체 요청을 이해할 수도 있고, 여러 처리자가 각자의 맥락을 가지고 협력할 수도 있다. 기다리는 요청을 VIA 코드가 직접 관리할 수도 있고, 중단과 재개를 지원하는 실행 기반에 맡길 수도 있다. 이런 선택을 빠뜨리지 않고 논의하기 위해 이 문서를 사용한다.

**여기서 14개는 아키텍처 종류의 수가 아니라, 무엇을 결정할지 나눈 영역의 수다.** 각 영역에는 여러 방안이 있다. 하나의 VIA 구조는 여러 영역에서 선택한 방안들을 함께 사용한다. 예를 들어 중앙에서 처리를 조정하면서도 여러 프로세스로 실행할 수 있고, 업무별 처리자를 두면서도 공통 기억 서비스를 사용할 수 있다.

이 분류는 외부 표준의 완전한 목록이 아니다. Agent 관련 공식 문서와 VIA의 설계 질문을 바탕으로 구성한 검토 지도다. 일부 영역은 서로 겹치고, 한 영역 안에도 따로 결정할 수 있는 작은 질문이 있다. 따라서 모든 행에서 하나씩 고르면 설계가 완성된다고 해석하면 안 된다.

### 1.1 먼저 알아둘 용어

| 용어 | 이 문서에서 사용하는 뜻 |
| --- | --- |
| 구조적 결정 영역 | 설계자가 답해야 하는 질문의 범위다. 예를 들어 “여러 처리자를 누가 조정할 것인가?”가 하나의 영역이다. |
| 아키텍처 방안 | 그 질문에 답하는 구체적인 조직 방식이다. 예를 들어 중앙 조정자가 지휘하는 구조와 여러 처리자가 협의하는 구조가 있다. |
| Architectural style 또는 pattern | 반복해서 사용되는 구조에 붙인 이름이다. 이름만으로 전체 설계가 정해지지는 않는다. 실제 상태 소유자와 처리 흐름을 설명해야 한다. |
| Agent | 자신에게 주어진 범위에서 모델 등의 판단을 사용해 다음 처리나 도구 사용을 결정하는 실행 주체다. 자료를 반환하는 함수나 모델 호출 한 번을 모두 Agent라고 부르지는 않는다. |
| Sub-agent | 상위 Agent가 일부 일을 맡기는 하위 Agent다. 여러 Agent가 동료로 협력하는 구조 전체를 sub-agent 구조라고 부르지는 않는다. |
| Framework | Agent, 도구, 상태, 실행 흐름 등을 작성할 때 사용하는 개발 도구 모음이다. 같은 Framework로 서로 다른 아키텍처를 만들 수 있다. |
| Runtime | 작성한 처리 흐름을 실제로 실행하고 대기, 취소, 재개 등을 관리하는 실행 기반이다. Agent Runtime과 모델의 수치 계산을 수행하는 추론 Runtime은 서로 다른 책임이다. |
| Component | 다른 부분과 구별되는 책임과 인터페이스를 가진 SW 구성요소다. 별도 Component라는 이유만으로 별도 Agent나 프로세스가 되는 것은 아니다. |
| Actor | 자기 상태와 메시지 수신함을 가지고 사건을 처리하는 논리 실행 단위다. Actor가 반드시 AI Agent이거나 별도 OS 프로세스인 것은 아니다. |
| 상태 소유자 | 특정 정보의 의미를 해석하고 올바른 변경을 결정할 책임자다. 같은 DB에 저장하더라도 정보 종류마다 소유자가 다를 수 있다. |
| 확정 또는 commit | 임시 제안을 실제 상태나 처리 근거로 채택해 기록하는 일이다. “모델이 답을 생성했다”, “VIA가 위임을 기록했다”, “외부 Agent가 접수했다”는 각각 다른 사실이다. |
| Context | 현재 요청을 이해하는 데 제공하는 대화, 화면, 자료, 업무 상태 등의 근거다. 모델이 이전에 생성한 설명과 실제로 확인된 사실을 구별해야 한다. |
| Task와 Execution | Task는 사용자가 여러 번의 대화에 걸쳐 이어서 다루는 하나의 업무다. Execution은 그 업무를 수행하는 외부 Agent의 실제 실행이다. 같은 보고서를 다시 수정하면 같은 Task에 새 Execution이 연결될 수 있다. |
| 내구 기록 또는 내구 상태 | 프로그램이 종료되거나 다시 시작되어도 사용할 수 있도록 디스크 등에 저장한 기록이나 상태다. 처리 중인 메모리에만 보관하는 정보와 구별한다. |
| 세션 | 서로 구별하여 유지하는 입력과 처리 맥락의 묶음이다. 같은 모델을 사용해도 세션을 나누면 각 요청의 대화 이력과 계산 상태를 따로 관리할 수 있다. |
| 파생 view와 cache | 원본에서 필요한 정보를 뽑거나 정리해 둔 것이 파생 view다. 이미 얻은 값을 다시 사용하려고 보관하는 것이 cache다. 둘 다 원본과 다른 시점의 내용을 가질 수 있으므로 갱신과 폐기 조건이 필요하다. |
| 참조 아키텍처 | 기능 전반을 검토해 둔 기존 설계다. `target-architecture/`라는 경로에 있지만 최종 선택된 목표 구조라는 뜻은 아니다. |

### 1.2 일반적인 방안과 VIA의 방안을 구분하는 방법

각 상세 표는 다음 순서로 읽는다.

1. **목적과 사례**에서 사용자가 어떤 문제를 겪는지 확인한다.
2. **일반 구조**에서 실제 처리 원리가 어떻게 다른지 읽는다. 외부 자료가 설명하는 패턴과 이 문서가 구성한 분류를 구별한다.
3. **현재 참조 구조**에서 VIA가 지금 어떤 책임과 경로로 설계되어 있는지 확인한다.
4. **VIA 방안**에서 그 구조를 VIA에 적용하려면 무엇이 바뀌어야 하는지 읽는다.

VIA 방안의 표시는 다음 뜻이다.

| 표시 | 의미 |
| --- | --- |
| 검토 가능 | 현재 제품 책임 경계 안에서 설계를 구체화해 볼 수 있다. 실제 구현 가능성과 품질 이익이 검증됐다는 뜻은 아니다. |
| 조건부 검토 | 해당 책임 분리나 동작이 VIA에 필요한지부터 확인해야 한다. 필요한 이유가 약하면 작은 기능 개선으로 남을 수 있다. |
| 전제 변경 필요 | 공유 모델 구성처럼 현재 지정된 조건과 충돌한다. 일반적인 구조 목록에는 포함하지만 현 조건의 자유로운 대안으로 제시하지 않는다. |
| VIA 범위 밖 | 외부 Agent의 업무 계획과 실행 같은 책임이다. VIA 내부 구조를 논의하면서 가져오지 않는다. |

**VIA는 사용자와의 상호작용과 업무 위임을 맡고, Downstream Agent는 실제 업무의 계획과 도구 선택 및 실행을 맡는다.** VIA 내부 처리자를 나누더라도 이 경계를 바꾸지 않는다. 사용자가 명시한 “이 일이 끝나면 저 일을 해줘”라는 관계를 보존하는 것과, 보고서를 만들기 위한 조사 단계를 VIA가 스스로 계획하는 것은 다르다. 제품 경계의 원문은 [시스템 목적](../../01-system-mission-and-boundary.md)과 [고정 기능 범위](../../03-fixed-architecture-scope.md)에 있다.

## 3. 영역별 설명과 선택지

다음 사례를 여러 표에서 사용한다. 보고서 업무와 메일 업무가 진행 중이다. 사용자는 “보고서는 PDF로 하고, 메일에는 그 보고서 결론을 넣어줘”라고 말한다. 이후 “메일에는 결론 대신 표만 넣어줘”라고 정정할 수 있다. 외부 Agent의 질문이나 결과는 사용자의 다음 발화와 다른 시점에 도착할 수 있다.

여기서 VIA는 사용자의 답과 정정을 올바른 업무에 연결한다. 보고서 내용을 작성하거나 메일을 실제로 발송하는 일은 Downstream Agent가 한다. 각 영역은 이 동일한 상황에서 서로 다른 설계 질문을 다룬다.

### 3.1 모델과 코드의 제어권

예를 들어 “그 보고서 결론”이 어느 결과물을 뜻하는지 아직 모른다고 하자. 모델이 다음에 읽을 자료를 결정할 수도 있고, 코드가 미리 정한 조회 절차를 진행할 수도 있다. 이 차이는 최종 결과를 승인하는 주체와 별도로 판단해야 한다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 요청을 해결하는 동안 다음 조회, 해석, 반복, 종료를 누가 결정하는지 정한다. 모델이 처리 흐름을 바꿀 수 있는 범위와 코드가 책임지는 범위를 명확히 한다. |
| 일반 구조: 코드 주도 Workflow | 개발자가 단계와 분기를 코드로 정의한다. 모델은 특정 단계에서 의미를 해석하거나 자료를 생성한다. 다음 단계로 넘어갈 조건은 코드가 결정한다. |
| 일반 구조: 모델 주도 Agent loop | 모델이 관측한 결과를 바탕으로 다음 조회나 도구 사용을 선택한다. 실행 결과를 다시 모델에 제공하고 필요한 만큼 판단을 이어 간다. 허용 범위와 종료 조건은 별도로 강제할 수 있다. |
| 일반 구조: 혼합 구조 | 전체 흐름은 코드가 관리하고 특정 단계의 탐색을 모델에 맡긴다. 예를 들어 자료를 찾는 구간에서는 모델이 조회 순서를 정하고, 결과 채택과 사용자 전달은 코드가 결정한다. |
| 현재 VIA 참조 구조 | Request Interpreter가 요청 의미와 부족한 근거를 제안한다. Request Controller는 일반 코드로 조회 권한, 범위, 예산을 검사하고 Context Manager에 읽기를 요청한다. 읽은 결과를 바탕으로 다시 해석할지도 Request Controller가 제어한다. 최종 의미는 모델이 생산하지만 자유로운 실행 loop는 아니다. |
| VIA 방안: 현재와 같은 코드 제어 | **검토 가능.** Request Controller가 정한 흐름 안에서 모델의 의미 제안과 추가 읽기 제안을 사용한다. 제한된 흐름으로 충분한 요청이 많을 때 단순한 제어를 유지할 수 있다. 필요한 근거 탐색이 그 흐름을 자주 벗어나는지 확인해야 한다. |
| VIA 방안: 모델이 요청 이해를 주도 | **검토 가능.** 모델이 허용된 자료 조회와 재해석을 선택하고 최종 요청 의미를 만든다. 코드는 조회 범위와 현재 권한을 강제한다. 자료 관계를 유연하게 탐색할 수 있지만 모델 호출과 잘못된 탐색이 늘 수 있다. |
| VIA 방안: 모델의 틀을 코드가 완성 | **검토 가능.** 모델이 목표와 미해결 관계를 구조화된 틀로 반환한다. 코드의 해결 엔진이 필요한 근거를 조회하고 관계를 구성한다. 코드가 표현할 수 없는 관계는 질문하거나 별도 처리해야 한다. |
| 기존 논의와 연결 | [41](./04-41-request-resolution-control.md)은 모델 주도 해석과 모델의 틀을 코드가 완성하는 구조를 비교한다. 참조 구조가 코드로 제어된다는 이유만으로 41의 코드 완성 방안과 같다고 보지 않는다. 최종 의미를 실제로 만드는 주체가 다르다. |
| 근거 | 참조 설계의 [architecture.md §6~7](../target-architecture/architecture.md), [제어 계약 §3](../target-architecture/control-and-lifecycle.md). 일반 구조의 근거는 [E1](#source-e1)이다. |

### 3.2 Agent의 분해 단위

보고서와 메일에 관한 한 문장을 하나의 해석기가 함께 읽을 수 있다. 또는 보고서 담당과 메일 담당이 각자의 맥락을 보고 의미를 만들 수 있다. 처리자를 나눈 뒤 누가 조정할지는 영역 4에서 따로 다룬다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 하나의 판단 주체가 담당할 범위를 정한다. 기능, 대화 주제, 업무, 일시적인 하위 문제 중 무엇을 기준으로 판단과 Context를 나눌지 선택한다. |
| 일반 구조: 단일 Agent와 도구 또는 Skill | 하나의 판단 주체가 필요한 도구나 전문 지식을 불러 쓴다. Skill은 특정 일을 위한 지침과 자료를 뜻하며, 이를 읽는 것만으로 별도 Agent가 생기는 것은 아니다. |
| 일반 구조: 기능별 전문 Agent | 검색, 대상 해석, 관계 확인 등 전문 기능별로 판단 주체를 나눈다. 각 주체가 받는 근거와 반환할 결과를 정해야 한다. 한 기능의 결과가 다른 기능의 판단에 어떤 제약을 주는지도 필요하다. |
| 일반 구조: 업무나 대화별 지속 처리자 | 보고서 대화와 메일 대화처럼 이어지는 주제마다 자기 상태를 가진 처리자를 둔다. 새 입력이나 외부 질문이 도착하면 해당 처리자가 자기 상태를 사용한다. 이런 처리자를 Agent로 구현할 수도 있지만, 상태를 가진 일반 코드로 구현할 수도 있다. |
| 일반 구조: 일시적 sub-agent | 특정 요청에서 필요한 하위 문제를 맡기기 위해 생성하고 결과를 받은 뒤 종료한다. 오래 살아 있는 업무별 처리자와 달리 상태를 어디까지 보존할지 별도로 정한다. |
| 현재 VIA 참조 구조 | Request Interpreter가 목표, 대상, Task 연결과 처리 방향을 통합 해석한다. Context Manager는 근거를 제공하고 Task Manager는 업무 상태를 관리한다. 이들은 기능별 Component이며 업무별 자율 sub-agent 조직으로 정의되어 있지 않다. |
| VIA 방안: 통합 해석 유지 | **검토 가능.** 관련 업무의 근거만 모아 하나의 해석 주체가 관계를 판단한다. 같은 문장이 여러 업무를 연결할 때 유리할 수 있다. 필요한 맥락을 정확히 모으고 오래된 조건을 유지하는 책임이 중앙에 남는다. |
| VIA 방안: 기능별 전문 해석 | **조건부 검토.** 화면 지칭이나 업무 연결 등 실제로 독립시킬 가치가 있는 해석 책임을 나눈다. 추가 왕복과 부분 결과 불일치를 감수할 만큼 전문화가 도움이 되는지 확인해야 한다. |
| VIA 방안: 업무별 지속 대화 처리자 | **검토 가능.** 각 업무의 미해결 질문과 사용자 조건을 가진 처리자가 다음 대화 상태를 제안한다. 업무 간 참조를 연결하는 협력 계약이 추가된다. 외부 업무 자체의 계획을 이 처리자가 맡지는 않는다. |
| VIA 방안: 일시적인 해석 보조 | **조건부 검토.** 특정 모호함을 해결할 때만 보조 판단을 요청한다. 보조 주체가 실제로 별도 Context와 판단 책임을 갖는지, 같은 모델 호출을 한 번 더 하는 수준인지 구분해야 한다. |
| 기존 논의와 연결 | [33](./04-33-dialogue-coordination.md)의 B가 업무별 지속 대화 처리자와 관련된다. 문서의 Actor를 이름만 바꿔 AI sub-agent로 간주하지 않는다. |
| 근거 | 참조 설계의 [architecture.md §4~7](../target-architecture/architecture.md). 전문 Agent와 일시적 sub-agent의 참고는 [E2](#source-e2), 상태를 가진 Actor의 참고는 [E10](#source-e10)이다. |

### 3.3 사실과 목표 및 의도의 표현과 실행

“메일에는 결론 대신 표만 넣어줘”라는 정정을 받았을 때 보고서를 PDF로 만들라는 조건은 유지되어야 한다. 이전 문장을 다시 읽어 이를 복원할 수도 있고, 별도로 저장한 조건을 수정할 수도 있다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 시스템이 이해한 사실과 사용자 목표, 아직 해결하지 못한 조건을 어떤 형태로 유지할지 정한다. 새 입력이 들어왔을 때 전체 의미를 다시 만들지, 명시적으로 관리하는 상태를 변경할지도 관계된다. |
| 일반 구조: 대화 이력을 중심으로 재해석 | 관련 대화와 자료를 모델에 제공해 현재 의미를 다시 구성한다. 확정 사실의 별도 기록과 함께 사용할 수 있으며, 이력 중심이라는 말이 모든 대화를 매번 읽는다는 뜻은 아니다. |
| 일반 구조: 명시적 작업 상태 | 목표, 제약, 후보, 의존 관계 등을 구조화된 값으로 유지한다. 처리자는 이 상태를 읽고 허용된 변경을 적용한다. 표현할 수 있는 관계와 새 정보의 반영 규칙을 정의해야 한다. |
| 일반 구조: BDI | Belief는 관측하거나 전달받아 현재 믿는 사실, Desire는 달성하려는 목표, Intention은 수행하기로 선택한 목표를 뜻한다. BDI 구조는 이런 상태와 계획 실행을 연결하는 실행 절차를 가진다. Task 필드의 이름을 바꾸는 것으로 BDI가 되지는 않는다. |
| 현재 VIA 참조 구조 | Request Controller가 요청 기록, 확정 의미인 Semantic Commit, 독립 사용자 목표 사이의 Request Graph를 소유한다. 목표와 조건은 구조화해 기록하지만 의미 제안은 Request Interpreter가 만든다. 별도 BDI 계획 실행 엔진은 두지 않는다. |
| VIA 방안: 요청별 의미 생성 | **검토 가능.** 이전에 확정한 조건과 필요한 이력을 입력으로 사용해 현재 요청의 의미를 생성한다. 기존 조건의 보존 검사와 일부 수정도 허용할 수 있다. 매번 모든 것을 잊는 약한 방안으로 만들지 않는다. |
| VIA 방안: 지속 의미 작업공간 | **검토 가능.** 목표, 후보, 조건을 유지하는 작업공간이 새 해석을 변경 제안으로 받아 의미를 구성한다. 어떤 관계를 코드가 다루고 어떤 관계를 모델이 새로 판단하는지 명확히 해야 한다. |
| VIA 방안: 상호작용에 한정한 BDI | **조건부 검토.** 질문을 해결하고 결과를 전달하는 VIA 내부 목표를 유지하는 데 BDI 실행 구조가 필요한지 검토할 수 있다. 단순 요청 상태 전이보다 이익이 없다면 도입 이유가 약하다. 보고서 작성 방법 같은 업무 계획을 VIA가 소유하는 것은 범위 밖이다. |
| 기존 논의와 연결 | [31](./04-31-semantic-construction.md)은 요청별 생성과 지속 Meaning Workspace를 비교한다. Meaning Workspace는 31 대안의 이름이며 현재 참조 설계의 Component가 아니다. 31을 BDI 비교라고 부르지 않는다. |
| 근거 | 참조 설계의 [architecture.md §5, §7, §10](../target-architecture/architecture.md). BDI의 구체적인 실행 설명은 [E4](#source-e4), 대화 상태와 기억 구분은 [E5](#source-e5)를 참고한다. |

### 3.4 조직과 조정 권한

보고서 담당과 메일 담당이 모두 “그 보고서”가 자기 업무를 가리킨다고 주장할 수 있다. 이때 누가 참가자를 다시 정하고, 누락이나 충돌을 해결하며, 최종 적용을 요청할지 필요하다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 여러 처리자의 참가, 역할 배분, 상충 결과의 조정을 누가 맡는지 정한다. 영역 2에서 처리자를 여러 개 두기로 했다고 이 조직 방식까지 자동으로 정해지지는 않는다. |
| 일반 구조: 코드 기반 중앙 조정 | 중앙의 일반 코드가 참가자를 정하고 필요한 결과를 요청하며 흐름을 관리한다. 개별 판단에 모델을 사용할 수 있지만 전체 조정 권한은 코드가 가진다. |
| 일반 구조: Supervisor와 sub-agent | 상위 Agent가 어떤 하위 Agent에 무엇을 맡길지 판단하고 결과를 통합한다. 조정 자체에도 모델의 판단이 들어갈 수 있다는 점을 구분한다. |
| 일반 구조: 동료형 협력 | 처리자들이 서로 결과와 요청을 교환해 분담이나 관계를 해결한다. 반드시 투표로 결정하는 것은 아니며 충돌, 누락, 종료를 다루는 협력 규칙이 필요하다. |
| 일반 구조: 다단계 계층 또는 혼합 | 전체 조정자 아래에 영역별 조정자를 두거나, 지역 판단은 분산하되 전체 적용은 중앙에서 관리한다. 여러 계층의 책임이 중복되지 않도록 해야 한다. |
| 현재 VIA 참조 구조 | Request Controller가 코드로 요청 해석과 질문 연결 및 처리 허용을 조정한다. Task Manager는 외부 업무 상태를 소유하고 Agent Gateway가 외부 Agent와 통신한다. 중앙 조정 구조이지만 모델 기반 Supervisor가 업무를 분해하는 구조는 아니다. |
| VIA 방안: 중앙 코드 조정 | **검토 가능.** 현재 구조처럼 전체 발화와 여러 업무의 관계를 중앙에서 조정한다. 지역 상태를 조회하는 인터페이스를 잘 나누면 중앙 구조 안에서도 모듈화를 할 수 있다. |
| VIA 방안: 의미 처리 Supervisor | **조건부 검토.** VIA 내부 요청 이해에 필요한 전문 처리자를 모델 기반 조정자가 선택한다. 범위와 최종 실행 권한은 VIA 코드가 관리한다. 모델의 조정 오류와 추가 호출 비용을 드러내야 한다. |
| VIA 방안: 지역 제안과 중앙 채택 | **검토 가능.** 업무별 처리자가 자기 상태 변경을 제안하고, 중앙이 참가자와 참조 교환 및 채택을 관리한다. 중앙이 각 업무의 상태 변경을 다시 작성한다면 실제 분산 의미 생산이 사라진다. |
| VIA 방안: 일부 동료형 협력 | **조건부 검토.** 제한된 내부 해석 문제를 동료 처리자들의 협력으로 풀 수 있다. 전체 발화가 빠짐없이 처리됐는지와 결과 충돌을 누가 책임지는지는 추가 설계가 필요하다. |
| 기존 논의와 연결 | [33](./04-33-dialogue-coordination.md)의 B는 지역 제안과 중앙 채택에 가깝다. 33의 A/B를 계층형 Agent와 완전한 동료형 Agent의 비교로 대응시키지 않는다. |
| 근거 | 참조 설계의 [architecture.md §3~4, §12](../target-architecture/architecture.md). 여러 Agent의 조직과 조정 패턴은 [E2](#source-e2), [E3](#source-e3)를 참고한다. |

### 3.5 협력 매체와 진행 방식

메일 담당자가 보고서의 결론을 필요로 할 때 직접 요청할 수 있다. 보고서 결과가 도착했다는 사건을 받아 처리할 수도 있고, 공동 작업공간에 새 결과가 기록된 것을 보고 진행할 수도 있다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 처리자 사이에 어떤 자료를 전달하고 무엇이 다음 처리를 시작시키는지 정한다. 중간 결과의 보관 위치와 정정의 전달 방식도 달라진다. |
| 일반 구조: 요청과 응답 | 호출자가 특정 처리자에게 일을 요청하고 결과를 받는다. 비동기 호출도 가능하므로 요청과 응답 방식이 반드시 다른 처리를 멈추게 하는 것은 아니다. |
| 일반 구조: 데이터 흐름 또는 Pipes and Filters | 처리 단계가 앞 단계의 산출물을 입력으로 받아 다음 산출물을 만든다. 어떤 입력을 바꿨을 때 어떤 결과를 다시 만들어야 하는지 의존 관계를 표현할 수 있다. 갱신과 취소는 별도 계약이 필요하다. |
| 일반 구조: 사건 발행과 구독 | 생산자가 발생한 사건을 알리고, 그 사건에 관심을 등록한 소비자가 반응한다. 누가 사건을 만들었는지와 누가 처리하는지를 분리할 수 있지만 중복과 순서 및 처리 실패를 다뤄야 한다. |
| 일반 구조: Blackboard | 여러 전문 처리자가 공동 문제 상태를 읽고 부분 해답을 기여한다. 무엇이 새로 풀렸는지에 따라 다음 전문 처리가 진행된다. 단순한 공용 DB와 달리 공동 중간 상태가 문제 해결을 이끈다. |
| 현재 VIA 참조 구조 | 해석과 자료 조회는 명시적인 요청 및 반환 경로를 사용한다. 외부 Agent 사건은 받은 내용을 먼저 기록하는 inbox를 거치며, 내부 알림은 보내야 할 내용을 기록하는 outbox를 사용한다. 여러 추론 주체가 공동 의미 상태를 발전시키는 Blackboard는 아니다. |
| VIA 방안: 요청과 사건 전달의 결합 | **검토 가능.** 현재처럼 즉시 필요한 조회는 요청하고, 나중에 도착하는 업무 결과는 사건으로 전달한다. 서로 다른 역할에 다른 협력 방식을 쓰는 구조다. |
| VIA 방안: 의존 관계가 이끄는 처리망 | **조건부 검토.** 근거, 의미, 응답의 연결을 실행 구조로 만들고 입력 변경 시 영향을 받은 결과를 다시 처리한다. 재사용만 추가한 기존 제어기와 얼마나 다른지 확인해야 한다. |
| VIA 방안: 상태 소유자들의 사건 협력 | **조건부 검토.** 각 소유자가 사건을 받아 자기 상태를 바꾸고 다음 사건을 발행한다. 중앙 호출 관계를 줄일 수 있지만 전체 요청의 완료와 오류 책임을 다시 설계해야 한다. |
| VIA 방안: 공동 의미 작업공간 | **조건부 검토.** 여러 해석 전문 주체가 공동 작업공간에 부분 결과를 기여한다. 단일 의미 처리자와 저장소만 있는 구조라면 Blackboard의 이익을 주장할 수 없다. |
| 기존 논의와 연결 | [31](./04-31-semantic-construction.md)의 지속 작업공간과 [33](./04-33-dialogue-coordination.md)의 제안 및 참조 교환이 부분적으로 관련된다. 31 B가 곧 전형적인 Blackboard라는 뜻은 아니다. |
| 근거 | 참조 설계의 [architecture.md §3, §11~12](../target-architecture/architecture.md). 협력 방식의 근거는 [E8](#source-e8), [E9](#source-e9), [E11](#source-e11)이다. |

### 3.6 사용자 상호작용과 지속 입력

VIA가 보고서를 설명하는 중 사용자가 “아니, 메일에 넣을 표만 말해줘”라고 끼어들 수 있다. 기존 음성을 즉시 멈추는 일과 새 요청의 의미를 해석하는 일은 서로 다른 시간 안에 처리되어야 한다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 추론이나 외부 업무가 진행 중이어도 새 입력과 중단을 받고, 여러 응답 생산자의 결과를 한 대화로 전달하는 구조를 정한다. 입력 반응 구조와 대화 담당권은 서로 조합할 수 있는 두 질문이다. |
| 일반 구조: 입력 차례 중심 처리 | 하나의 확정 입력을 하나의 처리 실행으로 연결해 응답을 만든다. 새 입력의 수신을 별도 I/O에서 계속할 수 있으므로 이 구조 자체가 입력 차단을 뜻하지는 않는다. |
| 일반 구조: 즉시 반응과 의미 처리 분리 | 입력 수신이나 재생 중단은 짧고 독립적인 경로에서 처리하고, 오래 걸리는 해석과 상태 변경은 다른 경로에서 처리한다. 두 경로는 입력 버전과 취소 정보를 교환해야 한다. |
| 일반 구조: 공통 대화 중개 | 여러 처리자가 질문이나 결과를 만들더라도 공통 대화 주체가 게시 순서와 대화 연결을 관리한다. 개별 처리자는 사용자에게 직접 경쟁해서 말하지 않는다. |
| 일반 구조: 대화 담당권 이전, Handoff | 현재 대화를 맡는 Agent를 다른 Agent로 넘긴다. 어느 이력과 권한이 함께 이동하는지, 이전 담당자의 늦은 응답을 어떻게 처리할지 정해야 한다. |
| 현재 VIA 참조 구조 | Interaction Manager가 입력 수집과 로컬 재생 중단을 담당한다. Request Controller는 주로 확정 입력으로 의미 처리를 진행하고 입력 중에는 근거를 준비한다. Request Controller의 허용을 받은 응답을 Response Manager가 게시한다. S2S 직접 응답도 이 게시 경계를 거친다. |
| VIA 방안: 독립 입력과 요청별 처리 | **검토 가능.** 현재처럼 입력은 계속 받되 의미 처리의 주요 단위는 확정 입력으로 둔다. 발화 중 준비와 미리 생성한 답변을 사용할 수 있으므로 아무 준비도 하지 않는 방안으로 축소하지 않는다. |
| VIA 방안: 독립 입력과 수정 가능한 의미 처리 | **조건부 검토.** 발화 중 의미 처리를 진행하면서 정정에 따라 중간 상태와 결과를 갱신한다. 입력 조각, 근거, 의미, 응답 사이의 소유와 무효화가 실제 구조로 설명되어야 한다. |
| VIA 방안: 내부 대화 담당권 이전 | **조건부 검토.** 특정 주제의 대화를 전문 처리자에게 맡길 수 있다. VIA는 공통 기록과 실제 전달, 정정과 취소의 책임을 유지해야 한다. 외부 Agent로 사용자를 넘긴 뒤 대화 연결을 포기하는 구조는 현재 제품 목적과 맞지 않는다. |
| 기존 논의와 연결 | [34](./04-34-incremental-voice.md)는 확정 발화 처리와 잠정 처리의 차이를 다룬다. 이 차이가 충분히 중요한 SW 구조 비교인지에 대한 논의는 남아 있다. 이 지도에 적었다는 이유로 처리 전략의 차이를 검증된 주요 구조 대안으로 승격하지 않는다. |
| 근거 | 참조 설계의 [architecture.md §6, §8, §13](../target-architecture/architecture.md), [공유 Omni 계약 §3](../target-architecture/shared-omni-runtime.md). Handoff와 실행 중단 및 재개의 참고는 [E2](#source-e2), [E7](#source-e7)이다. |

### 3.7 기억과 Context의 소유 및 공유

사용자가 “보고서는 PDF로 해줘”라고 말한 뒤 한참 다른 대화를 나눌 수 있다. 나중에 메일을 수정하더라도 그 보고서 조건은 필요할 때 찾아야 한다. 반대로 사용자가 삭제한 선호를 과거 요약에서 다시 꺼내 적용해서는 안 된다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 누가 대화와 업무의 정보를 기억하고, 어떤 범위의 근거를 다른 처리자에게 제공하는지 정한다. 현재 요청의 작업 기억, 여러 대화에서 사용하는 장기 기억, 실제 업무 사실의 원본을 구분한다. |
| 일반 구조: 중앙 기억 서비스 | 공통 기억 주체가 원본이나 검색 가능한 기억을 관리하고 요청마다 필요한 Context를 제공한다. 정정과 삭제의 관리 지점을 모을 수 있지만 다양한 소비자의 요구를 함께 지원해야 한다. |
| 일반 구조: 처리자별 지역 기억 | 각 Agent나 대화 처리자가 자기 맥락을 보유한다. 지역 판단을 이어가기 쉽지만 다른 주제와 연결되는 사실의 공유와 정정 전파를 설계해야 한다. |
| 일반 구조: 공통 기억과 지역 작업 상태의 결합 | 공통 선호와 사실은 공유하고, 각 업무의 질문이나 미완료 해석은 지역 상태로 유지한다. 공유 사실을 복사한 경우 원본 변경이 지역 상태에 반영되는 규칙이 필요하다. |
| 일반 구조 안의 표현 선택 | 대화 원문 중심 검색과 구조화된 사실 중심 기억을 조합할 수 있다. 벡터 검색을 쓰는지보다 누가 원본을 관리하고 어떤 근거를 제공하는지가 이 영역의 중심이다. |
| 현재 VIA 참조 구조 | 단기 입력 근거, 중기 요약과 검색 view, 장기 User Memory를 나눈다. Context Manager가 근거를 구성하되 대화, Task, 실제 전달의 원본은 각 소유자에게 조회한다. 장기 기억은 명시적 요청으로 저장하며 모델 세션을 원본으로 삼지 않는다. 별도 embedding 모델과 vector DB는 기본 구성에 없다. |
| VIA 방안: 중앙 Context 구성 유지 | **검토 가능.** 각 원본 소유자는 유지하고 Context Manager가 요청에 필요한 정보를 모은다. 중앙에서 과거 요약과 원본의 버전 및 권한을 함께 확인한다. |
| VIA 방안: 업무별 작업 기억 | **검토 가능.** 업무별 대화 처리자가 자기 질문과 조건을 유지하고 공통 User Memory를 조회한다. 다른 업무 결과를 사용하는 경우 참조와 변경 통지를 통해 연결해야 한다. |
| VIA 방안: 공유 사실과 역할별 view | **조건부 검토.** 출처가 있는 공통 사실을 관리하고 각 역할에 필요한 범위만 별도 view로 제공한다. 역할별 view는 원본이 바뀌거나 권한이 철회되면 사용할 수 없게 해야 한다. |
| 선택할 때 확인할 비용 | 지역 기억의 복사본이 늘면 정정과 삭제를 빠짐없이 전파하기 어려워질 수 있다. 중앙에서 모든 정보를 모으면 Context 크기와 조회 비용이 커질 수 있다. 새 저장소의 이름보다 실제 사용 근거와 원본의 관계를 비교한다. |
| 기존 논의와 연결 | [31](./04-31-semantic-construction.md)은 의미 작업 상태, [33](./04-33-dialogue-coordination.md)은 업무별 대화 상태와 관련된다. 두 문서가 User Memory와 Context 전체의 소유 구조를 비교한 것은 아니다. |
| 근거 | [기억과 Context 계약 §1~6](../target-architecture/memory-and-context-lifecycle.md). 세션 상태와 장기 기억을 나누는 Framework 사례는 [E5](#source-e5), [E6](#source-e6)이다. |

### 3.8 상태 원본과 확정 권한

사용자의 답을 보고서 업무에 연결했다는 기록과, 그 업무에 PDF 형식을 적용하라는 명령이 서로 어긋나면 안 된다. 두 기록을 한 번에 저장할 수도 있고, 서로 다른 소유자가 요청과 접수 결과를 주고받으며 기록할 수도 있다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 어떤 기록을 확정 사실의 원본으로 삼는지, 여러 관련 변경을 누가 함께 확정하는지 정한다. 원본의 형태와 확정 경계는 서로 다른 하위 질문이다. |
| 일반 구조: 현재 상태 중심 저장 | 현재 질문, 업무 상태, 적용된 조건 등을 원본으로 저장하고 갱신한다. 변경 이력, 감사 로그, backup을 함께 둘 수 있다. 이런 보조 기록이 있다고 모두 Event Sourcing이 되는 것은 아니다. |
| 일반 구조: Event Sourcing | 상태를 바꾼 사건의 순서를 원본으로 저장하고, 그 사건들을 적용해 현재 상태를 만든다. 과거 상태를 재구성하기 쉬울 수 있지만 사건 표현의 변경과 재적용 규칙을 관리해야 한다. |
| 일반 구조: 공동 트랜잭션 | 여러 관련 변경을 하나의 저장 작업으로 확정한다. 전부 반영하거나 전부 반영하지 않는 범위를 정하는 방식이다. 같은 DB를 사용하더라도 각 상태의 의미 소유자는 유지할 수 있다. |
| 일반 구조: 소유자별 독립 확정 | 각 소유자가 자기 저장 경계에서 변경을 확정하고, 다른 소유자에게 명령이나 사건을 전달한다. 중간에 한쪽만 반영된 상태와 접수 응답 유실을 명시적으로 관리해야 한다. |
| 현재 VIA 참조 구조 | 각 Component가 자기 내구 상태의 의미를 소유하고 송수신 및 실제 전달 기록을 보관한다. 관련 요청, 명령, 전송 상태는 하나의 local State Store 트랜잭션으로 함께 확정할 수 있다. 전체 시스템을 사건 이력만으로 재구성하는 Event Sourcing으로 명시하지는 않았다. |
| VIA 방안: 현재 상태와 공동 확정 | **검토 가능.** 현재 상태와 내구 송수신 기록을 원본으로 사용하고 관련 소유자의 변경을 한 번에 저장한다. 외부 Agent의 실제 접수는 이 로컬 저장과 별도 사실로 확인한다. |
| VIA 방안: 특정 영역의 사건 이력 원본 | **검토 가능.** 대화나 업무의 의미 있는 변경을 사건으로 저장하고 상태를 재구성한다. 모든 데이터를 같은 방식으로 바꿀 필요는 없으며, 적용 영역과 재생으로 발생시키면 안 되는 외부 효과를 명확히 해야 한다. |
| VIA 방안: 대화와 업무의 독립 확정 | **검토 가능.** 대화 쪽은 요청 의도를 기록하고 업무 쪽은 접수와 명령을 자기 저장소에 기록한다. 대화는 접수 결과를 받아 다시 기록한다. 같은 요청의 중복 생성과 응답 유실을 처리하는 계약이 추가된다. |
| 기존 논의와 연결 | [35](./04-35-state-authority.md)는 현재 상태와 사건 이력이라는 원본 선택을 다룬다. [42](./04-42-lifecycle-ownership.md)는 대화와 업무의 상태 소유 및 독립 실행을 다루며 확정 경계도 달라진다. 42 전체를 저장 트랜잭션 문제로 축소하지 않는다. |
| 근거 | [제어 계약 §5, §7](../target-architecture/control-and-lifecycle.md), [architecture.md §11~12](../target-architecture/architecture.md). Event Sourcing의 정의와 비용은 [E12](#source-e12)를 참고한다. |

<a id="area-09"></a>

### 3.9 실행의 지속성과 재개

보고서 형식을 묻는 질문에 사용자가 다음 날 답할 수 있다. 그동안 VIA가 종료되었더라도 무엇을 기다렸는지 알아야 한다. 질문 문장을 보관하는 것과 그 답을 받아 처리할 실행을 복원하는 것은 다른 책임이다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 사용자 답변이나 외부 결과를 오래 기다리는 처리와 실패한 처리를 누가 다시 진행시키는지 정한다. 진행 상태와 대기 조건, 재개 책임을 어디에 둘지 선택한다. |
| 일반 구조: 애플리케이션 상태 머신 | 애플리케이션 코드가 현재 상태와 사건을 읽고 허용된 다음 처리를 결정한다. 재시작 때도 저장 기록을 읽어 무엇을 재조회하거나 재개할지 코드가 판단한다. |
| 일반 구조: 체크포인트 기반 실행 그래프 | Runtime이 처리 단계와 중간 상태를 저장한다. 다시 시작할 때 저장된 진행 지점과 필요한 입력을 사용해 실행을 이어 간다. 체크포인트는 재개에 필요한 저장 지점을 뜻한다. |
| 일반 구조: Durable Workflow | Runtime이 실행 이력과 대기, 재시도, 재개를 관리한다. 외부 호출의 결과와 다시 실행해도 되는 처리를 구별하는 계약이 필요하다. 일반 함수의 메모리를 그대로 영원히 보관하는 방식은 아니다. |
| 일반 구조: 지속 Entity 또는 Actor 실행 | 같은 업무를 계속 담당하는 실행 주체가 사건을 받아 상태를 바꾼다. 사용하지 않을 때 메모리에서 내리고 필요할 때 복원할 수 있다. Actor라는 사실만으로 내구 저장이 생기지는 않으므로 복원 방식을 함께 선택한다. |
| 현재 VIA 참조 구조 | Request Controller가 사용자 대기, 근거 대기, 선행 결과 대기를 관리한다. 재시작 시 소유자 상태와 inbox 및 outbox를 복원하고 Agent 상태를 조회한다. 별도 Durable Workflow 제품이나 그래프 실행 Runtime은 지정하지 않았다. |
| VIA 방안: VIA 코드의 대기와 복구 | **검토 가능.** 현재처럼 Request Controller와 관련 상태 소유자가 대기 조건을 검사하고 다음 처리를 구성한다. 대기와 복구 동작을 VIA가 직접 시험하고 유지해야 한다. |
| VIA 방안: 실행 그래프의 저장과 재개 | **조건부 검토.** 요청 이해와 질문 및 반환 경로를 실행 그래프로 표현하고 중간 상태를 Runtime에 맡긴다. VIA의 Request와 Runtime의 개별 실행이 어떻게 연결되는지 정해야 한다. |
| VIA 방안: Durable Workflow에 대기 위임 | **조건부 검토.** 사용자 답변과 명시적 선행 결과를 기다리는 흐름을 Runtime이 재개한다. PC 배치와 저장 비용, 실행 정의의 버전 변경, 장기 대기의 삭제 처리가 맞아야 한다. |
| VIA 방안: 지속 업무 상호작용 실행자 | **조건부 검토.** 업무별 실행자가 질문과 상태 사건을 받아 자기 대화를 이어 간다. 외부 Agent 내부의 업무 수행 과정을 VIA가 실행하는 것으로 확대하지 않는다. |
| 공통으로 남는 책임 | 어느 Runtime을 사용해도 외부 Agent가 명령을 받았는지 불명확하면 그 사실을 확인해야 한다. 내부 실행 재개 기능만으로 메일 발송 같은 외부 효과가 정확히 한 번 발생한다고 보장할 수는 없다. |
| 기존 논의와 연결 | [35](./04-35-state-authority.md)의 저장 원본과 [42](./04-42-lifecycle-ownership.md)의 실행 수명은 관련 조건이다. 두 문서 모두 애플리케이션 상태 머신과 Durable Workflow Runtime을 직접 비교하는 문서는 아니다. |
| 근거 | [제어 계약 §3~7](../target-architecture/control-and-lifecycle.md). 실행 상태 저장과 재개의 사례는 [E6](#source-e6), [E7](#source-e7), [E13](#source-e13)이다. |

### 3.10 실행과 배포 및 장애 경계

대화창을 닫아도 보고서 업무는 남아야 한다. 그러나 이 요구만으로 대화와 업무를 별도 서비스로 나눠야 하는 것은 아니다. 하나의 배경 Core도 서로 다른 데이터 수명을 관리할 수 있다. 별도 서비스를 두는 선택은 실행과 상태 권한을 독립시키는 추가 선택이다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 어떤 책임들이 같은 프로세스, 시작과 종료, 장애 범위를 공유할지 정한다. 독립 실행을 얻는 대신 메시지 전달과 상태 조정 및 추가 메모리 비용이 생긴다. |
| 일반 구조: 모듈화된 단일 프로세스 | 책임을 내부 모듈로 구분하되 한 OS 프로세스에서 실행한다. 직접 호출과 공유 자원을 사용할 수 있다. 별도 모듈이 있다는 사실만으로 프로세스 장애가 분리되지는 않는다. |
| 일반 구조: 통합 Core와 격리 Worker | 중요한 상태 권한은 Core에 두고 무거운 계산이나 위험한 연동을 Worker로 분리한다. Worker는 맡은 처리를 수행하며 Core의 상태 권한을 자동으로 가지지는 않는다. |
| 일반 구조: 독립 서비스 | 각 서비스가 자기 상태와 실행 수명을 소유하고 계약으로 협력한다. 반드시 다른 PC나 클라우드 서버에 둘 필요는 없다. 같은 PC에서도 별도 서비스로 실행할 수 있다. |
| 일반 구조: Actor Runtime | 논리 Actor들의 사건 처리를 Runtime이 실행한다. 여러 Actor를 한 프로세스에 둘 수도 있고 배치를 나눌 수도 있다. 논리 소유와 물리 장애 격리를 같은 것으로 보지 않는다. |
| 현재 VIA 참조 구조 | Core에 주요 대화 및 업무 상태 권한이 있다. UI, Voice, Shared Inference Service, Speech Input Worker를 나누고 위험한 연동은 Connector Worker로 격리한다. local embedded DB는 별도 DB 서버 없이 Core에서 접근하는 영속 저장소다. |
| VIA 방안: 통합 Core와 필요한 격리 유지 | **검토 가능.** 대화와 업무의 서로 다른 수명을 하나의 Core가 관리한다. 내부 책임과 인터페이스를 나눌 수 있으며, 대화창 종료가 업무 기록 삭제를 뜻하지 않는다. |
| VIA 방안: 대화와 업무 서비스 독립 | **검토 가능.** 대화 서비스와 업무 서비스가 각자 상태와 실행 수명을 소유한다. 업무 서비스가 접수한 Task를 독립적으로 추적할 수 있지만 새 사용자 의도 해석 등 대화 서비스의 책임까지 대신하지 않는다. |
| VIA 방안: 일부 실행 경계 조정 | **조건부 검토.** 역할별 Worker를 합치거나 나누고 Actor Runtime을 사용할 수 있다. 현재 입력과 지연 요구를 유지하면서 실제 장애 또는 실행상의 이익이 생기는지 확인해야 한다. 상자 수를 늘리는 것이 목표가 아니다. |
| 기존 논의와 연결 | [42](./04-42-lifecycle-ownership.md)가 통합 Core와 독립 대화 및 업무 서비스를 비교한다. 드문 갱신이나 재시작만으로 B의 대표 이익을 설명하는 접근은 사용자 검토에서 부족하다고 지적됐다. 정상 사용에서의 선택 근거는 별도로 평가해야 한다. |
| 근거 | 참조 설계의 [architecture.md §14](../target-architecture/architecture.md). Actor와 실행 배치의 구분은 [E10](#source-e10), 실제 독립 처리 서비스의 예는 [E14](#source-e14)를 참고한다. 일반 구조의 목록은 이런 SW 배치 방식을 VIA 질문에 맞춰 분류한 것이다. |

### 3.11 모델 실행 자원의 소유

보고서의 긴 결과를 요약하는 동안 사용자가 다시 말하기 시작할 수 있다. 여러 Agent가 있다는 사실만으로 모델 계산이 동시에 빨라지는 것은 아니다. 누가 모델과 세션을 소유하고 입력 처리에 필요한 자원을 유지할지 정해야 한다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 모델 가중치, 요청별 세션, 계산 중 기억과 추론 자원을 어디에서 관리하는지 정한다. 여기서 가중치는 모델의 학습된 값이고, KV는 이전 입력의 계산 결과를 재사용하기 위한 세션별 상태다. |
| 일반 구조: 애플리케이션 내장 추론 | 애플리케이션 프로세스가 모델을 직접 적재하고 호출한다. 별도 서비스 통신은 줄어들 수 있지만 모델 실행과 애플리케이션의 실행 및 장애 수명이 더 결합된다. |
| 일반 구조: 공유 추론 서비스 | 여러 호출자가 하나의 추론 서비스에 요청한다. 서비스가 모델과 세션을 관리하므로 호출자마다 모델을 복제할 필요가 없다. 서비스 통신과 공통 자원 경합은 관리해야 한다. |
| 일반 구조: 역할별 추론 인스턴스 | 역할마다 별도 모델 실행 인스턴스를 둔다. 자원과 장애 범위를 분리할 수 있지만 가중치 복제와 추가 메모리 비용이 생길 수 있다. |
| 일반 구조: 원격 추론 또는 로컬과 원격의 결합 | 네트워크로 모델 기능을 사용한다. 장비 자원, 연결 지연, 자료 전송과 장애 조건이 바뀐다. 원격 사용은 단순 구현 교체로 취급할 수 없는 제품 조건을 포함한다. |
| 현재 VIA 참조 구조 | Model Access의 서버 측 책임을 Shared Inference Service에 둔다. 한 벌의 Omni 가중치를 Voice와 Semantic 역할이 공유하며 세션과 KV 및 권한은 분리한다. 별도 Speech Input Worker의 경량 Streaming ASR이 지속 음성 인식을 맡는다. |
| VIA 방안: 독립된 공유 추론 서비스 | **검토 가능.** 현재처럼 가중치 소유자를 한 곳에 두고 Voice와 Core가 요청한다. 서비스가 멈추면 두 Omni 역할이 함께 영향을 받지만 입력 수집과 별도 ASR 및 로컬 재생 중단은 독립적으로 유지한다. |
| VIA 방안: 공유 모델을 프로세스에 내장 | **조건부 검토.** 가중치를 한 번만 적재한 채 일부 실행 경계를 합칠 수 있다. 무거운 추론 중에도 입력 수집과 인식 및 요청 제어가 진행되도록 해야 한다. 실제 장비에서 가능한지는 검증되지 않았다. |
| VIA 방안: 역할별 Omni 복제 또는 원격 이전 | **전제 변경 필요.** 현재 공유 on-device Omni 조건과 충돌한다. 일반적인 선택지에는 포함되지만 현 조건의 대안처럼 몰래 도입하지 않는다. |
| 구조와 정책의 구분 | 어떤 job을 먼저 처리할지의 세부 순서만 바꾸는 것은 이 표의 주요 구조 선택이 아니다. 모델 소유자, 호출 계약, 세션 수명, 취소와 자원 회수 경계가 어떻게 달라지는지 설명해야 한다. |
| 근거 | [공유 Omni 계약 §1~8](../target-architecture/shared-omni-runtime.md), [architecture.md §14](../target-architecture/architecture.md). 모델 실행을 서비스로 조직하는 사례는 [E14](#source-e14)다. |

<a id="area-12"></a>

### 3.12 권한과 강제 격리

메일에 넣을 표를 찾는 처리자가 다른 개인 파일까지 읽을 수 있는 환경에 있을 수 있다. 코드가 읽기 전에 검사하는 방식과, 애초에 그 처리자가 다른 파일에 접근할 권한이 없는 방식은 서로 다르다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 어떤 자료를 허용할지뿐 아니라 그 허용 범위를 실제로 누가 강제하는지 정한다. 처리 코드에 결함이 있거나 침해되었을 때 넘을 수 있는 경계가 달라진다. |
| 일반 구조: 신뢰 프로세스 내부 검사 | 처리 코드가 자료 접근 권한을 가진 환경에서 실행되고, 접근 전에 정책 검사를 한다. 검사 경로가 올바르게 유지된다는 전제와 침해 시의 보장 범위를 명시해야 한다. |
| 일반 구조: Broker 중개 | Broker는 권한을 가진 중개자다. 제한된 처리자는 필요한 자료를 직접 읽지 않고 중개자에게 요청한다. 중개자가 자료 범위와 현재 권한을 검사해 허용된 결과만 제공한다. |
| 일반 구조: OS Sandbox | 운영체제가 파일, 네트워크, 프로세스 접근을 제한한다. 프롬프트에 금지 문장을 쓰는 것과 달리 실행 환경이 직접 제약을 건다. |
| 일반 구조: 작업별 제한 실행 환경 | 작업마다 접근 가능한 자료와 기능이 제한된 환경을 제공한다. 환경을 준비하고 종료하며 자료를 정리하는 비용이 추가된다. Broker나 Sandbox와 조합할 수 있다. |
| 현재 VIA 참조 구조 | Policy Manager가 현재 허용 범위를 판단하고 Request Controller 및 실제 자료 사용 경로가 조건을 검사한다. 위험한 연동은 Worker로 분리한다. Context 구성과 의미 처리 전체가 별도의 무권한 Sandbox에 들어가는 설계는 아니다. |
| VIA 방안: 신뢰 Core와 선택적 격리 | **검토 가능.** 현재처럼 Core의 검사와 위험 연동의 격리를 결합한다. 필요한 보장 수준이 이 신뢰 경계로 충족되는지 확인해야 한다. |
| VIA 방안: 제한 처리자와 권한 Broker | **검토 가능.** Context 구성이나 의미 처리 코드가 원본 자료에 직접 접근하지 못하게 하고 허용된 참조만 중개받게 한다. 자료 복사, 통신, 세션 정리와 권한 철회 경로가 추가된다. |
| VIA 방안: 확장 기능별 격리 | **조건부 검토.** 외부 제공자나 plugin의 신뢰 수준에 따라 제한 실행 환경을 나눈다. 실제 접근 권한까지 분리하지 않은 프로세스 분리는 같은 보장을 주지 않는다. |
| 공통으로 남는 책임 | 외부 업무 Action의 실제 권한 강제는 Downstream Agent 책임이다. VIA의 검사가 이를 대신하지 않는다. native 코드 침해까지 막아야 한다는 필수 조건이 있다면 그 조건을 만족하지 못하는 신뢰 Core 방안은 적합하지 않다. |
| 기존 논의와 연결 | [36](./04-36-capability-isolation.md)이 이 영역을 직접 다룬다. [42](./04-42-lifecycle-ownership.md)의 서비스 분리는 상태와 실행 수명의 분리이며 보안 격리와 동일하지 않다. |
| 근거 | [architecture.md §9~10, §14](../target-architecture/architecture.md), [기억과 Context 계약 §5](../target-architecture/memory-and-context-lifecycle.md). OS 수준 격리의 실제 설명은 [E15](#source-e15)다. |

### 3.13 기능 발견과 연결 및 갱신

새로운 문서 작성 Agent를 추가했다고 하자. VIA는 그 Agent가 무엇을 할 수 있는지, 이미 실행 중인 업무를 어떻게 조회하는지, 수정과 취소를 지원하는지 알아야 한다. 설명 문장만 읽고 모든 기능을 지원한다고 간주할 수는 없다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 새로운 모델, 자료원, Agent를 누가 등록하고 연결하며 기능과 버전 변경을 어디에서 흡수할지 정한다. Agent 후보의 점수를 계산하는 알고리즘과 연동 구조는 구별한다. |
| 일반 구조: 명시적 연동과 Adapter | 알고 있는 제공자를 코드나 설정으로 연결하고 Adapter가 제공자별 형식을 공통 형식으로 바꾼다. Adapter는 계약을 번역하는 모듈이며, 제공자 교체 시 영향을 그 경계에 가두려는 방식이다. |
| 일반 구조: Plugin 또는 Microkernel 계열 | 작은 공통 기반이 확장 지점을 제공하고 기능을 별도 plugin으로 추가한다. 어떤 기능을 등록할 수 있는지, 언제 활성화하고 제거하는지, 버전이 맞지 않을 때 어떻게 할지를 기반이 관리한다. |
| 일반 구조: Registry와 연결 Broker | Registry는 제공자와 기능의 등록소다. 연결 Broker는 등록된 기능과 조건을 확인해 사용할 제공자에 연결한다. 모델이 후보를 고르는지와 등록 및 연결 책임의 위치는 따로 정할 수 있다. |
| 일반 구조: 공통 Protocol 기반 서비스 연동 | 제공자가 공개한 기능과 메시지 계약으로 통신한다. MCP는 자료와 도구 등 기능의 연결, A2A는 Agent와 작업 및 메시지 교환의 참고다. 둘은 같은 계약을 제공하는 대체품이 아니다. |
| 현재 VIA 참조 구조 | Model Access, Context Manager, Agent Gateway가 각 의존성의 Adapter를 가진다. Agent Gateway는 버전 있는 capability profile, 즉 지원 기능 정보를 소유한다. Request Interpreter가 적합성을 제안하고 Request Controller가 기능과 권한 및 제어 지원을 검사한다. 동적 plugin 플랫폼이나 MCP 및 A2A 채택까지 지정하지 않았다. |
| VIA 방안: 공통 계약과 명시적 Adapter | **검토 가능.** 현재 구조를 유지하며 등록된 기능과 버전을 사용한다. 일반적인 제공자 변경을 이 방식으로 충분히 국소화할 수 있다면 더 큰 플랫폼이 필요하지 않을 수 있다. |
| VIA 방안: 확장 수명을 관리하는 plugin 기반 | **조건부 검토.** 자료원과 Agent 연동을 등록, 활성화, 교체, 제거하는 공통 기반을 둔다. 실제로 독립적인 확장 배포가 필요한지와 권한 격리의 추가 요구를 확인해야 한다. |
| VIA 방안: 독립 기능 등록과 연결 서비스 | **조건부 검토.** 여러 소비자가 공유하는 기능 등록, 적합성 확인, 연결 수명을 별도 서비스가 소유한다. 등록소 하나를 추가한 정도로 얻는 이익이면 주요 구조 비교로 보지 않는다. |
| VIA 방안: 공통 Protocol을 외부 경계에 적용 | **검토 가능.** 외부 메시지를 VIA의 내부 계약으로 변환해 기존 소유 구조와 결합할 수 있다. Protocol을 바꾸는 것만으로 요청이나 Task의 권한이 이동하지는 않는다. |
| 근거 | [architecture.md §4, §12](../target-architecture/architecture.md), [제어 계약 §5, §7](../target-architecture/control-and-lifecycle.md). 확장 계약은 [E16](#source-e16), 외부 기능 연동은 [E17](#source-e17), [E18](#source-e18)를 참고한다. |

### 3.14 검증과 결과 채택의 권한

모델이 “메일에 표를 넣으라는 뜻”이라고 해석했어도, 사용자가 그 뒤에 요청을 취소했을 수 있다. 결과를 잘 생성하는 일과 지금 그 결과를 실제로 적용해도 되는지 결정하는 일은 분리할 수 있다.

| 구분 | 설명 |
| --- | --- |
| 이 영역의 목적 | 결과를 생산한 주체와 별도로 누가 그 결과를 실제 상태 변경, 위임, 사용자 게시에 사용할지 결정하는지 정한다. 검증 의견을 내는 역할과 적용을 거부할 수 있는 권한을 구별한다. |
| 일반 구조: 생산 경로 안의 자체 검사 | 결과를 만드는 코드나 모델 호출 경로가 조건을 검사한다. 구조가 단순할 수 있지만 같은 오해나 결함이 생산과 검사를 함께 통과할 수 있다. |
| 일반 구조: 독립 검증 Component | 별도 책임을 가진 검증자가 근거와 조건을 검사하고 채택 여부를 결정한다. 독립성이 어떤 자료와 구현 및 실패 경계에서 생기는지 설명해야 한다. 이름만 분리한 함수와는 다르다. |
| 일반 구조: Generator와 Critic | 생성자가 결과를 만들고 다른 추론 단계가 평가와 수정 의견을 낸다. 보통은 결과 개선 Workflow다. Critic에게 실제 채택 권한이 있는지, 다른 근거로 판단하는지는 추가 선택이다. |
| 일반 구조: 제안과 채택 분리 | 생산자는 상태 변경이나 응답을 제안한다. 상태 소유자 또는 공통 실행 경계가 현재 조건을 확인한 뒤 적용한다. 여러 생산자가 있더라도 실제 적용 권한을 제한할 수 있다. |
| 현재 VIA 참조 구조 | Request Interpreter는 의미를 제안하고 Request Controller가 필요한 정보, 근거, 후보 범위, 현재 버전과 권한을 검사해 확정한다. Agent Gateway와 Response Manager 등은 전송과 게시 시의 조건을 확인한다. 별도 Critic Agent나 독립 검증 서비스는 없다. |
| VIA 방안: 현재 코드 검사와 사용 지점 검사 | **검토 가능.** Request Controller에서 의미 제안을 검사하고 실제 전송 및 게시 경로가 현재 조건을 다시 확인한다. 코드 검사를 통과했다는 사실이 사용자의 진짜 의도를 증명하지는 않는다. |
| VIA 방안: 근거 검증 책임의 독립 | **조건부 검토.** 별도 검증자가 결과의 근거와 적용 조건을 소유하고 채택을 결정한다. 중앙 검사에 작은 기능을 추가하는 것으로 같은 성질을 얻을 수 있는지 먼저 확인해야 한다. |
| VIA 방안: 특정 오류를 찾는 Critic | **조건부 검토.** 조건 누락이나 근거 없는 설명처럼 특정 오류를 찾아 수정 의견을 제공한다. 같은 Omni를 여러 번 호출하면 같은 오해를 반복할 수 있고 추가 지연도 생긴다. Critic 추가만으로 주요 구조 대안이 성립하지는 않는다. |
| VIA 방안: 지역 제안과 공동 채택 | **검토 가능.** 업무별 처리자가 자기 상태 변경을 제안하고 관련 소유자가 검사한 변경만 함께 적용한다. 중앙 조정자가 지역 의미를 다시 생산하는지와 최종 저장을 조정하는지를 구분한다. |
| 기존 논의와 연결 | [33](./04-33-dialogue-coordination.md)의 제안과 채택, [41](./04-41-request-resolution-control.md)의 공통 최종 검사와 관련된다. 41은 주로 의미를 해결하는 주체의 비교이며, 두 안 모두 최종 적용 검사를 가질 수 있다. |
| 근거 | [architecture.md §6~8, §11~13](../target-architecture/architecture.md), [제어 계약 §5~6](../target-architecture/control-and-lifecycle.md). Generator와 Critic에 해당하는 평가 및 개선 Workflow의 참고는 [E1](#source-e1)이다. |

### 4.1 서로 다른 질문을 같은 선택으로 합치지 않는다

| 함께 읽을 영역 | 구별해야 하는 질문과 VIA 예시 |
| --- | --- |
| 1 제어권과 14 채택 권한 | 모델이 다음 자료 조회를 선택해도 최종 업무 위임은 코드가 거부할 수 있다. 모델의 탐색 자율성과 외부 실행 권한은 같은 것이 아니다. |
| 2 분해 단위와 4 조직 | 보고서와 메일 처리자를 나누더라도 중앙 코드, 모델 기반 Supervisor, 동료형 협력 중 여러 조정 방식을 사용할 수 있다. |
| 3 의미 상태와 7 기억 | 미완료 요청의 조건을 저장하는 것과 사용자 선호를 장기 기억하는 것은 수명과 사용 목적이 다르다. 하나의 저장소를 사용해도 구별해야 한다. |
| 4 조직과 10 배치 | 중앙 조정 구조를 여러 프로세스로 실행할 수 있고, 여러 논리 Agent를 같은 프로세스에서 실행할 수도 있다. 중앙과 분산이라는 표현만으로 두 질문을 함께 답하지 않는다. |
| 5 협력과 8 상태 원본 | 사건을 메시지로 전달하는 구조가 반드시 Event Sourcing인 것은 아니다. 송수신 기록과 현재 상태를 원본으로 사용하는 사건 기반 시스템도 가능하다. |
| 8 상태 원본과 9 실행 재개 | Event Sourcing은 상태를 어떻게 재구성할지, Durable Workflow는 실행을 어떻게 이어갈지 다룬다. 하나를 사용한다고 다른 하나가 자동으로 생기지 않는다. |
| 10 배치와 12 권한 | 프로세스를 나눠도 두 프로세스가 같은 파일과 자격 정보를 모두 사용할 수 있다면 접근 권한은 충분히 분리되지 않았을 수 있다. |
| 2 Agent 분해와 11 모델 자원 | 여러 Agent가 같은 Omni의 서로 다른 세션을 사용할 수 있다. Agent 수만큼 가중치를 복제하거나 추론 속도가 증가한다고 가정하지 않는다. |
| 13 연동과 4 조정 | A2A 같은 통신 계약을 사용해도 중앙 조정 구조를 유지할 수 있다. 외부 통신 방식이 내부 협력 조직을 자동으로 결정하지 않는다. |

### 4.2 조합 예시를 읽는 방법

다음은 조합 원리를 설명하는 예시이며 선택된 새 VIA 설계가 아니다.

**예시 A:** 하나의 해석 주체가 요청을 이해하고, 코드가 자료 조회를 조정하며, Context Manager가 필요한 기억을 제공하고, 공통 DB에서 관련 상태를 확정할 수 있다. 계산은 독립 공유 추론 서비스가 수행한다. 이 조합에서 의미 처리는 중앙에 있지만 실행 프로세스는 여러 개다.

**예시 B:** 업무별 대화 처리자가 지역 의미와 질문 상태를 유지하고, 조정자가 업무 간 참조를 연결하며, 공통 User Memory를 조회할 수 있다. 여러 처리자가 제안한 변경을 하나의 DB에서 함께 확정할 수도 있다. 업무별 처리자가 있다는 이유로 각각 별도 DB나 프로세스가 필요하지는 않다.

실제 조합에서는 같은 상태에 두 명의 최종 소유자를 만들지 않아야 한다. 예를 들어 지속 의미 작업공간과 업무별 대화 처리자를 함께 사용한다면, 작업공간이 먼저 확정한 상태를 중앙이 다시 확정하는 이중 권한을 피해야 한다. [31과 33의 결합 설명](./04-33-dialogue-coordination.md#42-04-31과-함께-선택할-때의-소유-경계)은 이런 문제를 다룬다. 그 문서가 임의의 모든 조합을 검증했다는 뜻은 아니다.

## 6. 이 지도에서 실제 비교 주제로 발전시키는 방법

이 문서는 선택지를 찾기 위한 지도다. 각 방안의 구현을 설계하거나 모두를 주요 DP로 만드는 작업을 완료한 문서는 아니다. 여기서 관심 있는 선택지를 찾으면 [비교 가이드 §4](./04-30-comparison-guide.md#4-sw-구조적으로-다른-대안의-정확한-의미)에 따라 다음을 구체화한다.

1. **중요한 사용자 상황을 정한다.** 예를 들어 “여러 업무가 질문한 상황에서 사용자의 한 문장을 정확히 연결한다”처럼 결과를 설명한다. Framework 기능을 먼저 골라 사용 이유를 만들지 않는다.
2. **같은 입력으로 두 구조를 설명한다.** 누가 근거를 읽고 의미를 만들며 상태를 저장하고 사용자에게 돌려주는지 순서대로 적는다. 기존 참조 구조를 반드시 어느 한쪽에 맞출 필요는 없다.
3. **정상 사용과 정정을 모두 따라간다.** 사용자가 조건을 바꿨을 때, 결과가 늦게 도착했을 때, 권한을 철회했을 때 무엇이 달라지는지 확인한다. 장애와 재시작도 다루되 드문 사건만으로 대표 이익을 만들지 않는다.
4. **강한 상대 방안을 유지한다.** 중앙 구조도 비동기 처리, 업무별 검색, cache, 부분 갱신을 가질 수 있다. 상대 안의 합리적인 기능을 빼서 차이를 만들지 않는다.
5. **작은 변경으로 충분한지 확인한다.** 기존 코드에 작은 모듈이나 Adapter를 추가해 같은 이익을 얻을 수 있다면, 독립적인 주요 결정으로 다룰 이유를 다시 검토한다. 되돌리기 어렵게 만드는 복잡성을 일부러 추가하지 않는다.
6. **품질의 이익과 비용을 함께 적는다.** [03-00의 13개 관점](./03-00-quality-scenarios.md)을 사용한다. 정확성, 사용 목적에 맞는 결과, 기능 지원 범위, 반응 시간, VIA의 처리 완료 시간, 자원, 복구, 변경, 분석과 시험, 기밀성, 연동과 공존, 사용 중 오류 방지, 설치를 빠짐없이 검토한다. 이 지도는 그 검토를 대체하지 않는다.

부분 기능을 지원하는 방안도 탐색할 수 있다. 다만 지원하지 못하는 사용자 결과와 추가 질문 또는 수동 작업을 명시해야 한다. 기능을 덜 수행한 결과를 같은 성공으로 간주하거나 더 빠른 처리로 세지 않는다. 참조 설계, 모델 자원 조건, 기능 요구를 바꾸는 선택은 별도의 근거와 명시적 논의가 필요하다.
