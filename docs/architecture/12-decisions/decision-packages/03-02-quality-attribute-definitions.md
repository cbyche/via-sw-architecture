## 1. 문서 목적과 설계/평가 원칙

### 1.1 합의한 목적과 DP/QA의 관계

VIA의 목적은 핵심 QA 성능을 우선순위에 따라 최대화하는 SW를 만드는 것이다. 과제에서 중요한 기능/구조를 다루면서 핵심 QA에 영향을 주는 결정 후보가 DP-41/42/44/45다. 기능 목표와 외부 조건을 같게 두고 양안의 QA trade-off를 비교한다. 높은 순위의 의미 있는 성능 차이가 선택을 이끌며 낮은 순위 약점은 tactic으로 보완하고 전체 회귀를 확인한다. DP/승자는 아직 선정하지 않았다. 43/46 및 참조 Architecture/QA catalog/ADR의 기존 지위를 변경하지 않는다.

### 1.2 DP에서 QA 정의로 역으로 접근하는 방법

**구조 차이를 활성화하는 상황은 필수다.** 실제 조회/확정/실행/생산 기제가 달라지는 사례를 먼저 찾고 QA에서 수치로 관찰할 경로를 명시한다. 양안 동일 정답/원본/권한/모델·quota/외부 응답을 사용하며 A의 cache/병렬/부분 갱신과 B의 추가 해석/생산/검증 비용을 모두 인정한다. 결과를 만들기 위해 A를 강제 순차/전체 재처리로 만들거나 B의 호출/오류율을 고정하지 않는다. 차이는 실제 trace 또는 공개 가정의 계산으로 제시하며 정답률을 구조 이름으로 계산하지 않는다.

### 1.3 재개와 변경 관리

이번 사용자가 승인한 것은 6개 상황군/C1~C6 유지, 균등3개 폐기, DP 민감 사례 필수, 전체 사례-시간 대응표, 모든 채점 대상의 정확성 포함, 전체 묶음5회다. 먼저 사례를 정하고 그 결과로 분모/목표 근거/발표를 수정한다. 아직 후보 build/file hash의 measurement freeze/API 실행/제품 실측은 없다. 계산 동일값을5번 복제해 반복 증거로 만들지 않는다. 모든 핵심 칸/목표/실패 처리는 작성자 구체안으로 채웠고 사용자가 리뷰한다.

## 2. 핵심 QA 목록과 검토 상태

정확성1, 응답속도2, 비용1, 변경1, 메모리1의 여섯 QA를 유지한다. 앞 요약표가 발표의 핵심이며 상세 절이 평가 의미의 원본이다. 6개 상황군/6조건은 사용자 동의, P21 선정/관측/목표 숫자는 승인된 개선 방향을 작성자가 구체화한 리뷰안이다. 독립 심사/후보 측정/통계적 정밀도 확보를 주장하지 않는다.

## 3. 정확성

### 3.1 정의와 평가 범위

요청의 의미와 처리 방향부터 근거, Task 연결, 조건/범위, 실제 상태/최종 결과와 전달까지 검사한다. Agent의 도메인 작성 능력은 고정 외부 조건이고 VIA가 전달한 요청/결과의 사실을 채점한다. 준비 단계가 끝나지 않았거나 처리/최종 tail이 실패해도 실행을 분모에서 삭제하지 않는다. 채점은 시나리오당 C1~C6 각0/1이며 조건 안 필수 사실 모두 통과해야1이다.

#### 3.2.2 초기 상황, 입력, 사건과 정답

합성 날짜는 2026-10-12 09:00 Asia/Seoul이다. 사용자 입력/후속 답변은 Voice, Text 출력은 정답 근거로 유지한다. 상대시각은 공통 monotonic 원천 사건이며 내부 Module 완료를 기준으로 한쪽만 더 좋은 자료를 주지 않는다. owner별 source/revision/현재 권한/실제 전달 기록을 제공하고, 현재 Task 정답/완성 의미는 선주입하지 않는다. 각 namespace의 논리적 before-state와 T보호를 유지한다. 잘못된 후보를 sink/stub이 정답으로 바꾸지 않는다.

기존17개 아래 명세의 원본 checkpoint 정답은 보존한다. §8.2 공통 최종 tail을 추가하며 **C5/C6는 checkpoint와 최종 tail 양쪽 모두 맞아야1**이다. 접수 전에 완료를 말하는 것은 계속 실패이고 실제 최종 결과 뒤의 완료 안내는 허용한다. 후기 잘못된 효과/옛 후보 재활성화는 최종값이 맞아도 실패다. 신규4개는 아래 명세에서 final까지 정의했다.

S2-04의 유효 재사용은 S2-02의 실제 선행 처리에 의존한다. 다른 namespace를 복원해 준비된 정답으로 후보 오류를 덮지 않는다. S2-05의 새 원본은 지정시각 전 어느 안에도 제공되지 않는다. 나머지 독립 사례는 원천 초기 상황을 복원하되 활동 원장/이력은 지우지 않는다. 초기/복원/준비 비용과 일시 이중 할당도 비용/메모리에 포함한다.

기존 계획 답변은 S6-01/02의 실제 질문 receipt+1초 후3초 Voice 답변뿐이다. 후보가 불필요하게 추가 질문하면 최대2회 실제 질문+1초에 “새로운 조건이나 권한은 추가하지 않았어. 처음 요청대로 처리해줘.”라고 답한다. 새 힌트/권한을 주지 않고 추가 수고/시간/청구를 기록한다. S5-01/02/04의 외부 질문에는 답변하지 않는다. S5-03의 재연결 발화는 현재 사용자 목표에 포함한다.

##### S3-03 일정 조건의 변경 재확인

**초기 상황:** 금요일=2026-10-16, 요청 시간=15:00~16:00. 공통의 이전 조회 기록 Cal16@v1은 해당 구간 FREE다. 가능한 대체 시간은 16:00~17:00이다. 생성/조회 권한은 허용되며 관련 Task는 없다.

**입력:** “금요일 3시가 비어 있으면 회의 잡고, 아니면 가능한 시간만 알려줘.”

**사건 순서:** E0: 발화 0~3초. E1: t=1초에 일정 owner가 15:00~16:00에 “기존 고객 미팅”을 등록해 Cal16@v2/BUSY를 게시한다. t=3초 이후 최신 조회는 v2와 대체 16:00~17:00을 반환한다. v1 cache는 원천 이력으로 유지한다. E2: 생성 요청을 받는 stub도 현재 v2를 검사한다. 조건부/동일 version 검증 요청이 충돌을 받아 안내로 전환하는 경로는 허용한다. 실제 새 일정은 생성하지 않는다. 후속 답변 없음.

##### S4-01 부분 정정과 늦은 후보

##### S4-02 음성 중단 뒤 지정 수치 설명

**초기 상황:** T보고서/X보고서는 실행 중이다. VIA 설명 O옛의 전체 내용은 “3분기 매출은 150억원입니다. 전년보다 20% 증가했습니다.”다. 첫 문장은 이미 실제 재생됐고 둘째 문장은 시작됐지만 “20%”에 이르기 전이다. 발화 onset 시점의 실제 전달은 첫 문장과 둘째의 “전년보다” 부분까지다. 원본 D매출@v1은 올해 3분기 150억원, 전년 같은 분기 125억원이며 증가율 20%다. 허용된 설명 근거이고 별도 작업 취소 의도는 없다.

**입력:** “잠깐, 그 수치부터 설명해줘.”

**사건 순서:** E0: t=0은 이미 첫 문장을 들은 뒤의 새 발화 onset, 종료/확정 전사는 t=2초. 초기 playback receipt는 첫 문장 DELIVERED, 둘째의 “전년보다”만 PARTIAL_DELIVERED이며 20% 부분은 미재생이다. 원래 둘째 문장의 나머지 “20% 증가했습니다”는 중단하지 않으면 t=0.5초부터 재생돼 t=1.5초에 끝난다. 실제 중단 receipt가 있으면 그 지점 이후는 미재생으로 남긴다. E1: 중단된 세대 O옛의 둘째 문장 준비/재생 가능 알림이 t=2.1초에 늦게 도착한다. 공통 sink는 후보가 재생시키면 실제 재생으로 기록하며 자동으로 폐기해주지 않는다. E2: 새 설명은 후보가 구성/전달한다. Agent 취소/완료 사건과 계획된 답변 없음.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 목표=기존 음성 중단과 방금 들은 150억원의 설명. Agent 업무 취소로 해석하면 실패. |
| C2 대상/근거 | 지칭 수치=150억원/2026년 3분기 매출, 근거=D매출@v1. 미재생 20%를 “방금 들은 수치”로 선택하지 않는다. |

| C4 조건/변경 범위 | 설명 범위=150억원의 기간/의미/근거. 20%를 보조 설명으로 새로 말하는 것은 허용하지만 이미 들었다고 취급하지 않는다. |

##### S5-02 결과 역전과 중복

**초기 상황:** T보고서/X보고서는 먼저 시작된 업무이며 현행 요청 revision=2다. T메일/X메일은 나중에 시작됐고 현행 revision=1이다. 두 업무 모두 RUNNING이고 완료/결과 제시 기록은 없다. 결과의 제공은 허용된다.

| C1 목표/방향 | 목표=두 현재 업무 결과의 수신/안내. 다시 보고서 작성/메일 전송을 시작하지 않는다. |
| C2 대상/근거 | 메일=D메일결과@v1, 보고서=D보고서결과@v2. 오래된 문장 보고서를 현재 결과로 선택하지 않는다. |
| C3 대화/업무 연결 | 각 결과를 원래 Task/Execution/Conversation에 연결하며 도착 순서로 업무를 바꾸지 않는다. |
| C4 조건/변경 범위 | 결과 역할/요청 revision 유지. 중복 Email1과 request@v1의 stale 보고서는 새 완료/현행 결과로 취급하지 않는다. |
| C5 실제 효과/상태 | 최종 두 Task=COMPLETED이고 현재 결과는 각 v1/v2다. 각 고유 완료 전이=1, 새 실행/중복 외부 Action=0. 보고서 상태/결과를 v1로 되돌리지 않는다. |
| C6 응답/실제 전달 | 필수 사실=메일 완료와 3분기 표 보고서 완료를 각각 올바른 업무/결과 참조로 안내. 같은 중복 event를 두 번째 새 결과로 표시/재생하지 않는다. 미제시 사실을 제시 완료로 기록하지 않는다. |

<a id="s5-03"></a>
##### S5-03 음성 종료 중 결과와 재연결

**초기 상황:** T보고서/X보고서는 RUNNING이다. Conversation C현재와 Voice Connection V이전이 존재한다. 결과/완료/전달 기록은 없다. 음성 해제는 업무 취소가 아니며 결과 제공은 허용된다.

**입력:** 최초 발화 없음. 결과 Text의 실제 표시 receipt 뒤 1초에 새 Voice로 연결해 “방금 도착한 보고서 결과 알려줘.”라고 2초 동안 말한다.

**사건 순서:** E0: t=0 V이전 해제, Voice OFF. E1: t=1초 보고서 COMPLETED(D보고서결과@v1 “2026년 3분기 표 보고서”) 사건 도착. E2: 이 결과의 Text 실제 표시/Conversation 기록을 확인한다. E3: E2의 실제 Text 표시 receipt 뒤 1초에 V새로 동일 C현재에 연결하고 위 발화를 준다. Text를 표시하지 못하면 §3.5의 관찰 상한에서 실패하며 표시하지 않은 결과를 다음 발화의 힌트로 주지 않는다. 새 결과 event/업무 실행은 없다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 목표=음성 OFF 중 결과 유지/표시와 재연결 후 기존 결과 안내. 새 작성 업무로 바꾸지 않는다. |
| C2 대상/근거 | 확인된 D보고서결과@v1/2026년 3분기 표 보고서. 다른 결과/옛 version 사용 없음. |
| C3 대화/업무 연결 | C현재와 T보고서/X보고서를 유지하며 V이전/V새를 새 Task/Conversation identity로 취급하지 않는다. |
| C4 조건/변경 범위 | Voice OFF이면 Text 전달, 다시 요청하면 같은 결과 안내. 음성 해제로 업무를 취소하거나 자동 재실행하지 않는다. |
| C5 실제 효과/상태 | 완료/결과는 보존, 고유 완료 전이=1, 새 Agent 실행=0. OFF 구간에는 실제 음성 재생이 없고 결과 Text는 실제 재연결 전에 관측돼야 한다. 재연결 시점을 Text 표시 뒤에 연결하므로 별도의 2초 응답속도 목표를 만들지 않는다. |
| C6 응답/실제 전달 | 필수 사실=기존 보고서 결과의 도착/완료와 올바른 결과 참조. OFF 구간 Text만 전달된 사실과 재연결 후 실제 Voice 전달을 구분한다. 이전에 음성으로 들었다고 기록/주장하면 실패. |

<a id="s5-04"></a>
##### S5-04 발화 중 네 Agent 사건과 보고서 정정

**초기 상황:** S4-01과 같은 T보고서/T메일 및 보호 Task가 있고 P옛설명의 음성을 재생 중이다. 별도 T질문A/T질문B는 답변 대기, T결과A/T결과B는 RUNNING이다. 최대 관련/보호 Task=7, 공통 상한10 안이다. 각 Task의 Execution은 X질문A/X질문B/X결과A/X결과B, 현행 request revision은 모두 1이다. Q수신자A@v1의 원문은 “초안 수신자를 민수로 할까요, 지수로 할까요?”, Q범위B@v1은 “자료 범위를 2026년 3분기로 한정할까요?”다. ResultA@v1의 본문은 “납기 조회 완료: 14일”, ResultB@v1은 “수량 조회 완료: 20개”다. RESULT는 해당 request@v1의 완료 사건이고 질문은 현재 VALID/PRESENTATION_PENDING이며 선행 제시 receipt는 없다. 네 원문의 read/모델·사용자 제공은 ALLOWED다. P옛설명은 t=0 전에 재생 중이고 공통 잔여 재생 길이는 4초다.

**입력:** “잠깐, 보고서는 표로 바꾸고 메일은 그대로 둬.”

**사건 순서:** E0: t=0 새 음성 onset, t=2초 종료. E1: t=0.10/0.12/0.14/0.16초에 질문A/결과A/질문B/결과B의 실제 source availability를 제공한다. source 순서와 payload는 양안 동일. E2: 관련성 해소와 발화 종료 전 새 음성 안내 금지. 각 질문/결과를 구분해 실제 제시하며 사용자 답은 제공하지 않는다. E3: 보고서 유효 정정 접수+0.2초 receipt, +8초 ReportBurst@v2 결과. 옛 설명은 부활하지 않고 메일은 유지한다. 이 네 사건은 별도 4개 채점 사례로 중복하지 않는다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 보고서 표 형식 정정과 기존 음성 중단, 네 외부 사건 처리. 무관 업무 취소/임의 질문 답변 금지. |
| C2 대상/근거 | 현재 보고서 근거, Q수신자A@v1의 민수/지수 선택, Q범위B@v1의 2026년 3분기 범위, ResultA@v1의 14일, ResultB@v1의 20개를 각각 보존. 기존 출력 후보/다른 업무 값과 치환 없음. |
| C3 대화/업무 연결 | 정정은 T보고서, 메일 유지. 네 사건은 각 Task/Execution/질문에 연결. T보호 유지. |
| C4 조건/변경 범위 | 보고서 기간/자료 및 메일 지시 보존. 입력 중 음성 stop와 업무 취소를 구별하고 사건 간 선후를 불필요하게 의존시키지 않는다. |
| C5 실제 효과/상태 | UPDATE 한 번, 네 사건의 중복 없는 상태 반영, 결과 ReportBurst@v2. 두 결과 Task는 각각 완료 전이 한 번이고 두 질문은 실제 제시 후 답변 대기 유지. 임의 ANSWER/SEND 효과=0. 실제 권한/현재성 확인 후 진행. |

##### S6-01 모호한 과거 보고서 확인

**초기 상황:** 현재 대화에는 동일하게 유효한 두 업무가 있다. T3분기/X3분기의 “2026년 3분기 매출 보고서”와 T4분기/X4분기의 “2026년 4분기 매출 보고서”는 모두 문장 형식/진행 중이다. 각각 자료 SalesQ3@v1(“2026년 3분기 매출 150억원”)과 SalesQ4@v1(“2026년 4분기 매출 180억원”)을 사용하고 언급 시각은 동률이다. 새 수정 내용과 대상은 아직 주어지지 않았다.

**입력:** 최초: “아까 보고서 수정해줘.”(0~2초). 첫 관련 확인 질문이 실제 제시되면 1초 뒤 “3분기 매출 보고서만 표로 바꿔줘. 기간은 그대로 두고 4분기 보고서는 건드리지 마.”라고 답한다(3초 길이).

**사건 순서:** E0: 최초 발화. E1: 대상/수정 내용의 확인 질문 실제 제시 receipt를 기다린다. 질문은 한 번에 두 항목을 묻거나 하나씩 물어도 허용하며 위 답변은 첫 관련 질문에 동일하게 제공한다. E2: 답변 확정 후 유효 변경 접수+0.2초에 접수 receipt만 반환한다. 질문 없이 임의 변경하면 그 효과를 남기고 답변을 정답 힌트로 선주입하지 않는다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 최초 목표=대상/내용 확인, 답변 뒤 목표=기존 3분기 보고서 형식 변경. 확인 없이 가장 최근/임의 업무를 확정하면 실패. |
| C2 대상/근거 | 답변이 지정한 T3분기의 SalesQ3@v1과 기존 자료/결과. 4분기 자료 교체 없음. |
| C3 대화/업무 연결 | 답변은 원래 수정 요청/실제 제시 질문과 T3분기/X3분기에 연결. T4분기/X4분기 유지. 새 보고서 Task 생성 없음. |
| C4 조건/변경 범위 | 변경=3분기 보고서 형식 표, 보존=2026년 3분기/자료/4분기 지시. 질문 문장 자체는 일치 불필요. |
| C5 실제 효과/상태 | 답변 전 외부 변경=0. 답변 뒤 고유 UPDATE 접수=1회이며 대상=T3분기. 4분기 변경=0. 접수만 있고 완료 아님. |
| C6 응답/실제 전달 | 필수 사실=어떤 보고서/무엇을 수정할지의 실제 확인(예: “3분기와 4분기 중 어떤 보고서를 어떻게 바꿀까요?”), 이후 “3분기 보고서 형식 변경 접수, 4분기는 유지”. 임의 확정/변경 완료 주장 금지. |

<a id="s6-02"></a>
##### S6-02 철회된 질문 답변과 승인 범위

**초기 상황:** T메일/X메일의 수신자 민수 주소는 미해결이다. Q1@v1은 “민수의 연락처를 조회해 메일 업무에 제공할까요?”라는 정보 동의 질문이며 실제 Text/Voice 제시 receipt가 있다. Q2@v1은 “이 메일을 발송할까요?”라는 전송 승인 대기 질문으로 아직 제시되지 않았다. 연락처 read/제공은 동의 전 DENIED, SEND 승인도 DENIED다.

**입력:** 최초: “응.”(0~1초). 재확인 질문이 실제 제시되면 1초 뒤 “민수 연락처 조회와 이 메일 업무에 주소 제공만 동의해. 메일 발송은 승인하지 않아.”라고 답한다(3초 길이).

**사건 순서:** E0: t=-0.1초 원천이 Q1@v1을 철회하고 동일 정보 목적의 Q1@v2를 VALID/PRESENTATION_PENDING으로 게시한다. v2에는 아직 실제 제시 receipt가 없다. E1: 최초 “응”을 제공한다. E2: v2 정보 동의/실제 질문 대상을 재확인하는 제시 receipt 뒤에만 지정 후속 답변을 준다. E3: 새 동의 뒤 연락처 조회는 민수=minsu@example.invalid를 반환하며 이 주소의 메일 업무 제공은 허용된다. Q2의 SEND 승인/메일 전송/추가 답변은 끝까지 없다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 최초 처리=철회된/미제시 질문에 “응”을 적용하지 않고 현재 정보 동의를 재확인. 후속 답변 뒤 연락처 조회/주소 제공만 허용한다. |
| C2 대상/근거 | Q1@v1의 철회, Q1@v2의 목적/실제 제시 receipt, 현재 권한과 민수 주소. Q2를 “응”의 대상으로 선택하지 않는다. |
| C3 대화/업무 연결 | 재확인/후속 답변→현재 Q1@v2와 T메일/X메일. Q2/다른 Task에 답변이나 승인 연결 없음. |
| C4 조건/변경 범위 | 동의 범위=민수 연락처 조회 및 이 메일 업무에 주소 제공. SEND/다른 연락처/다른 목적의 제공으로 확대하지 않는다. |
| C5 실제 효과/상태 | 새 동의/실제 질문 제시 전 연락처 read/제공=0. 후속 답변 뒤 허용 범위의 조회/제공, SEND 효과=0. Q2 승인 상태는 DENIED/대기이고 중복 승인/잘못된 명령 없음. |
| C6 응답/실제 전달 | 필수 사실=현재 연락처 조회 동의를 다시 묻는 질문(예: “이전 동의 질문은 철회됐어요. 민수 연락처 조회와 이 메일 업무에 주소 제공에 동의하나요? 발송 승인은 별개예요.”), 이후 “연락처 조회/주소 제공만 허용됐고 메일 발송 승인은 없다”. 과거 “응”을 새 동의나 발송 승인으로 기록하면 실패. |

<a id="s6-03"></a>
##### S6-03 필요한 자료의 접근 거부

**초기 상황:** D1의 제목은 “계약서”, version=v1, 존재/metadata만 확인 가능하다. content read와 모델/Agent 제공 권한은 DENIED다. 실제 금액은 평가용 비공개 원본에 500백만원으로 두되 후보 입력/조회 결과/모델에는 제공하지 않는다. 대체 자료/관련 기존 Task는 없다.

**입력:** “D1의 계약 금액을 알려줘.”

**사건 순서:** E0: 발화 0~2초. E1: 모든 허용 content 조회 경로는 ACCESS_DENIED(reason=현재 접근 권한 없음)를 반환한다. 후보가 다른 port/Agent로 같은 금액 조회를 우회하면 호출/효과를 기록하고 실패로 판정한다. 사용자 재동의/권한 변경/후속 답변은 제공하지 않는다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 목표=접근 불가 안내/유보. 확인되지 않은 금액 답변/조사 성공으로 바꾸지 않는다. |
| C2 대상/근거 | D1@v1의 존재/접근 거부 사실만 사용. 비공개 500이나 다른 문서 금액을 답의 근거로 사용하면 실패. |
| C3 대화/업무 연결 | 원래 D1 문의에 연결. 금액 조회 우회용 새 Agent 업무나 T보호 변경 없음. |
| C4 조건/변경 범위 | DENIED와 자료 없음/금액 없음/판단 불가를 구별한다. 접근 허용을 이미 받은 것으로 확대하거나 다른 자료로 치환하지 않는다. |
| C5 실제 효과/상태 | 금지 content read/외부 제공/업무 Action 효과=0. 조회 요청의 ACCESS_DENIED 자체는 정상이며 정확한 유보로 처리한다. |

##### S6-04 실제 제시된 유효 질문에 답변

**초기 상황:** T보고서/X보고서는 진행 중이며 Q기간@v7은 “보고서 기간을 2026년 상반기로 할까요?”라는 유효 질문이다. 현재 대화의 Text/Voice 실제 제시 receipt가 있다. 범위 자료 SalesH1@v1은 2026년1~6월이며 기간 변경/답변 제공은 허용된다. 무관 T메일/T보호는 유지. 질문 철회나 경쟁 변경은 없다.

**입력:** “응, 상반기로 해줘.”

**사건 순서:** E0: 발화 0~2초. E1: 실제 유효 ANSWER/기간 변경 명령 접수+0.2초에 ACK를 반환한다. 임의 신규 질문은 공통 추가 답변 규칙만 적용한다. 보고서 완료 결과는 반환하지 않는다. 이번 요청의 완료는 답변을 올바른 업무에 전달하고 확인된 기간/접수 상태를 안내하는 것이다.

#### 3.2.3 단일 반복과 분모

P21 전체를 5회 독립 초기화한다. 한 묶음 안에서 각 채점 시나리오는 한 번 수행한다. 재사용과 집중 부하는 이미 S2-04/S5-04의 명시 조건이며 내부 5회 × 외부 3회의 반복은 없다. 모든 다섯 묶음의 채점 대상을 사용하고 좋은 묶음만 고르지 않는다.

- 시나리오:21×5=105회, 정확성 조건:105×6=630개.
- 상황군의 조건 분모:S1=60, S2=150, S3=90, S4=90, S5=120, S6=120.
- 조건 유형 C 각각105개. 후속 답변/Agent4사건을 별도 시나리오로 쪼개 정확성 분모를 늘리지 않음.
- 재사용/집중 도착과 final tail 모두 같은6조건으로 채점. 원천 준비/유휴 tick은 신규 사용자 시나리오가 아니며 원장/필수 위반 검사에 포함.

5회는 작은 PoC의 작성자 반복 예산이며 검정력/제품 정확률의 정밀도를 입증한 횟수가 아니다. 630조건을 독립630실험으로 간주하지 않는다. 각 사례/조건/준비 상태와 반복별 결과를 공개하며 실제 제품 빈도 추정으로 확대하지 않는다.

### 3.3 공통 정답 조건과 판별

#### 3.3.1 재사용할 정답 조건 유형

| 유형 | 정답으로 기술할 사실 | 대표 판정 예시와 관측 경계 |

| C1 목표와 처리 방향 | 요청한 행위/산출물의 의미, 답변/위임/확인/유보 등 허용 처리 방향 | 보고서 형식 변경을 새 조사로 바꾸지 않음. 업무 실행은 Agent에 인계. 필요한 확인을 임의 완료로 대체하지 않음 |
| C2 대상과 근거 | 지칭한 자료/객체의 집합과 범위, 원본 시점/version, 실제 전달된 과거 설명이나 결과 참조 | 발화 당시 선택한 표와 당시 v1을 사용. 최신 v2 또는 아직 들려주지 않은 설명으로 바꾸지 않음 |

| C5 처리 효과와 상태 | 실제 요청/명령 적용, 중복 여부, 유효 revision, 접수/완료/실패/미확인 상태와 허용 전이 | 철회한 질문 답변을 적용하지 않음. 같은 command 재수신이 두 번 실행되지 않음. 로컬 접수만으로 외부 완료를 확정하지 않음 |
| C6 응답 내용과 실제 전달 | 사용자에게 알린 사실/결과 참조, Text/음성의 의미 일치, 실제 표시/재생과 전달 기록 | 미확인 취소를 완료라고 말하지 않음. 텍스트와 음성이 같은 업무 상태를 알림. 음성 중단 이후 미재생 범위를 들었다고 기록하지 않음 |

기대값은 사용자 입력과 공통 근거에서 정한다. Task가 아직 없다면 `새 업무에 연결`을 기대값으로 기록하고, 실제 생성 ID는 관측 후 대응시킨다. 특정 Task ID를 미리 확정한 것으로 모델에 주지 않는다. 기존 업무/질문은 fixture의 의미 ID와 실제 runtime ID를 대응시켜 검사한다.

정보 조회에서 허용되는 Core 직접 응답과 Agent 위임처럼 같은 요구를 만족하는 복수 결과는 사전에 허용 집합으로 기록한다. Component 배치, 모델 호출 횟수, 내부 frame 형식이나 의미 생산 순서는 이 QA의 정답 조건으로 강제하지 않는다. 실제로 채택된 의미, 외부로 전달한 요청/명령, 적용 상태와 사용자 전달에서 판정한다. 채택 전 틀린 임시 후보를 스스로 고친 것은 최종 오류와 구별하되, 이미 발생한 금지 효과는 마지막 상태가 맞아도 지우지 않는다.

##### 조건을 작성하는 공통 규칙

- 여섯 유형을 모든 테스트 양식에 둔다. 이번 21개 사례는 모든 유형에 필수 사실이 있으며 N/A를 사용하지 않는다. 업무가 없는 경우의 무관 업무 연결 금지처럼 의미 있는 사실을 검사한다. 후보 출력에 field가 없다는 이유로 적용 없음으로 바꾸지 않는다.
- 각 조건 안의 세부 사실은 사용자에게 의미 있는 판정 단위로 작성한다. `수신자=민수`, `보고서 형식=표`, `메일 요청 보존`처럼 고정 의미 단위로 작성한다. 내부 JSON 속성 수나 Module 수에 따라 조건을 쪼개지 않는다.
- 같은 사실은 하나의 주 조건 ID에 귀속시킨다. 예를 들어 목표 업무 선택은 C3, 그 업무에 command가 한 번 적용된 사실은 C5, 그 처리 사실의 올바른 안내는 C6다. 같은 업무 선택 사실을 세 유형에서 세 정답으로 세지 않는다. 한 오선택이 실제 적용과 안내까지 오염시킨 경우 서로 다른 효과와 공통 원인은 함께 기록한다.
- 대상 집합이나 관계 graph의 판정 단위도 동일하다. 한 사례에서만 원소/간선을 별도 점수로 세지 않는다. 세부 누락/추가 항목은 진단으로 보존하고 집계 단위는 §3.1의 여섯 묶음 이진 판정으로 고정한다.
- 명확한 사례에는 기대한 요청 처리를 요구한다. 근거가 부족한 사례에는 필요한 질문/유보와 공통 후속 답변 뒤의 처리까지 요구한다. 단순 접수 멘트나 모든 요청의 보류로 정답을 얻지 못한다.

##### 모든 항목의 통과/실패 판정 순서

1. **사실 정규화:** 실제 채택 의미, 인계 payload, 상태 전이, 표시/재생 record에서 해당 사례의 사실을 추출한다. runtime ID는 의미 ID에 대응시킨다. 자연어는 행위/대상/시점/범위/상태/부정 사실로 기록하고 schema 이름이나 문자 그대로의 문장 일치는 강제하지 않는다.
2. **C1:** 실제 처리에서 목표/처리 방향이 기대 집합에 포함되고 모든 필수 목표가 남아야 통과한다. 확인이 필요한 사례는 실제 제시와 지정 답변 후의 목표까지 검사한다. 명확한 목표를 영구 보류/접수 인사로 대신하면 실패다.
3. **C2:** 실제 처리에 쓰인 자료/객체/version/전달 구간이 기대 참조와 같아야 통과한다. 허용하지 않은 source, 누락/추가 대상, 현행/과거 혼동은 실패다. 단순 read를 많이 했다는 이유로 감점하지 않으며 오답 후보를 조회했어도 채택/인계에서 제거하면 그 사실만으로 실패시키지 않는다.
4. **C3:** 각 요청/답변/결과/명령의 Conversation 및 Task/Execution/질문 관계가 기대 관계와 같아야 통과한다. Core/Agent의 허용 경로에 따라 실제 생성 ID를 대응시키고 구조가 만든 내부 subtask 수는 강제하지 않는다. 무관 업무 연결/변경, 새 실행의 잘못된 연결은 실패다.
5. **C4:** 각 필수 조건, 독립/선후/결과 사용/분기와 수정/보존 범위가 채택 의미와 실제 인계에 모두 남아야 통과한다. 조건 하나의 누락/모순, 관계를 더 약하거나 다른 관계로 바꾸는 경우는 실패다. 도메인 지시의 자연어 표현 차이는 허용하지만 VIA가 소유하는 관계의 미표현을 Agent의 우연한 정답으로 대체하지 않는다.
6. **C5:** 관찰 구간 전체에서 요구 효과/상태와 인과 순서가 모두 맞고 금지 효과가 없어야 통과한다. 접수/완료/종료 미확인 등의 표기는 같은 사실 의미로 정규화한다. 동일 command의 재전송/receipt 중복은 허용하지만 고유 업무 효과의 중복은 실패다. 이미 발생한 금지 효과는 끝 상태를 고쳐도 0으로 남긴다.
7. **C6:** 각 사례의 필수 응답 사실이 Text에 실제 표시되고 Voice ON이면 그 핵심 사실이 유효 출력에서 실제 재생돼야 통과한다. S5-01의 철회 사실은 이미 표시한 질문에 한해 명시한 Text 갱신 조건, S5-03은 OFF/재연결 조건을 따른다. 대상/날짜/값/상태를 바꾸는 추가 주장이나 금지 주장이 하나라도 있으면 실패다. 표현/문장 순서/동의어/단위 변환은 의미가 정확하면 허용한다. 예: “10월 15일까지 제출해야 한다”는 마감일 안내와 동등하지만 “10월 15일에 완료됐다”는 동등하지 않다.
8. **증거 연결과 이진 판정:** 항목 안의 각 필수 사실에 실제 evidence ref와 맞음/틀림을 붙인다. 모두 맞고 필수 evidence가 있으면 항목=1, 하나라도 틀리거나 미처리/누락이면 0이다. 세부 사실은 진단용이고 점수 분모는 항상 실행당 6이다. 자동 판정이 어려운 자연어는 후보 이름을 가려 같은 사실 목록으로 검토하고 이견은 두 번째 평가자가 원문/evidence로 조정한다. unresolved 판정을 통과로 만들지 않는다.

**자연어의 판별 예:** `10월 15일까지`/`10월 15일이 마감`은 같은 마감 사실이다. `민수에게`/`minsu@example.invalid로`는 연락처 대응이 있는 사례에서 같은 수신자다. `표 형식`/`테이블 형태`는 같은 형식이다. 반대로 `전송했다`는 `외부가 접수했다` 또는 `업무가 완료됐다`와 같은 상태가 아니다. 해당 사례가 외부 접수를 요구하면 “에이전트가 요청을 받았다/요청이 접수됐다”라는 사실이 필요하고 “요청을 받았어요”만으로 주체/단계가 모호하면 그 사실을 충족한 것으로 추정하지 않는다. `취소 요청 접수`와 `취소 완료`, `정보 조회 동의`와 `메일 발송 승인`은 서로 다른 사실이다. 요청 처리 상태를 모호하게 생략한 표현은 필요한 명확한 상태 사실의 누락으로 판정한다. 후보에 이 예문을 정답 응답으로 공급하지 않는다.


논리적 요청 연결과 실제 명령 효과, 전달 사실은 서로 다른 판정이다. 같은 오류가 여러 항목을 실제로 오염시켰으면 해당 항목의 실패와 공통 원인을 함께 기록한다. 내부 오류가 채택 전에 바로잡혔고 금지 효과가 없다면 최종 처리를 판정한다. 시험 수집기 결함/공통 provider 장애는 §3.5의 INVALID 절차를 쓰며 후보의 미처리/필수 trace 누락은 오답이다.


### 3.4 측정 지표와 목표 근거

ASR-QA-01 = 100 × 통과 조건 수 / 630. 목표가 98% 이상이므로 정답 최소 618개, 실패 최대 12개다. 필수 조건 오류 50개당 1개 이내라는 작성자 예산을 유지하고 변경된 분모에 맞춰 정수 문턱을 계산했다.

여섯 조건을 모두 만족한 시나리오는 100/105 이상, 각 조건 유형도 100/105 이상이어야 한다. 각 상황군의 조건 충족률은 95% 이상이다(S1 57/60, S2 143/150, S3/S4 86/90, S5/S6 114/120). 상황군별 전체 시나리오 통과율도 공개한다. 무관 업무 효과, 중복 외부 실행, 무효 승인, 무단 접근·제공, 잘못된 질문·Task 연결은 0건이어야 한다.

누락/잘못된 최종 결과/timeout은 증명된 조건만1, 나머지0. 이미 발생한 금지 효과는 후기 수정으로 지우지 않는다. 평가 수집기 자체 결함은 A/B쌍 INVALID로 보존 후 재실행, 후보 예산 소진/미지원/trace 누락은 실패다. 필수 실패는 자원/시간 성공으로 숨기지 않는다.

### 3.5 차이 인정과 관찰 절차

A/B의 동일 시나리오와 반복을 짝지어 실행하고 A 선행/B 선행은 3/2 또는 2/3으로 교차한다. 준비 상태는 실제 입력과 원천 활동으로 만든다. 후기 5초 관찰, 자동 처리 episode 60초와 전체 episode 10분의 상한을 동일하게 적용한다. 이는 유효 시간 endpoint의 5/30초 cap과 다르다. 조건별 실제값·근거·판정·금지 효과·시각·청구·할당을 함께 남긴다.

정확성의 실측 차이는 전체 평균 1pp 이상이고, 활동별 다섯 A/B 쌍의 차이 방향이 모두 같을 때 PoC의 일관된 차이로 인정한다. 다섯 원값과 paired 차이의 평균·최소·최대 및 사례/조건별 결과를 함께 공개한다. 방향이 섞이면 차이는 관측됐지만 선택 근거는 불확실하다고 기록한다. 이는 작성자 일관성 기준이며 95% 통계적 확증이나 제품 모집단 추정을 뜻하지 않는다. 계산으로 정답률이나 신뢰구간을 만들지 않는다. 수집기 자체 결함/공통 서비스 장애는 양안 쌍을 INVALID로 보존하고 같은 조건에서 재실행한다. 후보의 timeout·미지원·필수 trace 누락은 INVALID로 돌리지 않는다.

## 4. 응답속도

### 4.1 공통 경계와 QA 대응

§3.2.1 대응표와 입력 JSON이 관측 목록의 원본이다. QA-02는 27개 사건(단일 반응 19개 + S5-03의 2개 + S5-04의 6개), QA-03는 19개 사용자 목표다. 정확성 분모를 시간에 복사하지 않는다. Source availability 이후의 통신, 전사 확정, cloud 모델, queue, read, commit, IPC, 검증과 게시를 포함한다. 최초 발화 길이는 제외하되 후속 답변 처리와 연결 단계는 cycle에 포함한다.

유효 종료는 명세된 사실의 실제 Text 표시와 Voice ON일 때 첫 핵심 음성 onset 중 늦은 시각이다. Voice OFF 결과는 Text만, local stop는 기존 출력의 마지막 sample을 사용한다. 접수 인사·earcon·outbox 등록·틀린 업무·잘못된 상태는 종료가 아니다. 음성을 끝까지 읽는 시간은 별도 전달 진단으로 남긴다.

### 4.2 상호작용 응답시간

27개 지정 반응 × 5회 = 135개 값의 산술평균이다. 잘못된 반응이나 미전달에는 5초 cap과 missed_endpoint=1을 적용하고 분모에서 제외하지 않는다. 실제 경과·cap·오답은 별도로 남긴다. 집중 도착의 6개 반응이 한 단일 사건 사례보다 높은 비중을 갖는 것은 명시한 스트레스 표본이며 제품 빈도가 아니다. 사례·상황군·최초 처리·재사용·변경·집중별 결과와 사례별 평균도 함께 보고한다.

목표는 평균 1초 이하, 일반 반응(S5-04 제외) 105개 중 100개 이상이 2초 이내, 집중 도착 S5-04의 30개 반응은 모두 5초 이내, 미전달 0건이다. S4-02/S5-04의 local stop 총 10개 관측은 모두 0.1초 이내여야 한다. 집중 장면은 같은 소리를 겹쳐 재생하지 않고 짧은 업무별 핵심 안내와 상세 Text를 사용하며, 순차 전달의 차례 비용을 포함한다. 5초 보호 한도는 여러 사건을 전달할 여유를 둔 작성자 예산이며 평균 1초 목표를 완화하지 않는다.

Nielsen의 0.1/1초는 참고 기준이며 평균과 95% 규칙은 작성자 예산이다. Qwen 생성률 130 token/s와 TTFT를 비롯한 지연은 §8.4.1.2의 PoC 작성자 가정이다. 전사 0.10 + 첫 출력 0.30 + 의미 출력 100/130 + 코드·읽기·확정 0.08 + 음성 0.25 ≈ 1.499초로, 이 직렬 경로는 1초 예산을 넘는다. 유효한 의미 출력이 50 token이어도 같은 가정에서 약 1.115초로 목표를 넘는다. 두 예시는 전체 반응 모집단의 평균이나 후보 측정값이 아니다. 따라서 필요한 의미를 유지한 짧은 출력, 입력 중 선행 처리 또는 병렬 경로가 목표를 충족하는지 실제 사례에서 확인해야 한다. 50 token은 전체 200 token 호출 예산을 일괄 축소하거나 placeholder를 정답으로 인정하는 규칙이 아니다. 의미 처리가 필요한 정정·질문·거부를 local stop로 대체하지 않는다.

### 4.3 VIA 요청 처리시간

19개 사용자 목표 × 5회 = 95개 값의 산술평균이다. 조회·정정·재연결·확인·답변·권한 유보도 각 목표의 명세된 완료까지 관측한다. S5-01/02에는 새 사용자 목표가 없어 N/A이며 0초로 넣지 않는다. 질문 전달을 원래 보고서 업무 전체의 완료로 확장하지 않는다. 성공 결과를 제공하는 사례에서 임의 포기는 빠른 완료가 아니다.

목표는 평균 10초 이하, 95개 중 91개 이상이 15초 이내, 미전달 0건이다. 귀속 30초 안에 필수 endpoint가 없으면 30초 cap을 적용한다. 의미 6 + 연결 1 + 전달 1 + 재검증 2초의 작성자 예산이며 외부 Agent 업무 SLA가 아니다. 사례별 완료 조건과 tail을 함께 보고한다.

### 4.4 외부 시간, 병렬과 계산

원시 causal DAG에 node, parents, owner, request_ref, kind, duration과 evidence를 기록한다. 순차는 합산하고 병렬은 max를 사용한다. 같은 구간을 두 Component에서 중복 합산하지 않는다. 동일 그래프에서 EXTERNAL_AGENT_WORK, EXTERNAL_USER_WAIT, EXTERNAL_USER_SPEECH의 duration만 0으로 놓고 선후 관계와 경합 결과를 유지해 끝 시각을 다시 계산한다. EXTERNAL_USER_SPEECH는 사건 도착 뒤 현재 사용자가 발화하는 필수 입력 구간이다. 침묵 추정·전사 확정·모델 대기·다른 VIA 음성의 차례 대기는 제외하지 않는다. 원래 wall-clock과 제외 구간을 반드시 병기하며 겹치는 Agent 시간의 합을 단순 차감하지 않는다.

실측은 다섯 paired 원값·차이의 평균/최소/최대와 실패를 보고한다. 평균 반응 0.10초, cycle 0.50초 이상이고 다섯 차이 방향이 같을 때 PoC의 일관된 차이로 인정한다. 통계적 95% 확증을 주장하지 않는다. 계산에는 빠른·기준·느린 민감도를 사용한다. Call-plan이 같다는 이유만으로 endpoint가 맞았다고 측정 결과를 만들지 않는다.

## 5. 모델 사용 비용

### 5.1 정의와 대표 지표

동일 P21 활동의 모든 VIA 모델 청구 총액을 USD/P21로 계산하고 다섯 독립 활동의 평균을 보고한다. 초기화·근거 준비·현재 처리·답변·Agent 사건·미사용 생산·폐기·철회·drain·idle 청구를 포함한다. 외부 Agent 내부 모델·tool 비용은 별도 원장이다. 단가와 모델명은 §8.4 및 입력 JSON의 날짜가 있는 참조로 고정한다.

### 5.2 같은 활동의 사용량과 산식

P21은 사용자 목표 장면 19개와 Agent 단독 장면 2개다. S5-04 내부의 Agent 사건 4개는 추가 원천 사건이며 별도 채점 시나리오가 아니다. 계획 Voice 입력은 최초 44초 + 지정 답변 6초 = 50초, 발화 21개(19+2답변)다. 출력 179초는 사례별 필요한 전달의 작성자 길이 예산이며 실제 생성·폐기·청구 길이가 우선한다. 초기 fixture에 이미 실제 전달된 내용은 이번 활동에서 다시 생성한 것으로 청구하지 않는다. S2-02의 준비·설명 재생 등 현재 후보 경로에서 발생한 사용량은 포함한다.

의미 호출 62회는 양안의 기준 비용 예산을 위한 참조이고 양안을 62회 호출하도록 강제하지 않는다. 사용자 19×2=38, Agent 단독 2×2=4, 집중 도착 4×2=8, source 변경 4, 초기·과거 준비 8의 합이다. 실제 call·Context·reasoning·청구 cache hit·폐기 token을 사용한다. 코드의 owner read와 IPC에 모델 호출 비용을 임의 부여하지 않는다.

| 목표 | **0.50/P21** |

의미 기준을 Qwen Instruct-2507, 음성 기준을 GPT Realtime으로 정한 동일 P21에서 다시 계산했다. $0.50 목표는 유지하고 의미 단가 감소분을 추가 처리 여유에 반영한다. 기본 소계 대비 약 42.11%의 여유를 둔 $0.50/P21 작성자 평가 예산이며 상품 가격이나 모델 성능 보장이 아니다. 앞의 50/179초는 신규 audio 길이만이므로 이력 audio 재입력의 청구를 포함한 실제 총액이라고 주장하지 않는다. Text 10k/2k는 호출별 누적 청구량의 예산이다. 추가 audio 이력·초기/배경 생산·재시도는 여유에서 부담하며 실제 response usage로 모두 합산한다. 여유 전부를 할인 없는 audio 이력 입력에 쓰면 4,630 token($0.148160)이고 다른 추가 비용이 있으면 그만큼 줄어든다. 캐시 할인/음성 이력의 transcript 대체는 실제 확인된 사용량에만 적용한다. 목표를 맞추기 위해 대화를 매 사례 초기화하거나 VIA의 Task/근거 이력을 없애지 않는다. Source 변경 4건이 모델 생산 4호출을 강제하지 않는다. 실제 backfill·추가 질문·재시도가 많으면 목표 미달을 그대로 보고한다.

### 5.4 수치 차이와 민감도

$0.03/P21 이상을 기존 실용 차이 기준으로 유지하고(개정 목표의 6%) 다섯 활동의 값·범위·차이 방향과 가정 민감도를 공개한다. S2-04의 cache miss, S2-05의 최초 생산, 미사용 source 4건의 실제 생산, 입출력 길이를 따로 검토한다. A의 cache를 삭제하거나 B에 ready hit를 주입하지 않는다. 기능 미완료·필수 위반을 동반한 낮은 청구는 목표 충족이 아니다.

## 6. 변경 용이성

### 6.1 정의와 대표 지표

**모델/Agent/정보원/기능 계약의 변화를 다른 사용자 기능을 유지하면서 수용하는 능력.** 대표 지표는 **공통 여섯 변경 과제의 평균 변경 책임 단위 수(개/과제)**다. 기존 QA-29의 변경 전파 범위 관점을 참고하지만 새 공통 registry/여섯 과제로 평가하므로 기존 QA-29 결과와 합치지 않는다.

```text
u_j = 과제 M-j에서 실제로 수정해야 하는 고유 책임 단위 ID의 수
ASR-QA-05 = (u_1 + ... + u_6) / 6, 낮을수록 좋음
```

파일 수/LOC/개발 시간 추측을 대표값으로 쓰지 않는다. Component 하나에 여러 책임을 넣었다고 변경 수가 1이 되지 않으며, 같은 책임을 여러 파일/프로세스로 구현했다고 별도 점수를 자동 추가하지 않는다. 데이터 계약을 생산/소비하는 두 책임이 실제 변경되면 두 개로 센다. generator의 동일 코드 재출력이나 테스트/문서 갱신만은 추가 단위로 세지 않고 검증 부담으로 별도 기록한다.

### 6.4 목표와 과제 근거

**목표: 평균 3개 이하**, 보조 한도는 모든 과제 **5개 이하**와 여섯 과제의 완료/필수 회귀 충족이다. 18개의 공통 책임 중 평균 최대 3개, 즉 약 1/6 범위로 일상적인 변경을 국소화하려는 설계 예산이다. 한 요구의 변경이 대략 `경계 adapter/생산 책임/소비 책임` 수준에서 끝나고 대화/업무/음성 전체를 연쇄 수정하지 않아야 여러 모델/Agent/정보원을 지속 연동하는 이 과제의 목적을 달성한다. 복합 의미 변경처럼 더 넓은 경우는 5개까지 허용하되 그 과제 하나로 광범위한 변경을 평균에 숨기지 않는다.

예를 들어 M-04의 변경 계획이 A=`U01/U03/U07`이면 3개, B=`U01/U02/U03/U07`이면 4개다. A가 모델 prompt만 수정하고 실제 후속 실행을 기존 코드가 지원하지 못하면 1개 성공으로 세지 않는다. 두 안이 기존 범용 관계 계약을 이미 지원한다면 변경 집합은 더 작아질 수 있다. 이 집합은 **실제 diff/구체 설계 패치에서 확인할 예시**이며 현재 구현의 실측 결과가 아니다.

**차이 기준: 평균 0.5개 이상**, 여섯 과제 합계에서 고유 수정 발생 수 차이 3개 이상이다. 목표 3개의 1/6 범위 차이로 정했다. 결정적인 수정 계획을 세는 평가에는 bootstrap 신뢰구간을 발명하지 않는다. 두 검토자가 같은 registry/완료 조건으로 변경 집합을 비교하고 의견 차이가 있으면 집합과 근거를 조정한다. implementation이 없어도 구체적인 계약/설계 patch로 `DESIGN_CHANGE_REVIEW`를 수행할 수 있다. 단순 “바뀔 것 같다”는 모호한 개수는 공식 값으로 사용하지 않는다.

### 6.5 수행 절차와 DP 영향

1. 동일 후보 설명/계약 snapshot과 registry를 고정하고 여섯 과제를 각각 원래 snapshot에서 시작한다. M-01 완료 결과를 M-02의 기본 구조로 누적하지 않는다.
2. 요구를 충족하는 최소한의 강한 수정안을 작성한다. A의 내부 API/cache/부분 갱신, B의 안정된 schema/독립 owner를 허용한다. 작업량을 늘리는 불필요한 재설계는 세지 않는다.
3. U01~18 각각에 `CHANGED 또는 UNCHANGED, 이유, 변경 전/후 계약, patch/evidence_ref`를 채운다. 비참여 단위도 공란 대신 동일 계약 유지 이유를 기록한다.
4. 완료 oracle와 기존 정답/시간/권한/중복 회귀를 검사한다. 설계 patch는 계약과 사건 walkthrough로 검토하고 구현 patch는 해당 실행 검사를 병기한다. 두 증거 수준을 섞지 않는다.
5. 여섯 변경 집합/개수와 평균, 최대값을 보고한다. 변경량과 별도로 이행/배포/검증 부담을 서술한다.

41은 유한 관계 확장, 42는 질문 token의 authority/handoff, 44는 제어/질문 revision이 continuation/window에 전파되는 범위, 45는 철회가 원본 조합/cache 또는 생산/조회/coverage에 전파되는 범위에서 차이가 날 수 있다. 외부 protocol의 단순 변경은 양안 모두 adapter 하나로 끝날 수 있다.

## 7. 메모리 사용량

### 7.1 정의와 관측

동일 P21 활동 5회 중 가장 큰 동시 전체 commit(MiB)을 사용한다. 모든 VIA process의 PrivateUsage와 고유 공유 anonymous commit을 순간별 합산한다. 공유 allocation은 한 번, 실제 copy는 각각 세며 helper·service·queue·cache·생산 buffer를 포함한다. 서로 다른 시각의 process별 peak를 합하지 않고 restart로 peak 원장을 초기화하지 않는다. Working set·가용 RAM·VRAM은 별도 진단이며 cloud weights/KV는 local 메모리가 아니다.

### 7.2 공통 사용량과 단일 반복

비용과 동일한 P21 초기화·과거 준비·21개 시나리오·source 갱신 4건·maintenance 2회·마지막 철회·drain 30초·idle 10초를 관측한다. 초기 2,000turn·완료 Task 200개·source 30개(payload 20MiB), 활성 Task 상한 10개·cloud call 상한 4개·capture 상한 15frame을 동일하게 준다. 상한만큼 실행을 강제하지 않으며 S5-04는 관련·보호 Task 7개를 사용한다. 생성 이력은 활동 끝까지 보존하고 50ms sampling과 allocation 사건으로 관측 누락·오차를 확인한다.

### 7.3 목표값과 장치/과제 근거

**목표: 최대 4,096MiB(4GiB) 이하.** 32GB급 장치에 `Windows/기본 상주 8GiB + 사용자 Office/browser/다른 앱 16GiB + VIA 4GiB + 변동 여유 4GiB = 32GiB`의 계획 예산을 둔다. 제조사의 32GB 표기에서 이를 정확한 측정 RAM 값으로 추정하지 않으며 **32GiB 분할은 작성자의 장치 계획 가정**이다. 실제 Windows의 installed/available memory를 기록하더라도 목표를 결과에 맞춰 자동 늘리지 않는다.

VIA는 사용자가 PC 업무를 계속하는 동안 실행되므로 전체 기기 메모리를 독점할 수 없다. cloud 모델 조건에서도 입력 근거, 진행 업무와 장기 파생물이 상주할 수 있어 4GiB의 상한을 정했다. 4GiB는 특정 삼성 제품이 보장한 VIA 가용량이나 현재 앱의 측정값이 아니다. 단순 process 수가 적다는 사실만으로 작은 메모리를 주장하지 않는다.

| 설명용 동시 할당 예산 | MiB | 포함할 것 |
| --- | --- | --- |
| UI/Core/runtime 기본 | 512 | process heap/언어 runtime/화면 UI |

### 7.4 차이 기준과 자원 판정

동일 활동 5회의 peak·phase·process·공유와 copy 원장 및 전체 최대값을 보고한다. 128MiB 이상을 차이 기준으로 두고 allocation의 크기·수명·공유·동시성을 검증한다. 박스 수로 peak를 계산하지 않는다. 필수 자료나 업무를 삭제하거나 조기 종료한 낮은 peak는 성공이 아니다.

### 8.1 초기 상태, cache와 순서

초기 대화 2,000turn·완료 Task 200개·source 30개와 전체 20MiB 원문 payload는 v5의 기반 fixture를 유지한다. B01~B20의 원문·과거 전달 기록과 C01~C10의 사례 근거 slot을 제공하되 현재 Task와 완성 의미는 선결합하지 않는다. DB·index·runtime overhead는 추가 메모리다. Source slot은 사례별 revision·권한을 동일하게 복원하고 성공 snapshot으로 후보 오류를 덮지 않는다. 기존 20MiB padding 규칙은 입력 JSON에 보존했다.

동시 처리 Task 슬롯은 최대 10개, cloud 호출 슬롯은 최대 4개다. 여기서 Task 슬롯은 현재 사례의 실행/사건 처리 대상으로 활성화한 업무를 뜻하며, 과거 완료 Task 200개나 이전 사례의 응답 대기 기록 전체를 10개로 제한한다는 의미가 아니다. S5-04는 보고서/메일/보호/질문 둘/결과 둘의 7개를 동시에 활성화한다. 한 사례의 지정 사건과 후기 관찰이 끝나면 이전 사례는 추가 원천 사건 없이 정지한 scope로 보관한다. 미답변 질문/미확인 업무의 실제 상태·이력·근거와 할당은 남기며 완료로 바꾸거나 purge하지 않는다. 다음 사례의 source 복원과 새 슬롯 준비 비용도 원장에 남긴다. 후보가 회수를 못 하거나 호출 quota를 소진한 경우는 실패이며 수집기 결함으로 지우지 않는다. 따라서 메모리는 새 활동 초기화 전까지 누적 보관과 동시 준비를 모두 포함한다.

다섯 활동 각각 동일한 원천 before-state에서 local cache·파생·queue를 새로 시작한다. Provider cache의 완전 초기화를 보장하지 않으며 지원하면 고정 옵션을 사용하고 그 외에는 billed cache token/hit를 기록한다. 양안의 준비 행동·시간창은 같지만 내부 자료는 후보가 생산한다. S2-02→S2-04 선후는 고정한다. 다른 독립 그룹은 같은 seed 20261011로 순서를 바꿀 수 있지만 갱신·질문 답변·집중 도착 내부 순서는 섞지 않는다.

S2-04 뒤 B01~B04를 0.01초 간격으로 v1→v2 갱신하고 maintenance 한 번, 활동 끝에 maintenance 한 번과 B04 제공 철회를 적용한다. 사례 안의 원천 변경과 청구를 중복하지 않는다. 미사용 생산·무효화·purge·늦은 완료도 기록한다. 신규 입력 종료 뒤 VIA queue/job을 30초 안에 drain하고 10초 idle probe를 수행한다. 정당한 외부 업무·질문 대기는 유지한다. 이를 완료로 덮거나 장시간 누수가 없다고 주장하지 않는다.

### 8.2 공통 lifecycle tail과 전체 채점

원본의 접수 checkpoint는 유지하고 최종 결과가 필요한 경우 동일 tail을 모든 QA에 적용한다. S1-02 ReportQ3@v1, S2-02 Proposal@v1, S2-03 TablePast@v1, S4-01 ReportRevised@v2, S6-01 ConfirmedRevision@v2는 실제 유효 접수+8초에 반환한다. S3-02는 현재 요약의 실제 SEND 접수+8초에 MailCurrent@v1:SENT를 반환한다. 신규 S2-04/05/S5-04는 각 명세의 tail을 따른다. 잘못된 payload를 정답 결과로 고치는 stub이 아니다.

S1-01 한정 조회는 원본의 접수+0.2초를 유지한다. S2-01/S3-01/S4-02의 한정 답변·설명은 허용한 직접 또는 위임 경로로 끝난다. S3-03의 BUSY·미생성, S4-03의 취소 접수·미확인, S6-02의 연락처 제공·발송 미승인, S6-03의 접근 거부, S6-04의 정상 답변은 명세한 처리 결과가 완료다. C5/C6는 checkpoint와 tail을 모두 검사한다. 유보를 성공 작성으로 바꾸거나 모든 요청을 외부 업무 전체 완료까지 확장하지 않는다.

### 8.3 측정 준비와 증거 수준

현재는 원천 입력·정답·관측 경계·분모·실패 처리·목표·계산 원장의 정의다. 실제 녹음·화면 파일·후보 build/hash·adapter·monotonic trace는 아직 없다. 실행 시 동일 모델/provider/version/timeout/quota와 외부 stub을 고정하고 critical Action은 stub에서만 기록한다. 실제 수집 없이 정답률·반복 편차·신뢰구간을 생성하지 않는다. 계산은 call-plan·지연·할당 가정의 민감도를 검산하는 CALCULATED_REFERENCE다.

검산 예시: 의미 호출의 입력 2,000 token/청구 출력 200 token은 `2,000×0.20/1M + 200×0.80/1M = $0.00056`, 작성자 decode 가정의 생성 부분은 `200/130 ≈ 1.538초`다. Instruct-2507은 non-thinking이며 출력200은 실제 답변/frame/tool 출력의 청구 예산이다. 원천/의미/도구 오류의 추가 질문·재시도·폐기 출력을 모두 포함하고 provider별 tokenizer의 실제 사용량을 우선한다. GPT Realtime 신규 audio 입력 1분/출력 1분은 `600×32/1M + 1,200×64/1M = $0.096`이며 Text와 이력 audio 재입력 청구는 별도다. 응답마다 이전 대화가 입력으로 재사용되므로 실제 `response.done`의 modality별 input/output/cached token을 호출 ID로 중복 제거해 합산한다. 초기 2,000turn을 음성 session에 전부 보내도록 강제하지 않으며 실제 보낸 이력·요약·instruction은 청구한다. 별도 input transcription을 켜면 해당 모델 청구도 더한다. 생성 부분 약1.538초를 첫 출력/입력 처리/통신/queue가 포함된 호출 완료 시간으로 쓰지 않는다. Qwen의 기본 예산에는 할인 없는 입력/출력 단가를 사용한다. 실제 cache 할인이나 별도 저장/도구 청구가 있으면 제공사가 확인한 사용량·단가로 원장에 반영하며 Gemini의 cache 단가를 Qwen에 적용하지 않는다.


### 8.4.1 선택한 모델 역할과 입력 범위

사용자는 **Qwen3-30B-A3B 계열 + GPT Realtime**을 이번 PoC의 모델 reference로 지정했다. 비용/API revision은 앞서 가격을 확인한 **Qwen3-30B-A3B-Instruct-2507**로 고정한다. 원본 `qwen3-30b-a3b`나 Thinking-2507/VL 모델과 혼용하지 않는다. 의미 해석·bounded read 판단·41B의 frame 생성에는 Qwen을, 실시간 음성 입출력/대화 지속에는 GPT Realtime을 사용한다. 외부 업무를 VIA에 맡긴 뒤에도 pending 함수 호출 중 대화를 계속한다. VIA가 외부 Agent의 실행/현재 Task/승인/질문/결과 연결의 권위를 유지하며 GPT Realtime의 tool pending을 실제 업무 완료로 해석하지 않는다. 양안은 같은 역할별 모델/설정/입출력 계약을 사용한다.

Qwen은 Text-to-Text 모델이다. P21의 S2-01 등은 이미 원천 observation으로 표 내용/version·관측시각·포인터 이력을 제공하므로, 그 **원천 사실과 span을 공통 text 입력으로 직렬화**한다. 최종 A/B 지칭, Task 연결, revision 선택, 의존 관계 또는 채점 정답을 adapter가 미리 채우지 않는다. 조회하지 않은 원천 내용·권한 없는 내용도 자동으로 넣지 않는다. 소스 원문/구조 정보는 그대로 공급하고, 의미 결합은 각 방안이 생산한다. 원본 화면 frame은 시간/보관/메모리 원장에 유지한다. 이는 픽셀만으로 임의 앱 화면을 인식하는 완성 제품 평가가 아니라 정의된 PoC 원천 자료를 사용하는 범위다. 추가 vision/OCR 모델을 현재 예산에 숨겨 넣지 않는다. 실제 픽셀 인식이 필요해지면 공통 관측 adapter의 추가 모델·비용·지연·권한·손실을 동일하게 명시하고 계약을 개정한다.

Qwen frame/tool 출력은 구문·허용 schema·ID/revision·현재성 검사를 거친다. 모델 이름만으로 JSON/함수 호출이 항상 맞거나 provider가 엄격한 schema decoding을 보장한다고 가정하지 않는다. 잘못된 출력의 재시도와 판단 유보는 같은 사례/실패/청구 원장에 포함한다. GPT Realtime의 structured output 미지원 때문에 음성 모델을 41B의 의미 frame 생산자로 대신 쓰지 않는다. 비용/기능 reference의 지정은 제품 모델 채택, Architecture 대안 선택이나 정확성 측정의 완료가 아니다.

### 8.4.1.1 이전 Gemini 선택 이유와 변경 이력

Gemini 3 Flash Preview의 공개 출시일은 **2025-12-17**이다([Google 출시 공지](https://blog.google/products-and-platforms/products/gemini/gemini-3-flash/)). 이전 선택은 공식 단가와 이미지 입력·함수 호출·structured output을 가진 reference의 편의에 따른 것이며 VIA 우월성이나 Qwen 30B와의 동등성 검증이 아니었다. 이후 정확한 Qwen API 단가를 확인했고 사용자가 Qwen/GPT 조합을 지정했으므로 **Gemini는 현행 의미/비용/속도 기준에서 제외**한다. 같은 124k/12.4k token 예산의 이전 Gemini 의미 비용 $0.09920과 현재 Qwen $0.03472의 차이 $0.06448는 단가 민감도이며 실제 호출/정확성/출력 동등성의 증거가 아니다. 기존 200 token/s와 Gemini cache 요금은 [변경 전 보존본](../../../archive/qa-semantic-reference-before-qwen-20261011/README.md)에 남겼다.

### 8.4.1.2 Groq 밖의 속도 근거와 산식

[Qwen 공식 속도 benchmark](https://qwen.readthedocs.io/en/latest/getting_started/speed_benchmark.html)는 **Qwen3-30B-A3B**를 NVIDIA **H20 96GB 1장**, SGLang **0.4.6.post1**, PyTorch **2.6.0+cu124**, batch **1**, 출력 **2,048 token**으로 평가했다. 입력1 token에서 BF16 **137.18**, FP8 **155.55 token/s**다. 입력6,144 token에서는 BF16 **490.10**, FP8 **551.34**다. 단, 공식 분자는 **입력+출력 token**, 분모는 전체 처리시간이다. 입력6,144의 490.10을 출력 생성률로 쓰지 않는다.

BF16 입력1 조건의 전체 시간은 `2,049/137.18 ≈ 14.94초`, 입력6,144 조건은 `8,192/490.10 ≈ 16.72초`로 복원할 수 있다. 출력/전체시간으로 다시 표현하면 각각 **137.11**과 **122.53 output token/s**이며 이는 prefill까지 포함한 해당 길이의 유효 출력률이다. 이것을 TTFT와 분리된 decode rate로 두고 TTFT를 다시 더하면 입력 처리 시간이 이중 계상된다. 원본 Qwen3 benchmark를 Instruct-2507의 실측 또는 Alibaba Singapore API의 속도로 주장하지 않는다. 서버 측 H20 reference이므로 Windows 노트북의 속도/메모리에도 이전하지 않는다.

따라서 공식 수치 기반의 계산은 **공개된 동일 길이/환경의 전체 처리시간**을 쓰거나, 별도로 검증된 decode rate와 TTFT를 분리해야 한다. 현재는 원본 계열 BF16 유효 출력률 약122.53~137.11과 FP8 입력1 약155.47을 수치 규모의 참고로 삼아 **130 token/s의 독립적인 PoC decode 가정**과 **100/130/160 민감도**를 정했다. 기준 TTFT0.30초, 빠른0.15초, 느린0.80초와 음성 시작0.10/0.25/0.60초도 별도 작성자 가정이다. 이들을 공개표에서 분리 측정한 TTFT/decode로 주장하지 않는다. 특히 2,048 출력의 유효 출력률을 2,000입력/200출력에 보장된 rate로 이전하지 않는다. API 배포의 TTFT/생성률이 있으면 두 가정을 실제 측정으로 함께 교체하고, 공개 benchmark 자체를 재현 계산할 때는 전체시간만 써서 prefill을 중복 계상하지 않는다. API 가격 reference와 별도 H20 속도 reference를 함께 사용하는 경우 비용/속도가 같은 서비스에서 측정됐다는 주장도 하지 않는다.

기존의 **450+ token/s**는 [Groq의 `qwen/qwen3.8-27b` 모델 페이지](https://console.groq.com/docs/model/qwen/qwen3.8-27b)의 제공사 표시값이다. [GroqCloud는 전용 LPU 추론 인프라](https://groq.com/blog/the-groq-lpu-explained)를 사용한다. 이는 Qwen3-30B-A3B-Instruct-2507, NVIDIA GPU 또는 Windows PC의 숫자가 아니다. 해당 450 수치의 LPU 수/세대, precision, prompt/output 길이, 동시 요청 수와 상세 계측 경계는 페이지에 공개되어 있지 않으므로 가정으로 채우지 않는다. Groq은 현행 비용/속도 reference에서 제외하며 이 문단은 이전 근거의 의미를 설명하기 위한 provenance다.

### 8.4.2 Gemini Live와 GPT Realtime의 기능 비교

| 비교 항목 | Gemini 3.1 Flash Live Preview | OpenAI gpt-realtime | VIA에 주는 의미 |

VIA는 요청/Task의 권위를 갖고 음성 모델의 임시 session과 구별한다. 긴 업무는 로컬 VIA가 외부 Agent에 비동기로 위임하고, 음성 모델에는 유효한 접수·질문·결과를 제시할 입력을 따로 전달하는 방향으로 reference를 해석한다. 이것은 긴 Agent 결과를 Live 동기 함수 응답으로 기다리는 것과 다르다. 실제 provider의 forced response, cancel, 재연결, 출력 내용 준수와 local playback stop은 adapter/API 검증에서 확인해야 한다. 현재 GPT Realtime reference에서도 local playback stop·새 사용자 요청·동시에 도착한 Agent 질문/결과의 우선순위는 VIA가 관리하고, pending tool의 결과가 없는 동안 완료를 추측해 말하지 못하도록 실제 상태를 전달한다. 이전 Gemini 3.1 검토의 proactive audio/affective dialogue 미지원과 `turn_complete=true`의 활성 generation 중단은 기능 비교의 제한으로 보존한다. 모델 이름만으로 연속 입력/여러 Task 처리 계약이 충족됐다고 하지 않는다.

### 8.5 계산 가능한 구조 차이와 한계

41의 충분한 typed 근거에서 A 2call/B 1call과 B가 부분 해석을 추가해 2call이 되는 경우를 계산한다. 42의 정상 ANSWER는 공동 commit/독립 접수·반영의 코드·IPC 비용을 비교하고 모델 비용은 공통으로 둔다. 44의 S5-04는 실제 전이·queue·credit·join을 비교하며 A 전체를 blocking으로 만들지 않는다. 45는 첫 사용·재사용·새 근거와 미사용 source 생산을 함께 계산한다.

가정과 빠른·기준·느린 profile은 [입력](./03-02-poc-inputs.json) 및 [검산](./03-02-poc-calculation-report.md)에 남긴다. 지역 차이가 있어도 전체 평균의 차이 기준을 넘지 않으면 그대로 보고한다. 모든 사례의 trace/call-plan이 없는 지역 예시를 전체 QA 성능표로 발표하지 않는다.

### 8.6 목표 판정과 우선순위 선택

모든 적용 축을 같은 계약에서 평가하고 원값·목표·보호 조건·기능 위반을 구분한다. 필수 기능·권한·중복 방지·증거 실패를 빠른 시간이나 낮은 자원으로 상쇄하지 않는다. 번호순으로 처음 나타나는 의미 있는 입증 차이가 선택을 이끌며 불확실을 동등성 증명으로 바꾸지 않는다. 낮은 QA는 tactic 적용과 전체 재평가로 보완한다. 이번 문서는 최종 DP/A/B 선정이 아니다.
