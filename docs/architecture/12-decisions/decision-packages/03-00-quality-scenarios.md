# 3단계 — VIA의 품질 요구는 어떤 상황에서 충돌하는가

> 상태: **STAGE_3_REVIEW_READY / 사용자 검토 대기** / 2026-10-01
> 입력: 승인된 [02-00 요구와 해결 수단](./02-00-requirements-and-choices.md), [01-00 중요 문제 원장](./01-00-problem-coverage.md)
> P-01~16의 품질 시나리오와 충돌을 정리했다. 구조 대안, DP, 새로운 ASR을 선정한 문서가 아니다.

## 1. 이번에 검토할 핵심

**같은 사용자 결과를 지키더라도, 그것을 얻는 데 필요한 시간과 자원, 장애 대응, 변경 비용은 서로 달라질 수 있다.** 3단계에서는 그 차이가 중요해지는 상황을 찾는다. 4단계에서 여러 구조를 탐색할 때 무엇을 설명해야 하는지 정하기 위한 자료다.

예를 들어 “아까 가리킨 자료”를 정확히 찾으려면 당시 근거가 필요하다. 근거를 풍부하게 남기면 사후 확인에 도움이 될 수 있지만, PC 자원과 접근 통제, 삭제 처리가 늘어난다. 반대로 적게 남겨도 같은 대상을 확인할 수 있다면 비용을 줄일 수 있다. 어느 쪽이 가능한지는 입력의 모호함, 자료 변화, 실제 지원 기능에 달려 있다. **많이 저장하면 항상 정확하거나, 적게 저장하면 항상 안전하다고 미리 결론 내리지 않는다.**

읽는 순서는 **§2의 품질 기준 → §3의 충돌 요약 → §4의 관심 있는 P 상세 → §5의 11개 관점 후속 검토표**다. §4의 각 표는 자극, 환경, 대상, 기대 반응, 충돌, 관찰 항목을 갖는다. P 하나가 하나의 DP나 독립 QA라는 뜻은 아니다.

### 절충으로 허용하지 않는 것

[02-00 §2](./02-00-requirements-and-choices.md#2-모든-문제에-공통으로-적용할-경계)의 R/B는 유지한다. 당시 화면 대신 마지막 화면으로 답하기, 모호한 대상을 임의 확정하기, 철회된 정보를 쓰기, 확인 가능한 업무를 복구하지 않기, 입력만 받고 정상 요청을 영원히 미루기는 성능을 위한 절충으로 인정하지 않는다. 필수 기능을 뺀 제한 모드도 전체 요구를 만족한 안과 구별한다.

아래 충돌은 **조건부 설계 가설**이다. 요구 충족 여부와 각 품질의 실제 값은 나중에 같은 조건에서 확인해야 한다. 규칙을 지키겠다는 선언만으로 정확성이나 신뢰성이 동등한 것은 아니다. 현재는 목표 수치, 가중치, workload, 시험 모집단을 동결하지 않는다. **03에서는 품질의 의미와 시나리오를 정하고, 04에서는 여러 구조를 탐색하며, 05에서는 실제 target과 강한 대안의 품질 차이를 검토한다. 정확한 QA 정의, 지표와 측정 방법은 실제 측정 전에 전체 DP 공통으로 확정한다.**

## 2. 어떤 품질을 보고 있는가

기준은 **ISO/IEC 25010:2023 제품 품질 모델**이다. 판본은 [ISO 공식 소개](https://www.iso.org/standard/78176.html), 기능 적합성, 성능 효율성, 호환성 및 아래 상호작용 부특성은 [공개 원문 preview의 §3.1~3.4](https://cdn.standards.iteh.ai/samples/78176/13ff8ea97048443f99318920757df124/ISO-IEC-25010-2023.pdf)를 확인했다. 나머지 기존 QA 대응과 공개 자료의 한계는 [저장소의 ISO 대응 근거](../../08-quality-attributes/iso-25010-quality-basis.md)를 따른다. 아래 한국어 설명과 VIA 시나리오는 우리 과제의 적용 해석이며 표준의 공식 번역이나 적합성 인증이 아니다.

아래 **11개 검토 관점을 04의 구조 탐색과 05의 두 방안 비교까지 계속 사용한다.** 기존 QA 번호나 대표 지표에서 출발하지 않고 VIA의 품질 질문에서 출발한다. `V-01~11`은 문서 안의 추적 표식이며 새 QA ID, ASR 선정 또는 측정 계약이 아니다. ISO 상위 특성이 11개라는 뜻도 아니다. 일부 행은 함께 살펴볼 부특성을 묶었으며, 각 부특성의 차이는 유지한다.

| 관점 | ISO 특성 → 부특성 | 이번 문서에서 묻는 공통 질문 |
| --- | --- | --- |
| **V-01 기능 정확성** | Functional suitability → Functional correctness | 목표, 대상, 요청 관계, 실행 상태와 전달 사실이 사용자의 의도 및 확인 가능한 사실에 맞는가? |
| **V-02 기능 완전성과 적절성** | Functional suitability → Functional completeness / Functional appropriateness | 필요한 기능과 완료 범위를 빠뜨리지 않는가? 충분한 근거가 있는데도 같은 설명이나 선택을 반복시키는가? 기능 누락과 불필요한 사용자 단계를 각각 본다. |
| **V-03 시간 특성** | Performance efficiency → Time behaviour | 입력, 유효한 답, 제어와 업무 진행을 얼마나 기다리는가? 일부 요청이 계속 밀리지는 않는가? |
| **V-04 자원 활용성과 수용량** | Performance efficiency → Resource utilization / Capacity | 필요한 기능을 함께 유지하는 데 메모리, 연산, 에너지, 저장공간이 얼마나 필요한가? 어느 부하에서 처리 능력의 한계가 드러나는가? 자원 소모와 지원 부하 범위는 구별한다. |
| **V-05 결함 허용성과 복구성** | Reliability → Fault tolerance / Recoverability | 장애 중 필요한 기능과 무관한 업무를 유지하는가? 장애 뒤 근거가 남은 상태와 제어를 올바르게 복원하는가? |
| **V-06 변경 용이성과 모듈성** | Maintainability → Modifiability / Modularity | 계약이나 기능이 바뀔 때 변경의 영향이 어디까지 퍼지고, 다른 책임을 훼손하지 않고 수정과 검증을 할 수 있는가? |
| **V-07 분석 및 시험 용이성** | Maintainability → Analysability / Testability | 실패의 원인을 구분하기 쉬운가? 필요한 사건과 장애를 통제하고 기대 결과를 판정하기 쉬운가? 원인 분석과 시험 가능성은 각각 확인한다. |
| **V-08 기밀성** | Security → Confidentiality | 허용된 대상과 목적에만 정보를 읽고 제공하며, 철회 또는 삭제 뒤의 신규 사용을 막는가? |
| **V-09 상호운용성과 공존성** | Compatibility → Interoperability / Co-existence | 외부 제품과 교환한 정보의 의미를 보존해 기능을 수행하는가? 다른 PC 앱과 자원을 공유할 때 서로의 필요한 기능을 방해하지 않는가? 두 질문을 별도로 본다. |
| **V-10 조작 용이성과 사용자 오류 방지** | Interaction capability → Operability / User error protection | 사용자가 현재 상태와 제어 대상을 알아보고 원하는 동작을 할 수 있는가? 잘못된 대상이나 범위를 조작하는 일을 막는가? |
| **V-11 설치 용이성** | Flexibility → Installability | 필요한 runtime과 helper를 설치, 갱신 또는 제거할 수 있는가? 실패했을 때 남은 dependency와 자료의 상태를 파악하고 정리할 수 있는가? |

**§3은 이 11개 관점의 충돌, §4는 구체 상황에서의 관찰, §5는 04~05로 가져갈 질문을 연결한다.** 각 문제에 11개 모두의 효과를 억지로 만들지는 않는다. §4에는 현재 시나리오에서 인과가 드러나는 관점을 쓰고, 아직 연결되지 않은 관점은 비적용 확정이 아닌 구조 탐색에서 재점검할 항목으로 남긴다. 04~05에서는 각 구조에 대해 11개 모두를 점검하여 영향 경로 또는 영향 없음의 근거, 미확인 사항을 기록한다. 불리한 관점을 조용히 빼지 않는다.

묶인 부특성 사이에 다른 효과가 생기면 각각 설명한다. 예를 들어 연동 기능을 잘 유지하더라도 다른 PC 앱과의 공존은 나쁠 수 있다. 이것을 하나의 점수로 합치지 않는다. 관점의 추가, 분리 또는 통합이 필요하면 전체 목록과 연결표를 함께 검토하며 특정 DP에서만 의미를 바꾸지 않는다. 최종 QA와 ASR의 구성, 우선순위, 지표와 방법은 아직 미확정이다.

ISO의 Safety 특성도 전체 모델에 존재하지만 현재 저장소의 “safety qualification”이라는 이름과 동일시하지 않는다. 이 단계의 권한, 오실행, 복구 문제는 위의 실제 품질 경로로 다룬다. 별도 위해 상황과 인과가 제시되지 않은 상태에서 Safety 점수를 새로 만들지 않는다.

## 3. 여러 문제에 걸친 품질 충돌 요약

11개 관점마다 어떤 다른 품질과 긴장이 생기는지 정리했다. 두 품질이 항상 반비례한다거나 필수 요구를 포기해도 된다는 뜻은 아니다. 같은 사건이 여러 행에 나타나도 비용이나 효과를 중복 계산하지 않는다.

| 중심 관점 | 연결 문제 | 다른 관점과의 충돌 및 이유 | 차이를 좌우할 조건 |
| --- | --- | --- | --- |
| V-01 기능 정확성 | P-01, 02, 03, 06 | 근거를 더 확보하고 재확인하면 오류를 줄일 여지가 있지만 V-03 대기와 V-04 자원이 늘 수 있다. 항상 질문하는 우회는 V-02의 불필요한 단계를 늘린다. | 모호한 후보 수, 자료 변화, 시간 근거의 오차, 읽기 비용 |
| V-02 기능 완전성과 적절성 | P-01, 04, 05, 06, 10 | 필요한 직접 응답, 독립 요청, 후속 대화를 모두 지원하고 반복 입력을 줄이려면 처리 경로와 유지 상태가 필요하다. V-04 비용이 늘 수 있고 자동 연결이 잘못되면 V-01도 나빠진다. | 필요한 처리 경로, 독립 목표 수, 이미 확보된 근거, 재접속 시 유효한 정보 |
| V-03 시간 특성 | P-04, 08, 09, 14 | 빠른 응답 준비와 즉시 제어에는 V-04 자원 여유가 필요할 수 있다. 검증과 전달 확인을 앞당기거나 늦추는 선택은 V-01 및 V-05와 함께 확인해야 한다. | 자체 지식/자료 의존 요청, 전송 경계, audio buffer, 공유 연산 경합 |
| V-04 자원 활용성과 수용량 | P-02, 03, 10, 12, 14 | 상주 자료나 보조 실행체를 줄이면 자원을 아낄 여지가 있지만 V-03 재처리 대기가 늘거나 V-05의 장애 영향 경계가 달라질 수 있다. 입력 보호와 정상 처리 모두를 유지해야 한다. | 메모리 압박, 연속 입력, background 준비 및 정리, 긴 비선점 연산 |
| V-05 결함 허용성과 복구성 | P-05, 07, 09, 10, 13 | 복구에 필요한 내구 기록과 외부 확인은 V-03 정상 경로의 시간, V-04 저장 및 연산 비용을 늘릴 수 있다. 상태 형식 변경은 V-06 부담도 만든다. | crash 시점, 저장 상태, 외부 조회 지원, 미완료 업무량 |
| V-06 변경 용이성과 모듈성 | P-03, 05, 07, 11, 13, 15, 16 | 공통 계약으로 변경 범위를 제한하려 해도 제공자 의미를 담지 못하면 V-09 연동과 V-02 기능 유지가 나빠진다. 저장 상태까지 바뀌면 V-05 복구 검증도 필요하다. | 형식 변경/의미 변경, 진행 실행, 새 source와 사용 경로, 저장 version |
| V-07 분석 및 시험 용이성 | P-04, 11, 16 | 자세한 근거와 통제 가능한 시험 경계는 원인 구분을 돕지만 V-04 기록 비용과 V-03 지연을 만들 수 있다. V-08이 허용하는 범위 안에서 필요한 근거를 확보해야 한다. | 사건 순서, 관측 gap, 보관 동의와 삭제, 원인을 구분할 최소 자료 |
| V-08 기밀성 | P-02, 03, 10, 11, 12, 16 | 철회 전파와 파생 자료 정리는 V-03 시간 및 V-04 자원을 요구한다. 보관 제한은 V-07 사후 원인 분석에 한계를 만들 수 있다. 권한 위반을 이익으로 상쇄하지 않는다. | 자료 복제와 파생 관계, 사용 시점, 철회 및 삭제 시점, 외부 제공 여부 |
| V-09 상호운용성과 공존성 | P-07, 14, 15 | 제공자별 의미를 보존하려면 V-06 변환 및 검증 부담이 생길 수 있다. 다른 PC 앱과 공존하도록 자원 사용을 제한하면 VIA의 V-03 대기와 V-04 지원 부하가 달라질 수 있다. | Agent/source capability 차이, 외부 앱 부하, CPU/메모리/장치 공유 |
| V-10 조작 용이성과 사용자 오류 방지 | P-06, 08, 09 | 대상과 실제 효력을 확인하게 하면 오조작을 줄일 수 있지만 V-02 사용자 단계와 V-03 대기가 늘 수 있다. 자동 선택은 V-01의 정확한 binding을 필요로 한다. | 실제 제시된 질문, 유효 후보 수, 중단과 취소의 구별, 전달 불명 |
| V-11 설치 용이성 | P-14, 15 | 별도 dependency가 V-01 기능이나 V-05 장애 대응에 도움이 되더라도 설치 및 제거 경로가 늘 수 있다. 묶음 배포는 준비 단계를 줄일 수 있지만 V-04 설치 자원과 V-06 변경 범위에 영향을 준다. | runtime/helper 구성, 버전 충돌, 부분 설치, 제거 뒤 잔여 자료와 실행체 |

## 4. 문제별 품질 시나리오

여기서 **대상**은 관찰할 시스템 책임이다. 대안에 target의 Component 배치를 강제하지 않는다. **기대 반응**은 [승인된 02-00](./02-00-requirements-and-choices.md)의 R/B를 구체 상황에 적용한 것이다. **관찰**은 후속 검증에서 확인할 항목이며 이번에 측정했다는 뜻이 아니다. 관찰은 §2의 같은 V 관점을 각 상황에 적용한 예다. 문제별로 다른 정의나 대표 지표를 채택한 것이 아니며 정확한 지표와 측정 방법은 전체 DP 공통으로 정한다. U 번호는 [02-00 §5](./02-00-requirements-and-choices.md#5-지원이-필요하다는-것과-이미-확보했다는-것은-다르다)의 미검증 지원을 가리킨다.

### P-04. 빠른 직접 답변을 같은 대화의 업무로 이어가기

| 항목 | 시나리오 |

| 관찰할 것 | V-01: 답변과 실행 및 질문의 정확한 연결. V-02: 불필요한 확인이나 재선택. V-03: 답변 후 유효한 재개까지의 대기. V-04: 여러 질문의 유지 비용. V-10: 사용자가 어느 질문에 답하는지 알 수 있는지, 다른 실행에 답변이나 승인을 적용하는 조작을 막는지. |

### P-08. 즉시 말을 멈추게 하면서 실제 업무 제어 결과는 정확히 알리기

| 항목 | 시나리오 |
| --- | --- |
| 자극과 환경 | 음성 재생 중 사용자가 정정하거나 취소한다. 요청은 전송 직전, 접수 불명, 실행 중, 완료 직후 중 하나에 있고 모델 계산도 진행 중이다. 사용자가 지금 멈추는 대상이 음성인지 업무인지 알아보고 제어할 수 있어야 한다. |

## 6. 이후 비교에서 같은 조건으로 유지할 것

이 절은 후속 비교를 위한 경계다. 시험 계약이나 수치를 지금 freeze하지 않는다.

### 6.1 모든 DP와 모든 방안에서 같은 QA를 사용한다

**2026-10-01 사용자 명시 합의: 같은 QA를 채택했다면 모든 DP와 모든 방안에서 동일한 정의, 동일한 지표, 동일한 측정 방법을 사용한다. 이 DP에서는 이렇게, 다른 DP에서는 다르게 정의하거나 측정하는 것은 금지한다.** 이 원칙은 이후 DP 선발, QA 구체화, 측정 계약과 결과 해석까지 적용한다.

예를 들어 Functional correctness를 채택한다면 어떤 DP에서는 의미 field 정답률, 다른 DP에서는 검색 recall, 또 다른 DP에서는 업무 성공률을 각자 대표값으로 정하고 같은 QA라고 부를 수 없다. 어떤 지표를 쓸지는 아직 미정이지만, 확정할 때는 모두가 참조할 공통 계약으로 정한다. 공통 계약이 여러 관찰을 포함할 수도 있으나 구성과 집계 규칙 역시 모든 DP와 방안에 동일하게 적용해야 한다.

| 공통으로 고정할 것 | DP 또는 방안별로 바꾸면 안 되는 것 |
| --- | --- |
| 품질 정의와 평가 단위 | 같은 QA를 한곳에서는 모델 정확성, 다른 곳에서는 제품 업무 성공으로 재해석하기 |
| 지표와 판정 | 정답 기준, oracle, 분자와 분모, 단위, 가중치, 집계, 실패 및 timeout 처리의 개별 변경 |
| 측정 방법 | 관찰 시작과 종료, 포함 및 제외 비용, 입력 및 부하 구성 규칙, 반복과 관측 절차의 개별 변경 |
| 모집단과 적용 규칙 | 같은 QA 이름 아래 유리한 사례만 고르거나 불리한 사례를 제외하여 평가 대상을 바꾸기 |
| 계약 version과 결과 해석 | 서로 다른 정의나 방법으로 얻은 값을 같은 QA의 비교 가능한 결과로 제시하기 |

구조마다 품질에 영향을 주는 경로는 다를 수 있다. 그 차이는 공통 계약이 정한 적용 규칙으로 설명하며, QA 자체를 바꾸는 이유가 되지 않는다. 내부 계측 위치나 adapter가 달라도 같은 사용자 사건, 관찰 경계와 판정에 연결해야 한다. 미참여와 미지원, 미확인은 동등이나 0점으로 바꾸지 않는다. 추가 진단을 붙일 수는 있지만 공통 QA를 대체하거나 DP별 대표 지표로 바꿀 수 없다.

QA의 권위 정의와 측정 계약은 **한 공통 원본**에서 관리하고 모든 DP가 같은 version을 참조한다. 개정이 필요하면 공통 원본과 영향받는 모든 DP를 함께 검토한다. 이전 결과는 원래 계약과 함께 보존하고 새 결과와의 비교 가능성을 다시 판정한다. 측정 전에는 모든 DP 및 모든 방안의 정의, 지표, 방법, 모집단 적용 규칙이 같은 계약인지 확인한다. 기존 문서의 DP별 평가 기록을 이 원칙의 예외 근거로 사용하지 않는다.

### 6.2 공통 평가 계약을 구체화할 때의 경계

| 경계 | 유지할 원칙 |
| --- | --- |
| 사용자 결과 | 같은 목표, 완료 조건, 정정, 권한, 삭제 및 복구 요구를 둔다. 02-00의 T를 모든 안의 공통 조건으로 복제하지 않는다. |
| 외부 지원 | 동일 Agent/source/OS capability와 같은 모델 제약을 적용한다. 추가 helper나 저장소가 필요하면 설치, 자원, 장애, 변경, 삭제 비용을 포함한다. U 미확인을 성공 조건으로 가정하지 않는다. |
| 환경과 부하 | 같은 장비, 입력과 자료 변화, 동시 업무, 외부 앱 부하, 장애 및 변화 상황을 사용한다. warm/cold, 정상/포화, 확인 가능/불명 조건을 나눠 본다. FA의 평가 조건을 제품 최대치로 확대하지 않는다. |
| 실제 관찰 경계 | 실제 사용자 또는 외부 사건과 software 인지를 구분하고 구조가 만든 비용을 숨기지 않는다. 구체 시작과 종료, 포함 및 제외 구간과 관측 절차는 품질 질문에 맞게 공통으로 설계한다. 기존 endpoint 계약을 자동 채택하지 않는다. |
| 기존 QA의 취급 | 이전 정의와 결과의 의미는 보존한다. 새 비교에서는 품질 질문에 맞는지 검토한 뒤 재사용 또는 개정한다. 재사용할 때는 기존 의미를 정확히 지키고, 개정할 때는 공통 원본에서 변경 이유와 영향 범위를 기록한다. 어느 경우도 DP별 별도 정의나 분모 산정 규칙을 허용하지 않는다. |
| 실패와 한계 | 잘못된 빠른 결과, 누락, timeout, 미복구를 남긴다. 필요한 기능이 미지원이면 적용 한계를 밝히고 같은 기능의 성공으로 처리하지 않는다. 현재 target도 U 지원이 확보됐다고 주장하지 않는다. |
| 조합과 중복 | P-02/14의 입력 근거, P-03/12의 파생 자료, P-05/06/13의 재개 상태처럼 공통 비용과 효과를 두 번 세지 않는다. 조합에 따라 충돌이 바뀌면 해당 의존성을 기록한다. |

5단계에서는 실제 target을 방안 1, 같은 문제를 푸는 강한 구조를 방안 2로 놓고 **ISO 품질 → 구체 조건 → (+)/(-)/(0) → 쉬운 이유 → 확인할 근거** 순서의 표를 만든다. `(0)`은 실제로 같은 한정 경로 등 근거가 있을 때만 쓰고, 지원이나 상대 결과가 미확인이면 **미확인**으로 표시한다. 이번 단계에는 두 구조가 아직 없으므로 우열 기호를 붙이지 않는다.

후속 DP의 ASR 적용은 확정될 ASR 집합에 대해 `PRIMARY`, `REGRESSION_ONLY`, `NOT_APPLICABLE`, `UNRESOLVED`로 판단한다. 현재 11개 관점의 시나리오 연결은 그 DP 적용 판정이 아니다. 04~05에서 11개 모두를 검토하고 ASR의 최종 구성도 그 근거로 논의한다. 낮은 우선순위를 이유로 실제 영향을 받는 축을 빼거나, 한 축의 실패 때문에 다른 축의 근거를 지우지 않는다.

## 7. 사용자 리뷰와 다음 단계

| 이번에 확인할 내용 | 의견을 남기는 예 |
| --- | --- |
| 실제 VIA에서 중요한 충돌인가? | “P-xx에서는 이 비용보다 ○○가 더 중요하다.” |
| 필수 결과를 절충 가능한 품질로 잘못 풀었는가? | “이 상황의 ○○는 느려져도 반드시 유지해야 한다.” |
| 충돌의 조건과 관찰 항목이 충분한가? | “△△ 부하 또는 실패 조건이 빠졌다.” |
| 11개 관점이 문서 전체와 후속 단계까지 이어지는가? | “V-xx는 §2에만 있고 구체 시나리오나 후속 질문이 부족하다.” |

현재 P-01~16의 품질 시나리오 작성과 작성자 대조를 마쳤으며 [검토 기록](./03-01-quality-review.md)에 범위와 검사 결과를 남긴다. 사용자 검토 뒤 4단계의 여러 구조 탐색으로 이어간다. 기존 네 비교안을 자동 선정하지 않으며 target, QA 의미와 지위, ADR, 이전 증거를 변경하지 않았다. 구현, 모델 실행, 성능 측정, 수치 freeze는 수행하지 않았다.

## 참고 — 기존 QA 자료의 위치와 취급

[기존 Core ASR 계약](../../08-quality-attributes/core-asr-contract.md), [기존 event 경계 계약](../../11-measurement/event-boundary-contract.md)과 기존 평가 기록은 이전 정의와 결과를 해석할 때 사용한다. 이번 품질 질문의 지표나 방법을 자동으로 결정하지 않는다. 재사용 여부는 11개 관점의 시나리오와 실제 구조 차이를 검토한 뒤 전체 DP 공통 계약을 설계할 때 판단한다. 기존 정의와 결과는 원래 의미로 보존하며, 현재 target의 설계 우선순위를 새 QA 구성과 동일시하지 않는다.
