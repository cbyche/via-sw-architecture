# 3단계 — VIA의 품질 요구는 어떤 상황에서 충돌하는가

> 상태: **STAGE_3_REVIEW_READY / 사용자 검토 대기** / 2026-10-01
> 입력: 승인된 [02-00 요구와 해결 수단](./02-00-requirements-and-choices.md), [01-00 중요 문제 원장](./01-00-problem-coverage.md)
> P-01~16의 품질 시나리오와 충돌을 정리했다. 구조 대안, DP, 새로운 ASR을 선정한 문서가 아니다.

## 1. 이번에 검토할 핵심

**같은 사용자 목표를 기준으로 구조마다 지원하는 기능의 범위와 정확성, 사용자 수고, 시간, 자원, 장애 대응과 변경 비용을 비교한다.** 3단계에서는 그 차이가 중요해지는 상황을 찾는다. 4단계에서 여러 구조를 탐색할 때 무엇을 설명해야 하는지 정하기 위한 자료다.

예를 들어 “아까 가리킨 자료”를 정확히 찾으려면 당시 근거가 필요하다. 근거를 풍부하게 남기면 사후 확인에 도움이 될 수 있지만, PC 자원과 접근 통제, 삭제 처리가 늘어난다. 반대로 적게 남겨도 같은 대상을 확인할 수 있다면 비용을 줄일 수 있다. 어느 쪽이 가능한지는 입력의 모호함, 자료 변화, 실제 지원 기능에 달려 있다. **많이 저장하면 항상 정확하거나, 적게 저장하면 항상 안전하다고 미리 결론 내리지 않는다.**

읽는 순서는 **§2의 품질 기준 → §3의 충돌 요약 → §4의 관심 있는 P 상세 → §5의 13개 관점 후속 검토표**다. §4의 각 표는 자극, 환경, 대상, 기대 반응, 충돌, 관찰 항목을 갖는다. P 하나가 하나의 DP나 독립 QA라는 뜻은 아니다.

### 기능 범위 차이도 비교한다

**2026-10-01 사용자 리뷰에 따라 기능 완전성을 독립 비교 관점으로 유지한다. 일부 기능을 지원하지 않거나 제한적으로 지원하는 구조도 04의 탐색과 05의 비교에 포함할 수 있다.** 완전한 기능 충족을 후보 진입 조건으로 두어 현실적인 대안을 미리 제거하지 않는다. 기능을 줄여 얻는 시간, 자원과 변경 비용의 이익도 설명하되 그 대가로 포기한 사용자 목표와 상황을 함께 적는다.

[02-00](./02-00-requirements-and-choices.md)의 R/B와 UC는 공통 비교 기준으로 남긴다. 대안에 맞춰 요구 목록을 줄이지 않고 **지원, 부분 지원, 미지원, 미확인**을 구별한다. 지원 수준은 현재 설계의 설명이며 구현 검증 결과가 아니다. 제한 조건, 포기한 기능, 사용자 영향, 수동 우회와 그 비용을 기록한다. 기능 누락만으로 대안을 탈락시키지 않으며, 최종 판단에서도 완전성의 손실과 다른 품질의 이익을 함께 검토할 수 있다. 특정 기능을 이미 포기하기로 확정한 것은 아니다.

기능 축소는 잘못된 결과를 정답으로 세거나 미확인을 성공으로 보고하는 근거가 아니다. 미지원 안내와 원래 목표의 완료는 구별한다. 권한 위반이나 다른 업무의 오실행을 기능 미지원으로 감추지 않는다. 이 합의는 새 비교의 후보 수용 원칙을 바꾼 것이며, reviewed target과 승인된 요구 원문을 축소하지 않는다. 이전 문서의 완전 충족 전제를 새 대안의 자동 제외 규칙으로 적용하지 않는다.

아래 충돌은 **조건부 설계 가설**이다. 현재는 목표 수치, 가중치, workload, 시험 모집단을 동결하지 않는다. **03에서는 품질의 의미와 시나리오를 정하고, 04에서는 여러 구조를 탐색하며, 05에서는 실제 target과 강한 대안의 품질 차이를 검토한다. 정확한 QA 정의, 지표와 측정 방법은 실제 측정 전에 전체 DP 공통으로 확정한다.**

## 2. 어떤 품질을 보고 있는가

기준은 **ISO/IEC 25010:2023 제품 품질 모델**이다. 판본은 [ISO 공식 소개](https://www.iso.org/standard/78176.html), 기능 적합성, 성능 효율성, 호환성 및 아래 상호작용 부특성은 [공개 원문 preview의 §3.1~3.4](https://cdn.standards.iteh.ai/samples/78176/13ff8ea97048443f99318920757df124/ISO-IEC-25010-2023.pdf)를 확인했다. 나머지 기존 QA 대응과 공개 자료의 한계는 [저장소의 ISO 대응 근거](../../08-quality-attributes/iso-25010-quality-basis.md)를 따른다. 아래 한국어 설명과 VIA 시나리오는 우리 과제의 적용 해석이며 표준의 공식 번역이나 적합성 인증이 아니다.

아래 **13개 검토 관점을 04의 구조 탐색과 05의 두 방안 비교까지 계속 사용한다.** 기존 QA 번호나 대표 지표에서 출발하지 않고 VIA의 품질 질문에서 출발한다. `V-01~13`은 문서 안의 추적 표식이며 새 QA ID, ASR 선정 또는 측정 계약이 아니다. ISO 상위 특성이 13개라는 뜻도 아니다. 일부 행은 함께 살펴볼 부특성을 묶었으며, 각 부특성의 차이는 유지한다.

| 관점 | ISO 특성 → 부특성 | 이번 문서에서 묻는 공통 질문 |
| --- | --- | --- |
| **V-01 기능 정확성** | Functional suitability → Functional correctness | 목표, 대상, 요청 관계, 실행 상태와 전달 사실이 사용자의 의도 및 확인 가능한 사실에 맞는가? |
| **V-02 기능 적절성** | Functional suitability → Functional appropriateness | 제공하는 기능이 사용자의 목표 달성을 얼마나 잘 돕는가? 충분한 근거가 있는데도 같은 설명, 선택이나 수동 연결을 반복시키는가? |
| **V-03 기능 완전성** | Functional suitability → Functional completeness | 공통 요구 목록 중 어떤 기능과 완료 범위를 지원, 부분 지원 또는 미지원하는가? 포기한 기능 때문에 어떤 사용자 목표와 상황을 처리하지 못하는가? 지원 미확인은 별도로 남긴다. |
| **V-04 상호작용 반응성** | Performance efficiency → Time behaviour | 입력이나 제어 사건에 대해 유효한 응답 또는 실제 제어 효과가 나타나기까지 VIA가 얼마나 시간을 쓰는가? |
| **V-05 VIA 귀속 요청 완료 시간** | Performance efficiency → Time behaviour | 요청 시작부터 필요한 최종 결과의 실제 전달까지 전체 경로에서 VIA가 책임지는 처리와 대기가 얼마나 발생하는가? Downstream Agent의 업무 실행 시간은 외부 조건으로 제외한다. |
| **V-06 자원 활용성과 수용량** | Performance efficiency → Resource utilization / Capacity | 필요한 기능을 함께 유지하는 데 메모리, 연산, 에너지, 저장공간이 얼마나 필요한가? 어느 부하에서 처리 능력의 한계가 드러나는가? 자원 소모와 지원 부하 범위는 구별한다. |
| **V-07 결함 허용성과 복구성** | Reliability → Fault tolerance / Recoverability | 장애 중 필요한 기능과 무관한 업무를 유지하는가? 장애 뒤 근거가 남은 상태와 제어를 올바르게 복원하는가? |
| **V-08 변경 용이성과 모듈성** | Maintainability → Modifiability / Modularity | 계약이나 기능이 바뀔 때 변경의 영향이 어디까지 퍼지고, 다른 책임을 훼손하지 않고 수정과 검증을 할 수 있는가? |
| **V-09 분석 및 시험 용이성** | Maintainability → Analysability / Testability | 실패의 원인을 구분하기 쉬운가? 필요한 사건과 장애를 통제하고 기대 결과를 판정하기 쉬운가? 원인 분석과 시험 가능성은 각각 확인한다. |
| **V-10 기밀성** | Security → Confidentiality | 허용된 대상과 목적에만 정보를 읽고 제공하며, 철회 또는 삭제 뒤의 신규 사용을 막는가? |
| **V-11 상호운용성과 공존성** | Compatibility → Interoperability / Co-existence | 외부 제품과 교환한 정보의 의미를 보존해 기능을 수행하는가? 다른 PC 앱과 자원을 공유할 때 서로의 필요한 기능을 방해하지 않는가? 두 질문을 별도로 본다. |
| **V-12 조작 용이성과 사용자 오류 방지** | Interaction capability → Operability / User error protection | 사용자가 현재 상태와 제어 대상을 알아보고 원하는 동작을 할 수 있는가? 잘못된 대상이나 범위를 조작하는 일을 막는가? |
| **V-13 설치 용이성** | Flexibility → Installability | 필요한 runtime과 helper를 설치, 갱신 또는 제거할 수 있는가? 실패했을 때 남은 dependency와 자료의 상태를 파악하고 정리할 수 있는가? |

**§3은 이 13개 관점의 충돌, §4는 구체 상황에서의 관찰, §5는 04~05로 가져갈 질문을 연결한다.** 각 문제에 13개 모두의 효과를 억지로 만들지는 않는다. §4에는 현재 시나리오에서 인과가 드러나는 관점을 쓰고, 아직 연결되지 않은 관점은 비적용 확정이 아닌 구조 탐색에서 재점검할 항목으로 남긴다. 04~05에서는 각 구조에 대해 13개 모두를 점검하여 영향 경로 또는 영향 없음의 근거, 미확인 사항을 기록한다. 불리한 관점을 조용히 빼지 않는다.

묶인 부특성 사이에 다른 효과가 생기면 각각 설명한다. 예를 들어 연동 기능을 잘 유지하더라도 다른 PC 앱과의 공존은 나쁠 수 있다. 이것을 하나의 점수로 합치지 않는다. 관점의 추가, 분리 또는 통합이 필요하면 전체 목록과 연결표를 함께 검토하며 특정 DP에서만 의미를 바꾸지 않는다. 아래 우선순위는 이번 구조 탐색과 비교의 검토 순서다. 최종 QA와 ASR의 구성, 지표와 방법은 아직 미확정이다.

ISO의 Safety 특성도 전체 모델에 존재하지만 현재 저장소의 “safety qualification”이라는 이름과 동일시하지 않는다. 이 단계의 권한, 오실행, 복구 문제는 위의 실제 품질 경로로 다룬다. 별도 위해 상황과 인과가 제시되지 않은 상태에서 Safety 점수를 새로 만들지 않는다.

### 2.1 이번 비교의 우선순위

사용자가 제시한 순위를 분리된 관점에 이어 적용한다. 기존 기능 완전성과 적절성의 1순위는 V-02와 V-03에, 시간 특성의 2순위는 V-04와 V-05에 함께 적용한다. 같은 순위 안의 우열이나 수치 가중치를 새로 정하지 않는다.

| 우선순위 | 관점 |
| --- | --- |
| 공동 1순위 | V-01 기능 정확성, V-02 기능 적절성, V-03 기능 완전성 |
| 공동 2순위 | V-04 상호작용 반응성, V-05 VIA 귀속 요청 완료 시간 |
| 3순위 | V-08 변경 용이성과 모듈성 |
| 4순위 | V-06 자원 활용성과 수용량 |
| 5순위 | V-07 결함 허용성과 복구성 |
| 공동 6순위 | V-09 분석 및 시험 용이성, V-10 기밀성, V-11 상호운용성과 공존성, V-12 조작 용이성과 사용자 오류 방지, V-13 설치 용이성 |

높은 순위의 작은 이익으로 다른 품질의 모든 손실을 무시하거나 하나의 가중 총점으로 합치지 않는다. 기능 완전성도 중요한 비교 대상이지만 완전 충족을 대안의 사전 통과 조건으로 강제하지 않는다.

### 2.2 정확성, 적절성, 완전성의 경계

V-01은 요청을 이해하는 정확성과 VIA가 관계, 상태와 전달을 처리하는 정확성을 함께 다룬다. V-02는 목표 달성에 필요한 사용자 수고를, V-03은 제공하는 기능의 범위를 본다. Downstream Agent 내부의 업무 계획과 도구 실행 품질은 VIA의 정확성으로 평가하지 않는다.

예를 들어 “보고서를 만들고 완성된 보고서로 발표자료도 만들어줘”라는 요청에서 잘못된 보고서로 후속 요청을 시작하는 것은 V-01이다. 사용자가 결과를 옮기고 같은 내용을 재설명해야 하는 부담은 V-02다. 결과 의존 요청의 자동 연결을 지원하지 않는 기능 범위는 V-03이다. 같은 사건이 여러 관점에 영향을 줄 수 있지만 효과를 독립 표본처럼 중복 합산하지 않는다. 누락 기능을 사용자에게 떠넘긴 경우 완전성과 적절성 양쪽의 영향을 드러낸다.

### 2.3 반응성과 완료 시간의 경계

V-04는 필요한 개별 응답과 제어 효과까지, V-05는 요청의 최종 결과를 실제로 전달하는 전체 경로까지 본다. 빠른 접수 안내가 요청 완료를 대신하지 않는다. 대화 반응을 우선한 구조가 업무 진행을 늦추거나 그 반대가 될 수 있으므로 두 관점을 각각 비교한다. 직접 응답에서는 일부 구간이 겹칠 수 있으며 두 값을 더해 총점을 만들지 않는다.

**두 관점 모두 VIA 귀속 시간을 다룬다. Downstream Agent의 내부 대기, reasoning, 계획과 업무 실행 시간은 외부 조건이며 VIA의 성능으로 평가하지 않는다.** Agent가 오래 걸려도 그 시간 자체는 VIA의 책임이 아니다. 같은 외부 profile 아래 VIA가 만든 준비, 내부 queue, 경합, 인계, 후속 해제, 결과 검증과 전달 지연을 관찰한다. 외부 대기 중 상태가 쌓여 VIA에 생긴 추가 지연은 제외하지 않는다. 다른 dependency도 물리적 위치만으로 비용을 제외하지 않고 책임 경계에 따라 포함 및 제외 구간을 공통으로 정한다.

전체 사용자 경과 시간을 확인하더라도 외부 실행과 사람의 답변 대기를 섞어 VIA 시간으로 보고하지 않는다. 불필요한 사용자 작업은 V-02에 남긴다. 병렬 실행과 겹친 구간을 고려해야 하므로 전체 경과 시간에서 외부 시간의 합을 단순 차감하거나 VIA 처리 시간을 무조건 합산하는 계산식을 지금 채택하지 않는다. 정확한 사건 경계, 귀속 및 집계 방법은 모든 DP와 방안에 같은 계약으로 정한다.

## 4. 문제별 품질 시나리오

여기서 **대상**은 관찰할 시스템 책임이다. 대안에 target의 Component 배치를 강제하지 않는다. **기대 반응**은 [승인된 02-00](./02-00-requirements-and-choices.md)의 R/B를 구체 상황에 적용한 것이다. **관찰**은 후속 검증에서 확인할 항목이며 이번에 측정했다는 뜻이 아니다. 관찰은 §2의 같은 V 관점을 각 상황에 적용한 예다. 기대 반응은 완전 지원 시의 비교 기준이며 모든 후보의 진입 조건이 아니다. 제한된 안의 지원 차이는 V-03에, 수동 우회 부담은 V-02에 기록한다. 문제별로 다른 정의나 대표 지표를 채택한 것이 아니며 정확한 지표와 측정 방법은 전체 DP 공통으로 정한다. U 번호는 [02-00 §5](./02-00-requirements-and-choices.md#5-지원이-필요하다는-것과-이미-확보했다는-것은-다르다)의 미검증 지원을 가리킨다.

## 6. 이후 비교에서 같은 조건으로 유지할 것

이 절은 후속 비교를 위한 경계다. 시험 계약이나 수치를 지금 freeze하지 않는다.

### 6.1 모든 DP와 모든 방안에서 같은 QA를 사용한다

**2026-10-01 사용자 명시 합의: 같은 QA를 채택했다면 모든 DP와 모든 방안에서 동일한 정의, 동일한 지표, 동일한 측정 방법을 사용한다. 이 DP에서는 이렇게, 다른 DP에서는 다르게 정의하거나 측정하는 것은 금지한다.** 이 원칙은 이후 DP 선발, QA 구체화, 측정 계약과 결과 해석까지 적용한다.

예를 들어 Functional correctness를 채택한다면 어떤 DP에서는 의미 field 정답률, 다른 DP에서는 검색 recall, 또 다른 DP에서는 업무 성공률을 각자 대표값으로 정하고 같은 QA라고 부를 수 없다. 어떤 지표를 쓸지는 아직 미정이지만, 확정할 때는 모두가 참조할 공통 계약으로 정한다. 공통 계약이 여러 관찰을 포함할 수도 있으나 구성과 집계 규칙 역시 모든 DP와 방안에 동일하게 적용해야 한다.

| 공통으로 고정할 것 | DP 또는 방안별로 바꾸면 안 되는 것 |
| --- | --- |
| 품질 정의와 평가 단위 | 같은 QA를 한곳에서는 모델 정확성, 다른 곳에서는 제품 업무 성공으로 재해석하기 |
| 지표와 판정 | 정답 기준, oracle, 분자와 분모, 단위, 가중치, 집계, 실패 및 timeout 처리의 개별 변경 |
| 측정 방법 | 관찰 시작과 종료, 포함 및 제외 비용, 입력 및 부하 구성 규칙, 반복과 관측 절차의 개별 변경 |
| 모집단과 적용 규칙 | 같은 QA 이름 아래 유리한 사례만 고르거나 불리한 사례를 제외하여 평가 대상을 바꾸기 |
| 계약 version과 결과 해석 | 서로 다른 정의나 방법으로 얻은 값을 같은 QA의 비교 가능한 결과로 제시하기 |

구조마다 품질에 영향을 주는 경로는 다를 수 있다. 그 차이는 공통 계약이 정한 적용 규칙으로 설명하며, QA 자체를 바꾸는 이유가 되지 않는다. 내부 계측 위치나 adapter가 달라도 같은 사용자 사건, 관찰 경계와 판정에 연결해야 한다. 미참여와 미지원, 미확인은 동등이나 0점으로 바꾸지 않는다. 추가 진단을 붙일 수는 있지만 공통 QA를 대체하거나 DP별 대표 지표로 바꿀 수 없다.

QA의 권위 정의와 측정 계약은 **한 공통 원본**에서 관리하고 모든 DP가 같은 version을 참조한다. 개정이 필요하면 공통 원본과 영향받는 모든 DP를 함께 검토한다. 이전 결과는 원래 계약과 함께 보존하고 새 결과와의 비교 가능성을 다시 판정한다. 측정 전에는 모든 DP 및 모든 방안의 정의, 지표, 방법, 모집단 적용 규칙이 같은 계약인지 확인한다. 기존 문서의 DP별 평가 기록을 이 원칙의 예외 근거로 사용하지 않는다.

### 6.2 공통 평가 계약을 구체화할 때의 경계

| 경계 | 유지할 원칙 |
| --- | --- |
| 사용자 결과 | 같은 목표와 요구 목록을 기준으로 비교하되 일부 기능을 포기한 대안도 포함한다. V-03에 지원 차이와 사용자 영향을 드러내며 대안별로 요구 목록을 축소하지 않는다. 02-00의 T를 모든 안에 복제하지 않는다. |
| 외부 지원 | 동일 Agent/source/OS capability와 같은 모델 제약을 적용한다. Downstream Agent 내부 실행 시간은 외부 조건으로 두고 V-04와 V-05에는 VIA 귀속 시간만 평가한다. 추가 helper나 저장소가 필요하면 설치, 자원, 장애, 변경, 삭제 비용을 포함한다. U 미확인을 성공 조건으로 가정하지 않는다. |
| 환경과 부하 | 같은 장비, 입력과 자료 변화, 동시 업무, 외부 앱 부하, 장애 및 변화 상황을 사용한다. warm/cold, 정상/포화, 확인 가능/불명 조건을 나눠 본다. FA의 평가 조건을 제품 최대치로 확대하지 않는다. |
| 실제 관찰 경계 | 실제 사용자 또는 외부 사건과 software 인지를 구분하고 구조가 만든 비용을 숨기지 않는다. 구체 시작과 종료, 포함 및 제외 구간과 관측 절차는 품질 질문에 맞게 공통으로 설계한다. 기존 endpoint 계약을 자동 채택하지 않는다. |
| 기존 QA의 취급 | 이전 정의와 결과의 의미는 보존한다. 새 비교에서는 품질 질문에 맞는지 검토한 뒤 재사용 또는 개정한다. 재사용할 때는 기존 의미를 정확히 지키고, 개정할 때는 공통 원본에서 변경 이유와 영향 범위를 기록한다. 어느 경우도 DP별 별도 정의나 분모 산정 규칙을 허용하지 않는다. |
| 실패와 한계 | 잘못된 빠른 결과, 누락, timeout, 미복구를 남긴다. 필요한 기능이 미지원이어도 후보는 비교에 남기며 V-03의 손실로 드러낸다. 빠른 거절을 성공 완료로 세거나 미지원 사례를 평가 대상에서 조용히 빼지 않는다. 공통 지원 범위의 시간 및 자원 비교는 그 범위를 명시하고 전체 기능 차이와 함께 보고한다. 수치의 실패 처리는 후속 공통 계약에서 정한다. 현재 target도 U 지원이 확보됐다고 주장하지 않는다. |
| 조합과 중복 | P-02/14의 입력 근거, P-03/12의 파생 자료, P-05/06/13의 재개 상태처럼 공통 비용과 효과를 두 번 세지 않는다. 조합에 따라 충돌이 바뀌면 해당 의존성을 기록한다. |

5단계에서는 실제 target을 방안 1, 같은 문제를 푸는 강한 구조를 방안 2로 놓고 **ISO 품질 → 구체 조건 → (+)/(-)/(0) → 쉬운 이유 → 확인할 근거** 순서의 표를 만든다. `(0)`은 실제로 같은 한정 경로 등 근거가 있을 때만 쓰고, 지원이나 상대 결과가 미확인이면 **미확인**으로 표시한다. 이번 단계에는 두 구조가 아직 없으므로 우열 기호를 붙이지 않는다.

후속 DP의 ASR 적용은 확정될 ASR 집합에 대해 `PRIMARY`, `REGRESSION_ONLY`, `NOT_APPLICABLE`, `UNRESOLVED`로 판단한다. 현재 13개 관점의 시나리오 연결은 그 DP 적용 판정이 아니다. 04~05에서 13개 모두를 검토하고 ASR의 최종 구성도 그 근거로 논의한다. 낮은 우선순위를 이유로 실제 영향을 받는 축을 빼거나, 한 축의 실패 때문에 다른 축의 근거를 지우지 않는다.

## 7. 사용자 리뷰와 다음 단계

| 이번에 확인할 내용 | 의견을 남기는 예 |
| --- | --- |
| 실제 VIA에서 중요한 충돌인가? | “P-xx에서는 이 비용보다 ○○가 더 중요하다.” |
| 기능 축소의 이익과 사용자 손실을 함께 드러냈는가? | “이 기능을 포기한 안도 비교하되 지원 범위와 우회 부담을 적자.” |
| 충돌의 조건과 관찰 항목이 충분한가? | “△△ 부하 또는 실패 조건이 빠졌다.” |
| 13개 관점이 문서 전체와 후속 단계까지 이어지는가? | “V-xx는 §2에만 있고 구체 시나리오나 후속 질문이 부족하다.” |

현재 P-01~16의 품질 시나리오 작성과 작성자 대조를 마쳤으며 [검토 기록](./03-01-quality-review.md)에 범위와 검사 결과를 남긴다. 사용자 검토 뒤 4단계의 여러 구조 탐색으로 이어간다. 기존 네 비교안을 자동 선정하지 않으며 target, QA 의미와 지위, ADR, 이전 증거를 변경하지 않았다. 구현, 모델 실행, 성능 측정, 수치 freeze는 수행하지 않았다.

## 참고 — 기존 QA 자료의 위치와 취급

[기존 Core ASR 계약](../../08-quality-attributes/core-asr-contract.md), [기존 event 경계 계약](../../11-measurement/event-boundary-contract.md)과 기존 평가 기록은 이전 정의와 결과를 해석할 때 사용한다. 이번 품질 질문의 지표나 방법을 자동으로 결정하지 않는다. 재사용 여부는 13개 관점의 시나리오와 실제 구조 차이를 검토한 뒤 전체 DP 공통 계약을 설계할 때 판단한다. 기존 정의와 결과는 원래 의미로 보존하며, 현재 target의 설계 우선순위를 새 QA 구성과 동일시하지 않는다.
