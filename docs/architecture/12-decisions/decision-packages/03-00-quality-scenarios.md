# 3단계 — VIA의 품질 요구는 어떤 상황에서 충돌하는가

> 상태: **STAGE_3_REVIEW_READY / 사용자 검토 대기** / 2026-10-01
> 입력: 승인된 [02-00 요구와 해결 수단](./02-00-requirements-and-choices.md), [01-00 중요 문제 원장](./01-00-problem-coverage.md)
> P-01~16의 품질 시나리오와 충돌을 정리했다. 구조 대안, DP, 새로운 ASR을 선정한 문서가 아니다.

## 1. 이번에 검토할 핵심

**같은 사용자 결과를 지키더라도, 그것을 얻는 데 필요한 시간과 자원, 장애 대응, 변경 비용은 서로 달라질 수 있다.** 3단계에서는 그 차이가 중요해지는 상황을 찾는다. 4단계에서 여러 구조를 탐색할 때 무엇을 설명해야 하는지 정하기 위한 자료다.

예를 들어 “아까 가리킨 자료”를 정확히 찾으려면 당시 근거가 필요하다. 근거를 풍부하게 남기면 사후 확인에 도움이 될 수 있지만, PC 자원과 접근 통제, 삭제 처리가 늘어난다. 반대로 적게 남겨도 같은 대상을 확인할 수 있다면 비용을 줄일 수 있다. 어느 쪽이 가능한지는 입력의 모호함, 자료 변화, 실제 지원 기능에 달려 있다. **많이 저장하면 항상 정확하거나, 적게 저장하면 항상 안전하다고 미리 결론 내리지 않는다.**

읽는 순서는 **§2의 품질 기준 → §3의 충돌 요약 → §4의 관심 있는 P 상세 → §5의 추가 품질 검토 제안**이다. §4의 각 표는 자극, 환경, 대상, 기대 반응, 충돌, 관찰 항목을 갖는다. P 하나가 하나의 DP나 독립 QA라는 뜻은 아니다.

### 절충으로 허용하지 않는 것

[02-00 §2](./02-00-requirements-and-choices.md#2-모든-문제에-공통으로-적용할-경계)의 R/B는 유지한다. 당시 화면 대신 마지막 화면으로 답하기, 모호한 대상을 임의 확정하기, 철회된 정보를 쓰기, 확인 가능한 업무를 복구하지 않기, 입력만 받고 정상 요청을 영원히 미루기는 성능을 위한 절충으로 인정하지 않는다. 필수 기능을 뺀 제한 모드도 전체 요구를 만족한 안과 구별한다.

아래 충돌은 **조건부 설계 가설**이다. 요구 충족 여부와 각 품질의 실제 값은 나중에 같은 조건에서 확인해야 한다. 규칙을 지키겠다는 선언만으로 정확성이나 신뢰성이 동등한 것은 아니다. 현재는 목표 수치, 가중치, workload, 시험 모집단을 동결하지 않는다.

## 2. 어떤 품질을 보고 있는가

기준은 **ISO/IEC 25010:2023 제품 품질 모델**이다. 판본은 [ISO 공식 소개](https://www.iso.org/standard/78176.html), 기능 적합성, 성능 효율성, 호환성 및 아래 상호작용 부특성은 [공개 원문 preview의 §3.1~3.4](https://cdn.standards.iteh.ai/samples/78176/13ff8ea97048443f99318920757df124/ISO-IEC-25010-2023.pdf)를 확인했다. 나머지 기존 QA 대응과 공개 자료의 한계는 [저장소의 ISO 대응 근거](../../08-quality-attributes/iso-25010-quality-basis.md)를 따른다. 아래 한국어 설명과 VIA 시나리오는 우리 과제의 적용 해석이며 표준의 공식 번역이나 적합성 인증이 아니다.

| ISO 특성 → 부특성 | 이번 문서에서 묻는 질문 | 현재 QA와의 관계 |
| --- | --- | --- |
| Functional suitability → Functional correctness | 목표, 대상, 실행, 전달 사실을 맞게 연결하는가? | QA-19는 QA-11/12의 해당 field를 집계한다. QA-13~15의 추가 관계 및 연속성 판정은 별도 회귀다. |
| Functional suitability → Functional completeness / Functional appropriateness | 필요한 기능을 모두 제공하는가? 충분한 근거가 있는데도 사용자에게 같은 선택이나 설명을 반복시키는가? | 기능 누락 점검은 1단계 추적을 사용한다. 불필요한 사용자 단계는 추가 검토 대상이며 QA-19의 새 분모로 넣지 않는다. |
| Performance efficiency → Time behaviour | 유효한 답, 제어 상태, 정상 진행을 얼마나 기다리는가? | QA-09와 QA-01/02/03/05가 기존 기준이다. 음성 중단 QA-04는 별도 회귀다. |
| Performance efficiency → Resource utilization / Capacity | 같은 PC에서 요구를 유지하는 데 어떤 자원이 들며, 어느 부하에서 진행이 막히는가? | 메모리 QA-41은 진단이다. CPU, 에너지, 저장공간, 지원 부하 범위는 추가 관찰 제안이다. |
| Reliability → Fault tolerance / Recoverability | 장애가 무관한 업무까지 막는가? 정상 근거가 남은 업무를 올바르게 되살리는가? | QA-39와 QA-31/32. 재시작 시간만으로 복구 성공을 판정하지 않는다. |
| Maintainability → Modifiability / Modularity | 같은 계약 변화가 어느 책임, interface, 상태 schema, 배포 요소의 변경으로 이어지는가? | QA-29와 QA-21~23. 파일 수나 Component 수를 줄이는 것 자체가 개선은 아니다. |
| Maintainability → Analysability / Testability | 오류 원인을 찾고, 사건 순서를 통제하여 계약을 시험하기 쉬운가? | QA-61/62가 필요한 근거를 지원한다. 근거 완전성과 분석 또는 시험 용이성 전체는 다르다. |
| Security → Confidentiality | 읽기, 제공, 보관, 삭제의 허용 범위를 지키는가? | QA-51과 접근 규칙은 필수 qualification이다. 검사 및 삭제 비용은 별도의 시간과 자원 항목에서 본다. |
| Compatibility → Interoperability / Co-existence | 같은 지원 조건의 외부 제품과 의미를 보존해 연동하는가? 다른 PC 앱과 자원을 공유해도 필요한 기능이 유지되는가? | P-07, 14, 15의 추가 검토 대상이다. 실제 연동 기능과 개발 변경량 QA-29를 구별한다. |
| Interaction capability → Operability / User error protection | 사용자가 실제 상태를 알고 원하는 업무를 제어할 수 있는가? 잘못된 대상의 조작을 막는가? | P-06, 08, 09의 추가 검토 대상이다. 내부 binding 정확성만으로 사용자의 제어 용이성을 대신하지 않는다. |
| Flexibility → Installability | 필요한 runtime과 helper를 설치하거나 제거할 때 기능 및 남은 자료의 상태가 분명한가? | P-14, 15의 조건부 추가 검토 대상이다. 다운로드 크기만으로 설치 용이성을 판정하지 않는다. |

현재 core ASR는 QA-19, QA-09, QA-29, QA-39이고 target 설계 우선순위도 이 순서를 유지한다. **이 네 가지가 앞으로 탐색할 품질의 상한은 아니다.** 이 문서는 새 ASR의 채택, 우선순위 변경 또는 기존 QA 정의 수정을 하지 않는다. 메모리는 사용자가 중요성을 제기한 ASR 후보로 검토하되 QA-41을 자동 승격하지 않는다.

ISO의 Safety 특성도 전체 모델에 존재하지만 현재 저장소의 “safety qualification”이라는 이름과 동일시하지 않는다. 이 단계의 권한, 오실행, 복구 문제는 위의 실제 품질 경로로 다룬다. 별도 위해 상황과 인과가 제시되지 않은 상태에서 Safety 점수를 새로 만들지 않는다.

## 3. 여러 문제에 걸친 품질 충돌 요약

각 행은 DP 후보가 아니라 함께 살필 충돌이다. 두 품질이 항상 반비례한다는 주장도 아니다. 뒤의 조건에서 실제 비용이 발생하는지 설명할 수 있어야 한다.

| 함께 볼 문제 | 개선하려는 품질 | 함께 생길 수 있는 비용과 이유 | 차이를 좌우할 조건 |
| --- | --- | --- | --- |
| P-01, 02, 03 | 정확한 목표와 당시 대상 확인 | 근거 획득과 재확인이 응답 시간을 늘린다. 미리 보존한 자료는 메모리, 저장, 갱신 및 삭제 처리가 필요하다. | 지칭의 모호함, 화면 변화 속도, source 읽기 비용, 시간 근거의 오차 |
| P-01, 06, 08 | 오해나 잘못된 업무 조작 방지 | 불필요한 재질문은 사용자 단계를 늘린다. 자동 연결의 범위를 넓히면 잘못된 승인이나 취소 위험이 생긴다. | 유효 후보 수, 실제 제시된 질문, 답변 지연과 정정 시점 |
| P-04, 09, 10 | 빠른 직접 응답과 끊기지 않는 후속 대화 | 허용 판단, 채널별 전달 확인, 대화 반영에 시간이 들고 상태가 늘어난다. 미사용 생성은 자원을 소모한다. | 자체 지식인지 자료 의존인지, 중도 인계 빈도, 음성 중단과 재접속 |
| P-05, 06, 07, 13 | 중복 없는 대기 재개와 복구 | 내구 기록, 외부 확인, 결과 version 검사가 정상 경로의 쓰기와 통신을 늘린다. | 중복 및 역순 사건, 저장 지연, 외부 조회 지원, 장애 직전의 전송 상태 |
| P-08, 14 | 즉각적인 입력과 제어, 정상 요청의 지속 진행 | 입력 보호에 쓴 실행 및 메모리 여유만큼 다른 작업이 기다릴 수 있다. 취소해도 backend 연산은 계속될 수 있다. | 연속 발화, 비선점 연산 길이, 동시 추론, 전체 메모리와 열 제한 |
| P-03, 10, 11, 12 | 빠른 재사용과 과거 대화의 연속성 | 오래된 파생 자료가 많으면 현재 권한과 삭제를 적용할 경로가 늘어난다. 재구성은 다시 읽고 처리하는 비용이 든다. | 자료 변경과 철회 빈도, 보존 기간, 파생 관계 추적, 재접속 빈도 |
| P-07, 15 | 제공자 교체의 변경 범위 제한 | 공통 표현이 다른 제공자의 의미를 담지 못하면 기능 손실이나 별도 확장이 생긴다. 확장이 퍼지면 변경 범위도 넓어진다. | 실제 capability 차이, event 및 질문 계약, 진행 중인 실행과 저장 형식 |
| P-13, 15 | 오래된 상태를 정확히 복원하고 변경 후에도 유지 | 재구성, 검증, migration이 복구 시간을 늘리고 시험해야 할 상태 조합이 많아진다. | 미완료 상태의 양, 상태 version, 외부 실행의 생존 기간, 저장 장애 |
| P-11, 12, 16 | 원인 분석과 평가 재확인 | 상세 근거에는 보관 자원과 접근 통제 비용이 든다. 원문을 남길 수 없으면 사후 분석의 한계가 커질 수 있다. | 사전 수집 동의, 삭제 요청, 필요한 원인 구분 수준, 사건 연결의 누락 |

## 4. 문제별 품질 시나리오

여기서 **대상**은 관찰할 시스템 책임이다. 대안에 target의 Component 배치를 강제하지 않는다. **기대 반응**은 [승인된 02-00](./02-00-requirements-and-choices.md)의 R/B를 구체 상황에 적용한 것이다. **관찰**은 후속 검증에서 확인할 항목이며 이번에 측정했다는 뜻이 아니다. U 번호는 [02-00 §5](./02-00-requirements-and-choices.md#5-지원이-필요하다는-것과-이미-확보했다는-것은-다르다)의 미검증 지원을 가리킨다.

<a id="p-01"></a>
### P-01. 빠진 조건을 보완하면서 요청을 확정하기

| 항목 | 시나리오 |
| --- | --- |
| 자극과 환경 | 사용자가 “아까 그 자료 보내줘”라고 말한 뒤 수신자를 정정한다. 이미 읽을 수 있는 자료와 후보가 여러 개인 자료를 구분하며 음성 인식과 의미 해석이 충돌하는 경우도 포함한다. |
| 대상과 기대 반응 | 요청 해석, 근거 확보, 질문과 확정 경계. 충분한 근거는 활용하고 미해결 후보는 묻는다. 새 답변과 정정을 반영하되 먼저 확정한 유효 조건을 잃지 않는다. |
| 품질 충돌 | 기능 정확성 ↔ 시간 특성, 자원 활용성, 기능 적절성. 더 읽고 재해석하면 잘못된 확정을 줄일 여지가 있지만 대기와 모델 사용이 늘어난다. 항상 질문하면 자동 확정 오류를 피할 수 있어도 불필요한 사용자 단계가 늘어난다. |
| 조건별로 확인할 차이 | 정보가 이미 명확할 때의 추가 처리 비용과, 불명확할 때 근거 보완의 효과를 나눠 본다. 같은 모델의 두 역할이 일치했다는 사실만으로 독립 검증 효과를 주장하지 않는다. |
| 관찰과 기존 QA | 확정한 목표, 대상, 제약의 정오와 정정 반영(QA-19의 해당 field), 유효 확정 또는 질문까지의 시간, 추가 읽기와 추론량, 불필요한 재질문. 사람의 답변 대기와 VIA 처리 시간을 나눈다. 질문 수를 QA-19에 합산하지 않는다. |
| 근거와 지원 | [02 P-01](./02-00-requirements-and-choices.md#p-01), B-05, U-01/03/04 |

<a id="p-02"></a>
### P-02. 화면이 바뀐 뒤에도 말한 당시의 대상을 찾기

| 항목 | 시나리오 |
| --- | --- |
| 자극과 환경 | 사용자가 여러 항목을 가리키며 “이것들은 남기고 저것만 바꿔”라고 말한다. 화면은 계속 바뀌고 전사는 늦게 수정된다. 구조 정보가 없는 화면, 시간 오차와 관측 gap도 포함한다. |
| 대상과 기대 반응 | 음성 및 화면 근거의 생산, 시간 결합, 보존. 당시의 집합과 역할을 유지하고 불명확한 범위를 드러낸다. 과거 관측이 현재 Action 대상의 유효성을 보장하지는 않는다. |
| 품질 충돌 | 기능 정확성 ↔ 시간 특성, 자원 활용성, 기밀성 유지 비용. 촘촘한 근거는 변화를 구별할 여지가 있지만 capture와 저장 부하를 늘린다. 늦은 전사를 기다리면 정확한 연결 기회와 함께 대기가 늘어난다. |

| 제안 | 중요한 이유와 연결 문제 | 다음 단계에서 확인할 조건 | 현재 지위 |
| --- | --- | --- | --- |
| 메모리를 ASR 후보로 명시 검토 | P-02, 03, 10, 12, 14의 근거, 파생 자료, model 작업 상태가 같은 PC에 쌓인다. 메모리 부족은 기능 진행과 복구에도 영향을 줄 수 있다. | 공유 weights 외에 encoders, decoder, helper, KV, activation, IPC/buffer, 저장소 cache와 OS 여유를 포함한다. 상주량과 재구성 시 peak를 구분하고 공통 비용과 구조별 차이를 함께 설명한다. | 사용자 제기 후보. QA-41은 진단 그대로이며 예산, 우선순위, 승격 여부 미정 |
| 지속 부하에서의 수용량과 공존성 | P-14의 평균 응답이 좋아도 특정 요청이 계속 밀리거나 다른 PC 앱을 방해할 수 있다. | 입력 인식과 foreground 진행을 함께 유지하는 부하 범위, queue 증가, 자원 압박을 본다. 장비와 외부 부하를 같게 두며 평균 응답만으로 판단하지 않는다. | Capacity와 Co-existence의 추가 시나리오 제안. 제품 최대치 미확정 |
| 불필요한 사용자 단계와 제어 용이성 | P-01, 06, 08, 09, 10에서 같은 정보를 반복 설명하거나 현재 제어 대상을 다시 찾게 만들 수 있다. | 필요한 확인은 유지한다. 불필요한 질문과 반복 선택, 실제 상태를 이해하고 조작할 수 있는 근거가 구조에 따라 달라지는지 본다. 문구만 다른 비교는 구조 DP가 아니다. | Functional appropriateness, Operability, User error protection의 추가 검토 |
| 의미를 보존하는 상호운용성 | P-07, 15의 공통 interface가 같은 기능을 표현하는지, 외부 기능을 깎아 맞추는지 확인해야 한다. | 동일 제공자 profile의 질문, 취소, 결과, source revision을 양쪽에서 처리하는가? 지원 자체가 다른 경우는 별도 환경 조건으로 둔다. | Interoperability 추가 검토. QA-29와 별도 질문 |
| 분석 및 시험 용이성 | P-05~09, 11~13, 16의 경쟁 상태와 실패 원인을 확인하지 못하면 구조의 주장을 검증하기 어렵다. | 필요한 순서와 장애를 통제할 수 있는지, 원인을 구분할 근거가 허용 범위 안에 있는지 본다. 기록량 증가를 개선으로 단정하지 않는다. | QA-61/62 qualification 유지. 추가 속성의 대표 지표는 미정 |
| 메모리 외 자원과 설치 부담 | P-03, 12~15의 준비 작업, 내구 쓰기, 복구 및 helper가 CPU, 에너지, 디스크, 설치 절차에 영향을 줄 수 있다. | 자원별 원인을 분리하고 요청 밖의 준비 및 정리 비용도 포함한다. 설치 및 제거의 실제 절차가 달라질 때만 설치 용이성을 비교한다. | Resource utilization의 추가 관찰과 조건부 Installability 검토 |

기밀성과 접근 및 Action 규칙은 위 후보와 별개로 계속 필수다. 위반을 응답성이나 메모리 이익으로 상쇄하지 않는다. 추가 품질이 기존 QA와 같은 실패를 설명하더라도 가중 총점에 중복 반영하지 않는다.

## 6. 이후 비교에서 같은 조건으로 유지할 것

이 절은 후속 비교를 위한 경계다. 시험 계약이나 수치를 지금 freeze하지 않는다.

| 경계 | 유지할 원칙 |
| --- | --- |
| 사용자 결과 | 같은 목표, 완료 조건, 정정, 권한, 삭제 및 복구 요구를 둔다. 02-00의 T를 모든 안의 공통 조건으로 복제하지 않는다. |
| 외부 지원 | 동일 Agent/source/OS capability와 같은 모델 제약을 적용한다. 추가 helper나 저장소가 필요하면 설치, 자원, 장애, 변경, 삭제 비용을 포함한다. U 미확인을 성공 조건으로 가정하지 않는다. |
| 환경과 부하 | 같은 장비, 입력과 자료 변화, 동시 업무, 외부 앱 부하, 장애 및 변화 상황을 사용한다. warm/cold, 정상/포화, 확인 가능/불명 조건을 나눠 본다. FA의 평가 조건을 제품 최대치로 확대하지 않는다. |
| 실제 관찰 경계 | [Event & Boundary Contract](../../11-measurement/event-boundary-contract.md)를 따른다. 실제 발화 종료와 software 인지, source 상태 발생과 VIA 수신, 생성과 audible 전달을 구분한다. IPC, 검증, 저장, playback 비용을 경로에서 숨기지 않는다. |
| 기존 집계 | QA-09의 applicable QA-01/02/03/05 평균, QA-19의 QA-11/12 field 집계, QA-29의 해당 변화별 Architecture Element, QA-39의 fault trial 성공 조건을 보존한다. 추가 관찰을 기존 분모에 임의로 넣지 않는다. |
| 실패와 한계 | 잘못된 빠른 결과, 누락, timeout, 미복구를 남긴다. 필요한 기능이 미지원이면 적용 한계를 밝히고 같은 기능의 성공으로 처리하지 않는다. 현재 target도 U 지원이 확보됐다고 주장하지 않는다. |
| 조합과 중복 | P-02/14의 입력 근거, P-03/12의 파생 자료, P-05/06/13의 재개 상태처럼 공통 비용과 효과를 두 번 세지 않는다. 조합에 따라 충돌이 바뀌면 해당 의존성을 기록한다. |

5단계에서는 실제 target을 방안 1, 같은 문제를 푸는 강한 구조를 방안 2로 놓고 **ISO 품질 → 구체 조건 → (+)/(-)/(0) → 쉬운 이유 → 확인할 근거** 순서의 표를 만든다. `(0)`은 실제로 같은 한정 경로 등 근거가 있을 때만 쓰고, 지원이나 상대 결과가 미확인이면 **미확인**으로 표시한다. 이번 단계에는 두 구조가 아직 없으므로 우열 기호를 붙이지 않는다.

후속 DP의 ASR 적용은 확정될 ASR 집합에 대해 `PRIMARY`, `REGRESSION_ONLY`, `NOT_APPLICABLE`, `UNRESOLVED`로 판단한다. 지금 문제별로 QA를 연결한 것은 그 DP 적용 판정이 아니다. 낮은 우선순위를 이유로 실제 영향을 받는 축을 빼거나, 한 축의 실패 때문에 다른 축의 근거를 지우지 않는다.

## 7. 사용자 리뷰와 다음 단계

| 이번에 확인할 내용 | 의견을 남기는 예 |
| --- | --- |
| 실제 VIA에서 중요한 충돌인가? | “P-xx에서는 이 비용보다 ○○가 더 중요하다.” |
| 필수 결과를 절충 가능한 품질로 잘못 풀었는가? | “이 상황의 ○○는 느려져도 반드시 유지해야 한다.” |
| 충돌의 조건과 관찰 항목이 충분한가? | “△△ 부하 또는 실패 조건이 빠졌다.” |
| 추가 품질을 더 검토해야 하는가? | “메모리 외에 ○○도 구조 탐색에서 따로 보자.” |

현재 P-01~16의 품질 시나리오 작성과 작성자 대조를 마쳤으며 [검토 기록](./03-01-quality-review.md)에 범위와 검사 결과를 남긴다. 사용자 검토 뒤 4단계의 여러 구조 탐색으로 이어간다. 기존 네 비교안을 자동 선정하지 않으며 target, QA 의미와 지위, ADR, 이전 증거를 변경하지 않았다. 구현, 모델 실행, 성능 측정, 수치 freeze는 수행하지 않았다.
