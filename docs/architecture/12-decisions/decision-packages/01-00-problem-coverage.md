# VIA 중요 문제 원장 — 1단계 공동 검토본

> 상태: **STAGE_1_REVIEWED_FOR_STAGE_2 / 공동 검토 후 2단계 진행 승인** / 2026-10-01
> 사용자와 문제 원장과 VIA 특성을 검토한 뒤 [2단계 요구/수단 분리](./02-00-requirements-and-choices.md) 진행과 GitHub 반영을 승인받았다. 이후 발견사항에 따라 문제 범위는 근거와 함께 보완할 수 있다.
> 문제 ID `P-01~16`은 추적용이다. **16개 DP를 선정했다는 뜻이 아니다.**

## 먼저 읽을 결론

초기 10개는 모두 VIA와 관련이 있지만, 응답, 대화, 기억, 동의를 너무 크게 묶었고 자원 포화와 검증 근거를 충분히 드러내지 못했다. 제품 목적에서 다시 추출하고 고정 요구, UC, 운영, 변화 조건으로 역검토한 결과, **공동 검토할 문제를 16개 영역으로 정리했다.** 기능별 Component를 만들거나 DP 수를 늘리기 위한 분해가 아니다. 각각의 실패와 완료 조건을 별도로 설명할 필요가 있는지로 나눴다.

현재 확정된 범위 안에서 빠뜨린 요구가 없는지를 확인했다. 이 기록은 **문제 탐색의 coverage**이지 구현 검증, target 결함 판정, ASR 변경 또는 모든 미래 VIA 기능의 포괄을 의미하지 않는다. 중요성은 제품 목적, 실패 피해와 여러 흐름에 미치는 영향으로 설명한다. 사용 빈도와 발생 확률이 없으므로 점수, 순위, 가중 총점은 만들지 않았다.

## 왜 중요한 문제로 남겼는가

- **과제의 핵심 경험:** P-01~04, 09, 10이 깨지면 자연스러운 Voice/Text/화면 interaction과 업무 인계라는 VIA의 목적을 달성하지 못한다.
- **잘못된 업무와 통제 상실 방지:** P-05~08, 11~13이 깨지면 대상 혼동, 무단 제공, 삭제 무효와 중복 실행 등 단순 답변 수정으로 끝나지 않는 실패가 생긴다.
- **실제로 운영하고 발전시킬 조건:** P-14~16은 PC 자원 한계, 외부 생태계 변화, 품질 주장 검증에 관한 문제다. 단일 정상 시연만으로는 드러나지 않지만 여러 사용자 흐름 전체에 영향을 준다.

이 세 묶음은 우선순위 점수가 아니다. **중요 문제라는 판단과 주요 DP로 선발할지는 별개**다. 여러 문제를 하나의 구조 선택이 풀 수도 있고, 중요한 문제라도 합리적인 구조 대안 차이가 작아 DP로 선정되지 않을 수도 있다. 그 판단은 4~6단계에서 한다.

## 일반적인 업무 Agent와 비교한 VIA의 특성

여기서 비교 대상은 **Text로 업무를 요청받아 계획을 세우고 Tool로 실행하는 일반적인 Agent**다. 다른 제품도 음성, 화면, 다중 업무를 지원할 수 있으므로 아래는 VIA만 독점적으로 가진 기능의 목록이 아니다. [제품 목적](../../01-system-mission-and-boundary.md#11-system-mission)과 [고정 책임 경계](../../03-fixed-architecture-scope.md#34-via에-고정되는-책임)에 비추어 **VIA의 설계를 설명할 때 특히 두드러지는 문제**를 구분한 것이다.

VIA는 사용자의 말, 화면, 대화를 계속 받아들이면서 직접 응답과 여러 외부 Agent의 업무를 같은 사용자 창구로 연결한다. 이 특성이 강하게 드러나는 문제는 **P-02, 04, 06, 08, 09, 10**이다. **P-14**는 현재 검토 완료 target의 on-device 공유 모델 조건에서 특히 중요한 실행 제약이다.

| 문제 | VIA에서 특히 두드러지는 특성 | 직관적인 상황 |
| --- | --- | --- |
| **P-02 화면 지칭** | 말, 포인터, 선택, 화면 변화의 **시간 관계**를 함께 해석한다. 화면을 한 번 읽는 것으로는 부족하다. | 두 문서를 오가며 “여기와 저기를 비교해줘”라고 했을 때, 마지막 화면이 아니라 각각 지시한 당시의 대상을 찾는다. |
| **P-04 직접 응답과 업무 인계** | S2S 직접 대화, Context 기반 설명, 외부 Agent 업무를 **같은 대화에서 이어간다.** | 설명을 듣다가 “방금 내용으로 발표자료 만들어줘”라고 하면 Task 없이 했던 답을 업무의 근거로 넘긴다. |
| **P-06 여러 업무, 질문 연결** | 사용자가 Agent나 thread를 직접 선택하지 않아도 **하나의 대화에서 여러 업무를 구별한다.** | 두 Agent가 각각 질문한 상황에서 “그건 취소하고, 아까 것은 계속해”를 올바른 업무에 연결한다. |
| **P-08 중단, 정정, 취소** | 계속 듣는 음성 interaction에서 **말을 멈추는 것, 요청을 고치는 것, 실제 업무를 취소하는 것**이 교차한다. | “잠깐”이라고 하면 설명은 멈추지만 뒤에서 만드는 보고서까지 취소하지 않는다. |
| **P-09 실제 응답 전달** | 답변 생성, Text 표시, 음성 재생은 각각 다른 사건이고, **실제로 재생된 범위**가 후속 대화의 근거가 된다. | 첫 항목만 재생된 뒤 사용자가 끼어들었다면, 나머지 내용까지 들려준 것으로 기록하거나 후속 요청에 사용하지 않는다. |
| **P-10 채널과 업무의 연속성** | 음성 연결, Conversation, Task, 외부 실행의 **수명이 서로 다르다.** | Voice를 끄고 Text로 돌아와도 업무는 이어지고 앞서 설명한 내용을 다시 참조한다. |
| **P-14 PC 자원 경합** | 현재 target에서는 한 PC의 공유 Omni가 음성, 의미 처리를 담당하는 동안 **입력, 제어, 정상 업무를 함께 진행**해야 한다. | 긴 문서를 해석하는 중에도 새 말을 인식하고 중단을 받으며, 반복 입력 때문에 기존 업무를 무기한 밀어두지 않는다. |

아래 문제들도 VIA에서 중요하지만, **제목만 보면 일반적인 Agent에도 필요한 문제**다. VIA의 입력, 대화, 위임 책임을 함께 설명해야 이 과제에서 다루는 어려움이 선명해진다.

| 문제 | 일반적인 문제 | VIA에서 추가되는 조건 |
| --- | --- | --- |
| **P-01 요청 이해** | 불완전한 지시 보완 | 발화, 화면, 정정, 진행 업무를 함께 해석한다. |
| **P-03 Context 확보** | 올바른 자료 검색, 조회 | 현재 화면, 과거 대화, 외부 업무 결과를 연결한다. |
| **P-05 복합 요청** | 순서, 조건, 결과 의존성 유지 | 직접 답변, 새 업무, 기존 업무 취소가 한 발화에 섞인다. 업무 내부 계획은 Agent 책임이다. |
| **P-07 Agent 연동** | 외부 실행의 기능, 상태 연결 | 서로 다른 Agent의 질문, 취소, 결과를 VIA의 단일 창구로 제공한다. |
| **P-11 동의와 승인** | 권한과 승인 통제 | PC 자료 읽기, 외부 제공, Agent Action 승인이 서로 다른 경계에 있다. |
| **P-13 복구** | 상태 복원, 중복 실행 방지 | VIA가 재시작해도 외부 Agent 업무는 계속될 수 있고 응답 전달 상태도 별도로 확인한다. |
| **P-15 변경 대응** | 제공자, 계약, 저장 형식 변화 수용 | 음성, 의미 모델, PC 정보원, 여러 Agent가 바뀌어도 같은 interaction을 유지한다. |

**P-12 개인화 기억과 P-16 원인 분석과 평가 근거**는 현재 정의만으로는 공통 기반 문제에 가깝다. VIA에도 필요하지만 그 자체만으로 VIA의 특색을 설명하기는 어렵다. 이 구분은 발표에서 문제를 소개할 때의 설명력에 관한 **1단계 검토 의견**이며 중요도 순위나 DP 선발 결과가 아니다. 구조 대안과 품질 차이는 후속 단계에서 검토한다.

## 문제별 상황, 중요성, 어려움과 완료 조건

아래의 “어려움”은 SW가 함께 보존해야 하는 관계와 충돌이다. 아직 해결 Component, 알고리즘, 정책을 선택하지 않았다. 근거의 구체적인 UC 변형과 예외는 [사용자 흐름 추적표](./01-01-problem-coverage-use-cases.md), 운영, 변화, 품질 항목은 [횡단 점검표](./01-02-problem-coverage-crosscutting.md)에 연결했다.

### P-01. 불완전한 말에서 사용자가 원하는 일을 확정하기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | “아까 그 자료로 정리해줘”에서 자료, 결과 형식, 수신자가 빠졌거나 중간에 바뀐다. |
| 이 과제에서 중요한 이유 | 잘못된 일을 정확하게 수행해도 사용자 목표는 실패한다. 특히 잘못된 수신자, 대상은 외부 변경으로 이어질 수 있다. |
| Architecture 관점에서 어려운 점 | 입력, 이전 대화, 화면, 확인 답변이 서로 다른 시점에 도착한다. 확정한 조건은 보존하면서 부족한 조건만 다시 물어야 하고, 모호함을 억지로 해소해서는 안 된다. |
| 지켜야 할 결과 | 목표, 대상, 제약과 확인 필요 여부가 맞고, 답변은 원래 요청을 보완한다. 새 목표, 철회는 별도로 인식한다. 같은 발화의 부정, 숫자, 수신자 등이 입력 근거와 해석에서 충돌하면 임의 확정하지 않는다. |
| 근거 | UC-06; UC-01.3, UC-09.5 |
| 인접 문제와의 경계 | 문장의 의미와 확정 여부가 초점이다. 화면 근거는 P-02, 질문의 업무 연결은 P-06, 정정의 효력은 P-08이다. |

### P-05. 한 번에 부탁한 여러 일의 관계를 잃지 않기

| --- | --- |

| 근거 | UC-09 전체; UC-14 |
| 인접 문제와의 경계 | 사용자가 명시한 관계가 대상이다. 단일 업무의 Tool 순서, 조사 전략, 업무 분석을 통한 조건 판단은 Agent 책임이다. Workflow Engine을 미리 전제하지 않는다. |

### P-06. 여러 업무와 대기 질문 사이에서 정확한 대상을 이어가기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | 같은 Agent가 두 업무를 실행하고 각각 질문한 상황에서 사용자가 “응, 그건 계속해”라고 한다. |
| 이 과제에서 중요한 이유 | 질문 답변, 수정과 취소가 다른 업무에 반영되면 사용자 통제를 잃는다. 한 업무의 대기 때문에 전체 대화가 멈춰도 실패다. |
| Architecture 관점에서 어려운 점 | 사용자 목표, 결과물, VIA Task, 외부 실행, 개별 질문의 수명이 다르다. 완료된 실행 뒤에도 같은 업무가 이어지고, 같은 자료로 새 업무를 만들 수도 있다. |
| 지켜야 할 결과 | 답, 상태를 원래 Request/질문에 연결하고 관련 Task가 있으면 그 Task/실행도 연결한다. Task 없는 직접 응답 요청도 확인 대기할 수 있다. 기존 결과 수정과 별도 새 목표를 구분하고, 모호하면 확인하며 무관한 업무는 유지한다. |
| 근거 | UC-06.4, UC-10, 14, UC-16.5 |
| 인접 문제와의 경계 | 어느 업무/질문인가가 초점이다. 관계 자체는 P-05, 실제 Agent 계약은 P-07, 허용할 수 있는 답인가는 P-11이다. |

<a id="p-07"></a>
### P-07. Agent가 실제 할 수 있는 일과 실제 처리 상태를 연결하기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | Agent마다 질문, 취소, 후속 요청, 결과 조회의 지원 방식이 다르고 접수 뒤 완료 통지가 늦게 온다. |
| 이 과제에서 중요한 이유 | 연결 성공을 업무 성공으로 착각하거나 지원하지 않는 기능을 약속하면 사용자는 일을 맡길 수 없다. |

| 지켜야 할 결과 | 가능한 Agent에 목표, 제약, 허용 자료를 전달하고 접수/진행/완료/실패/미확인을 구별한다. 질문, 결과물과 후속 실행을 같은 업무에 연결한다. |
| 근거 | UC-08, 10, 12, 13, 18; FA-13 |
| 인접 문제와의 경계 | 평상시 외부 계약 처리다. 장애 후 재연결은 P-13, 제공자/프로토콜의 계획된 변경은 P-15이다. Agent 내부 복구와 실행 능력은 VIA 범위 밖이다. |

### P-08. 말 끊기, 정정과 업무 취소를 각각 맞는 효과로 반영하기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | 음성을 끊은 직후 옛 응답이 도착하거나, 발송 취소와 Agent 완료가 동시에 발생한다. |
| 이 과제에서 중요한 이유 | 원치 않는 음성이 되살아나거나 정정 전 요청이 실행되면 즉각적인 사용자 통제가 무의미해진다. |

| 근거 | UC-11, 12, UC-04.6, UC-06.5 |
| 인접 문제와의 경계 | 음성 중단은 업무 취소가 아니다. 이미 수행한 외부 변경을 소급 취소했다고 말하지 않는다. 처리 여력은 P-14, 중단된 전달 기록은 P-09이다. |

### P-11. 정보 접근, 외부 제공과 업무 승인을 현재 허용 범위에 묶기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | 자료 읽기는 허용했지만 외부 전달은 거부하거나, 여러 승인 중 하나에만 “응”이라고 답한다. |
| 이 과제에서 중요한 이유 | 허용하지 않은 정보 제공이나 잘못된 Action 승인은 나중에 답을 고치는 것으로 회복할 수 없다. |

| 지켜야 할 결과 | 접근/제공 Consent와 Action Approval을 구별하고 유효한 대상에만 반영한다. 거부, 축소, 철회, 늦은 승인에도 허용 범위를 넘지 않는다. 문서, Agent 내용의 지시문을 사용자 명령, 승인으로 승격하지 않는다. |
| 근거 | UC-16 전체; 03 §3.4 Policy; QA-51 |
| 인접 문제와의 경계 | 모든 일반 질의에 새 승인 절차를 요구하지 않는다. 이미 외부로 제공된 정보의 소급 회수를 보장하지 않는다. 질문 identity는 P-06, 기억 삭제는 P-12이다. |

<a id="p-12"></a>
### P-12. 허용된 기억을 쓰되 사용자가 바꾸고 잊게 할 수 있기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | 장기 선호를 저장한 뒤 “이번에는 다르게”, “그 선호는 잊어줘”라고 한다. 오래된 요약이 나중에 도착할 수도 있다. |
| 이 과제에서 중요한 이유 | 잘못 저장한 개인 정보나 삭제한 선호가 계속 살아나면 개인화의 신뢰가 무너진다. |
| Architecture 관점에서 어려운 점 | 임시 지시와 지속 기억을 구분하고, 원본뿐 아니라 파생 맥락, 늦은 결과, 복구 후 재사용까지 삭제 효과를 유지해야 한다. |
| 지켜야 할 결과 | 허용된 preference/routine/stable fact를 사용하고 확인, 등록, 변경, 삭제할 수 있게 한다. 현재 요청을 우선하고 임시 지시를 무단 승격하거나 삭제 기억을 재사용하지 않는다. |
| 근거 | UC-17 전체; target memory-and-context-lifecycle §5 |
| 인접 문제와의 경계 | User Memory와 RAM 사용량(P-14)은 다른 문제다. 대화 삭제, 업무 취소와 외부 정보 회수도 기억 삭제와 같은 효과로 취급하지 않는다. |

<a id="p-13"></a>
### P-13. 문제가 생겨도 일을 잃거나 중복 실행하지 않고 복구하기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | Agent에 요청을 보낸 직후 VIA가 죽거나 결과 저장 뒤 화면 반영 전에 멈춘다. 외부 상태를 확인할 수 없을 때도 있다. |
| 이 과제에서 중요한 이유 | 사용자는 업무를 다시 설명해야 하고, 무심한 재시도로 메일 발송 같은 외부 변경이 중복될 수 있다. |
| Architecture 관점에서 어려운 점 | 로컬 기록, 외부 실행, 사용자 전달이 동시에 완료되지 않는다. 복구 가능한 장애와 확인할 근거가 사라진 경우를 구별하고 무관한 기능을 살려야 한다. |
| 지켜야 할 결과 | 근거가 남은 기본 조건에서는 진행 업무/완료 결과를 실제 재연결한다. 확인 불가이면 정직하게 안내하고 중복 시작하지 않는다. 부재, 거부, 미지원, 부분 실패도 구별한다. |
| 근거 | UC-18 전체; FA-14 세 조건; target 예외 목록 |
| 인접 문제와의 경계 | Agent 내부 checkpoint 복구, 물리 재해, 모든 장애의 자동 복원은 요구하지 않는다. UNKNOWN 안내만으로 복구 가능한 기본 사례를 통과시킬 수 없다. |

<a id="p-14"></a>
### P-14. 제한된 PC 자원에서도 입력과 제어를 놓치지 않기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | 긴 의미 추론, 화면 근거, 여러 Task, 음성 출력이 겹치고 메모리나 저장 공간이 부족해진다. |
| 이 과제에서 중요한 이유 | 평소에는 동작해도 사용 중 입력이나 취소가 멎거나 기록을 잃으면 PC 상시 interaction 소프트웨어로 사용할 수 없다. |
| Architecture 관점에서 어려운 점 | 시간에 민감한 입력, 제어와 무거운 계산, 저장이 자원을 함께 쓴다. 대기, 거부, 축소를 하더라도 필요한 근거와 사용자 통제를 몰래 희생해서는 안 된다. |
| 지켜야 할 결과 | 음성 capture/recognition과 제어가 의미 추론에 통째로 막히지 않는다. 입력과 제어를 보호하는 동안에도 지원 범위의 정상 요청, 결과 처리가 무기한 밀리지 않는다. 처리 불가, 용량 한계, 저장 실패를 명시하고 기존 업무/근거를 정상인 것처럼 훼손하지 않는다. |
| 근거 | QC-06, 07; QA-41; FA-08, 10; shared-omni-runtime |
| 인접 문제와의 경계 | 최대 Task 수, 자원 상한, latency 수치는 아직 제품 보장이 아니다. 독립 ASR, queue, 특정 scheduling은 문제 정의가 아니라 이후 검토할 수단이다. |

<a id="p-15"></a>
### P-15. 외부 연동과 저장 형식이 바뀌어도 사용자 기능을 유지하기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | 모델 이벤트, 입력 한도, 배치, Agent 실행/질문 계약, Source나 저장된 대화 형식이 바뀐다. |
| 이 과제에서 중요한 이유 | 교체 때마다 대화, 권한, 업무 기능이 깨지거나 광범위한 수정이 필요하면 변화가 빠른 생태계에서 제품을 유지하기 어렵다. |
| Architecture 관점에서 어려운 점 | API 포장만 아니라 identity, 완료 의미, 인증, 수명, 저장 데이터가 바뀐다. 기존 데이터와 삭제 효과, 진행 업무의 연결까지 보존해야 한다. |
| 지켜야 할 결과 | 제공자, 계약, 형식이 바뀌어도 기존 요청 처리, 대화/업무 연결, 허용 범위, 삭제 효과가 유지되고, 기록 이행에 실패하면 기존 자료를 보존한다. 24개 M/A/C 및 5개 E 변화에서 추가/교체/공존/이행의 차이를 확인한다. |
| 근거 | 07 M-01~09, A-01~09, C-01~06; QA-21~23 |
| 인접 문제와의 경계 | 계획된 변화다. 무중단 교체, Agent 내부 실행의 자동 이전, 모든 앱 지원을 요구하지 않는다. 구조 변경량 평가는 이후 단계이며 지금 계산하지 않는다. |

<a id="p-16"></a>
### P-16. 보호정보를 과다 기록하지 않고 원인과 평가 근거를 확인하기

| 관점 | 내용 |
| --- | --- |
| 대표 상황 | 잘못된 대상이나 중복 응답이 발생했는데 어떤 입력, 자료, 실행, 정정이 원인인지 알 수 없다. 과거 평가 결론도 재계산되지 않는다. |
| 이 과제에서 중요한 이유 | 오류를 설명하고 고칠 수 없고, 심사에서 제시한 품질 주장을 검증할 수 없다. 단순 로그 양으로 신뢰를 확보할 수 없다. |
| Architecture 관점에서 어려운 점 | 흩어진 요청, 자료 revision, 실행, 전달을 연결하면서 비밀 원문 노출을 제한해야 한다. 운영 원인 재구성과 평가 재계산은 서로 다른 완료 조건이다. |
| 지켜야 할 결과 | 실행의 입력 근거, 처리, 상태, 결과 관계를 확인할 수 있고, 평가 시에는 보존한 근거/설정/판정 도구로 동일 결론을 재계산할 수 있어야 한다. |
| 근거 | QC-10; QA-61, 62; E-01~05 |
| 인접 문제와의 경계 | 평가 근거 요건을 일상 사용자 기능으로 부풀리지 않는다. 모델을 재실행하여 똑같은 문장을 만들라는 뜻도 아니다. 실제 로그/측정 구현은 이번 범위 밖이다. |

## 초기 10개에서 무엇을 바꿨는가

| 초기 질문 | 처리 | 새 원장에서 보존한 것과 변경 이유 |
| --- | --- | --- |
| 1. 요청 이해, 확정 | 분리 | P-01 의미, 확인과 P-05 명시적 복합 관계를 구별. 언어 이해가 맞아도 후속 실행 관계를 잃을 수 있음 |
| 2. 말한 시점의 화면 | 유지하고 보강 | P-02. 집합/범위/보존, 수정 역할과 화면, 전사 교차를 명시 |
| 3. Context 확보 | 유지하고 경계를 명확히 함 | P-03. 현재/과거 자료, 출처와 최신성, 내용 읽기. 허용 여부는 P-11, 기억 관리 자체는 P-12 |

| 5. 정정, 중단, 취소 | 유지하고 보강 | P-08. 위임 전후, 이미 완료, 미확인의 효과를 구별 |
| 6. 여러 업무, 대기 질문 | 분리 | P-06 업무/질문 연결과 P-05 의존 관계. 하나의 “상태 관리”로 둘을 뭉개지 않음 |
| 7. Agent 위임, 연동 | 분리 | P-04 직접 처리/위임의 책임과 P-07 외부 계약/실제 상태. 가능한 처리 구조를 탐색할 질문이 달라짐 |
| 8. 응답, 기억, 통제 | 분리하고 재배치 | P-09 실제 전달, P-10 대화 수명, P-12 지속 기억. 여러 초기 질문에 흩어진 동의/승인을 P-11로 명시 |

| 초기 목록에서 묻힌 관심사 | 명시적 추가 | P-16 원인 재구성, 평가 근거. P-14 자원 전체 및 P-11 정보/실행 통제도 독립 완료 조건을 드러냄 |

## coverage의 확인 범위와 남은 검토

- [사용자 흐름 추적표](./01-01-problem-coverage-use-cases.md): 18개 UC의 **94개 명명된 필수 변형**, 각 UC의 정상/실패 조건, 공통 8원칙과 화면 경계 유형을 대조한다.
- [횡단 점검표](./01-02-problem-coverage-crosscutting.md): 고정 책임, FA-01~16, 24개 M/A/C 변화, 5개 E 변화, QC-01~10 및 현재 QA, 주요 교차 예외를 대조한다.
- [검토 기록](./01-03-problem-coverage-review.md): 작성자와 별도 검토자의 발견사항, 수정, 재검토 및 검사 결과를 남긴다.

**공동 검토에서 확인한 질문:** 이 16개가 VIA의 중요한 문제를 빠뜨리지 않았는지, P-04/P-07과 P-09/P-10 등의 구별이 설계 탐색에 유용한지, 중요성을 과장하거나 불필요하게 세분한 영역은 없는지 검토했다. 수량보다 문제의 의미와 경계가 먼저다. 사용자는 VIA 특성 설명을 확인한 뒤 요구/현재 수단을 분리하는 2단계 진행을 요청했다.

상세 device 상한, 발생 빈도, 모델/Agent capability의 실증, QA 수치 목표는 현재 자료로 확정하지 않았다. 이들은 문제 목록의 누락과 구별되는 후속 설계와 검증 사항이다. 기존 네 DP, target, ASR 지위 및 정의, ADR은 보존했다.
