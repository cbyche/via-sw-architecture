# 공통 변경 과제와 자원 가정의 근거

2026-10-21 / **SYNTHETIC_AUTHORED_NOT_MEASURED**

이 문서는 새 공통 합성 평가의 QA04 변경 과제, QA05 비용 경계와 QA06 자원 해석을 설명한다. 수치는 설계 가정을 계산한 예시다. 실제 Rust diff, 모델 호출, 메모리 계측이나 제품 달성값으로 해석하지 않는다. 기존 합성 자료, COMMON-28, 공통9 계약과 과거 실측은 원래 판본으로 보존한다.

## 1. 비교 구성과 가상 모듈의 의미

| 구성 | DP2 의미 판단 실행 | DP5 위임 관계의 해석 | 역할 |
| --- | --- | --- | --- |
| BASE | A 대화 실행 | A 요청 시 관계 해석 | 공통 대조 구성 |
| EXEC | B 요청별 실행 | A 요청 시 관계 해석 | DP2만 교체 |
| REL | A 대화 실행 | B 사전 관계 메모리 | DP5만 교체 |

BASE는 최종 채택안이 아니라 효과를 구분하기 위한 고정 비교 조건이다. EXEC와 REL을 직접 비교해 어느 DP가 우수하다고 결론내리지 않는다. DP2 B와 DP5 B의 조합은 별도 구성과 같은 공통 시나리오로 검토해야 하며 두 변화의 개선량을 더해 결과를 만들지 않는다.

[change-spec.json](change-spec.json)의 `concept::` 경로는 **가상 Rust 운영 모듈의 소유 경계를 나타내는 설계 식별자**다. 실제 저장소에 해당 모듈이 존재하거나 이 파일을 수정했다는 주장이 아니다. 동일 기능과 같은 공통 adapter 경계를 먼저 가정한 뒤 변경 책임을 추적했으며, 상자 수를 세거나 특정 안의 점수를 맞추기 위해 모듈을 분할하지 않았다.

| 가상 모듈 | 변경 책임과 사전 가정 |
| --- | --- |
| `concept::model_wire` | 모든 VIA 의미 호출의 provider 요청, 응답, 취소, usage를 같은 내부 계약으로 변환 |
| `concept::agent_wire` | 후속 위임과 취소 및 receipt 형식의 정규화 |
| `concept::source_normalization` | 외부 화면, 이력 자료의 좌표, 원본 시각, source/revision/extent 정규화 |
| `concept::response_sections` | 실제 텍스트 표시와 section patch, 출처 표시용 응답 표현 |
| `concept::delivered_history` | 실제 전달한 내용과 판본 및 원본 근거 연결의 보존, 조회 |
| `concept::speech_queue` | 준비된 음성 중 아직 전달하지 않은 section의 교체, 무효화 |
| `concept::permission_scope` | 문서와 구간별 현재 사용 허용 범위의 소유 |
| `concept::evidence_access` | 실제 원본 읽기와 모델 입력의 현재 허용 범위 적용 |
| `concept::publication_guard` | 준비한 출력, 새 인계 직전 현재 판본과 권한의 재검사 |
| `concept::relation_dependencies` | REL의 파생 관계와 원본 span 의존, dirty/revoked 갱신. 공통 권한 판정과 원본 접근을 재사용 |

현재성, 권한, 실제 전달 이력과 이미 확정한 사실의 재사용은 모든 기본안의 필수 기능이다. B만 별도 검사비용을 내는 것처럼 표현하지 않는다. 관계 생산은 별도 물리 서비스나 모델 가중치 복제를 요구하지 않는다.

## 2. 모든 구성에 적용하는 C01~C06

요구의 정본은 [QA04 상세 명세 §4](../qa-candidate-package/qa04-change-scope.md#4-지표와-공통-변경-모집단)와 [COMMON-28 변경 과제](../qa-candidate-package/common-scenarios.md#6-개발-변경-과제와-qa07-대조-실행)다. [공통9 계약 §6](../seven-problem-review/19-common9-evaluation-contract.md#6-모든-구성의-동일한-qa04-과제)의 동일 과제, 독립 시작점 원칙도 따른다. 공통9는 Voice OFF PoC에 맞춰 C04를 text section으로 한정했지만, 이번 설계 변경 분석은 원 C04의 **대기 음성까지 포함한 기능 요구**를 사용한다. 런타임 합성표의 음성 범위와 이 개발 변경 분석의 범위를 혼동하지 않는다.

| 과제 | 같은 완료 요구의 요약 | BASE | EXEC | REL |
| --- | --- | ---: | ---: | ---: |
| C01 | 모델 wire가 바뀌어도 요청, 지칭, 취소, usage 의미 유지 | 1 | 1 | 1 |
| C02 | Agent wire가 바뀌어도 identity와 실제 접수, 완료, 취소 구별 | 1 | 1 | 1 |
| C03 | 좌표, 시각, 판본 형식이 바뀌어도 같은 위치와 대상 집합 | 1 | 1 | 1 |
| C04 | 지정 section과 그 대기 음성만 교체하고 실제 전달 이력, 나머지 section, 다른 Task 보존 | 3 | 3 | 3 |
| C05 | 실제 전달한 설명에 원본 위치, 판본을 표시하고 미전달 자료 제외 | 2 | 2 | 2 |
| C06 | 구간 철회를 신규 사용, 대기 출력, 파생 관계에 적용하고 허용 구간 유지 | 3 | 3 | 4 |
| **합계 / 과제 수** | **여섯 독립 변경의 동일 비중** | **11/6** | **11/6** | **12/6** |

모든 행은 `DESIGN_CHANGE_REVIEW`이며 실제 수정 완료나 수용 검사 통과가 아니다. C01 적용 결과를 다음 과제에 누적하지 않는다. 과제 안에서 같은 모듈은 한 번 세며, 다른 과제에서 다시 바뀌면 각 과제에 한 번 포함한다. 부모 모듈과 테스트 및 생성 결과를 자동 가산하지 않는다. 실제 구현 시 소유 prompt/schema/config와 연결 코드의 수정까지 추적해야 한다.

DP2 실행 분리는 여기의 공통 변환, 게시 책임을 바꾸지 않는다고 가정했으므로 BASE와 EXEC는 동점이다. DP5 REL의 작은 추가 수는 **C06에서 문서 단위 관계 무효화를 구간 단위로 확장한다는 구현 가정**에서만 발생한다. 파생 관계에 source span을 이미 저장한 기본 요구는 유지한다. 관계 모듈이 공통 범위 판정기를 그대로 사용한다면 추가 수정 없이 같은 과제를 수행할 수도 있다. 이때 REL도 11/6이 되며, 이를 감춰 구조의 필연적 열위로 주장하지 않는다.

C04는 기존 source revision 변경의 dirty/원본 보완 경로를 재사용한다. C05도 기존 provenance를 공통 전달 결과에 연결하므로 REL producer의 변경을 추가하지 않았다. 관계 저장소가 있다는 사실만으로 매 과제의 변경 수를 늘리거나, 미래 consumer 재사용을 이번 여섯 과제에서 확인한 이익으로 만들지 않는다.

## 3. QA05 비용 경계와 이전 세대 보존

이번 공통 합성판은 [원 QA05 정의](../qa-candidate-package/qa05-model-cost.md#1-발표-한-장에-넣을-내용)에 맞춰 **VIA의 음성, 의미 모델 사용 비용**을 대표 QA05로 계산한다. 준비, 관계 생산, 갱신, 미소비 생산, 현재 요청, 원본 보완, 실패, 재시도, 폐기, 후속 정산을 모두 포함한다. 동일한 모델, 단가, usage bucket 가정을 모든 구성에 적용한다.

| 원장 | 포함하는 비용 | 이번 사용 |
| --- | --- | --- |
| `C_VIA` | VIA가 수행한 요청 이해, 근거/관계 생산, 응답/음성 준비 및 그 유지, 실패 비용 | QA05 대표 원값 |
| `C_receiver` | Downstream Agent/receiver가 수행한 업무 해석, 계획, 실행 모델 비용 | 별도 진단. 숨기거나 VIA 비용으로 재분류하지 않음 |
| `C_total = C_VIA + C_receiver` | 같은 episode의 두 역할 모델 비용 합계 | 구조 변경으로 비용이 외부로 이동했는지 확인하는 보조값 |

[공통9 계약 §5](../seven-problem-review/19-common9-evaluation-contract.md#5-qa별-같은-측정과-집계)는 당시 PoC의 **실제 receiver까지 포함한 전체 모델 비용**을 보고했다. 그 승인된 세대의 수치, 분모, 명칭은 그대로 보존한다. 이번 분리는 과거 결과를 소급 수정하는 것이 아니라 새 합성판의 명시적인 비용 범위다. 기존 수신자 포함 금액을 새 QA05로 이름만 바꾸지 않으며, 원장에 역할 구분이 없다면 해당 값은 변환 불가로 둔다.

공통 활동 묶음이 28개 전체가 아니라면 그 비용은 해당 새 묶음의 USD 값이다. 기존 `$2.55 / COMMON-28` 목표, 점수를 일부 사례의 비용에 바로 적용하거나 사례 수로 단순 환산하지 않는다. 관계 producer가 새 입력과 경합한 시간은 QA01/03에도 남기되 동일 호출 비용은 원장에 한 번만 센다. local code/helper에 API 청구가 없다는 것은 CPU, RAM, 개발 비용까지 없다는 뜻이 아니다.

## 4. QA06 클라우드 모델 환경의 공통 자원 가정

이번 자원 예시는 **모델이 원격에 있는 동일한 로컬 VIA profile**을 사용한다. 로컬 UI, Core, 공통 코드, 현재 대화와 Task 상태, 실제 원본 복사본, 이미지, 직렬화 버퍼, 요청 작업 상태와 관계 cache/producer 작업 메모리를 포함한다. 원격 모델 가중치, 원격 KV와 외부 Agent의 자체 메모리는 로컬 QA06에 더하지 않는다. 이후 로컬 모델을 배치하는 판본에서는 그 가중치와 runtime/KV를 새 profile에 포함해야 하며 이번 수치를 on-device Omni 제품 값으로 전용하지 않는다.

같은 시각 `t`에서 중복되지 않는 가상 메모리 구간을 다음처럼 둔다.

```text
M_config(t) = 공통 VIA 기반 RAM(t)
           + 공통 원본, 대화, Task 상태(t)
           + 활성 실행의 고유 상태(t)
           + 진행 중 작업의 고유 입력, 출력 버퍼(t)
           + 파생 관계 cache와 producer의 고유 상태(t)

QA06 예시 = max_t M_config(t)
```

현재 생성기는 첫 사용자 입력을 `t=0`으로 두고 REL의 초기 관계 생산을 `t=-8초`에 시작한다. 같은 원본 이력에서 대상 관계와 미사용 관계를 순서대로 생산하며, 두 생산의 종료가 첫 입력보다 앞선다는 계산을 확인한다. 준비에 충분한 시간이 있다는 **명시적인 warm 조건**이다. 준비가 늦어 첫 요청과 경합하는 cold 조건을 검증한 결과가 아니며, 이번 수치의 적용 조건으로 남긴다. 준비가 요청 전이라는 이유로 모델 비용과 로컬 메모리를 관측 범위에서 빼지 않는다.

F05의 정정 원문은 초기 관계 생산이 끝난 뒤 첫 입력 직전인 `t=-0.1초`에 도착한다고 가정한다. 따라서 초기 생산이 읽은 이전 피드백과 U01에서 읽을 수 있는 정정 원문을 구별하며, 생산된 관계는 dirty다. 정정 원문은 별도 평가 입력을 몰래 추가한 발화가 아니라 이 episode 시작 전의 사용자 이력으로 제공한다. F09는 U01 뒤 새로 제공된 외부 검토 메모를 U02에서 참조하는 미생산 조건이며 별도 사용자 발화를 추가하지 않는다.

F05의 dirty 관계와 F09의 미생산 관계는 요청에서 원본을 보완한다. 해당 관계의 추가 갱신은 이번 두 입력의 모든 목표 처리가 종료된 뒤 유휴 구간에 수행한다. 따라서 이번 판본에서는 그 갱신이 QA01/03 임계 경로와 겹치지 않지만, 갱신 모델 사용량과 실제 가정한 생산 상태는 QA05/06에 포함한다. 새 요청이 유휴 갱신 중 도착하는 조건의 손익은 별도 민감도 사례가 필요하다. 갱신을 모든 기본안의 필수 무경합 성질로 일반화하지 않는다.

REL의 관계 cache **38 MB**는 초기 생산부터 종료 후 갱신까지 미리 확보하고 RAM에 상주시킨 전용 영역이라는 가정이다. 주소 공간만 예약한 reserve나 사용하지 않는 commit을 RAM으로 세는 가정이 아니다. 모델 입력 payload와 producer 작업 상태는 이 cache와 겹치지 않는 별도 복사본으로 센다. cache 크기를 실측하거나 38 MB가 필요한 최소 크기를 도출한 것은 아니며, 공유 저장소, 압축, 페이지 교체를 반영하면 새 자원 profile을 만들어 다시 계산해야 한다.

공통 불변 입력을 여러 실행이 참조하면 물리 복사본 가정만 한 번 계산한다. 각 실행이 실제 별도 직렬화 payload를 만든다는 가정이면 그 복사본은 별도로 포함한다. EXEC의 동시 실행은 같은 순간에 살아 있는 상태와 버퍼를 더하고, REL의 producer가 요청과 겹칠 때는 관계 cache, 생산 버퍼, 요청 버퍼를 함께 더한다. REL이 A의 큰 원본 작업 버퍼를 줄이면 그 감소도 같은 시간축에서 반영한다. 추가 저장 책임이 있다고 QA06의 우열을 먼저 정하지 않는다.

**서로 다른 시각의 역할별 최고값을 합산하지 않는다.** episode별 peak의 평균이나 합계도 전체 최고량이 아니다. 공통 자원 시점표의 각 행에서 합을 구한 뒤 전체 최댓값을 선택한다. 최종 MB 값과 최대가 생긴 시점은 그 시점표에서 계산하며 여기서 임의의 최종 수치를 먼저 정하지 않는다.

메모리 값의 종류를 명시한다.

- 이번 표의 MB는 가정한 로컬 RAM이며 `1 MB = 1,000,000 bytes`를 사용한다.
- commit은 OS가 저장 공간을 보장한 양이고 실제 RAM 상주량과 다르다. reserve, 디스크 파일 크기, 원격 token 수를 RAM에 합산하지 않는다.
- 논리 객체 byte와 프로세스 RSS는 서로 다른 관측이다. 둘을 더해 전체 RAM으로 만들지 않는다.
- 공통9의 50ms 최고 동시 RSS는 공유 물리 페이지 중복 제거가 검증되지 않은 PoC proxy다. 이번 합성 RAM 가정이나 실제 Windows 제품 RAM 달성값과 같은 값으로 취급하지 않는다.
- 원 QA06의 512 MB는 사용자 지정 시스템 요구사항으로 유지한다. 합성값이 작더라도 실제 요구 달성을 입증하지 않는다.

기준은 [QA06 상세 명세](../qa-candidate-package/qa06-local-memory.md)의 동일 시각 합산, 전체 최고량, 공유 중복 규칙이다. 구현 후에는 실제 process와 buffer 소유, 시작, 종료, 같은 시각 표본의 완전성을 확인하고 측정 판본을 별도로 남긴다.
