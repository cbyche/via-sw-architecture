## 2026-10-16 최신 사용자 지시: VIA의 QA에서 중요한 기능 설계 문제를 먼저 도출

**탐색의 출발점은 VIA의 QA01~05다.** 이 QA를 만족시키려면 VIA의 어느 기능을 어떻게 설계해야 하는지 먼저 판단한다. 그 기능 설계 문제의 실용적인 A/B/C를 찾기 위해 reference Agent harness의 관련 설계를 조사한다. 아래의 이전 해석은 작성자의 오해였으며 현재 탐색 순서로 사용하지 않는다.

현재 순서는 **`VIA의 QA와 실제 사용 장면 → QA 달성을 좌우하는 기능 → 그 기능의 어려운 설계 문제와 품질 충돌 → 관련 harness의 해결 메커니즘 조사 → VIA의 A/B/C 구성 → QA01~05의 손익과 DP 자격 판단`**이다. 기존 DP 번호와 harness 간 차이 목록은 후보 발굴의 제약으로 삼지 않는다. 기존 DP의 변경이나 제외는 이 탐색만으로 결정하지 않는다.

### QA에서 먼저 물을 VIA의 기능 설계 질문

| QA | 먼저 살펴볼 VIA 기능 | 설계에서 답할 질문 |
| --- | --- | --- |
| QA01 첫 응답 지연시간 | 입력과 Agent 사건을 이해하고 첫 내용 응답을 실제 표시 | 첫 내용 응답 전에 꼭 필요한 근거 취득과 판단은 무엇이며, 어떤 후속 처리는 별도로 진행할 수 있는가? 다른 요청과 사건 때문에 생기는 대기는 어디서 발생하는가? |
| QA02 지칭 대상 식별 정확도 | 말, 포인터, 선택, 화면 변화와 과거 대상을 연결 | 같은 발화의 대상 집합과 시점을 어떻게 보존하며, 빠진 단서와 정정된 범위를 어떻게 다시 확인하는가? |
| QA03 VIA 처리시간 | 근거 조회부터 요청 해석, 위임 준비, 결과 해석과 전달 준비까지 연결 | 어떤 작업이 선행 결과를 반드시 기다려야 하며, 어떤 결과를 재사용하고 어떤 부분을 다시 처리해야 하는가? |
| QA04 변경 범위 | 외부 형식 변경 수용, 응답의 부분 수정, 출처 조회와 구간별 사용 철회 | 이 기능을 바꿀 때 의미, 상태와 전달 책임 중 무엇이 함께 바뀌며, 어떤 계약이 변경 전파를 제한하는가? |
| QA05 모델 사용 비용 | 근거 선택, 의미 해석, 기억 생산, 응답 생성과 정정 후 재판단 | 모델이 읽고 생산하는 정보 중 반복되거나 쓰이지 않는 것은 무엇이며, 재사용과 선행 가공이 실제로 줄이거나 늘리는 비용은 무엇인가? |

이 다섯 행은 다섯 DP를 뜻하지 않는다. 같은 기능이 여러 QA에 영향을 주는 경로를 함께 찾는다. QA02를 일반적인 업무 상태 정확성으로 넓히거나, QA04를 Component 개수로 바꾸지 않는다.

### 기능 중심으로 먼저 구체화할 탐색 영역

아래는 작성자의 초기 작업 분류이며 사용자가 선택한 DP 목록은 아니다.

1. **현재 지칭 대상을 결정하는 근거 처리:** “여기와 여기, 아니 두 번째는 이쪽”에서 말과 실제 지시, 화면 변화 및 정정을 연결한다. 근거를 더 보존하고 검토하는 일과 QA01/03/05의 시간 및 비용이 어떻게 충돌하는지 찾는다.
2. **여러 요청과 업무 사건 속 첫 내용 응답 준비:** 이전 요청의 근거 조회 중 새 질문이나 Agent의 확인 요청이 들어와도 해당 입력의 의미 있는 첫 응답을 만든다. 입력 연결, 필수 판단과 결과 표시의 의존을 먼저 설계하고 실행 분리는 그 대안으로 검토한다.
3. **정정 이후 유효한 작업과 준비된 응답의 재사용:** 조건 일부, 지칭 대상 또는 답변 문단만 바뀌었을 때 어떤 판단과 출력이 영향받는지 결정한다. 재판단 및 재생성 비용과 의존 상태 관리, 부분 수정 기능의 변경 범위를 함께 살핀다.
4. **과거 설명과 여러 업무 결과의 맥락 재구성:** 실제 전달된 설명, 다른 업무의 결과와 자료 버전을 현재 요청에 연결한다. 필요한 근거의 보존 및 회수와 요청 중 처리, 사전 생산 및 유지 비용을 함께 살핀다.

먼저 각 영역의 입력, 필요한 사용자 결과, 병목과 오류 원인, 기능 변경 과제를 적는다. 이후 그 문제를 해결하는 harness 메커니즘을 찾는다. 예를 들어 1번을 조사할 때에는 원본 관측과 구조화된 대상의 취급, 누락된 근거의 추가 조회, 정정 뒤 재판단을 살핀다. 특정 harness 두 개를 먼저 골라 구조 차이를 VIA에 맞추지 않는다.

### reference 조사와 최종 산출물

OpenClaw, OpenHands, Deep Agents, Magentic-One, CrewAI는 문제별 대안의 근거를 찾을 조사 대상이다. 관련 기능이 없는 프로젝트에 억지로 대응을 만들지 않는다. 하나의 harness가 여러 대안의 근거를 제공할 수도 있고, 여러 harness의 실제 메커니즘을 조합해 VIA에 맞는 대안을 만들 수도 있다. 직접 확인한 구현과 VIA를 위해 추가한 설계를 구별한다.

각 후보는 **VIA 사용자 장면 → 중요한 QA와 설계 난점 → 기능 및 책임 범위 → 실제 근거를 가진 A/B/C → 같은 장면의 처리와 QA 손익 → 강한 대안 및 혼합 반론 → 주요 DP 판단** 순서로 설명한다. 중요한 기능 문제의 발견과 방안의 선정은 구별한다. 현재 절은 탐색 방법과 초기 기능 질문의 정정이며 새로운 대안 조사 또는 DP 도출이 완료됐다는 보고가 아니다.

## 2026-10-16 이전 해석: harness 간 차이에서 출발한다는 오해

작성자는 직전 답변에서 사용자의 출발점을 **같은 문제를 해결하는 기존 Agent harness들의 서로 다른 아키텍처를 비교하고, 그 차이에서 VIA의 DP와 A/B를 도출하는 것**으로 해석했다. 사용자가 다시 정정했으므로 이 해석과 아래 순서는 현재 지시가 아니다. 조사한 메커니즘은 후속 기능별 조사에 재사용할 수 있는 근거로 보존한다.

이전 답변은 `harness의 공통 설계 문제 → 실제 서로 다른 책임과 실행 및 상태 구조 → 그 선택의 이익과 비용 → 같은 VIA 문제의 A/B → QA01~05의 차이 가설` 순서를 제시했다. 이 순서는 위의 QA 및 VIA 기능 중심 탐색으로 대체한다. 다음 표는 이전 설명의 이력이다.

| 공통 설계 문제 | 실제 A 근거 | 실제 B 근거 | 여기서 도출할 설계 질문 |
| --- | --- | --- | --- |
| 여러 처리자의 작업을 조정하고 통합 | Magentic-One: 조정자가 공유 진행 맥락과 ledger로 작업자 응답 뒤 다음 담당과 지시를 결정 | Deep Agents: 부모가 작업을 위임하고 child가 독립 문맥에서 내부 loop를 수행한 뒤 결과를 반환 | 중앙이 작업자 응답마다 조정할지, 여러 단계의 판단을 작업 단위로 위임할지 |
| 위임한 작업의 완료를 호출자에게 연결 | OpenHands Task/Delegate 경로: 부모 도구 호출이 child 완료를 기다리고 결과를 반환 | OpenClaw subagent 경로: 별도 세션에서 실행하고 이후 완료를 요청자에 연결. Deep Agents async도 별도 thread/run을 제공 | 위임을 현재 호출의 완료 의존으로 유지할지, 독립 실행과 후속 완료 사건으로 연결할지 |
| 긴 과거 이력을 다음 판단에 제공 | OpenHands condenser: 기록된 event에서 압축한 모델 입력 view를 구성 | CrewAI memory 경로: 결과에서 별도 기억을 추출하고 저장해 이후 회상. OpenClaw의 배경 기억 정리도 관련 근거 | 다음 판단에 과거 이력을 압축해 이어 줄지, 별도 의미 기억의 생산과 검색을 맡길지 |

세 행은 **구조 차이에서 도출한 비교 후보**다. 프로젝트의 모든 모드가 상호 배타적이라는 주장이나 VIA DP 선정 결과가 아니다. 첫째와 둘째는 조정 단위와 실행 수명이라는 서로 다른 축이므로 자동으로 한 A/B에 묶지 않는다. 셋째도 양쪽의 원본 접근, cache와 다른 기억 기능을 함께 확인해야 한다. 공식 코드와 링크는 [조사 기록](../../../references/agent-harness-20261015.md)에 있다.

당시 답변은 VIA의 근거 수집, 요청 이해와 정정, 사용자 질문과 진행/결과 전달에 적용할 것을 제안했다. 외부 Agent의 업무 계획과 실행을 VIA 책임으로 가져오지 않는 경계는 유지한다. 다만 harness 구조부터 설명하던 순서는 위 최신 사용자 지시에 따라 변경한다.

## 2026-10-15 검토 본문

**우선 검토할 주제는 두 가지다. 첫째는 여러 요청을 이해하는 작업 문맥을 주 대화에 모을지, 독립된 활동 문맥으로 나눌지다. 둘째는 과거 근거를 요청별로 조합할지, 생산자가 유지하는 공통 관계로 제공할지다.** 첫째는 VIA 전체의 요청 이해와 대화 실행에 걸친 새로운 비교 방향이고, 둘째는 기존 DP-45를 실제 harness 근거로 보강하는 방향이다. 두 주제를 같은 확신도로 취급하지 않는다. 현재 QA에 대한 손익은 둘째가 더 분명하다.

Conversation과 Task 중 무엇을 중심으로 삼는다는 표현, 별도 실행 수명, 오래된 결과의 채택 권한만으로는 주요 DP의 품질 차이가 충분히 설명되지 않는다. 이 질문들을 실제 문맥, 모델 호출, 중간 상태, 재판단과 전달의 설계로 구체화해야 한다. 강한 중앙 구조도 비동기 실행, Task별 검색, 부분 갱신과 독립적인 외부 업무를 지원할 수 있다.

이 검토는 [현재 QA 정의](./qa-candidate-package/README.md)와 [선정 조건](./00-workplan.md#qa-dp-selection-contract-20261014)을 사용한다. 공식 소스의 확인 사실과 VIA에 적용한 설계, 품질 가설을 구별한다. [다섯 harness의 commit과 상세 구현 근거](../../../references/agent-harness-20261015.md)를 함께 읽을 수 있다. 구현, 모델 실행과 측정 결과는 없다. 기존 DP와 QA 문서는 이 제안으로 변경하지 않는다.

| QA03 VIA 처리시간 | 외부 업무와 사용자 대기를 제거한 실제 인과 경로의 평균. VIA 모델과 검색, 전달 준비는 포함 | Agent가 보고서를 작성하는 시간을 VIA 병렬 처리의 이익으로 세지 않음 |

QA01~04는 현재 DP-RELATED-v2의 원칙대로 구조가 관여하는 관련 관측을 양안에 동일하게 적용한다. 새로운 구조의 S/U/A/B/G/C 적용 목록은 아직 등록하지 않았다. QA05는 공통 전체 28개 묶음을 유지한다. 기존 예상값을 이 구조의 결과로 옮기지 않는다. QA06의 512 MB 요구도 공존 조건으로 남으며 QA01~05의 빈칸을 대신 채우지 않는다.

## 공통 VIA 경계

두 안 모두 LLM으로 발화 의미, 추가 근거의 필요성과 다음 대응을 판단한다. 일반 코드는 접근 권한, 식별자와 revision, 실행 허용, 채택, 취소 전달과 실제 표시 기록을 관리한다. 업무 조사, 업무 계획과 외부 도구 실행은 Downstream Agent 책임이다.

입력 수신과 즉시 음성 중단은 긴 의미 추론과 분리한다. 모든 사용자는 VIA의 같은 대화에서 질문에 답하고 결과를 받는다. 별도 Agent 창이나 내부 thread ID를 사용자가 관리하도록 요구하지 않는다. 공통 모델, 자원 예산, 접근 가능한 원본과 권한을 유지한다. 별도 문맥은 모델 가중치 복제를 뜻하지 않는다.

직접 설명에는 Task가 없을 수 있다. Task와 연결할지 판단하기 전에 사용자의 입력과 근거를 받아야 한다. 아래의 **활동**은 요청 이해, 근거 조회, 확인과 관련 후속 입력을 함께 다루는 논리적 처리 범위다. 특정 앱이나 보고서 종류의 Component가 아니며 Task와 항상 일대일이지도 않다.

## 비교 1 대화의 작업 문맥을 어디에 둘 것인가

### VIA에서 중요한 이유

VIA는 현재 보고 있는 자료, 이전에 설명한 내용, 진행 중인 여러 업무를 같은 발화에서 연결한다. 사용자가 “그 보고서에는 아까 두 번째 기준을 쓰고, 이 메일은 표만 넣어줘”라고 말하면 자료 지칭, 기존 업무 연결과 일부 조건 변경을 함께 판단해야 한다. 이어서 무관한 질문과 Agent의 확인 요청이 올 수 있다.

이때 대화 안에서 수행한 모든 읽기와 중간 판단을 계속 공유하면 암묵적인 연결을 함께 보기 쉽다. 그러나 큰 자료와 여러 업무의 도구 결과가 모델 문맥에 누적된다. 별도 문맥에서 처리하면 주 대화에 필요한 정보만 반환할 수 있지만, 나누는 순간 빠진 단서와 업무를 가로지르는 관계를 다시 가져와야 한다. 이 정보 전달과 재판단이 설계의 어려움이다.

### A 주 대화가 통합된 작업 문맥을 유지

1. 공통 입력 기록에서 원문, 화면 근거 참조와 실제 전달 이력을 받는다.
2. 대화 의미 처리자가 현재 요청과 관련된 대화, Task와 자료를 선택해 같은 의미 판단 loop에서 읽는다. 필요한 독립 읽기는 병렬로 실행할 수 있다.
3. 같은 작업 문맥에서 대상, 조건, 요청 관계와 후속 처리를 판단한다. 충분한 구체적 수행 의도가 채택되면 외부 위임 전에 표시한다.
4. 외부 업무를 위임한 뒤 기다리는 상태는 코드가 보존한다. 외부 업무 전체가 끝날 때까지 대화 loop를 잠그지 않는다.
5. 정정이나 새 결과가 오면 관련 기록과 현재 문맥을 사용해 영향받은 의미만 다시 판단한다.

**강한 A:** 원본 전체를 매번 넣지 않는다. Task별 검색, 문맥 선택, 요약과 offloading, prompt cache, 비동기 읽기, 부분 patch와 필요할 때의 보조를 허용한다. 주요 해석의 작업 이력과 의미 통합을 주 대화가 계속 맡는 구성이다.

실제 근거는 OpenHands의 conversation Agent step과 직접 도구 결과 입력, OpenClaw의 세션별 loop, Deep Agents의 일반 도구 loop와 문맥 관리다. Magentic-One의 중앙 ledger와 공유 메시지는 전체 조정 맥락을 유지하는 참고 근거이며, 전문 Agent도 사용하는 해당 구현을 순수한 단일 Agent의 증거로 부르지 않는다.

### B 주 대화가 독립 활동의 문맥을 연결

1. 같은 입력을 받은 공통 대화 처리자가 최근 실제 전달 내용과 활동 목록을 보고 새 활동, 기존 활동, 여러 활동에 걸친 입력과 미해결을 판단한다. 이 판단도 모델 호출 및 비용에 포함한다.
2. 여러 번의 조회나 판단이 필요한 부분은 독립된 활동 문맥에 원문, 필요한 근거 참조, 현재 제약과 revision을 전달한다. 간단한 직접 응답은 공통 대화 처리자가 처리할 수 있다.
3. 활동 처리자는 해당 범위의 bounded read와 의미 판단을 이어 간다. 큰 원본과 탐색 중간 결과는 이 문맥에 유지한다. 사용자에게 필요한 결과에는 근거 참조, 범위, 불확실성과 현재 revision을 포함한다.
4. 주 대화는 반환된 결과를 다른 활동 및 사용자의 새 입력과 연결한다. 여러 활동의 결과를 함께 해석해야 하면 추가 의미 판단을 수행한다. 단순 기술적 상태 전달까지 무조건 모델을 다시 호출하도록 만들지는 않는다.
5. 코드의 공통 채택과 출력 경로가 현재 권한, 입력 revision과 Task 사실을 확인한다. 실제 질문이 표시된 뒤 받은 짧은 답변을 해당 대기 활동에 연결한다.

**강한 B:** 매 입력마다 모든 활동을 호출하지 않는다. typed Agent 사건은 이미 확인한 연결을 사용한다. 과거 활동을 재사용할 수 있고, 필요한 부모 문맥을 상속하거나 누락된 원본을 다시 요청할 수 있다. 무조건 좁은 요약만 받고 원본 접근을 금지하지 않는다. 여러 활동을 합치는 판단과 문맥 확대의 비용은 남긴다.

Deep Agents의 isolated/fork subagent와 별도 async thread/run, OpenHands의 Task/Delegate 도구, CrewAI의 명시적인 task context와 위임이 실제 메커니즘의 근거다. OpenClaw의 child session과 부모 검토 경로도 참고한다. 이들 중 어느 하나가 VIA의 질문 연결과 부분 정정까지 완성해 제공한다는 주장은 아니다.

### 비용 경로를 확인하는 식

아래 식은 손익을 검토하는 개념식이며 시간이나 요금의 예측값이 아니다.

- A의 모델 비용은 각 판단에 실제로 전달한 공통 문맥, 관련 원본, 중간 이력과 출력의 청구 합계다.
- B는 공통 대화 판단, 위임 설명, 활동 내부의 모든 판단, 반환 근거, 교차 활동 재조립의 청구를 합한다.
- B의 비용 이익은 **A에서 실제로 반복되던 입력 비용의 감소가 B의 위임과 재조립 추가비용보다 클 때**에만 생긴다. A가 이미 같은 양의 관련 문맥만 보낸다면 이 이익은 사라질 수 있다.
- 진행 중 다른 요청을 위한 B의 첫 응답 이익은 **A에서 남는 응답 전 대기가 B의 추가 연결과 검증 및 자원 경합보다 클 때**에만 생긴다. Python `async`, 별도 thread 또는 actor의 존재만으로 이 부등식을 충족하지 않는다.

### 강한 반론과 주요 DP 자격

가장 강한 반론은 “A에 선택적 subagent와 Task별 문맥 view를 추가하면 필요한 장점만 가져올 수 있다”다. 실제 harness들이 이런 혼합을 지원한다. 그래서 Agent 개수나 전체 대화 대 Task라는 이름만으로 A/B를 고정해서는 안 된다.

주요 DP로 유지하려면 **무엇을 독립 작업 문맥으로 지속 보존하고, 어느 해석을 그 문맥에서 끝내며, 원 대화가 무엇을 다시 판단하는지**를 계약으로 정해야 한다. 요청과 근거 envelope, 질문 대기, 정정의 의존 범위, 재개와 결과 반환의 의미가 실제로 달라져야 한다. 양안이 같은 문맥과 호출 경로로 수렴하면 주제를 실행 정책 수준으로 낮춘다.

이 검토는 [43에서 제외한 Task별 B](./04-43-request-interpretation.md#0-비교를-다시-구성한-이유와-b의-제외)를 자동 복원하지 않는다. 그때 지적한 사전 Task 판별 문제와 강한 A의 기능을 그대로 반론에 적용했다. 현재 사용자가 Conversation과 Task 중심의 구조를 다시 탐색하도록 요청했으므로, 그 반론을 통과할 수 있는 범위만 새 검토 대상으로 남긴다. 아직 통과를 확정하지 않았다.

**전환 판단:** A에서 B로 바꿀 때 입력 수신, 원본 접근, 외부 Agent 연동과 최종 표시를 재사용한다. 지속적인 의미 작업을 분리한다면 그 중간 상태, 질문 대기, 정정 전달과 결과 반환을 활동 문맥의 계약으로 옮긴다. B에서 A로 바꿀 때는 저장된 원본과 활동 결과를 대화의 조회 근거로 재사용하고 의미 작업의 조정을 합친다. 기록 변환은 데이터 이행비이며 핵심 재설계와 구별한다. 이미 선택적 subagent와 재개 가능한 작업을 가진 A라면 이 전환의 상당 부분이 내부 정책 변경으로 끝날 수 있다. **따라서 현재 근거로는 새 주요 DP로 승격할 것을 권고하지 않으며, 실제로 남는 책임 차이를 검토할 구조 후보로 둔다.**

## 비교 2 과거 근거를 요청별로 조합할지 공통 관계로 제공할지

### VIA에서 중요한 이유

사용자는 “아까 네가 두 번째로 설명한 것”, “고치기 전 보고서의 표”, “방금 들은 부분만”이라고 말한다. VIA는 대화 내용을 기억하는 것과 함께 실제로 표시하거나 들려준 구간, 당시 자료 버전, 수정 전후 관계를 알아야 한다. 요약에 적힌 사실과 실제 전달한 내용이 일치하지 않으면 다른 자료를 지정할 수 있다.

요청의 소비자가 원본별 읽기를 조합하면 필요한 관계를 복원하는 시간이 첫 응답 경로에 참여할 수 있다. 생산자가 공통 관계를 게시하고 유지하면 소비자는 그 읽기 계약에 의존할 수 있다. 대신 생산하지 않은 범위의 보완, 사용하지 않을 자료의 가공, 변경과 철회 전파, 잘못된 추출의 보정 비용을 부담한다. 이 충돌은 현재 QA01, QA03, QA05에 직접 연결된다.

[기존 DP-45 §1.3](./04-45-memory-and-context.md#13-그-근거-연결을-어떤-방식으로-제공할-것인가)의 구조 차이를 유지한다. **A는 요청별 조합과 누락 해결을 소비 경로가 맡고, B는 생산과 게시 범위의 지속 계약을 별도로 둔다.** A도 선행 요약, 색인과 cache를 사용할 수 있다. 단순히 가공 시점을 앞당기거나 선택적 cache를 추가한 것만으로 B가 되지는 않는다.

### A 요청 시 원본과 필요한 관계를 조합

1. 입력, 채택 요청, 실제 전달, Task 결과와 자료 버전의 원본 기록을 유지한다.
2. 최근 작업에 필요한 요약과 검색 색인, 유효 cache를 사용할 수 있다. 모든 이력을 무가공으로 보관하기만 하는 안이 아니다.
3. 새 지칭이 오면 그 목적에 맞춰 원본 후보를 찾고 실제 전달 범위와 버전을 확인한다.
4. 필요한 의미 관계를 현재 해석에서 판단해 근거 묶음을 만들고 최종 지칭을 채택한다.
5. 반복 조회는 cache를 쓰고 바뀐 원본에 의존하는 부분만 다시 읽는다.

Deep Agents의 요약과 원본 offloading 및 재읽기, OpenHands의 event history와 condensed view가 실제 근거다. 이 제품들이 VIA의 원본 서비스 조합 계약을 그대로 구현했다는 주장은 하지 않는다.

### B 원본과 함께 공통 관계를 생산하고 게시

1. 같은 원본 기록을 유지하면서 지원할 관계를 별도 생산한다. 기존 45의 `PRESENTS`, `HAS_RESULT`, `REVISES`, `EXPLAINS_ITEM`을 출발점으로 삼을 수 있다.
2. 명시적인 식별자 관계는 코드로 만들고 의미 해석이 필요한 항목만 모델을 사용한다. 모델이 생성한 설명을 독립 원본 사실로 승격하지 않는다.
3. 각 기억에 원본, 범위와 revision, 생성 근거와 무효화 상태를 연결한다. 실제 전달 이후의 receipt가 있어야 전달 관계를 생산한다.
4. 요청 시 유효한 관계를 읽고 연결된 원본 구간을 확인한 뒤 최종 지칭을 판단한다. 지원 관계가 미준비이면 생산과 게시를 요청하고 재조회한다. 게시되지 않은 범위를 완성된 근거로 반환하지 않는다.
5. 철회와 정정은 관련 기억과 진행 중 생산에 전파한다. 쓰기와 조회가 겹치면 기다리거나 원본으로 보완한 실제 비용을 남긴다.

게시된 locator의 원문을 확인하는 읽기와 원본별 검색 및 교차 조합으로 누락을 해결하는 경로를 구별한다. 후자는 기존 45의 **명시적 B+ 혼합안**이다. 순수 B에서 지원하지 않는 관계는 반복 생산으로 해결되지 않으며 지원 제한을 남긴다. 강한 실용 대안을 위해 B+도 검토하되 순수 B의 경로와 점수에 몰래 섞지 않는다.

CrewAI의 결과에서 memory를 추출하고 저장하는 경로, OpenClaw의 배경 consolidation과 query 전 기억 주입이 실제 근거다. 두 제품의 기억이 이미 VIA의 전달 구간과 자료 버전을 정답으로 제공하는 것은 아니다. 특히 CrewAI의 recall은 pending save를 기다릴 수 있고 deep recall에는 추가 모델 호출이 있다.

### QA trade-off

| QA | 예상 손익 | 반증 또는 축소 조건 |
| --- | --- | --- |
| QA01 | **B의 유효한 선행 관계가 첫 조회 전에 있으면 유리할 가능성이 높음** | A의 첫 조회가 이미 metadata만으로 끝나거나 cache에 적중하면 차이가 작음. B의 갱신 대기와 원본 보완은 이익을 줄임 |
| QA02 | 원본 직접 확인과 파생 관계의 재사용이 서로 다른 오류 경로를 만듦. **승자 미정** | 양안이 같은 근거를 충분히 보완하면 정확도가 같을 수 있음. 중간 memory recall 정확도를 최종 대상 집합의 정확도로 대체하지 않음 |
| QA03 | 조회 단계가 완료 경로에 참여하면 B가 줄일 수 있음 | 첫 응답 뒤의 전체 처리, 보완 조회와 요약 준비까지 포함하면 이익이 작아질 수 있음 |
| QA04 | B의 생산과 provenance, 무효화 계약이 추가 변경 지점이 될 수 있음 | 공통 provenance 타입과 단일 사용 검사로 흡수하면 동점 가능. 실제 C01~C06 diff 전에는 A의 우위를 확정하지 않음 |
| QA05 | **재사용이 낮거나 원본 갱신이 많으면 A가 유리할 가능성이 높음** | 재사용으로 절약한 후속 해석 비용이 생산, 갱신과 미사용 비용을 넘으면 B가 유리할 수 있음 |

이 후보에서 가장 설득력 있는 충돌은 **준비된 공통 관계를 읽는 B의 경로 단축과 A의 불필요한 생산 및 유지 비용 절감**이다. 차이가 남으려면 A의 기존 요약과 cache로 충분하지 않은 실제 관계를 B가 제공해야 한다. B에 원본 확인과 추가 생산을 허용하면 정확도가 반드시 더 나쁘다고 말할 수 없으며, 그 보완의 시간과 비용으로 비교한다. 미지원 관계에 대한 B의 기능 손실과 B+의 보완도 별도로 남긴다.

초기 200턴과 완료 Task 20개, 최대 5개 진행 Task를 복원하는 COMMON-28 조건을 그대로 사용한다. B에게 미리 완성한 정답 관계를 주지 않는다. 첫 입력 전 준비 5초와 입력 후 경합, 시나리오별 초기화, S11 내부의 반복 조회, 끝난 뒤 청구되는 작업까지 포함한다. 이 시험이 하루 종일 누적된 steady-state라는 설명도 하지 않는다.

### 전환과 혼합에 대한 판단

A의 요청별 cache만으로 충분한 장면에서는 B의 이익이 작다. B가 별도 구조로 남는 범위는 여러 원본의 공통 관계를 소비자들이 지속적으로 사용하고, 누락 해결을 생산 및 게시 계약으로 옮기는 부분이다. 생산 기준, 원본 의존, 지원 범위와 게시 및 무효화의 수명이 이 계약을 뒷받침한다.

B를 “필요할 때만 생산”하도록 바꾸면 정상 미적중 경로가 A에 가까워진다. 일부 관계만 선행 생산하는 혼합은 실용적인 대안이다. 생산 대상과 비용을 명시하고 두 안의 기본 정책에 포함할 수 있다. 혼합이 양쪽의 이익을 대부분 얻으면 단순 A/B 승자를 강제하지 않고 그 이유를 남긴다.

**A에서 B로 전환:** 공통 입력과 최종 채택은 재사용한다. 원본별 조합을 실행하던 소비 경로를 관계 Reader로 바꾸고, 생산자와 지원 범위 및 게시를 운영 책임으로 둔다. 기존 자료의 backfill은 데이터 이행비이며 이 읽기와 누락 해결 책임의 변경과 구별한다.

**B에서 A로 전환:** 원본과 최종 해석은 재사용한다. 각 소비 요청에서 원본별 검색과 조합, 누락 및 원본 변경을 처리할 경로를 다시 제공한다. 이미 존재하는 관계를 cache로 재사용할 수 있으므로 과거 기억을 모두 버려야 한다고 가정하지 않는다.

**가장 싼 혼합에 대한 판단:** A에 유효 cache와 소수의 선행 관계만 더해 주요 정상 장면을 처리할 수 있다면, 별도 공통 관계 계약의 필요성은 약해진다. 외부 harness의 memory 기능만으로 이 반론을 해결할 수는 없다. 따라서 현재는 실용적인 품질 충돌을 가진 보강 대상으로 권고하며, 주요 DP 자격이 새롭게 확정됐다고 보고하지 않는다.

## 화면 지칭 DP에서 확인한 근거와 남은 문제

Magentic-One의 WebSurfer는 native interactive target, focus와 이미지를 함께 사용한다. OpenHands의 browser 도구도 텍스트와 선택적 이미지를 모델에 돌려준다. 따라서 **실제 object 정보와 원본 시각 근거를 함께 사용하는 방안은 실용적 근거가 있다.**

그러나 이 사실로 기존 DP-47의 B가 A보다 정확하다고 결론낼 수 없다. 강한 A도 native selection과 crop 및 원본 재조회를 사용할 수 있다. WebSurfer의 대상 목록은 브라우저 상호작용용이며, 사용자가 말하며 가리킨 여러 시점과 원형으로 지정한 집합을 뜻하지 않는다.

47의 B를 강화할 때 검토할 구체적인 내용은 **소스별 관측에서 얻은 후보를 원본과 함께 재사용하고, 변경된 근거에 의존하는 후보만 갱신하는 경로**다. 그 결과 다음 요청의 모델 입력이나 재판단이 실제로 줄어드는지 확인해야 한다. A의 cache와 부분 patch를 그대로 두고 비교한다. B에 필요한 후보 생성과 결합이 비용을 더하면서 QA02에도 차이가 없으면 현재 QA 집합에서 균형 있는 주요 DP로 완성됐다고 말할 수 없다.

따라서 47은 중요한 VIA 문제로 유지한다. 이번 조사는 실제 관측 메커니즘의 근거를 보강했지만 B의 정상 사용 이익을 해결했다는 결론에는 이르지 않았다.

| 의미 호출 실패 | A는 해당 의미 단계, B는 실패한 활동 단계부터 재개한다. 양안 모두 확정 상태와 미확정 후보를 구분해야 하며 context 분리만으로 process 장애 격리가 생기지 않음 | A는 조회 및 조합을 재시도하고 B는 실패한 생산을 재시도한다. 미완성 관계와 Coverage를 게시하지 않음 |
| 재시작 후 질문 대기 | A의 대기 기록 또는 B의 활동과 부모 연결을 복원한다. 실제 질문을 표시했는지와 이미 받은 답변을 함께 복원하고 질문을 중복 전달하지 않음 | A의 진행 조회 또는 B의 생산/게시 상태와 요청 의존을 복원한다. 원본부터 재구성할 수 있어도 소요 시간과 모델 비용은 다시 발생할 수 있음 |
| 접근 철회 뒤 늦은 결과 | 주 대화 또는 활동의 임시 결과도 공통 사용 검사에서 차단한다. B의 하위 작업 취소는 이미 실행한 외부 동작의 취소를 뜻하지 않음 | 원본, cache, 관계와 진행 중 생산을 같은 철회 범위에 연결한다. 이전 job의 늦은 게시를 막아야 함 |
| 실패 뒤 재사용 가능한 부분 | 입력과 의존 revision이 그대로인 부분만 재사용한다. 어느 결과가 의미적으로 독립적인지는 모델 판단과 기록된 의존에 근거해야 함 | 유효한 원본 locator와 관계를 재사용한다. 원본이 그대로여도 잘못 추출된 의미는 별도 이의 제기와 재생산이 필요 |

이 계약들은 구현해야 할 제안이다. 외부 harness의 checkpoint나 writer 검사만으로 VIA의 복구가 완성됐다고 주장하지 않는다. 이번 QA01~05의 정상 사용 이익을 드문 재시작 사례로 대신 설명하지 않는다.

## 앞서 제안한 세 질문에 대한 답

### Conversation과 Task 중 어디에 중심을 둘 것인가

두 identity와 수명은 모두 필요하다. 주요 선택으로 발전할 부분은 비교 1의 **어느 문맥에서 지속적으로 의미를 판단하고, 다른 문맥에 무엇을 전달하는가**다. DB의 기본 키, box 이름 또는 Task별 handler만 달라지면 주요 DP 근거가 부족하다. 새 입력의 Task 관계를 미리 알고 있다고 가정하지 않는다.

### 비동기 작업을 내부에 둘 것인가 독립 수명으로 둘 것인가

OpenClaw, Deep Agents와 OpenHands에 독립 실행과 상태 연결의 실제 근거가 있다. 다만 독립 실행은 대화가 계속되기 위한 유일한 방법이 아니다. 통합 구조도 외부 실행 ID와 내구 상태를 관리하면서 다른 입력을 받을 수 있다. **대화 내부에서 계속 수행하는 VIA 의미 작업을 어떻게 분리하는가**까지 바뀔 때 비교 1의 QA 가설이 생긴다. process 분리는 별도 선택이다.

### 늦은 결과의 효력을 어디서 판단할 것인가

다음 세 가지를 분리해야 한다.

1. **기술적 유효성:** 입력 revision, run identity, 현재 쓰기 권한과 중복 여부를 코드로 검사한다.
2. **의미적 유효성:** “수신자만 변경” 뒤 기존 보고서 내용은 유지해도 되는지 의미 처리자가 판단한다.
3. **확인된 외부 사실과 전달:** 이미 실행된 동작과 실제 표시 및 청취를 기록한다. 취소 요청이나 모델 결과 폐기로 외부 동작이 되돌아갔다고 해석하지 않는다.

이 계약은 두 비교의 실용성을 위해 필요하다. 검사 위치만 바꾼 A/B를 별도 주요 DP로 추가하면 현재 QA01~05의 차이 근거가 빈약하다. 특히 2번의 정확성을 QA02의 모든 지칭 이외 오류까지 넓혀 채점하지 않는다.

## 최종 권고와 다음 판단 기준

**DP-45는 실용적인 A/B 근거와 현재 QA 사이의 충돌이 가장 잘 연결된다.** 기존의 원본별 요청 조합과 생산자가 유지하는 공통 관계 계약을 보존하면서, 어떤 관계의 생산과 재사용이 실제 요청 경로 및 전체 비용을 바꾸는지 명확히 설명한다. 코드 색인, 요약, cache와 원본 확인은 양쪽에 허용하고 생산 및 갱신 비용을 비교한다. 직접 원본 조합을 사용하는 B+는 별도로 표시한다.

**새로운 전체 구조 후보는 통합 작업 문맥과 독립 활동 문맥이다.** 기존 44의 짧은 dispatcher와 stage 연결보다 모델 문맥과 재판단 경로에 더 직접적인 차이가 있다. 단, 강한 A의 선택적 격리와 B의 공통 처리 fast path를 포함한 뒤에도 다른 선택으로 남아야 한다. 현재 근거만으로 과거 Task별 B를 다시 주요 DP로 승격시키거나 44를 대체했다고 선언하지 않는다.

이 후보를 발전시킬 때 먼저 결정할 것은 Agent 개수가 아니다. 같은 사건에 대해 **모델에 실제 들어가는 근거, 다른 문맥으로 넘기는 내용, 반환 후 필요한 재판단, 어느 상태를 다음 입력까지 보유하는지**를 두 안에서 확정해야 한다. S05, S11, S18, S19의 겹침과 S13, S15, S20의 교차 맥락에 적용하되, source에서 온 단순 상태를 코드로 즉시 표시할 수 있는 공통 경로를 남긴다. 양안이 같은 경로가 되면 차이 없음으로 판정한다.

현재 자료만으로 **4개 DP 각각의 3~4개 QA 차이, 모든 QA의 2개 이상 DP 커버리지, QA01의 3~4개 DP 차이**를 충족했다고 말할 수 없다. 이번 조사에서는 실용적인 품질 충돌이 있는 보강 방향 하나와 구조 후보 하나를 구체화하고, 각각 아직 통과하지 못한 반론을 남겼다. 47과 42의 열린 문제도 유지한다. 수치나 모집단을 조정해 이 빈칸을 채우지 않는다.
