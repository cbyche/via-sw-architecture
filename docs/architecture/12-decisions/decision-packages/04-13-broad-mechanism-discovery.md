## 1. 결론부터

다섯 문제군에서 각각 세 가지 원리를 검토했다. **15개 모두가 새 아이디어이거나 주요 후보라는 뜻은 아니다.** 기존 안의 재검토, 기존 설계 안의 선택, 다른 구조와 비교할 안을 구별했다.

**구조 비교 후보로 세 가지를 남긴다.**

| 후보 | 같은 목적 | 실제 T | 비교할 다른 구조 | 남긴 이유 |
| --- | --- | --- | --- | --- |
| M-2 [단계별 의미 해석](./04-14-staged-semantic-resolution.md) | 목표, 지칭과 업무 관계를 정확하게 연결 | 선택한 근거를 한 semantic 호출에 넣어 관계를 함께 해석 | 발화 해석, 근거 결합, 업무 연결을 명시적 중간 자료로 연결하는 처리 파이프라인 | 추론 횟수 증가와 조기 해석 오류를 감수하고 판단별 입력, 근거, 재처리 범위를 분리하는 선택. S-02의 전처리 추가와 달리 최종 통합 해석을 대체 |
| S-1 [이력 원본과 상태 재구성](./04-15-event-authoritative-state.md) | 확정한 대화/업무 관계를 복구하고 설명 | 현재 owner 상태와 미완료 원장이 원본 | 모든 의미상 전이를 원본 이력에 확정하고 현재 상태는 이력에서 생성 | 저장소 API 교체가 아니라 owner의 쓰기, 원본 권위, 상태 생성과 복구의 공동 교체. 이전 네 참고안 중 하나를 새 기준으로 재심사한 결과 |
| S-2 [권한별 처리 격리](./04-16-capability-compartments.md) | 허용한 자료만 처리하고 범위 밖 사용을 막기 | 공유 Core의 처리 코드가 현재 권한을 검사 | 권한 있는 중개자와 자료 범위별 제한 process를 분리하고, 처리 코드는 부여받은 자료 handle만 사용 | 모든 자료 경로와 실행 권한의 배치를 바꾸는 선택. 단순 connector process 분리나 검사 함수 추가와 구별 |

이는 **구조 자격과 비교할 가치에 대한 설계 판단**이다. C의 품질 우위나 제품 채택을 확정한 것이 아니다. 상위 기능 품질에 직접 연결되는 M-2를 먼저 검토하고, 상태 정확성 및 복구의 S-1, 권한 경계의 S-2 순으로 읽는다. 마지막 두 안을 의미 해석 정확성 개선으로 포장하지 않는다.

이전 **C-대화는 주요 후보에서 제외**한다. **C-독립의 단순 비동기 조정도 제외**한다. 엄격한 분산 확정 형태는 W-3에서 구조 차이는 인정하되 이번 주요 후보에서는 보류한다고 판정했다. 확장으로 되는지 모른다는 상태를 유지하지 않는다.

## 2. 기존 C-대화의 국소 전환 판정

이전 [04-11 §2](./04-11-mechanism-family-proposals.md)의 기대 이익은 사건에 맞춰 필요한 근거와 다음 처리를 판단하는 유연성이었다. T는 이미 질문 답변과 정정 뒤 재해석하고, 선행 결과를 받은 `WAIT_DEPENDENCY`에서도 `RESOLVING/READY`로 진행한다. 다음 대응으로 C의 제안 범위를 수용할 수 있다.

| C가 필요로 하는 것 | 기존 T를 가장 적게 바꾸는 대응 | 바꿀 필요 없는 핵심 |
| --- | --- | --- |
| 사건마다 현재 문맥으로 판단 | Request Controller의 해당 사건 처리에서 Request Interpreter 재호출. 일상 progress는 기존 무모델 경로 유지 | Task source 사실, 사건 inbox/outbox, 질문 및 전달의 owner |
| 읽기를 순서대로 선택 | Request Interpreter 안의 bounded 실행 loop 또는 기존 read/refinement 경로 확장. 횟수 정책은 명시적으로 조정 | Context Manager의 scope/receipt, 현재 권한 검사와 source 계약 |
| 후속 목표나 처리 변경 | 기존 Semantic Proposal의 목표, 관계, handling을 현재 graph revision의 변경 제안으로 적용 | Request Graph, command identity와 admission, 이미 나간 실행의 조회/정정 |
| 이전 처리 기억 | 이미 내구적인 입력, Semantic Commit, Task와 publication receipt를 owner port로 제공 | KV가 아닌 업무 원본, 삭제 원장, 현재 policy epoch |
| 장애 후 이어가기 | 기존 graph와 미완료 원장을 복원한 뒤 필요한 지점에서 재판단 | UNKNOWN command의 외부 조회, 오래된 승인/음성 재실행 금지 |

“다음 행동을 모델이 제안한다”는 성질을 얻는 데 graph를 없애고 사건 기록만 원본으로 삼을 필요가 없다. C의 별도 Conversation Agent와 Interaction Guard라는 이름도 필요 조건이 아니다. 이 대응은 새 언어 엔진, 새 권위 저장 구조나 owner 간 확정 프로토콜을 요구하지 않는다. 추가 호출의 예산 및 회귀 검증은 필요하지만 그것을 대규모 구조 전환이라고 주장하지 않는다.

**판정: C-대화는 이 과제에서 계열 내부 확장이다. 주요 후보에서 제외한다.** 확정한 의미 관계를 지우고 매번 다시 추론하는 변형은 만들 수 있지만, 그런 손실을 감수해야만 얻는 중요한 이익을 제시하지 못했으므로 별도 대안으로 남기지 않는다. 역방향도 새 요청부터 재판단 호출을 줄이고 기존 전이로 돌아가면 되며 권위 상태 이전은 필요 없다.

## 4. 이전 C-독립과 W-3의 판정

비동기 상태 복제로는 Request Controller의 hold 확정 뒤 Agent Gateway가 옛 상태로 전송하는 간격이 생긴다. 정책 철회도 같다. ACK나 최종 조회를 하나 더 붙여도 조회와 전송 사이 경합이 남는다. **이전 C-독립의 단순 형태는 주요 후보에서 제외한다.**

W-3은 다른 안이다. 관련 owner가 버전/전송 조건을 검증한 뒤 변경을 준비 상태로 내구 기록하고, transaction ID에 결합한 공동 commit/abort 결정으로 적용한다. 외부 네트워크 전송은 공동 commit 이후의 outbox만 수행한다. hold/철회와 전송은 충돌하는 준비를 동시에 확정할 수 없게 직렬화한다. coordinator 또는 participant 실패로 결정이 불명하면 관련 scope를 막고, durable 결정과 participant 상태를 복원해 완료한다. 사용자에게 접수된 입력과 전송 보류가 확정된 시점을 구분해야 하며 이 지연은 V-04 비용이다. 단순 eventual consistency와 이 보장을 한 방안의 장점으로 합치지 않는다.

이 형태는 원리상 구현 가능한 구조이며 별도 제품 채택을 뜻하지 않는다. 예를 들어 [Orleans의 공식 transaction 문서](https://learn.microsoft.com/en-us/dotnet/orleans/grains/transactions)는 여러 owner의 persistent 상태를 공동 확정하는 구현 계열이 존재함을 보여준다. VIA에 해당 framework를 채택하거나 그 성능을 가져오지 않는다.

**설계 판정:** T와 W-3은 다른 구조다. 전환 시 admission, 질문 종료, command/정책 검증을 participant 변경 집합으로 분리하고 불명 결정의 복구를 새로 작성해야 한다. 반대로 T로 합칠 때도 중간 준비 상태와 독립 확정을 하나의 owner UoW로 재구성해야 한다. 작업 drain은 자료 이전 부담을 줄이지만 이 프로토콜 교체를 없애지 않는다.

**선발 판정:** 이번 주요 비교군에서는 보류한다. 현재 PC 범위에서 model/voice/ASR/위험 connector는 이미 격리되어 있다. W-3의 추가 이익은 Core 내부 owner crash의 국소화인데, 정확성을 유지할 공동 확정은 관련 경로의 독립 진행을 다시 제한하고 정상 경로의 자원/지연도 늘린다. 서로 다른 기기에 분산하거나 owner를 제각각 배포하는 요구를 새로 만들지 않는다. 기존 격리로 다루지 못하는 내부 owner 장애가 중요한 기능 중단 원인으로 확인되는 변경 상황에서 재검토할 대상으로 남긴다. 이는 확장 가능성 판단의 미결이 아니라 현재 범위와 우선순위에 따른 보류다.
