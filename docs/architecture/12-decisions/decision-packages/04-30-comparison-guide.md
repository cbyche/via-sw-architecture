# 04-30. VIA 구조 비교를 읽고 작성하는 가이드

> 2026-10-04 발표 설명/도식 기준 반영 / §4는 구조 자격, §5는 독립 이해의 필수 기준

> **2026-10-05 번호 사용:** 30번대 주제 문서는 논의 대상, 40번대 주제 문서는 정제된 유력 Decision Point 후보로 읽는다. [41](./04-41-request-resolution-control.md)은 의미 해결 주체, [42](./04-42-lifecycle-ownership.md)는 대화·업무 수명의 상태 권한과 실행 경계를 비교한다. 기존 37은 검토 기록이다. 40번대도 최종 DP 선정·A/B 승인·측정 결과를 뜻하지 않는다. 42의 메인 비교도는 한 장으로 발표할 수 있는 16:9 구성이며 본문 없이 공통 기능과 다른 소유·확정 경계를 읽을 수 있어야 한다.

## 1. 이 문서부터 읽는 이유

VIA는 PC에서 말, 글, 화면 지칭을 받아 직접 답하거나 외부 Agent에 업무를 맡긴다. 사용자는 Agent마다 대화창을 옮기지 않고 VIA에서 앞 대화와 여러 업무를 이어간다. 여기서 Agent는 실제 업무의 조사, 계획과 실행을 맡는 외부 프로그램이다. VIA는 사용자의 뜻, 대상, 업무 연결과 결과 전달을 책임진다.

이 문서들은 **같은 중요한 목적을 서로 다른 메커니즘으로 해결하고, 전환하려면 핵심 SW 설계를 상당 부분 바꿔야 하는 구조 대안**을 비교한다. 단순 기능 추가, 설정 변경, adapter 교체나 호출 경로 선택으로 상대방의 주요 성질을 얻으면 주요 구조 비교로 충분하지 않다. 바꾸기 어렵게 만드는 것이 목표는 아니다. 구조 차이에서 중요한 품질의 장단점이 나와야 한다.

기존 `target-architecture/`는 기능 전반을 검토한 **참조 구조**다. 어느 방안을 참조 구조로 고정하지 않으며 아래 각 안은 독립적으로 정의한다. 33은 A/B/C 세 계열을 비교한다. 문서 작성 완료는 대안의 채택이나 구현 검증을 뜻하지 않는다.

## 2.1 31 복원과 별도 41 비교

2026-10-04 사용자 지시에 따라 31 본문/그림은 ReAct 적용 직전 `ee2fcf31`로 복원했다. 새 비교는 [04-41 — 모델 중심 ReAct와 모델 틀/코드 완성](./04-41-request-resolution-control.md)이다. 31은 요청별 생성과 지속 의미 상태, 41은 조회/해석 진행과 최종 의미 생산의 주체를 비교한다. 두 문서를 같은 A/B의 설명 보완으로 섞지 않는다. 41은 별도 탐색 문서이며 최종 DP를 하나 추가 선정한 것이 아니다.

## 3. 비교 전에 고정하는 것과 바꿀 수 있는 것

- **같은 사용자 요구:** [고정 범위](../../03-fixed-architecture-scope.md)와 [18개 UC](../../05-representative-use-cases.md)의 목표와 완료 조건을 유지한다. 일부 기능을 포기한 대안도 비교하되 미지원, 추가 조작과 얻는 이익을 드러낸다.
- **같은 외부 조건:** 같은 입력과 앱/Agent capability, 정책, 모델 자원 조건을 사용한다. 한쪽에만 정답 객체 ID나 더 좋은 모델을 주지 않는다. 구조가 어떤 공개 입력을 사용하지 않는 선택은 비용과 손실로 설명한다.
- **VIA 책임:** 자료의 한정된 읽기와 이해는 가능하다. 앱을 조작하거나 실제 업무 계획을 세워 외부 변경을 수행하는 것은 Agent 책임이다.
- **모델 배치:** 단일 on-device Omni weights를 공유한다. 역할, 요청 Context와 세션은 구별한다. 독립 Streaming ASR과 계속되는 음성 수신을 양안에 포함한다. 새 learned helper를 숨겨 넣지 않는다. 새 runtime capability는 설계 요구와 미확인 상태로 표시한다.
- **바꿀 수 있는 것:** 내부 의미 생성의 주체, 자료 획득과 표현, 대화 상태의 소유와 협력, 실행 단위와 의존성, 저장 원본과 권한 배치. 기존 Component 분해와 호출 횟수를 대안에 강제하지 않는다.
- **공통 확정 경계:** 외부 실행에는 현재 권한과 유효한 사용자 의도가 필요하다. 임시 해석이나 소리 생성만으로 업무 완료, 사용자 승인 또는 실제 청취를 확정하지 않는다.

## 4. “SW 구조적으로 다른 대안”의 정확한 의미

### 4.1 목적과 판정 단위

**같은 중요한 사용자 목적을 서로 다른 해결 메커니즘으로 달성하고, 그 메커니즘 때문에 핵심 SW의 책임, 데이터와 상태, 실행 및 상호작용 방식이 달라지는 두 설계**다. 전환하려면 그 처리 체계를 상당 부분 재설계해야 하며, 그 차이가 VIA에 중요한 품질상의 이익과 손실을 만들어야 한다.

판정 단위는 상자 수, 파일 수나 문서 분량이 아니라 **목적을 달성하는 실제 처리 체계**다. 어떤 조건에서 무엇을 읽고 누가 결과를 만들며, 무엇을 상태로 남기고 다음 처리가 무엇에 의존하는지 비교한다. 새로운 Component는 이 책임 차이를 표현한 결과여야 한다.

어려운 전환을 만드는 것이 목적은 아니다. 양방향 비용은 다를 수 있고, 구현을 이미 둘 다 가진 경우 경로 선택은 쉬울 수 있다. 같은 외부 API를 유지한다고 내부 재설계가 반드시 작은 것도 아니다. 반대로 내부 코드를 새로 많이 작성한다는 사실만으로 주요 Architecture 결정이 되는 것도 아니다.

이 예시들은 모든 Component를 다르게 만들어야 한다는 뜻이 아니다. 공통 Framework나 목적은 남아도 **목적을 달성하는 중심 수단과 그것을 지탱하는 연결 설계**가 달라진다. 두 수단을 혼합할 수 있다는 사실만으로 비교를 폐기하지 않으며, 실제 혼합 비용과 남는 손익을 검토한다. VIA에 서버, 다중 모델이나 외부 Agent 내부 계획을 무단 도입하는 허가로 해석하지 않는다.

### 4.3 주요 구조 비교로 통과시키면 안 되는 경우

- 공통 Framework와 내부 직렬 처리 틀을 고정한 뒤 Module 이름, 색이나 설명만 바꾸는 경우.
- 같은 결과 생산 경로에 cache, validator, helper 또는 adapter를 조금 보태 주요 이익을 얻을 수 있는데 별도 구조 계열이라고 하는 경우.
- 모델 호출 횟수, prompt 입력, 설정 또는 한 내부 알고리즘만 바꾸고 정상 처리의 책임과 상태/실행 계약은 그대로인 경우. 내부 변경도 Architecture적일 수 있지만 파급과 품질상의 이유를 실제로 설명해야 한다.
- 참조 구조의 Component 배치와 처리 순서를 양안에 강제해 대안을 그 틀 안의 변형으로 축소하는 경우.
- 서로 독립적으로 선택할 수 있는 기능을 억지로 묶거나, 상대 안의 cache/검사/복구 기능을 빼서 차이를 키우는 경우.
- “계약 N개 변경”, “회귀 시험 필요”, “과거 데이터는 복원 불가”, “새 엔진 개발 필요”만으로 큰 구조 차이를 주장하는 경우.
- 그림의 상자 배치를 바꾼 것, 링크/렌더/CI 통과, 13개 품질 행의 존재를 구조 자격의 검증으로 보고하는 경우.

### 4.4 설계부터 도식까지 수행하는 순서

1. **같은 목적을 고정한다.** 중요한 정상 사용자 장면과 실패, 두 안이 달성할 결과를 먼저 적는다. 부분 지원이면 손실을 표시한다.
2. **각 안을 독립적으로 설계한다.** 입력 생산자, 결과 생산자, 중간 자료, 상태 owner, 읽기/쓰기, 실행 주체, 확정과 반환 경로를 각각 작성한다. 참조 구조는 기능/조건 확인에 활용한다.
3. **메커니즘의 교체를 설명한다.** A에서 없어지거나 역할이 바뀌는 핵심 처리와 B에서 이를 대신하는 처리를 지목한다. “모듈 추가” 다음에 실제로 무엇이 달라지는지 설명할 수 없으면 부족하다.
4. **같은 사건을 추적한다.** 정상 처리, 보완/정정, 외부 사실 변경, 철회, 실패와 재시작을 비교한다. 구조 차이가 처리 결과와 품질 비용에 어떻게 이어지는지 적는다.
5. **가장 싼 구현으로 반박한다.** 작은 추가, 기존 구현 재사용, adapter, 설정 변경과 혼합을 구체적으로 시도한다. 그것으로 주요 성질을 얻으면 비교 축을 수정한다. 결과를 미결 질문으로 사용자에게 떠넘기지 않는다.
6. **세 비용을 분리한다.** 기능 개발비, 진행 상태/데이터 이행비, 핵심 처리 체계의 재설계비다. 새 설치나 진행 작업 종료로 없어지는 이행비를 본질적 전환 난이도로 세지 않는다. 양방향을 각각 판단한다.
7. **설계에서 그림을 만든다.** 공통 요소만 정렬한다. 서로 다른 분기/결합, 반복, 저장 원본, process/배포 및 신뢰 경계를 같은 상자 수와 직렬 연결에 끼워 맞추지 않는다. 차이를 크게 보이게 하려고 없는 경로를 추가하지 않는다.
8. **그림에서 설계를 역으로 읽는다.** 본문을 덮고도 누가 무엇을 만들어 어디에 넘기며, 각 안의 어떤 전제가 달라졌는지 설명할 수 있어야 한다. 단순 배치 차이와 실제 책임/실행 차이를 구별한다.

### 4.5 완료 보고 전 필수 판정

각 문서 §8~9와 전체 검토 기록에는 다음 네 답을 반드시 남긴다.

- 목적을 달성하는 원리는 A와 B에서 각각 무엇인가?
- 전환할 때 유지할 수 있는 부분과 반드시 재설계할 핵심 부분은 무엇인가?
- 가장 싼 추가/교체/혼합으로 충분하다는 반론을 어떻게 판단했는가?
- 어떤 사용자 조건에서 A를, 어떤 조건에서 B를 선택할 이유가 있으며 그 대가는 무엇인가?

답이 약하면 **주제의 중요성은 보존하고 대안을 재설계**한다. 문서 수를 채우기 위해 자격을 통과시키거나 중요한 기능 주제를 복구/보안 주제로 대체하지 않는다. 해결하지 못한 경우 무엇이 약한지 명시하고 “완료/검증”으로 보고하지 않는다. 자동 검사는 작성 품질의 보조 검사이며 이 설계 판정을 대신하지 못한다.

## 5. 초심자를 위한 문서와 도식 규칙

1. 제목은 품질 목적과 설계 질문을 표현한다. 새로운 기술 이름을 알고 있어야 읽을 수 있는 제목은 피한다.
2. 도입부에서 VIA에 중요한 이유와 어려운 SW 문제를 각각 설명한다. “모델이 잘 이해해야 한다”로 끝내지 않는다.
3. 각 주제에 **구조 비교도와 구체 사건 처리도**를 둔다. 첫 그림은 책임, 자료와 의존성, 둘째는 요청/반환 순서와 수정 효과를 보여준다. 복잡한 한 장으로 합치지 않는다.
4. 공통 부분은 검정, A 고유는 파랑, B 고유는 초록이다. 색은 추천이 아니다. 같은 요소의 위치를 맞추되 실제 topology가 다른 부분은 다르게 펼친다.
5. Component는 책임을 가진 상자, 내부 Module은 그 안의 둥근 상자, 저장은 원통, 자료는 접힌 종이, 외부 모델/연동은 육각형이다. 논리 actor는 OS process와 구별한다.
6. **네모 박스 안에는 Component 또는 Module 이름만 쓴다.** 이름 아래 역할 문장/처리 절차/입출력 값을 넣지 않는다. 저장 원통은 상태/저장소 이름만 쓴다. 흐름, 순서, 보내는 데이터와 조건은 관련 화살표에 적는다. 상황/장단점/범례는 상자 밖에 둔다. 요청과 반환은 별도 방향으로 표시한다. 구조도는 각 안의 실제 처리 번호를, 사건도는 본문 §4와 같은 사건 번호를 쓴다. 둘을 하나의 번호 체계라고 오해하게 하지 않는다.
7. 각 안의 생산자/소비자와 상태 접근을 별도로 도출한 뒤 배치한다. 같은 개수의 상자와 같은 직렬 연결을 먼저 만들고 이름을 채우지 않는다. 공통 위치 정렬은 실제로 공통인 책임에만 적용한다. 색과 이름을 가려도 핵심 분기, 결합, 반복, 원본 접근 또는 실행 경계의 차이를 지목할 수 있어야 한다. 모양을 다르게 만드는 것만으로 구조 자격을 인정하지 않는다.
8. SVG와 draw.io를 함께 유지하고 실제 렌더를 본다. 텍스트가 겹치거나 화살표가 엉뚱한 상자를 향하면 자동 검사 통과로 덮지 않는다.

9. **글만 읽는 검토:** 그림을 가리고 목적, 어려움, 양안의 입력/생산자/상태/결과/정정/실행 허용, 선택 조건을 설명할 수 있어야 한다. 약어/새 개념은 첫 등장에 풀어 쓴다.
10. **그림만 보는 검토:** 본문을 가리고 같은 사용자 상황, 각 안의 실제 처리와 되돌아오는 결과, 다른 구조의 위치, 이익/비용/지원 한계를 설명할 수 있어야 한다. 핵심 호출을 설명 문장에만 남기지 않고 화살표로 드러낸다. 무관한 내부 상세는 생략하되 경유 책임을 화살표에 밝힌다.
11. 여섯 항목 모두 설계 반론 검토 → 본문/그림 대조 → 실제 렌더 → 발견 사항 수정 → 재확인 순서로 반복한다. 횟수를 채우는 것보다 발견한 문제와 수정 내용을 04-37에 남기는 것이 중요하다. 자동 검사는 의미 품질을 판정하지 않는다.

12. **사건도는 같은 미분류 입력과 같은 사용자 출력 경계로 비교한다.** 한쪽의 모델/조회/응답 경로를 생략해 차이처럼 보이게 하지 않는다. 공통 참여자는 같은 열/범위로 표시하되 내부 구조를 같게 만들라는 뜻은 아니다. 신규/보완 여부나 정답 Task를 미리 제공하지 않는다.
13. **강한 대안과 비교축을 함께 보존한다.** cache, patch, 검증과 동등한 자료 접근을 허용하되, 핵심 생산/제어 책임을 다른 쪽으로 옮기면 설계 변경이나 혼합안으로 기록한다. 41에서 B에 자료를 읽을 능력을 주는 것과 모델이 조회 도구/최종 관계를 자율 결정하게 하는 것은 다르다. 후자를 설명 보완으로 몰래 추가하지 않는다. 참조 모델 호출 상한을 대안에 자동 적용하거나 호출 최소화를 기능 품질보다 앞세우지 않는다.

상세 표기 원칙은 [그림 가이드](./diagram-design-guide.md)를 따른다. 부연 계약은 뒤에 두고 먼저 전체 처리 원리가 이해되게 한다.

## 6. 품질 비교의 공통 규칙

V-01~13의 의미와 우선순위는 [03-00 §2](./03-00-quality-scenarios.md#2-어떤-품질을-보고-있는가)가 유일한 원본이다. 기능 정확성/적절성/완전성이 공동 1순위, 반응/완료 시간이 공동 2순위다. 변경, 자원, 복구, 나머지 관점도 빠뜨리지 않는다.

모든 문서에서 13개를 점검하되 **구조 원인 → 중간 효과 → 사용자 이익/손실**로 설명한다. 인과가 없으면 공통이라고 쓰고, 미확인은 미확인으로 남긴다. V-04/05는 VIA 귀속 시간이며 Agent 내부 실행 시간을 성능 이익으로 세지 않는다. 병행 작업의 시간은 단순 합산하지 않는다. 자원과 수용량, 분석과 시험, 연동과 PC 공존은 각각 구별한다.

품질 결과의 수치/별점/가중 총점을 만들지 않는다. 사용자가 요청한 심사 관점의 별점은 04-37에서 작성자의 문서 평가로만 표시하며, 품질 성능값이나 실제 심사 점수와 구별한다. 향후 QA 정의, 지표, 모집단, 실패/미지원 처리와 측정 방법은 모든 문서에 같은 공통 계약을 적용한다. 안별 유리한 사건만 고르거나 기능을 포기한 안을 빠른 성공으로 처리하지 않는다.

## 7. 완료와 리뷰의 조건

- 여섯 문서가 모두 도입, 두 구조, 동일 사건, 지원 범위, 13개 품질, 최소 전환과 판단을 갖춘다.
- 각 안의 실제 적용 토대와 없는 capability를 구별한다. 공개 pattern 문서는 VIA 성능 검증이 아니다.
- 04-31~34의 기능 주제는 중요한 이유를 잃지 않으면서 이전 약한 대안의 문제를 실제로 고친다.
- 서로 독립적으로 조합할 선택과 결합이 필요한 선택을 여섯 문서 전체에서 검토한다. 하나의 비용/이익을 여러 DP의 독립 증거로 중복 계산하지 않는다.
- 작성자 자기 반론, 도식 렌더, 링크/용어/QA/생성물 검사와 실제 diff를 확인한다. 자동 검사는 구조 자격이나 품질 우위를 증명하지 않는다.
- 여섯 항목을 모두 작성한 뒤 사용자와 리뷰한다. 작성자가 붙인 “비교 유지”는 설계 판단이며 사용자 승인, 독립 검증, 최종 DP 선정 또는 구현/측정 허가가 아니다.

## 8. 메인 그림과 강한 대안의 최종 대조

32에 관한 아래 대조는 범위 변경 전 이력이다. 32는 주요 비교 후보에서 제외했으며, 이전 도식은 공통 설계 참고 문서의 현행 대안으로 사용하지 않는다.

메인 그림에서 다음을 직접 짚는다: 31의 의미 상태 쓰기/변경 전달, 32의 관측 생산과 요청 조회의 독립 수명, 33의 통합/Task별/기능별 의미 생산, 상태와 공통 채택, 34의 선행 읽기와 의존 실행망, 35의 감사 기록과 권위 사건 원장, 36의 직접 권한과 OS/Broker 경계. 주요 차이를 사건도나 본문에만 숨기지 않는다.

A의 합리적 개선도 그린다. 조건 보존/patch, Task별 선택 갱신, 선행 읽기, 감사 기록/backup와 기존 격리를 삭제해서 B를 유리하게 만들지 않는다. 별점 상승을 목표로 삼지 않고 이 강한 반론과 같은 요구를 견디는지를 검토한다.
