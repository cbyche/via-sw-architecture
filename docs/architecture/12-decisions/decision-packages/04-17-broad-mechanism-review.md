## 1. 이번 판정은 끝냈는가

**15개 방향 중 3개는 구조 비교 후보로 유지, 11개는 주요 후보에서 제외, 1개는 구조 차이를 인정하되 현재 VIA 범위에서 보류한다.** 이는 작성자의 설계 선별이며 사용자 채택, 독립 리뷰, 측정 우위나 Stage 5 진행 승인을 뜻하지 않는다.

## 3. 남긴 후보의 13개 관점

방향은 T 대비 구조에서 이어지는 가설이다. 동일 QA의 정의, 평가 단위, oracle, 시간 경계, 모집단과 실패 처리는 모든 후보에서 공통이어야 한다. 별점, 공수 수치나 품질 점수는 만들지 않았다. V-04/05는 VIA 귀속 시간이며 Agent 내부 업무 시간을 이익으로 가져오지 않는다.

| V-06 자원/수용량 | weights는 같은 한 개. 단계별 작은 문맥과 중간 후보/추가 호출 비용, 세션/시간 예산에 따른 수용량 변화 | journal/current view/checkpoint 저장, write amplification, replay 작업 메모리. 저장량과 RAM을 구별. 유한 journal/replay 예산 필요 | 제한 process, IPC buffer, 범위별 cache와 handle 증가. weights 복제 없음. 동시 범위 수가 수용량 제약 |
| V-07 결함 허용/복구 | 현 owner 원본 복구 유지. 중간 stage는 폐기/재계산, dependency 검사 없는 부분 재개 금지 | 파생 view 손상은 온전한 journal에서 재구성. journal 자체 손상/잘못된 event는 공통 원본 장애. replay/삭제 규칙 실패 위험 | 이동한 처리 코드 crash/오접근 범위 제한. Broker/Core/OS/공유 model 장애는 공유. 재시작 후 새 handle과 자료 범위 필요 |
| V-08 변경/모듈성 | 단계 계약에 맞는 변경 국소화 가능. schema를 넘는 의미 변화는 앞뒤 stage와 조립/재실행 규칙 공동 수정 | view 변경을 event 원본과 분리 가능. event 의미 변경은 reader/reducer/checkpoint 및 삭제 변환 유지 부담 | 처리 코드와 권한 코드 분리. 자료 형식/범위 변경이 IPC/handle/Broker/폐기 계약에 걸치면 공동 변경 |
| V-09 분석/시험 | 원인: 어떤 단계의 후보/근거가 틀렸는지 추적. 시험: 각 stage와 오류 전파/feedback/총예산 조합 필요 | 원인: 확정된 domain 전이 순서 추적. 시험: replay 결정성, effect 중복 금지, 버전 및 삭제 후 재구성 필요 | 원인: Broker 허용/거절 및 실제 handle 사용 추적. 시험: 우회 파일/네트워크/IPC 접근, stale handle/철회 및 process crash 필요 |
| V-10 기밀성 | 단계별 자료 노출 범위 제한 가능. 중간 사본/모델 job의 삭제 의존성 증가. 권한 owner는 동일 | 이력 payload의 잔존/옛 checkpoint 부활 위험. 삭제 가능한 본문과 비민감 metadata를 분리해야 함 | 비교의 직접 축. 제한 처리기의 범위 밖 접근을 줄이지만 trusted Broker/model/OS는 보호 주장 밖. 권한 tag만으로 OS 격리 주장 금지 |
| V-11 연동/공존 | 연동: 외부 Agent canonical 계약 유지, 모델 중간 schema 지원 필요. 공존: 더 많은 호출이 PC 연산에 경합 | 연동: Agent/source 계약 유지. 공존: journal/checkpoint I/O와 replay 메모리가 다른 앱에 부담 | 연동: source/OS 제한과 Broker 계약 지원 필요. 공존: process/복사/IPC가 다른 PC 앱과 자원 경합 |
| V-12 조작/오류 방지 | 원문/대상/Task의 어떤 조건이 부족한지 질문 가능. 단계 고착으로 질문이 늘 수 있음. UI가 내부 stage 용어를 사용자에게 노출할 필요 없음 | 기존 Task/질문/전달 UI 유지. 복구 중 검증 범위와 미확인을 알리고 과거 승인 자동 재사용 금지 | 실제 권한 범위와 미지원 이유를 표현. 권한 확대를 조용히 수행하지 않으며 필요 없는 재동의 질문을 강제하지 않음 |
| V-13 설치 | 새 weights 없음. pipeline/schema/prompt 호환 배포 필요 | journal/current/checkpoint version 및 reader의 호환 갱신/복구 절차 추가 | OS별 제한 process/Broker 실행 및 signing/권한 설정의 구현 부담. 제거 시 임시 영역/권한/handle 정리 필요 |

## 4. 같은 요구 목록에서 기능 차이를 숨기지 않았는가

| 공통 요구 묶음 | 세 후보의 처리 |
| --- | --- |
| Voice/Text, 시점별 화면, 좁은 자체 지식 S2S, local stop | 공통 경로 유지. M-2는 Context가 필요한 해석 경로를 교체. 어느 후보도 새 helper/Omni weights 복제를 전제로 하지 않음 |
| 불완전 요청, 복합 관계, 질문 답변, Task 연결 | M-2는 단계 표현과 결합의 기능을 설계하지만 실제 모델 지원/정확성 미검증. 다른 두 안은 같은 semantic 계약을 유지 |
| Agent 위임, actual status, 정정과 취소 | 모든 안에서 Task Manager/Agent Gateway의 외부 capability 기준 유지. C가 없는 cancel/조회 기능을 만들지 않음 |
| 현재 동의/제공/삭제 | 공통 요구 유지. S-1의 옛 event/checkpoint, S-2의 process 사본/handle, M-2의 단계 자료까지 각각 추적. 물리 정리 미완료는 별도 상태 |
| 실제 Text/Voice 전달과 채널/재시작 연속성 | 생성, 접수, 완료, 청취 구별 유지. 정상 권위 기록과 외부 조회로 복구해야 하며 무조건 UNKNOWN 종료로 우회하지 않음 |
| 변화 대응과 오류 설명 | 각 안의 새 schema/원본/권한 경계 비용을 V-08/09/13에 공개. 이전 QA 측정이나 타 제품 결과로 대체하지 않음 |

## 5. 가장 강한 자기 반론과 처리 결과

| 반론 | 처리 및 최종 판단 |
| --- | --- |
| 이전 C-대화도 판단 못 했는데 새 안만 늘린 것 아닌가? | 기존 graph, Semantic Proposal, owner 기록과 재해석에 대응시켜 주요 후보에서 제외. 미결 상태 해소 |
| 하나의 Component 안에서 교체되면 모두 사소한 것 아닌가? | 외부 port 보존과 내부 처리 구조 보존을 구별. M-2의 단계 계약, 후보 전달, 결합/feedback 및 무효화 구조를 명시. 주변 Task/전송까지 재작성한다고 하지 않음 |
| M-2도 화면 전처리를 추가한 S-02와 같은가? | 마지막 통합 모델에 전체 raw 문맥을 다시 넣는 안은 별도 hybrid로 분류. M-2는 그 최종 통합 판단을 실제로 없애고 명시적 결합으로 의미를 생산 |
| M-2는 단계가 많으니 정확하다고 주장하는가? | 조기 오류 전파, 동일 Omni의 상관 오류, 교차 문맥 손실과 질문 증가를 명시. 후보 유지와 정확도 우위를 분리 |
| S-1의 손상 복구는 backup으로 가능한가? | 그렇다. 단순 저장 손상만으로 선택하지 않음. 원본 domain 전이에서 상태 생성/변경/재구성하는 이익과 비용으로 좁힘 |
| 완전한 이력/replay를 T에 추가하면 S-1 전환은 작은가? | 점진 hybrid 가능. 다만 owner 전체의 event/동시 확정, reader/reducer, 삭제/효과 재생 방지 및 두 원본 충돌 처리까지 필요. 이 설계비와 데이터 이행비를 분리 |
| S-2도 기존 connector worker가 이미 해주는가? | 기존에 격리된 연동은 이익에서 제외. 추가로 이동하는 Context 조립/cache와 해석 입력 구성 코드의 전역 권한 제거를 비교 |
| S-2의 공유 model이나 Broker가 다른 범위를 읽을 수 있지 않은가? | 해당 영역은 신뢰 경계 안에 남음. 모든 공격/정보 유출 방어라고 주장하지 않음. 제한 대상이 직접 우회할 경로를 막는 성질만 유지 |
| 원칙을 완화해서 세 개를 억지로 통과시킨 것 아닌가? | 같은 port라는 이유만으로 싸다고 판정하던 오류를 고쳤다. 각 안에서 가장 싼 추가/병행/drain 경로를 제시하고 그래도 필요한 구체 구조 변경을 명시. T 유지 조건과 후보 필요성이 무너지는 조건도 남김 |
| 세 안 모두 역방향도 크게 고쳐야 한다고 과장했는가? | 기존 T 엔진을 보존한 전환, reducer를 직접 갱신 함수로 재사용하는 전환, Broker를 남긴 sandbox 해제는 더 쌀 수 있음을 개별 §5에 명시. 첫 도입/구조 유지비와 운영 rollback을 구별하고 양방향 공수가 같다고 주장하지 않음 |
| 낮은 품질 문제로 도피했는가? | 상위 기능 문제군 M/D/W를 우선 탐색하고 M-2를 첫 비교로 둠. 자원 정책과 자료 source 확장은 제외 사유를 공개. 복구/권한 후보를 의미 정확성 개선으로 승격하지 않음 |

## 6. 이번 보고 경계와 남은 검증

이번 설계 검토의 결론은 **세 구조를 실제 T의 대안으로 비교할 가치가 있다**는 것이다. 최종 DP 선정 및 기능/품질 우위는 사용자 검토와 후속 공통 평가 계약에 따른다. 구조의 전환 판정은 끝냈으며, 미측정 값을 핑계로 사용자에게 설계 판단을 넘기지 않는다.

그림은 남긴 세 안의 비교 범위와 정상 처리/복구 또는 권한 경계를 설명한다. 본문에서 다루는 모든 장애 조합을 한 장에 넣어 검증됐다고 주장하지 않는다. SVG와 draw.io의 일치 및 렌더 확인, 저장소 문서 검사의 실행 기록은 현재 [WORKPLAN](./00-workplan.md)에 남긴다.

작성자 대조만 수행했다. 별도 독립 리뷰, 구현 실행, 모델 capability 시험이나 성능 측정은 수행하지 않았다. 기존 target, 01~03의 승인된 요구/품질, QA registry, accepted/deferred ADR와 이전 evidence의 의미는 유지했다. 대안별 모델 호출 및 OS enforcement의 실제 지원, 전환 공수와 품질 수치는 확인 전이다.
