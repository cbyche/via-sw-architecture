## 1. 목적과 공통 기준

목적은 같은 사용자 활동에서 네 DP의 실제 처리 구조가 정확성, 시간, 모델 비용,
변경 책임과 로컬 메모리에 어떤 tradeoff를 만드는지 관측하는 것이다. 목표값 달성,
발표 예시 수치 재현과 A/B 우열 만들기를 구현 목표로 삼지 않는다. 동점, 작은 차이,
목표 미달과 판단 불확실성도 결과에 남긴다.

현재 기준은 [공통 실행 계약](./04-40-common-execution-contract.md),
[QA 정의](./03-02-quality-attribute-definitions.md),
[관측 목록](./03-02-workload-manifest.json)과 [조합 검토](./composition-review.md)다.
QA-02의 세 평균, QA-03의 두 평균과 Mac 메모리의 두 지표는
[사용자 지정 보고 요구사항](../../../../benchmark/architecture/README.md#poc-결과-보고-요구사항--2026-10-11-사용자-지정)을 함께 적용한다.
현재 ASR-QA-v6/P21 전체 실행은 정확성 630조건, 반응 135관측, 사이클 95관측이다.
대표 사례 몇 개의 pilot에 이 분모나 최종 QA 점수를 붙이지 않는다.

VIA는 현재 Mac에서 실행하고 클라우드 음성 모델과 의미 LLM을 의존성으로 사용한다.
Conversation, Request, Task와 전달 상태의 권위는 로컬 VIA에 둔다. VAD는
Interaction Manager의 Turn-taking Control에 두고 발화 종료와 전사 완료를 구별한다.
이 비교를 이전 on-device Omni 참조 Architecture에 자동 동기화하지 않는다.

초기 실행 구성은 다음 다섯 개다. 첫 구성은 실험 기준이지 A의 최종 선택이 아니다.

| 구성 | DP41 | DP44 | DP45 | DP42 |
| --- | --- | --- | --- | --- |
| 공통 기준 | A | A | A | A |
| 41 교체 | B | A | A | A |
| 44 교체 | A | B | A | A |
| 45 교체 | A | A | B | A |
| 42 교체 | A | A | A | B |

처음부터 16개 조합을 평가하지 않는다. 다섯 구성의 차이는 이 기준 구성에서 해당
DP 하나를 바꾼 효과다. 다른 조합에도 같은 효과가 난다고 일반화하지 않는다.
공통 계약을 통과해도 DP 간 상호작용 때문에 결론이 달라질 근거가 있으면 해당
조합과 반증 사례를 추가하고 추가 이유와 모집단을 결과 전에 명시한다.

## 2. 새 코드와 결과의 위치

### 2026-10-11 후속 지시: 비교 기제 보존과 필요한 확인만 수행

사용자는 완전한 VIA 구현이 아니라 DP별 QA tradeoff 수치를 얻는 작은 PoC라는 목적을
재확인했다. 합리적인 mock/stub은 허용하지만 비교 기제를 대신하여 A/B의 차이를
지우면 안 된다. 이후 단계 진행에서는 아래 원칙을 우선한다.

| 비교 | 실제 후보에 남길 기제 | 공통 mock/stub으로 줄일 수 있는 범위 |
| --- | --- | --- |
| 41 | 모델 주도 반복/조회 결과 재입력과 코드 주도 frame 해결/부분 호출. 실제 호출 경로/context/재시도 보존 | source와 외부 업무. 모델 지정 반환은 구조 검증에만 사용하며 최종 의미 정확성/실제 모델 지연/청구를 대신하지 않음 |
| 44 | 중앙 비동기 continuation과 Stage별 대기/후속 실행/Join. 실제 queue와 release 경합 | 동일 payload에 대한 외부 업무 진행/완료. A를 직렬화하거나 공통 runner가 양안 후속 처리를 대신하지 않음 |
| 45 | A의 요청별 read/조합/cache와 B의 실제 생산/검증/게시/조회, 준비/갱신/미사용/coverage/source 확인 | 원천 owner와 도메인 업무. 파생 정답 선주입이나 생산을 고정 delay 하나로 대체하지 않음 |
| 42 | A의 공동 로컬 확정과 B의 독립 owner/저장소/process 및 명령/접수/사건. 실제 IPC/copy/정합 처리 | 외부 Agent. 같은 메모리의 공통 상태를 양안의 권위로 써서 확정 경계를 지우지 않음 |

mock 값은 DP별 기대 우열에 맞춰 다르게 주지 않는다. 동일 외부 조건 아래 후보가
스스로 발생시킨 호출/조회/대기/명령/할당만 관측한다. 공통 코드가 이런 작업을 대신
하거나 선주입하여 차이를 지웠는지 trace로 확인한다. 차이를 드러낼 조건이 빠져 있으면
민감 사례/관측을 보완하고, 실제로 경로가 동등해서 나온 작은 차이/동점은 그대로 인정한다.
차이를 만들기 위한 지연/호출/메모리 padding은 넣지 않는다.

기존 검토 ①의 문서 항목마다 승인을 요구하지 않는다. 구현 경로, 자료형, 파일 배치와
무상 구조 검증은 위 원칙에 따라 진행한다. 아직 닫히지 않은 S3 반응 endpoint/오답 후
정정 membership은 draft policy로 구별하고 최종 QA 계약을 확정할 때 확인한다.
새로운 비용 지출, 정답/모집단/채점 의미의 중요한 변경, 또는 비교 기제를 보존할 수 없는
범위 변경은 사용자가 확인할 시점이다. 유료 호출의 총 비용 상한은 아직 미정이며 실제
API 실행 전 검토 ②는 유지한다. 본 측정 전 계약 검토 ③와 해석상 불확실한 결과 검토 ④도 유지한다.

아래 하위 경로는 구현 시작 후 만들 제안이다. 이전 source는
[전체 보관 안내](../../../../scripts/archive/pre-dp41-45-experiment-tools-20261011/README.md)에 연결한 archive에 유지한다.

| 위치 | 책임 |
| --- | --- |
| `prototypes/candidates/dp41_45_poc/` | 공통 local 상태와 검증, 각 DP의 A/B 구현, 실제 모델과 source adapter, telemetry |
| `benchmark/architecture/dp41_45_poc/` | 공통 입력, 평가 전용 정답, Agent stub, 사건 replay, runner, 판정과 집계, 변경 실험 |
| `results/architecture-evaluation/current/`의 새 campaign directory | 실행 계약, source/input digest, 환경, raw trace/audio/메모리/청구, 판정과 집계 |

후보 입력과 oracle은 저장 경로 및 실행 접근을 분리한다. Agent stub은 실제로 받은
payload에 따라 동작하며 잘못된 대상, 조건, revision이나 발송을 정답으로 고치지 않는다.
사건 재현은 source의 동일 monotonic offset과 실제 접수 뒤의 동일 반환 지연을 사용한다.
후보의 내부 완료 시각에 맞춰 한쪽만 유리한 사건 순서를 만들지 않는다. 예약 시각과
실제 주입 시각, 중복 event ID, 늦은 반환과 취소 이후의 효과를 함께 기록한다.

## 3. 수행 순서와 완료 기준

### 2026-10-12 음성 경계 축소 제안

사용자는 반복 WAV/전사 API 대신 동일 전사 fixture와 소수 지연 보정/공통 모형을
제안했다. [전사 입력과 음성 경계 모사안](./poc-preimplementation-review/05-speech-boundary-simulation.md)은
DP41의 주 실행을 전사 fixture와 실제 의미 LLM/후보 코드로 축소하는 것을 권고한다.
기존 실제 음성 pilot은 필수 반복 경로가 아니라 실제 음성 endpoint/내용/자원을
검증할 때의 선택 실험으로 재검토한다. 아직 API/보정 실행과 QA 원문 개정은 하지 않았다.
원천 onset/end/span과 전사 도착을 구별하고 공통 지연은 사건 주입에 반영한다.
음성 포함 시간/비용의 추정과 실제 후보의 관측을 분리하며 임의 A/B 가감은 하지 않는다.

### 다음 완료 목표 제안: DP41 A/B의 여섯 QA 결과를 먼저 묶음

사용자는 중간 mock 검토에서 멈추기보다 DP41 A/B의 여섯 QA가 모두 정리된 시점에
확인하기를 원한다. 아래 범위를 다음 완료 목표로 제안한다. 유료 실행 허용과 총 지출
상한은 아직 정하지 않았으며 이 범위 제안만으로 실제 API 호출을 시작하지 않는다.

- 비교는 `C0=41A+44A+45A+42A`와 `C41=41B+44A+45A+42A` 두 구성이다.
  다른 DP의 B 구현을 기다리지 않는다. 공통 A는 P21에 필요한 경로만 실제 구현하고
  외부 Agent 업무/source/device 주변은 비교 기제를 보존하는 범위에서 모사한다.
- 세 사례의 무상 구조 검증 → P21 지원 확장 → 실제 모델/음성/judge의 작은 pilot →
  계약 고정과 전체 반복 → 변경 실험/집계/원인 분석을 이어서 수행한다.
  작은 pilot의 실패를 보존하고 본 측정 전에 개선하되 본 측정 실패를 선택적으로 바꾸지 않는다.
- QA01~04는 각 구성 P21 5회다. 구성마다105사례/630조건,135반응/95사이클이며
  두 구성을 합하면210사례/1,260조건/270반응/190사이클이다. 집계는 구성별 분모를 유지한다.
- QA05는 두 구성×M01~06의 **12개 독립 변경 job**이다. 실제 patch/완료/회귀와
  U01~U18 고유 책임 집합을 복수 검토자가 확인한다. 다른 DP의18개 job은 후속이다.
- QA06는 전체 활동에서 Mac의 phys_footprint와 resident size/RSS를 각각 보고한다.
  Windows commit 등급을 자동 환산하지 않는다. 실제 프로세스/공유/copy와 포함 범위를 공개한다.
- 결과에는 각 QA 원지표/보호 조건, QA02 세 평균, QA03 두 평균, 실제 usage 기반 비용,
  실제 변경 책임 수와 Mac 두 peak, raw 재계산 경로와 모든 실패/불확실 원인을 함께 넣는다.
  비용은 usage 환산과 provider 청구 확인 수준을 구별하고 청구 미확인/누락은 남긴다.

첫 구현 완료 예상은 mock 세 사례3~5시간, 모든 QA 결과 묶음은 **집중 작업18~30시간
(약2~3일)**이다. 기존3~5시간은 전체 QA 측정 예상이 아니다. 이는 현재 문서 계약과
sub-agent 분업을 전제로 한 작업 추정이며, API/권한/음성 수집 문제나 사용자의 설정
대기 시간은 보장할 수 없다. 큰 문제가 확인되면 영향과 수정한 예상을 알려준다.

일상적인 구현 선택, mock trace 검토와 정상 범위 재시도마다 중단하지 않는다.
시작 전에 중요한 판정 규칙/실제 provider와 가격/유료 허용 범위/지출 상한을 한 묶음으로
확정하면 같은 범위에서 결과 묶음까지 이어간다. 비용 상한 도달, 실제 계정/권한 차단,
또는 비교/채점 의미를 바꾸는 문제가 생기면 필요한 확인만 요청한다.

설정 세션의 사용자 실행 보고에서 Qwen `qwen3.6-35b-a3b`, OpenAI 텍스트와
Realtime의 텍스트 응답은 확인됐지만 Realtime 음성 입출력은 미확인이다.
기존 QA 가격 reference의 Qwen ID와 실제 확인된 ID가 다르므로 실제 모델/region/
revision/price는 본 측정 전에 검증하여 실행 manifest에 고정한다. 이전 가격 reference를
새 모델의 실제 비용으로 재사용하거나 이 기록만으로 QA 원문을 자동 개정하지 않는다.

이 우선 순서는 아래1~6단계의 작업 내용을 DP41 결과 중심으로 묶는다. DP44/45/42의
B와 나머지 변경18개를 붙인 뒤에는 영향받는 공통 코드/입력/계약 버전에 맞춰
기준 C0와 필요한 비교를 재실행한다. 버전이 다른 기준 실행을 독립 표본처럼 복제하거나
공통 구현 변경의 영향을 DP41 효과로 설명하지 않는다.

### 1단계: 구현 전 검토 묶음

2026-10-11 [사용자 검토용 요약과 상세 부록](./poc-preimplementation-review/README.md)을 작성했다.
세 사례/정답, DP41 runtime draft, 여섯 QA/30개 변경 job과 raw 형식을 구체화한 문서이며
실행 코드, 측정 freeze와 실행 결과는 아니다. 기존 Frame v1의 실행 빈틈, QA-02의 오답 후
정정 membership, S3-02 반응 경계와 M04/M06의 baseline 지원 audit는 검토 ①에서 확인한다.

먼저 두세 쪽의 요약과 상세 부록으로 다음을 구체화한다.

- 대표 사례는 현재 P21의 **S1-01 한정 조회, S3-02 결과 의존 요청,
  S4-01 부분 정정과 늦은 반환** 세 개를 우선 제안한다. 입력, source, 사건,
  checkpoint와 final 정답 C1~C6, 금지 효과와 관측 경계를 연결한다.
- [기존 RequestFrame v1](./contracts/dp41-request-frame-v1.schema.json)은 설계 검토용이다.
  이를 바탕으로 첫 세 사례의 goal/selector/relation/constraint, 항목별 상태,
  bounded read 반환, 부분 모델 반환과 확인 질문을 실제 코드 분기로 정의한다.
  P21 확장에 필요한 지원 연산과 미지원 구간을 미리 구별한다. 임의 expression을
  실행하거나 VIA 관계를 자유 instruction에 숨기지 않는다.
- 공통 raw event, model call/context/usage/retry/discard, 실제 효과, 전달 receipt,
  causal DAG, 메모리와 cap 집계 필드의 예시를 작성한다.
- QA-05의 동일 U01~U18 책임 registry와 M-01~06 계약 차이를 확인하고 다섯 구성의
  **30개 독립 변경 작업**을 명시한다. 현재 baseline이 이미 가진 계약과 변경으로
  추가할 계약을 구별해 변경 전에 정답 기능을 미리 넣지 않는다.
- 첫 구현의 언어/runtime, process/storage 경계와 공통 port를 정한다. 초기 제안은
  Python async와 SQLite다. 42B는 독립 process와 상태 owner를 실제로 구현한다.

**검토 묶음 ① — 구현 경계의 기록:** 세 사례의 정답과 범위, 강한 A/B 구현 내용,
RequestFrame 지원 범위와 변경 책임의 평가 단위를 남긴다. 이 묶음의 수치는 실행
결과가 아니다. 위 후속 지시에 따라 각 항목의 일괄 승인을 새로 요구하지 않는다.
최종 채점 의미에 영향을 주는 미정 사항은 본 측정 계약 확정 전에 확인한다.

### 2단계: 공통 환경과 DP41의 작은 실행

공통 상태/ID/revision, bounded source read, adoption/권한/중복 검사, Task 인계와
실제 전달 기록을 구현하고 DP41 A/B를 붙인다. DP44/45/42의 기준 A도 세 사례에
필요한 공통 경로를 갖추되 후속 기능은 구현 범위에 명시한다.

41A는 조회 결과가 모델 판단에 돌아오는 반복 제어, 41B는 frame 항목 상태와
코드의 다음 처리 및 전체 binding 구성을 실행한다. B도 범위를 지정한 부분 모델
호출과 확인 질문을 허용한다. 마지막에 모델이 전체 의미를 다시 만드는 경로는
순수 B와 구별한다. 조건부 반복 횟수와 예산은 같게 정의하며 B를 1회 호출로 고정하지 않는다.

이 단계의 모델은 지정 반환을 주는 mock이다. 먼저 정상 trace와 함께 잘못된
payload, stale revision, 늦은 반환, 중복 사건, 누락 종료를 의도적으로 넣어
oracle와 시간/비용/메모리 원장이 오류를 그대로 드러내는지 검증한다.
cap과 실측 평균의 차이는 고정된 검증 입력의 산술로 확인한다.

완료 조건은 세 사례를 양안에서 입력부터 최종 효과/전달과 집계까지 연결하고,
각 집계 행에서 raw 근거를 찾아 재계산할 수 있는 것이다. 검증 성공과 후보의
QA 통과는 구별한다. 잘못된 후보를 평가자가 고쳐 통과시키지 않는다.

**사용자 검토 ② — 첫 DP41 실행 후, 실제 API 호출 전:** 한 사례의 A/B trace,
실제 인계 payload, 판정 근거와 raw/집계 파일을 확인한다. 의미 정확성과 실제
음성 응답시간은 아직 측정하지 않았다. 다음 단계의 실제 호출 목록, 준비와 재시도,
judge를 포함한 예상 비용, 총 지출 상한을 제시한다. 유료 실행은 기존에 사용자가
허용한 범위가 있으면 그 범위 안에서 진행하며, 현재 미정인 비용 상한은 실행 전에 정한다.

### 3단계: 실제 모델의 소규모 DP41 pilot

승인한 범위에서 Qwen 의미 LLM과 GPT Realtime adapter를 연결하고 세 대표 사례를
실제 모델로 실행한다. provider/model/region/revision, 입력 context와 실제 usage,
재시도/폐기/늦은 청구를 기록한다. 음성 입력과 핵심 출력의 실제 경계를 수집할 수
있는지 확인하며, model packet이나 재생 queue 시각으로 음성 onset을 대신하지 않는다.

구조와 상태는 자동 판정하고 자유문은 필수 사실/금지 주장 rubric으로 LLM-as-a-judge를
사용한다. 사용자가 소수의 기준 응답과 불확실/불일치 사례를 검토할 수 있게 제시한다.
judge의 입력에 정답을 주더라도 그 정답을 후보나 Agent stub에 공급하지 않는다.
judge prompt/version/판정 근거와 비용도 별도 기록한다.

완료 조건은 실제 모델 출력과 실제 효과의 일치, 음성 경계의 수집 가능성,
호출별 청구 원장과 집계 재현을 확인하는 것이다. 이 pilot으로 P21 점수나 제품
정확률을 주장하지 않는다. provider capability나 구현 범위 문제는 확대 실행 전에 해결한다.

### 4단계: DP44 → DP45 → DP42 추가

공통 port, source/stub, raw 형식과 판정기를 재사용하면서 제어와 상태 소유의 차이는
각 후보 안에 구현한다. runner가 후보 대신 후속 실행이나 currentness를 결정하지 않는다.

- **44:** A의 중앙 continuation 회수와 비동기/병렬 지시, B의 Stage 입력/대기와
  Publication Join을 구현한다. 같은 동시 사건과 늦은 반환에서 비교한다.
- **45:** A의 원본 read/조합과 허용된 유효 cache, B의 실제 원본 생산/검증/게시/조회를
  구현한다. cache는 보완 tactic으로 구별하되 강한 A를 금지하지 않는다. 초기 생산,
  반복 사용, 미사용 갱신, coverage 부족, 원본 재확인과 철회 비용을 양안에 포함한다.
- **42:** A의 모듈형 Core 공동 확정과 B의 독립 상태 owner, process, 저장소 및
  command/receipt/event 연결을 구현한다. 양안의 논리적 수명은 동일하게 구별하고
  정상 질문 답변, 정정/취소 경합과 늦은 접수까지 확인한다.

각 B를 추가할 때 전체 QA의 공통 의미가 유지되는지와 해당 DP의 SENSITIVE 사례를
확인한다. 계획한 차이가 실제 실행 경로에 없으면 구현 범위 또는 비교 자격 문제로
기록하며 delay나 allocation을 인위적으로 붙여 차이를 만들지 않는다.

### 5단계: 전체 평가 준비와 계약 확정

P21 전체 입력/정답/관측 목록을 구현에 연결하고 다섯 구성의 지원 범위를 공개한다.
QA-01의 자동 판정과 자유문 판정, QA-02/03 집계, QA-04 전체 청구,
QA-05의 실제 변경 및 회귀, QA-06의 Mac 두 지표를 각각 준비한다.
QA-06의 process 합과 공유/copy 원장을 구별하고 초기 준비부터 drain/idle까지 관측한다.

**사용자 검토 ③ — 본 측정 직전:** 전체 사례 대응표, 미지원/불확실 항목,
judge 검수 예시, 30개 변경 과제, source와 환경, 호출/비용 상한을 한 묶음으로
확인한다. 계약/fixture/oracle/prompt/source digest, 반복, 실행 순서, timeout과
실패 처리, 점수 경계를 결과 전에 고정한다. 같은 준비 상태와 사건을 제공하는지
확인하고 선행 pilot과 본 측정 결과 directory를 분리한다.

현재 QA-06의 Windows commit 점수 경계를 Mac footprint/RSS에 자동 적용하지 않는다.
Mac에서는 먼저 두 지표의 실측 tradeoff를 보고한다. Mac용 점수가 필요하면 경계와
근거를 이 검토에서 결과 전에 별도로 정한다.

### 6단계: 본 측정, 변경 실험과 결과 검토

각 구성의 P21을 5회 독립 초기화하여 같은 원천 입력/사건으로 실행하고 A/B 순서를
교차한다. 공통 기준을 한 번의 실행 자산으로 재사용할 때 source_execution_key를
남기며 독립 표본으로 복제하지 않는다. QA-05는 각 구성의 같은 변경 전 baseline에서
M-01~06을 각각 독립 적용하여 총 30개 patch와 회귀 결과를 남긴다. 수정 기능 책임의
집합과 이유는 구현자 외의 복수 검토자가 현재 QA 계약에 따라 재확인한다.

**사용자 검토 ④ — 결과와 원인 해석:** 여섯 QA의 값과 raw 근거, 반복별 paired 차이,
모든 실패와 한계를 함께 리뷰한다. QA-02 세 평균과 QA-03 두 평균, Mac 두 메모리
지표를 모두 공개한다. mock 실행, 실제 모델 관측과 계산 추정의 evidence label을
구별하며 mock Agent가 포함된 PoC를 완성 제품의 PRODUCT_E2E로 표시하지 않는다.

정확성 오류는 원천 input, 모델 출력, 코드 상태 전이, 실제 효과와 전달을 따라
분류한다. 계약을 이미 지원하는 코드가 잘못 동작하면 구현 버그, 유한 표현이
필요 의미를 지원하지 못하면 현재 구조/지원 범위의 한계, 모델이 잘못 해석하면
모델 출력 오류로 우선 기록한다. 구조적 한계와 모델 오류의 인과를 확정하지 못하면
불확실로 둔다. 버그 수정 전 실패를 보존하고 수정 source를 별도 version으로 기록하며
영향 범위의 양안을 같은 조건에서 다시 실행한다. 결과를 본 뒤 유리한 관측만 교체하지 않는다.

## 4. 사용자 참여와 자동 진행

사용자는 중요한 범위/정답 변경, 검토 ②의 첫 동작과 비용 상한, 검토 ③의 본 측정
계약, 검토 ④의 결과 해석을 확인한다. API 계정/키와 billing 설정은 사용자가
제공하고 secret은 Git과 raw trace에 넣지 않는다. judge 기준의 소수 예시와
불확실 판정을 검토하되 630조건 전체의 수동 채점을 기본으로 요구하지 않는다.

승인된 단계 안의 구현, 검증, 분석과 수정은 에이전트가 이어서 수행한다. 매 파일
수정마다 승인을 요청하지 않는다. 범위나 비용 계약을 바꿔야 하는 문제가 생기면
구체적인 영향과 대안을 제시한다. 검토 가능한 단계마다 이번 작업만 commit/push하고
다른 세션의 미커밋 변경과 기존 archive를 보존한다.

## 5. 준비 문서 게시 전 검증

2026-10-11 이번 게시 파일만 반영한 사본에서 활성 링크/용어, QA catalog,
P21 계약/참고 계산, 두 QA 발표 투영, DP41 출력 예시와 공통 실행 예시 검사가
통과했다. 보관 manifest의 11개 파일은 원본 bytes/hash/mode와 일치하며 기존
archive의 1,200개 파일은 변경되지 않았다. 이는 정적 문서 및 보관 검증이며 PoC
구현이나 모델 품질 측정이 아니다.

전체 도식 검사에는 기존 **DP42 structure, DP44 structure/event, DP45 structure의
생성물 불일치**가 남아 있다. 이번 변경을 제거한 기준 HEAD
`7cfa35c2de8f8339bf1a719fa20535e9ec184c2e`에서도 동일하게 재현했다.
[기존 main CI](https://github.com/cbyche/via-sw-architecture/actions/runs/38145263902)는
DP42 검사에서 실패했다. 이 준비 문서 게시에서 해당 그림/생성 코드를 수정하지
않으며 전체 CI 통과로 표시하지 않는다. push 이후 실제 CI 상태는 게시 보고에 남긴다.
