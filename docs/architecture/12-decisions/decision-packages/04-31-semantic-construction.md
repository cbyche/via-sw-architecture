# 04-31. 요청 이해의 정확성을 위한 의미 구성 — 전체 의미 생성과 제약 결합

> 구조 재설계안 / 2026-10-03 / [가이드와 읽기 순서](./04-30-comparison-guide.md) / 다음: [화면 대상](./04-32-screen-grounding.md)

## 1. 왜 VIA에서 중요한가

사용자가 두 표를 가리키며 “작년 표만 보고서에 넣어줘. 메일은 보내지 말고 초안만 만들어”라고 한다. VIA가 문장을 자연스럽게 답해도 표, 금지 조건 또는 기존 업무를 틀리게 연결하면 다른 일을 시킨다. VIA의 핵심은 Agent에게 넘길 **목표, 대상, 조건과 업무 관계**를 맞게 만드는 것이다. 실제 보고서 작성 방법은 Agent가 결정한다.

관련 요구는 UC-03/04의 지칭, UC-06의 보완, UC-09의 복합 요청, UC-10의 기존 업무 연결이다. Request는 이번 사용자 지시, Task는 여러 지시에 걸쳐 이어지는 업무다. 요청 의미란 이 둘과 자료의 관계를 표현한 결과다.

## 2. SW Architecture에서 무엇이 어려운가

“작년”을 해석하려면 표의 내용이 필요하고, “초안만”의 뜻은 메일 업무 상태에 따라 달라진다. 판단을 합치면 다양한 관계를 함께 볼 수 있지만 어디에서 오결합했는지 분리하기 어렵다. 판단을 규칙으로 나누면 검증과 수정이 쉬워질 수 있지만 규칙이 표현하지 못하는 뜻을 잃는다.

**모델이 완성된 의미 관계를 생성하게 할 것인가, 모델은 후보를 제시하고 명시적 타입과 제약으로 의미 관계를 구성할 것인가**가 결정이다. 타입은 `자료`, `업무`, `금지 조건`처럼 값의 종류이며, 제약은 `수정 대상은 자료여야 함`, `발송 금지와 발송 실행은 함께 선택 불가` 같은 관계 규칙이다. 단순히 LLM 호출을 세 번으로 나누는 문제가 아니다.

## 3. 공통 준비와 두 구조

Interaction Manager가 발화와 당시 지칭 근거를 전달한다. Request Controller는 Context Manager에서 허용 자료와 Task 후보를 조회해 반환받는다. 같은 원문, 당시 근거, 현재 권한과 Task 사실을 양안에 제공한다. Model Access는 동일 Omni를 호출한다. 최종 외부 실행 허용은 Request Controller가 현재 사실을 확인한 후에만 내린다.

### A. 모델이 전체 의미를 생성하고 프로그램이 실행 가능성을 검사

Request Interpreter의 **통합 의미 생성 Module**이 원문과 관련 근거를 모델에 전달한다. 모델이 `표 A를 보고서 Task에 사용`, `메일 Task에는 초안 생성만 허용`처럼 전체 관계를 제안한다. **제안 검증 Module**은 존재하는 ID, 권한, 필수 값, 금지된 실행 조합과 현재 버전을 검사한다. 모순이나 미해결은 추가 읽기, 재해석 또는 질문으로 반환한다.

A도 구조화된 출력, 강한 검증, 관련 자료 선별과 부분 재시도를 사용할 수 있다. 모델이 오류를 낸다는 이유로 무검사 실행을 비교안으로 만들지 않는다. 다만 대안 관계를 찾아 최종 조합을 만드는 정상 생산자는 모델이다.

### B. 후보를 타입 있는 표현으로 바꾸고 제약 해법으로 의미를 구성

Request Interpreter 안에서 **표현 변환 Module**이 원문과 근거로 목표/부정/지칭 후보를 만든다. 모델은 이 후보의 원문 구간과 근거를 제시한다. **후보 결합 Module**은 자료/Task ID 후보와 가능한 관계를 유한한 표로 만든다. **제약 해결 Module**은 이 후보 중 규칙을 함께 만족하는 배정을 찾아 의미를 구성한다. **질문 생성 Module**은 해가 여러 개면 서로 다른 필드를, 해가 없으면 충돌한 조건을 질문 대상으로 만든다.

예를 들어 표 후보가 A/B이고 보고서 후보가 R인 경우 `삽입 대상 ∈ {A,B}`, `대상.year=작년`, `대상.type=table`, `수정 업무=R`을 결합한다. `초안만`은 메일 실행 관계에서 `SEND`를 제거한다. 그러나 year 추출이나 `초안만`의 의미 후보 자체가 틀릴 수 있다. 규칙을 만족하는 해가 하나라는 사실은 사용자 의도가 맞다는 증거가 아니다. 불확실한 후보나 누락된 근거는 미해결로 남긴다.

이 중간 표현을 **의미 IR**이라고 부른다. IR은 후속 결합이 소비하는 명시적 자료 형식이다. B의 변경 단위는 prompt 하나가 아니라 타입 체계, 후보 생성기, 제약 집합과 질문/수정 처리다. 실제 업무의 Tool 계획을 IR로 작성하지 않는다.

## 8. 가장 싼 전환과 혼합 반론

**“A에 validator를 붙이면 B 아닌가?”** A에도 validator가 있다. 완성 제안의 가능/불가능을 검사하는 것과, 복수 후보에서 관계를 생성하고 충돌에 따른 질문을 만드는 것은 다르다. validator가 후보를 열거하고 조합을 수정하며 질문을 결정하기 시작하면 이미 B의 핵심 의미 구성기를 도입한 것이다. 반대로 B가 만든 IR을 단지 힌트로 넣고 모델이 최종 관계를 자유롭게 다시 쓰면 A의 전처리형 혼합이다.

| 구별 | A → B | B → A |
| --- | --- | --- |
| 기능 개발 | 후보 추출과 규칙/해법 구현 | 전체 관계 생성과 제안 검증 구현 |
| 상태 이행 | 진행 요청 종료 후 임시 제안 이행은 작음 | 동일, 확정 Task/명령 기록 재사용 |
| 남는 재설계 | 관계를 모델 출력으로 받던 가정 제거. IR 타입, 후보 완전성, 해/충돌/미지원, 수정 의존성 및 질문 생산을 함께 설계 | 명시 해법의 보장을 모델 제안/검증으로 다시 나눔. 타입 밖 문맥과 관계를 입력하고 모순/질문 생산을 교체 |

두 엔진을 이미 구현했다면 선택 스위치는 작다. 여기서 중요한 비용은 스위치가 아니라 의미를 생성하는 체계의 신규 설계와 이후 의미 변경을 양쪽에 적용하는 일이다. 모든 정책을 코드로 만드는 과도한 문법을 강제하지 않고 후보 생성에는 모델을 사용한다. 혼합이 작은 규칙 검사로 같은 이익을 내면 B 전체를 도입할 이유는 줄어든다.

## 9. 판단과 실제 적용 조건

**구조 비교로 유지한다.** 이전의 “통합 호출 대 세 단계 호출”을 “생성된 전체 의미의 검증 대 명시적 후보의 제약 구성”으로 바꿨다. 해법의 생산 책임과 표현 체계가 달라지므로 단순 호출 분할과 구별된다. 다만 실제 중요한 표현을 타입/규칙으로 담지 못하면 B는 기능 손실이 큰 안이다.

A는 열린 언어와 교차 문맥이 중요할 때, B는 반복되는 VIA 제어 관계의 명시적 일관성과 변경 추적이 중요할 때 유력하다. 작은 A validator가 필요한 오류를 충분히 막는다면 B의 추가 비용은 정당화되지 않는다. B의 후보 추출과 규칙 범위는 실제 구현/검증 전이며 정확도 우위는 주장하지 않는다.

제약 해법의 구분은 [OR-Tools 공식 설명](https://developers.google.com/optimization/cp/cp_solver)의 feasible/infeasible/unknown 개념을 참고했다. VIA에 OR-Tools를 선정하거나 자연어 의도를 solver가 증명한다고 주장하는 근거는 아니다. 본 문서의 의미 IR과 처리 구성은 설계 제안이다.
