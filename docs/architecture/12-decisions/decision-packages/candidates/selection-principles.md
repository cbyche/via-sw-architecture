# Decision Point 선발 원칙

> 상태: **사용자와 논의한 원칙의 기록 / 적용 절차는 이번 문서화 제안**
> 기록일: 2026-09-30 · [후보 목록](./README.md)

**VIA의 핵심 문제를 해결하면서 대안에 따라 SW 구조, 특히 Component 구성·책임·연결이 실질적으로 달라지는 선택을 우선 발굴한다.** 심사위원이 두 구조 그림을 보고 해결 방식의 차이를 먼저 이해할 수 있어야 한다.

## 1. 사용자 지시와 논의에서 정한 원칙

| 원칙 | 선발 기준 | 부족한 예 |
| --- | --- | --- |
| SW 구조적 선택 | 책임, Component, Interface, 상태 소유권, 호출 경로, 배치 또는 장애 경계가 달라진다 | 같은 구조에서 retry 횟수나 queue 우선순위만 변경 |
| Component 변화 우선 | 추가·제거·분리·통합·핵심 책임 이동·연결 재구성이 있는 후보를 우선한다 | 그림의 박스 이름·색·배치만 변경 |
| 과제 목적과 관련 | 지속적인 Voice/Text/screen interaction과 Agent 업무 연결의 중요한 문제를 해결한다 | 제품 요구와 관계없는 범용 설계 패턴 나열 |
| 강한 현실적 대안 | 같은 사용자 목표를 충족하며 대안을 선택할 합리적 조건이 있다 | 상태 복구·동시 입력을 빼서 간단하고 빠르게 만든 대안 |
| 실제 설계 차이 | 그림의 변화가 책임·상태·계약의 변화로 설명된다 | 함수 하나를 새 Component로 그리되 책임·변경 경계는 그대로 |
| 일관된 질문 단위 | 하나의 구조적 선택과 그 필연적 결과를 다룬다 | Component 통합, 모델 변경, DB 교체, 알고리즘 변경을 한꺼번에 비교 |

Component 수가 반드시 달라져야 하는 것은 아니다. 수가 같아도 핵심 책임과 연결이 이동하면 구조적 변화다. 반대로 process만 나누었다면 배치 대안이지 논리 Component를 새로 만든 것으로 세지 않는다. 중요한 상태·장애 경계라면 후순위 후보로 남길 수 있다.

## 2. 제품 요구와 구조 선택을 나눈다

“음성 연결이 끝나도 업무를 이어간다”는 공통 제품 요구다. 이를 위해 대화와 업무에 별도 상태 소유자를 둘지, 한 소유자가 서로 다른 lifecycle을 관리할지는 구조적 선택이다. 대안에 현재 기준선의 Component 분할·adapter·저장 순서를 그대로 강제하지 않는다.

반대로 VIA가 interaction·orchestration을 소유하고 Downstream Agent가 domain reasoning·planning·실행을 소유한다는 경계는 유지한다. 하나의 공유 on-device Omni, 독립된 역할·session·권한, semantic 수행 중 발화 수신·인식, 허용된 좁은 S2S 직접 응답 등 사용자 지정도 유지한다. 대안이 이를 충족하려면 필요한 기능·계약을 명시하고 미확보를 숨기지 않는다.

기준선에 이미 선택된 구조에서 출발한다. 구조적 후보를 만든다는 이유로 목표 설계를 처음부터 다시 설계하거나 검토 완료 상태를 미완료로 되돌리지 않는다.

## 3. 후보를 만드는 절차

1. **사용자 상황:** “해석 중 사용자가 대상을 고쳤다”처럼 구체적인 상황을 고른다.
2. **설계 문제:** 그 상황에서 분리하거나 결합해야 할 책임·상태·경계를 찾는다.
3. **기준선 방안:** 현재 누가 무엇을 소유하고 어떤 계약으로 연결하는지 확인한다.
4. **강한 대안:** 같은 행동을 다른 책임 배치로 달성하는 가장 설득력 있는 방안을 구성한다.
5. **Component 차이:** 제거·추가·분리·통합·책임 이동·화살표 변경을 명시한다.
6. **자체 반론:** 대안에 빠진 필수 기능, 현재 구조의 숨은 비용, 불필요한 묶음을 점검한다.
7. **우선 검토·조건부·보류 판정:** 실제 구조 차이와 중요성을 설명할 수 있는 후보만 남긴다.

같은 Component가 여러 후보에 등장해도 결정이 독립적이면 별도 후보가 될 수 있다. 반대로 Component가 있다는 이유로 후보를 하나씩 만들지 않는다. 후보의 개수보다 각 질문의 선명함을 우선한다.

## 4. 발표 그림으로 설명 가능한지 확인한다

각 후보는 **문제 상황 → 두 방안의 처리 구조 → 책임·상태·계약의 변화 → 이점·비용·반론**으로 설명한다. Senior SW Architect가 그림부터 보더라도 “무엇을 어디로 옮겼고, 왜 그 경계가 필요한가”를 검토할 수 있어야 한다.

| 그림에 있어야 할 것 | 확인할 질문 |
| --- | --- |
| 공통 사용자 상황과 외부 조건 | 두 방안이 같은 문제를 해결하는가? |
| Component와 내부 책임의 구분 | 새 owner인가, 기존 기능의 내부 모듈인가? |
| 실제 호출·event·전달 payload | 누가 누구에게 무엇을 요청하고 결과를 확정하는가? |
| 상태·원장·cache와 변경 권한 | 어떤 상태가 이동하고, 누가 쓰며, 재시작 시 무엇을 복구하는가? |
| 번호가 붙은 핵심 흐름 | 정상 처리를 어디서 시작하고 어떤 계약으로 이어가는가? |
| 해당 선택의 예외·장애 경계 | 정정, 중단, 오래된 revision, 전달 불명, process 종료를 누가 처리하는가? |
| 양쪽의 구조적 이점과 비용 | 대안도 실제로 선택할 만하며, 현재 구조를 반박할 조건이 있는가? |

**공통 부분은 검정, 서로 다른 부분은 양쪽 모두 파랑으로 표시한다.** 방안별로 다른 색을 주거나 방안 2의 변경점만 강조하지 않는다. 경계만 이동하고 내부 기능이 같다면 파란 경계 안의 기능은 검정으로 남긴다. 가능하면 대응하는 기능을 같은 위치·크기로 배치하고, 책임 이동 때문에 달라지는 연결은 명시한다.

Component 통합은 내부 모듈·상태 타입까지 하나로 뭉갠다는 뜻이 아니다. 분리는 무조건 별도 process나 네트워크 호출이라는 뜻도 아니다. 논리 Component, 내부 모듈, process, 모델 dependency, 내구 기록을 표기로 구분해 호출 비용이나 장애 격리 이점을 과장하지 않는다.

그림을 크게 바꾸기 위해 불필요한 Component를 추가하지 않는다. 박스를 지웠다면 그 책임이 어디로 갔는지, 박스를 추가했다면 독립적으로 소유하는 상태·계약·변경 책임이 무엇인지 드러낸다. 박스 수를 늘리는 것보다 **주장하는 장단점의 원인을 그림에서 따라갈 수 있는지**를 우선한다.

사용자가 제공한 네 비교 슬라이드는 중첩 경계·내부 모듈·저장소·번호 흐름·장단점의 표현 깊이를 참고한 자료다. 해당 도메인의 모델 보호·재학습 구조, 수치, 점수는 VIA의 근거나 결과로 옮기지 않는다. [그림 작성 규칙](./diagrams/README.md)을 함께 적용한다.

## 5. 현재 작업의 경계

사용자가 요청한 순서에 따라 **지금은 구조적 후보를 검토하고 ASR은 뒤에 논의한다.** 따라서 구조적 비용과 예상 효과는 설명하되 ASR 목록·정의·우선순위·적용 여부를 확정하지 않는다. 후보 채택 후 이 원칙만으로 중요성이 충분한지 ASR과 함께 다시 검토할 수 있다.

기존 DP에 매핑하지 않고 정식 번호·선정 개수를 미리 정하지 않는다. 새 후보를 accepted 결정이나 구현·측정 결과로 취급하지 않으며, 검토 완료 target 문서와 기존 ADR은 변경하지 않는다.
