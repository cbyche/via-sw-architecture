# 04-37. 여섯 발표 후보의 구조 비교와 반복 검토

> 2026-10-04 / 작성자 설계 검토 / [가이드](./04-30-comparison-guide.md) / [작업 기록](./00-workplan.md)

## 1. 무엇을 보완했는가

**31~36을 모두 발표 후보로 보완했다.** 32는 옛 화면/객체 비교를 되살리지 않고, 공동 해석과 분리 근거 결합이라는 새 메커니즘으로 교체했다. 31/33을 포함한 모든 구조도와 사건도를 다시 작성했다. 네모에는 Component/Module 이름만, 화살표에는 순서/자료/조건을 두었다. 각 그림에 사용자 상황, 구조, 결과와 선택 조건/대가를 넣었다.

본문도 쉬운 요약과 용어부터 시작해 왜 VIA에 중요한지, 무엇이 어려운지, 누가 무엇을 만드는지, 어떤 조건에서 각 안을 고를지 설명한다. 상세 계약은 첫 이해 뒤에 읽는다. 이전 15쌍은 [이력](../../../archive/decision-comparisons-before-presentation-2026-10-04/README.md)에 남기고, 현재는 구조도 6쌍과 사건도 6쌍이다.

앞 네 주제는 VIA의 상위 기능 품질에 직접 연결된다. 35/36은 기능을 안정적으로 유지하는 기반 선택이다. 어느 안도 참조 구조와 같아야 한다는 제한은 없다. 이 표는 품질 우위나 최종 선택을 선언하지 않는다.

## 2. 가장 싼 확장으로 충분한가

| 주제 | 먼저 인정한 싼 확장/혼합 | 그래도 남는 핵심 재설계 | 역전환과 선택 조건 |
| --- | --- | --- | --- |
| 31 | A의 validator, 질문 상태, 필드 patch와 cache | B는 새로운 완성안 대신 변경을 정상 입력으로 삼고, 질문/근거 변경이 지속 의미 상태를 갱신. A가 이미 동일 권한을 가지면 같은 계열로 분류 | B 구현을 남긴 채 전체 재해석 모드를 쓰는 것은 쉬울 수 있음. 짧은 자유 발화는 A, 조건을 오래 유지하는 보완은 B의 선택 근거 |
| 32 | A에 장면 후보를 힌트로 제공하거나 시간/ID 검증 추가. B에 공동 해석 fallback 가능 | 최종 대응을 코드 결합으로 옮기려면 후보/조건 표현, 두 생산자의 버전, 미해결/부분 재생산을 실제 설계해야 함. 외부 Task 계약은 재사용 | B→A는 공동 경로를 되넣고 조합기를 제거해 더 쉬울 수 있음. 자유 시각 표현은 A, 명시적 순차 지칭/정정은 B. 혼합도 현실적 후보 |

| 34 | A의 Streaming ASR/TTS와 미리 읽기 하나 | 수정 가능한 입력을 의미/자료/응답 준비가 함께 소비하고 무효화/게시 계약을 공유 | B에서 잠정 시작을 끄기는 쉬움. A의 단순한 코드로 돌아가는 작업은 별도. 짧은 발화는 A, 긴 발화의 유효 준비는 B |
| 35 | A의 감사 log/inbox/outbox/backup | 사건을 원본으로 writer, reducer, 정상 읽기, schema/삭제/복구를 재구성 | B의 최신 projection을 A의 시작 상태로 쓰기 가능. 현재 운영은 A, 과거 전이 재구성은 B. 단순 log로 충분하면 B 불필요 |
| 36 | 기존 connector worker, scope 검사, 일부 코드만 격리 | 처리 코드의 직접 raw/credential/파일/네트워크/DB 권한을 제거하고 Broker 수명으로 전환 | sandbox 해제는 쉬울 수 있지만 보호 성질을 잃음. 작은 신뢰 코드/자원은 A, 침해 범위 제한의 가치가 크면 B |

모든 안의 변경량을 같은 등급으로 부풀리지 않는다. 35/36은 상태 원본/실제 권한이라는 차이가 분명하다. 31~34는 의미 생산/실행 계약을 구현할 때 어느 부분이 실제로 교체되는지 정확히 설명해야 한다. 각 §8의 반론을 발표의 질문 대비 자료로 사용한다. “컴포넌트가 많아서”, “계약이 여러 개 바뀌어서” 또는 “과거 자료를 바꿀 수 없어서”를 단독 근거로 사용하지 않는다.

### 32를 다시 후보로 올린 이유와 한계

옛 A/B는 이미지/객체를 같은 참조에 넣는 작은 확장으로 결합할 수 있었다. 그 결론은 바꾸지 않았다. 새 비교는 **누가 말과 화면의 대응을 생산하는가**를 바꾼다. 장면 후보를 공동 모델에 넣는 것만으로 B가 되지 않는다. B에서는 화면 후보와 언어 조건이 독립 자료이고 Join Engine이 최종 결합을 생산한다.

그렇다고 새 B를 완전한 대안으로 과장하지 않는다. 복잡한 도형 관계나 함축적 표현을 후보/조건에 담지 못하면 재지칭이 필요하다. 이 손실이 실제 VIA에 크면 A 또는 혼합이 낫다. 한 모델을 두 역할로 호출한 비용, 후보 누락과 언어 오해도 시험해야 한다. 현재 판정은 **반론과 손익을 명시한 발표 후보로 복귀**이며 사용자 채택이나 측정된 우위가 아니다.

## 3. 글과 그림을 각각 읽었을 때 남아야 할 설명

| 주제 | 그림에서 직접 찾을 구조 | 본문만 읽어도 설명할 수 있는 사례 | 발표 때 빠뜨리면 안 되는 한계 |
| --- | --- | --- | --- |
| 31 | A의 생성/검증 루프, B의 Workspace/Engine/자료/Task 변경 연결 | “오른쪽 표”가 대상을 바꿔도 메일 발송 금지는 유지 | B도 변경 후보의 말뜻을 틀릴 수 있음; A도 금지 조건 검증 가능 |

| 33 | A의 중앙 상태, B의 각 actor 상태와 공통 해석기, 제안/채택 왕복 | 보고서 PDF 답변과 메일의 보고서 결론 참조를 함께 처리 | 단일 모델의 처리량 자동 증가 아님; 채택 전 취소는 별도 변형 |
| 34 | A의 확정 요청 경로, B의 잠정 배정/의존 상태/수정 루프와 게시 허용 | “보내… 아니 설명만”에서 유효 읽기는 유지하되 발송은 안 함 | 공유 모델 취소 불가/낭비, 이미 들은 말은 소급 취소 불가 |
| 35 | A의 record 직접 복원, B의 journal/reducer/checkpoint/조회 상태 | c9 전송 후 ACK 없이 종료해도 접수를 발명하거나 무조건 재전송하지 않음 | replay는 외부 재실행이 아님; 현재 state 운영은 A도 가능 |
| 36 | 공유 process와 실제 제한 process/Broker의 다른 접근 경로 | 자료 조립 코드가 무관한 파일을 열려 할 때 차단 주체가 다름 | OS 강제와 모든 우회 경로 검증 전. Broker/공유 모델 자체는 신뢰 영역 |

구조도는 생산/저장/실행의 배치를, 사건도는 이름이 붙은 참여자 사이 요청과 반환을 보여준다. 길게 쓴 처리 문장을 네모 안에 넣어 구조처럼 보이게 하지 않았다. 상자 밖의 상황과 장단점은 그림 독립 이해를 위한 설명이며 측정 결과가 아니다.

## 5. 여섯 선택의 결합과 중복 방지

| 두 주제 | 독립 선택 여부와 결합 시 확인할 것 |
| --- | --- |
| 31 + 32 | 31은 대화 목표/조건의 구성, 32는 말과 화면의 대상 결합. 32의 참조/미해결을 31의 후보로 소비. 같은 후보 선택 이익을 두 번 계산하지 않음; 모델 역할 Context와 오류 전파를 함께 검토 |
| 31 + 33 | 33 §4.2에서 소유 결합을 정함. 두 B이면 actor별 Workspace가 미채택 다음 상태를 제안하고 Coordinator 채택 뒤 저장/게시. 전역 Workspace 복제 원본 없음. 임의 전역 제약의 해법은 미완성이므로 질문/재제안 한계를 유지. 이익의 독립 합산 금지 |
| 31 + 34 | 잠정 fragment와 여러 입력에 걸친 의미 상태는 수명이 다름. 34의 잠정 결과 중 어떤 의미 변경을 31의 내구 상태로 채택할지 명시해야 함. 잠정 전사를 매번 확정 사건으로 저장하지 않음 |
| 31 + 35 | Workspace의 채택 상태도 current record 또는 사건 원본으로 저장할 수 있음. 지속 의미 상태가 event sourcing을 강제하지 않으며 잠정 후보 전체를 영구 보존할 필요 없음 |
| 31 + 36 | 제한 process의 후보 생성은 Broker 자료만 사용. 지속 Workspace의 원본과 최종 허용은 신뢰 영역에 남기는 배치 가능. 이름상 Workspace라고 raw/전역 권한을 자동 부여하지 않음 |
| 32 + 33 | 결합한 관측 참조를 actor 사이에 전달 가능. 같은 원문/관측으로 actor마다 재결합해 비용을 중복시키지 않도록 요청 범위 공유. actor별 독립 해석이면 결과 충돌 처리 필요 |
| 32 + 34 | 부분 전사의 수정은 32 B의 언어 조건/결합을 무효화. 화면 후보 재사용과 34의 잠정 읽기 재사용은 실제 동일 작업이면 한 번만 셈. 32 B가 34 B를 강제하지 않음 |
| 32 + 35 | 채택된 대상 참조는 현재 record나 사건으로 저장 가능. 잠정 장면 후보를 모두 내구 이력으로 만들 필요 없음. journal에 썼다고 관측/객체가 영구 유효해지지 않음 |
| 32 + 36 | 32 B의 입력 분리는 보안 경계가 아님. 제한 process에서 두 Producer를 실행한다면 원본/후보/모델 job을 Broker 범위에 결합. Coordinator/Join Engine도 어떤 자료를 볼 수 있는지 명시 |
| 33 + 34 | actor 협력과 부분 입력은 조합 가능하지만 proposal 버전/참가 라운드가 증가. 공동 backlog와 재처리 비용을 별도로 검토 |
| 33 + 35 | actor 상태도 현재 record 또는 사건 원본으로 저장 가능. actor 메시지를 모두 영구 domain event로 취급하지 않음 |
| 33 + 36 | actor라는 논리 경계만으로 자료 권한 격리는 생기지 않음. 별도 실제 process/권한 배치가 필요 |
| 34 + 35 | 잠정 dependency는 버려도 되는 실행 상태, event journal은 확정 상태의 원본. 연속 처리 때문에 event sourcing이 필수라는 주장은 금지 |
| 34 + 36 | 취소/철회되는 model job과 source handle을 Broker 수명에 연결. 중개 대기와 복사는 VIA 시간/자원에 포함 |
| 35 + 36 | 권위 journal/current DB는 신뢰 Core에 남길 수 있음. 제한 처리의 직접 쓰기 권한을 주지 않고 owner의 확정 계약을 사용 |


31/33 B를 함께 쓰면 actor별 Workspace가 미채택 변경을 생산하고 Coordinator 채택 뒤 저장/질문 게시가 이루어진다. 별도 전역 Workspace를 같은 의미의 두 번째 원본으로 만들지 않는다. 32의 후보/조건과 34의 잠정 작업도 같은 자료/모델을 사용하는 경우 비용을 한 번만 세며, 전체 조합의 이익을 각 문서의 독립 이익 합으로 주장하지 않는다.

## 6. 현재 결과와 확인 범위

여섯 본문, 각 13개 품질 관점, 실제 구조도와 동일 사건도 **총 12쌍의 SVG/draw.io**를 작성했다. 이전 설명과 그림은 이력에 보존했다. 링크/용어/QA registry/생성물/XML/소유 경계/경로 및 이름만 있는 Component 칸 검사를 통과했고, 현재 도식 전체를 PNG로 렌더해 직접 확인했다. 최종 실행 기록은 [00-workplan](./00-workplan.md)의 현재 절에 남겼다.
