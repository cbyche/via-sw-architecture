# 04-37. 여섯 구조 비교의 작성자 검토

> 2026-10-03 / [04-30 가이드](./04-30-comparison-guide.md)의 적용 기록 / 독립 리뷰, 구현 및 측정 없음

## 1. 무엇을 다시 작성했는가

사용자는 중요한 기능 주제를 찾는 것과 그 주제에서 다른 SW 구조 두 개를 만드는 것을 구분했다. 이전 문서들은 기능 추가와 내부 호출 변경을 주요 구조 차이로 과장할 여지가 있었다. 이번에는 번호만 바꾸지 않고, 앞 네 주제의 메커니즘을 다시 정의하고 뒤 두 주제를 같은 읽기 순서로 재작성했다.

| 문서 | 이전 약점 | 이번에 바꾼 실제 선택 | 작성자 판단과 남는 반론 |
| --- | --- | --- | --- |
| [04-31](./04-31-semantic-construction.md) | 모델 호출을 단계로 나눈 것만으로 큰 결정이라고 함 | 모델이 완성 관계를 생성하는 구조와 타입/후보/제약 해법이 관계를 생성하는 구조 | 비교 유지. 작은 validator로 충분하면 B의 비용은 불필요. 자연어 후보 오해를 solver가 보장하지 않음 |
| [04-32](./04-32-screen-grounding.md) | 객체 cache 추가와 raw 재해석 금지로 차이를 만듦 | 화면 관측 기반 대상과 source 객체/버전/resolver 기반 획득 및 인계 | 비교 유지. 기존 참조 계약이 두 표현을 이미 지원하면 주변 변경은 작음. 실제 provider 범위가 핵심 |
| [04-33](./04-33-dialogue-coordination.md) | Task별 Context 선별/소유자 이름 변경으로 끝날 수 있음 | 중앙 대화 의미/상태 갱신과 actor의 상태 전이 제안/참조 협력/채택 | 협력 실행이 필요한 조건으로 유지. actor가 수동 cache라면 자격 없음. 단순 분할로 장점이 생긴다고 주장하지 않음 |
| [04-34](./04-34-incremental-voice.md) | 원음/Text 입력과 출력 생성이라는 독립 축을 묶음 | 확정 발화 요청과 수정 가능한 fragment/의존 작업의 연속 실행 | 비교 유지. 단순 ASR/TTS streaming과 구별. 작은 prefetch로 충분하면 B 선택 가치는 약함 |
| [04-35](./04-35-state-authority.md) | 중요도보다 변경량이 앞설 위험 | 현재 record 원본과 확정 사건 원본에 따른 쓰기/상태 생성/복구 | 조건부 후순위. 정상 복구에 이력이 꼭 필요하다고 하지 않음. 역전환은 더 쌀 수 있음 |
| [04-36](./04-36-capability-isolation.md) | process 추가 자체를 보호로 읽을 위험 | raw 접근 권한을 실제로 제거한 제한 처리와 Broker 중개 | 조건부 후순위. OS enforcement와 실제로 줄인 권한이 필요. 공유 모델/Core 위험은 남음 |

“비교 유지”는 제시한 설계에 따른 판단이다. 여섯 개 모두 최종 DP로 선정됐다는 뜻이나 큰 전환 비용을 구현으로 검증했다는 뜻은 아니다. 새 구조를 약하게 만들거나 명칭만 달리한 문제가 확인되면 해당 비교를 다시 수정해야 한다.

## 2. 같은 중요한 목적과 실용성을 대조한 결과

각 문서 §1~2에서 사용자 실패, VIA 책임과 설계 난이도를 먼저 설명했다. 각 안을 선택하는 조건과 포기할 기능은 §5~9에 있다. 정정/철회/실패를 정상 기능 설명보다 먼저 쌓아 난이도를 과장하지 않았다.

- 04-31 B는 업무 계획 compiler가 아니다. VIA의 목표/대상/조건/Task 관계만 구성한다. 타입/규칙 밖 표현과 후보 추출 오류를 공개했다.
- 04-32 B는 이미지를 볼 수 없도록 억지 제한한 안이 아니다. source 객체를 실제 읽기/재확인/인계에 사용하는 안이며 opaque 영역의 자동 지원 손실과 혼합 가능성을 공개했다.
- 04-33 B의 actor는 외부 Agent나 process가 아니다. 자기 대화 상태의 사건 처리, 원문 구간별 제안, 경쟁/누락 판정과 교차 참조 protocol을 포함한다. 공유 모델의 물리적 병렬 성능은 주장하지 않았다.
- 04-34 B의 잠정 처리는 승인 전 외부 변경의 조기 실행이 아니다. 허용된 준비만 앞당기며, 확정 경계와 실제 전달/정정을 유지한다. 이미 들려준 말을 소급 취소하지 않는다.
- 04-35 replay는 모델 재추론, 외부 command 재전송이나 음성 재생을 수행하지 않는다. local 기록으로 외부 ACK를 복원하지 않는다.
- 04-36 B는 scope 문자열 검사만 하지 않는다. 직접 파일/DB/network 접근과 모델 port 우회를 제거해야 한다. Broker와 Model Access는 신뢰 경계에 남는다.

새 learned helper, 무한 KV, Task별 Omni 복제, 분산 DB나 cloud 규모를 전제로 사용하지 않았다. 요구한 runtime/provider 기능의 실제 지원과 품질 수치는 미확인으로 남긴다.

## 3. 여섯 선택은 서로 얼마나 독립적인가

표에서 “조합 가능”은 품질 효과가 독립이라는 뜻이 아니다. 함께 쓰면 생기는 계약과 비용을 실제 조합에서 한 번만 센다.

| 두 주제 | 독립 선택 여부와 결합 시 확인할 것 |
| --- | --- |
| 31 + 32 | 의미 생성 방식과 대상 획득은 별개. A/B 각 참조를 31의 후보/근거로 넣을 수 있어야 하며 source의 정확성을 의미 해법의 정확성으로 중복 주장하지 않음 |
| 31 + 33 | 같은 의미 엔진을 중앙 또는 actor가 호출할 수 있음. actor별 해를 통합할 때 교차 절/조건이 사라지지 않아야 함 |
| 31 + 34 | 발화 단위/부분 입력은 어느 의미 엔진에도 적용 가능. B/B 조합은 IR 후보와 해의 버전/무효화가 필요하며 solver를 streaming 설정만으로 바꾸지 못함 |
| 31 + 35 | 의미 생산과 영구 상태 원본은 별개. 임시 IR 전체를 event로 저장할 필요 없음. 확정 의미 사건의 형식만 연동 |
| 31 + 36 | 의미 엔진과 권한 배치는 별개. 제한 process의 후보/IR 생성이 필요한 자료를 Broker로 얻도록 연동 |
| 32 + 33 | 객체/관측 참조를 대화 단위 사이에 전달 가능. 어느 actor가 참조하든 같은 유효성/삭제 의미 유지 |
| 32 + 34 | source 변경/관측 시점이 fragment의 dependency가 됨. 늦은 제공자 결과를 과거 입력에 붙이지 않음 |
| 32 + 35 | 확정 대상 참조의 저장 방식과 source 획득은 별개. journal에 썼다고 외부 객체가 영구 유효해지지 않음 |
| 32 + 36 | source adapter의 필요 권한이 sandbox 설계를 제한. provider가 전역 권한을 필요로 하면 Broker에 두거나 미지원 명시 |
| 33 + 34 | actor 협력과 부분 입력은 조합 가능하지만 proposal 버전/참가 라운드가 증가. 공동 backlog와 재처리 비용을 별도로 검토 |
| 33 + 35 | actor 상태도 현재 record 또는 사건 원본으로 저장 가능. actor 메시지를 모두 영구 domain event로 취급하지 않음 |
| 33 + 36 | actor라는 논리 경계만으로 자료 권한 격리는 생기지 않음. 별도 실제 process/권한 배치가 필요 |
| 34 + 35 | 잠정 dependency는 버려도 되는 실행 상태, event journal은 확정 상태의 원본. 연속 처리 때문에 event sourcing이 필수라는 주장은 금지 |
| 34 + 36 | 취소/철회되는 model job과 source handle을 Broker 수명에 연결. 중개 대기와 복사는 VIA 시간/자원에 포함 |
| 35 + 36 | 권위 journal/current DB는 신뢰 Core에 남길 수 있음. 제한 처리의 직접 쓰기 권한을 주지 않고 owner의 확정 계약을 사용 |

특히 04-31~34는 같은 요청의 서로 다른 구간/책임이다. 이후 전체 조합의 시간 이익을 각 문서의 독립 이익 합으로 계산하지 않는다. 04-35와 04-36은 이 기능 선택을 강제하는 선행 결정이 아니다.

## 4. 자기 반론에서 수정한 항목

| 발견한 문제 | 수정 |
| --- | --- |
| 기존 좋은 주제를 그대로 두고 상태/계약 설명만 늘릴 위험 | 31의 solver 생산, 32의 source 획득, 33의 actor 협력, 34의 연속 작업 수명으로 선택 축 자체를 변경 |
| 새 안의 이익을 기존 안에서 빼는 위험 | A에도 validator, 관련 Task cache, 앱 ID 힌트, streaming ASR/TTS, 감사 log와 기존 connector 격리를 인정 |
| B의 처리량/지원이 무조건 좋아 보일 위험 | 후보 폭발, provider 누락, actor 라운드, 잠정 추론 낭비, replay와 IPC 비용을 같은 품질 표에 포함 |
| 그림에서 자료가 처리자처럼 보임 | 중앙 의미 제안은 접힌 자료 모양과 결과 이름으로 표시. 실제 처리 Component와 구별 |
| 의미 반환과 요청 화살표 혼동 | 반환 방향/범례를 대조하고 확정 경로의 결과 전달을 점선으로 수정 |
| 자료 조립기가 의미 처리를 직접 소유하는 것처럼 보임 | Request Controller 경유와 별도 Request Interpreter/Model Access 경로 명시 |
| 배우기 어려운 순서와 용어 | 여섯 문서 모두 사용자 상황과 난이도부터 시작. IR, actor, fragment, projection, handle은 사용 전에 정의 |

이 표는 작성자의 실제 대조와 수정 기록이다. 다른 독립 검토자가 검증했다는 기록은 아니다.

## 5. 검증 범위와 사용자 리뷰 위치

여섯 본문은 각각 §1~9와 13개 품질 행, 구조/사건 도식 2쌍을 갖춘다. 자동 검사는 링크, 정식 명칭, QA registry 및 SVG/draw.io 생성물/좌표/연결을 확인한다. 렌더와 본문 대조는 사람이 읽을 수 있는지와 표기 오류를 확인한다. 이 두 검사가 구조의 효과나 모델/OS 기능을 입증하지는 않는다.

현재는 **여섯 문서를 모두 읽고 두 방안의 구조와 손익을 함께 리뷰할 단계**다. 실제 구현, 모델 실행, 측정과 최종 선택은 하지 않았다. 검사 결과와 게시 기록은 [WORKPLAN](./00-workplan.md)의 현재 절에서 확인한다.
