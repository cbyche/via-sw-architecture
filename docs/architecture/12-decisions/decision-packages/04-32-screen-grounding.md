# 04-32. 시간에 따라 사라지는 화면과 사용자 행동의 관측 근거 확보

> 2026-10-04 / 주요 구조 비교 후보 제외 / 공통 설계 참고 및 검토 이력 / [가이드](./04-30-comparison-guide.md) / [작업 기록](./00-workplan.md)

**32는 화면과 포인터, 클릭, 드래그 등 시간에 따라 사라지는 관측 근거를 어떻게 확보하고 보존하여 이후 해석에 제공할지만 다룬다.** 지칭 대상의 의미 판단, 추가 조회와 해석의 제어, 요청 의미의 확정은 이번 논의에서 제외한다. 사용자는 41을 현재 내용 그대로 두고 논의를 확장하지 않도록 지시했다. 31도 현재 정리를 유지한다.

**현재 처리: 32를 주요 구조 비교 후보에서 제외하고 공통 설계 참고로 보존한다.** 새 A/B 탐색을 미결 과제로 넘기지 않는다. 화면 관측 기능 자체를 제외하거나 구현 방식을 선택한 것은 아니다.

**제외 근거:** §6~10에서 요청 처리 런타임이 원본 기록을 소유하는 A와 독립 관측 런타임이 소유하는 B를 구체화했다. 실제 상태/장애 경계 차이는 있지만, 강한 A와 기존 참조 구조의 생산자 버퍼를 대조하면 별도 주요 구조 대안으로 추천할 근거는 부족하다. B는 조건부 배치 선택으로 남기며 새 주력 A/B로 채택하지 않는다.

## 1. 같은 사용자 장면과 목적

사용자가 첫 화면의 표를 가리키며 “이 표와”라고 말하고, 스크롤한 뒤 다른 표를 가리키며 “저 표를 비교해줘”라고 한다. 나중에 요청을 해석할 때 첫 화면이 이미 사라졌더라도 당시 화면과 포인터, 사용자 행동을 확인할 근거가 있어야 한다. 현재 화면의 같은 좌표를 과거 관측 대신 사용하면 안 된다.

이 문서는 두 표가 무엇인지 결정하는 해석기를 설계하지 않는다. 그 해석에 필요한 당시 관측을 제공할 수 있는지, 없으면 무엇이 누락되었는지 식별하는 문제를 다룬다.

## 2. 합의한 범위와 경계

| 32에서 다룰 것 | 이번 논의에서 다루지 않을 것 |
| --- | --- |
| 화면과 입력 이벤트의 취득, 수집 시작과 종료 | 모델 중심 ReAct와 코드 중심 의미 완성의 비교 |
| 관측 시각, 발화 시각과 도착 시각의 구별 및 시간 대응 | “이 표”가 실제로 어느 대상을 뜻하는지 판단 |
| 창, 화면 및 좌표 기준과 스크롤 전후 관측의 구별 | 화면의 대상과 관계를 의미 상태로 미리 생산 |
| 원본 버퍼의 소유, 보존, 조회와 만료 | 잠정 의미 후보의 증분 연결과 철회 전파 |
| 지연, 누락, 자원 초과, 접근 철회와 삭제 | Task 연결, 최종 요청 의미와 외부 실행의 확정 |

관측의 시간 대응은 의미 결합과 구별한다. 같은 시점의 화면과 포인터를 연결해도 사용자 의도가 확정된 것은 아니다. 관측 출력의 구체 형식과 소유 Component는 아직 선택하지 않았다.

## 3. 현재 공통 전제와 미결정 사항

- 양안 모두 사용자 발화가 시작되면 수집을 시작한다는 합의를 유지한다. 상시 수집이나 발화 전 기록을 새 전제로 추가하지 않는다.
- 화면과 포인터, 클릭, 드래그를 모두 같은 고정 주기로 취득할 필요는 없다. 이벤트 취득과 화면 캡처의 방식, 주기, 처리량은 아직 결정하지 않았다.
- 입력 기록, 시간 대응, 근거 보존과 의미 모델 호출은 서로 다른 처리다. 매 관측마다 의미 모델을 호출하는 전제를 두지 않는다.
- 발화 전에 선택한 상태가 시작 시점에도 남아 있다면 읽을 수 있지만, 이미 사라진 발화 전 행동을 기록 없이 복원할 수 있다고 가정하지 않는다.
- 수집 종료, 보존 기간과 예산, 늦은 자료의 처리, 조회 중 만료, 철회 및 장애 시 동작은 후속 설계에서 비교한다. 수치는 확정하지 않는다.

## 4. 공통 설계에 남기는 질문

1. 사라지는 근거를 어느 생산자가 언제 확보하며, 어떤 상태를 누가 소유하는가?
2. 화면과 사용자 행동이 다른 속도와 지연으로 도착할 때, 시간 대응과 누락을 어떻게 표현하는가?
3. 후속 해석기가 과거 관측을 읽는 동안 화면 변경, 만료, 철회 또는 수집 실패가 발생하면 무엇을 반환하는가?
4. 서로 다른 메커니즘이 실제 확보 가능한 근거, 응답 대기, 메모리와 복구에 어떤 손익을 만드는가?
5. 작은 버퍼, 조회 또는 설정 변경만으로 상대안의 주요 이익을 얻을 수 있는가?

이 질문들은 향후 관측 기능의 상세 설계를 위한 참고다. §6~10의 검토 결과 현재 32는 주요 비교 후보에서 제외한다. 단순 주기 변경, 보조 모듈 추가나 모델 교체를 새 주요 A/B로 제시하지 않으며, 이 질문을 미완료 대안 탐색 과제로 넘기지 않는다.

## 5. 이전 비교의 상태

요청 시 원본 해석 대 관측 시 의미 상태 생산/조회 비교와 당시 도식은 [이전 검토 이력](../../../archive/screen-grounding-before-evidence-scope-2026-10-04/04-32-screen-grounding.md)에 보존했다. 현재 32의 대안이나 품질 근거로 사용하지 않는다. 기존 생성기의 choice32 도식은 이전 세대 산출물로 남아 있으며, 새 범위의 구조도로 제시하지 않는다.

대화 중 제안한 독립 기록 대 관측 요청, 요청 단위 결과 대 증분 연결도 현재 32의 A/B로 채택하지 않는다. 이번 범위 합의를 이유로 41을 변경하거나 논의를 확장하지 않는다. 구현, 모델 실행, 측정 또는 최종 선정은 하지 않았다.

## 6. 구체화한 후보: 원본 기록의 소유와 실행 수명

사용자가 OS 관측 수단을 유지하면서 소유/실행/수명 구조의 비교를 검토하도록 요청했다. 아래 A/B는 그 검토용 이름이며 §5의 옛 A/B와 다르다. 앞서 논의한 앱 상태 재구성은 앱 지원 범위가 좁아 사용자가 기각했으므로 재도입하지 않는다.

### 6.1 비교를 위해 명시한 공통 조건

- 동일한 OS 캡처와 입력 API, 화면 범위, 시간 정밀도 및 원본 형식을 사용한다. 앱별 plugin이나 앱 내부 수정은 요구하지 않는다. 보호 화면 등 OS가 제공하지 않는 관측은 양쪽 모두 얻을 수 없다.
- Interaction Manager가 발화 시작을 알리면 관측 구간을 연다. 요청 의미가 확정되기 전에도 사용할 수 있는 관측 구간 ID를 부여한다. 실제 첫 관측 시각과 시작 통지 사이의 공백은 별도로 표시한다.
- 원본 보존의 전체 메모리 예산, 허용 기간과 관측 범위는 같다. B에 더 긴 보존이나 더 큰 버퍼를 주어 이익을 만들지 않는다. staging queue와 전달 사본도 예산에 포함한다.
- 수집 종료와 저장 자료의 만료는 구별한다. 발화 종료가 원본 즉시 삭제를 뜻하지 않는다. 재시도, 늦은 전사와 정정은 같은 허용 기간 안에서 기존 구간을 조회할 수 있다.
- 양쪽 모두 독립 수집 thread, 유한 queue, 비동기 조회, 참조 계수, 중복 없는 원본 보관을 사용할 수 있다. A를 모델 호출 중 수집까지 멈추는 구조로 만들지 않는다.
- 외부에 반환하는 것은 관측 원본/참조, 시각과 오차, 화면/창/좌표 기준, 생산자 세대와 누락 정보다. 대상의 의미, Task 연결이나 실행 허가는 반환하지 않는다.
- 이 검토의 기본 저장은 유한 RAM이다. 전체 PC 재시작 뒤의 원본 복원은 어느 안에도 보장하지 않는다. 같은 내구 저장을 추가한 경우도 §8에서 별도로 대조한다.

### 6.2 A: 요청 처리 런타임이 관측 기록을 소유

이전의 넓은 ‘OS 캡처형’에 소유 조건을 추가한 구체화다. 참조 구조 자체가 A라고 주장하지 않는다. 요청 처리 런타임은 여러 요청을 다루는 Core 실행체이며 요청 하나마다 생기는 process가 아니다.

1. Interaction Manager → Context Manager: 관측 구간 ID, 시작 시각과 유효 수집 범위를 전달한다. Context Manager가 Core 안에서 구간과 원본 기록을 소유한다.
2. Context Manager → 관측 생산자: 해당 구간의 OS 화면/입력 수집을 시작한다. 생산자는 별도 thread 또는 기존 worker일 수 있다.
3. 관측 생산자 → Context Manager: 시각/순서/세대가 있는 원본을 전달한다. Context Manager의 관측 기록 모듈이 RAM 원본 버퍼와 시간 색인에 보관하고, 실제 보관 완료 범위를 기록한다. 생산자의 일시 전달 queue는 과거 조회의 원본 소유자가 아니다.
4. Request Controller → Context Manager: 필요한 구간의 근거를 읽는다. Context Manager → Request Controller: 원본/참조와 보관 범위, 공백 또는 만료를 반환한다. 이후 의미 해석은 이 비교 밖이다.
5. Interaction Manager의 수집 종료/철회 통지와 공통 보존 한도에 따라 Context Manager가 생산을 중지하거나 원본을 폐기한다. 요청 해석 취소만으로 무관한 구간을 삭제하지 않는다.

Core 안의 서로 다른 해석 시도는 같은 원본을 재사용할 수 있다. 요청별 파일 복제, 해석 실패 시 원본 삭제, UI thread에 동기 캡처를 강제하지 않는다. 논리적 요청 실패와 원본 소유 process의 실패를 구별한다.

### 6.3 B: 독립 관측 런타임이 관측 기록을 소유

새 책임인 **Observation Recording Service**가 별도 로컬 process에서 관측 구간, 원본 버퍼, 시간 색인과 읽기 참조를 소유한다. 시스템 관리자 권한의 Windows Service를 요구하는 뜻은 아니다. 사용자 세션 안에서 실행할 수 있다. 수집 API, 원본 형식과 모델 구성은 A와 같다.

1. Interaction Manager → Observation Recording Service: 같은 시작 시각/구간/허용 범위를 보낸다. 서비스가 관측 생산자를 시작한다. process가 미리 준비되어 있어도 발화 전에 화면을 기록하지 않는다.
2. 관측 생산자 → Observation Recording Service: 같은 원본과 시각/순서/세대를 전달한다. 서비스가 보관한 뒤 구간 ID, 보관 범위와 자신의 실행 세대를 알린다. Context Manager는 원본 전체를 정상 경로에서 다시 저장하지 않는다.
3. Request Controller → Context Manager → Observation Recording Service: 과거 구간을 조회한다. 서비스는 현재 읽기 권한과 유효 범위를 확인하여 원본 또는 제한된 읽기 참조를 반환하고, Context Manager가 이를 Request Controller에 전달한다. 공유 메모리를 쓸지 복사할지는 이 구조의 필수 조건이 아니다.
4. 소비자는 읽기 완료를 알린다. 서비스가 읽기 참조와 원본 수명을 관리하며, 느리거나 죽은 소비자가 공통 보존 한도를 무한 연장하지 못하게 한다. 만료/철회된 참조의 신규 사용은 거절한다.
5. Core의 해석 시도가 교체되어도 서비스는 같은 허용 구간을 소유한다. Core process 재시작 후에는 살아 있는 서비스의 세대, 보관 범위와 현재 권한을 확인한 뒤 재연결한다. 옛 메모리 주소나 handle을 그대로 재사용하지 않는다.

Core 장애 중에도 새 관측을 계속할 수 있다는 보장은 process 분리만으로 생기지 않는다. 유효한 수집 허용 범위, 독립적인 종료/철회 통지와 입력 생산 경로가 계속 살아 있어야 한다. 이를 확인할 수 없으면 수집/신규 제공을 중지하고 공백을 남긴다. 서비스가 살아 있다는 사실만으로 음성 인식, 화면 지칭 또는 요청 처리가 계속된다고 말하지 않는다.

### 6.4 실제로 바뀌는 연결

| 경로/상태 | A | B |
| --- | --- | --- |
| 시작 제어 | Interaction Manager → Core의 Context Manager → 관측 생산자 | Interaction Manager → Observation Recording Service → 관측 생산자 |
| 원본 쓰기 | 생산자 → Core 소유 원본 버퍼 | 생산자 → 서비스 소유 원본 버퍼 |
| 원본 읽기와 반환 | Request Controller ↔ Context Manager의 버퍼 | Request Controller ↔ Context Manager ↔ 서비스의 버퍼 |
| 원본의 실행 수명 | Core process 수명에 종속. 해석 시도와는 독립 가능 | 관측 서비스 process 수명에 종속. Core와 독립 |
| 종료/철회 | Context Manager가 생산과 기록을 정리 | 서비스가 생산, 원본 및 소비자의 읽기 참조를 정리 |
| 사라지는 책임 | 해당 없음 | Context Manager의 원본 보관/회수 책임을 서비스로 이전 |

단순 ‘서비스 상자 추가’와 구별되는 부분은 원본 쓰기와 회수의 실제 소유권 이전이다. 그러나 이 차이가 주요 구조 비교를 정당화하는지는 가장 싼 확장과 품질 손익으로 판단한다.

## 7. 같은 사건으로 확인한 차이와 공통 한계

| 사건 | 강한 A | B | 판단 |
| --- | --- | --- | --- |
| 첫 표를 가리킨 뒤 스크롤하고 두 번째 표를 가리킴 | 두 시점 원본과 입력 기록을 보존하여 조회 | 같은 근거를 서비스에 보존하여 조회 | 수집 품질이 같으면 근거 정확성의 차이는 없음 |
| 전사/해석이 늦게 도착 | 수집 thread와 유한 버퍼가 계속 처리, 나중에 같은 구간 조회 | 서비스가 계속 처리, 나중에 같은 구간 조회 | 비동기 수집과 버퍼만으로 양쪽 모두 대응 가능 |
| 해석 시도 취소 후 다른 시도로 재시도 | Core가 살아 있으면 기존 원본 ID로 재사용 | 같은 서비스 원본 ID로 재사용 | B 전용 이익이 아님 |
| 해석 결과가 여러 논리적 요청으로 나뉨 | 동일 원본과 참조 계수 사용 가능 | 동일 원본과 읽기 참조 사용 | A가 원본을 복제해야 한다는 주장은 기각 |
| Core process crash | RAM 소유자는 사라짐. 이미 내구 저장한 자료나 생산자 staging에 남은 자료는 별도 복구 가능 | 살아 있는 서비스의 원본은 유지 가능. 계속 수집은 §6.3 조건에 따름 | B의 분명한 조건부 차이. 모든 장애 보호는 아님 |
| 관측 서비스 자체 crash 또는 PC 재시작 | Core/관측 생산자 및 저장 방식에 따른 실패 | RAM 원본 상실 가능, 모든 옛 읽기 참조 무효 | B도 관측 원본 소유자의 실패를 해결하지 못함 |
| 같은 메모리 한도에 도달 | 정책에 따른 거절/회수 및 누락 표시 | 동일. 서비스/runtime/참조 관리가 같은 총예산을 소비 | 무한 대기나 B의 더 큰 버퍼를 이익으로 세지 않음 |
| 화면 잠금, 권한 철회, 사용자 수집 종료 | 생산 중지/원본 정리. 읽은 사본까지 추적 | 같은 처리에 진행 중 IPC와 읽기 참조 정리 추가 | 별도 process라고 자동 삭제/권한 격리가 되는 것은 아님 |
| 재연결 도중 오래된 결과 도착 | 입력/생산자 세대와 구간 유효성 검사 | 같은 검사에 서비스 세대/읽기 참조 검사 | 어떤 안도 옛 관측을 현재 관측으로 대체하지 않음 |

앱을 다시 보여달라는 사용자 요청은 근거를 이미 잃은 경우의 공통 복구 수단이다. 이를 B의 정상 처리나 기능 우위로 제시하지 않는다.

## 8. 가장 싼 확장과 실제 전환 비용

| 반론/시도 | 얻는 효과 | 검토 판정 |
| --- | --- | --- |
| A의 수집을 별도 thread로 옮김 | UI/해석 지연과 수집 실행을 분리 | 정상 지연 문제는 이 정도로 해결될 수 있음. B 필수라는 근거 없음 |
| A의 원본을 해석 시도보다 오래 보관하고 ID로 재사용 | 재시도/정정/복수 요청의 재사용 | 보존 규칙과 내부 자료 소유 정리로 충분한 경우가 많음 |
| A에 동일한 내구 원본 저장을 추가 | Core crash 전 저장 완료한 근거 복구 | B의 과거 자료 보존 이익 일부를 얻음. 저장 전 자료와 중단 중 새 관측은 별도 문제 |
| 기존 UI/관측 생산자의 버퍼에서 재조회하도록 확장 | Core와 다른 실행 수명에 근거를 남김 | B의 핵심 성질을 기존 실행체에서 얻을 수 있음. 별도 서비스 신규 도입이 필수는 아님 |
| A의 원본 모듈을 분리해 IPC로 호출 | 독립 소유/재연결 경계 구성 | 상태 회수와 참조 계약의 변경은 실제 작업이지만, 동일 캡처/색인/원본 형식을 재사용 가능. 근거 확보 메커니즘 전면 교체라고 과장하지 않음 |
| B를 유지하며 Context Manager에 cache 추가 | 읽기 왕복 감소 가능 | 현실적 혼합. 추가 사본/철회 비용은 있지만 혼합이 본질적으로 어렵다고 하지 않음 |
| B를 Core에 다시 포함 | 외부 읽기 계약을 내부 호출로 바꾸고 운영 실행체 축소 | 소유 서비스의 모듈/원본 형식을 재사용할 수 있어 역전환은 비교적 국소적일 수 있음 |

| 비용 종류 | A → B | B → A |
| --- | --- | --- |
| 기능 개발 | 독립 시작/종료, 조회/반환/해제, 세대 재연결과 서비스 운영 | 서비스 모듈을 Core로 포함하고 호출 경로 변경 |
| 진행 상태 이행 | 기존 구간을 만료까지 drain하거나 명시적으로 이전. 이행 중 새 원본 소유자를 하나로 유지 | 같은 drain/이전. 과거 화면을 다시 캡처해서 메울 수는 없음 |
| 핵심 재설계 | 원본/색인/읽기 참조의 owner와 Core 장애 시 계약 변경 | 독립 장애 수명을 포기하고 원본 수명을 Core와 다시 결합 |

**가장 강한 반례는 현재 참조 구조다.** [architecture.md의 runtime 배치](../target-architecture/architecture.md)는 이미 UI process 쪽 화면/포인터 수집과 제한된 evidence buffer, Core의 시간 대응을 분리한다. 이것이 곧 B의 재조회/철회/재연결 계약까지 구현했다는 뜻은 아니다. 하지만 기존 생산자 버퍼에 구간 조회와 수명 계약을 보완하여 B의 주요 이익을 얻을 경로가 있으므로, 약한 단일 process A만 대조해 주요 대안이라고 할 수 없다. 참조 구조나 그 정책은 이번에 변경하지 않았다.

실제 기반도 별도 서비스의 필수성을 뒷받침하지는 않는다. Windows의 [CreateFreeThreaded](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded?view=winrt-26100)는 DispatcherQueue 의존 없이 내부 worker thread에서 FrameArrived를 전달한다. 이는 A도 UI 처리와 수집을 분리할 수 있다는 근거이지 무손실 보장은 아니다. [PipeWire의 설계](https://docs.pipewire.org/page_design.html)는 별도 process의 생산/소비자와 공유 버퍼 기반 서비스가 실제 사용되는 구조임을 보여준다. Linux 미디어 기반 사례이며 Windows VIA의 완성된 관측 서비스나 측정 결과는 아니다.

## 9. 같은 13개 품질 관점의 검토

[공통 품질 의미](./03-00-quality-scenarios.md#2-어떤-품질을-보고-있는가)를 적용한다. 아래는 설계 인과와 미확인 사항이며 측정값이 아니다. 기본 관측의 앱 지원, 시간 정밀도와 총보존 예산은 같게 둔다.

| 관점 | A와 B의 차이 및 한계 |
| --- | --- |
| V-01 기능 정확성 | 정상 수집의 근거는 같음. B는 Core 실패로 잃을 근거가 줄어드는 조건에서만 간접 이익. 의미 해석 정확도 자체를 높이지 않음 |
| V-02 기능 적절성 | B의 살아 있는 원본이 재지칭을 줄일 수 있으나, 강한 A의 버퍼/내구 보존으로도 가능한 범위를 제외해야 함 |
| V-03 기능 완전성 | 동일한 OS 기반 앱 범위와 관측 기능. Core 중단 중 근거 유지/수집은 앞서 밝힌 생존/권한 조건에 따라 부분 지원 또는 미확인 |
| V-04 상호작용 반응성 | A도 수집 thread 분리 가능. B는 서비스 조회와 시작 통신 비용 추가. 어느 안이 빠른지 미확인 |
| V-05 VIA 귀속 요청 완료 시간 | 정상 경로의 조회 왕복과 재연결 비용을 포함. 장애 시 재지칭 회피는 조건부 이익이며 Agent 수행 시간은 공통 |
| V-06 자원과 수용량 | A도 원본 공유 가능. B의 별도 runtime/IPC/참조 관리 및 일시 사본 비용 포함. 프로세스 분리는 CPU/GPU/메모리 대역폭 경합을 제거하지 않음 |
| V-07 결함과 복구 | B의 핵심 영향 축. Core와 원본 소유자 분리의 조건부 이익과 관측 서비스 자체 실패, OS 실패를 함께 기록 |
| V-08 변경과 모듈성 | 캡처와 원본 형식은 재사용. B의 서비스 계약/세대/읽기 참조/종료 호환 관리가 추가되며 별도 배포의 이익은 필요 조건에 따름 |
| V-09 분석과 시험 | 양쪽 모두 시각/순서/보관 범위 기록 필요. B는 재연결, 늦은 반환, 만료와 소비자 crash의 경합 시험 추가 |
| V-10 기밀성 | 동일한 허용 범위/철회 의무. B의 참조와 IPC 사본 정리 추가. 별도 process를 36의 권한 격리와 동일시하지 않음 |
| V-11 연동과 공존 | 앱/OS 연동은 동일. B는 IPC/공유 버퍼 호환 경계 추가. 장치 및 다른 앱과의 자원 공존 이익은 자동으로 생기지 않음 |
| V-12 조작과 오류 방지 | 같은 시작/종료/공백 안내 필요. 서비스 생존을 현재 요청 정상 처리로 표시하지 않음. 새로운 정상 사용자 조작을 요구하지 않음 |
| V-13 설치 | B는 서비스 시작/중지, 버전 호환, 제거 시 잔여 원본/실행체 처리 필요. A도 기존 worker 운영 비용을 포함 |

## 10. 판정과 후속 범위

**실제 SW 구조 차이는 있지만, 현재 32의 독립적인 주요 A/B로 추천하지 않는다.** 공통 OS 관측 계열 안의 상태 소유/배치 선택으로 기록한다. 정책/알고리즘 차이여서 제외하는 것이 아니라, 주요 이익이 기존 버퍼와 비동기 실행의 국소적 보완으로 상당 부분 달성 가능하고 남는 차이가 주로 원본 소유 process의 실패 경계이기 때문이다.

- **A의 선택 조건:** 같은 보존 기간 안에 요청 처리와 재시도를 지원하면 충분하고, 원본 owner 분리의 추가 운영 비용을 감수할 이유가 약한 경우. A도 독립 수집과 원본 재사용을 갖춘다.
- **B의 선택 조건:** Core process의 교체/장애와 독립적으로 원본을 보존하고 다시 조회하는 성질이 필수이며, 기존 UI/생산자 런타임만으로 그 성질을 충족하지 못하는 경우. 이 요구나 부족함은 아직 확인되지 않았다.
- **주요 대안 승격의 반증:** 기존 생산자 버퍼의 구간 조회/재연결 보완으로 같은 관측 범위, 보존 및 장애 대응을 얻을 수 있으면 신규 독립 서비스의 주요 구조 주장은 성립하지 않는다. 단순 해석 지연/재시도/원본 중복을 이유로는 승격하지 않는다.
- **다른 문서와의 경계:** 31/41의 의미 구성은 그대로다. 35의 내구 상태 원본, 36의 강제 권한 격리도 새로 선택하지 않는다. B의 장애 경계 효과를 이 문서들과 독립 이익으로 중복 합산하지 않는다.

이번 논의는 **32의 주요 비교 후보 제외와 공통 설계 참고 보존**으로 마무리한다. 주요 구조 자격이 부족한 쌍을 새 발표용 메인 도식으로 승격하지 않고 실제 경로와 사건 대조를 위 표에 남겼다. 향후 중요한 품질 차이를 설명하는 새로운 메커니즘과 근거가 제시되면 별도 검토할 수 있으나, 자동으로 재탐색하지 않는다. Stage 4 전체 완료, 다른 비교안의 사용자 수용, 구현 검증 또는 측정된 성능 결론은 아니다.
