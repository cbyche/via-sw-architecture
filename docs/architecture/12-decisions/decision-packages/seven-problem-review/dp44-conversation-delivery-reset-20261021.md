# DP44 재정립: 준비된 응답을 실제 대화로 전달하는 구조

> **최신 검토 — QA01을 실제 첫 음성까지로 보는 경우:** 사용자는 화면·음성 독립을 유지하면서 QA01의 종료점을 실제 음성 시작으로 바꿨을 때의 구조 손익을 요청했다. [§0.2](#02-qa01을-실제-첫-음성까지로-보는-조건부-재평가)의 응답별 독립 준비 A 대 현재 발화 소유 준비 B는, 대기 중 음성 준비가 가능한 조건에서 **A의 첫 음성 대기 감소와 B의 미전달 구판 생성 비용 회피**를 설명한다. 기존 음성 준비 축의 새 조건 아래 재평가이며 새 아이디어나 실측으로 포장하지 않는다. 아래 UI 기준의 부정적 판단은 해당 정의 아래의 이력으로 유지한다. QA 공식 정의·점수 변경, 제품 S2S capability 검증과 기본안 선정은 아직 아니다.

> **최신 사용자 정정:** 화면과 음성의 독립 처리는 공통 전제다. 이를 결합하는 안은 사용자가 부적절하다고 명확히 기각했으며 다시 비교하지 않는다. 현재 핵심은 여러 전달 의무, 현재 발화, 중단된 응답과 미해결 질문을 보존하면서 사용자 개입을 관련 범위에만 적용하는 전달 제어다. 아래 §0의 권고를 이 경계로 수정했다.

> **최신 논의 정리:** 아래 §0이 현재 판단이다. 음성 선행 준비 A/B는 사용자의 재질문 뒤 주요 DP44 대안에서 폐기했다. 문제의 중요성은 유지하지만, 지금까지 강한 QA tradeoff를 갖춘 A/B를 확보했다고 주장하지 않는다. 이전 ‘현재 비용 비교’ 안내는 탐색 이력이다.

> **2026-10-21 비용 추적 결과:** §0.1에서 동일한 사용자 개입·Agent 질문·결과의 겹침을 따라 전달 시 평가와 의존 상태 유지의 실제 계산·상태 비용을 비교했다. 구조 차이는 설명할 수 있지만, 현재 QA01~07에서 주요 DP에 필요한 양방향 손익은 확보하지 못했다. 새 기본안 선정이나 문제의 자동 강등을 뜻하지 않는다.

## 0. 지금까지의 결론과 DP44를 이어갈 방향

**유지할 문제:** 사용자 발화와 여러 Agent의 질문·결과가 한 대화에서 만날 때, 준비된 내용을 제때 전달하고 실제 전달 상태를 다음 상호작용에 연결한다. 다운스트림 업무나 응답 문안을 VIA에서 다시 생성하는 문제가 아니다.

### 합의한 책임과 제외 범위

- Agent가 결과·질문 내용을 제공한다. VIA는 그 내용과 Task/Request·판본을 연결하고 현재 전달 조건을 확인한다.
- 사용자가 말하면 음성을 중단하고, 정정·취소의 의미와 범위는 DP2에서 채택된 관계를 적용한다. 무관한 질문·결과는 유지한다.
- 화면 표시와 음성 전달은 서로 다른 사실이다. 질문을 받았거나 만들었다는 이유만으로 사용자가 들었다고 기록하지 않는다.
- S2S에는 텍스트를 입력한다. 직전 음성 비교는 그 출력 오디오를 선행 생산·보관한다는 별도 가정이었다. 해당 비교를 주요 DP44 대안으로 유지하지 않는다.
- 모델의 다중 접속을 인정한다. 전역 모델 mutex나 불필요한 추가 LLM으로 대안의 시간·비용 차이를 만들지 않는다.

### 대안이 반복해서 약해진 이유

| 탐색 | 판단 |
| --- | --- |
| Dispatcher 대 Stage | 동일한 게시 조건·원본·출력 경로 위의 실행 연결 차이에 집중하여 큰 QA 손익 근거가 약했음 |
| 의미 해석 병행·잠정 실행 | DP2의 문제로 이동함 |
| 응답 재작성·묶음 생성 | Agent가 제공한 내용을 VIA가 다시 생성하는 일을 추가함 |
| 응답별 Workflow 대 desired/actual 대조 | 구현 구조는 다르지만 해당 QA의 반대 방향 이익을 확보하지 못함 |
| 음성 선행 준비 대 발화 시점 준비 | 음성 생산·보관의 별도 선택으로 좁아졌고 실제 S2S 계약을 확인하지 않은 채 주요 DP로 과대평가함 |

문제의 중요성, 구현 구조의 차이와 주요 QA tradeoff의 성립은 별도 판정이다. 한 가지를 확인했다고 나머지까지 성립한 것으로 설명하지 않는다.

### 두 가지 제약을 함께 풀어야 한다

첫째, 공통 기능을 정하는 과정에서 모든 제어 구현까지 고정하지 않는다. 상세 텍스트와 음성 요약을 제공하고 현재성·권한·실제 전달을 보존하는 것은 공통 요구다. **텍스트 게시와 음성 전달의 독립성도 사용자가 확정한 공통 전제다.** 재검토할 것은 현재 발화와 미전달 의무, 정정의 영향 범위와 실제 제시 근거를 유지하는 제어 상태·실행이며, 채널을 결합해 UI 지연을 만드는 비교는 제외한다.

둘째, 현재 QA의 관측 경계를 그대로 인정한다. QA01은 첫 UI 표시까지이고 QA03은 전체 상세 표시·음성 준비까지이며 실제 청취·재생 차례 대기를 제외한다. 따라서 발언권과 중단·재개를 바꾸어도 두 지표에는 차이가 없을 수 있다. QA02/새 QA07은 의미 판단 자체를 고정한 출력 비교의 정확도 점수로 전용할 수 없다. QA04·QA06은 실제 변경 범위·상주 메모리로 비교하며 추상적 복잡도를 대신 넣지 않는다. QA05는 실제 모델 작업량이 달라져야 한다.

### 권고하는 다음 결정

화면과 음성의 독립 처리는 사용자 정정에 따라 공통 전제로 고정한다. 이 둘을 결합하는 비교 권고는 철회한다. **현재 발화, 중단된 응답, 아직 전달하지 않은 내용과 답변을 기다리는 질문을 어떤 상태와 실행으로 관리하는가**가 DP44의 핵심이다.

설계 출발점은 Response Manager가 전달 상태와 출력 의무를 소유하고 Interaction Manager가 실제 출력·즉시 중단과 receipt를 담당하는 것이다. 이것을 새 강한 A/B나 측정 승자로 제시하지 않는다. 다음 상태는 분리한다.

| 상태 | 소유할 정보와 사용 |
| --- | --- |
| 응답별 전달 기록 | response/request/task/question ID, 내용 참조, 판본, 대체 관계, 필수 채널 |
| 현재 발화 | 유효한 출력권 하나, 출력 세대, 해당 응답과 범위 |
| 미전달·중단 상태 | 대기 범위, 실제 전달 범위, 중단 이유와 재개 가능 여부 |
| 질문 제시 근거 | 실제 text 표시와 실제 발화 범위의 별도 receipt; Request Controller의 질문 등록·답변 채택에 공급 |

Response Manager의 짧은 사건 처리는 `신규 전달 등록`, `출력 중단 receipt 반영`, `채택된 정정 적용`, `다음 유효 전달 선택`, `실제 전달 범위 갱신`으로 나눈다. 현재성·권한 검사를 통과한 UI는 음성과 독립적으로 게시한다. Interaction Manager는 사용자 발화 시작 때 모델 해석을 기다리지 않고 출력 세대를 바꾸고 실제 재생을 멈춘다. Request Controller가 DP2의 관계 판단을 채택하면 그 명령의 ID와 범위를 사용해 해당 응답만 대체·폐기·재개한다. 코드가 사용자 의미를 임의로 추론하지 않는다.

보고서 설명 R1 중 메일 질문 Q1이 도착하면 Q1의 유효 text는 바로 표시하고 음성 전달 의무는 별도로 남긴다. 사용자가 보고서의 결론만 요청하면 현재 재생을 즉시 중단하고 R1의 실제 전달 범위를 기록한다. 관계 채택 뒤 R1의 해당 전달 의무만 바꾸며 Q1은 보존한다. 새 결론 내용이 필요하면 원래 내용 생산 책임자에게 맡긴다. 새 내용의 전달이 끝난 뒤 Q1은 유효한 다음 발화 대상으로 남는다. Q1을 말한 뒤에도 그 전달 완료와 사용자의 답변 채택은 다른 상태다. 침묵을 답변·재개 허가로 처리하지 않는다.

이 설계의 판단은 큐에서 하나를 꺼내는 것보다 넓다. 현재 말하던 응답을 중단해도 다른 질문을 잃지 않고, 준비와 실제 제시를 구별하며, 후속 답변에 입력 당시 전달 근거를 제공한다. 반면 이 필수 동작을 설명했다는 이유만으로 상대적인 QA tradeoff까지 확보했다고 세지 않는다.

정상 단일 요청, 다른 Agent 질문 도착, 사용자 중단·정정, 이후 재개의 같은 장면에서 `내용 최초 가용 → 대화 연결·게시 조건 → 첫 UI → 전체 준비 → 실제 발화 → 후속 입력 연결`을 그린다. 어느 실제 선행 작업·상태 수명이 달라지고 무엇을 더 지불하는지 찾는다. 작은 callback 차이에 머무르면 주요 대안으로 승격하지 않는다.

QA01~07 안의 실질 손익을 우선 탐색한다. 그러나 DP44의 주된 이익이 실제 음성 전달에 있다면 그 가치를 측정할 축을 함께 재검토해야 한다. [기존 QA09](../qa-candidate-package/qa09-audio-delivery-lag.md)는 별도 음성 지연 검토 자료이지 자동 해결책은 아니다. 이 정의도 공통 차례상 기다릴 시간을 제외하고 현재 핵심 QA 승격 제외 상태이므로 그대로 읽어야 한다. 음성 관련 지표를 넣는 것만으로 강한 구조 대안이나 QA coverage가 생기지 않는다.

**현재 권고:** DP44의 문제는 유지하고, 채널·대화 생명주기의 설계 경계와 QA 관측 범위를 함께 맞춘다. 기존 A/B를 되살리거나 QA의 의미를 몰래 바꾸지 않는다. 이 정리는 QA 변경·새 기본안 선택·구현·측정의 승인이 아니다.

> **폐기한 비교 이력:** [음성 선행 준비 대 발화 시점 준비](dp44-audio-preparation-tradeoff-20261021.md)는 별도 음성 준비 계약 아래 QA03과 QA05의 교환을 탐색했지만 주요 DP44 대안에서 폐기했다. 앞서 구성한 [응답별 전달 절차와 출력 상태 대조](dp44-workflow-and-reconciliation-20261021.md)도 구현 구조만으로 QA 교환을 확보하지 못해 주 비교 권고를 철회했다. 현재 권고나 실측 결과로 사용하지 않는다.

### 0.1 사용자 발화·정정과 Agent 통지의 겹침에서 실제 비용 추적

**이번 요청의 충족 여부:** 실제 구조 후보와 비용 충돌은 구체화했다. 그러나 QA01~07의 의미를 유지하면서 양안의 중요한 이익과 손해가 분명한 주요 DP 비교를 만들었다고 답할 수는 없다. 아래 후보를 새 ‘강한 A/B’로 승격하지 않는다. 아직 찾지 못했다는 판단이며 가능한 모든 구조의 부재를 증명한 것은 아니다.

#### 고정한 입력과 책임

- Agent는 질문·결과 본문과 원본 Task·revision을 제공한다. VIA에 새 업무 reasoning이나 재작성 모델 호출을 넣지 않는다.
- 사용자 의미와 정정의 대상·범위는 DP2에서 채택해 제공한다. 발화 시작에 대한 즉시 음성 중단은 그 판단을 기다리지 않는다.
- 두 안 모두 유효한 상세 text를 음성 준비·차례와 독립적으로 게시한다.
- 현재 권한·판본, 중복 방지, 실제 출력 범위와 미해결 질문은 모두 보존한다. 본문은 공유 참조하고 같은 저장·모델·process 조건을 사용한다.

#### 먼저 분리한 비용

| 수행할 일 | 양안 모두 필요한 비용 | 이번에 바꿀 수 있는 부분 |
| --- | --- | --- |
| 질문·결과 수신 | ID와 원본 revision 확인, 내용 참조 등록 | 전달 조건을 이때 계산할지, 유지 중인 조건과 연결할지 |
| 발화 시작 | 실제 음성 정지, 출력 세대 변경, 전달 범위 receipt | 재개할 후보들의 상태를 즉시 갱신할지, 선택 시 평가할지 |
| 채택된 정정 | 해당 요청·응답 범위 변경, 영향을 받은 실제 출력 차단 | 관련 대기 응답을 찾는 방식과 파생 readiness 갱신 |
| 다음 전달 | 최신 권한·판본·출력 세대 검사, 유효 내용 전달 | 후보별 조건을 다시 계산할지, 미리 유지한 ready 집합에서 선택할지 |
| 후속 답변 | 실제 제시된 질문과 전달 범위 제공 | 원본 기록과 조회 형태의 차이. 기록 자체를 한쪽에서 생략하지 않음 |

여기서 실제 교환 가능한 것은 **소비 시 반복 평가량 ↔ 변경 시 갱신량과 유지 상태**다. 순서나 우선순위 설정을 바꾸는 것과 구별한다. 하지만 계산량의 교환을 곧바로 QA01·QA03의 시간 우위나 QA06의 제품 RAM 우위로 읽을 수는 없다.

#### 구조 후보 A: 전달 시 현재 상태 평가

`응답 등록부 + 현재 원본 상태 조회 + 전달 조건 평가기 + 실제 출력 기록`으로 구성한다. 후보를 전달하거나 재개할 때 현재 Task/Request revision, 권한, 보류와 전달 범위를 읽어 결정한다. 보류 원인과 깨울 사건은 기록하지만 조건별 결과와 역방향 의존 그래프 전체를 상시 유지하지 않는다.

내용 도착 때 처음 조건을 검사하고, 조건 해소 사건이나 실제 출력 종료로 다음 전달을 선택할 때 필요한 후보를 재평가한다. 무효 항목은 선택 과정에서 걸러낼 수 있다. 이미 출력 중인 항목은 명시적 ID·범위를 가진 정정 명령으로 즉시 차단한다. 이력 전체 재생, 매번 DB/RPC, polling 지연을 강제하지 않는다.

**선택 이유:** 활성 응답이 적고 정정으로 후보가 자주 사라지면, 끝내 사용하지 않을 readiness를 계속 갱신하는 일을 줄인다. **대가:** 다시 선택할 때 조건을 읽고 평가하는 일이 남는다.

#### 구조 후보 B: 조건 변경에 따라 전달 가능 상태 유지

`응답 등록부 + 조건별 의존 인덱스 + 변경 전파기 + ready 집합 + 실제 출력 기록`으로 구성한다. 응답 등록 때 어느 Task/Request revision·권한·질문 상태에 의존하는지 연결하고 파생 전달 가능 상태를 만든다. 원본 조건이 바뀌면 연결된 응답의 readiness와 ready 집합을 갱신한다.

다음 전달은 ready 집합에서 선택한다. 다만 변경 전파와 실제 출력 사이에 새 정정이 생길 수 있으므로 출력 경계의 최신 판본·권한·세대 검사는 A와 동일하게 남는다. 파생 상태가 원본 사실이나 실제 출력 receipt를 대체하지 않는다.

**선택 이유:** 같은 응답들이 여러 번 보류·재개되고 영향을 받는 범위가 작으면 반복 조건 평가를 줄일 수 있다. **대가:** 응답 등록·조건 변경마다 의존 관계와 파생 상태를 갱신하고, 폐기된 응답의 연결도 해제해야 한다. 최종 출력 검사까지 없애지는 못한다.

조건을 유지하는 구조가 매번 빠른 것은 아니다. 새 질문은 의존 등록을 새로 해야 하며, 하나의 공통 조건 변경이 모든 대기 응답에 영향을 주면 전파 비용도 커진다. A 역시 같은 원본 구조와 공유 참조를 사용할 수 있다.

**선택에 필요한 반대편 이익이 아직 없다.** A는 파생 상태를 적게 유지하고 B는 반복 계산을 줄일 수 있다. 그러나 B의 절약이 현재 시간 QA 안에 의미 있게 남는지, 유지 상태가 실제 QA06 피크를 바꾸는지 확인되지 않았다. 이것을 ‘A는 메모리, B는 응답 속도 승리’로 요약하면 근거보다 강한 결론이다.

#### 왜 이 지점에서 비교를 과장하지 않는가

현재 [QA01](../qa-candidate-package/qa01-first-response-latency.md)은 첫 UI까지, [QA03](../qa-candidate-package/qa03-via-processing-time.md)은 필수 상세 표시와 전체 음성 준비를 포함한 완료 경로까지다. 실제 음성 차례·재생 대기는 제외한다. 따라서 DP44에서 중요한 중단된 응답의 재개, 미해결 질문의 전달 차례와 전달 뒤 후속 연결이 달라졌다는 사실만으로 이 두 지표의 큰 차이가 생기지 않는다.

이 정의를 유지하고 준비된 내용과 의미 해석도 고정한 현재 탐색에서는, 큰 호출·대기를 없앴다는 증거가 없다. 정상 상황의 소수 활성 응답을 다루는 코드·인덱스 비용을 수초나 수백 MB 차이로 확대할 수 없다. 시간 QA를 바꾸거나 모델을 추가하지 않고도 다른 구조가 중요한 차이를 만들 가능성은 열어 두지만, 그 구체적인 경로를 찾기 전까지 주요 DP 성립을 선언하지 않는다.

실제 선택·정정 적용·누락과 중복 방지의 가치를 별도 평가해야 하는지 검토할 이유는 남는다. 이는 QA 추가·변경의 채택이 아니며, 새 지표만 넣으면 강한 대안이 생긴다는 주장도 아니다. DP44의 문제와 기본 기능 설계는 유지하고 이번 후보의 한계를 기록한다. 구현·모델 실행·측정·점수 산출은 하지 않았다.

#### 공식 구조 자료와 적용 한계

- [Microsoft Materialized View pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)은 조회를 위한 사전 계산과 저장·갱신의 교환을 설명한다. 이 패턴의 존재가 VIA의 작은 응답 집합에서 주요 QA 이익을 입증하지 않는다.
- [W3C SCXML](https://www.w3.org/TR/scxml/)은 병렬 활성 상태와 history를 통한 상태 복원 메커니즘의 참고 자료다. parallel 상태가 곧 여러 thread나 더 빠른 실행을 뜻하지 않는다.
- [Apache Drools rule engine](https://kie.apache.org/docs/10.2.x/drools/drools/rule-engine/index.html)의 eager/lazy 평가와 상태 유지도 실제 메커니즘 참고다. 대규모 규칙 시스템의 성능 설명을 VIA의 정상 활성 응답 수에 그대로 적용하지 않는다.

### 0.2 QA01을 실제 첫 음성까지로 보는 조건부 재평가

**결론:** 측정 종료점이 달라지면 의미 있는 구조 후보가 생긴다. 직전의 ‘조건을 매번 평가 대 상태로 유지’가 갑자기 강해지는 것은 아니다. 이번에 직접 연결되는 결정은 **실제 발화권을 받기 전에 응답별로 S2S 준비 실행과 산출물을 보유할 것인가, 발화 대상으로 선택된 뒤 그 발화 실행 안에서 준비할 것인가**다. 전자는 음성을 시작할 때의 대기를 줄이고 후자는 대기 중 정정으로 사라질 내용의 음성 생성 비용을 피한다.

이것은 [폐기된 음성 준비 탐색](dp44-audio-preparation-tradeoff-20261021.md)의 축을 새 QA01 가정으로 재평가한 것이다. 당시의 작은 RAM 차이나 LiveKit TTS 예제만으로 주요 DP라고 주장했던 한계가 소급해 사라지지는 않는다. 여기서는 실제 첫 음성의 인과, 같은 장면의 구판 비용, S2S 계약과 반증 조건을 분리한다.

#### 이번 비교에서만 사용하는 QA01 음성 검토안

| --- | --- |

| 종료 | 그 입력·사건에 대응하는 첫 실질 내용 음성의 실제 출력 시작. 완결 내용 단위를 실제 발화 기록에서 확인하고 그 단위의 시작 sample에 연결 |

Voice OFF와 음성 의무 없는 사건은 사전 구분한다. 정당하게 대체·취소된 구판에는 임의로 0초를 주거나 구판 발화를 강제하지 않는다. 공통 원장에 대체 관계와 미발화 상태를 보존하고 최신 응답이 담당할 전달 의무를 양안 같게 정한다. 사후에 느린 후보를 취소하여 평균에서 빼는 것은 허용하지 않는다. 아래 지연 비교는 양안 모두 여전히 전달해야 하는 메일 질문 Q1에서 성립하며 구판을 분모에서 지우는 데 기대지 않는다.

#### 실제 비용 충돌과 공통 조건

S2S가 다중 접속을 지원하더라도 사용자에게 동시에 여러 음성을 재생하지 않는다. 모델 호출과 실제 발화권 사이에는 시차가 생길 수 있다. 그 시간을 사용해 준비하면 다음 음성의 시작 대기를 줄일 수 있지만, 아직 말하지 않은 내용이 정정되면 이미 사용한 생성 비용은 되돌릴 수 없다.

- Agent/VIA의 해당 책임자가 상세 내용과 발화할 내용을 제공한다. 새로운 업무 답변이나 요약 LLM을 추가하지 않는다. 발화용 내용 공급이 별도로 필요하면 양안 같은 공통 경로와 비용으로 둔다.
- S2S 입력은 **텍스트**다. 아래 버퍼는 S2S가 반환한 **출력 음성**이며 입력 WAV 제작을 뜻하지 않는다. S2S에 도구·업무 실행 권한을 주지 않는다.
- UI 게시, DP2 의미 판단, 최종 판본·권한 검사, 공통 발화 순서와 즉시 중단은 같다. 순서를 바꿔 한쪽 QA01을 빠르게 만들지 않는다.
- 의미가 미해결인 새 사용자 요청의 답을 추측해서 만들지 않는다. 이미 채택되어 당시 유효한 응답의 음성화를 앞당긴다.
- 사용자 발화는 로컬 출력 세대를 바꾸어 즉시 정지시킨다. 원격 취소 완료를 기다리지 않는다. 늦게 온 구판 audio는 재생하지 않는다.
- 이미 실제 발화를 시작했던 응답의 유효한 미재생 음성·전달 범위는 양안 모두 보존·재사용할 수 있다. B만 그것을 버리고 다시 합성하게 만들지 않는다.

#### A: 응답별 준비 실행과 실제 발화를 분리

Response Manager 안에 응답별 준비 실행 등록부와 미전달 음성 보관소를 둔다. 응답이 채택되고 준비 조건이 충족되면 발화권과 독립적으로 S2S 호출을 시작한다. 출력 제어는 현재 발화권을 소유하며 준비된 응답 중 유효한 하나를 Interaction Manager에 전달한다.

```text
유효 내용 → 상세 UI 게시
        → response/revision별 S2S 준비 실행 → 미전달 음성 보관
                                             → 발화권·최신성 검사 → 실제 출력
```

개념상 `prepare_speech(response_id, revision, text)`가 반환하는 stream을 응답별 보관소에 쓴다. `play(response_id, revision, from_range, playback_epoch)`는 별도 동작이다. 모델별 SDK 명칭이 아닌 VIA adapter 계약이다. 첫 재생 가능한 내용 chunk가 있으면 시작할 수 있으며 전체 생성 완료를 선행조건으로 강제하지 않는다.

`response_id + content_revision + preparation_id`는 준비 실행과 산출물의 수명을 식별하고 `playback_epoch`는 실제 출력 허가의 수명을 식별한다. 사용자 발화로 현재 epoch를 폐기해도 무관한 메일 질문의 유효 준비물이 자동 폐기되지는 않는다. DP2가 채택한 정정 범위에 따라 관련 준비만 취소·무효화한다. 원격 취소가 늦으면 추가 사용량도 비용에 포함한다.

내용·권한의 source와 의존 관계는 보존하고 매 출력 release에서 검증한다. 준비된 음성을 실제 대화 이력의 ‘이미 들은 말’로 넣지 않는다. 실제 제시 근거는 Interaction Manager의 receipt에서만 만든다.

#### B: 현재 발화 실행이 S2S 준비를 소유

Response Manager는 미전달 의무를 텍스트·ID·판본으로 등록한다. 다음 발화 대상으로 선택되고 준비를 시작할 권한을 받으면 현재 발화 실행이 S2S 호출과 stream 버퍼를 만든다. 아직 한 번도 발화 대상으로 선택되지 않은 대기 항목에는 준비 job과 audio 산출물이 없다.

```text
유효 내용 → 상세 UI 게시
        → 텍스트 전달 의무 등록
             → 발화 대상 확정 → 현재 발화의 S2S 호출 → streaming 실제 출력
```

개념상 `speak(response_id, revision, text, playback_epoch)` 안에서 S2S 생성·실제 출력을 연결한다. B의 기본안은 현재 발화 종료·중단 후 다음 발화 실행을 만든다. 모델 서버의 접속 한계가 아니라, 실제 전달 대상으로 선택되기 전의 생성과 보관을 피하는 설계다. 현재 입력 청취·DP2·UI·Agent 사건 수신은 이 실행을 기다리지 않는다.

대기 중 정정은 해당 텍스트·판본의 교체로 끝난다. 실제 발화를 이미 시작한 항목은 A와 같은 즉시 중단·원격 취소·전달 범위 처리가 필요하다. 이때 이미 생성한 유효 나머지를 재사용할 수 있으므로 ‘B는 버퍼 한 개 외에는 아무것도 보존하지 못한다’고 주장하지 않는다.

#### 같은 겹침 상황: 빠른 질문 전달과 폐기 결과의 비용이 함께 발생

기존 안내 R0가 발화 중이다. 메일 Agent의 질문 Q1과 5월 보고서 결과 R1이 도착한다. 두 안 모두 즉시 유효 text를 표시한다. 그 뒤 사용자가 **“보고서는 6월 기준으로 다시 해줘. 메일 질문부터 들려줘.”**라고 요청한다. DP2는 보고서 요청의 변경과 Q1 우선 전달을 같은 결과로 채택한다. 이 요청은 기존 의미 해석의 오답을 가정한 것이 아니라 사용자가 요구를 바꾼 경우다. 6월 보고서 내용 R1′은 Downstream Agent가 다시 제공한다.

| 시점 | A | B |
| --- | --- | --- |
| R0 발화 중 Q1·R1 도착 | Q1·R1의 음성 준비를 시작. UI는 독립 표시 | Q1·R1의 텍스트 의무만 대기. UI는 동일하게 표시 |
| 사용자 발화 시작 | R0 즉시 중단, 실제 범위 기록 | 동일 |
| DP2가 정정·전달 순서를 채택 | R1 구판 준비·산출물 무효화. Q1 준비물은 유지 | 대기 R1을 구판으로 처리. 구판 S2S 작업은 없었음 |
| Q1을 말할 수 있음 | Q1의 첫 내용 음성이 준비되어 있으면 최종 검사 후 출력 | 이 시점에 Q1 S2S를 시작하므로 첫 내용 음성 생성 대기가 남음 |
| R1′ 도착 | 새 revision을 준비. Q1 실제 발화 중에도 독립 준비 가능 | 새 텍스트 의무 등록. 해당 발화 실행에서 준비 |

**A의 이익:** Q1의 실제 첫 음성 대기를 앞의 준비 시간으로 가린다. **A의 손해/B의 이익:** 사용자가 듣기 전에 대체한 5월 보고서의 음성 생성 사용량이 A에만 발생한다. **B의 손해:** Q1이 실제 차례를 얻은 뒤에도 생성 대기가 필요하다.

공통 R0와 DP2 호출을 제외하면 이 장면의 음성 준비 호출은 A가 `Q1, R1, R1′`이고 B가 `Q1, R1′`이다. R1의 모든 음성이 완성됐다고 가정하지 않으며 취소 전 실제 사용량만 센다. 새 내용이 기존 음성의 유효 구간으로 충족되면 A도 그것을 재사용한다. 단순히 ‘결론만’ 골라 말하면 되는 경우와 내용 자체가 달라진 이번 경우를 혼동하지 않는다.

#### QA01 이익의 크기를 결정하는 식

첫 후속 발화 Q1에 대해, `a`는 유효 내용으로 준비를 시작할 수 있는 시각, `T`는 동일한 사용자 발화·DP2 채택·공통 순서 아래 Q1을 말할 수 있는 시각, `f`는 같은 S2S 조건에서 첫 내용 음성까지 걸리는 시간, `d`는 공통 최종 검사·실제 출력 지연이라고 한다. `a ≤ T`, 생성 간섭이 없고 그 사이 내용이 유효하다는 설명용 조건이다.

```text
A 실제 시작 = max(T, a + f) + d
B 실제 시작 = T + f + d
A의 시작 이익 = min(T − a, f)
```

이는 실측·예상 성능값이 아닌 의존관계 계산이다. 두 안 모두 같은 원래 사건 시각에서 QA01을 시작한다. A의 보관·연결 overhead는 실제 구현에서 포함해야 한다. 후보 선택 때문에 이후 발화권 시각 자체가 달라지면 각 실제 경로로 계산하며 모든 후속 `T`를 같다고 강제하지 않는다.

이미 준비된 Q1을 선택하는 장면에서는 모델의 첫 내용 출력 대기가 제거되므로 작은 callback 최적화와 원인이 다르다. 반대로 준비할 선행 시간이 없거나 첫 음성이 거의 즉시 생성되는 환경이면 차이는 작다. 정정으로 새로 만들어야 하는 R1′ 자체의 첫 생성 대기를 미리 끝낸 것으로 가정하지 않는다.

#### QA01~07의 손익과 증거 수준

| QA | 이 비교의 예상 손익 | 범위·한계 |
| --- | --- | --- |
| **QA01 실제 첫 음성 — 이번 검토안** | **A 유리:** 유효한 대기 응답을 선행 준비할 시간이 있으면 첫 내용 음성 생성 대기 일부·전체를 차례 전에 수행 | 위 식의 조건 아래 인과가 명확. 실제 크기와 전체 평균은 미측정. 단일 즉시 응답은 거의 동점 |

QA03은 같은 길이 `g`의 두 유효 음성 준비가 동일 시점에 가능하고 두 원래 목표의 시작점 이후이며 병행 간섭이 없다는 설명 조건에서, A의 준비 완료가 각각 `g, g`, B는 발화 실행 의존 때문에 `g, 2g`가 되는 경로를 가질 수 있다. B의 실제 재생 길이를 더한 계산이 아니다. 원래 목표의 시작점 이전 작업은 제외하고, 실제 전체 DAG의 외부 대기 제거와 임계 경로로 재검토해야 한다. QA01 절약과 QA03 절약을 독립 절약량으로 합산하지 않는다.

QA06에서는 예를 들어 24kHz·16bit·mono 30초의 PCM이 산술상 1.44MB라는 정도만 말할 수 있다. 미전달 음성 몇 개만으로 수백 MB 차이를 만들 수 없다. A를 파일 보관으로 보완해도 생성에 이미 사용한 QA05 비용은 없어지지 않는다.

#### 왜 순서 설정 이상의 차이인가, 어디부터 tactic인가

같은 질문을 같은 차례에 선택해도 A에는 발화 전에 살아 있는 준비 실행·audio 산출물이 있고 B에는 없다. A는 준비와 출력의 취소 범위·ID·수명을 분리하고 B는 현재 발화 실행에 준비를 묶는다. A로 전환하려면 독립 준비 job 관리, 결과 저장·수용량, revision별 폐기와 늦은 chunk 방어를 지원해야 한다. UI와 음성을 함께 묶는 변경은 필요하지 않다.

반대로 이미 공통 음성 서비스가 이 독립 실행·보관·취소 계약을 모두 갖췄고 설정 하나로 선행량만 바꾸는 상황이라면 그것은 그 구조 안의 tactic 비교다. 구조가 없는 기본안 B와 독립 준비를 내재한 기본안 A의 차이로 설명해야 하며, 준비 수 1·2·3을 각각 별도 주요 구조로 세지 않는다.

- **A1:** 다음에 전달할 가능성이 있는 제한된 항목만 준비한다. 불필요한 작업을 줄이는 대신 예측하지 못한 다음 응답의 QA01 이익이 줄 수 있다.
- **B1:** 다음 한 응답을 선행 준비하는 실행·보관 경로를 추가한다. 첫 음성 간격을 줄이는 대신 그 응답의 정정 비용을 받아들인다.
- **A2:** 산출물을 파일에 보관한다. RAM을 줄이는 대신 I/O·파일 cache 비용을 포함한다. QA05 비용은 유지된다.

기본안 선택을 위해 보완을 미리 강제하지 않는다. 다만 B1이 실제 제품에서 필요한 독립 준비 구조를 이미 도입한 것인지, 기본 구조 분류를 바꿔야 하는지 함께 밝힌다.

#### 구현 근거와 아직 검증하지 않은 S2S 계약

[Alibaba Qwen-Omni 문서](https://www.alibabacloud.com/help/en/model-studio/qwen-omni)는 text 입력·audio 출력과 반환 음성의 저장 또는 streaming 재생 경로를 설명한다. 이는 S2S/Omni 출력의 생성과 로컬 재생을 분리할 수 있는 공개 구현 근거다. [Realtime client events](https://www.alibabacloud.com/help/en/model-studio/client-events)에는 response 생성·취소가, [server events](https://www.alibabacloud.com/help/en/model-studio/server-events)에는 response ID별 audio delta와 상태·사용량이 있다. 서로 다른 API의 기능을 한 제품에 모두 있다고 합치지 않으며 확인일은 2026-10-21이다.

현재 VIA가 사용할 특정 S2S의 외부 텍스트 의미 보존, 사용자 청취 중 별도 출력 요청의 동시 진행, 생성과 재생 분리, 중단 후 남은 구간 대응, 취소 사용량 확인은 통합 검증하지 않았다. 같은 response의 `audio.done`은 취소 시에도 나올 수 있으므로 전체 준비 성공은 최종 status·범위와 함께 판단한다. SDK stream을 닫는 것만으로 원격 생성·과금까지 즉시 중단됐다고 간주하지 않는다.

따라서 **구현 가능한 설계 후보와 손익 인과는 제시했지만 제품 검증 완료는 아니다.** 지원하지 않는 S2S를 다른 모델이나 TTS로 몰래 대체해 성립시키지 않는다. 모델 자체를 바꾸는 비교는 별도 결정이다.

#### 선택 이유와 반증 조건

- A를 선택할 이유: 여러 유효 질문·결과가 겹칠 때 다음 실제 음성을 빠르게 시작하는 QA01을 우선한다. 그 대가로 전달 전 변경될 내용에도 사용량과 보관 비용을 지불한다.
- B를 선택할 이유: 대기 중 결과가 자주 갱신·대체되고 실제 음성으로 전달할 최신 내용만 생산하는 QA05 이익을 우선한다. 그 대가로 각 새 발화 실행에 첫 음성 생성 대기가 남는다.
- 반증: 선행 준비 시간이 거의 없거나 S2S 첫 내용 지연이 작으면 A의 QA01 이익이 약해진다. 전달 전 폐기할 내용이 거의 없으면 B의 QA05 이익이 약해진다. 동시 준비가 실제로 불가능하면 A의 핵심 실행 가정이 성립하지 않는다.
- 지위: QA01 음성 정의 아래 **QA01 대 QA05의 구조적 교환을 가진 재검토 후보**다. QA03은 관련 완료 경로, QA06은 부가 비용 가설이며 모든 QA나 과정의 3~4개 강한 독립 축을 확보했다고 선언하지 않는다. 기존 QA01 공식 정의·점수·COMMON-28·ADR 변경, 구현·모델 실행·실측·선정은 하지 않았다.

> 2026-10-21 / 사용자 정정에 따른 문제 경계와 구조 탐색 재정립 / 새 A/B 미선정 / 이번 재검토의 구현·모델 실행·측정 없음
>
> 현재 DP44 논의는 이 문서에서 시작한다. 사용자는 DP44를 VIA의 핵심 설계 문제로 다시 깊게 검토하도록 요청했다. 이전의 상세 설계 유지 권고를 이번 탐색의 종료 조건으로 사용하지 않는다. [INTENT.md](../../../../../INTENT.md), [원래 DP44](../04-44-continuous-interaction.md), 현재 QA01/03을 다시 읽고 세 독립 검토의 문제 경계·구조·QA 인과 검토를 반영했다.

## 1. 다시 잡은 문제

**여러 생산자가 준비한 응답과 질문을 현재 대화에 맞춰 신속히 전달하고, 실제 전달 상태를 유지하여 중단·정정·후속 답변을 이어가는 구조를 설계한다.**

Downstream Agent는 업무를 수행하고 질문과 결과 내용을 제공한다. VIA에는 그 내용이 어느 업무와 요청의 어느 판본에 해당하는지 연결하고, 지금 제시할 수 있는지 확인하고, 화면과 음성으로 전달하며, 실제 전달한 범위를 다음 상호작용에 제공하는 일이 남는다.

문제는 의미 해석 중 짧은 시간에 새 발화가 겹치는 경우에 한정되지 않는다. 해석과 Agent 업무가 끝난 뒤에도 사용자가 설명을 듣는 시간이 존재한다. 그동안 다른 업무의 질문·결과가 도착하고 사용자가 끼어들 수 있다. 발화를 시간 간격을 두고 하더라도 계속 필요한 전달 생명주기다.

### 이번에 바로잡은 범위

| 항목 | DP44에서 다루는 것 |
| --- | --- |
| Agent 응답 내용 | 이미 준비된 질문·진행·결과를 받는다. 업무 분석이나 문안 생성을 다시 하지 않는다. |
| VIA 수행 안내·확인 질문 | 다른 책임자가 채택한 구체적 내용을 받는다. 전달을 위해 의미 판단을 다시 하지 않는다. |
| 사용자 발화 | 시작·중단 사건을 받고, 의미 판단 책임자가 채택한 관계·정정·철회를 적용한다. 해석 알고리즘은 DP2에 남긴다. |
| 업무 사실과 권한 | 원본 owner의 사실·판본·허가를 사용한다. 내용이 있다는 이유로 이 확인을 생략하지 않는다. |
| 사용자에게 전달 | 첫 화면 표시, 음성 준비·재생·중단, 미전달 내용과 실제 전달 기록을 관리한다. |
| 후속 대화 | 실제 제시된 질문과 전달 범위를 의미 판단 책임자에게 제공한다. 질문의 답이 무엇을 뜻하는지 최종 판단하는 책임은 가져오지 않는다. |

이 표는 책임 경계다. 기존 Component 이름이나 Dispatcher/Stage 구현을 새 대안의 필수 골격으로 고정하지 않는다. 원래 Task 사실 확인과 대화 연결 기능도 없어지는 것이 아니다.

## 2. 응답 내용이 있다는 것과 전달됐다는 것은 다르다

다음은 개념상 구분해야 할 사실이며, 모두 직렬로 실행해야 한다는 뜻은 아니다.

| 사실 | 예시 | 아직 보장하지 않는 것 |
| --- | --- | --- |
| 내용 준비 | 메일 Agent가 “수신자는 김 대리인가요?”를 보냄 | 현재 질문인지, 지금 표시 가능한지 |
| 대화 연결과 게시 조건 충족 | Task·Request·질문 판본과 권한을 확인함 | 실제 화면 표시·실제 청취 |
| 화면 표시 | 해당 질문 카드가 실제 표시됨 | 사용자가 읽었거나 음성으로 들었다는 사실 |
| 음성 준비 | 필요한 음성 데이터와 출력 참조가 준비됨 | 실제 음성 재생 |
| 실제 음성 전달 | 어느 구간까지 재생했는지 확인됨 | 사용자가 이해했거나 승인했다는 사실 |
| 질문 응답 대기 | 유효한 질문이 제시됐고 답이 필요함 | 전체 대화나 다른 Task를 정지해야 한다는 뜻 |

화면 표시와 음성 준비는 병행할 수 있다. 응답별로 어느 단계인지 달라도 된다. 단일 `done`으로 준비·표시·청취·답변 완료를 합치지 않는다.

**내용 준비를 공통 입력으로 고정하는 것은 맞지만, 게시 조건 처리와 실제 전달 연결까지 이미 끝난 것으로 가정하면 DP44의 핵심 기능을 비교 밖으로 빼버린다.** 반대로 음성 준비나 앞 응답의 발화 완료를 화면 표시의 필수 선행조건으로 추가해서 지연 차이를 만들지 않는다.

## 3. 같은 정상 장면에서 반드시 해결해야 할 것

### 설명 중 다른 업무 질문과 정정이 도착하는 경우

1. 보고서 결과 R1의 상세 내용이 화면에 표시됐다. 음성 설명은 일부만 전달됐다.
2. 메일 Task의 질문 Q1이 도착한다. 질문 내용은 Agent가 이미 작성했다.
3. VIA는 Q1의 업무·질문 판본과 게시 조건을 확인한다. 허용된 질문은 앞 설명의 음성이 끝났다는 조건을 추가하지 않고 화면에 표시할 수 있다. 음성 전달 상태는 별도로 관리한다.
4. 사용자가 끼어들면 로컬 음성 출력을 즉시 멈춘다. 이 시점만으로 보고서 업무나 메일 질문을 취소하지 않는다.
5. DP2의 판단이 “보고서의 결론 부분만 이어서 설명”으로 채택된다. 이 관계에 따라 R1의 미전달 범위를 갱신한다. 관계없는 Q1은 보존한다.
6. 사용자가 이후 “응”이라고 말하면, 그 입력 시점까지 어떤 질문이 실제 화면에 제시되고 음성으로 어느 범위까지 전달됐는지 제공한다. 단지 가장 최근에 생성된 질문을 답변 대상으로 확정하지 않는다. 둘 이상이 남으면 의미 판단 책임자가 모호함을 처리한다.

1번의 보고서 설명과 2번의 질문 내용을 VIA가 다시 작성하는 단계는 없다. 5번에서 새 내용이 필요하면 해당 내용 생산 책임자에게 맡긴다. DP44는 그 결과와 기존 전달 상태를 연결한다.

### 함께 확인할 기본 장면

| 장면 | 유지할 결과 |
| --- | --- |
| 일반 단일 요청 | 채택된 구체적 수행 안내를 필요한 조건 확인 뒤 바로 표시. 위임 완료나 결과 도착을 무조건 기다리지 않음 |
| 같은 Task의 진행 직후 결과 | 진행과 결과의 관계를 보존하고 오래된 안내의 새 전달을 방지. 합쳤어도 원래 사건의 QA01 시작 시각·분모 보존 |
| 질문에 대한 사용자 답변 대기 | 질문의 상태를 유지하면서 다른 유효 응답의 처리와 표시를 계속함 |
| 부분 정정·원본 구간 사용 철회 | 영향받은 미전달 내용에만 적용하고 다른 내용·다른 Task를 유지함 |
| 음성 연결 중단·재연결 | 텍스트에 표시된 사실과 실제 발화 범위를 구분. 전체 내용을 이미 들었다고 가정하지 않음 |

새 입력의 관계가 아직 알려지지 않았다면 코드가 임의로 무관하다고 추측하지 않는다. 관계가 채택된 뒤에는 그 범위를 사용한다. 미해결 입력을 풀기 위한 확인 질문은 자기 입력의 해석 완료를 기다리면 안 된다.

## 4. 실제 SW 구조에서 다시 열어야 할 결정

원래 Dispatcher/Stage 비교에서는 원본 owner, 게시 조건, 최종 게시 제어와 실제 전달 기록을 상당 부분 공통으로 유지했다. 그 결과 주로 완료 callback의 회수·재배정·Join이 비교 차이로 남았다. 이 비교의 차이가 약하다는 사실은 DP44 전체 문제가 작다는 근거가 아니다.

새 대안은 다음 결정까지 구체화해야 한다.

| 결정 | 구체적으로 정해야 할 것 |
| --- | --- |
| 전달 의무의 상태 단위 | 응답별 생명주기를 보존하는지, 대화 전체의 미전달 상태에서 각 출력을 도출하는지 |
| 게시 가능 조건의 유지 | 전달 시 원본 조건을 조회·결합하는지, 조건 변화로 응답별 readiness를 계속 갱신하는지 |
| 표시·발화 확정 | 누가 최종 판본과 허가를 검사하고 출력에 연결하며, 실제 표시·재생 결과를 어디에 반영하는지 |
| 중단·정정의 적용 | 어떤 의존 관계로 영향받은 준비·대기·재생을 찾고, 무관한 전달 의무를 유지하는지 |
| 다음 입력과의 연결 | 입력 당시까지 실제 전달된 범위를 어떻게 고정해서 후속 의미 판단에 제공하는지 |

### 비교할 가치가 있는 첫 구조 질문

**전달할 때 필요한 상태를 모아 판단할 것인가, 전달 가능 상태를 계속 갱신해서 유지할 것인가?**

| 항목 | 전달 시 조회·결합 | 조건 변화에 따른 상태 유지 |
| --- | --- | --- |
| 응답 도착 | 원본 내용 참조와 판본을 등록한 뒤 현재 조건을 읽음 | 내용 참조를 의존 관계에 등록하고 이미 유지한 조건 상태와 결합 |
| 보류된 조건 해소 | 관련 사건으로 깨워 원본 조건을 다시 확인 | 바뀐 조건에 연결된 항목의 readiness를 갱신 |
| 필요한 상태 | 응답·보류 사유·원본 참조와 실제 전달 기록 | 공통 상태에 더해 의존 인덱스·조건 판본·ready 집합 |
| 최종 표시 | 현재 판본·권한 확인 후 게시 | 동일한 최종 검사 유지. 캐시만 믿고 검사 생략하지 않음 |
| 이익 가설 | 조건 갱신과 파생 상태 유지의 부담을 줄임 | 반복 조회·결합을 첫 표시 경로 밖에서 처리할 수 있음 |
| 비용 가설 | 필요한 조회·결합이 QA01/03 경로에 남음 | 갱신·무효화·재구성 책임과 추가 상태가 생김 |

이는 **강한 A/B로 확정한 결과가 아니라 실제 상태·실행 차이를 검토할 출발점**이다. 같은 process와 같은 원본 저장 경계를 유지하며, 한쪽만 DB/RPC로 느리게 만들지 않는다. 원본을 작은 메모리 구조에서 읽는 비용이면 차이가 작을 수 있다. 두 번째 안도 최초 등록과 최신 조건 도착을 기다려야 하며 최종 검사를 없앨 수 없다.

조회 방식에 간단한 cache/index를 더하는 것으로 두 안이 수렴한다면 보완안인지 기본 구조 전환인지 구분한다. 파생 상태 관리가 실제 설계 선택인지, 작은 최적화인지를 통과하지 못한 후보를 주요 DP로 확정하지 않는다.

응답별 상태와 대화 전체 상태는 별도 선택 축이다. 두 축을 임의로 묶어서 배타적인 A/B로 만들지 않는다. 응답별 상태라도 공통 전달 조회 뷰를 둘 수 있으며, 대화 전체 상태라도 내용은 참조로 공유할 수 있다.

### 후속 답변을 연결하는 구체적인 상태 계약

구현 후보 중 하나는 실제 출력 경로의 전달 사건과 사용자 입력에 비교 가능한 순서·범위 참조를 붙이는 것이다. 입력 시점까지 확인된 text 표시와 audio 전달 기록을 모아 후속 해석에 제공한다. 응답별 상태라면 그 기록들을 결합하는 조회 경로가 필요하고, 대화 전체 상태라면 같은 상태 전이에서 조회 뷰를 유지할 수 있다.

이 방식도 구현으로 검증된 사실이 아니다. UI와 audio의 관측 시점 및 순서가 불명확하면 `UNKNOWN`을 유지한다. 현재 출력 중인 문장을 끝까지 기다리는 장벽과, 입력 당시의 실제 전달 기록을 확보하는 장벽을 혼동하지 않는다. 두 안 모두 올바른 근거를 제공해야 하므로 한쪽만 전달 기록을 부실하게 만들어 정확도 차이를 주장하지 않는다.

## 5. QA01을 중심에 놓되 정의를 지킨다

[QA01](../qa-candidate-package/qa01-first-response-latency.md)은 입력·Agent 사건에서 첫 완결 내용의 실제 UI 표시까지다. 응답 내용의 도착 시각으로 시작점을 옮기거나 마지막 게시 함수만 재어 VIA 내부 대기를 숨기지 않는다.

```text
Agent 사건 최초 가용
  → 발견·수신
  → 업무 사실 확인·대화 연결
  → 게시 조건 처리
  → 실제 첫 내용 표시  [QA01 종료]

내용·판본 확정
  → 필요한 상세 표시와 전체 음성 준비  [QA03 완료조건 일부]
  → 실제 음성 전달·중단·후속 입력 연결 [별도 실제 전달 기록]
```

각 화살표는 책임 경계이며 모두 직렬 처리해야 한다는 뜻이 아니다. 실제 음성은 준비와 병행해 streaming 재생할 수 있다. DP44 외부의 의미 판단·Agent 업무 등은 같은 조건으로 두고 DP44가 바꾼 실제 선행 의존을 표시한다.

| QA | 이번 범위의 판정 |
| --- | --- |
| QA01 첫 응답 | 핵심 목표. 이미 준비된 유효 내용의 첫 표시를 막는 상태·조건·실행 대기를 찾아야 함. 개선 크기는 아직 미확정 |
| QA02 지칭 정확도 | 이미 채택한 지칭을 후속 전달 오류로 재채점하지 않음. 다음 입력이 전달 근거를 사용한다면 영향 경로는 추적하되 구조만으로 정확성 우위 주장 금지 |
| QA03 VIA 처리시간 | 목표 완료 전에 필요한 연결·표시·음성 준비 경로의 차이를 평가. 총 작업량 감소와 임계 경로 단축 구별 |
| QA04 변경 모듈 수 | C04 부분 정정과 C06 구간 사용 철회에서 실제 변경 범위를 확인할 후보. 상자 수·복잡도만으로 우열 확정 금지 |
| QA05 전체 모델 비용 | 불필요한 재작성 모델 호출을 추가하지 않음. 실제 음성 준비·취소·재준비 차이가 없다면 차별화 근거 없음 |
| QA06 최대 로컬 RAM | 실제 동시 보유 상태·버퍼의 수명 차이를 확인. 공유 내용 중복 계산과 queue 개수만의 큰 차이 주장 금지 |
| 새 QA07 요청 의미 정확도 | DP2의 판단 자체는 고정. 실제 전달 근거가 이후 최초 의미 판단에 미치는 경로와, 이미 끝난 판단 이후의 전달 오류를 구별 |

음성 차례와 실제 재생 개선만으로 QA01/03이 좋아졌다고 말할 수 없다. 현재 정의가 그 구간을 포함하지 않기 때문이다. [기존 QA09 음성 전달](../qa-candidate-package/qa09-audio-delivery-lag.md)은 별도 정의이며 이번에 핵심 QA로 채택하거나 QA01을 변경하지 않는다. 이 관측 범위의 한계를 DP44 기능의 중요성이 낮다는 판단으로 바꾸지도 않는다.

## 6. 이번 재검토의 판단과 다음 통과 기준

**DP44는 중요한 대화 전달 구조 문제로 계속 깊게 검토한다. 기존 A의 열세를 만들기 위해 새로운 응답 생성 업무를 추가하지 않는다.**

이번에 완료한 것은 문제 경계 정정, 정상 장면과 실제 상태 구분, 기존 비교가 좁아진 이유 및 다시 열어야 할 구조 결정의 정리다. 새로운 두 기본안에서 강한 QA 교환을 확보한 결과는 아직 아니다.

새 기본안을 확정하려면 다음을 설명할 수 있어야 한다.

1. 같은 내용·원본 사실·사용자 목표에서 실제로 읽고 유지하는 상태와 실행 의존이 다르다.
2. 정상 단일 입력, 독립 질문 도착, 부분 정정과 후속 답변을 같은 완료 조건으로 처리한다.
3. QA01의 어느 실제 대기가 줄고, 상대 안은 어떤 필수 처리·상태의 비용을 줄이는지 짚는다.
4. 비용 축을 추가 LLM, 전역 동기 대기, 현재성 검사 생략이나 가상 부하로 만들지 않는다.
5. 공통 기능과 구조 고유의 재사용을 갖춘 뒤에도 기본 설계의 차이가 남는다. 별도 tactic으로의 수렴 가능성도 공개한다.

독립 검토 세 건은 문제 경계, 구조 후보, QA 인과를 각각 검토했다. 공통 지적은 내용 준비와 게시 허용을 구별할 것, QA01/03의 실제 음성 차례 제외를 지킬 것, 기존 비교의 공통 부분까지 재탐색할 것이었다. 작성 후 QA 검토자는 핵심 오류를 보고하지 않았고, 전체 음성 준비와 실제 재생이 직렬로 읽힐 수 있다는 명료화 의견을 반영했다. 로컬 링크의 존재도 확인했다. 이 검토는 제품 구현·성능·정확성을 검증한 것이 아니다.

## 7. 이전 제안의 상태와 참고 근거

- [응답 문안 경유 대 채널별 생성](dp44-output-generation-tradeoffs-20261020.md), [개별 생성 대 묶음 생성과 가상 수치](dp44-batched-response-synthetic-example-20261021.md)는 사용자 정정에 따라 현재 DP44 대안에서 철회한다. Downstream Agent가 제공한 응답 내용을 VIA에서 다시 생성하는 비교로 범위를 옮겼다. 가상 수치는 새 DP44의 예상값이나 실측 근거가 아니다.
- [원래 A/B 재평가](dp44-original-alternatives-reassessment-20261020.md)는 그 비교의 제한된 손익에 대한 과거 작성자 판단으로 보존한다. 이번 사용자 요청 이후의 탐색 종료나 최종 선택으로 사용하지 않는다.
- [원래 DP44](../04-44-continuous-interaction.md)의 연속 청취, 제어, 실제 전달과 질문 연결 요구는 재검토의 출발점이다. 기존 그림·Reference Architecture·QA 정의·ADR은 수정하지 않았다.
- [LiveKit의 speech 제어 문서](https://docs.livekit.io/agents/multimodality/audio/)는 이미 정해진 발화를 전달하는 `say()`와 해당 발화의 상태·재생 완료를 다루는 `SpeechHandle`을 구별한다. [turns 문서](https://docs.livekit.io/agents/logic/turns/)는 끼어들기 뒤 실제 전달 범위에 맞춰 대화 기록을 조정하는 동작을 설명한다. 생성과 실제 전달의 분리가 구현상 필요한 책임이라는 참고이며, 특정 라이브러리 채택이나 VIA 대안의 성능 우위를 입증하지 않는다. 확인일 2026-10-21.
