# DP44 재탐색: 겹치는 사건의 실행권과 중단·재개

> **후속 산출물:** [DP2+DP44 통합 해석·확정 구조 비교](dp2-dp44-integrated-interpretation-and-commit-20261020.md)가 §13의 사용자 방향에 따른 현재 탐색이다. 이 문서의 자원 스케줄링 A/B/C 및 재판정은 이전 논의 이력으로 보존한다.

2026-10-20 / 사용자 정정 반영 / 설계 후보·미선정·미구현·미측정

> **최신 사용자 방향:** DP2와 DP44를 구분해 두 DP를 유지하는 것이 우선이 아니다. [§13](#13-dp-경계보다-via의-구조적-결정을-우선)의 통합 문제 탐색을 따른다. DP2 고정과 공통 scheduler 고정을 새 대안의 필수 자격 조건으로 사용하지 않는다. 통합 가능성을 열어 둔 것이며 합병이나 기본안을 이미 선정한 것은 아니다.

> **후속 경계 검토:** 사용자가 모델 자원 스케줄링 정책과 DP2의 중복을 지적했다. [§12의 재판정](#12-dp2와의-경계와-bc의-구조성-재판정)을 현재 판단으로 따른다. B/C는 구현 계약의 차이는 있지만 조합 가능한 중단·재시도와 자원 예약 축이며, 독립된 주요 DP44의 배타적 기본안으로 성립했다고 보지 않는다. 아래 §11의 B/C 우선 심화 권고는 직전 제안 이력이다. DP44의 기능 문제와 기존 자료는 유지한다.

## 1. 이번 비교의 문제

사용자는 [직전 응답 생산 탐색](dp44-response-production-exploration-20261020.md)이 출력 분할에 가깝다고 지적하고, **사용자 발화·정정·Agent 통지가 겹칠 때 실제 처리 구조가 달라지는 방안**을 요청했다. 직전 탐색은 응답 정책의 별도 검토로 보존하며 DP44의 주 비교 권고로 사용하지 않는다.

이번 질문은 **이전 VIA 작업이 실행 자원을 사용 중일 때 새 발화와 Agent 사건을 처리하기 위해, 실행 중인 작업을 유지할지, 중단하고 다시 만들지, 처음부터 개입용 처리 여력을 보호할지**다. 차이는 출력 문장 길이가 아니라 새 의미 판단의 시작 시각, 진행 중 계산의 수명, 폐기·재시도와 다른 목표의 완료에 생긴다.

새 비교의 A/B/C는 이 문서 안에서만 사용한다. 기존 Dispatcher/Stage나 직전 응답 생산 A/B/C의 재명명이 아니다. 기존 문서와 참조 Architecture, QA 정의·점수·ADR은 보존한다.

비교는 VIA의 실행 의도와 Model Access/runtime의 실제 수용 계약을 연결한다. 단순 queue 이름이나 priority 값만 바꾸고 실행 중 작업의 수명·자원 회수·재개가 같으면 큰 구조 차이라고 보지 않는다. 세 안을 같은 라이브러리의 설정만으로 동일 비용에 제공할 수 있다면 주요 DP 자격도 다시 판단한다.

## 3. 모든 안에서 같은 사용자 제어와 정합성

1. Interaction Manager는 계속 입력을 받고 발화 시작에 음성을 로컬에서 즉시 중단한다. ASR·실시간 음성의 필수 진행 예산은 세 안 모두 보호하며, 전체 모델 호출을 묶는 전역 mutex를 두지 않는다.
2. Request Controller는 새 발화와 관련될 수 있는 미전송 효과를 보류한다. 관계가 미해결이면 안전하게 좁힐 수 없는 범위를 보류하되, 의미 해석 전에 특정 Task 정정을 정답처럼 붙이지 않는다.
3. Agent Gateway는 통지를 수신하고 Task Manager가 확인된 업무 사실을 보존한다. 모델 자원 대기 때문에 중요 질문·결과·실패를 버리지 않는다. 외부 업무의 사실 기록과 대화에 게시하는 행위는 분리한다.
4. 이미 확인된 상태·명시적 질문을 추가 의미 판단 없이 표시할 수 있으면 모든 안이 코드 경로를 사용한다. Agent 통지마다 모델 호출을 강제하지 않는다.
5. Request Interpreter의 같은 의미 기능으로 새 입력을 해석하고 Request Controller가 정정·독립 요청·질문 답변 관계를 채택한다. Response Manager는 현재 revision·권한·게시 허가를 확인하고 Interaction Manager의 실제 receipt를 기록한다.
6. 실제 제시한 질문만 짧은 답변의 근거로 사용한다. 가장 늦게 도착한 Agent 질문을 자동으로 대화 focus로 삼지 않는다.
7. VIA의 계산 중단은 외부 Agent 업무 취소와 다르다. 입력이 들어왔다는 이유만으로 Agent 작업을 취소하거나 같은 외부 명령을 재전송하지 않는다. 취소 접수와 확인된 종료도 구별한다.
8. 논리적 결과 무효화와 실제 계산 종료·KV/호출 credit 반환은 별도 사건이다. cancel 요청을 보냈다는 이유만으로 슬롯을 재사용하지 않는다.
9. 대기열·활성 실행·재시도에 유한 상한을 둔다. 사용자 입력이 반복돼도 유효한 다른 요청과 Agent 질문에 처리 기회를 보장하고, 과부하·실패를 기록한다. 무조건 최신 사건만 남기는 구조는 아니다.

## 4. 세 가지 기본안

### A. 공유 실행 자원, 현재 작업 경계에서 전환

사용자 해석, Agent 사건 연결, 긴 응답 준비가 semantic 실행 자원을 공유한다. 준비된 작업을 공통 admission에서 배정하고, 이미 실행한 유효 작업은 현재 호출/작업 경계까지 진행한다. 새 입력은 즉시 보존하고 다음 배정에서 우선하지만, **새 입력을 시작시키기 위해 아직 유효한 실행을 선제 취소하지 않는다.**

1. 입력/통지를 보존하고 공통 hold·음성 stop을 적용한다.
2. 여유가 있으면 새 제어 해석을 즉시 시작한다. 여유가 없으면 현재 작업의 다음 자원 반환 경계를 기다린다.
3. 새 의미를 채택한 뒤 영향받은 기존 결과를 무효화하고, 무관한 목표를 이어간다.

현재 호출 경계는 Task 전체 완료가 아니다. 외부 Agent나 사용자 답변을 기다리는 작업은 계산 슬롯을 반환한다. 같은 runtime의 짧은 kernel 교대, 음성 보호, 호출 deadline도 유지한다. 이미 무효임이 확정된 job 취소는 공통으로 허용한다.

**이점:** 아직 유효한 계산을 버리지 않고 공유 자원을 활용한다. 유효한 완료 step·근거를 재사용하며, 선제 중단/재구성 기록이 적다.

**비용:** 활성 semantic 작업의 admission/KV 여유가 모두 소진되면 새 발화의 해석이 기다린다. UI가 입력을 받았다는 사실과 구체적 첫 응답을 낼 수 있다는 사실은 다르다. 호출이 짧거나 여유가 있으면 이 비용은 작다.

### B. 개입 시 실행을 중단하고 자원을 회수한 뒤 재구성

자원은 A처럼 공유하지만, 새 사용자 개입이나 처리 기한이 가까운 중요 사건을 시작할 여유가 없으면 **낮은 우선순위의 취소 가능한 VIA 계산을 선점 대상으로 고른다.** 그 작업이 의미적으로 무효라고 단정하는 것이 아니라, 실행권을 일시적으로 새 사건에 넘기는 선택이다.

1. 공통 hold·입력 보존 뒤 중단 가능한 응답 준비/일반 처리 job을 선택한다. 늦은 반환의 사용을 막을 job 세대와 중단 이유를 기록한다.
2. Model Access에 backend 중단을 요청한다. 실제 종료·자원 반환 확인 뒤 새 해석을 시작한다.
3. 새 입력이 기존 요청의 정정이면 관련 기존 준비만 폐기한다. 독립 요청이면 앞선 목표를 유지하고, **마지막 완결된 유효 step부터** 중단 작업을 다시 시작한다.
4. 미완성 모델 내부 상태가 재개 가능한 checkpoint라고 가정하지 않는다. 기본 B는 중단한 호출 내부의 계산을 잃을 수 있으며, 재호출·재입력을 비용으로 센다.

유효 목표와 근거·완료된 step·이미 전달한 범위·외부 명령 식별자는 host에 남긴다. 중단한 호출의 결과가 늦게 와도 새 세대의 결과처럼 채택하지 않는다. 우선순위 분류는 입력 주체와 확인된 Task 사건 종류에서 시작하며, 미해석 발화가 어떤 Task를 바꿀지 추측해서 victim을 정하지 않는다.

**이점:** 남은 호출 전체를 기다리는 대신 backend 취소/회수 시간 뒤 새 발화 해석을 시작할 수 있다. 정정으로 어차피 버릴 준비를 일찍 중단하면 계산도 절약한다.

**비용:** 독립 질문이었으면 유효했던 계산을 버린 셈이다. 문맥 재입력·재계산과 이전 목표 완료 지연이 발생한다. 반복 개입은 재시작을 누적시키므로 재시도 상한·aging·일반 작업 최소 진행 계약이 필요하다. 취소가 느리거나 실제 실행 자원을 돌려주지 않는 공급자에서는 QA01 이점이 사라진다.

### C. 개입 처리 경로와 일반 준비 경로의 자원 수용 분리

Request Controller가 요청하는 새 입력 관계 해석·필수 확인과, Response Manager 등의 긴 상세 준비에 **별도 수용 대기열과 실행 credit 계약**을 둔다. Model Access는 같은 가중치 아래 개입 처리에 필요한 최소 연산 서비스와 context/KV 수용 여력을 미리 보호한다.

1. 일반 준비가 많아도 개입 경로의 예약분을 침범해 모두 차지할 수 없다. 기본 C에서는 일반 작업이 비어 있는 예약분을 빌리지 않는다.
2. 새 입력은 개입 경로에서 의미 판단을 시작한다. 앞선 유효 일반 작업은 남은 예산으로 계속 진행한다.
3. 정정 관계가 확정되면 영향받은 job만 취소하고, 독립 요청이면 기존 작업은 유지한다. 긴 후속 처리로 전환된 작업은 일반 경로에 넘겨 개입 예약분을 무기한 점유하지 않게 한다.

이는 별도 모델이나 OS process 두 개를 요구하지 않는다. 다만 queue를 나누는 것만으로는 부족하다. 실제 scheduler의 서비스 시간, KV admission, 비선점 kernel 상한이 함께 보장되어야 한다. 취소 불가능한 긴 kernel이나 공급자의 보이지 않는 queue가 예약을 무효화하면 C의 이점도 주장할 수 없다.

**이점:** 기존 계산을 버려 자리를 만들지 않고도 새 입력을 시작할 수 있다. B처럼 독립 질문 때문에 유효한 준비를 다시 할 필요가 줄어든다.

**비용:** 사용자 개입이 드문 동안 일반 작업이 예약된 수용 여력을 다 활용하지 못할 수 있다. 긴 답변·Agent 결과의 상세 준비가 늦어지며, 개입 경로 자체에 사건이 몰리면 그 안에서 대기한다. 물리 연산·메모리 한도를 늘린 해결책이 아니다.

## 5. 같은 겹침 장면의 끝까지 비교

**초기 상태:** 보고서 R1의 상세 설명과 다른 Agent 결과의 VIA 요약이 실행 중이고 현재 semantic 수용 여력이 소진돼 있다. 사용자가 “아니, 보고서는 표만 설명해줘”라고 말하는 동안 메일 업무의 수신인 확인 질문 Q1과 R1의 이전 결과가 도착한다. 수용 여력이 있는 같은 장면도 대조군으로 포함한다.

| 시점/사건 | A | B | C |
| --- | --- | --- | --- |
| 사용자 발화 시작 | 세 안 모두 음성 즉시 중단, 입력 계속 수신, 관련 미전송 효과 보류 | 동일 | 동일 |
| Agent Q1 도착 | 세 안 모두 Task 사실과 질문을 보존. 바로 표시 가능한 확인 사실은 공통 경로 사용 | 동일 | 동일 |
| 새 발화 확정, 의미 판단 대기 | 현재 호출의 자원 반환 후 우선 해석 | 중단 가능한 준비를 취소하고 실제 회수 후 해석 | 보호한 개입 예산에서 해석. 해당 queue 대기는 남음 |
| “R1은 표만” 채택 | 뒤늦은 R1 전체 설명을 신규 결과로 게시하지 않음 | 중단 R1 준비 중 불필요해진 부분 폐기 | R1의 영향받은 일반 준비만 취소 |
| Q1과 다른 결과 처리 | 무관 목표·질문 유지. 관계/허가에 따라 표시 | 중단 victim이 무관 업무였다면 유효 step에서 재구성 | 일반 예산 내에서 유지하고 중요 질문은 정해진 공정성 계약으로 처리 |
| 사용자가 짧게 답함 | 실제 표시/재생한 질문에만 연결 | 동일 | 동일 |
| 최종 완료 | 표 설명, 메일 답 연결, 다른 유효 결과까지 확인 | 동일. 재계산과 실패도 포함 | 동일. 일반 경로 지연도 포함 |

**반대 사례:** 사용자가 “그건 계속하고 다른 자료도 봐줘”라고 했으면 A의 진행 중 계산은 그대로 유용하고, B의 선제 중단은 손실일 수 있다. C는 기존 계산을 보존하지만 예약 때문에 이미 느리게 진행했을 수 있다. 새 발화 시작만으로 정정인지 독립 요청인지 알 수 없다는 VIA의 특성에서 손익이 생긴다.

**간섭이 없는 사례:** 이전 업무가 외부 Agent 결과를 기다릴 뿐 VIA 연산은 사용하지 않거나, Q1을 확인된 필드로 바로 표시할 수 있으면 A도 빠르다. 해당 장면을 B/C의 독점적인 QA01 개선으로 세지 않는다.

## 6. 첫 응답 지연의 인과

같은 출력 정책 아래 새 입력의 첫 응답은 `실행 admission 대기 + 필요한 의미 판단/근거 처리 + 채택/게시/실제 표시`를 지난다. 이번 차이는 첫 항과 자원 간섭에 있다.

| 안 | 포화 시 admission 대기의 주요 원인 | 반드시 같이 확인할 것 |
| --- | --- | --- |
| A | 진행 중 호출의 다음 자원 반환까지 대기 | 짧은 호출이면 B의 취소보다 먼저 반환할 수 있음 |
| B | victim 선택·backend safe point·취소 완료·자원 회수 | cancel API 응답과 실제 자원 회수는 다름. 재계산으로 다음 사건이 다시 밀릴 수 있음 |
| C | 개입 queue와 다음 보장 서비스 시점 | 예약이 새 입력 계산 자체를 빠르게 하는 것은 아님. 좁은 예약분에서는 의미 실행 시간이 더 길 수도 있음 |

**개입한 사용자 한 건의 개선은 QA01 전체 평균 개선과 다르다.** 그동안 지연된 Agent 질문/결과와 이전 요청의 의무 첫 응답도 같은 고정 분모에 포함한다. 현재 입력만 골라 평균을 만들지 않으며, 무응답·실패를 숨기지 않는다. 실제 첫 내용 표시와 단순 접수 신호, 음성 재생 시점을 구별한다.

## 9. 구현 근거와 적용 한계

- [VIA 공유 runtime의 기존 참조 계약](../../target-architecture/shared-omni-runtime.md)은 이미 서비스 예산, KV 수용, backend safe point, 실제 취소 확인, 재개 불가 시 원본 재계산을 다룬다. 이번 비교는 이 조합의 비용과 대안을 설명하는 용도이며 기준선의 미완료를 선언하지 않는다.
- [Temporal Python message passing](https://docs.temporal.io/develop/python/workflows/message-passing)은 async handler의 실행이 await 경계에서 교차하고, 공유 상태에는 별도 동시성 제어가 필요함을 설명한다. 입력 수신과 진행·완료 상태를 분리하는 참고다. Temporal을 도입하면 VIA의 모델 실행권과 의미 정합성이 자동 해결된다는 뜻은 아니다.
- [vLLM optimization: preemption](https://docs.vllm.ai/en/latest/configuration/optimization/#preemption)은 KV 공간 회수를 위한 선점과 이후 재계산이 끝단 지연에 비용을 줄 수 있음을 설명한다. B의 회수 대 재계산 메커니즘에 대한 구현 참고이며, 해당 기능이 VIA 사용자 우선순위 선점이나 현재 장비의 QoS를 이미 보장한다는 뜻은 아니다.

자료 확인일 2026-10-20. 공식 구현의 메커니즘을 확인했으며 VIA 후보 성능을 측정한 것이 아니다.

## 11. 현재 제안과 반증 조건

**A/B/C를 기본안으로 비교하되 B 대 C를 우선 심화한다.** 둘 다 개입 반응성을 확보하려 하지만 B는 개입 때 계산을 버리고 재구성하는 비용을, C는 평소 일반 작업의 자원 활용을 제한하는 비용을 낸다. A는 개입이 드물거나 현재 작업이 짧을 때의 공유 효율 대안이다. 아직 최종 선택이 아니다.

다음 설계 검토에서 일반/겹침/반복 정정/독립 새 질문/통지 burst를 함께 대조하고, 동일 자원에서 실제 admission 지연·취소 회수·재계산·일반 목표 지연이 발생하는지 확인해야 한다. 현재 사용자 입력만 빠르고 전체 QA01은 나빠지는 결과도 보존한다. 취소가 다음 자연 경계보다 느리거나, 일반적인 장면에서 자원 경합이 거의 없거나, 값싼 대여/회수로 세 안이 수렴하면 큰 QA 차별화 주장을 철회한다.

이번 작업은 설계 문서와 탐색 방향의 수정이다. 새로운 코드 구현·모델 실행·측정·수치/점수·Git 발행은 수행하지 않았다.

## 12. DP2와의 경계와 B/C의 구조성 재판정

2026-10-20 후속 사용자 질문과 [INTENT.md](../../../../../INTENT.md) §6~8에 따른 재검토다. **설정값보다 많은 구현이 필요하다는 사실만으로 주요 DP가 성립하지 않는다.** 처리 구조의 선택, 그 구조를 지원하는 자원 정책, 공통 필수 복구를 구별한다.

### DP2가 정하는 것과 이번 제안이 정한 것

| 구분 | DP2 의미 실행 구성 | 이번 B/C의 실행 자원 관리 |
| --- | --- | --- |
| 질문 | 같은 대화 실행에서 후속 입력을 처리할지, 공통 관계 해석과 요청별 실행으로 나눌지 | 이미 존재하는 실행을 중단해 자리를 만들지, 자리를 미리 보호할지 |
| 상태 | 의미 문맥·요청별 잠정 판단·입력 전달·결과 재결합 | 시도 세대·backend 종료 확인·재시도 지점·자원 예약/반환 |
| 결정의 결과 | 독립적으로 진행 가능한 의미 실행과 그 의존 관계가 달라짐 | 준비된 실행의 시작/중단/재개 시점이 달라짐 |
| 첫 응답 이익 | 앞선 의미 실행에 묶였던 논리적 대기를 분리할 가능성 | 실행 가능하지만 자원이 없는 상태의 대기를 줄일 가능성 |

구별 가능한 층위이지만 완전히 독립적인 모든 조합이 자동 성립하는 것은 아니다. DP2의 단일 대화 실행이 기존 의미 호출의 반환을 기다리는 중이라면 C가 자원만 예약해도 새 발화 해석이 독립 실행되지 않는다. C를 성립시키려고 새 관계 해석 세션과 요청별 실행을 추가하면 **DP2 구조를 함께 변경한 것**이다. 반대로 DP2의 공통 관계 해석과 요청 실행이 이미 분리돼 있다면 C는 그 실행들에 예약을 적용하는 상세 설계가 될 수 있다. 기존 응답 준비와 의미 해석이 이미 독립된 경우에도 같은 판단을 적용한다.

### B에서 우선순위 숫자 밖에 필요한 처리

B에는 다음 실행 수명 계약이 필요하다. 이는 설계상 필요한 계약이며 신규 구현 완료 주장이 아니다.

1. 의미 요청의 revision과 모델 실행 attempt를 구별한다. 자원 때문에 중단한 attempt가 의미 요청 취소를 뜻하지 않는다.
2. 재시도 기술에는 Request/Task 연결, 사용 근거의 revision, 마지막 유효한 완료 단계, 이미 게시/전송한 효과의 식별자를 연결한다. 공통 owner의 원본을 불필요하게 복제하지 않는다.
3. `중단 요청 → backend 종료·credit 회수 확인 → 재시도 대기 → 새 attempt 시작`을 구별한다. 늦은 이전 attempt의 반환은 현재 결과로 채택하지 않는다.
4. Request Controller는 목표·revision과 계속할 의도를, Model Access는 실제 호출 수명과 회수를, Response Manager는 게시와 전달 원장을 각각 소유한다. 공통 실행 연결이 이 상태를 이어준다.
5. 외부 업무 재전송이나 이미 전달한 내용의 중복 없이 유효 단계부터 다시 실행한다. 모델 내부의 임의 중간 token을 재개 가능한 checkpoint라고 하지 않는다.

이것은 단순 dequeue 순서보다 넓은 SW 계약이다. **그러나 취소, 늦은 결과 거부, 실패 재시도와 중복 방지는 A/C에도 필요하다.** 참조 runtime에도 상당 부분 이미 존재한다. 기존 계약으로 B를 구현할 수 있다면 주된 추가 선택은 언제 선제 중단을 발동하느냐이며, 위 공통 장치를 B만의 구조 비용으로 모두 계산할 수 없다.

### C에서 우선순위 숫자 밖에 필요한 처리

C는 다음 자원 수용 계약이 있어야 효과를 낸다.

1. 작업의 개입/일반 class와 그 class의 사용 종료·전환을 표시한다. 호출의 이름만 바꾸는 것으로 끝나지 않는다.
2. Model Access/runtime에서 전체 한도 안의 예약·사용·반환 credit을 관리한다. 일반 작업을 받아들이기 전에 개입용 context 수용 여력이 남는지 확인한다.
3. 서비스 시간과 가장 긴 비선점 계산 구간을 제한한다. 실행 대기열을 둘로 나누는 것만으로 새 호출의 메모리 수용이나 계산 진행을 보장하지 않는다.
4. 개입 경로에서 긴 후속 처리로 바뀌면 class를 전환하고 예약을 반환한다. 두 class 모두 포화와 공정성 처리를 명시한다.

이 역시 순서 설정만으로 구현되지 않을 수 있다. 하지만 **요청 의미의 owner·문맥·Task 관계·결과 채택 방식은 그대로일 수 있다.** 기존 runtime이 이 수용 계약을 제공한다면 C는 runtime의 상세 설계/정책이다. 별도 대화 조정 실행과 독립 해석 문맥을 새로 도입해 구조성을 만들면 DP2 변경을 먼저 공개해야 한다.

### B와 C는 서로 배타적인 축이 아니다

| 자원 예약 | 선제 중단·재시도 없음 | 선제 중단·재시도 있음 |
| --- | --- | --- |
| 없음 | 이전 A의 기본 방향 | 이전 B의 기본 방향 |
| 있음 | 이전 C의 기본 방향 | 예약분을 보호하면서 부족할 때 일반 작업도 중단하는 조합 |

조합 가능성 하나만으로 기본 구성을 무조건 폐기하는 것은 아니다. 그러나 기존 설명은 이 두 축을 같은 결정의 배타적 대안처럼 묶었고, 어떤 조합을 기본으로 비교할지와 효과를 분리할 이유를 충분히 제시하지 못했다. 참조 구조도 예약과 background 중단을 함께 사용한다. 따라서 **B 대 C를 DP44의 핵심 비교라고 한 이전 권고를 철회한다.**

### 현재 판정과 이후 탐색의 경계

- B/C는 자원 스케줄링·실행 복구의 상세 설계 또는 보완 후보로 남긴다. 이미 구현된 공통 계약으로 해결되는지에 따라 분류하며, 새 Module을 억지로 추가해 주요 DP로 만들지 않는다.
- QA01의 자원 대기, QA03의 재계산/수용 제한, QA05의 사용 비용 경로는 가능한 가설로 남는다. 그러나 그 손익이 DP2와 독립된 주요 DP44를 입증하지는 않는다. 논리적 실행 분리와 runtime 여력 확보의 이익을 중복 계산하지 않는다.
- DP44 자체를 폐기하거나 사용자 우선순위를 바꾸는 결론은 아니다. 발화·정정·Agent 사건의 겹침에서 **공통 scheduler를 그대로 두어도** continuation, 사건의 처리 의존, 보류/확정 단위와 재개 기준이 달라지는 대안을 찾아야 한다. 특정 대안을 새로 채택한 것은 아니다.
- 새 QA07 요청 의미 해석 정확도는 INTENT.md의 사용자 정의를 따른다. 우선순위·목표·점수는 이번 검토에서 정하지 않는다.

이번 재판정은 설계 설명과 문서 정정이며 구현·모델 실행·측정·Git 발행을 수행하지 않았다.

## 13. DP 경계보다 VIA의 구조적 결정을 우선

2026-10-20 사용자는 **DP2와 DP44가 하나로 합쳐지더라도 VIA에서 의미 있는 구조적 결정을 하는 것이 중요하다**고 정정했다. 두 DP의 독립성 입증이나 개수 보존을 탐색 목표로 삼지 않는다. 이는 INTENT.md의 문제 중심 탐색과 주요 DP 성립 조건을 이번 문제에 적용한 명시적 지시다.

탐색 질문은 **“진행 중인 대화와 업무를 어떤 실행 단위·문맥·상태로 관리하고, 새 발화·정정·Agent 질문과 결과를 어떻게 반영하여 유효한 처리를 이어갈 것인가?”**로 함께 다룬다. 기존 DP2와 DP44는 입력 자료이며 대안의 경계를 미리 정하는 제약이 아니다.

- 의미 실행 분리, 사건 연결, 보류·확정·재개가 하나의 구조 선택을 이루면 통합 DP로 비교할 수 있다. DP2와 겹친다는 사실은 대안의 탈락 이유가 아니다.
- 각각 독립적인 선택 이유와 QA 손익이 확인되는 경우에만 별도 DP로 나눈다. 분리 여부와 개수는 구조 분석의 결과다.
- scheduler를 고정하는 대조는 효과를 분해하는 분석 수단으로 사용할 수 있지만, 모든 후보가 scheduler를 고정해야 주요 DP가 된다는 조건은 철회한다. 실행 구조에 필수적인 자원 계약은 함께 설명하되 설정 차이만으로 구조성을 주장하지 않는다.
- 통합은 기존 두 문서를 단순 합치거나 같은 QA 이익을 두 번 세는 것이 아니다. 같은 사용자 장면에서 각 대안의 실행 단위, 상태 수명과 owner, 사건 반영, 확정·중단·재개, QA01 및 다른 QA 비용을 연결해야 한다.
- 앞선 B/C는 유지해야 할 비교안이 아니다. 통합 탐색에서 기본 구조의 필수 계약인지, 조합 가능한 보완인지, 중요하지 않은 상세 정책인지 다시 판단한다.

현재 승인된 것은 이 문제 중심의 설계 검토 방향이다. 통합 DP의 최종 선정·번호 변경, 기존 결과의 재분류, 구현·측정·Git 발행을 수행한 것은 아니다.
