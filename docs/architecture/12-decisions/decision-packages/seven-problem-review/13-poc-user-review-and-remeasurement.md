## 2. QA01과 QA03의 경계

### 사용자가 설명한 진행 안내는 QA01에 해당한다

`x와 y를 참고해서 보고서를 작성해줘`에 대해 실제 대상과 수행 내용이 채택됐다면 `x와 y를 참고해 보고서를 작성하겠습니다`는 첫 응답이다. 보고서 작성이나 인계 준비가 끝날 때까지 기다릴 필요가 없다. [현재 QA01 정의](../qa-candidate-package/qa01-first-response-latency.md)도 이를 허용한다. 이번 사용자 리뷰 때문에 새 의미로 바꾸는 것이 아니라 기존 정의에 맞춰 구현해야 한다.

측정할 순서는 다음과 같다.

1. 사용자 입력 수신.
2. 대상·범위·수행 의도 채택 또는 필요한 구체적 확인 질문 결정.
3. 그 내용을 해당 Request/Task UI에 첫 완성된 내용 단위로 표시: **QA01 종료**.
4. 필요한 자료 구성, 위임, 결과 수신과 상태 연결, 상세 결과 표시 등 해당 사용자 목표에 필요한 VIA 처리.
5. 해당 목표의 VIA 처리 종료: **QA03 종료**. 그 사이 외부 Agent 실행과 사용자 대기는 기존 정의대로 제외한다.

단순 `네`, `처리 중입니다`, 아직 식별하지 못한 `이것`을 그대로 반복하는 문장은 조기 응답으로 인정하지 않는다. 반면 실제로 제시한 구체적 응답이 틀렸다는 이유로 시간을 제거하거나 고정 벌점을 넣지도 않는다. 시간·정확도·미응답은 각각 보고한다.

### 이번 코드가 한 일

근거 공급·의미 판단·화면 지칭은 거의 모두 최종 모델 결과를 받은 뒤 `DISPLAY_PROXY`를 호출하고 곧바로 같은 결과로 `GOAL_COMPLETE`를 남겼다. 따라서 두 시간 차이는 수십~백수십 μs 수준의 로컬 기록 처리였다. 계산식 둘의 이름만 달랐던 것은 아니지만, 실제 서로 다른 사용자 사건을 충분히 구현하지 않았다. 현재 계산기는 표시 텍스트가 비었는지를 주로 확인하므로 요청문 반복까지 유효 첫 내용으로 통과할 수 있다.

또한 실제 브라우저 프레임 표시가 아니라 출력 callback을 쟀다. 실제 UI 표시 지연과는 구별해야 한다. 짧은 질문에 첫 응답 자체가 전체 답변인 경우 QA01과 QA03이 가까운 것은 정상이다. 모든 시나리오에서 차이를 강제로 만들지는 않는다.

업무 인계만 구체적인 목적 안내를 먼저 표시했지만, **목적을 이미 채택한 상태에서 시계를 시작**했다. 다른 DP의 사용자 입력 시점과 동일한 경계가 아니다. 새 비교에서는 모든 인계 안에 같은 실제 사용자 입력→목적 채택 경로를 포함하거나, 이 숫자를 명시적으로 후채택 부분 측정으로 한정해야 한다. 임의의 공통 상수를 더해 전체 QA로 만들지 않는다.

### 의미 판단에서 추가로 발견한 모집단 오류

[QA03 정의](../qa-candidate-package/qa03-via-processing-time.md)는 Agent 알림 자체를 새 사용자 목표로 세지 않는다. 그런데 현재 구현은 Q-MAIL-1 질문 표시를 새 `STIMULUS`와 `GOAL_COMPLETE`로 만들었고 약 0.004ms인 표시 3건이 A/B 평균에 포함됐다. 이 3건만 뺀 사후 평균은 A 13,102.27ms, B 10,723.76ms이지만, 이것만으로 정정·답변과 원래 목표의 인과 관계가 복구되지는 않는다. 정식 수정 QA03으로 대체하지 않는다.

## 3. QA04와 메모리

### QA04: 무엇을 실제로 바꿨는가

| 변경 과제 | 실제 변경 범위 | 한계 |
| --- | --- | --- |
| C01 모델 wire 형식 | `model_wire` 1개 모듈 | Rust↔Python 실행기 IPC 형식을 바꾼 모사. 실제 Qwen HTTP API나 모델 능력·출력 의미 변경 전체를 시험한 것은 아님 |
| C03 원본 형식 | crate root `main`과 `source_contract`, 2개 모듈 | 입력 JSON의 판본·좌표·수집 시각을 공통 진입점에서 정규화. 실제 화면 수집 API 전체 변경은 아님 |

평균은 **(1+2)/2 = 1.5개**이며 모든 안에서 같다. 두 과제를 합친 고유 파일 수가 3개일 뿐, C03이 3개라는 결과는 없다. 실제 diff와 계약 실행은 있지만 공통 adapter가 모두 흡수하는 과제이므로 기본 구조 간 차이를 충분히 관찰하지 못한다. 기존 여섯 변경 과제를 모두 수행한 결과도 아니다.

후속 비교에서는 기존 두 과제를 동점 대조군으로 유지하고, 기존 C04 부분 응답 갱신, C05 실제 전달 답변의 출처 조회, C06 범위별 철회 중 각 DP에 실질적으로 적용되는 기능 변경을 고른다. 적용 과제와 요구 결과를 구현 전에 고정하고, 같은 DP의 모든 안에 동일하게 적용한다. 수정 모듈 수가 여전히 같으면 동점이다. 차이를 얻으려고 모듈 경계를 재편하지 않는다.

### 메모리: 지금 분해 가능한 것과 불가능한 것

PID별 동시 RSS 표본으로 **합계가 최대였던 같은 시점의 프로세스별 기여**는 복원할 수 있다. 예를 들어 의미 판단 A의 39.092224MB는 PID 77370의 36.601856MB와 PID 77374의 2.490368MB다. B의 39.190528MB는 PID 77656의 36.716544MB와 PID 77662의 2.473984MB다. 각 프로세스의 서로 다른 시점 최대값을 더한 결과가 아니다.

당시 PID의 역할·PPID를 저장하지 않아 이를 Python/Rust라고 확정해서 붙이지 않는다. 대화 문맥, 이미지, JSON 직렬화, HTTP 버퍼, 중간 후보가 각각 몇 MB인지도 현재 자료로 분리할 수 없다. 원격 Qwen 가중치는 로컬 RAM에 들어 있지 않다. 브라우저와 외부 controller도 현재 합계에서 제외됐다.

최소 후속 계측은 PID 역할과 기본 런타임 RSS, 입력·상태·이미지·직렬화 버퍼의 논리 크기 및 생존 시점을 기록한다. **논리 객체 크기와 RSS는 다른 값**이므로 둘을 합치거나 RSS를 빈틈없이 설명한 것처럼 표시하지 않는다. 한 번의 공통 peak 시점 표와 기능 단계별 변화량을 함께 제공하고, UI를 포함할 경우 별도 항목으로 표시한다. 공유 page 중복과 짧은 프로세스의 표본 누락도 남긴다.

## 4. DP1 근거 공급

### 구조와 시간의 직관적인 설명

| 안 | 실제로 한 일 | 구조 때문에 생길 수 있는 손익 |
| --- | --- | --- |
| A 대화별 유지 문맥 | 앞서 읽은 근거를 유지하고 새 질문 판단에 사용 | 같은 자료의 후속 질문은 추가 원본 읽기·답변 단계를 줄일 수 있음. 주제 전환 때 남은 문맥 입력 비용이 있음 |
| B 요청별 근거 구성 | 최소 문맥에서 현재 질문에 필요한 원본을 골라 읽고 판단 | 매 질문의 근거가 좁고 명확하지만 같은 자료도 다시 구성할 수 있음 |
| C 관계 근거 생산과 게시 | 원본 변화 때 관계 기록을 생산하고 질문은 그 기록에서 시작 | 준비가 끝난 요청의 후속 단계를 줄일 수 있으나 준비와 긴 기록의 비용이 추가됨 |

이번 36개 요청 판단에서 A는 첫 판단 36회+추가 답변 27회, B는 36+33회였다. A가 절약한 6회는 모두 **같은 자료의 후속 질문 E1**이다. E1 지연 A 5.200초/B 6.876초에는 설명할 실제 단계 차이가 있다. 전체 평균 7.226초/7.589초의 작은 차이 전부가 구조 때문이라고 확정하지는 않는다. 다른 사례의 문맥 길이, 출력량과 서비스 변동도 섞였다.

C는 생산 33회+요청 첫 판단 36회+추가 답변 3회다. 준비 뒤 지연 6.958초는 생산이 끝난 조건의 값이며 생산 중 새 요청이 도착하는 조건은 시험하지 않았다. 현재 QA01과 QA03은 앞 절의 이유로 거의 같다.

### 정확도 결론

**A/B 36/36, C 32/36은 지칭한 원본 ID 집합과 지정 판본의 일치율이다.** C의 E4 오류 네 건은 두 원본을 가리켜야 하는데 과거 설명 자료를 추가하거나 대체한 실제 오류다. 그러나 A/B가 요청한 요약을 100% 제대로 제공했다는 뜻은 아니다.

새 감사에서 A/B E3 q2는 본문 근거 부족으로 직접 완료를 거부한 뒤에도 재조회 없이 최종 호출로 진행하는 결함이 확인됐다. 최종 출력의 source/version 선언만으로 채택됐고, 내용은 요청 표현의 반복이었다. C도 최신 본문을 읽은 뒤 실제 요약을 완성하지 못했다. 일부 다른 답변에서는 C가 실질적인 본문을 설명하고 A/B가 요청문만 반복했다. 따라서 지칭 정확도만으로 A/B의 완결 기능 정확도가 더 높다고 발표하면 안 된다.

현재 QA02 정의는 유지한다. 별도 기능 완료 검사에서 본문을 실제 활용했는지와 필요한 사실을 전달했는지를 판정한다. 평가용 정답은 후보에게 주지 않는다. host는 근거 부족·판본·사용 허용 계약을 지키고, 평가기는 별도 oracle로 내용의 성공을 확인한다.

### C 비용이 큰 이유

| 안 | 호출 수 | 입력 token | 출력 token | 전체 비용 USD |
| --- | ---: | ---: | ---: | ---: |
| A | 63 | 48,284 | 10,959 | 0.0368480 |
| B | 69 | 44,864 | 11,004 | 0.0355520 |
| C | 72 | 90,100 | 53,977 | 0.1224032 |

C는 A의 **3.32배**, B의 **3.44배**다. 호출 횟수만의 차이가 아니라 긴 관계 기록의 생산·입력 때문이다. C의 사전 생산만 $0.076316로 전체의 **62.35%**이고, 요청 경로도 $0.0460872로 A보다 비쌌다. 생산 API 구간 합계 710.429초는 요청 지연에서 제외되지만 비용에는 포함됐다. 질문이 소비하기 전에 다음 판본으로 교체된 중간 관계 생산비용도 포함한다. 모든 게시 구조가 항상 이 배수라는 일반 법칙은 아니다.

### A2 변경 조각 갱신

유효한 근거는 남기고 원본 변경에 영향을 받은 조각만 갱신해 재조회·모델 입력을 줄이려는 보완이다. 같은 E3 세 반복의 결과는 다음과 같다.

- QA01: **8.385→7.800초**, 약 585ms 감소. QA03도 거의 같은 변화.
- QA02: **6/6→6/6**. 별도 요약 내용 성공은 **0/3→0/3**.
- 비용: **$0.006036→$0.006170**, 2.22% 증가.
- 모델 호출: **12→12**, 실제 파일 읽기 **6→9**.

즉 기대했던 읽기·비용 절약은 확인되지 않았다. 기본안의 최신 본문 누락까지 있어 대칭적인 성능 비교로도 부족하다. A2를 유효한 QA 보완으로 채택한 상태가 아니며, 기본 기능을 고친 후 다시 판단해야 한다.

## 5. DP2 후속 입력의 의미 판단 실행

### A/B의 구조적 차이

A는 같은 대화 실행의 step 경계에서 후속 입력을 반영한다. 이미 끝난 앞 step의 미게시 판단을 활용할 수 있지만 후속 질문이 앞 단계의 대기를 부담한다. B는 요청별 실행을 분리하므로 여유 호출 슬롯이 있으면 겹쳐 처리한다. 대신 앞 요청의 판단을 어느 시점·어떤 조건으로 새 실행에 연결할지 관리해야 한다. B도 같은 원본 자료를 읽을 수 있다.

| 사례 | 상황 | 관측한 QA01 A / B | 해석 |
| --- | --- | --- | --- |
| E1 | 겹침 없는 순차 질문 | 5.889 / 8.805초 | 양쪽이 같은 직렬 경로와 문맥 구성 방식. 앞 모델의 반환 내용은 달라질 수 있음. 구조적 이익으로 세지 않음 |
| E2 | 긴 판단 중 별도 질문, 동시 호출 2개 | 11.739 / 6.070초 | B는 두 요청의 대기를 겹칠 수 있음. A는 앞 step 경계의 대기를 부담 |
| E3 | E2와 같은 입력, 동시 호출 1개 | 14.169 / 20.345초 | B도 실제 모델 동시 실행 불가. 문맥·출력 차이와 서비스 변동이 함께 있으며 약 6초 전부를 구조 비용으로 단정하지 않음 |
| E4 | 진행 요청 정정과 Agent 질문·답변이 겹침 | 13.582 / 2.313초 | B의 6개 빈 응답이 시간 평균에서 빠짐. B가 목표 전체를 이 시간에 끝냈다는 뜻이 아님 |

위 값은 현재 표시 proxy의 사례별 평균이며, E4에는 짧은 Agent 질문 표시도 있다. QA03의 목표 모집단 오류와 조기 응답 경로 누락을 고친 뒤 정식 비교를 다시 해야 한다.

특히 E3의 A도 기다린다. A는 enqueue 전 step 대기에 평균 11.184초를 쓰고, B는 enqueue 후 슬롯 대기에 평균 15.953초를 썼다. 양쪽 모두 실질적으로 앞 요청 뒤에 후속 요청을 직렬 처리한다. 모든 사례의 첫 R1 모델 request body는 A/B가 동일했고 그 반환 시간·출력에는 변동이 있었다. 따라서 B의 queue 시간만 추가 구조 비용으로 계산하면 틀린다. E2의 실제 호출 겹침은 구조적 원인이지만 E3의 평균 반전 크기는 이번 소수 반복으로 인과 확정할 수 없다.

### 정확도와 비용

이 DP에는 기존 **QA02 지칭 정확도는 적용되지 않는다.** 별도 관계 진단 N-R은 A/B 모두 **21/27, 77.78%**다. 혼합 발화 “기존 작업은 계속하고, 별도로 TCP/UDP를 설명해 달라”에 하나의 관계 label만 정답으로 강제한 계약이 부정확하다. 이 점수로 A/B 정확도 우열을 주장하지 않는다.

B의 정정 미응답 6건은 별개의 실제 실패다. A의 앞 판단 문맥 재사용과 B의 요청별 문맥 연결 차이가 실패를 이해할 단서지만, 현재 출력 계약·검증·복구가 부족한 상태에서 분리 구조의 본질적 정확도 열세라고 결론내릴 수 없다.

전체 모델 호출은 **양쪽 30회**, 비용은 A **$0.0528276**, B **$0.0535072**다. 시간은 기다리는 구간을 겹칠 수 있는지에 민감하고, 비용은 호출한 입력·출력 토큰 총량에 따른다. 병행했다고 호출 자체가 사라지지는 않는다. B의 null 호출 비용도 전부 포함했다.

### 누락된 6건의 실제 시간

| 반환 종류 | 건수 | 원래 해당 입력부터 실제 반환까지 평균 |
| --- | ---: | ---: |

사용자의 판단대로 **복구까지 포함해도 B가 빠르고 필요한 정확도를 만족한다면 B를 선택할 수 있다.** 현재의 A 선택은 최종 선택으로 유지하지 않는다.

### 현재 보완과 필요한 보완

실험한 것은 **A1 제한된 별도 질문**이다. 도구가 필요 없는 짧은 독립 질문이면 작은 별도 응답을 만들고 실제 전달 이력에 반영한다. 그 조건을 벗어나면 A의 본 실행으로 돌아간다.

| E2 세 반복 | 기본 A | A1 |
| --- | ---: | ---: |
| 전체 응답 평균 | 11.739초 | 7.553초 |

원래 요청은 한 반복에서 8.740→14.513초로 느려졌다. N-R 상승은 혼합 발화 label 진단이며 일반 정확도 향상으로 쓰지 않는다. A1은 **B 정정 실패를 고치는 보완이 아니다.**

기존 B1은 불변 문맥 참조 공유로 로컬 buffer를 줄이는 안, B2는 같은 총 호출 한도 안에서 foreground 여유를 예약하는 안이다. 둘 다 이번에 실행하지 않았고 B 정확도 개선 수치도 없다.

우선 null을 유효 응답처럼 끝내지 않는 검증, 정정이 참조하는 요청·revision·수정 조건의 전달, 목표별 재판단과 종료 조건은 기본 기능으로 고쳐야 한다. 선택 보완은 그 뒤에 판단한다. 예를 들어 관련 판단 상태를 요청 실행에서 가져와 정정에 필요한 좁은 문맥을 공급하는 방안은 추가 후보가 될 수 있으나, 별도 B3 등을 확정하거나 수치 개선을 주장한 상태는 아니다. 복구 비용·시간을 모두 넣어 A/B를 다시 비교한다.

## 6. DP3 화면과 발화의 지칭 결합

### 시간·비용의 원인

A는 화면·발화·관측 기록을 한 번에 판단했다. B는 화면 후보 생산, 발화 의미 생산, 필요한 경우 최종 결합을 순서대로 했다.

| 항목 | A | B |
| --- | ---: | ---: |
| 호출 | 공동 판단 15회 | 화면 15 + 발화 15 + 모델 결합 9 = 39회 |
| 출력 token | 4,358 | 19,556 |
| 평균 표시 지연 | 5.710초 | 23.786초 |
| 총 비용 | $0.0155436 | $0.0458792 |

B 화면 생산이 **$0.030336, 전체 비용의 66.1%**다. 전체 15 revision으로 각 단계의 API 구간 합계를 나누면 화면 약 15.901초, 발화 4.352초, 결합 3.518초다. 결합 3.518초에는 code 결합으로 모델을 호출하지 않은 6 revision도 분모에 포함하며, 실제 9회 결합 API 호출 자체의 평균은 5.863초다. 이번 큰 차이는 추가 생산·긴 후보 출력, 기본 구현의 초기 순차 실행 정책과 생산→결합 의존에 있다. 화면과 발화 생산 사이에 필수 선후 의존이 있는 것은 아니다. 실제 원본 확장·재조회는 0회여서 이를 원인으로 설명하면 틀린다. cloud 내부 추론과 network 시간의 세부 인과는 분리하지 못한다.

### 62.5%가 된 구체적인 이유

| 장면 | A/B 지칭 성공 | 실제 문제 |
| --- | --- | --- |
| 밀집 카드 | 양쪽 0/6 | 숫자 pointer 좌표를 다른 카드와 연결. B는 자신의 bbox와 pointer가 모순돼도 잘못된 관계를 채택 |
| 그래프에서 자유 범위 | 양쪽 0/3 | A는 바깥 점 포함·안쪽 점 누락. B는 발화에서 세 점을 요구한다고 생산하고도 최종 결합이 여섯 점 채택 |
| 페이지 이동 | 양쪽 3/3 | 이전 시점 화면을 보존해 연결 |
| 부분 정정 | 양쪽 12/12 | 정정 범위와 revision을 반영 |

합계는 **15/24**다. 글자가 심하게 뭉개진 PNG였다는 증거는 없다. 이번 난점은 별도 숫자로 보낸 pointer/loop와 이미지 위치의 대응이었다. B의 producer 기하 모순과 최종 count 검증 누락은 구체적인 구현 문제이며, 분리 구조에서 피할 수 없는 오류가 아니다. 같은 명시 제약은 A에도 적용할 수 있어야 한다.

### B가 유리할 수 있는 부분

- **QA02:** 정확한 화면 생산자가 명시적인 위치·영역·관계를 제공하고 최종 결합이 그 제약을 검사하면 시각 혼동을 줄일 가능성. 이번 범용 Qwen 생산자로는 입증하지 못함.
- **QA03/05:** 이미 만든 충분한 후보가 같은 판단의 반복 결합을 실제로 대체하거나 더 저렴한 native/code 생산 경로가 있는 조건. 이번 A도 여러 지칭을 한 호출로 처리해 B 이익 없음. 다른 입력 사이 cache는 별도 B1로 평가.
- **QA04:** 화면 형식 변화가 producer 내부에 머물 때 수정 범위를 줄일 가능성. 현재 공통 adapter 두 과제로는 확인하지 못함.
- **QA01/06:** 첫 화면의 추가 생산 대기와 중간 상태 때문에 불리할 수 있다. 현재 수치에서 B의 우위를 주장할 근거 없음.

따라서 **현재 BASIC에는 B가 더 좋은 것으로 입증된 QA가 없다.** 전용 parser를 실제로 쓴 결과도 아니다. 기능 계약을 고치고도 반대편 이익이 없다면 이 비교의 trade-off 증거가 부족하다고 보고해야 한다. 강한 경쟁안을 확보했다는 표현만으로 메우지 않는다.

### 보완 번호와 수치

번호는 독립 후보이며 자동 누적하지 않는다. 각 안에 네 가지씩 있다.

| 번호 | A의 보완 | B의 보완 |
| --- | --- | --- |
| 1 | 유효 crop/cache로 반복 읽기 절약 | 새 입력 사이 유효 후보 재사용 |
| 2 | 영향 범위만 binding 재판단 | 영향받은 producer·binding만 재생산 |

## 7. DP4 Agent 간 업무 인계

### 0.02ms와 18ms가 측정한 것

QA01은 약 **0.02ms**이며 0.2ms도, 자연어 요청을 이해한 시간도 아니다. 이미 목표·조건·수신자가 채택된 입력을 문장으로 만들어 표시 callback을 호출한 시간이다. 사용자 첫 응답의 충분한 측정으로 쓰지 않는다.

QA03 C의 **18.25ms**는 그 이후 자료 목록, 접근 범위 확인, 읽기 제공과 결과 연결 등 VIA 로컬 처리 구간이다. 수신자 API 구간은 제외했다. A/B는 VIA에서 의미 가공 모델을 호출하므로 약 8.826/12.545초가 포함된다. 이 평균에는 무위임 목표도 있어 실제 인계 18건의 전체 시간과 분모도 다르다.

### C는 어떤 구조인가

C는 필수 목표·조건·금지 범위와 접근 가능한 자료 목록을 수신 Agent에 주고, 수신자가 필요한 원본 범위를 요청하도록 한다. VIA는 허용 범위와 현재 판본을 검사해 자료를 제공하고 결과를 대화·Task에 연결한다. 이번 C는 수신자 자료 선택과 결과 생성 **36회**의 실제 모델 호출을 했다.

| 12 episode 비용 / 실제 인계 18건 평균 시간 | A 목적별 묶음 | B 지속 기록 | C 수신자 읽기 |
| --- | ---: | ---: | ---: |
| VIA 모델 비용 | $0.0256812 | $0.1629320 | $0 |
| 수신자 모델 비용 | $0.0298096 | $0.0310880 | $0.0383716 |
| 합계 | $0.0554908 | $0.1940200 | $0.0383716 |
| 채택 후 상세 결과까지 실제 전체 시간 | 22.788초 | 27.885초 | 15.358초 |
| 그중 수신자 API 구간 | 12.491초 | 13.249초 | 15.336초 |

**C의 모델 비용이 0인 것은 VIA 역할 부분뿐이다.** 비용·처리가 수신자에게 이동했으며 코드·I/O·RAM도 남는다. 이번 읽기 도구 지원 수신자에서는 실제 동작했지만 상용 Agent마다 이 도구와 권한·판본 계약을 지원하는지는 별도다. 이미 채택한 조건을 공통 입력으로 준 작은 Qwen 수신자 시험이며 상용 Agent 연결 검증은 아니다.

### A/B의 기본 경로도 보완 검토가 필요하다

A는 원본 선택 후 별도 구성 호출을 항상 수행한다. 유효 source-span 참조 표현은 있지만, 이미 확보한 근거나 참조만으로 인계 조건을 만족할 때 별도 구성을 생략하는 경로가 없다. 두 호출이 모든 A의 필수 비용이라는 결론은 과하다.

B는 준비 기록을 실제 읽었지만 18/18건에서 원본을 다시 읽고 구성 호출까지 수행했다. 준비만 **51회, $0.117164**여서 중복 가공이 컸다. 기본 문서가 허용한 충분한 기록의 직접 추출이 실제로 동작하는지, 기록이 부족했는지 또는 prompt가 재읽기를 유도했는지 확인해야 한다. 이를 확인하는 일은 모든 cache·batching을 기본안에 추가하는 것과 다르다.

C가 이번 구현에서는 유리했지만, 일반적인 A/B/C 최종 선택은 위 기본 경로와 동일 시작점 보완 후 판단한다.

### 보완 후보

| 안 | 보완 1 | 보완 2 |
| --- | --- | --- |
| A | 같은 목적·조건·판본의 인계 묶음 cache | 같은 Agent의 검증된 native session 재사용 |
| B | 여러 변화의 업무 기록 생산을 묶음 | 변경 영향을 받은 기록 조각만 갱신 |
| C | 특정 원본의 사전 읽기 | 허용된 같은 판본·범위의 읽기 결과 cache |

실험한 C2는 실제 파일 읽기 **18→6**, cache hit 12회다. 그러나 QA03은 **20.73→24.37ms**이고 수신자 호출은 같았다. 공통 읽기 제공 구간만 약 **1.591→1.466ms**로 0.124ms 감소했다. 저장·권한 검증 비용을 포함한 전체 QA 개선은 없어 기본 적용을 보류한다.

## 8. 최소 보완·재실험 제안

제품 전체를 구현하거나 음성 모델을 붙일 필요는 없다. **지금 문제는 표본 수보다 측정 경계와 기본 기능의 누락**이다. 단순히 같은 실행을 많이 반복하면 해결되지 않는다.

### 1단계: 새 호출 전 수정할 계약과 기록

1. 같은 사용자 입력부터 실제 채택·조기 내용 표시·목표별 완료를 구별한다. UI 표시를 실제 계측하거나 callback proxy로 명확히 한정한다. 화면 후보/답변 텍스트만 생성한 시간을 완결 기능 완료로 부르지 않는다.
2. Agent 알림은 관련 사용자 목표에 연결하고 정정은 원래 목표의 revision으로 연결한다. 새 독립 요청은 별도 목표다. 여러 의도는 하나의 label로 억지 채점하지 않는다. 기존 oracle 변경은 별도 버전·이유를 남긴다.
3. 근거 부족 재조회, 정정 입력과 문맥 전달, 명시 개수·좌표 범위의 모순 검사, 유효 출력 형태·충분한 출력 용량을 기본 기능으로 수정한다. 필요한 재조회·수정·실패와 모든 비용은 기록한다. 정답을 후보에 주입하지 않는다.
4. 인계 A의 충분한 참조·기확보 근거 경로와 B의 충분한 기록 직접 사용을 명확히 한다. 준비, 요청 경로, 수신자 경로의 시간·비용을 각각 기록한다.
5. PID 역할과 메모리 단계 기록을 추가하고, QA04에서 실제 기능 변경 과제를 사전에 고정한다.

각 DP의 VIA 완료 범위는 유지한다. 예를 들어 화면 지칭은 현재 revision의 지칭 집합을 채택하고 표시하는 기능이며, 자료의 업무 비교·분석까지 VIA가 실행하도록 늘리지 않는다. 실제 채택·표시 시간과 지칭 정확도는 별도 보고한다.

### 2단계: 기본안 전체를 같은 새 계약으로 비교

**기존 네 episode × 세 반복 × 열 개 기본안 = 120회**를 새 freeze에서 다시 비교하는 것이 가장 단순하다. 실패 사례를 빼거나 불리했던 안만 바꿔 기존 상대 수치와 붙이지 않는다. 실행 순서를 교차하고 모든 반복을 보존한다. C의 준비가 완료된 경우와 준비 중 요청이 들어오는 경우는 조건을 구별한다.

기능 오류가 고쳐지기 전에는 전체 비용을 쓰지 않도록 적은 입력으로 smoke를 먼저 수행한다. 이 smoke는 공식 결과에 섞지 않는다. 실제 모델 호출 수·추가 비용은 수정된 경로에 따라 달라지므로 지금 개선값이나 예산 소진액을 확정하지 않는다.

### 3단계: 선택 후 필요한 보완만 추가

- 의미 판단 B의 기본 정정 처리·복구를 포함한 A/B 비교를 먼저 한다. 이후 실제 약점에 맞는 B 보완을 선택한다. A1 수치로 B 정확도 개선을 대신하지 않는다.
- 화면은 dense/free의 좌표 대응과 최종 제약을 먼저 바로잡고 A/B를 비교한다. A4 출력 용량과 B4 병행은 각각 별도 보완·진단으로 남긴다. 전용 parser를 실제로 쓰지 않으면 범용 Qwen 생산자라는 결론 범위를 유지한다.
- 근거 A2와 인계 C2는 약점이 실제로 확인되고 기능 경로가 정상화된 뒤 해당 사례만 다시 본다. 모든 보완을 동시에 넣은 A/B/C로 바꾸지 않는다.
- QA04 실제 기능 변경과 메모리 분해는 대부분 고정 응답기·replay로 할 수 있어 추가 의미 모델 비용을 최소화한다. replay의 지연을 새 실제 API 지연이라고 표시하지 않는다.

### 결과물과 완료 기준

1. QA별 시작·종료·분모와 단계별 시간·비용·메모리 표.
2. 열 개 기본안의 같은 입력 비교: 실제 오답 시간, 미응답/미완료, 회복·폐기 비용 포함. 타임아웃 벌점이나 결측 성공시간 추정 없음.
3. 각 관측 차이에 대응하는 실제 호출·읽기·상태·대기 차이. 같은 코드 경로의 cloud 변동은 구조 이익으로 세지 않음.
4. 선택안과 보완 전후. 개선이 확인되지 않으면 미채택, 반대편 이익이 없으면 trade-off 미확인으로 기록.

이 문서는 사용자 리뷰에 대한 감사와 다음 실행 제안이다. 이번 검토에서 새 모델 호출, 새 freeze 실행, 원시 결과 덮어쓰기, 최종 ADR 변경이나 외부 발행은 하지 않았다.
