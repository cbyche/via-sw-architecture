# 보완 PoC 실행 전 검토 기록

2026-10-18 / 사용자 리뷰에 따른 구현·계측 보완 / calibration 진행, 본 비교 전

[현재 계약](../14-corrected-poc-contract.md)과 `benchmark/architecture/four_dp_poc_v2/CONTRACT.md`를 기준으로 검토한다. 이전 결과의 기능 누락이나 계산 오류를 새 결과의 성공으로 대체하지 않는다. 기존 원시 기록과 별도로 새 generation을 실행한다.

## 1. 역할과 검토 범위

계획·계약·통합 설명은 주 담당, 코드 개발과 실행은 사용자가 지정한 GPT-6.1 Sol High 담당 세 명이 수행한다. 런타임 담당은 공통 계측과 DP02, 근거·인계 담당은 DP01/05, 화면 담당은 DP04를 소유한다. 화면 담당이 DP02·모집단 계약을 교차 검토하고, 런타임 담당이 화면의 채택 검사를 검토한다. 주 담당은 공통 코드와 각 실행 경로를 읽고 경계·실패·재사용·비용·freeze를 검토한다.

이 단계의 deterministic 응답기 검사는 실제 Rust 코드의 계약과 분기를 검사한다. Qwen의 의미 정확도나 응답 시간 측정으로 쓰지 않는다.

## 2. 확인 및 수정 사항

| 검토 사항 | 조치와 남는 범위 |
| --- | --- |
| 빈 결과를 완료로 취급하는 경로 | 공통 완료 검사는 비어 있지 않은 실제 내용과 후보별 계약 검사 완료를 요구한다. 각 의미 단계는 최초 시도와 한 번의 복구 후 실패를 명시한다. |
| 정정 후 원래 목표 시작 시각 소실 | 최초 실제 입력 시각을 유지한다. 화면 첫 revision 실패 뒤 다음 revision 성공에도 최초 시각이 보존되는 별도 검사를 추가했다. |
| Agent 질문을 새 목표로 계산 | 질문은 표시 응답 모집단에만 포함한다. 사용자 답변을 기존 Task에 실제 전달하는 구간은 별도 이름의 하위 목표이며 전체 메일 업무 완료라고 표시하지 않는다. |
| 모델의 원본 판본 주장 | DP02도 실제 제공한 원본 ID·판본과 대조한다. shape 검사만 통과한 값을 곧바로 resolved로 표시하지 않는다. |
| 근거 없는 직접 완료 | DP01은 실제 본문과 출처 검사를 요구한다. 부족한데 읽기 목록도 없으면 현재 선택한 대상의 원본 보완 또는 한정된 선택 복구를 수행한다. |
| 인계 A/B의 불필요한 재가공 | A의 유효 참조와 기확보 근거, B의 충분한 생산 기록을 직접 사용할 수 있게 했다. 모든 인계에 compose 호출을 강제하지 않는다. |
| 화면 producer 자신의 개수 주장만 검사 | 지원하는 명시 숫자 표현을 실제 발화에서도 읽어 A/B의 채택 대상 수와 대조한다. 지원 밖 표현과 대상의 의미 정답은 모델·별도 평가에 남는다. |
| 화면 좌표 검증 범위 | 실제 frame 범위, point와 bbox, circle 영역과 대상 중심, 후보·binding 일관성을 검사한다. 잘못 생산한 bbox가 모순 없이 통과할 가능성을 정확도 보장이라고 숨기지 않는다. |
| 무관한 병렬 목표의 외부 시간을 차감 | 목표별 인과 범위와 제외 구간을 요구한다. 정확한 DAG를 만들 수 없는 경우 추정치를 정밀한 값처럼 제시하지 않는다. 외부 실행이 없는 목표는 실제 입력→종료 경과시간을 유지한다. |
| 메모리 기준과 역할 | 매 trial 새 Python/Rust, 동일 시각의 역할별 RSS, 같은 실행의 초기 기준과 peak를 사용한다. 기록용 event/call buffer는 실험 장치 비용으로 구별한다. |
| source와 binary의 freeze | 실행 전 binary를 복사·해시하고 매 trial 전후 해시를 확인한다. harness·fixture·oracle도 freeze 대상이며 QA04 변경은 독립 scratch에 둔다. |
| 누적 비용 한도 | calibration/basic/tactic가 다른 freeze를 사용하더라도 동일 campaign $4 원장을 공유해야 한다. 실패·준비·수신자 호출도 포함한다. |
| 설계 문서의 오래된 선택 문장 | 01/02/04/05의 진입 설명을 정정했다. 초기 선택을 최종 결론으로 읽지 않도록 현재 보완 계약에 연결한다. |

## 3. 작은 실제 calibration의 허용 범위

다음 12 episode 실행을 별도 `CALIBRATION`으로 승인한다. 본 비교의 120회에 합산하지 않는다.

- DP01 E3의 A/B/C: 변경된 실제 본문 보완과 출력 내용 계약.
- DP02 E4의 A/B: 정정, 기존 Agent 질문의 답변 연결, 원래 목표 완료.
- DP04 dense/free의 A/B: 좌표 표현, 출력 용량, 기하·개수 검사와 복구.
- DP05 E3의 A/B/C: 유효 근거 직접 사용과 실제 수신자 읽기.

원시 입력·응답·검사 실패·비용을 보존한다. 출력 계약이나 실행 결함을 고치면 이유와 전후 코드를 남긴 뒤 본 비교를 동결한다. 같은 개발 사례로 계약을 확인하는 것이므로 blind holdout이나 일반 사용자 평가라고 표현하지 않는다.

## 4. 본 비교를 시작할 조건

1. 예정 입력과 목표의 고정 목록을 evaluator에서 읽고, 사건이 누락되어도 분모를 보존한다.
2. 진행 안내와 최종 완료의 실제 callback, 실패 및 실제 복구 시간이 별도로 계산된다.
3. calibration의 프로토콜·계측 오류를 정리하고 미해결 의미 실패는 그대로 공개한다.
4. source, binary, harness, fixture, oracle, 출력 상한과 복구 한도를 동결한다.
5. QA04의 실제 모듈 registry와 독립 기능 확장 과제를 동결한다.

이 문서는 실행 전 검토다. 실제 수치와 최종 검토 상태는 후속 결과 보고서에서 확인한다.

## 5. Calibration 중 확인한 계약 수정

### DP01 출처 statement와 표시 문장의 불필요한 중복 일치 요구

첫 `calibration-v1`의 DP01 E3 A에서 q1의 최초 상세 제안과 한 번의 복구 제안이 모두 거절됐다. 실제 제안은 가격·유지보수 비교 기준과 받아둔 견적을 요약했고, 여섯 출처 quote는 실제 제공한 현재 원본의 해당 줄에 있었다. 거절 사유 다섯 개는 `facts.statement`의 원문 문장이 바꾸어 쓴 `text`에 그대로 들어 있지 않다는 검사였다. 이 거절을 지칭이나 내용의 의미 오류로 분류하지 않는다.

공통 A/B/C의 계약에서 이 문자열 중복 조건을 제거한다. 실제 공급된 quote·줄 범위·판본·대상별 근거와 비어 있지 않은 본문, 원문/지칭 표현만의 반복 거부는 유지한다. `facts`는 본문과 함께 반환한 출처 claim 메타데이터이며, quote 일치가 본문의 의미적 함의까지 증명하지 않는다. 최종 본문이 목표를 충족했는지는 사전에 작성한 evaluator-only 내용 조건으로 따로 평가한다.

v1의 실패, 시간, 비용과 동결본을 보존한다. 수정은 별도 동결본에서 실제 DP01 E3 A/B/C 세 번을 재확인한다. 이 세 번도 calibration이며 BASIC에 합산하지 않는다.

같은 수정에서 최근 전달 답변의 재사용 자료도 검토한다. 실제 표시하지 않은 `facts.statement`를 전달문으로 재사용하지 않는다. 최근 답변에는 실제 표시한 `text`와 그 출처를 보존하고, 파생된 전달 기록임을 표시한다. 그 기록에 대한 quote는 실제 표시문 안에 있어야 하며 원본 문서 quote와 구별한다.

### DP02 정정 복구와 채택 단계

E4 B에서 본문은 반환됐지만 실제 공급 원문에 없는 생략 인용과 사용자 입력 ID를 문서 출처로 쓴 주장이 거절됐다. 이후 재개 분기가 이미 실패한 같은 revision을 다시 실행했다. 이 세 번째 상세 호출은 정한 복구 한도를 벗어난 host 버그다. 이전 revision이 실제 완료된 뒤 정정으로 다시 열린 경우와 현재 revision 복구 소진을 구별하도록 고친다. 실제 잘못된 quote·ID와 실패 이유를 공통 복구 입력에 포함하며 원시 실패와 추가 비용은 유지한다.

A의 U2 해석은 나중에 수신한 U3 원문까지 읽고 U3의 답변 의도를 U2에 덧붙였다. 해당 입력까지의 captured 원문과 현재 발화의 해석 범위를 명시한다. 전체 미해석 입력은 여전히 상태에 남고, 그 관계가 해소되기 전 결과 게시 보류도 유지한다.

기존 의미 채택 호출의 출력 역할도 공통 A/B에 구체화한다. 상세한 다항목 비교는 대상·관계·수행 의도를 먼저 채택하고 실제 상세 생성 단계로 진행한다. 요청을 짧은 직접 답으로 완결할 수 있으면 기존 한 번의 호출 경로를 유지한다. 첫 응답과 완료의 차이를 만들기 위한 무조건적인 추가 호출이나 긴 답변의 임의 절단은 하지 않는다.

### DP04 기하 검사의 누락과 채택 메타데이터

v1 dense/free 한 번씩에서 A/B의 최초 채택 집합은 각각 dense 2/2, free 1/1이었다. 이는 calibration 관측이며 BASIC 정확도에 합산하지 않는다. 잘린 출력은 없었다. A dense의 최초 bbox 모순은 복구 뒤 채택됐다.

올바른 대상과 별개로 A free가 `point_inside`와 `pointer_path`를 함께 내어 region 검사 분기를 통과하지 않는 누락이 있었다. 관계와 실제 cue 종류가 맞지 않으면 검사를 생략하지 않고 복구·미해결 경로로 처리하도록 한다. B의 검증된 count/cue가 최종 채택 메타데이터에서 사라지는 직렬화 문제도 고친다. 사용자에게 표시하는 수행 의도는 실제 비교·평균 등 사용자의 목적을 표현하며 내부의 `Bind` 작업 이름을 그대로 안내하지 않는다.

따라서 다음 `calibration-v2`는 DP01 E3 A/B/C, DP02 E4 A/B, DP04 dense/free A/B의 총 9회를 별도 동결본에서 확인한다. 추가 호출도 같은 $4 원장에 포함한다.

### DP05 공통 출처 계약과 실제 수신자 내용

DP05도 같은 완료 검사를 사용했으므로 E3 A에서 유효 인계 자료로 만든 직접 답변이 문자열 중복 조건 때문에 거절되어 읽기·복구 비용이 커졌다. 같은 guard 수정의 실제 수신자 경로를 확인하기 위해 E3 A/B/C 세 회를 v2에 추가한다. 따라서 **v2는 v1과 같은 12개 episode 실행**이다.

일부 미표시 초안에는 유지보수 우선 조건을 가격 동률 밖으로 넓힌 표현도 있었다. 이것은 위 문자열 검사 오류와 별개의 의미 문제다. 최종 게시 본문과 `constraints_respected` 같은 모델의 자기 주장을 구분하여 검토한다. 인계 명세의 필수 조건 보존 검사 N-H를 수신자 문안 전체의 정확도로 표현하지 않는다.

### 의도와 결과의 평가 자료

N-R은 발화별 relation/target/question/task의 다중 의도 집합 전체를 비교한다. 기대한 의도만 찾고 잘못 추가된 의도를 무시하지 않는다. 기존 단일 label 문제와 구별하며 QA02로 이름을 바꾸지 않는다. 내용 검사는 실제 최종 `GOAL_COMPLETE`의 출력으로도 복구하고, 후속 오류로 episode의 보조 결과 배열이 없어져도 이미 표시한 내용을 잃지 않는다. 사용한 oracle와 목표 목록은 해당 phase의 동결본을 읽는다.

첫 calibration의 실제 실행은 **12/12, Qwen 77호출, 고정 단가 환산 $0.1385664**다. 이 값은 BASIC 성능 표에 들어가지 않으며 모든 실패·추가 호출을 포함한 개발 확인 비용으로 보존한다.

### 짧은 실제 원문 인용

실행 전 추가 검토에서 원문 quote를 최소 세 문자로 제한한 검사가 `8W` 같은 짧은 실제 값을 거절할 수 있음을 확인했다. 빈 quote는 거절하되, 비어 있지 않은 quote는 실제 공급한 현재 원본과 범위 안의 일치 여부로 검사하도록 공통 A/B/C에 수정한다. 실제로 관측한 모델 실패를 고친 사례가 아니라 사전 계약 결함의 수정이다. 두 문자 유효 인용과 빈 인용 거절을 회귀 검사한다. 짧든 길든 인용 일치만으로 최종 요약의 의미적 정확도를 보장하지 않는다.

### 화면의 시각 오류와 관계 표현 계약 실패

calibration-v2의 dense A는 실제 포인터 y=315가 자신이 반환한 bbox의 y=380 이상 구간 안이라고 주장했다. 한 번의 재판단에도 모순이 남았으므로 기하 검사가 정상 거절했다. 두 응답은 정상 종료했고 출력 한도 이내였다. 이는 실제 지칭 채택 실패로 남긴다.

같은 phase의 free A는 제안 대상 집합 P3/P4/P5가 맞았지만, 원형 경로를 `point_inside` 관계로 표현했다. 현재 코드 계약은 이 이름을 포인터가 대상 bbox 안에 있는 경우에만 허용하며, 원형 경로는 `within_region`을 요구한다. 따라서 채택 실패와 미완료를 보존하되 시각 대상을 틀린 사례로 설명하지 않는다. prompt가 enum과 loop geometry를 설명하면서도 enum과 사건 종류의 대응을 명시하지 않은 모호함이 있어, 본 비교 전에 공통 인터페이스 의미를 명시하는 최소 정정을 검토한다. 정답 대상이나 사례별 힌트를 추가하지 않는다.

최소 정정은 공통 관계 정의를 각 역할의 호출에 한 번만 제공하는 방식으로 승인했다. 반복 피드백에는 실제 실패 이유와 수정 지침만 붙인다. 검사 조건, 출력 schema와 상한, 복구 횟수, 원본과 정답은 바꾸지 않는다. 별도 `calibration-v3`에서 free A/B 각 한 번만 확인하며, 이후 의미 성적을 높이기 위한 추가 prompt 조정 없이 본 비교를 진행한다.

calibration-v2는 **12/12, 실제 Qwen 66호출, $0.1087512**로 종료됐다. 첫 phase까지 새 campaign의 확인 비용은 **143호출, $0.2473176**이다. 이 phase의 실패는 성공한 이전 실행으로 대체하지 않는다.

### 내용의 누락과 동등한 단위 표기

DP01 E3의 실제 여섯 답변을 대조하니 A/B의 정정 뒤 답변은 납기 날짜를 빠뜨렸고, C는 유지보수를 `36-month`로 표현하여 기존 `36months` 문자열 검사에서 실패했다. 기존 literal 결과 2/6은 보존한다. 일반적인 월 단위와 영어 날짜 표기만 정규화하는 별도 평가기의 결과는 4/6이며, 실제 날짜 누락은 여전히 실패다. 36과 136, 1일과 11일, 월·일 혼동과 잘못된 날짜의 경계 검사를 통과했다.

이 평가기는 DP01/05의 유한 내용 조건에만 사용하고 원본 literal 결과와 함께 보고한다. DP02의 필수 goal revision과 receipt 검사는 기존 전용 평가기를 유지한다. 독립 담당자가 실제 여섯 본문에 다시 적용해 같은 결과를 확인했다. 후보가 읽는 정답이나 입력을 바꾸지 않았으며, 본 비교에서 사용할 외부 평가기 파일과 hash도 동결한다.

## 6. 본 비교 실행 승인

주 담당은 다음 순서로 본 비교 120회를 실행하도록 승인했다. 사용자에게 이미 받은 구현·테스트 승인 안에서 수행하며 추가 확인을 요구하지 않는다.

1. calibration-v1/v2의 원시와 실패를 보존한다.
2. 공통 relation 정의의 최소 정정 후 기존 기하 guard 11개, A/B 경로 18개와 60개 mock payload의 계약 중복 여부를 검사했다. 모두 통과했으며 guard/schema/cap과 복구 한도는 유지했다.
3. 별도 calibration-v3에서 free A/B 각 한 회를 실행한다. 모델 의미 실패를 다시 고쳐 통과시키는 것을 시작 요건으로 삼지 않는다.
4. 최종 source/binary/fixture/oracle/추가 내용 평가기와 QA04 적용 과제를 고정하고, 예정 120개 키와 QA01 261/QA03 243 분모를 확인한다.
5. 같은 campaign $4 원장으로 기본 실행을 시작한다. 한 번에 하나의 episode만 실행하고 구조 내부의 동시성만 허용한다. 무거운 기능 확장 compile/test는 기본 실행 전에 끝낸다.

본 비교 이후 prompt나 입력을 고쳐 유리한 이전 결과와 섞지 않는다. 측정 오류가 발견되면 원시를 보존하고 계산기 수정 이유와 버전을 남긴다. 실제 의미 실패와 미완료는 그대로 비교 결과가 된다.

### 최종 동결과 기본 실행 시작

calibration-v3는 free A/B 두 회, 각 두 호출로 완료했다. A는 관계 이름을 올바르게 사용했으나 잘못된 시각 좌표를 반환했고, 재판단에서는 요구한 세 대상 중 하나를 빠뜨려 미완료였다. B는 세 대상을 채택했다. 두 phase의 성공 사례를 골라 기본 비교로 합치지 않는다. 본 실행 전 새 campaign 누적은 **147호출, $0.2531908**이다.

`basic-v1`의 120회 실행을 시작했다. freeze SHA-256은 `50e4116e1fa86807c19abecac6586110e88968087542eececcfc4e379a7cecf2`, binary는 `8229089b04b66231f58cbb44b35c12950735cfbbad83dfe03993d5d34cd773e9`다. 운영 모듈 registry, 네 과제 QA04 집계, 추가 내용 평가기와 수신자 문안 검토 기준이 포함됐다. QA04 검사 기준 candidate와 최종 candidate의 27개 파일 및 binary는 동일함을 별도로 확인했다. 기본 실행 중에는 후보 수정과 추가 모델 튜닝, 무거운 기능 확장 빌드를 하지 않는다.
