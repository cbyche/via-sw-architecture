## 3. 실제 PNG 검토와 수정

네 번 생성하면서 PNG를 총 17회 열었다. 첫 세 차례의 3회, 6회, 6회 검토 뒤, 마지막 갱신 화살표가 바뀐 문제 01 A와 문제 05 B를 각각 다시 열었다. 최종 파일 6개 모두 실제 화면에서 확인했다.

1. 보완 기법 한 덩어리를 두 상자로 나누고 실제 추가 비용을 함께 표시했다. 기본의 원본 보완, 권한 확인, artifact 참조를 선택적 보완으로 옮기지 않았다.
2. 문제 05는 4번 계약 확정, 5번 실제 송신 등록, 이후 외부 수신/수행 사실을 구분했다. A/B의 결과가 외부 Agent를 거쳐 돌아오는 화살표로 수정했다.
3. 문제 05 C는 manifest 전송 뒤 수신자의 읽기 요청이 있어야 6번 serving으로 들어가는 순서를 확인했다. 외부 비용 이동과 QA03 종료 이후의 serving을 기본 이익으로 계산하지 않는 문구를 확인했다.
4. 긴 영문 명칭이 든 줄을 나눠 줄당 길이를 제한했다. 주요 Component 이름은 유지했다.
5. 문제 01 A의 6번에서 지속 view로, 문제 05 B의 6번에서 지속 업무 기록으로 돌아가는 외곽 갱신 화살표를 추가했다. 최종 PNG에서 화살표가 본문 글자를 가리지 않음을 확인했다.
6. 그림의 A1/A2, B1/B2, C1/C2와 두 본문의 보완 기법 표를 일치시켰다. 서로 다른 기본안과 A+C 또는 B+C의 구조 조합을 작은 보완 기법으로 표시하지 않았다.

최종 시각 검토 범위에서 잘린 문자, 상자 겹침, 본문 글자를 가리는 연결선은 발견하지 못했다. 원본 참조, 삭제/철회, 실패/복구, 조건부 모델 호출, VIA 채택 또는 외부 전송 경계가 구분되어 있다.

## 4. 한계

이 기록은 PNG 렌더와 생성기의 상자/문자 검토다. draw.io 편집기의 독립 열기 검증, 제품 API 실험, 각 기본안의 실제 성능 비교는 수행하지 않았다. 연결선 사이의 일부 교차는 남아 있으며 실행 순서는 중앙의 정수 번호와 경계 문구를 함께 읽는다. 외부 harness의 실제 구현과 VIA 추가 설계의 구분은 각 본문과 source 원장에 유지된다.
