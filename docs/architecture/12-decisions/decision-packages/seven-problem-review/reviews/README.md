## 설계 문서 검토 당시 상태

세 담당자가 문제를 나누어 조사하고 다른 담당자의 문서를 교차 검토했다. 주 담당자는 전체 선정, QA의 같은 의미, 문제 간 비용 귀속과 그림/본문을 통합했다. **현재 기록된 독립 검토에서 열린 P1/P2/P3는 없다.** 이는 제품 구현이나 성능의 검증 결과가 아니다. 과정 coverage의 미충족은 오류가 숨겨진 상태가 아니라 [현재 결과](../09-qa-tradeoffs.md)에 공개한 한계다.

| 검토 | 검토자 | 발견과 처리 |
| --- | --- | --- |
| [01/05 근거 공급과 인계](evidence-handoff-independent-review.md) | screen_grounding | 인계의 두 선택 축과 B+C 조합, 공통 Task/01 근거 이후 실제 남는 인계 생산의 예를 보완하고 재확인 |
| [02/03 의미 실행과 단계 연결](execution-independent-review.md) | evidence_handoff | 01의 근거 정책을 고정한 채 실행 분리만 비교하고 실제 호출 비용을 한 번 귀속하도록 보완 후 재확인 |
| [06 및 종합 08/09](selection-independent-review.md) | continuous_interaction | 기본 B의 전체 계약 재생산을 현재 구성으로 한정. N-S의 허용 보류를 종합 표에도 포함하고 재확인 |
| [화면 지칭의 종합 결론](screen-review-of-final-set.md) | screen_grounding + 주 담당자 통합 | OmniParser를 VIA temporal binding/소유권 우위의 직접 검증으로 읽지 않도록 외부 간접 근거라는 문구로 통일 |

screen_grounding은 자신의 화면 설계 본문을 독립 심사한 사람이 아니다. 해당 본문은 주 담당자가 source 적용 범위, 추가 parser 의존/비용, A4와 parser 없는 B 교차 구성, 후보 밖 원본 확장과 최종 PNG를 별도로 읽었다. “세 독립 reviewer가 모든 문서 전부를 검토했다”고 확대하지 않는다.

## 판단을 바꾼 통합 검토

1. **근거 공급 ABC의 축:** A/B의 문맥 수명과 B/C의 관계 선생산은 조합 가능하다. A+C를 별도 구조 조합으로 공개하고 주 비교/하위 비교를 구별했다.
2. **화면 지칭 B의 실용 근거:** typed 관계를 코드로 결합할 수 있다. 별도 screen parser의 표현 효과에는 외부 비교 근거가 있으나 producer 소유권의 효과는 분리해야 한다. 같은 parser를 A4에 넣는 보완을 공개했다.
3. **업무 인계의 판정:** 실제 QA03/05 설계 손익과 과정의 세 번째 축 부족을 구별했다. 세 번째 지표가 약하다는 이유만으로 의미 있는 설계 선택까지 없다고 결론내리지 않았다. 공통 근거의 단순 복제이면 B 이익이 사라지는 반례는 유지했다.
4. **DP-44/DP-42의 위치:** 구조 차이는 인정하되 정상 모델 대기나 일반 wire 변경의 개선을 자동 부여하지 않았다. A를 추천하고 독립 상세 설계로 남겼다.

비교 개요 7장과 주요 DP의 방안별 상세 10장은 작성자가 실제 PNG를 열어 확인했다. 주 담당자도 개요 전체와 주요 상세의 핵심 분기/상태/실패 경로를 PNG로 대조했다. 이미지의 가독성 확인과 실제 구조가 기능을 만족하는지의 실행 검증은 다르다.

## 설계 문서 검토 당시 미검증 영역

아래는 PoC 이전의 범위 기록이다. 이후 실제 Qwen 호출·후보 구현·기능 변경·RSS 계측으로 확인한 부분은 [15 현재 결과](../15-corrected-poc-results.md)에서 구분한다. 상용 Agent, 전체 제품, Windows와 실제 음성 경로는 여전히 이번 최소 PoC의 범위 밖이다.

- 실제 cloud 모델/화면 parser 품질과 가격, 호출 동시성 및 cache 동작.
- 실제 후보 Agent의 protocol, session 복구와 제한 자료 읽기 지원.
- Windows 전체 로컬 실제 상주 RAM의 공유 중복 제거 계측과 실제 운영 Rust 변경 범위.
- COMMON-28의 새 대안 실행, QA 원값과 점수, 사용자 대안 채택.

원문/코드에 있는 메커니즘을 확인한 조사와 VIA에서 그 조합을 구현해 시험한 것을 구별한다. 앞의 한계를 없애기 위해 임의 수치, 성공률이나 최종 구현 상태를 추가하지 않았다.
