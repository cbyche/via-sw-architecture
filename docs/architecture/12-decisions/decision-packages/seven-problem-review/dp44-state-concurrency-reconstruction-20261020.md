# DP44 재구성: 대화 의미 상태의 직렬 갱신과 낙관적 병행 갱신

> **후속 사용자 정정:** 이 의미 해석 실행 문제는 DP2 세션에서 구체화한다. 현재 DP44는 [여러 응답과 Agent 통지의 전달 구조](dp44-response-delivery-structure-20261020.md)를 검토한다. 아래 제목과 본문은 탐색 이력이며 현재 DP44 범위로 사용하지 않는다.

2026-10-20 / 새 구조 후보 / 설계 예측 / 미구현·미측정·미선정

## 1. 현재 요청과 비교 질문

사용자는 원래 DP44의 사용자 발화·정정, Agent 질문·결과, 내부 처리 완료와 실제 전달 사건을 유지하면서 기존 Component와 Dispatcher/Stage를 고정하지 않는 구조 대안을 요청했다. 단일 요청 중심 재탐색은 앞선 방향의 기록으로 보존한다.

**같은 대화의 요청 의미와 업무 연결을 한 해석씩 확정할 것인가, 여러 해석을 상태 사본에서 먼저 진행하고 확정할 때 충돌을 해결할 것인가?**

- A는 대화 의미 상태의 갱신을 직렬화한다. 의미 판단을 시작할 때 앞선 의미 변경을 반영한 상태를 읽는다.
- B는 여러 의미 판단이 판본이 붙은 상태 사본을 읽고 병행한다. 결과가 돌아오면 읽었던 조건의 유효성을 검사하고 확정하거나 재판단한다.
- 이 비교는 이전 DP2의 의미 실행 질문과 중첩된다. 별도 DP 두 개로 세거나 새 주제를 발견했다고 주장하지 않는다. 사용자가 허용한 통합 후보로 취급한다.
- 이전의 사건별 해석 뒤에 별도 대화 조정 LLM을 항상 추가하는 안을 복원하지 않는다. B의 추가 모델 호출은 의미상 재판단이 필요한 충돌에서 발생한다.

가장 분명한 가설은 **독립된 후속 입력의 QA01 대 충돌 시 QA03·QA05 재처리 비용**이다. A의 QA02/QA07 우위를 가정하지 않는다. 이 후보의 중요성은 의미 판단이 실제 겹치는 빈도와 충돌률에 달려 있으며 전체 VIA의 최상위 DP로 확정한 것은 아니다.

## 2. 공통 요구와 이번 비교의 범위

양안 모두 입력·사건을 계속 받는다. 음성 중단은 즉시 처리하고 응답 생성·음성 준비·외부 Agent 업무·사용자 답변 대기를 의미 상태의 실행권 안에 넣지 않는다. 식별자와 상태가 명시된 Agent 질문·결과는 코드로 저장·표시할 수 있다. 모든 사건에 LLM 호출을 강제하지 않는다.

일반 LLM은 원문과 허용된 대화·Task 근거로 요청 의미를 제안한다. S2S는 음성 입출력을 맡으며 업무 tool call을 갖지 않는다. 화면 근거 구조는 DP3 범위이며 양안의 접근 능력을 동일하게 둔다. 같은 모델 서비스의 다중 요청 지원을 전제로 하고 자원 부족이나 GPU 우선순위로 차이를 만들지 않는다.

사용자 정정이 들어오면 관련될 수 있는 미전송 효과를 보류한다. 과거 조건의 Agent 결과는 사실로 보존하되 최신 요청의 완료로 자동 게시하지 않는다. 권한, 현재 요청 판본, 중복 실행과 실제 질문 제시 기록은 공통 검사다. 코드 검사는 자연어 의미의 정답을 보장하지 않는다.

실제 업무는 Downstream Agent가 수행한다. 외부 업무가 진행 중이라는 이유만으로 A가 다른 입력을 기다리게 하지 않는다. 이번 직렬 구간은 **VIA의 공유 의미 상태를 읽어 변경안을 만드는 실행부터 그 제안의 처리까지**이며 보고서 작성·메일 발송 전체가 아니다.

## 3. A: 대화 단위의 단일 의미 갱신 실행

후보 구성은 기존 Component의 고정 배치가 아니라 다음 책임에서 출발한다.

- 사건 수신·실제 전달 기록: 입력과 외부 사실을 계속 보존한다.
- 대화 의미 실행: 한 대화에 하나의 의미 변경 실행을 허용한다.
- 확정 상태와 효과 기록: 채택 의미와 응답·위임 의도를 저장하고 비동기 전달한다.
- 조회·모델·Agent·음성 어댑터: 외부 호출을 수행한다.

흐름:

```text
의미 판단이 필요한 사건
→ 앞선 의미 변경이 끝난 상태 읽기
→ 일반 LLM 호출 / 필요한 읽기 도구 / 후속 모델 호출
→ 현재성·권한 검사와 의미 채택
→ 실행권 반환
→ 응답 준비와 위임은 비동기 진행
```

의미 실행권은 논리적인 제어 장치다. LLM을 기다리는 동안 DB transaction이나 OS thread를 점유하는 구현을 요구하지 않는다. 늦게 도착한 사용자 입력은 수신·보존하며 관련 출력은 즉시 hold할 수 있지만, 다음 의미 판단은 현재 실행이 끝나거나 취소 처리된 뒤 시작한다.

A가 막는 것은 내부 의미 변경끼리의 동시 갱신이다. 외부 자료 변경, 권한 철회, 이미 도착한 정정으로 인한 무효화까지 없어지는 것은 아니다. A도 이런 경우 현재 제안을 버리거나 재해석해야 한다.

**선택 이유:** 앞선 의미 변경을 반영해 다음 판단을 시작하므로 서로 경쟁하는 해석 결과의 재결합·재해석이 적다. 별도의 동시 스냅샷과 충돌 복구가 단순해진다.

**비용:** 실제로 독립적인 새 입력도 앞선 의미 실행이 끝나기를 기다릴 수 있다. 그 대기는 모델 처리 용량이 남아 있어도 발생한다.

## 4. B: 판본별 독립 의미 실행과 확정 검사

후보 구성:

- 사건 수신·실제 전달 기록.
- 판본이 있는 의미 상태 저장소.
- 사건별 의미 실행과 읽기 이력 기록.
- 확정 검사와 재판단 경로.
- 확정된 응답·위임 효과 기록과 비동기 전달.

흐름:

```text
의미 판단이 필요한 사건
→ 입력 시점의 대화 근거 + 현재 업무 상태 사본
→ 별도 일반 LLM 실행 / 필요한 읽기 도구
→ 의미 제안 + 실행기가 기록한 읽기 조건
→ 확정 검사
   ├ 유효: 의미와 효과 의도 기록
   ├ 코드로 독립성을 확인할 수 있음: 해당 범위만 반영
   └ 의미에 영향을 주는 충돌 또는 판단 불가: 최신 상태에서 재해석
```

LLM의 메시지에 포함하거나 조회 도구로 반환한 상태의 판본과 범위를 실행기가 기록한다. 모델이 “나는 이 값만 읽었다”고 주장한 것을 그대로 신뢰하지 않는다. 검색 결과는 반환 항목뿐 아니라 검색 범위와 후보 집합 변화도 고려해야 한다. 관계를 좁힐 수 없으면 넓은 범위로 검사하고 더 자주 재판단하는 비용을 받아들인다.

사용자가 발화할 때 실제로 본 질문·결과는 입력에 고정된 근거다. 나중에 다른 질문이 표시됐다는 이유로 과거 입력의 지칭 대상을 최신 질문으로 바꾸지 않는다. 반면 현재 적용할 Task·권한의 판본은 확정 시 다시 확인한다.

충돌 시의 재해석 입력은 사용자 원문, 유효한 조회 근거, 최신 의미 상태와 변경 사실이다. 고정된 의미 필드의 독립 변경은 코드로 처리할 수 있지만, 임의 자연어 변경을 문자열 병합으로 해결하지 않는다.

**선택 이유:** 새 입력이 앞선 의미 실행의 완료를 기다리지 않고 시작할 수 있다. 서로 다른 업무를 바꾸는 해석이 독립이면 먼저 끝난 결과부터 확정한다.

**비용:** 같은 상태에 의존한 판단이 겹치면 이미 수행한 LLM 호출을 재사용하지 못할 수 있다. 충돌 검사, 후보 판본·읽기 범위, 재시도와 미확정 효과의 수명을 관리해야 한다. 반복 충돌에는 재시도 상한과 일시적인 직렬 복구가 필요하다.

## 5. 같은 사건 순서에서의 동작

다음은 계산 예시이며 실제 측정이 아니다. 각 의미 실행 5초와 표시·코드 처리 비용 생략을 가정한다. 모델의 실제 call 수와 지연은 고정 사실이 아니다.

| 시각 | 양안에 같은 사건 |
| --- | --- |
| 0 | 사용자가 보고서 업무 R의 조건 변경을 요청. 의미 실행 시작 |
| 1 | 메일 Agent가 업무 M의 수신인을 질문. Task ID와 질문 ID가 명시돼 코드로 양안 모두 표시 |
| 2 | 사용자가 실제 표시된 질문에 “김 대리로 해줘”라고 답함 |
| 3 | 보고서 Agent가 이전 조건의 결과를 반환. 사실로 저장하고 정정 영향이 해소될 때까지 관련 게시를 보류 |

### 5.1 독립 변경: 보고서 정정과 메일 수신인 답변

- A: R의 의미 실행이 5에 끝난 뒤 M 답변을 해석한다. M의 내용 응답이 10에 표시된다면 두 번째 입력의 QA01은 8초다.
- B: M 답변의 해석을 2에 시작한다. 실제 질문 제시 기록과 필요한 M 상태를 읽고, R의 의미 변경과 독립임을 확인할 수 있으면 7에 표시한다. 두 번째 입력의 QA01은 5초다.
- Agent 질문과 이전 보고서 결과의 기본 저장·표시는 공통 경로다. 그 시간을 B만의 이익으로 세지 않는다. 최신 조건으로 보고서를 다시 처리해야 하면 양안 모두 Downstream Agent에 전달한다.

이는 모든 입력이 항상 3초 빨라진다는 예측이 아니다. 단순 사실 표시, 의미 실행이 겹치지 않는 요청, 광범위한 상태 의존으로 B가 재해석하는 입력에서는 이 계산이 적용되지 않는다.

### 5.2 관련 변경: 두 해석이 같은 상태에 의존

두 번째 입력이 같은 R의 변경을 포함하며, 병행 실행이 읽었던 의미 상태가 앞선 확정으로 달라졌다고 하자. 단순 병합으로 유효성을 증명할 수 없는 경우를 비교한다.

- A는 5 시점의 새 상태에서 두 번째 해석을 시작해 10에 끝낼 수 있다.
- B는 2~7에 수행한 해석을 채택하지 못하고 7~12에 재해석할 수 있다.
- 이 조건에서는 B가 먼저 시작했어도 더 늦게 끝나고 모델 호출 비용을 더 낸다.

모든 같은 Task 변경이 충돌하거나 재해석을 요구하는 것은 아니다. B가 원문에서 변경 관계를 이미 해결했거나 독립 필드임을 검사할 수 있으면 재사용한다. 반대로 A도 외부 자료·권한 변경 때문에 재해석할 수 있다. 위 비교는 B에만 추가된 내부 병행 충돌을 설명한다.

## 6. QA check matrix

| QA | 직접 관련성 | 대안 차이의 경로 | 현재 판정 |
| --- | --- | --- | --- |
| QA01 첫 응답 | 직접 | A의 선행 의미 실행 대기 대 B의 병행 시작·충돌 대기 | 독립 입력은 B 유리 예상. 충돌이 많으면 역전 가능 |
| QA02 지칭 정확도 | 직접 | 실제 전달·지칭 근거를 양안 모두 읽고 최초 채택 | 구조만으로 우위 없음. 회귀 확인 |
| 새 QA07 요청 의미 정확도 | 직접 | 양안 모두 최초 의미 채택 전 원문·조건 확인 | 직렬화는 의미 정답 보장이 아님. 우위 주장 안 함 |
| QA03 VIA 처리시간 | 직접 | 독립 작업 중첩과 충돌 재해석·폐기 | 독립 목표는 B 유리 가능, 충돌 목표는 A 유리 가능 |
| QA04 변경 모듈 수 | 관련 | 판본·읽기 범위·복구 계약의 변경 전파 | 실제 변경 과제 전 우열 미확정. 복잡성을 모듈 수로 환산하지 않음 |
| QA05 전체 모델 비용 | 직접 | B에서 추가로 발생한 충돌 재해석과 입력 반복 | 충돌 구간 A 유리 예상. 충돌 없으면 병행만으로 비용 증가를 단정하지 않음 |
| QA06 로컬 메모리 | 관련 | 병행 후보·읽기 이력·응답 buffer | 로컬 추가 상태 경로는 있음. 크기·점수 차이는 미확인, 원격 KV는 제외 |

QA01은 사용자·Agent 의무 사건을 같은 분모로 센다. 쉬운 사실 통지를 빼고 해석이 겹친 입력만으로 전체 평균 우위를 선언하지 않는다. QA03에서 사용자 답변 대기와 외부 Agent 업무 시간을 구별한다. QA02/07의 최초 오류를 나중의 재해석으로 소급 성공 처리하지 않는다.

## 7. 왜 이전 Dispatcher/Stage나 모델 우선순위 설정과 다른가

이전 비교는 같은 의미 job과 상태 권위를 두고 다음 실행의 전달 경로를 바꿨다. 이번 비교는 **어느 판본으로 의미 판단을 시작할 수 있는지, 여러 미채택 변경안을 함께 유지하는지, 언제 재해석이 필요한지**를 바꾼다.

동일한 API 동시접속 용량에서도 A는 의미 갱신의 직렬성을 위해 기다리고 B는 사본으로 진행한다. 모델 우선순위만 조절해서 판본별 읽기·확정·재해석 계약이 생기지는 않는다.

A에 B의 상태 사본·확정 검사를 도입해 병행할 수 있다. 그 경우 비교의 핵심 계약을 바꾸는 혼합안으로 기록한다. 변경이 가능하거나 간단하다는 이유만으로 기본 비교를 폐기하지 않는다. 반대로 단순한 코드 설정 수준이고 사용자 QA 차이도 작다면 최상위 DP가 아닌 상세 설계로 남길 수 있다.

## 8. 공식 메커니즘 참고와 한계

- [Orleans request scheduling](https://learn.microsoft.com/en-us/dotnet/orleans/grains/request-scheduling): 비재진입 실행은 비동기 대기 중에도 다음 요청 진입을 막을 수 있고, 재진입은 실행을 교차시키므로 공유 상태 처리가 달라진다. 이는 논리 실행 격리의 참고이며 VIA에서 오래된 모델 결과의 의미를 판단해 주지는 않는다.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html): snapshot·격리와 충돌 후 재시도는 병행 상태 갱신의 구현 참고다. SQL isolation만으로 LLM의 자연어 의미 의존성을 완전히 탐지할 수 있다는 주장은 하지 않는다.

구현체 채택·기능 검증·성능 측정은 수행하지 않았다. 새 후보를 과거 DP2/44 실험의 승자나 결과로 표시하지 않는다.

## 9. 선택 조건과 반증

- 독립적인 의미 처리가 겹치고 첫 응답 지연이 중요하면 B를 우선 검토한다.
- 같은 업무의 연속 수정이 많거나 상태 의존을 좁히기 어렵고 재해석 비용이 크면 A를 우선 검토한다.
- 실제 겹침이 드물거나 양안이 거의 모두 코드 경로로 처리하면 주요 QA 차별화가 약하다.
- B의 보수적인 읽기 범위 검사 때문에 대부분 재해석하거나, A의 선행 대기가 실용적으로 작으면 B의 속도 가설이 반증된다.
- 이 후보는 속도 대 정확성의 확보된 비교가 아니다. QA01·QA03·QA05의 조건별 손익을 먼저 검증할 비교다.

기존 DP44 본문, 참조 Architecture, QA 정의·점수·우선순위와 ADR은 보존한다. 새 기본안 채택, 구현, 모델 실행, 측정 또는 Git 발행은 하지 않았다.
