# VIA 기본 동작 구조 재탐색

> **후속 사용자 요청:** 원래 DP44의 문제 상황을 유지하면서 Component와 Dispatcher/Stage 제약 없이 재구성하는 [새 후보](dp44-state-concurrency-reconstruction-20261020.md)를 작성했다. 아래 단일 정상 요청 중심 방향은 앞선 논의의 기록이며, 현재 요청에서 겹치는 사건을 다루지 못하게 하는 제약이 아니다.

2026-10-20 / 사용자 정정과 다음 탐색 기준 / 후보·구현·측정·ADR 변경 없음

## 1. 현재 사용자 방향

VIA의 가장 큰 구조적 결정을 단일 정상 요청부터 탐색한다. 기존 Component 구성을 공통 골격으로 고정하지 않는다. 참조 Architecture는 비교할 입력 중 하나이며 새 대안의 필수 형태가 아니다.

- 화면 근거의 취득·유지·표현 및 발화와의 grounding 구조는 DP3 세션에서 다룬다. 여기서는 동일한 근거 접근 능력을 제공하며 정답 대상을 미리 공급하지 않는다.
- 사용자가 제시한 현재 논의 조건은 음성 입출력 S2S 모델과 일반 LLM이다. S2S에 특별한 업무 tool call 기능을 부여하지 않는다. 이전 공유 Omni 참조 설계를 이 탐색의 필수 모델 구성으로 강제하지 않는다.
- 모델 서비스의 다중 요청 지원을 전제로, 자원 경합을 이번 주요 구조 문제로 삼지 않는다. 경합이 없다고 실측한 것은 아니다.
- 긴 보고서 분석·업무 계획·실제 실행은 Downstream Agent에 위임한다. VIA 자신의 요청 이해 시간과 외부 업무 시간을 섞지 않는다.
- 단일 정상 요청의 QA01 첫 응답, QA02 지칭 정확도, 새 QA07 요청 의미 정확도, QA03 VIA 처리시간을 우선 설명한다. 겹치는 발화·정정·Agent 통지는 기본 구조를 검토하는 확장 장면이다.
- Component의 존재, 이름, 책임 배분과 실행 경계는 설계 결과다. 요청·업무·대화 상태 보존 요구를 특정 Manager의 존재와 동일시하지 않는다.

## 2. 앞선 비교의 현재 지위

| 앞선 탐색 | 현재 판단 |
| --- | --- |
| 겹친 입력의 별도 실행·조정 | 비동기 순차 사건 처리로도 가능한 범위를 먼저 인정한다. 추가 의미 조정의 필요성이 충분히 입증되지 않았다. 이번 최상위 탐색의 중심에서 내려놓는다. |
| 통합 대화 Agent 대 대화/업무 해석 분리 | 구체화 후 B에 선행 분류 호출과 별도 문맥을 추가한 차이만 남았다. B의 정확성 이점을 설명하지 못했으므로 주요 A/B 비교로 제시한 판단을 철회한다. A의 최종 선택을 뜻하지 않는다. |
| Response Manager에 입력 분류 배치 | 앞선 설명의 잘못된 책임 배치다. 응답 책임에 요청 해석을 추가할 필요성을 제시하지 못했다. |
| 기본 Context와 고정 호출 횟수 | report ID 사전 제공과 두 번/세 번 호출은 예시 조건이었다. 필수 구조가 아니다. 사용자 원문과 최근 대화에서 필요한 자료를 도구로 찾는 구조도 허용한다. |
| 속도 대 정확성 | 통합이 빠르고 분리가 정확하다는 일반 명제는 성립하지 않는다. 실제 의존·상태·첫 의미 확정 경로로 다시 설명해야 한다. |

이전 설계 본문과 결과는 이력으로 보존한다. 이전 측정을 새 기본 구조의 결과로 재해석하지 않는다.

## 3. 다음 작업의 구체적인 출발점

다음은 작업 제안이며 새 구조나 DP 선정이 아니다.

1. 정상 요청 세 가지로 실제 처리 의무를 고정한다: 단순 업무 위임, 정보가 부족한 업무 요청, 사용자가 순서·조건을 명시한 복합 요청. 입력이 겹치지 않는 상황부터 시작하고 직접 답변도 지원 여부를 확인한다.
2. 각 장면에서 사용자 원문, 이미 알려진 사실, 조회해야 할 사실, 위임 내용, 최초 표시 가능한 내용과 완료 조건을 구분한다. Agent 실행에 필요한 보고서·수신인 등의 정답을 편의상 선행 제공하지 않는다.
3. 기존 Component 이름 없이 전체 동작 구조를 탐색한다. 판단 실행을 누가 시작·재개하는지, 후속 처리를 무엇이 결정하는지, 어떤 중간 상태를 저장하는지, 무엇을 언제 확정하는지를 적는다.
4. 각 후보에 동일한 요청을 넣어 LLM API 입력·출력, 도구 요청과 실제 코드 실행, 상태 쓰기, Downstream Agent API, 사용자 표시를 순서대로 기록한다. 역할 분리와 호출 추가만 남으면 최상위 대안의 근거로 쓰지 않는다.
5. 후보가 의미 있게 다르면 QA 인과와 반례를 비교하고 그 결과로 Component와 인터페이스를 도출한다. 역할·상태 차이를 확인하기 전에 기존 여섯 Component에 다시 배치하지 않는다.

| 후보별 필수 설명 | 확인할 질문 |
| --- | --- |
| 시작과 진행 | 첫 LLM 입력은 무엇이며 다음 호출·위임을 누가 결정하는가? |
| 지속 상태 | 모델 메시지, 확정 요청, 업무 기록 중 무엇이 원본이며 재시작 후 무엇으로 재개하는가? |
| 의미 확정 | 목표·대상·조건을 언제 처음 채택하는가? |
| 첫 응답 | 구체적인 채택 내용이 실제 표시되기 전 어떤 처리를 기다리는가? |
| 후속 실행 | Agent 결과·확인 답변을 받으면 코드로 진행하는가, 다시 의미 판단하는가? |
| 손익과 반례 | 어떤 정상 장면에서 이득이며, 어떤 장면에서 추가 호출·정보 손실·재처리가 생기는가? |

QA02와 새 QA07은 최초 의미 채택을 평가하며 이후 인계 손실을 정확성 개선으로 바꾸지 않는다. QA01에서 일반 접수 멘트는 제외한다. QA03에 외부 Agent 업무 시간을 포함하지 않는다. 의미 검토에 영향을 주지 않는 저장·진행 구조라면 정확성 우위를 부여하지 않는다.

공식 구현과 원자료 조사는 실제 메커니즘 후보를 구체화할 때 수행한다. 현재 문서는 조사 완료나 새 대안의 우위를 주장하지 않는다.
