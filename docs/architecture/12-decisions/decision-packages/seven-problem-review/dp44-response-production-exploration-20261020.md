# DP44 재탐색: 첫 내용 응답의 생산과 확정 경계

> **사용자 정정 이후의 위치:** 사용자는 이 비교가 응답 분할 방식에 가깝다고 지적했다. DP44의 현재 주 탐색은 [겹치는 사건의 실행권과 중단·재개](dp44-overlapping-events-exploration-20261020.md)다. 아래 내용과 B 우선 권고는 직전 탐색 이력으로 보존하며 현재 DP44 주 비교의 권고로 사용하지 않는다.

2026-10-20 / 사용자 요청에 따른 설계 탐색 / 새 후보 미선정·미구현·미측정

## 1. 이번에 바꾸는 질문

사용자는 DP44를 우선 검토하며 기존 Dispatcher 대 Stage 비교에 얽매이지 않고, 첫 응답 지연시간을 중심으로 실제 QA trade-off가 발생하는 대안을 요청했다. **다음 작업을 누가 활성화하는가에서, 첫 내용 응답을 확정하려면 어떤 생산 작업까지 기다려야 하는가로 비교 범위를 넓힌다.**

[기존 DP44 재검토](03-execution-coordination.md)의 중앙 비동기 Dispatcher도 긴 작업과 다른 사건 수신을 병행한다. 같은 모델 작업·선행 조건·게시 검사를 그대로 두면 Stage 연결로 바꿔도 큰 QA01 차이를 기대하기 어렵다. 기존 설계와 그림은 보존하며 아래 A/B/C는 **이번 탐색에만 쓰는 후보 이름**이다. 기존 DP44 A/B 또는 이전 DP1 실험 A/B/C의 재명명이 아니다.

새 후보는 Request Interpreter의 의미 결과 반환, Request Controller의 채택, Response Manager의 후속 내용 생산·게시 계약을 함께 다룬다. DP2의 요청별 의미 실행 배치, DP3+47의 근거 표현·지칭 해석, DP4+1+45의 이력·인계 구조는 고정한다. 기존 연결 방식은 어느 후보와도 조합할 수 있다. 참조 Architecture와 accepted ADR을 변경한 것이 아니다.

## 2. 공통 기능과 비교의 경계

- **QA01:** 지정 입력/사건부터 첫 완결된 내용의 실제 UI 표시까지의 시간이다. 구체적으로 채택한 수행 안내, 직접 답, 확인 질문, 업무 상태가 대상이다. 인사·spinner·미채택 추측·미완결 token은 제외한다. 오답도 실제 표시 시간을 보존하고 오류는 별도로 판정한다. [현재 정의](../qa-candidate-package/qa01-first-response-latency.md)를 바꾸지 않는다.
- **이미 확인된 사실은 공통으로 바로 표시한다.** Task Manager가 확인한 업무 상태, 이미 채택한 대상과 수행 의도를 다시 말하기 위해 모델 호출을 강제하지 않는다. Response Manager는 확정 필드로 문장을 구성하고 Interaction Manager가 표시할 수 있다. 이 경로에서 후보 간 QA01 차이는 작거나 없을 수 있다.
- 새 요청의 대상·조건·관계가 아직 미해결이면 먼저 해석한다. 특정 대상을 확인하지 않고 그럴듯한 수행 안내를 만들어 시간을 줄이지 않는다. 필요한 확인 질문 자체는 첫 내용 응답이 될 수 있다.
- 입력·음성 수신과 로컬 음성 중단은 계속된다. 첫 텍스트를 음성 재생 순서나 외부 Agent 업무 완료 뒤로 미루지 않는다. 같은 모델·근거 접근·전체 자원 한도·필수 검사를 적용한다.
- Request Controller가 의미를 채택한다. Response Manager는 게시 허가·전달 원장을, Interaction Manager는 실제 표시/재생·receipt를 맡는다. 생성 결과와 사용자 전달을 구별한다.
- 새 revision, 권한 철회와 원본 변경을 최종 게시/전송에서 검사한다. 먼저 표시한 안내가 업무 수행 완료를 뜻하지 않는다. 상세 생산 실패 시 이미 표시한 안내는 전달 이력으로 남고, 실제 실패 상태를 후속 표시한다.
- 참조 모델 구성에서는 하나의 Omni 가중치를 공유하고 세션·문맥을 분리한다. 별도 호출을 별도 가중치 복제로 구현하지 않는다. 기존 원격 모델 PoC 비용/RAM과 참조 온디바이스 모델 자원을 같은 측정값으로 섞지 않는다.

## 3. 같은 장면으로 보는 세 후보

예: 사용자가 화면의 두 견적을 가리키며 **“이 둘을 설치비는 빼고 가격과 납기로 비교해줘”**라고 한다. 같은 근거에서 실제 두 견적과 해당 판본, 설치비 제외, 가격/납기 비교라는 의미를 해결해야 한다. VIA가 직접 제공할 수 있는 제한된 비교 설명을 대상으로 하며, 외부 Agent의 도메인 계획을 VIA로 가져오지 않는다.

첫 안내 예시는 “A사와 B사의 견적에서 설치비를 제외하고 가격과 납기를 비교하겠습니다.”다. 두 대상과 조건을 실제로 채택한 뒤 표시한다. 뒤의 비교 설명은 별도 목표 완료에 포함한다. 사용자 목표가 짧은 답 하나로 끝나면 안내와 상세를 억지로 둘로 나누지 않는다.

| 후보 | 첫 표시까지 기다리는 것 | 이후 생산 | 얻는 이점 | 감수하는 비용 |
| --- | --- | --- | --- | --- |
| **A. 한 응답 단위를 완성한 뒤 확정** | 필요한 의미와 즉시 제공할 답변을 포함한 반환 단위의 완성·검사 | 필요할 때만 다음 작업 | 동일 근거를 한 번에 사용하고 후속 호출·문맥 인계를 줄임 | 새 의미가 내부적으로 먼저 해결돼도 아직 확정 가능한 반환이 없으면 상세 생성만큼 첫 표시 지연 |
| **B. 짧은 의미 결과를 먼저 확정하고 상세를 후속 생성** | 필수 의미와 구체적 안내/질문/짧은 답의 완성·검사 | 필요할 때 별도 호출로 상세 생성 | 첫 응답 경로에서 긴 상세 생성을 제거하고 그 사이 사용자 정정을 받을 수 있음 | 추가 호출 시작·문맥 입력·큐 대기, 후속 작업 상태 및 전체 완료 지연 가능성 |
| **C. 한 추론 스트림에서 완결된 기록마다 확정** | 먼저 닫힌 의미 기록과 게시 가능한 첫 내용의 검사 | 같은 스트림에서 상세 기록 계속 생산 | B처럼 먼저 표시하면서 동일 호출의 문맥을 이어 쓸 가능성 | 부분 스트림의 확정·보류·폐기·중단 복구 계약, 채택 대기 중 생성된 꼬리의 낭비 |

### A. 한 응답 단위를 완성한 뒤 확정

1. Request Interpreter가 같은 입력과 근거로 필수 의미와 제한된 즉시 응답 후보를 생성한다.
2. 완성된 반환 단위를 Request Controller가 검사·채택한다.
3. Response Manager가 허용 내용을 게시하고 Interaction Manager가 실제 표시한다.

한 시도에는 하나의 반환 단위와 채택 경계가 있다. 모델이 상세 내용을 구성하는 동안 발견한 조건 충돌을 반환 전에 반영할 수 있다. 그러나 이것이 정확도 우위를 보장하지는 않는다. 내용 생성이 길면 첫 구체적 안내도 늦어진다.

**A를 약하게 만들기 위해 네트워크 스트리밍을 금지하지 않는다.** 전송은 스트리밍이어도 채택 계약이 완성된 단일 객체라면 부분 bytes를 확정 의미로 쓰지 못한다. 별도로 닫힌 의미 기록을 먼저 반환하고 채택하도록 계약을 바꾸면 C에 접근한다. 이 변경이 작은 parser/출력 순서 수정으로 충분하면 A/C를 큰 구조 선택으로 과장하지 않는다.

짧은 질문, 즉시 답 하나가 충분한 입력, 큰 공통 문맥을 재입력하기 비싼 환경에서 유리할 수 있다. 외부 Agent의 긴 작업이나 대화 전체가 끝날 때까지 기다리는 구조는 아니다.

### B. 짧은 의미 결과 확정과 후속 상세 생성

1. Request Interpreter의 첫 실행은 목표·대상·조건·요청 관계·정정 범위 중 해당 입력에 필요한 필드를 완성한다. 해결되지 않은 필수 항목이 있으면 구체적 확인 질문을 만든다.
2. Request Controller가 의미를 채택한다. Response Manager는 채택 필드에서 첫 안내를 구성하고 Interaction Manager가 표시한다. 첫 안내만을 위한 추가 문장 다듬기 호출은 기본안에 넣지 않는다.
3. 상세가 남으면 Response Manager가 채택 revision·근거 참조·미완료 응답 범위를 연결한 후속 작업을 유지하고 Model Access를 통해 생성한다.
4. 상세 반환을 현재 revision과 다시 대조해 표시한다. 첫 단계에서 실제 답이 끝났으면 후속 호출은 없다.

추가 상태는 `채택 revision, 이미 표시한 내용, 남은 응답 범위, 후속 작업/재시도 참조`다. 상세 생성 실패를 의미 채택 실패와 구별할 수 있고, 후속 시작 전에 정정되면 불필요한 상세 실행을 피할 수 있다.

반대편 비용은 첫 호출 종료와 다음 호출 시작 사이의 대기, 동일 근거/조건의 재전달, 연속성 관리다. 캐시나 세션 재사용이 있으면 입력 비용을 줄일 수 있지만 무료라고 가정하지 않는다. 기본안은 채택 후 상세를 시작한다. 채택 전 상세 추측 실행은 별도 보완이다.

### C. 같은 추론 스트림의 단계별 확정

1. Request Interpreter의 실행은 먼저 완결된 의미 기록을 출력하고, 같은 스트림에서 상세 후보를 이어서 출력한다. 의미 기록에는 필수 조건 전체가 들어가며 반쪽 JSON/누락 필드로 채택하지 않는다.
2. Request Controller가 닫힌 의미 기록을 검사·채택한다. Response Manager는 승인된 첫 내용을 표시한다.
3. 후속 내용은 `채택 revision, 내용 순서, 완결 경계`로 연결한다. 의미 채택 대기 중 먼저 도착한 내용은 임시 보관하고 허가 후에만 게시한다.
4. 의미 기록이 거절되거나 정정이 들어오면 관련 미전달 꼬리를 폐기/중단한다. 이미 전달한 내용은 실제 receipt와 함께 남긴다.

스트림 수신 중 유효한 기록 경계를 인식하고, 채택 전후를 구별하며, 끊어진 시도의 재생과 중복 표시를 막아야 한다. 중간에서 모델을 실제로 멈출 수 없다면 검사 대기 동안 생성한 내용도 비용에 포함한다. 별도 API 호출로 재개했다면 그 구간은 B와 같은 후속 호출 비용을 보고한다.

새로운 가중치나 매 문장 검증용 LLM을 기본 비용으로 임의 추가하지 않는다. 완결성·revision 검사는 코드로 할 수 있으나 내용의 의미적 진실까지 증명하지 않는다. 부분 출력 지원 자체가 정확한 의미 채택을 보장하지도 않는다.

**C는 반드시 B보다 복잡하고 비싸다고 결론 낼 수 없다.** 현재 런타임이 기록별 출력·취소·재접속을 충분히 지원하면 C가 B의 첫 응답 이점과 A의 호출 수 이점을 함께 얻을 수 있다. 반대로 스트림 재개가 불가능하거나 채택이 오래 걸리면 폐기·재시도가 늘 수 있다. 이 조건을 비교하지 않고 B를 선택하면 안 된다.

## 4. 시간과 비용이 갈리는 실제 위치

아래는 수치 예측이 아니라 임계 경로의 설명이다. 모든 안에서 공통 수신/근거 준비와 실제 표시 비용을 포함한다. 짧은 상태 안내의 공통 직접 경로는 별도로 구별한다.

| 비교 | QA01에 남는 대기 | QA03·QA05의 반대편 비용 |
| --- | --- | --- |
| A → B | 긴 응답 전체의 반환 대기 대신 짧은 의미 결과의 반환까지 기다림 | 상세가 필요한 건의 추가 시작·문맥 입력·후속 호출. 짧아진 첫 출력/줄어든 폐기 비용을 함께 계산 |
| A → C | 전체 객체의 종료 대신 첫 완결 기록과 채택까지 기다림 | framing·검사·게시 처리, 채택 실패 뒤 이미 생성된 꼬리의 폐기/재시도 |
| B → C | 같은 시점에 의미 기록이 완성되면 첫 응답은 동점 가능 | 후속 호출/문맥 인계를 줄일 수 있지만 스트림 유지·중단 복구 비용 발생 |

B가 C보다 QA01이 빠르다는 보장은 없다. 짧은 첫 호출의 출력 목적이 더 집중되어 빠를 가능성은 있으나, 첫 의미 기록을 먼저 생성하도록 한 C와 실제로 대조해야 한다. A도 상세가 짧거나 이미 채택된 필드로 첫 안내를 표시할 수 있으면 차이가 사라진다.

## 5. 시나리오별 이익과 반증

| 장면 | 이익이 생길 수 있는 후보 | 비용·동점·반증 조건 |
| --- | --- | --- |
| 새 의미 해석 뒤 긴 VIA 설명이 필요 | B/C: 상세 완성 전에 채택한 의도 표시 | 의미 해석 자체가 대부분의 시간이면 개선은 작음. A도 같은 시점에 독립 의미를 반환하면 C와 수렴 |
| 짧은 직접 질문 | A: 한 반환으로 종료. B도 첫 단계에서 끝날 수 있음 | B에 무조건 두 호출을 강제해 손해를 만들지 않음. C의 framing 비용만 남을 수 있음 |
| 확인된 Agent 질문/실패/결과 도착 | 모든 안의 확정 사실 직접 표시 | 사실 연결에 추가 해석이 필요 없는 한 새 구조의 QA01 이익으로 세지 않음 |
| 견적 지칭 자체가 모호함 | 모든 안이 필요한 근거를 읽거나 구체적 질문 | B/C가 대상 해결을 생략해 시간을 줄이는 것은 기능 저하. 질문의 필요성 오류도 별도 보존 |
| 안내 직후 “납기는 됐고 가격만” 정정 | B는 아직 시작하지 않은 상세를 피할 수 있음 | 이미 상세가 시작했으면 이익 축소. C는 생성 중인 꼬리 폐기, A도 진행 중 계산 취소. 먼저 안내한 내용을 정정하는 사용자 부담 존재 |
| 첫 표시 후 연결/모델 실패 | B는 채택된 의미로 후속 재시도 가능 | C는 마지막 전달 기록과 이어 생성할 문맥을 복원해야 함. A도 게시 이후 실패는 공통 전달 원장으로 처리 |
| 긴 공통 근거와 잦은 상세 응답 | A/C: 한 호출 문맥의 연속 사용 가능 | B의 재전달 비용 증가. 실제 prompt cache/세션 재사용이 효과적이면 차이 축소 |
| 같은 모델 자원이 포화 | B의 짧은 첫 단계가 먼저 끝날 가능성 | 별도 우선순위/추가 slot을 B에만 주지 않음. 두 번째 호출과 C의 긴 세션이 다른 요청에 주는 간섭도 포함 |

## 6. QA check matrix: 직접 영향과 차별화 근거

## 9. 공식 SW 자료로 확인한 구현 가능성과 한계

- [LangGraph streaming](https://docs.langchain.com/oss/python/langgraph/streaming)은 상태 갱신, 모델 token, custom event를 구별하여 전달한다. 내용과 상태의 반환 경계를 나눌 구현 수단의 근거이며 VIA의 의미 채택·게시 허가를 대신 제공한다는 뜻은 아니다.
- [Anthropic fine-grained tool streaming](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)은 부분 JSON을 조기에 전달할 수 있고 불완전/잘못된 JSON과 출력 제한 종료를 소비자가 처리해야 함을 설명한다. **빠른 bytes 수신과 채택 가능한 완결 의미는 별개**라는 C의 검증 조건을 뒷받침한다. 공급자 변경을 제안하는 것은 아니다.
- [Adaptive Cards templating](https://learn.microsoft.com/en-us/adaptive-cards/templating/)은 데이터와 표시 layout의 분리를 제공한다. 확정 필드를 UI로 투영하는 공통 경로의 구현 참고이며, 그 데이터의 의미 정확성을 보장하는 도구는 아니다.

자료 확인일: 2026-10-20. 어느 자료도 VIA 후보 간 성능 우위를 입증하지 않는다.

## 11. 현재 판단과 다음 비교 조건

**B를 QA01 우선의 유력 후보로 두고, A를 전체 처리·비용 대안, C를 B의 추가 호출이 꼭 필요한지를 검증하는 경쟁안으로 비교한다.** 이것은 사용자 채택이나 최종 승자 선정이 아니다. C가 저비용으로 동일 기능과 첫 응답을 제공하면 B 대신 C를 택하거나, 분리 호출을 특정 장면의 tactic으로 낮추는 것이 타당하다.

비교의 첫 조건은 같은 의미·필수 근거·사용자 목표다. 긴 설명만 고르지 않고 짧은 직접 답, 확인된 업무 통지, 모호한 지칭, 후속 정정과 중간 실패를 함께 둔다. 같은 모델/전송 streaming 기능과 총 자원 한도에서 첫 실제 표시, 상세 완료, 전체 음성 준비, 호출/토큰/폐기/재시도를 각각 기록해야 한다. 출력 순서 하나로 차이가 사라지는지, 후속 문맥이 실제로 중복되는지, C가 별도 API 재개를 필요로 하는지가 주요 반증 조건이다.

이번 작업은 설계 탐색과 기존 증거 재해석이다. 새로운 구현·모델 호출·측정·점수 변경·commit/push는 수행하지 않았다. 현재 결과만으로 DP44가 과정의 모든 QA coverage 기준을 충족한다고 선언하지 않는다.
