# DP44 재탐색: 응답 문안 경유와 채널별 직접 생성

> **2026-10-21 현재 DP44 대안에서 철회:** 사용자는 Downstream Agent가 응답 내용을 제공한다는 책임 경계를 다시 확인했다. 이 문서는 추가 응답 생성 업무로 비교 범위를 옮긴 이전 탐색으로 보존한다. 아래 손익을 현재 DP44의 구조적 이익이나 비용으로 사용하지 않는다. 현재 문제 경계는 [대화 전달 구조 재정립](dp44-conversation-delivery-reset-20261021.md)을 따른다.

## 1. 사용자 기준과 이번 판단

사용자는 자연스러운 전달 경험을 새 QA로 추가하지 않고, DP2의 의미 해석을 제외한 응답 전달 구조에서 현재 QA01~07의 실제 손익을 설명하도록 요청했다. [직전 사건별 산출물 대 통합 상태 비교](dp44-response-delivery-structure-20261020.md)는 주요 대안으로 유지하지 않는다.

이번에 남기는 비교 질문은 **응답 내용을 일반 LLM에서 사용자용 문안으로 만든 뒤 음성 모델에 전달할 것인가, 텍스트와 음성 생산자가 확정된 전달 사실을 직접 받아 독립적으로 생성할 것인가**다.

가장 구체적인 가설은 **B의 QA03 단축 가능성 대 A의 QA05 절감 가능성**이다. 긴 전달 자료, 음성 준비가 임계 경로인 목표, 모델별 입력 단가 조건에서 성립한다. QA01 이익은 공통 즉시 표시 때문에 기본적으로 주장하지 않는다. 현재 상태는 두 축의 조건부 설계 후보이며, 3~4개 QA 차별화나 주요 DP 선정 기준을 충족한 결과가 아니다.

별도로 RAM 보관 대 파일 spool의 QA03/QA06 손익도 검토한다. 이 축은 A/B와 조합 가능하며 주 비교의 대안 C로 섞지 않는다.

## 2. 같은 입력, 기능과 의미 확정

입력은 `event_id`, `task_id`, `revision`, 확정된 질문/사실, 결과 자료, 필수 전달 항목, 대체 관계다. Agent의 도메인 분석과 사용자의 요청 의미는 완료된 상태다. VIA는 그 결과를 사용자에게 표현하며 원본 보고서를 재분석하거나 업무 계획을 다시 세우지 않는다.

- 상세 텍스트와 음성 요약에 반드시 포함할 사실을 공통으로 고정한다. B가 더 짧게 말하거나 일부 사실을 생략한 결과를 속도 이익으로 세지 않는다.
- 확정된 상태와 질문은 모든 안에서 코드로 바로 표시한다. 상세 텍스트가 이미 사용자용이면 그대로 표시한다. 추가 표현 작업이 필요한 경우만 일반 LLM을 사용한다.
- 동일한 일반 LLM과 S2S 모델을 사용한다. S2S에 업무 tool call을 제공하지 않는다. 사용자 해석 세션과 응답 생성 세션의 권한/문맥을 분리한다.
- 모델 서비스의 다중 요청을 전제로 한다. GPU 경합이나 전체 호출 mutex를 만들어 상대편을 늦추지 않는다.
- 생성한 상세 텍스트와 음성에 같은 응답 ID, 요청 판본, source ID를 붙인다. 게시와 재생 전에 유효성을 검사하고 실제 전달 receipt를 남긴다.
- 모델 생성의 사실 보존은 공통 기능 검증 대상이다. 표현 과정의 누락/왜곡을 QA02나 새 QA07의 최초 요청 해석 오류로 재분류하지 않는다.
- 사용자가 응답 중 말하면 재생은 즉시 중단한다. 그 발화의 의미와 기존 응답의 유효성 변경은 DP2/업무 상태 처리 결과를 받는다.

## 3. A: 일반 LLM에서 만든 문안을 음성 경로가 사용

```text
확정된 전달 사실/결과
  ├─ 코드로 상태·질문·이미 완성된 상세 텍스트 표시
  └─ Response Composer: 일반 LLM
       → 필요한 상세 텍스트
       → 음성으로 전달할 짧은 문안
            → Speech Renderer: S2S
                 → 음성 데이터와 출력 참조
```

`Response Composer`와 `Speech Renderer`는 이번 후보의 책임 이름이며 참조 Architecture Component의 개명이 아니다.

1. 코드가 전달 대상의 현재 판본을 고정한다.
2. 일반 LLM에 확정된 결과와 필수 전달 항목을 주고 사용자용 문안을 요청한다. 업무 reasoning이나 tool call은 요구하지 않는다.
3. 음성 문안의 완결된 단위가 나오면 즉시 S2S로 넘긴다. **상세 텍스트 전체가 끝날 때까지 기다릴 필요는 없다.**
4. 상세 표시와 음성 준비 완료를 독립적으로 기록한다. 사용자에게 들려줄 차례를 기다리는 시간과 음성 생성 시간은 구분한다.

짧고 이미 완성된 Agent 질문은 일반 LLM을 거치지 않는다. 필요한 문안을 코드로 구성할 수 있으면 같은 우회가 적용된다.

주된 저장물은 확정 자료와 일반 LLM이 만든 문안, 그 문안에서 나온 음성이다. 음성 생성이 실패하면 같은 문안으로 다시 시도할 수 있다.

**이익:** 긴 전달 자료를 일반 LLM에서 정리한 뒤 음성 모델에는 작은 입력을 줄 수 있다. 상세 표현 생성과 요약 생성을 같은 일반 LLM 실행에서 공유할 수 있는 경우 추가 일반 LLM 입력도 줄일 수 있다.

**비용:** 음성 생성은 필요한 문안이 나오기 전에는 시작할 수 없다. 이 실제 데이터 의존이 QA03에 남는다.

S2S가 문안을 반드시 문자 그대로 읽는다고 가정하지 않는다. 양안 모두 같은 필수 사실 보존 조건을 만족해야 한다. 정확한 대본 읽기가 제품 필수 요구라면 지원 capability 또는 별도 TTS가 필요하며, 후자를 비용 없이 추가하지 않는다.

## 4. B: 확정된 사실에서 텍스트와 음성을 독립 생성

```text
확정된 전달 사실/결과 snapshot
  ├─ 코드 표시 / 필요 시 일반 LLM으로 상세 텍스트 생성
  └─ Speech Response Generator: S2S
       확정 사실을 직접 받아 음성 요약 생성

두 경로 → 판본 검사 → 각 채널에 게시/준비 완료
```

1. A와 같은 자료와 필수 사실을 읽는다.
2. 상세 텍스트 경로를 시작하면서 S2S에도 필요한 전달 자료를 보낸다.
3. S2S는 사용자 의도나 위임 대상을 판단하지 않고, 확정된 결과의 음성 표현을 만든다.
4. 상세 텍스트와 음성이 각각 준비되는 대로 기록한다. 한쪽의 문장이 다른 쪽의 필수 입력이 되지 않는다.

일반 LLM과 S2S를 병렬로 호출한다는 이름보다 **S2S가 읽는 입력의 권위와 내용이 달라진다**는 점이 핵심이다. A에서는 채택된 응답 문안이 입력이고, B에서는 확정된 전달 자료가 직접 입력이다.

**이익:** 일반 LLM의 문안 생산을 기다리는 의존이 없다. 음성 준비가 목표 완료의 가장 늦은 경로였다면 QA03을 줄일 수 있다.

**비용:** 음성 모델도 긴 결과를 읽고 필요한 표현을 생산한다. 상세 텍스트 경로에서도 같은 자료가 필요하면 자료 처리가 중복된다. 더 비싼 입력 단가의 모델로 긴 입력이 이동할 수 있다. 추가 청구량과 취소 전 사용량을 모두 센다.

B에 항상 별도 LLM 검수나 양 채널 자연어 비교를 강제하지 않는다. 양안의 공통 사실 보존 조건을 모델이 만족하는지 확인한다. B에만 추가 검증이 실제 필요하다면 그 경로를 포함하고 예상 속도 이익을 재판정한다.

## 5. 여러 응답이 겹치는 동일 장면

앞선 안내의 음성이 재생되는 동안:

1. 보고서 Task에서 완료 결과와 전달 자료가 도착한다.
2. 메일 Task에서 이미 완성된 제목 선택 질문이 도착한다.
3. 보고서 Task의 같은 결과에 대한 정정 통지가 도착한다. 정정 범위와 대체 관계는 이미 확정돼 있다.

| 단계 | A | B |
| --- | --- | --- |
| 보고서 결과 수신 | 완료 사실을 UI에 표시. 필요한 문안 작성 시작 | 같은 사실을 UI에 표시. 상세 표현과 음성 표현 경로를 독립 시작 |
| 메일 질문 수신 | 질문을 바로 표시. 이미 있는 질문 문구로 음성 준비 가능 | 동일. 질문이 짧고 완성돼 있으면 구조 차이 작음 |
| 보고서 정정 수신 | 해당 판본의 문안/음성만 무효화하고 새 문안에서 생성 | 해당 판본을 읽은 텍스트/음성 실행을 각각 무효화하고 새 snapshot으로 생성 |
| 메일 질문 보존 | 이미 준비한 질문 산출물 유지 | 동일하게 유지 |
| 실제 전달 | 공통 순서/중단 정책과 현재 판본 검사 | 동일 |

B는 정정 도착 전에 음성 생성을 먼저 시작했기 때문에 더 많은 음성 작업을 폐기할 수 있다. 다만 A도 문안이 일찍 나와 이미 음성을 생성했다면 같은 폐기 비용이 생긴다. 겹침 자체가 B의 추가 비용을 항상 보장하지 않는다.

이 비교는 단일 응답에도 적용되는 응답 생산 구조다. 여러 Agent 통지의 겹침은 동시 산출물과 취소 대상 수를 늘리지만, 겹침에서만 발생하는 고유 원리라고 주장하지 않는다.

## 6. QA03: 실제 데이터 의존의 비교

다음 값은 결과 도착 이후 응답 준비 구간이다. 전체 QA03은 원래 사용자 목표의 공통 앞 경로와 필수 후속 경로까지 포함해 계산한다.

```text
D_A, D_B: 필수 상세 표시까지의 시간
U: A에서 필요한 음성 문안이 준비되는 시간
V: A가 그 문안으로 전체 음성을 준비하는 시간
W: B가 확정 자료에서 직접 전체 음성을 준비하는 시간

A 응답 준비 종료 = max(D_A, U + V)
B 응답 준비 종료 = max(D_B, W)
```

문안 전체를 기다리지 않는 streaming이면 `U + V`는 해당 스트림의 실제 생성/소비 의존으로 대체한다. 모든 단계를 단순 합산하지 않는다.

**설명용 가정:** 두 안 상세 표시가 각각 3초, A의 문안 준비가 1.5초이고 그 뒤 음성 준비가 2초, B의 직접 음성 준비가 2.5초이면 A는 3.5초, B는 3초다. 이것은 구조식의 예이며 실제 모델 속도나 성능 예측값이 아니다.

상세 표시가 5초로 가장 느리면 두 안 모두 5초일 수 있다. 긴 입력 때문에 `W`가 커지거나 A의 짧은 문안이 아주 일찍 나오면 B의 이익은 사라지거나 역전된다. 재생 차례를 기다리는 시간의 감소로 QA03 이익을 주장하지 않는다.

## 7. QA05: 한 번 호출하는 B가 더 비쌀 수 있는 조건

상세 텍스트가 이미 완성돼 있고 음성 요약만 생성하는 단순 경우를 먼저 비교한다.

```text
N = 확정 전달 자료의 입력 토큰
S = A가 만든 짧은 문안 토큰

A = 일반 LLM 입력 N + 문안 출력 S
    + S2S 입력 S + 음성 출력 비용
B = S2S 입력 N + 음성 출력 비용
```

입력 자료가 6,000토큰이고 문안이 150토큰인 예에서 A는 음성 모델로 보내는 자료를 줄인다. 그러나 토큰 수나 호출 수가 QA05는 아니다.

같은 음성 출력 비용을 가정한 단순 비교에서, 일반 LLM 입력/출력 단가를 `p_Li`, `p_Lo`, S2S text 입력 단가를 `p_Si`라 하면:

```text
C_B - C_A = N(p_Si - p_Li) - S(p_Lo + p_Si)
```

이 값이 양수인 가격/입력 조건에서 A가 저렴하다. 상세 표현과 문안의 생산을 A가 실제로 공유하면 그 재사용도 반영한다. 반대로 S2S 입력이 저렴하거나 B의 직접 생성이 충분히 짧으면 A의 비용 이익은 없어질 수 있다.

실제 평가는 provider/model/version과 같은 단가 manifest, cached bucket, 추론/음성/출력 사용량, 실패와 폐기 비용을 모두 적용한다. 새 모델 선택이나 가격을 확정하지 않았다. QA05의 최종 단위는 공통 활동 전체 비용이며 긴 결과 한 건의 비용을 전체 비교값으로 대체하지 않는다.

## 8. QA01~07 check matrix

| QA | 구조가 관여하는가 | 이번 비교에서 남는 손익 |
| --- | --- | --- |
| QA01 첫 응답 | 공통 표시 경로에 관여 | 확정 상태/질문의 즉시 표시를 공통 허용하므로 큰 차별화 주장 없음 |
| QA02 지칭 정확도 | 최초 해석은 범위 밖 | 차별화 없음. 출력 오류를 지칭 해석 오류로 바꾸지 않음 |
| QA03 VIA 처리시간 | 직접 관여 | B의 문안 생성 의존 제거 대 긴 입력 처리 비용. 음성 경로가 임계 경로일 때 우위 후보 |
| QA04 변경 모듈 수 | 생성 경로/계약 변경에 관여 | 미확정. 컴포넌트 수나 코드 복잡도로 모듈 수를 추정하지 않음 |
| QA05 모델 비용 | 직접 관여 | A의 긴 자료 압축/생산 공유 대 추가 일반 LLM 호출. 위 가격 조건에서 A 우위 후보 |
| QA06 최대 로컬 RAM | 요청/산출물 버퍼에 관여 | B가 두 입력 복사본을 반드시 보유할 필요 없음. 클라우드 KV를 로컬 RAM으로 세지 않음. 주 차별화 축 아님 |
| 새 QA07 요청 의미 정확도 | 최초 의미 확정은 범위 밖 | 차별화 없음. S2S의 결과 표현은 요청 의미 재판단이 아님 |

## 9. 별도 저장 축: RAM 산출물과 파일 spool

같은 생성 구조에서 다음 저장 방식을 교차 적용할 수 있다.

- **RAM 산출물:** 아직 전달하지 않은 응답의 텍스트/음성을 메모리 버퍼로 유지하고 전달 참조가 그 버퍼를 가리킨다. 복사나 파일 I/O 없이 준비/접근할 수 있지만 동시 응답 수만큼 RAM을 사용한다.
- **파일 spool:** 생성 데이터를 작은 버퍼로 받아 파일에 쓰고, 출력 참조가 파일 구간을 가리킨다. 중단/재개 때 필요한 구간만 읽는다. 제한된 애플리케이션 버퍼 대신 쓰기/읽기와 파일 수명 관리가 추가된다.

QA03에 들어가는 것은 전체 음성과 출력 참조가 준비되기 전의 실제 I/O 의존이다. 생성과 쓰기를 병렬로 하면 일부 또는 전부 숨겨질 수 있다. 실제 재생 시 파일을 읽는 지연은 QA03 종료 뒤라면 QA03 손실로 세지 않는다. crash durability가 공통 요구가 아닌데 fsync를 강제해 spool을 느리게 만들지 않는다.

QA06은 버퍼 할당량이 아니라 실제 로컬 RAM이다. 파일 캐시/매핑의 해당 상주 영역도 공통 계약에 따라 계측하며 저장 파일 크기를 그대로 RAM으로 세지 않는다.

24kHz, 16bit, mono PCM 30초는 1.44MB이고 8개는 11.52MB다. 산술 예이며 제품 출력 포맷이 아니다. 압축하면 더 작다. 짧은 음성 요약 몇 개 때문에 매우 큰 메모리 차이가 난다고 주장하지 않는다.

**판정:** 저장 메커니즘의 실제 손익은 있지만 현재 규모에서 주요 DP보다 보완/상세 설계에 가깝다. 이 축을 주 A/B에 붙여 인위적으로 세 번째 QA 차별화를 만들지 않는다.

## 10. 공식 참고와 미검증 경계

- [LiveKit Realtime models](https://docs.livekit.io/agents/models/realtime/)는 realtime 모델의 직접 음성 응답과 대본 읽기 제약을 설명한다. 지시를 넣는 것만으로 정확한 문구 재현이 보장되지 않으며 특정 대본을 요구하면 별도 TTS 사용을 고려하도록 한다. 양안의 모델 어댑터 검증 항목이며 VIA 성능의 증거가 아니다.
- [LiveKit Text and transcriptions](https://docs.livekit.io/agents/multimodality/text/)는 음성 재생과 텍스트 전달의 동기화를 끌 수 있음을 설명한다. 텍스트의 첫 표시를 실제 음성 차례에 묶지 않는 공통 설계의 참고다.
- [Python SpooledTemporaryFile](https://docs.python.org/3/library/tempfile.html#tempfile.SpooledTemporaryFile)는 메모리에서 크기 한계에 따라 파일로 전환하는 실제 저장 메커니즘이다. Rust 구현 선택이나 Windows 실측 결과를 뜻하지 않는다.

## 11. 권고와 반증

현재는 A/B를 **QA03 대 QA05의 조건부 비교 후보**로 남긴다. 긴 결과를 음성으로 요약하는 작업에서 문안 의존이 완료를 늦추고 S2S의 긴 입력 비용이 실질적일 때 선택 이유가 생긴다.

다음이면 주요 DP 후보로 승격하지 않는다: 대부분의 입력이 짧고 완성된 문구여서 공통 직접 경로를 타는 경우, 상세 텍스트 경로가 늘 임계 경로인 경우, 모델 가격/캐시로 비용 차이가 사라지는 경우, A의 streaming으로 음성 의존이 이미 숨겨지는 경우. B의 사실 보존을 위한 추가 처리가 이익을 상쇄하는 경우도 포함한다.

QA01이 주 차별화인 최우선 DP라는 주장은 하지 않는다. 이번 문서는 기존 QA에서 남는 인과를 구체화한 설계 분석이며 새 QA, baseline/ADR 변경, 모델 실행과 측정, commit/push를 포함하지 않는다.
