# 일곱 설계 문제의 분석과 선정 기준

2026-10-18 / 사용자 승인에 따른 통합 분석

## 1. 이번 분석의 목적

VIA의 중요한 기능에서 어려운 설계 선택을 찾고, 실제 agent harness와 인접 SW의 작동 메커니즘을 근거로 구현 가능한 기본안을 비교한다. 중요한 QA의 이익과 비용이 선택을 바꾸는 문제를 최종 DP 세트에 포함한다. 자료의 완성은 설계 분석과 선정 근거의 완성을 뜻하며 측정하지 않은 성능을 실적으로 만들지 않는다.

사용자는 일곱 문제 전체의 분석과 최종 DP 세트 구성을 위임했다. 네 개라는 수량 제한은 없다. 기존 추천이나 DP 번호 때문에 포함 또는 제외 결론을 고정하지 않는다.

| 검토 주제 | 통합 또는 독립 관계 | 현재 통합 문서 |
| --- | --- | --- |
| 현재 요청을 위한 근거 공급 | 문제 1과 DP-45 통합 | [01](01-evidence-supply.md) |
| 후속 입력의 의미 판단 실행 | 문제 2 독립 | [02](02-interpretation-execution.md) |

| 발화와 화면 조작의 지칭 해석 | 문제 3과 DP-47 통합 | [04](04-screen-speech-grounding.md) |
| 다음 Agent로 업무 조건과 결과 인계 | 문제 4 독립 | [05](05-agent-handoff.md) |

01~07은 이 자료의 읽기 순서다. 새로운 공식 DP 번호가 아니다. 문제 2와 DP-44를 하나의 비교나 tactic으로 흡수하지 않는다. 기존 DP 본문과 그림은 이전 상세 설계 및 provenance로 보존하고 이 통합 분석으로 안내한다.

## 2. 모든 대안에 공통으로 요구할 기능

- VIA가 사용자 입력과 실제 전달 기록, Request와 Task 및 외부 실행의 관계를 소유한다. 외부 Agent는 업무 계획과 실행을 담당한다.
- 원문과 관측 시점, source revision, 실제 전달 범위, 변경된 조건과 유지할 조건을 구별한다. 정답 Task 연결은 입력으로 주어지지 않는다.
- 미해결 의미는 모델 또는 사용자 확인을 통해 해결한다. 코드가 모호한 지칭과 사용자 목적을 이미 안다고 가정하지 않는다.
- 현재 권한과 요청 revision을 검사하며 오래된 결과를 최신 결과로 채택하지 않는다. 외부 Action 수행 여부가 불명인 동일 작업을 중복 실행하지 않는다.
- 사용자의 말을 계속 받고 음성 재생을 중단할 수 있다. 이것은 외부 업무의 취소 확인과 다르다.
- VIA가 읽을 수 있는 실제 자료와 Agent의 지원 인터페이스만 사용한다. 비공개 내부 추론이나 모든 외부 앱의 session 이전을 가정하지 않는다.
- 같은 기능, 원본, 최종 의미 모델 capability, 전체 호출 한도와 장치 조건에서 비교한다. 구조가 추가 learned producer를 요구하면 그 dependency와 모든 비용을 공개하고 같은 producer를 반대안에 붙이는 교차 구성을 구별한다. 현 비교는 로컬 VIA와 cloud 모델 조건이며 기존 on-device 참조 설계를 제품 제약으로 재도입하지 않는다.

## 3. 기본안과 보완안

각 기본안은 공통 기능을 수행하는 최소한의 완결 구조다. A/B/C가 무엇을 언제 읽고 생산하며 어떤 상태를 유지하고 누가 다음 처리를 결정하는지 명시한다. 기본 구조에 내재한 재사용과 누락 보완은 남긴다. 선택적 cache, 예약, 병렬 실행과 부분 재계산을 모든 기본안에 미리 넣지는 않는다.

하나의 비교에서 달라지는 선택을 식별한다. 조합 가능한 선택을 배타적인 A/B로 설명하지 않는다. 여러 축을 바꾼 완결 구성을 비교할 경우 각 축과 교차 조합을 공개하고 어느 차이에서 효과가 생겼는지 구별한다.

기본안의 선택 이유를 먼저 제시하고, 약한 QA를 줄일 보완을 A1/A2 또는 B1/B2로 제시한다. A2는 A1을 포함하지 않는다. 결합 적용은 A1+A2로 쓰고 상호작용 비용을 확인한다. 다른 기본안으로 상태 소유나 정상 경로가 바뀌면 작은 tactic으로 이름 붙이지 않는다.

## 4. 유지할 QA 정의

| QA | 이번 분석에서 유지할 의미 | 차이를 만드는 잘못된 방법 |
| --- | --- | --- |
| QA01 첫 응답 지연시간 | 실제 입력 또는 통지부터 구체적인 첫 내용의 Request/Task UI 표시까지 | 단순 접수 인사를 종료점으로 사용하거나 이미 첫 내용 표시 뒤의 Agent 인계를 포함 |
| QA02 지칭 대상 식별 정확도 | 사용자가 지칭한 대상 집합의 완전 일치율 | Agent 선택, 질문 연결, 인계 조건 누락을 지칭 정확도로 변경 |
| QA03 VIA 처리시간 | 실제 완료 목표 경로의 VIA 귀속 시간. 상세 표시와 필요한 전체 음성 요약 준비 포함 | 외부 Agent 실행과 사용자 대기를 VIA 절약으로 세거나 기존 종료점을 인위적으로 연장 |
| QA04 변경 범위 | 동일 변경 과제를 완료한 실제 운영 Rust 모듈 수 | 그림 상자, 서비스 또는 파일 개수를 실제 변경 모듈 수로 간주 |

| QA06 최대 RAM | Windows에서 전체 로컬 VIA의 실제 상주 RAM 최고량. 공유 물리 페이지는 중복 제거. 요구 512 MB | commit을 실제 RAM으로 간주하거나 cloud KV/디스크 크기 또는 여러 시점의 peak를 합산 |

QA01/03은 산술평균이며 오답의 실제 시간과 오류 표식을 함께 남긴다. 시간 벌점을 새로 부여하지 않는다. 미응답과 실패를 숨기지 않는다. 서로 겹치는 시간 축은 각각 관측하되 독립적인 시간 절약으로 합하지 않는다. QA07~09는 기존 부하, 병행 변경과 음성 전달의 보조 또는 필수 회귀 위치를 유지한다.

N-H 업무 인계 정확도, N-S Agent 선택 정확도와 N-R 요청 관계 연결 정확도는 별도 정의 제안이다. 기존 QA02를 넓히거나 임의 목표/배점을 붙이지 않는다. 하나의 DP에만 관련된 지표로 전체 핵심 QA coverage가 완성됐다고 주장하지 않는다.

COMMON-28과 기존 점수표를 변경하지 않는다. 추가 분석 장면은 별도 설계 사고실험으로 식별하고 그 결과를 기존 점수에 넣지 않는다.

## 5. 최종 선정 판정

각 문제는 다음을 모두 확인한다.

1. 정상적인 VIA 사용에서 중요하고 어려운 선택인가.
2. 대안이 같은 일을 수행하고, 실제 데이터/실행/상태/확정/복구 메커니즘이 다른가.
3. 공식 구현에서 확인한 부분과 VIA에 추가한 설계를 구별했는가.
4. 각 대안에 그것을 선택할 만한 사용 조건과 반대편 비용이 있는가.
5. 중요한 QA에서 그 차이로 이어지는 인과가 있고, 반증 조건을 적을 수 있는가.
6. 비교축이 중복되거나 다른 DP의 이익을 가져오지 않았는가.

최종 결과는 **주요 DP 포함**, **독립 상세 설계로 유지**, **현재 대안 제외**로 구별한다. 기능의 중요성과 현재 비교쌍의 주요 DP 자격은 별개다. 제외한 경우 공통 기능은 남기고, 채택할 상세 구조와 재검토 조건까지 결정한다. 신규 대안으로 재구성할 때는 기존과의 차이를 남긴다.

설계 단계의 조건부 차이는 실측 coverage가 아니다. 과정의 DP별 3~4 QA 차이와 QA별 2개 이상 DP 차이 조건을 따로 감사한다. 부족한 경우 빈칸과 해결에 필요한 근거를 공개하고 측정 없이 충족 판정을 만들지 않는다. 기존 네 개 고정 수량은 이번 사용자 지시로 해제됐지만 지표의 의미를 바꿔 coverage를 채우는 것은 허용되지 않는다.

## 6. 증거와 검토

- **구현 근거:** 공식 문서, 고정 commit 코드, 해당 논문 원문. 제품 전체를 한 대안으로 분류하지 않는다.
- **설계 분석:** 동일 사건 순서, 상태 전이, 의존 경로, 호출/재사용 비용 수식과 경계 조건. 변수 값은 실측 없이 대입하지 않는다.
- **선정:** 위 근거와 명시한 VIA 사용 가정에 대한 설계 결론. 작동 보장이나 실측 승리와 구별한다.
- **독립 검토:** 다른 담당자가 기능 누락, 비교축 혼합, source 과장, QA 오용과 tactic 혼입을 확인한다. 열린 발견과 수정 결과를 기록한다.

이번 분석에서는 후보 제품 구현, 유료 모델 실행, Windows 성능 측정과 새 점수 산출을 수행하지 않는다. 기존 accepted ADR과 reference Architecture는 보존한다. 문서 완성과 실제 성능 확인을 서로 대신하지 않는다.
