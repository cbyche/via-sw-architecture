## 1. 무엇을 최종 결과로 가져가는가

**주요 DP는 01 근거 공급, 02 의미 판단 실행, 04 화면과 발화의 지칭 결합, 05 업무 인계로 선정한다.** 각 문제에는 VIA의 정상 사용에서 반복되는 어려움, 실제 구현 가능한 다른 구조, 반대편 이익과 비용이 있다. 03 처리 단계 연결, 06 Agent 선택, 07 상태/서비스 경계는 기능과 설계가 필요하지만 현재 비교쌍의 주요 품질 선택 근거가 상대적으로 약해 독립 상세 설계로 정리한다.

이는 “모든 수치가 확인된 네 개의 평가 완료 DP”라는 결론은 아니다. 설계 단계에서 어떤 선택을 주요 의사결정으로 다룰지 정한 결과다. [과정 QA coverage](09-qa-tradeoffs.md)는 별도 판정이며 부족한 부분을 감추지 않는다.

## 2. 주요 DP마다 실제로 결정한 내용

### 2.1 현재 요청의 근거 공급: 기본 A 권고

**VIA 문제:** “아까 네가 설명한 결론만 다시”, “그 결과를 지난 견적과 비교해줘”를 처리하려면 현재 화면뿐 아니라 과거 원본과 실제 전달 범위가 필요하다. 읽었던 근거를 작업 문맥에 계속 유지할지, 현재 요청마다 원본을 선택해 구성할지 정해야 한다.

- **A:** 대화별 작업 문맥을 유지하고 부족한 원본을 읽는다. 짧은 후속 지칭에 이미 유효한 근거가 있을 수 있다. 더 큰 지속 입력, 압축과 수정 비용을 낸다.
- **B:** 공통 최소 상태에서 이번 요청에 맞는 근거 묶음을 만든다. 무관한 자료의 유지 부담을 줄이지만 필요 범위 발견과 재조합을 반복할 수 있다.
- **C:** 관계 근거를 요청과 별개로 생산/게시한 뒤 요청별로 조회하고 원본으로 보완한다. 반복 관계 조회를 줄일 기회와 선생산/미소비 비용이 함께 있다.

**A/B와 B/C는 서로 다른 선택 축이다.** A+C도 가능하며 세 안을 배타적인 세 철학처럼 취급하지 않는다. 주 비교 A/B는 문맥 수명이고 C는 과거 관계 생산의 하위 구조 선택으로 포함한다. 같은 조회 절약을 두 DP의 독립 이익으로 늘리지 않는다.

VIA의 연속 대화에서 같은 자료의 짧은 후속 질문을 우선해 **A**를 추천한다. **A1 입력 prefix cache**는 반복 입력 비용을, **A2 변경 조각 갱신**은 작은 정정의 재구성 비용을 보완한다. cache 지원/적중과 dependency 관리 비용을 따로 센다. 새로운 주제로 계속 바뀌어 유지 근거의 재사용이 낮다면 B가 더 적합하다.

근거: OpenHands rolling view/condensation, Deep Agents offload/범위 읽기, OpenClaw와 CrewAI의 기억 생산. [상세 분석과 기존 DP-45 계약 통합](01-evidence-supply.md).

### 2.2 후속 입력의 의미 판단 실행: 기본 B 권고

**VIA 문제:** 앞선 문서의 긴 판단이 진행 중일 때 사용자가 다른 질문을 하거나, 이전 조건을 바꾸거나, 다른 Agent의 실제 질문에 답한다. 이 입력을 어느 판단 실행에 넣고 어떻게 결과를 다시 대화에 연결할지 정해야 한다.

- **A:** 하나의 대화 해석 실행이 현재 step 경계에서 후속 입력을 반영한다. 앞선 목표 전체의 완료나 외부 Agent 업무를 기다리는 안은 아니다. 같은 문맥 재사용이 쉽다.
- **B:** 공통 대화 해석이 입력 관계를 판단하고 긴 읽기/판단을 요청별 실행에 맡긴다. 짧은 답은 공통 경로에서 처리한다. 호출 여유가 있으면 새 입력이 앞선 VIA 호출 뒤에 묶이지 않는다.

**B**를 추천한다. 사용자가 메인 인터페이스를 계속 쓰는 동안 독립 입력이 들어오는 장면에 직접 대응한다. 전제는 같은 전체 호출 예산에서 둘 이상의 실행이 실제 진행할 수 있다는 것이다. 포화와 거의 없는 입력 겹침에서는 A의 문맥 재사용 이익이 더 클 수 있다.

**B1 불변 문맥 참조 공유**는 로컬 중복 상태를 줄이는 보완이고 **B2 foreground 호출 여유 예약**은 요청 실행이 새 입력을 전부 막는 상황을 줄이는 보완이다. B2는 원래 요청의 진행을 늦출 수 있다. 기본 실행 분리의 이익과 예약 효과를 따로 기록한다.

근거: OpenClaw steering, OpenHands 수신/step 분리, Deep Agents 별도 run/thread와 제한된 side 질문. [정정/독립 질문/확인 답변/Agent 통지의 정확한 정의](02-interpretation-execution.md).

### 2.3 화면과 발화의 지칭 결합: 기본 A 권고, B의 반대편 근거 강화

**VIA 문제:** 사용자가 말하는 동안 여러 화면을 가리키고 페이지를 바꾸면 마지막 screenshot으로 이전 의도를 복원할 수 없다. 당시 원본을 보존한 뒤 지칭 범위를 어떻게 해석할지 정해야 한다. 원본 보존과 시각 대응은 A/B 모두의 필수 기능이다.

- **A:** 당시 원본과 말을 함께 읽어 최종 대상 범위와 관계를 직접 생산한다. 한 번에 여러 지칭을 처리할 수 있다.
- **B:** 화면과 발화의 후보를 각각 생산하고 결합한다. 표현된 관계가 충분하고 일의적이면 코드 결합이 가능하다. 새 범위가 필요하면 원 생산자가 원본에서 후보를 확장한다. 구체 B의 visual 경로에는 detector/OCR/local semantics parser 의존을 명시했다.

QuickSet은 부분 의미의 코드 결합을, OmniParser의 동일 최종 모델 비교는 화면 표현을 명시적으로 생산했을 때의 정확도 개선 가능성을 뒷받침한다. **VIA의 시간에 따른 지칭 정확도나 producer 소유권 자체의 우위가 입증된 것은 아니다.** 추가 cloud parser/producer 비용, 잘못된 영역 분할과 crop의 맥락 손실을 함께 남겼다.

초기 기본으로 **A**를 추천한다. VIA에는 자유로운 문서 부분 범위, 순서와 정정이 있고 현재 B의 정확도 근거는 더 좁은 화면 대상 연결에 있다. **A1 제한된 원본 crop/cache**와 **A2 영향 부분 재판단**으로 media와 재처리 비용을 보완한다. **A4 동일 parser 보조 입력**도 공개한다. A4만으로 B의 정확도 이익을 얻는다면 producer 소유 후보 구조의 추가 선택 근거는 약해진다.

근거: Magentic-One WebSurfer와 공동 media 입력, QuickSet, ReALM, OmniParser, Windows 관측 API. [통합 설계와 근거 적용 한계](04-screen-speech-grounding.md).

### 2.4 Agent 간 업무 인계: 기본 A 권고

**VIA 문제:** 조사 Agent의 결과를 사용자가 수정한 뒤 다른 Agent에게 발표자료를 맡기고, 다시 다른 Agent에게 메일을 맡긴다. VIA가 현재 조건과 공개 결과를 이어 주어야 사용자가 같은 설명을 반복하지 않는다. 외부 Agent의 비공개 기억과 실행 상태 전체를 이동시키는 요구는 아니다.

- **A:** 실제 위임 때 목적별 인계 묶음을 구성한다. 기존에 확보한 유효 자료와 참조도 사용한다.
- **B:** 공개 사건과 정정에 따라 인계용 업무 설명/관계를 지속 생산한다. 반복 인계의 구성 작업을 줄일 기회와 끝내 쓰지 않는 기록의 생산 비용이 있다.
- **C:** 필수 목표/조건은 VIA가 보내고, 지원 가능한 수신자가 manifest의 상세 자료를 선택해 읽는다. 읽기 지원과 권한/만료/철회, 외부의 추가 선택 비용이 필요하다.

초기에는 미래 인계의 반복률을 과대평가하지 않는 **A**를 추천한다. **A1 인계 묶음 cache**, **A2 확인된 같은 Agent native session 재사용**으로 반복 구성을 보완한다. session ID가 있다는 이유만으로 전달된 자료를 생략하지 않는다.

이 DP는 **QA03의 위임 시 준비 대기와 QA05의 전체 선생산 비용**이라는 실제 선택을 가진다. 다만 세 번째 중요한 QA 차이는 아직 부족하다. 새 N-H 인계 정확도를 제안했지만 B가 자동으로 더 정확하다고 쓰지 않는다. 공통 Task나 01의 기억을 단순 복제하는 B라면 별도 구조를 둘 이유도 사라진다.

근거: CrewAI task context, Deep Agents isolated/fork와 backend 읽기, Magentic-One ledger 재배포, OpenHands child session, OpenClaw/acpx의 지원 확인 후 재개. [계약과 실제 지원 범위](05-agent-handoff.md).

## 3. 나머지 세 문제의 결론

### DP-44: 독립 상세 설계, A 추천

중앙 Dispatcher가 비동기 완료를 회수해 다음 작업을 시작하는 A와 Stage가 준비된 입력을 소비하는 B는 실재하는 구조다. 그러나 A도 입력을 계속 받고 worker를 병렬로 시작한다. B가 직접 연결한다고 같은 의미 모델 호출이 사라지지 않는다. 현재의 정상 사용에서 제어 전달 절약이 중요한 QA 이익이라고 내세울 근거가 약하다.

**A를 사용하고 단순 진행 통지 준비 합치기와 의존 참조 인덱스로 보완하는 설계를 남긴다.** 정상적인 생산 경로 조합에서 중앙의 짧은 전이 자체가 중요한 대기가 되거나 실제 동일 변경 과제에서 국소 변경 이익이 확인되면 B와 주요 DP 지위를 다시 검토한다. [03](03-execution-coordination.md).

### Agent 선택: 독립 상세 설계, A 추천

요청의 의미와 후보 적합성을 함께 판단하는 A, 요청 계약 후 별도 selector를 실행하는 B 모두 실제 harness 메커니즘으로 만들 수 있다. B는 후보만 바뀔 때 선택만 반복할 수 있지만, 동일한 판단 모델을 한 번 더 둔다는 사실이 더 좋은 Agent 선택의 증거는 아니다. AgentCard의 기능 선언은 비교 성능 정답도 아니다.

**초기 A와 공통 적격성 검사를 추천한다.** N-S는 같은 후보군에서 독립 근거로 허용 가능한 Agent 집합을 판정해야 한다. 실제 후보와 반복 선택 부하가 정해지고 별도 선택 문맥이 중요한 정확도/지연 이익을 보일 때 B를 재검토한다. 새 Agent 연동과 기존 wire 형식 변경을 같은 QA04 과제로 섞지 않는다. [06](06-agent-selection.md).

### DP-42: 독립 상세 설계, A 추천

두 안 모두 Conversation, Request, Task와 실행의 수명을 구별한다. A는 모듈화한 Core에서 관련 변경을 함께 확정하고, B는 대화/업무 서비스가 각자 접수한 사실을 반영한다. B의 독립 writer와 장애 경계는 가능하지만 A에도 짧은 transaction, 비동기 worker와 별도 논리 상태가 있다.

**A를 추천하고 저장 admission과 읽기 snapshot을 보완으로 남긴다.** 정상 부하에서 대화와 업무의 writer 경합이 중요하거나 독립 fault domain 자체가 상위 요구가 되면 B의 비용을 감수할 이유가 생긴다. 업데이트/재시작만을 대표 이익으로 제시하지 않는다. [07](07-lifecycle-boundaries.md).

## 4. 기존 아홉 항목을 어떻게 읽는가

| 이전 항목 | 현재 읽을 문서 | 이전 자료의 역할 |
| --- | --- | --- |
| 문제 1 + DP-45 | **01** | DP-45의 원본/게시/철회/복구 계약을 통합. 이전 도식과 논의 이력은 보존 |
| 문제 2 | **02** | 의미 실행과 문맥 수명 선택 |
| DP-44 | **03** | 비동기 단계의 후속 활성화 선택. 02에 흡수하지 않음 |
| 문제 3 + DP-47 | **04** | 당시 관측/원본/후보/정정 계약을 통합하고 실제 B 생산과 결합 근거 보강 |
| 문제 4 | **05** | 외부 수신자를 위한 인계 계약 |
| 문제 5 | **06** | Agent 적격성과 목적별 적합성 판단 |
| DP-42 | **07** | 상태 확정과 서비스 경계 |

현재 분석의 이해를 위해 먼저 이전 아홉 문서를 모두 읽을 필요는 없다. 새 01~07과 근거 원장이 현재 분석의 진입점이며 기존 문서는 세부 도식/역사와 차이를 추적할 때 읽는다. 기존 ADR이나 reference Architecture의 내용을 자동 교체한 것은 아니다.

## 5. 추천 구조는 함께 동작할 수 있는가

추천 조합은 **01A + 02B + 03A + 04A + 05A + 06A + 07A**다. 네 주요 DP의 모든 보완을 동시에 기본으로 켜는 제안은 아니다.

1. 07A의 모듈화한 Core 안에서 03A가 짧은 전이로 비동기 job을 연결한다.
2. 02B의 공통 대화 해석은 01A의 최근 작업 문맥을 사용한다. 긴 요청 실행은 필요한 유효 근거 참조와 좁은 문맥을 받는다. 01A를 모든 worker에 전체 대화를 복제하는 뜻으로 해석하지 않는다.
3. 화면 지칭이 필요하면 04A가 당시 원본으로 binding을 생산한다. 최종 채택된 근거/대상은 01의 다음 해석 입력에도 재사용될 수 있다.
4. 06A가 현재 요청과 실제 후보 정보를 함께 판단해 Agent를 제안한다. 05A는 채택된 목적/조건과 같은 유효 자료로 외부 인계 계약을 구성한다.
5. 07A가 관련 요청/업무/송신 의도를 확정하고, 외부 수신/수행 사실과 실제 사용자 전달은 별도로 기록한다.

이 조합에서 01과 05가 같은 자료를 재사용하면 한 번의 생산/조회 비용만 센다. 02B의 별도 의미 실행이 03B의 Stage를 요구하지 않으며 03A의 중앙 조정도 07B의 별도 서비스를 막지 않는다. 해당 2×2 조합은 [02](02-interpretation-execution.md)와 [03](03-execution-coordination.md)에 명시했다.

## 6. 완성의 범위

일곱 문제의 포함/상세 유지, 구조와 상태, 실제 근거, 같은 장면 비교, QA 인과, 반증, 추천과 tactic을 정리했다. 완료하지 않은 실증을 남은 분석처럼 숨기지 않는다. **실제 차이의 크기와 제품 의존의 지원/가격/메모리 적합성은 구현/실행 후 확인할 영역**이다. 제한된 확인 방법은 각 본문의 마지막 절과 [09](09-qa-tradeoffs.md)에 준비했다. 현재 결과로 새 성능 수치나 점수를 만들지 않는다.
