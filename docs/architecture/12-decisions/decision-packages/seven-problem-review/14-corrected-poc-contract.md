## 1. 이번 실행의 목적과 승인

사용자는 [13 사용자 리뷰](13-poc-user-review-and-remeasurement.md)에 주석으로 답하고, 기본 기능과 계측을 보완하여 실제 테스트하도록 요청했다. 실제 UI 구조가 같으면 callback 시간을 비교하는 것을 허용했다. 프로세스·단계별 메모리와 현실적인 미래 기능 추가의 변경 범위를 요구했으며, 모든 방안의 모든 QA에 구조적 직관과 실제 측정의 연결 설명을 요청했다.

**구조상 예상 이익을 실제로 확인할 수 있는 사용 조건을 포함한다.** 예상과 다른 결과도 보존하며 원인을 구현 미충족, 입력 조건, 모델·서비스 변동 또는 구조 가설 반증으로 구별한다. 특정 안의 승리를 만들어 내기 위해 정답, 실패 분모, 호출 비용, 모듈 포장을 바꾸지 않는다. 예상을 확인하는 것과 예상에 맞는 수치만 고르는 것은 다르다.

계획·설계 해석·통합은 주 담당, 코드 개발·실행·모델 호출과 파생 분석 코드는 사용자 지정 **GPT-6.1 Sol High** 담당들이 수행한다. 이전 결과와 freeze는 보존한다. reference Architecture, accepted ADR, COMMON-28, 기존 QA 정의·목표·점수는 변경하지 않는다.

| 구분 | 새 위치 |
| --- | --- |
| 후보 | `prototypes/candidates/four_dp_poc_v2/` |
| 입력·별도 정답·실행기·분석기 | `benchmark/architecture/four_dp_poc_v2/` |
| 원시·동결·보고 | `results/architecture-evaluation/current/four-dp-qwen37-review-v2-20261018/` |

이 문서는 구현 전에 합의할 기능과 측정 계약이다. 실제 소스·실행 파일·fixture·oracle·모듈 registry의 해시는 기능 검사 후 결과 디렉터리의 freeze에 고정한다. 구현 중 구체화와 변경 이유는 freeze 전에 기록한다. formal 실행 이후 변경은 새 phase/freeze로 분리한다.

## 2. 공통 조건

- 기본안은 01 A/B/C, 02 A/B, 04 A/B, 05 A/B/C의 **10개**다. 문서의 04는 사용자 순서 DP3 화면 지칭, 05는 DP4 인계다.
- 기존 네 사례를 각 세 번 적용하는 **120회 기본 실행**을 원칙으로 한다. 기존 실패 사례를 제거하지 않는다. 원시 입력 표현의 변경과 oracle의 계약 오류 수정은 판본·이유를 남기고 같은 DP의 모든 안에 적용한다.
- evaluator의 고정 목록을 합산한 기본 실행의 분모는 **QA01 261건, QA03 243개 목표**다. DP별로 QA01은 108/60/30/63건, QA03은 108/48/24/63개다. 화면의 중간 입력과 정정, Agent 질문 통지는 첫 응답 대상이 될 수 있지만 모두 새로운 완료 목표가 되지는 않는다.
- 의미·vision 모델은 기존 고정 Qwen `qwen3.7-plus-2026-05-26`을 유지한다. 실제 ASR/TTS와 로컬 Qwen 가중치는 실행하지 않는다. 음성은 전사와 관측 사건으로 대체한다.
- 수신 Agent도 실제 Qwen 호출과 제한된 자료 읽기 도구로 구현한다. 상용 Agent 제품의 통합 성공으로 확대하지 않는다.
- 인계의 수신자는 명시적 접수·반환 사건을 가진 작은 model-backed receiver shim이다. 이 수신자의 내부 의존성인 Qwen HTTP 전송→반환 구간을 downstream 역할 구간으로 분류한다. VIA의 로컬 전달·receipt·원본 serving은 포함한다. provider 내부 연산과 네트워크를 추정해 나누지 않는다. 이 프로필의 QA03은 API 경계 proxy임을 밝히고 실제 전체 wall time과 제외 구간을 함께 보고한다. 상용 원격 Agent의 network 비용을 분리해 측정한 결과는 아니다.
- 비용은 이전과 같은 고정 가격표(입력 $0.40/M, 출력 $1.60/M)에 실제 usage를 곱한 비교값이다. 현재 청구서 금액을 보장하지 않는다. 실패·재시도·미소비 생산·수신자 비용을 역할별로 남긴다.
- 새 campaign 모델 비용 관리 상한은 **$4**다. 기능 확인과 기본·보완·진단을 모두 포함한다. 기존 약 $0.72와 합쳐 이전 $5 범위 안에서 진행한다. 초과 예상 시 불필요한 진단을 먼저 줄이며, 미실행을 실행 완료라고 쓰지 않는다.
- 결과 전 모델 설정, 역할별 최대 출력, 복구 한도, 동시 호출 조건, 순서와 제외 구간을 고정한다. 비교 순서를 교차해 어느 한 안이 항상 먼저 실행되지 않게 한다.
- 후보에는 실제 질문·관측·허용 원본만 공급한다. 정답 ID, 정답 좌표, 기대 문장·금액 등 evaluator-only oracle는 후보 코드·prompt에 전달하지 않는다.

## 3. 측정 사건과 실패 처리

### QA01: 실제 채택된 내용을 전달하는 첫 callback

`INPUT_CAPTURED → 의미/대상 판단 → ADOPTION_COMMITTED → CONTENT_DISPLAY_PROXY`의 실제 시각을 남긴다. 예를 들어 대상 x/y와 보고서 작성 의도가 채택되면 자료 가공 전에도 그 의도를 안내할 수 있다. 단순 접수·미해결 지칭 반복·내부 proposal은 첫 응답으로 세지 않는다.

사용자 승인에 따라 UI 경로가 같은 이번 비교는 callback을 endpoint로 삼는다. 결과명에 `DISPLAY_PROXY`를 표시한다. UI 단계 자체의 메시지 수·분할·전달 경로가 다른 비교를 추가하면 그 비용을 별도로 계측한다. 첫 응답이 최종 답변인 사례에서는 QA01과 QA03이 가까워도 정상이다. 차이를 만들기 위해 가짜 후속 일을 추가하지 않는다.

실제로 제시한 구체적 응답이 틀렸어도 실제 시간은 남기고 정확도를 별도 판정한다. 첫 오답을 나중 정답의 시각으로 바꾸지 않는다.

### QA03: 사용자 목표별 실제 VIA 처리

사용자 입력과 목표의 연결은 의미 판단의 출력이다. 미리 후보에게 정답 Task를 주지 않는다. 관계가 채택된 뒤에도 시작 시각은 실제 원래 입력 시각을 참조한다.

- 새 독립 요청은 새 사용자 목표로 연결한다.
- 정정과 확인 답변은 관련 기존 목표와 revision에 연결한다.
- Agent 통지·질문은 관련 목표에 연결하며 통지 자체를 새 사용자 목표로 만들지 않는다.
- 구체적 진행 안내와 실제 상세 결과·필요한 상태 연결 완료를 구별한다.
- VIA 모델, 큐, 읽기, 복구·재판단은 포함한다. 실제 외부 Agent 처리와 해당 목표의 사용자 대기만 기존 인과 경로 정의대로 제외한다.
- 잘못된 결과의 실제 시간과 의미 실패는 별도 보존한다. 모델 출력이 비었다는 이유만으로 목표를 성공 완료하지 않는다.

`GOAL_COMPLETE`는 필요한 출력 형태·상태 연결 등 완료 계약을 만족한 실제 terminal, `GOAL_FAILED`는 한정 복구 후 완료하지 못한 terminal이다. 내용의 정답 판정은 별도 oracle가 한다. source quote 검증만으로 요약·업무 정답을 증명하지 않는다.

### 실패 6건을 빼고 빠른 평균을 만드는 일을 반복하지 않는다

모든 예정 입력·목표의 목록을 실행 전 evaluator에 고정한다. 후보가 사건을 남기지 않아도 분모에서 사라지지 않는다. 실제 복구 시도와 그 시간·토큰을 모두 기록한다.

| 관측 | 표시 |
| --- | --- |
| 첫 내용 응답과 목표 종료가 관측됨 | 실제 값과 기능 성공/실패를 각각 보고 |
| 빈 응답 후 복구 성공 | 원래 입력부터 첫 유효 내용·실제 완료까지의 전체 값, 복구 비용 포함 |
| 복구 소진·종료 미관측 | 실패 건수와 실패까지 실제 시간, QA 미관측 건수 표시 |
| 일부만 관측된 평균 | 진단 표로만 제공. 전체 완료시간의 우열/승자 근거로 사용하지 않음 |

고정 벌점 시간을 만들거나 빈 반환 시간을 성공 완료시간으로 대체하지 않는다. 첫 응답 coverage와 목표 completion coverage, 별도 기능 성공률을 시간표 바로 옆에 둔다. 요구된 완료가 누락되면 결과 비교 상태를 `INCOMPLETE`로 명시한다.

화면 입력의 v2 보완은 원시 pointer/path 사건으로 만든 공통 overlay를 같은 PNG에 표시하는 방법을 포함할 수 있다. 정답 bbox나 target ID를 overlay로 만들지 않는다. 원본 PNG·원시 좌표·변환된 PNG·변환 규칙을 함께 저장한다. 기존 기대 지칭 집합은 유지한다. 새로운 native source 지원이 없는 장면에 정답 기하를 원래 관측인 것처럼 넣지 않는다.

화면 지칭의 완료는 현재 revision의 지칭 집합 채택과 표시다. 자료의 업무 분석까지 VIA에 넣어 QA03을 늘리지 않는다. 해당 경우 첫 응답과 완료가 같을 수 있다.

### 미래 기능으로서의 현실성

- [A2A 공식 규격](https://a2a-protocol.org/latest/specification/)은 작업 상태와 artifact의 점진적 전달을 다룬다. 따라서 전체 답변만 받던 VIA가 부분 결과·수정 결과를 반영하는 C04는 현실적인 확장이다. 지정 section과 VIA의 전달·음성 대기 관리까지 규격이 구현해 준다는 뜻은 아니다.
- [MCP 2025-06-18 Resources 규격](https://modelcontextprotocol.io/specification/2025-06-18/server/resources)은 resource URI와 변경 통지를 제공한다. 자료가 바뀌는 동안 파생 답변·기록의 출처와 사용 가능 범위를 관리해야 한다는 C05/C06의 환경 근거다. 부분 철회는 VIA에서 추가한 기능 요구이며 MCP 규격의 자동 보장이라고 하지 않는다.
- [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)와 [persistence](https://docs.langchain.com/oss/python/langgraph/persistence)는 중단·재개와 지속 상태의 실제 지원 근거다. 여러 요청·승인·정정이 진행 상태와 다시 연결되는 VIA 변경 과제를 정당화하는 참고이며, VIA의 정정 의미 판단을 해결했다는 증거는 아니다.

공식 자료 확인일 2026-10-18. 외부 기능의 존재는 변경 과제의 현실성을 뒷받침하며 A/B/C의 수정 모듈 수를 미리 결정하지 않는다.

## 7. QA06 breakdown

현재 원격 모델 프로필에서는 Qwen 가중치·원격 KV를 로컬 RAM에 넣지 않는다. 각 PID의 역할과 PPID, 시각, 실제 RSS, 실행 phase를 저장한다. 같은 시점의 프로세스 기여 합을 기준으로 peak를 설명한다.

추가로 입력 원본·이미지, 유지 문맥, 요청별 상태, 생산 후보/기록, 직렬화·HTTP buffer 등 실제 객체의 논리 크기와 생존 단계를 기록한다. 논리 크기와 RSS는 다른 측정이며 합산해 빈틈없는 RAM 분해처럼 표시하지 않는다. 초기 runtime 기준값과 실행 중 증가량을 같은 run에서 보고한다. 기존 36.60MB를 모든 실행의 불변 기본값으로 쓰거나 2.49MB만 설계 비용으로 떼지 않는다.

## 8. 실행 순서와 최종 산출물

1. **사전 기능 검사:** deterministic contract double로 누락/정정/현재성/기하/권한/출력 계약을 검사. 실제 모델 정확도 결과로 보고하지 않음.
2. **작은 실제 calibration:** 실제 모델이 새로운 출력 계약을 수행할 수 있는지 확인. 모든 기록·비용 보존. 출력 용량·프로토콜 결함을 고친 뒤 formal freeze. 같은 개발 사례로 계약을 보완했다는 범위를 공개하며 blind holdout처럼 설명하지 않음.
3. **기본 120회:** 같은 새 계약과 입력으로 모든 기본안. 결과 후 불리한 실행을 삭제하거나 조용히 재시도하지 않음.
4. **독립 QA04 변화:** baseline 모듈 registry를 고정한 scratch patch와 수용 검사. 새 기능은 기본 runtime 수치에 섞지 않음.
5. **선택 후 보완:** 기본 결과의 실제 약점을 기준으로 필요한 사례만 별도 phase에서 비교. A2, A1, A4/B4, C2의 기존 정의와 번호를 유지하며 자동 누적하지 않음. 새 보완이면 번호·기능·이유를 먼저 기록.
6. **검토와 보고:** QA×안별 예상, 실제값, 분모/실패, 호출·읽기·상태·대기 원인, 반대 조건, 보완 전후를 연결. 실험 기록을 재생하는 자료도 새 generation으로 제공.

결과 보고서에는 각 DP마다 다음 표를 둔다: **QA → 구조상 예상 → 예상이 성립할 시나리오 → 실제값 → 실제 단계·토큰·변경 모듈·메모리 근거 → 일치/불일치 이유 → 선택에 미치는 영향**. 원값·같은 사례·모든 반복과 실패 기록으로 되돌아갈 수 있어야 한다.

이번 작업의 완료는 새 코드가 존재하는 시점이 아니라, 모든 기본안 실행·필요한 기능 복구·QA04 실제 변경·메모리 계측·설명 보고서와 검토가 끝난 시점이다. 반대안의 이익이 확인되지 않은 축은 미확인/동점으로 기록하고 다른 QA의 숫자로 대신하지 않는다.

모든 기본·보완·calibration 호출은 같은 $4 캠페인 원장을 사용한다. 실행 전 usage 기반 비용 전망은 여유가 있지만 실제 사용량과 예약으로 계속 제한한다. 보완의 실패·복구·토큰도 포함하며, 전후 비교의 날짜·phase를 공개한다. 보완 후 좋아진 일부 사례로 기본 결과를 소급 수정하거나, 다른 시점의 작은 서비스 지연 차이를 구조 효과로 확정하지 않는다.

## 10. 원문 행 번호 표현의 공통 민감도 확인

2026-10-18, 최초 BASIC 결과를 읽고 진단 실행 전에 기록. DP05 E4 첫 반복에서 A와 C의 일부 수신 결과가 실제 인용이 있는 행을 한 줄 앞 번호로 반환해 복구 후에도 완료되지 않았다. A/B/C의 32개 실제 요청과 102개 원본 구간을 대조한 결과 payload의 시작·끝 범위와 실제 원문은 일치했다. 다른 offset을 검증한 harness 오류는 발견되지 않았다. 다만 모든 안이 `start_line/end_line`과 번호 없는 다중 행 원문을 제공해 모델이 행을 직접 세어야 했다.

이 공통 입력 표현과 안별 자료 구성의 상호작용을 구조 자체의 인계 실패로 단정하지 않기 위해 **E4 × A/B/C × 3회, 총 9회**의 독립 진단을 추가한다. 위 120회 BASIC과 27회 보완 및 아래 §11의 업무 인계 기본 기능 교정을 마친 뒤, 교정된 같은 실행 파일에서 수행한다. 기존 결과·실패·비용을 보존하고, 진단에서 좋아진 수치를 기본 비교의 실패 자리에 넣지 않는다.

- 동일한 원문 passage의 모델 전달용 표현에 실제 원본 행 번호를 붙인다. host 원문·판본·범위·인용 검사·정답·복구 한도는 바꾸지 않는다.
- 원문을 한 벌 더 넣는 대신 전송용 복사본의 텍스트를 번호가 있는 간결한 표현으로 바꾸고, 인용에는 번호 prefix를 포함하지 않도록 같은 설명을 적용한다. 요약·자유문 statement에는 원본 행 번호를 만들어 붙이지 않는다.
- A의 가공·수신, B의 생산·수신, C의 실제 읽기·복구에 같은 공통 변환을 적용한다. 특정 안이나 정답을 아는 사례 분기를 만들지 않는다.
- 변환 전 payload와 실제 전송 요청을 모두 보존한다. 시작 행·빈 줄·범위·중복 번호를 offline 검사한 뒤 별도 소스·실행 파일·목록을 동결한다.
- 동일 E4의 안별 세 반복과 고정 인계 목표를 모두 보고한다. 추가 입력 토큰, 실패·복구, VIA·수신자 시간과 전체 경과시간도 포함한다.

이 진단은 원문 표현의 민감도를 확인한다. 전체 네 사례를 다시 실행한 새 기본 성능이나 모든 인용 오류의 해결을 주장하지 않는다. 실제 실행 결과를 본 뒤 더 유리한 표현으로 반복 조정하지 않으며, 같은 $4 캠페인 상한을 유지한다.

## 11. 업무 인계의 기확보 근거 연결 누락 교정

2026-10-18, 추가 교정 실행 전 기록. 최초 BASIC의 실행 경로 검토에서 A가 이전 인계의 VIA 가공 단계에서 실제 읽은 원본을 후속 인계의 공통 기확보 근거로 받지 못하는 것을 확인했다. `05-agent-handoff.md` §2.2·§4.1은 A에도 이미 확보한 유효 근거를 제공한다고 명시한다. 현재 코드에는 별도 `acquire` 입력의 읽기만 공통 근거에 추가되고, 실제 가공 중의 읽기는 반환 묶음과 인계 이력에만 남는다. 따라서 이 차이를 A 구조가 본래 부담해야 하는 재조회 비용으로 설명하지 않는다.

이는 선택 보완 tactic이 아닌 기본 기능 누락이다. 기존 120회와 소스·실행 파일은 보존하고, 별도 복사본에서 실제 VIA의 원본 읽기 결과를 공통 근거에 연결한다. 현재 판본·접근 허용 범위·철회 검사를 유지하고, ABC 모두 동일한 실제 확보 근거 보존 규칙을 적용한다. 미래 목적이나 정답을 보고 근거를 미리 선택하지 않으며, 수신자 내부 상태를 무조건 VIA의 지식으로 복사하지 않는다. 구체적인 소유 경계와 현재성 검사는 구현 검토 후 새 freeze에 기록한다.

- **DP05 네 사례 × ABC × 세 번, 36 episode 전체를 다시 비교한다.** A의 유리한 사례만 다시 실행하거나 과거 B/C의 숫자와 합치지 않는다.
- 동일 원본·질문·목표·Qwen 모델·동시 호출 한도·복구 한도를 유지한다. 행 번호 표현 진단은 이 36회와 분리한다.
- 실제 읽기 결과의 보존·중복 제거·판본 변경·접근 철회·후속 전달을 먼저 offline 검사한다. 기존 QA04 변경 과제도 새 baseline에서 수용되는지 확인하고 차이가 있으면 보고한다.
- 이전 36회는 누락이 있었던 구현의 증거로 남긴다. 발표용 DP05 기본 비교는 교정된 새 36회 전안 결과를 사용하며, 실제 재사용이 일어난 횟수와 남은 읽기·가공·수신자 비용을 함께 제시한다.
- 충분한 근거가 있어도 모델이 재조회를 선택할 수 있다. 재사용 성공을 보장하도록 답변이나 분기를 강제하지 않는다.

별도 `acquire` 입력을 추가하는 세 episode 진단은 실행하지 않는다. 그 방식은 이미 확보한 조건의 분기만 확인하고 기본 흐름의 연결 누락을 고치지 못하기 때문이다. 전체 예상 실행 수는 calibration 26 + 최초 BASIC 120 + 보완 27 + DP05 교정 36 + 행 번호 진단 9 = **218 episode**다. 모든 실제 호출은 기존 $4 원장과 상한에 포함한다.

## 12. 실제 공급한 인접 원문 범위의 검증 누락 교정

2026-10-18, 최종 교정 실행 전 추가 기록. §11의 교정 실행 중 B E3 첫 반복의 회의자료 결과에서, 실제로 제공한 같은 원문의 2–3행과 4행을 모델이 집계 출처 범위 2–4행으로 표기했다. 사실별 quote와 행은 원문에 일치하고 두 공급 구간 사이에 빈 행 범위가 없었다. 하지만 host는 하나의 공급 passage 안에 전체 집계 범위가 들어가야만 인정해 결과와 한 번의 복구를 모두 거절했다. 실제 프롬프트는 인접 원문 범위의 합집합을 금지하지 않았다. 따라서 이를 미공급 원문의 인용이나 B의 의미 판단 실패로 분류하지 않는다.

실제 요청·공급 원문·quote·검사 함수의 근거는 [범위 검증 감사](../../../../../results/architecture-evaluation/current/four-dp-qwen37-review-v2-20261018/analysis/dp05-corrected-union-span-audit.md)에 남겼다. 입력부터 55.012초의 실패와 미표시 결과는 그대로 보존하며, 사후 검사로 당시 실제 완료 사건을 만들어 넣지 않는다.

알려진 기본 검사 결함을 최종 비교에 포함하지 않도록 다음을 수행한다.

1. 진행 중인 episode는 끝까지 기록하고 다음 job 접수 경계에서 §11의 중간 phase를 중단한다. 완료 행, 실제 비용, 아직 실행하지 않은 계획과 중단 이유를 보존한다. 중간 phase를 36회 완료로 보고하지 않는다.
2. `dp05_sources.rs`의 공통 검사만 최소 수정한다. 같은 source·판본·단위의 실제 공급 구간이 빈틈없이 덮는 범위는 인정한다. 현재 판본·현재 허용 범위·정확한 원문 quote 검사는 유지하고, 빈틈·다른 판본·철회 범위·잘못된 quote를 인정하지 않는다.
3. 동결 전 양성·음성 기능 검사와 실제 wire 검사를 수행하고 독립 검토한다. 모델·프롬프트·입력·정답·복구 한도는 바꾸지 않는다. 특정 안이나 특정 정답을 위한 예외를 추가하지 않는다.
4. 새 source·binary·freeze에서 **ABC 네 사례 × 세 번, 36회 전체**를 비교한다. 앞선 중간 phase의 성공 행도 최종 표에 섞지 않는다. 최종 effective BASIC 120회는 DP01/02/04의 84회와 이 새 36회다.
5. 행 번호 표현 진단 9회는 이 최종 교정 binary에서 별도로 수행한다. 이미 합의한 표현 변화 외에 수신자 입력이나 검사 의미를 바꾸지 않는다.

최종 실제 episode 수는 앞선 218회 계획에 중간 phase에서 실제로 수행한 건수를 더한 값이다. 모든 호출은 같은 **$4 상한** 안에 포함하고 중간 비용을 제외하지 않는다. 이 조치는 알려진 기본 기능 결함을 고치는 것이며 선택안의 정확도 tactic으로 계산하지 않는다.

경계 중단 결과는 **11회 완료·25회 미실행**이다. 진행 중인 API를 취소하지 않았고 모든 완료 행의 원시·usage를 보존했다. 따라서 새 전체 실행 계획은 **229 episode = calibration 26 + 최초 BASIC 120 + 보완 27 + 중간 교정 11 + 최종 교정 36 + 번호 표현 진단 9**다. 최종 기본 비교 모집단은 여전히 120회이며, 중간 11회의 성공도 포함하지 않는다. 중단 직후 전역 usage 원장은 939호출·$1.6487404, 미확인 usage 0이었다.
