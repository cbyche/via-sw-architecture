# DP44 후보: 개별 응답 생성과 묶음 생성

> **2026-10-21 현재 DP44 대안에서 철회:** 응답 내용은 Downstream Agent가 제공한다는 사용자 정정에 따라, 추가 문안 생성의 묶음 단위를 DP44의 주 비교로 사용하지 않는다. 아래는 철회된 가정의 계산 이력이며 새 DP44의 예상값·평가 근거·실측으로 사용할 수 없다. [현재 대화 전달 구조 재정립](dp44-conversation-delivery-reset-20261021.md)을 읽는다.

## 1. 새 비교의 질문

사용자는 기존 Stage B를 고집하지 않고 A가 기존 QA에서 불리해지는 새 대안을 요청했다.

**응답 생성 모델의 실행 단위를 사건 하나로 둘 것인가, 여러 독립 응답 항목을 하나의 모델 실행에 담을 것인가?**

- A: 중앙 비동기 Dispatcher가 모델 생성이 필요한 각 응답을 별도 job으로 즉시 시작한다.
- B: 같은 대화/권한 범위에서 생성 가능한 응답 항목을 bounded Pending Set에 모아 한 모델 job으로 생산한다. 출력은 응답 ID별로 분리한다.

중앙 Dispatcher 자체가 사건마다 별도 모델 호출을 강제하지는 않는다. 이번 A는 원래 A의 중앙 실행 연결을 유지하면서 **응답별 생성 job**을 비교 기준으로 명시한 것이다. 원래 A가 이미 묶음 생성한다면 이 비용 차이는 없다. B도 중앙 실행 연결을 사용할 수 있다. 원래 Dispatcher 대 Stage와 다른, 조합 가능한 생성 단위 축이다.

단순 batching parameter 변경에 그치면 tactic이다. 여기서는 여러 응답 revision을 한 실행에 연결하고 부분 완료/무효화/재시도를 처리하는 상태와 계약까지 비교한다. 그 범위만으로 주요 DP의 규모와 중요성이 자동 입증되지는 않는다.

## 2. 공통 기능

- DP2에서 사용자 의미, Task 연결, 정정 범위와 전달할 사실을 확정한 후 시작한다.
- 확정된 질문/상태는 두 안 모두 코드로 즉시 표시한다. 짧고 완성된 문구에는 모델 호출을 강제하지 않는다.
- 묶는 대상은 실제로 추가적인 사용자용 표현/음성 문안 생성이 필요한 항목뿐이다. 보고서의 도메인 분석은 Agent가 끝낸 상태다.
- 같은 모델, 원본, 필수 전달 사실, output 길이 조건, 현재 판본/권한 검사와 전체 수용량을 사용한다.
- 음성은 각 응답의 문안이 준비되면 공통 S2S 경로에서 생성한다. S2S에 업무 tool call을 제공하지 않는다.
- A의 독립 호출은 병렬 실행 가능하다. B도 완결된 응답 record가 나오면 전체 batch 종료를 기다리지 않고 넘길 수 있다.
- 질문·결과의 통합/삭제로 의무 응답이나 분모를 줄이지 않는다. 서로 다른 Task의 답을 자연어 한 문장으로 합치는 구조가 아니다.

## 3. SW 실행 차이

### A: 응답마다 독립 job

```text
R1 → 공통 응답 규칙 P + R1 자료 → LLM job 1 → R1 문안 → S2S
R2 → 공통 응답 규칙 P + R2 자료 → LLM job 2 → R2 문안 → S2S
R3 → 공통 응답 규칙 P + R3 자료 → LLM job 3 → R3 문안 → S2S
```

각 job에 한 응답 revision과 cancel handle을 연결한다. 새 항목을 기다리지 않는다. 같은 규칙 P가 각 모델 입력에 포함되며 제공되는 prompt cache 할인은 허용한다.

### B: 여러 응답을 한 job에서 생성

```text
R1/R2/R3 → Pending Set
         → Batch Manifest [(R1, rev), (R2, rev), (R3, rev)]
         → P + 각 항목 자료 → LLM job
         → Record Demultiplexer
              ├─ R1 문안 → S2S
              ├─ R2 문안 → S2S
              └─ R3 문안 → S2S
```

Pending Set은 count/token/deadline 상한을 둔다. 숫자 예시에서는 최대 3건, 최대 수집 대기 150ms를 가정한다. 3건이 이미 모였으면 즉시 시작하고, 한 건뿐이면 기한 뒤 singleton job으로 진행한다. deadline이나 권한 조건이 다른 항목은 섞지 않는다.

출력은 각 항목의 `response_id`, `revision`, `text`, `speech_brief`를 가진 완결된 record다. batch의 마지막까지 기다리지 않고 닫힌 record부터 소비한다. provider의 비동기 Batch API 할인이나 서버 내부 inference batching을 가정하지 않는다. 애플리케이션이 한 prompt에 여러 응답 항목을 넣는 방식이다.

### 정정/취소가 겹칠 때

- A는 해당 응답의 job만 취소/무효화한다.
- B는 Manifest의 해당 항목을 무효화하고 늦게 나온 그 record만 게시하지 않는다. 다른 유효 항목은 보존한다. 이미 진행 중인 LLM 입력을 수정할 수 있다고 가정하지 않는다.
- 바뀐 항목은 새 revision으로 다시 준비한다. 한 항목 때문에 전체 batch를 항상 다시 실행하지 않는다.
- 누락/파싱 오류 항목은 ID별로 복구한다. 특정 항목의 출력에 다른 항목 사실이 섞였으면 기능 오류이며 재시도 비용을 기록한다.

## 4. 비용 차이의 인과

동일한 항목 3개를 생성할 때:

```text
A 입력 = 공통 규칙 P 세 번 + 개별 자료 세 개
B 입력 = 공통 규칙 P 한 번 + 개별 자료 세 개 + batch framing H
```

cached-input 단가를 적용해도 다음 조건이면 A가 더 비싸다.

```text
절감액 = (3 - 1) × P × cached-input 단가
         - H × 일반 input 단가
         - B에서 추가된 출력/실패/재시도 비용
```

이것은 특정 모델의 실제 청구액이 아니라 성립 조건이다. 무료에 가까운 cache, 짧은 공통 규칙, 드문 겹침, B의 추가 오류/재시도에서는 이익이 없어질 수 있다. 입력을 일부러 불필요하게 길게 만들어 절감을 확보하지 않는다.

## 6. QA03 계산 가정

세 개의 독립 목표가 같은 시점에 응답 준비 단계에 도착했다고 놓는다. 각 목표의 공통 선행 VIA 경로는 1.5초이며 외부 업무/사용자/재생 대기는 제거된 상태다. 필수 상세 표시는 음성 준비보다 먼저 끝난다고 가정한다.

- 항목별 출력: 120토큰
- 단일 호출의 출력 시작 전 처리: 0.8초
- 묶음 호출의 출력 시작 전 처리: 1.1초
- 출력 속도: 초당 200토큰
- 완결된 문안 이후 음성 준비: 항목별 1.2초, 서로 병렬
- 이 장면의 batch 수집 대기: 0초. 세 항목이 이미 준비돼 있으므로 150ms 상한을 강제로 기다리지 않는다.

```text
A 각 목표 = 1.5 + 0.8 + 120/200 + 1.2 = 4.10초

B 첫 번째 = 1.5 + 1.1 + 120/200 + 1.2 = 4.40초
B 두 번째 = 1.5 + 1.1 + 240/200 + 1.2 = 5.00초
B 세 번째 = 1.5 + 1.1 + 360/200 + 1.2 = 5.60초
B 평균 = 5.00초
```

B의 모든 목표에 마지막 종료시간 5.60초를 대입하지 않는다. A의 세 독립 호출 시간을 더하지 않는다. 실제 사용 중 S2S가 하나만 생성할 수 있다면 이 가정은 맞지 않으며 양안 같은 실행 한도로 다시 계산해야 한다.

## 7. QA05 계산 가정

공통 규칙 2,000토큰, 개별 자료 1,000토큰, 각 출력 120토큰, B의 framing 200토큰으로 놓는다. 가상 단가는 100만 토큰당 일반 입력 $2, cache 입력 $1, 출력 $8이다. 실제 provider 가격표가 아니다.

양안 모두 공통 규칙의 cache hit를 허용한다. cache 준비/쓰기와 음성 등 공통 비용은 아래 공통액에 포함됐다고 가정한다.

```text
3응답 A:
  cached 6,000 × $1/M + input 3,000 × $2/M + output 360 × $8/M
  = $0.01488

3응답 B:
  cached 2,000 × $1/M + input 3,200 × $2/M + output 360 × $8/M
  = $0.01128

가상 활동: 위와 같은 묶음 6개, 나머지 모든 공통 비용 $2.01072
A = $2.01072 + 6 × $0.01488 = $2.10000
B = $2.01072 + 6 × $0.01128 = $2.07840
```

해당 응답 생성 소계는 24.2% 감소하지만 **전체 활동 모델 비용 감소는 약 1.0%**다. 전자를 전체 비용 감소라고 쓰지 않는다. 추가 취소/실패 비용 차이는 이 예시에서 0으로 가정했으며 실제 관측에서는 모두 포함해야 한다.

cache 입력 단가가 $0.10/M이면 묶음당 prefix 절감 $0.0004와 framing 비용 $0.0004가 같아져, 추가 실패가 없어도 이 모형의 비용 이익이 사라진다.

## 8. QA04 숫자를 만들 때 둔 가상 모듈 분해

모듈 명칭과 개수는 실제 코드의 관측값이 아니다.

- C04 부분 결과 정정: A는 `response_state`, `composer`, `publication` 3개를 수정한다고 가정한다. B는 같은 3개와 `batch_manifest` 1개를 수정한다고 가정한다.
- C06 부분 사용 철회: A는 `source_policy`, `dependency_index`, `composer`, `publication` 4개를 수정한다고 가정한다. B는 같은 4개와 `batch_manifest`, `record_demux` 2개를 수정한다고 가정한다.
- A 평균 `(3+4)/2 = 3.5`, B 평균 `(4+6)/2 = 5.0`.

실제 B의 공통 manifest 계약이 처음부터 구간 의존을 전달한다면 이 추가 변경은 없을 수 있다. 이 숫자를 독립적으로 확인된 세 번째 trade-off 축으로 세지 않는다.

## 9. 참고와 판단

[Batch Prompting, EMNLP 2023](https://arxiv.org/abs/2301.08721)은 여러 샘플을 한 prompt에 넣어 공통 입력 비용을 나누는 메커니즘의 참고다. 그 논문의 데이터셋/모델 속도 결과는 VIA의 QA01/03 수치가 아니다.

[BatchPrompt](https://arxiv.org/abs/2309.00384)는 묶음 크기와 항목 순서가 출력 품질에 영향을 줄 수 있음을 다룬다. VIA에서 정답 보존이 자동으로 유지된다고 가정할 근거가 아니며, 출력 오류를 QA02/새 QA07의 최초 해석 오류로 바꾸어 세지도 않는다.

이번 B는 특정 조건에서 A보다 QA05가 낮은 기제를 갖는다. 그러나 예시의 전체 비용 이익은 작고, 기존 Dispatcher에 추가하는 tactic으로 구현될 가능성도 있다. **이 수치 예시만으로 강한 주요 DP를 확보했다고 결론내리지 않는다.** 실제 검증을 하려면 응답별 작업량, 겹침 빈도, cache, 출력 충실도와 부분 재시도까지 확인해야 한다.
