# DP44: 음성의 선행 준비와 발화 시점 준비

> **현재 판정: 주요 DP44 대안에서 폐기.** 사용자가 이 비교의 의미를 다시 물었고, 음성 합성·보관 시점의 조건부 손익만으로 요구한 DP44의 주요 구조 대안을 충족하지 못했다고 정정했다. 아래 설계와 식은 탐색 이력이며 현재 추천 A/B나 QA coverage 근거가 아니다. [최신 논의 정리](dp44-conversation-delivery-reset-20261021.md#0-지금까지의-결론과-dp44를-이어갈-방향)를 따른다.

> **후속 입력·출력 구분과 근거 한계:** 사용자 확인대로 Downstream Agent가 만든 텍스트를 S2S에 넣는다. 아래 ‘음성 준비’는 입력 WAV 생성이 아니라 S2S가 출력하는 오디오를 재생 전에 받아 보관하는 추가 설계 가정이다. LiveKit의 인용 예제는 고정 문구의 사전 TTS·첫 사용 cache·API 조회 중 대기 안내 재생이며, 여러 Agent 결과의 독립 선행 합성을 검증한 예제가 아니다. 또한 `session.say()`는 TTS plugin을 요구한다. VIA S2S에서 내용 보존, 독립 음성 생산과 재생 분리를 지원하는지는 확인하지 않았다. 아래 인과는 그 계약이 가능할 때의 조건부 비교이며 DP44의 강한 주 대안이 확보됐다는 근거로 사용하지 않는다.

> 2026-10-21 / 사용자 요구: 구현 가능한 두 구조에 더해 실제 QA 이익과 비용이 반대 방향으로 발생해야 함 / 설계 분석, 미구현·미측정·미선정

**주 비교는 A의 QA03 준비 완료 이익과 B의 QA05 불필요한 음성 생성 비용 절감이다.** RAM에 음성을 보관하는 기본 구현에서는 B의 음성 보관량이 작아지는 경로도 있다. 전체 VIA peak를 보는 QA06 우열은 미측정이다. QA01은 양안이 같은 내용을 즉시 UI에 표시하므로 동점이다. 이전의 [응답별 Workflow 대 상태 대조](dp44-workflow-and-reconciliation-20261021.md)는 이 교환을 만들지 못했으며 현재 강한 대안으로 권고하지 않는다.

## 1. 같은 입력과 책임

Downstream Agent 또는 VIA의 해당 책임자가 이미 작성·채택한 상세 내용과 음성 안내 내용을 받는다. DP2 의미 해석, 업무 계획과 문안 재작성은 추가하지 않는다. 음성 안내 내용이 별도로 필요한 경우 그 공급 계약과 비용은 양안 공통이다.

두 안 모두 Task/Request, 판본, 권한과 게시 조건을 확인하고 상세 텍스트를 즉시 표시한다. 음성 생성 완료나 다른 발화 종료를 UI 표시의 선행조건으로 만들지 않는다. 모델의 다중 접속도 양안 모두 허용한다.

공통 출력기는 한 대화의 실제 음성을 하나만 재생한다. 판본·권한 검사를 출력 직전에 적용하고 사용자 발화 시 즉시 중단한다. 준비 완료와 실제 전달을 분리하여 기록하며, 구판의 늦은 실제 전달 receipt도 역사적 사실로 보존한다. 재생 중단 자체로 Agent 업무를 취소하지 않는다.

## 2. A: 응답마다 음성을 미리 만들어 보관

```text
검증된 DeliveryItem ──→ 상세 텍스트 UI
       └─→ 응답별 AudioPreparationJob
                 └─→ AudioArtifactStore
                           └─→ 출력할 응답 선택 → 현재성 검사 → 음성 출력
```

- 응답 도착이 음성 준비 실행을 시작한다. 모델 호출의 입력은 제공받은 음성 안내 내용이며 업무 해석 tool call은 없다.
- 응답별 실행이 음성 chunk를 자기 산출물에 쓴다. 준비 실행은 현재 스피커의 발화와 독립적이다.
- 산출물은 `response_id + revision + voice_config`에 연결한다. 마지막 chunk 수신과 전체 범위·출력 참조 확정 후 준비 완료로 기록한다. 준비 중 streaming 재생도 가능하다.
- 기본 구현은 미전달 산출물을 메모리에 보관한다. 재생 완료나 유효한 철회 뒤 해제한다. 같은 내용을 잠시 멈췄다 이어 말할 때 이미 생성한 구간을 재사용한다.
- 정정은 해당 실행 취소와 구판 산출물 폐기를 유발한다. 이미 사용한 모델 자원과 취소가 전달될 때까지의 실제 사용량은 비용에 남는다.

## 3. B: 현재 발화가 음성 준비 실행을 소유

```text
검증된 DeliveryItem ──→ 상세 텍스트 UI
       └─→ PendingContentRegistry
                 └─→ 현재 발화 응답 선택
                           └─→ ActiveSpeechProducer → 현재 응답 버퍼 → 음성 출력
```

- 대기 중인 응답은 상세 내용·음성 안내 내용의 참조와 전달 의무만 유지한다. 아직 음성 생성 호출을 하지 않는다.
- 출력기가 현재 전달할 응답을 선택하면 그 발화 실행이 producer와 버퍼를 만든다. producer는 현재 발화 생명주기에 속한다.
- 기본 B에는 현재 응답용 producer 하나가 있다. 해당 실행이 종료·취소되고 출력권이 넘어가야 다음 producer가 생긴다. 모델 서버가 다중 접속을 못 해서가 아니라, 아직 전달하지 않을 음성의 생산과 보관을 피하는 기본 구조다.
- 현재 응답은 A와 같은 전체 안내 내용으로 모델을 한 번 호출한다. B만 작은 문장으로 쪼개 반복 호출하게 만들지 않는다.
- 전체 응답 데이터를 현재 버퍼에 모으고 전체 범위와 출력 참조를 확정하여 QA03 완료를 관측한다. streaming 재생은 허용하되 이 확인 이전에 prefix를 버려 전체 준비를 입증하지 못하는 구현은 비교에 쓰지 않는다. 현재 발화가 끝나면 버퍼를 해제한다.
- 따라서 B의 기본 버퍼 상한은 ‘현재 응답 한 개’다. 몇 초짜리 ring buffer만으로 전체 SDK·네트워크 메모리까지 제한했다고 주장하지 않는다.
- 대기 응답이 정정되면 내용 참조만 새 판본으로 바꾼다. 구판 producer가 없었으므로 그 음성 모델 비용이 발생하지 않는다. 이미 시작한 현재 응답은 A와 동일하게 실제 사용·취소 비용을 낸다.

**구조의 차이는 생산과 소비 사이의 중간 산출물이다.** A는 발화와 독립된 준비 실행과 음성 저장소를 가지며, B는 발화가 선택된 뒤에 실행과 현재 버퍼를 만든다. 두 안의 발화 우선순위를 같게 두어도 실행 시작, 상태 수명과 폐기되는 작업량이 달라진다.

## 4. QA03: 왜 실제 재생시간을 빼도 A가 빨라질 수 있는가

서로 다른 세 사용자 목표에 속한 Agent 결과 R1/R2/R3가 함께 준비된다. 세 목표의 최초 사용자 입력은 이 시점보다 앞서 있다. 의미·내용·권한은 같은 조건이며 모두 최종 전달 대상이다. 세 음성 준비가 서로 간섭하지 않고 각각 같은 VIA 시간 `g`가 걸린다는 설명용 조건을 둔다.

| 남는 준비 의존 | R1 완료 | R2 완료 | R3 완료 | 이 준비 부분의 목표별 평균 |
| --- | ---: | ---: | ---: | ---: |
| A: 세 준비 실행 병행 | g | g | g | g |
| B: 현재 producer 종료 뒤 다음 producer 생성 | g | 2g | 3g | 2g |

**이는 측정치나 전체 QA03 예상값이 아니라, 공통 선행 경로를 생략한 준비 부분의 의존관계 산식이다.** 실제 재생·사용자 청취·차례 대기 node는 QA03 계약대로 0초로 처리했다. B의 `R1 음성 생성 → R2 producer 시작 → R2 음성 생성`에서 앞 생성의 VIA 작업은 남는다. 앞 음성의 재생 길이를 더한 결과가 아니다.

원래 사용자 목표의 t0 이전에 끝난 준비는 현재 목표에 더하지 않는다. 시작 전에 이미 모든 음성이 준비됐거나 겹치는 준비가 없다면 이 이익은 줄거나 사라진다. 병렬 호출이 실제로 느려지는 모델 환경이면 각 호출의 실측 경로를 사용해야 한다. 모델 자원 경합을 가정해서 차이를 만들지는 않는다.

## 5. QA05: A가 감수해야 하는 실제 비용

R1을 전달하는 동안 대기 중인 R2가 유효한 새 판본 R2′로 교체되는 경우를 본다. 이 교체 관계는 DP2 또는 업무 사실 책임자가 이미 확정하여 전달한다.

| 동작 | A | B |
| --- | --- | --- |
| 구판 R2 도착 | 음성 준비를 시작 | 내용과 전달 의무만 등록 |
| R2′로 교체 | 구판 실행 취소·산출물 폐기, 새 음성 준비 | 아직 시작하지 않은 내용 참조 교체 |
| 음성 모델 비용 | 구판에서 실제 사용한 양 + 새 판본 사용량 | 새 판본 사용량 |

이 경우 A의 추가 비용은 **미전달 구판에 실제 사용한 모델 비용**이다. 텍스트를 다시 쓰는 LLM을 추가해서 만든 비용이 아니다. 단순히 SDK의 stream을 천천히 읽는다고 원격 생성 비용이 줄어드는 것도 아니다. B의 절약은 구판 호출 자체를 시작하지 않은 데서 나온다.

모든 응답이 그대로 전달되고 호출 방법·단가가 같으면 QA05는 비슷하다. 아직 미전달 범위를 보존 중인 응답을 중단 후 재개할 때 A는 남은 산출물을 재사용할 수 있다. B가 다른 발화로 전환하면서 해당 버퍼를 해제했다면 남은 내용을 재생성해야 하므로 A의 비용이 오히려 유리한 구간도 있다. 재생 완료 뒤의 재요청에 대비한 장기 cache는 기본 A에 포함하지 않은 별도 보완이다. 전체 COMMON-28 비용의 크기와 방향은 해당 사건과 재사용을 모두 포함하여 평가해야 한다.

## 6. 기존 QA 전체 판정

| QA | 이 비교의 직접 경로와 판단 |
| --- | --- |
| QA01 첫 응답 | 동점. 같은 구체적 텍스트를 같은 게시 조건 확인 뒤 바로 표시 |
| QA02 지칭 정확도 | 직접 차이 없음. 이미 채택한 지칭을 전달 구조 때문에 재채점하지 않음 |
| QA03 VIA 처리시간 | 준비가 겹칠 때 A 이익. B의 실제 producer 선행 생성 의존을 포함하되 재생·차례 대기는 제외 |
| QA04 변경 모듈 수 | 미확정. C04/C06 실제 변경 없이는 중앙화·상태 수만으로 차이 주장 불가 |
| QA05 전체 모델 비용 | 음성 준비 전 대기 판본이 대체되는 경우 B 이익. A는 이미 수행한 구판 음성화 비용 부담. 전체 묶음의 크기는 미측정 |
| QA06 최대 로컬 RAM | 기본 메모리 보관 구현에서 B 이익 경로: A는 여러 미전달 음성, B는 현재 응답 음성을 보유. 전체 제품 peak의 크기는 미측정 |
| 새 QA07 요청 의미 정확도 | 직접 차이 없음. 의미 해석은 같은 DP2 경로 |

RAM은 같은 음성 형식으로 비교하고 SDK 버퍼·현재 재생 버퍼·공유 자료를 중복 계산하지 않는다. 예를 들어 24kHz·16bit·mono 30초 PCM은 산술상 1.44MB다. 짧은 안내 몇 개로 수백 MB의 차이나 512MB 목표 통과·실패를 주장할 수 없다.

## 7. 선택 조건과 보완

- **A 선택 이유:** 겹치는 여러 응답의 준비 완료를 빨리 확보하고, 이미 만든 음성을 중단·재개 때 활용하고 싶다. 그 대가로 미전달 음성의 생성·보관·무효화 비용을 받는다.
- **B 선택 이유:** Agent 통지가 자주 최신 판본으로 바뀌고 사용자가 모든 중간 안내를 음성으로 듣기 전에 상황이 바뀐다. 아직 전달할 차례가 아닌 음성에 모델 비용을 쓰지 않는 것을 우선하고 후속 준비의 의존을 받는다.
- **A1 파일 보관:** 음성 artifact를 파일에 두어 메모리 비용을 줄일 수 있다. 파일 cache와 실제 I/O 비용을 포함해야 하며, 구판 음성을 이미 생성한 QA05 비용은 없어지지 않는다.
- **B1 다음 응답 선행 준비:** 다음 한 응답의 producer와 보관 상태를 추가할 수 있다. QA03 차이를 줄이는 대신 미전달 음성의 비용과 상태를 일부 받아들인다. 기본 B에 처음부터 이 보완을 의무로 넣지 않으며 B1의 실제 병행 의존을 따로 평가한다.

이 비교는 QA03 대 QA05의 구체적 비용 교환을 설명한다. QA01까지 차별화한 비교나 과정의 모든 QA coverage를 충족했다는 뜻은 아니다. 실제 사용에서 폐기 음성이 거의 없고 버퍼도 작으면 A의 비용 열세가 작아진다. 반대로 겹치는 준비가 거의 없으면 A의 QA03 이익이 작아진다. 이 두 조건이 비교의 반증·적용 경계다.

## 8. 구현 근거와 검토 범위

[LiveKit 음성 제어](https://docs.livekit.io/agents/multimodality/audio/)는 발화 실행과 중단을 제어하는 API를 제공한다. [사전 합성·보관 음성 재생 예](https://docs.livekit.io/agents/multimodality/audio/customization/)는 음성 생성과 재생을 분리하고 음성 frame을 보관해 다시 공급하는 실제 구현 경로를 제시한다. 이는 생산·소비 분리의 구현 참고이며 특정 S2S 모델이 동일 API를 지원하거나 VIA 성능이 검증됐다는 뜻이 아니다. 본 안의 S2S adapter에는 제공받은 내용을 음성으로 출력하고 완료 범위를 보고하는 계약이 필요하다. 별도 의미 판단이나 tool 호출 권한은 추가하지 않는다. 확인일 2026-10-21.

세 독립 검토는 실제 producer edge, t0 절단, 재생 대기 제외, 선행 생산의 불필요한 호출, 파일 보관 반례와 B의 전체 음성 완료 증거를 점검했다. 이 문서는 무한 upstream queue를 무시한 작은 ring-buffer 주장 대신 현재 응답 전체 버퍼를 사용하는 기본 B로 좁혔다. 설계와 계약 검토이며 실행 시간·비용·메모리 측정은 아니다.
