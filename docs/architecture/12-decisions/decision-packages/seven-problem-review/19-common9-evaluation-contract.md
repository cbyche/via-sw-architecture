# 모든 DP에 동일하게 적용하는 공통 9개 시나리오 평가 계약

2026-10-19 / `COMMON9-20261019` / 정식 모델 실행 전 계약

상태: 사용자가 **공통 대표 9개로 구현하고 재측정**하도록 선택했다. 연결된 후보와 실행기를 준비하는 중이며, 이 문서의 예정 수량은 측정 완료 수량이 아니다. 실행 manifest, 소스와 입력 및 oracle의 hash, 자원 설정과 사전 검사를 확인한 뒤 정식 실행을 동결한다. 결과는 [17 발표 결과](17-presentation-results.md)에 별도 절로 기록한다.

## 1. 평가 목적과 이전 계약의 보존

**모든 DP의 모든 방안에 같은 시험을 적용하고 같은 QA를 같은 모집단과 집계 방식으로 계산한다.** 특정 DP에 유리하거나 그 DP와 관련된 사건만 골라 대표 평균을 만들지 않는다. 해당 구조가 바꾸지 않는 경로도 분모에 남기므로 차이가 작거나 동점일 수 있다.

[COMMON-28-v1](../qa-candidate-package/common-scenarios.md)은 최초 공통 시나리오 원장이다. 이후 [DP-RELATED-v2](../qa-candidate-package/common-evaluation-population-plan.md)에는 DP별 관련 모집단을 당시 비교 방법으로 채택한 이력이 있다. 과거 결과를 소급해서 모두 계약 위반이라고 하지 않는다. 이번에는 사용자가 지적한 DP 간 일관성을 충족하도록 새로운 공통 대표 평가를 구성한다.

[18 조건 진단 계약](18-prediction-validation-contract.md)의 부분 실행은 보존한다. 그 사례들은 구조가 작동하는 조건을 설명하는 자료이며 이번 대표 점수에 합치지 않는다. 이전 발표 캠페인, 조건 진단, 이번 공통 캠페인은 각각 다른 입력 및 구현 세대다. **대표 결과는 새 캠페인만으로 구성한다.** 반복 수를 늘리기 위해 세 세대의 값을 합산하지 않는다.

이번 범위는 공통 시나리오 28개 중 9개의 연결된 PoC다. 전체 제품, 전체 28개, 모든 UC 변형의 검증이나 통계적으로 대표적인 사용자 분포를 주장하지 않는다. 기존 QA 의미와 우선순위, 목표와 점수 구간, accepted ADR 및 참조 Architecture는 변경하지 않는다.

모든 구성에 이 묶음을 **5회** 적용한다. 구성당 45episode이며 QA01 예정 215사건, QA03 예정 115목표, QA02 예정 75판정이다. 같은 사례의 반복을 별개의 사용자 상황으로 세지 않는다. S20과 S26의 모호한 짧은 답변은 확인 질문이 필요한 기능 검사에 남기며 지칭 집합 분모에 새로 넣지 않는다.

범위 조회, 재사용, 판본 변경, 화면 정정, 실제 전달 이력의 인계, 독립 사건 경합과 권한을 함께 포함하려고 이 9개를 선택했다. 자유 곡선 영역, 여러 페이지 이동, 음성 중단, 앱 재연결 등 빠진 상황의 성능이나 기능을 이 결과로 대신하지 않는다. 별도 진단을 나중에 추가해도 위 분모를 늘리거나 유리한 사례로 교체하지 않는다.

## 3. 한 DP만 교체하는 구성

발표 DP1/DP2/DP3/DP4는 저장소01/02/04/05에 대응한다. 아래 네 자리의 순서는 발표 DP 순서다. A/A/A/A는 비교 기준을 하나로 고정하기 위한 **실험 대조 구성**이며 최종 설계 채택이나 권고가 아니다.

| 고유 실행 구성 | DP1 근거 공급 | DP2 의미 판단 실행 | DP3 화면 지칭 | DP4 업무 인계 | 비교 목적 |
| --- | --- | --- | --- | --- | --- |
| A/A/A/A | A 유지 근거 | A 실행 경계에서 수용 | A 원본 공동 판단 | A 목적별 전달 | 공통 대조 |
| B/A/A/A | B 요청별 구성 | A | A | A | DP1 B |
| C/A/A/A | C 근거 기록 생산 | A | A | A | DP1 C |
| A/B/A/A | A | B 요청별 실행 | A | A | DP2 B |
| A/A/B/A | A | A | B 후보 생산 후 결합 | A | DP3 B |
| A/A/A/B | A | A | A | B 업무 기록 생산 | DP4 B |
| A/A/A/C | A | A | A | C 수신자의 선택 읽기 | DP4 C |

고유 실행은 **7구성 × 9사례 × 5반복 = 315episode**다. 발표용 10개 방안 행에서 네 DP의 A는 동일한 대조 실행을 재사용한다. 그것을 네 번 독립 측정한 것처럼 표본 수나 전체 비용을 늘리지 않는다. 고유 예정 관측은 응답 1,505건, 목표 805개, 지칭 525판정이다.

이 설계는 고정된 주변 구조에서 한 DP를 바꾼 효과를 비교한다. 다른 DP를 동시에 바꾼 조합의 상호작용이나 네 DP 이익의 합산을 입증하지 않는다. 같은 사례와 반복 번호의 구성을 교차 순서로 실행하며 정확한 순서는 결과 전에 manifest로 고정한다. 변동을 숨기기 위한 좋은 반복 선택이나 사후 순서 변경을 하지 않는다.

## 4. 연결된 실행과 공통 외부 조건

### 4.1 실행 책임과 정답 분리

- 공통 실행기가 입력 capture, Request/Task/revision, 권한, 실제 응답 게시와 목표 종료를 한 번씩 소유한다. 기존 독립 PoC의 `run()`을 이어 붙여 중복 응답이나 중복 완료를 만들지 않는다.
- DP1은 실제 허용 원본과 전달 이력에서 근거를 공급한다. A의 이미 확보한 유효 원문 재사용과 C의 유효 기록 소비를 허용하고, 준비 및 갱신과 미사용 생산을 비용에 포함한다.
- DP2는 근거 공급, 화면 지칭과 의미 판단을 포함하는 전체 workflow의 실행 정책이다. 뒤에 별도 해석 호출을 붙여 만든 비교가 아니다. A도 실제 작업 경계에서 새 입력을 수용하고 원래 workflow를 이어갈 수 있다. B는 독립 실행 상태를 가진다. 두 안 모두 동일한 capture와 현재성 검사를 거친다.
- DP3은 원본, frame, revision과 extent를 가진 실제 지칭 결과를 공통 workflow에 반환한다. native 선택이 실제 원본에 있을 때만 사용하고, 없는 선택이나 정답 crop을 시험자가 제공하지 않는다. B는 실제 화면 파서 생산과 필요 시 확장을 수행한다.
- DP4는 공통 의미 채택과 실제 획득 자료를 받아 인계한다. A가 이미 읽은 원문은 재사용할 수 있다. 모든 수신자는 같은 원문 범위 읽기 도구를 지원한다. 업무 기록이나 목록만 넘겼다는 이유로 실제 읽기와 수신자 비용을 생략하지 않는다.
- 최초 지칭, Task 연결, 정정 관계와 의미적으로 필요한 자료는 후보가 판단한다. evaluator의 기대 Task, goal, binding 집합을 후보에게 전달하거나 사건 ID로 조회해서 정답을 미리 구성하지 않는다. 제어 사건의 실제 Task ID와 권한 설정처럼 외부에서 관측 가능한 사실은 제공한다.
- source/revision/권한과 대기 출력의 유효성 검사를 공통 게시 경계에 연결한다. 의미 판단 중 바뀐 권한이나 revision을 옛 검사 결과만으로 통과시키지 않는다. 실제 구현 범위는 검사 결과와 함께 공개한다.

### 4.2 초기 상태와 시각

- 각 episode는 같은 원본 200턴, 완료 Task 20개, 사례에서 필요한 진행 Task 최대 5개의 snapshot에서 시작한다. 이는 작성한 합성 이력이며 실사용자의 수집 이력이라고 주장하지 않는다. 반복되는 배경 문장의 단순성도 한계로 공개한다. 원장에 정의된 과거 전달 내용은 원본 사실로 제공할 수 있지만 미래 정답 요약이나 파생 관계를 공짜로 넣지 않는다.
- 원본 제공부터 **5초 후 첫 입력 시작**을 고정한다. producer가 완료될 때까지 기다리지 않는다. 남은 준비는 사용자 처리와 경합하며 전체 비용과 RSS에 포함된다.
- 같은 episode 안의 실제 cache와 유효 기록은 유지한다. 다음 episode와 반복은 새 snapshot에서 시작한다. 이 결과를 장기간 계속 실행한 상태의 비용이나 RAM으로 해석하지 않는다.
- 원본 화면은 2880×1800, 보존 범위 최대 15장이다. 같은 범위의 원본 읽기와 crop을 허용한다. parser와 직접 판단의 모델 입력이 구조에 따라 달라지는 것은 비교 대상이며 원본 권한은 같다.
- S11/S18/S19의 BG 사건은 첫 사용자 입력 종료 -100ms와 +100ms에 발생한다. 후보가 늦게 읽었다고 source 시각을 늦추지 않는다.
- 일반 후속 입력은 지정 상세 응답 이후 2초, S08의 정정은 첫 내용 게시 이후 +200ms의 시작 조건을 사용한다. 원장에 지정한 전사 발화 길이를 유지하고 실제 audio를 처리한 시간이라고 하지 않는다. 30초에 anchor가 없으면 실패를 남기고 지정 fallback으로 다음 입력을 제공한다.
- Agent 결과는 실제 올바른 ingress와 선행 의존 이후에만 제공한다. 외부 업무 8초와 기술 receipt 100ms는 동일한 시험 profile이며 측정된 Agent 성능이 아니다. 실제 receiver 모델 실행을 붙인 경우 준비 완료와 이 profile의 관계, 비용 및 제외 시간을 실행 manifest에서 명시한다. ingress 실패를 성공 결과로 대신하지 않는다.

### 4.3 이번 PoC의 대체 범위

실제 원격 의미 모델과 이미지 판단, 실제 로컬 파서, Rust 후보와 Python 실행기를 사용한다. UI 표시 endpoint는 공통 callback proxy다. ASR/TTS, 음성 장치와 상용 Agent 제품 및 완성한 Windows UI는 구현 범위가 아니다. 이 한계를 모든 구성에 동일하게 적용한다.

음성 원장의 발화는 지정 길이와 종료 시각을 가진 전사 입력으로 재생한다. 음성 생성과 재생은 수행하지 않으며 결과 표에 Voice OFF 및 text callback 범위를 명시한다. S15의 이전 설명과 채널 전환 후 Text 요청이라는 이력 연결은 보존하되 실제 음성 전환 지연을 측정했다고 하지 않는다. 원문과 변환한 trigger의 대응표를 보존한다. QA09나 전체 음성 제품의 점수를 이 값으로 채우지 않는다.

모든 Qwen 호출은 같은 고정 모델 snapshot과 공통 호출 한도 K=2를 사용한다. 준비, 복구, 수신자 호출의 한도 적용과 대기 기록을 manifest에 명시한다. local parser의 CPU thread 한도와 실제 버전도 고정한다. 로컬 CPU parser와 원격 Qwen의 배치 차이는 결과 해석에 남기며 일반적인 B 구조의 고유 비용이라고 확대하지 않는다.

화면은 한국어 원문을 포함한다. 실제 parser의 지원 언어와 OCR 가중치를 동결하고 모든 준비 및 추론과 메모리를 관측한다. 영어 전용 OCR의 준비 확인을 한국어 화면 비교의 완성 결과로 쓰지 않는다. 정식 실행 전의 실패한 호환성 probe와 언어 설정 수정 이력도 보존한다.

| QA05 전체 모델 비용 | 준비, 미사용, 폐기, 실패, 복구와 실제 수신자를 포함한 usage | **9episode 한 묶음 비용의 5회 평균**. 45episode 전체 비용, 역할별 비용과 미확정 사용량 별도 |
| QA06 로컬 메모리 | Python, Rust와 실제 local helper의 동일 시각 RSS 합, 50ms 관측 | **45episode 전체에서 최고 동시 RSS**. 역할별 최고값의 합산이나 episode별 피크 합산 아님 |

QA01 callback과 QA03 host 완료는 본문의 모든 의미 조건이 정확하다는 보증이 아니다. 지칭은 QA02, Task 연결과 승인 및 실제 본문 조건은 별도 기능 진단으로 함께 공개한다. 잘못된 내용도 출력 시각 관측에서는 지우지 않으며, 미출력은 `NOT_OBSERVED`로 예정 분모에 남긴다. 실패를 임의 벌점 시간으로 바꾸거나 성공 사례 평균을 전체 성공 속도로 쓰지 않는다.

QA03은 겹친 시간 구간을 무작정 빼서 계산하지 않는다. 원래 목표와 정정 및 의존 관계를 기록하고, 외부 대기 노드의 비용만 0으로 둔 인과 경로를 재구성한다. VIA의 모델 실행과 읽기, 재시도 및 자원 경합은 남는다. 미관측 목표는 억지 종료값으로 채우지 않는다. 같은 관측 성공 교집합의 시간은 보조 설명이며 고정 115목표를 대체하지 않는다.

QA05는 입력 $0.40/M token 및 출력 $1.60/M token의 고정 비교 단가를 사용한다. 현재 청구서나 최신 가격이라고 주장하지 않는다. local parser는 API 청구가 없더라도 CPU 시간과 RAM 및 준비 비용을 공개한다. 사용량 미확정 호출은 0으로 처리하지 않고 예약 상한 및 불완전 비용 상태를 별도로 기록한다. 예전 12episode 비용 합계와 이번 9episode 평균 비용으로 단순 절감률을 계산하지 않는다.

QA06에는 원격 가중치, 원격 KV와 미구현 전체 UI가 없다. 공유 물리 페이지 중복 제거는 검증 전이다. 논리 상태 byte와 저장 파일 크기는 별도 진단이다. 작은 RSS 변동만으로 구조의 메모리 우위를 확정하지 않는다.

QA06은 50ms 간격의 **관측 최고 RSS**이며 연속시간의 실제 최고값을 보장하지 않는다. 하나의 RSS 조회가 진행되는 동안 해당 process의 실제 종료가 확인된 표본은 `CONFIRMED_EXIT_BOUNDARY`로 분리한다. 그 표본을 정상 0으로 쓰지 않고 최고값 계산에서 제외하며 원시 값, process lifecycle 및 제외 건수는 남긴다. 정상적인 완전 표본만 관측 최고값에 사용한다. 살아 있는 process 누락, 종료 여부 미확정 및 sampler 실패는 계속 `INVALID`/`INCOMPLETE`로 처리한다. 이 정책은 정식 모델 실행 전에 정하며 모든 구성에 동일하게 적용한다.

process 시작 직후 실제 `ps` 결과에 PID 행이 존재하면서 RSS가 0으로 보고된 경우와 PID 누락을 0으로 채운 경우를 구별한다. 성공한 조회에서 모든 등록 PID가 관측되고 시작 기록이 확인되며 해당 PID의 첫 양수 RSS 관측 이전이면 `STARTUP_ZERO_RSS`로 명시해 실제 숫자를 보존한다. 그 필수 PID의 양수 RSS가 같은 episode에서 이후 확인돼야 완전 관측으로 인정한다. 끝까지 양수 관측이 없는 필수 process, PID 누락 및 조회 실패는 불완전이며, 양수를 관측한 뒤 실행 중 다시 나타난 0은 근거 없이 예외 처리하지 않는다. 이를 피하기 위해 helper PID 등록을 늦추거나 초기화 대기를 숨기지 않는다.

최종 의무 source 이후 60초까지 완료를 관측하고 미완료면 취소를 요청한다. 이후 120초까지 종료와 늦은 사용량을 수집한다. 계측 누락이나 미정산은 각각 미관측 또는 `INCOMPLETE_COST`다. 실패한 사례와 반복, 실패 뒤 비용을 원장에서 제거하지 않는다.

7구성 각각 6과제의 독립 변경으로 평가한다. 공통 모듈이 바뀌어도 실제 운영 변경 수에 포함한다. 테스트, 주석, generated 산출물만 바꾼 파일은 운영 모듈 수로 세지 않는다. 한 과제 안의 여러 변경 줄을 여러 모듈로 부풀리지 않는다. diff와 수용 검사, 구성별 실제 적용 경로를 보존한다.

원래 COMMON-28 계약은 전체 28개 회귀를 요구했다. 이번은 **공통 9개 회귀와 각 변경 과제의 필요한 결정적 수용 검사**로 한정한다. 전체 28개 회귀를 통과했다고 표기하지 않는다. 원래 C04의 해당 문단 대기 음성 교체는 Voice OFF 범위 밖이다. 이번 C04는 실제 전달한 Agent 결과의 text section 수정과 Task 결과 및 표시 이력, 수정 원본의 후속 참조까지 확인한다. 아직 표시하지 않은 모델 생성 중 본문 수정이나 음성 대기열 취소를 구현했다고 주장하지 않는다. 같은 소스 변경이 여러 구성에 동일하게 적용되면 같은 수가 나오는 것을 허용하고 변경 범위를 일부러 벌리지 않는다.

최종 일치 표는 `조건부 지지`, `반대 관측`, `메커니즘 미발동`, `상쇄`, `관측 동점`, `사전 순위 없음`, `미확정`, `미측정`을 구별한다. 수치 방향과 관련 실제 경로가 함께 확인돼야 구조 예측의 지지로 설명한다. 전체 평균과 영향을 받은 사전 지정 사건의 진단을 함께 공개하되 후자로 대표 점수를 교체하지 않는다. 과정의 QA×DP 차별화 개수를 채우기 위해 순위를 만들지 않는다.

예를 들어 S19에 다른 Task의 진행과 완료가 도착해도 그 사실을 공통 코드가 직접 표시할 수 있다면, 사건 도착 자체를 DP2 의미 실행의 병행 이익으로 세지 않는다. 새 의미 판단이 실제로 겹쳤는지 확인한다. 차이를 만들기 위해 모든 Agent 통지를 불필요한 모델 호출로 바꾸지 않는다. 공통9에서 충분히 발동하지 않은 조건은 별도 조건 진단의 결과로 설명하고 대표 모집단은 그대로 유지한다.

코드 개발과 실행은 사용자 지정 GPT-6.1 Sol High 담당이 수행한다. 주 담당은 계약과 통합 및 범위 검토를 담당한다. 정식 API 실행 전 source/fixture/oracle/asset hash, 실제 typed 연결, 입력 및 권한 검증, 예정 분모, 시간 구간, 비용 projection과 역할별 상한을 검토한다. 구현 가능성 확인용 probe와 offline 검사는 정식 결과에 합치지 않는다.

초기 관리 예산은 이전 조건 진단을 포함한 $4다. 이전 부분 실행 환산 $0.1016136을 별도 원장에 유지한다. 공통9의 예상 호출은 구현 후 직렬화 token과 출력 상한으로 다시 산정한다. 모든 사례를 공정하게 수행할 수 없는 예산이면 결과를 보기 전에 실행 계획과 상한을 재검토하며, 실패하거나 비싼 안의 사례를 조용히 잘라내지 않는다.

2026-10-19 실행 전 비용 projection은 315episode에서 약 2,740회의 cloud 단계 호출을 예상한다. text 직렬화량을 3byte/token으로 가정한 예시는 약 $12.17, 같은 입력 가정과 출력 상한을 사용한 값은 약 $15.31다. text를 1byte/token으로 계산하고 출력 상한을 쓰면 약 $31.90이며, 이미지 byte proxy 약 $6.81과 이전 비용을 더한 계산은 약 $38.81이다. 이미지 tokenization과 실제 복구 호출은 이 계산으로 보장할 수 없다. 이는 provider usage나 실제 청구액이 아닌 계획용 가정이다. 사용자의 $40 상한 승인을 요청한 상태이며, 답변 전에는 $4 원장 상한을 유지하고 새 캠페인 유료 호출을 시작하지 않는다. 상세 가정은 실행기의 `preflight/cost-projection.json`과 `.md`에 보존한다.

모델 측정 창은 하나의 실행기만 사용한다. 다른 담당의 대규모 로컬 검사를 정식 RSS/지연 측정에 겹치지 않는다. 공통 원본과 결과, 모든 실패 및 늦은 응답, API usage와 예약, 명령, OS와 기기 및 dependency 정보를 보존한다. 가중치와 task-local 환경 및 build cache는 Git에 넣지 않고 hash와 재현 절차를 기록한다.

동결 이후 구현 수정이 필요하면 현재 세대를 보존하고 변경 사유 및 새 동결을 남긴다. 수정 전 실패를 수정 후 성공으로 덮어쓰지 않는다. 관련 없는 AGENTS, workplan, 04-50, work/ 및 다른 세션의 PPT 작업은 이 변경에 포함하지 않는다.
