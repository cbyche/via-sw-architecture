## 측정한 기능과 비교 범위

네 설계 문제의 기본안 열 개를 같은 입력으로 비교했다. 사용자 순서의 DP3 화면 지칭은 이 폴더의 DP04, DP4 업무 인계는 DP05다. 각 안에 네 사례를 세 번 적용하며, 첫 응답 261건과 완료 목표 243개를 사전에 고정했다. 사례와 반복을 삭제하지 않고 실제 실패와 복구 비용을 포함한다. 최초 비교 중 발견한 DP05의 기확보 근거 연결 누락은 별도 소스에서 교정하고 ABC 전체 36회를 다시 비교했다. 최종 표는 기존 DP01/02/04의 84회와 교정 DP05의 36회를 연결하며, 교정 전 DP05와 비용도 보존한다.

화면 B와 A4의 화면 생산자도 이 Qwen을 사용한다. 설계 참고 자료의 OmniParser나 별도 학습한 검출기를 실행한 결과가 아니다. 같은 모델을 쓰되 화면 후보를 생산하고 보존·검사하는 경로와 최종 결합 책임이 다른 구성의 결과다.

실행 전 예상은 [14 보완 계약의 QA별 예상](14-corrected-poc-contract.md#5-실행-전-구조적-예상--모든-방안과-qa)에 고정했다. 원본과 평가용 정답을 분리했고, 정답 대상 목록·평가 좌표·필수 답변 조건을 후보에 주지 않았다. 원문에 적힌 가격·날짜나 사용자가 실제로 지정한 좌표는 정상 입력이다. 최종 결과는 구조상 예상이 실현된 조건과 실현되지 않은 조건을 함께 해석한다.

## 첫 응답과 완료시간의 의미

**QA01은 사용자가 입력한 뒤 구체적인 처리 의도나 답변을 처음 전달한 callback까지의 시간이다.** 예를 들어 두 자료와 보고서 작성 목적을 실제 채택하면 “두 자료를 참고해 보고서를 작성하겠습니다”라는 안내를 먼저 전달할 수 있다. 단순 접수 인사와 아직 해석하지 않은 지칭의 반복은 세지 않는다. 이번 비교의 UI 전달 경로는 같으므로 사용자와 합의한 callback proxy를 사용한다.

표의 QA01 시간은 **실제로 전달한 첫 구체적 callback의 지연 proxy**다. 기존 QA01 정의에 있는 “올바른 내용”을 전체 문장의 의미까지 자동 판정한 값은 아니다. 채택·현재성·출력 계약을 통과했어도 지칭이나 내용 오류가 있을 수 있으므로 QA02, 관계 진단과 실제 문안 검토를 함께 제시한다. 알려진 오답의 빠른 callback을 정확한 첫 응답 성공으로 설명하지 않으며, 그 시각을 삭제하거나 사후에 더 유리한 응답으로 바꾸지도 않는다. 공통 UI를 생략한 것과 의미 정답 검사 범위의 한계는 별개의 사항이다.

**QA03은 해당 입력의 목표를 끝내기까지 VIA가 부담한 시간이다.** 상세 답변 생성과 실제 복구가 남아 있으면 첫 응답 이후에도 계속 측정한다. 정정은 원래 목표의 새 판본이며, 정정 시점으로 시작을 다시 잡지 않는다. 화면 지칭처럼 대상 확정 자체가 목표인 경우에는 첫 응답과 완료가 같을 수 있다.

이번 목표 완료 사건은 동결한 PoC 계약의 비어 있지 않은 결과, 현재 판본, 인용·기하 등 해당 검사에 따른다. 별도 본문 검토에서 의미 누락이 발견되면 “계약상 반환 완료, 내용 미충족”으로 함께 남긴다. 제품 수준의 완전한 업무 성공률과 구별하며, 완료 사건만으로 상세 설명이 모두 정확했다고 주장하지 않는다.

DP02 E4에서 사용자 답변 U3의 목표는 **기존 메일 Task의 질문에 수신인 답변을 전달하고 대응하는 접수 확인을 받는 것**이다. 원래 메일 작성·발송 업무 전체를 끝내는 시간이 아니다. Agent의 질문 통지는 첫 표시를 측정하지만 새 사용자 업무의 QA03 목표로 추가하지 않는다.

DP05의 수신자는 로컬 실행기에 연결된 작은 Agent다. 해당 목표에 연결된 수신자 역할의 실제 Qwen API 전송부터 반환까지 구간의 합집합을 외부 처리로 기록한다. 전송 전 queue·호출 슬롯 대기와 VIA의 의미 채택·자료 가공·자료 제공·결과 연결은 QA03에 포함한다. 따라서 DP05에는 **VIA 처리시간, 실제 전체 경과시간, 제외한 수신자 구간**을 함께 제시한다. 상용 Agent의 네트워크와 내부 연산을 분리 측정한 수치는 아니다.

엄밀한 타이머 경계는 클라이언트의 HTTP 요청 객체 구성 직전부터 응답 외피 JSON 읽기 종료까지다. 작은 요청 구성·외피 파싱이 이 구간에 들어가므로 물리 패킷 전송 시각이나 순수 cloud 연산시간이라고 부르지 않는다. 전송용 payload 직렬화·전송 전 대기와 assistant 본문의 후속 JSON 파싱은 VIA 시간에 포함된다.

응답을 끝내지 못한 목표에는 임의의 완료시간을 넣지 않는다. 모든 예정 건수와 실제 관측 건수, 실패까지의 시간을 남기며, 관측된 일부만의 평균은 `INCOMPLETE` 진단값으로 표시한다. 그 값을 전체 완료시간의 우열 근거로 사용하지 않는다. 실제 게시한 오답의 시간도 보존하고 내용 성공 여부를 별도로 평가한다.

## 정확도와 비용의 구분

QA02는 DP01과 DP04의 **최초 채택 지칭 대상 집합과 판본이 정답과 일치한 비율**이다. DP02의 요청 연결과 DP05의 인계 조건 보존은 별도 진단 N-R, N-H로 제공한다. 서로 다른 성공률에 QA02라는 이름을 붙이지 않는다.

출처 인용이 원문에 있다는 검사는 최종 설명 전체의 의미를 증명하지 않는다. 상세 답변은 별도의 유한 내용 조건으로 검사한다. DP05는 조건의 의미가 바뀌었는지, 실제 전달 문안이 요청을 충족하는지도 사전에 고정한 기준으로 전수 검토한다. 미표시 초안과 실제 전달문은 구별한다.

DP01에는 실행 결과를 읽으면서 발견한 추가 허위 주장과 누락을 확인하는 작성자 의미 검토도 붙인다. 이 검토는 실행 전 동결한 QA02나 자동 내용 점수를 바꾸지 않는 **사후 진단**이다. 안별 실제 전달문을 같은 원본·요청과 대조하고, 표기 차이·필수 사실 누락·추가 허위 주장·미전달을 구분한다. 두 진단의 성공률을 같은 정의의 정확도처럼 섞지 않는다.

DP01/05의 내용 진단에는 기존 문자열 일치 결과와 일반적인 단위·날짜 표기를 정규화한 결과를 함께 남긴다. `36-month`와 `36months`처럼 같은 사실의 표기만 다른 경우를 실제 누락과 구분하기 위한 것이다. 이 평가기 차이를 설계나 tactic의 정확도 개선으로 세지 않으며, 모든 비교안에 같은 버전을 적용한다.

QA05는 실제 usage에 고정 비교 단가인 입력 백만 토큰당 $0.40, 출력 백만 토큰당 $1.60을 곱한 값이다. 사전 생산, 소비되지 않은 기록, 실패한 호출, 복구와 수신자 호출까지 포함한다. VIA와 수신자의 비용을 나누어 보여도 전체 비용은 빠뜨리지 않는다. 호출 수가 같아도 출력 길이와 다시 입력하는 기록 길이가 다르면 비용이 달라진다.

기본안 비용 표의 한 행은 그 안에 적용한 **네 사례 × 세 번, 총 열두 episode의 합계**다. 첫 응답과 완료시간은 각 지표에 해당하는 입력·목표의 평균이며, 메모리는 해당 열두 실행 중 관측한 최고 동시 RSS다. 비용 합계·시간 평균·메모리 최고값의 집계 단위가 다르다. 보완 실험은 선택한 동일 사례와 반복에 해당하는 기본 결과를 따로 뽑아 비교한다.

### 첫 안내가 빠른 구조와 완료가 빠른 구조

A와 B는 대상을 채택한 뒤 필요한 자료를 더 읽고 상세 답변을 만들 수 있다. 그 경우 먼저 진행 안내가 나가므로 QA01이 QA03보다 짧다. C는 준비된 관계 근거로 36건 중 34건에서 첫 판단 호출 안에 상세 답변까지 만들었다. 이 구현은 비스트리밍 JSON 반환 뒤 callback을 보내므로, 상세 본문이 만들어질 때까지 첫 안내도 기다린다. **C의 요청 후 완료시간은 줄었지만 첫 안내는 늦어진 이유다.** 유지·게시 구조에서 반드시 그런 출력 순서를 사용해야 한다는 뜻은 아니다.

전체 모델 호출은 A 63회, B 70회, C 71회였다. C의 사전 생산은 33회, $0.0729348이며 실제 생산 시간 합은 677.041초였다. 이 생산은 해당 요청 전에 끝난 조건이므로 요청 후 지연에 넣지 않고 전체 비용에 포함했다. 준비를 할 여유가 없는 요청에도 같은 이익이 있다고 일반화하지 않는다. C의 전체 비용은 A의 약 2.42배였다.

### A가 실패한 이유와 B의 실제 이익

A는 자유 영역 지정 세 번에서 모두 완료하지 못했고, 부분 정정 사례의 첫 판본 두 번에서도 응답하지 못했다. 정정의 최신 판본은 세 번 모두 완료했으므로 첫 응답 미관측은 5건, 최종 목표 미완료는 3건이다. 최초 실패를 나중 정답으로 바꾸어 세지 않았다.

주된 문제는 **대상 이름을 맞게 제안해도 위치 근거를 일관되게 만들지 못한 것**이었다. 예를 들어 P3·P4·P5를 제안하면서 P5의 위치를 사용자가 그린 닫힌 경로 밖으로 반환했다. 복구는 위치를 바로잡는 대신 P5를 빼면서 “세 개” 조건을 유지해 다시 거절됐다. 정정 사례에서는 반환한 영역의 아래쪽 좌표가 화면 높이를 넘었다. 출력 잘림이나 API 장애는 없었으며 64개 호출이 모두 정상 HTTP·종료 응답이었다.

B는 별도 화면 생산자가 만든 후보와 발화 제약을 코드 또는 모델로 결합해 모든 예정 지칭을 채택했다. **이번 이익은 유효한 근거 계약을 만족하는 지칭 결과를 끝까지 전달한 데 있다.** 모델이 제안한 위치가 픽셀 수준에서 완벽했다거나, 생산자를 분리하면 모든 화면에서 정확해진다는 결론은 아니다.

## DP05 결과 — Agent 간 업무 인계

**A는 위임할 때 목적별 자료를 구성하고, B는 활동 중 생산한 업무 기록에서 추출하며, C는 필수 명세와 자료 목록을 보낸 뒤 수신자가 세부 범위를 고르게 한다.** A/B가 이미 확보한 유효 원문이나 기록만으로 충분하면 추가 가공을 생략한다. 같은 원문을 다시 읽게 강제하는 것이 A의 기본 설계는 아니다.

이번 세 안은 **읽기 기능을 지원하는 동일한 수신자**를 사용한다. A/B도 받은 자료가 부족하면 허용 원문을 추가로 읽을 수 있다. 따라서 최초 인계 자료의 준비 효과를 비교한 것이며, 읽기 기능이 없는 다양한 Agent에 A/B가 더 폭넓게 연결되는 장점은 이번에 측정하지 않았다. B의 생산은 합성 사건 순서에서 후속 입력 전에 끝난 조건이다. 그 생산 중 사용자 입력이 도착할 때의 자원 경쟁까지 검증한 결과는 아니다.

### 최종 비교에 앞서 교정한 기본 기능

최초 120회 중 DP05는 그대로 최종 성능으로 채택하지 않는다. A의 VIA 가공 단계가 실제 읽은 원본이 이후 인계에 공급되는 공통 근거에 연결되지 않는 누락을 발견했다. B는 생산한 업무 기록을 직접 사용했지만, A의 앞선 원문 읽기가 후속 인계의 재조회·재가공을 대체할 기회는 제대로 제공되지 않았다.

이는 A의 목적별 구성 구조가 요구하는 비용이나 선택 보완 tactic이 아니다. 기본 설계가 허용한 기확보 원문 재사용을 구현에서 연결하지 못한 것이다. [추가 교정 계약](14-corrected-poc-contract.md#11-업무-인계의-기확보-근거-연결-누락-교정)에 따라 실제 VIA 원문 읽기의 보존·현재성·철회를 연결하고 ABC 전체 네 사례를 세 번씩 다시 비교한다. 원래 모델과 입력·정답·복구 한도는 유지하며, 충분한 근거가 있어도 모델의 재조회 선택을 강제로 막지 않는다.

수신자 Agent가 내부에서 읽은 내용이나 모델이 만든 요약을 VIA가 실제 확보한 원문으로 자동 승격하지 않는다. 실패한 가공에서도 이미 성공적으로 읽은 현재 원문은 보존할 수 있으나, 그 실패한 제안의 판단 내용이 승인됐다는 뜻은 아니다. 교정 후 실제 재사용 횟수·추가 입력 토큰·유지 메모리와 전체 비용을 함께 보고한다.

중간 교정 실행에서는 B가 실제로 받은 인접 원문 2–3행과 4행을 집계 출처 2–4행으로 표기했는데 host가 거절하는 검사 누락도 확인했다. quote는 실제 원문과 일치했고 프롬프트는 이 합집합을 금지하지 않았다. 이 실패는 B의 의미 오답으로 세지 않는다. 당시 실패와 미표시 결과를 보존하고 [공통 범위 검사 교정 계약](14-corrected-poc-contract.md#12-실제-공급한-인접-원문-범위의-검증-누락-교정)에 따라 최소 수정을 검토한 뒤 새 ABC 36회 전체를 최종 비교에 사용한다. 사후에 검사만 통과시켜 과거 callback이나 완료 시각을 만들어 넣지 않는다.

| 단계 | A 호출 / 비용 | B 호출 / 비용 | C 호출 / 비용 |
| --- | ---: | ---: | ---: |
| 요청 전 기록 생산 | 0 / $0 | 51 / **$0.1493156** | 0 / $0 |
| 요청 후 VIA 의미 채택·인계 준비 | 51 / $0.0338936 | 39 / $0.0598472 | 21 / $0.0113928 |

B의 요청 전 생산 시간 합계는 **814.739초**였으며, 다음 입력 전에 준비가 끝난 조건이다. 준비 비용은 전체의 약 51.7%이고 위임이 일어나지 않은 E1의 생산 **9호출·$0.0172844**도 포함한다. B가 수신자 호출은 적어도 더 긴 기록·출력 때문에 수신자 비용은 C보다 컸다. “호출 수가 적으면 비용도 작다”는 가정은 여기서 성립하지 않는다. C는 비용의 약 85%를 수신자에서 썼지만 수신자 비용의 절대액 자체도 A/B보다 작았다. VIA의 일을 수신자로 옮겼다는 사실을 수신자 비용 증가로 자동 해석하지 않는다.

실제 원문 읽기는 A가 VIA 가공에서 24회·수신자에서 13회, B가 기록 생산에서 99회·수신자에서 11회, C가 수신자에서 34회였다. 원문 파일 읽기 호출 수이며 물리 디스크 I/O 횟수는 아니다. A의 직접 인계 5건은 기확보 원문 재사용 경로가 실제 작동한 증거다. 모든 모델 선택이 충분한 원문에서 반드시 DIRECT가 되도록 강제하지 않았다.

대표 차이는 **“가격이 같을 때만 유지보수가 긴 제품을 우선한다”는 전제의 보존**이다. E3 세 번째 반복의 B는 실제 전달 이력의 해당 원문을 생산 기록의 supporting 근거로 보존하고, 직접 인계에서 선택해 수신자 메일에도 같은 전제를 남겼다. A는 실제 비교표와 견적을 재사용했으나 이 전달 이력을 선택하지 않았고, 인계 선택 요약부터 “가격이 더 높아도 우선”으로 바뀌어 본문 조건도 뒤집혔다.

이는 B의 기록이 조건 원문을 다음 판단에 공급한 실제 경로다. 요약만으로 논리가 보장된 것은 아니다. B에서도 축약한 요약과 함께 원문을 전달했으며, 다른 반복에는 조건 오류가 남았다. 작은 반복 표본의 결과를 모든 모델·업무에서 B가 더 정확하다는 일반 법칙으로 확대하지 않는다.

독립 담당자는 사전에 정한 27개 본문과 추가 경계 2개를 별도로 검토했다. A의 예산 조건 누락 3건은 작성자가 PARTIAL, 독립 담당자가 FAIL로 분류했지만 **필수 조건이 빠졌고 full-PASS가 아니라는 판단은 같다.** 양쪽 라벨을 보존했고 유리한 라벨을 골라 성공률을 조정하지 않았다. 추가 경계 2개는 지정 27개의 분모에 넣지 않는다. 27개 중 1개는 이전에 같은 본문과 판정을 본 노출 한계가 있다.

**VIA가 여러 Agent 사이에서 조건을 이어 주는 목적을 우선하면 B를 조건부 권고한다.** 이번 본문 충족이 가장 많았고, 실제 조건 원문을 기록에서 다음 인계로 넘긴 경로가 확인됐다. 대가는 A의 2.83배·C의 3.81배 모델 비용, 더 큰 유지 상태와 철회 변경 범위다. 기존 QA01~06에서 B가 전반적으로 우수했다고 해석하지 않으며, 본문 조건 보존이라는 기능 진단을 선택 이유로 명시한다.

**읽기 기능을 가진 수신자에서 적은 VIA 준비와 비용을 우선하면 C가 유력한 대안이다.** 필수 조건은 계속 VIA가 명시하고 수신자의 읽기·결과를 검사해야 한다. A는 요청 때만 목적별 구성을 하고 기확보 원문을 재사용하는 중간 선택이지만, 이번 측정에서는 B의 본문 충족이나 C의 비용 이익을 동시에 얻지 못했다. 세 안 모두 오류·미완료가 남아 제품의 무조건적인 성공 또는 accepted ADR 선택으로 선언하지 않는다.

## 변경 용이성을 측정한 기능 확장

QA04는 모델 연결 형식 C01과 원본 표현 C03의 대조 과제에, 각 DP의 기능을 관통하는 확장 두 개를 추가한다. 실제 Rust 모듈을 고친 독립 복사본에서 기능 수용과 회귀 검사를 실행한다. 주지표는 네 과제의 동일 가중 평균이며, 새 기능 두 과제만의 평균과 과제별 변경 파일도 함께 제공한다.

추가 기능은 전달한 답변·지칭의 출처 조회, 이미 전달한 결과의 지정 section 갱신, 원본 일부 범위의 사용 철회다. 같은 요구를 각 안의 실제 상태와 처리 경로에 적용한다. 생산과 소비가 나뉘어 있으면 양쪽을 수정할 수 있고, 이미 공통 전달 이력에서 해결할 수 있으면 구조가 달라도 모듈 수는 같을 수 있다. 모듈 수와 구현 난이도 전체를 같은 의미로 취급하지 않는다.

| 미래 기능 | 실제 수용 조건 | Agent 발전과 연결되는 이유 |
| --- | --- | --- |
| 결과의 일부만 갱신 | 지정 section만 새 판본으로 바꾸고 다른 section·Task·이미 전달한 이력은 보존. 이후 인계와 대기 중인 음성 항목은 새 판본을 참조 | Agent가 전체 최종 답변뿐 아니라 진행 중 artifact와 부분 수정 결과를 계속 전달하는 상황에 대응 |
| 실제 전달 내용의 출처 조회 | 사용자가 실제로 받은 답변 또는 채택 지칭의 source·판본·범위 반환. 실패한 제안과 표시하지 않은 초안은 제외 | 여러 Agent의 공개 결과를 재사용할수록 VIA가 설명한 내용과 원문을 다시 확인할 필요가 커짐 |

부분 artifact 전달, resource 변경 통지, 중단·재개를 제공하는 공식 구현과 이 변경 과제의 연결은 [실행 전 계약의 근거](14-corrected-poc-contract.md#미래-기능으로서의-현실성)에 정리했다. 규격이 VIA의 부분 철회나 이력 갱신까지 자동 구현해 준다는 뜻은 아니다.

## 메모리 수치를 읽는 방법

이번 QA06은 같은 시각에 관측한 **Python 실행기·API 연결 프로세스와 Rust 후보 프로세스의 RSS 합계**다. 각 실행을 새 프로세스로 시작하고, 처음 두 프로세스를 함께 관측한 기준값과 실행 중 최고값, 그 최고 시점의 역할별 기여를 남긴다. 서로 다른 시점의 프로세스별 최고값을 더하지 않는다.

## 구조와 결과를 연결하는 판정 규칙

발표에서는 **“이 구조는 어느 일을 앞당기거나, 생략하거나, 추가하는가”를 먼저 설명하고 실제 사건 기록으로 확인한다.** 예를 들어 요청별 실행의 이익은 두 API 호출이 실제 겹쳤는지, 유지 문맥의 이익은 원본 재조회와 응답 호출을 실제 생략했는지로 확인한다. 평균 시간의 차이만으로 해당 메커니즘이 작동했다고 판단하지 않는다.

| 관측 | 발표에서 사용할 설명 | 함께 공개할 조건 |
| --- | --- | --- |
| 선행 호출을 기다리지 않고 후속 판단이 진행됨 | 요청별 실행으로 대기를 줄였음 | 같은 총 호출 한도, 원래 목표의 완료 지연, 추가 입력·호출 비용 |
| 이전 근거로 후속 답변 단계를 생략함 | 문맥 재사용으로 반복 처리를 줄였음 | 근거가 현재 판본이고 충분한 경우, 유지한 입력의 토큰 비용 |
| 사전에 만든 기록을 바로 사용함 | 준비 비용을 지불해 요청 이후 처리를 줄였음 | 준비 시간·전체 비용·미사용 기록, 준비되지 않은 요청의 경로 |

| 인계 수신자가 필요한 자료를 직접 읽음 | VIA의 가공을 수신자 읽기로 옮겼음 | 수신자 시간과 비용, 실제 전체 경과시간, 자료 접근·조건 보존 |

같은 입력을 세 번 반복하고 안의 실행 순서를 바꿨지만, 원격 모델 서비스의 시간 변동을 제거한 실험은 아니다. 사례별 개별값과 범위를 함께 읽는다. 호출 수와 의존이 같고 시간만 조금 다르면 구조 자체의 우위로 확대하지 않는다. 여러 DP의 시간·비용 차이를 합쳐 전체 VIA의 예상 절감량으로 계산하지 않는다.

**실패도 서로 다른 종류로 설명한다.** 모델이 반환하지 않은 경우, 출력 형식·현재성·출처·기하 검사를 통과하지 못한 경우, 실제 표시했지만 내용이 틀린 경우를 구분한다. 계약 검사에서 막힌 초안은 정답 문구가 들어 있어도 전달 성공이 아니다. 반대로 실제 표시한 답변의 시간은 내용 오답이라는 이유로 지우지 않는다. 시간·응답 범위·정확성의 세 기록을 함께 평가한다.

DP02의 보조 대기 분해에는 계측 한계가 있다. API 연결 실행기의 enqueue부터 실제 전송까지는 직렬화·기록·예산 확인과 호출 슬롯 대기를 함께 포함한다. 현재 시각 기록으로 순수 슬롯 대기만 분리하지 못하므로 그 합을 보고한다. Rust의 판단 경계 대기와 실제 API 전송·반환 구간은 별도 기록이며, QA01/03 전체 경과에는 모두 포함된다.

**A4는 A의 정확도를 회복했지만 단계·비용을 추가했다.** A4의 최고 동시 RSS는 45.122MB이며, 보완 QA04는 다시 변경 과제를 수행하지 않았으므로 별도 수치가 없다. A4의 비용은 기본 A의 약 1.35배다.

같은 완료 사례의 최종 시간은 dense **17.789→31.372초**, page **10.012→18.808초**, correction **19.071→28.323초**였다. free는 기본 A가 0/3 완료였고 A4는 3/3, 20.484초에 완료했다. 미완료인 기본 A에 가상의 시간을 넣어 free의 속도 개선율을 만들지 않는다.

이 결과는 **화면 생산자의 구조화된 표현이 A에도 도움이 됨**을 보여 준다. B의 후보 저장·소유 구조 전체만이 정확도 이익의 유일한 원인이라는 주장은 성립하지 않는다. A4는 생산 이후에도 최종 공동 판단을 수행하므로, 별도 표현을 얻는 정확도 이익과 그 뒤 처리의 비용을 구분한다. 기본 B 및 B4와의 선택에는 같은 정확도에서 남는 대기·토큰·상태를 함께 사용한다.

A4는 화면 생산 이후의 공동 판단에도 원본 이미지와 생산 결과를 함께 제공했다. 실제 이미지 전송 수는 **A4 54개, B 27개**였다. A4의 비용은 화면 생산 $0.0294532와 공동 판단 $0.0267116이고, B는 화면 생산 $0.0285444와 발화·결합 $0.0145728이었다. **같은 화면을 생산자와 최종 공동 판단에 보내는 A4의 입력 부담**이 실제 요청과 비용에 나타났다. 모델 내부의 시각 연산 중복 자체를 측정한 것은 아니다. 화면 생산의 요청은 15/15 같았으나 반환 후보는 8/15만 동일했으므로, 완전히 같은 후보를 고정한 인과 실험과도 구별한다.

### B4: 정확도를 유지하면서 두 생산 단계의 대기를 겹침

B4도 네 사례 × 세 번을 모두 완료했다. 기본 B와 같은 호출 한도 안에서 초기 화면 생산과 발화 생산을 병행했다. QA02 **24/24**, 첫 callback **15/15**, 최종 완료 **12/12**를 유지했다. 첫 응답은 **18.344→14.468초**, 완료는 **22.930→18.085초**로 약 21% 짧아졌다.

전체 비용은 **$0.0431172→$0.0435792**로 거의 같았고, 최고 동시 RSS는 **45.351→46.973MB**였다. 같은 일을 겹쳐 수행했으므로 대기 감소를 모델 비용 절감으로 설명하지 않는다. 실제 호출은 38→37회였다. page 사례에서 모델 결합이 한 번 줄어든 분기 차이도 있으므로, 관측한 시간 차이 전부를 순수 병행 효과라고 귀속하지 않는다. 실제 HTTP 구간의 겹침과 사례별 값을 함께 확인한다. 보완 QA04는 다시 측정하지 않았다.

실제 초기 화면·발화 호출 **15쌍 모두 겹쳤으며 겹친 시간 합은 66.745초**였다. 호출별 서비스 시간의 단순 합은 B4가 오히려 8.668초 길었다. 그럼에도 겹친 구간이 생겨 12개 목표의 QA03 합계가 **58.143초 줄었다**. 이 기록이 “병행으로 대기를 줄인다”는 설명을 뒷받침한다. 정확도는 24/24로 같았으며, 병행이 정확도를 높였다고 설명하지 않는다. [보완 단계별·사례별 증거](../../../../../results/architecture-evaluation/current/four-dp-qwen37-review-v2-20261018/analysis/dp04-tactic-comparison.md)에 실제 요청·호출·토큰·시간을 연결했다.

**이번 화면 비교의 권고는 기본 B를 선택하고 B4로 생산 대기를 보완하는 구성이다.** 기본 B는 A보다 정확한 지칭을 끝까지 전달하는 대신 생산 대기를 부담했다. A4도 정확도를 회복했지만 같은 정확도의 B4보다 시간·비용이 컸다. 이 결론은 이번 Qwen·화면 사례·호출 한도 조건에 한정하며, B의 모든 상태 소유 설계를 일반적으로 입증한 결론은 아니다.

### 업무 인계의 공통 원문 표현 진단

**최초 BASIC 세대**의 DP05 E4 첫 반복에서 A와 C의 일부 인용 행 번호가 실제 원문보다 한 줄 앞서 있었다. 당시 실제 A/B/C 요청 32개와 원본 구간 102개를 대조했으며, 시작·끝 범위의 offset 오류는 발견하지 못했다. 이 대조는 번호 표현 진단을 정한 사전 근거이며 최종 교정36의 실패 목록과 구별한다. 최종 교정36에서는 B의 정정 두 건과 C의 초기 두 건에서 개별 인용 행 오류가 남았다. 모든 안이 번호 없는 원문에 시작·끝 번호만 제공해 모델이 행을 직접 세어야 했다. B의 준비 기록과 A/C의 읽기 구간은 서로 달라 이 입력 부담과 구조가 상호작용한다.

이를 특정 구조 자체의 불가능성으로 단정하지 않도록, 전송 원문에 실제 행 번호와 공통 설명을 붙이는 E4 × A/B/C × 3회의 별도 진단을 완료했다. 실제 원문·검증기·정답·복구 한도는 유지했다. 이 9회는 위 27회 보완과 DP05 기확보 근거 교정 36회 이후에 같은 교정 실행 파일에서 수행했다. 기존 실패나 기본 평균을 소급 교체하지 않는다.

**이 진단의 RAM은 기본 비교와 직접 비교할 수 없다.** 번호 진단 실행기의 사전 검증이 기존 전체 `runs.jsonl`을 읽어 Python 초기 메모리부터 커졌다. 실제 두 프로세스 초기 합계는 A 695.861MB, B 695.484MB, C 695.681MB이고 최고 합계는 각각 **703.955MB, 702.562MB, 703.906MB**였다. 원시값을 보존하되 이를 번호 표현이나 VIA 상태가 약 650MB 늘어난 결과로 설명하지 않는다. 별도로 추적한 번호 표현 buffer 약 11~17KB와도 같은 지표가 아니다. 기본 QA06은 최종 기본36의 A 49.119MB, B 57.229MB, C 48.153MB를 사용한다. 이 도구 전처리 부담을 숨기거나 작은 buffer 값으로 대체하지 않는다.

최종 기본 비교 120회는 위 표 중 명시한 84+36회이며 **625회 호출, $1.0864784**다. VIA $0.8746112와 수신자 $0.2118672를 포함한다. 첫 callback은 고정 261건 중 **255건**, 목표 완료는 고정 243개 중 **233개**가 관측됐다. 미관측 첫 응답 여섯 건과 미완료 목표 열 개를 삭제하지 않았으며 개별 실패까지의 시간과 실제 복구 호출을 보존했다. usage를 확인하지 못한 호출과 남은 예약 비용은 모두 0이다.

이는 과금 청구서가 아니라 실제 usage에 같은 비교 단가를 적용한 비용이다. 이전 [초기 캠페인](12-poc-results.md)의 $0.7207640과 합치거나 교체하지 않는다. 사용자가 요청한 최소 PoC 범위의 실제 실행을 완료한 것이며, 열 개 안 모두의 제품 수준 정확성·전체 UI·Windows 메모리 목표를 충족했다는 판정은 아니다.
