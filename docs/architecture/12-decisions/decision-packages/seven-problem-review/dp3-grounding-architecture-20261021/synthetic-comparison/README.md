# DP3 네 실행 구조의 가상 QA 비교

2026-10-21 / `DP3-GROUNDING-CPU-SYN-1.0` / **SYNTHETIC_AUTHORED_NOT_MEASURED**

**이 CPU 가정과 QA01 우선순위에서는 A를 선택한다.** B는 지칭 정확도 6.67%p와 cloud 비용 약 12.5%를 얻는 것으로 설정했지만, B-R2도 첫 응답이 평균 1.82초 늦고 RAM이 1,782 MB 더 든다. B 계열을 선택할 조건이라면 R2가 기본 후보이며, R1은 메모리 회수가 중요할 때, R3는 독립 복구나 동시 운영이 중요할 때의 대안이다.

수치는 실행 결과가 아니라 작성한 가정과 원장으로 계산한 설계 평가다. 공개 모델 파일 크기에서 CPU 속도·RAM·오류율을 추정했다는 뜻도 아니다. 이전 [실행 구조](../cpu-runtime-architecture.md)의 네 안을 그대로 사용한다. 512 MB 제한은 이번 비교에서 유보하며 기존 QA 점수·ADR·측정 결과는 바꾸지 않는다.

## 비교 계약과 자료

## 같은 입력과 서로 다른 관측 단위

6개 유형에 각각 이름·문서 번호를 바꾼 작성 변형 20개를 두어 **평가 음성 입력 120개**를 구성했다. 각 입력은 새 목표 하나와 지칭 표현 하나를 갖는다. 따라서 이번에는 QA01·QA02·QA03·QA07 분모가 우연히 모두 120이며, 일반적으로 같다는 뜻은 아니다. 작성 변형 20개는 20회 모델 시험이나 통계적 표본이 아니다.

S3·S4·S5에는 각각 평가 이전의 동일한 사용자 활동 20개, 총 **60개 준비 이력**이 있다. S4/S5는 기존 화면의 견적 목록을 확인했고 UI 모델만 사용했다. S3는 이전의 별도 두 시점에서 짚은 견적들을 중복 제거한 이력이 있어 UI와 SAM을 사용했다. 현재 평가 clip과 선택 집합은 그 준비 때 아직 도착하지 않았다. A도 이전 원본·확정 이력을 보존하고 B 세 안은 같은 후보/episode를 보존한다. 사용한 모델만 R1은 회수하고 R2/R3는 유지한다. 준비 활동은 120개 평가 분모 밖이지만 네 안 모두 비용·메모리와 별도 시간 원장에 포함한다. 준비를 완료한 이력이 있다는 조건이며 목표의 도중을 평가 시작점으로 잘라낸 것이 아니다.

| QA | 이번 관측 |
| --- | --- |
| QA01 | 발화 종료에서 **첫 구체적 채택 내용 표시**까지 120입력 평균. 오답 첫 표시도 유지하며 일반 접수 인사는 제외 |
| QA02 | 표현/revision별 최초 대상 집합 완전 일치 / 120표현 |
| QA03 | 평가의 새 목표 120개별 VIA 인과 완료시간 평균. 외부 Agent 8초를 제외하고 전체 상세 결과·음성 요약 준비를 포함 |
| QA04 | 공통 C01~06별 예상 운영 Rust 모듈 수 평균. 실제 diff 아님 |
| QA05 | **120평가+60준비 전체 활동 묶음의 VIA 청구액**. Agent 비용 별도 |
| QA06 | 준비와 평가의 같은 시점에 함께 생존하는 로컬 RAM의 최고값. MB=1,000,000 bytes |
| QA07 | 입력/revision별 최초 필수 의미 전체 일치 / 120입력. 새 우선순위나 점수 미부여 |

원본은 화면 해상도·좌표·표시 내용·동작·시각을 작성한 fixture 명세다. 실제 screenshot이나 WAV를 생성·실행한 자료는 아니다. 정답 객체 ID는 평가자 원장에 두고, 실제 모델에 정답을 제공한 것으로 취급하지 않는다. ASR 전사·단어 timestamp·좌표 변환은 네 안 모두 정확하다. 공통 S2S 최종 텍스트 잔여 대기 0.30초는 포함하지만 발화 중 완료한 ASR 연산을 다시 더하지 않는다.

20개씩의 비중은 설계 coverage를 위한 균등 배치다. 실제 사용 빈도 조사값이 아니다. 평균과 유형별 결과를 함께 판단한다. 모든 주 비교 요청은 평가 시점에 다른 무거운 시각 작업과 겹치지 않으며, R3도 동일한 총 CPU 예산에서 순차 시각 admission을 사용한다. 별도 동시 작업과 장애 조건은 뒤에서 분리한다.

## 작업별 가정과 시간 계산

장치 가정은 CPU 물리 8코어, RAM 16 GB, SSD이며 GPU를 쓰지 않는다. 시각 추론은 네 안에 같은 총 예산을 적용하고 B는 최대 4개 연산 thread를 사용한다. 이는 코어 독점 예약을 뜻하지 않는다. 공통 ASR·UI 자원 비용을 포함한다.

| 작업 | 가정 시간 |
| --- | ---: |
| S2S 최종 텍스트 잔여 | 0.30초 |
| 공통 화면 필요 판단 | 0.65초 |
| 원본 읽기 | 0.08초 |
| worker/runtime 첫 준비 | 1.20초 |
| UI detector/OCR 모델 준비 | 1.10초 |
| SAM 모델 준비 | 0.65초 |
| 새 UI 화면 검출+OCR | 1.60초 |
| SAM 새 frame의 encoder+분할/추적 | frame당 2.05초 |
| R1의 UI 회수 후 SAM 전환 준비 | 0.15초 |
| R3 추가 worker 전달 | 해당 요청 0.06초 |
| R3 두 worker cold 준비의 추가 임계 경로 | 0.30초. 기동 겹침 이후 남는 추가 작업 가정 |
| 최초 채택·표시 | 0.07초 |

cloud 의미 호출은 모든 구성에 같은 식을 적용한다.

```text
호출 시간 = 0.20 + (text 입력 + image-equivalent 입력)/6000 + 출력/80  [초]
```

image-equivalent는 계산용 가상 단위이며 provider의 실제 tokenizer가 아니다. A의 화면 원본과 B의 후보 JSON+crop을 모두 센다. A에 추가 호출을 무조건 붙이지 않는다. S3만 첫 해석에서 과거 crop을 추가 조회하는 경로를 작성했고, 나머지는 단일 직접 해석이다. 이 추가 조회를 제거하면 A는 더 빨라지므로 선택 결론이 B에 유리하게 바뀌지 않는다.

| 첫 해석 입력과 출력 | A text / image / output | B text / image / output |
| --- | --- | --- |
| S1 | 1200 / 0 / 64 | 같음 |
| S2 | 1800 / 6000 / 96 | 1800 / 1400 / 96 |
| S3 | 1800 / 4800 / 96, 추가 1200 / 2400 / 80 | 2000 / 1600 / 96 |
| S4 | 1800 / 3600 / 96 | 1600 / 1200 / 96 |
| S5 | 1600 / 1600 / 80 | 1400 / 600 / 80 |
| S6 | 1600 / 3000 / 72 | 1400 / 800 / 72 |

B는 모든 crop을 없앤 텍스트 전용 입력이 아니다. 후보와 원본 부분 화면을 함께 보낸다. S5에서 A도 이전 확정 내용을 재사용하므로 B의 입력 절감은 작게 설정했다.

## S2 한 장면의 끝까지 추적

화면의 견적 L과 R은 원 안에 있고 Z는 바로 밖에 있다. 사용자는 **“방금 원으로 묶은 이 두 견적을 설치비는 제외하고 비교표로 만들어줘.”**라고 말한다. 첫 응답은 **“견적 L과 R의 설치비를 제외한 비교표 작성을 맡기겠습니다.”**다. 이는 지칭과 처리 의도를 채택한 구체적 내용이고 비교표가 이미 완성됐다는 주장은 아니다. UI box로 포함 관계를 판단할 수 있어 SAM은 호출하지 않는다.

| 최초 내용 표시까지 | A | B-R1 | B-R2 | B-R3 |
| --- | ---: | ---: | ---: | ---: |
| S2S 잔여+gate+원본 읽기 | 1.03 | 1.03 | 1.03 | 1.03 |
| runtime 준비 | 0 | 1.20 | 1.20 | 1.20 |
| UI 모델 준비 | 0 | 1.10 | 1.10 | 1.10 |
| UI 검출·OCR | 0 | 1.60 | 1.60 | 1.60 |
| UI 회수·전환 | 0 | 0 | 0 | 0 |
| SAM 모델 준비 | 0 | 0 | 0 | 0 |
| SAM 추론 | 0 | 0 | 0 | 0 |
| 추가 IPC | 0 | 0 | 0 | 0.06 |
| 원본 직접 해석 또는 후보 결합 | 2.70 | 1.933 | 1.933 | 1.933 |
| 채택·첫 표시 | 0.07 | 0.07 | 0.07 | 0.07 |
| **QA01** | **3.800** | **6.933** | **6.933** | **6.993** |

첫 화면에서는 R2도 cold여서 R1과 같은 시간이 든다. 상주 이익은 이후 새 화면을 처리할 때 나타난다. S4에서는 R1의 UI 재로딩 **1.10초**를, S3에서는 UI/SAM 재로딩 1.75초와 전환 0.15초를 합한 **1.90초**를 R2가 피한다.

첫 응답 뒤의 공통 경로는 Agent 전달 0.15초 → 외부 업무 8초 → 결과 연결 0.10초 → 최종 상세·요약 의미 호출 1.8667초 → 전체 음성 요약 준비 0.35초 → UI 0.05초다. 외부 업무만 제외한 **2.5167초**가 이번 단일 새 목표의 QA03에 추가된다. 따라서 S2 QA03은 **A 6.3167 / R1 9.4500 / R2 9.4500 / R3 9.5100초**다. 이는 이 완료 경로에서 산출한 결과이며 모든 DP에서 QA03=QA01+상수라는 뜻은 아니다. 정정으로 시작점을 당기거나 이전 작업 시간을 지운 사례도 아니다.

모델 회수는 최종 입력 복사 이후 Agent 전달과 병행하므로 QA03에 다시 더하지 않는다. 생성기는 선행 edge와 외부 업무 duration=0인 인과 경로를 별도로 계산해 wall time에서 8초를 뺀 값과 일치하는지 확인한다.

## 정확도의 작성 근거

| 유형 20개씩 | A 지칭 정답 | 모든 B 지칭 정답 | 대상은 맞고 의미만 틀린 공통 입력 |
| --- | ---: | ---: | ---: |
| S1 | 20 | 20 | 1 |
| S2 | 17 | 19 | 1 |
| S3 | 16 | 18 | 1 |
| S4 | 18 | 19 | 1 |
| S5 | 17 | 19 | 1 |
| S6 | 19 | 20 | 0 |
| 합계 | **107/120** | **115/120** | **5/120** |

A의 13개 대상 오류는 경계 밖 카드 포함, 작은 영역 누락, 두 시점의 같은 대상을 다른 대상으로 처리하거나 다른 대상을 같은 것으로 묶는 오류로 작성했다. B는 그중 9개를 해결하지만, S5의 얇은 경계 후보를 잘못 보존한 별도 1개에서 A가 맞고 B가 틀리는 것으로 구성했다. 공통 실패 4개와 B 신규 실패 1개가 있어 B의 오류는 5개다. 전문 모델이 항상 정답을 제공하는 설정이 아니다.

5개의 순수 의미 오류는 네 안 모두 설치비 제외를 누락하고, 지칭 오류와 겹치지 않는다. 따라서 QA07은 A **102/120=85.00%**, B **110/120=91.67%**다. QA02 **89.17% 대 95.83%**와 같은 대상 개선을 독립적인 두 효과로 더하지 않는다. B 세 안의 최초 채택은 동일하다. 로딩 정책으로 정확도를 높이는 가정은 없다.

예를 들어 S2-01에서 A는 L+Z를 처음 채택하고 B는 L+R을 채택한다. A의 틀린 구체적 첫 응답도 3.8초로 남긴다. S2-10에서는 네 안 모두 L+R은 맞지만 설치비를 포함한 비교를 채택한다. QA02는 성공, QA07은 실패이며 이후 Agent가 그 잘못된 의미대로 작업한 것을 성공 의미로 바꾸지 않는다.

오류 빈도 자체는 구조에서 도출된 통계가 아니다. 각 오류가 그 구조에서 생길 수 있는 이유를 붙여 작성한 값이다. 120개 행과 산술 검사가 그 확률의 실제성을 증명하지 않는다.

## 비용과 변경 범위

가상 요율은 공통판과 같은 text 입력 $1/M, 출력 $4/M, 음성 생성 $0.002/초에 image-equivalent 입력 $1/M와 음성 입력 $0.001/초를 명시적으로 추가했다. 모든 평가와 준비 입력은 음성 6초, 결과 요약은 4초로 구성했다. 시장 가격이 아니다.

| 비용 USD | A | 모든 B |
| --- | ---: | ---: |
| 평가 120개 VIA | 2.60368 | 2.24928 |
| 준비 60개 VIA | 1.30152 | 1.16952 |
| **QA05** | **3.90520** | **3.41880** |
| 수신 Agent 별도 | 0.32400 | 0.32400 |

local 생산·로딩의 cloud 요금은 0이고 CPU 시간·RAM에는 비용이 남는다. R1의 재로딩을 API 요금에 가산하지 않는다. B의 절감액 **$0.4864, 약 12.46%**는 원본 영상 입력·S3 추가 조회 감소에서 나오며, 후보 text·crop·준비 활동·음성도 모두 포함한 값이다. COMMON-28의 비용 목표·점수나 기존 Text 120묶음과 직접 비교하지 않는다.

QA04의 C01~C06은 A **1,1,1,3,2,3**, B **1,1,1,3,2,4** 모듈이다. B의 C06은 구간별 근거 철회가 후보·track 의존 무효화로 전파되도록 `concept::candidate_dependencies`를 추가 수정한다는 가정이다. 따라서 **A 11/6=1.83, B 12/6=2.00**이다. Python 파일, 모델 수, worker 수를 Rust 변경 수로 세지 않는다. 공통 범위 판정기로 후보 의존성까지 처리할 수 있다면 B도 1.83으로 동점이다. 이 작은 차이를 선택의 주요 근거로 쓰지 않는다.

## RAM의 같은 시점 합계

공통 560 MB는 core/UI 180, local ASR+audio 220, 압축 원본 이력 96, 공통 요청·대화 상태 64다. B의 episode는 가중치와 별도인 보존 frame/embedding/track 버퍼이며 최대 180 MB다. 새 입력에서는 필요한 용량을 확보하는 가정이며, 준비되지 않은 의미 결과가 미리 있다는 뜻은 아니다. raw 압축 이력과 중복 계상하지 않는다.

R1의 해당 peak에서는 UI 모델을 회수한 뒤 SAM이 동작한다. UI 추론 때의 workspace 260 MB와 로딩 임시 버퍼 380/156 MB는 다른 시점 원장에 포함하며 위 peak를 넘지 않는다. 공유 runtime 페이지 60 MB를 R3에서 한 번만 세고 private 280 MB를 worker별로 센다. 실제 checkpoint 크기를 그대로 RAM으로 옮긴 값이 아니다. 할당·해제 후 이 가정대로 물리 RAM이 회수된다는 실행 profile이며 allocator 잔류가 크면 R1의 이익은 줄어든다.

## R3가 유리한 조건을 별도로 본다

주 비교의 단일 요청에서는 R3에 병렬 보너스를 주지 않았다. **독립된 UI와 SAM 작업이 겹치면** 다른 결과가 가능하다. 보조 계산으로 UI 1.6초와 SAM 잔여 4.1초를 두자.

- R2 기본 순차: SAM 완료 4.1초, 뒤의 UI 완료 5.7초. 두 작업 완료시간 평균 4.9초.
- R3 CPU 예산 분할: 총 4 threads를 2+2로 나누고 각각 1.6배 느려진다고 가정하면 UI 2.56초, SAM 6.56초다. 각 IPC 0.06초를 포함하면 2.62/6.62초, 평균 4.62초다.
- 짧은 UI의 대기는 줄었지만 긴 SAM 완료와 두 작업 전체 완료시각은 늦어진다. UI workspace 최소 260 MB와 추가 episode 상태가 동시에 필요하다.
- R2도 제한 병렬을 허용하면 같은 계산을 할 수 있다. 이 속도 이익은 process 분리만의 독점적 효과가 아니다.

이 값은 시각 stage 경합만의 보조 계산으로 QA01/03 headline에 합치지 않는다. 전체 요청과 두 목표를 평가하려면 각각의 의미·출력 경로와 자원 edge를 포함해야 한다.

SAM worker가 native crash나 강제 종료로 복구돼야 할 때 R3는 UI worker의 모델과 상태를 보존한다. R2는 공유 worker를 재시작하면 둘 다 잃는다. 이 독립 복구가 R3의 가장 명확한 고유 이익이다. 현재 7개 QA의 정상 요청 집계만으로 그 이익을 충분히 표현하지 못하며, QA04 모듈 수를 복구성 점수로 바꾸지 않는다.

## 선택과 뒤집히는 조건

**현재 합의 순서 QA01→QA02→QA03→QA04→QA05→QA06을 적용해 A를 선택한다.** 새 QA07을 임의로 먼저 두지 않는다. 이번 가정에서 A는 B-R2보다 첫 응답과 목표 완료가 모두 평균 1.817초 빠르고, peak RAM은 1,782 MB 적다. 그 대가로 지칭/전체 의미 성공률을 6.67%p씩 잃고 청구액 $0.4864를 더 쓴다. 정확도 차이는 같은 오류 개선이므로 두 번 합산하지 않는다.

B-R2는 B-R1보다 첫 응답이 평균 0.500초 빠르지만 RAM을 420 MB 더 쓴다. 정확도와 청구액은 같다. B-R3는 R2보다 정상 단일 요청이 평균 0.04초 늦고 RAM은 288 MB 더 쓴다. 독립 복구 요구가 없는 현재 조건에서는 그 추가 비용을 선택할 이유가 약하다.

이 결론을 바꾸는 조건은 수치로도 드러난다.

1. **A의 원본 해석·재조회가 현재 가정보다 평균 1.817초 이상 더 오래 걸리면** 다른 조건이 같을 때 R2가 QA01에서 역전할 수 있다. 현재 A를 약화해 그 지연을 미리 추가하지 않았다.
2. S5 재사용 장면에서는 A 2.833초, B 2.633초다. 나머지 다섯 장면 비율을 동일하게 둔 채 S5 비중만 높이면 **약 91.7%**를 넘을 때 R2의 전체 QA01이 A보다 짧아진다. 이는 작성한 profile의 민감도이며 실제 사용 빈도 예측이 아니다.
3. 정확도를 시간보다 우선하거나 사전에 별도 최소 정확도 자격을 합의하면 B-R2를 선택할 수 있다. 결과를 본 뒤 A를 탈락시키기 위해 문턱을 새로 만들지는 않는다.
4. 메모리가 가장 큰 제약이면 B-R1, 독립 복구·운영이 강한 요구이면 B-R3가 선택 이유를 얻는다. 512 MB는 이번에 적용하지 않는다.

작성한 profile에서의 결론은 명확하지만, 이 자료가 실제 제품의 승자를 측정한 것은 아니다. CPU 생산 시간·원본 직접 해석 시간·실제 오류 빈도·RAM 반환 특성을 이후 검증하면 선택을 재판단할 수 있다.

## 재생성과 확인

`python3 build.py`는 이 디렉터리 안의 JSON/CSV/집계만 다시 만든다. 모델 설치·API 호출·후보 구현이나 성능 계측을 수행하지 않는다. 입력·표현·목표 ID, 최초 채택 정답 판정, 60개 준비 포함, B 세 안 비용/정확도 일치, 단계 선행 순서, 외부 구간 제거 DAG, RAM 최고점 합계와 보존 상태 재사용을 검사한다. hash는 작성 자료의 연결을 식별하며 사실성의 인증이 아니다.
