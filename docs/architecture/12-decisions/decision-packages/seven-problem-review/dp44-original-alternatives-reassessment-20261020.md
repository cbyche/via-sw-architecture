# 원래 DP44 A/B의 설득력 재평가

> **2026-10-21 후속 사용자 방향:** DP44를 VIA의 핵심 대화 문제로 다시 깊게 탐색한다. 아래는 원래 Dispatcher/Stage 비교에 대한 당시 작성자 판단이며 현재 탐색의 종료나 최종 선택이 아니다. [대화 전달 구조 재정립](dp44-conversation-delivery-reset-20261021.md)에서는 기존에 공통화했던 게시 조건·실제 전달·후속 상호작용 연결까지 구조 탐색 범위로 다시 연다.

2026-10-20 / 원래 설계에 대한 작성자 재평가 / 미구현·미측정·사용자 미선정

## 1. 결론

**중앙 비동기 Dispatcher A와 Stage 연결 B는 실제 Architecture 대안이다. 다만 현재 VIA 범위와 QA01~07로 보면, 주요 DP로서의 품질 교환은 약하다.** 기능적으로 중요한 문제이고 구조 차이도 있지만, B를 선택할 정상 사용의 품질 이익이 현재 자료만으로 충분하지 않다.

현 시점 구현 출발점으로는 A를 권고한다. 이는 QA01/03/04/06의 실측 승리나 사용자 채택이 아니라, 필요한 공통 동시성을 제공하면서 교차 사건의 진행 연결을 한 위치에서 표현할 수 있다는 설계 판단이다. B의 분산 활성화/조건 상태를 도입할 추가 이유는 중앙 처리의 실제 병목 또는 현재 변경 과제에서의 국소화 이익으로 확인해야 한다.

이 평가는 [원래 DP44](../04-44-continuous-interaction.md), [구현 가정 설명](../dp44-implementation-structure.md), [2026-10-18 재검토](03-execution-coordination.md)를 대상으로 한다. 최근 제안한 응답 통합/문안 생성 후보로 원래 A/B를 대체하지 않는다. 기존 설계·그림·QA 정의·ADR을 변경하지 않는다.

## 2. 설계 차이는 실재한다

| 질문 | A 중앙 비동기 Dispatcher | B typed Stage 연결 |
| --- | --- | --- |
| 작업 완료를 누가 받는가 | 중앙 Event Mailbox와 Dispatcher | 시작한 Stage의 Done port |
| 다음 실행을 누가 시작하는가 | 중앙 continuation의 코드 | 고정 port의 결과를 소비하는 Stage |
| 실행 중·대기 상태는 어디에 있는가 | Progress State와 Job Index | 각 Stage의 Job/Window와 Publication Join |
| 관련 정정의 전달 | 중앙이 관련 job/candidate를 찾아 무효화 | 관련 Stage에 판본/무효화 전달, 각 Window와 Join 갱신 |
| 확정 원본과 최종 게시 권한 | 공통 owner와 Publication Control | 동일. Join만으로 게시 권한을 대체하지 않음 |

단순히 handler를 별도 모듈로 나누거나 함수 이름을 Stage로 바꾸는 것은 B가 아니다. 후속 실행을 시작하는 책임과 임시 상태의 소유가 바뀌어야 한다. 반대로 B에 공통 runtime이나 최종 게시 지점이 있다는 이유만으로 A와 같아지는 것도 아니다.

## 3. 동일한 사건을 끝까지 비교

같은 대화에서 R1의 응답 준비가 진행 중이다. 별도 메일 Task의 확정된 질문 Q가 도착한다. 이후 R1만 바꾸는 정정이 채택되고, R1의 이전 준비 결과가 늦게 반환된다. 의미 해석 기능/결과는 동일하게 두며 그 실행 방식은 여기서 바꾸지 않는다.

### A

1. R1의 응답 준비 job은 worker에서 실행 중이며 Dispatcher를 점유하지 않는다.
2. Q가 Mailbox에 들어오면 Dispatcher가 대화 연결/허가를 반영하고 필요한 준비 job을 시작한다. Q가 이미 표시 가능한 문구라면 공통 직접 표시 경로를 쓴다.
3. Q의 준비 완료를 Dispatcher가 회수하고 게시를 요청한다.
4. R1 정정이 채택되면 관련 job/candidate 참조를 무효화한다. 별도 메일 Q는 유지한다.
5. 이전 R1 결과가 늦게 오면 판본을 확인해 폐기한다.

### B

1. R1의 응답 준비 job은 worker에서 실행 중이며 Stage의 짧은 Pump를 점유하지 않는다.
2. Task Notice Stage가 Q를 소비하고 유효 Notice를 Response Composer에 전달한다. 직접 표시 가능한 Q는 같은 공통 기능으로 표시한다.
3. Composer의 준비 완료가 Candidate Queue로 가고, Publication Join이 해당 Q의 조건을 결합해 게시를 요청한다.
4. R1 정정은 관련 Window와 Join에 전달된다. Q의 별도 참조는 유지한다.
5. 이전 R1 결과는 Composer의 Done 처리와 최종 유효성 검사에서 탈락한다.

**양쪽 모두 R1 준비 전체가 끝나야 Q를 처리하는 구조가 아니다.** B만 병렬인 것으로 설명하면 A를 잘못 구현한 비교가 된다.

## 4. QA01/QA03: 차이는 어떤 대기인가

공통 작업과 검사 외에 A에는 중앙 완료 회수/재배정이 있고, B에는 Stage 전달/readiness/Join이 있다.

```text
A: 공통 작업 + 임계 경로에 남는 중앙 queue/handler/재배정
B: 공통 작업 + 임계 경로에 남는 Stage queue/handler/조건 결합
```

- B의 이익 후보는 중앙에 모인 **다른 흐름의 짧은 제어 처리** 때문에 생기는 대기를 피하는 것이다. 다른 흐름의 긴 모델 호출 자체를 피하는 이익은 아니다.
- B의 비용 후보는 여러 Queue 전달, 조건 도착 차이와 Join 관리다. Stage 수가 많다고 항상 더 느리다는 뜻도 아니다.
- A의 handler에서 네트워크/모델/장시간 저장을 동기 대기시키거나 모든 음성 frame을 중앙에 보내서 병목을 만들지 않는다.
- B가 중앙 Dispatcher를 없애더라도 공통 Response Composer, 모델 서비스와 최종 게시 지점의 한계까지 사라지지는 않는다.
- 같은 bounded 실행/전체 payload 예산과 공통 제어 우선권에서 비교한다. B에만 여유 worker를 주거나 A에만 FIFO를 강제하지 않는다.

**판정:** QA01과 QA03에 직접 관여하지만, 정상 사용에서 어느 쪽의 잔여 대기가 큰지는 미확정이다. 코드 경로가 짧다는 이유만으로 차이가 절대 작다고 단정하지도 않는다. 현재 큰 차이를 예측할 제품 부하/trace 근거가 없다는 판단이다.

QA01의 첫 UI 표시와 QA03의 전체 상세/음성 준비까지를 각각 관측한다. 실제 음성 차례의 변화만으로 두 지표를 개선했다고 말하지 않는다.

## 5. QA04: 어떤 변경에서 유리한가

원래 B의 가장 합리적인 선택 이유 중 하나는 생산 경로의 독립 변경이다. 하지만 현재 QA04는 추상적인 결합도나 팀 충돌 수가 아니라 실제 Rust 변경 모듈 수다.

| 변경 | A에 남는 작업 | B에 남는 작업 | 판단 |
| --- | --- | --- | --- |
| C01~03 외부 형식 변경 | 공통 adapter에서 흡수될 수 있음 | 동일 | 기존 실행 연결까지 바뀐다는 근거 없으면 차이 없음 |
| C04 응답 중 지정 문단만 수정 | 부분 범위와 영향 job/candidate 처리 | 부분 범위 envelope, Window, Join의 영향 처리 | A가 중앙에서 표현하기 쉬울 수 있으나 공통 Composer/게시 변경도 포함해야 함 |
| C05 실제 전달한 설명의 원본 범위 표시 | 전달 원장/조회 경로 변경 | 같은 원장을 쓰므로 공통 변경 가능 | 자동 차별화 아님 |
| C06 원본의 지정 구간만 사용 철회 | 영향 의존을 찾아 준비/게시 제한 | 관련 Stage에 구간 무효화 전파, 조건 결합 | B의 국소 변경이라고 단정하기 어려움 |

기존 port 계약 안의 독립 생산 단계 추가/교체라면 B가 유리할 수 있다. 그러나 A도 handler 등록과 공통 interface를 사용할 수 있다. 새 Agent 하나를 연결한다는 사실만으로 VIA의 새 실행 Stage가 필요하지도 않다. 이 변경은 현재 C01~06에 없는 별도 설명 사례이며 평가 모집단에 몰래 추가하지 않는다.

중앙 모듈 하나에 변경이 집중되는 개발 경험의 부담은 실재할 수 있으나, 그 사실만으로 QA04의 변경 **개수**가 증가했다고 세지 않는다.

**판정:** QA04는 유효한 비교 후보이지만 현재 모듈 registry/diff 없이 A/B의 우위를 확정할 수 없다. 특히 “Stage 분리이므로 B 변경성이 우수하다”는 결론은 지지되지 않는다.

| QA | 원래 A/B의 직접 관련성 | 차별화와 근거 상태 |
| --- | --- | --- |
| QA01 첫 응답 | 있음 | 중앙 대기 대 분산 전달/Join. 방향/실용 크기 미확정 |
| QA02 지칭 정확도 | 동일 의미 기능을 실행 연결함 | 같은 판단 근거와 첫 채택 결과이면 구조 자체 우위 없음 |
| QA03 VIA 처리시간 | 있음 | 후속 실행 활성화/조건 대기 차이. QA01과 같은 원인이 일부 겹치며 독립 절약량으로 합산하지 않음 |

| 새 QA07 요청 의미 정확도 | 동일 의미 기능을 연결함 | 출력 현재성/무효화 오류를 최초 요청 의미 정확도로 바꾸지 않음 |

B에 queue가 많다는 사실만으로 RAM이 배수로 증가하지 않는다. 불변 payload 참조 공유를 허용하고 동일 총량 상한으로 비교한다. A의 중앙 인덱스가 끝난 참조를 더 오래 붙잡을 가능성도 있다.

## 7. B를 선택할 합리적인 조건

B는 존재 이유가 없는 안이 아니다. 다음 조건에서는 유지할 가치가 있다.

1. 현실적인 정상 사용에서 서로 독립된 여러 생산 경로의 완료가 중앙에 집중되고, 짧게 구현한 Dispatcher에서도 첫 게시까지의 대기가 의미 있게 남는다.
2. 소비 Stage의 독립 활성화가 그 대기를 실제로 줄이며 추가 Queue/Join과 공통 병목이 이익을 상쇄하지 않는다.
3. 안정된 port 계약 아래 바꾸는 생산 단계가 많고, 같은 변경을 A보다 적은 실제 모듈 수정으로 완료할 수 있다.

이는 조건부 선택 이유이지 현재 제품에서 관측한 사실이 아니다. 고빈도 음성 frame 처리나 독립 서비스 장애 격리를 비교 범위 밖에서 가져와 B의 이익으로 세지 않는다.

## 8. 설득력 판정과 권고

| 평가 질문 | 판정 |
| --- | --- |
| VIA에서 해결할 중요한 문제인가 | 그렇다. 여러 사건의 진행·대기·정정·실제 전달을 연결해야 함 |
| A/B가 실제 SW 구조 차이인가 | 그렇다. 후속 실행 권한과 임시 상태/조건 관리가 다름 |
| 두 안이 현실적으로 구현 가능한가 | 그렇다. 같은 공통 기능을 비동기로 제공하는 설계 |
| 현재 QA01~07에서 양쪽 선택 이유가 강한가 | 아직 부족. B의 정상 사용 속도/변경 범위 이익이 미확정 |
| QA 3~4축의 명확한 교환을 보여주는 주요 DP인가 | 현재 자료로는 부족 |

**권고는 A를 구현 출발점으로 두고 원래 DP44를 독립 상세 설계로 보존하는 것이다.** B가 요구하는 실행 조건/판본 전파를 감수할 이유를 아직 확보하지 못했기 때문이다. A가 측정상 우수하다는 결론과 구별한다.

반증 조건은 명확하다. 정상 사용의 실제 중앙 대기가 QA01/03을 악화시키고 B가 이를 줄이거나, 현재 QA04 변경 과제에서 B가 더 적은 모듈 변경을 요구하면 이 권고를 재검토한다. 유의미한 품질 차이 없이 구현 스타일만 달라지는 결과라면 상세 설계 판정을 유지한다. 미실측만을 이유로 결론을 유예하는 것이 아니라 현재 구조의 인과로 큰 차이를 예측할 근거가 약하다는 평가다.

## 9. 참고의 적용 범위

[Microsoft Choreography](https://learn.microsoft.com/en-us/azure/architecture/patterns/choreography)는 중앙 조정과 참여자별 다음 처리의 차이, 조건 합류/실패/이벤트 계약의 부담을 설명한다. 원래 DP44의 실행권 분산을 이해하는 참고이며 서비스 분리·클라우드 확장성 이익을 VIA에 자동 적용하지 않는다.

[Reactive Streams](https://www.reactive-streams.org/)는 비차단 backpressure를 다룬다. bounded 수용량은 A에도 구현할 수 있으므로 B만의 메모리/수용량 이익이 아니다.

기존 상세 소스 분석은 [실행 연결 원장 E05~E07/E10](../../../../references/seven-problem-review/execution-lifecycle.md)에 있다. 이번 평가는 신규 독립 에이전트 리뷰, 제품 구현, 모델 실행, 성능 측정, QA 점수 변경 또는 commit/push를 수행한 결과가 아니다.
