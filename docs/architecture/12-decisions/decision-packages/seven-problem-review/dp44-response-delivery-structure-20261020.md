# DP44: 여러 응답과 Agent 통지의 전달 구조

> **후속 사용자 기준 반영:** 사용자는 자연스러운 전달 경험을 QA로 추가하지 않고 현재 QA01~07의 손익으로 비교하도록 요청했다. 아래 A/B는 주요 대안으로 유지하지 않는다. 최신 재탐색은 [응답 문안 경유와 채널별 직접 생성](dp44-output-generation-tradeoffs-20261020.md)이며 QA03/QA05의 조건부 후보와 한계를 기록한다.

2026-10-20 / 사용자 범위 정정 반영 / 설계 검토 / 미구현·미측정·미선정

## 1. 이번 비교의 경계와 결론

사용자는 의미 해석 실행을 DP2 세션에서 구체화하고, DP44에서는 여러 응답과 Agent 통지가 겹칠 때 사용자에게 전달하는 구조를 비교하도록 요청했다. [직전 의미 상태 동시성 비교](dp44-state-concurrency-reconstruction-20261020.md)는 DP2 검토 입력으로 남긴다.

이번 구조 질문은 **사건별 응답을 독립 산출물로 만들고 전달할 것인가, 현재 전달해야 할 사실들을 하나의 응답 상태로 관리하고 그 상태에서 표현물을 만들 것인가**다. 출력 우선순위가 아니라 생성 입력, 산출물 식별자, 무효화 범위와 실제 전달 기록의 연결이 달라진다.

다만 아래 두 구조에서 **A는 QA01, B는 QA03이 유리하다는 교차 우위를 현재 정의로 뒷받침할 수 없다.** 확정된 질문과 업무 상태는 두 안 모두 코드로 바로 표시할 수 있다. 음성 생성량 감소도 병렬 실행의 임계 경로 단축과 같지 않다. 구조 후보의 구체화와 강한 QA trade-off의 성립을 구별한다.

## 2. 공통 입력과 완료 조건

DP44가 받는 입력은 원문 해석 요청이 아니라 다음 내용이 이미 확정된 전달 요청이다.

```text
DeliveryIntent {
  event_id, task_id, request_revision,
  kind: progress | question | result | response | withdrawal,
  adopted_facts, source_content_ref,
  supersedes_ids, question_id,
  required_text_fields, required_audio_facts
}
```

- Task 연결, 사용자 정정의 의미와 적용 범위, 필요한 후속 업무는 상위 의미/업무 처리에서 확정한다. DP44의 LLM은 사용자 의도 재판단이나 Agent 업무를 수행하지 않는다.
- 형식화된 상태와 질문은 코드로 표시한다. 길거나 비정형인 결과의 사용자용 표현과 음성 요약에 필요할 때만 일반 LLM을 호출한다.
- S2S에는 확정된 전달 내용과 음성 생성 요청만 전달한다. 업무 tool call을 제공하지 않는다. 확정 문구의 음성 생성과 버퍼 수신은 모델 어댑터에 요구하는 capability이며 특정 S2S API의 지원을 확인한 사실은 아니다.
- 생성 완료와 실제 UI 표시, 실제 재생은 서로 다른 receipt로 남긴다. 질문이 준비됐다는 사실을 사용자가 질문을 들었다는 사실로 취급하지 않는다.
- 요청 판본과 철회 여부를 실제 게시/재생 전에 검사한다. 이미 전달한 내용을 나중에 정정한 기록은 지우지 않는다.
- 재생 순서와 중단 정책, 모델의 다중 요청 지원은 양안 동일하다.

[QA01](../qa-candidate-package/qa01-first-response-latency.md)은 첫 완결된 내용의 실제 UI 표시까지다. [QA03](../qa-candidate-package/qa03-via-processing-time.md)은 원래 사용자 목표의 필수 상세 표시와 전체 음성 요약 준비를 포함하는 VIA 귀속 임계 경로다. 실제 청취 차례는 QA03에 포함하지 않는다. 공통 필수 사건을 임의로 병합해 분모에서 제거하지 않는다.

## 3. 같은 사건

사용자에게 앞선 설명의 음성이 재생되는 동안 다음 사건이 온다.

1. 보고서 Task에서 “자료 수집 완료, 보고서 작성 중”이라는 확정 상태가 온다.
2. 별도 메일 Task에서 “제목을 A와 B 중 무엇으로 할까요?”라는 질문이 온다.
3. 보고서 Task의 완료 결과와 링크가 온다. 이전 진행 상태의 현재 표시를 대체한다.

질문과 결과의 내용 판단은 완료돼 있다. 보고서 읽기와 분석을 VIA가 다시 수행하지 않는다. 메일 질문은 보고서 완료로 해결되지 않으며 반드시 보존한다. 과거 진행 사건의 평가 의무와 최신 음성 요약의 필수 사실은 공통 계약을 따른다.

## 4. A: 사건별 독립 응답 산출물

```text
DeliveryIntent
  → Event Response Builder
      ├─ 확정 필드의 UI 표시
      └─ 필요 시 일반 LLM으로 표현/음성 문구 작성
           → S2S 음성 생성
           → ResponseArtifact 저장
  → Delivery Arbiter가 현재 유효성을 확인하고 전달
  → Delivery Ledger에 실제 전달 receipt 저장
```

새 이름은 이번 대안의 책임 설명이며 참조 Architecture의 Component를 개명한 것이 아니다.

`ResponseArtifact`는 사건 ID, 요청 판본, 상세 텍스트, 음성 문구와 버퍼 참조를 소유한다. 서로 독립인 사건의 준비 작업은 병렬로 수행한다. 짧은 질문은 원문을 바로 쓰며 LLM 호출을 강제하지 않는다.

같은 장면에서 진행 응답 P, 메일 질문 Q, 완료 응답 R이 각각 생성된다. R이 오면 코드가 이미 확정된 대체 관계에 따라 미전달 P를 무효화한다. Q의 텍스트와 음성 버퍼는 재사용한다. 이미 표시한 진행 상태는 완료 상태로 갱신하고 전달 이력은 보존한다.

**이익:** 독립 응답끼리 생성 의존이 없다. 다른 Task의 완료 때문에 준비된 질문을 다시 만들지 않는다. 개별 실패와 재시도 범위가 작다.

**비용:** 짧은 시간에 바뀌는 상태도 사건마다 표현/음성을 만들면 폐기되는 산출물이 생긴다. 산출물별 유효성, 버퍼, 전달 위치를 관리해야 한다. 준비된 여러 응답을 연속 재생할 때 문맥 연결이 부자연스러울 수 있다.

완성된 응답을 반드시 하나의 자연어 문장으로 재합성하는 LLM 단계는 A의 필수 요소가 아니다. 이를 억지로 추가해 QA03을 불리하게 만들지 않는다.

## 5. B: 현재 전달 상태에서 응답 표현물 생성

```text
DeliveryIntent
  → Response State Reducer
      ├─ Task별 현재 사실/미해결 질문/전달 기록 갱신
      ├─ 확정 필드의 UI 표시
      └─ 변경된 응답 영역의 snapshot
           → Response View Compiler
              → 필요 시 일반 LLM으로 연결된 표현/음성 요약 작성
              → S2S 음성 생성
              → snapshot과 연결된 표현물 게시
```

주된 지속 상태는 사건마다 만들어진 발화가 아니라 **현재 전달할 사실, 해결되지 않은 질문, 실제 전달 범위**다. 표현물은 이 상태에서 파생되며 원본 사건과 의존 관계를 보존한다. 전체 대화를 매번 재작성할 필요는 없고 관련된 응답 영역만 갱신할 수 있다.

같은 장면에서 보고서 영역은 진행 상태에서 완료 상태로 바뀌고, 메일 영역에는 Q가 남는다. 연결된 음성 표현을 만들 필요가 있으면 컴파일러는 “보고서는 완성됐습니다. 메일 제목은 A와 B 중 무엇으로 할까요?”처럼 생성한다. 원래 질문 ID와 보고서 결과 ID를 각 부분에 연결한다.

컴파일 중 관련 사실이 바뀌면 그 사실에 의존하는 미전달 부분을 무효화하고 현재 상태로 다시 만든다. 독립된 질문까지 무조건 폐기하거나 새 사건이 왔다는 이유만으로 모든 생성을 취소하지 않는다. 이미 생성한 관련 없는 부분은 유지할 수 있다.

**이익:** 현재 상태에 맞는 연결된 안내를 만들기 쉽고, 아직 표현하지 않은 과거 상태를 별도 음성 산출물로 만들지 않을 수 있다. 여러 통지의 반복 설명을 줄일 여지가 있다.

**비용:** 사실과 표현 부분의 의존 관계, 상태 판본, 실제 전달 범위의 대응이 필요하다. 여러 사실을 함께 표현한 부분은 하나의 변경 때문에 재생성될 수 있다. 여러 Task를 묶는 작업은 각각의 완료 경로에 의존을 추가할 수 있다.

“일정 시간 기다려 묶는다”는 B의 구조 정의가 아니다. debounce는 B1 같은 별도 tactic이다. A에도 생성 지연 tactic을 붙일 수 있으므로, B만 과거 상태의 생성 비용을 줄일 수 있다고 주장하지 않는다.

## 6. QA01과 QA03의 실제 판정

| 경로 | A | B | 현재 판정 |
| --- | --- | --- | --- |
| 확정된 진행/완료 사실의 첫 UI 표시 | 필드로 즉시 표시 | 상태 반영 후 필드로 즉시 표시 | 큰 QA01 차이 근거 없음. 실제 코드/표시 지연은 남음 |
| 확정된 Agent 질문의 첫 UI 표시 | 질문을 바로 표시 | 미해결 질문을 바로 표시 | 의미/표현 LLM 대기를 강제하지 않음 |
| 독립된 여러 응답의 상세/음성 준비 | 각각 병렬 준비 | 영역별 독립 준비 가능. 결합 시 공동 생성 의존 추가 | QA03의 B 우위는 자동 성립하지 않음 |
| 생성 중 관련 사실의 변경 | 관련 사건 산출물을 교체 | 변경된 사실에 의존하는 표현 부분을 갱신 | 실제 무효화/재사용 범위와 완료 의존에 따라 달라짐 |
| 반복 문구 감소 | 사건별 문구에 반복 가능 | 연결된 요약에서 반복을 줄일 가능성 | 음성 생성 시간/비용 가설. 실제 재생 시간 절약은 QA03 이익이 아님 |
| 요청 의미/지칭 정확도 | DP2 결과를 받음 | DP2 결과를 받음 | QA02/새 QA07의 차별화로 세지 않음 |

예를 들어 A에서 필요한 독립 음성 3개의 준비 시간이 각각 `g1, g2, g3`이면 준비 완료의 병렬 경로는 합계가 아니라 `max(g1, g2, g3)`다. B의 통합 준비가 `gB`라면 QA03 이익에는 `gB`와 앞선 컴파일/변경 대기까지 포함해 비교해야 한다. 호출이 3회에서 1회가 된 것만으로 `gB < max(...)`를 결론낼 수 없다. 서로 다른 사용자 목표의 QA03을 하나의 전체 배치 종료시간으로 대체하지 않는다.

표현 생성이 반드시 필요한 사건에서는 A의 작은 개별 생성과 B의 통합 생성 사이 첫 상세 표시 차이가 날 수 있다. 그러나 그 전에 구체적 질문이나 완료 사실을 표시했다면 QA01은 이미 종료됐다. 이 차이를 QA01로 이름 붙이지 않는다.

**따라서 이번 대안들은 출력 순서 이상의 구조 차이가 있지만, 요청한 QA01 대 QA03의 강한 trade-off는 아직 성립하지 않는다.** 이를 만들기 위해 B의 확정 내용 표시를 막거나 A에 불필요한 최종 통합 호출을 추가해서는 안 된다. 현재 근거로 DP44를 QA01 차별화 coverage에 넣지 않는다.

## 7. 참고 구현과 적용 한계

- [Microsoft Materialized View](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)는 원본으로부터 파생 상태를 유지하고 전체/부분 갱신, 판본 교체와 갱신 비용을 선택하는 구조를 설명한다. B의 파생 응답 상태에 참고한 SW 패턴이지 VIA 응답 지연 개선의 증거가 아니다.
- [LiveKit Agent speech and audio](https://docs.livekit.io/agents/multimodality/audio/)는 준비된 음성 재사용과 발화 handle, 생성/재생 제어의 구분을 제공한다. 특정 S2S 모델이 동일 API나 정확한 문구 음성화를 지원한다는 증거로 사용하지 않는다.

이번 검토는 QA의 빈칸을 확인한 설계 분석이다. baseline, QA 의미/점수/모집단과 ADR을 변경하지 않았으며 구현, 모델 호출, 성능 측정과 Git 발행을 수행하지 않았다.
