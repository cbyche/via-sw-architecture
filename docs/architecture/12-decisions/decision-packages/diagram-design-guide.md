# 설계 대안 그림 작성 기준

> 적용: Stage 4~6의 구조 비교와 실행 상세. 2026-10-01 사용자 리뷰 반영.
> [04 전체 지도](./04-00-structural-alternatives.md) / [그림 모음](./diagrams/stage4-review.html)

그림의 목적은 **어떤 SW 책임과 메커니즘이 달라지고, 그 결과 어떤 비용이나 제약이 생기는지** 독자가 직접 확인하게 하는 것이다. 제목은 설계 질문을, 그 아래 한 문장은 비교 축을 설명한다. 박스 수나 장식으로 구조 차이를 대신하지 않는다.

## 1. 먼저 결정할 메시지

| 그림 | 가장 먼저 보여줄 차이 | 확대하거나 분리해서 보여줄 내용 |
| --- | --- | --- |
| S-01 | 호출 사이에서 추가 읽기를 조정하는 구조와 하나의 해석 작업에서 읽고 재개하는 구조 | 기본 Context는 공통. 별도 실행 상세에서 호출 종료, 중단, 반환과 재개 수명을 비교 |
| S-02 | 요청 시 원시 관측 해석, 사전 객체 생산, 사용자 명시 선택의 차이 | 입력 생산자, 파생 저장과 소비 순서. 줄어드는 기능과 추가 생산 비용 |
| S-03 | 기존 owner 조회와 지속적인 의미 후보 생산의 차이 | 색인 생산과 게시를 확대. 후보 발견과 현재 원문 검증의 권한을 분리 |
| S-04 | 현재 domain 상태, workflow continuation, 세션 상태 중 무엇이 재개의 원본인지 | 상태 소유자와 저장 장치를 구별. 유지되는 Task 원장과 포기하는 복구를 함께 표시 |
| S-05 | S2S 직접 경로의 유지 또는 제거 | 보류 generation과 admission, 실제 release를 확대. 공통 Core 해석과 전달 책임 유지 |
| S-06 | 독립 인식 실행과 공유 Omni에 묶인 인식 실행 | VIA 연동 코드, 실제 worker 경계, 모델 의존성을 분리. Omni 장애의 영향 범위 설명 |

## 2. 경계와 표기

1. VIA의 논리 책임 경계와 외부 의존성을 먼저 나눈다. 그 안에서 필요한 Component와 서브시스템만 펼친다. 일부 책임만 담은 그림은 `비교 영역`이라고 밝힌다.
2. 논리 책임, process, 데이터, 저장소, 모델을 같은 종류의 박스로 읽게 하지 않는다. 각 박스 상단의 종류 표식과 경계 이름으로 구별한다. `Request Graph`는 자료이며 별도 실행 Component가 아니다.
3. 모델은 VIA가 사용하는 의존성이다. 모델 내부와 학습을 책임지지 않는다는 표시를 원격 배치로 오해하게 하지 않는다. Model Access의 client, adapter, scheduler는 VIA에 속한다. 같은 모델을 여러 역할이 사용해도 weights를 여러 벌 그리지 않는다.
4. 내부 owner와 외부 source를 함께 펼친 참조는 그 사실을 그림에 표시한다. 원본을 그림 아래에 놓았다는 이유로 내부 소유권을 VIA 밖으로 옮기지 않는다.
5. 실제 process를 나타낼 때만 실행 경계라고 명시한다. 별도 상자나 확대 영역을 그렸다는 사실만으로 장애 격리, 서버 배포나 복제 instance를 주장하지 않는다.

## 3. 배치와 시각적 위계

1. 한 비교 안의 공통 요소는 양안에서 같은 좌표, 크기, 이름과 읽기 방향을 유지한다. 삭제되는 구조의 자리는 남겨 무엇이 사라졌는지 보여준다. 서로 다른 S에 의미 없는 동일 배치를 강제하지 않는다.
2. 읽는 순서는 설계 질문, T/A/B 이름, 큰 책임 경계, 핵심 구조와 흐름, 비용과 제약, 범례다. 결과를 읽기 전에 범례를 찾아 헤매게 하지 않는다.
3. Component 이름은 약칭 대신 정확한 전체 이름을 쓰고, 종류 표식 아래의 본문 영역에 수평 및 수직 중앙 정렬한다. 긴 이름은 의미 단위로 줄을 나누고 박스를 넓힌다. 그림을 맞추기 위해 글자를 계속 줄이지 않는다.
4. 검정은 공통 구조, 파랑은 구조 차이 또는 확대 대상, 황갈색은 비용과 기능 손실을 뜻한다. T에도 비교할 메커니즘을 파랑으로 표시한다. 색만으로 승자나 추천을 암시하지 않는다.
5. 표준 구조도는 2560 × 1660 벡터 canvas를 사용한다. 제목, 방안 제목, Component 이름, 동작 설명, 종류 표식의 크기를 구분한다. 여백은 책임 그룹을 구별하는 데 쓰고 박스 사이에 문장을 채워 넣지 않는다.
6. 한 장에 구조와 모든 시간 순서를 넣기 어려우면 구조도와 실행 상세를 나눈다. 확대도는 원래 책임의 상세이며 추가 instance가 아니다. 글로 쓴 비용 설명을 확대 구조도라고 부르지 않는다.

## 4. 화살표와 실행 순서

1. 화살표는 실제 송신자와 수신자에 닿게 한다. 직교 경로를 사용하고 무관한 박스를 관통하지 않는다. 교차점은 합류를 뜻하지 않는다.
2. 요청과 반환을 별도 방향의 선으로 그린다. 실선은 호출 또는 전달, 점선 화살표는 결과 또는 복원이다. 화살표 없는 점선은 생명선이나 확대 연결이며 호출로 읽게 하지 않는다.
3. 번호와 동작은 선 옆에 쓴다. 각 번호가 본문의 송수신자, payload와 일치하는지 대조한다. 반복 경로는 복수 번호를 표시하고, 그림에 생략한 공통 흐름은 설명한다.
4. 최초 준비, 차이의 시작, 합류와 최종 확정을 찾을 수 있어야 한다. 실행 상세는 위에서 아래로 읽고, 세로 막대는 수명을 나타낸다. 막대 길이를 측정 시간이나 연산 점유량으로 해석하지 않는다.
5. 상태와 출력의 소유권을 지킨다. 자료가 스스로 판단하거나 저장소가 업무 권위를 가진 것처럼 그리지 않는다. 생성 결과, 게시 허용, 실제 전달과 사용자 청취는 서로 다른 사건이다.

## 5. 원본과 검수

- SVG 미리보기와 편집 가능한 draw.io를 함께 관리하고 Markdown에서 둘 다 연결한다. 생성 좌표와 이름의 원본은 `scripts/architecture/generate_stage4_structure_diagrams.py`, 공통 표현은 `scripts/architecture/stage4_diagram_design.py`다. 생성된 SVG만 수정하지 않는다.
- 원본 생성 후 XML, ID, canvas 범위, 직교 경로, 무관한 박스 관통과 생성물 일치를 검사한다. 실제 브라우저 렌더링에서도 글자 겹침, 박스 내부 여백, 잘림, 선과 주석의 혼동을 확인한다.
- 구조와 번호는 본문 및 reviewed target의 소유권 계약에 대조한다. 레이아웃 검사가 통과했다고 Architecture가 검증되었거나 대안이 채택된 것은 아니다.
- 비용, 기능 손실과 지원 미확인을 그림 가까이에 표시한다. Stage 4 그림에는 측정값이나 품질 승자를 만들어 넣지 않는다.
