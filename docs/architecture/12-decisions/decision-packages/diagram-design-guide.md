# 설계 대안 그림 작성 기준

> 적용: Stage 4~6의 구조 비교와 실행 상세. 2026-10-01 사용자 후속 리뷰 반영.
> [04 전체 지도](./04-00-structural-alternatives.md) / [그림 모음](./diagrams/stage4-review.html)

그림만 본 심사자가 **무엇이 어디에서 처리되고, 어떤 경로와 상태가 달라지는지** 설명할 수 있어야 한다. 이름과 색만 바꾼 상자는 구조 비교가 아니다. 기능을 제거했으면 대체 처리 위치 또는 실제 기능 포기를 함께 표시한다. 도메인 지식이 필요한 계약명은 짧은 일상 표현을 먼저 쓰고 본문 용어와 연결한다.

## 1. 구성요소와 포함 관계

아래는 이 저장소 비교 그림의 표기 규칙이다. 모든 아키텍처 방법론에서 Component와 Module의 정의가 동일하다는 주장이 아니다. 기존 target의 Component 책임을 기준으로, 대안에서도 같은 추상화 수준으로 비교한다.

| 요소 | 이 그림에서의 의미 | 표기와 포함 관계 |
| --- | --- | --- |
| Component | 외부에 드러나는 책임과 계약을 가진 아키텍처 구성요소. 상태가 있으면 의미상 소유자를 밝힘 | 이름이 있는 제목 칸과 본문 칸을 가진 상자. 내부 Module과 소유 자료를 펼칠 수 있음 |
| Module | Component의 책임을 내부에서 나눠 수행하는 기능 단위 | 둥근 상자. 반드시 소유 Component 안에 배치. 독립된 대안 책임을 표현할 때 편의상 Module이라고 붙이지 않음 |
| Subsystem | 여러 Component와 저장 요소가 함께 제공하는 기능 영역 | 이름이 있는 점선 경계. 내부 구성요소를 실제로 펼치고 별도 서버나 process로 오해하지 않도록 설명 |
| 자료 | 입력 묶음, 실행 중 상태, 읽은 자료 목록처럼 처리에 사용하는 정보 | 모서리가 접힌 종이. 처리 Module이나 능동 실행체처럼 그리지 않음 |
| 저장소 | 이력, 대기열, 색인, 내구 기록을 보관하는 구조 | 원통. RAM인지 내구 저장인지 명시. State Store 안의 원통은 보관 형태이며 의미 권한을 State Store로 옮기지 않음 |
| 연동 대상 또는 모델 | 이 비교 영역에서 내부를 펼치지 않는 화면/OS, 자료 소유자, 외부 업무 Agent, 모델 등. 자료 소유자는 VIA 내부일 수도 있으며 그 경우 명시 | 육각형. 별도 Input source, Model dependency 등의 종류 이름을 상자마다 늘리지 않음 |
| Process | 실제 실행 및 장애 경계 | process임을 명시한 점선 경계. 논리적 Component와 별도 관점. S-06에서 Model Access의 연동 책임과 실제 worker를 함께 설명 |

대안의 Semantic Resolution Worker와 Capability Read Broker는 독립된 책임과 인터페이스를 제안하므로 Component로 표시한다. Worker 내부의 대기/재개 제어와 Broker 내부의 읽기 검사는 Module이다. Component라고 해서 별도 process라는 뜻은 아니다.

Target 내부에 표시한 Module 이름은 승인된 책임을 읽기 쉽게 분해한 설명 이름이다. 새로운 target Component나 구현 클래스의 확정이 아니다. 실제 Component 이름은 target의 정식 이름을 그대로 쓴다. 상세도에서 Module의 영어 이름까지 새로 만들 필요는 없다.

## 2. 색은 비교안에서의 존재와 역할을 나타낸다

- **검정:** 비교안에 공통으로 남는 구성과 처리. 대안에서 더 많이 호출된다는 이유로 Component 전체를 다른 색으로 칠하지 않는다.
- **파랑:** T에서만 유지하는 구조 또는 T 고유의 처리 경로.
- **초록:** A/B에서 추가하거나 교체하는 구조 또는 대안 고유의 처리 경로.
- 비용과 지원 한계 설명은 별도 주석 색을 사용할 수 있지만 추천이나 품질 점수를 뜻하지 않는다.

Component의 일부만 바뀌면 바깥 Component는 검정으로 남기고 달라진 내부 Module과 연결만 파랑 또는 초록으로 표시한다. S-05의 Request Interpreter는 양안 공통이며 검정이다. A에서 모든 요청이 이 경로를 따르는 변화는 초록 화살표로 나타낸다.

T/A/B 세 안을 함께 그릴 때 일부 두 안에 공통인 구성도 검정으로 표시한다. 예를 들어 S-02의 원시 화면 이력은 T와 A에 남지만 B에는 없다. 색만 보고 전체 적용 범위를 추측하게 하지 않고 각 안의 실제 구성과 손실을 함께 표시한다.

이전 네 참고 비교안은 당시 범례를 유지한다. 새 색 규칙은 현재 S-01~06과 이후 작성할 비교 그림에 적용하며 이전 그림의 색을 새 의미로 읽지 않는다.

## 3. 그림마다 보여줄 메커니즘

| 그림 | 반드시 눈으로 확인할 차이 |
| --- | --- |
| S-01 | T의 Request Controller 내부에 있는 추가 조회 조정과 새 호출. A의 별도 Worker/Broker, 작업 중간 상태와 Model Access의 중단 및 재개 계약. 중간 제안과 최종 제안의 반환 목적지를 분리 |
| S-02 | T/A의 화면 수집, RAM 이력, 발화 구간 보존 경로. A의 별도 객체 생산과 저장. B의 선택 시점 1회 캡처와 자료 묶음, 제거되는 이력 및 시간 결합 단계 |
| S-03 | 공통 Context Manager의 기존 조회와 원문 확인. A의 의미 검색 Subsystem 내부 검색, 색인 생산과 모델 연동 Component, 색인 저장 및 갱신 경로 |
| S-04 | T의 Request Controller 내부 요청 관계와 전이. A의 Workflow Runtime 내부 수신, 다음 활동과 대기 상태 및 내구 기록. B의 세션 상태와 없는 복원 경로. 남아 있는 업무 원장은 공통 |
| S-05 | T의 직접 음성 생성, 보류 자료와 직접 허용 및 해제. A에서 모든 요청이 일반 해석과 Text 기반 음성 생성으로 가는 순서. 일반 음성 응답은 유지하고 직접 S2S 기능은 포기 |
| S-06 | T의 독립 ASR 대기열, adapter, 모델. A의 공유 Omni와 Native Evidence Adapter로 옮긴 인식 경로. 인식을 수행하는 모델과 결과를 변환하는 VIA 모듈 구별 |

새 상자를 채우기 위해 target에 없는 메커니즘을 만들지 않는다. 실제 메커니즘 차이가 약하면 그림으로 과장하지 않고 본문에 탐색의 한계로 남긴다. 부분 기능 대안은 포기하는 사용자 결과를 눈에 띄게 표시한다.

## 4. 배치와 읽는 순서

1. 설계 질문, 같은 사용자 상황, 방안 이름을 먼저 배치한다. 그 아래 VIA 책임 경계, 담당 Component, 내부 처리와 상태, 외부 의존성을 읽게 한다.
2. 같은 Component는 양안에서 가능한 한 같은 위치와 크기로 놓는다. 내부 Module과 상태의 수명이 달라 크기가 달라지는 부분은 그 차이를 직접 펼친다. 삭제되는 구조의 자리를 억지로 다른 이름의 상자로 채우지 않는다.
3. Component 이름은 전체 이름을 사용하고 제목 칸에 정렬한다. 내부 Module의 이름은 둥근 상자 안에 중앙 정렬한다. 동작의 순서와 송수신 내용은 화살표 옆에 적는다.
4. 제목 칸, Component 책임 설명, 내부 Module, 연결 설명의 크기를 구분한다. 긴 글을 작은 글씨로 채우지 말고 의미 단위로 나누거나 별도 상세도로 분리한다.
5. `receipt`, `epoch`, `continuation`, `admission`처럼 모르는 용어에 의존하지 않는다. 그림에서는 각각 읽은 자료와 버전, 유효한 입력/출력 버전, 대기 중 실행 위치, 현재 조건 확인과 허용처럼 문맥에 맞는 쉬운 말을 쓴다. 정확한 기술 의미는 본문의 계약과 대응시킨다.
6. 구조 비교도와 실행 상세도를 구분한다. S-01 상세도의 세로 막대는 호출 또는 작업의 수명이며 측정 시간이나 연산 점유량이 아니다.

## 5. 흐름과 경계

1. 요청과 반환은 각각 방향을 가진 선으로 표시한다. 실선은 요청 또는 전달, 점선 화살표는 결과 또는 복원이다. 번호는 본문의 단계와 맞춘다. 비동기 사건 생산과 요청 처리의 번호를 하나의 강제 직렬 실행으로 해석하게 하지 않는다.
2. 내부 Module의 호출은 소유 Component의 경계를 통과할 수 있다. 무관한 상자를 관통하지 않으며 선의 교차를 합류처럼 표시하지 않는다. 선이 글자를 가리지 않도록 경로와 주석을 옮긴다.
3. 중간 결과, 최종 의미 확정, 외부 실행 승인, 사용자 전달은 다른 사건이다. 중간 제안을 최종 확정 Module로 바로 연결하지 않는다.
4. 공통 시작, 차이의 시작, 최종 합류와 실패 시의 결과를 그림에서 찾을 수 있어야 한다. 재개와 복구를 비교한다면 원본 상태, 저장, 다시 읽는 경로와 외부 확인을 설명한다.
5. 모델 내부와 학습은 VIA 책임 밖이다. 모델을 VIA 밖에 그린다고 원격 서버 배치를 뜻하지 않는다. 모델 연동 코드는 VIA에 두고 공유 모델의 가중치를 여러 벌 그리지 않는다.
6. 내부 owner와 외부 자료를 함께 펼친 참조는 그 사실을 표시한다. 자료의 위치를 아래로 옮겼다는 이유로 내부 소유권을 외부로 옮기지 않는다.

## 6. 원본과 검수

SVG와 편집 가능한 draw.io를 함께 관리한다. 생성 원본은 `scripts/architecture/generate_stage4_structure_diagrams.py`, 공통 표기는 `scripts/architecture/stage4_diagram_design.py`다. 생성된 SVG만 수정하지 않는다.

생성기 검사는 모든 Module의 Component 소유자와 실제 포함 좌표, XML, ID, 연결 참조, canvas 범위, 직교 경로와 무관한 노드 관통을 확인한다. SVG와 draw.io는 같은 좌표 및 책임 모델을 사용하며 서로 다른 Python 버전에서도 같은 문자열을 생성해야 한다.

실제 브라우저 렌더링에서 이름 넘침, 글자 겹침, 잘림을 검사하고 그림을 열어 흐름을 대조한다. 자동 검사는 선과 글의 의미나 대안의 타당성을 보장하지 않는다. 실제 target과 대안 본문의 소유권, 기능 손실 및 지원 미확인을 별도로 확인한다. Stage 4에는 측정값이나 품질 승자를 만들어 넣지 않는다.
