## 1. 결론

**독립 DP로 진행할 문제 3개, 조건부 DP 후보 1개, 상세 설계로 유지할 문제 1개를 권고한다.** 개수를 먼저 정하지 않았다. 같은 일을 수행하는 기본 구조 사이에 실제로 감수할 이익과 비용이 있는지를 판단했다. 중요한 기능이어도 현재 A/B의 반대편 이익을 설명하지 못하면 완성된 DP라고 세지 않는다.

## 2. 세 문제를 독립 DP로 권고하는 이유

### 2.1 문제 1: 앞에서 이해한 문맥을 유지할지, 필요할 때 다시 구성할지

사용자가 “두 번째 건 왜 그랬지?”라고 이어 말할 때 문맥을 유지한 A는 이미 읽은 근거를 이용할 수 있다. B는 필요한 원본을 요청마다 선택하므로 주제가 바뀌거나 사용 범위가 작을 때 입력과 사전 생산을 줄일 수 있다. C는 여러 대화에서 같은 과거 관계를 재사용할 때 회상 지연을 줄일 수 있지만, 사용하지 않는 기억도 생산하고 정정에 맞춰 갱신한다.

이것은 정상 사용에서 **QA01/03의 준비 및 조회 지연과 QA05의 반복 입력 / 선생산 비용**이 충돌하는 실제 선택이다. QA02는 원본 검색 누락, 압축 누락과 오래된 기억이 채택 대상에 미치는 경로로 비교한다. 필요한 원본 보완 후 같아질 수 있으므로 정확도 승자를 미리 정하지 않는다.

**A 추천의 전제는 VIA가 계속 이어지는 사용자 대화의 주 인터페이스라는 점이다.** 최근 연속 대화보다 독립적인 단발 요청이 지배하면 B가 더 적합할 수 있다. 장기 회상의 반복 이익이 생산과 갱신 비용을 회수하면 C로 권고가 바뀔 수 있다. 실제 이용 비중이 확인됐다는 주장은 아니다.

근거는 OpenHands의 유지되는 view와 condensation, Deep Agents의 offload와 범위별 읽기, OpenClaw / CrewAI의 기억 저장 및 회상이다. 제품 전체를 복제하지 않고 이 메커니즘을 비교했다. [상세 권고](01-evidence-supply.md) / [고정 소스](../../../../../references/five-problem-study/evidence-and-handoff.md)

### 2.2 문제 2: 지금 진행 중인 VIA 판단이 다음 발화를 막지 않게 할 것인가

대표 상황은 **VIA가 보고서 근거를 읽거나 의미 판단을 하는 동안, 사용자가 이전 요청을 바꾸고 다른 질문도 하는 경우**다. 다른 외부 Agent가 보낸 질문에 사용자가 짧게 답하는 경우도 포함한다. 외부 Agent가 오래 일하고 있다는 사실만으로 VIA 모델이 점유돼 있다고 가정하지 않는다.

A는 같은 판단 실행의 다음 처리 경계에서 입력을 다룬다. 문맥을 유지하기 쉽지만 새 독립 요청이 그 경계까지 기다릴 수 있다. B는 공통 대화 조정에서 입력 관계를 판단하고 필요한 요청별 실행을 둔다. 기존 실행을 보존하면서 다른 요청을 진행할 수 있으나 문맥 준비, 조정과 모델 비용이 추가된다.

**B를 추천하되 무조건 빠르다고 판단하지 않는다.** A에서 남은 대기 `W`보다 B의 추가 관계 판단 / 문맥 준비 / 자원 대기 `H`가 클 때는 B의 반응성 이익이 없다. 단순 질문은 공통 해석에서 바로 답할 수 있고, 구조화된 Agent 통지는 필요한 상태 반영만 한다. 모든 입력에 worker나 모델 호출을 강제하지 않는다.

주 비교는 QA01/03과 QA05이며 요청별 상태 증가를 QA06에 함께 남긴다. 요청 연결의 정확성은 신규 N-R로 진단한다. 새로운 요청을 엉뚱한 Task에 붙인 오류를 QA02의 지칭 오류로 바꾸지 않는다.

OpenClaw의 처리 경계와 큐, Deep Agents의 별도 task 수명과 제한된 별도 질문 경로, OpenHands의 독립 conversation 및 수신 / step 경계를 참고했다. [상세 권고](02-continuous-interaction.md) / [추가 확인](../../../../../references/five-problem-study/interaction-recommendation-check-20261017.md)

### 2.3 문제 4: Agent 독립성을 위해 모든 이력을 계속 의미 기억으로 만들어야 하는가

**Agent 독립성에는 VIA가 관측한 요청, 수정, 실제 전달, 확인된 수행과 결과의 보존이 필요하다. 모든 이력을 미리 의미 기억으로 가공해야 하는 것은 아니다.** A/B/C는 이 공통 기록을 다음 위임에 쓸 수 있게 만드는 시점과 자료 선택 책임을 달리한다.

A는 실제 위임 때 인계 묶음을 만든다. B는 여러 후속 위임이 재사용할 공통 업무 기록을 계속 갱신한다. C는 필수 조건과 자료 목록을 주고 수신 Agent가 원본 세부를 고른다. 따라서 **위임 시 준비 시간, 미리 만든 기록의 재사용 및 미사용 생산 비용, 수신자의 읽기 능력과 인계 누락 위험**이 달라진다.

현재는 **A를 기본으로 추천한다.** 이종 Agent의 읽기 / session 기능을 공통으로 가정하지 않고도 필수 조건과 허용 자료를 전달할 수 있다. 같은 자료로 여러 위임이 이어지면 B가 선행 조합 비용을 회수할 수 있다. C는 실제로 필요한 세부가 크고 수신 Agent의 범위별 읽기가 확인된 경우 유력하다. native session 재사용은 어느 안에도 별도 tactic으로 적용한다.

주 비교는 QA03/05와 **N-H 업무 인계 정확도**다. N-H는 새로운 평가 후보이며 아직 core QA로 승인되지 않았다. A의 즉석 구성 누락, B의 오래되거나 압축된 기록, C의 필수 manifest / 자료 접근 실패를 같은 확정 인계 계약에서 판정한다. N-H 우열이나 과정의 세 축 차이가 이미 확인된 것은 아니다. 첫 처리 의도를 먼저 표시할 수 있으므로 QA01 이익을 억지로 만들지 않는다.

Deep Agents의 명시적 task 입력과 공유 backend, CrewAI의 위임 context와 memory, OpenClaw의 session / 외부 연동 경로에서 가져온 구조다. 실제 pull 및 resume 지원 범위를 별도 확인했다. [상세 권고](04-agent-independent-handoff.md) / [추가 기능 확인](../../../../../references/five-problem-study/handoff-capability-check-20261017.md)

## 3. 두 문제는 왜 같은 수준의 DP로 세지 않는가

### 3.1 문제 3: 중요한 기능이며 A를 추천하지만, B의 반대편 이익은 더 입증해야 함

A와 B는 실제로 다른 구조다. A는 말과 화면 원본에서 대상 연결을 직접 만들고, B는 음성 후보와 화면 후보를 각각 생산한 뒤 결합한다. QuickSet의 부분 의미 결합과 OmniParser의 화면 후보 인터페이스는 B의 구현 가능성을 뒷받침한다. Magentic-One WebSurfer와 OpenHands의 screenshot / text 입력은 A의 근거다.

그러나 **B의 결합 입력이 작다는 사실만으로 전체 모델 비용이 낮아지지 않는다.** 후보 생산의 원본 입력과 출력, 결합 입력과 출력, 누락 후보 확장 비용도 든다. A는 여러 지칭을 하나의 공동 입력에서 해석할 수 있으므로 지칭 개수만큼 원본을 매번 입력한다고 계산하면 안 된다.

또한 B의 후보와 원본을 함께 유지하는 것이 정확도 우위를 보장하지 않고, producer 분리가 실제 Rust 변경 수를 줄인다는 증거도 없다. B1/B2의 revision 간 재사용과 부분 갱신은 기본 B의 성과에 포함하지 않는다. B의 초기 producer 순차 정책을 필연적 구조 한계라고 설명하지도 않는다.

**결론은 기본 A 추천, 현재 A/B의 주요 DP 확정 권고 보류다.** B의 후보가 충분한 장면에서 전체 처리량, 최종 정확도나 local RAM 등 적용 QA의 이익이 생산 및 확장 비용과 맞서는지 확인해야 한다. B4의 병행 민감도 확인과 다른 적용 QA까지 검토해 반대편 이익이 남지 않으면 화면 지칭 기능과 A 설계는 유지하면서 이 A/B를 독립 주요 DP로 제출하지 않는다. 기존 DP-47을 삭제하거나 그 선택을 확정한 것은 아니다. [상세 권고](03-screen-speech-grounding.md)

### 3.2 문제 5: 실제 Agent와 선택 목적을 갖추기 전에는 별도 selector를 정당화하기 어려움

Deep Agents와 CrewAI는 현재 판단에서 후보를 선택하는 A의 근거이고, AutoGen SelectorGroupChat과 Magentic-One은 별도 선택 실행 B의 근거다. 사용 가능한 대안은 있다.

다만 선택 기준이 단순한 기능 / 권한 / 사용자 지정이면 공통 적격성 검사로 결정되는 경우가 많다. ‘그때 최고 성능’은 후보 card만으로 판정할 수 없다. 실제 연결 후보, 업무별 검증 자료와 사용자의 품질 / 시간 / 비용 목적이 있어야 한다. 별도 selector를 추가했다는 이유로 선택 정확도가 높아지지도 않는다.

**현재는 상세 설계로 A를 추천한다.** 요청은 유지되고 후보만 바뀌는 재선택이 정상 사용에서 반복되거나, 독립 선택 문맥의 이익이 N-S/QA03/QA05에서 확인되면 주요 DP를 다시 검토한다. ‘후보 수가 늘었다’만으로 승격하지 않는다. [상세 권고](05-agent-selection-and-transition.md) / [등록 및 독립 정답 근거](../../../../../references/five-problem-study/selection-recommendation-check-20261017.md)

| 갱신을 요구하는 사건 | 새 발화, 지칭, 실제 전달 및 과거 근거 사용 | 실제 위임, 수신자 변경, 위임 조건 변경. B는 공개 결과, 실제 전달과 사용자 정정에 따라 미래 인계용 기록도 선행 갱신 |
| 독립 조합의 예 | 대화 작업 문맥 A를 유지 | 위임은 B의 지속 업무 기록에서 구성 가능 |
| 다른 조합의 예 | B로 요청마다 원본 조회 | 위임은 A로 그때 묶음을 구성 가능 |

독립성은 trigger가 항상 다르다는 뜻이 아니다. 같은 사용자 정정이 두 계약을 모두 바꿀 수 있어도 소비자, 출력과 상태 생산 방식을 각각 교체할 수 있다는 뜻이다. 같은 물리 저장소를 사용해도 위 두 계약이 자동으로 같아지지는 않는다. 반대로 같은 파생 기억이 양쪽 역할을 수행한다면 생산 비용을 두 번 더해서도, 각 DP의 독립 절감으로 두 번 주장해서도 안 된다.

PoC에서는 한 문제의 대안을 바꿀 때 다른 문제의 구조를 고정한다. 통합 조합에서는 공유 호출과 저장을 고유 ID로 한 번 집계한다. 문제 1 C와 문제 4 B가 결국 동일한 상태, 갱신 trigger와 소비 계약을 갖게 되면 그 결합 설계는 하나의 DP로 통합해야 한다. 현재 추천 1A + 4A는 해석 문맥과 위임 시 산출물이 분명히 다르다.

## 5. 기본안 추천 뒤 적용할 보완

아래는 **적용한 결과가 아닌 추천 순서**다. 기본 비교표에 효과를 미리 반영하지 않는다. 각 tactic은 부모 안에 하나씩 적용하여 비용을 확인하고, 둘을 함께 쓰면 `A1+A2`처럼 따로 기록한다.

| 문제 / 추천 기본안 | 우선 보완 | 겨냥한 단점 | 새로 감수할 비용 |
| --- | --- | --- | --- |
| 1 / A | **A1 입력 prefix cache**, 이어서 정정이 잦으면 **A2 변경 조각만 갱신** | 문맥 반복 입력의 QA05, 재구성의 QA03 | provider cache 조건과 무효화, source별 의존 관리. cache 지원 여부 확인 필요 |
| 2 / B | **B1 불변 local 문맥 참조**, 대화 대기가 남으면 **B2 전경 호출 용량 예약** | 문맥 사본의 QA06, 새 발화의 QA01/03 | 참조 수명 / 철회 관리. 같은 총 호출 한도에서 배경 실행 처리량 감소. B1은 cloud 토큰 절감이 아님 |
| 3 / A | **A1 crop/cache**, 이어서 **A2 영향받은 binding만 갱신** | 공동 원본 입력과 정정의 QA03/05 | crop 누락, cache 수명과 binding 의존 추적. 원본 추가 조회는 유지 |
| 4 / A | **A1 유효 인계 묶음 cache**, 지원이 확인된 동일 Agent에서 **A2 native session 재사용** | 반복 인계 구성의 QA03/05 | 조건 / 권한 변경 무효화, session capability 확인과 실패 후 재구성. session ID만으로 보존 성공을 간주하지 않음 |
| 5 / A | **당장은 기본 A**. 후보 설명이 병목이면 A1 후보 검색 | 후보 입력 증가의 QA03/05 | index 갱신과 후보 누락 위험. 후보 확대와 공통 실행 적격성 검사 유지 |

crop/cache, 부분 갱신과 용량 예약을 한꺼번에 넣은 조합을 기본 A/B라고 부르지 않는다. 필수 현재성, 권한, 늦은 결과 차단과 원본 보완은 모든 기본안에서 이미 지킨다.

## 6. QA와 과정 요구에 대한 판정

표는 **구조에서 설명되는 차이 가설**이며 실측 coverage가 아니다. `직접`은 차이가 생기는 처리 경로가 있다는 뜻이다. `미확인`은 방향 또는 실용적인 크기를 아직 정할 수 없다는 뜻이다.

| QA | 1 근거 공급 | 2 후속 발화 처리 | 3 화면 지칭 | 4 업무 인계 | 5 Agent 선택 |
| --- | --- | --- | --- | --- | --- |
| QA01 첫 응답 | 직접: 유지 문맥 / 조회 / 사전 생산 | 직접: 기존 판단 대기 / 별도 실행 | 직접: 공동 판단 / 생산 후 결합 | 주 비교 제외: 인계 전에 의도 표시 가능 | 주 비교 제외: 선택 전에 의도 표시 가능 |
| QA02 지칭 집합 | 직접, 우열 미확인 | 기본 비교에서는 회귀 | 직접, 우열 미확인 | 공통 지칭 결과를 사용하면 회귀 | 공통 지칭 결과를 사용하면 회귀 |
| QA03 VIA 처리시간 | 직접 | 직접 | 직접 | 직접, 기존 endpoint 안의 인계 준비만 | 직접, 기존 endpoint 안의 선택만 |
| QA04 실제 변경 모듈 | 전파 경로만 검토, 숫자 및 우열 미확인 | 동일 | 동일 | 동일 | 동일 |
| QA05 전체 VIA 모델 비용 | 직접: 반복 입력 / 생산 / 조회 | 직접: 문맥 / 독립 판단 / 폐기 | 직접: 원본 / 생산 / 결합 / 확장 | 직접: 위임 시 생산 / 지속 갱신 | 직접: 결합 / 별도 선택 / 재선택 |
| QA06 최대 local RAM | 공통 512 MB, 구조별 기여 확인 | 공통 512 MB, 실행 상태 확인 | 공통 512 MB, 원본과 후보 확인 | 공통 512 MB, 생산 / serving 확인 | 공통 512 MB, 별도 선택 상태 확인 |

| N-R 요청 관계 정확도 | 이번 단독 비교의 주축 아님 | 기능 진단 | 정정 관계 진단 | 공통 관계 결과 사용 | 공통 관계 결과 사용 |

**기존 QA01~05의 우선 관심을 유지한다.** QA06의 512 MB는 반드시 충족해야 할 장치 조건으로 계속 확인한다. 새로 검토할 QA의 우선순위는 이 조사에서는 N-H가 높다. 이는 Agent 교체에도 이어지는 업무라는 가치와 직접 연결된다. N-S는 실제 후보 및 정답 근거를 확보할 때, N-R은 요청 연결의 실패 진단으로 사용한다. 이번에 새로운 QA 번호, 목표나 점수를 확정하지 않는다.

과정의 ‘DP마다 3~4개 QA, 핵심 QA마다 두 DP 이상의 차이’ 요구를 충족했다고 결론내릴 수는 없다.

- 문제 1과 2는 QA01/03/05의 손익을 설명할 수 있으나 두 시간 지표의 겹침을 독립 이익처럼 합산하지 않는다.
- 문제 4는 QA03/05와 N-H가 적절하다. QA03은 실제 Agent 결과 표시까지 필요한 S15-G03 등의 목표에서 인계 준비가 ingress에 선행하는 경로를 사용한다. 연결 근거는 [09 §3.4](09-poc-decision-plan.md#34-업무-인계-즉석-구성과-지속-기록의-손익)에 있다. **이 적용 경로에서 시간 차이가 확인돼야 하며, N-H를 채택하지 않거나 정확도 차이가 없다면 세 개의 차별화 축도 확보되지 않는다.** 이것은 남은 명확한 과정 적합성 조건이다.
- 문제 3의 B 이익, QA02의 두 문제 간 실제 차이, QA04의 변경 모듈 차이는 미확인이다. 이 칸을 채우기 위해 후보나 점수 경계를 바꾸지 않는다.
- 확인된 실측 차이는 현재 0개다. 현재 결과는 **무엇을 설계하고 무엇을 비교할지에 대한 권고**이며 점수로 선정한 최종 Architecture가 아니다.
