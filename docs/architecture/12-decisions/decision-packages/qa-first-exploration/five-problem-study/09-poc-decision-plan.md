# 권고안을 확인할 최소 PoC와 결론 변경 조건

2026-10-17 / 실행 설계만 작성 / 구현, 모델 실행과 측정 freeze 전

[설계 권고와 DP 판정](08-decision-recommendations.md)의 가설을 확인하는 범위다. 현재 계획을 작성한 것으로 실행이나 API 비용 발생을 승인받았다고 해석하지 않는다. 새 제품 전체, 외부 Agent의 내부 계획과 장기 성능 benchmark는 이 PoC의 구현 대상이 아니다.

## 1. 무엇을 확인하고 어떤 결과를 낼 것인가

| 확인 순서 | 질문 | 남길 결과 |
| --- | --- | --- |
| 1. 기본 비교 | 같은 기능에서 기본 A/B/C의 이익과 비용이 실제로 다른가 | 구조별 시간 / 모델 원장, 오류와 실패, 기본안 추천 유지 또는 변경 |
| 2. tactic 단독 | 추천 부모안의 약한 QA를 해당 tactic 하나가 개선하는가 | A 대 A1, A 대 A2 등 전후 차이와 추가 비용. 효과가 없으면 제외 |
| 3. 필요한 조합 | 유효한 보완 두 개가 함께 작동하는가 | A1+A2 같은 명시적 조합. 단독 절감량을 단순 합산하지 않음 |
| 4. 통합 확인 | 추천한 문제별 구조를 연결했을 때 효과와 공통 비용이 유지되는가 | 중복 없는 전체 활동 원장과 COMMON-28 회귀. 부분 PoC를 전체 점수로 바꾸지 않음 |

최종 표의 상태는 `추천 유지`, `추천 변경`, `차이 불확실`, `요구 미충족`으로 구별한다. 기능 실패를 이유로 raw 시간과 비용을 지우지 않는다. 빠른 오답을 성공한 빠른 응답으로 선정하지 않으면서도, QA01/03의 원시간에 임의 벌점이나 timeout을 대신 넣지 않는다.

## 2. 공통으로 고정할 것

1. 같은 원음, 화면 / pointer / selection, 원본 자료, 실제 전달 이력, 수정 조건과 외부 통지를 제공한다. 특정 안에 정답 Task나 target을 미리 주지 않는다.
2. 같은 cloud 모델 capability와 version, capture 범위, 읽기 한도와 전체 동시 호출 한도를 사용한다. 별도 local 의미 모델은 넣지 않는다. 각 안의 추가 호출과 출력은 비용으로 남긴다.
3. 기본안과 tactic의 경계를 [07](07-basic-designs-and-tactics.md)에 고정한다. 기본 구조에 고유한 문맥과 상태 재사용은 유지한다. 필수 원본 보완, 권한 검사와 현재 revision 확인도 유지한다.
4. 한 문제만 바꾸고 다른 네 문제의 처리는 동일하게 둔다. 문제 1과 4가 공유하는 생산 호출과 자료에는 고유 ID를 부여하여 통합 비용에서 한 번 센다.
5. 실제 관측 event와 software가 인지한 event를 나눈다. [공통 사건 원칙](../../../../11-measurement/event-boundary-contract.md)의 이 원칙을 쓰되, 그 문서의 이전 QA ID와 음성 endpoint를 현재 후보 QA01의 텍스트 표시 endpoint로 가져오지 않는다.
6. QA01~06의 정의와 점수, COMMON-28을 바꾸지 않는다. [현재 QA 명세](../../qa-candidate-package/README.md)와 [관련 모집단 규칙](../../qa-candidate-package/thought-experiment/population.md)을 먼저 적용한다. 아래 EX 부분집합은 원인 확인용이며 새로운 공식 모집단이나 점수표가 아니다.
7. 구조 확인을 위한 결정적 대역은 의미 정답을 oracle로 대신 생산하지 않는다. 정해진 반환을 주어 큐, 채택과 철회 경로를 확인할 수 있지만 그것을 모델 정확도나 실제 지연 측정으로 부르지 않는다.

## 3. 문제별 최소 범위와 반증

### 3.1 근거 공급: A의 연속 대화 이익과 유지 비용

**비교:** 기본 A/B/C. 다른 문제의 실행 / 인계는 고정한다. EX01 최근 대화, EX03 실제 음성 / 화면 전달 범위, EX04 과거 복수 결과와 반복, EX10 누락 / 모호함, EX16 철회, EX17 판본 변경을 쓴다.

- 연속된 같은 주제, 주제가 바뀌는 단발 요청, 여러 대화를 가로지르는 과거 회상을 별도 장면으로 비교한다. 비중을 실제 이용 통계라고 만들지 않는다.
- A의 유지 및 condensation, B의 원본 읽기, C의 생산 / 갱신 / 회상을 모두 trace에 남긴다. C에서 만들고 사용하지 않은 기억도 모델 원장에 포함한다.
- 최초 지칭 채택의 QA02와 이후 수정 결과를 별도로 남긴다. 채택 전 fallback으로 성공하면 성공이며, 잘못 채택한 뒤 고친 기록으로 처음 오류를 지우지 않는다.

**손익 확인식:** 구조별 총비용은 `사전 생산 + 모든 요청의 조회 / 입력 / 판단 + 갱신 / 폐기`다. A의 절약은 피한 조회와 재구성에서, 부담은 유지 / 반복 입력에서 나온다. C의 사전 생산 비용은 실제 재사용에서 절약한 비용과 비교한다. 가상의 높은 재사용률로 상각하지 않는다.

**추천 변경:** 연속 대화에서도 A의 절감이 작고 B의 반복 비용이 낮거나, C의 장기 회상 이익이 전체 생산 비용을 회수하면 기본안 추천을 재검토한다. A와 B가 같아지면 그 결과를 보존한다.

**보완 순서:** A 대 A1 prefix cache, 이어 A 대 A2 부분 갱신. 지원 provider가 cache hit를 확인하지 못하면 A1은 미지원으로 표시한다. token 입력 감소와 실제 과금 감소를 구별한다.

### 3.2 후속 입력 처리: 새 발화 대기가 줄어드는가

**비교:** 기본 A/B. 한 대화, 최대 세 개의 겹친 요청과 외부 Task 두 개의 통지 대역으로 제한한다. 양안 모두 총 동시 모델 호출 한도 1과 2의 조건을 각각 사용한다. 고정된 근거 D1/D2의 읽기와 판단을 사용하며 모델 한도와 source 지연을 한 안에만 늘리지 않는다.

| 대조 장면 | 확인할 것 |
| --- | --- |
| VIA 자체 처리도 외부 업무도 없는 짧은 요청 | B의 공통 조정이 불필요한 worker / 호출을 강제하는지 |
| 외부 Agent만 오래 실행 중인 상태 | VIA 의미 모델이 비어 있으면 A/B 모두 새 질문을 처리하는지. 외부 실행 길이만으로 B 이익을 만들지 않음 |
| VIA가 자료를 읽는 중 별도 짧은 질문 | A의 처리 경계 대기와 B의 공통 해석 / 새 실행 비용 |
| VIA 모델 호출 중 별도 질문 | 남은 모델 대기와 추가 호출 capacity의 효과 |
| 이전 요청을 바꾸는 후속 발화 | 양안 모두 이전 revision의 채택을 막고 필요한 수정만 현재 요청으로 연결하는지 |
| Agent 질문 후 사용자 짧은 답, 다른 Agent의 늦은 결과 | 실제 제시한 질문에 답을 붙이고 늦은 결과를 올바른 요청에 보존하는지 |
| 모든 허용 호출이 사용 중인 상태 | B도 대기하는지, 숨은 초과 호출이나 무제한 worker가 없는지 |

**손익 확인식:** 새 입력의 공통 처리를 뺀 A의 잔여 대기를 `W`, B가 더 쓰는 관계 판단 / 문맥 준비 / 자원 대기를 `H`라 두면 B의 개선 후보는 `W − H`다. 공통 경로와 상세 응답 생성이 다르면 해당 차이도 trace에서 포함한다. 이 식은 실측값이나 모든 입력의 보장치가 아니다.

**추천 변경:** 쉬운 입력과 호출 포화를 포함해 B의 추가 비용이 대기 절감을 상쇄하고, 독립 실행이 필요한 장면에서도 이익이 없으면 A 추천으로 바꾼다. A1의 제한된 별도 질문 처리만으로 주로 쓰는 독립 질문을 처리할 수 있는지는 기본 비교 뒤 별도 확인한다. A1을 몰래 기본 A에 넣지 않는다.

**보완 순서:** B 대 B2 전경 용량 예약과 B 대 B1 local 문맥 참조를 각각 확인한다. B2는 같은 총 호출 한도 안에서 배경 실행을 늦추는 비용을 포함한다. B1은 사본 RAM을 줄이는 기법이며 cloud KV나 API 과금을 줄였다고 계산하지 않는다.

### 3.3 화면 지칭: B의 반대편 이익이 실제로 있는가

**비교:** 기본 A/B. EX02 명시 selection, EX08 화면 이동 지칭, EX09 부분 정정, EX10 불완전 관측을 사용한다. 각각 단일 대상, 복수 대상, 언어에 따라 visual 범위가 달라지는 장면을 포함한다. 같은 발화 구간의 원본과 관측 gap을 준다.

- 기본 A는 현재 요청에 필요한 원본을 한 공동 입력으로 사용할 수 있다. 지칭마다 같은 원본 입력을 강제하지 않는다.
- 기본 B는 후보 생산과 결합, 원 producer의 확장을 모두 실행한다. 두 안에 같은 원본을 주되 언어가 요구하는 visual 범위와 집합 난이도를 다양하게 구성하고 실제 생산 결과의 누락과 분할 오류를 관찰한다. B에 불리한 후보를 미리 주입하거나 B가 실패한 출력만 골라 입력 집합을 만들지 않는다. 강제 오류 주입은 별도 대역 기반 복구 진단으로 구별한다.
- 두 기본안은 발화 종료 후 주요 의미 판단을 시작한다. 발화 중 수집을 의미 선생산으로 계산하지 않는다. native 정보가 충분하면 양안 모두 불필요한 image 호출을 생략할 수 있다.

**손익 확인식:** `비용 A = 공동 입력 / 출력 + 필요한 재판단`, `비용 B = 음성 후보 생산 + 화면 후보 생산 + 결합 + 필요한 후보 확장 / 재결합`이다. B의 작은 결합 입력만 비교하지 않는다. 한 번의 A 입력과 B의 전체 합을 비교한다.

**조건부 DP 판정:** 기본 B가 전체 비용, 최종 지칭 정확도나 local RAM 등 적용 QA에서 이익을 보이고 그 이익이 A의 다른 QA 이익과 대립하면 주요 DP로 승격할 근거가 된다. 아래 B4 민감도 확인까지 수행하여 순차 정책만의 지연을 구별한 뒤, B가 같은 정확도에 더 비싸고 더 느리며 QA06 및 실제 확인한 다른 적용 축에도 이를 상쇄할 이익이 없다면 이 A/B를 주요 DP로 제출하지 않을 것을 권고한다. 예를 들어 B만 512 MB 조건을 충족한다면 시간 / 비용 열세만으로 제외하지 않는다. 기능과 A 설계는 유지한다.

**보완 확인:** A1, A2를 부모 A와 각각 비교한다. B의 구조 자체가 불리하다거나 주요 DP로 제출할 가치가 없다고 최종 판정하기 전에는 B4 병행을 별도 구성으로 반드시 확인한다. 이는 이번 기본 B의 순차 정책에서만 나온 지연을 구별하는 민감도 확인이며 모든 tactic을 기본 비교 전에 넣는 규칙은 아니다. B4의 결과를 기본 B 결과로 덮어쓰지 않으며, 병행 후에도 남는 producer → resolver 의존과 전체 비용을 공개한다. B1/B2에서만 나타난 재사용 이익으로 기본 B의 QA 표를 채우지 않는다.

### 3.4 업무 인계: 즉석 구성과 지속 기록의 손익

**비교:** 기본 A/B/C. EX11 다른 Agent에게 후속 위임, EX12 동일 Agent 수정, EX14 실행 중 전환, EX16 철회 / locator 만료, EX17 재접속을 쓴다. 한 업무의 단일 위임과 같은 결과로 여러 후속 위임을 하는 장면을 구별한다.

- 다음 Agent는 같은 완료 조건을 받고 같은 허용 원본에 접근한다. A/B도 자료 참조를 보낼 수 있다. 전체 문서를 매번 복사해야 한다는 불리한 조건을 넣지 않는다.
- C의 수신자는 실제 범위별 읽기 인터페이스를 사용하는 경우와 미지원인 경우를 구별한다. 미지원 수신자에 임의 도구를 추가해 기능을 입증했다고 하지 않는다.
- 공통 원본 기록은 전부 보존한다. B의 지속 의미 기록 생산과 갱신만 차이 비용으로 분리한다. native session 재사용은 A2/B3/C3 등의 별도 tactic이며 기본에 넣지 않는다.

**손익 확인식:** A는 `위임별 구성 + 원본 보완 / 재구성`, B는 `위임 여부와 무관한 지속 생산 / 갱신 + 위임별 추출 + 원본 보완 / 재구성`, C는 `필수 manifest + 접근 준비 + VIA 보완 / 재구성 + 실제 serving`을 기록한다. 각 처리의 모델 비용은 QA05, 실제 인과 경로의 시간은 QA03, local buffer는 QA06 원장으로 구별한다. 모델 없는 I/O를 모델 비용으로 만들지 않는다. C 수신자의 읽기 및 모델 비용도 별도 장부에 공개한다. 그 외부 비용을 QA05에 합치지는 않지만 전체 작업이 싸졌다는 근거로 숨기지도 않는다.

**QA 경계:** QA03은 정해진 상세 표시와 전체 음성 요약 준비까지 실제 필요한 VIA 경로만 포함한다. 그 이후 발생한 pull 제공은 별도 serving 진단이다. N-H는 위임을 허가하며 확정한 계약의 목표, 조건, 자료, revision과 범위가 oracle을 만족하는지 본다. 참조가 유효하고 필수 자료를 전달한 경우 수신자가 읽지 않은 사실을 VIA의 계약 오류로 바꾸지 않는다.

**기존 목표와의 구체적인 연결:** [COMMON-28의 S15-G03](../../qa-candidate-package/common-scenarios.md#s15)은 S15-U03의 “아까 문단 설명으로 발표자료 파일을 만들어줘”부터 S15-A01의 새 Task 결과 파일 참조 표시까지다. 위임 전 첫 수행 안내는 QA01에서 끝날 수 있지만 QA03 목표는 끝나지 않는다. `S15-U03 제출 → 이미 채택된 설명에 대한 인계 준비 → Agent ingress → 외부 결과 → R15 참조 표시` 중 인계 준비가 ingress에 선행한다. 외부 실행 8초 대역은 QA03에서 제외하고 실제 VIA 경로를 남긴다. 이 목표에는 Voice OFF 조건을 그대로 적용한다. S16-G01~04도 실제 Agent 결과 확인이 완료 조건이다. 이 연결을 확인한 장면에서만 인계 준비의 QA03 경로를 주장하며, EX의 다른 변형은 해당 목표와 일대일로 같다고 간주하지 않는다. 결과 이후의 읽기나 독립 배경 serving은 이 경로에 더하지 않는다.

**추천 변경:** 반복 위임에서 B의 상각 이익이 전체 생산 비용을 회수하거나, 지원이 확인된 C가 큰 자료의 불필요한 전달을 줄이면 권고를 바꿀 수 있다. 정확도는 A의 조합 누락, B의 stale / 압축, C의 manifest / 접근 오류를 비교하며 어느 쪽의 승리도 미리 넣지 않는다.

**보완 순서:** A 대 A1 capsule cache, 지원 수신자에 한해 A 대 A2 native session 재사용. session resume 실패 뒤 fresh session이 만들어지면 기존 문맥이 유지됐다고 취급하지 않고 인계를 다시 구성한다.

### 3.5 Agent 선택: 주요 DP 승격 전에 확보할 것

우선 실제 연동 가능한 Agent의 후보 자료, 사용자 선택 목적과 독립 허용 집합을 만든다. EX13 후보만 변경, EX15 복수 적격 후보, EX11 최초 위임, EX12 명시적 같은 Agent를 사용한다. 실행 여부가 불명확한 전환은 공통 admission의 보류 조건이다.

그 다음 기본 A/B가 같은 정보를 보고 선택하도록 구성한다. N-S는 채택 시 후보 또는 정당한 보류를 판정한다. card의 자기 설명을 oracle로 사용하지 않는다. 작은 후보군과 명시적 지정에서 별도 선택 실행을 억지로 추가하지 않는다.

이 단계에서 B의 독립 재선택 이익과 추가 계약 / 호출 비용이 대립하면 주요 DP 승격을 검토한다. 그렇지 않으면 상세 설계 A를 유지한다. 별도 B 구현이나 모델 성능 경연을 이번 문서 작업에 포함하지 않았다.

## 4. 어떤 근거로 어디까지 말할 수 있는가

| 확인 방법 | 가능한 결론 | 불가능한 결론 |
| --- | --- | --- |
| 문서 / code path 정적 조사 | 실제로 존재하는 처리 방식, 상태와 API 조건 | VIA에서의 시간, 정확도와 비용 승리 |
| 결정적 dependency 대역과 제한된 후보 경로 | 처리 순서, 같은 revision의 채택, 취소 / 늦은 결과 / 권한 처리 | 모델 지칭 및 선택 정확도, 실제 cloud 지연 |
| 동일 모델을 사용하는 제한된 실제 호출 | 해당 모델 / 입력에서의 의미 결과, 호출 원장과 처리 시간 | 전체 제품 평균, 다른 모델의 성능, 실제 Windows 최대 RAM |
| 실제 Rust 변경 과제 C01~C06 | 사전 registry에 따른 QA04 변경 모듈 수 | 상자 수로 추정한 변경 용이성 |
| 실제 목표 Windows 환경과 전체 경로 | 정의된 전체 VIA RAM 최고량과 UI 표시 시점 | 축소 PoC의 RAM으로 전체 512 MB 준수 주장 |

QA04는 코드가 필요하므로 이번 보고서에는 예상 모듈 수를 만들지 않는다. QA06 역시 후보의 buffer만 재어 시스템 목표를 통과시킬 수 없다. 새로운 정확도 N-H/N-S/N-R은 아직 지표 제안이며 목표와 점수는 별도 합의 전이다.

## 5. 결과를 보고 결론을 바꾸는 규칙

1. **동일 기능을 못하면 미충족으로 기록한다.** 그래도 raw 시간, 비용과 실패 증거는 남긴다. 빠른 실패를 성공 사례에서 제외해 평균을 좋게 만들지 않는다.
2. **방향이 안정적이지 않거나 관측 오차보다 작으면 불확실로 보고한다.** 한 장면의 승리로 전체 추천을 바꾸지 않는다. 기존 목표 / 점수 구간과 원값을 함께 사용하되 작은 차이를 숨기거나 임의 등급 차이를 만들지 않는다.
3. **기존 목표 달성 여부를 바꾸는 차이는 명확히 표시한다.** 다만 좁은 EX subset이 목표를 넘었다는 것만으로 공식 QA 통과 / 실패를 확정하지 않는다. 공식 관련 모집단과 전체 비용 단위에서 재확인한다.
4. **새 정확도 목표나 실용 차이 기준이 필요하면 실행 전에 정한다.** 현재 근거 없는 퍼센트와 점수를 만들어 결과를 재단하지 않는다. 기존 값의 개정이 필요하면 이유, 새 판본과 양안 동일 적용을 남긴다.
5. **기본안의 차이가 없으면 그 사실을 인정한다.** tactic에서 생긴 효과로 기본 비교를 소급 채우지 않는다. 문제 3/5의 승격 조건이 성립하지 않으면 보완된 기능 설계로 남긴다.

최종 실행 산출물은 `원본 fixture와 oracle`, `구조별 trace`, `호출 / 비용 원장`, `오류와 미완료 사례`, `기본안 비교표`, `tactic 전후 표`, `권고 변경 이유`다. 현재 파일은 이 실행의 설계이며 그런 결과 파일을 이미 생성했다고 주장하지 않는다.
