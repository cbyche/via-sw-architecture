# 다섯 VIA 문제의 공동 조사 기준

2026-10-17 / 사용자 리뷰 반영 / 기본 구조 비교와 선택 후 보완 설계

## 1. 목적과 범위

사용자가 승인한 탐색은 QA와 VIA 사용 장면에서 중요한 기능 설계 문제를 찾고, 실제 Agent harness의 메커니즘으로 기능을 수행할 수 있는 복수의 기본 설계안을 구성하는 것이다. 기본 구조 A/B/C를 먼저 비교하고, 선택된 구조의 약점을 보완하는 tactic은 A1/B1 등으로 별도 평가한다. [비교와 보완 설계 규칙](07-basic-designs-and-tactics.md)을 함께 적용한다. 아래 다섯 문제를 한 조사 주기에서 다룬다. 문제 번호는 탐색 식별자이며 DP 번호가 아니다.

1. 현재 요청을 이해하는 데 필요한 근거 공급
2. 앞선 요청 처리 중 들어오는 사용자의 후속 발화와 외부 Agent의 진행 상태, 질문 및 결과 통지 처리
3. 발화 중 바뀌는 화면과 지칭의 보존 및 결합
4. Agent가 바뀌어도 이어지는 업무 기억과 인계
5. 적절한 Downstream Agent의 선택과 전환

대안 수는 제한하지 않는다. 각 문제 안에서는 A/B/C를 기본 설계안으로, A1/A2 또는 B1/B2를 해당 기본안의 보완안으로 표기한다. 모든 최적화와 혼합을 기본안에 미리 넣지 않는다. 각 기본안이 기능을 수행하는 데 필요한 계약과 구조 고유의 상태 재사용은 유지한다. 이 조사에서 구현, 모델 호출, 측정 freeze, 성능 측정, 기존 DP의 교체나 최종 A/B 선정, commit/push는 수행하지 않는다.

## 2. 공통 기능 및 품질 계약

공식 출발점은 [현재 QA 논의](../../03-03-qa-dp-evaluation-plan.md), [고정 기능](../../../../03-fixed-architecture-scope.md), [대표 UC](../../../../05-representative-use-cases.md), [공통 실행 계약](../../04-40-common-execution-contract.md)이다. 기존 target는 검토한 reference Architecture이며 모든 대안의 정답 구조가 아니다. 기존 source와 설계를 그대로 요약하는 것으로 탐색을 끝내지 않는다.

- VIA는 대화와 화면 interaction, bounded read / search / understand, 요청 해석과 채택, 위임과 결과 재연결을 소유한다. 업무 내부 계획, domain reasoning과 외부 Action은 Downstream Agent 책임이다.
- 현재 비교 캠페인의 로컬 VIA와 cloud 음성 / 의미 모델 조건을 사용한다. 각 비교 안에서는 모델과 사용 가능한 원본, 권한과 자원 예산을 동일하게 둔다. 모델 차이를 구조 우위로 바꾸지 않는다.
- 원본 사건, 현재 업무 조건, 파생 요약 / index, 사용자가 명시적으로 허용한 User Memory를 구별한다. 외부 Agent의 비공개 내부 추론이나 내부 memory를 자동 수집할 수 있다고 전제하지 않는다.
- 최종 의미 채택, 입력 revision, 실제 표시 / 음성 전달 사실과 업무 실행의 확인 사실을 구별한다. Task 연관성은 해석의 출력이며 정답 ID를 사전 제공하지 않는다.
- 기본안에는 범위를 제한한 읽기, 필요한 원본 보완, 현재 revision 및 권한 확인 등 기능 수행에 필요한 처리를 둔다. cache, 병렬 읽기와 부분 재계산 같은 추가 기법은 기본 구조에 필수인지 별도 tactic인지 밝힌다. 대화 문맥이나 공통 업무 기록을 유지하는 구조 자체의 재사용은 기본안에 남긴다. 쉬운 입력과 반복 입력을 공통으로 비교하되 cache hit는 cache를 실제 포함한 구성에서만 평가한다.
- [ADR-001](../../../../../../docs/adr/ADR-001-agent-integration-contract-boundary.md)의 integration edge 정규화와 미지원 기능의 명시 원칙을 보존한다. 내부 API 추상화만 바꾸는 제안을 새 주요 DP로 만들지 않는다.

| QA | 같은 뜻으로 유지할 경계 |
| --- | --- |
| QA01 첫 응답 | 첫 완결된 내용의 실제 Request/Task UI 표시. 구체적인 채택 의도는 위임 전에 표시 가능. 오답도 실제 시간 보존, 미응답은 임의 벌점 시간으로 대체하지 않음 |
| QA02 지칭 대상 정확도 | 지정 표현과 revision에 대해 채택한 대상 집합의 완전 일치. routing / 이력 일관성 / 인계 정확도와 혼합하지 않음 |
| QA03 VIA 처리시간 | 외부 업무, 사용자 발화와 대기를 제거한 실제 인과 경로. VIA 모델 / 검색 / 조정과 상세 표시 및 전체 음성 요약 준비 포함 |
| QA04 변경 범위 | 같은 관련 변경 요구를 완료하는 실제 운영 Rust 모듈 수. 소스가 없는 현 단계에는 영향 경로만 예측하고 숫자를 만들지 않음 |
| QA05 모델 비용 | COMMON-28의 전체 VIA 음성 / 의미 비용 단위를 보존. 준비, 미사용 생산, 재시도, 폐기와 tail 포함. 외부 Agent 내부 모델 / tool 비용 별도 |
| QA06 최대 RAM | 사용자 지정 512 MB 요구를 유지. 로컬 상태 / buffer / worker의 기여를 구별하고 cloud 메모리를 로컬 RAM으로 세지 않음 |

QA07~09는 사용자 평가대로 이번 핵심 후보 탐색에서 우선도가 낮다. 기존 정의와 필수 기능 검증은 보존한다. 새로운 QA 후보는 문제와 대안에서 도출할 수 있다. 지표 의미와 판정 근거, 여러 DP에 적용할 경로를 제안하고 신규 목표 / 점수 / 번호를 확정하지 않는다. 특히 Downstream Agent 선택 정확도는 capability 충족과 실제 업무 적합성, 복수 적합 후보와 정당한 보류를 구별한다.

### 문제 2의 입력과 범위

- **한 발화 안의 자기 정정:** “월요일, 아니 화요일”처럼 발화를 마치기 전에 말을 고친 경우다. VIA가 이미 중간 발화로 판단을 시작했다면 진행 중 판단의 갱신 문제가 된다. 발화 종료 뒤 처음 판단한다면 일반적인 요청 이해에 속한다. 음성 인식기가 전사 가설을 고치는 것은 사용자의 자기 정정과 별개다.
- **후속 발화에서 이전 요청을 변경:** 앞선 발화가 끝난 뒤 “아까 보고서는 최근 두 달 기준으로 바꿔줘”라고 하는 경우다. 앞선 발화가 끝났어도 VIA의 판단이나 외부 Agent의 업무는 진행 중일 수 있다. 문제 2의 주된 비교 장면이다.
- **사용자의 별도 질문 또는 새 업무 요청:** 사용자가 다음 발화에서 새로운 내용을 묻거나 일을 요청하는 경우다. VIA가 모호성을 해소하려고 사용자에게 하는 확인 질문과 구별한다. 사용자가 그 확인 질문에 답하는 후속 발화도 별도 입력 유형으로 다룬다.
- **외부 Agent의 통지:** 진행 상태, 추가 정보 또는 승인 요청, 부분 / 최종 결과, 실패와 취소 확인을 포함한다. 통지의 도착과 VIA가 이를 유효한 결과로 채택하는 시점은 다르다.

자세한 입력 정의, 같은 시간 순서의 예와 처리 구조는 [문제 2](02-continuous-interaction.md)에 둔다.

정상 사용을 어려운 예외보다 먼저 설명한다. Agent 내부 업무 성공과 VIA의 올바른 위임 / 인계가 다른 결과임을 기록한다. 외부 시스템의 기능을 사용할 수 있는지 확인하지 않은 장면은 해당 dependency가 필요한 설계 조건으로 표시한다.

## 4. 소스 조사 방식

기존 [고정 source 원장](../../../../../references/agent-harness-20261015.md)과 [근거 공급 조사](../../../../../references/qa-first-evidence-supply-20261016.md)를 재사용할 수 있다. 다시 확인한 경로와 새로 조사한 경로를 구별한다. GitHub 검색은 경로 발견용이고 중요한 주장은 고정 commit의 실제 코드를 읽는다. 도구명은 functions의 ALL_TOOLS에서 GitHub fetch / search를 찾을 수 있다. 공개 웹은 공식 docs / 논문 / 원 저자 구현을 사용한다.

각 source 기록에는 저장소 / commit / 파일과 위치, 정상 실행, 상태와 수명, 기본 구조와 추가 보완 기능, 실패 / 정정 경로, VIA에 직접 옮길 수 없는 부분을 남긴다. 제품별 소개 문단만으로 충분한 조사라고 보지 않는다. 동일 구조를 다른 이름으로 반복한 자료와 새로운 대안을 제공한 자료를 구별한다.

다섯 프로젝트 모두 조사 범위에 포함하되 모든 문제에 모든 제품을 억지로 배정하지 않는다. 근거가 없는 기능은 ‘이번 확인 범위에서 미확인’으로 쓰고 저장소 전체의 기능 부재로 단정하지 않는다. 다른 종류의 실제 SW를 참고했다면 그 이유를 기록한다.

## 5. 결과 문서의 필수 내용

1. VIA의 사용자 가치와 기능 실패, 관련 UC와 여러 구체 장면
2. 구조와 무관한 공통 완료 조건, 가정과 dependency
3. 조사 범위, 확인한 source와 탐색에서 남긴 / 제외한 메커니즘
4. 기본안 A/B/C: 데이터, 호출 의존, 상태 소유 / 수명, 정정과 실패, 필요한 공통 / 추가 모듈
5. 같은 장면의 기본안 비교. 단순 요청, 반복과 대안이 불리한 장면 포함. cache 등 보완 효과는 보완안에 따로 기록
6. QA01~06과 신규 후보의 인과: 차이 → 처리 / 상태 비용 → 지표 → 방향을 바꾸는 조건
7. 기본안별 선택 근거와 반증 조건. 선택 후 적용할 A1/B1 등의 보완 후보, 대상 QA, 추가 비용과 보완 전후 비교
8. DP 후보로 더 발전시킬지, 다른 문제와 통합할지, 상세 설계로 둘지에 대한 작성자 권고
9. 품질 우위, 기능 지원과 조사 근거의 미확인 범위

숫자 예측, 점수, 순위를 소스 없이 만들지 않는다. 과거 DP의 결과나 수치를 새 후보의 성과로 옮기지 않는다. 구조도는 필요하면 paired SVG / draw.io로 만들고 같은 문서에 표시한다. 문서의 ASCII 흐름과 표로 충분한 부분은 그림을 억지로 늘리지 않는다. 새 prose와 그림에 middle-dot 문자를 쓰지 않는다.
