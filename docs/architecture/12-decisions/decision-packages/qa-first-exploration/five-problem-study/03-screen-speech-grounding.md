# 문제 3: 발화 중 바뀌는 화면과 지칭을 어떻게 보존하고 결합할 것인가

2026-10-17 / 기본 구조 비교 후 선택안 보완 / 작성자 권고 A / 공식 채택 미정 / 구현과 측정 없음

> **현재 설계 권고:** 화면과 발화의 지칭 해석은 VIA의 핵심 기능이며 **기본 A 원본 공동 해석을 추천**한다. 선택 후 우선 보완은 **A1 crop/cache와 A2 부분 binding patch**다. 다만 기본 B의 반대편 QA 이익을 현재 근거만으로 충분히 지지하지 못하므로 **A/B는 조건부 DP 후보로 유지하고 주요 DP 확정 권고는 보류**한다. 추천 이유, B가 유리할 조건, 동일 입력 PoC와 반증은 [§13](#13-2026-10-17-설계-권고)에 둔다. §1~12의 기본 비교에 보완 효과를 소급하지 않으며, 작성자 추천은 사용자 채택이나 측정 승자가 아니다.

## 1. 이번 비교의 순서와 결론

**이 문제는 VIA가 직접 풀어야 하는 핵심 DP 후보다.** 사용자가 말하며 가리킨 화면은 발화가 끝났을 때 이미 바뀌어 있을 수 있다. 마지막 화면만 읽어서는 당시 대상을 복구할 수 없다. VIA는 당시 근거와 지칭, 이후 정정의 관계를 보존하고 Downstream Agent에 넘길 대상을 정확하게 정해야 한다.

먼저 같은 기능을 수행하는 **기본 A/B**를 비교한다. 어느 안을 선택할지는 아직 정하지 않았다. 이어서 각 기본안의 약점을 줄이는 **A1/A2/A3, B1/B2/B3/B4**를 제안한다. 보완 번호는 자동 누적되지 않는다. A2는 기본 A에 부분 binding 갱신만 추가한 안이며, A1의 crop/cache까지 함께 쓰면 A1+A2라고 표시한다. 현재 기본안의 QA 표와 시나리오에는 보완 효과를 넣지 않는다.

| 기본안 | 현재 지칭을 생산하는 핵심 구조 | 기본 구조에서 기대하는 이익 | 기본 구조가 부담하는 비용 |
| --- | --- | --- | --- |
| **A 원본 공동 해석** | 하나의 해석 책임이 발화와 당시 화면 / 동작의 원본을 함께 읽고 직접 target 연결을 생산 | 언어가 화면 범위를 결정하는 경우 중간 후보를 별도로 다시 만들 필요가 적고, 직접 binding까지의 의존 단계가 짧음 | 공동 입력 범위가 크거나 정정이 반복되면 원본 입력과 전체 binding 재판단 부담이 커짐 |
| **B 생산자 소유 후보의 교환과 결합** | 발화의 표현 후보와 화면의 대상 후보를 각각 생산하고, 결합자가 이 후보를 연결. 부족한 후보는 원 생산자가 원본에서 확장 | 한 판단 안에서 화면 대상을 구조화하고 여러 표현이 이를 함께 참조. 결합 판단의 입력을 명시적 후보와 관계로 줄일 수 있음 | 후보 생산과 결합을 모두 수행하며, 빠진 대상은 producer 재생산을 거쳐야 함. 원본과 후보를 함께 보존 |

두 기본안은 **완성 입력의 revision이 준비된 뒤 의미 판단을 시작**한다. 원본 수집은 발화 중 계속하며, 유효한 발화 전 selection과 실제 보존된 허용 pre-roll도 포함한다. 발화 중 잠정 의미 판단은 A3/B3의 보완이다.

기본 차이가 직접 드러날 가설은 QA01/QA03의 판단 의존 경로와 QA05의 전체 모델 처리량이다. QA02의 정확도, QA04의 실제 변경 범위와 QA06의 RAM도 비교하되 우위를 선결하지 않는다. 보완으로 약점을 줄일 수 있다는 이유만으로 기본 구조 비교를 폐기하지 않는다. 현재 문서만으로 과정의 3~4개 QA 차별화 요건이나 최종 DP 선정을 충족했다고 선언하지도 않는다.

## 2. VIA 기능과 공통 완료 조건

주 관련 UC는 [UC-03, UC-04, UC-05, UC-06, UC-09, UC-10, UC-11](../../../../05-representative-use-cases.md)이다. 입력 채널 재연결, 접근 철회와 실패는 UC-15, UC-16, UC-18과 연결한다.

대표 장면은 “이 표는 그대로 두고, 이 두 그래프의 차이를 설명해줘”라고 말하며 표를 가리키고 다음 페이지로 이동해 두 그래프를 둘러싼 뒤, “아니 아래 것만”이라고 고치는 경우다. 결과는 화면의 object 목록이 아니라 **각 표현의 대상 / 범위와 유지 / 교체 관계**다. 문서 수정 같은 외부 Action은 해석 뒤 Downstream Agent에 위임한다.

### 2.1 양안이 처음부터 갖추는 기능

1. 발화 중 실제 취득한 원음 / 전사, frame, pointer / selection과 source별 관측 범위를 보존한다. 발화 전 selection이 첫 조회 시 여전히 유효하면 초기 상태로 포함한다. 사전에 허용해 보존한 pre-roll이 실제 있으면 양안에 같은 범위를 제공한다. 상시 수집을 새로 요구하거나 미관측 과거 화면을 생성하지 않는다.
2. 표현별 단일 대상, 집합과 범위를 판단한다. native 참조가 실제 있으면 참조와 revision을 쓰고, 없으면 당시 이미지의 visual extent로 표현한다. native 자료가 충분한 장면에서 불필요한 image 모델 호출을 강제하지 않는다.
3. 원형 동작, page 이동과 우연한 pointer 통과를 구별할 근거를 남긴다. timestamp의 인접성이나 pointer 통과만으로 의도를 확정하지 않는다. 정확한 단어 시각과 모든 앱의 stable object ID는 보장하지 않는다.
4. 정정 후 유지할 대상과 바꿀 대상을 구별한다. 이전 채택 binding을 입력으로 받아 사용자가 변하지 않은 조건까지 반복해서 말하지 않게 한다. 전체를 재판단하는 것과 유지 조건을 버리는 것은 다르다.
5. 원본 추가 조회, B의 후보 부족 시 원 producer 확장, 실제 모호함의 확인, source gap의 미해결 반환을 지원한다. 근거가 충분한데도 질문으로 해결을 넘기는 것을 정상 성공으로 처리하지 않는다.
6. 현재 input revision과 사용권에 유효한 제안만 채택한다. 취소되거나 오래된 판단은 현 결과로 채택하지 않는다. 원본 철회는 관련 파생 후보와 사본에도 적용한다.
7. 같은 cloud 모델 capability, 입력 원본, capture 범위 / 해상도 / 한도와 실행 예산을 쓴다. cloud가 원음과 image의 공동 입력을 지원하지 않으면 양안 모두 전사와 알려진 구간을 쓰고 지원 한계를 기록한다. 숨은 local 의미 모델을 추가하지 않는다.

원본 범위는 현재 요청에 필요한 관측 구간으로 제한한다. 기본 A가 대화 전체나 모든 저장 frame을 항상 보내는 것은 아니다. 필수 추가 조회와 원본 보존은 기본 기능이며, 의미적으로 골라 만든 crop의 재사용, cache, 부분 재계산과 발화 중 판단은 후술하는 별도 보완이다.

### 2.2 다른 문제와의 경계

| 문제 | 이 비교가 주고받는 자료 | 여기서 결정하지 않는 부분 |
| --- | --- | --- |
| 1 현재 요청의 근거 공급 | 과거 원본, 실제 전달 이력과 채택 binding 조회 | 대화 문맥 유지 / 요청별 retrieval 전략 |

| InproTKS 원 논문, ReTiCo core | incremental unit의 의존, add / revoke / commit과 update queue | A3/B3의 잠정 의미 갱신 참고. ReTiCo의 생성 시각은 센서 관측 시각과 같지 않고, commit은 VIA 채택과 다름 |

Deep Agents와 CrewAI는 공동 harness 조사에 포함되지만 이 문제의 시간 지칭을 직접 입증하는 새 근거로 사용하지 않았다. 다중 agent 지원만으로 B의 multimodal 결합을 입증할 수는 없다. A/B의 temporal binding, source coverage, producer 재확장과 사용자 정정 계약은 확인한 구조를 VIA 기능에 맞게 확장한 설계다.

### 3.1 독립 기본안으로 남기지 않은 방향

- 마지막 screenshot만 읽는 방식은 사라진 지칭 근거를 보존하지 못한다. 같은 기능을 수행하는 주요 대안으로 남기지 않는다.
- native 우선 조회는 양안의 실제 입력 활용이다. native가 없는 visual 대상까지 제외하는 제약으로 만들지 않는다.
- screen 1위 후보를 먼저 확정하는 방식은 B가 아니다. B는 복수 후보, unknown과 원본 확장을 기본으로 갖춘다.
- 매번 selection / overlay 확인을 강제하면 사용자 동작 조건이 달라진다. 실제 모호함의 확인은 공통 기능으로 둔다.
- 별도 process, cache, crop과 발화 중 증분 판단만으로 새로운 의미 생산 구조 C를 만들지 않는다. 이번 조사에서는 세 번째 독립 기본 구조를 추가하지 않았다.

## 4. 비교에 고정한 데이터와 기본 처리

### 4.1 공통 데이터와 수명

다음은 설명용 데이터 계약이다. target Component 이름은 그대로 쓰며 내부 Module과 별도 process를 동일시하지 않는다.

| 자료 | 작성 / 보존 책임 | 수명과 의미 |
| --- | --- | --- |
| `ObservationWindow` | Interaction Manager가 capture하고 bounded buffer에 보존 | 발화 중 audio / frame / pointer, 첫 조회에서 유효한 selection, 허용된 기존 pre-roll, source 시각 / 도착 시각 / 오차 / gap. 정답 target을 미리 넣지 않음 |
| `GroundingInput` | Request Controller → Request Interpreter | 완성 입력의 revision, 원본 조회 권한, 이전 채택 binding과 예산. 모든 media의 복사본이 아닌 참조 |
| `GroundingProposal` | Request Interpreter의 A 또는 B | 표현별 target 집합, extent / source revision, 근거, 불확실성과 유지 / 교체 제안. 외부 실행 허가 자체는 아님 |
| 채택 binding | Request Controller가 검증하고 상태 계약에 따라 보존 | 후속 대화와 인계의 입력. 과거 snapshot 참조와 현재 Action selector를 구별 |
| 사용권 / 만료 | Policy Manager와 Context Manager의 공통 계약 | 원본과 파생 자료의 허용 수명을 통제. 철회된 자료를 재사용하거나 미보존 과거를 현재 화면으로 대체하지 않음 |

원본은 필요한 정정과 근거 확인을 위해 보존한다. 이것만으로 semantic cache를 구현한 것은 아니다. local buffer, decode, staging, queue, 후보와 serialization 사본은 QA06에 모두 포함한다. 디스크 사용만으로 512 MB 준수를 선언하지 않는다.

### 4.2 기본안에 있는 처리와 없는 처리

| 항목 | 기본 A | 기본 B |
| --- | --- | --- |
| 발화 중 | 원본 수집 / 보존만. 잠정 의미 판단 없음 | 동일 |
| 판단 시작 | 공통 완성 입력 정책으로 revision 준비 후 | 동일 |
| 첫 의미 생산 | 필요한 원본을 함께 읽고 현재 요청의 binding 집합을 직접 생산 | 표현 후보 생산 → 화면 후보 생산 → 후보 결합. 이 기본 비교에서는 순차 실행 |
| 필수 재판단 | 근거 부족 / 모순이면 원본을 추가 읽고 현재 binding 집합 재판단 | 부족한 후보를 해당 producer가 원본에서 확장하고 결합 재판단 |
| 후속 정정 | 이전 채택 결과와 정정을 받아 현재 요청의 binding 집합 전체 재판단 | 이전 채택 결과와 정정을 받아 현재 요청의 표현 / 대상 후보를 다시 생산하고 결합 |
| 기본 상태 사용 | 과거 채택 binding과 원본은 기능상 입력. 과거 모델 응답을 계산 cache로 사용하지 않음 | 한 판단 안에서 같은 target 후보를 여러 표현이 참조. 이전 완료 revision의 후보 생산 결과를 계산 cache로 재사용하지 않음 |
| 기본에 없는 보완 | semantic crop/cache, 부분 binding patch, 발화 중 의미 판단 | revision 간 안정 후보 cache, 부분 후보 재생산, 발화 중 의미 판단, 두 producer의 병행 실행 |

B의 현재 후보를 더 자세히 확장하는 기본 복구와, 후속 정정에서 바뀐 후보만 계산하는 B2는 구별한다. B의 후보 기록을 provenance로 보존할 수는 있지만, 기본 B가 이를 새 revision의 생산 결과로 그대로 인정하지는 않는다. 전체 재판단 범위는 **현재 요청의 지칭 집합**이며 모든 대화와 Task가 아니다.

B의 두 초기 producer 사이에는 필수 데이터 의존이 없다. **순차 실행은 같은 budget에서 단순하게 구성한 이번 기본안의 실행 정책**이다. 후보 생산을 나눴기 때문에 반드시 서로 기다려야 한다는 뜻은 아니다. 반면 Resolver가 결합하려면 두 producer의 필요한 후보 read-set이 준비되어야 한다는 의존은 B의 핵심 구조에 남는다. B4는 앞의 실행 정책을 보완하며, 그 개선량을 원본 공동 해석과 후보 결합 사이의 필연적 우열로 해석하지 않는다.

원본 읽기와 입력량에는 양안의 같은 한도를 적용한다. 정확한 native 선택이 이미 제공한 범위를 쓰는 것은 A1의 선택적 image crop과 다르다. 완성 입력을 기다린다고 모든 source를 무제한 기다리지도 않는다. source별 유한 대기 후 부족 범위를 명시하고, 필요한 자료가 없으면 미해결로 반환한다.

## 5. 기본 A: 원본 공동 해석

Request Interpreter의 **Joint Grounding Interpreter**가 원본에서 표현별 target 연결을 직접 생산한다. 별도 화면 의미 producer의 후보를 반드시 거칠 필요가 없다.

### 5.1 입력, 실행과 반환

1. Request Controller가 완성 입력의 `GroundingInput`을 전달한다. Task association을 정답으로 미리 주지 않는다.
2. Joint Grounding Interpreter가 필요한 실제 발화 / frame / 동작 범위를 읽는다. 반환 자료는 native 상태, 원본 참조, 관측 시각 / 오차와 gap이다.
3. Model Access를 통해 공통 cloud 의미 모델에 원본과 이전 채택 binding, 정정 내용을 함께 제공한다. 현재 요청의 target 집합, 유지 / 교체 관계 또는 추가 근거 요구를 받는다.
4. 부족하면 허용 원본을 더 읽고 현재 binding 집합을 다시 판단한다. 기본에는 crop/cache와 영향 부분만 갱신하는 patch가 없다.
5. Request Interpreter가 `GroundingProposal`을 반환한다. Request Controller가 revision / 권한을 확인하고 전체 요청 해석과 응답 / 위임에 사용한다.

### 5.2 상태, 정정과 정상 손익

요청별 `Joint Grounding State`에는 현재 원본 참조, 판단 revision과 미채택 proposal을 둔다. 정정 도착 시 이전 proposal의 채택을 막고, 이전 채택 binding과 새 정정을 함께 읽어 **현재 요청 전체의 binding**을 다시 생산한다. “문단은 유지”라는 조건도 이 재판단의 입력이므로 사라지지 않는다. 완료 후에는 필요한 채택 binding과 근거를 공통 상태에 남기며 계산 재사용용 cache는 별도로 만들지 않는다.

A는 언어가 visual target의 경계를 정해야 하는 장면에서 유리할 수 있다. “figure 하나가 아니라 오른쪽 두 그래프”를 원본에서 직접 새 범위로 표현할 수 있으므로 별도 producer와 재생산 협상을 하지 않는다. 그러나 공동 입력이 크고 여러 정정에서 대부분의 대상이 유지되어도 기본 A는 현재 binding 집합을 다시 계산한다. 이 반복 입력과 재판단이 A1/A2가 다룰 약점이다. 원본을 함께 본다는 사실만으로 정확도를 보장하지 않는다.

## 6. 기본 B: 생산자 소유 후보의 교환과 결합

Request Interpreter의 **Speech Reference Producer**는 표현 / 수정 관계 후보를, **Screen Target Producer**는 화면 대상 / 동작 후보를 생산한다. **Multimodal Binding Resolver**는 후보를 결합한다. **Grounding Coordinator**는 실행과 version을 관리하며 의미를 대신 채우지 않는다.

### 6.1 입력, 실행과 반환

1. Grounding Coordinator가 A와 같은 완성 입력의 `GroundingInput`을 받는다.
2. Speech Reference Producer가 발화 원본에서 수, 순서, 지칭 관계와 수정 범위의 후보를 생산한다. 다음으로 Screen Target Producer가 화면 / 동작 원본에서 native 또는 visual 범위, navigation / designation의 경쟁 해석과 coverage를 생산한다. 초기 screen 생산이 speech 후보를 필요로 해서 기다리는 것은 아니다. 이 기본안의 단순 순차 정책을 적용한 것이며 B4에서 병행을 검토한다.
3. 각 producer는 원본 근거와 자신의 revision을 가진 `Candidate Revisions`를 게시한다. native 자료로 후보를 만들 수 있으면 해당 단계의 모델 호출을 강제하지 않는다.
4. Coordinator가 호환되는 후보 read-set, 관련 원문 excerpt와 이전 binding을 Resolver에 전달한다. Resolver는 필요한 결합을 판단하되, 후보에 없는 새 target을 원본에서 직접 생산하지 않는다.
5. 후보가 부족하면 Resolver가 `RejudgeRequest`를 반환한다. 예를 들어 하나의 figure 안의 두 graph가 필요하면 Screen Target Producer가 해당 원본을 읽어 새 후보 revision을 만든다. Resolver는 바뀐 후보 집합으로 다시 결합한다. 이는 기능 성립에 필요한 기본 경로다.
6. Resolver가 producer version에 의존하는 `GroundingProposal`을 반환한다. Request Controller의 공통 최신성과 사용권 검사 후 채택한다.

후보 목록이 작더라도 producer가 이미 소비한 image 입력과 출력 비용은 남는다. 관련 excerpt를 쓰는 것은 결합 맥락을 주는 것이며, Resolver가 후보 밖의 target을 직접 만들어 채택하는 우회 경로는 아니다.

### 6.2 상태, 정정과 정상 손익

| 상태 | 의미 생산 / 수정 책임 | 기본 수명과 재판단 |
| --- | --- | --- |
| 표현 후보 | Speech Reference Producer | 완성 입력 revision별 생산. 정정 후 현재 요청의 표현 후보 다시 생산 |
| 대상 후보 | Screen Target Producer | source extent / revision과 coverage를 참조. 현재 판단 안에서 여러 표현이 공유하고, 부족하면 원본에서 확장. 후속 완료 revision에서는 다시 생산 |
| 결합 proposal | Multimodal Binding Resolver | 사용한 producer read-set에 의존. 후보 교체 시 결합 다시 판단 |
| job / 예산 / 반환 상태 | Grounding Coordinator | 요청별 bounded 상태. 추가 왕복 한도, 실패, 취소와 늦은 결과 처리 |

B의 기본 이익은 **생산과 결합의 분리**에서 찾는다. 한 발화에 여러 지칭이 있으면 화면 후보를 한 번 구성하고 각 표현이 같은 대상 / 집합 관계를 참조할 수 있다. 후보가 원본의 중요한 단서를 보존하면 Resolver의 입력이 작고 명시적일 수 있다. 자료 유형별 변경 책임을 나눌 여지도 있다. 이 세 효과가 전체 비용, 정확도나 변경 모듈 수의 우위로 이어지는지는 별도 확인이 필요하다.

기본 B는 다음 정정에서 안정 target을 그대로 사용하는 이익을 아직 갖지 않는다. 그 이익은 B1이다. 후보 누락 시 확장과 재결합의 의존, 생산 오류의 전파, 원본에 더해 후보를 보존하는 비용은 기본부터 발생한다. 후보 생산 실패를 “대상이 없음”으로 바꾸지 않으며, 원본 확장 후에도 불명확하면 A와 같은 미해결 / 확인 경로를 쓴다.

### 7.1 EX08의 실행 경계

1. 발화 중 chart A, chart B와 마지막 빈 곳의 원본 관측을 보존한다. 이때 양안의 의미 판단은 아직 실행하지 않는다.
2. 실제 발화 종료 뒤 전사 등 공통 완성 입력 정책을 충족하면 판단을 시작한다. 늦은 source는 정한 유한 대기 / gap 규칙을 따른다.
3. A는 필요한 원본에서 직접 binding을 만든다. B는 표현과 대상 후보를 순차 생산한 다음 결합한다. B의 figure 분할이 필요하면 원 producer가 확장한다. A도 오류 / 근거 부족이면 원본을 다시 읽는다.
4. 현재 proposal만 채택한다. 채택한 두 대상을 구체적으로 밝히는 첫 완결 내용이 표시되면 QA01이 끝날 수 있다. 상세 내용과 전체 음성 요약 준비까지 필요한 실제 경로는 QA03에 남는다.
5. 배경 Agent 완료가 겹쳐도 원본을 그 Task의 자료로 바꾸지 않는다. 사건 우선순위는 문제 2의 결정이다.

| **QA01 첫 응답** | 첫 내용 전에 binding이 필요하면 A의 직접 판단이 이번 B의 순차 생산 / 결합 경로보다 짧을 수 있음. B의 생산 → 결합 의존과 두 초기 producer의 순차 실행 정책은 구별 | B의 작은 결합 입력 효과가 생산 비용보다 크거나 native로 생산 단계가 저렴하면 방향 / 차이 변화. binding과 무관한 유효 첫 내용이 먼저 가능하면 차이 축소 | 이번 기본 구성에서 A의 지연 이익 가설. 순차 정책의 차이를 구조의 필연적 우위로 일반화하지 않음 |
| **QA02 대상 집합 정확도** | A는 공동 원본 단서를 직접 사용. B는 명시적 후보 / 관계로 결합하지만 중간 누락이 생길 수 있고 producer 확장으로 복구 | B의 채택 전 확장이 충분하거나 A가 공동 단서를 놓치면 동점 / 역전. 첫 잘못된 채택을 이후 정정으로 지우지 않음 | 직접적인 핵심 문제이나 어느 안의 우위도 미확인 |
| **QA03 VIA 처리시간** | A의 공동 media 판단과 B의 후보 생산 / 결합 / 재생산의 실제 critical path가 다름 | 분리 단계의 짧은 입력이 overhead를 상쇄하면 B 유리 가능. 공통 입력 확정 대기와 상세 응답 생산이 지배하면 차이 축소 | 차이 가설. 실제 발화 종료부터 재며 완성 입력 대기를 빼지 않음 |
| **QA04 실제 Rust 모듈 변경 범위** | C03 source 좌표 / 시각 / version, C05 실제 전달 근거와 extent, C06 철회가 공동 해석 또는 producer / 결합 계약에 전파 | 공통 adapter가 변경을 흡수하면 동점. B 분리가 수정 범위를 국소화할 수도 있고 계약을 더 바꾸게 할 수도 있음 | 같은 C01~C06의 실제 변경으로 확인. 모듈 / 상자 수만으로 우위 선언 금지 |
| **QA05 전체 VIA 모델 비용** | A의 공동 입력 / 전체 재판단과 B의 생산 입력 / 출력 + 결합 + 확장 비용을 모두 합산. 기본 양안은 정정 시 전체를 다시 계산 | 한 판단에 지칭이 많고 작은 후보 결합의 절감이 생산 비용을 넘으면 B 유리 가능. 후보 확장이 잦거나 입력이 작으면 A 유리 가능 | 전체 COMMON-28 비용에서 확인. 모델 호출 수나 Resolver 입력만으로 결론 내리지 않음 |
| **QA06 최대 RAM** | 같은 원본 buffer 외에 A의 공동 입력 staging과 B의 후보 / 교환 상태가 추가. 기본 B는 순차 producer 상태도 필요한 동안 보유 | 참조 표현과 decode / staging 수명에 따라 방향이 바뀜. 원본을 버려 B의 RAM을 줄이는 가정은 불가 | 512 MB 공통 요구. 실제 최대값과 차이는 미확인 |

QA01은 일반 수신 확인을 제외한 첫 실제 내용 표시다. 틀린 첫 내용의 시각을 임의 timeout으로 바꾸지 않는다. QA03은 기존 trial의 상세 표시 / 전체 음성 요약 준비 endpoint 안에 있는 VIA 인과 경로를 다루며, 외부 Agent의 업무 수행이나 endpoint 이후 자료 serving까지 늘리지 않는다. QA01과 QA03은 겹치는 지연을 포함하므로 합산하지 않는다.

QA05에는 재시도와 폐기 판단, 마지막 정리까지 실제 VIA 모델 비용을 포함한다. 기본에는 발화 중 speculative 판단이 없지만, 보완 비교에서는 그 비용까지 같은 집계에 더한다. QA06에는 local RAM만 포함하고 cloud 모델 memory는 넣지 않는다.

지칭 정답은 QA02가 다루므로 별도 핵심 QA를 새로 만들지 않는다. source coverage, 후보 miss와 재생산 횟수는 원인 진단이다. 잘못된 target이 인계에 남으면 문제 4의 확정 인계 계약에도 영향을 줄 수 있지만, Agent 선택 정확도나 별도 정확도 이득으로 중복 주장하지 않는다. 입력 수신, 실제 전달, 복구와 접근 통제의 회귀 조건도 유지한다.

## 9. 기본안 선택에 사용할 근거

**현재 선택은 보류한다.** 다음 조건을 같은 장면에서 확인한 뒤 QA 우선순위와 감수할 단점을 설명해야 한다.

| 선택을 검토할 조건 | 선택 이유 | 선택 시 받아들이는 약점 | 후속 보완 방향 |
| --- | --- | --- | --- |
| A가 언어와 visual 범위의 강한 상호 의존에서 QA02를 유지하며 QA01/QA03/QA05를 줄임 | 직접 원본 binding과 짧은 재판단 의존을 채택 | 반복 원본 입력과 정정 시 전체 binding 계산 | A1의 입력 재사용, A2의 부분 갱신. 긴 안정 발화라면 A3 검토 |
| B의 후보가 필요한 단서를 충분히 보존하고 한 판단의 다수 지칭에서 전체 비용 또는 정확도에 실질 이익을 보임 | 생산자가 관리하는 대상 / 관계를 결합하는 계약을 채택 | 후보 생산, 누락 복구와 결합 단계의 지연 및 상태 비용 | B1/B2의 반복 계산 감소. B3 또는 B4의 대기 감소 검토 |
| 핵심 QA에서 한 안의 기능 실패 또는 감당할 수 없는 비용이 확인됨 | 실패 / 비용의 실제 원인을 선택 근거에 포함 | 낮은 우선순위 QA를 숨기거나 제외하지 않음 | 보완 후 회복되는지 같은 정의로 확인. 회복되지 않으면 선택 재검토 |
| 중요한 QA가 대부분 같거나 API 한계가 지배함 | 현재 근거로 승자를 정하지 않음 | 차별화 요건이 미확인 상태임을 유지 | 추가 자료 / 검증 필요성을 기록하며 QA의 의미를 바꿔 차이를 만들지 않음 |

B의 후보 명시성이 자동으로 더 정확하거나 수정하기 쉽다는 주장은 하지 않는다. A의 적은 의존 단계도 자동으로 더 빠르거나 저렴하다는 뜻은 아니다. 기본 비교에서 어떤 약점을 받아들였는지가 정해져야 보완의 목적도 구체적이 된다.

## 10. 선택한 기본 구조의 약점을 줄이는 보완 후보

각 행은 **기본 A 또는 기본 B에 그 기법만 추가한 안**이다. 여러 행의 이익을 기본 비교에 미리 반영하거나 합산하지 않는다. 기법을 함께 쓰면 A1+A2 또는 B1+B2처럼 적고 결합 후 비용을 다시 본다.

| 보완안 | 기본안의 약점 / 목표 QA | 추가하는 실제 처리와 상태 | 기대 개선과 적용 조건 | 추가 비용 / 다른 QA 영향 |
| --- | --- | --- | --- | --- |
| **A1 원본 crop/cache** | 공동 원본의 반복 입력. QA01/QA03/QA05 | source revision / extent / 입력 조건 / 사용권에 묶인 crop 또는 처리 입력 cache를 추가. 필요한 주변 원본으로 확장하는 경로 유지 | 대상 위치가 안정적이고 같은 원본을 다시 읽을 때 입력 / 준비량 감소 가능. 단순 raw 보존이나 native 선택 사용과 구별 | crop이 관계 단서를 지우면 QA02 회귀. cache key / 무효화 모듈과 local RAM 증가 가능. crop만 적용, cache만 적용, 둘을 함께 적용한 조건을 구별 |
| **A2 부분 binding patch** | 작은 정정에도 현재 요청 전체 재판단. QA01/QA03/QA05 | 표현 / target / 조건의 dependency와 변경 범위를 관리하고 영향 binding만 다시 판단. 영향 범위 불확실하면 전체 재판단 | EX09처럼 P2는 유지하고 표 집합만 바뀔 때 반복 계산 감소 가능. A1을 자동 포함하지 않음 | 영향 범위를 잘못 좁히면 QA02 회귀. dependency / patch 검증과 추가 state의 QA04/QA06 비용 |
| **B1 안정 target 후보 재사용** | 후속 완료 revision마다 같은 화면 후보 재생산. QA01/QA03/QA05 | source revision / extent / coverage / 생산 조건 / 사용권을 검사하는 target candidate cache를 추가. 새 발화와 맞지 않으면 producer 확장 또는 재생산 | EX09-G1처럼 대상과 관측 근거가 안정적일 때 screen 생산을 생략 가능. 한 판단 안의 후보 참조와 구별 | stale 후보와 좁은 coverage가 QA02를 해칠 수 있음. 보존 RAM, 무효화와 producer 계약 변경 비용 |
| **B2 부분 후보 재생산과 결합** | 작은 정정에도 현재 요청의 후보와 결합 전체 재생산. QA01/QA03/QA05 | producer별 candidate dependency와 변경 집합을 관리. 해당 후보만 재생산하고 영향을 받는 binding만 재결합. 불확실하면 전체로 확대 | EX09의 수정 범위가 분명하면 유지 후보 / binding의 계산 감소 가능. 후보 누락 시 원본 확장이라는 기본 기능과 구별 | 누락된 의존 관계와 서로 다른 revision의 조합 위험. QA02 검증, QA04 계약과 QA06 state 비용. B1과 별개 |
| **A3 발화 중 증분 공동 판단** | 완성 입력 뒤 공동 판단이 시작되어 남는 대기. 주 목표 QA01/QA03 | 안정된 부분 입력에서 잠정 binding 생산을 시작. input dependency, coalescing과 revoke / replace를 추가하고 현재 revision만 채택 | 긴 발화에서 앞부분 의미가 안정되고 판단 일부를 실제로 먼저 끝낼 때 종료 후 대기 감소 | 미사용 / 폐기 모델 호출의 QA05와 장기 잠정 state의 QA06 증가. 정정이 잦으면 오히려 지연 / 정확도 손실 |
| **B3 발화 중 증분 후보와 결합** | 완성 입력 뒤 producer와 Resolver 경로가 모두 남음. 주 목표 QA01/QA03 | 표현 / 대상 후보의 잠정 revision을 발화 중 갱신하고 호환 read-set만 결합. revoke / replace와 취소된 후보 전파 | 긴 안정 구간에서 생산과 일부 결합을 앞당길 때 대기 감소. B1/B2를 자동 포함하지 않음 | producer별 폐기 / 재결합의 QA05, queue / 후보 수명의 QA06 증가. 호환 revision 검사와 회귀 부담 |
| **B4 독립 producer 병행** | 기본의 표현 생산 → 화면 생산 순차 대기. 주 목표 QA01/QA03 | 같은 완성 입력에서 독립적인 초기 생산을 병행하고 양쪽 read-set이 준비되면 Resolver 실행. 같은 worker / 호출 예산 유지 | 초기 생산에 상대 producer 결과가 필요 없고 동시 실행 여유가 있을 때 경로 단축 | 동시 staging / decode / 후보 생성으로 QA06 증가 가능. provider 제한이나 공통 queue 포화 시 이익 소멸. 누락 후 재생산 의존까지 없어지지는 않음 |

A1 crop/cache는 원본 취득 권한이나 관측 범위를 확대하지 않는다. B1도 과거 대상 후보를 현재 Action selector로 승격시키지 않는다. 모든 보완에서 원본 / 파생 자료 철회와 현재 revision 검사를 유지한다.

B1과 B2의 재사용 단위도 다르다. B1은 source와 생산 조건이 맞는 기존 target 생산 결과를 조회해 다시 사용하는 cache이며, 표현별 수정 dependency가 없어도 적용할 수 있다. B2는 현재 요청의 후보 / binding state를 이어 가지고 변경 영향을 계산해 일부만 교체하는 방식이다. 바뀌지 않은 상태를 유지하지만, 다른 요청에서도 source key로 후보를 찾아 쓰는 B1 cache를 전제하지 않는다. 둘을 함께 쓰면 B1+B2로 별도 평가한다.

A3/B3는 기본안과 판단 시작 시점이 다르다. 원본 capture 자체를 증분 의미 판단의 이익으로 세지 않는다. partial ASR마다 모델 호출할 의무는 없으며, 합치기와 실행 횟수 한도를 함께 설계한다. Inpro의 commit은 해당 처리자의 가설 확정 표시로만 참고한다. VIA의 영속 채택이나 이후 사용자 정정 금지를 뜻하지 않는다.

B4는 독립 초기 producer의 순차 실행 정책에서 생긴 대기를 줄인다. 후보가 준비된 뒤 결합한다는 의존과 최종 target을 producer가 생산하는 권한은 바꾸지 않는다. 따라서 B 대 B4의 개선량은 이 실행 정책의 보완 효과다. 이와 달리 Resolver가 원본에서 새 target을 직접 만들어 채택하면 A형 경로를 추가한 **혼합 구조**다. 그런 변경은 단순 B4의 성능 이익으로 숨기지 않고 입력, 권한과 유지 비용을 따로 설명해야 한다.

| 긴 안정 발화와 잦은 정정 발화 | 양안 모두 완성 입력 뒤 판단 시작 | A 대 A3, B 대 B3 | 발화 종료 후 대기 감소와 전체 폐기 / 추가 호출을 함께 확인. QA03 시작을 보완의 판단 시작으로 바꾸지 않음 |
| 초기 후보 생산이 독립적인 EX08 | B의 순차 생산 대기 | B 대 B4 | 동일 budget에서 경로 단축이 있는지와 동시 local RAM 증가 확인 |
| EX16-G1 접근 철회 | 공통 권한 확인 | 기본 대 각 cache / 증분 보완 | 원본 외에 새로 생긴 cache / 잠정 후보 / in-flight 자료의 차단이 유지되는지 확인 |

이 과정은 선택한 기본안의 약점을 어느 정도 회복할 수 있는지 보이기 위한 것이다. 보완이 저렴하거나 효과적이라는 이유만으로 그 이전의 기본 구조와 QA 손익이 사라지는 것은 아니다. 반대로 보완 효과도 확인 없이 기본안의 우위로 가져오지 않는다.

## 11. 권고와 확인해야 할 주장

문제 3은 기존 DP-47과 같은 의미 생산 축의 심화 후보로 유지한다. 별도 DP로 중복 계산하지 않는다. 먼저 기본 A/B의 차이와 선택 조건을 설명하고, 선택 후 필요한 보완을 붙이는 방식으로 발전시킨다. 현재 기본안, 보완안과 조합안은 모두 미선정이다.

후속 검증이 허용될 때 다음 주장을 반증 가능하게 다룬다.

1. **A의 짧은 의존 경로:** B의 작은 입력과 저비용 native 생산이 전체 대기를 상쇄하면 A의 단계 수만으로 지연 우위를 주장할 수 없다.
2. **B의 후보 기반 결합 이익:** 같은 판단의 다수 지칭에서도 생산 / 확장 비용이 절감을 넘거나 중요한 단서를 잃으면 전체 비용 / 정확도 이익이 성립하지 않는다.
3. **부분 갱신의 회복 효과:** A2/B2가 반복 계산은 줄여도 수정 범위를 잘못 보존하면 QA02 손실을 함께 기록한다. 기본안과 보완안의 정확도 기준은 같다.
4. **재사용의 회복 효과:** A1/B1이 실제 hit를 얻지 못하거나 source / 권한 변경에서 무효화를 자주 요구하면 기대 비용 절감은 작아진다. 그 결과를 숨기기 위해 반복 장면만 고르지 않는다.
5. **증분 / 병행의 회복 효과:** A3/B3/B4가 추가 호출과 RAM만 늘리고 실제 first-content 또는 endpoint를 앞당기지 못하면 해당 보완의 선택 이유가 약해진다.
6. **공통 capability 한계:** 양안이 같은 API 한계로 중요한 장면을 해결하지 못하면 이를 구조의 우열로 숨기지 않는다. 기능 중요성과 QA 차별화 확인을 구별한다.

공통 source와 완료 조건을 유지한 명시 선택, 이동 / 집합 지칭, visual 후보 누락, 반복 / 부분 정정, 모호함과 gap을 함께 다룬다. QA의 정의나 모집단을 바꿔 기본안 또는 보완의 차이를 만들지 않는다. 이 문서는 비교 구조와 검증할 이유를 정리했으며 PoC, 모델 실행, 측정 freeze나 새로운 점수를 만들지 않았다.

## 12. 조사 범위와 이번 개정의 한계

- 직접 읽은 공개 코드: Magentic-One, OpenHands, OpenClaw, Google Live Console, OmniParser, Psi와 ReTiCo의 고정 commit 경로. 직접 읽은 원 논문: QuickSet §3과 InproTKS §2–5.
- 공식 구현에서 확인한 입력 / 생산 / 결합 방식과 VIA가 추가한 시간 지칭 / 정정 계약을 구별했다. 공개 코드 존재가 Windows 앱이나 한국어 지칭에서의 성능을 대신하지 않는다.
- 미확인: 실제 source 노출, cloud media / timestamp capability, 대상 집합의 성공, 호출 / queue / local RAM과 전체 모델 비용. QA 우위는 구조에서 예상한 가설이다.
- 이번 개정은 조사된 근거를 유지하면서 기본 비교와 선택 후 보완을 분리한 것이다. 기존 DP-47의 본문 / 그림, 승인 상태와 reference Architecture는 변경하지 않는다.

## 13. 2026-10-17 설계 권고

### 13.1 설계는 A를 추천하고 DP 자격은 조건부로 남긴다

**추천은 기본 A 원본 공동 해석이다.** 원본 보존과 채택 계약을 갖춘 A에서 출발하고, 선택 후 A1과 A2로 반복 입력과 부분 정정 비용을 줄이는 설계가 현재 VIA 요구에 가장 타당하다. 이것은 정확도 우위를 측정했다는 결론이 아니라 다음 설계 근거에 따른 추천이다.

**기능의 중요성과 현재 A/B 비교의 주요 DP 적합성은 구별한다.** 이 기능은 반드시 설계해야 하고 A/B의 생산 권한도 실제로 다르다. 그러나 같은 cloud 모델을 쓰며 원본도 유지하는 기본 B가 A보다 얻는 정상 사용의 반대편 이익은 아직 충분히 뒷받침되지 않는다. 후보가 작다는 것만으로 전체 모델 비용이 줄지 않으며, 후보를 명시했다는 것만으로 정확도나 실제 변경 모듈 수가 개선되지도 않는다. 따라서 지금은 **기본 A의 설계 권고까지 내리고, 현재 A/B를 주요 DP로 확정할 근거는 부족하다고 판단**한다. B1/B2의 보완 효과를 기본 B의 이익으로 옮겨 이 빈칸을 채우지 않는다.

1. VIA가 받아야 할 지칭 범위는 앱의 native 객체 목록으로 고정되지 않는다. figure 내부의 두 graph, click 없는 원형 집합과 “아니 아래 것만”처럼 **언어가 visual 범위와 동작의 의미를 바꾸는 요구**가 이미 있다. A는 같은 의미 책임이 이 원본에서 새 target을 직접 만들 수 있다. B는 이런 요청도 지원하지만, 기존 후보에 범위가 없으면 원 producer의 확장과 재결합을 거쳐야 한다.
2. 현재 요구는 화면 전체의 독립된 의미 목록을 계속 게시하는 것이 아니라 현재 요청의 지칭을 해결하는 것이다. A는 이 출력까지 직접 진행한다. B의 별도 표현 / 대상 / 결합 계약과 유지 상태는 필요한 단서를 충분히 압축하거나 반복 결합을 줄일 때 가치가 생긴다. 그 대가를 처음부터 모든 요청의 필수 경로로 둘 근거는 현재보다 더 강해야 한다.
3. A도 한 발화의 여러 표현을 한 공동 입력에서 함께 판단할 수 있다. 따라서 B의 후보 재사용만 보고 A가 같은 image를 표현 수만큼 전송한다고 가정하지 않는다. 아래 식처럼 기본 A와 B의 실제 입력과 모든 생산 비용을 비교하면 A를 출발점으로 두고 필요한 반복 계산부터 보완하는 편이 설계상 합리적이다.

B의 초기 생산을 일부러 순차 실행한 것만으로 A를 추천하지 않는다. **두 producer를 병행한 B4에서도 생산된 후보를 결합하고, 부족하면 producer로 돌아가는 의존은 남는다.** 반대로 병행과 충분한 후보 덕분에 B가 실제로 더 빠르고 정확하다면 추천을 바꾼다. B의 구조를 유지하는 정상 구현이며 불리한 우회안으로 취급하지 않는다.

공동 원본 공급은 [WebSurfer 코드](https://github.com/microsoft/autogen/blob/027ecf0a379bcc1d09956d46d12d44a3ad9cee14/python/packages/autogen-ext/src/autogen_ext/agents/web_surfer/_multimodal_web_surfer.py)와 [Google Live Console](https://github.com/google-gemini/live-api-web-console/blob/0a4542fe0e39d07956ea7af5de45d7c81fde8960/src/components/control-tray/ControlTray.tsx)에서, 별도 부분 의미와 결합은 [QuickSet 원 논문 §3](https://aclanthology.org/P97-1036.pdf)과 [OmniParser의 생산 API](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/omnitool/omniparserserver/omniparserserver.py)에서 다시 확인했다. 이들이 VIA의 temporal binding이나 후보 확장 정확도까지 구현했다는 뜻은 아니다. [이번 재확인 원장](../../../../../references/five-problem-study/grounding-recommendation-check-20261017.md)에 사실과 설계 추론을 나눴다.

### 13.2 B의 다수 표현 재사용 이익과 전체 비용

같은 화면에서 “이 표는 유지하고, 이 두 그래프를 비교해줘. 그중 오른쪽 그래프에는 제목도 붙여줘”라고 하며 세 영역을 순서대로 가리키는 장면을 보자. 정답 영역은 평가기에만 두고 해석 입력에 미리 주지 않는다. 실제 제목 작성은 이 지칭 해석 뒤 Downstream Agent가 맡는다.

- **A:** 원본 관측 구간과 완성 발화를 공동 입력 한 번으로 제공해 유지 대상, 비교 집합과 제목을 붙일 대상을 함께 만들 수 있다. 관계별로 원본을 새로 입력할 의무가 없다. 다만 원본 범위가 크거나 공동 판단을 반복하면 그 입력과 판단 비용을 부담한다.
- **B:** 화면 생산자가 만든 표와 graph의 후보를 유지 / 비교 / 제목 지정 표현이 같은 read-set에서 참조한다. 후보가 충분하면 결합자가 작은 후보 자료로 비교 집합의 오른쪽 graph가 제목 지정의 대상과 같은지 판단할 수 있다. 원본 화면을 결합 단계마다 다시 생산하지 않아도 된다. 이것은 **현재 판단 안의 기본 재사용**이며 후속 요청의 B1 cache와 다르다.
- **B의 비용:** 초기 화면 / 표현 후보 생산, 출력 직렬화와 결합 입력이 추가된다. “오른쪽 것”이 기존 figure 내부의 일부라면 producer가 원본을 다시 읽어야 한다. 후보 조합이 많아지거나 필요한 관계를 표현하지 못하면 작은 입력이라는 이익도 줄어든다.

다음은 모델의 내부 계산량을 주장하는 수식이 아니라 **관찰할 처리 항목의 합**이다. `R`은 실제 사용한 화면 / 동작 원본, `U`는 발화, `m`은 지칭 표현 수, `C`와 `S`는 화면 / 표현 후보다. `cost`는 해당 처리에서 발생한 VIA 모델 비용이며 모델 없는 처리는 모델 비용이 0이다.

```text
기본 A 비용 = cost(Joint(R, U, m)) + A의 추가 조회 / 재판단 비용
기본 B 비용 = cost(Screen(R)) + cost(Speech(U))
            + cost(Bind(C, S, m)) + B의 확장 / 재결합 비용

A의 판단 경로 = Joint 시간 + 필요한 후속 재판단 경로
B4의 판단 경로 = max(Screen 시간, Speech 시간)
               + Bind 시간 + 필요한 확장 / 재결합 경로 + 실제 조정 대기
```

B4 식은 같은 예산에서 두 생산자가 실제로 병행될 수 있을 때다. 제한된 worker와 cloud queue로 겹치지 못한 시간도 기록한다. A의 원본 입력 비용은 0으로 두지 않고, B의 producer 비용도 Resolver 밖이라는 이유로 빼지 않는다.

**표현 수 `m`이 늘었다는 사실만으로 B가 저렴해지는 것은 아니다.** A가 공동 호출 한 번에 해결한다면 B의 후보 입출력이 오히려 추가 비용일 수 있다. B의 전체 이익이 생기려면 작은 후보에서의 관계 판단 절감, native 자료의 저비용 후보 생산 또는 원본 재판단 감소가 생산 / 교환 / 확장 비용보다 커야 한다. 같은 revision에서 B가 여러 번 결합할 때 후보를 재사용하는 이익은 있지만, A도 이미 생산한 binding만으로 후속 검토가 충분하다면 원본 재전송을 강제하지 않는다. 실제 경로를 기록해 이 조건을 판별한다.

### 13.3 추천에서 감수하는 QA 상충

검토할 축은 **QA02, QA03, QA05와 QA06**이다. QA01은 별도 첫 표시 경계를 유지하되 QA03과 같은 지연을 독립 이익으로 합산하지 않는다. 아래는 설계상 손익과 반대안이 유리할 조건이며, 기본 A/B가 네 축에서 대립 이익을 확보했다는 뜻은 아니다. 특히 기본 B의 정확도 / 총비용 / RAM 이익은 조건부 가설이다. 이 한계가 현재 주요 DP 확정을 권고하지 않는 이유다.

| QA | A를 추천하면서 기대하는 점 | A가 감수할 비용과 B가 유리할 조건 |
| --- | --- | --- |
| **QA02 지칭 대상 정확도** | 후보에 없던 범위도 원본과 언어를 함께 보고 직접 제안할 수 있음. 중간 후보의 표현 범위를 최종 지칭의 필수 제한으로 두지 않음 | 공동 판단이 여러 표현 / 동작을 혼동할 수 있음. B의 후보가 충분하고 관계 제약이 명시적이면 더 안정적일 수 있음. **A의 정확도 우위는 미확인**이며 B의 채택 전 확장도 정상 성공으로 인정 |
| **QA03 VIA 처리시간** | 원본에서 binding까지 직접 진행하고 필요한 범위 확장도 같은 의미 책임에서 처리 | 큰 media의 공동 판단이 길어질 수 있음. B4의 병행 생산과 작은 결합이 이보다 짧으면 B 유리. 정정에서 A 전체 재판단이 반복되는 비용도 포함 |
| **QA05 전체 VIA 모델 비용** | 별도 후보 출력과 결합 입력을 모든 요청에 요구하지 않음 | 공동 입력이 크고 재판단이 반복되면 A 비용 증가. B의 native 생산, 충분한 후보와 반복 결합이 실제로 원본 처리를 줄이면 B 유리. source 생산 / 폐기까지 같은 비용 경계 적용 |
| **QA06 최대 local RAM** | 별도 producer 후보와 교환 state를 필수로 유지하지 않음 | A의 공동 media decode / staging이 커질 수 있음. B가 compact reference와 단계별 수명을 잘 사용하면 더 작을 수 있음. 두 안 모두 원본을 보존하며 512 MB 요구 유지 |

A1은 입력량과 준비 비용을 줄일 수 있지만 cache RAM과 무효화 책임을 늘린다. A2는 정정 비용을 줄일 수 있지만 잘못 좁힌 변경 범위가 QA02를 해칠 수 있다. 따라서 **정확성 유지와 지연 / 비용 절감, 로컬 상태 증가 사이의 상충**을 기본안과 보완안에서 각각 보인다. QA06 차이가 작으면 그 사실을 남기며 네 번째 차이를 억지로 만들지 않는다. QA04는 C03/C05/C06 변경 경로를 검토하되 실제 Rust 모듈 변경 없이 우위를 점수화하지 않는다.

### 13.4 B를 추천할 조건과 추천 보완 두 개

B를 선택할 조건은 다음처럼 구체적이다. 단순히 지칭 표현이 많거나 모듈이 나뉜다는 것만으로 충분하지 않다.

1. 같은 관측 구간의 native / visual 후보가 여러 표현의 범위와 관계를 실제로 포괄하며, 원본 확장 빈도가 낮다.
2. 표 / chart / 선택 범위의 구조가 안정적이고 생산이 저렴해, 후보 생성과 결합의 전체 비용이 A 공동 판단보다 작다.
3. 같은 입력에서 후보 관계를 이용한 B의 최종 target 집합이 A보다 안정적이고, 그 이익이 지연 / 비용 / RAM 부담을 정당화한다.
4. 특히 기본 A가 큰 공동 입력에서 반복 오류나 재판단을 일으키는데 기본 B가 충분한 후보로 이를 피하고 비용을 감수할 이익을 보이면 **기본안 추천을 B로 변경**할 수 있다. 그 뒤 A1/A2와 B1/B2의 효과는 보완 구성으로 별도 비교한다. 기본 B가 보완된 A까지 이겨야만 기본안 추천을 바꿀 수 있다는 조건을 두지 않는다.

현재 추천할 보완은 다음 **두 개**다. 실제 적용이나 측정 완료를 뜻하지 않으며, 먼저 A 대 A1과 A 대 A2를 따로 본 뒤 A1+A2를 확인한다.

| 추천 보완 | 우선 도입할 설계 | 목표와 대가 |
| --- | --- | --- |
| **A1 crop/cache** | 실제 관측한 범위에서 주변 문맥을 포함한 crop을 만들고, source / extent / revision / 권한을 key로 준비된 입력을 재사용. 전체 원본 확장과 bounded eviction 유지 | QA03/05의 반복 입력 부담을 줄이는 목적. crop 준비 cache만으로 cloud 입력 요금이 줄었다고 세지 않음. 실제 전달 image 범위 감소나 provider가 관측한 cache 적용이 있어야 그 모델 비용 절감을 기록. QA02의 관계 단서 손실과 QA06 증가 확인 |
| **A2 부분 binding patch** | 현재 채택 binding과 원본 dependency를 기준으로 정정 영향 범위를 제안하고, 영향을 받은 binding만 재판단. 영향 불명 / 교차 관계 변경이면 전체로 확대 | EX09의 표 집합 변경에서 유지 문단까지 재생산하는 비용을 줄이는 목적. 코드가 의미 변경 범위를 임의 확정하지 않음. 유지된 binding의 QA02와 dependency 관리 / RAM 비용 확인 |

**증분 판단은 이번 우선 보완에 넣지 않는다.** A3/B3 모두 가능하며 긴 안정 발화의 이익과 잦은 정정의 폐기 비용을 확인한 뒤 별도 선택할 수 있다. [InproTKS §2](https://aclanthology.org/W14-4312.pdf)의 수정 가능한 가설은 그 설계 참고이며, VIA의 영속 채택이나 원본 동기화를 자동 제공하지 않는다.

### 13.5 동일 입력 bounded PoC 제안과 추천 반증

후속 실행 승인이 있을 때, 제품 전체나 여러 Agent의 실제 업무를 만들지 않고 **원본 replay → binding 제안 → revision 채택 → 최소 Request UI 표시**만 비교하는 PoC를 제안한다. 아래 숫자는 작업량 상한 제안이며 QA 목표, 점수 또는 모집단 freeze가 아니다. 지금은 입력 생성, 모델 호출과 제품 실행을 하지 않았다.

- **입력 상한:** 6개 장면군의 2개 변형, 총 12개 고정 episode. episode별 최대 2개 발화, 6개 보존 frame과 발화당 4개 지칭 표현으로 제한한다. 실제 관측 시각 / 오차 / 공백과 실제 초기 selection을 같은 순서로 재생한다. oracle target과 수정 범위는 평가기에만 둔다.
- **비교 구성:** 기본 A, 기본 B, B4, A1, A2, A1+A2의 6개. 기본 A/B의 표를 먼저 작성하고 보완별 열을 분리한다. 각 episode 2회 반복이면 최대 144 episode 실행이며, 정정 / 확장 호출은 해당 episode의 비용에 포함한다. 이는 효과와 실패 경로를 찾는 작은 범위이며 통계적 우위의 증명은 아니다.
- **공정 조건:** 동일 모델 capability, 원본, capture 품질, 완성 입력 trigger, 권한, 최종 deadline과 총 실행 예산을 사전에 고정한다. 필요한 기본 단계 수가 다른데 모델 호출 수만 같게 잘라 B를 실패시키지 않는다. 반대로 B4에만 추가 worker budget을 주지 않는다. 어느 안도 미래 입력이나 정답 target을 받지 않는다.
- **재사용 조건:** 입력 cache가 없는 기본 비교, 초기 cache 준비 비용을 포함한 A1, episode 안의 실제 후속 재사용을 분리한다. 다른 평가 episode에서 얻은 정답이나 의미 결과를 다음 episode에 넘기지 않는다. 기본 B의 한 판단 내 후보 재사용은 그대로 허용한다.

| 장면군 | 두 변형의 목적 | 확인할 구조적 주장 |
| --- | --- | --- |
| 명시 선택 | native 범위가 충분한 경우 / 화면은 같지만 native 범위가 제공되지 않은 경우 | 쉬운 경로의 동점과 visual 판단 비용. 없는 native target을 양안에 만들어 주지 않음 |
| 이동과 원형 집합 | 두 대상 지칭 뒤 화면 전환 / 원형 집합 뒤 page drag | 당시 원본 사용과 navigation 구별. 마지막 frame만 사용하는 실패를 A/B 차이로 만들지 않음 |
| 같은 화면의 복수 표현 | 두 표현 / 네 표현의 유지, 비교와 제목 지정 관계 | A 원본 한 번 입력과 B 후보 한 번 생산의 실제 비용. B의 후보 재사용을 표현 수만큼의 image 절감으로 가정하지 않음 |
| 언어가 범위를 결정 | figure 전체 / 내부 두 graph를 요구하는 발화 | B 후보가 실제 부족할 때만 확장 비용 기록. B에 의도적으로 잘못된 후보를 주입해 정확도 열세를 만들지 않음 |
| 부분 정정 | T1/T2에서 T1/T3로 교체하며 P2 유지 / 새 정정이 기존 집합 전체의 의미를 바꾸는 경우 | A2의 절감과 전체 확대 조건. 기본 B의 새 후보 생산 비용도 포함 |
| 근거와 권한 변화 | 모호함 / frame gap이 있는 입력 / 유효 원본 사용권 철회와 늦은 결과 | 정당한 확인, 미해결과 현재 revision 채택. 회복할 수 없는 과거를 새로 만들어내지 않음 |

QA02는 지정 표현 / revision의 최초 채택 target 집합으로 판정하고, 후속 수정이 앞선 오류를 지우지 않는다. 실제 모호함과 관측 부족의 별도 oracle을 사전에 정하며, 해결 가능한 대조 입력에 불필요한 질문을 성공으로 세지 않는다. QA01은 실제 UI 표시를 관측할 때만 부르고, 모델 반환 시각만 있다면 진단값으로 남긴다. QA03은 실제 발화 종료 뒤 공통 입력 확정 대기부터 기존 endpoint까지의 VIA 인과 경로를 유지한다. 외부 업무 시간을 끌어와 차이를 만들지 않는다.

PoC의 episode별 비용은 준비 / 재판단 / 폐기와 cache 비용을 모두 포함한 **비용 진단**이다. 이 12개 입력을 전체 COMMON-28의 QA05 결과로 바꾸지 않는다. local 최대 RAM도 buffer / decode / staging / 후보와 cache를 함께 관측한다. QA04의 실제 운영 Rust 변경 평가는 이 작은 mechanism PoC 결과로 대체하지 않는다.

이 PoC는 기본 비교의 실질 차이와 추천 A의 약점 회복을 확인하는 범위다. B1/B2까지 최적화한 제품 전체의 최종 우열을 판정하지 않는다. 기본 B의 대립 이익이 확인되면 DP 적합성 판단을 갱신하며, 뒤의 A1/A2가 그 격차를 줄였다는 이유로 기본 trade-off를 없애지 않는다.

**추천을 뒤집는 조건:** 같은 입력의 기본 비교에서 B가 더 정확한 target 집합을 안정적으로 만들거나 다른 적용 QA의 이익을 보이고 그 지연 / 비용 / RAM 부담을 수용할 수 있다면 기본 B를 추천할 수 있다. 기본안 추천 뒤 A1/A2 등의 보완 비교는 별도로 남긴다. B4에서만 이익이 나타나면 그것은 B4 구성의 추천 근거로 기록한다. B4만으로 A의 지연 이익이 사라지면 초기 순차 정책에서 나온 이익을 구조 자체의 이익으로 설명하지 않는다. A1/A2가 QA02 손실, 불필요한 확인 또는 512 MB 초과를 만들면 그 보완을 제거하거나 범위를 좁힌다. 모든 안이 원본 관측 한계로 실패하면 캡처 capability의 공통 문제로 남기며 승자를 만들지 않는다.

**지금의 결론은 ‘이 핵심 기능에는 A를 기본으로 추천하고 A1과 A2를 우선 보완으로 검토하되, 현재 A/B는 조건부 DP 후보로 유지한다’다.** B의 반대편 기본 이익이 같은 입력에서 확인되기 전에는 주요 DP 자격을 충족했다고 하지 않는다. 추천과 PoC 조건은 이번 조사 결과이며, 실제 품질 차이와 사용자 최종 채택은 별개의 단계로 남긴다.
