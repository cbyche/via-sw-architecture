# 문제 2. 앞선 요청을 처리하는 동안 추가 발화와 외부 Agent 통지를 어떻게 처리할 것인가

2026-10-17 / 기본 구조와 선택 후 보완 분리 / **작성자 권고: 기본 B** / 사용자 미채택, 품질 차이 미측정

§1~9는 기본 비교와 보완 후보를 보존한다. 사용자 요청에 따라 도출한 현재 추천, 감수할 비용과 제한된 PoC 설계는 **[§10 설계 권고](#10-2026-10-17-설계-권고)**에 있다. 작성자 추천은 사용자 채택이나 구현 / 측정 승인을 뜻하지 않는다.

## 1. 풀어야 하는 문제와 기본 비교

**VIA가 자료를 읽고 의미를 판단하는 동안 사용자가 질문을 더 하거나 조건을 바꾸면, 새 입력은 무엇을 기다리고 어느 해석 실행에 반영되어야 하는가?** 같은 시점에 외부 Agent가 보낸 진행 통지나 추가 정보 요청도 처리해야 한다. 새 입력에 응답한 뒤에는 원래의 유효한 목표로 돌아갈 수 있어야 한다.

입력을 계속 받는 것과 그 뜻을 즉시 판단하는 것은 다르다. 앞선 VIA 모델 호출이 끝난 뒤 같은 문맥에서 새 입력을 판단할 수도 있고, 별도 요청 실행에서 판단한 뒤 대화에 다시 연결할 수도 있다. 이 실행 의존과 유지 상태를 기본 구조의 차이로 비교한다. VIA의 자료 읽기는 요청 이해를 위한 범위 제한 조회이며, 업무 내부 계획과 실행은 외부 Agent의 책임이다. 외부 업무 완료를 기다리는 시간 자체는 VIA 의미 해석 시간을 점유하지 않는다.

| 기본안 | 핵심 구조와 처리 | 유리한 QA와 이유 | 불리한 QA와 이유 | 유리한 사용 조건 |
| --- | --- | --- | --- | --- |
| **A. 하나의 대화 해석 실행에서 차례로 처리** | 사용자 입력과 의미 판단이 필요한 외부 통지를 같은 실행의 다음 판단에 넣음. 앞서 읽은 근거와 잠정 판단을 계속 활용 | QA05: 문맥 재구성과 실행 간 재판단을 줄일 가능성. QA06: 별도 실행 문맥과 완료 대기가 적음 | QA01/03: 진행 중인 긴 의미 호출이 새 질문의 판단을 늦출 수 있음 | 같은 자료에 대한 연속 요청과 정정이 많고 해석 단계가 짧음 |
| **B. 요청별 해석 실행과 공통 대화 조정** | 긴 요청은 자기 문맥에서 진행. 공통 대화 조정이 새 입력의 관계를 판단해 해당 실행에 보내거나 새 실행을 만듦 | QA01/03: 긴 요청의 완료를 기다리지 않고 독립 질문이나 다른 업무의 통지를 판단할 가능성 | QA05: 문맥 전달과 반환 판단 비용. QA06: 여러 실행의 문맥과 결과를 동시에 유지 | 서로 다른 자료를 이해하는 요청과 추가 질문이 자주 겹치고 호출 여유가 있음 |

표의 방향은 조건부 예측이다. A의 넓어진 문맥을 반복 입력하는 비용이나 B의 좁은 요청 문맥에 따른 절감도 함께 확인해야 한다. **기본 A/B를 먼저 비교하고, 선택한 구조의 약점을 보완할 A1/A2/B1/B2는 §7에서 별도로 비교한다.** 표기와 비교 순서는 [기본 설계와 보완 설계 기준](./07-basic-designs-and-tactics.md)을 따른다. 예전 C였던 제한된 별도 질문은 A1으로 옮겼으며 기본 A에 미리 포함하지 않는다.

## 3. 공통 필수 기능과 기본 구조

### 3.1 모든 안이 지켜야 하는 것

관련 기능은 [대표 UC-01, 06, 09~15, 18](../../../../05-representative-use-cases.md), 품질과 실행 조건은 [공동 조사 기준](./00-research-contract.md)을 따른다. 같은 원본과 권한, cloud 모델, 전체 호출 한도와 로컬 RAM 조건을 사용한다.

1. **수신과 목표 보존:** Interaction Manager는 의미 호출 중에도 입력을 받고 사용자 발화 시작에 음성을 즉시 중단한다. Request Controller는 입력 원문과 revision, 미해결 요청과 질문을 보존한다. 입력에 정답 Task ID를 미리 넣지 않는다.
2. **의미와 실제 전달 구별:** Request Interpreter가 새 요청, 정정, 답변, 취소 관계를 제안한다. Request Controller가 관계를 채택하며 Response Manager는 실제 표시와 음성 전달 범위를 기록한다. 질문이 도착하거나 생성되었다는 사실만으로 사용자가 그 질문에 답했다고 판단하지 않는다.
3. **최신 조건과 권한 확인:** 새 입력의 영향이 아직 불명확하면 관련 미전송 응답과 실행 허가를 보류하고, 해석 뒤 영향 범위를 정한다. 결과가 늦게 도착해도 현재 요청 revision과 권한을 확인한다. 정정 후 이전 조건을 현재 결과로 되살리지 않는다.
4. **외부 업무 사실과 취소 구별:** Task Manager와 Agent Gateway는 확인된 진행과 실행 사실을 보존한다. 음성 중단, VIA 모델 호출 중단, 외부 업무 취소 요청과 외부 종료 확인은 각각 다른 사실이다. 수행 여부가 불명인 외부 Action을 중복 실행하지 않는다.
5. **한도와 복구:** 입력, 실행 수와 대기 결과에 한도를 둔다. 포화 시 입력을 보존하고 대기를 알린다. 재접속 시 State Store의 입력 / 요청 / 질문 / 실행 식별 정보와 외부 상태를 대조한다. 단순한 thread ID나 비동기 함수로 복구가 보장되지는 않는다.

위 조건을 어느 안에서도 빼지 않는다. 반면 별도 질문 경로, 진행 중 모델 호출의 선제 중단, 문맥의 공유 표현과 호출 여유 예약은 보완 기법으로 분리한다. 채택된 조건의 변경과 다른 조건의 보존은 필수이며, 영향받은 부분만 다시 계산하는 최적화와는 구별한다.

### 3.2 A. 하나의 대화 해석 실행에서 차례로 처리

1. 입력과 외부 통지를 먼저 기록한다. 의미 판단이 필요한 항목을 현재 대화 해석 실행의 대기 목록에 넣는다.
2. Request Interpreter는 진행 중인 모델 호출 또는 근거 읽기 단계가 끝나는 경계에서 대기 입력을 읽는다. 기본 A는 새 입력만을 위해 별도 해석 실행을 만들거나 진행 중 호출을 선제 중단하지 않는다.
3. 앞선 근거와 새 입력을 같은 문맥에서 판단한다. 독립 질문이면 원래 목표를 남긴 채 새 질문을 처리하고, 정정이면 해당 요청 조건을 갱신한다. 현재 단계 뒤의 모든 기존 작업을 먼저 끝내야 하는 것은 아니다.
4. Request Controller의 채택과 Response Manager의 실제 전달 뒤 미해결 목표를 이어간다. 외부 Agent의 답이나 사용자의 확인 답변을 기다릴 때는 그 대기를 기록하고 다른 입력을 처리할 수 있다.

**유지 상태:** Request Interpreter의 대화별 해석 문맥 하나에 읽은 근거와 요청별 잠정 판단이 들어간다. Request Controller에는 유효 목표와 채택한 조건이 별도로 남는다. Context Manager의 원본을 다시 읽을 수 있어 문맥을 줄였다는 이유로 목표를 잃지 않는다. A의 핵심 이익은 이 문맥의 연속적 활용이다. 별도 process를 쓰지 않는다는 뜻이나 모든 외부 업무를 동기적으로 기다린다는 뜻은 아니다.

### 3.3 B. 요청별 해석 실행과 공통 대화 조정

1. 입력과 통지를 기록한 뒤, Request Interpreter의 공통 대화 해석이 최근 실제 전달, 활성 요청과 원문을 보고 관계를 판단한다. 짧은 질문은 이 단계에서 답할 수 있다.
2. 긴 근거 조회와 의미 판단이 필요하면 요청별 실행을 만든다. 각 실행은 요청 revision, 필요한 근거, 잠정 판단과 미해결 조건을 가지고 진행한다. 공통 대화 해석은 해당 실행의 완료를 기다리지 않고 다음 입력을 처리한다.
3. 정정은 관계를 판단한 뒤 해당 실행에 전달한다. 그 실행의 다음 판단 경계에서 변경을 반영하고 다른 요청은 유지한다. 첫 판단에서 관계가 불명확하면 입력 ID와 관련 후보를 남겨 추가 근거를 읽는다. 올바른 Task를 미리 알아야 시작할 수 있는 구조는 아니다.
4. 완료는 Request Controller로 돌아온다. 현재 revision과 사용 근거를 대조하고, 필요할 때 Request Interpreter가 최신 대화와 결합해 다시 판단한다. 채택된 결과만 사용자에게 전달한다.

**유지 상태:** Request Controller는 입력과 요청별 실행의 대응을, Request Interpreter는 실행별 문맥을 유지한다. 요청이 끝나거나 답변 대기 상태가 되면 활성 실행 자원은 반환하고 재연결에 필요한 기록은 남긴다. 공통 해석과 여러 요청 실행의 모델 호출은 같은 전체 한도 안에서 경쟁한다. 호출 여유가 없으면 B도 기다리며, 공통 관계 판단 자체가 긴 경우 병목이 될 수 있다. 별도 실행이 추가 모델, 별도 process나 내구 workflow engine을 필수로 요구하지는 않는다.

## 4. 한 사용 장면의 시간 순서

다음은 **EX06의 구체적인 사건 순서이며 실측 시간이 아니다.** 사용자는 두 문서의 비교를 요청했고, 이전에 위임한 메일 작성 Task도 진행 중이다. `R1`, `T1`, `Q1`은 설명용 식별자다. 새 발화가 어느 요청에 연결되는지는 VIA가 판단해야 한다.

| 순서 | 사용자 / 외부에서 생긴 일 | A의 처리 | B의 처리 |
| --- | --- | --- | --- |
| 1 | “D1과 D2를 비교해서 설명해줘.” VIA가 R1의 자료를 읽고 긴 의미 호출을 시작 | 대화 해석 실행이 R1을 처리 | R1 실행이 처리. 공통 대화 조정은 다음 입력을 받을 수 있음 |
| 2 | 사용자가 “비용 부분만 설명해줘”라고 후속 정정 | 입력을 보존하고 관련 미전송 결과를 보류. 진행 중 호출의 경계 뒤 같은 문맥에서 정정을 판단 | 공통 대화 해석이 R1 정정인지 판단해 변경을 전달. R1의 진행 중 호출 자체는 기본 B에서도 즉시 종료되지 않음 |
| 3 | 메일 Agent가 T1에 대해 “받는 사람은 누구인가요?”를 보냄 | 외부 사실은 바로 기록. 의미 처리가 필요하면 같은 대화 해석의 다음 판단에 반영 | 외부 사실은 바로 기록. 공통 대화 조정이 R1 완료를 기다리지 않고 질문을 처리할 수 있음 |
| 4 | VIA가 정정과 Agent 질문을 판단하고 “메일을 누구에게 보낼까요?”를 제시. 처리 순서는 오른쪽처럼 달라짐 | **진행 중 R1 호출 종료 → 이전 결과 보류 → 정정과 Agent 질문 판단 → Q1 실제 제시** | 호출 여유가 있으면 **공통 해석에서 정정과 Agent 질문 판단 → Q1 실제 제시**. 이때 R1 호출은 아직 진행 중일 수 있음 |
| 5 | Q1을 실제로 받은 사용자가 “김 대리에게”라고 답함 | Q1의 실제 전달과 R1 정정을 같은 문맥에서 보고 답변 관계를 판단 | 공통 대화 해석이 Q1 답변으로 판단해 T1에 연결. R1의 비용 조건을 바꾸지 않음 |
| 6 | 남아 있는 R1 처리를 비용 범위에 맞춰 이어감 | 4번에서 보류한 결과를 그대로 현재 답으로 게시하지 않고, 최신 범위에 맞는 판단을 준비 | 이전 조건의 호출이 반환될 때 revision을 확인. 4/5번보다 늦게 반환돼도 현재 답으로 자동 채택하지 않음 |

4번의 실제 표시 시각은 대안마다 달라질 수 있다. 5번 입력은 각 안에서 Q1을 실제 제시한 뒤 발생하는 같은 사용자 행동으로 둔다. 이미 늦은 결과를 금지하는 기능은 공통이며, **새 정정과 질문을 의미적으로 처리하기 전에 무엇을 기다리는가**가 비교 대상이다.

## 5. 네 가지 공통 시나리오

같은 원본, 요청 목표, 진행 중 호출과 입력 순서를 제시한다. 아래 장면은 사고 실험이며 평가 모집단이나 수치 목표를 확정하지 않는다. A1/A2/B1/B2의 효과는 이 기본 비교에 포함하지 않는다.

| 장면과 같은 완료 조건 | 기본 A | 기본 B | 확인할 trade-off |
| --- | --- | --- | --- |
| **S1. 긴 VIA 판단 중 짧은 독립 질문** (EX05): 문서 비교 중 “UDP는 언제 써?” → 새 답과 원래 비교 모두 유지. 실행 중 판단이 없는 쉬운 후속 질문(EX01)을 대조 장면으로 포함 | 다음 판단 경계에서 새 질문에 답하고 비교를 이어감 | 요청 실행과 별개로 공통 대화 해석에서 답할 수 있음 | 긴 선행 판단의 대기 대 별도 문맥 준비 / 호출 경쟁. 쉬운 대조 장면에서는 차이가 작거나 없을 수 있음 |
| **S2. 다른 자료를 읽는 새 요청** (EX05 변형): D1 설명 준비 중 “D2의 결론도 설명해줘” → 두 목표를 유지하며 각각의 자료에 근거해 답 | D1 잠정 상태를 남기고 같은 실행이 D2를 읽고 판단한 뒤 미해결 목표를 이어감 | D2 요청 실행을 추가해 서로 독립적인 VIA 읽기와 판단을 진행할 수 있음 | B의 진행 중첩 가능성과 추가 실행 문맥 / 반환 비용. 같은 호출 예산이 포화되면 이익 감소 |
| **S3. 정정, 다른 업무의 질문과 짧은 답** (EX06/09): §4의 순서. “표만 바꾸고 문단은 유지”도 같은 범위 보존 조건으로 포함 | 이미 읽은 근거와 모든 후속 입력을 같은 문맥에서 판단 | 요청 변경과 질문 답변을 공통 대화에서 연결한 뒤 해당 실행에 전달 | A의 문맥 연속성 대 B의 관계 전달과 실행별 격리. 관계 오류와 지칭 대상 오류는 별도로 판정 |
| **S4. 특정 업무의 취소 발화 수신 뒤 늦은 통지** (EX07/17): 사용자의 T1 취소 발화를 수신한 뒤 진행 / 결과 / 취소 확인이 도착하고 T2는 계속됨. 외부 cancel 전송과 종료 확인은 별도 사건. 연결 중단 뒤 복귀 변형도 포함 | 취소 관계를 같은 실행에서 판단. 외부 사실과 현재 결과 효력을 구별하며 T2 목표 유지 | 해당 실행에 취소 관계를 전달하고 다른 실행 유지. 완료 반환에서 현재 상태 대조 | B의 실행 대응 / 복구 기록 비용과 A의 같은 문맥 처리 대기. 외부가 확인하지 않은 종료나 복구를 양안 모두 주장하지 않음 |

상태 코드만으로 올바르게 표시할 수 있는 단순 진행 통지는 양안 모두 공통 코드 경로를 사용할 수 있다. 모든 통지에 모델 호출을 강제해 차이를 만들지 않는다. 통지의 자유문 의미, 다른 요청과의 관계 또는 사용자 답변을 해석해야 하는 경우가 본 비교에 해당한다.

QA01의 일반적 접수 인사는 내용 응답으로 세지 않는다. 오답의 실제 지연과 미응답 실패도 보존한다. QA03은 상세 표시와 전체 음성 요약 준비를 포함하는 공동 경계를 유지한다. QA01과 QA03의 겹친 구간을 독립적인 두 시간 절약으로 합산하지 않으며, QA05의 외부 Agent 내부 비용은 별도다. QA07~09의 우선도가 낮아도 필수 기능을 없애지 않는다.

**신규 후보 N-R 요청 관계 연결 정확도**는 입력 revision의 최초 관계 채택이 독립적으로 정한 허용 관계 집합과 일치하는 비율이다. 독립 요청, R1 정정, 실제 제시한 Q1의 답변, T1 취소를 구별하되 대상 문서나 화면 영역의 값은 QA02로 남긴다. 시간 초과와 불필요한 확인 질문을 성공으로 처리하지 않는다. [공통 후보 정의](./06-qa-candidates-and-coverage.md#4-신규-후보-n-r-요청-관계-연결-정확도)를 따르며 A/B의 정확도 우위는 미확인이다.

문제 4/5에서 최초 관계 채택 이후의 인계나 Agent 선택만 바꾸면 N-R 차이는 없다. 같은 관계 오류가 잘못된 인계로 이어져 N-H도 실패한 경우에는 두 관측의 인과를 기록하고 독립적인 두 이익으로 합치지 않는다.

**기본안 예측의 반증:** 같은 조건에서 B의 문맥 준비와 호출 경쟁 때문에 새 질문의 실제 첫 표시가 빨라지지 않는다면 QA01 이익 주장을 철회한다. 반대로 A의 복합 문맥 반복이 B의 분리 / 재연결 비용보다 크다면 A의 QA05 이익 주장을 철회한다. 기본 차이가 존재하더라도 그 크기가 중요한지는 미확인이다. 보완 가능성만으로 이 기본 비교를 없애지는 않는다.

## 7. 선택 후 약점을 줄일 보완 후보

각 번호는 기본안에 **해당 기법 하나를 추가한 안**이다. A2가 A1을 포함하지 않으며 결합은 A1+A2로 따로 표시한다. 아직 어떤 기본안이나 보완안도 선택하지 않았고, 아래 모든 개선량과 before/after 값은 미측정이다.

| 보완안 | 기본안의 단점과 목표 QA | 추가 구조와 처리 | 예상 개선과 추가 비용 | 검증 조건과 비교 대상 |
| --- | --- | --- | --- | --- |
| **A1. 읽기 전용 별도 질문** | 긴 판단 때문에 간단한 독립 질문도 기다림. QA01/03 | 주 실행을 유지하고 작은 대화 snapshot으로 도구 없는 별도 답을 생성. 근거 부족이나 정정이면 원문을 A의 주 실행에 전달. 실제 표시한 답은 공통 대화에 기록 | 제한된 질문의 대기를 줄일 가능성. 별도 호출과 snapshot의 QA05/06 비용, 잘못 분류한 답 또는 A로 돌아가는 추가 대기 | **A 대 A1.** 이미 가진 근거로 답할 수 있는 질문과 추가 자료 / 정정이 필요한 질문을 모두 포함. 자동 독립성 판정과 동일 호출 예산을 확인 |
| **A2. 영향받은 모델 호출 중단과 재개** | 정정이 들어와도 현재 호출 경계를 기다림. QA01/03 | 입력을 보존한 뒤 영향받은 호출에 취소를 요청하고 최신 입력으로 다시 판단. 실제 호출 종료와 자원 반환을 확인 | 남은 호출 대기를 줄일 가능성. 취소 정리, 폐기 토큰과 재입력의 QA03/05 비용. 외부 업무 취소는 별도 | **A 대 A2.** 호출 초반 / 후반 정정, 독립 질문, 취소 지연과 실패를 포함. provider가 실행 중 호출을 실제로 종료하는 범위 확인 |
| **B1. 변하지 않는 문맥의 참조 공유** | 요청마다 복사한 대화 / 근거 문맥으로 RAM 증가. 주로 QA06 | 공통 불변 문맥 조각을 한 번 보유하고 각 실행은 참조와 변경분을 유지. version과 사용 권한, 참조 수명 관리 추가 | 로컬 중복 buffer를 줄일 가능성. 직렬화와 참조 해제 / 철회 처리 비용. 로컬 공유만으로 cloud 입력 토큰이나 QA05가 줄지는 않음 | **B 대 B1.** 같은 근거를 쓰는 복수 요청과 서로 다른 근거 요청, 큰 입력의 직렬화 peak를 포함. 전체 최대 RAM과 QA03 재구성 비용 확인 |
| **B2. 새 사용자 입력을 위한 호출 여유 예약** | 긴 요청들이 한도를 차지해 공통 대화 해석도 기다림. QA01 | 같은 총 호출 한도 안에서 새 입력 처리용 여유를 남기고 요청 실행의 시작 수를 제한 | 공통 관계 판단의 시작 대기를 줄일 가능성. 배경 요청의 시작 / 완료가 늦어지고 예약이 비는 시간 발생 | **B 대 B2.** 독립 질문이 잦은 경우와 드문 경우, 정정 burst를 같은 전체 예산으로 비교. QA01 개선과 QA03의 원래 요청 지연을 함께 확인 |

A1의 근거인 Deep Agents Btw는 사용자가 명시적으로 여는 별도 질문 경로다. 자연어를 자동 분류해 보내는 기능은 VIA의 추가 설계다. 별도 답이 틀린 관계를 전제로 생성되었다면 단순 revision 검사로 의미 오류가 해결되지는 않는다. A1에 장기 읽기, 독립적인 변경 처리와 지속 실행을 추가하면 B의 핵심 구조로 접근하므로 작은 보완으로 숨기지 않는다.

A2에서 입력과 요청의 관계가 아직 불명확하면 현재 판단을 잠정 중단해 새 입력을 해석할 수 있다. 이후 독립 질문으로 판명되면 원래 목표와 근거를 보존해 재개하며 그 비용도 센다. 입력 수신만으로 특정 Task의 취소나 변경 관계를 이미 안다고 전제하지 않는다.

A2의 호출 중단과 B2의 예약은 다른 기본안에도 적용할 수 있는 기법이다. 적용할 때는 그 기본안의 별도 보완 번호와 비용을 기록한다. A1과 A2를 결합해도 이익을 단순 합산하지 않는다. 보완 후에도 모든 입력 보존, 실제 전달, 권한과 중복 방지 조건은 동일하다.

## 8. 실제 harness에서 가져온 근거와 적용 한계

공식 코드의 고정 commit, 함수와 줄 번호는 [소스 원장](../../../../../references/five-problem-study/continuous-interaction.md)에 보존했다. 다음은 확인한 메커니즘과 이 설계의 대응이다. 제품 전체가 A 또는 B라는 분류는 아니다.

| 구현에서 확인한 메커니즘 | 이번 기본안 / 보완에 준 근거 | VIA에 별도로 필요한 것과 한계 |
| --- | --- | --- |
| **OpenClaw**: session lane과 같은 run steering, 실행 중 도구 뒤 입력 반영, 불가 시 followup | A의 같은 문맥 활용과 실제 입력 반영 경계 | 실행 중 도구의 즉시 중단을 뜻하지 않음. 입력 저장과 queue의 재시작 replay도 다름 |

| **OpenHands SDK / Agent Server**: 입력 기록과 실행 분리, I/O 중 lock 해제, ACP prompt supersede와 재실행, 실제 실행 종료 전 permit 보존 | 공통 비동기 수신과 A2의 중단 / 재개 비용 | ACPAgent 경로를 모든 Agent로 확대하지 않음. waiter 취소가 sync worker 종료나 외부 Action 취소를 보장하지 않음 |

| **Deep Agents Btw**: 도구를 제거한 별도 답변과 읽기 전용 snapshot | **A1**의 제한된 별도 질문 | 원본은 main checkpoint에 쓰지 않음. VIA는 실제 전달한 답과 지칭 근거를 대화 원본에 남겨야 함 |
| **AutoGen Magentic-One**: 결과 반영 뒤 progress ledger 판단과 다음 참가자 한 명 지정 | A와 같은 문맥에서 결과를 보고 다음 처리를 정하는 의존의 참고 | async event만으로 동시 사용자 개입을 입증하지 않음. domain 계획은 VIA로 가져오지 않으며 save/load가 외부 실행의 중복 없는 복구를 증명하지 않음 |
| **CrewAI**: async Task의 join, 새 conversational turn에서 일시 실행 추적 초기화와 대화 이력 보존 | 실행의 병렬성과 결과 대기, 대화 기록과 일시 상태 수명의 구별 | async 함수만으로 독립적인 대화 해석을 주장하지 않음. 같은 Flow에 동시 사용자 turn이 안전하다는 보장은 이번 범위에서 미확인 |

`steer`, `interrupt`, `followup`은 실행 변경 정책이므로 각각을 독립 DP로 늘리지 않는다. 모든 입력마다 원래 목표를 버리는 방식도 대안으로 두지 않는다. 중앙 dispatcher와 Stage 연결은 [기존 DP-44](../../04-44-continuous-interaction.md)의 다른 축이며 그 문서를 이번 개정으로 교체하지 않는다.

## 9. DP 후보 권고와 다음 판단

**문제 2는 주요 DP 후보로 유지한다.** 길게 진행 중인 VIA 의미 판단과 새 입력의 실행 관계를 바꾸므로 기본 A/B에서 QA01/03/05의 손익을 설명할 수 있다. QA06은 추가 상태의 실제 크기를 확인해야 하며, QA02와 QA04에 차이가 있다는 결론은 아직 없다. 모든 QA를 억지로 차별화하지 않는다.

다음 판단 순서는 기본 A/B의 사용 조건과 감수할 비용을 검토하고, 선택한 기본안의 약점에 필요한 보완만 적용한 뒤 같은 QA로 다시 비교하는 것이다. A1을 미리 포함한 A만을 기본 B의 비교 대상으로 삼는 이전 의무는 적용하지 않는다. 새 DP 번호, 기본안 선택, 보완 적용이나 측정 승인을 이 문서가 대신하지 않는다.

문제 1은 각 실행에 공급할 근거, 문제 3은 발화와 화면 원본의 보존 / 결합을 다룬다. 본 비교는 그 입력 조건을 동일하게 두고 실행과 대기를 바꾼다. 문제 4의 인계 내용 생산, 문제 5의 Agent 적합성 판단을 이 문제의 이익으로 선점하지 않는다.

이번 개정은 기존 공식 코드 조사 결과를 기본 구조와 보완으로 다시 정리한 문서 작업이다. 자동 관계 판단, provider 취소 지연, 실제 RAM과 QA 우열은 검증하지 않았다. 구현, harness / 모델 실행과 성능 측정, commit / push는 수행하지 않았다.

## 10. 2026-10-17 설계 권고

### 10.1 DP로 남기고 기본 B를 추천한다

**이 문제를 주요 DP로 유지하고, VIA에는 기본 B인 ‘요청별 해석 실행과 공통 대화 조정’을 추천한다.** 의미 판단을 계속하는 요청과 새 사용자 입력의 실행 의존을 나누는 것이 핵심이다. 짧은 질문은 공통 해석에서 답하고, 근거 읽기나 추가 의미 판단이 필요한 요청만 별도 실행으로 이어간다. 모든 입력에 worker와 모델 호출 두 개를 강제하지 않는다.

VIA는 사용자가 하나의 창에서 자료를 이해하고, 정정하고, 다른 업무의 질문에 답하는 인터페이스다. 기존 판단을 버릴 필요가 없는 독립 입력 때문에 앞선 VIA 판단을 기다리게 하는 것보다, 요청별 문맥과 반환 계약의 비용을 받아들이는 방향이 이 역할에 더 맞는다. 원래 요청의 진행을 유지하면서 새 요청에 응답할 수 있는 실행 경로를 먼저 확보한다는 작성자 판단이다. 입력 교차 빈도나 지연 우위를 실측했다는 결론은 아니다.

**외부 Agent의 장기 업무만으로는 이 추천이 성립하지 않는다.** 외부 업무가 진행되더라도 VIA가 기다리는 동안 모델 호출을 점유하지 않으면 A도 새 입력을 바로 판단할 수 있다. 구조 차이가 필요한 곳은 VIA 자신의 범위 제한 읽기와 의미 호출이 진행 중인 경우다. 수신, 즉시 음성 중단, 구조가 정해진 진행 상태 기록과 표시, 이미 식별된 질문 답변의 전달은 양안의 공통 코드 경로로 둔다. 자유문 관계 판단이 필요한 사건만 의미 해석에 넣는다.

공식 문서를 다시 읽어 [steering의 다음 판단 경계](https://docs.openclaw.ai/concepts/queue), [별도 실행의 반환과 자원 부족 시 대기](https://docs.langchain.com/oss/python/deepagents/async-subagents), [실행 중 메시지 수신과 이후 step 반영](https://docs.openhands.dev/sdk/guides/convo-send-message-while-running)을 확인했다. 구현 사실과 VIA에 대한 추론, 현재 문서와 기존 고정 commit의 차이는 [추가 확인 기록](../../../../../references/five-problem-study/interaction-recommendation-check-20261017.md)에 구별했다.

### 10.3 선행 대기와 추가 처리를 분리하는 인과식

같은 새 입력의 공통 근거가 준비된 시점부터 첫 내용의 실제 표시까지를 보자. `W`는 A가 앞선 VIA 모델 호출 또는 읽기 단계의 다음 판단 경계를 기다리는 잔여 시간이다. `H_A`, `H_B`는 그 외에 해당 응답의 실제 인과 경로에서 필요한 처리다. 여기에는 호출 자원 대기, 문맥 구성, 관계 해석, 필요한 조회, 채택과 표시가 들어간다. 한 호출에서 함께 처리하는 구간을 여러 단계로 중복 합산하지 않는다.

```text
첫 응답의 남은 시간 A = W + H_A
첫 응답의 남은 시간 B = H_B
A 대비 B의 단축 = W - (H_B - H_A)
```

따라서 **선행 잔여 대기 W가 분리로 늘어난 처리 ΔH보다 클 때** B의 첫 응답 이익이 있다. B의 호출 자원 대기는 `H_B`에 포함하므로 동시 실행 한도가 하나이거나 포화되면 W만큼 빨라진다고 계산할 수 없다. 외부 Agent의 업무 시간은 W에 넣지 않는다. 구체적인 처리 의도를 앞서 실제 표시할 수 있으면 그 지점까지만 계산한다.

QA03에도 같은 방식으로 기존 endpoint까지의 실제 인과 경로를 분해한다. 전체 모델 호출 시간을 단순 합하거나 원래 요청과 새 요청의 공통 구간을 두 번 빼지 않는다. 비용과 RAM에는 시간과 다른 기준을 적용한다.

- 모델 비용 차이의 주요 항은 **B가 추가한 문맥 준비 / 관계 / 반환 / 재시도 비용과 A의 넓은 문맥 반복 비용 절감 여부**다. 병행 실행 자체는 모델 요금을 없애지 않는다. 전체 차이는 COMMON-28의 실제 청구 입력 / 출력과 tail 원장에서 산출한다.
- RAM 차이는 같은 시점에 살아 있는 문맥, 원본 buffer, 반환 결과와 직렬화 사본의 차이다. 각 구조의 개별 allocation 최대값을 서로 다른 시점에서 더해 peak를 만들지 않는다. 공통 앱 비용도 포함한다.

현재 추천은 B다. 다만 배포할 모델 연결이 실질적으로 단일 호출만 허용하거나, 정상 workload가 외부 업무 대기와 짧은 같은 문맥 수정에 집중되어 B가 제거할 VIA 선행 대기가 없다면 **기본 A로 추천을 바꾼다.** 반대로 비용과 상태가 늘더라도 겹치는 VIA 판단에서 첫 응답의 대기가 지속적으로 줄고 기능 조건을 지킨다면 B를 유지한다. 정확한 비용 허용량이나 새 점수 기준을 이 문서에서 임의 확정하지 않는다.

| --- | --- | --- | --- |
| **B2 새 입력용 호출 여유 예약** | 같은 총 한도 안에서 장기 요청의 시작 수를 제한해 공통 대화 해석이 사용할 여유를 남김. 이미 실행 중인 호출은 강제 종료하지 않음 | QA01의 자원 대기 감소. 원래 요청의 시작 / 완료 지연과 미사용 여유를 감수 | 같은 한도에서 새 질문도 빨라지지 않거나 원래 요청의 QA03 지연만 커지면 적용하지 않음. 단일 호출 조건에서는 별도 여유가 생기지 않음 |
| **B1 불변 문맥 참조 공유** | 같은 대화 / 원본의 변하지 않는 조각을 한 번 보유하고 요청별 참조와 변경분을 유지. cloud 요청 직렬화 사본은 별도로 계상 | QA06의 중복 보유 감소. version, 사용권, 참조 수명과 재구성 비용 추가 | 실제 peak가 직렬화 사본 때문에 줄지 않거나 재구성 QA03 비용이 크면 더 단순한 기본 B 상태를 유지 |

A1/A2는 A를 선택할 때의 대안 보완으로 §7에 남긴다. 기본 B와 A1 또는 A2의 우열을 기본 A/B 결과로 섞지 않는다. 이 선택의 목적은 원래 목표를 계속 유지하면서 새 입력을 처리하는 것이므로, 모든 추가 입력마다 원래 호출을 취소하는 방식은 추천 기본 정책으로 삼지 않는다.

### 10.6 제한된 PoC 설계

**PoC의 질문:** 같은 입력과 호출 한도에서 B가 실제로 제거하는 선행 대기는 얼마이며, 그 대가로 추가하는 판단, 비용과 RAM은 무엇인가? 제품 전체, 모든 Agent 통합이나 정확도 전반을 구현하는 범위가 아니다. 다음은 후속 실행 승인을 위한 설계이며 이번에는 구현하거나 실행하지 않는다.

**범위 제안:** 대화 하나, 동시에 유지할 요청 최대 세 개, 고정된 문서 D1/D2와 외부 Task 두 개를 사용한다. 외부 Task는 진행 / 질문 / 결과 / 취소 확인을 반환하는 대역으로 두며 실제 외부 Action은 하지 않는다. 기본 A/B의 비교를 먼저 수행하고 B1/B2는 별도 단계로 붙인다. 총 모델 동시 호출 한도 1과 2를 각각 양안에 동일하게 준다. 이 숫자는 제한된 구조 검증의 설정안이며 VIA 요구나 성능 목표가 아니다.

| 입력 묶음 | 고정할 사건과 완료 조건 | 확인하려는 것 |
| --- | --- | --- |
| P0 쉬운 순차 대화 | TCP 다음 UDP 설명 뒤 후속 질문. 진행 중 의미 호출 없음 | B에 불필요한 worker나 추가 관계 호출을 강제하지 않았는가 |
| P1 외부 업무 대기 대조 | 외부 메일 Task만 진행하며 VIA는 쉬는 중 추가 질문과 구조화된 진행 통지 | 외부 시간을 W로 잘못 세거나 모든 통지를 LLM에 보내지 않는가 |
| P2 VIA 모델 호출 중 독립 질문 | D1 판단 호출이 시작된 뒤 짧은 독립 질문. 호출 초반 / 중간 / 끝 직전 도착 변형 | 선행 잔여 W와 새 답변의 추가 H를 실제로 구별할 수 있는가 |
| P3 VIA 읽기 중 다른 자료 요청 | D1의 범위 제한 읽기 중 D2 결론 요청 | 읽기 대기와 의미 호출 대기를 구별하고 두 원래 목표를 모두 완료하는가 |
| P4 호출 포화 | 두 VIA 요청이 겹친 상태에서 세 번째 입력. 동일 총 한도 1 / 2 | 별도 실행이 있어도 admission이 막히는 경우, B2의 새 입력 이익과 원래 요청 지연 |
| P5 정정과 질문 답변 | §4의 비용 범위 정정, 외부 수신인 질문, 실제 질문 표시 후 “김 대리” | 현재 조건과 실제 질문 연결, 늦은 결과의 보류. 같은 발화 안의 고침은 해석 시작 전 / 후를 나누고 ASR partial 교체와 구별 |
| P6 취소와 늦은 결과 | 특정 외부 Task 취소 요청 뒤 진행 / 결과 / 취소 확인, 다른 Task는 계속 | 공통 안전 조건과 원래 목표 보존. 수행 여부가 불명인 동일 외부 Action의 중복 재위임 금지. 확인된 자료를 사용하는 별도 허용 업무까지 막지 않음 |

입력은 같은 녹음 / 전사 revision, 문서 version, 화면 근거와 외부 사건 기록으로 제공한다. 목표와 허용 결과는 실행 입력에 정답 Task ID로 넣지 않고 평가용 원장에 따로 둔다. P5의 확인 답변은 각 안에서 질문이 실제 표시된 뒤 같은 지연으로 전달한다. 도착 시점 실험은 논리적으로 같은 VIA 호출의 시작을 기준으로 하며, 먼저 실행한 안이 만들어낸 출력 시각을 다른 안의 절대 입력 시각으로 복사하지 않는다.

**검증을 두 층으로 구별한다.** 먼저 정해진 응답과 대기를 가진 모델 / 읽기 대역으로 실행 의존, 입력 누락과 늦은 결과 채택을 확인한다. 이 결과는 구조 확인이며 모델 정확도, 실제 QA01 우위나 실제 요금의 증거로 쓰지 않는다. 이후 승인된 동일 cloud 모델과 실제 호출로 같은 묶음을 실행해 문맥 준비와 반환 비용을 포함한다. 기본안별 입력 구성은 기록하되 모델, 원본, 권한과 한도는 같게 둔다. 두 층의 결과를 하나의 평균에 섞지 않는다.

기록할 사건은 입력 수신 / revision, 실제 발화 종료, VIA 읽기 시작 / 끝, 모델 admission / 요청 송신 / 응답 끝, 관계 최초 채택, 결과의 근거 revision, 첫 내용의 실제 표시와 전체 음성 요약 준비다. provider 내부 실행 시작은 직접 관측할 수 있을 때만 별도 기록하며 요청 송신 시각으로 대신 단정하지 않는다. 표시 요청을 보낸 시각도 실제 UI 표시로 대체하지 않고 기존 관측 등급을 보존한다. 원래 요청과 새 요청의 endpoint를 모두 남기며 B의 새 입력만 빨라진 결과로 전체 이익을 선언하지 않는다.

이 작은 묶음에서는 QA01/03의 적용 장면과 모델 usage, 로컬 상태의 원인 차이를 확인한다. **부분 묶음의 비용을 QA05 전체 COMMON-28 점수로, 축소 shell의 RAM을 전체 VIA 512 MB 충족으로 발표하지 않는다.** 최종 QA05는 공통 전체 workload, QA06은 공통 앱 비용을 포함한 전체 peak에서 판정해야 한다. PoC는 그 판단에 필요한 구현 원인과 추가 비용의 범위를 제공한다.

### 10.7 추천의 반증과 중단 조건

1. **B의 핵심 이익 반증:** P2/P3에서 호출 여유가 있는데도 실제 `W - ΔH`가 양수가 아니거나, 첫 내용과 기존 endpoint가 앞당겨지지 않으면 B의 응답 이익 주장을 철회한다. 대기 시간을 과장하거나 자료를 더 많이 주어 회복하지 않는다.
2. **정상 사용 비용 반증:** P0/P1과 같은 문맥의 정정에서 불필요한 분리 호출이 반복되고, 그 비용을 감수할 독립 입력 이익이 없으면 A로 추천을 바꾼다. 호출 지연만 개선되더라도 QA05/06 악화를 공개한다.
3. **기능 실패:** 목표 유실, 잘못된 질문 답변 연결, 오래된 조건 게시, 실제 종료 없는 완료 선언과 중복 외부 Action은 속도 이익으로 상쇄하지 않는다. 해당 실패를 남기고 실행 대응 / 채택 계약을 먼저 수정한다.
4. **보완 반증:** B2가 새 입력 지연을 줄이지 못하고 원래 요청만 늦추거나, B1이 실제 peak를 줄이지 못하면 해당 보완을 철회한다. 기본 B 추천과 보완 선택을 자동으로 함께 폐기하지 않는다.

**현재 결론은 기본 B 추천이며, 먼저 반증할 주장은 ‘원래 VIA 판단을 유지하면서 새 입력의 잔여 대기를 줄인다’이다.** 정확도 우위나 무료 병렬성까지 추천 이유에 포함하지 않는다.
