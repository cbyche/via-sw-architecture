## 1. 범위와 현재 결론

사용자가 DP 수를 네 개로 제한하지 않고 의미 있는 설계 결론을 요청한 뒤 수행한 검토다. [08 설계 권고](../08-decision-recommendations.md), [09 PoC 계획](../09-poc-decision-plan.md)과 다섯 문제의 최신 권고 절을 대상으로 했다. 앞선 [기본안 / tactic 개정 검토](user-review-20261017.md)와 별개다.

세 담당자가 자기 담당 문제의 추천을 작성한 후 종합과 다른 문제의 경계를 교차 검토했다. root는 문제 5와 종합을 작성하고 기본 비교와 보완 비교의 추천 변경 조건을 추가 점검했다. 모두 같은 repository 자료를 사용하므로 별도 평가팀이나 실험 검증의 독립성을 뜻하지 않는다.

**현재 판정은 독립 DP 진행 권고 3개, 조건부 후보 1개, 상세 설계 1개다.** P2 두 건과 P3 일곱 건을 수정하고 재확인했다. 아래 범위에서 열린 발견은 없다. 기본 구조의 실제 성능 우위, 코드 변경 수와 과정의 실측 QA coverage는 이 검토로 입증하지 않는다.

## 3. 확인한 설계 판단

- 문제 1과 4는 입력 소비자, 산출 계약과 준비 / 갱신 방식이 독립적으로 바뀌므로 별도 비교가 가능하다. 같은 생산물을 공유하면 비용은 한 번 센다.
- 문제 2의 B 이익은 VIA 자신의 읽기 / 의미 판단 잔여 대기에서 나온다. 외부 Agent가 실행 중이라는 사실만으로 VIA 모델 점유를 만들지 않는다.
- 문제 4의 B에는 반복 인계에 준비 비용을 상각하는 실제 대립 경로가 있다. 다만 N-H 우위와 세 번째 차별화 축은 미확인이다. 독립 DP 진행 권고가 과정 요건 충족 선언은 아니다.
- 문제 3의 B에는 별도 후보 생산과 결합의 구현 근거가 있다. 같은 raw를 한 번 공동 입력하는 A보다 B의 전체 비용이나 정확도가 유리하다는 근거는 아직 부족하다. 기능 중요도와 조건부 DP 판정을 구별했다.
- 문제 5는 실제 후보, 선택 목적과 독립 oracle 없이 별도 selector의 정확도 이익을 주장하지 않는다. 요청 해석의 일반 분할과 중복 DP로 세지 않는다.

## 4. 확인 한계

추가 source notes는 실제 protocol과 고정 code 또는 조회일의 공식 문서를 읽은 근거다. 모든 상용 Agent의 현재 배포 기능과 API 동작을 실행 확인한 목록이 아니다. 기존 고정 source 중 web 재열람에 실패한 경우는 새로 확인한 사실로 표시하지 않았다.

이번 작업은 제품 테스트, model call, 성능 / RAM 측정, candidate 구현, measurement freeze나 사용자 최종 선택을 포함하지 않는다. PoC 입력 목록은 실행 설계이며 fixture와 결과 파일이 아니다. 부분 PoC를 전체 COMMON-28 점수로 환산하지 않는다.

문서 정합성 검사 결과는 다음과 같다. 모두 통과했다.

- 활성 Markdown 468개 로컬 링크 검사.
- canonical 용어와 target Component 이름 검사.
- `git diff --check`.
- 이번 study / reference Markdown 27개와 로컬 파일 링크 168개, 줄 끝 공백과 중간점 검사.

이 결과는 문서 연결과 표기 범위이며 설계 성능 검증이 아니다.
