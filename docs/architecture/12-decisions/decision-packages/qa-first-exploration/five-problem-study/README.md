## 1. 이번에 바로잡은 비교 방식

**기본 구조 A/B/C의 trade-off를 먼저 비교하고, 방안을 선택한 뒤 그 안의 약한 QA를 A1/B1 등의 tactic으로 보완한다.** 이전 문서는 cache, 병렬 처리와 부분 갱신까지 기본안에 미리 넣어 구조의 차이를 읽기 어렵게 만들었다. 이번 정리에서는 기본안이 기능을 수행하는 데 필요한 처리와 선택 후 추가할 보완을 나눴다.

각 문제 안에서 기본안은 **A/B/C**, 그 안에 붙는 보완안은 **A1/A2, B1/B2, C1/C2**로 쓴다. E-와 H-는 각각 근거 공급과 인계 문제를 구별하려고 붙인 편집용 약칭이었으며 설계 의미가 없어 제거했다. 다른 문제의 A를 함께 말할 때는 “문제 1의 A”, “문제 4의 A”처럼 쓴다.

A1은 A에 첫 번째 tactic을 추가한 안이고, A2는 A에 두 번째 tactic을 추가한 안이다. **A2가 A1을 자동 포함하지 않는다.** 두 기법을 함께 적용할 때는 A1+A2라고 명시한다. 기본안과 tactic의 작성자 추천은 08에 있으며 사용자 채택이나 실제 적용 결과는 아니다. 공통 규칙과 첨부 예시의 반영 내용은 [07 기본 구조와 보완 설계](07-basic-designs-and-tactics.md)에 있다.

| **3. 발화 중 바뀌는 화면과 지칭 근거를 보존하고 결합하는 구조** | 사용자가 말하면서 가리키거나 선택한 대상과 당시 화면을 어떤 표현으로 결합할 것인가 | **A** 음성 및 화면 원본을 함께 해석 / **B** 음성과 화면의 부분 해석 후보를 각각 생산하고 결합 |
| **4. 외부 Agent를 바꾸어도 이전 업무의 조건과 결과를 전달하는 구조** | VIA가 보존한 이력 중 다음 Agent에 필요한 내용을 언제 구성하고 어떻게 제공할 것인가 | **A** 위임 시 인계 묶음 구성 / **B** 공통 업무 기록을 계속 갱신해 제공 / **C** 필수 조건과 자료 목록을 주고 수신 Agent가 필요한 원본을 읽음 |

### 문제 2는 어떤 상황을 해결하는가

예를 들어 사용자가 “이 보고서를 요약해줘”라고 말한 뒤 VIA가 자료를 읽는 동안 “아까 요청은 최근 두 달 기준으로 바꿔줘”라고 말한다. 이어 “그동안 이 용어 뜻도 알려줘”라고 묻고, 다른 업무를 수행 중인 외부 Agent가 “수신인은 누구인가요?”라는 질문을 보낸다. 사용자가 “김 대리”라고 답한 뒤, 변경 전 조건으로 준비된 결과가 늦게 도착할 수도 있다.

VIA는 각 입력이 **이전 요청의 변경인지, 별도 요청인지, 실제 제시한 질문에 대한 답인지** 판단해야 한다. 이전 요청의 처리가 끝나기를 무조건 기다리게 하지 않으면서, 새 입력을 잘못된 업무에 붙이거나 변경 전 결과를 현재 결과로 표시하는 일도 막아야 한다. 이때 **판단 실행을 어떻게 나누고 어떤 상태를 유지할지**가 문제 2의 구조 선택이다.

| 이전에 축약한 말 | 정확한 뜻과 범위 |
| --- | --- |
| 정정 | **같은 발화 안에서 말을 고치는 경우와 후속 발화로 이전 요청을 바꾸는 경우를 모두 구별해 다룬다.** 전자는 VIA가 발화 도중 이미 판단을 시작했을 때 이 실행 조정 문제에 들어온다. 발화 종료 후 처음 판단하면 일반적인 요청 이해다. 후자는 이전 발화가 끝났어도 판단이나 위임 업무가 진행 중인 경우가 핵심이다. |
| 새 질문 | **사용자가 새로운 발화에서 하는 별도 질문 또는 새 업무 요청**이다. VIA가 사용자에게 하는 확인 질문을 뜻하지 않는다. 확인 질문에 대한 사용자의 답변은 또 다른 입력 유형이다. |
| Agent 사건 | **외부 Agent가 보내는 진행 상태, 추가 정보 / 승인 요청, 부분 / 최종 결과, 실패와 취소 확인 통지**다. 결과 반환만 뜻하지 않는다. |
| 처리 중 | VIA의 근거 조회, 의미 판단과 응답 준비, 외부 Agent의 업무 수행을 구별한다. 외부 업무가 실행 중이라는 이유로 VIA의 의미 모델 호출도 계속 실행 중이라고 가정하지 않는다. |

세부 입력 정의와 시간 순서별 A/B 동작은 [02 후속 발화와 외부 Agent 통지 처리](02-continuous-interaction.md)에서 읽는다.

## 3. 기본 구조와 보완 설계의 읽는 순서

1. **공통 기능과 완료 조건:** 두 안이 같은 사용자 일을 수행하는지 확인한다.
2. **기본안 A/B/C:** 입력, 호출 순서, 보존 상태와 결과 채택 경계의 차이를 읽는다.
3. **기본안의 QA trade-off:** 같은 여러 장면에서 이익과 비용, 각 안을 선택할 조건을 비교한다.
4. **선택 이유:** 중요 QA와 상황을 근거로 기본안을 고른다. 현재 작성자 추천과 반증 조건은 08 및 각 문서 끝의 권고 절에 있다.
5. **선택한 안의 A1/B1 등:** 약한 QA를 개선할 tactic과 새로 생기는 비용을 확인한다.
6. **보완 전후 비교:** 같은 QA와 장면으로 개선 효과와 회귀를 별도로 남긴다.

문제 2를 예로 들면 다음과 같다. **A를 선택했다는 뜻은 아니다.**

| 단계 | 비교할 내용 |
| --- | --- |
| 기본 비교 A 대 B | A는 하나의 판단 실행에서 대화 문맥을 재사용하지만 뒤에 온 별도 질문이 기다릴 수 있다. B는 요청별 판단 실행으로 별도 질문을 처리할 수 있지만 문맥 준비와 조정 비용이 늘 수 있다. |
| A 선택 시 보완 후보 A1 | A의 본 실행을 유지하고 간단한 별도 질문만 제한된 보조 경로에서 답한다. 별도 질문의 대기를 줄일 수 있으나 추가 호출과 질문 분류 비용이 생긴다. |
| 보완 전후 A 대 A1 | QA01과 QA03의 대기 개선, QA05의 추가 모델 비용과 QA06의 상태 비용을 같은 조건에서 확인한다. A1이 모든 후속 요청을 독립 처리하는 B와 같다고 설명하지 않는다. |

cache나 부분 갱신을 모두 빼야 한다는 뜻은 아니다. **대화 문맥 유지, 공통 업무 기록 유지처럼 구조를 성립시키는 상태와 재사용은 기본안에 남긴다.** 추가 기법은 무엇을 개선하고 무엇을 더 요구하는지 별도 표로 보인다. 유효 revision, 권한, 필요한 원본 보완과 중복 실행 방지 같은 필수 처리는 기본 비교에서도 유지한다.

## 4. 조사 근거와 QA 판단의 상태

OpenClaw, OpenHands, LangChain Deep Agents, AutoGen Magentic-One, CrewAI의 구현 근거에서 처리와 상태 메커니즘을 가져왔다. 화면 지칭은 인접한 실제 시스템도 참고했다. 제품 전체를 A/B로 두지 않고 필요한 메커니즘을 VIA의 기능에 맞춰 구성했다. 구현 사실과 VIA에 추가할 설계는 [소스 원장](../../../../../references/five-problem-study/README.md)과 문제별 본문에서 구별한다.

17개 공통 장면과 문제별 변형을 사용한다. 쉬운 입력, 반복, 후속 요청 변경, 독립 질문, 화면 전환, Agent 교체와 늦은 결과를 다룬다. **기본안끼리의 비교와 선택안의 보완 전후 비교에서 같은 QA 정의를 유지한다.** cache가 있는 보완안의 효과를 기본안의 결과로 섞지 않는다.

기존 QA01~06의 의미와 점수 및 COMMON-28은 변경하지 않았다. 신규 제안은 다음과 같다.

| 신규 QA 후보 | 평가할 내용 |
| --- | --- |
| N-S Downstream Agent 선택 정확도 | 채택한 Agent 또는 정당한 보류가 독립 근거로 정한 허용 집합에 속하는가 |
| N-H 업무 인계 정확도 | 외부 위임 시 확정한 계약에 유효한 목표, 조건, 근거와 실행 범위가 보존되는가 |
| N-R 요청 관계 연결 정확도 | 처음 채택한 별도 요청, 이전 요청 변경, 질문 답변, 취소의 관계가 맞는가 |

아직 실측과 승자는 없다. 각 DP의 3~4개 QA trade-off와 QA별 최소 두 DP 차이라는 과정 조건도 충족했다고 단정하지 않는다. 첫 구체적 의도 표시 뒤에 하는 인계나 선택 작업을 QA01에 넣거나, 지칭 오류가 아닌 실패를 QA02에 넣어 차이를 만들지 않는다. 세부 경계와 빈칸은 [06 QA 후보와 적용 범위](06-qa-candidates-and-coverage.md)에 있다.
