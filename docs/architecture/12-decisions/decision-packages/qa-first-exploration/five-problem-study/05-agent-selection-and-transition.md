# 문제 5. 현재 업무를 맡길 외부 Agent를 선택하고 수행 중인 업무의 담당 Agent를 바꾸는 구조

2026-10-17 / 기본 A/B와 보완안 분리 / §8에 작성자 권고 추가 / 사용자 채택과 측정 전

> **현재 결론:** 별도 주요 DP 승격은 유보하고, 상세 설계에는 **A 요청 해석과 Agent 선택의 결합**을 추천한다. 후보 선택의 중요성은 유지한다. 실제 후보와 독립 성과 근거 없이 별도 selector의 정확도 이익을 주장하지 않는다. 아래 §1~7의 미선정 표현은 권고 전 비교 이력이며 최신 판단은 §8이다.

## 1. 어떤 상황을 해결하는가

사용자가 “앞서 비교한 결과로 발표자료 만들어 줘”라고 요청한다. VIA는 사용할 결과와 수정 조건을 이해한 다음, 연결된 외부 Agent 중 발표자료를 작성할 수 있고 자료 접근 권한이 있는 대상을 선택해야 한다. 이후 사용자가 “이 수정은 다른 Agent에게 맡겨 줘”라고 하면 기존 업무의 확인된 수행 범위를 보존하면서 담당을 바꿔야 한다.

기능, 권한과 연결 상태를 만족하는 후보를 찾는 것과, 그중 해당 업무에 더 적합한 후보를 고르는 것은 구별한다. 후자의 판단에는 사용자의 품질 / 시간 / 비용 목적과 업무별 독립 근거가 필요하다. Agent의 자기소개만으로 최고 성능을 보장할 수는 없다.

**설계 질문은 요청의 뜻을 판단하는 실행에서 Agent까지 함께 선택할지, 요청을 정리한 뒤 별도 실행에서 Agent를 선택할지다.**

## 2. 모든 기본안에 필요한 기능

- VIA의 업무 식별자와 현재 조건은 Agent 교체 뒤에도 유지한다. 외부 Agent의 내부 memory나 실행 상태를 자동 이식하지 않는다.
- 등록 후보의 기능, 자료 접근과 사용자 지정 조건을 확인하고, 실행 허가 직전에 요청 및 후보 정보의 현재 version을 다시 검사한다.
- 적합 후보가 없으면 제한을 설명하거나 필요한 조건을 질문한다. 임의의 첫 후보를 실행하지 않는다.
- 후보가 하나로 확정된 경우 두 안 모두 선택 모델 호출을 생략할 수 있다. 선택할 여지가 없는 사례에 인위적인 추가 판단을 만들지 않는다.
- 이전 실행의 종료가 불명확하면 새 Agent에서 같은 외부 Action을 중복 실행하지 않는다. 취소 요청 접수와 실제 종료 확인은 별개다.
- 업무 내부 계획과 도구 선택은 Downstream Agent의 책임이다. VIA는 누구에게 어떤 조건으로 맡길지 정한다.

여기서 후보 정보는 Agent의 이름, 지원 기능, 사용 조건과 확인 가능한 업무 성과 자료다. 두 안은 같은 자료와 모델, 실행 예산을 사용한다. 기본 비교에는 후보의 의미 검색 index, 선택 결과 cache와 선택 부분만 재판단하는 보완을 미리 포함하지 않는다. 현재 요청과 명시적 Agent 지정 등 기본 상태는 그대로 제공한다.

## 3. 기본 구조 A와 B

| 기본안 | 핵심 판단 경로 | 유지하는 상태 | 실제 구현 근거 |
| --- | --- | --- | --- |
| **A 요청 해석과 Agent 선택을 함께 수행** | 사용자 입력 / 대화 / 자료와 적격 후보 설명을 같은 의미 판단에 제공 → 요청과 후보를 함께 제안 → 공통 실행 허가 검사 | 요청 해석 문맥과 그 요청의 선택 제안 | Deep Agents task catalog, OpenHands TaskTool, CrewAI A2A card 주입과 위임 응답 |
| **B 요청 해석 후 별도의 선택 실행 수행** | 요청 해석 → 목적 / 대상 / 조건을 정리한 요청 계약 → 선택 실행 → 현재 요청과 연결 → 공통 실행 허가 검사 | 요청 계약과 별도 선택 문맥 / 후보 판단 상태 | AutoGen SelectorGroupChat의 별도 selector context, Magentic-One의 다음 수행자 판단 |

두 안 모두 모델을 사용할 수 있다. A/B의 차이는 모델과 code 중 무엇을 쓰는지가 아니라, **Agent 선택이 요청 해석과 같은 실행인지 별도 실행인지**다.

### A의 기본 처리

1. Request Interpreter가 사용자 발화, 관련 대화 / 자료와 적격 후보 정보를 읽는다.
2. 같은 의미 판단에서 요청의 목적과 대상, 위임 여부와 Agent를 제안한다. 자료가 부족하면 필요한 원본을 추가 조회한다.
3. Request Controller가 현재 요청 version과 권한을 검사하고 Task Manager 및 Agent Gateway의 위임 경로로 연결한다.
4. 후보 정보가 바뀌어 재선택이 필요하면 현재 요청과 새로운 후보 정보로 결합 판단을 다시 수행한다. 원본을 다시 수집할 필요까지 강제하지는 않지만 선택 의미만 따로 갱신하는 기법은 A2로 구별한다.

현재 대화의 미묘한 목적을 선택에 바로 사용할 수 있고 별도 요청 계약의 전달이 없다. 후보 설명이 많으면 요청 해석 입력도 커지고, 후보 변화가 선택과 요청의 결합 재판단을 일으킨다.

### B의 기본 처리

1. Request Interpreter가 목적, 대상 자료, 완료 조건, 필수 기능, 사용자 지정과 불확실성을 요청 계약으로 정리한다.
2. 별도의 선택 실행이 요청 계약과 적격 후보 정보를 읽어 후보 또는 보류 이유를 제안한다.
3. 요청 정보가 빠졌으면 필요한 원본을 확인하거나 요청 해석에 보완을 요구한다. 이 기본 구성에서는 보완한 근거로 현재 요청 계약 전체를 다시 생산하고 선택을 이어간다. 이 왕복과 재생산은 B의 비용이다. 계약 필드별 부분 교체는 B2로 분리한다.
4. Request Controller가 사용한 요청 및 후보 정보의 version을 확인한 뒤 위임한다.
5. 요청 계약은 그대로이고 후보 정보만 바뀌면 선택 실행만 다시 수행한다. 이것은 분리된 기본 구조의 성질이다.

선택 판단에 필요한 정보를 집중시키고 후보 변화의 재판단 범위를 나눌 수 있다. 대신 요청 계약의 구성 / 전달, 별도 의미 호출과 정보 누락 시 왕복이 추가된다. 별도 실행을 둔다고 정확도가 자동으로 높아지지는 않는다.

| 상황 | 공통 완료 조건 | 기본 A | 기본 B |
| --- | --- | --- | --- |

## 5. 기본안의 QA trade-off

보완안 A1/A2/B1/B2를 적용하기 전의 가설이다. 기본 상태와 필수 기능은 §2를 따른다.

| QA | A에서 예상하는 이익 / 비용 | B에서 예상하는 이익 / 비용 |
| --- | --- | --- |
| QA01 첫 응답 | 선택이 첫 내용의 전제이면 별도 선택 왕복을 줄일 수 있음. 큰 후보 입력은 판단을 늘릴 수 있음 | 계약과 선택이 직렬로 필요하면 대기 증가. 후보 변경만 있는 재선택에서는 기존 계약 활용 가능 |
| QA02 지칭 대상 정확도 | 같은 문맥의 후보 정보가 대상 해석에 간섭할 가능성 | 지칭 해석과 후보 비교를 분리. 그러나 지칭 결과가 같으면 차이 없음 |
| QA03 VIA 처리시간 | 작은 후보군과 처음 요청에서는 결합 판단이 간단. 후보 변경으로 결합 판단을 반복하면 비용 증가 | 별도 호출과 보완 왕복 비용. 후보만 바뀌는 경우 요청 계약 재사용 이익 |
| QA04 실제 Rust 모듈 변경 범위 | 공통 edge와 결합 판단의 입력 변경 경로 | 공통 edge 외 선택 계약의 변경 경로. 실제 동일 변경을 수행하기 전 우위 미확인 |
| QA05 VIA 모델 비용 | 요청과 후보를 함께 입력. 별도 호출이 적을 수 있으나 반복 선택 때 같은 요청을 다시 처리 | 요청 계약과 selector 입력 / 출력 비용. 선택 재실행에서 요청 해석을 반복하지 않을 수 있음 |
| QA06 최대 RAM | 후보 자료와 요청 문맥의 로컬 상태 | 별도 선택 상태와 전달 buffer 추가 가능. cloud memory를 로컬 RAM으로 세지 않음 |
| Agent 선택 정확도 | 현재 대화의 목적을 함께 고려. 후보가 많으면 간섭 가능 | 후보 정보에 집중. 요청 계약의 누락과 오래된 선택 상태가 오류 원인 |
| 업무 인계 정확도 | 문제4의 같은 인계 구조를 사용하면 직접 차이가 약함 | 선택을 맞혔다는 이유로 인계까지 성공한 것으로 계산하지 않음 |

선택 전에 “이 비교 결과로 발표자료 작성을 진행하겠습니다”라는 구체적인 채택 의도를 표시할 수 있다면 이후 선택 비용은 QA01 밖이다. QA03도 기존 상세 표시 / 전체 음성 요약 준비 endpoint를 늘리지 않는다. QA01과 QA03의 겹치는 시간을 독립 이익으로 합산하지 않는다.

## 6. 선택 후 검토할 보완안

현재 선택안은 없다. 아래는 해당 기본안을 선택했을 때 검토할 후보이며 기본 비교에는 포함하지 않는다.

| 보완안 | 보완할 단점과 목표 QA | 추가 처리 | 기대 효과와 추가 비용 |
| --- | --- | --- | --- |
| **A1 후보 설명을 검색해 필요한 후보만 입력** | 큰 후보군에 따른 QA03 / QA05 비용 | 기능 / 권한의 필수 필터 뒤에 설명 검색 index와 후보 확대 경로 추가 | 요청 입력량 감소 가능. index 갱신 / 검색 비용과 적격 후보 누락 위험 발생. 최종 적격성 검사는 유지 |
| **A2 기존 요청 해석을 유지하고 선택 부분만 다시 판단** | 후보 변화마다 결합 판단을 반복하는 QA03 / QA05 비용 | 이전 해석의 의존 version과 선택 결과를 나누어 보존하고 선택 관련 입력만 재판단 | 반복 처리를 줄일 수 있음. 요청과 선택의 영향 범위 추적 비용. 독립적인 선택 실행 / 수명까지 두면 B로 구조가 바뀌는지 재분류 |
| **B1 유효한 선택 결과 재사용** | 별도 선택 호출이 반복되는 QA01 / QA03 / QA05 비용 | 요청 조건과 후보 정보 version을 key로 선택 cache를 두고 채택 전 유효성 검사 | 같은 조건 반복에서 호출 절약. 저장 / 무효화 비용과 오래된 선택 재사용 위험 |
| **B2 부족한 요청 정보만 원 해석에 되묻기** | 계약 누락 때 전체 요청을 재생성하는 QA03 / QA05 비용 | selector가 누락 필드와 근거 요청을 반환하고 해당 부분만 계약에 반영 | 보완 입력과 왕복량 감소 가능. 필드 의존 관리와 잘못된 수정 범위의 추가 오류 가능 |

A1은 B에도 별도 번호를 붙여 검토할 수 있다. 사용 가능성이 있다는 이유로 기본 B에 자동 포함하지 않는다. AutoGen Swarm의 현재 worker가 다음 후보를 제안하는 방식도 후속 보완 후보지만, 실제 지원 Agent와 목적을 정한 뒤 번호를 부여한다.

SelectorGroupChat의 prompt 후보 축소는 hard admission이 아니다. 확인한 구현은 모델 반환 이름을 전체 participant 기준으로 검사한다. VIA의 최종 적격성 검사는 모든 기본안에 필요한 별도 code 계약이다. [SEL-05](../../../../../references/five-problem-study/agent-selection.md).

## 7. 선정 근거를 작성할 때

기본 A/B 비교에서는 별도 선택 실행의 왕복 / 상태 비용과 후보 변화에 따른 요청 해석 반복 범위가 핵심이다. A를 선택한다면 후보 입력량과 재판단 비용을 A1/A2로 보완할 수 있다. B를 선택한다면 선택 호출과 계약 보완 비용을 B1/B2로 줄이는 방향이다. 보완이 가능하다는 이유로 기본 비교를 없애지 않는다.

현재는 실제로 연결할 Agent의 기능, 후보 수와 변경 빈도, 독립적인 선택 정답 근거가 충분히 정해지지 않았다. 따라서 별도 선택 실행의 정상 사용 이익과 주요 DP 자격은 검토 중이다. 선택 / 인계의 중요성만으로 QA 차이를 확정하지 않으며, 어느 기본안이나 보완안도 선정하지 않았다.

## 8. 2026-10-17 설계 권고

### 8.1 결론: 상세 설계로 유지하고 A에서 시작

**VIA에는 Agent 선택이 필요하다. 현재 비교의 A/B는 실제로 가능한 구조지만, 별도 주요 DP로 승격할 근거는 아직 부족하다.** A를 추천하는 이유는 요청의 목적과 사용자 지정 조건이 이미 해석 중에 있고, 별도 선택 계약과 호출을 추가하기 전에 그 자리에서 적격 후보를 제안할 수 있기 때문이다. 이것은 정확도 우위의 주장이 아니다.

VIA가 스스로 ‘항상 최고 성능의 Agent’를 고른다는 제품 주장은 현재 근거로 지원하지 않는다. 현재 지지할 수 있는 설계는 **호출과 자료 접근이 확인된 후보 중 사용자 목적과 검증된 기능에 맞는 후보를 고르고, 조건이 부족하면 지정 또는 보류를 사용**하는 것이다. 외부 Agent의 내부 계획과 도구 선택은 계속 외부 책임이다.

이 권고는 이번 탐색의 작성자 추천이며 기존 선택 관련 ADR과 기본 architecture를 변경하지 않는다. [현재 공식 문서의 추가 확인](../../../../../references/five-problem-study/selection-recommendation-check-20261017.md)은 A와 B의 실재성을 보강하지만 우열을 입증하지는 않는다.

### 8.2 추천 기본안의 실제 처리

1. code가 실제 연결, 권한과 이미 확정된 입력 / 출력 요구 및 명시적 선택으로 사전 후보를 거른다. “지난번 비교한 그 Agent”처럼 아직 해석할 지정이나 새로운 출력 요구를 code가 미리 안다고 가정하지 않는다. 지원 선언과 시험으로 확인한 능력은 구별한다.
2. 이미 확정된 사용자 지정 또는 단일 적격 후보면 그 사실을 사용한다. 미해결 요청 조건과 복수 후보는 요청 해석과 같은 의미 실행에서 판단한다. 그 결과로 새로 확정된 조건도 마지막 실행 적격성 검사에 반영한다.
3. 해석한 요청, 후보와 선택 이유를 함께 제안한다. 품질 근거가 없어 사용자 목적에 맞는 대상을 구별할 수 없으면 확인을 요청하거나 보류한다.
4. Request Controller가 현재 요청 revision과 후보의 현재 적격성을 재확인하고 Agent Gateway의 실행으로 연결한다. 진행 중 전환에서는 기존 실행의 실제 수행 범위가 확인되어야 한다.

### 8.3 어떤 손익을 받아들이는가

| 주 판단 축 | A를 추천하며 기대하는 이익 | 받아들이는 단점과 B가 유리한 조건 |
| --- | --- | --- |
| QA03 VIA 처리시간 | 최초 요청에서 계약 전달과 선택 전용 왕복을 줄일 수 있음 | 같은 요청으로 후보만 자주 바뀌면 A는 결합 판단을 반복. B의 선택만 재실행하는 경로가 유리할 수 있음 |
| QA05 모델 비용 | 별도 계약 생성 / 전달 / selector 출력이 필요하지 않음 | 후보 설명이 크면 요청 해석 입력도 커짐. 계약을 여러 재선택에 재사용하면 B가 비용을 회수할 수 있음 |
| N-S Agent 선택 정확도 | 원래 사용자 맥락을 선택에 바로 사용 | 후보 설명의 간섭과 근거 부족 위험. B도 계약 누락 위험이 있으므로 정확도 방향은 미확인 |

QA01은 선택 전에 구체적인 처리 의도를 표시하는 장면에서 차이가 없다. QA04는 같은 C01~C06의 실제 Rust 변경을 보기 전에는 별도 selector를 이유로 우위를 주지 않는다. 따라서 위 세 항목을 **차이가 입증된 세 QA**로 세지 않는다. N-S의 독립 oracle이 없고 정상 사용에서 반대편의 이익 크기도 미확인인 점 때문에 주요 DP 승격을 유보한다.

### 8.4 보완 권고와 재검토 기준

- **현재 추천 구성은 기본 A다.** 작은 적격 후보군에서 추가 index나 cache를 의무화하지 않는다.
- **A1은 후보 설명량이 요청 판단의 병목으로 확인될 때의 첫 보완이다.** 적격성 필터 뒤에 의미 검색을 붙이고 누락 후보 확대를 지원한다. QA03/05 개선과 검색 갱신 비용 및 N-S 누락을 같이 평가한다. 기본 A의 성과에 A1 효과를 미리 넣지 않는다.
- **A2는 지금 추천에 포함하지 않는다.** 후보만 바뀌는 재선택이 반복되면 A2와 B의 수명 및 계약 차이를 다시 비교한다. 별도 선택 실행을 지속시키는 수준이면 B로 명시한다.

주요 DP 재검토는 실제 후보 등록 자료, 사용자 선택 목적, 독립 허용 후보 집합을 확보한 뒤 한다. 그 조건에서 후보 변화가 요청 해석과 독립적으로 반복되고, B의 QA03/05 이익이나 N-S 개선이 추가 호출 / 계약 누락 비용과 맞서는 경우 승격할 수 있다. 단순히 후보 이름이 많아졌다는 사실만으로는 충분하지 않다.

### 8.5 최소 확인 계획

EX13의 후보만 변경, EX15의 둘 이상 적격 후보, EX11의 처음 위임과 EX12의 명시적 동일 Agent 수정을 사용한다. 두 안에 같은 원본 요청, 후보 자료와 모델 예산을 제공한다. 계약 누락이 있는 경우 양쪽 모두 원본 보완을 허용한다. N-S는 최종 Agent 채택 또는 정당한 보류에서 평가하고 후보가 하나인 경우 불필요한 선택 호출이 없는지도 확인한다.

등록과 admission의 code 경로는 mock으로 확인할 수 있다. 의미 선택의 정확도와 총 모델 비용은 실제 모델을 실행하기 전에는 판정하지 않는다. **B가 반복 선택에서도 호출 비용을 회수하지 못하거나 A/B가 같은 후보를 같은 비용 범위에서 선택하면 상세 설계 유지 결론을 강화한다.** 지금은 그 실행을 하지 않았다.
