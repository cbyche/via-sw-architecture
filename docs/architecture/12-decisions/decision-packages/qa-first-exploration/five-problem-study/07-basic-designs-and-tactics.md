# 기본 설계 비교와 선택 후 보완 설계 기준

2026-10-17 / 사용자 리뷰 반영 / 비교 방법의 공통 규칙

작성자 추천은 [08 설계 권고](08-decision-recommendations.md), 추천의 확인 및 변경 조건은 [09 PoC 계획](09-poc-decision-plan.md)을 따른다. 사용자 채택과 실제 tactic 적용은 아직 없다.

## 1. 비교 순서

**먼저 기본 구조 A/B/C의 QA trade-off를 비교하고, 선택한 구조에서 부족한 QA를 보완안 A1/B1/C1 등으로 개선한다.** 처음부터 모든 최적화를 기본안에 넣을 필요는 없다. 각 기본안이 어떤 처리 구조를 택했는지와 그 선택 때문에 생기는 이익 / 비용이 보여야 한다.

1. 같은 사용자 상황과 완료 조건을 정한다.
2. 기본안 A/B/C의 구성, 처리 순서와 유지 상태를 설명한다.
3. 보완 기법을 적용하지 않은 기본안끼리 같은 QA로 비교한다.
4. QA 우선순위와 손익에 따라 기본안을 선택하고 감수할 단점을 적는다.
5. 선택안의 특정 단점을 줄일 보완 기법을 적용한다.
6. 선택한 기본안과 보완안을 같은 QA로 다시 비교한다. 개선 대상 외 QA의 비용도 함께 남긴다.

현재는 1~3의 설계 설명과 5의 보완 후보를 준비한다. 선택안은 아직 없으므로 특정 A1/B1을 적용했다고 표시하지 않는다. 다른 기본안에 붙일 수 있는 보완 후보도 목록에 남겨 둘 수 있지만, 기본 비교 수치에 미리 반영하지 않는다.

## 2. 공통 필수 조건, 기본 구조와 보완 기법

| 구분 | 의미 | VIA 예 |
| --- | --- | --- |
| 공통 필수 조건 | 어느 기본안에서도 지켜야 할 기능과 제약 | 사용자 입력 보존, 실제 전달 기록, 현재 요청 version 확인, 접근권한, 외부 수행 여부가 불명일 때 중복 실행 방지 |
| 기본 구조 A/B/C | 입력, 판단 책임, 실행 의존이나 지속 상태를 정하는 핵심 선택 | 하나의 대화 해석 실행에서 처리 / 요청별 해석 실행으로 분리 |
| 보완안 A1/B1/C1 | 선택한 기본 구조를 유지하면서 특정 QA의 단점을 줄이는 추가 설계 | A의 긴 실행 중 도구 없는 별도 질문 경로 추가, B의 실행별 문맥을 참조로 공유 |

기본안도 실제로 동작해야 한다. 대화 문맥을 유지하는 A에서 문맥의 재사용 자체를 제거하거나, 화면 후보를 결합하는 B에서 필요한 후보가 없을 때 원본을 다시 읽는 경로를 모두 제거하면 핵심 기능이 달라진다. 반면 반복 조회 cache, 독립 읽기의 병렬화, 수정된 부분만 다시 계산하기, 발화가 끝나기 전 잠정 의미 판단 시작 등은 목적과 적용 범위를 정해 보완안으로 둘 수 있다.

일부 기능을 지원하지 않는 기본안을 검토할 수는 있다. 그 경우 모든 안에 같은 요구를 제시하고 미지원 결과 / 사용자 수작업 / 실패를 그대로 기록한다. 필수 권한과 실행 안전 조건을 빼서 빠른 안으로 만드는 것은 허용하지 않는다.

## 3. 표기

- 기본안은 각 문제 안에서 **A, B, C**로 쓴다. 여러 문제를 함께 설명할 때는 **문제 1의 A**, **문제 4의 B**라고 쓴다.
- 이전 `E-`는 Evidence, `H-`는 Handoff를 구분하려고 붙인 작성용 약자였다. 설계 의미가 다르다는 표시는 아니었고 다른 문서와 일관되지 않아 제거한다.
- **A1은 A에 첫 번째 보완 기법을 적용한 안**, A2는 A에 두 번째 보완 기법을 적용한 안이다. 번호는 자동 누적되지 않는다.
- 두 기법을 함께 적용하면 **A1+A2**처럼 쓴다. 결합한 결과는 별도로 평가하며 각 보완의 이득을 단순 합산하지 않는다.
- 서로 다른 기본안에 같은 기법을 적용할 때도 A1 / B1처럼 부모 구조를 표시한다. 번호가 같다고 서로 같은 기법이라는 뜻은 아니다.
- 보완 때문에 핵심 판단 책임, 실행 단위 또는 주된 저장 권위가 다른 기본안으로 바뀌면 그 사실을 설명하고 기본 구조를 재분류한다. 작은 성능 보완을 과장해 새 C로 만들거나, 구조 교체를 작은 A1으로 숨기지 않는다.

| 첨부 사례 | 기본 구조의 선택 | 선택 후 보완의 표현 |
| --- | --- | --- |
| DP1 AI 모델 보호 | 서비스 내부 제어와 외부 서버 제어를 비교한 뒤 내부 제어 선택 | 사업자별 설정 분리와 생성 시 filtering을 추가하여 변경 비용의 약점을 보완 |
| DP2 추론 요청 처리 | 다중 작업 동시 처리와 단일 작업 순차 처리를 비교한 뒤 순차 처리 선택 | 전처리 분리와 shared memory를 사용해 대기를 줄임. 증가하는 memory도 함께 표시 |

## 5. 기본 비교 표와 보완 표

기본 비교는 다음 형식으로 작성한다.

| 기본안 | 핵심 구조와 처리 | 유리한 QA와 이유 | 불리한 QA와 이유 | 유리한 사용 조건 |
| --- | --- | --- | --- | --- |
| A | A에 필요한 기본 처리만 | 구조에서 발생하는 이익 | 구조에서 발생하는 비용 | 같은 시나리오의 조건 |
| B | B에 필요한 기본 처리만 | 구조에서 발생하는 이익 | 구조에서 발생하는 비용 | 같은 시나리오의 조건 |

보완 후보는 다음 형식으로 작성한다.

| 보완안 | 기본안의 단점 / 목표 QA | 추가하거나 바꾸는 처리 | 예상 개선 | 추가 비용과 다른 QA 영향 | 비교할 대상 |
| --- | --- | --- | --- | --- | --- |
| A1 | A의 특정 단점 | 구체적인 기법과 상태 | 조건부 기대 효과 | 입력 / 실행 / 메모리 / 변경 비용 | A 대 A1 |
| B1 | B의 특정 단점 | 구체적인 기법과 상태 | 조건부 기대 효과 | 개선 대상 외 QA도 기록 | B 대 B1 |

기본 비교와 보완 비교에서 QA 정의, 관찰 지점, 동일 입력과 실행 예산은 유지한다. cache가 없는 기본의 반복 조회와 cache를 넣은 보완의 반복 조회를 따로 설명한다. 본래 유지하는 대화 문맥이나 게시 기억의 재사용은 해당 기본 구조의 성질로 남긴다.

## 6. 이전 검토와 달라진 점

2026-10-16에는 가능한 보완을 먼저 양쪽에 모두 넣고, 작은 혼합으로 차이가 사라지면 주요 DP 자격을 낮추는 접근을 강조했다. 사용자는 핵심 구조의 비교와 선택 후 보완을 분리하도록 정정했다. 이번 개정은 그 지시를 따른다.

보완 가능성이 있다는 사실만으로 기본 구조 비교를 없애지 않는다. 기본 trade-off와 선택 이유를 남긴 뒤 보완의 개선량과 비용을 설명한다. 다만 두 기본안이 이름이나 배치만 다르고 실제 처리 차이가 없다면 여전히 구조 비교가 성립하지 않는다. 근거 없는 정확도 / 변경 용이성 이득을 만들거나 미측정 수치를 제시하지 않는 원칙도 유지한다.
