## 1. 사용 장면과 기본 A/B/C

사용자가 비교 Agent에게 제품 비교를 맡긴 뒤 “가격보다 유지보수 기간을 우선하고 Z는 제외해”라고 수정한다. 이어 다른 제작 Agent에게 “그 결과로 발표자료를 만들어줘”라고 한다. VIA가 사용자의 메인 interface라면 최종 조건과 사용할 결과를 이어 주어야 하며, 사용자가 처음부터 설명하지 않아도 돼야 한다.

**설계 질문은 다음 Agent가 업무를 시작할 수 있도록 VIA가 어떤 기록을 유지하고, 인계할 자료를 누가 언제 고르는가다.** 관련 UC는 05, 07~10, 12~18이다.

| 기본안 | 실제 처리 | 정상 사용에서 선택할 이유 | 기본 비용 |
| --- | --- | --- | --- |
| **A. 위임 시 인계 묶음 구성** | 위임이 확정될 때 VIA가 원본과 현재 조건을 읽어 인계 묶음(capsule)을 만듦 | 인계가 드물고 업무마다 필요한 자료가 다름 | 위임마다 근거를 찾고 조합하는 대기 |
| **B. 공통 업무 기록 유지** | VIA가 Agent와 무관한 업무 기록(work record)을 계속 갱신하고 위임에 필요한 부분을 추출 | 같은 결과와 수정 조건을 여러 후속 업무에 사용 | 쓰지 않을 기록 생산과 변경 반영 |
| **C. 필수 명세와 수신자 읽기** | VIA가 목표와 필수 조건 명세(manifest), 자료 참조와 읽기 권한을 전달. 수신 Agent가 업무에 필요한 세부를 선택해 읽음 | 자료가 크고 수신 작업자가 필요한 세부를 더 잘 판단 | 실행 중 읽기 왕복과 읽기 기능의 지원 의존 |

세 안은 각각 완결된 기본 경로다. 기본 A/B는 VIA가 업무 입력 묶음을 준비하고, 기본 C는 필수 명세 뒤의 세부 자료 선택을 수신 Agent에 맡긴다. 조합 가능성은 §7의 보완책에서 다룬다.

기본 B의 업무 기록 재사용은 핵심 구조다. 별도 cache, native session의 숨은 문맥을 활용한 인계 생략, 자료 미리 읽기와 갱신 묶음 처리는 기본 비교에 넣지 않는다. 필요한 원본 보완과 현재 조건 / 권한 확인은 기본 기능이다.

## 2. 공통 기록과 완료 조건

VIA는 **자신을 통해 관측한 공개 이력을 허용 범위에서 보존하고 재사용**한다. 외부 Agent의 비공개 추론이나 내부 기억, 실행 중 도구 상태를 자동 수집하거나 이전한다고 전제하지 않는다.

| 기록 | 수집 출처와 인계 용도 |
| --- | --- |
| 목표, 수정과 제외 조건 | 실제 사용자 입력과 Request Controller의 채택 revision(변경 판본). 현재 조건과 취소된 조건 구별 |
| 위임 입력과 실행 연결 | Task Manager의 VIA Task, Agent Gateway의 전송 기록과 외부 식별자 |
| 접수, 진행, 질문과 결과 | 실제 외부 관측. 전송, 접수, 완료와 불명 상태 구별 |
| 자료와 결과물 | 접근 위치, 허용 범위와 실제 외부 판본. 외부 판본이 없으면 보존 복사본의 로컬 식별자 사용 |
| 사용자 채택과 실제 전달 | 선택 / 수정 기록과 Response Manager의 텍스트 표시 / 음성 전달 범위 |
| 파생 기록과 허용 User Memory | 출처 있는 인계 자료와 사용자 허용 선호. 임시 업무 조건을 장기 선호로 자동 승격하지 않음 |

State Store와 기존 소유자의 기록을 사용하며 모든 자료를 항상 모델 입력이나 RAM에 올리지 않는다. 일부만 관측하거나 API가 지원되지 않으면 그 한계를 기록한다. native revision을 만들거나 외부 receipt(접수 확인)가 없는 상태를 접수 완료로 바꾸지 않는다.

모든 기본안은 다음을 만족해야 한다.

1. 현재 목표, 결과물 형식, 필수 제약과 제외 조건을 전달한다.
2. 필요한 결과의 정확한 원본 / 판본 / 범위와 유효한 접근 방법을 제공한다.
3. 이미 완료한 일, 취소 요청, 확인된 종료와 실행 불명을 구별한다. 불명 상태의 외부 Action을 다른 Agent에서 중복 시작하지 않는다.
4. 승인 범위를 확대하지 않고 철회된 자료를 사용하지 않는다. 전송 직전 현재 위임 revision과 권한을 다시 확인한다.
5. 수신 Agent의 실제 지원 형식을 사용한다. 필수 자료를 제공하지 못하면 가능한 범위를 명시하거나 인계를 보류한다.
6. 원본 보존, 파생 자료 생산, 전송과 외부 접수의 성공을 구별한다.

사용자 조건과 실제 업무 사실의 권위는 공통 소유자에 있다. Context Manager의 요약이 이를 덮어쓰지 않는다. VIA는 문맥 인계를 담당하고 실제 발표자료의 계획과 제작은 Downstream Agent가 수행한다.

## 3. 기본 구조와 reference 근거

### A. 위임할 때 인계 묶음을 만든다

1. Request Interpreter가 “그 결과”의 대상과 현재 후속 요청을 판단하고 공통 채택 경로로 연결한다.
2. Context Manager가 원본 결과, 사용자 수정과 필요한 근거를 범위를 정해 읽는다.
3. 이번 업무에 필요한 목표 / 조건 / 자료를 인계 묶음으로 구성한다. 큰 결과물은 유효한 첨부나 명시적 자료 참조로 전달할 수 있지만, 무엇을 사용할지는 VIA가 준비한다.
4. 현재 revision과 권한을 검사한 뒤 Agent Gateway가 전송한다. 실제 전송 내용과 접수 여부를 남긴다.

기본 A는 미래의 인계를 위한 의미 기록을 매 사건마다 생산하지 않는다. 각 위임의 입력을 구성하며, 이전 묶음은 이력으로 보존하되 별도 cache로 자동 재사용하지 않는다. 후속 수정에도 현재 유효한 인계 계약을 만든다. 같은 Agent를 선택하는 것은 가능하지만 native session의 내부 문맥만 믿고 조건 전달을 생략하지 않는다.

정정이 준비 중 들어오면 옛 묶음을 무효화하고 현재 조건으로 해당 위임 묶음을 다시 만든다. 바뀌지 않은 사용자 조건을 버리거나 재입력을 요구하지 않는다. 원본 일부를 읽지 못하면 인계 내용에서 숨기지 않고 필요한 보완 또는 보류를 수행한다.

**근거:** Deep Agents의 isolated 위임 설명과 공개 문맥 전달, CrewAI의 지정 Task 출력 조합, [R07](../../../../../references/five-problem-study/evidence-and-handoff.md#r07-isolated-인계와-부모-문맥-fork), [R09](../../../../../references/five-problem-study/evidence-and-handoff.md#r09-명시-task-출력-조합과-추출-기억). 같은 framework의 state fork를 이종 Agent의 내부 상태 이전으로 확대하지 않는다.

### B. Agent에 독립적인 업무 기록을 유지한다

1. Context Manager가 공개 업무 결과와 사용자 수정을 받아 해당 업무의 기록을 갱신한다. 목표 / 제약, 채택한 결과, 자료 관계와 남은 불확실성을 출처와 함께 유지한다.
2. 원본 및 현재 조건 revision을 대조한 뒤 새 기록을 게시한다. 이미 구조화된 사실은 코드로 처리하고 의미 정리가 필요한 부분만 모델을 사용한다.
3. 후속 위임에서는 현재 업무 기록에서 필요한 부분을 뽑아 전송 묶음을 만든다. 기록에 없는 필수 세부는 원본에서 보완한다.
4. 현재 revision과 권한 검사, 전송 및 접수 기록은 A와 같다.

기록은 업무 수명 동안 유지하고 여러 인계에서 재사용한다. 기본 비교는 대상 사건이 들어올 때 해당 업무 기록을 갱신하며, 변경을 모아서 처리하거나 바뀐 필드만 재생산하는 최적화를 미리 넣지 않는다. 현재 조건처럼 이미 확정된 값까지 매번 모델이 다시 추론하도록 강제하지는 않는다.

기억 생산이 늦거나 실패하면 낡은 기록을 현재 사실로 사용하지 않는다. 유효한 기록과 필수 원본을 조합하거나, 필요한 범위를 원본에서 다시 구성한다. 일부 자료 철회는 관련 기록의 사용을 차단하고 유효한 판본으로 갱신한다.

**근거:** OpenClaw의 기억 생산과 출처 관계, CrewAI의 저장 / 회상 및 갱신, [R03~04](../../../../../references/five-problem-study/evidence-and-handoff.md#r03-먼저-생산한-기억과-조건부-별도-recall), [R09](../../../../../references/five-problem-study/evidence-and-handoff.md#r09-명시-task-출력-조합과-추출-기억). VIA의 필수 조건과 실제 실행 사실을 인계하는 계약은 추가 설계다.

### C. 필수 명세를 넘기고 수신 Agent가 세부를 읽는다

1. VIA가 현재 목표, 필수 제약과 제외 조건, 사용할 결과 판본을 명세로 만든다. 필수 조건을 선택적 검색 뒤에 숨기지 않는다.
2. 자료를 읽을 수 있는 저장 영역과 범위 제한 읽기 API, 유효기간이 있는 읽기 권한을 준비한다.
3. Agent Gateway가 수신 Agent의 읽기 지원을 확인하고 명세와 자료 참조를 전달한다.
4. 수신 Agent가 업무에 필요한 원본의 세부 범위를 선택해 읽는다. VIA의 읽기 경계는 요청마다 실제 판본, 권한과 반환 범위를 확인한다.
5. 결과와 관측 가능한 자료 사용 사실을 VIA Task에 연결한다. 공개하지 않는 내부 읽기나 추론을 안다고 가정하지 않는다.

기본 C는 수신자가 필요한 자료를 선택하는 경로이며 VIA가 자주 쓰는 본문을 미리 읽어 붙이지 않는다. 한 실행에서 이미 읽은 정보를 그 실행이 사용하는 것은 정상 동작이다. VIA가 실행 간 조회 결과를 별도 cache로 제공하는 최적화는 §7로 분리한다.

정정이나 철회가 생기면 옛 명세와 읽기 권한의 사용을 막고 새 인계 revision을 전달한다. 이미 전달한 내용이 읽기 권한 철회만으로 삭제되는 것은 아니다. 읽기 API를 지원하지 않는 Agent에는 기본 C를 그대로 적용할 수 없다. A/B 형태의 묶음으로 바꾸는 경우는 구조 전환을 명시한다.

**근거:** Deep Agents의 thread 간 StoreBackend, 경로별 CompositeBackend와 범위 읽기, [R02](../../../../../references/five-problem-study/evidence-and-handoff.md#r02-큰-자료를-원본-저장소에-두고-필요한-범위-재조회), [R08](../../../../../references/five-problem-study/evidence-and-handoff.md#r08-source--artifact를-공유하는-저장-경계). 이종 외부 Agent의 실제 읽기 API 지원과 권한 계약은 별도로 확인해야 한다.

| **EX06 / EX09 부분 정정:** 표 조건만 바꾸고 문단 수정은 유지 | 옛 묶음을 무효화하고 현재 조건으로 재구성 | 대상 업무 기록 갱신 후 새 묶음 구성 | 명세와 관련 읽기 권한 갱신. 실행 중 Agent에 새 revision 연결 |
| **EX14 실행 중 전환:** 파일 생성 확인, 외부 전송은 불명 | 확인된 파일과 전송 불명을 묶음에 명시 | 업무 기록의 확인 / 불명 상태를 전달 | 명세에 전송 금지 / 확인 필요 명시. 파일 읽기만 허용 |
| **EX16 철회 / 만료:** 일부 source 철회 또는 결과 URL 만료 | 새 묶음에서 제외하거나 허용 원본 복구. 필수 자료 없으면 보류 | 기록의 출처를 따라 사용 차단 / 갱신 후 인계 | 읽기 권한 폐기 또는 위치 복구. 기존 외부 복사본 삭제와 구별 |
| **EX17 재접속:** native session 없음, 결과 v3 도착 | 공개 원본과 현재 조건으로 새 묶음 구성 | 기록의 반영 지점 확인 후 v3 갱신과 인계 | 현재 자료와 명세 및 읽기 권한 재발급 |
| **EX13 텍스트만 받는 Agent 추가** | 허용 형식에 맞춰 준비한 묶음 전달 | 업무 기록에서 허용 형식의 묶음 추출 | 기본 C 지원 조건 미충족. 가능한 구조 전환이나 보류를 명시 |

EX11의 원본에는 최초 가격 우선 요청, 비교 v1, 사용자 수정, 비교 v2와 채택이 모두 있다. 후보에게 v2라는 정답을 먼저 알려 주지 않는다. VIA가 현재 요청과 기록의 관계를 판단하고 세 안 모두 최종 조건을 전달해야 한다.

## 5. 기본안의 QA trade-off

| QA | 기본 A | 기본 B | 기본 C |
| --- | --- | --- | --- |
| **QA01 첫 응답** | 첫 대상 채택에 원본 조합이 필요하면 대기 | 현재 기록이 필요한 근거를 포함하면 채택 준비 단축 가능 | 필수 명세의 대상과 조건 판단 필요 |
| **QA02 지칭 정확도** | 공통 지칭 채택 뒤 인계만 바꾸면 동점 | 공통 지칭 채택 뒤 인계만 바꾸면 동점 | 공통 지칭 채택 뒤 인계만 바꾸면 동점 |
| **QA03 VIA 처리시간** | 위임 시 원본 취득, 의미 조합과 검증 | 기록 추출, 부족한 근거 보완과 필요한 갱신 대기 | 명세 / 읽기 준비 및 기존 trial 인과 경로 안의 읽기 응답 |
| **QA04 변경 범위** | 인계 묶음과 source 계약에 영향 | 업무 기록 schema, 생산 및 인계 계약에 영향 | 명세, 자료 접근 및 읽기 권한 계약에 영향 |
| **QA05 모델 비용** | 실제 인계 때 조합 비용 | 아직 안 쓰는 기록 생산 / 갱신과 각 인계의 추출 비용 | 필수 명세 생산과 VIA 보완 호출. 자료 선택 비용 일부는 외부 Agent로 이동 |
| **QA06 최대 RAM** | 인계 구성 중 읽기 버퍼 | 기록 생산 대기열과 활성 기록 | 자료 제공 버퍼와 동시 읽기 권한 상태 |
| **N-H 업무 인계 정확도** | 즉석 조합에서 필수 조건 누락 | 낡거나 축약된 기록의 조건 누락 | 필수 명세 누락 또는 읽을 수 없는 자료 참조 |

지칭이 이미 채택된 뒤 묶음이나 명세에 잘못된 source를 넣은 오류는 N-H에서 판단한다. 인계 자료가 실제로 채택 전 지칭 판단에 되먹임되는 결합 설계에서만 QA02에 조건부 영향이 있으며, 인계 구조만의 기본 이익으로 세지 않는다.

첫 구체적인 처리 의도를 인계 준비 전에 표시할 수 있으면 뒤의 묶음 생성과 Agent 접수를 QA01에 넣지 않는다. QA03도 상세 표시와 전체 음성 요약 준비라는 endpoint를 늘리지 않는다. 그 이후 외부 Agent의 요청에 응답한 VIA 읽기 시간은 별도 진단으로 남긴다.

QA05는 전체 COMMON-28의 준비, 미사용 생산과 폐기를 포함한다. C가 외부 Agent로 읽기 / 판단을 옮긴 비용을 전체 업무 비용 절약으로 주장하지 않는다. QA06은 로컬 최대 RAM과 512 MB 요구를 유지한다. QA04의 Rust 모듈 수와 실제 수치 우위는 미확인이다.

### N-H의 동일 관찰 지점

[공통 N-H](./06-qa-candidates-and-coverage.md#3-신규-후보-n-h-업무-인계-정확도)는 `(Task, request revision, execution attempt, delegation revision)`별로 **외부 실행을 허가하며 확정한 인계 계약**을 판정한다. 목표, 필수 제약과 제외, source / 판본 / 범위, 현재 접근 방식과 허가된 수행 범위가 oracle과 의미상 일치해야 한다. 필수 항목 누락이나 옛 조건 재도입은 계약 전체의 실패다.

A/B의 실제 확정 묶음과 C의 명세 / 유효 자료 접근 계약을 같은 조건으로 판단한다. 원본 전체를 복사할 필요는 없지만 만료된 위치나 존재하지 않는 필수 자료는 실패다. 외부 Agent가 유효 자료를 읽지 않거나 domain 작업을 잘못한 결과와 구별한다. receipt 시점이나 모델 중간 입력으로 관찰 경계를 바꾸지 않는다. 공통 검증 뒤 계약이 같으면 N-H는 동점이다.

## 6. 선정에 사용할 근거와 현재 판단

| 우선 사용 조건 | 선택 이유 | 선택 후 남는 약점 |
| --- | --- | --- |
| 다음 위임이 드물고 업무별 필요한 자료가 크게 다름 | **A:** 필요한 때만 목적에 맞는 묶음을 생산 | 반복 인계에서 같은 근거를 다시 조합 |
| 조건 수정과 결과가 여러 후속 업무에 반복 사용 | **B:** Agent와 무관한 업무 기록을 여러 인계에 재사용 | 미사용 기록 생산과 잦은 정정의 갱신 비용 |
| 큰 자료의 필요한 세부를 수신 작업자가 결정하며 읽기 API를 지원 | **C:** VIA의 선행 자료 선택과 복사를 줄임 | 지원 가능한 Agent 범위, 실행 중 읽기 대기와 자료 제공 책임 |

**기본 A/B/C는 미선정이다.** 사용자 가치와 필요한 처리의 차이를 기준으로 비교하고, 선택한 구조의 부족한 QA는 다음 보완책으로 다룬다. C와 A/B를 조합할 수 있다는 이유로 현재 기본 비교를 무효화하지 않는다.

A의 반복 조합이 너무 큰 경우, B의 기록이 새 목적에 맞지 않아 매번 원본 재구성과 갱신을 모두 치르는 경우, C의 지원 Agent가 부족하거나 작은 자료에도 읽기 왕복이 많은 경우는 각각의 선정 근거가 약해진다. 인계 준비가 첫 응답 뒤에 가능하고 최종 계약도 같다면 QA01/N-H 차이는 작을 수 있다. 주요 DP의 QA coverage가 이미 확보됐다고 결론 내리지는 않는다.

## 7. 선택한 기본안의 부족한 QA를 보완하는 tactic

[공통 규칙](./07-basic-designs-and-tactics.md)에 따라 A1은 기본 A에 첫 보완책을 적용한 구성, A2는 기본 A에 둘째 보완책을 적용한 구성이다. 자동 누적하지 않고 함께 쓰면 `A1+A2`로 명시한다. 같은 방식으로 B1, C1 등을 표기한다.

| 구성 | 추가하는 보완책 | 기대 개선 | 추가 비용과 적용 범위 |
| --- | --- | --- | --- |
| **A1** | 원본 / 조건 / 권한 판본으로 인계 묶음 cache | 같은 목적의 반복 인계에서 QA03/05 개선 가능 | cache 저장, 판본과 철회 확인. 업무 목적이 달라지면 재구성 |
| **A2** | 같은 native session의 유효한 문맥을 확인하고 수정 내용 중심으로 인계 | 같은 Agent 후속 수정의 조합 / 입력 비용 감소 가능 | resume / 반영 확인 capability 의존. 공개 조건 보존과 이종 Agent 인계는 그대로 필요 |
| **B1** | 여러 변경을 모아 업무 기록 한 번 갱신 | 반복 생산의 QA05와 대기열 부하 감소 가능 | 최신 기록 준비 지연. 옛 기록은 즉시 사용 차단하고 원본으로 보완 |
| **B2** | 기록의 변경 필드와 의존 조각만 재생산 | 부분 정정의 QA03/05 개선 가능 | 세부 dependency 관리와 누락 검사. 모든 필드가 함께 바뀌면 이익 작음 |
| **B3** | 같은 native session을 확인해 기록 전체 대신 필요한 수정만 전달 | 같은 Agent 후속 입력량과 준비 비용 감소 가능 | 외부 session 유효성 및 수정 반영 확인. 업무 기록 갱신은 계속 필요 |
| **C1** | 반복해서 쓰는 구절을 미리 읽어 명세에 함께 전달 | 수신자의 실행 중 읽기 왕복 감소 가능 | 안 쓰는 자료의 준비 / 전송, 선택 판단 비용. VIA 모델 호출이면 QA05 포함 |
| **C2** | VIA 자료 제공 경계에 판본별 읽기 결과 cache | 반복 읽기의 로컬 I/O와 응답 시간 개선 가능 | RAM / 저장과 철회 검사. 모델이 없는 단순 I/O cache에 QA05 절감을 부여하지 않음 |
| **C3** | 같은 native session의 유효한 읽기 문맥을 재사용 | 같은 Agent가 읽었던 자료를 반복 취득하는 비용 감소 가능 | session과 자료 판본 / 권한 확인, 이미 외부에 전달한 내용의 처리 책임 |

A/B가 이미 지원하는 유효한 자료 참조 전달은 별도 tactic으로 중복 등록하지 않는다. 자료의 세부 선택 책임까지 수신자에게 넘기면 기본 C를 결합하는 구조 변경으로 설명한다.

OpenHands의 이름별 child conversation 재사용과 OpenClaw의 외부 harness session 재개는 A2/B3/C3의 구현 근거다([R06](../../../../../references/five-problem-study/evidence-and-handoff.md#r06-계속-재사용할-수-있는-child-conversation), [R10](../../../../../references/five-problem-study/evidence-and-handoff.md#r10-외부-harness의-session을-재사용하고-출력-경계를-번역)). 같은 framework의 fork는 이종 서비스로 private memory를 옮기는 기능이 아니다. 보완책의 지원 여부와 비용을 기록하며 기본안에 이미 적용된 것으로 취급하지 않는다.

| --- | --- | --- |

## 9. 문제 1과의 관계와 DP 권고

문제 1은 현재 발화를 이해하는 VIA의 입력을 만드는 문제이고, 문제 4는 외부 Agent가 업무를 수행할 인계 계약을 만드는 문제다. **문제 1 A + 문제 4 A**, **문제 1 B + 문제 4 B**, **문제 1 C + 문제 4 C**처럼 독립적으로 구성할 수 있다.

문제 4를 Agent 교체 후 일관된 경험을 설명하는 주요 심화 후보로 유지한다. 문제 4 B와 문제 1 C가 실제로 같은 기억 생산 상태를 사용한다면 공통 비용을 중복 계산하지 않고 하나의 구조 선택에서 두 사용 장면을 다룰 수 있다. 같은 기록을 이용한다는 이유만으로 인계 계약과 현재 발화 이해를 동일 문제로 합치지는 않는다.

기본 A/B/C의 선정은 미정이다. 선택할 정상 사용 조건, QA03/05 및 N-H의 차이, C의 지원 범위를 근거로 판단하고 필요한 tactic을 후속 선택한다. 이번 수정은 비교 순서와 설명을 정리한 것이며 source 사실, 외부 API 지원의 미확인 범위, 구현 및 측정 전 상태는 유지한다.

## 10. 2026-10-17 설계 권고

### 10.1 결론: 별도 DP로 유지하고 기본 A를 권고한다

**DP 질문은 ‘Agent가 바뀌는 후속 업무에 필요한 자료를 VIA가 위임 시 구성할지, 공통 업무 기록으로 계속 준비할지, 필수 명세 뒤의 세부 선택을 수신자에게 맡길지’다. 기본 A를 추천한다.** 작성자 권고이며 사용자 선정이나 실측 승자가 아니다. 세 안 모두 VIA가 허용된 공개 이력과 현재 조건을 보존한다.

사용자에게 제공할 핵심 가치는 Agent가 바뀌어도 목표, 수정, 채택한 결과와 실제 수행 범위를 다시 설명하지 않는 것이다. 이 기능은 A의 공통 기록과 목적별 인계 계약으로 성립한다. 지속적인 별도 의미 기록 B나 수신자 읽기 C를 반드시 요구하지 않는다. **현재는 이종 Agent와 달라지는 후속 목적을 기본으로 지원하되, 미래 재사용이 확인되지 않은 별도 의미 기록의 생산을 의무화하지 않는 선택을 권고한다.** 인계가 드물다는 실측 가정은 두지 않는다.

A의 단점은 위임 때마다 근거를 찾아 조합하는 대기다. 예를 들어 같은 비교 결과로 발표자료, 메일, 회의 안건을 연속 요청하면 B의 공통 기록이 이 조합을 상각할 수 있다. 그럼에도 A를 먼저 권고하는 이유는 현재 확정된 조건과 결과를 보존하는 공통 비용에 더해, 매 사건마다 별도 의미 기록을 만들 만큼 **추가 조합이 반복된다**는 근거가 아직 없기 때문이다. 단순 필드 복사만 필요한 업무에서는 A/B의 모델 비용 차이도 작을 수 있다.

A도 큰 결과 전체를 본문으로 복사하지 않는다. VIA가 필요한 자료와 판본을 정해 유효 첨부나 참조로 전달하는 기본 경로를 유지한다. C의 독자적 이익은 참조 사용 자체가 아니라 **수신 Agent가 상세 자료의 선택을 맡는 것**이다.

### 10.3 기본안의 세 주 평가 축과 상쇄

| 주 QA | 추천 A의 손익 | B의 반대편 이익 / 비용 | C의 반대편 이익 / 비용 |
| --- | --- | --- | --- |
| **QA03 VIA 처리시간** | 인계 때 원본 선택과 조합을 기다림. 이전 사건에는 미래 인계용 생산 대기를 추가하지 않음 | 현재 기록에서 추출하면 반복 인계의 준비를 단축. 갱신이 늦었거나 목적이 다르면 원본 보완까지 수행 | VIA의 상세 선택을 줄이고 명세 / 접근 계약을 준비. 읽기 준비가 기존 trial 경로에 있으면 그 대기 포함 |
| **QA05 VIA 모델 비용** | 실제 위임에 필요한 의미 조합만 수행. 같은 자료를 여러 번 조합하면 비용 반복 | 한 번 생산한 관계를 여러 번 사용. 미사용 기록과 정정 후 갱신, 목적별 추출도 모두 비용 | VIA의 상세 선택 호출을 줄일 수 있으나 수신 Agent의 판단 / 읽기로 비용이 이동. 전체 업무 비용 절감과 다름 |
| **N-H 업무 인계 정확도** | 현재 원본과 조건에서 조합하므로 stale 기록을 거치는 단계가 적음. 즉석 조합의 필수 항목 누락 가능 | 지속 기록이 조건 관계를 준비하지만 압축 누락 / 갱신 지연도 존재. 원본 보완으로 같은 계약이면 동점 | 필수 조건을 명세에서 누락하거나 필수 참조가 읽히지 않으면 실패. 세부 선택을 수신자에게 맡겼다는 이유만으로 실패시키지 않음 |

**QA03/05는 실제 기본 처리의 시간과 비용 차이 가설이고 N-H의 우열은 미확인이다.** B가 오래 기억한다는 이유로 인계 정확도를 높게 주지 않는다. 세 안의 공통 최종 검증이 같은 계약을 만들면 N-H는 동점이다. 현재는 세 축으로 평가할 의미 있는 독립 DP라는 권고이지, ‘서로 다른 세 QA의 실측 우열’이 확보됐다는 결론은 아니다.

권고의 판단 순서는 필수 인계 계약 충족, 실제 사용자 경로의 QA03 지연, 그다음 QA05 비용이다. A의 비용이 작아도 중요한 인계 장면에서 QA03 요구를 넘고 B가 이를 해소한다면 A를 유지할 근거가 약하다. A가 필요한 처리시간을 만족하는 범위에서는 쓰지 않을 의미 기록 생산을 추가하지 않는 이익을 선택한다. 기존 시간 / 비용 목표는 아직 검토 제안이므로 여기서 합격했다고 판정하거나 새 목표를 만들지는 않는다.

구체적 처리 의도를 먼저 표시했다면 그 뒤 인계 준비는 QA01 이득이 아니다. QA03의 상세 표시 / 전체 음성 요약 준비 종료점 이후 수신자의 읽기를 제공한 VIA 시간은 **별도 인계 운영 진단**으로 남긴다. 시험을 인계 준비가 끝나야 첫 응답을 하는 흐름으로 바꾸지 않는다. QA04는 실제 Rust 변경, QA06은 로컬 최대 RAM으로 회귀 확인하며 구조도만으로 수치 우위를 만들지 않는다.

| --- | --- | --- |
| **B 공통 업무 기록** | 여러 Agent가 동일한 공개 결과와 사용자 조건의 관계를 반복 소비하고, 추가 목적에도 기록의 상당 부분이 유효하며, 변경 빈도가 재사용 이익을 없애지 않음 | 업무 기록의 생산 / 갱신과 추출까지 넣어도 A의 반복 조합보다 QA05가 낮거나 QA03의 중요한 대기를 줄임. N-H가 요구를 만족하며 새 목적마다 원본 재구성을 반복하지 않음 |

단순히 Agent를 자주 바꾼다는 사실만으로 B를 고르지 않는다. 바뀌는 목적 때문에 기존 기록을 거의 못 쓰면 생산과 재구성 비용을 모두 낸다. 반대로 공통 업무 관계를 매번 재해석해야 한다면 A가 단순하다는 이유로 유지할 필요도 없다. C는 지원되는 작업자 집합에서 합리적인 주 구조가 될 수 있고, 미지원 Agent에는 A/B로 전환한 사실을 명시한다.

### 10.5 추가 source 확인과 적용 계약

[추가 근거 HC01~HC05](../../../../../references/five-problem-study/handoff-capability-check-20261017.md)에서 다음을 직접 확인했다.

- Deep Agents는 child FilesystemMiddleware에 같은 backend를 실제 전달하고 권한 검사 후 범위 읽기를 실행한다. 저장 namespace도 맞아야 하며 이종 Agent의 읽기 지원을 뜻하지 않는다.
- OpenClaw의 acpx adapter와 의존 버전에 맞는 acpx 0.19.4는 capability를 확인해 resume 또는 load를 호출한다. 재개는 같은 harness의 지원 기능이며 다른 제품으로 내부 상태를 이동하는 기능이 아니다.
- OpenClaw에는 저장 session 초기화가 실패하면 ID 없이 새로 초기화하는 경로가 있다. VIA는 session ID가 있다는 사실만으로 이전 문맥이 복원됐다고 판단할 수 없다.
- acpx의 파일 읽기는 파일 내용을 읽은 뒤 요청 줄 범위를 잘라 반환한다. C의 작은 반환량만으로 QA06이나 I/O 절약을 주장할 수 없다. protocol과 adapter마다 지원이 다르다.

이는 A/B/C의 실현 가능한 경로와 지원 조건을 보강한다. VIA의 source revision, 철회, 필수 조건 계약과 실제 재개 판정은 추가 설계이며 외부 source의 구현 완료 사실로 표시하지 않는다.

### 10.6 선택 후 추천 tactic: A1, 조건부 A2

| 추천 구성 | 보완할 A의 약점 | 추가 처리와 손익 | 적용 경계 |
| --- | --- | --- | --- |
| **A1 인계 묶음 cache** | 같은 목적 / 원본 / 조건으로 다시 구성하는 QA03/05 | 유효 묶음을 재사용하되 현재 source, 조건, 접근권한과 수행 범위를 검사. 저장과 무효화 비용 증가 | 같은 목적의 반복에 우선 적용. 목표나 완료 조건이 달라지면 cache 적중으로 세지 않고 기본 A로 구성 |
| **A2 native session 재사용** | 같은 Agent의 짧은 후속 수정에 이미 제공한 자료를 다시 조합 / 전송 | 지원과 동일 session 재개가 확인되면 이미 전달한 유효 자료 본문을 재사용. capability, 반영 지점과 session 실패 처리 추가 | 필수 목표 / 조건 / 금지 수행 범위는 새 인계 revision에 명시. 새로운 Agent, fresh session 또는 재개 불명일 때는 기본 A로 돌아감 |

A2가 외부 입력 token만 줄이면 그 이익은 외부 비용 진단이다. VIA의 조합 호출까지 줄어야 QA05 이익이고, 원래 QA03 경로 안의 준비가 줄어야 QA03 이익이다. native session에서 특정 자료가 유효하게 남았는지 확인할 방법이 없으면 그 자료를 생략하지 않는다. A1과 A2는 자동 누적하지 않으며 결합 비용도 별도로 기록한다. 현재 조건 / 실행 불명 검사와 큰 자료 참조는 원래 기본 기능이다.

먼저 해석 입력과 최초 지칭 / 관계 채택을 고정하여 인계 구조만 비교한다. 원본, 현재 조건, Agent capability, 사건 시간, 모델, 자원 예산과 oracle은 같다. 각 기본안에 필요한 파생 상태는 동일 사건으로 실제 생성해야 하며 B의 준비된 기록이나 C의 유효 접근 계약을 무료로 주지 않는다. A/B는 원래 지원하는 첨부 / 참조를 사용할 수 있다.

외부 실행을 허가하는 고정 지점에서 `(Task, request revision, execution attempt, delegation revision)`의 계약을 N-H로 판정한다. 참조의 유효성은 동일한 자료 읽기 계약으로 확인한다. C의 수신자가 이후 어느 범위를 고르는지는 고정된 읽기 요청으로 자료 제공 동작만 분리 확인할 수 있으나, 이 대역 시험으로 실제 Agent의 좋은 자료 선택이나 업무 품질을 증명하지 않는다.

**완료 및 권고 변경 규칙은 다음과 같다.**

1. 필수 조건, source 판본, 허용 범위, 실행 불명, 철회가 같은 oracle과 일치해야 한다. 재현되는 필수 계약 위반은 해당 구현 / 구성의 보완 사유이며, 나중의 수정 계약으로 실패를 지우지 않는다. 올바른 보류는 미리 정한 보류 계약으로만 성공 판정한다.
2. 같은 기능과 N-H를 유지하면서 A가 B보다 실제 위임 목적에 맞는 총 준비 비용이 작다면 A 권고를 지지한다. 반복 인계에서 B의 생산 / 갱신을 포함해도 QA03/05가 개선되고 목적 변경 시 재구성이 적다면 B 권고로 바꿀 근거가 된다. 반대로 유지 기록이 매번 원본 보완을 요구하면 B의 상각 가설은 반증된다.
3. C는 지원 가능한 adapter에서만 구조 효과를 따로 확인한다. 지원 불가 비중을 제거한 수치를 전체 지원 결과로 제시하지 않는다. VIA 비용만 외부 Agent로 옮겼거나, A가 유효 자료 참조를 보내는 것과 처리 차이가 없다면 C의 비용 우위는 반증되거나 미확인이다.
4. QA03 종료점 이후 serving, 외부 token 비용과 작업 완료시간은 별도 진단으로 보존한다. 공식 QA05는 COMMON-28 전체 비용이며 위 장면만의 부분합으로 대체하지 않는다. 준비 / 미사용 생산, 폐기와 재시도를 포함한다. 기존 목표와 모집단을 이번 문서에서 바꾸지 않는다.
5. QA01/02는 공통 채택 뒤 인계만 바꾸는 장면에서 동점이다. N-H도 동점이면 이 DP는 QA03/05의 설계 trade-off와 기능 중요성으로 유지하되, 세 번째 실측 차이를 확보했다고 발표하지 않는다. 반응시간 차이가 반복 변동과 구별되지 않으면 그 축도 차이 확인으로 세지 않는다.

현재 권고는 **공개 이력의 지속 보존 + 문제 4의 A + 반복 장면의 A1, 지원이 확인된 같은 Agent에서의 A2**다. B/C는 실제 비용과 조건이 다른 대안으로 유지한다. 이 결론은 의미 기록 생산이나 native session에 사용자의 전체 경험을 종속시키지 않고도 Agent 교체 가치를 구현할 수 있다는 설계 판단이다.
