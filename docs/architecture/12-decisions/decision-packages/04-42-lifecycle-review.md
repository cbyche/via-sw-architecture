## 3. 메인 그림 반복 검수

메인 그림은 2560×1440이고 1280×720 축소 렌더도 확인했다. 공통 입력·Omni·업무 기능을 같은 검정으로 두고, A의 트랜잭션 관리자/저장과 B의 각각의 저장·process 경계만 다른 topology로 표시한다. 아래는 최초 작성 검수이며 이후 사용자 리뷰의 수정은 §5에 기록한다.

| 발견 | 조치 |
| --- | --- |
| 첫 렌더에서 Agent 연동 축약 주석과 업무 확정 화살표 라벨이 겹침 | 주석을 본문 범위 설명으로 옮기고 화살표 주변 여백 확보 |
| 입력·모델 선이 process 제목과 겹침 | component 제목과 입력 port를 이동하고 모델 왕복을 별도 통로로 배치. SVG와 draw.io 제목 위치를 함께 조정 |
| 모델 입력과 결과 라벨의 실제 glyph 영역이 겹침 | 반환 라벨을 별도 높이에 배치하고 browser text bounding box로 재확인 |
| 단순 ‘위임’ 화살표가 저장 이전의 외부 실행처럼 읽힐 수 있음 | 양안 모두 ‘확정 후 위임’으로 표기하고 접수·질문·결과 반환을 분리 |
| B 장점 문구가 모듈성 우위를 무조건 주장할 수 있음 | ‘계약 호환 시 독립 갱신’으로 조건을 그림 안에 명시 |

**그림만 읽는 검토:** 사용자 입력 → 대화 처리 → 업무 변경 → A 공동 확정/B 각자 확정 → 외부 위임 → 접수/질문/결과 → 사용자 응답을 따라갈 수 있는지 대조했다. 저장소 이름과 process 경계만으로도 핵심 차이를 확인한다. 공통 Omni는 양안의 같은 dependency를 반복한 표시다.

**글만 읽는 검토:** §3의 owner와 commit, §4의 동일 사건, §8의 cheap conversion, §9의 반대 선택 조건이 그림 없이 연결되는지 확인했다. 그림의 요약과 본문이 서로 다른 수준의 권한을 주장하지 않게 맞췄다.

## 4. 검증 결과와 한계

도식의 직교 경로·XML·생성물 일치 검사는 설계 효과 검증이 아니다. 렌더는 별도 임시 프로필의 headless Chrome에서 로컬 SVG를 열어 수행했다. 사용자 브라우저의 기존 탭이나 로그인 정보는 사용하지 않았다.

| 검사 | 결과 |
| --- | --- |
| 신규 42 생성기 `--check` | 다섯 SVG/draw.io 쌍과 gallery 일치, XML ID/참조, owner 포함, canvas, 직교 경로 PASS |
| 기존 도식 생성기 일곱 종류 | target, 기존 decision package, Stage 4, mechanism, functional, 31~36, 41 모두 PASS |
| 활성 문서 링크·용어·QA registry | Markdown 144개 링크, 정식 용어, QA 23개와 기존 핵심 ASR 4개 registry PASS |
| 브라우저 실제 렌더 | 다섯 SVG 전체 시각 검사. 메인 2560×1440와 1280×720 확인. 최종 글자 canvas 넘침 및 글자 영역 간 겹침 없음 |
| 보존 범위 대조 | Git HEAD 대비 31~36/41 본문과 기존 choice 도식, 참조 Architecture, QA/ADR 변경 없음 |
| 공백 검사 | `git diff --check` PASS |

메인 PNG는 최종 SVG의 브라우저 렌더를 내보낸 발표 편의본이다. 편집 원본은 draw.io, 재생성 원본은 Python scene이다. 원본을 수정하면 SVG/draw.io를 함께 생성하고 PNG도 다시 내보내야 한다. 로컬 CI 항목 실행 결과이며 원격 CI 실행이나 commit/push 완료를 뜻하지 않는다.

- native draw.io 편집기에서 직접 이동·저장하는 round-trip 검증은 하지 않았다. XML의 owner/edge 참조와 SVG와의 생성 source 일치를 확인하는 범위다.
- 외부 사례는 읽기만 수행했고 runtime을 설치·실행하지 않았다. 저장소의 후보 구현·모델·측정도 실행하지 않았다.
- 31·33·41과 참조 Architecture의 본문·도식, 32의 제외 상태는 보존한다.
- 작성 완료는 사용자 승인이나 선택안의 효과 입증이 아니다. B의 독립 운영 가치와 상위 기능 품질 유지가 이후 판단의 핵심이다.

## 5. 사용자 리뷰에 따른 메인 그림 수정 (2026-10-05)

사용자는 갱신·재시작을 드문 사례로 판단하고 B의 대표 이익으로 설명하는 것을 거부했다. 또 ‘공동 확정기’의 역할과 B에서 이를 대신하는 처리가 메인 그림에 드러나야 하며 이름도 역할을 대표해야 한다고 지적했다.

- 이름을 **트랜잭션 관리자**로 바꿨다. 양쪽 변경을 모아 한 번에 저장하고 실패하면 둘 다 미반영하는 로컬 저장 책임이다. 중앙 의미 판단, 외부 Agent 접수 보장, 전역 직렬화를 뜻하지 않는다.
- 같은 일상 요청 “이 자료로 보고서를 만들어줘”를 메인 그림의 사례로 삼았다. A의 요청↔T1 연결과 T1·전송 명령이 합쳐지는 경로를 라벨에 표시했다.
- B의 대기 요청 저장 → 업무 측 접수·로컬 저장 → 대화에 접수 결과 반영을 표시했다. B에도 각자의 트랜잭션과 조정이 필요함을 드러냈다. 갱신·장애를 메인 그림의 이익 문구에서 빼고 저장 소유와 비용을 적었다.
- **판정 한계:** 이는 설명 보완이다. B의 중요한 정상 사용상 이익은 여전히 강한 A와의 추가 설계 판단이 필요하다. 구조 설명 개선을 주요 비교 자격의 최종 승인이나 B 선택 근거 확보로 취급하지 않는다.
- 변경한 메인 그림과 A 사건도를 실제 렌더해 확인했다. 메인은 2560×1440/1280×720으로 확인했고, 두 그림의 텍스트 canvas 넘침 및 텍스트 영역 간 겹침은 없었다. 생성물 일치/경로 검사, 활성 Markdown 링크 검사와 공백 검사를 수행했다. 나머지 설계의 재심사나 성능 측정을 한 것은 아니다.

## 6. 조회 응답과 내부 접수 및 외부 Agent 알림 분리 (2026-10-05)

사용자는 양안의 5번 ‘접수 결과·상태’가 모두 필요한지, 업무→대화 방향이 맞는지 지적하고 구분을 요청했다. 기존 라벨은 A의 저장 결과와 B의 별도 내부 접수 응답, 외부 Agent 사실을 섞어 차이를 감췄다.

- 양안 공통 5번은 **Agent 알림**이며 외부 Agent의 접수·진행·질문·결과만 가리킨다. 외부 Agent→업무 관리기 화살표에도 같은 외부 사실을 표시했다.
- 양안에 조회 응답 화살표를 별도로 두었다. 변경 요청/질문 답변은 반대 방향의 2번 제안/명령 경로다.
- B에만 **VIA 내부 접수 결과 (4 저장 후)**를 업무→대화 별도 경로로 표시했다. A는 트랜잭션 관리자가 보내는 **로컬 저장 결과**를 사용하며 같은 사실을 업무→대화로 재전달하는 단계를 필수로 추가하지 않았다.
- 본문 §1에 각 반환 경로의 생산자·소비자·의미를 대응시켰다. E4 사건도의 조회 응답, B 내부 접수 응답, 외부 접수 반환과 대조했다. A 사건도에서 생략했던 트랜잭션 관리자→대화 처리기의 로컬 저장 결과도 표시해 메인 그림과 맞췄다.
- 첫 렌더에서 외부 Agent 설명과 반환 라벨의 겹침을 발견해 이동했다. B 내부 응답의 긴 우회 경로를 저장소 위의 짧은 반환 경로로 줄이고 모델 결과 경로와 조회 응답 라벨도 분리했다. 최종 메인 원본/720p와 A 사건도를 렌더해 확인했고 텍스트 영역 간 겹침·canvas 넘침은 없었다. XML·생성물·경로, 활성 링크와 공백 검사도 통과했다. 메인 PNG를 최종 SVG 렌더로 갱신했다. 설명과 경로의 정정이며 구조의 품질 효과 검증은 아니다.

## 7. 수명·소유·협력 세 층으로 메인 그림 재구성 (2026-10-05)

사용자는 원래 A/B의 의도를 유지하고, 같은 수명 기능·소유 경계·협력 방식이 메인 그림 자체에서 모두 읽혀야 한다고 요구했다. 그림이 별도 설명에 의존하면 실패라는 검토 기준이다. A의 한 Core를 모든 일을 하는 한 모듈로 해석해 재정의하려던 답변은 철회했으며, 중앙/분산 Omni 해석이라는 새 비교를 도입하지 않는다.

| 그림만 읽을 때 확인할 질문 | 그림 안의 근거 |
| --- | --- |
| 요청 접수 뒤 무엇이 남는가? | 상단 R1은 접수 후 종료. C1 기록과 Task T1, 실행 X1은 이어지는 서로 다른 선 |
| 다른 대화로 이동하면 Agent 질문은 어떻게 되는가? | C2 전환 시점을 가로질러 Q1 대기가 이어지고 C1 복귀·답변에서 종료 |
| 결과 뒤 수정은 기존 실행을 재개하는가? | T1은 유지되지만 X1은 결과 시점에 끝나고 후속 수정에서 X2 시작 |
| 이 상태를 누가 관리하는가? | 하단의 대화 C1·요청 R1과 업무 T1·실행 X1/X2·Agent 질문 Q1을 대화/업무 관리 영역에 직접 표시. A는 한 Core process, B는 각각의 service process와 저장 권한 |
| 어떻게 협력하며 어디서 결과를 받는가? | A 내부 조회/변경 제안·공동 저장·로컬 저장 결과, B 조회/명령·별도 저장·내부 접수 응답. 양안 공통 외부 Agent 알림은 별도 경로 |

### 수정과 의미 대조

- 메인 그림을 한 요청의 저장 절차 중심에서 공통 수명 축과 소유 구조 중심으로 재구성했다. 트랜잭션 관리자를 작게 배치하되 역할과 반환을 삭제하지 않았다.
- 입력·Omni·Downstream Agent의 공통 경로를 유지했다. Omni 호출 위치를 바꾸거나 새 업무 의미 해석기를 추가하지 않았다. A도 논리적으로 서로 다른 수명을 지원한다.
- 검토 중 A의 로컬 저장 결과 반환이 5번 외부 알림과 같은 선 구간/port를 공유해 양방향 화살표처럼 보이는 문제를 발견했다. 저장 결과는 Module 하단 port, 외부 알림은 업무→대화 측면 port로 분리했다.
- 외부 Agent 알림 라벨과 업무 서비스 제목의 겹침, 입력 선과 Core 제목의 관통을 실제 렌더에서 발견해 우회 경로와 위치를 수정했다. 단순 텍스트 겹침 검사만으로 경로 의미를 확인했다고 판단하지 않았다.
- C1/R1/T1/X1/X2/Q1 표기를 수명 축과 상태 소유 영역에 반복해 초심자가 두 층을 대응할 수 있게 했다. 종료된 처리의 기록 삭제를 뜻하지 않으며 시간축은 소요시간 측정이 아니다.

최종 메인 그림의 2560×1440 원본과 1280×720 축소본을 렌더해 시각 확인했다. 텍스트 영역 간 겹침·canvas 넘침 없음, 42 생성물/소유/직교 경로 검사, 활성 Markdown 144개 링크, 용어 및 공백 검사 통과를 확인했다. 메인 PNG는 최종 SVG 렌더로 갱신했다. draw.io는 같은 scene의 XML 원본이며 native 편집기 round-trip은 검증하지 않았다.

생성물·렌더·본문 정합 검사는 이번 그림의 표현 범위에 한정한다. 세 층의 이해 가능성에 대한 최종 사용자 수용이나 A/B 구조의 품질 효과 입증으로 해석하지 않는다. B의 강한 A 대비 중요한 정상 사용상 이익은 별도로 검토 중이다.
