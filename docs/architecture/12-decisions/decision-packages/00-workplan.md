**다음 작업:** QA 문서를 처음부터 다시 만들지 말고 상세안과 독립 리뷰의 최종 상태부터 읽는다. 목표값은 모두 검토 제안이며 실제 점수는 없다. 44의 실용 속도 차이, 47의 B 이익, 42의 세 번째 차이 축과 정상 사용 B 이익이 부족한 상태다. 이 구조 손익을 먼저 보강 검토하고 선정 조건을 다시 확인한다. QA 정의의 완성과 DP 비교구도의 적합성은 별개다. 추가 07·08·09를 자동 핵심 QA로 넣거나 새로운 구현·모델 실행·Windows 측정·최종안을 시작하지 않는다.

사용자는 SW Architect 양성과정에서 핵심 QA로 각 DP의 두 설계 방안을 평가하고 trade-off를 근거로 최종안을 선정해야 한다고 설명했다. 아래 기준에 대한 이해를 확인한 뒤 저장소에 기록하고 QA와 DP를 오가며 검토하도록 요청했다. 이 절은 앞으로의 QA·DP 선정 작업 기준이다. 기존 QA 정의와 측정 결과를 새 기준에 맞는 것으로 소급 해석하지 않는다.

### 합의한 선정 기준

| 항목 | 기준 |
| --- | --- |
| 핵심 QA 수 | 4~6개 정도 |
| QA의 명확성 | 각 QA는 하나의 분명한 품질과 하나의 명확한 지표로 정의한다. |
| 핵심 DP 수 | 4개 정도. 실제 처리 구조가 다른 두 강한 방안을 비교한다. |
| DP별 비교 범위 | 핵심 QA 중 3~4개 정도에서 두 방안의 성능 차이와 trade-off를 평가한다. |
| QA별 커버리지 | 각 핵심 QA는 최소 2개 이상의 DP에서 실제 성능 차이를 평가하는 대상으로 쓰여야 한다. |
| 1순위 QA와 DP | 1순위 QA는 1순위 DP의 주된 설계 목표여야 한다. |
| 1순위 QA의 커버리지 | 4개 DP 모두에서 두 방안의 성능 차이를 평가하는 것이 가장 바람직하며 차선은 3개 DP다. |

**커버리지는 단순한 관련성이나 측정 가능성이 아니다.** 해당 QA에서 두 방안의 성능 차이가 확인되고 그 차이가 선택 근거로 쓰이는 DP를 센다. 동점인 QA는 그 DP의 trade-off 커버리지로 세지 않는다. 동점인 기능·품질의 회귀 확인은 여전히 필요하지만 차별화 근거와 구별한다.

### 여러 DP에서 동일한 QA를 사용하는 조건

- QA의 정의, 측정 대상, 평가 단위, 지표와 판정 의미를 유지한다. 시험 상황은 달라도 무엇을 측정하는지가 바뀌어서는 안 된다.
- 같은 백분율 산식이나 같은 이름만으로 서로 다른 품질을 묶지 않는다. DP별로 지칭 정답, 이력 검색 정답, 상태 오류를 따로 측정하고 하나의 정확성으로 표시하는 방식은 허용하지 않는다.
- 반대로 특정 DP에서만 유효한 좁은 지표를 핵심 QA로 확정한 뒤 다른 DP에 억지로 적용하지 않는다. 필요하면 개별 DP의 보조 진단으로 남긴다.
- 하나의 대표 지표는 다른 품질의 점수를 가중 합산해 만드는 종합 점수가 아니다. 오류 원인 진단과 필수 기능 조건은 대표 지표의 의미를 바꾸지 않도록 별도로 설명한다.
- DP별 평가 사례의 구성이 다르면 수치를 단순 합산하거나 DP 사이의 절대 성능 순위로 읽지 않는다. 각 DP 안에서는 동일한 입력과 조건으로 두 방안을 비교한다.

### 반복 검토 방법

1. **사용자 가치에서 QA 후보를 정의한다.** 이름, 한 문장 정의, 단일 지표, 평가 단위, 좋은 방향, 포함·제외 범위를 적는다.
2. **DP 구조에서 차이의 원인을 찾는다.** 방안별 데이터, 실행 의존, 저장·확정·재처리 차이가 어떤 경로로 그 지표를 바꾸는지 설명한다. 유리한 조건과 불리한 조건, 반증 조건을 함께 적는다.
3. **QA×DP 대응표로 왕복 확인한다.** DP별 3~4개 QA, QA별 최소 2개 DP, 1순위 QA의 3~4개 DP 연결을 점검한다.
4. **부족한 연결을 재검토한다.** QA의 의미와 범위, 지표 또는 DP의 비교 구도와 선정 근거를 다시 살핀다. 현재 DP를 임의로 제외하거나 번호를 바꾸지 않고 변경 필요성과 근거를 사용자와 검토한다.
5. **측정 방법과 차이 판정 기준을 구체화한다.** 동일 기능 목표, 원본 근거, 모델 조건과 외부 조건에서 비교한다. 강한 방안의 cache, 병렬 처리, 부분 갱신을 제거해 차이를 만들지 않는다.
6. **평가 결과로 선정 근거를 갱신한다.** 평가 전의 차이 가설과 평가 후의 확인된 차이를 구별한다. 동점·불확실 결과는 보존하고 커버리지 부족을 드러낸다. 차이가 확인된 QA의 우선순위와 손익을 근거로 최종안을 논의한다.

대응표의 각 칸에는 **차이의 구조적 원인 / 적용 상황 / 예상 손익 / 확인 방법 / 근거 상태**를 남긴다. 근거 상태는 `미검토`, `차이 가설`, `차이 확인`, `동점`, `불확실`, `비적용`으로 구별한다. 설계 단계의 가설 연결 수와 평가 후 확인된 커버리지 수를 따로 표시하며 현재 단계에서 측정 결과를 만들어 채우지 않는다.

매 논의가 끝나면 다음 내용을 이 작업 계획 또는 연결된 검토 문서에 갱신한다.

- 합의한 내용과 아직 제안인 내용
- QA 정의·지표 또는 DP 비교에 미친 변경과 이유
- 대응표의 가설 및 확인 상태와 커버리지 부족
- 다음에 검토할 질문

| 6 | 로컬 메모리 사용량 | 동시 최대 전체 commit 메모리 | Windows PC의 다른 업무와 공존해야 한다. 요구 장치의 수용 한계는 순위와 별도로 지킨다. |

사용자 기능과 합의한 최소 품질·자원 조건을 충족하는 대안 사이에서 우선순위를 적용한다. 빠른 오답이나 저비용 미처리를 상위 QA 우세로 취급하지 않는다. 차이의 실용적 크기와 불확실성을 확인하며 미세한 상위 차이로 모든 하위 손실을 자동 정당화하지 않는다. 실제 최소 기준과 차이 판정값은 아직 미정이다.

**DP 제안 순서: 44 → 47 → 45 → 42.** 44는 사용자 입력과 Agent 사건이 교차할 때 첫 반응과 후속 대화 실행을 직접 다룬다. 47은 말과 화면 행동으로 대상을 지정하는 VIA의 핵심 사용 방식을 다루며 첫 반응과 지칭 정확성을 함께 좌우한다. 45는 과거 근거의 재사용과 새 관계 구성으로 반복 요청의 정확성·반응·비용에 영향을 준다. 42는 대화와 업무 수명을 연결하는 기반이며 비교안의 정상 사용 이익이 아직 약해 구체 검증이 필요하다. 이 순서는 기능 구현 순서나 대안의 승패가 아니다.

| --- | --- | --- | --- | --- | --- |
| 상호작용 응답시간 | 후보 | 후보 | 후보 | 후보 | 4 |
| 지칭 대상 식별 정확성 | — | 후보 | 후보 | — | 2 |
| VIA 요청 처리시간 | 후보 | — | — | 후보 | 2 |
| 변경 용이성 | 후보 | — | 후보 | — | 2 |
| 모델 사용 비용 | — | 후보 | 후보 | — | 2 |
| 로컬 메모리 사용량 | — | 후보 | — | 후보 | 2 |
| DP별 우선 검토 축 | 3 | 4 | 4 | 3 | 확인된 커버리지 아님 |

빈칸은 비적용 확정이 아니며 우선 설명할 축을 고른 것이다. 다른 축의 중요한 손익도 공개한다. 실제 확인된 차이는 아직 없으며 변경 용이성의 모듈 수 차이와 DP-42 분리안의 정상 사용 이익은 주요 검증 질문이다. 세 축 모두 한 안이 우세하면 차이는 있어도 반대편 이익을 가진 trade-off가 설명된 것은 아니다.

**지칭 정확성의 동일 평가 경계:** 47과 45 모두 최종 채택한 지칭 대상 집합을 사용자 의도의 정답 집합과 비교한다. 47에서는 화면 자료·범위, 45에서는 과거 자료·설명 항목·버전이 대상이다. 45에서 반환 근거 자체의 채점으로 지표를 바꾸지 않으며 후속 판단 조건을 고정하고 근거 공급 구조의 영향을 평가한다. 무관한 내용 요약 오류나 처리 상태 오류를 이 정확성 지표에 섞지 않는다.

#### 변경 모듈 수 제안

Rust의 `mod`와 crate root가 만드는 모듈 경로를 식별 단위로 삼는다. 모듈은 관련 함수·자료형과 공개/비공개 범위를 묶는 코드 단위다. `.rs` 파일, crate와 process는 각각 다른 개념이다. 한 파일에 inline 모듈을 여러 개 둘 수 있으므로 파일 수를 대신 세지 않는다. [Rust 공식 모듈 설명](https://doc.rust-lang.org/book/ch07-02-defining-modules-to-control-scope-and-privacy.html), [파일 분리 설명](https://doc.rust-lang.org/book/ch07-05-separating-modules-into-different-files.html), [package/crate 설명](https://doc.rust-lang.org/book/ch07-01-packages-and-crates.html)을 기준으로 한다.

- 평가 전 양안의 실제 구현 예정 모듈 목록, crate 식별자(lib/bin 구별), 경로, 소스·소유 자산, 인터페이스와 의존을 고정한다. 양안의 모듈 수나 구성을 같게 만들지는 않는다.
- 같은 변경 과제를 완료하기 위해 수정·추가·삭제한 고유 운영 모듈을 각 1개로 센다. 하나의 모듈에서 여러 함수를 바꿔도 1개다.
- 자식 코드 수정만으로 부모를 재귀 가산하지 않는다. 부모 자신의 연결 코드나 API도 변경해야 한다면 별도로 센다. inline 자식의 수정도 부모 파일 전체 수정으로 중복 계산하지 않는다.
- 테스트 전용 코드, 주석·포맷 변경과 자동 생성 결과의 재출력은 별도 모듈로 가산하지 않는다. 수작업 생성 원본과 실제 운영 API·연결 변경은 추적한다.
- prompt/schema/config 같은 동작 자산을 외부 파일로 옮겨 변경 수를 0으로 만들지 않는다. 사전에 해당 자산을 소유하는 실제 모듈에 매핑하고 그 구현 자산의 변경을 해당 모듈의 변경으로 센다. 단순 파일 이동·이름 변경은 동일 모듈의 이력을 연결해 이중 계산하지 않는다.
- 모듈 크기와 분해 원칙을 사전 검토한다. 모든 책임을 한 거대 모듈에 몰아 점수를 낮추거나 대안 한쪽만 미세 분할하지 않는다. 전체 모듈 수와 규모·실제 diff를 보조 자료로 남긴다. 책임 수로 다시 합산하지 않는다.
- 지표는 `공통 변경 과제별 고유 변경 모듈 수의 합 / 변경 과제 수`다. 낮을수록 수정 파급이 작다는 뜻이며 개발시간 전체를 직접 측정한 값은 아니다.

현재 확인한 활성 구현 경로에 Cargo.toml/`.rs` 파일은 없다. Rust 모듈 대응을 먼저 구체화하고 구현 전에는 설계 기반 변경 영향 분석이라고 표시한다. 실제 변경·검증을 수행한 뒤에만 실측 수정 모듈 수로 보고한다. 이 문서 검토로 Rust 구현을 시작하지 않는다.

#### 첫 유효 반응의 구체화 제안

설명 용어를 **필수 응답 개시시간**으로 구체화한다. 의미는 `입력 사건 이후 그 사건에 대해 사전에 정한 필수 응답 내용이 실제 사용자 출력에서 전달되기 시작할 때까지의 시간`이다. 무엇이 필수 응답인지는 평가 전에 사례별로 정한다.

| 사건 | 시작점 | 인정할 응답 |
| --- | --- | --- |
| 사용자 Voice 요청·정정 | 실제 발화의 마지막 음성 sample 종료 | 정답 정보 또는 대상·범위가 식별되고 실제 접수 단계와 일치하는 처리 상태 안내 |
| 사용자 Text 요청·정정 | 사용자가 입력을 제출한 시점 | 위와 같은 필수 응답 |
| Agent 질문·결과·상태 | source interface에서 해당 사건이 소비 가능해진 최초 시점 | 해당 업무에 연결된 질문·결과·확인된 상태의 전달 |

종료점은 Voice ON에서 정답 응답 구간의 핵심 내용이 실제 재생되기 시작한 시점, Voice OFF에서 해당 내용이 화면에 실제 표시된 시점이다. 음성 평가에서 먼저 표시된 Text나 첫 토큰/audio packet·enqueue 시각으로 대체하지 않는다. 의미 있는 내용의 첫 sample은 녹음된 실제 출력과 미리 정한 필수 내용으로 판정한다. 처음의 핵심 단어만 맞고 응답 구간의 의미가 틀리면 유효 종료점으로 인정하지 않는다.

`네`, `알겠습니다`, `처리할게요` 같은 단독 접수 인사, earcon/spinner, 식별되지 않은 지칭의 반복과 근거 없는 완료 선언은 제외한다. 확인이 필요한 사례는 구체적 확인 질문을 정답 응답으로 정하고 명확한 요청에 불필요한 재질문을 한 것을 빠른 성공으로 세지 않는다. 접수·전송·외부 접수·업무 완료를 구분해 실제 확인한 단계만 안내한다. 대상과 범위를 확정해 요청을 저장한 사실을 알리는 응답은 외부 Agent 작업 완료까지 기다릴 필요가 없다.

끼어들기 이후 음성 중단은 `사용자 발화 시작 → 중단 대상의 마지막 실제 재생 sample`로 별도 제어 반응을 관측하고 위 내용 응답 평균에 혼합하지 않는 안을 제안한다. 중단 뒤 정정에 대한 내용 응답은 사용자 발화 종료부터 별도로 잰다. 이는 기존 ASR-QA-02 모집단을 그대로 유지한 것으로 표시하지 않는다.

미응답·오답을 평균에서 삭제하지 않는다. 사전 공통 평가 상한까지 유효 응답이 없으면 상한값과 실패를 함께 기록하는 방식으로 구체화한다. 응답 유형별 사례 비율, 필수 내용, 상한값, 합격선과 차이 판정값은 평가 전 합의할 항목이며 아직 수치를 정하지 않았다. 기존 [사건 경계 원칙](../../11-measurement/event-boundary-contract.md)의 실제 사건·실제 재생 관측 원칙을 따르되 이전 QA ID와 집계 계약을 소급 변경하지 않는다.

## 2026-10-14 DP-47 reference를 반영한 실제 구현 요소와 pattern 구체화

사용자는 §8.5의 그림만으로 실행 흐름, SW 구성요소의 실체와 architectural style/pattern을 이해할 수 있도록 구체화해 달라고 요청했다. [47 §8.5](./04-47-screen-voice-grounding.md#85-구현을-가정한-상세-구조와-실행-계약)의 A/B 구조도와 두 사건도를 갱신했다. A는 비동기 workflow와 하나의 binding aggregate, B는 coordinator가 제어하는 Fork–Join/feedback dataflow와 생산자별 candidate repository다. 공통 30개 요소는 같은 좌표에 두었다.

로컬 bounded FIFO, 단일 consumer 제어 loop, 역할별 async worker, immutable job/outcome DTO, 원본 ring 및 RAM Map, State Store의 영속 채택을 서로 다른 기호와 이름으로 표시했다. 공통 read/model adapter는 R/M 명명 port로 연결했다. BeginRevision과 TryPublish의 요청별 RevisionGate, queue 포화와 완료 통지, B의 snapshot 준비 조건 및 producer 재판단을 본문과 사건도에 맞췄다. 외부 message bus/pub-sub는 선택하지 않았으며 이유를 명시한다. 공개 reference의 확인 사실과 이 구현 가정을 구별한다.

네 SVG/draw.io와 PNG 및 렌더 해시를 동기화했고 실제 PNG를 열어 확인했다. [작성자 검수 §9](./dp47-design-review.md#9-reference를-반영한-queue-data-model과-pattern-검수--2026-10-14)에 검사와 한계를 기록했다. 생성물, 본문 그림 포함, 링크, 용어, QA registry 및 가운데 점 검사가 통과했다. 제품 코드 구현, Windows/API/모델 실행, 측정 또는 A/B 선택을 수행한 기록은 아니다.

## 2026-10-13 DP-47 안별 구현 수준 구조와 정정 사건도

사용자는 DP-44 §3.7을 참고하여 DP-47도 실제 구현을 가정한 안별 SW Architecture와 주요 flow를 더 상세히 설명하고 commit/push하도록 요청했다. [47 §8.5](./04-47-screen-voice-grounding.md#85-구현을-가정한-상세-구조와-실행-계약)에 A/B 구조도 두 장과 정상 생성/후보 부족/부분 정정/늦은 결과 사건도 두 장을 추가했다. 공통 27개 요소의 위치와 크기를 고정하고 A의 원본 기반 직접 binding/patch와 B의 생산자별 후보 게시, version 결합과 원 생산자 재판단을 실제 호출/반환 및 상태로 구별한다.

네 그림은 SVG/draw.io와 3840×2160 PNG를 동기화하며 본문 그림 목록에 모두 등록했다. 번호별 실행 계약, owner별 조건부 상태 게시, source/peer 의존, 외부 전송 전 사용권 검사와 최종 채택 경계를 구체화했다. 생성기, 렌더 해시와 본문 등록 검사를 기존 DP-47 검사 및 CI에 연결했다. [작성자 검수](./dp47-design-review.md#8-구현-수준의-안별-구조와-사건도-검수--2026-10-13)를 기록하며 제품 구현, 모델/API 실행, 성능 측정이나 대안 선택으로 확대하지 않는다. 기존 MAIN/배경과 다른 DP, 참조 Architecture, QA/ADR 및 PPTX는 유지한다.

## 2026-10-13 DP-44 대화 실행 범위와 본문 그림 통합

사용자는 DP-44를 자연스러운 청취와 발화 실행 구조로 설명하고, 가운데 점 제거와 관련 그림의 본문 통합을 요청했다. [44 §0](./04-44-continuous-interaction.md#0-먼저-확인할-dp의-범위와-전체-그림)에 핵심 세 Component와 사용자 입력 및 Agent 질문/결과의 공통 경로를 명시했다. Agent Gateway 다음의 Task Manager 사실 확인과 저장, Request Controller의 대화 연결 및 admission을 생략하지 않으며 Request Controller와 Task Manager의 협력은 A/B 공통이다.

배경, 공통 경로, 전체 및 집중 비교, 구현 A/B와 사건도 일곱 장을 모두 본문에 직접 표시했다. DP-44 문서와 개별 도식, 생성 원본 및 통합 draw.io의 해당 페이지에서 문장부호와 배선을 정리했다. 실제 일곱 PNG의 렌더 검수와 생성물 일치 검사를 수행하며 본문 그림 포함, 가운데 점 금지 및 렌더 해시를 CI에서 검사한다. [작성자 검수 기록](./04-44-interaction-review.md#대화-실행-주제-공통-경로와-전체-그림-통합-2026-10-13)에 범위를 남긴다. 통합 PPTX, 다른 DP, 참조 Architecture와 QA/ADR은 변경하지 않으며 새 구현, 모델 실행, 측정 또는 대안 선택으로 확대하지 않는다.

## 2026-10-13 DP-44 구현을 가정한 실행 구조 구체화

사용자는 기존 DP-44 구조도가 추상적이라 실제 구현을 이해하기 어렵다고 지적했다. [44 §3.7](./04-44-continuous-interaction.md#37-구현을-가정한-코드-조직과-취소-경로)과 [구현 가정 구조 설명](./dp44-implementation-structure.md)에 두 코드 조직 구조도와 번호별 실행, 상태 소유, 정정 및 취소 처리를 추가했다. ### 1단계의 범위·중요성 판정

- **양방향 점검:** 요구마다 설명할 문제를 찾고, 각 문제도 실제 요구·실패 영향으로 정당화한다. 대안을 떠올리기 쉬운 문제부터 골라 빈칸을 채우지 않는다.
- **정상 흐름:** Voice/Text 입력, 화면 지칭, 불완전/복합 요청, 직접 응답·위임, 진행·질문·결과, 후속 대화, 기억 관리.
- **교차·예외:** 동시 업무, 역순/중복/늦은 사건, 정정·취소, 채널 전환, 동의·철회·삭제, 미지원/불명 상태, crash·재연결·sleep/lock, 저장소 포화·모델 경합.
- **운영·변화:** PC 전체 자원과 메모리, Model/Agent/Context/State 계약 변화, 필요한 provenance와 시험 근거. 사용자 UC에만 맞춰 QA-29·분석/시험 관심사를 빠뜨리지 않는다.
- **중요성 근거:** 제품 목적과의 직접 관계, 실패의 사용자 영향·되돌리기 어려움, 여러 흐름에 미치는 영향, 품질 충돌과 구조적 파급을 서술한다. 실제 사용 빈도·장비 수치가 없으면 추정 순위나 가중 총점을 만들지 않는다.
- **coverage의 의미:** 합의된 제품 범위 안의 요구를 빠뜨리지 않았는지 확인한다. 향후 모든 가능한 VIA 기능을 망라하거나 구현을 검증했다는 뜻이 아니다. 카메라·다기기·무인 예약 등 제외된 기능을 임의로 추가하지 않는다.

### 기록 방식과 검토 순서

문제 원장은 `문제 / 사용자 상황 / 실패 결과 / 중요성 근거 / 연결 요구·UC 변형 / 경계·중복 / 열린 질문 / 상태`로 쓴다. 품질 시나리오와 구조 대안은 다음 단계에서 연결하며, 초기에 해결 기술 이름으로 문제를 정의하지 않는다.

독립 검토는 **1단계 범위, 중요성**, **2단계 요구/수단 분류**, **4단계 대안 탐색의 충분성**, **5~6단계 구조, QA 인과, 그림**에서 수행한다. 리뷰는 작성된 문서의 오류뿐 아니라 누락한 문제, 대안을 찾는 역할을 가진다. 발견사항, 반영/보류 이유, 재검토 결과를 남긴다. 일반적인 단계 완료 조건은 내부 작업 기준이지만, **1단계 공동 검토 후 2단계 진행을 승인받았고, 전달한 02-00도 사용자 승인을 받았다. 이후 13개 관점의 정리를 검토한 사용자가 4단계 진행을 승인했다.** 새로운 제품 요구나 명시 제약 변경이 필요하면 별도로 드러낸다.

### 4단계의 탐색 노력 배분

**사용자 지시: P-01~16을 같은 깊이와 분량으로 탐색하지 않는다. 합의한 품질 우선순위와 직결되는 문제에 더 집중한다.** 03의 관점 연결을 출발점으로 사용하되, 연결된 V의 개수나 P 번호 순서로 작업량을 균등 배분하지 않는다. 특히 V-03, V-04와 V-05는 모든 P에 연결되어 있으므로 단순 연결 여부만으로 모든 문제를 집중 대상으로 만들지 않는다.

우선 V-01~03의 기능 품질과 V-04/05의 VIA 시간에 직접적인 차이를 만드는 구조 질문을 깊게 본다. 이어 V-08 변경, V-06 자원, V-07 장애와 복구의 순위를 반영한다. 상위 품질을 좌우하는 전제나 병목이면 낮은 순위와 연결된 문제도 함께 깊게 본다. 품질의 우선순위와 해당 P에서 구조가 그 품질을 바꿀 수 있는 직접성 및 범위를 설명하며, 근거 없는 영향 수치나 가중 총점은 만들지 않는다.

| 탐색 깊이 | 적용 기준 | 기록할 내용 |

04는 먼저 `P / 상위 품질과의 직접 연결 / 구조적으로 바꿀 수 있는 것 / 탐색 깊이 / 이유 및 연계 P`를 정리한다. 집중 대상 수, P별 대안 수나 문서 분량을 미리 맞추지 않는다. 근거가 부족한 문제를 살펴보지 않고 대안이 없다고 단정하지 않으며, 새 인과가 발견되면 탐색 깊이를 조정한다. 이 분류는 작업 노력 배분이며 최종 DP 선발이 아니다.

**문제 탐색의 깊이와 대안 평가의 품질 범위를 구별한다.** 모든 P를 같은 노력으로 보지는 않지만, 구체화한 구조 대안에서는 13개 관점 모두의 영향 경로, 영향 없음의 근거 또는 미확인을 점검한다. 불리한 품질을 생략하지 않으며 같은 QA의 공통 정의, 지표와 측정 방법을 유지한다. 일부 기능을 포기한 대안도 비교에 남긴다.

### 현재 체크포인트와 재개 순서

**2026-10-01 후속 합의 — QA를 구체화하는 순서와 전체 DP 일관성**

- 03은 품질의 의미, 시나리오, 필수 결과와 관찰 후보를 정한다. 04는 여러 구조를 탐색하고 05는 실제 target과 강한 대안의 품질 차이를 조건부 가설로 비교한다. 정확한 QA 정의, 지표와 측정 방법은 실제 측정 전에 확정한다.
- **같은 QA는 모든 DP와 모든 방안에서 동일한 정의, 지표, 측정 방법을 사용한다.** Functional correctness라는 이름만 같고 DP마다 의미 field 정확도, 검색 recall, 업무 성공률을 달리 쓰는 것은 금지한다. 여러 지표를 채택하더라도 그 구성과 집계는 공통이다.
- 공통 QA 원본과 version을 참조하고, 판정 기준, 관찰 경계, 실패 처리, 모집단과 적용 및 집계 규칙도 공통으로 관리한다. 유리한 사례 선택이나 DP별 진단으로 대표 QA를 바꾸지 않는다. 구조적 참여 차이는 공통 적용 규칙으로 설명한다.
- 기존 QA 정의와 결과의 보존은 새 비교에서의 자동 채택을 뜻하지 않는다. 재사용, 개정 또는 새 공통 QA의 필요성을 검토한다. 계약을 개정하면 영향받는 모든 DP를 함께 검토하고 이전 결과의 비교 가능성을 명시한다.
- 03의 §2에 있는 13개 관점 V-01~13을 §3 충돌, §4 시나리오, §5 후속 검토에 연결하고 04~05에서도 모두 점검한다. 각 구조의 실제 영향 또는 영향 없음의 근거, 미확인을 명시한다. 기존 QA 번호와 핵심/추가 구분으로 되돌아가지 않는다. 관점 표식은 새 QA ID가 아니며 묶인 부특성도 각각의 효과를 보존한다.
- **2026-10-01 사용자 후속 지시:** V-02 기능 적절성과 V-03 기능 완전성을 분리하고, V-04 상호작용 반응성과 V-05 VIA 귀속 요청 완료 시간을 분리했다. 기존 V-04~11은 V-06~13으로 이동했다. 분리 전 순위를 이어 V-01~03 공동 1순위, V-04/05 공동 2순위, V-08 3순위, V-06 4순위, V-07 5순위, V-09~13 공동 6순위로 기록한다.

## 이전 작업 기록 — 기존 네 비교안의 작성·ISO 보완

이하 완료 상태는 당시 자료와 그 검토 범위에 한정된다. 전체 문제 탐색의 충분성은 위 새 절차로 재검토한다.

## 1. 이번 작업의 목적과 고정 조건

VIA의 중요한 사용자 문제를 해결하는 **서로 다른 SW Architecture**를 비교한다. 방안 1은 REVIEWED_BASELINE target의 실제 구조다. 방안 2는 같은 기능·완료 조건을 달성하는 독립적인 설계이며 target의 Component 목록·책임 배치에 갇히지 않는다. 새 Component가 필요한 이유, 없어지거나 대체되는 책임, 별도 저장소·실행체·인터페이스가 실제로 설명되어야 한다.

Component 이름만 바꾸기, 기존 함수를 둘로 나누기, 호출 순서·알고리즘·정책·설정값만 바꾸기는 선발 근거가 아니다. Component 수를 늘리거나 그림을 비대칭으로 꾸미기 위한 구조도 제외한다. 대안을 채택했을 때 유지해야 할 독립 계약·상태·수명·장애 처리가 실제로 달라져야 한다.

고정: VIA는 interaction·orchestration, Agent는 업무 planning·execution. 한 on-device Omni의 가중치를 공유하고 음성 입력 지속성을 유지한다. 추가 helper dependency는 목적과 전체 비용을 명시한다. 사용자 기능·권한·삭제·중복 실행 방지 요구는 유지하되 이를 구현하는 책임 배치는 대안으로 바꿀 수 있다. Target 본문·accepted/deferred ADR·기존 증거는 수정하지 않는다. 구현·모델 실행·성능 측정·수치 freeze·우열 확정은 하지 않는다.
