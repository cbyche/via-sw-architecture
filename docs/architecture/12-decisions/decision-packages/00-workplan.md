### 목적과 현재 범위

사용자가 동의한 순서대로 **문제 정의 → 요구/수단 분리 → 품질 충돌 → 여러 구조 탐색 → 강한 대안 비교 → DP 선발, 상세화**를 수행한다. 대화에서 나온 10개 문제는 검증할 초안이며 최종 개수, 분해 기준이 아니다. 먼저 그 목록이 VIA의 중요한 요구를 충분히 드러내는지 점검한다. 1단계 자료와 VIA 특성 두 표를 사용자와 검토했다. 사용자는 문제 이해를 확인한 뒤 요구/수단을 분리하는 다음 단계와 GitHub 반영을 명시적으로 요청했다. 2단계 자료를 전달한 뒤 사용자가 2026-10-01에 02-00을 명시적으로 승인했다. 요청한 순서대로 **01-00을 정리하여 먼저 commit/push한 뒤 3단계 품질 충돌 자료를 작성했다. 13개 관점으로 정리한 03을 검토한 뒤 사용자가 다음 단계 진행에 동의했다.** 현재 04는 품질 우선순위에 따라 7개 P를 집중 탐색하고, 6개 구조 질문에서 target 밖 대안 7개를 스케치했다. 나머지 문제의 연계 검토 및 보류 이유를 기록했다. 사용자 요청에 따른 독립 에이전트 3명의 검토에서 중복 제외 P2 3건을 수정했고 재검토로 해결을 확인했다. 이후 사용자 리뷰에 따라 S-01~06을 04-01~06 개별 문서로 나누고 실제 T/A/B 비교 SVG와 draw.io를 추가했다. 기존 네 자료를 선택적으로 참고한 계약과 제외 이유를 각 문서에 남겼다. 그림의 독립 검토에서 발견한 별도 P2 3건도 수정하고 재확인했다. 04-01의 첫 사용자 리뷰에서 공통 시작과 용어 설명, 송수신자와 순서, 그림의 요청 및 반환 화살표가 부족하다는 지적을 받았다. 이 지적을 04 전체의 작성 원칙으로 기록하고 S-01~06의 글과 그림을 같은 기준으로 수정했다. 현재 사용자 재검토 대기이며 DP 선정이나 05 착수의 뜻이 아니다.

Target은 검토 완료 비교 기준선으로 보존한다. 문제 목록을 재정리한다는 이유로 target을 미완료로 바꾸거나 재설계하지 않는다. 기존 네 비교안은 재평가 입력으로 남겨두며, 개별 타당성 검토와 전체 탐색의 충분성을 구별한다. 새 후보가 선정되기 전에 기존 파일·그림을 삭제하거나 통째로 archive하지 않는다. 실제 대체 세대가 생기면 사유·이동 경로·추적 링크를 기록한다.

### 1단계의 범위·중요성 판정

- **양방향 점검:** 요구마다 설명할 문제를 찾고, 각 문제도 실제 요구·실패 영향으로 정당화한다. 대안을 떠올리기 쉬운 문제부터 골라 빈칸을 채우지 않는다.
- **정상 흐름:** Voice/Text 입력, 화면 지칭, 불완전/복합 요청, 직접 응답·위임, 진행·질문·결과, 후속 대화, 기억 관리.
- **교차·예외:** 동시 업무, 역순/중복/늦은 사건, 정정·취소, 채널 전환, 동의·철회·삭제, 미지원/불명 상태, crash·재연결·sleep/lock, 저장소 포화·모델 경합.
- **운영·변화:** PC 전체 자원과 메모리, Model/Agent/Context/State 계약 변화, 필요한 provenance와 시험 근거. 사용자 UC에만 맞춰 QA-29·분석/시험 관심사를 빠뜨리지 않는다.
- **중요성 근거:** 제품 목적과의 직접 관계, 실패의 사용자 영향·되돌리기 어려움, 여러 흐름에 미치는 영향, 품질 충돌과 구조적 파급을 서술한다. 실제 사용 빈도·장비 수치가 없으면 추정 순위나 가중 총점을 만들지 않는다.
- **coverage의 의미:** 합의된 제품 범위 안의 요구를 빠뜨리지 않았는지 확인한다. 향후 모든 가능한 VIA 기능을 망라하거나 구현을 검증했다는 뜻이 아니다. 카메라·다기기·무인 예약 등 제외된 기능을 임의로 추가하지 않는다.

### 기록 방식과 검토 순서

문제 원장은 `문제 / 사용자 상황 / 실패 결과 / 중요성 근거 / 연결 요구·UC 변형 / 경계·중복 / 열린 질문 / 상태`로 쓴다. 품질 시나리오와 구조 대안은 다음 단계에서 연결하며, 초기에 해결 기술 이름으로 문제를 정의하지 않는다.

독립 검토는 **1단계 범위, 중요성**, **2단계 요구/수단 분류**, **4단계 대안 탐색의 충분성**, **5~6단계 구조, QA 인과, 그림**에서 수행한다. 리뷰는 작성된 문서의 오류뿐 아니라 누락한 문제, 대안을 찾는 역할을 가진다. 발견사항, 반영/보류 이유, 재검토 결과를 남긴다. 일반적인 단계 완료 조건은 내부 작업 기준이지만, **1단계 공동 검토 후 2단계 진행을 승인받았고, 전달한 02-00도 사용자 승인을 받았다. 이후 13개 관점의 정리를 검토한 사용자가 4단계 진행을 승인했다.** 새로운 제품 요구나 명시 제약 변경이 필요하면 별도로 드러낸다.

### 4단계의 탐색 노력 배분

**사용자 지시: P-01~16을 같은 깊이와 분량으로 탐색하지 않는다. 합의한 품질 우선순위와 직결되는 문제에 더 집중한다.** 03의 관점 연결을 출발점으로 사용하되, 연결된 V의 개수나 P 번호 순서로 작업량을 균등 배분하지 않는다. 특히 V-03, V-04와 V-05는 모든 P에 연결되어 있으므로 단순 연결 여부만으로 모든 문제를 집중 대상으로 만들지 않는다.

우선 V-01~03의 기능 품질과 V-04/05의 VIA 시간에 직접적인 차이를 만드는 구조 질문을 깊게 본다. 이어 V-08 변경, V-06 자원, V-07 장애와 복구의 순위를 반영한다. 상위 품질을 좌우하는 전제나 병목이면 낮은 순위와 연결된 문제도 함께 깊게 본다. 품질의 우선순위와 해당 P에서 구조가 그 품질을 바꿀 수 있는 직접성 및 범위를 설명하며, 근거 없는 영향 수치나 가중 총점은 만들지 않는다.

| 탐색 깊이 | 적용 기준 | 기록할 내용 |
| --- | --- | --- |
| 집중 탐색 | 상위 품질의 직접적인 차이를 만드는 문제 또는 그 차이를 좌우하는 전제 | 서로 다른 메커니즘, 실행과 상태 흐름, 기능 손실, 품질 충돌, 성립 조건과 강한 대안 가능성 |
| 연계 탐색 | 집중 대상과 상태, 데이터, 자원 또는 복구 경로를 공유하는 문제 | 연결된 구조의 영향과 별도 선택이 필요한 부분. 같은 구조를 P마다 중복 작성하지 않음 |
| 간략 점검 또는 보류 | 현재 상위 품질의 직접 효과가 약하거나 독립 구조 차이의 근거가 부족한 문제 | 확인한 범위, 현재 판단 이유와 재검토 조건. 깊게 보지 않았다는 사실을 품질 동등이나 무영향으로 바꾸지 않음 |

04는 먼저 `P / 상위 품질과의 직접 연결 / 구조적으로 바꿀 수 있는 것 / 탐색 깊이 / 이유 및 연계 P`를 정리한다. 집중 대상 수, P별 대안 수나 문서 분량을 미리 맞추지 않는다. 근거가 부족한 문제를 살펴보지 않고 대안이 없다고 단정하지 않으며, 새 인과가 발견되면 탐색 깊이를 조정한다. 이 분류는 작업 노력 배분이며 최종 DP 선발이 아니다.

**문제 탐색의 깊이와 대안 평가의 품질 범위를 구별한다.** 모든 P를 같은 노력으로 보지는 않지만, 구체화한 구조 대안에서는 13개 관점 모두의 영향 경로, 영향 없음의 근거 또는 미확인을 점검한다. 불리한 품질을 생략하지 않으며 같은 QA의 공통 정의, 지표와 측정 방법을 유지한다. 일부 기능을 포기한 대안도 비교에 남긴다.

### 현재 체크포인트와 재개 순서

**2026-10-01 후속 합의 — QA를 구체화하는 순서와 전체 DP 일관성**

- 03은 품질의 의미, 시나리오, 필수 결과와 관찰 후보를 정한다. 04는 여러 구조를 탐색하고 05는 실제 target과 강한 대안의 품질 차이를 조건부 가설로 비교한다. 정확한 QA 정의, 지표와 측정 방법은 실제 측정 전에 확정한다.
- **같은 QA는 모든 DP와 모든 방안에서 동일한 정의, 지표, 측정 방법을 사용한다.** Functional correctness라는 이름만 같고 DP마다 의미 field 정확도, 검색 recall, 업무 성공률을 달리 쓰는 것은 금지한다. 여러 지표를 채택하더라도 그 구성과 집계는 공통이다.
- 공통 QA 원본과 version을 참조하고, 판정 기준, 관찰 경계, 실패 처리, 모집단과 적용 및 집계 규칙도 공통으로 관리한다. 유리한 사례 선택이나 DP별 진단으로 대표 QA를 바꾸지 않는다. 구조적 참여 차이는 공통 적용 규칙으로 설명한다.
- 기존 QA 정의와 결과의 보존은 새 비교에서의 자동 채택을 뜻하지 않는다. 재사용, 개정 또는 새 공통 QA의 필요성을 검토한다. 계약을 개정하면 영향받는 모든 DP를 함께 검토하고 이전 결과의 비교 가능성을 명시한다.
- 03의 §2에 있는 13개 관점 V-01~13을 §3 충돌, §4 시나리오, §5 후속 검토에 연결하고 04~05에서도 모두 점검한다. 각 구조의 실제 영향 또는 영향 없음의 근거, 미확인을 명시한다. 기존 QA 번호와 핵심/추가 구분으로 되돌아가지 않는다. 관점 표식은 새 QA ID가 아니며 묶인 부특성도 각각의 효과를 보존한다.
- **2026-10-01 사용자 후속 지시:** V-02 기능 적절성과 V-03 기능 완전성을 분리하고, V-04 상호작용 반응성과 V-05 VIA 귀속 요청 완료 시간을 분리했다. 기존 V-04~11은 V-06~13으로 이동했다. 분리 전 순위를 이어 V-01~03 공동 1순위, V-04/05 공동 2순위, V-08 3순위, V-06 4순위, V-07 5순위, V-09~13 공동 6순위로 기록한다.
- **완전 충족을 후보 진입 조건으로 삼지 않는다.** 현실적인 구조 탐색과 비교를 위해 일부 기능의 포기를 허용한다. 공통 요구 목록을 유지하면서 지원, 부분 지원, 미지원과 미확인, 사용자 영향과 우회 비용을 기록한다. 기능 손실과 다른 품질의 이익을 함께 검토하며 이전 완전 충족 규칙으로 후보를 자동 제외하지 않는다. 승인된 02와 target 원문은 비교 기준으로 보존하며 특정 기능의 포기나 target 변경을 이번에 확정하지 않는다.
- V-04와 V-05 모두 VIA 귀속 시간을 평가한다. Downstream Agent 내부 실행 시간은 외부 조건이며 VIA 성능으로 세지 않는다. 같은 외부 profile에서 VIA가 만든 준비, 경합, 인계, 후속 해제와 결과 전달 지연을 구별한다. 전체 경과 시간의 단순 차감 등 계산식은 아직 정하지 않는다.
- 측정 전 전체 DP와 전체 방안이 같은 QA 계약을 쓰는지 확인한다. 세부 합의는 [03-00 §6.1](./03-00-quality-scenarios.md#61-모든-dp와-모든-방안에서-같은-qa를-사용한다)에 있다. 이 QA 공통 계약 합의 자체는 측정 freeze 승인이 아니다. 이후 사용자 리뷰로 04 진행은 승인받았다.

## 이전 작업 기록 — 기존 네 비교안의 작성·ISO 보완

이하 완료 상태는 당시 자료와 그 검토 범위에 한정된다. 전체 문제 탐색의 충분성은 위 새 절차로 재검토한다.

## 1. 이번 작업의 목적과 고정 조건

VIA의 중요한 사용자 문제를 해결하는 **서로 다른 SW Architecture**를 비교한다. 방안 1은 REVIEWED_BASELINE target의 실제 구조다. 방안 2는 같은 기능·완료 조건을 달성하는 독립적인 설계이며 target의 Component 목록·책임 배치에 갇히지 않는다. 새 Component가 필요한 이유, 없어지거나 대체되는 책임, 별도 저장소·실행체·인터페이스가 실제로 설명되어야 한다.

Component 이름만 바꾸기, 기존 함수를 둘로 나누기, 호출 순서·알고리즘·정책·설정값만 바꾸기는 선발 근거가 아니다. Component 수를 늘리거나 그림을 비대칭으로 꾸미기 위한 구조도 제외한다. 대안을 채택했을 때 유지해야 할 독립 계약·상태·수명·장애 처리가 실제로 달라져야 한다.

고정: VIA는 interaction·orchestration, Agent는 업무 planning·execution. 한 on-device Omni의 가중치를 공유하고 음성 입력 지속성을 유지한다. 추가 helper dependency는 목적과 전체 비용을 명시한다. 사용자 기능·권한·삭제·중복 실행 방지 요구는 유지하되 이를 구현하는 책임 배치는 대안으로 바꿀 수 있다. Target 본문·accepted/deferred ADR·기존 증거는 수정하지 않는다. 구현·모델 실행·성능 측정·수치 freeze·우열 확정은 하지 않는다.
