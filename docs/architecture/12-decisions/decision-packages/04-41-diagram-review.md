# 04-41 실행 계약과 그림 검수

## 후속 사용자 교정 — 판단 흐름과 교환 데이터의 시각적 대비 (2026-10-09)

사용자는 같은 Component를 같은 그리드로 나열한 그림에서 설계 차이가 보이지 않는다고 지적했다. 이어 실제 동작을 더 바꾸라는 뜻이 아니라, 주고받는 데이터와 판단 주체를 overlay해 기존 차이를 한눈에 보이게 하라고 명확히 했다. 독립 DP의 자격이나 A/B 실제 동작을 이번 표현 보완에서 다시 변경하지 않는다.

- A는 모델이 선택한 ReadRequest → 읽기 → EvidenceBundle → 모델 재판단의 큰 순환과 모델 생산 MeaningProposal을 강조한다. B는 모델 생산 RequestFrame v1 → Engine의 항목 해결·코드 결합 → 같은 MeaningProposal을 강조하고 부분 모델 요청은 조건부 가지로 표시한다.
- 문서형 도형은 교환 데이터의 설명용 예시이며 실행 Module이나 영속 상태가 아니다. 두 후보 T7/T8의 질문·새 답변 뒤 T7를 연결하는 선후, 요청 범위의 send=false, A도 구조화 출력 가능/B도 추가 호출 가능/BOUND는 정답 보증이 아니라는 계약을 유지한다. 새로운 API 필드나 스키마를 채택하지 않는다.
- Component·Module·상태·외부 의존성 및 공통 흰색/검정·차이 작은 Module의 살구색 표기를 유지한다. 공통 입력·근거·권한·저장·실제 전달·위임은 각 칸의 주변에 작게 배치하며 A/B 칸 사이 실행 연결은 없다. 사건도와 실제 실행·저장 계약은 보존한다.

표현 보완과 그 검수는 아래 첫 재구체화 검수와 구별한다. 독립 검토자가 MAIN·발표 PNG와 41 PPTX 재렌더를 직접 대조했다. 과정에서 PM 선의 권한/전체 현재성 혼동과 반복 인스턴스 안내 누락을 보완했고, 문서형 Legend·검정 공통 경계·원통 이름과 선의 분리도 확인했다. 최종 표현 수정 범위에 미해결 P1/P2를 발견하지 않았으며 실제 설계/책임이 새로 바뀐 표현은 없다고 보고했다. 이후 A의 구조화 출력 설명을 RI 하단 경계에서 외곽 여백으로 옮긴 작은 배치 보완도 작성자가 검수했다.

- 전용 MAIN/사건도 생성 일치·XML·소속·경계·경로 검사와 문서 주석 관통선 검사를 통과했다. MAIN 실제 렌더의 텍스트 겹침·canvas 초과·문서 내부 범위 오류는 0이다.
- 발표 scoped/전체 source 검사, PNG geometry, 11장 PPTX flow와 native 재렌더 대조를 통과했다. 두 PPTX의 41 comparison/notes만 교체했으며 다른 59/35 part 및 42~45 개별 assets·JSON entries·합본 페이지 원문은 이전 판본을 보존했다.
- 이번 표현 보완 시작 시 보존한 사건도 생성기/네 사건 파일 및 다른 비교 산출물 17개 해시가 모두 일치한다. 최초 재구체화와 구별하여 이번 후속 표현에서 사건도 계약을 바꾸지 않았다.
- 최종 전체 활성 Markdown 링크 검사(154개 파일), 정식 용어/Component 이름과 diff 검사가 통과했다. 아래 최초 재구체화 때 기록한 병행 입력 근거 문서의 미생성 링크는 이후 병행 파일이 완성되어 더 이상 전체 검사를 막지 않는다. 해당 파일은 이번 작업에서 수정하지 않았다.

검수는 본문/도식의 일치와 가독성에 한정하며 DP 우열·모델 실행/측정 결과가 아니다. 검수 뒤 사용자는 데이터 표시가 이해를 돕는다고 확인했고 정기적인 작업 단위 commit/push를 지시했다. 위 검수는 미커밋 판본에서 수행했고 후속 게시 결과는 Git 이력과 사용자 보고로 연결한다.

## 현재 재구체화 — 공통 로컬/클라우드 구성 (2026-10-09)

사용자 승인 범위는 공통 책임과 41 실행 계약·그림·발표 자료의 재구체화다. 44→45→42 및 전체 Architecture 동기화는 후속 작업이다. 아래 2026-10-08 이전 기록은 당시 판본의 이력이며, 독립 Engine Component·공유 on-device Omni·이전 수치와 과거 보존 설명을 현재 계약으로 읽지 않는다.

- [41 §3](./04-41-request-resolution-control.md#3-공통-구성과-두-실행-구조)과 [공통 계약](./04-40-common-execution-contract.md)에 같은 10개 Component를 기록했다. B Request Resolution Engine은 Request Interpreter 내부 Module, 읽기 도구 실행기·의미 제안 검증기는 공통 Module이다. Engine 편입은 별도 수명·권한·영속 원본의 근거가 부족해서이며, 코드의 조회 진행/전체 결합 기제와 A/B 미선정 상태는 유지한다.
- 첫 입력과 Context/Task 직접 읽기 port, B 유한 항목 상태·schema 확장·조건부 부분 모델 해석, 확인 질문/후보/금지 조건 복원, 정정과 늦은 job 검사를 명시했다. RI 상태는 transient, 채택 의미/질문은 RC durable 원본, 실제 전달 원본은 RM이다. State Store는 Component로, 데이터 원통은 owner 안의 상태로 표시했다.
- 로컬 VAD는 Turn-Taking Control에 두고 Model Access의 로컬 adapter와 외부 cloud 음성/의미 모델을 구분했다. MAIN와 A/B 사건도 및 발표 비교·편집 가능한 두 PPTX를 갱신했다. 41의 검증되지 않은 수치/점수는 조건별 정확성·응답성·전체 모델 호출 비용·변경 용이성으로 대체했다.

### 독립 대조에서 발견한 문제와 재검토

두 읽기 전용 검토자가 본문/공통 계약과 완성된 도식을 대조했다. 본문 계약에서 P1/P2는 발견하지 않았으며 그림에서 다음 두 P2를 발견하고 수정했다.

1. 발표 비교에 실제 출력과 receipt/focus 및 RM 모델 연결이 없었다. RM→IM release, IM→RM receipt, RM→RC 질문 focus/게시 참조, RM↔Model Access 조건부 응답/음성 요청·결과를 실제 선으로 추가했다. B 부분 해석 요청을 실선으로, VAD를 Module 이름 밖 주석으로 맞췄다.
2. 사건도에서 질문 채택이 저장 성공보다 먼저 표현됐다. 질문/완성 의미 모두 현재성·권한 검사와 저장 준비 → State Store 성공 → 채택 → 현재 유효한 경우 게시/인계로 수정하고 MAIN 주석도 맞췄다.

수정 후 해당 두 검토자가 생성 source/SVG와 발표 PNG를 재대조했으며 검토 범위에 미해결 P1/P2가 없다고 보고했다. 이는 독립 문서/도식 대조이지 사용자 승인이나 구현/성능 검증이 아니다.

- 전용 생성기 `--check`로 세 SVG/draw.io 쌍의 일치·XML·Module/상태 소속·경계·경로를 검사했다. MAIN 2560×1440 PNG와 A/B 사건도의 실제 브라우저 렌더에서 글자 겹침과 canvas 초과가 없었다.

현재 41은 재구체화된 검토용 대안이다. 구현·모델/API 실행·성능 측정·최종 A/B 선택·commit/push는 하지 않았다. 42B/44 hold·전송 계약은 [04-40 §6](./04-40-common-execution-contract.md#6-네-dp가-실제-프로그램에서-결합되는-지점)에 미결로 유지한다.

## 최신 사용자 교정 — A/B 칸 독립, 비교 설명 행 제거

사용자는 첫 16:9 그림에서 공통 경로가 두 칸에 걸친 점과 장점·대가·선택 조건을 그림에 포함한 점을 지적했다. 아래 §1~4는 첫 게시본의 검수 이력이며 현재 배치 설명이 아니다. 첫 게시본의 렌더 검사 통과를 사용자 수용으로 해석하지 않는다.

- A의 모든 구성요소와 연결선은 왼쪽 칸, B는 오른쪽 칸에 둔다. 공통 기능도 각 칸에 독립적으로 반복 표시한다. 각 칸의 입력, 해석, 조회, 현재 권한/버전 검사, 채택 기록, 사용자 전달과 외부 위임을 모두 추적할 수 있다.
- 전체 폭의 공통 입력·채택·위임 경로와 A/B 연결선을 제거했다. 상단의 같은 사용자 사례와 하단 범례는 설명이며 실행 Component나 공통 처리 영역이 아니다.
- 장점·대가·선택 조건의 세 행을 삭제했다. 품질 비교와 선택 조건은 본문 §7~9에 보존한다. 확보된 공간에는 각 안의 Policy Manager, State Store, Request Controller, Task Manager, Response Manager, Interaction Manager, Agent Gateway와 Downstream Agent 경로를 넣었다.
- 16:9 크기, 기존 해석 책임·임시 상태·질문·추가 조회·부분 해석·채택·반환 계약은 유지했다. A/B 사건도와 다른 비교 문서는 변경하지 않았다.
- 생성기 검사에 구성요소와 모든 연결점의 칸 내부 포함, A/B 사이 연결 금지 검사를 추가했다. 최종 2560×1440/1920×1080 렌더에서 텍스트 겹침·잘림과 칸 경계를 확인했다. 이는 배치 검수이며 새로운 아키텍처 검증이나 품질 측정이 아니다.

## 1. 첫 게시본 범위와 결과 (현재 배치로 대체됨)

메인 그림을 2560×3340에서 **2560×1440(16:9)**으로 재배치했다. 위에 같은 입력, 가운데 A/B의 해석 구조, 아래에 공통 채택·위임·사용자 전달을 배치하고 마지막에 장점·대가·선택 조건을 대조했다. 공통 경로를 한 번만 펼쳐 세로 중복을 줄였다. A/B로 나뉘는 입력선은 대체 설계의 비교이며 두 해석 경로를 동시에 실행하는 구조가 아니다.

A는 모델이 다음 조회와 최종 의미를 제안하고 코드는 읽기 실행·검증을 담당한다. B는 모델이 틀/부분 해석을 생산하고 Request Resolution Engine이 조회 진행과 최종 관계 결합을 담당한다. 기존 설계, 기능 지원 한계, 상태 소유권과 조건부 선택 근거는 변경하지 않았다. 모델 호출 감소, 품질 우위나 승자를 새로 주장하지 않는다.

수정 범위는 41 메인 그림의 SVG/draw.io, 해당 생성 scene과 진입점, 발표용 PNG, 본문의 그림 안내와 이 검수 기록이다. A/B 사건도 두 쌍과 다른 비교의 본문·그림은 그대로다. 작업 시작 시 이미 변경되어 있던 35/36 및 공통 안내 파일은 이번 커밋 대상에서 제외한다.

## 2. 내용 보존 대조

이전 SVG의 Component/Module/저장소/의존성 이름 18종을 새 scene과 비교했으며 누락은 없다. 기존 설명에 있던 Policy Manager와 State Store는 그림의 공통 경로에 추가로 펼쳤다. 같은 이름이 반복된 요소는 같은 논리 인스턴스이며, Omni는 PC의 가중치 한 벌을 공유한다.

## 3. 렌더 검수와 수정

작성자 검수이며 독립 심사나 사용자 승인 기록이 아니다.

- 첫 가로 렌더에서 B의 조회 왕복이 Engine 제목 부근에 몰리는 것을 확인했다. 미해결 항목 처리기를 자료 제공자 가까이 옮겨 직접 조회하고 반환받게 했다.
- 텍스트 경계 검사에서 B의 부분 해석 라벨과 Engine 제목, 결합 결과 라벨과 공통 인계 라벨이 겹친 것을 수정했다. 마지막으로 부분 해석/모델 반환 라벨의 겹침과 범례의 화면 밖 잘림을 수정했다.
- A의 읽기 도구 실행기를 옆 아래에 두어 모델이 선택한 조회와 결과 재판단 경로를 구분했다. 유효 기록 회수 라벨을 저장소 밖으로 이동했다.
- 로컬 Chrome에서 2560×1440과 발표 표시 크기인 1920×1080을 렌더링하여 확인했다. 마지막 렌더의 SVG 텍스트 bounding box 대조에서 겹침과 canvas 밖 텍스트는 없었다. 자동 대조는 의미 검증을 대신하지 않으며, 루프·채택·인계·반환 경로는 그림과 본문을 수작업으로 대조했다.
- SVG와 draw.io는 같은 scene으로 생성하며 XML, ID/연결 참조, Module 소유·포함, canvas 범위와 직교 경로/무관한 노드 관통 검사를 수행한다. PNG는 최종 SVG의 브라우저 렌더다.
