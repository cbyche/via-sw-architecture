# Decision Point 선발 원칙 — 기능 구현의 선택을 복원한다

> 상태: **사용자 리뷰를 반영한 작업 원칙 / 후보 선정은 별도 공동 검토**
> 2026-09-30 · [후보 목록](./README.md)

## 1. 출발점

사용자가 요구한 것은 **target Architecture의 주요 기능을 구현할 때 선택했을 방식과, 누구나 합리적이라고 인정할 다른 방식을 찾는 것**이다. Component 변화는 그 작동 차이를 드러내는 결과다. Component를 합치거나 나누는 그림을 먼저 만든 뒤 장점을 붙이지 않는다.

기준선에서 확인할 수 있는 현재 선택과 이번에 재구성한 대안을 구분한다. 대안을 당시 실제 검토한 사실로 서술하지 않는다. 기존 설계의 좋은 점만 찾아 설명하는 작업도 아니다. 선택한 수단이 불필요하거나 반대안이 더 나을 조건을 함께 남긴다.

## 2. 후보가 통과해야 하는 질문

| 검사 | 통과에 필요한 설명 | 제외할 경우 |
| --- | --- | --- |
| 과제의 중요성 | 어떤 핵심 기능·UC의 성공 여부나 중요한 처리 비용을 좌우하는가 | 어느 제품에도 붙일 수 있는 유지보수 일반론뿐 |
| 현재 선택의 근거 | target의 어느 절이 어떤 처리 방식을 선택했는가 | 현재 설계에 없는 수단을 선택안으로 발명 |
| 대안의 합리성 | 같은 기능을 제공하며 어떤 상황에서는 이쪽을 고를 이유가 있는가 | 검증·기능·근거를 뺀 대안, 무한 자원이나 미확인 모델 능력에 의존 |
| 작동 구조의 차이 | 정보 획득·변환, 작업 의존, 확정·저장·복구 중 무엇이 어떻게 달라지는가 | 이름·코드 소속만 바꾸고 동작은 같음 |
| 인과 설명 | 어떤 대기·오류·갱신·메모리 경로가 생기거나 없어지는가 | “분리해서 빠르다/정확하다/변경이 쉽다”만 제시 |
| 반대안의 완결성 | 정상 흐름뿐 아니라 정정·stale·실패·결과 전달도 성립하는가 | 새 발화나 연결 단절 한 번에 필수 기능 상실 |
| 판단의 독립성 | 다른 선택을 함께 바꾸지 않고 효과를 설명할 수 있는가 | 모델·조회·저장·처리 범위를 한꺼번에 바꾼 우열 |

미확인 capability가 있다는 이유만으로 가치 있는 주제의 상세화를 생략하지 않는다. 대안의 필요한 입력·출력·실행·장애 계약을 먼저 적고, **설계로 정의할 수 있는 조건과 실제 build에서 확인할 조건을 구분**한다. 기존 제품 요구를 위반하는 대안과 구현 적합성이 아직 검증되지 않은 대안은 다르다. 후자는 조건부 후보로 검토할 수 있지만 이미 지원·측정됐다고 표현하지 않는다.

**테두리 지우기 검사:** Component의 이름·테두리를 지우고 데이터와 실제 작업만 남겨도 두 안의 차이를 설명할 수 있어야 한다. 이를 통과한 뒤 Component의 추가·제거·책임·연결 변화가 선명한 후보를 우선한다. 최상위 Component 수가 같더라도 처리 파이프라인·중간 계약·저장 상태가 달라질 수 있다. 다만 내부 단계에 새 이름을 붙이는 것만으로 새 Component나 변경 용이성의 이점을 인정하지 않는다.

## 3. 알고리즘·설정과 Architecture의 경계

재시도 횟수, cache TTL, queue 순위, prompt 문구, 검색 점수만 바뀌면 독립 후보로 삼지 않는다. 반면 **여러 의미 판단을 중간 결과와 재처리 계약이 있는 파이프라인으로 구성하는 선택**, **자료 준비를 첫 해석의 앞이나 뒤에 배치하는 선택**, **event에서 상태를 재구성하거나 snapshot을 조회해 구성하는 선택**은 실제 의존·상태 계약이 달라질 때 구조적 후보가 된다.

“LLM 호출이 많다/적다”도 결론만으로 부족하다. 각 호출에 어떤 정보가 들어가고 무엇을 확정·보류하며, 다음 단계가 어떤 결과를 기다리고 잘못된 중간 결과를 어떻게 고치는지까지 설명한다. 이것이 없으면 prompt 분할 실험으로 축소된 것이므로 후보를 보류한다.

## 4. 제품 요구와 선택한 수단을 구분한다

- 공통으로 유지: 고정 UC의 목표·성공 조건, 사용자 정보 통제, 실제 전달과 생성의 구분, VIA의 interaction/orchestration과 Agent의 업무 reasoning/planning/실행 경계.
- 사용자 지정·명시 합의 유지: 공유 on-device Omni, 동시 입력 수신·인식, 좁은 S2S 직접 응답, 한 업무 전체의 Agent 위임, 독립 업무의 별도 추적 등. [합의 목록](../target-architecture/README.md#사용자-지정과-검토-기준선의-구분)을 확인한다.
- 변경 가능한 비교 수단: 요청 해석의 단계, 근거를 확보하는 순서, 진행 상태를 구성하는 수단, generation을 먼저 시작할지 여부와 필요한 계약.
- 수단을 바꾸면 관련 baseline 계약과 충돌하는 지점을 후보 문서에 명시한다. 후보 설명만으로 기준선의 숫자·schema·상태를 수정하지 않는다.

각 후보는 한 가지 중심 선택을 비교한다. 무관한 source·모델·Agent 능력 차이로 이점을 만들지 않는다. 같은 모델을 두 번 호출하는 것을 독립된 정답 검증으로 표현하지 않는다. 실제 기능이 필요한 대안에는 capability 전제와 확인 공백을 가까이 적는다.

기존 설계 문서도 아이디어·반론을 얻는 자료로 읽는다. 기존 ID·Core 분류·A/B 문자·실험 결과를 새 목록에 배정하지 않는다. 현재 target의 선택과 충돌하는 과거 가정은 명시하고, 유용한 설계 메커니즘만 현재 기능·계약에서 다시 성립시키는지 검토한다. [기존 7개·VIA-DP-01~18 검토 기록](./reference-idea-review.md)이 그 근거다.

## 5. 작업과 리뷰 순서

1. 주요 기능과 현재 구현 방식을 target 본문·상세 계약에서 추출한다.
2. 해당 방식이 해결하려는 난점과 감수하는 대가를 복원한다.
3. 같은 기능의 합리적 대안을 구성하고 정상·정정·실패 사건을 양쪽에서 따라간다.
4. 실행 의존·상태·계약의 차이와 대안이 유리한 조건을 기록한다.
5. 위 검사와 후보 간 중복 검사를 거쳐 짧은 목록을 사용자와 검토한다.
6. 남긴 후보의 ASR을 메모리까지 포함해 검토하고, 이후 정식 rationale와 반증·검증 계약을 작성한다.

일곱 개 또는 Component 수만큼을 채우지 않는다. 처음 제안한 후보라도 좁혀 보니 설정 차이만 남거나 강한 대안이 성립하지 않으면 제외한다. 형식이 갖춰진 문서가 후보의 중요성을 입증하지는 않는다.

반대로 최초 네 개를 선정 상한으로 삼지 않는다. 후속 검토에서 가치가 확인된 주제는 같은 깊이의 개별 문서와 반례 검토까지 수행한다. 같은 최적화를 허용하면 차이가 사라질 우려가 있는 경우도 실제로 양안을 구성해 수렴 조건을 밝힌 후 통합·제외한다. ‘더 구체화가 필요하다’는 판단만 남기고 발굴을 끝내지 않는다.

## 6. 발표 자료로 표현하는 방식

배경 1장은 **VIA의 주요 기능 → 문제가 드러나는 구체적인 상황 → 함께 만족하기 어려운 요구 → 구현 방식을 선택해야 하는 질문**으로 구성한다. 배경에서 특정 Component 분리가 필수라고 결론 내리지 않는다.

비교 1장은 같은 사용자 상황을 두 실행 흐름으로 펼친다. Component·내부 작업·process·dependency·저장 기록을 구분하고, 정보와 제어의 흐름·중간 상태·예외 경로를 표시한다. 그림만 보아도 대기 위치, 만들어지는 데이터, 버리거나 다시 처리하는 작업의 차이를 따라갈 수 있어야 한다.

공통은 검정, 차이는 양쪽 모두 파랑이다. 필요한 경우 동일 Component 안에서도 달라지는 내부 작업·계약·cache를 파랑으로 표시한다. `.drawio` 편집 원본과 `.svg` preview를 함께 관리한다. 사용자가 준 예시는 표현 깊이의 참고이며 수치·도메인 구조를 VIA의 근거로 옮기지 않는다.

후보 채택 전에는 상세 비교 그림 제작으로 검토를 앞지르지 않는다. 이번 문서는 배경·비교 페이지의 원고와 도식 설계까지 제공한다. 상세 그림은 공동 후보 검토 뒤 만든다.

## 7. 현재 하지 않는 일

기존 DP 번호에 매핑하지 않고 목표 Architecture를 다시 설계하지 않는다. ASR 정의·우선순위·적용 분류는 후속 공동 검토다. 구현·모델 실행·성능 측정·freeze·승자 선정은 시작하지 않는다. 정성적 기대 효과는 구조에서 도출한 가설이며 측정 사실로 표현하지 않는다.
