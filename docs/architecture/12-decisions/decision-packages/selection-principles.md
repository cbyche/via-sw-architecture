## 반복 지적 후 반드시 적용하는 구조 판정

[04-30 §4](./04-30-comparison-guide.md#4-sw-구조적으로-다른-대안의-정확한-의미)를 주요 구조 비교의 구체 판정 원본으로 사용한다. 같은 중요한 목적, 다른 해결 메커니즘, 실제 책임/자료/상태/실행의 변화, 그로 인한 품질 손익과 핵심 전환 비용을 연결해야 한다. 상자 이름/배치, Component 추가, 내부 호출 교체와 계약 변경 목록만으로 통과시키지 않는다.

각 안을 독립적으로 설계한 뒤 최소 전환/혼합으로 반박하고 그 결과에서 도식을 도출한다. 공통 pipeline을 먼저 만들고 안별 이름을 채우는 방식은 금지한다. 최신 사용자 지시는 이전 문서의 낙관적인 “유지/완료”보다 우선한다. 주제는 중요하지만 방안 차이가 약하면 주제를 보존하고 다시 설계한다.

## 2026-10-03 사용자 리뷰에 따른 우선 적용

기존 `target-architecture/`는 VIA 기능 전반을 지원하는 **검토 완료 참조 구조**다. 비교할 방안 1로 고정하거나 방어할 목표로 취급하지 않는다. 두 안 모두 달라도 되며, 실제 참조 설계를 인용할 때는 그 내용을 정확히 설명한다. 이 지시는 아래 이전 T 중심 설명과 과거 workplan보다 우선한다.

VIA의 정상적인 음성/화면 대화와 업무 연결에서 발생하는 중요한 기능 문제를 먼저 찾는다. 전형적인 구조 비교도 기능 품질 손익과 현실적인 선택 이유가 뚜렷하면 탐색한다. 대안을 완성된 것처럼 포장하지 않되, 일부 미확인이 있다는 이유만으로 기능 주제를 접고 복구/격리처럼 구조 차이를 설명하기 쉬운 문제로 치우치지 않는다. M-2는 주제 차원의 긍정 평가이며 방안 승인 또는 DP 선정이 아니다.

## 1. 목적

**VIA의 중요한 품질 목표를 달성하기 위해 어떤 SW 구조를 선택해야 하는지, 그 선택의 이유와 비용을 설득력 있게 설명한다.** 검토 완료 참조 구조는 기능과 기존 수단을 확인하는 출발점이다. 같은 사용자 목적과 요구 목록을 기준으로 실질적으로 다른 해결 메커니즘을 만들고 품질상의 이익과 손실을 비교한다.

서로 전환하려면 핵심 설계를 상당 부분 바꿔야 할 정도로 다른 구조를 주요 DP 후보로 삼는다. 기능이나 Component의 국소적인 추가, 제거, 내부 구현 교체로 상대 방안이 되는 안은 주요 구조 비교로 충분하지 않다. 양안은 각각 선택할 현실적인 조건을 가져야 한다.

**되돌리기 어려움은 중요한 선택인지를 판단하는 기준이다.** 변경하기 어렵게 만드는 것, 큰 시스템을 그리는 것, 전환 비용을 높이는 것 자체가 목적은 아니다. 높은 전환 비용만 있고 중요한 품질 문제에 도움이 되지 않는 구조는 선발하지 않는다.

## 2. 유지할 비교 조건

- [01-00 문제](./01-00-problem-coverage.md), [02-00 요구와 선택](./02-00-requirements-and-choices.md), [03-00 품질 충돌](./03-00-quality-scenarios.md)을 출발점으로 쓴다. S-01~06, 이전 네 비교안과 VIA-DP 번호는 후보 수나 분해를 결정하지 않는다.
- 같은 사용자 목적, 요구 목록, 완료 조건, 외부 Agent/source 지원과 모델 배치 제약을 유지한다. 부분 기능 대안은 허용하되 지원, 부분 지원, 미지원과 미확인, 잃는 결과와 사용자 우회 비용을 명시한다. 비교 모집단을 줄여 손실을 숨기지 않는다.
- target의 실제 cache, 동시 실행, 역할 격리, 내구 기록과 검증을 보존한다. 대안에 target의 Component 배치나 모든 중간 계약까지 강제하지 않는다.
- 하나의 on-device Omni 가중치를 공유하며 추가 helper의 전체 비용을 공개한다. Downstream Agent의 업무 계획과 실행을 VIA로 옮겨 대안을 만들지 않는다.
- 우선순위는 기능 V-01~03 공동 1순위, 시간 V-04/05 공동 2순위, 변경 V-08 3순위, 자원 V-06 4순위, 복구 V-07 5순위, V-09~13 공동 6순위다. 순위 안의 가중치와 미측정 수치를 만들지 않는다.
- 모든 구체 대안에서 V-01~13의 실제 영향, 영향 없음의 이유 또는 미확인을 기록한다. 같은 QA의 정의, 지표, 방법과 적용 규칙은 모든 DP 및 방안에 공통이다. 이번 탐색은 QA freeze나 측정이 아니다.

## 3. 같은 계열부터 묶는다

각 T/A/B가 공유하는 입력, 중간 표현, 실행 결정, 상태 원본, 확정 및 복구 방식을 먼저 찾는다. 기존 기능을 유지하며 두 안을 선택적으로 지원하는 가장 간단한 구조를 만들고, 기능별 경로 선택이나 내부 구현 교체로 양안을 수용할 수 있는지 확인한다.

쉽게 조합할 수 있으면 하나의 구조 계열 안의 선택으로 묶는다. `superset(T, A)`는 이 조합 가능성을 검토하기 위한 가상 확장이다. 실제 reviewed target이나 이미 구현된 안으로 기록하지 않는다. 서로 모순되는 상태 권위를 동시에 두거나 기능 손실과 복구 지원을 동시에 주장하는 가짜 합집합은 만들지 않는다. 결합 비용과 제한도 기록한다.

S-01~06은 현재 기준에서 **주요 DP 후보 자격 재검토 대상**이다. 이전 문서와 그림의 완성, 독립 검토의 오류 수정은 서로 다른 구조 계열이라는 입증이 아니다. 기존 자료는 기능과 계약의 참고 입력으로 보존한다.

## 4. 다른 해결 메커니즘을 만든다

**사용자 상황 → 중요한 품질 충돌 → 현재 계열이 비용을 발생시키는 원인 → 같은 목적을 달성할 다른 원리 → 실제 구조** 순서로 작성한다.

공통 골격의 전제를 바꿀 때는 그 전제가 제공하던 기능도 다른 수단으로 설명한다. 데이터 획득과 표현, 실행을 진행시키는 주체, 다음 단계의 조건, 원본 상태와 수정 방식, 확정과 복구 중 무엇이 함께 달라지는지 밝힌다. 차이를 키우려고 무관한 분산 배치, 새 모델이나 영구 기록을 묶지 않는다.

동일한 입력과 준비부터 정상 결과, 정정, 권한 철회, 부분 실패, 재시작을 따라간다. 매 호출, 반환과 확정의 송수신자와 자료를 밝힌다. 중요한 충돌에서 어떤 비용을 줄이고 어떤 비용을 새로 부담하는지 설명할 수 없으면 구조명만 제시한 것으로 본다.

사용자 제공 사례는 접근 권한 검사와 저장 분할, 독립 메시지 실행과 공유 실행, 사전 개선과 실행 중 복구처럼 해결 원리를 비교하는 방법의 참고다. 사례의 수치, 별점이나 선택 결과를 VIA의 근거로 가져오지 않으며, 다른 시스템의 기능과 규모를 VIA에 추가하지 않는다.

## 5. 가장 저렴한 전환을 먼저 시도한다

대안 작성자는 다음 전환 방법을 최대한 유리하게 구성한다. 반론을 약하게 만들지 않는다.

| 시도 | 확인할 것 |
| --- | --- |
| 내부 구현 또는 adapter 교체 | 외부 계약의 의미와 권위 상태를 유지한 채 같은 효과를 얻을 수 있는가 |
| 기능 추가와 점진 적용 | 원래 처리와 상태 모델을 유지한 채 새 기능을 붙일 수 있는가 |
| 요청별 경로 선택 | 같은 핵심 계약 아래 일부 요청만 다른 방식으로 처리하면 충분한가 |
| 두 안의 병행 | 호환성 계층으로 양쪽을 유지하면 되는가, 그 계층이 새로운 확정과 복구 프로토콜을 실제로 필요로 하는가 |
| 중단 후 전환 | 진행 중 작업을 끝내고 바꾸면 어떤 비용이 없어지고 어떤 핵심 설계 변경이 남는가 |

전환이 어렵다는 주장은 `깨지는 기존 전제 → 변경할 상태/계약/실행 → 함께 바꿔야 하는 책임 → 회귀를 확인할 사용자 상황`으로 연결한다. 파일이나 상자 수가 많다는 이유로 큰 비용을 주장하지 않는다. 외부 API가 같다는 이유만으로 내부 전환이 싸다고 단정하지도 않는다.

2026-10-02 후속 검토에서는 이 구별을 실제로 적용한다. Adapter로 새 엔진을 감쌀 수 있다는 것은 주변 호출자를 보존한다는 뜻이다. 그 안에서 핵심 알고리즘의 내부 구현이 아니라 여러 처리 단계의 계약, 정보 전달, 상태 권위와 오류 복구를 다시 설계해야 한다면 그 구조 비용은 남는다. 반대로 새 엔진이라는 이름 아래 현재 해석과 확정 경로를 그대로 호출하면 같은 계열이다. 결합 가능성 자체와 작은 노력으로 결합 가능한지를 혼동하지 않는다.

**새 기능 자체의 개발비, 운영 중 자료와 작업의 이전비, 해결 메커니즘을 바꾸는 설계비를 구분한다.** 과거에 잃은 자료를 소급 복원할 수 없음, 일반적인 배포나 데이터 migration, “계약이 여러 개 바뀐다”는 목록만으로 구조적 중요성을 입증하지 않는다. T에서 C, C에서 T 양방향을 살피며 비용의 비대칭을 기록한다. 예상 인일이나 비용은 근거 없이 산출하지 않는다.

국소 전환이 가능하면 주요 후보에서 내리고 계열 내부 선택으로 남긴다. 근거가 부족하면 보류한다. 강한 후보를 반드시 만들어 보여주기 위해 한계를 숨기지 않는다.

## 6. 후보를 남기는 조건

| 판단 | 필요한 근거 |
| --- | --- |
| 중요한 문제인가 | 고정 사용자 상황과 높은 우선순위 품질에 대한 직접 인과. 낮은 순위도 상위 효과를 결정하면 심화 |
| 다른 계열인가 | 같은 사건을 처리하는 정보, 실행, 상태와 확정 원리가 실제로 다름 |
| 되돌림이 실질적으로 어려운가 | 저렴한 전환을 검토한 뒤에도 남는 핵심 설계 교체. 비용을 부풀리지 않은 양방향 설명 |
| 선택할 이유가 있는가 | 양안 각각이 유리한 VIA 조건, 감수할 비용과 기능 손실. 실제 빈도와 규모가 미확인이면 가설로 표시 |
| 반증 가능한가 | 기존 계열의 작은 확장으로 같은 효과를 얻거나 추가 비용이 이익을 상쇄하는 등 후보 주장이 무너지는 조건 |

상태는 `계열 내부 선택`, `다른 계열 가능성 검토 중`, `사용자 검토에 제시`, `보류`로 구별한다. `사용자 검토에 제시`도 Stage 5 진행 승인, DP 선정, baseline 변경이나 측정 우위가 아니다. 중요한 문제가 빠졌으면 S 번호를 채우는 대신 문제 원장으로 돌아가 탐색한다.

## 7. 이번 보고 시점과 산출물

원칙과 계획을 먼저 저장하고 GitHub에 반영한 뒤, 같은 계획에 따라 Stage 4를 재수행한다. 이번 보고는 기존 T/A의 계열 분류, 중요한 품질 충돌에서 발굴한 대안, 가장 유력한 후보의 같은 사건 흐름과 양방향 전환 검토, 13개 품질 검토, 보류 이유와 재검토 조건이 준비된 시점이다. 후보 수를 미리 정하지 않는다. 적합 후보가 없으면 시도와 근거를 보고한다.

첫 결과는 짧은 비교 문서와 명시적인 계약 표로 작성한다. 구조 자격이 약한 후보를 상세 그림과 긴 문서로 포장하지 않는다. 그림을 만들거나 고칠 때는 [설계도 기준](./diagram-design-guide.md)에 따라 SVG와 draw.io를 함께 유지한다.

문서 검증과 작성자의 반론 검토를 수행하되 독립 리뷰나 구현 검증을 했다고 표현하지 않는다. 사용자에게 보고한 뒤 Stage 5와 Stage 6의 진행을 별도로 판단한다. 구현, 모델 실행, 성능 측정과 QA freeze는 이번 범위에 포함하지 않는다.
