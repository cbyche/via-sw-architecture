## 10.1 목적 — 코드를 모두 만들기 전에 무엇을 셀 것인가

**Architecture Element는 설계에서 책임·계약·상태·배치를 독립적으로 설명하고, 변경 전후를 확인할 수 있는 단위이다.** 단순히 그림에 그린 박스나 소스 파일 수가 아니다.

ASR-04·05에서 세는 것은 **같은 변경을 받아들이기 위해 수정·추가·제거해야 하는 설계 요소의 수**이다. 개발 시간, M/M, 코드 줄 수, 컴파일 대상 수가 아니다.

| 지금 확정할 기준 | 대안 명세를 작성할 때 채워야 하는 내용 |
| --- | --- |
| 요소의 네 유형, 한 개로 인정하는 규칙, 검토할 전체 책임/계약 범위, 변경 원장 양식 | 그 대안에 실제로 존재하는 요소 ID, 소유자·계약·상태·배치와 의존 관계 |
| 중복·추가·제거·설정·적용 없음 처리 | 변경 전후 구체적인 설계 차이와 관련 UC 유지 증거 |

**현재 최종 Component 설계나 후보별 요소 수는 존재하지 않는다.** 이를 만들었다고 주장하지 않는다. 대신 모든 후보에 공통인 검사 범위와 셈법을 먼저 정한다. 실제 대안의 전수 목록은 그 대안 명세와 함께 작성하여 **어떤 변경량도 계산하기 전에** 잠근다. 변경 결과를 본 뒤 목록을 잘게 쪼개거나 합치지 않는다.

이 두 단계는 서로 다르다.

```mermaid
flowchart LR
    R["지금: 10에서 공통 기준 검토<br/>유형·범위·셈법"]
    A["대안 명세 작성 시<br/>실제 요소 전체 목록·연결 작성"]
    F["변경 전 목록 검토·동결"]
    C["07의 변경을 하나씩 적용"]
    L["수정·추가·제거 ID와 근거"]
    V["기능 유지 확인 후 변경량 비교"]
    R --> A --> F --> C --> L --> V
```

## 10.2 네 가지 요소 유형

06에서 합의한 네 유형을 사용한다. 아래 조건을 만족할 때만 별도 집계 ID를 부여한다.

| 유형 | 무엇을 한 개로 보는가 | 별도로 세지 않는 것 |
| --- | --- | --- |
| **C — Component / 책임 단위** | 입력·출력과 책임 범위가 구분되고, 처리 행위의 변경 여부를 설명할 수 있는 설계 책임. 실제 소유 Component와 연결 | 함수·파일·클래스·메서드 하나하나, 상위 시스템 박스 |
| **I — Interface / 계약** | 책임 경계의 제공자와 소비자가 함께 준수해야 하는 독립된 의미·오류·수명 계약 | API 필드·메서드별 개수, 내부 private helper 호출, 문서와 Rust trait의 같은 계약 중복 |
| **S — State / Data Schema** | 소유자·참조자·수명·갱신/이행 규칙이 독립적으로 정의된 상태 모델 또는 저장 형식 | 변수·테이블 열·레코드 한 건, API payload를 이름만 바꾼 중복 모델 |
| **D — Runtime / 배치 단위** | 실행 위치·시작/종료·복구·통신 결합을 독립적으로 관리하는 배치 명세 | 동일 배치의 프로세스 인스턴스 수, 사용자 Task 수, 모델 가중치 내부 구조 |

네 유형의 합은 **변경된 설계 항목의 개수**라는 구조적 범위 지표이다. C 하나와 S 하나의 개발 비용이 같다는 뜻이 아니다. 대표값과 함께 반드시 유형별 내역을 공개한다. 중요도나 개발 공수 가중치는 임의로 추가하지 않는다.

### Component와 책임 단위의 관계

하나의 큰 Component에 서로 다른 책임이 들어 있어도 그것을 통째로 1개라고만 세지 않는다. 아래 범위 점검표와 같은 깊이에서 독립된 책임을 식별한다. 반대로 같은 책임의 내부 helper를 여러 파일로 분할했다고 여러 C로 늘리지 않는다.

서로 다른 곳에서 **독립적으로 유지되는 구현**이 같은 기능을 중복 수행하면 각각의 C를 등록할 수 있다. 같은 구현을 여러 번 실행하는 replica나 Task Controller 인스턴스는 같은 C이다. 구현 중복과 실행 인스턴스 수를 구분한다.

## 10.3 한 요소를 인정하는 등록 규칙

요소를 세기 전에 다음 다섯 가지를 모두 설명해야 한다.

1. **정체성:** 무엇을 책임지거나 약속·저장·배치하는 단위인가?
2. **경계:** 누가 소유하고 누가 사용하며, 어떤 내용이 내부 상세인가?
3. **독립성:** 이미 등록한 요소의 다른 이름·하위 필드·그림 복사본이 아닌가?
4. **변경 판정:** 무엇이 달라지면 이 요소를 수정했다고 볼 것인가?
5. **설계 근거:** 계약, 상태표, 의존 관계, 배치 설명 중 어디에서 확인할 수 있는가?

설명할 수 없는 박스는 목록에 `상세 부족`으로 남기고 값을 만들지 않는다. “필요하면 adapter 하나” 같은 주장만으로 1개를 부여하지 않는다.

### 상위·하위 중복 금지

- 상위 `VIA Core`를 요약 박스로 두고 그 안의 책임들을 세면 VIA Core는 다시 세지 않는다.
- `I-Agent`를 하위의 독립 계약들로 나누기로 사전에 정했다면 I-Agent는 요약 항목이고 하위 계약만 센다. 같은 변경에서 부모와 자식을 함께 세지 않는다.
- API의 한 필드가 바뀌면 I가 수정된 것이다. 필드 개수만큼 더하지 않는다.
- 같은 wire payload의 문서 정의와 Rust `struct`는 같은 계약 표현이다. I와 S를 자동으로 두 개로 만들지 않는다.
- API payload와 별도의 수명·버전·이행 규칙이 있는 저장 모델은 **서로 다른 I와 S**이다. 실제로 둘 다 바뀐 경우 각각 센다.
- C의 구현과 독립된 I 계약이 함께 바뀌면 두 개다. C를 소비하는 모든 상위 Component가 자동으로 변경되는 것은 아니다. 실제 행위 변경을 확인한다.

## 10.4 전체 책임 범위 점검표

아래 **RC-01~18은 누락 확인용 참조 항목**이다. 18개의 필수 Component나 18개의 ASR을 새로 만든 것이 아니다. 책임을 묶거나 분리하는 구조, 모델 재사용, 내부 직접 처리 여부는 03·04의 선택권을 유지한다.

각 대안은 모든 행에 `어느 요소가 담당하는지 / 공통 기반을 사용하는지 / 허용된 위임인지 / 해당 없음의 근거`를 답한다. 실제 집계는 RC 개수가 아니라 뒤의 후보별 E-ID 목록으로 한다.

| **RC-16 User Memory 관리** | 허용된 기억의 사용·확인·변경·삭제. Routine 저장을 무인 실행기로 확대하지 않음 | UC-17, C-04 |
| **RC-17 저장·재연결·이행** | 담당 상태의 저장·재시작 복원·schema 이행과 외부 실행 확인. 별도 중앙 저장소를 강제하지 않음 | UC-18, FA-14, C-04·06 |

**한 RC 행을 여러 군데서 담당할 수 있고 한 Component가 여러 RC를 담당할 수 있다.** 다만 집계 C의 책임 깊이는 후보 사이에서 맞춘다. 하나의 거대 박스에 RC 전체를 숨긴 후보와 세부 책임을 모두 노출한 후보를 그 박스 수로 비교하지 않는다.

## 10.5 계약·상태·배치에서 빠뜨리지 않을 범위

아래는 별도 요소의 강제 목록이 아니라 **설계 명세를 펼쳐볼 검사 범위**이다. 실제 별도 계약이나 상태가 없다면 그 책임이 어디에 흡수되어 있는지 기록한다. 공통 Port나 중앙 DB를 정답으로 미리 선택하지 않는다.

| 유형 | 확인할 전체 범위 | 별도 등록의 판단 |
| --- | --- | --- |
| **I 입력·모델** | User Turn/입력 정정, S2S 입출력·시각·generation, 의미 판단 요청/완료/취소, 모델 대화 이력 계약 | native 직접 사용과 공통 계약 사용 모두 가능. 같은 계약의 여러 구현은 I 한 개, 별도 변환 C는 각각 |
| **I Context·Request** | 화면 원천 evidence, 정보원 읽기/오류/권한, 소비 Context·참조 resolution, 정리된 Request·복합 관계 | 실제 책임 경계를 넘는 계약을 등록. private 중간 객체는 자동으로 별도 I가 아님 |
| **I 대화·업무·응답** | 대화 기록 접근, Task 조회·제어, Agent capability·위임·event·질문·결과, Voice/Text·artifact 전달 | 제공자/소비자와 독립 수명이 있으면 구분. 모든 메서드를 따로 세지 않음 |
| **I 정책·저장** | 권한/동의 판단, 승인 응답 연결, 상태 저장·복원·이행, 관측 계약 | 업무 내부 private 상태와 여러 소비자가 의존하는 계약을 구분 |
| **S 음성·Context** | Voice Connection/generation/재생 상태, 화면 evidence의 시점/identity, referent·source 참조 | transient라도 독립 소유·수명을 설계하면 등록 가능 |
| **S 요청·대화·업무** | Request와 관계, Conversation/실제 응답 기록, VIA Task 상태, Agent 실행 correlation, pending interaction | 각 수명이 다름. 하나의 DB에 저장되더라도 자동으로 S 한 개는 아님 |
| **S 권한·기억·복구** | 유효 권한/동의 범위, Agent capability/연결 metadata, User Memory/삭제 상태, 복원 기록·버전 | 동일 상태를 메모리와 저장장치에 둔다는 이유만으로 두 개가 되지는 않음. 별도 형식·이행 규칙이면 구분 |
| **D 실행·연결** | VIA 본체, 추가한 보조/연동 프로세스, S2S·의미 판단 모델 binding, Context/Agent 접속 수명 | local/remote 여부보다 VIA가 바꾸어야 할 실행·연결 명세를 확인 |
| **D 저장·업데이트** | 사용한 저장 서비스/파일의 실행·접근·복구/배포 수명, 계획된 이행의 시작/실패 처리 | 스키마(S)와 저장 서비스 배치(D)는 다름. 실제 별도 배치일 때만 D 등록 |

### 외부 dependency와 VIA 변경량의 경계

Model 가중치, Agent 내부 planner/Tool, 외부 Calendar 서버의 내부 코드는 변경량에서 제외한다. **그 변화에 맞추어 VIA가 고쳐야 하는 호출·계약 변환·상태·설치·접속 명세는 포함한다.** PC 안에 있다는 이유로 Agent 내부를 포함하거나 Cloud에 있다는 이유로 VIA 모델 binding을 제외하지 않는다.

외부 API가 바뀌었다는 사실 자체는 stimulus이다. 그 외부 문서를 VIA의 변경 I로 자동 가산하지 않는다. VIA가 직접 의존하는 계약의 정의·사용 방식이나 변환 책임이 실제로 어떻게 바뀌는지 기록한다.

## 10.6 후보별 요소 전수 목록 양식

각 후보는 다음 양식으로 실제 요소를 모두 등록한다. `E-C-001`, `E-I-001`, `E-S-001`, `E-D-001` 형태의 ID는 **후보 버전 안에서 유일**하다. 최종 식별자는 `후보 ID + 기준 버전 + 요소 ID`이다.

| 필드 | 반드시 적을 내용 |
| --- | --- |
| 후보/버전/요소 ID/유형 | 변경 전 동일 출발점을 식별 |
| 이름과 한 문장 책임 | 그 요소가 무엇인지 처음 읽는 사람도 구분 |
| RC 연결과 구체 범위 | 실제 담당하는 책임, 다루지 않는 영역 |
| 소유자와 사용 요소 | Component·계약 제공자·소비자, 또는 state writer/reader |
| 입력·출력 / 상태 수명 / 실행 수명 | 해당 유형의 의미·실패·갱신 경계를 설명 |
| 상위·하위 / 같은 요소의 별칭 | 요약 항목과 실제 집계 단위의 구분 |
| 의존 요소 ID | 변경 영향이 어디로 전파될 수 있는지 확인 |
| 집계 여부와 근거 | 집계 / 요약 / 외부 / 구현 상세를 명시 |
| 설계 명세 위치 | 계약 표·상태표·sequence·배치 설명의 근거 |
| Rust 연결 계획 또는 실제 위치 | 구현 시 crate/module/type/binary에 어떻게 대응하는지. 코드 없어도 작성 가능 |

### 전수 목록을 잠그는 기준

모든 RC 항목이 담당 요소 또는 타당한 비적용 사유에 연결되어야 한다. 필수 제품 책임을 `해당 없음`으로 지울 수 없다. 직접 답변 가능한 업무를 Agent에 위임하는 선택은 가능하지만 VIA의 grounding·대화·위임·결과 연결 책임은 남는다.

필수 상태·계약·배치가 누락된 후보는 변경량을 계산하지 않는다. 특히 **공통 infrastructure도 후보 목록에 포함**한다. 저장소·인증·factory·관측 기능을 “공통이라 무료”라고 숨기지 않는다. 변경 없는 공통 요소의 변경량은 0이다.

## 10.7 무엇을 변경 1개로 세는가

| 작업 분류 | 집계 | 판정 |
| --- | --- | --- |
| **수정** | 기존 ID 1개 | 해당 책임의 처리 방식, 계약 의미, 상태 모델/이행 또는 배치 명세가 실제로 달라짐 |
| **추가** | 새 ID 1개 | 기존에 없던 독립 책임·계약·상태·배치가 필요함 |
| **제거** | 기존 ID 1개 | 실제 역할/계약/상태/배치가 사라짐. 기능 유지 및 잔여 의존성 확인 |
| 설정값만 변경 | 0개 | 기존 계약 안의 endpoint·모델명·키·한도 값 교체. 설정/배포 작업은 별도 기록 |
| 검사·재빌드만 수행 | 0개 | 소비자 코드·행위·계약은 그대로이고 재검증만 필요함 |
| 명칭·파일 경로만 변경 | 0개 | 의미가 같은 요소의 rename. 새로 추가/제거한 것으로 부풀리지 않음 |
| 모델/VIA 프롬프트 조정 | 내용에 따라 C/I | 값 조정만이면 설정; 책임의 처리 의미나 structured output 계약을 바꾸면 해당 C/I 변경 |
| 데이터 이행 실행 | S/C/D 실제 변화만 | 레코드 수나 SQL 문장 수가 아님. 이행 도구·loader·schema·배치 명세 중 바뀐 것만 등록 |

한 요소가 여러 문서·소스 파일에서 바뀌어도 **그 변경 시나리오 안에서는 한 번** 센다. 수정·추가·제거 집합은 서로 겹치지 않게 기록한다. 같은 identity를 유지한 변경은 이름이 달라져도 수정이고, 완전히 다른 독립 역할로 교체하면 기존 제거와 새 추가를 구분한다. 이 판정은 결과에 유리한 쪽으로 바꾸지 않는다.

```text
변경 e의 요소 수 N(e)
= |수정 ID 집합 ∪ 추가 ID 집합 ∪ 제거 ID 집합|

유형별 내역
= C 몇 개 / I 몇 개 / S 몇 개 / D 몇 개
```

### 07의 전체 집합과 대표값

전부 적용 가능하고 기능 유지 근거를 갖춘 경우:

```text
ASR-04 = [N(A-01) + ... + N(A-09)] / 9
ASR-05 = [N(M-01) + ... + N(M-09) + N(C-01) + ... + N(C-06)] / 15
```

각 변경은 같은 후보의 원래 baseline에서 **독립 적용**한다. 다음 변경이 앞 변경의 이점을 물려받게 하지 않는다. M/C별 내역은 보존하되 08이 정한 비Agent 15개 대표값을 임의의 가중 평균으로 바꾸지 않는다.

적용 불가·미측정 항목이 있으면 위 식의 숫자를 그대로 채운 전체 완료 점수를 내지 않는다. 10.10의 상태 분류와 07의 공통 분모 규칙을 적용한다. 일부 성공 항목만의 평균은 부분 결과라고 표시한다.

## 10.8 계산 예시 — 실제 후보의 결과가 아님

다음 숫자는 **셈법을 검토하기 위한 가상 설계 원장**이다. VIA의 실제 변경량, 성능, 개발 공수나 특정 DP의 우열을 뜻하지 않는다.

| 사례 | 가정한 실제 변경 | 집계 | 왜 그런가 |
| --- | --- | ---: | --- |
| 동등 endpoint 교체 | 기존 설정의 주소만 변경 | **0** | 계약·행위·상태·배치 수명은 그대로 |
| Model 응답 포장 변경 | `E-C-001 Model Binding`의 내부 변환만 수정. 소비 계약은 동일 | **1** | private mapping 수정. I/S/D가 바뀌었다고 자동 가산하지 않음 |
| 새 Agent Adapter 도입 | `E-C-002 Adapter` 추가 + `E-C-003 연결 Factory`의 선택 로직 수정. 기존 I/S/D는 유지 | **2** | 새 구현도 센다. Factory가 기존 설정 등록만으로 처리했다면 Factory 수정은 0이어서 총 1이 됨 |
| 대화·업무 저장 형식 이행 | `E-S-001 저장 모델` 수정 + `E-C-004 Repository`의 읽기/쓰기 수정 + `E-C-005 Migration` 추가 | **3** | 저장 형식과 처리 책임은 독립. 별도 API/배치 변경은 없다는 가정 |
| 동일 처리 코드를 파일 6개로 분할 | 한 C의 내부 파일 구성만 변경 | **1** 또는 **0** | 행위도 바뀐 change이면 C 1개, 순수 file 정리이면 0. 파일 6개로 세지 않음 |
| 같은 Agent Controller 인스턴스 증가 | 같은 코드·계약·배치에서 실행 중 Task만 증가 | **0** | 실행 workload 변화이며 새 Architecture Element가 아님 |

### 변경 전후 원장 예

| Change | 요소 | 유형 | 전 상태 → 후 상태 | 작업 | 근거 |
| --- | --- | --- | --- | --- | --- |
| C-06 예시 | E-S-001 | S | 기존 연결 record → 분리된 record 구조 | 수정 | 같은 의미, 별도 저장 형식 버전과 이행 규칙 |
| C-06 예시 | E-C-004 | C | 구형 loader/writer → 신형 형식 처리 | 수정 | Repository 책임의 처리 변경 |
| C-06 예시 | E-C-005 | C | 없음 → 구형 정보의 변환 책임 | 추가 | 기존 기록을 보존하며 이행하는 별도 책임 |

이 예시의 변경량은 `C=2, I=0, S=1, D=0`, 총 **3개**다. Consumer가 같은 인터페이스로 계속 읽는다면 모든 Consumer를 수정 항목으로 자동 추가하지 않는다. 실제 consumer 변경이 있으면 그 ID와 이유를 추가한다.

## 10.9 Rust로 구현할 때 무엇과 연결하는가

Rust의 코드 단위와 Architecture Element는 일대일 대응하지 않는다. 공식 Rust 문서 기준으로 `crate`는 컴파일 단위, `module`은 코드 구성·가시성 단위, `package`는 Cargo.toml을 가진 crate 묶음이며, `workspace`는 함께 관리하는 package 집합이다. [Rust-1][Rust-2][Rust-3]

| Rust 표현 | Architecture에서 볼 것 | 자동으로 세면 안 되는 이유 |
| --- | --- | --- |
| `mod` / 소스 파일 | C 책임의 구현 위치 또는 내부 상세 | 파일 분할로 개수가 바뀜 |
| library / binary `crate` | C 구현 묶음 또는 실행 파일 후보 | 한 crate가 여러 책임을 가질 수 있고, 하나의 책임이 여러 crate를 이용할 수 있음 |
| `trait`, 공개 API | I 계약의 구현 표현 | 모든 trait가 외부 Architecture 계약은 아님 |
| `struct`, `enum`, 저장 record | I payload 또는 S 상태 모델 | 같은 의미를 I와 S로 중복 세지 않아야 함 |
| binary 실행·서비스 명세 | D의 근거 | 모든 binary가 독립 배포·복구 단위인 것은 아님 |
| Cargo workspace / dependency | 공통 빌드·의존 연결 | workspace나 재빌드 개수는 변경 책임 개수가 아님 |

예를 들어 한 `via_core` crate 안에 Voice와 Task 책임이 독립적으로 있으면 두 책임은 별도로 설명한다. 반대로 `model_binding` 책임을 여러 파일로 분할해도 하나의 C일 수 있다. **Rust 구현이 아직 없어도 책임·계약·상태·수명 명세로 먼저 등록할 수 있다.** 코드가 생기면 요소 ID와 실제 위치를 연결하여 추정을 확인한다.

AI coding 환경에서 여러 담당자가 변경해야 하는 범위는 이 지표의 해석에 도움이 된다. 그러나 **요소 3개 = 충돌 3회 = 일정한 토큰/M/M**이라고 환산하지 않는다. 실제 협업 충돌과 공수의 증거가 없기 때문이다.

## 10.10 변경 평가 상태와 증거 수준

| 상태 | 뜻 | 숫자 처리 |
| --- | --- | --- |
| **평가 완료** | 전후 설계·변경 ID·기능 유지 근거가 있음 | N(e)와 증거 수준 기록 |
| **설정만 변경** | 기존 계약으로 대응, 설계 변경 없음 | N(e)=0, 설정/검증 작업은 별도 |
| **적용 없음** | 해당 변화의 실제 대상이 후보에 없음 | 사전 근거 필요. 0으로 평균에 넣지 않음 |
| **처리 불가** | 정의된 변화 뒤 필수 기능을 유지할 설계가 제시되지 않음 | 유효한 작은 값으로 취급하지 않음 |
| **분석 부족·미검증** | 변경/기능 유지의 증거가 부족 | 미측정으로 표시. 0이나 성공값 금지 |

별도 Semantic Model이 없어도 S2S가 그 판단 역할을 맡으면 관련 Model 변경의 실제 적용 여부를 먼저 확인한다. Thin VIA도 외부 Agent/Context와의 접점이 없어지는 것은 아니다. 비적용을 유리한 항목만 남기는 수단으로 쓰지 않는다.

**설계 분석, 모의시험, 실제 구현 검증을 구분한다.** 설계 변경량은 구현 전에 추정할 수 있으나, UC가 실제로 성공했다고 말하려면 실행 증거가 필요하다. 설계 분석 단계에서는 계약·상태 전이·필요 데이터의 유지 논증을 남기고 `설계 추정`으로 표시한다.

공통 적용 집합의 부분 비교가 필요하면 동일 분모와 빠진 항목을 공개한다. 공통 부분에서 유리하다는 것과 전체 24개 변화에 더 잘 대응한다는 결론은 다르다.

## 10.11 변경 원장과 검토 순서

한 Change마다 다음 내용을 남긴다.

```text
후보 ID / baseline 버전 / Change ID
변경 전 → 변경 후 계약 (07 원문 연결)
적용 여부와 그 이유
수정 ID / 추가 ID / 제거 ID
각 ID의 전후 차이·파급 의존성·설계 근거
변경하지 않은 주요 소비자와 그 이유
C / I / S / D별 개수와 중복 없는 총수
설정·빌드·배포·데이터 이행·회귀 작업 (별도)
유지해야 할 UC / 검증 결과 또는 설계 유지 논증
실측·모의시험·설계 추정 구분 / 남은 불확실성
```

검토는 **기능 유지 → 전후 변경 근거 → 누락·중복 → 집계** 순서로 한다. 먼저 숫자를 정하고 이유를 맞추지 않는다. 모델 성능·코드 생성 속도가 아니라 구조 변경 범위를 비교한다.

## 10.12 09/10 승인 결과

| 확인할 것 | 통과 조건 |
| --- | --- |
| 코드 완성 없이 사용할 수 있는가? | 책임·계약·상태·배치 명세로 E-ID를 등록하고 변경 전후를 설명 가능 |
| 전체 설계 범위를 놓치지 않는가? | RC-01~18과 I/S/D 범위를 모든 후보가 점검 |
| 그림 크기나 crate 수로 점수가 바뀌지 않는가? | 같은 깊이의 책임, 부모/자식 중복 금지, 구현·replica 구분 |
| Adapter를 무료 또는 과다 계산하지 않는가? | 새 C와 실제 수정만 집계; 변경 없는 I/S/D는 추가하지 않음 |
| 24개 Change가 같은 규칙을 쓰는가? | 같은 baseline, 동일 셈법, Agent 9/비Agent 15 집계 소유권 유지 |
| 예시를 실제 결과처럼 주장하지 않는가? | 예시는 셈법 확인으로만 표기 |

**공통 요소 정의와 집계 규칙은 사용자 승인 완료 상태이다.** 후보별 실제 요소 목록과 변경량은 아직 산출하지 않았으며, 11-A/B의 측정·시험 정의를 검토한 뒤 11-C에서 목표값·0~5점·최종 집계를 승인하고 이후 12의 DP 후보에 동일 규칙을 적용한다.
