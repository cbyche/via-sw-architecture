# 목표 근거와 측정 설계

작성일: 2026-10-06. 이 문서는 사용자의 리뷰를 반영한 **근거 기반 목표 제안**이다. VIA의 실측 결과나 동결된 측정 계약으로 해석하지 않는다.

## 1. 발표 범위와 목표 설정 원칙

V-01~10 중 기존 우선순위를 유지한 10개를 발표한다. V-08은 V-06보다 앞에 배치한다. 공동 순위 내부에는 추가 순위를 만들지 않는다. 각 항목은 하나의 품질 속성과 하나의 주지표만 가진다.

V-11은 발표에서 제외하고, PC 공존 비용 중 메모리 부분만 V-06에 반영한다. 메모리 지표가 외부 시스템과의 상호운용성 전체를 평가하는 것은 아니다. V-12와 V-13도 현재 발표의 DP 연결이 약하다는 사용자 판단에 따라 제외한다. 원본 V 목록과 기존 Architecture 및 QA 계약은 그대로 보존한다.

외부 논문의 결과를 VIA의 성능처럼 옮겨 적지 않는다. 각 목표는 아래에서 **출처가 실제로 말하는 사실**, **VIA의 목표로 선택한 이유**, **적용 한계**로 나눠 설명한다. 동일한 제품과 시험이 없는 항목에는 출처의 원칙이나 장치 사양을 바탕으로 VIA의 예산을 계산한다. 특히 90%, 3개, 16GB는 외부 문헌이 VIA에 직접 규정한 수치가 아니다.

100%는 고정 계약의 완전 지원과 연구용 시험 기록의 전수 재구성을 뜻한다. 0건은 고정 권한 계약의 금지 사건 예산이다. 둘 다 미래의 모든 입력이나 모든 공격에 대한 보증을 뜻하지 않는다. 목표를 달성하지 못한 대안도 결과와 비용을 보존하며, 이 발표만으로 후보 탈락이나 승자를 결정하지 않는다.

## 2. 공통 모집단과 시험 조건

### 2.1 기능 모집단

[대표 UC 원문](../../architecture/05-representative-use-cases.md)은 UC 18개와 필수 변형 94개를 포함한다. 기능 단위는 가장 구체적인 필수 변형으로 잡는다. 상위 UC를 다시 합산한 112개를 분모로 쓰면 동일 기능을 두 번 센다.

| UC | 필수 변형 수 | UC | 필수 변형 수 | UC | 필수 변형 수 |
| --- | ---: | --- | ---: | --- | ---: |
| UC-01 | 4 | UC-07 | 5 | UC-13 | 6 |
| UC-02 | 6 | UC-08 | 5 | UC-14 | 5 |
| UC-03 | 6 | UC-09 | 5 | UC-15 | 5 |
| UC-04 | 7 | UC-10 | 5 | UC-16 | 5 |
| UC-05 | 4 | UC-11 | 5 | UC-17 | 5 |
| UC-06 | 5 | UC-12 | 5 | UC-18 | 6 |

[functional-coverage.json](functional-coverage.json)에 94개 ID를 고정한다. 각 변형을 구체적인 상황 5개로 만들고 각 상황을 4회 반복하여 **94 × 5 × 4 = 1,880회**를 제안한다. 5개는 정답이 같은 단순 문장 복사 대신 표현, 참조 대상, 업무 이력, 화면 상황과 사건 순서를 바꾸되 해당 변형의 필수 동작을 유지한다. 변형 자체가 음성 전용이면 텍스트 사례를 억지로 추가하지 않는다. 오류나 예외가 원래 변형이면 기대되는 거절 또는 보류를 정답으로 정한다.

다섯 사례와 네 반복은 시험 규모 선택이며 논문이 규정한 값이 아니다. 동일 사례를 무작위 순서와 같은 seed 집합으로 모든 후보에 적용한다. 분석 시 94개 변형이 동일한 가중치를 갖는다. 아직 구체 입력 fixture나 실행 runner는 만들지 않았으며, JSON은 시험 목록 설계이다.

한 시험은 하나의 사용자 목표를 위한 상호작용 전체이다. 정정, 질문 답변, 후속 제어가 있더라도 같은 목표의 시험에 포함한다. 모델 호출, tool 호출이나 하위 Task를 별도 성공 표본으로 늘리지 않는다. 사용자가 독립적인 새 목표를 자발적으로 추가하면 새 시험으로 구분한다.

### 2.2 정답과 외부 경계

각 사례에는 시험 전 정답 manifest를 작성한다. 필드는 기대 의도, 대상, Conversation과 Task 연결, 요청 관계, 수정 범위, 허용 처리, 상태 변화, 필요한 결과 전달이다. 적용하지 않는 필드는 실행 전에 이유를 명시한다. 두 검토자가 기대 상태를 작성하고 불일치를 해결한 뒤 후보에 동일하게 적용한다. 후보가 내놓은 문장을 정답으로 삼지 않는다.

Downstream Agent는 동일한 capability와 성공, 실패, 지연, 중복 알림 script를 제공하는 결정적 simulator로 고정한다. VIA가 받는 외부 결과와 실행 사실을 oracle에 기록한다. Agent 내부의 도메인 답변 품질을 VIA 성공률에 섞지 않는다. VIA의 잘못된 위임, 업무 연결, 상태 판단이나 결과 전달은 포함한다.

시험 timeout은 최종 외부 사건 후 60초의 VIA 책임 시간으로 제안한다. 시간 목표 1초 또는 10초와 구분되는 관측 종료 조건이다. timeout과 crash도 전체 목록에 남긴다. 미지원, 미확인, 로그 누락을 성공 표본에서 제거하지 않는다. 실제 평가 전에 사례 manifest, seed, timeout, 환경 및 집계를 함께 확정한다.

### 2.3 장치와 부하

삼성 Galaxy Book6 Ultra NP960UJH-XG3IN의 32GB RAM, RTX 5070 Laptop 전용 GPU 8GB, Windows 11 구성을 발표의 장치 예산 기준으로 삼는다 [S06]. 실제 시험 장치는 모델명, BIOS, OS build, driver, 전력 모드, CPU, GPU, 저장장치와 사용 가능한 물리 메모리를 별도 기록한다. 다른 장치의 결과를 같은 장치 실적으로 표시하지 않는다.

Omni와 Streaming ASR 및 모든 helper의 버전, 파라미터 수, 정밀도, 실제 파일 크기와 loaded bytes를 기록한다. 하나의 공유 Omni 가중치를 전제하고 역할별 Context와 KV의 실제 비용을 포함한다. 모델 호출량이나 의미 지원 범위를 줄여 메모리만 통과한 구성은 V-01과 V-03의 결과에서 드러나야 한다.

시험 부하는 한 개의 활성 대화, 미완료 Task 네 개, 동시에 진행하는 외부 실행 두 개를 기본 profile로 제안한다. 이는 현재 측정된 수용량이 아닌 명시적인 비교 조건이다. 더 큰 부하는 별도 민감도 시험으로 공개한다. 입력 시간축과 최대 retained Context, KV, 화면 근거, 오디오 버퍼의 설정을 manifest에 적어 임의의 cache 한도 차이가 결과를 결정하지 않도록 한다.

Cold 시작, warm 요청, 연속 정정, Task 전환, 음성 출력 중 새 입력, 재접속 및 장시간 background 상태를 분리해서 표시한다. 전체 평균만 공개해 어려운 조건을 숨기지 않는다.

## 3. V-01 기능 정확성

**설명:** 사용자 요청을 의도에 맞게 정확히 처리해야 한다.

**단일 목표:** 정확 처리율 90% 이상.

**근거:** Joint BERT 연구의 SNIPS 시험은 문장 전체의 의도와 slot이 모두 맞는 semantic frame accuracy 92.8%를 보고한다 [S01]. slot F1 97.0%나 intent 정확도 98.6%를 전체 요청 성공률처럼 쓰지 않는다. VIA의 첫 통합 평가에서는 더 복잡한 화면과 업무 상태 판단까지 포함하므로 이 문장 단위 결과를 그대로 달성했다고 가정하지 않고, 가까운 정수 10% 단위의 보수적인 목표인 90%를 제안한다. 이는 허용 오류 예산이 전체 시험의 10%라는 뜻이다.

92.8%와 VIA 90%는 서로 다른 모집단이다. 비교 실적이나 최종 제품 출시 기준으로 주장할 수 없다. tau-bench가 대화 종료 후 실제 DB 상태를 정답 상태와 대조하는 방법은 전체 요청의 성공 판정에 참고한다 [S02]. 그 benchmark에서 보고한 낮은 Agent 성공률은 VIA의 90%를 증명하거나 반박하는 직접 비교 수치가 아니다.

**분모와 식:**

```text
N = 94개 필수 변형 × 5개 구체 사례 × 4회 반복 = 1,880회
success(i) = 사례 i의 적용 가능한 필수 oracle 판정을 모두 만족하면 1, 아니면 0
정확 처리율 = 100 × Σ success(i) / 1,880
목표 성공 수 = 1,692회 이상
```

미지원도 분모에 포함한다. 원래 예외 시험에서 올바른 보류나 거절은 성공이지만, 기능을 지원하지 못해 정상 요청을 거절한 경우는 실패이다. 정확한 안내 문구만 내놓고 필요한 처리를 수행하지 않으면 성공으로 세지 않는다.

시험 전 manifest와 실제 semantic output, 채택된 상태, 명령, Agent 사실 및 사용자에게 전달한 결과를 자동 대조한다. 동등한 표현의 의미 판정이 필요하면 후보를 가린 검토자가 rubric으로 판정한다. 전체 판정과 필드별 오류를 모두 보존한다. 모델을 judge로 사용할 때도 사람과 일치도를 먼저 검증하며 judge의 답을 무검토 정답으로 삼지 않는다.

90%는 이 비율 하나의 목표이다. 다른 업무 오실행과 중복 실행을 별도의 0건 목표로 이 행에 넣지 않는다. 이런 사건은 해당 시험의 정확성 실패와 오류 유형으로 남기며 기존 실행 안전 계약도 유지한다. 반복은 독립 사용자 표본이 아니므로 신뢰구간은 470개 구체 사례를 cluster로 묶어 추정한다.

## 4. V-02 기능 적절성

**설명:** 사용자가 적은 추가 입력으로 요청을 마칠 수 있어야 한다.

**단일 목표:** 평균 사용자 개입 1회/요청 이하.

**근거:** 시각 질의의 정보가 부족할 때 CoA는 필요한 경우 하나의 집중된 질문을 하고 답변을 반영하는 접근을 사용한다 [S03]. VIA도 근거를 먼저 활용하고 한 번의 답변에 필요한 정보를 모으는 상호작용을 목표로 삼아 추가 개입 예산을 1회로 제안한다. 이 연구는 VIA의 모든 요청이 질문 하나로 해결된다는 실증 근거가 아니며, VIA의 권한 승인 비용도 아래 횟수에 포함한다.

**분모와 식:** 같은 1,880회 전체 시험에 대해, 최초 목표 입력 이후 VIA가 요구한 추가 사용자 입력을 센다.

```text
u(i) = VIA가 요구한 추가 답변, 선택, 승인 또는 수동 우회 횟수
사용자 개입 횟수 = Σ u(i) / 1,880
```

하나의 질문에 음성과 선택 UI를 함께 사용해 답하면 하나의 응답 episode로 센다. VIA가 다시 질문하여 새 답변을 받으면 한 번을 더 센다. 자동 정보 읽기와 시스템 내부 재시도는 사용자 개입이 아니다. 자발적 새 목표는 최초 입력으로 분리하지만, 기능 부족 때문에 사용자가 수동으로 앱을 조작하는 우회는 포함한다.

시험 사용자는 script에 정해진 최소 답변을 제공한다. 실패 응답 뒤 원래 목표를 다시 요청하거나 앱에서 수동으로 마무리하는 동작도 script에 넣고 실제 개입으로 센다. 필요 권한을 생략하거나 불확실한 대상에 대해 추측해 개입을 줄인 시험은 V-01이나 V-10에서 실패한다. 미완료 시험도 당시까지의 실제 횟수로 분모에 남기고 성공 여부에 따른 개입 분포를 함께 공개한다. 아무것도 수행하지 않는 구현의 0회는 낮은 부담의 근거로 해석하지 않는다. 이 지표는 V-01과 V-03의 기능 결과와 함께 평가하며 성공 시험만 뽑은 평균을 쓰지 않는다.

## 5. V-03 기능 완전성

**설명:** 고정된 사용 시나리오의 필수 기능을 모두 지원해야 한다.

**단일 목표:** 기능 지원 달성률 100%.

**근거:** 94개 필수 변형은 제품 기능 계약 자체이다 [S00]. 선택적인 benchmark 문항이 아니므로 완전 지원의 목표는 94개 모두를 지원하는 100%로 정한다. 이 수치는 문헌의 통계적 정확도에서 가져오지 않는다.

**분모와 식:**

```text
support(v) = 변형 v의 필수 동작 전체를 구현하고 검증 증거를 제공하면 1, 아니면 0
기능 지원 달성률 = 100 × Σ support(v) / 94
```

각 변형에는 입력, 필요한 VIA 처리, 정상 종료, 변형 고유의 예외 및 책임 경계를 체크리스트로 작성한다. 구현 경로와 실제 동작 witness를 대조한다. 모든 구체 사례의 필수 capability를 입증해야 완전 지원으로 표시한다. 기능이 있지만 일부 실행에서 발생한 확률적 의미 오류는 V-01에서 집계하며 그 사실만으로 capability를 미구현이라고 바꾸지 않는다. 반대로 지원하지 않는 관계를 사용자가 수동으로 해결하면 부분 지원이다.

부분 지원, 미지원, 미확인은 분모에 남고 분자에는 들어가지 않는다. 표에는 한 비율만 표시하고 상세 support ledger에는 제한과 증거 링크를 남긴다. 설계 문서만 검토한 시점에는 '설계상 지원'을 별도 표시하며 구현 지원률 결과를 만들지 않는다. 현재 실제 support ledger와 실행 결과는 없다.

## 6. V-04 응답 신속성

**설명:** 사용자 입력에 대한 유효한 반응이 빠르게 나타나야 한다.

**단일 목표:** 종류별 p95 반응 지연의 최댓값 1초 이하.

**근거:** Nielsen은 상호작용의 반응시간 기준으로 0.1초, 1초, 10초를 제시한다 [S04]. VIA의 첫 유효 반응에는 1초 기준을 선택한다. p95와 종류별 최댓값은 VIA의 시험 집계 선택이며 Nielsen의 원문 통계 정의가 아니다.

| 종류 | 실제 시작 사건 | 실제 종료 사건 |
| --- | --- | --- |
| 요청 반응 | 실제 발화 종료 또는 텍스트 제출 | 해당 요청의 의미 있는 응답이 표시되거나 첫 유효 음성이 재생됨 |
| 상태 전달 | 외부 상태가 VIA에게 이용 가능해진 source 사건 | 그 사실을 반영한 상태가 사용자에게 표시됨 |
| 업무 제어 | 사용자 제어 명령의 실제 입력 | VIA가 제어를 적용하고 그 사실을 확인할 수 있음 |
| 음성 중단 | 사용자의 새 발화가 실제 시작함 | 이전 음성의 마지막 출력 sample |

업무 취소에 Agent의 실행 중단 확인이 필요하면 상태 전달 지연의 시작은 실제 외부 확인이다. 사용자 요청부터 외부 확인까지의 실제 체감 시간도 함께 공개한다. 음성 출력 중단을 업무 취소 완료로 세지 않는다. 접수 인사, 의미 없는 filler, spinner, enqueue와 model 내부 완료는 종료점이 아니다.

동일 monotonic clock으로 시작 사건과 실제 출력 사건을 수집한다. 음성은 녹음된 입력 기준점과 OS 오디오 loopback을 정렬하고 장치 오차를 기록한다. 종류마다 최소 20회 이상 관측하며 1,880회 시험에서 해당하는 모든 사건을 포함한다. 종류별 nearest-rank p95를 구한 뒤 가장 큰 값을 대표값으로 한다. 사건이 발생했는데 유효 반응이 없으면 지연을 무한대로 기록한다. Cold와 warm 결과를 각각 공개하고 긴 지연을 pooled 평균으로 숨기지 않는다.

## 7. V-05 요청 완료 신속성

**설명:** 필요한 최종 결과를 사용자에게 빠르게 전달해야 한다.

**단일 목표:** 처리 경로별 p95 VIA 완료시간의 최댓값 10초 이하.

**근거:** Nielsen의 10초 기준은 사용자가 상호작용에 주의를 유지하는 상한을 제안한다 [S04]. 이 값을 VIA 책임 처리의 완료 예산으로 적용한다. 외부 Agent의 긴 도메인 작업을 포함한 전체 업무가 10초에 끝난다는 뜻은 아니다. 따라서 발표 표에도 'VIA 완료시간'이라고 명시한다.

직접 응답은 VIA가 결과를 만드는 경로이고 위임은 Downstream Agent가 실제 업무를 수행하는 경로이다. **의존 관계**는 앞 결과를 다음 작업의 입력으로 쓰는 관계이다. 예를 들어 보고서 결과로 발표 슬라이드를 만드는 경우이며, 직접 응답과 위임 모두에 생길 수 있다. 세 번째 상호 배타적인 처리 경로로 분류하지 않는다.

측정은 직접 응답과 위임을 각각 의존 관계 없음과 있음으로 나눈 네 층으로 수행한다. 모든 층에 같은 10초 목표를 적용하고 최악 층의 p95를 보고한다. 층별 별도 목표 세 개를 만들면 동일한 VIA 완료 예산의 의미가 흐려지므로 채택하지 않는다.

**VIA 책임 시간 계산:** 최초 입력부터 필수 최종 전달까지의 사건 의존 그래프를 만든다. 해석, 근거 읽기, 자원 대기, 상태 채택, routing, 직렬화, Agent 통합 통신, 결과 결합과 실제 출력의 VIA 책임 구간을 포함한다. 외부 Agent의 도메인 작업과 사용자의 답변 대기 구간은 비용 0으로 치환한다. 이 그래프의 최장 경로 시간이 VIA 완료시간이다. 중첩된 parent span과 child span을 동시에 더하지 않는다. 병렬 작업도 모두 직렬 합산하지 않는다. 단순히 모든 Agent 시간을 총 wall time에서 빼면 겹치는 대기로 음수가 생길 수 있으므로 사용하지 않는다.

동시에 실제 사용자 체감 wall time과 외부 대기 시간을 보조 기록한다. 필수 결과의 text, artifact 접근 및 필요한 최종 음성 전달이 모두 끝나야 종료한다. 첫 packet이나 첫 음절만으로 완료를 판정하지 않는다. 실패 시험과 필수 결과 누락은 무한대 지연으로 남긴다.

자료 길이는 양쪽에 동일한 manifest로 고정한다. 일상 결과의 요약과 상세 artifact, 긴 음성 설명은 별도 층으로 표시한다. 소리의 실제 재생 시간도 VIA 비용에 포함하므로 10초를 넘는 필수 발화를 이 목표 안에 억지로 통과시킬 수 없다. 출력 축약이 필수 내용을 없애면 V-01이나 V-03에서 실패한다. 결과 크기가 다른 사례를 삭제해 목표를 통과시키지 않으며 적용 범위 변경은 측정 전에 승인한 공통 계약에만 반영한다.

## 8. V-08 변경 용이성

**설명:** 기능 변경이 적은 설계 요소에만 영향을 주어야 한다.

**단일 목표:** 평균 변경 요소 수 3개/변경 이하.

**근거:** SEI는 변경 비용을 바뀌는 책임과 다른 요소로의 전파 및 시험 비용으로 설명한다 [S05]. 이를 VIA에서 한 책임 요소, 그 요소의 계약, 그 계약을 소비하는 요소까지의 국소 변경 예산으로 구체화하여 평균 3개를 제안한다. 논문이 3이라는 상한을 제시한 것은 아니다. 모든 변경이 항상 세 역할을 바꿔야 한다는 뜻도 아니다.

공통 변경 과제는 아래 여섯 개를 제안한다. 양쪽 대안은 같은 사용자 동작과 외부 capability를 유지해야 한다.

1. 참조 대상에 표의 선택 범위를 추가한다.
2. 기존 Task를 이어 쓰는 요청 관계 규칙을 추가한다.
3. Downstream Agent의 진행 및 결과 protocol을 변경한다.
4. 음성 중단 정책을 바꾸되 Task 실행은 유지한다.
5. Context 보존기간과 삭제 전파 정책을 변경한다.
6. 외부 결과 중복 알림의 재접속 처리 규칙을 변경한다.

측정 전 후보별 논리 요소 ledger를 같은 수준으로 작성한다. Module, 독립 interface 계약, 공유 schema 및 별도 runtime 배치 단위를 등록하고 동일 정의를 따른다. 파일이나 코드 줄을 요소로 세지 않는다. 책임 Module의 내부 구현과 그 Module 전용 private schema는 한 요소로 센다. 공개 공유 계약을 변경하면 독립 계약 요소로 센다. 그림의 사각형을 임의로 합쳐 수를 줄일 수 없다.

과제별로 실제 추가, 수정, 삭제가 필요한 요소의 ID 합집합 크기 N을 센다. 공통 코드, 설정, 테스트 harness를 변경해야 기능이 성립하면 해당 논리 요소도 포함한다. 같은 요소의 여러 파일과 여러 commit은 한 번만 센다. 설계만 있을 때는 예상 영향 수로 표시하고 실제 수행 비용으로 주장하지 않는다. 해결하지 못한 과제를 평균에서 빼지 않고 미달로 기록한다.

```text
평균 변경 요소 수 = Σ N(s) / 6
MH 추정(s) = a(변경 종류) + b(변경 종류) × N(s)
MM 추정(s) = MH 추정(s) / H_month
```

MH는 person-hour, MM는 person-month이다. a는 분석과 공통 검증의 고정 비용, b는 요소당 추가 수정과 시험의 비용이다. 완료된 실제 과제에서 작업시간을 기록하고 변경 종류별 회귀로 보정한다. 자료가 적으면 임의의 a와 b를 채우지 않는다. H_month는 조직의 표준 월 근무시간이며 160시간을 선택한다면 8시간 × 20일이라는 환산 규약을 명시한다. 3개를 3MH 또는 3MM로 곧바로 환산할 수 없다. 보정 자료 수, 추정 오차와 실제 MH를 함께 공개한다.

## 9. V-06 메모리 효율성

**설명:** 상시 실행 중에도 다른 PC 작업을 위한 메모리를 남겨야 한다.

**단일 목표:** 최대 전체 메모리 16GB 이하. GB는 10^9 bytes이다.

**장치 근거:** Samsung의 Galaxy Book6 Ultra NP960UJH-XG3IN 공식 사양은 32GB LPDDR5X RAM과 RTX 5070 Laptop GPU의 전용 8GB GDDR7을 명시한다 [S06]. 이 고사양 노트북을 기준으로 사용자 PC의 RAM 절반 이상을 VIA 외 용도로 남기는 예산을 설정한다.

| 32GB RAM의 배정 | 예산 | 성격 |
| --- | ---: | --- |
| Windows와 기본 상주 프로그램 | 6GB | VIA가 제안하는 예약량, 실측 OS 사용량 아님 |
| 사용자의 browser와 문서 및 개발 앱 | 6GB | 공존 부하 예산, 실제 foreground app manifest로 검증 필요 |
| 부하 변동과 작업 확장을 위한 여유 | 4GB | 설계상 headroom |
| VIA의 전체 메모리 상한 | 16GB | 32 - 6 - 6 - 4로 계산한 단일 목표 |

전용 GPU의 8GB를 RAM에 더해 VIA 예산을 24GB로 키우지 않는다. 목표는 VIA가 사용하는 CPU RAM과 전용 VRAM의 실제 물리 사용량을 합친 16GB이므로 CPU RAM만 16GB를 사용하는 경우에도 비 VIA RAM 예산을 보존한다. GPU 전용 메모리에는 별도의 물리적 장치 한계가 있다. 16GB가 전부 GPU에 들어간다고 가정하지 않는다. 64GB 장치를 사용하더라도 발표 목표를 자동으로 배증하지 않는다.

**모델 근거와 할당:** 현재 reference Architecture의 약 10B는 Thinker/backbone의 목표 크기이다. encoders, Talker, Streaming ASR와 기타 learned helper까지 10B라고 간주하지 않는다. 원시 가중치 bytes는 N × bit / 8이므로 10B backbone만 FP16에서 약 20GB, 8bit에서 약 10GB, 4bit에서 약 5GB이다. AWQ는 4bit LLM 배포의 실제 연구 근거이다 [S07]. 양자화 선택이나 VIA의 정확도 보존을 승인했다는 뜻은 아니다.

16GB 안에서 backbone 가중치와 양자화 부대 정보 6GB, 나머지 learned weights 4GB, KV와 중간 상태 3GB, runtime과 UI 및 관측 버퍼 3GB의 할당을 제안한다. 모두 상한 예산이며 실제 모델 크기 주장이 아니다. 전체 weight inventory가 예산을 초과하면 목표 미달로 보고하고, 모델 구성을 바꿀 때에는 기능 정확성도 다시 확인한다. CPU staging copy와 GPU loaded copy가 실제로 공존하면 둘 다 포함하므로 이 예산을 더 빠르게 소진한다.

**측정 식:**

```text
M(t) = VIA의 CPU 고유 상주 물리 bytes
     + VIA의 전용 GPU 물리 bytes
     + 다른 항목에 포함되지 않은 pinned 및 공유 물리 bytes
최대 전체 메모리 = max_t M(t) / 10^9
```

여러 프로세스가 같은 물리 페이지를 매핑하면 한 번만 센다. 실제 CPU와 GPU 복제본은 별개이다. Windows Working Set의 단순 프로세스별 합계는 공유 페이지를 중복 셀 수 있고 Private Bytes만 쓰면 공유 가중치를 놓칠 수 있으므로 page 및 allocation ID와 GPU allocation ledger로 보정한다. process tree는 VIA launcher가 기록하고 모든 worker와 helper를 포함한다. pagefile로 밀어낸 bytes와 commit은 보조 기록으로 공개하여 swapping으로 피크를 낮춘 결과를 드러낸다.

8시간 시험을 다음 순서로 수행한다. 상주 대기 두 시간, 요청 burst 한 시간, 정상 대화와 두 외부 실행 병행 두 시간, 화면 및 Context 보존 한도 도달과 삭제 한 시간, 장애 및 모델 재로딩 한 시간, 무입력 대기 한 시간이다. burst는 15초마다 한 요청을 제안하며 처리되지 않은 요청도 적체 상태로 남긴다. 나머지 단계의 입력 시간축은 동일 fixture로 고정한다. browser와 문서 앱 부하는 같은 파일과 tab 목록으로 유지하고 실제 사용량을 기록한다.

최소 100ms 간격의 CPU 및 GPU 계측과 allocation high-water mark를 함께 사용한다. 짧은 load peak를 sampling만으로 놓치지 않도록 allocator의 생성과 해제 사건을 보조로 사용한다. 시작부터 종료까지의 최대값 하나를 목표와 비교하고 대기, 요청 및 복구 피크는 원인 분석용으로 분리한다. 장시간 무입력의 idle 메모리도 공개한다. CPU나 전력의 별도 목표를 새로 만들지는 않는다.

## 10. V-07 복구 용이성

**설명:** 장애 뒤 기존 업무를 이어갈 수 있는 상태로 돌아와야 한다.

**단일 목표:** 최대 정상 복구시간 10초 이하.

**근거:** 사용자의 주의 유지 한계인 10초를 장애 후 재개 예산으로 채택한다 [S04]. microreboot 연구는 실행 단위를 재시작하면서 필요한 상태를 보존하는 회복 구조와 짧은 복구의 가능성을 보여준다 [S08]. 그 웹 시스템의 시간은 VIA의 Omni 로딩이나 전체 복구 성능이 아니므로 그대로 적용하지 않는다. 논문에서 VIA 복구가 10초라고 측정했다는 표현도 쓰지 않는다.

각 장애는 저장 전, 저장 후 외부 전달 전, 외부 전달 후 확인 전의 적용 가능한 세 지점에 주입하고 각각 4회 반복한다. 부적합한 지점은 이유를 사전에 정하고 같은 지점을 양쪽 후보에서 제외한다. 정상 복구의 oracle은 필요한 사용자 입력을 받고, 현재 상태를 정확히 설명하며, 다음 필요한 처리 또는 명확한 보류 상태로 이어가는 것이다. Agent의 긴 작업이 끝나야 복구되는 것은 아니다.

| ID | 장애 | 확인할 상태 |
| --- | --- | --- |
| F01 | semantic model 호출 timeout | 미채택 해석을 완료 사실로 쓰지 않고 새 입력 처리 가능 |
| F02 | shared model runtime 종료 | cold weights와 세션 재구성 후 입력과 해석 재개 |
| F03 | 음성 출력 오류 | Task 사실을 보존하고 text나 정상 음성으로 상태 확인 가능 |
| F04 | 관측 producer 종료 | 근거 공백을 표시하고 해당 없는 참조를 추측하지 않음 |
| F05 | VIA 상태 owner 종료 | 채택 상태와 미완료 의도를 올바르게 구분 |
| F06 | 저장 실패 또는 crash | 미확정 상태를 확정 사실로 발표하지 않음 |
| F07 | Agent 연결 단절 | 외부 실행이 미확인임을 보존하며 접속 재개 가능 |
| F08 | 결과 확인 응답 유실 | 재접속 후 실제 Agent 결과로 상태 정정 |
| F09 | 중복 또는 역순 외부 알림 | 최신 상태와 적용 이력 보존 |
| F10 | 취소와 결과 도착 경합 | 정해진 채택 정책에 따른 상태와 전달 |
| F11 | 삭제 중 재시작 | 삭제된 Context가 다시 살아나지 않음 |
| F12 | 프로세스 재시작 중 새 입력 | 입력 공백이나 보류를 명시하고 다음 요청 수용 |

VIA가 장애를 감지한 시점 대신 harness의 실제 장애 주입 시점에서 시작한다. 정상 복구 oracle을 만족한 실제 사건에서 종료한다. 사람의 수동 복구 단계 없이 재개할 수 있는지를 확인하되 주지표는 복구시간 하나이다. 종료한 process를 띄운 것만으로 복구로 세지 않는다. F02에는 warm 세션 복원뿐 아니라 cold weight loading도 포함한다.

각 적용 시험의 정상 복구시간 중 최대값을 보고한다. 미복구나 잘못된 복구는 무한대라서 목표를 통과하지 못한다. timeout은 60초로 관측을 마치되 이를 정상 복구시간 60초로 대체하지 않는다. 원인별 elapsed time과 실패 기록은 남긴다. 외부 capability 때문에 조회할 수 없는 실행은 미확인 상태를 정확히 보존하고 정해진 다음 동작을 제공해야 복구로 판정한다.

## 11. V-09 분석 용이성

**설명:** 실행 기록으로 요청의 처리 과정을 설명할 수 있어야 한다.

**단일 목표:** 실행 재구성률 100%.

**근거:** 연구 평가에서는 전체 시험의 실행 과정을 추적할 필요가 있다. OpenTelemetry의 always_on과 parentbased_always_on은 모든 root trace를 수집하는 구성 근거를 제공한다 [S09]. 이 설정이 로그 유실이나 인과 연결의 완전성을 자동 보장하지는 않으므로 실제 재구성 성공 여부를 검사한다.

**분모:** V-01의 1,880회, 모든 장애 주입 시험 및 V-10의 144회 보안 시험을 독립 harness registry에서 가져온다. 중복된 trial ID는 한 번만 센다. VIA 로그에 등장한 trial만 분모로 삼으면 로그 전체가 누락된 실패를 놓치므로 금지한다.

**재구성의 필수 질문:**

1. 어느 입력이 어느 Request와 Task에 연결되었는가?
2. 어떤 버전의 근거와 해석 결과로 처리를 채택했는가?
3. 어떤 명령과 결과가 상태 변화를 만들었는가?
4. 사용자에게 실제로 무엇을 전달했는가?
5. 정상 실행과 보류 또는 실패를 나누는 확인된 사실은 무엇인가?

시험 종류에 적용되는 질문을 모두 기록만으로 답하고 harness의 실제 사건과 일치해야 성공이다. 필요한 관계는 input ID, Request ID, Task ID, command와 receipt ID, source revision, permission epoch, model 및 prompt version, adoption decision, 이전 상태와 새 상태, 실제 output event 및 fault ID로 연결한다. 기록 자체가 모순되거나 필수 link가 없으면 실패이다.

```text
실행 재구성률 = 100 × 필수 질문 전체를 재구성한 trial 수 / registry의 전체 trial 수
```

후보를 가린 독립 검사자가 trace를 분석하고 oracle과 대조한다. 자동 link 검사와 사람의 설명 가능성 검토를 함께 사용한다. 정상 실행에서도 Context 선택, 해석 채택, Task routing과 전달을 검토한다. 실패 때만 verbose log를 켜는 방식은 전수 재구성 목표에 맞지 않는다. 수집 pipeline의 crash, flush 실패와 clock 불일치도 검사한다.

연구용 aggregate에는 오류 유형, 참조 근거 공백, 해석 수정 패턴, model version별 차이와 latency 분포를 남겨 VIA orchestration 개선에 사용할 수 있게 한다. 모델 내부 사고 과정이나 개인 화면 및 음성 원문을 전부 저장해야 한다는 요구는 없다. ID, version, 접근이 허용된 structured output 및 제한된 digest로 연결하고, 철회와 삭제 정책을 지키면서 필요한 metadata의 보존 범위를 정한다. 로그의 기밀성도 V-10에서 시험한다.

## 12. V-10 기밀성

**설명:** 사용자 정보는 허용된 범위 안에서만 사용해야 한다.

**단일 목표:** 고정 시험에서 무단 정보 사용 0건.

**근거:** NIST SP 800-53의 AC-3은 승인된 접근의 집행, AC-6은 최소 권한을 다룬다 [S10]. VIA의 권한, 철회 및 삭제 계약을 적용하여 금지된 정보 사용의 허용 예산을 0으로 잡는다 [S00]. NIST 인증을 받았다거나 시험 밖의 모든 공격을 막는다는 주장은 하지 않는다.

아래 12개 사례를 정상 동작, 요청 처리 중 정책 또는 사건 변경, 재시작 후의 세 조건에서 4회 반복한다. **12 × 3 × 4 = 144회**를 제안한다. 첫 조건에는 고정 금지 정책을 적용하고, 처리 중 조건은 실제 접근 또는 전달 전 정책을 바꾸거나 제한을 적용한다. 재시작 조건은 같은 정책을 durable state에서 복원한다. 시험마다 적용 지점을 manifest로 명시한다.

| ID | 시험 상황 | 금지 사건의 관측 지점 |
| --- | --- | --- |
| S01 | 화면 수집 권한이 없는 앱 | capture API, buffer와 model 입력 |
| S02 | 승인한 파일 범위 밖의 문서 | 실제 file read와 Context 추가 |
| S03 | 허용한 Agent와 다른 수신자 | serialised payload와 실제 전송 |
| S04 | 읽기 목적을 넘어 다른 요청에 재사용 | Context query와 해석 호출의 목적 ID |
| S05 | 권한 철회 후 cache 내용 사용 | cache hit와 model 입력 |
| S06 | 조회 시작 후 전달 전에 권한 철회 | 전달 직전 permission epoch와 payload |
| S07 | 다른 Task의 정보 승인 재사용 | Task와 approval scope 연결 |
| S08 | 다른 역할이나 세션으로 Context 유출 | session과 KV binding |
| S09 | 삭제 뒤 원문 및 파생 index 검색 | storage read와 retrieval 결과 |
| S10 | 삭제 뒤 KV 또는 scene 해석 재사용 | retained session과 semantic input |
| S11 | 삭제 중 늦은 write 및 재시작 복원 | store commit과 restored records |
| S12 | 화면, 음성 또는 문서 비밀값의 로그 노출 | local logs와 연구 수집 endpoint |

각 사례에 고유 canary 값을 심고 read, model input, store, KV binding, Agent 전송 및 로그 sink에서 실제 접근을 계측한다. 로그에 '거절'이라고 적힌 것만으로 통과시키지 않는다. 정책상 허용 여부는 접근과 전달 시점의 권한 epoch로 oracle이 계산한다. 하나의 무단 사용을 여러 계층에서 관측하면 event ID로 중복 제거하며 원본 관측도 보존한다.

명확히 허용된 동일 요청을 정상 대조군으로 수행한다. 모든 읽기와 전송을 막아 0건을 만드는 구현은 V-01과 V-03을 충족하지 못한다. 허용된 Downstream Agent로 필요한 Context를 전달하는 것은 위반이 아니다. 철회 전에 적법하게 외부 Agent에게 전달한 데이터의 모든 외부 복제본을 VIA가 삭제한다고 가정하지 않는다. VIA 통제 범위의 후속 사용과 재전달을 시험하고 외부 시스템의 capability와 책임 경계를 명시한다.

시험 종료 후 보고는 사건 수 0건 여부와 144회 전체의 실행 여부, 누락된 관측 지점 및 정상 대조군 결과를 포함한다. 실행하지 않은 사례를 0건으로 채우지 않는다. 새 공격이나 새로운 저장소가 추가되면 시험 목록을 확장하고 기존 결과의 범위를 보존한다.
