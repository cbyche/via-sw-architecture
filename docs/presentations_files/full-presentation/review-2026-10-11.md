## 1. 핵심 판단

VIA와 업무 수행 Agent의 책임 구분, 부분 정정 시 유지할 조건, 동일 입력에서의 실제 A/B 구조 차이는 전달된다. 특히 2쪽과 19쪽의 책임 설명, 3쪽과 4쪽의 정정 예시는 유지할 가치가 크다.

가장 먼저 보완할 것은 **소개 순서, 여섯 QA가 필요한 이유, 공통 기능에서 구조 선택으로 넘어가는 연결**이다. 현재는 전체 구조를 처음 보기 전에 기능과 QA 평가 설명이 길게 이어진다. DP 배경은 사용자 요구를 잘 보여주지만 그 요구 때문에 왜 두 구조를 고민해야 하는지는 노트에서 더 분명하다. 비교 화면은 상세 계약과 평가표까지 함께 담아 발표 중 핵심 구조를 따라가기 어렵다.

권장 흐름은 다음과 같다.

**관련 동향과 PC의 기회 → 사용 중 생기는 문제와 설계 필요성 → VIA의 역할, 대표 시나리오와 간단한 전체 구조 → 필요한 기능과 제약 → 고정된 여섯 QA → 네 설계 질문 지도 → 각 DP의 문제, 선택 질문, A/B 구조와 조건부 손익**

현재 DP 설명 순서인 41 → 44 → 45 → 42는 유지할 수 있다. 평가 정의를 줄이는 것이 아니라 본문 설명과 상세 근거의 읽는 순서를 구분한다.

### 비교 화면의 밀도 근거

통합본은 20×11.25in이다. PPTX의 명시된 native text run 크기를 확인하면 22쪽에 7.5pt 400자와 8.25pt 401자, 31쪽에 7.5~9pt 1,245자가 들어 있다. 이는 상속된 글꼴이나 그림 내부 글씨를 포함하지 않은 수치다. 실제 1920×1080 화면에서도 작은 데이터 예시, 순서도 조건과 하단 QA 표를 동시에 읽어야 한다.

화면에 내용이 잘렸다는 판정이 아니라 **발표 중 핵심 구조의 읽기 순서와 가독성이 부족하다는 판정**이다. 단순히 글씨를 키우는 것으로 해결하기보다 본문 MAIN과 상세 계약의 역할을 나눈다.

26쪽의 지역 계산은 A 0.060초/B 0.050초이고 전체 응답시간 차이 기준은 0.10초다. 이는 서로 범위가 다른 값이므로 지역 0.010초 차이로 전체 효과나 DP의 중요성을 입증할 수 없다. 32쪽의 확정/접수 지역 계산과 추가 메모리 예산도 독립 계약을 선택할 이유를 대신하지 못한다. 현재 계약이 설명하는 조건부 이익과 반대 비용, 아직 확인하지 못한 부분을 함께 보여준다.

이 표는 기존 기능/QA 간 발표 설명의 연결이다. 새 PRIMARY 분류, 효과 크기, 승자 또는 필수 기능을 정하지 않는다. 기존 5쪽의 관련 DP는 **직접 설계 영향**이고, 공통 제약의 준수 여부는 네 비교에서 따로 유지한다.

### 두 응답시간을 구별하는 화면

대표 보고서 요청의 한 시간축에서 첫 알맞은 반응을 표시하고, 해석/인계/결과 수신/실제 전달까지의 VIA 구간을 별도로 표시하면 QA-02와 QA-03을 직관적으로 구별할 수 있다. 외부 Agent 업무, 사용자 대기와 VIA 대기를 같은 색으로 묶지 않는다. 설명용 시간축은 측정된 시간 비율처럼 보이지 않게 한다. 기존 목표와 귀속 DAG 계산은 그대로 유지한다.

## 4. DP별 제목, 배경과 설계 비교

아래 제목은 명명 규칙을 만족시키는 **발표 제목 후보**다. 기능, 모델/코드 판단 권한, 지원 범위와 품질 정의는 바꾸지 않는다. 부제에는 현재 구조 대비를 유지한다.

| DP | 제목 후보 | 배경의 마지막 질문 | 본문 그림에 반드시 남길 대비 | 함께 보여줄 비용과 한계 |
| --- | --- | --- | --- | --- |
| 41 | **요청 처리 정확성을 위한 맥락 기반 요청 해석 설계** | ‘조회 결과에 따라 다음 조회와 전체 의미 완성을 모델이 결정할까, 코드가 표현된 요청 항목의 해결 상태로 진행할까?’ | A 모델 판단 반복과 최종 의미 제안. B 모델 RequestFrame, 코드 소유의 항목 해결/전체 결합, 필요한 항목의 조건부 모델 해석. 같은 입력과 공통 채택 경계. | A의 구조화 출력과 부분 갱신을 보존한다. B는 유한 표현의 지원 범위, 표현 밖 관계와 추가 호출/확인 비용을 가진다. B를 항상 한 번의 모델 호출로 그리지 않는다. |
| 44 | **상호작용 응답시간을 위한 지속 대화 실행 설계** | ‘완료마다 중앙이 후속 실행을 지시할까, 연결된 단계가 입력과 조건을 확인하며 실행될까?’ | A 중앙의 완료 회수와 다음 실행 결정. B 입력/알림 단계와 상태, 게시 Join의 조건 활성화. 동일한 늦은 응답 후보의 무효화. | A도 비동기, 우선순위와 병렬 실행이 가능하다. B의 Stage/Join/수용량 상태와 대기는 비용이다. 즉시 음성 중단과 업무 취소를 구별한다. |
| 45 | **VIA 요청 처리시간과 모델 사용 비용을 위한 과거 맥락 제공 설계** | ‘현재 요청에 맞춰 원본을 조합할까, 여러 요청이 읽을 공통 과거 관계를 생산하고 관리할까?’ | A 요청별 조합 책임과 유효 cache/부분 갱신. B 별도 공통 관계 생산, 저장소/coverage 유지와 현재 Reader의 조회/원본 확인. | 첫 사용, 준비된 반복 사용, 정정 직후와 미지원 관계를 구별한다. B의 초기/미사용 생산과 철회, A의 cache miss 비용을 모두 남긴다. 정확성도 같은 QA로 비교하며 시간/비용 설명에서 제외하지 않는다. |
| 42 | **요청 처리 정확성과 변경 용이성을 위한 대화와 업무 상태 관리 설계** | ‘관련 대화/업무 상태를 함께 확정할까, 독립 상태 권위의 접수와 확인 응답으로 맞출까?’ | A 강한 모듈형 통합 Core와 공동 local commit. B 독립 대화/Task 서비스의 상태 권위, 각 local commit과 접수 receipt 반영. 외부 Agent 확인은 별개. | A도 논리 수명 분리와 변경 국소화가 가능하다. B의 독립 운영은 조건부이며 인계/재확인과 추가 process/상태 비용이 있다. 분리 자체의 정확성/변경 우위를 주장하지 않는다. |

45의 제목에서 처리시간과 비용을 함께 쓰는 이유는 같은 과거 정보를 요청 시 조합할지 공통 생산할지에 따라 첫 사용/반복 사용의 기다림과 미사용 생산의 청구가 함께 달라지기 때문이다. 42의 정확성은 의미 모델의 능력보다 관계, 내부 접수와 실제 외부 확인을 잘못 반영하지 않는 경로를 뜻한다. 어떤 제목도 상대적 품질 결과를 선포하지 않는다.

42의 주요 품질속성 명명은 특히 유보다. 현재 화면만으로는 강한 A의 모듈화/공동 확정 대비 독립 서비스 계약이 어떤 중요한 변경/상태 정확성 조건에서 의미 있는 차이를 만드는지 충분하지 않다. 위 제목은 사용자 형식에 맞춘 후보이며, 현재 문서의 해당 조건과 비용을 화면에 연결한 뒤 문안을 정한다. 새 주요 품질이나 B의 이익을 만들어 제목을 정당화하지 않는다. 이는 후보 제외나 새 대안 탐색을 요구하는 판단이 아니다.

### 배경 그림에서 보완할 핵심

- 41: 선택 화면, 기존 보고서 후보와 조건을 유지하고, 조회 결과가 새 조회/해석을 필요하게 만든다는 흐름을 먼저 보여준다. 다음 처리 결정권이 왜 선택 문제인지 연결한다.
- 44: 같은 시점에 들어오는 새 입력, 업무 질문과 늦은 준비 결과는 그대로 사용한다. ‘모두 처리해야 한다’에 더해 유효성 확인과 후속 실행의 결정 책임을 보여준다.
- 45: 서로 다른 과거 기록을 한 요청에 연결하는 현재 그림은 유지한다. 필요할 때 조합하는 비용과 공통 관계를 지속 생산/관리하는 비용을 사용 전/사용 중 시간축으로 대조한다.
- 42: 제목이 Conversation 수명을 말한다면 실제 Conversation 행을 넣어 음성 연결 행과 구분하거나, 배경 제목을 실제 표시하는 수명에 맞춘다. 수명 분리가 A/B 공통임을 먼저 밝히고 상태 owner와 확정 경계 선택으로 이어간다. 장애/업데이트만으로 B의 일반 사용 이익을 주장하지 않는다.

### MAIN과 상세 화면의 역할

MAIN에서 먼저 읽을 정보는 같은 입력, 양쪽의 결정/생산/확정 책임, 상태 소유, 실행 의존성, 같은 결과를 만드는 경로와 대표 비용이다. JSON 필드 전부를 읽지 않아도 이 대비가 그림 자체에서 이해되어야 한다.

현재 상세 그림과 schema, 전체 순서도, 종료/지원 계약, 여섯 QA의 전체 평가표는 같은 통합본의 근거 구역에 보존한다. 공통 조건, A의 강점이나 B의 추가 비용까지 노트로만 밀어내서는 안 된다. 정식 Component/Module 이름을 임의의 별칭으로 바꾸지 않고 설명과 읽기 순서를 조절한다.

## 5. 권장 발표 구성

새 총 페이지 수나 발표 시간은 아직 정하지 않았다. 아래는 설명 순서와 기존 내용의 배치 제안이다. 현재 자료의 일괄 재병합은 하지 않고, 수정 시 통합본에서 작업한다.

| 순서 | 본문에서 할 일 | 기존 내용 활용 |
| --- | --- | --- |
| 1 | 업무 AI와 화면/음성 상호작용의 발전을 보여주고 PC 대화 접점의 가치를 연결 | 1쪽. 사례 나열 뒤 ‘업무 AI가 달라도 대화와 진행을 이어야 한다’는 연결을 분명히 한다. |
| 2 | 정확한 정정, 계속되는 입력과 서로 다른 도착 사건, 기술 변화, 모델/PC 자원 부담을 사용자 문제로 설명 | 3쪽 보완. QA/DP 명칭과 번호는 직접 넣지 않는다. |
| 3 | VIA의 역할과 외부 업무 실행 책임을 한 장으로 소개 | 2쪽, 19쪽 중복을 정리하고 메시지 흐름을 활용한다. |
| 4 | 대표 보고서/메일 시나리오와 필요한 시작 상태를 설명 | 4쪽. 20쪽 겹침 장면은 여기서 일부 활용하거나 설계 질문 도입에 사용한다. |
| 5 | QA/DP 표식 없는 간단한 전체 실행/의존성 구조를 먼저 소개 | 새 소개 그림. 18쪽을 통째로 이동하지 않는다. 로컬/클라우드와 업무 Agent 경계를 보인다. |

| 7 | 여섯 QA의 의미, 목표와 핵심 보호 조건을 소개 | 6~7쪽을 본문 기준으로 사용한다. 두 시간 지표의 차이와 비용/메모리 범위를 명확히 한다. |
| 8 | 같은 입력과 활동에서 비교한다는 평가 원칙을 설명 | 8쪽을 쉬운 공통 평가 원칙으로 압축. 전체 P21 원장과 조건은 근거 구역에서 보존한다. |
| 9 | 요구/QA가 왜 네 설계 질문으로 연결되는지 안내 | 18쪽을 설계 도입 지도에 유지하고 추적 이유를 보강한다. |
| 10 | 41의 배경, 선택 질문, A/B와 조건부 손익 | 21~23쪽. 지원 표현과 전체 의미 완성의 책임을 보인다. |
| 11 | 44의 배경, 선택 질문, A/B와 조건부 손익 | 24~26쪽. 중앙 회수/지시와 단계 조건 활성화의 차이를 보인다. |
| 12 | 45의 배경, 선택 질문, A/B와 조건부 손익 | 27~29쪽. 조합/공통 생산의 수명, 재사용과 미사용 비용을 보인다. |
| 13 | 42의 배경, 선택 질문, A/B와 조건부 손익 | 30~32쪽. 공통 논리 수명에서 소유/확정 경계로 연결한다. |
| 14 | 네 질문이 같은 VIA 경험을 만드는 데 어떻게 관여하는지 마무리 | 새 짧은 연결 화면을 고려한다. 후보/평가 전 상태를 유지한다. |
| 근거 | 사례 전수 대응, 목표/등급 계산, 전체 구조/계약과 평가표 | 9~17쪽과 DP 상세를 보존하고 본문에서 바로 찾을 수 있게 안내한다. |

QA의 보호 조건을 본문에서 전부 설명할 필요는 없지만 대표 목표만으로 통과가 결정된다고 오해시키면 안 된다. 본문에 핵심 보호 조건과 전체 근거 위치를 남기고, 상세 문서/부록의 값과 판정 의미는 유지한다.

### 전환 문장 후보

1. 배경에서 필요성: ‘업무 AI가 일을 할 수 있게 되면, PC의 사용자 접점은 요청을 정확히 연결하고 진행 중에도 대화를 이어가야 합니다.’
2. 필요성에서 소개: ‘VIA는 이 연결을 PC에서 맡고, 실제 조사나 문서 작성은 업무 AI에 위임합니다.’
3. 시나리오에서 요구사항: ‘방금 장면을 지원하려면 입력을 계속 받고, 대상과 조건을 보존하며, 질문과 결과를 해당 업무에 연결해야 합니다.’
4. 요구사항에서 QA: ‘기능을 제공하는 것과 함께, 정확하게 연결하고 제때 반응하며 사용량과 변경 범위를 관리하는 기준이 필요합니다.’
5. QA에서 DP: ‘이 기준에 영향을 주는 네 질문은 요청 해석의 진행, 후속 실행, 과거 맥락 공급, 대화와 업무 상태의 확정입니다.’

## 6. 용어와 사례의 정돈

일반 SW 용어인 비동기 실행, queue, cache, transaction, adapter, API를 일괄 제거하거나 다시 가르칠 필요는 없다. 청중이 처음 알아야 하는 것은 VIA에서 그 용어가 가리키는 책임, 상태와 시점이다.

| 첫 등장 설명 | 유지할 구분 |
| --- | --- |
| Request: 이번 입력에서 VIA가 처리할 개별 요청 | 한 입력의 복합 지시가 여러 요청을 만들 수 있다. 요청 처리 종료와 업무 완료를 구별한다. |
| Task: 여러 요청에 걸쳐 추적하는 사용자의 업무 목표 | 정정/조회 요청이 새로 생겨도 같은 업무를 가리킬 수 있다. |
| Agent 실행: 외부 업무 AI가 실제로 수행하는 실행 | Task와 Agent의 실행 ID/수명을 동일시하지 않는다. |
| Conversation: 이어지는 대화와 기록 | 음성 연결을 끊어도 대화/업무를 삭제하거나 취소하지 않는다. |
| Context: 요청을 이해하는 데 사용하는 화면, 대화와 자료 정보 | 가공한 관계와 원본 근거를 구별한다. |
| VAD: 사용자의 발화 시작/종료를 감지하는 로컬 기능 | 음성 인식/의미 판단과 다르다. 즉시 재생 중단은 원격 취소 확인을 기다리지 않는다. |
| 접수 receipt/실제 전달 기록 | 내부 서비스 접수, 외부 Agent 접수와 사용자에게 실제 표시/재생된 사실은 서로 다르다. |

3쪽의 ‘VIA 내부의 Agent 기술도 발전’은 ‘VIA의 요청 이해, 기억과 상호작용 기술도 발전’처럼 실제 기능으로 표현한다. 외부 업무 Agent의 발전과 VIA 내부 기술의 변화를 구별하면 2쪽 책임 경계를 유지할 수 있다.

20쪽에는 ‘시작 상태: 공급업체 견적 업무가 이미 진행 중’이라는 선행 상태, 4쪽에는 보고서 형식을 이전에 수정한 기록이 있다는 선행 상태를 짧게 알린다. 22/25/28/31쪽의 Input1/Task1/Question1은 해당 장면의 식별자이며 발표 전체에서 동일 객체라는 뜻으로 읽히지 않게 한다.

## 7. 수정 완료를 확인할 기준

1. 도메인을 처음 보는 검토자가 초반 소개만 보고 VIA의 입력, 직접 응답/업무 위임 경계, 로컬/클라우드 의존성과 결과 경로를 설명할 수 있다.
2. 필요성에는 QA/DP ID 없이 여섯 QA의 동기가 있고, QA 구간에서 새 관심사가 갑자기 등장하지 않는다.
3. 기능과 제약의 기존 직접 DP 매핑은 유지되고, 설계 구간에는 기능에서 품질 비용으로 이어지는 이유가 보인다.
4. QA-02와 QA-03의 시작/끝 및 외부 업무 제외 범위를 구별할 수 있다. QA 원문, 목표, 보호 조건, 모집단과 등급은 동일하다.
5. 네 DP 제목이 지정한 형식을 따르고, 주요 품질속성의 명명에 직접 영향 근거가 있다. 근거가 부족한 DP에는 후보와 유보 이유를 명시한다. 배경 마지막 질문을 다음 A/B 그림에서 바로 찾을 수 있다.
6. 노트와 JSON 필드를 읽지 않고도 양쪽의 판단/생산/확정 책임, 상태 owner, 실행 경로와 대표 비용을 설명할 수 있다. 상세 계약은 근거 구역에 보존되어 있다.
7. A의 비동기/부분 갱신/cache/모듈화와 B의 추가 상태/호출/생산/인계 비용을 양쪽 화면에서 공정하게 확인할 수 있다.
8. 사례 전환에는 필요한 선행 상태와 이유가 있으며, 음성 연결, 대화, 요청, 업무와 외부 실행을 혼동하지 않는다.
9. 목표/가정/지역 계산/전체 후보 평가와 실측 결과를 구별한다. 평가 전을 0점이나 실패로 표시하지 않는다.

검토에는 동일 해시의 PNG, native 텍스트와 선택된 발표자 노트를 사용했다. 실제 PowerPoint에서 GIF를 재생하며 진행한 리허설, 사람 심사위원의 이해도 실험, 모델 실행과 품질 측정은 하지 않았다. 이번 요청에서는 PPTX와 QA 정의를 수정하지 않았고, 리뷰 기록과 읽기 안내를 추가했다.

활성 Markdown 162개의 링크 검사, 활성 용어 검사, 리뷰/안내의 로컬 링크 검사와 diff 공백 검사를 통과했다. PPTX SHA-256도 검토 시작 값과 같다. 리뷰만 진행한 작업이므로 commit/push는 하지 않았다.
