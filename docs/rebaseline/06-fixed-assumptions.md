## 6.1 목적과 읽는 방법

**06은 같은 시험에서 무엇을 동일하게 놓을지, 07은 무엇이 바뀌었을 때도 대응할지를 정한다.** 같은 모델을 모든 시험에서 영원히 쓰겠다는 의미가 아니다.

먼저 6.2의 짝 비교표와 6.3의 제안값을 검토한다. 모델 비교는 6.5, Agent와 재시작은 6.7, 지연 측정 범위는 6.6을 집중해서 읽는다. 각 항목의 FA ID는 이후 평가 조건과 연결하는 식별자이며 새로운 QA/DP 번호가 아니다.

이 문서는 다음을 구분한다.

| 구분 | 의미 | 관리 위치 |
| --- | --- | --- |
| 제품 요구 | 복합 요청, 여러 업무, 장기 기억, 재시작 후 재연결처럼 반드시 지원할 행동 | 01~05 — 유지 |
| 공통 조건 | 한 비교에서 같은 사용자 입력·원천 자료·외부 환경을 사용 | 06 |
| 의도된 변화 | 모델·Agent·연동 계약 등이 바뀌는 변경 시나리오 | 07 |
| 내부 설계 선택 | 직접 처리/위임, Component 배치, 병렬화, 상태 소유권 | 03·04의 설계 질문 → 12 |

**제품에 필요한 기능이 모두 주요 DP가 되는 것은 아니다.** 반대로 필수 기능이라는 이유로 시험기가 대신 구현해 주어서도 안 된다. 기존 ASR 후보·목표·점수표를 이 문서에서 다시 확정하지 않는다.

### 동일한 시험 장비와 미정인 제품 장비의 구분

현재는 **설계 분석과 작은 시제품 검증을 기본 증거 방식**으로 사용한다. 실제 측정을 할 때는 비교 묶음마다 한 장비의 CPU/GPU/RAM, OS 빌드, 전원 모드, Model Runtime 버전, 다른 부하를 기록하고 동일하게 사용한다. 제품 출시 장비를 임의로 정하지 않는다.

장비가 다른 공개 벤치마크를 사용할 때는 그 장비와 조건을 함께 표기하고, 해당 수치로 계산한 결과를 **추정값**으로 표시한다. 실제 장비·출처 없이 tokens/s, 메모리 사용량, 절대 지연을 만들어 넣지 않는다. 근거가 없는 항목은 미측정으로 남기며 0이나 측정값으로 대체하지 않는다.

이는 제품 범위를 미루는 것이 아니라 **설계 결과와 실측 결과의 증거 수준을 구분하는 규칙**이다. 특정 제품 장비의 배터리·전력·최대 처리량 보장은 이번 기준선에서 선언하지 않는다.

## 6.4 동일하게 재생할 데이터와 시험기 경계

### FA-09. 같은 원천 정보, 정답은 별도

각 시험은 다음 세 부분으로 분리한다.

| 부분 | 들어가는 것 | 후보에게 제공하는 방법 |
| --- | --- | --- |
| 원천 입력 | 음성, Text, 실제 선택·포인터·창 변화, 원천 자료, 초기 대화·Task·기억, 외부 상태 변화 | 실제로 관측·조회할 수 있는 경로와 시점으로 제공 |
| 외부 동작 | Model/Source/Agent의 응답·지연·지원 기능·실패 조건 | 모든 후보에 같은 조건의 시험용 상대를 제공 |
| 평가 정답 | 의도한 대상, 관계, 허용·금지 결과, 성공/보류 조건 | **평가기에만 보관** |

사용자가 지칭한 당시의 시각과 이벤트가 후보에게 관측 가능한 시각은 따로 기록한다. 입력 지연·수정·순서 역전은 같은 패턴으로 적용한다. 시험기는 후보가 놓친 이력을 나중에 대신 주지 않는다.

Task Association을 평가하면서 정답 Task ID를 입력에 몰래 넣지 않는다. 명시적으로 Task를 선택한 UC에서만 그 선택을 입력으로 제공한다. 모델을 재생할 때도 후보가 주지 않은 Context를 모델이 알아낸 것처럼 답을 고정하지 않는다.

원천 자료는 같게 하지만 후보가 저장하는 이력, 조회 횟수, 전달하는 Context, 캐시, 보관 위치까지 동일하게 강제하지 않는다. 그것들이 설계 비교 대상이기 때문이다.

### 자료와 초기 상태

메일·웹·일정·파일은 시험용 고정 자료를 사용하며 실제 발송·결제·사용자 파일 변경은 하지 않는다. 온라인 서비스 연결 시험은 보조 통합 검증으로 분리한다. URL·자료 내용·접근 권한·갱신 시각이 바뀌는 실제 인터넷 결과를 후보별로 따로 가져와 공식 비교하지 않는다.

시험 시작 시 같은 의미의 대화·Task·Memory를 제공하되 후보의 실제 입력/저장 경로로 적재한다. 이후 상태 변화는 후보가 관리한다. 특히 재시작 직후에는 초기화 도구가 잃어버린 대화나 Task ID를 다시 채워주지 않는다.

### UC 커버리지

05의 UC 18개와 명시된 필수 하위 유형을 모두 Test Case에 연결한다. 정상·경계·실패 유형을 구분하고 결과도 구분한다. 좋은 결과가 나온 유형만 골라 전체 성능으로 발표하지 않는다.

복합 Request의 정답은 특정한 분해 트리 하나가 아니라 **사용자가 요청한 목표·대상·순서·조건·의존 관계**이다. 동등하게 요구를 만족하는 표현은 허용한다. 여러 대상이 가능한 모호한 발화는 임의의 대상 하나를 정답으로 만들어 채점하지 않는다.

## 6.5 모델 비교 규칙

### FA-10. 같은 모델을 고정할 때와 달라도 되는 때

| 비교 목적 | 동일하게 두는 것 | 달라도 되는 것 | 결과 해석 |
| --- | --- | --- | --- |
| 같은 판단 책임의 구조 비교 | 같은 기준 모델·버전·생성 설정, 같은 원천 입력, 같은 기능 요구 | 구조 때문에 달라진 Context 표현·입력 길이·호출 수·실행 순서 | 구조 효과를 우선 관찰 |
| 구조가 모델의 책임을 바꾸는 비교 | 같은 사용자 목표·완료 조건·허용 기능, 역할 적합성 확인 규칙 | 담당 책임에 필요한 모델, 역할별 지시문과 호출 구성 | **구조와 그에 필요한 모델 구성의 결합 결과**로 표시 |
| 07의 모델 교체 평가 | 같은 사용자 기능과 회귀 시험 | 모델 제공자·크기·API·배치 등 해당 변경 항목 | 변경량과 기존 기능 유지 여부를 평가 |

같은 책임이면 먼저 같은 모델을 사용하는 것이 기본이다. 그러나 S2S에 판단을 합치는 구조와 별도 의미 판단 모델을 사용하는 구조에 동일 모델·동일 프롬프트를 억지로 강제하지 않는다. 반대로 이유 없이 한쪽만 더 좋은 모델로 바꾸지 않는다.

**‘작은 모델은 반드시 단순 업무만 가능하다’ 또는 ‘큰 모델이어야 범용 업무가 가능하다’는 식으로 크기만으로 역할 적합성을 선언하지 않는다.** 01~05의 요구 동작을 다룰 수 있다는 근거와 지원 인터페이스를 제시한다. 같은 책임의 프롬프트 수정 기회와 시험 데이터 접근도 동등하게 제공하며 최종 시험 전에 버전을 고정한다.

### 모델 대신 응답을 재생할 때

정해진 모델 출력의 재생은 요청 연결·상태·취소·기록 검증에 유용하다. 하지만 그것만으로 실제 의미 이해 정확도를 측정했다고 하지 않는다.

- 실제 모델로 같은 역할을 비교한 결과
- 모델 응답을 고정하여 구조만 검증한 결과
- 모델 속도 자료로 계산한 지연 추정

이 세 결과를 한 종류의 실측값처럼 섞지 않는다. 후보의 추가 모델 호출을 재생하더라도 그 호출 지연을 자동으로 0으로 처리하지 않는다.

S2S 사용은 고정이나, 단어별 시각·수정된 전사·취소 이벤트를 모든 S2S가 제공한다고 가정하지 않는다. 모델/보조 기능이 실제로 주는 정보만 후보가 사용한다. 보조 ASR(음성 인식) 등이 필요하면 그 연동·호출·지연도 후보의 일부이다.

### 속도 추정에 필요한 기록

모델·버전, 역할, 실행 위치/장비, 입력 길이와 출력 길이, 최초 응답 지연, 후속 생성 속도, 초기화·캐시 조건, 자료 출처와 측정 조건을 기록한다. 속도는 입력 길이·캐시·동시 실행 조건에 맞는 값을 사용한다.

텍스트 모델의 token 기반 계산식을 S2S 오디오 처리에 그대로 적용하지 않는다. S2S에는 오디오 입력 길이, 스트리밍/최초 음성 지연 등의 해당 근거를 사용한다. 병렬 작업은 전부 직렬 합산하지 않는다.

## 6.6 통신·지연과 평가 범위

### FA-11. 같은 통신 조건

같은 배치의 비교에서는 같은 통신 조건을 적용한다. 배치 자체가 달라지는 비교에서는 달라진 통신 경로를 설계 결과로 포함한다.

설계 민감도 분석에는 다음 **합성 시험 조건**을 사용한다. 실측 네트워크나 제품 목표를 뜻하지 않는다.

| 조건 | 외부 통신에 추가하는 왕복 지연 | 사용 목적 |
| --- | --- | --- |
| 통신 영향 분리 | 0 ms | 왕복 지연을 제거한 논리 경로 비교 |
| 기본 원격 조건 | 50 ms | 원격 의존성을 가진 후보의 공통 시험점 |
| 지연 증가 조건 | 150 ms | 왕복 수에 대한 결과 민감도 확인 |

위 숫자는 전송되는 자료의 크기·직렬화·Model/Source 처리 시간을 포함하지 않는다. 큰 화면이나 문서의 전송 비용을 평가한다면 같은 대역폭 조건 또는 근거 있는 전송 측정도 포함한다. 그 근거가 없는 계산은 **왕복 지연만 반영한 추정**으로 제한한다. Local IPC도 공짜로 간주하지 않는다.

단절·재연결·지연 도착은 UC-15·18의 고정 이벤트로 따로 시험한다. 평상시 지연 결과에 임의의 장애 빈도를 섞지 않는다. 이 환경 변화는 코드 변경을 뜻하지 않으므로 07 변경 개수로 세지 않는다.

### FA-12. VIA가 책임지는 시간과 Agent의 업무 시간

위임 요청은 **사용자 입력 종료부터 Agent 실행 인계까지 + Agent 결과 준비 이후 사용자 응답 전달까지**의 VIA 책임 구간을 구분하여 기록한다. Agent 내부에서 조사·생성·앱 조작하는 시간은 별도이다. Agent가 준비한 결과의 수신·변환·Task 연결·음성/Text 전달은 VIA 구간에 포함한다.

VIA가 직접 사용한 S2S·의미 판단 모델·Context 조회는 VIA 처리 경로의 의존성이므로, 물리적으로 Cloud에 있더라도 전부 Agent 업무 시간으로 빼지 않는다. 응답 측정 종료는 음성/화면에서 사용자에게 유효한 내용이 전달된 시점이며, 접수 확인 문구로 결과 전달을 대신하지 않는다.

병렬 Agent 실행과 VIA 처리가 겹친 경우 전체 시간에서 Agent 시간 합계를 단순히 빼지 않는다. 각각의 경계와 대기 관계를 기록한다. 사용자에게 질문한 뒤 답변을 기다리는 시간은 따로 표시한다. Voice/Text와 직접 응답/위임 응답의 시작·종료 지점은 최종 지표 정의에서 한 번 정하고 모든 DP에 동일하게 적용한다.

### 반드시 피해야 할 잘못된 비교

“PDF 설명”을 후보 A가 VIA 안에서 수행하고 후보 B가 Agent로 넘긴다고 하자. B에서 그 설명 시간을 제외했다는 이유만으로 **B가 사용자에게 더 빨리 답했다**고 말할 수 없다.

따라서:

- 같은 업무 배치의 후보는 같은 VIA 측정 구간으로 비교한다.
- 업무 배치가 달라지면 VIA 내부 비용과 제외된 업무를 함께 표시한다. VIA overhead와 전체 응답 속도를 구분한다.
- 경로 선택까지 비교하려면 같은 정답·기능 조건과 공통 외부 업무 시간 가정을 사용한 별도 비교를 제시한다. 이를 기존 VIA-only 지표와 혼합하지 않는다.
- 외부 업무 시간을 바꾸어 결론이 역전되면 그 범위를 공개한다.

이 규칙은 기존 지연 지표를 바꾸려는 것이 아니라, **업무를 측정 경계 밖으로 옮긴 효과를 속도 개선으로 오해하지 않도록 하는 제한**이다.

## 6.7 Agent 기능과 재시작 조건

### FA-13. 시험용 Agent는 VIA 대신 일을 하지 않는다

Agent 내부 업무는 실행하지 않고, 요청에 따라 정해진 결과·이벤트를 반환하는 시험용 Agent를 사용한다. 이것은 실제 Agent의 지능을 검증하는 도구가 아니다.

기본 시험에는 서로 다른 업무 기능을 가진 복수 Agent와 같은 Agent의 복수 실행을 제공한다. 단순히 Agent 이름만 바꾸지 않고 입력 schema·실행 식별·상태/결과 제공 방법을 명시한다. 공통 변환 계층을 시험기에 몰래 구현하여 특정 adapter 구조를 모든 후보에게 무료로 제공하지 않는다.

| 외부 기능 조건 | 시험용 상대가 제공할 사실 | 후보가 해야 할 일 |
| --- | --- | --- |
| 정상 장기 업무 | 안정된 실행 식별, 접수·상태·결과, 후속 요청 및 취소의 확인 결과 | 원래 VIA Task와 연결하여 사용자를 안내 |
| 기능이 제한된 Agent | 상태 조회만 가능하거나 후속 지시·취소·재개 일부 미지원 | 없는 기능을 있다고 가정하지 않고 지원 범위대로 처리 |
| 문제 발생 Agent | 실패·부분 결과·중복/지연 이벤트·최종 상태 미확인 | 올바른 Task에 연결하고 확인된 사실만 보고 |

같은 시험에서는 모든 후보에게 같은 기능 조건을 준다. 항상 성공하는 Agent만으로 UC-12·18을 통과시키지 않는다. 내부 planning·Tool scheduling을 VIA가 구현하도록 요구하지도 않는다.

### FA-14. 재시작 후 재연결을 검증할 세 조건

| 조건 | 외부 상태 | 성공적인 VIA 동작 |
| --- | --- | --- |
| 복구 가능한 기본 조건 | VIA 프로세스는 종료됐지만 저장 장치는 손상되지 않고 Agent 실행은 살아 있으며 조회/재연결 가능 | 대화·Task·실행 관계를 복원하고 같은 업무를 이어감. 단순히 “다시 요청하세요”로 끝내면 통과 아님 |
| 외부 실행이 이미 종료 | Agent가 최종 결과와 실행 식별을 조회할 수 있게 제공 | 기존 Task에 결과 연결. 새로운 중복 업무를 시작하지 않음 |
| 확인 근거 없음 | Agent도 상태를 잃었거나 조회/재개를 지원하지 않음 | 확인 불가를 설명하고 중복 Action 없이 사용자에게 다음 판단 요청 |

시험에서는 후보 프로세스의 메모리를 실제로 잃게 하거나 그와 동등하게 제거한다. 복구는 **후보가 남긴 상태와 외부가 실제 제공하는 API**만 사용한다. 재시작 횟수만 세거나 같은 메모리를 유지한 채 잠깐 멈추는 것은 이 검증이 아니다.

기본 장애 범위는 VIA 프로세스 종료, Voice/Model/Agent 연결 단절이다. PC 저장 장치 물리 손상, 계정 탈취, Agent 내부 checkpoint 완전 복원까지 이 조건에서 보장하지 않는다. 정상적으로 복구 가능한 기본 조건의 재연결은 필수이며, 마지막 조건의 정직한 안내로 대체할 수 없다.

대화 기록·완료 업무·User Memory는 시험에 포함된 시간 범위 동안 유지하고, 명시적 삭제 결과를 재시작 후에도 보존해야 한다. 이를 근거로 제품의 평생 보관이나 무제한 저장을 주장하지 않는다.

## 6.8 권한·정확성·재현성 공통 규칙

### FA-15. 조건과 결과의 공정성

권한 있음, 최초 동의 필요, 거부/철회, Source 없음/접근 불가를 구분한 같은 Policy 상태를 사용한다. 일반 대화에 승인 단계를 강제로 추가하지 않는다. 과거 Conversation의 동의 문장을 현재 권한의 대체물로 사용하지 않는다.

시험 원본, 초기 상태, 평가 정답, 후보 설정을 평가 전에 버전으로 고정한다. 캐시가 비어 있는 경우와 준비된 경우를 구분하며, 한 후보만 미리 준비하지 않는다. 기록·검증·보안 기능을 한쪽에서만 꺼서 속도를 비교하지 않는다.

정확도 평가에는 실제 Model 결과인지, 고정 응답 재생인지 표시한다. 기능이 틀린 결과를 빠르다는 이유로 정상 성공군에 포함하지 않고, 실패·보류도 누락하지 않는다. 반복 횟수와 집계 방식은 08·11에서 모든 후보에 공통으로 정하며, 불확실성이 큰 값이나 미측정값을 0~5점의 정밀한 결론으로 바꾸지 않는다.

## 6.9 설계단계 변경량 평가 규칙

### FA-16. 구현 전에도 비교하되, 그림을 그리는 방식으로 점수를 바꾸지 않는다

07의 변경은 각 후보의 **같은 깊이로 작성된 설계도와 요소 목록**에 적용한다. 코드 전체가 완성될 필요는 없지만, 해당 변경의 영향이 드러날 정도의 책임·계약·상태·배치 정보는 있어야 한다. “Adapter 하나 고치면 된다”는 주장만으로 숫자를 쓰지 않는다.

요소 유형은 Component/책임 단위, Interface/계약, State/Data Schema, Runtime/배치 단위로 구분한다. 구체적인 전체 목록과 집계 단위는 10에서 한 번 확정한다. 같은 역할이 한 crate에 묶였다는 이유로 항상 1개가 되는 것은 아니며, 박스를 쪼개거나 합쳐 점수를 유리하게 만들지 않는다.

각 변경마다 **기존 요소 수정 / 새 요소 추가 / 제거**의 ID 집합과 이유를 남긴다. 동일 요소를 여러 파일에서 고쳐도 같은 변경 안에서는 중복 세지 않는다. 반대로 새 adapter 작성·연결 비용을 “기존 수정이 아님”이라는 이유로 숨기지 않는다. 서로 다른 유형을 임의 가중치로 M/M에 환산하지 않는다.

단순 모델명·endpoint·자격증명 값 교체만으로 기능을 유지하면 설계 변경은 0일 수 있다. 인증 방식이나 실행 배치 계약이 달라지면 그 영향을 센다. 설정값 변경, 배포 작업, 회귀 검증은 별도 근거로 기록한다. 무엇을 최종 대표 숫자로 집계할지는 08·10에서 공통으로 정하며 06·07에서 후보별 임의 점수를 만들지 않는다.

## 6.10 01~05 재검토 결과와 확정 사항

| 기준 문서 | 확인한 사항 | 06에서의 반영 |
| --- | --- | --- |
| 01 | PC 실행과 외부 Model 의존성 구분, Context 직접 처리는 허용, Agent 내부 제외 | FA-02, 10~12 |
| 02 | Task와 처리 경로 독립, 6종 Context, 실행 식별과 기억 관리 | FA-07, 09, 13~16 |
| 03 | 특정 Primary Agent에 종속되지 않음, 직접/위임·모델 배치가 내부 설계 선택 | 6.2, 6.5, 6.6 |
| 04 | 활동 순서 미고정, S2S 중복 처리 금지, 실제 전달·취소 상태 구분 | FA-09~15 |
| 05 | UC 18개와 필수 변형, Memory/Recovery 필수, 직접 조회는 할 수 있음 | 전 항목, 특히 6.4·6.7 |

01~05의 제품 범위를 바꿀 필요는 발견되지 않았다. 이에 따라 해당 문서는 수정하지 않고, 시험 조건과 변화 조건만 추가한다.

**이번 검토에서 확정한 비교 조건은 다음 네 묶음이다.**

1. Windows 데스크톱·한 활성 사용자·한국어 지시와 한영 자료라는 평가 기준.
2. active Task 0/1/4, 지칭 1/2/4, 복합 Request 2/3/4라는 시험점. 제품 상한은 아님.
3. 모델을 책임에 맞추어 비교하고, Agent 내부 시간 제외와 직접 처리 경로의 해석을 구분하는 규칙.
4. 재시작 기본 조건과 확인 불가 조건을 분리하고, 07의 전체 변경 집합을 함께 적용하는 규칙.

**실제 장비 사양, Model benchmark 수치, 녹음·화면 파일이 이미 확보되었다고 선언하지 않는다.** 현재 확정 대상은 선택 원칙과 시험 유형/기준값이다. 실행 증거에는 실제 값을 채우고 검증한 뒤에만 점수를 낸다. 이후 장비 기록·Test Case 파일 작성은 이 결정의 구현이지, 결과를 본 뒤 유리한 조건을 다시 고르는 작업이 아니다.


07의 변경 집합은 재검토를 반영한 **24개(M-01~09, A-01~09, C-01~06)**를 사용한다. 06의 공통 비교 규칙은 유지하며, 08은 [ASR 도출 및 평가 방향](./08-architecture-significant-requirements.md)에서 검토한다.
