# QA 공통 평가 시나리오 구성 방안

> 2026-10-14 / 사용자 지적에 따른 평가 구성 수정안 / 공통 목록과 N 확정 전 / 구현과 측정 없음

## 1. 현재 평가 구성의 문제

기존 상세안은 QA01의 응답 사건 30개와 QA02의 DP별 지칭 판단 20개 및 QA03의 완료 목표 12개와 QA04의 변경 과제 6개를 각각 만들었다. QA05와 QA06에는 사용자 요청 20개와 Agent 사건 6개를 배치했다. **같은 사용자 상황을 어떤 QA로 관찰하는지 연결하지 않고 지표별로 평가 자료를 따로 설계한 문제**가 있다.

20요청과 6개 Agent 사건을 합친 26은 독립적인 사용자 시나리오 26개가 아니다. 하나의 시나리오에는 여러 요청과 Agent 사건 및 응답이 포함될 수 있다. 현재 문서는 이 단위 차이와 공통 원본의 관계를 충분히 드러내지 못했다.

**수정 원칙은 공통 시나리오를 먼저 정하고 각 QA의 관측 대상을 그 안에서 지정하는 것이다.** 기존의 QA별 수량과 반복 횟수는 통합 전 초안으로 취급한다. 그 숫자들을 합하거나 가장 큰 수에 맞추어 새 N을 정하지 않는다.

## 2. 구분할 세 가지 수

| 구분 | 의미 | 기록 방법 |
| --- | --- | --- |
| 시나리오 수 N | 시작 상황과 사용자 목표 및 입력과 사건 흐름 및 완료 조건이 정해진 평가 상황의 수 | 공통 목록 S01~SN |
| 관측 건수 | 각 시나리오에서 평가할 응답 사건과 완료 목표 및 지칭 표현의 수 | S-ID에 속한 event ID / goal ID / referent ID |
| 반복 횟수 r | 같은 공통 입력 묶음을 다시 실행한 횟수 | run ID. 반복을 새로운 시나리오라고 세지 않음 |

예를 들어 “두 그래프 비교를 요청한 뒤 하나를 제외하도록 정정하는 상황”은 시나리오 하나다. 그 안에서 최초 요청과 정정에 대한 첫 응답을 각각 관측할 수 있다. 지칭 집합도 최초와 정정 뒤에 각각 판정한다. 서로 다른 관측 건수가 생겨도 출발점은 같은 시나리오다.

관측 건수는 실행 결과를 보고 늘리거나 줄이지 않는다. 시나리오마다 기대 응답과 완료 목표 및 지칭 판단을 먼저 지정한다. 응답을 만들지 않았거나 지칭에 실패했다고 해당 건을 분모에서 빼지 않는다. 후보가 내부 호출과 중간 응답을 더 만들더라도 평가 건수를 자의적으로 늘릴 수 없다.

## 3. 공통 시나리오를 만드는 출발점

[기존 대표 UC 18개](../../../05-representative-use-cases.md)는 사용자 기능 범위다. **UC 18개가 곧 실행 시나리오 18개라는 뜻은 아니다.** 한 UC에는 여러 필수 변형이 있고 한 시나리오가 여러 UC를 함께 다룰 수 있다.

현재 네 DP에서 다루는 기능과 기존 QA 초안의 평가 장면을 다음 관점으로 합친다.

| 기능 관점 | 포함할 상황 | 주요 관련 UC |
| --- | --- | --- |
| 말과 화면의 대상 연결 | 사전 선택 / 클릭 없는 가리키기 / 복수 대상 / 화면 전환 / 부분 정정 / 실제 모호함 | UC-03 / 04 / 06 / 11 |
| 과거 내용의 재참조 | 실제 전달한 답변 / 반복 조회 / 서로 다른 결과의 관계 / 전달 중단 / 변경 전후 버전 | UC-01 / 05 / 07 / 10 / 11 |
| 사용자 입력과 업무 사건의 교차 | 새 요청 / 정정 중 다른 업무의 질문과 결과 / 질문에 대한 답변 / 음성 중단 / 여러 업무 | UC-06 / 10 / 11 / 13 / 14 |
| 대화와 업무 상태의 연결 | 위임 / 진행 조회 / 순차 업무 / 변경 / 취소 / Voice와 Text 전환 및 재연결 | UC-07 / 08 / 09 / 10 / 12 / 15 |

UC-02와 UC-16~18의 자료 조회 및 권한과 정보 제어 및 실패 조건도 전체 기능 대조표에 남긴다. 정량 비교에 포함할 부분과 별도 기능 검증으로 관리할 부분 및 제외 이유를 사전에 명시한다. 현재 네 DP의 차이를 만들기 위해 기준선의 필수 기능을 없애지 않는다.

비슷한 장면은 같은 시나리오로 합치되 화면 변화와 과거 버전 및 동시 사건처럼 구조의 다른 경로를 검증하는 장면은 별도 변형으로 남긴다. **N은 이 목록의 중복 제거와 기능 누락 검토를 마친 결과로 정한다.** 숫자에 맞춰 시나리오를 채우지 않는다.

## 4. QA별 공통 시나리오 적용

| QA | 평가에 사용할 집합 | 공통 실행 기록에서 산출할 값 |
| --- | --- | --- |
| QA01 첫 응답 지연시간 | 공통 N개 전체의 사전 지정 응답 사건 | 사건별 첫 정답 내용 표시까지의 지연. 기존 최대값 집계 유지 |
| QA02 지칭 대상 식별 정확도 | 공통 목록 안에서 근거로 정답을 결정할 수 있는 지칭 표현 | 표현과 revision별 대상 집합의 완전 일치율. 화면과 과거 사례를 같은 규칙으로 식별 |
| QA03 VIA 처리시간 | 공통 N개 전체에 사전 지정한 완료 목표 | 목표별 완료 경로에서 외부 시간을 제외한 VIA 귀속시간. 기존 최대값 집계 유지 |
| QA04 변경 범위 | 공통 기능에 연결한 개발 변경 과제 | 변경 전후에 관련 시나리오를 만족시키는 데 필요한 운영 Rust 모듈 수 |
| QA05 모델 사용 비용 | 공통 N개를 정해진 순서와 조건으로 실행한 전체 묶음 | 준비와 갱신 및 재시도와 후속 청구까지 포함한 총 모델 비용의 반복 평균 |
| QA06 최대 RAM 사용량 | QA05와 같은 전체 실행 묶음 | 앱 시작부터 후속 종료까지 전체 VIA의 동시 RAM 관측 최고량 |
| QA07 부하 추가 지연 | 공통 목록의 동시 업무 사례와 같은 사례의 무부하 변형 | 동일 요청에서 다른 업무 부하가 추가한 첫 응답 지연 |
| QA08 병행 수정 중복 | QA04 변경 과제 중 사전 지정한 독립 변경 쌍 | 두 변경의 운영 모듈 집합 교집합 |
| QA09 음성 전달 지연 | 공통 목록에서 음성 요약을 전달해야 하는 응답 | 내용 채택부터 실제 재생까지의 재생 가능한 시간 |

QA02에 지칭이 없는 일반 지식 질문을 넣어 가짜 정답 집합을 만들지 않는다. 실제 모호한 지칭은 확인 질문 기능으로 검증하며 근거 부족이라는 이유로 아무 대상을 단정하지 않는지 함께 보고한다. QA07의 추가 부하와 QA09의 재생 가능 조건은 공통 시나리오의 이름 있는 변형으로 관리한다.

**QA별 숫자가 달라도 같은 시나리오의 어떤 관측 단위를 세었는지 ID로 설명할 수 있어야 한다.** 공통 조건에서 얻을 수 있는 여러 QA는 같은 실행의 기록에서 산출한다. 별도 계측이 필요한 경우에도 같은 입력과 초기 상태 및 외부 사건 순서를 재현한다. 일부 경로만 구현한 PoC의 부분 측정값을 전체 VIA의 비용이나 RAM 달성값으로 표시하지 않는다.

## 5. QA04는 공통 시나리오에 연결된 변경 과제로 관리한다

QA04는 프로그램을 실행하는 품질이 아니라 요구를 바꿀 때 수정이 퍼지는 범위를 평가한다. 사용자 시나리오 N개를 N번 실행하는 것으로 변경 용이성을 잴 수는 없다.

기존 C01~C06은 **개발 변경 과제 6건**이라는 별도 단위로 유지하되 다음 연결을 작성한다. 사용자 시나리오와 별개로 정의된 근거 없는 여섯 건으로 남기지 않는다.

| 변경 과제 | 공통 시나리오와 연결할 기능 |
| --- | --- |
| C01 모델 데이터 형식 변경 | 직접 응답과 화면 및 과거 내용 해석 |
| C02 Agent 데이터 형식 변경 | 위임과 접수 및 진행과 취소 |
| C03 화면과 과거 자료 형식 변경 | 화면 범위와 시점 및 과거 버전 해석 |
| C04 문단 단위 응답 수정 추가 | 응답 일부 정정과 대기 음성의 변경 |
| C05 과거 설명의 원본 위치와 버전 표시 추가 | 실제 전달한 설명의 재참조 |
| C06 정보 허용 철회를 구간 단위로 확장 | 화면과 과거 원본의 사용 허용 및 부분 철회 |

각 변경은 같은 시작 코드에서 독립 수행한다. 관련 시나리오의 추가 요구를 충족하는지 확인하고 공통 N개에 대한 기존 기능 회귀도 확인한다. 기능 확장은 해당 시나리오의 변경 후 기대 결과를 명시한 변형으로 관리한다. 미래 기능을 현재 모든 비교안이 이미 지원해야 하는 조건으로 끼워 넣지 않는다. 모듈 수의 집계 규칙과 ARGO 기반 평균 3개 목표는 이 분류 변경만으로 달라지지 않는다.

## 6. DP별로 공통 모집단을 바꾸지 않는다

각 DP의 두 안에는 공통 목록과 초기 상태 및 모델 조건과 외부 사건을 동일하게 적용한다. 다른 DP 영역은 같은 참조 구현이나 고정 주변부로 두고 비교하는 구조만 바꾼다. DP별로 유리한 지칭 20개나 응답 30개를 새로 뽑지 않는다.

시나리오와 QA의 적용 여부는 관측할 현상이 있는지에 따라 정한다. DP의 구조가 그 QA를 바꾸는지는 별도 칸에 기록한다. **측정할 수 있지만 구조 차이가 거의 없는 경우도 기록하며 차이 없는 결과를 trade-off 커버리지로 세지 않는다.** 비용과 RAM에서 구조와 무관한 공통 부분도 전체 범위에서 지우지 않는다.

QA01과 QA03의 최대값이 해당 DP에서 바꾸지 않는 공통 경로에서 나오면 대표값은 동점일 수 있다. 이 결과를 인정하고 DP가 영향을 준 경로는 보조 분석으로 제시한다. 차이를 만들려고 사후에 일부 사례만 최대값 집계에 남기지 않는다.

## 7. 문서 수정 순서와 현재 상태

1. 기존 QA의 장면 목록을 합치고 공통 시나리오 S01~SN에 UC와 네 기능을 연결한다.
2. 각 시나리오에 초기 상태와 자료 및 요청과 Agent 사건의 순서와 완료 조건을 작성한다.
3. 응답 사건과 완료 목표 및 지칭 표현을 등록하고 QA 적용 여부와 제외 이유를 붙인다.
4. 반복 횟수와 시나리오 실행 순서 및 캐시와 초기 준비 조건을 공통으로 정한다. 입력과 외부 사건의 상대 시각과 간격 및 겹침과 반복마다 초기화 여부 및 준비와 후속 종료 조건을 공통 실행 프로파일로 등록한다. 같은 순서라도 시간 간격이 다르면 경합과 지연 및 RAM 피크가 달라지므로 순서만 맞춘 실행은 동일 조건으로 인정하지 않는다. 동일 사례 반복을 새로운 시나리오나 독립 사용자 표본으로 부르지 않는다.
5. 시나리오 × QA × DP 표에서 기능 누락과 무리한 적용 및 유리한 사례 선별을 교차 검토한다.
6. QA 상세와 발표 표의 기존 수량을 공통 목록 참조로 교체하고 필요한 목표 산식과 점수 적용 판본을 함께 갱신한다.

**현재 완료한 것은 통합 방법과 기존 수량의 상태 정정이다.** 공통 N개 목록과 각 관측 건수 및 반복 횟수는 아직 확정하지 않았다. 기존 상세안의 30 / 20+20 / 12 및 20요청+6사건은 통합 전 초안이며 새 공통 평가의 최종 수량으로 사용할 수 없다.

QA05의 $0.71은 이전 20요청 활동에 대한 gpt-realtime과 Luna의 참조 견적이다. 공통 목록의 요청 수와 음성 길이 및 입력 자료가 달라지면 **새 활동을 같은 참조 방식으로 다시 견적**해야 한다. 기존 금액을 자동 이식하거나 요청 수에 비례해 단순 환산하지 않는다. 반복 수와 관측 범위가 달라지면 최대값 비교와 정확도 점수의 해상도 및 RAM 관측 최고량의 조건도 새 판본에 기록한다. QA06의 절대 목표와 계측 미완료 상태도 유지한다. 기존 수치의 동결이나 PoC 실행 또는 DP 대안 선정을 이 구성 변경에서 수행하지 않는다.

## 8. 독립 검토

`review_measurement`가 현재 QA 상세안과 이 통합 방향을 별도로 검토했다. 공통 시나리오와 QA별 분모의 구별 및 실행 순서와 초기화 조건 및 최대값의 공통 경로 동점 가능성과 신규 기능의 변경 후 수용 시나리오 및 비용 재견적을 요구했다. 이를 §2와 §4~7에 반영했다. 재검토에서 사건의 순서 외에 상대 시각과 간격 및 겹침을 명시해야 한다는 P2 한 건이 나와 §7에 보완했다. 검토는 통합 방법에 대한 것이며 공통 목록의 완성이나 목표 재견적 또는 PoC 결과 검증이 아니다.

보완 후 같은 검토자가 해당 P2의 해결을 확인했으며 이번 통합 방안 검토 범위에서 미해결 P1/P2는 없다.
