# QA01~06 목표 수치 도출 논리

> 2026-10-14 / 제품 요구 제안 / 출처 확인 및 문서 검토 / 구현과 PoC 측정 전

**목표는 구현에 필요한 시간을 나눠 정하는 값이 아니라 사용자나 제품이 요구하는 수준이다.** 이 문서는 확인한 외부 사실과 VIA에 적용하는 제품 판단을 연결한다. 실제 stakeholder 합의나 VIA 실측 결과가 없는 부분을 이미 합의했거나 달성한 것으로 표현하지 않는다.

읽는 순서는 이 문서 → [발표용 표](./quality-requirements-table.md#presentation-table) → 각 QA 상세안이다. [패키지 README](./README.md#4-qadp-대응과-예상-우열)에서 QA와 DP의 대응 및 예상 손익을 함께 확인한다. QA07~09는 별도 보조 후보로 유지하며 이번 목표 근거 재작성은 핵심 여섯 QA를 대상으로 한다.

## 2. QA01: 왜 1초인가

**사용자는 입력이 어떻게 이해됐는지 확인하고 생각과 행동을 이어갈 수 있어야 한다.**

- [Nielsen, Response Times: The 3 Important Limits, 1993](https://www.nngroup.com/articles/response-times-3-important-limits/)은 약 1초를 사용자의 사고 흐름 유지에 관한 UI 응답 지침으로 설명한다.
- [Microsoft Windows 응답성 지침, 2026-03-18 갱신](https://learn.microsoft.com/en-us/windows/apps/develop/performance/responsive)은 `Pause` 0.5~1초를 지연은 있지만 응답성이 유지되는 범위로 설명한다.
- VIA의 종료점은 해당 요청이나 업무 화면에 **첫 완결된 정답 내용이 보이는 때**다. 이 UI 동작에 위 지침을 적용하여 **1초 이하**를 요구한다.

평균 1초는 20초 걸린 한 사건을 수십 개의 빠른 사건으로 가릴 수 있다. 따라서 대표 사례 30개와 반복 3회의 **최대값**으로 판정한다. 한정된 시험에서 관측한 최대값이며 모든 미래 요청의 수학적 최악 시간을 보장하는 것은 아니다.

**심사 답변:** “생각과 행동의 흐름을 유지할 UI 반응 수준을 외부 HCI 지침에서 가져왔습니다. 인사나 로딩 표시를 제외한 첫 내용 표시를 1초 안에 제공하도록 요구합니다.”

**예시:** 발화 종료 0초 → ‘네’ 표시 0.1초 → 채택한 비교 수행 안내 0.8초 → Agent 전송 1.3초 → 음성 요약 재생 2.5초라면 해당 사건은 0.8초다. Agent 위임 완료나 음성 차례를 첫 표시의 종료점으로 사용하지 않는다.

## 3. QA02: 왜 99%인가

**말로 지정하는 편의성을 얻으면서 기존 직접 선택의 신뢰 수준을 크게 낮추지 않아야 한다.**

[Rajanna & Hammond, Can Gaze Beat Touch?, 2022, Table 2](https://arxiv.org/html/2208.01248)의 desktop Fitts 선택 실험에서 마우스 오류율은 **1.3%**다. 성공률은 **98.7%**이며 이를 정수 단위로 상향한 **99%**를 지칭 대상 선택의 제품 목표로 제안한다. [HFES 2009 실험](https://www.yorku.ca/mack/hfes2009)의 마우스 성공률 97.9%도 약 98% 수준의 참조 사례다.

이 수치는 잘못된 Agent 실행을 사용자가 1%까지 감내한다는 조사가 아니다. 2022 실험은 12명이 큰 표적을 선택한 운동 과제이며 VIA의 화면과 과거 이력에 대한 의미 해석 과제가 아니다. **기존 입력 수단의 성능을 목표 설정의 참조값으로 채택한 것**이다. VIA의 실제 비열등성은 같은 사용자 과제로 비교하지 않았으므로 주장하지 않는다.

**심사 답변:** “수동 선택을 음성 지칭으로 대체하는 기능이므로 기존 입력 수단에서 관찰된 신뢰 수준을 유지하도록 요구했습니다. 마우스 실험의 성공률 98.7%를 참조해 99%를 목표로 잡았고 VIA는 일부 대상만 맞히는 경우도 실패로 평가합니다.”

**예시:** 정답 집합이 `{표 A, 그래프 B}`일 때 `{표 A}`나 `{표 A, 그래프 C}`는 모두 실패다. 100개 판정 중 99개가 전체 집합과 일치하면 시험 점수는 99%다. 이는 독립 사용자의 모집단 성공률 99%를 통계적으로 입증한 것과 다르다.

**사용하지 않는 논리:** 일반 Agent benchmark의 업무 성공률을 잘못된 VIA 요청의 조건부 복구율로 대입하지 않는다. `0.9 + 0.1×0.9 = 0.99`가 성립하려면 앞의 0.9는 VIA 성공률이고 뒤의 0.9는 VIA 실패 조건에서의 실제 복구율이어야 한다. 후자를 측정한 증거 없이 같은 숫자를 넣을 수 없다.

## 4. QA03: 왜 5초인가

**VIA는 일의 실행을 연결하는 인터페이스이므로 자체 처리가 장시간 대기를 만들어서는 안 된다.**

[Microsoft Windows 지침](https://learn.microsoft.com/en-us/windows/apps/develop/performance/responsive)은 `Long wait`를 **2~5초**, 불가피하게 길고 복잡한 상황의 `Captive`를 **5~10초**로 분류한다. VIA의 해석과 상태 연결 및 응답 준비가 Long wait의 상단을 넘어 Captive 구간의 대기를 추가하지 않도록 **5초를 자체 처리의 상한**으로 채택한다. 이 값이 자연스럽거나 빠른 대화라는 뜻은 아니다. 첫 내용 반응은 QA01에서 1초를 요구한다.

입력부터 모든 VIA 처리와 상세 텍스트 표시 및 음성 요약 준비까지의 완료 경로에서 외부 Agent의 도메인 작업과 사용자 대기 시간을 제거한다. 12목표를 5회 수행한 귀속 처리시간의 **최대값**을 평가한다. 외부 업무가 없는 직접 응답은 실제 완료 지연과 일치한다. 위임 업무에서는 전체 대기에서 VIA가 소유한 처리 경로의 예산이다.

**심사 답변:** “해석 단계에 임의 시간을 배분해서 5초를 만든 것이 아닙니다. Windows가 구별하는 장시간 대기의 경계 5초를 가져와 VIA 자체 처리의 한계로 적용했습니다. 외부 업무까지 5초에 완료한다는 주장은 하지 않습니다.”

**예시:** VIA 1.2초 → 외부 작업 8초와 VIA 준비 3초가 병렬 → VIA 0.6초라면 실제 완료는 9.8초다. 외부 작업을 0초로 둔 VIA 경로는 `1.2 + max(0,3) + 0.6 = 4.8초`다. 이를 실제 경과시간에서 단순히 8초 빼서 1.8초로 보고하지 않는다.

## 5. QA04: 왜 평균 3개 모듈인가

**현재 가능한 국소 변경 수준을 기능과 공급자가 바뀌어도 유지한다는 개발 요구다.**

원본 VIA 저장소의 Git 이력을 읽어 독립적인 동작 수정 두 건을 확인했다. 운영 코드의 Rust `mod` 경로를 확인하고 테스트만 바뀐 파일은 제외했다. [상세안](./qa04-change-scope.md)에 전체 SHA와 운영 모듈 및 제외 항목을 기록한다.

| 실제 변경 | 운영 모듈 수 | 확인한 경로 |
| --- | ---: | --- |
| `06bfa51` 포트 재할당 결과를 자식 프로세스 실행 인자에 반영 | **3** | `via-backends::openclaw`, `via-backends::runtime`, `via-process::spawn` |
| `6d984b6` 첫 음성 입력에서 엔진 연결을 시작하고 입력을 보관 후 전달 | **1** | `via-app::realtime::connection` |

두 사례를 평균내서 3을 얻은 것이 아니다. **실제 국소 수정의 관측 상단 3개를 대표 변경 과제의 평균 상한으로 채택**한다. 변경 단위가 같은 독립 동작 사례를 선택했으며 여러 기능을 한꺼번에 넣은 대형 commit을 한 변경으로 섞지 않았다. 두 사례로 신규 기능 전체의 분포를 추정하거나 모든 확장이 3개 안에 가능하다고 주장하지 않는다.

[SEI의 modifiability 시나리오 연구, 2002](https://www.sei.cmu.edu/documents/689/2002_005_001_14063.pdf)는 변경 모듈 수를 변경 용이성의 응답 지표로 사용한다. 이 자료는 지표의 타당성을 뒷받침하며 숫자 3의 출처는 위 실제 VIA 선례와 이를 유지하려는 제품 개발 판단이다.

**심사 답변:** “AI 코딩으로 구현 시간보다 수정이 퍼지는 영역이 협업에 큰 부담이 됩니다. 기존 VIA에서 독립적인 수정이 운영 모듈 1개와 3개에 국한된 실제 사례를 확인했고 모델 변경과 기능 확장에서도 평균 3개 이하를 유지하도록 요구합니다.”

**예시:** 대표 변경 6건의 모듈 수가 `2, 2, 3, 4, 3, 4`라면 평균 3개다. 실제 C01~C06을 수행해 나온 수치는 아니다. 기능 확장의 수정 범위를 미리 5개로 정하거나 점수에 맞춰 필요한 모듈을 누락하지 않는다.

## 6. QA05: 왜 활동당 $0.47인가

**같은 기능 범주의 표준 활동을 범용 API로 구성하는 공개 견적 이내에서 제공한다는 원가 요구다.** 소비자의 월 구독료나 근무일 및 일일 요청 횟수에서 역산하지 않는다.

COST20-v2는 5분에 사용자 요청 20건과 Agent 사건 6건을 배치하는 시험 규격 제안이다. 참조 견적은 계기당 텍스트 입력 20,000토큰과 추론을 포함한 총 청구 출력 500토큰 및 화면 지칭 6건당 최대 15장으로 정의한다. 이는 고객 이용량 통계가 아니다. 호출 26회와 원문 입력량은 견적용 참조 구성이며 A/B의 실제 호출 수나 구조에 강제하지 않는다. 후보는 같은 원본과 응답 의무를 자기 구조로 처리하고 실제 사용량을 청구 원장으로 평가한다.

| 공개 견적 항목 | 단가와 조건 | 금액 |
| --- | --- | ---: |
| 음성 입출력 | GPT-Live 1 세션 5분 × $0.05/분 | $0.2500 |
| 텍스트 입력 | 26 × 20,000토큰 × $0.25/100만 토큰 | $0.1300 |
| 총 청구 출력 / 추론 포함 | 26 × 500토큰 × $1.20/100만 토큰 | $0.0156 |
| 화면 입력 | 90장 × 최대 3,000토큰 × $0.25/100만 토큰 | $0.0675 |
| **견적 상한** | 합계 | **$0.4631** |
| **목표** | 센트 단위 올림 | **$0.47** |

출처는 [GPT-Live 1](https://developers.openai.com/api/docs/models/gpt-live-1), [GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna), [공식 이미지 토큰 규칙](https://developers.openai.com/api/docs/guides/images-vision)이다. 확인일은 2026-10-14다. 입력은 기본 $0.20에 공개 캐시 쓰기 배율 1.25를 적용한 **$0.25**로 보수적으로 잡는다. 캐시 할인이나 무료 제공을 전제하지 않는다. 모든 입력에 이 상한을 적용한 견적이며 입력과 캐시 쓰기 비용을 중복 청구하는 식은 아니다.

**심사 답변:** “월 $20를 내는 사용자를 가정한 것이 아닙니다. 정해진 한 번의 표준 활동에 음성과 화면 및 문맥 처리를 제공하는 구매 대안의 공개 견적이 $0.4631이므로 $0.47 이내의 모델 원가를 요구합니다.”

**범위:** 이 참조 API 구성의 VIA 정확도 충족을 실측한 것은 아니다. 기능 범주의 견적을 비교 기준으로 사용하며 후보는 별도로 정확성 요구를 만족해야 한다. 제품의 모든 운영비나 출시 수익성을 이 금액으로 입증하지 않는다. 입력 WAV와 토큰 자산은 실행 전에 고정하고 준비와 재시도 및 5분 이후 후속 청구도 후보 비용에 포함한다.

## 7. QA06: 왜 최대 512MiB인가

**기본 탑재 VIA는 큰 모델을 클라우드에서 처리하며 다른 앱과 함께 실행할 수 있도록 로컬 자원 부담을 제한해야 한다.**

| 기능 참조 | 공개 수치 | 조건과 한계 |
| --- | ---: | --- |
| [Microsoft PowerToys Command Palette PR #40551](https://github.com/microsoft/PowerToys/pull/40551) | 시작 피크 5회 중 최고 **171MB** | 평균 피크 160.56MB. 입력과 확장 기능 사용은 제외. 정확한 카운터 검증 불가 |
| [Vosk 소형 음성인식 모델](https://alphacephei.com/vosk/models) | 실행 중 **약 300MB로 안내** / 원문 `300Mb` | 단위가 엄밀하지 않은 개발사의 대략적 안내. 특정 Windows 최고값 아님 |
| [Picovoice Orca TTS](https://picovoice.ai/docs/benchmark/tts/) | 합성 중 최고 RAM **41MB** | 공급사 공개 벤치마크. LLM과 Python 준비 비용 제외 |

위 자료는 **명령 UI 171MB와 소형 음성 기능 41~300MB의 독립적인 사례**다. 수십~수백 MB의 개별 사용 규모를 제품 부담의 참조점으로 삼아 1GiB보다 낮은 **0.5GiB = 512MiB**를 상한으로 선택한다. 정확한 512는 제품 예산 선택과 단위 변환에서 나온다. 공개 자료가 세 기능을 합친 512MiB를 측정한 것은 아니며 다른 카운터의 숫자를 합산한 값도 아니다.

**심사 답변:** “32GB RAM을 임의 분할하지 않았습니다. 명령 UI의 시작 피크 171MB와 소형 음성 기능의 41~300MB 사례를 참고해 기본 탑재 VIA에 0.5GiB 상한을 제안했습니다. 512MiB는 제품의 선택이며 실제 VIA의 달성과 다른 앱과의 공존은 별도로 검증합니다.”

**실제 검증:** 모든 VIA 프로세스와 공유 버퍼 및 VIA에 귀속되는 공유 GPU 시스템 RAM을 같은 시점에 중복 없이 합산한 최고량을 잰다. 시작 시나리오만 측정하지 않고 표준 활동과 이후 정리까지 포함한다. 전용 GPU VRAM은 별도 기록한다. 서로 다른 프로세스의 각자 최고값을 더하지 않는다. 연속 최고량을 정확히 구하는 Windows 계측 구현과 16GB 제품의 실제 앱 공존 시험은 아직 수행하지 않았다.

**예시:** 같은 시점의 합계가 380MiB와 400MiB였다면 관측 최고량은 400MiB다. 프로세스별 서로 다른 시점의 최고값을 더해 420MiB로 보고하지 않는다.

## 8. 변경과 평가 규칙

- QA01과 QA03의 평균을 최대값으로 바꿨으므로 기존 평균 결과와 점수를 그대로 옮기지 않는다. DP의 재사용 평균 이익만으로 최대값 이익을 주장하지 않는다.
- QA02는 98%에서 99%로 바꿨다. 반복 fixture 100판정은 독립 사용자 100명의 증거가 아니다.
- QA04는 기존 1개와 5개 가정을 폐기한 상태를 유지한다. 새 평균 3개는 실제 수정 선례를 참조한 요구안이다.
- QA05는 표준 활동의 내용과 가격표를 버전으로 고정해야 한다. 다른 활동량이나 단가에 같은 금액을 자동 재사용하지 않는다.
- QA06의 이전 확보량 1GiB는 재사용하지 않는다. 512MiB는 실제 RAM 최고량에 대한 제안이다.
- 0점은 목표 미달이며 1~6점은 목표 충족과 개선 여유다. 중간 경계는 비교 표현 규칙이며 논문이 정한 합격선으로 제시하지 않는다.
- 목표에 맞춰 측정값이나 실패를 고치지 않는다. 실제 수치가 예상과 다르면 경계와 구현의 대등성을 검토하고 정당한 결과를 보존한다.
