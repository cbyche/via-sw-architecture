## 1. 문서 목적과 설계/평가 원칙

VIA에서 중요한 품질속성의 의미, 범위, 우선순위와 평가 기준을 사용자와 함께 정의한다. 먼저 어떤 품질을 왜 중요하게 보는지 합의하고, 이후 지표와 측정 방법을 구체화한다. 새로운 정의 논의와 합의는 이 문서에 이어 기록한다.

[03-00 품질 시나리오](./03-00-quality-scenarios.md)는 기존에 검토한 13개 품질 관점과 충돌 상황의 근거다. [기존 Core ASR 계약](../../08-quality-attributes/core-asr-contract.md)은 QA-09, QA-19, QA-29, QA-39와 상세 QA의 현재 의미를 보존한다. 이번 초안은 이 자료를 바탕으로 재검토하며 기존 정의를 자동 대체하지 않는다.

최근 [04-40 공통 실행 계약](./04-40-common-execution-contract.md)은 로컬 VIA와 클라우드 음성/의미 모델을 전제로 한다. 이 조건에서 PC 자원과 모델 사용 비용, 네트워크 의존성이 품질에 미치는 영향을 다시 살핀다. 기존 on-device 참조 설계와 당시 QA 정의 및 결과는 원래 조건으로 보존한다.

### 1.1 합의한 목적과 DP/QA의 관계 — 재개 시 반드시 읽기

**VIA의 목적은 핵심 QA 성능을 우선순위에 따라 최대화하는 SW를 만드는 것이다.** 이 과제에서 중요한 기능과 구조를 다루면서 핵심 QA 성능에 영향을 미치는 설계 결정을 DP로 도출한다. 현재 유력 후보는 **DP-41, DP-42, DP-44, DP-45**다. 이 네 개가 최종 DP나 A/B 승자로 선정된 것은 아니다. 43과 별도 46 자료의 지위를 이번 논의로 변경하지 않는다.

정방향의 설계 논리는 다음과 같다.

1. 중요한 품질 목표와 우선순위를 정한다.
2. 그 품질에 영향을 주면서 과제 차원에서도 중요한 설계 결정을 도출한다.
3. 각 DP의 강한 방안 A/B에 대해 핵심 QA 전체의 trade-off를 확인한다.
4. 합의한 우선순위에서 더 좋은 QA 성능을 보이는 방안을 선택한다. 필수 규칙, 허용 한도, 동등 또는 불확실한 차이의 처리도 공통 선택 계약에서 정한다.
5. 선택한 방안의 낮은 우선순위 QA가 약하면 tactic으로 보완한다. 보완 후 높은 우선순위 QA의 회귀와 다른 비용을 함께 확인한다.

기본 구조와 적용한 tactic을 구별해 결과를 기록한다. 기본 구조 비교를 위해 필수 검사나 이미 허용한 정상 기능을 제거하거나, A 또는 B를 약한 구현으로 바꾸지 않는다. tactic으로 차이가 줄어드는 것은 정상적인 설계 과정이다. 여러 QA를 가중 총점으로 합쳐 trade-off를 숨기지 않는다.

### 1.2 이번에는 DP에서 QA 정의로 역으로 접근한다

사용자는 DP 후보가 이미 있는 상태에서 A/B 성능을 측정하거나 계산할 수 있도록, 다섯 품질 묶음의 정의, 세부항목, 대표 지표와 목표를 구체화하려 한다. **기존 QA 공식을 자동 적용하는 것으로 끝내지 않고, 실제 구조 차이의 중요한 품질 효과를 포착하는 공통 QA를 설계한다.** 다음 순서로 각 품질을 검토한다.

**A/B의 실제 작동 차이 → 품질이 달라지는 원인과 상황 → 사용자에게 중요한 QA 정의 → 공통 지표와 목표 → 측정/계산 → 우선순위에 따른 선택과 tactic 보완**

| 연결 | 확인할 질문 |
| --- | --- |
| 사용자 가치와 QA 정의 | 이 품질이 좋아지면 VIA 사용자가 무엇을 더 잘할 수 있는가? |
| 구조 차이와 품질 효과 | A/B의 어떤 판단, 근거 획득, 실행 의존성, 상태 또는 확정 차이가 품질을 바꾸는가? |
| 품질 효과와 지표 | 그 차이를 같은 입력과 조건에서 관찰하고 계산할 수 있는가? |

정의는 구조 차이에 민감하면서도 실제 사용자 가치에 근거해야 한다. 같은 조건에서 A/B 차이가 없거나 측정으로 구분되지 않는다면 그대로 남긴다. 모든 DP가 모든 QA에서 다른 값을 가져야 한다고 요구하지 않으며, 예상한 우열에 맞춰 사례나 분모를 고르지 않는다.

초기 측정/계산은 정의의 적합성을 확인하는 탐색에 사용할 수 있다. 이때 사용한 정의 version과 사례, 변경 이유를 남긴다. 최종 선택에 쓰는 비교는 검토를 마친 공통 계약을 결과 전에 고정한 뒤 수행한다. 탐색 결과를 개정된 계약의 최종 비교 결과로 재해석하지 않는다. 이번 합의는 정의와 평가 설계의 진행 방향이며 지금 구현, 모델 실행, 수치 freeze나 최종 선택을 시작하는 지시로 확대하지 않는다.

### 1.3 Compaction 또는 다른 세션에서 재개하는 순서

1. AGENTS.md와 00-workplan의 현재 QA 체크포인트를 읽고 실제 git 상태를 확인한 뒤, 맨 앞 ASR-QA 요약표에서 ID/최신 필수 항목/근거와 계약 version을 확인한다.
2. **§1.1~1.2의 합의한 방향**을 읽는다. 유력 DP 네 개, 역방향 정의, 우선순위 선택과 tactic 보완의 관계를 복원한다.
3. §2의 목록/검토 상태와 §9의 최신 변경 이력을 읽는다. 정확성은 한 축이며 우선순위는 ASR-QA 번호 오름차순이다. §1.7의 위임에 따라 지표/목표/계산 가정을 작성자가 완성하고 함께 리뷰한다.
4. 정확성은 **§3의 Voice PoC v3**와 **§8의 공통 시험 환경**을 따른다. 이전 Text/Voice × 모든 조건 교차 시험이나 초기 7개 항목을 복원하지 않는다. 18개 대표 사례 × 5회, 실행당 6개 이진 항목을 유지한다.
5. 각 QA의 현재 내용은 해당 절에 갱신하고 변경 이유는 §9에 남긴다. 이전 QA 지표를 자동 복원하거나 DP별로 다른 QA를 만들지 않는다. 구현/실측 착수는 별도 요청을 따른다.

### 1.4 모든 DP에 적용할 공통 정의 원칙

선정한 QA는 모든 DP와 모든 대안에서 동일한 정의, 대표 지표와 측정 방법을 사용한다. 평가 단위, 정답 판정, 시작/종료 사건, 시간 및 비용 경계, 집계, 모집단 적용, 분모와 제외 규칙, 실패 및 timeout 처리를 공통 원본에서 정한다. 각 DP는 구조의 인과적 참여와 내부 관측을 그 계약에 연결한다.

같은 QA를 특정 DP에서는 의미 field accuracy, 다른 DP에서는 검색 recall이나 업무 성공률로 바꾸어 사용하지 않는다. 추가 진단은 공통 QA를 대체하지 않는다. 미참여, 미지원과 미확인을 0점이나 동등으로 간주하지 않으며, 실패 사례를 조용히 제외하지 않는다.

QA의 개정 이유와 영향받는 문서를 함께 기록하고, 이전 정의 및 결과는 원래 계약으로 보존한다. 기존 자료의 재사용은 의미와 측정 방법이 맞는지 확인한 뒤 결정한다. 지표와 목표값을 확정하기 전에도 각 품질의 손익은 독립적으로 설명하며 가중 총점으로 합치지 않는다.

### 1.5 다른 품질 관점과의 관계

기능 적절성, 기능 완전성과 결함 허용성 및 복구성은 이번 핵심 QA 목록의 독립 항목에서 제외한다. 기밀성, 분석 및 시험 용이성, 상호운용성과 공존성, 조작 용이성과 사용자 오류 방지, 설치 용이성 및 메모리 외 자원도 기존 자료에서 참고한다. 이 문서에 핵심 QA를 추가할 때는 사용자가 정한 다섯 묶음의 범위와 관계를 다시 논의한다.

[03-00](./03-00-quality-scenarios.md)의 13개 관점과 기존 구조 비교 기록은 보존한다. 기능 지원 차이와 수동 우회 부담은 비교 조건 및 한계로 남긴다. 미지원 안내를 원래 목표의 성공 완료로 세거나 권한 위반을 비용 절감으로 정당화하지 않는다. 장애 상황의 잘못된 상태나 중복 실행은 해당 정확성의 범위와 공통 시험 조건에서 어떻게 판정할지 정한다.

### 1.6 문서 관리 방식

각 QA는 **ASR-QA-01, ASR-QA-02, ...**의 고정 ID로 관리한다. 문서 맨 앞의 요약표에 정의/대표 측정 지표/목표값/목표 근거를 모으고, §3~7의 해당 절에는 상세 범위/집계/판정/시험/DP 영향 경로와 검토 내용을 기록한다. 합의/개정 시 요약표와 상세 절을 함께 갱신해 서로 다른 최신 정의가 남지 않도록 한다. 작성자는 응답속도 이하의 항목도 §1.7에 따라 지표/숫자 목표/근거/절차를 완성하고 가정과 사용자 합의 여부를 구별해 표시한다.

**모든 핵심 QA의 발표 필수 항목은 ① 한 문장 정의 ② 대표 측정 지표 ③ 목표값과 과제 차원의 선택 근거다.** 목표 근거에는 VIA의 사용자 목표/고정 기능 요구와 연결해 왜 그 품질 수준이 필요한지, 숫자를 어떤 참조값/허용 예산/계약으로 선택했는지를 각각 쓴다. 계산식이나 “98% = 오류 2%” 같은 환산만으로 목표 필요성을 설명한 것으로 보지 않는다. 외부 참조와 VIA의 선택 판단, 평가 목표와 달성 사실을 구별한다. 기존 [QA 발표 요약](../../../presentations_files/quality-attributes.md)과 [목표 근거 부록](../../../presentations_files/quality-metrics/README.md)의 필수 구성을 참고하되 이전 지표/분모/숫자를 자동 이관하지 않는다.

공통 시험 환경과 A/B 비교 조건은 §8에서 관리하고 각 QA는 필요한 공통 조건을 참조한다. 정확성의 90회/540개 분모나 목표를 아직 정의하지 않은 다른 QA에 자동 적용하지 않는다. 합의와 작성자 제안, 정의 완료와 실제 측정 완료를 구별한다.

이전 제안은 archive에 보존하고 변경 이유/범위를 §9에 기록한다. 목차 이동 시 본문 참조와 README/00-workplan의 재개 안내를 함께 갱신한다. 문서 정리는 QA 정의 개정이나 DP 선정으로 취급하지 않는다.

### 1.7 자율 완성 계획과 중간 게시 단위 — 2026-10-11

사용자는 모든 요약 칸과 실제 평가 방안을 작성자가 구체적으로 채우고 이후 함께 리뷰하도록 지시했다. 애매한 부분은 근거를 찾아 판단하거나 수치 가정과 선택 이유를 명시해 닫는다. 목표 미달이나 결과 미실행과 정의의 빈칸을 구별한다. 공개 수치에 기반한 계산은 작은 PoC의 정당한 평가 수단이며 완성 제품/실제 외부 Agent/전체 모델 서비스를 선행조건으로 요구하지 않는다.

공개 자료가 단일 값을 보장하지 않는 첫 출력/queue/네트워크는 공통 기본값과 느린/빠른 민감도 값을 작성자가 선택한다. 그 가정에서 순위가 바뀌면 조건부 우열로 보고하고 정의를 비워두지 않는다. 실제 API 호출은 별도 보완 수단이며 이 계획 단위에서 유료 호출이나 후보 구현을 시작했다고 기록하지 않는다. 정답률은 시간/비용에서 역산하거나 A/B에 미리 정한 오류 확률로 만들어내지 않는다.

정의 단위 1~4를 완료했다. 기존 합의 보존, 정확성/시간, 비용/변경/메모리를 순서대로 commit/push했고, 네 DP 참여와 참조 계산도 같은 원본 계약으로 검수했다. 발표용 산출물은 [요약 2장](../../../presentations_files/quality-attributes/README.md)과 [목표 근거/등급 6장](../../../presentations_files/quality-metrics/README.md)이며 편집 가능한 PPTX, 각 장 PNG, 원문 연결과 재생성 방법을 함께 제공한다. 이전 자료는 [발표 archive](../../../archive/qa-presentations-before-asr-20261011/README.md)에 원래 bytes/hash로 보존했다.

각 단위는 완료된 정의/계산/자료와 근거를 리뷰할 수 있는 크기로 게시한다. 마지막에 여섯 QA를 함께 리뷰하고 목표를 조정할 수 있으며, 변경 전 계약과 결과가 있으면 원래 version으로 보존한다. 다른 세션의 04-50/입력 근거/발표 그림/`work/` 변경은 게시 범위에 넣지 않는다.

## 3. 정확성

### 3.1 정의와 평가 범위

**사용자가 지정한 목적은 설계 방안 A/B의 품질 차이를 확인하는 작은 PoC다.** 모든 UC 변형/채널의 기능 완전성이나 제품 수준 음성 인식/장치 성능을 검증하는 캠페인이 아니다. 같은 대표 Voice 장면을 공통 경계까지 추상화하고 DP가 바꾸는 판단/결합/확정/후속 실행/근거 생산의 차이를 유지한다. Text 입력을 제외하고 모든 사례에 모든 조건을 곱하지 않는다. §3의 분류/채점/목표와 §8의 공통 환경을 실행 기준으로 사용하며 실제 파일/모델/후보 build의 machine freeze와 실행은 별도 작업이다. [이전 v1](../../../archive/qa-request-accuracy-before-voice-poc-20261010/README.md)은 변경 근거로 보존했고 실행 결과는 없었다.

- **정의:** VIA가 사용자 입력과 외부 사건을 의도 및 확인 가능한 사실에 맞는 요청 처리 결과로 연결하는 능력. 의미, 근거/대상, 업무 연결, 관계/변경, 적용 상태와 실제 전달을 포함한다.
- **평가 상황:** §3.2.1의 S1~S6. 기본 사례는 §3.2.2의 상세 명세에 따라 상황군별 3개, 총 18개로 고정한다.
- **실행당 채점:** C1~C6를 각각 0 또는 1로 판정한다. 항목 안의 필수 사실을 모두 만족하면 1, 하나라도 틀리거나 필요한 결과/근거가 없으면 0이다. 세부 사실별 진단은 보존하지만 별도 점수로 더하지 않는다.
- **대표 지표:** 채점 항목 전체의 정답률. 여섯 항목은 같은 비중이며 비용/시간 등 다른 QA와 가중 합산하지 않는다.
- **완전 정답 처리율:** 한 실행의 여섯 항목이 모두 1인 비율. 같은 원시 판정에서 계산해 보조 품질 한도로 사용한다.

**대표 사례 18개를 한 번씩 실행하면 18 × 6 = 108개 항목을 채점한다.** 18개 사례에는 여섯 유형 모두에 의미 있는 필수 사실을 §3.3.2처럼 등록하므로 N/A 칸이 없다. 예를 들어 업무가 없는 경우의 C3은 `무관 Task에 연결하지 않음`, 상태 변경이 없는 조회의 C5는 `조회/응답을 처리하고 불필요한 외부 업무 효과를 만들지 않음`으로 검사한다. 빈 항목에 자동 1점을 주는 방식이 아니다.

**이번 PoC에서는 여섯 묶음의 이진 판정으로 집계한다.** 판정 후 N/A로 변경하거나 사례별 조건 수로 가중치를 바꾸지 않는다. v3은 v2에서 남았던 초기 자료/입력/사건/정답의 빈칸을 닫은 정의 개정이며 모델/파일 hash를 고정한 machine freeze는 아니다.

### 3.2 테스트 상황 분류와 18개 대표 사례

**테스트는 상황 6개 유형으로 분류하고, 정답은 조건 6개 유형으로 기술한다.** 상황 유형은 어떤 문제를 시험하는지, 조건 유형은 무엇이 맞아야 하는지를 나타낸다. 테스트마다 입력, 초기 상태, 사건 순서와 기대값을 바꾸되 조건의 의미와 판정 규칙은 재사용한다. 이 유형들은 새로운 QA 12개나 DP별 지표가 아니다.

기능 범위의 근거는 [고정 UC](../../05-representative-use-cases.md)이며, 네 DP의 영향 경로는 §3.7에 연결한다. 현재 네 비교에서 제외한 음성 모델의 자율 직접 응답은 [04-40](./04-40-common-execution-contract.md)의 경계를 따른다. UC-01의 기존 기능 요구 자체를 삭제하거나 Downstream Agent의 도메인 결과 품질을 VIA 판정으로 가져오지 않는다.

#### 3.2.1 공통 상황 분류

| 유형 | 시험할 상황과 경계 | 공통으로 확인할 핵심 결과 | 주 UC 연결 |
| --- | --- | --- | --- |
| S1 명시적 기본 요청 | 목표와 대상이 입력에 명시된 새 요청. 특별한 과거 지칭, 복합 관계, 정정이나 확인이 필요하지 않음 | 명시된 목표/제약을 누락하지 않고 적절히 답변하거나 위임 | UC-02, 08, 17 |
| S2 지칭과 근거 연결 | 화면, 선택, 생략, 과거 설명이나 업무 결과에서 대상을 찾아야 하는 요청 | 해당 시점/범위/version의 올바른 근거와 대상을 사용 | UC-03, 04, 05, 07, 10 |
| S3 복합 요청과 관계 | 한 입력에 여러 목표가 있고 독립, 순서, 결과 의존 또는 조건 관계가 있음 | 각 목표 및 관계/제약을 보존하고 관계에 맞게 처리 | UC-09 |
| S4 정정과 제어 | 기존 요청/업무의 변경, 음성 중단, 특정 업무 취소 또는 사용자 설정 변경/삭제 | 지정 범위만 바꾸고 무관한 내용/업무를 보존. 효력과 실제 상태를 구별 | UC-10, 11, 12, 17 |
| S5 외부 업무 사건 | Agent의 질문, 진행, 접수, 결과, 실패 등 외부 사건을 VIA가 수신 | 올바른 업무/대화로 연결하고 확인된 사실과 필요한 후속 동작을 전달 | UC-13, 14, 15, 18 |
| S6 확인과 판단 유보 | 처음부터 정보/대상/허용 범위가 불충분한 요청 또는 기존 질문에 대한 사용자 답변 | 필요한 확인/유보를 하고 질문 유효성, 답변의 대상과 승인 범위를 보존. 근거 없는 확정 금지 | UC-06, 14, 16, 18 |

**대표 상황은 후보 실행 전에 원천 입력과 초기 상태로 하나만 지정한다.** 중복되는 경우 다음 순서로 정한다.

1. 평가할 입력이 Agent 원천 사건이면 S5다. 이후 그 질문에 대한 사용자 답변은 별도 과제로 등록하면 S6다.
2. 평가할 입력이 기존 질문의 답변이거나, 필요한 정보/허용이 불충분하도록 작성한 사례면 S6다. 철회/만료된 질문에 대한 답변도 이 유형에서 적용 금지를 확인한다.
3. 기존 내용을 바꾸거나 제어하는 입력이면 S4다.
4. 여러 목표의 관계를 시험하는 입력이면 S3다.
5. 지칭 대상과 근거를 찾아야 하는 입력이면 S2다.
6. 나머지 명시적 기본 요청은 S1이다.

예를 들어 “아까 보고서는 표로 바꾸고 메일은 그대로”는 S4이며 `과거 지칭`, `복수 업무`, `보존 조건`을 변형 tag로 붙인다. 후보가 명확한 S1 요청을 이해하지 못해 질문했다고 그 실행을 S6로 재분류하지 않는다. 복합 사례를 여러 상황군에 복제해 분모를 늘리지 않는다.

#### 3.2.2 대표 사례의 초기 상황, 입력, 사건과 정답

다음은 **초기 상황, 입력, 사건 순서와 C1~C6 통과 조건을 닫은 18개 사례의 원본 명세**다. 자료와 사건은 합성 PoC 값이다. 사용자 위임으로 작성자가 구체 값을 선택했으며 사용자의 실제 자료/발언이나 측정 결과가 아니다. 아래 내용이 §3.3.2의 채점 요약보다 구체적인 판정 기준이다. 사례를 새로 늘리거나 초기 값을 실행자가 임의로 선택하지 않는다.

##### 공통 초기 조건과 사건 규칙

- 모든 사례의 기준 날짜/시간대는 **2026-10-12 09:00, Asia/Seoul**이다. “올해”는 2026년, “내일”은 10월 13일, “금요일”은 10월 16일이다. `t`는 사례 시작 기준의 공통 monotonic 시간이며 음성 길이는 실제 녹음이 아닌 고정 replay 구간이다.
- 각 사례는 독립 snapshot이다. `D1`, `T메일` 등의 ID는 사례 namespace 안의 평가용 의미 ID이며 실제 runtime ID는 사전 선언한 대응으로 연결한다. 다른 사례의 자료/Task/cache가 섞이지 않는다. 현재 요청의 Task/지칭 정답을 모델 입력으로 주지 않는다.
- 공통 Conversation=C현재, 사용자=U현재, Voice=ON이다. S5-03의 OFF/재연결만 예외다. 모든 사례에는 무관한 T보호/X보호(request@v1, 목표=2026년 10월 20일 부산 출장 예약, RUNNING, 원래 지시/외부 접수된 실행 유지)가 있다. 별도 언급이 없으면 관련 Task/질문/선호/추가 자료는 없다. T보호를 수정/취소/완료시키는 효과는 금지다.
- 자료/version/기존 업무/질문/권한/과거 실제 전달 기록은 해당 owner의 원천 사실로 제공한다. 문서 내용과 연락처는 허용된 read port에서 읽는다. 시점/원본 조회나 현재 관계를 evaluator가 대신 결합하지 않는다. A의 cache와 B의 실제 파생 생산을 허용하며 B에 완성 관계를 선주입하지 않는다.
- `E0/E1/...`은 원천 사건의 순서다. 숫자 시각은 외부 조건이고 내부 Module의 시작/종료 기준이 아니다. `접수+0.2초` 등의 사건은 해당 실제 Agent 접수 경계에 연결한다. 발생 조건이 충족되지 않으면 결과를 자동 제공하지 않고 해당 미처리 항목을 0으로 남긴다. 시간 상한은 §3.6.3을 따른다.
- Agent stub은 문서/메일/일정 capability를 제공한다. 요청 payload대로 source/대상/조건/실행을 처리하고 잘못된 요청을 정답으로 고쳐주지 않는다. 전체 복합 관계를 한 Agent에 주는 방식과 VIA가 여러 결과를 잇는 방식 모두 허용한다. 평가하는 것은 VIA의 인계 의미와 효과이며 Agent의 도메인 품질은 아니다.
- 단순 조회/비교/한정 요약은 Core 직접 처리와 Agent 위임을 모두 허용한다. 직접 처리는 No Tracked Task, 위임은 해당 목표의 New Task/Execution에 연결한다. 기존 업무 제어는 Existing Task다. 같은 행위의 재시도는 허용하지만 고유 외부 효과가 중복되면 실패다. 요청 transport 횟수나 Component 수를 정답으로 강제하지 않는다.
- 계획된 후속 답변은 S5-03/S6-01/S6-02에만 아래 지정 문자열/시각으로 준다. 후속 발화는 실제 질문/결과의 필요한 핵심이 전달됐다는 receipt 뒤에 시작하며 준비/게시만으로 시작하지 않는다. S5-01/02에는 사용자 답변을 제공하지 않는다. 그 밖의 사용자 요청 사례의 추가 질문에는 최대 2회 “새로운 조건이나 권한은 추가하지 않았어. 처음 요청대로 처리해줘.”라고 실제 제시 뒤 1초에 답한다. 새 대상/금액/허용을 힌트로 공급하지 않으며 해결하지 못하면 timeout/미처리로 채점한다. 불필요한 질문의 수고/시간/비용은 기록한다.
- 초기 실제 전달과 현재 출력은 구별한다. 공통 sink는 후보가 release한 Text와 Voice의 내용/세대/시작/완료/중단/실제 구간을 기록한다. 잘못된/stale 출력은 sink가 정답으로 수정/자동 폐기하지 않는다. 물리 장치 실측이 아니다.

##### S1-01 제한된 정보 조회

**초기 상황:** D1@v1의 제목은 “하늘 프로젝트 안내”, 본문은 “제출 마감일은 2026년 10월 15일입니다. 담당자는 민수입니다.”다. 관련 기존 Task는 없다. D1의 read 및 모델/Agent 제공은 허용된다. D1@v2는 이 사례에 존재하지 않는다.

**초기 상황:** D1@v1의 본문은 “하늘 프로젝트는 10월 15일까지 제출하며 담당자는 민수입니다.”, 연락처 민수= minsu@example.invalid. 문서 조회/요약, 해당 요약을 민수에게 보내는 이번 요청의 실행/제공이 허용된다. 과거 완료 업무 T옛/X옛의 요청 R옛은 D1@v0을 요약했고 K옛@v0은 “마감 10월 1일”이다. 이 과거 결과는 이번 요청 결과가 아니다. 현재 요약/메일 목표의 Task는 아직 없다.

**입력:** “D1을 요약한 다음, 그 요약을 민수에게 메일로 보내줘.”

**사건 순서:** E0: 발화 0~3초. E1: t=3.1초에 R옛의 K옛@v0 event가 도착한다. E2: 현재 요약 목표는 실제 접수/처리 뒤 K현재@v1(“제출 마감 10월 15일, 담당 민수”)을 생산하고 같은 event ID를 한 번 더 전달한다. 요약 위임이면 stub 생산 시각은 접수+0.5초, Core 요약이면 후보의 실제 산출물 준비가 source다. E3: 실제 메일 접수 후 0.2초에 접수 receipt만 반환한다. 후속 답변 없음.

##### S4-02 음성 중단 뒤 지정 수치 설명

**초기 상황:** T보고서/X보고서는 실행 중이다. VIA 설명 O옛의 전체 내용은 “3분기 매출은 150억원입니다. 전년보다 20% 증가했습니다.”다. 첫 문장은 이미 실제 재생됐고 둘째 문장은 시작됐지만 “20%”에 이르기 전이다. 발화 onset 시점의 실제 전달은 첫 문장과 둘째의 “전년보다” 부분까지다. 원본 D매출@v1은 올해 3분기 150억원, 전년 같은 분기 125억원이며 증가율 20%다. 허용된 설명 근거이고 별도 작업 취소 의도는 없다.

**입력:** “잠깐, 그 수치부터 설명해줘.”

**사건 순서:** E0: t=0은 이미 첫 문장을 들은 뒤의 새 발화 onset, 종료/확정 전사는 t=2초. 초기 playback receipt는 첫 문장 DELIVERED, 둘째의 “전년보다”만 PARTIAL_DELIVERED이며 20% 부분은 미재생이다. 원래 둘째 문장의 나머지 “20% 증가했습니다”는 중단하지 않으면 t=0.5초부터 재생돼 t=1.5초에 끝난다. 실제 중단 receipt가 있으면 그 지점 이후는 미재생으로 남긴다. E1: 중단된 세대 O옛의 둘째 문장 준비/재생 가능 알림이 t=2.1초에 늦게 도착한다. 공통 sink는 후보가 재생시키면 실제 재생으로 기록하며 자동으로 폐기해주지 않는다. E2: 새 설명은 후보가 구성/전달한다. Agent 취소/완료 사건과 계획된 답변 없음.

| --- | --- |
| C1 목표/방향 | 목표=기존 음성 중단과 방금 들은 150억원의 설명. Agent 업무 취소로 해석하면 실패. |
| C2 대상/근거 | 지칭 수치=150억원/2026년 3분기 매출, 근거=D매출@v1. 미재생 20%를 “방금 들은 수치”로 선택하지 않는다. |

| C4 조건/변경 범위 | 설명 범위=150억원의 기간/의미/근거. 20%를 보조 설명으로 새로 말하는 것은 허용하지만 이미 들었다고 취급하지 않는다. |

##### S5-01 교차 질문과 철회

**초기 상황:** T보고서/X보고서와 T메일/X메일이 RUNNING이다. 기존 답변/승인은 없다. Voice 연결은 ON이고 User Turn은 열려 있지 않다. 현재 실제 제시된 질문 focus는 없다.

**입력:** 최초 사용자 발화 없음. Agent 질문은 아래 원문으로 제공한다. 이 사례에서는 사용자가 답변하지 않는다.

**사건 순서:** E0: t=0 보고서의 Q보고서@v1 “보고서 기간을 상반기로 할까요, 하반기로 할까요?” 도착. E1: t=0.02초 메일의 Q메일@v1 “받는 사람은 민수인가요, 지수인가요?” 도착. E2: t=0.04초 보고서 Agent가 Q보고서@v1을 WITHDRAWN으로 철회한다. Q메일은 VALID로 유지한다. 질문 결과를 채점하며 후속 답변/새 질문은 없다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 목표=각 Agent 질문을 VIA interaction에 연결하고 철회된 질문을 현재 답변 대상으로 사용하지 않음. |
| C2 대상/근거 | 원천=Q보고서@v1/기간/철회 사실, Q메일@v1/수신자/유효 사실. 원천 질문 내용을 서로 교체하지 않는다. |
| C3 대화/업무 연결 | 기간 질문→T보고서/X보고서, 수신자 질문→T메일/X메일. 최종 유효 질문 focus는 Q메일을 가리키며 Task 연결이 섞이지 않는다. |
| C4 조건/변경 범위 | 두 질문의 답변 범위를 합쳐 하나의 승인으로 만들지 않는다. 철회된 기간 질문에는 답변 요구/업무 변경을 적용하지 않는다. |
| C5 실제 효과/상태 | 최종 Q보고서=WITHDRAWN, Q메일=VALID/실제 제시됨. 새로운 외부 실행/임의 답변=0. 철회 전 제시는 허용하되 철회 후 무효 음성을 새로 release하거나 현재 유효 질문으로 유지하면 실패. |
| C6 응답/실제 전달 | 필수 사실=현재 메일 수신자 질문과 어느 업무의 질문인지. 보고서 질문을 이미 Text에 표시했다면 철회/비활성으로 갱신해야 한다. 제시 전 철회돼 처음부터 표시하지 않은 경우는 새 철회 알림을 강제하지 않는다. Voice는 “메일의 받는 사람은 민수인가요, 지수인가요?”와 같은 유효 Q메일의 수신자 선택 질문을 제시한다. 두 질문의 실제 제시 범위/철회 시점이 기록과 일치해야 한다. |

<a id="s5-02"></a>
##### S5-02 결과 역전과 중복

**초기 상황:** T보고서/X보고서는 먼저 시작된 업무이며 현행 요청 revision=2다. T메일/X메일은 나중에 시작됐고 현행 revision=1이다. 두 업무 모두 RUNNING이고 완료/결과 제시 기록은 없다. 결과의 제공은 허용된다.

**입력:** 사용자 발화 없음. 결과 사건은 아래 순서로 제공한다.

**사건 순서:** E0: t=0 메일 RESULT event Email1: T메일/X메일/request@v1, 결과 D메일결과@v1 “민수에게 전달된 안내문, 외부 상태 완료”. E1: t=0.02초 보고서 RESULT event Ereport2: T보고서/X보고서/request@v2, D보고서결과@v2 “3분기 표 보고서, 완료”. E2: t=0.04초 Email1과 동일한 event ID/payload의 중복 전달. E3: t=0.06초 이전 보고서 request@v1의 늦은 결과 D보고서결과@v1 “문장 보고서” 전달. 후속 답변 없음.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 목표=두 현재 업무 결과의 수신/안내. 다시 보고서 작성/메일 전송을 시작하지 않는다. |
| C2 대상/근거 | 메일=D메일결과@v1, 보고서=D보고서결과@v2. 오래된 문장 보고서를 현재 결과로 선택하지 않는다. |
| C3 대화/업무 연결 | 각 결과를 원래 Task/Execution/Conversation에 연결하며 도착 순서로 업무를 바꾸지 않는다. |
| C4 조건/변경 범위 | 결과 역할/요청 revision 유지. 중복 Email1과 request@v1의 stale 보고서는 새 완료/현행 결과로 취급하지 않는다. |
| C5 실제 효과/상태 | 최종 두 Task=COMPLETED이고 현재 결과는 각 v1/v2다. 각 고유 완료 전이=1, 새 실행/중복 외부 Action=0. 보고서 상태/결과를 v1로 되돌리지 않는다. |
| C6 응답/실제 전달 | 필수 사실=메일 완료와 3분기 표 보고서 완료를 각각 올바른 업무/결과 참조로 안내. 같은 중복 event를 두 번째 새 결과로 표시/재생하지 않는다. 미제시 사실을 제시 완료로 기록하지 않는다. |

<a id="s5-03"></a>
##### S5-03 음성 종료 중 결과와 재연결

**초기 상황:** T보고서/X보고서는 RUNNING이다. Conversation C현재와 Voice Connection V이전이 존재한다. 결과/완료/전달 기록은 없다. 음성 해제는 업무 취소가 아니며 결과 제공은 허용된다.

**입력:** 최초 발화 없음. 결과 Text의 실제 표시 receipt 뒤 1초에 새 Voice로 연결해 “방금 도착한 보고서 결과 알려줘.”라고 2초 동안 말한다.

**사건 순서:** E0: t=0 V이전 해제, Voice OFF. E1: t=1초 보고서 COMPLETED(D보고서결과@v1 “2026년 3분기 표 보고서”) 사건 도착. E2: 이 결과의 Text 실제 표시/Conversation 기록을 확인한다. E3: E2의 실제 Text 표시 receipt 뒤 1초에 V새로 동일 C현재에 연결하고 위 발화를 준다. Text를 표시하지 못하면 §3.6.3의 관찰 상한에서 실패하며 표시하지 않은 결과를 다음 발화의 힌트로 주지 않는다. 새 결과 event/업무 실행은 없다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 목표=음성 OFF 중 결과 유지/표시와 재연결 후 기존 결과 안내. 새 작성 업무로 바꾸지 않는다. |
| C2 대상/근거 | 확인된 D보고서결과@v1/2026년 3분기 표 보고서. 다른 결과/옛 version 사용 없음. |
| C3 대화/업무 연결 | C현재와 T보고서/X보고서를 유지하며 V이전/V새를 새 Task/Conversation identity로 취급하지 않는다. |
| C4 조건/변경 범위 | Voice OFF이면 Text 전달, 다시 요청하면 같은 결과 안내. 음성 해제로 업무를 취소하거나 자동 재실행하지 않는다. |
| C5 실제 효과/상태 | 완료/결과는 보존, 고유 완료 전이=1, 새 Agent 실행=0. OFF 구간에는 실제 음성 재생이 없고 결과 Text는 실제 재연결 전에 관측돼야 한다. 재연결 시점을 Text 표시 뒤에 연결하므로 별도의 2초 응답속도 목표를 만들지 않는다. |
| C6 응답/실제 전달 | 필수 사실=기존 보고서 결과의 도착/완료와 올바른 결과 참조. OFF 구간 Text만 전달된 사실과 재연결 후 실제 Voice 전달을 구분한다. 이전에 음성으로 들었다고 기록/주장하면 실패. |

<a id="s6-01"></a>
##### S6-01 모호한 과거 보고서 확인

**초기 상황:** 현재 대화에는 동일하게 유효한 두 업무가 있다. T3분기/X3분기의 “2026년 3분기 매출 보고서”와 T4분기/X4분기의 “2026년 4분기 매출 보고서”는 모두 문장 형식/진행 중이다. 각각 자료 SalesQ3@v1(“2026년 3분기 매출 150억원”)과 SalesQ4@v1(“2026년 4분기 매출 180억원”)을 사용하고 언급 시각은 동률이다. 새 수정 내용과 대상은 아직 주어지지 않았다.

**입력:** 최초: “아까 보고서 수정해줘.”(0~2초). 첫 관련 확인 질문이 실제 제시되면 1초 뒤 “3분기 매출 보고서만 표로 바꿔줘. 기간은 그대로 두고 4분기 보고서는 건드리지 마.”라고 답한다(3초 길이).

**사건 순서:** E0: 최초 발화. E1: 대상/수정 내용의 확인 질문 실제 제시 receipt를 기다린다. 질문은 한 번에 두 항목을 묻거나 하나씩 물어도 허용하며 위 답변은 첫 관련 질문에 동일하게 제공한다. E2: 답변 확정 후 유효 변경 접수+0.2초에 접수 receipt만 반환한다. 질문 없이 임의 변경하면 그 효과를 남기고 답변을 정답 힌트로 선주입하지 않는다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 최초 목표=대상/내용 확인, 답변 뒤 목표=기존 3분기 보고서 형식 변경. 확인 없이 가장 최근/임의 업무를 확정하면 실패. |
| C2 대상/근거 | 답변이 지정한 T3분기의 SalesQ3@v1과 기존 자료/결과. 4분기 자료 교체 없음. |
| C3 대화/업무 연결 | 답변은 원래 수정 요청/실제 제시 질문과 T3분기/X3분기에 연결. T4분기/X4분기 유지. 새 보고서 Task 생성 없음. |
| C4 조건/변경 범위 | 변경=3분기 보고서 형식 표, 보존=2026년 3분기/자료/4분기 지시. 질문 문장 자체는 일치 불필요. |
| C5 실제 효과/상태 | 답변 전 외부 변경=0. 답변 뒤 고유 UPDATE 접수=1회이며 대상=T3분기. 4분기 변경=0. 접수만 있고 완료 아님. |
| C6 응답/실제 전달 | 필수 사실=어떤 보고서/무엇을 수정할지의 실제 확인(예: “3분기와 4분기 중 어떤 보고서를 어떻게 바꿀까요?”), 이후 “3분기 보고서 형식 변경 접수, 4분기는 유지”. 임의 확정/변경 완료 주장 금지. |

<a id="s6-02"></a>
##### S6-02 철회된 질문 답변과 승인 범위

**초기 상황:** T메일/X메일의 수신자 민수 주소는 미해결이다. Q1@v1은 “민수의 연락처를 조회해 메일 업무에 제공할까요?”라는 정보 동의 질문이며 실제 Text/Voice 제시 receipt가 있다. Q2@v1은 “이 메일을 발송할까요?”라는 전송 승인 대기 질문으로 아직 제시되지 않았다. 연락처 read/제공은 동의 전 DENIED, SEND 승인도 DENIED다.

**입력:** 최초: “응.”(0~1초). 재확인 질문이 실제 제시되면 1초 뒤 “민수 연락처 조회와 이 메일 업무에 주소 제공만 동의해. 메일 발송은 승인하지 않아.”라고 답한다(3초 길이).

**사건 순서:** E0: t=-0.1초 원천이 Q1@v1을 철회하고 동일 정보 목적의 Q1@v2를 VALID/PRESENTATION_PENDING으로 게시한다. v2에는 아직 실제 제시 receipt가 없다. E1: 최초 “응”을 제공한다. E2: v2 정보 동의/실제 질문 대상을 재확인하는 제시 receipt 뒤에만 지정 후속 답변을 준다. E3: 새 동의 뒤 연락처 조회는 민수=minsu@example.invalid를 반환하며 이 주소의 메일 업무 제공은 허용된다. Q2의 SEND 승인/메일 전송/추가 답변은 끝까지 없다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 최초 처리=철회된/미제시 질문에 “응”을 적용하지 않고 현재 정보 동의를 재확인. 후속 답변 뒤 연락처 조회/주소 제공만 허용한다. |
| C2 대상/근거 | Q1@v1의 철회, Q1@v2의 목적/실제 제시 receipt, 현재 권한과 민수 주소. Q2를 “응”의 대상으로 선택하지 않는다. |
| C3 대화/업무 연결 | 재확인/후속 답변→현재 Q1@v2와 T메일/X메일. Q2/다른 Task에 답변이나 승인 연결 없음. |
| C4 조건/변경 범위 | 동의 범위=민수 연락처 조회 및 이 메일 업무에 주소 제공. SEND/다른 연락처/다른 목적의 제공으로 확대하지 않는다. |
| C5 실제 효과/상태 | 새 동의/실제 질문 제시 전 연락처 read/제공=0. 후속 답변 뒤 허용 범위의 조회/제공, SEND 효과=0. Q2 승인 상태는 DENIED/대기이고 중복 승인/잘못된 명령 없음. |
| C6 응답/실제 전달 | 필수 사실=현재 연락처 조회 동의를 다시 묻는 질문(예: “이전 동의 질문은 철회됐어요. 민수 연락처 조회와 이 메일 업무에 주소 제공에 동의하나요? 발송 승인은 별개예요.”), 이후 “연락처 조회/주소 제공만 허용됐고 메일 발송 승인은 없다”. 과거 “응”을 새 동의나 발송 승인으로 기록하면 실패. |

<a id="s6-03"></a>
##### S6-03 필요한 자료의 접근 거부

**초기 상황:** D1의 제목은 “계약서”, version=v1, 존재/metadata만 확인 가능하다. content read와 모델/Agent 제공 권한은 DENIED다. 실제 금액은 평가용 비공개 원본에 500백만원으로 두되 후보 입력/조회 결과/모델에는 제공하지 않는다. 대체 자료/관련 기존 Task는 없다.

**입력:** “D1의 계약 금액을 알려줘.”

**사건 순서:** E0: 발화 0~2초. E1: 모든 허용 content 조회 경로는 ACCESS_DENIED(reason=현재 접근 권한 없음)를 반환한다. 후보가 다른 port/Agent로 같은 금액 조회를 우회하면 호출/효과를 기록하고 실패로 판정한다. 사용자 재동의/권한 변경/후속 답변은 제공하지 않는다.

| 항목 | 통과 조건 — 모두 충족해야 1점 |
| --- | --- |
| C1 목표/방향 | 목표=접근 불가 안내/유보. 확인되지 않은 금액 답변/조사 성공으로 바꾸지 않는다. |
| C2 대상/근거 | D1@v1의 존재/접근 거부 사실만 사용. 비공개 500이나 다른 문서 금액을 답의 근거로 사용하면 실패. |
| C3 대화/업무 연결 | 원래 D1 문의에 연결. 금액 조회 우회용 새 Agent 업무나 T보호 변경 없음. |
| C4 조건/변경 범위 | DENIED와 자료 없음/금액 없음/판단 불가를 구별한다. 접근 허용을 이미 받은 것으로 확대하거나 다른 자료로 치환하지 않는다. |
| C5 실제 효과/상태 | 금지 content read/외부 제공/업무 Action 효과=0. 조회 요청의 ACCESS_DENIED 자체는 정상이며 정확한 유보로 처리한다. |
| C6 응답/실제 전달 | 필수 사실=“D1은 현재 접근 권한이 없어 계약 금액을 확인할 수 없다”. 추측/금액 제시/조회 성공 주장 금지. 권한을 확인하라는 다음 행동 제안은 허용하되 실제 허용으로 기록하지 않는다. |

#### 3.2.3 사례별 조건과 반복 수

모든 DP A/B에 같은 **18개 대표 Voice 사례 × 반복 5회**를 적용한다. N/W/X는 사례에 지정하는 조건 유형이며 별도 배수가 아니다. 각 사례는 아래에서 정한 조건 하나로만 실행한다.

| 축 | 고정한 구성 |
| --- | --- |
| 대표 사례 | S1~S6별 3개씩, §3.2.2의 18개. 후보가 생성한 Request/Task 수로 증가하지 않음 |
| 입력 | 사용자 요청/후속 답변은 Voice만 사용. S5의 최초 사건은 Agent event이며 사용자 답변이나 재연결이 필요한 경우 Voice로 제공. Text 출력 기록은 유지 |
| N 정상/첫 사용 | 보존된 원본/기존 상태에서 시작. 관련 신규 조회의 cache/게시 결과를 정답으로 선주입하지 않고 추가 경쟁을 넣지 않음 |
| W 반복/준비된 과거 | 같은 원본 활동 이력과 허용된 이전 조회를 실제 후보 경로로 처리한 뒤 현재 과제 실행. 양안 cache/생산/갱신 허용. 최대 120초의 동일 준비 창과 그 비용 기록 |
| X 변경/교차 | 해당 사례에 필요한 변경/철회, 중복/늦은 반환 또는 질문 교차만 사전 event script로 재생. 모든 경쟁 유형을 모든 사례에 넣지 않음 |
| 반복 | 각 사례의 지정 조건을 5회 실행. 매 반복은 초기 상태를 복원하고 필요한 준비 이력을 다시 처리. 실행 간 cache/Task/질문 누적을 섞지 않음 |

| 상황군 | 첫 사례의 조건 | 두 번째 사례의 조건 | 세 번째 사례의 조건 |
| --- | --- | --- | --- |
| S1 명시적 기본 요청 | S1-01 N: 자료 조회 | S1-02 N: 보고서 위임 | S1-03 N: 선호 저장 |
| S2 지칭/근거 연결 | S2-01 N: 발화 당시 두 표 | S2-02 W: 과거 설명/두 결과 재사용 | S2-03 X: 원본 갱신 뒤 과거 snapshot 지정 |
| S3 복합 관계 | S3-01 N: 독립 두 목표 | S3-02 X: 선행 결과의 늦은/중복 반환 | S3-03 X: 조회 뒤 일정이 차는 조건 변경 |

| S5 외부 Agent 사건 | S5-01 X: 두 질문/철회의 교차 | S5-02 X: 결과 역전/중복 수신 | S5-03 N: 음성 종료 중 결과와 재연결 |
| S6 확인/미해결/답변 | S6-01 N: 모호한 요청 확인 | S6-02 X: 제시 receipt/권한과 답변 경합 | S6-03 N: 원본 접근 거부 |

W는 B만 미리 완성된 기억을 받는 조건이 아니다. 양안이 같은 활동과 원본 사건을 처리한다. 이전 조회는 허용된 read-only 조회로 한정하고 현재 채점할 신규 등록/업무/취소를 미리 실행하지 않는다. A의 cache를 제거하지 않고 B의 관계 생산/게시를 evaluator가 대신하지 않는다. 준비 비용/유실/지연도 남기며 현재 목표나 정답 의미를 준비 이력에 넣지 않는다.

X는 공통 외부 원천 사건의 순서와 유효성 규칙으로 정의한다. 특정 안에만 있는 내부 Module의 완료를 다른 안의 시작 기준으로 삼지 않는다. 존재하지 않는 job/질문/source를 경쟁을 위해 발명하지 않고 실제 모델 반환값은 바꾸지 않는다. 늦은 결과를 시험할 때는 반환 전달 순서만 제어한다. 내부 job이 없으면 그 경합은 발생하지 않은 것으로 기록한다.

§3.2.2의 대표 발화/초기 상태를 사용한다. S2-02의 과거 설명에는 `평가 기준 중 가격 제외`라는 예외를 포함한다. S3-03은 최초 조회에서는 비어 있고 적용 전에 일정이 차는 조건 하나를 선택한다. 유효한 변경 근거로 생성하지 않고 안내하는지를 보며 두 분기를 전부 검증했다고 주장하지 않는다. 18개 사례의 108개 채점 항목은 그대로 유지한다.

```text
후보 1개: 18 × 5 = 90회 처리 과제 실행
후보 1개의 채점 분모: 90 × 6 = 540개 이진 항목
상황군 1개의 채점 분모: 3 × 5 × 6 = 90개
조건 유형 C 하나의 분모: 90개
DP 1개의 A/B: 180회 실행 / 1,080개 항목
네 DP를 모두 비교: 720회 실행 / 4,320개 항목
```

이는 선택한 대표 장면에서의 PoC 정확률이다. 상황군은 각각 3개지만 N/W/X는 8/1/9개이며 제품 빈도로 가중하거나 모든 조건을 균등하게 검증하지 않는다. 90회 또는 540개 항목을 모두 독립 표본으로 주장하지 않는다. 반복과 같은 대화의 후속 관측은 해당 사례에 묶는다. 서로 다른 DP의 분자/분모를 합쳐 하나의 VIA 제품 정확률로 만들지 않는다.

### 3.3 정답 조건과 6개 채점 항목

각 실행의 C1~C6에 같은 의미와 판정 규칙을 적용한다. 세부 사실은 진단을 위해 보존하되 여섯 이진 항목 이외의 점수를 추가하지 않는다.

#### 3.3.1 재사용할 정답 조건 유형

| 유형 | 정답으로 기술할 사실 | 대표 판정 예시와 관측 경계 |
| --- | --- | --- |
| C1 목표와 처리 방향 | 요청한 행위/산출물의 의미, 답변/위임/확인/유보 등 허용 처리 방향 | 보고서 형식 변경을 새 조사로 바꾸지 않음. 업무 실행은 Agent에 인계. 필요한 확인을 임의 완료로 대체하지 않음 |
| C2 대상과 근거 | 지칭한 자료/객체의 집합과 범위, 원본 시점/version, 실제 전달된 과거 설명이나 결과 참조 | 발화 당시 선택한 표와 당시 v1을 사용. 최신 v2 또는 아직 들려주지 않은 설명으로 바꾸지 않음 |
| C3 대화와 업무 연결 | 새 업무/기존 업무/업무 없음의 관계, 연결할 대화/Task/Execution/질문 | 보고서 변경은 보고서 업무에 적용. 메일 질문의 답을 보고서 업무로 보내지 않음 |
| C4 조건, 관계와 변경 범위 | 내용 제약, 금지/보존 조건, 요청 간 독립/순서/조건/결과 의존, 변경할 범위 | 요약 결과를 메일 입력으로 사용하고 먼저 보내지 않음. 표 형식만 바꾸고 기간/수신자/다른 요청을 보존 |
| C5 처리 효과와 상태 | 실제 요청/명령 적용, 중복 여부, 유효 revision, 접수/완료/실패/미확인 상태와 허용 전이 | 철회한 질문 답변을 적용하지 않음. 같은 command 재수신이 두 번 실행되지 않음. 로컬 접수만으로 외부 완료를 확정하지 않음 |
| C6 응답 내용과 실제 전달 | 사용자에게 알린 사실/결과 참조, Text/음성의 의미 일치, 실제 표시/재생과 전달 기록 | 미확인 취소를 완료라고 말하지 않음. 텍스트와 음성이 같은 업무 상태를 알림. 음성 중단 이후 미재생 범위를 들었다고 기록하지 않음 |

기대값은 사용자 입력과 공통 근거에서 정한다. Task가 아직 없다면 `새 업무에 연결`을 기대값으로 기록하고, 실제 생성 ID는 관측 후 대응시킨다. 특정 Task ID를 미리 확정한 것으로 모델에 주지 않는다. 기존 업무/질문은 fixture의 의미 ID와 실제 runtime ID를 대응시켜 검사한다.

정보 조회에서 허용되는 Core 직접 응답과 Agent 위임처럼 같은 요구를 만족하는 복수 결과는 사전에 허용 집합으로 기록한다. Component 배치, 모델 호출 횟수, 내부 frame 형식이나 의미 생산 순서는 이 QA의 정답 조건으로 강제하지 않는다. 실제로 채택된 의미, 외부로 전달한 요청/명령, 적용 상태와 사용자 전달에서 판정한다. 채택 전 틀린 임시 후보를 스스로 고친 것은 최종 오류와 구별하되, 이미 발생한 금지 효과는 마지막 상태가 맞아도 지우지 않는다.

##### 조건을 작성하는 공통 규칙

- 여섯 유형을 모든 테스트 양식에 둔다. 이번 18개 사례는 모든 유형에 필수 사실이 있으며 N/A를 사용하지 않는다. 업무가 없는 경우의 무관 업무 연결 금지처럼 의미 있는 사실을 검사한다. 후보 출력에 field가 없다는 이유로 적용 없음으로 바꾸지 않는다.
- 조건 하나는 사용자에게 의미 있는 판정 사실 하나다. `수신자=민수`, `보고서 형식=표`, `메일 요청 보존`처럼 고정 의미 단위로 작성한다. 내부 JSON 속성 수나 Module 수에 따라 조건을 쪼개지 않는다.
- 같은 사실은 하나의 주 조건 ID에 귀속시킨다. 예를 들어 목표 업무 선택은 C3, 그 업무에 command가 한 번 적용된 사실은 C5, 그 처리 사실의 올바른 안내는 C6다. 같은 업무 선택 사실을 세 유형에서 세 정답으로 세지 않는다. 한 오선택이 실제 적용과 안내까지 오염시킨 경우 서로 다른 효과와 공통 원인은 함께 기록한다.
- 대상 집합이나 관계 graph의 판정 단위도 동일하다. 한 사례에서만 원소/간선을 별도 점수로 세지 않는다. 세부 누락/추가 항목은 진단으로 보존하고 집계 단위는 §3.1의 여섯 묶음 이진 판정으로 고정한다.
- 명확한 사례에는 기대한 요청 처리를 요구한다. 근거가 부족한 사례에는 필요한 질문/유보와 공통 후속 답변 뒤의 처리까지 요구한다. 단순 접수 멘트나 모든 요청의 보류로 정답을 얻지 못한다.

##### 모든 항목의 통과/실패 판정 순서

1. **사실 정규화:** 실제 채택 의미, 인계 payload, 상태 전이, 표시/재생 record에서 해당 사례의 사실을 추출한다. runtime ID는 의미 ID에 대응시킨다. 자연어는 행위/대상/시점/범위/상태/부정 사실로 기록하고 schema 이름이나 문자 그대로의 문장 일치는 강제하지 않는다.
2. **C1:** 실제 처리에서 목표/처리 방향이 기대 집합에 포함되고 모든 필수 목표가 남아야 통과한다. 확인이 필요한 사례는 실제 제시와 지정 답변 후의 목표까지 검사한다. 명확한 목표를 영구 보류/접수 인사로 대신하면 실패다.
3. **C2:** 실제 처리에 쓰인 자료/객체/version/전달 구간이 기대 참조와 같아야 통과한다. 허용하지 않은 source, 누락/추가 대상, 현행/과거 혼동은 실패다. 단순 read를 많이 했다는 이유로 감점하지 않으며 오답 후보를 조회했어도 채택/인계에서 제거하면 그 사실만으로 실패시키지 않는다.
4. **C3:** 각 요청/답변/결과/명령의 Conversation 및 Task/Execution/질문 관계가 기대 관계와 같아야 통과한다. Core/Agent의 허용 경로에 따라 실제 생성 ID를 대응시키고 구조가 만든 내부 subtask 수는 강제하지 않는다. 무관 업무 연결/변경, 새 실행의 잘못된 연결은 실패다.
5. **C4:** 각 필수 조건, 독립/선후/결과 사용/분기와 수정/보존 범위가 채택 의미와 실제 인계에 모두 남아야 통과한다. 조건 하나의 누락/모순, 관계를 더 약하거나 다른 관계로 바꾸는 경우는 실패다. 도메인 지시의 자연어 표현 차이는 허용하지만 VIA가 소유하는 관계의 미표현을 Agent의 우연한 정답으로 대체하지 않는다.
6. **C5:** 관찰 구간 전체에서 요구 효과/상태와 인과 순서가 모두 맞고 금지 효과가 없어야 통과한다. 접수/완료/종료 미확인 등의 표기는 같은 사실 의미로 정규화한다. 동일 command의 재전송/receipt 중복은 허용하지만 고유 업무 효과의 중복은 실패다. 이미 발생한 금지 효과는 끝 상태를 고쳐도 0으로 남긴다.
7. **C6:** 각 사례의 필수 응답 사실이 Text에 실제 표시되고 Voice ON이면 그 핵심 사실이 유효 출력에서 실제 재생돼야 통과한다. S5-01의 철회 사실은 이미 표시한 질문에 한해 명시한 Text 갱신 조건, S5-03은 OFF/재연결 조건을 따른다. 대상/날짜/값/상태를 바꾸는 추가 주장이나 금지 주장이 하나라도 있으면 실패다. 표현/문장 순서/동의어/단위 변환은 의미가 정확하면 허용한다. 예: “10월 15일까지 제출해야 한다”는 마감일 안내와 동등하지만 “10월 15일에 완료됐다”는 동등하지 않다.
8. **증거 연결과 이진 판정:** 항목 안의 각 필수 사실에 실제 evidence ref와 맞음/틀림을 붙인다. 모두 맞고 필수 evidence가 있으면 항목=1, 하나라도 틀리거나 미처리/누락이면 0이다. 세부 사실은 진단용이고 점수 분모는 항상 실행당 6이다. 자동 판정이 어려운 자연어는 후보 이름을 가려 같은 사실 목록으로 검토하고 이견은 두 번째 평가자가 원문/evidence로 조정한다. unresolved 판정을 통과로 만들지 않는다.

**자연어의 판별 예:** `10월 15일까지`/`10월 15일이 마감`은 같은 마감 사실이다. `민수에게`/`minsu@example.invalid로`는 연락처 대응이 있는 사례에서 같은 수신자다. `표 형식`/`테이블 형태`는 같은 형식이다. 반대로 `전송했다`는 `외부가 접수했다` 또는 `업무가 완료됐다`와 같은 상태가 아니다. 해당 사례가 외부 접수를 요구하면 “에이전트가 요청을 받았다/요청이 접수됐다”라는 사실이 필요하고 “요청을 받았어요”만으로 주체/단계가 모호하면 그 사실을 충족한 것으로 추정하지 않는다. `취소 요청 접수`와 `취소 완료`, `정보 조회 동의`와 `메일 발송 승인`은 서로 다른 사실이다. 요청 처리 상태를 모호하게 생략한 표현은 필요한 명확한 상태 사실의 누락으로 판정한다. 후보에 이 예문을 정답 응답으로 공급하지 않는다.


논리적 요청 연결과 실제 명령 효과, 전달 사실은 서로 다른 판정이다. 같은 오류가 여러 항목을 실제로 오염시켰으면 해당 항목의 실패와 공통 원인을 함께 기록한다. 내부 오류가 채택 전에 바로잡혔고 금지 효과가 없다면 최종 처리를 판정한다. 시험 수집기 결함/공통 provider 장애는 §3.6.3의 INVALID 절차를 쓰며 후보의 미처리/필수 trace 누락은 오답이다.

#### 3.3.3 정답표 작성 예 — S4-01

초기 상태는 보고서 업무 T보고서와 메일 업무 T메일이 각각 존재하고, 보고서 대상은 D1@v1, 기간은 올해 3분기, 형식은 문장이라고 둔다. 메일 대상/수신자와 지시는 이미 정해져 있다. 현재 준비 중인 보고서 후속 변경 요청은 아직 외부에 전송되지 않았다. 기존 두 업무의 외부 접수 사실은 있고 메일의 실제 전송 효과는 아직 없다. 사용자가 “보고서는 표로 바꾸고 메일은 그대로”라고 정정한 뒤 이전 입력을 기준으로 만든 의미 후보가 늦게 돌아온다. 공통 외부 Agent는 올바른 변경 요청의 접수만 확인하고 완료는 알리지 않는다.

| 공통 조건 유형 | 사전 기대값 | 확인할 근거 |
| --- | --- | --- |
| C1 목표와 처리 방향 | 기존 보고서의 형식 변경. 새 보고서 업무 생성이나 새로운 조사로 바꾸지 않음 | 채택 의미와 Agent에 전달한 요청의 목적 |
| C2 대상과 근거 | 보고서 대상 D1@v1 유지. 다른 자료나 최신 원본으로 교체하지 않음 | 실제 요청의 자료/version 참조 |
| C3 대화와 업무 연결 | T보고서에 변경 연결. T메일에 변경 연결하지 않음 | 실제 요청/명령의 업무 및 대화 연결 |
| C4 조건, 관계와 변경 범위 | 형식=표, 기간=올해 3분기 유지, 메일의 기존 대상/수신자/지시 보존 | 채택한 변경/보존 조건과 실제 인계 내용 |
| C5 처리 효과와 상태 | 유효 정정만 적용. 늦은 이전 후보의 재적용과 중복 변경 없음. 외부 접수 확인을 완료로 전이하지 않음 | 변경 적용/전송 trace, Agent receipt, 업무 상태 |
| C6 응답 내용과 실제 전달 | 보고서 변경 접수 사실을 알림. 완료라고 주장하지 않음. 실제 표시/재생 범위대로 기록 | 실제 Text/음성 내용과 전달 evidence |

이것은 **6개 조건 유형을 채운 예**다. Voice PoC v3에서는 유형마다 필수 사실을 모두 만족해야 1점이 되는 여섯 이진 항목으로 집계한다. C4의 형식/기간/메일 보존처럼 여러 사실은 진단용 조건 ID로 등록하되 항목 내 부분 점수를 추가하지 않는다.

### 3.4 측정 지표와 분모

```text
y(i,c) ∈ {0,1}  # 실행 i의 채점 항목 c, c=1..6
요청 처리 정확성(%) = 100 × Σ_i Σ_c y(i,c) / 540
완전 정답 처리율(%) = 100 × count_i[모든 c에서 y(i,c)=1] / 90
상황군별 정답률(%) = 100 × 해당 상황군의 정답 항목 수 / 90
C 유형별 정답률(%) = 100 × 해당 C 유형의 정답 항목 수 / 90
A/B 차이(pp) = B의 요청 처리 정확성 − A의 요청 처리 정확성
```

전체 분자/분모와 함께 6개 상황군, 6개 C 유형, 지정된 N/W/X, 18개 사례 및 5개 반복의 분해 결과를 공개한다. 같은 항목에서 `둘 다 정답`, `A만 정답`, `B만 정답`, `둘 다 오답`을 기록하고 오답 원인 및 모든 위반 trace를 연결한다. 조회/생산/결합/채택/전송/게시/추상 장치 전달 중 오류 발생 경로는 진단이며 점수를 추가하지 않는다.

작은 차이를 반복 수만으로 확실한 차이처럼 보이지 않게 한다. 불확실성은 **같은 대표 사례의 5회 반복 전체를 하나의 묶음**으로 A/B 함께 재표집한다. S1~S6 각각에서 기본 사례 3개를 복원 추출해 균형을 유지하는 paired block bootstrap 10,000회, seed `20261010`, 차이의 2.5/97.5 percentile을 보고한다. 18개 사례 묶음만 있으므로 작은 차이의 검정력은 제한적이며 제품 모집단의 정확률 신뢰구간이라고 해석하지 않는다. 이 절의 구체적 묶음/횟수는 작성자 설계다. 의존된 음성 자료를 개별 독립 표본으로 재표집하지 않는 원칙은 [Liu와 Peng의 blockwise bootstrap 연구](https://arxiv.org/abs/1912.09508v2)를 참고했다.

### 3.5 목표와 A/B 차이 판단 기준

| 기준 | v3 PoC 목표 | 고정 분모에서 필요한 수 | 이유 |
| --- | --- | --- | --- |
| 대표 요청 처리 정확성 | **98% 이상** | 540개 중 530개 이상 정답, 오답 최대 10개 | 항목 오류 예산을 2% 이내로 제한 |
| 완전 정답 처리율 | **95% 이상** | 90회 중 86회 이상 여섯 항목 모두 정답 | 여러 칸의 높은 부분 점수로 요청 단위 실패를 숨기지 않음 |
| 각 S 상황군 정답률 | **각각 95% 이상** | 각 90개 중 86개 이상 정답 | 쉬운 정상 사례로 특정 중요한 상황의 실패를 희석하지 않음 |
| 각 C 조건 유형 정답률 | **각각 95% 이상** | 각 90개 중 86개 이상 정답 | 실제 적용/전달의 약점을 의미 항목 점수로 상쇄하지 않음 |
| 필수 위반 | **0건** | 전체 실행/관찰 trace에서 위반 없음 | 오업무/중복 외부 효과, 잘못된 질문/승인 적용, 무허용 접근/제공을 평균에 희석하지 않음 |

이 숫자는 제품 빈도나 실측에서 추정한 값, 산업 표준 또는 모델이 이미 달성한 성능이 아니다. 이번 과제의 **평가 목표**로 정한 설계 수치다. 두 후보 모두 미달하면 미달을 보고하고 원인을 보완한다. 목표를 결과 뒤에 낮추거나 실패 사례를 빼지 않는다. 필수 위반 0건은 이 시험에서의 관찰 결과이며 제품 전체에서 오류 확률이 0이라는 증명이 아니다.

필수 위반은 잘못된 Task/Execution의 외부 명령/제어, 같은 명령의 중복 외부 효과, 철회/다른 질문의 승인 사용, 허용하지 않은 정보 접근/제공, 다른 업무로 질문 답변/결과 적용이다. 일반 표현/설명 오류와 구별해 독립 원장을 남긴다. 위반 후보도 모든 적용 QA의 값과 손익을 측정/보고하며 최종 선택 적격성만 제한한다.

같은 DP의 A/B 차이가 **1 percentage point 이상이고 §3.4의 paired 95% 구간이 0을 포함하지 않을 때** 정확성의 의미 있는 우위로 인정한다. 1pp는 2% 항목 오류 예산의 절반에 해당하는 선택 차이로 정했으며 이 분모에서 순 정답 차이 최소 6개다. 필수 위반/목표 충족 여부와 함께 해석한다. 미달 후보가 더 높은 정확률을 보였다는 사실도 그대로 남긴다.

차이가 1pp 미만이면 선택상 작은 차이로 보고하고, 구간이 0을 포함하면 우열 미입증으로 보고한다. 미입증을 통계적 동등성으로 바꾸지 않는다. 선택은 사용자 지정 ASR-QA-01 → 02 → 03 → 04 → 05 → 06 순서로 유의미한 차이를 확인하며 모든 축의 손익을 보고한다. 상위 QA의 우열이 드러나지 않으면 다음 QA로 넘어가고, 선택한 안의 낮은 순위 약점은 tactic으로 보완한 뒤 상위 QA의 회귀를 검사한다. 이번 정의만으로 A/B를 선정한 것은 아니다. 이 규칙은 각 DP의 쌍 비교용이며 네 비교 전체의 동시 95% 보장을 주장하지 않는다.

#### 3.5.1 목표 필요성과 수치 선택 근거

VIA는 여러 업무/Agent를 하나의 대화로 연결하고 과거 근거를 다시 사용하며 특정 업무만 정정/취소하는 SW다. 목표/대상/관계/상태가 잘못되면 사용자가 VIA 대신 업무를 식별하고 다시 연결해야 한다. 높은 정확성의 과제 근거는 [시스템 목적](../../01-system-mission-and-boundary.md), [고정 범위](../../03-fixed-architecture-scope.md)와 [UC](../../05-representative-use-cases.md)에 있다.

**수치 선택은 작성자가 정한 PoC 허용 오류 예산이다.** 외부 논문이나 사업자 합의에서 VIA의 98%를 발견했다고 주장하지 않는다. 사용자가 2026-10-11 허용 수준을 작성자가 구체화하고 이후 리뷰하도록 위임했으므로 다음 예산을 현재 정의로 채택한다.

| 목표 | 과제 차원 선택 판단 | 작은 PoC의 정수 한도 |
| --- | --- | --- |
| 항목 정확성 98% | 업무 연결과 적용까지 포함한 필수 조건에서 **50개 중 1개 이하 오류**를 허용하는 높은 신뢰 기준. 단순 해석 점수만 높고 적용/전달이 틀리는 구조를 걸러냄 | 540개에서 오류 최대 10개. 11개 오류는 97.963%로 미달 |
| 완전 정답 95% | 사용자가 **20번 중 1번을 넘게 전체 처리의 재확인/수정에 개입하지 않아야 한다**는 PoC 수용 판단. 반복 시험이 제품 사용 빈도를 대표한다는 주장은 아님 | 90회에서 실패 최대 4회. 5회 실패는 94.444%로 미달 |
| 각 S/C 95% | 정정/교차 질문/권한 경계를 평균 뒤에 숨기지 않도록 각 중요 묶음에도 같은 20회당 1회 수준의 보호 예산 | 각 90개에서 오류 최대 4개 |
| 필수 위반 0건 | 무관 업무 제어/중복 외부 효과/잘못된 승인/무허용 정보 사용은 고정 기능과 권한 계약상 허용할 수 없는 효과 | 관찰 범위에서 1건이면 적격성 미달. 발생 확률 0의 증명은 아님 |

98%와 95%는 서로 자동 변환되지 않는다. 오류 10개가 10개 요청에 하나씩 퍼지면 항목 목표는 충족해도 전체 처리 목표는 미달이다. 오류가 4개 요청 안에 집중되면 각 S/C 보호 조건까지 검사한다. 이 두 예산을 함께 두어 부분 점수와 실제 사용자의 수정 부담을 모두 관리한다. 모든 후보가 미달하면 보완해야 하며 결과 뒤에 숫자를 낮추거나 분모를 줄이지 않는다.

[이전 발표자료](../../../archive/qa-presentations-before-asr-20261011/README.md)의 V-01은 전체 요청 95%와 1,880회 시험을 제안했다. 현재 98%는 여섯 조건 묶음/90회/540개이며 그 외부 모델 사례를 직접 근거로 옮기지 않는다. 기존 수치의 약한 설명은 [완성 전 정의](../../../archive/qa-definitions-before-completion-20261011/README.md)에 보존한다. 현재 목표/분모/정답은 바꾸지 않고 과제 예산의 선택 이유를 명시했다.

### 3.6 측정 절차와 관측 근거

공통 환경/후보 구성은 §8을 사용한다. 아래에서는 정확성의 기대값과 실제 처리 evidence를 어떻게 연결하고 채점하는지 정한다.

#### 3.6.1 공통 검사 방식과 관측

정답 조건은 다음 검사 방식으로 표현한다. **테스트마다 새로운 채점 알고리즘을 만들지 않고 조건 유형, 비교 연산과 기대값을 지정한다.** 아래는 평가 설계이며 실행 harness나 runtime schema를 구현한 것은 아니다.

| 공통 검사 방식 | 용도 | 예 |
| --- | --- | --- |
| 값/의미 일치 | ID, version, 상태, 의미가 정해진 목표/제약 | 대상 업무=메일, 기간=3분기, 기대 상태=접수됨 |
| 집합 일치 | 필수 대상/조건의 누락 및 원치 않은 추가 | 참조 대상={A, B}, 다른 C 포함 금지 |
| 허용 결과 집합 | 요구를 만족하는 복수 경로/표현 | 제한된 조회의 허용 직접 응답/위임, 의미가 같은 질문/안내 |
| 관계/전이 충족 | 조건/의존 graph, 실제 상태 변화와 인과 순서 | 요약 결과 준비 뒤 해당 참조로 메일 인계, 취소 접수와 종료 구별 |
| 금지 효과 없음 | 정해진 관찰 구간 전체의 부정 조건 | 답변 전 임의 실행 없음, 다른 Task 취소 없음, 중복 외부 명령 없음 |

자연어 결과는 정확한 문자열 일치로 채점하지 않는다. 사전 등록한 의미 사실/허용 표현 기준에 맞춰 목표, 조건과 주장 사실을 판정한다. 문장마다 임의의 “그럴듯함” 점수를 주지 않으며 자동 판정이 어려운 사실은 같은 rubric과 검토 절차로 기록한다. 자동/수동 판정과 평가자 불일치 처리는 §3.6.3으로 고정했다.

관측은 각 조건의 경계에 맞춘다. C1~C4는 채택 의미와 실제 처리에 사용한 대상/관계를, C5는 명령 전송/Agent receipt/상태 반영을, C6는 실제 Text 표시/음성 재생과 기록을 연결한다. 공통 의미로 정규화한 관측 record를 쓰되 A/B의 내부 저장 필드나 중간 Module을 같은 형식으로 바꾸도록 요구하지 않는다. 필요한 adapter와 필수 evidence는 측정 계약에서 별도 설계한다.

정답 조건별 record에는 `과제 ID, 조건 ID, C 유형, 검사 방식, 기대값, 실제값, evidence 참조, 판정, 오류 원인`을 둔다. 이번 여섯 항목의 결과는 `정답/오답`으로 남기며 N/A는 사용하지 않는다. 필수 결과/관측의 후보 귀속 누락은 오답으로 남기고, 시험 수집기 결함은 §3.6.3의 INVALID 절차를 따른다. 금지 효과가 없다는 판정에는 전체 관찰 구간의 필수 trace가 필요하다. 끝 상태만 보고 중간 오실행이 없었다고 추정하지 않는다.

기존 검사 방식으로 표현할 수 없는 중요한 사실을 발견하면 공통 조건/검사 정의를 개정하고 영향받는 사례 전체에 적용한다. 특정 DP나 실패 사례 하나에만 다른 판정법을 추가하지 않는다. 정답 파일은 평가자만 보며 후보에는 정상 사용자가 접근할 수 있는 입력/근거와 동일한 외부 지원만 제공한다.

#### 3.6.2 모든 테스트에 사용할 작성 양식

```text
과제 ID / 대표 상황 S1~S6 / 고정 UC / 공통 변형 tag
초기 상태: 대화, 기존 업무/질문, 허용 정보/권한, 원본 version, 실제 전달 범위
입력과 사건: Voice 발화의 공통 전사/시각, 화면/행동 근거, Agent 원천 사건, 공통 후속 사용자 답변
사건 순서: 공통 원천 사건의 순서/경쟁 조건과 외부 지원 응답
기대 조건:
  C1 목표와 처리 방향       → 조건 ID, 검사 방식, 기대값 또는 허용 집합
  C2 대상과 근거            → 동일 양식
  C3 대화와 업무 연결       → 동일 양식
  C4 조건, 관계와 변경 범위 → 동일 양식
  C5 처리 효과와 상태       → 동일 양식
  C6 응답 내용과 실제 전달  → 동일 양식
금지 효과: 조건 ID에 연결해 관찰 구간 전체에서 확인
관찰 종료: 요구 결과의 관측 경계, 지연 사건 포함 구간, 공통 최대 대기 규칙
관측 및 판정: 조건별 실제값/evidence/정답 여부/오류 원인
```

이번 18개 사례는 필요한 확인 질문과 공통 답변을 같은 과제 안에 포함한다. 후속 질문을 별도 과제로 추가해 분모를 늘리지 않는다. 후보의 질문 문구/순서가 달라도 동일 의미의 답변을 제공한다. 답변 제공 규칙은 같은 질문 대상과 정보량을 유지하며 필요 없는 힌트를 추가하지 않는다.

사건 schedule은 공통 원천 사건과 외부 의미 경계에 맞춘다. 특정 안의 내부 Module 시작/완료를 기준으로 다른 안에 더 유리한 근거를 주지 않는다. 후보의 계산/조회/확정 순서는 구조가 만들도록 두고 경쟁 조건의 적용 방법을 계약에 명시한다. v3의 사례별 조건/관찰 종료/최대 대기는 §3.2.3과 §3.6.3을 따른다.

원본 fixture 제작과 관측 adapter는 §8.3의 실행 준비 단계다. 상황 분류/분모/목표를 다시 결정하는 작업으로 복원하지 않는다.

#### 3.6.3 실행과 관측 절차

1. **실행 자산 제작:** §3.2.2의 상세 명세와 §3.3.1의 판별 규칙을 파일/검사기로 옮기고 각 사례의 Voice 발화와 지정 조건 하나를 고정한다. 파일 hash, source event script, fixture 의미 ID와 runtime ID 대응, Voice/screen 시각, rubric을 고정한다. 후보에게 정답표를 제공하지 않는다.
2. **runner 검수:** 정답/누락/오선택/잘못된 상태/미전달 trace를 이용해 C1~C6와 위반 검출을 확인한다. 이는 검사기 검수이며 후보 정확성 점수에 넣지 않는다. critical Action은 stub 경계에서만 기록한다.
3. **모델/후보 binding:** 동일 build/설정과 실제 저장/인계/입력/표시/재생 경계의 관측을 확인한다. 구조별 prompt/운영 예산과 cache/생산의 version을 기록하고 준비 상태를 확인한다. 정답표를 보며 한쪽 prompt만 조정하지 않는다.
4. **동일 준비 상태 복원:** N/W/X의 동일 원본/외부 이력을 각각의 후보가 처리하게 한다. W에는 120초 준비 창, X에는 공통 변경/교차 script를 적용한다. 시험용 의미/파생 자료를 정답으로 선주입하지 않는다.
5. **쌍 실행:** 같은 사례/지정 조건/반복의 A/B를 가까운 시간에 연속 실행한다. 순서는 seed `20261010`으로 섞고 각 입력 조건의 5쌍에서는 A 선행/B 선행을 3/2 또는 2/3으로 배분한다. 같은 provider seed가 지원되면 대응시키되 동일 모델 응답을 강제하지 않는다.
6. **후속 사건/답변 제공:** 후보의 유효 질문에 정해진 의미의 Voice 답변을 공통 replay로 준다. 허용하지 않은 임의 추가 정보는 주지 않는다. 계획된 확인은 필요한 정보가 모두 채워질 때까지, 후보가 추가한 불필요한 확인은 최대 2회 답변 기회까지 제공하고 그 수고/시간/비용도 남긴다. 미지원 관계를 다른 목표로 바꾸는 답변은 제공하지 않는다.
7. **관찰:** 마지막 원천 입력/필수 외부 사실 또는 제공한 사용자 답변부터 각 자동 처리 구간을 최대 60초 관찰한다. 준비/대기 중에도 금지 효과를 기록한다. 필수 후속 사건은 script의 60초 안에서 발생시키고, 마지막 처리 후 5초간 늦은 반환/중복/옛 음성의 재활성화를 확인한다. 처리 episode 총 상한은 10분이며 외부 Agent의 실제 장기 업무가 끝날 때까지 기다리는 테스트가 아니다.
8. **판정/보고:** C1~C6의 실제값/evidence/0 또는 1, 세부 오류, 위반, 모델 사용량, 실제 완료/전달 시각을 저장한다. 같은 자료에서 §3.4의 전체/분해/완전 정답과 쌍 차이를 계산한다.

60초/10분은 미완료를 무한 대기로 숨기지 않기 위한 정확성 시험의 관찰 상한이다. 빠른 응답 목표나 정상적인 제품 응답시간 SLA를 이 숫자로 정의하지 않는다. 시간/비용/메모리 raw trace는 함께 수집할 수 있지만 그 QA의 대표 지표/목표는 이후 별도로 확정한다.

입력 onset→hold 수락→전송 시작의 경합에서는 **실제 순서**를 판정한다. 먼저 시작된 외부 효과는 확인/정정/취소의 대상으로 남기고, 이미 발생한 효과를 없었다고 표시하면 실패다. hold/권한 철회가 먼저 수락됐는데 이후 금지된 전송을 한 경우는 위반이다. 원천 사건과 software 인식 경계를 구별하는 원칙은 [event-boundary-contract](../../11-measurement/event-boundary-contract.md)를 따른다.

범위가 명확한 필수 사실을 자동 판정하고 자연어 출력/재생 구간은 목표/대상/조건/상태의 같은 사실 rubric으로 후보 이름을 가려 검토한다. 모호한 판정은 두 번째 평가자가 확인한다. 표현 차이는 허용하고 사실 추가/누락/모순은 허용하지 않는다. 불일치는 후보 이름을 가린 evidence와 원본으로 조정해 이유를 남긴다. 오답인 후보 출력을 정답으로 삼는 model judge를 단독 최종 판정자로 사용하지 않는다.

후보 누락/timeout이면 증명된 항목만 1로 남기고 나머지는 0이다. 예를 들어 의미는 맞았지만 Agent 인계/실제 전달이 없으면 C5/C6는 0이다. 이미 확인한 C1~C4를 무조건 모두 0으로 덮지는 않는다. 단, 후보 전체가 실패하여 근거가 없으면 여섯 항목 모두 0이다. 시험 수집기 결함이나 계획하지 않은 공통 provider 장애로 판정 자체가 불가능하면 A/B 쌍을 INVALID로 보존하고 복구 후 같은 쌍을 재실행한다. 후보의 잘못된 호출/예산 소진/필수 trace 미생성은 INVALID가 아니다. 원래 90개 유효 실행이 채워질 때까지 실패 사례를 유지하며 INVALID와 재실행도 공개한다.

#### 4.1.1 병렬 실행과 외부 시간 귀속

각 장면의 causal DAG에 `node_id, parent_ids, owner, request_ref, kind, duration_ms, evidence_ref`를 기록한다. 연산, queue, 전송, 모델 호출, 실제 전달을 독립 구간으로 둔다. 순차 duration은 합산하고 병렬 branch는 longest path로 계산한다. 같은 구간을 Request Controller와 Task Manager에서 두 번 더하지 않는다.

외부 업무 대기는 `EXTERNAL_AGENT_WORK`, 사람의 답변 대기는 `EXTERNAL_USER_WAIT`로 분리한다. **같은 사건/분기/결과를 고정한 그래프에서 이 두 종류의 duration만 0으로 놓고, 선후 관계를 유지해 종료시각을 다시 계산한 값**이 VIA 귀속 시간이다. 독립 실행 중인 VIA 작업을 외부 대기와 함께 제거하지 않는다. `wall_clock - 여러 Agent 실행시간의 합`을 쓰지 않는다. 외부 Agent에 보내는 Gateway/전송/접수 처리와 Agent source 사건을 VIA가 가져오는 polling/통신 지연은 포함한다.

이 계산은 원래 replay의 사건 순서와 의미 판정을 바꾸는 재실행이 아니다. 원래 graph의 의존성과 경쟁 outcome을 유지하는 귀속 계산이다. 외부 결과가 독립 작업보다 먼저 준비되도록 바꿔 semantic 성공률을 다시 생성하지 않는다. 전체 사용자 wall-clock, 제외한 구간과 계산 DAG를 함께 남긴다.

모든 장면은 §3의 동일 초기 자료/입력/권한/질문 규칙을 사용한다. Voice ON이고 사용자가 말하는 동안에는 새 음성 안내를 시작하지 않는다. I-04/05의 시작은 VIA inbox 도착이 아니라 **Agent source의 availability**이며 source→VIA 통신을 시간에 포함한다. 후보의 실제 선택 경로가 읽기/모델을 요구하면 그 시간도 포함한다.

```text
r_i = min(유효 반응의 VIA 귀속 시간, 5초)
유효 endpoint가 5초 안에 없으면 r_i = 5초, missed_endpoint = 1
ASR-QA-02 = sum(r_i) / 30, 단위 초, 낮을수록 좋음
```

**목표: 평균 1.0초 이하.** 보조 보호 조건은 `I-01의 5회 모두 stop ≤ 0.1초`, `30회 중 29회 이상 ≤ 2초`, `missed_endpoint = 0`이다. cap은 실패를 삭제하지 않는 집계 규칙이며 실패 시간이 실제 5초라고 관측했다는 뜻이 아니다. cap 값/실제 경과/오답/미전달을 별도 저장한다. 빠른 오답은 유효 반응으로 세지 않고 endpoint 실패로 남기며 정확성도 원래 rubric으로 판정한다.

**목표 근거:** VIA는 사람이 PC 작업을 계속하면서 끼어들고 다른 업무의 질문에 답하는 상시 대화 SW다. 반응마다 수초의 정적을 만들면 업무 전환과 제어가 끊긴다. [Nielsen의 0.1/1/10초 참조](https://www.nngroup.com/articles/website-response-times/)에서 즉각 제어 0.1초, 흐름 유지 1초를 참조하고, 평균 1초와 개별 2초 보호 조건을 이 과제의 예산으로 선택했다. 문헌이 평균 1초나 29/30을 규정한 것은 아니다. 2초는 일반 반응의 1초 예산에 일시적인 queue/재검증 1초를 허용하는 한도이고, 마지막 1회의 작은 tail을 별도로 보면서 전체 5초 누락은 허용하지 않는다. 끼어들기는 cloud 해석을 기다리지 않는 공통 local 경로이므로 0.1초를 따로 요구한다.

예산 예시는 `전사 확정 0.10 + 의미 호출 0.30 + 100/450 + code/read/commit 0.08 + 음성 준비/첫 재생 0.25 = 0.9522초`다. 450 token/s만 외부 참조이고 다른 값과 100 token은 작성자 가정이다. 이 예산을 넘는 반복 조회나 재해석은 실제 성능 차이로 드러난다. 예산에 맞추기 위해 필요한 내용이나 현재성 검사를 삭제하지 않는다.

S2-02/S6-01에 이미 지정한 목표/원문/후속 답변은 그대로다. 위 artifact 이름은 evaluator의 의미 ID이며 후보의 runtime ID는 대응표로 검사한다. Agent stub은 **실제로 접수한 payload를 읽고 그 payload에 대한 결과를 반환**한다. 잘못된 대상을 올바른 artifact로 바꿔주는 정답 stub을 만들지 않는다. 내용 검사는 참조/업무/조건/상태/전달의 VIA 사실만 검사하고 Agent 도메인 작성 능력은 고정 외부 조건이다.

```text
v_i = min(전체 사이클의 VIA 귀속 시간, 30초)
필수 최종 endpoint가 귀속 30초 안에 없으면 v_i = 30초, missed_endpoint = 1
ASR-QA-03 = sum(v_i) / 30, 단위 초, 낮을수록 좋음
```

**목표: 평균 10초 이하**, 보조 한도 `30회 중 29회 이상 ≤ 15초`, `missed_endpoint = 0`. 동일 의미/목표/성공 여부는 원시 결과에서 함께 확인한다. 알려진 외부 실패의 정당한 안내는 그 장면이 실패 안내를 요구할 때만 종료로 인정한다. T-02처럼 성공 결과를 반환하는 장면에서 임의 포기/미지원 안내는 빠른 완료가 아니다.

**목표 근거:** VIA는 Agent의 업무 실행을 대신하지 않지만 요청 이해, 확인, 인계와 결과를 다시 연결하는 오버헤드를 책임진다. 외부 업무가 끝나도 VIA 때문에 기다리는 시간을 제한해야 이 과제의 연속 interaction 목적을 달성한다. Nielsen의 10초 주의 유지 참조를 VIA 전체 오버헤드 상한 설계의 출발점으로 삼고, `의미 처리 6초 + read/commit/연결 1초 + 음성/게시 1초 + 재검증 여유 2초 = 10초`를 선택했다. 평균 10초는 긴 업무의 제품 SLA가 아니라 작은 PoC의 VIA 예산이다. 개별 15초는 10초 기본에 한 번의 추가 확인/재해석 예산 5초를 허용한 보호 한도다.

예시 요청 그래프의 두 독립 read는 양안 모두 병렬이다. 한 의미 호출의 `0.30 + 200/450 = 0.7444초`, read 두 개의 병렬 `max(0.04,0.04) = 0.04초`, 채택/게시 코드 `0.03초`, 음성/차례 `0.45초`라면 VIA 시간은 `1.2644초`다. 앞선 read가 다음 selector를 정하는 요청이면 read 구간은 0.08초로 바뀐다. **독립 read를 A에서는 강제로 순차로 만들지 않는다.** 여기에 Agent 업무 8초와 사용자 답변 2초가 순차로 필요한 예시의 전체 시간은 11.2644초이고, 귀속 시간은 1.2644초다. 병렬 overlap이 있으면 그래프를 다시 계산한다.

두 의미 호출을 41A의 조건부 loop, 한 frame 호출을 41B의 코드 해결로 둔 설명 예시에서는 호출 하나의 0.7444초 차이가 나지만, **B도 부분 해석이 필요하면 두 번 이상 호출하고 A도 한 번으로 끝날 수 있다.** 실제 call 수/길이를 trace나 명시된 call-plan에서 가져와야 한다. 이름만으로 호출 수나 우열을 확정하지 않는다.

### 4.5 측정 절차, 차이 기준과 DP 연결

1. 지정 6개 장면과 oracle/외부 사건을 A/B 동일하게 고정한다. 5개 반복의 실행 순서는 `A-B, B-A, A-B, B-A, A-B`로 교차한다. 같은 초기 snapshot/준비 이력을 복원한다.
2. replay 시작/발화 끝/Agent availability, call start/first output/end/usage, read/commit/IPC, 실제 표시/playback receipt를 monotonic clock으로 기록한다. 전체 사건과 causal edges를 보존한다.
3. 각 endpoint의 의미와 현재성을 확인한다. 없거나 틀린 종료는 cap과 실패로 남긴다. 계산 모드에서는 동일 oracle를 만족하는 명시적 call-plan만 계산하며 성공을 실측했다고 하지 않는다.
4. 외부 업무/사용자 대기만 제거한 DAG로 귀속값을 계산하고 원래 wall-clock을 병기한다. cap 적용 전 값과 30개 원시값/분자/분모/실패 수를 보고한다.
5. 실제 반복값의 A/B 차이는 같은 장면 5회 묶음을 paired bootstrap 10,000회, seed 20261011로 재표집해 95% 구간을 보고한다. 6개 장면으로 제품 모집단 전체를 추정하지 않는다. reference 계산에는 가짜 신뢰구간을 붙이지 않고 민감도를 사용한다.

**의미 있는 선택 차이:** QA-02는 평균 0.10초 이상, QA-03은 평균 0.50초 이상이며 실제 반복에서는 paired 구간이 0을 포함하지 않아야 한다. 각각 1초 목표의 10%, 10초 예산의 5%를 설계 판단으로 선택했다. 계산만으로 우열을 주장할 때는 기준/빠른/느린 세 profile에서 같은 방향과 그 차이 크기를 충족하는지를 보고하고 가정에 따라 뒤집히면 조건부로 기록한다. 작은 차이와 미입증을 동등성 증명으로 바꾸지 않는다.

| 44 | 중앙 완료 회수와 Stage 활성화/join/차례 대기. 공통 local stop | 전체 continuation 전이/유량 대기. A도 async/병렬, B도 join/폐기 비용 |
| 45 | 과거 질문/결과를 요구하는 반응에서 원본 조합 또는 게시 자료 조회 | 반복 과거 관계의 재해석 또는 생산/검증/미게시 backfill. 현재 입력 의미는 양안 별도 |

두 QA 모두 같은 값이 나올 수 있다. 예를 들어 44에서 첫 반응은 같은 local stop지만 전체 후속 준비 전이는 다를 수 있고, 45에서 게시 준비가 없는 첫 요청은 B가 느릴 수 있다. 모든 네 DP에 반드시 반대 부호의 결과를 만들도록 지표나 사례를 바꾸지 않는다.

## 5. 모델 사용 비용

**관리 ID: ASR-QA-04 — VIA 모델 사용 비용.**

### 5.1 정의, 대표 지표와 책임 경계

**동일한 사용자 활동을 처리하는 동안 VIA의 음성/의미 모델 사용에 드는 금액.** 대표 지표는 **표준 8시간 활동의 총 모델 비용(USD/8시간)**이다. 입력 목표 수를 후보가 만든 Task/호출 수로 나눠 비용을 낮추지 않는다. 100개 요청 목표는 고정 workload의 설명이며 대표 비용 분모는 동일한 8시간이다.

음성 입력/전사, 현재 의미, 과거 관계 생산/갱신, 질문/응답 내용과 음성 출력, 재시도, 늦어서 폐기된 청구 출력과 미사용 배경 생산을 포함한다. 외부 Downstream Agent가 자체 업무에 쓴 모델/도구 금액은 제외하고 별도 원장으로 남긴다. CPU/IPC/저장 비용은 모델 비용에 임의 단가로 섞지 않는다. 모델 call ID 하나를 41과 45 비용에 중복 가산하지 않는다.

```text
C8h = Σ 의미 호출(input_tokens × 0.80 + billed_output_tokens × 4.00) / 1,000,000
    + audio_input_minutes × 0.005 + audio_output_minutes × 0.018
    + (voice_text_input_tokens × 0.75 + voice_text_output_tokens × 4.50) / 1,000,000
```

단가는 §8.4의 공개 reference다. 분 기반 음성 환산과 audio token 청구를 동시에 적용하지 않는다. 실측에서는 사용량 응답/청구 규칙을 우선하며 reasoning, image token, retained context, tool schema와 재전송도 해당 청구 입력/출력으로 기록한다. caching 할인을 기준값에 넣지 않는다. 할인 profile은 같은 양안에 같은 공개 조건으로만 추가한다.

원장 열은 `call_id, source_execution_key, dp_option, role, trigger_event, purpose, source_vector, start/end, input/output/reasoning/image/audio_usage, billed, outcome, used_by, USD, evidence_level`이다. timeout/cancel/미사용을 `billed=false`로 추정하지 않는다. provider가 usage를 주지 않으면 요청/출력 기록에서 보수적인 token 상한을 적용해 **상한 계산**이라고 표시한다. 평가 세션 미실행은 결과 상태이고 비용 정의의 빈칸이 아니다.

### 5.3 목표값과 과제 근거

**목표: 8시간 평균 총 모델 비용 $1.50 이하.** 목표당 보조 환산은 $0.015이며 22일의 동일 활동이면 $33이다. USD 그대로 관리하고 환율/세금/마진/서비스 가격을 섞지 않는다. 이 금액은 사용자 또는 과제 사업자가 이미 확정한 상품 가격이 아니라 작성자가 제안한 모델 예산이다.

| 기준 workload의 계산 | 금액 |
| --- | --- |
| 의미 입력 600,000 × $0.80/1M | $0.4800 |
| 의미 출력 60,000 × $4.00/1M | $0.2400 |
| 음성 입력 30분 × $0.005/분 | $0.1500 |
| 음성 출력 10분 × $0.018/분 | $0.1800 |
| 음성 Text 입력 50,000 × $0.75/1M | $0.0375 |
| 음성 Text 출력 10,000 × $4.50/1M | $0.0450 |
| 기본 합계 | **$1.1325** |
| 추가 생산/재시도/길이 증가에 남는 예산 | **$0.3675** |

**과제 근거:** VIA는 상시 대화와 여러 업무의 후속 처리를 제공하므로 요청 때만의 싼 단일 호출을 제시해서는 지속 운용 가능성을 설명할 수 없다. 하루 100개 목표/40분 음성의 기본 reference $1.1325에 추가 처리 여유 $0.3675를 두어 $1.50을 선택했다. 기본값 대비 약 32.45% 여유이며 총 예산의 24.5%다. 품질을 위해 필요한 재판단은 허용하되 배경 생산이 이 여유를 지속적으로 소모하는지 비교한다. 비용을 맞추려고 확인/현재성/허용 검사를 제거하면 정확성에서 손실을 남긴다.

**차이 기준:** 하루 $0.15 이상, 즉 예산의 10% 차이를 의미 있는 비용 차이로 본다. 실제 반복이면 3회 각각의 비용/usage와 범위를 공개하고 같은 방향을 확인한다. 참조 계산이면 사용 횟수/재사용 빈도/음성 길이를 0.5배/1배/2배로 바꿔 조건부 손익을 보인다. 작은 차이는 그대로 금액으로 보고하고 등급 차이만으로 선택하지 않는다.

### 5.4 A/B의 비용 차이를 계산하는 예

45의 추가 과거 처리만 떼어 보는 예다. 공통 현재 요청 의미/음성 비용은 양안 같고 비교 원장에서는 한 번씩 포함한다. **A도 관계 cache를 사용하며 동일 source revision에서는 재조회/재해석하지 않는다.**

- A: 하루 실제 cache miss 40회, miss당 과거 근거 추가 입력 4,000/출력 200 token이면 `40 × $0.004 = $0.160`.
- B: 초기/변경으로 관계 생산 20회, 생산당 입력 6,000/출력 400 token이면 `20 × $0.0064 = $0.128`. 요청에서 게시 자료 조회는 코드이고 모델 청구를 만들지 않는 예지만 현재 요청 의미 비용은 공통으로 남는다.
- A의 miss가 10회면 $0.040으로 B보다 싸다. 생산 20회 기준 손익분기는 A의 **32회 miss**다. 동일 입력이라고 miss/생산 수가 자동으로 같아지는 것은 아니며 실제 cache/coverage 계획에서 도출한다.
- B의 게시가 부족해 backfill 모델 호출이 10회 추가되면 그 비용도 더한다. 이 예의 $0.032 차이는 $0.15 선택 기준보다 작아 비용 우위만으로 구조를 고를 수준이 아니다.

41의 model loop/부분 호출, 42의 접수 충돌 재해석과 44의 stale 준비/재시도도 같은 원장으로 계산한다. 42B의 IPC를 모델 호출 비용으로 세거나 44B Stage마다 무료 모델을 따로 둔다고 가정하지 않는다. 이 예는 가정 검산이며 실제 후보의 비용 측정이나 승자 판정이 아니다.

## 6. 변경 용이성

**관리 ID: ASR-QA-05 — VIA 변경 용이성.**

### 6.1 정의와 대표 지표

**모델/Agent/정보원/기능 계약의 변화를 다른 사용자 기능을 유지하면서 수용하는 능력.** 대표 지표는 **공통 여섯 변경 과제의 평균 변경 책임 단위 수(개/과제)**다. 기존 QA-29의 변경 전파 범위 관점을 참고하지만 새 공통 registry/여섯 과제로 평가하므로 기존 QA-29 결과와 합치지 않는다.

```text
u_j = 과제 M-j에서 실제로 수정해야 하는 고유 책임 단위 ID의 수
ASR-QA-05 = (u_1 + ... + u_6) / 6, 낮을수록 좋음
```

파일 수/LOC/개발 시간 추측을 대표값으로 쓰지 않는다. Component 하나에 여러 책임을 넣었다고 변경 수가 1이 되지 않으며, 같은 책임을 여러 파일/프로세스로 구현했다고 별도 점수를 자동 추가하지 않는다. 데이터 계약을 생산/소비하는 두 책임이 실제 변경되면 두 개로 센다. generator의 동일 코드 재출력이나 테스트/문서 갱신만은 추가 단위로 세지 않고 검증 부담으로 별도 기록한다.

### 6.4 목표와 과제 근거

**목표: 평균 3개 이하**, 보조 한도는 모든 과제 **5개 이하**와 여섯 과제의 완료/필수 회귀 충족이다. 18개의 공통 책임 중 평균 최대 3개, 즉 약 1/6 범위로 일상적인 변경을 국소화하려는 설계 예산이다. 한 요구의 변경이 대략 `경계 adapter/생산 책임/소비 책임` 수준에서 끝나고 대화/업무/음성 전체를 연쇄 수정하지 않아야 여러 모델/Agent/정보원을 지속 연동하는 이 과제의 목적을 달성한다. 복합 의미 변경처럼 더 넓은 경우는 5개까지 허용하되 그 과제 하나로 광범위한 변경을 평균에 숨기지 않는다.

예를 들어 M-04의 변경 계획이 A=`U01/U03/U07`이면 3개, B=`U01/U02/U03/U07`이면 4개다. A가 모델 prompt만 수정하고 실제 후속 실행을 기존 코드가 지원하지 못하면 1개 성공으로 세지 않는다. 두 안이 기존 범용 관계 계약을 이미 지원한다면 변경 집합은 더 작아질 수 있다. 이 집합은 **실제 diff/구체 설계 패치에서 확인할 예시**이며 현재 구현의 실측 결과가 아니다.

**차이 기준: 평균 0.5개 이상**, 여섯 과제 합계에서 고유 수정 발생 수 차이 3개 이상이다. 목표 3개의 1/6 범위 차이로 정했다. 결정적인 수정 계획을 세는 평가에는 bootstrap 신뢰구간을 발명하지 않는다. 두 검토자가 같은 registry/완료 조건으로 변경 집합을 비교하고 의견 차이가 있으면 집합과 근거를 조정한다. implementation이 없어도 구체적인 계약/설계 patch로 `DESIGN_CHANGE_REVIEW`를 수행할 수 있다. 단순 “바뀔 것 같다”는 모호한 개수는 공식 값으로 사용하지 않는다.

### 6.5 수행 절차와 DP 영향

1. 동일 후보 설명/계약 snapshot과 registry를 고정하고 여섯 과제를 각각 원래 snapshot에서 시작한다. M-01 완료 결과를 M-02의 기본 구조로 누적하지 않는다.
2. 요구를 충족하는 최소한의 강한 수정안을 작성한다. A의 내부 API/cache/부분 갱신, B의 안정된 schema/독립 owner를 허용한다. 작업량을 늘리는 불필요한 재설계는 세지 않는다.
3. U01~18 각각에 `CHANGED 또는 UNCHANGED, 이유, 변경 전/후 계약, patch/evidence_ref`를 채운다. 비참여 단위도 공란 대신 동일 계약 유지 이유를 기록한다.
4. 완료 oracle와 기존 정답/시간/권한/중복 회귀를 검사한다. 설계 patch는 계약과 사건 walkthrough로 검토하고 구현 patch는 해당 실행 검사를 병기한다. 두 증거 수준을 섞지 않는다.
5. 여섯 변경 집합/개수와 평균, 최대값을 보고한다. 변경량과 별도로 이행/배포/검증 부담을 서술한다.

41은 유한 관계 확장, 42는 질문 token의 authority/handoff, 44는 제어/질문 revision이 continuation/window에 전파되는 범위, 45는 철회가 원본 조합/cache 또는 생산/조회/coverage에 전파되는 범위에서 차이가 날 수 있다. 외부 protocol의 단순 변경은 양안 모두 adapter 하나로 끝날 수 있다.

## 7. 메모리 사용량

**관리 ID: ASR-QA-06 — 로컬 VIA 메모리 사용량.**

### 7.1 정의와 대표 지표

**동일한 활동과 동시 부하에서 VIA가 로컬 PC에 할당해 유지하는 메모리의 최대량.** 대표값은 **8시간 동안 VIA 전체 프로세스의 최대 동시 commit 메모리(MiB)**다. 순간별 모든 VIA process의 private committed bytes와 공유 anonymous section의 고유 committed bytes를 한 번씩 합한 뒤 최대값을 구한다.

```text
M(t) = Σ VIA 프로세스의 PrivateUsage(t) + 고유 shared-anonymous commit(t)
ASR-QA-06 = max_t M(t) / 1,048,576, 단위 MiB
```

UI/Core/독립 대화/업무 service, worker/helper, local VAD, 입력 근거/Context/cache/queue/DB cache, cloud adapter/암호화/직렬화 buffer를 포함한다. shared section을 private 항목에 이미 포함한 allocator에서는 section ID로 중복을 제거한다. 서로 다른 process가 같은 JSON을 각자 복사했으면 실제 private 할당이므로 둘 다 센다. 같은 immutable shared buffer 참조는 한 번만 센다.

**commit은 현재 물리 RAM에 올라온 working set과 다르다.** [Microsoft PrivateUsage 정의](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)에 맞춰 할당 압력을 관리한다. page-out으로 working set을 줄여도 commit을 낮췄다고 하지 않는다. 디스크의 DB/로그 전체 bytes와 cloud 서버 weights/KV는 제외한다. file-backed mapped page/DLL의 resident working set과 VRAM은 별도 진단에 포함하고 commit에 가산하지 않는다. primary가 물리 RAM 전체를 정확히 나타낸다고 주장하지 않는다.

file-backed mapping으로 private 할당을 옮겨 primary만 낮추는 경우에는 **보조 전체 process working-set 합계 6GiB 이하**를 함께 검사한다. 이 합은 shared page를 중복 셀 수 있는 보수적 보호값이고 unique physical RAM으로 부르지 않는다. GPU/NPU의 VIA 전용 할당도 원장에 공개한다. 현재 cloud 모델 조건에서 local 모델 weights는 0이며 local VAD나 렌더 자원이 0이라는 뜻은 아니다. 향후 local 모델 비교로 전환하면 weights/runtime/KV를 포함한 새 workload version을 만든다.

### 7.3 목표값과 장치/과제 근거

**목표: 최대 4,096MiB(4GiB) 이하.** 32GB급 장치에 `Windows/기본 상주 8GiB + 사용자 Office/browser/다른 앱 16GiB + VIA 4GiB + 변동 여유 4GiB = 32GiB`의 계획 예산을 둔다. 제조사의 32GB 표기에서 이를 정확한 측정 RAM 값으로 추정하지 않으며 **32GiB 분할은 작성자의 장치 계획 가정**이다. 실제 Windows의 installed/available memory를 기록하더라도 목표를 결과에 맞춰 자동 늘리지 않는다.

VIA는 사용자가 PC 업무를 계속하는 동안 실행되므로 전체 기기 메모리를 독점할 수 없다. cloud 모델 조건에서도 입력 근거, 진행 업무와 장기 파생물이 상주할 수 있어 4GiB의 상한을 정했다. 4GiB는 특정 삼성 제품이 보장한 VIA 가용량이나 현재 앱의 측정값이 아니다. 단순 process 수가 적다는 사실만으로 작은 메모리를 주장하지 않는다.

| 설명용 동시 할당 예산 | MiB | 포함할 것 |
| --- | --- | --- |
| UI/Core/runtime 기본 | 512 | process heap/언어 runtime/화면 UI |
| capture/전달 buffer | 512 | 같은 원본 보관/복사/전사/audio |
| 원문 Context/cache | 256 | source 발췌/현재/준비된 과거 |
| Task/요청/전달 상태 | 128 | 활성 상태와 pending 질문/receipt |
| DB/cache/영속 읽기 buffer | 128 | 디스크 DB bytes와 구별 |
| cloud call 임시 상태 | 64 | 최대 4호출 × 16MiB의 가정 |
| queue/직렬화/동시 burst | 128 | 제한 inbox/outbox/결과 copy |

보조 보호 조건은 앞의 working-set 합 6GiB 이하와 **470~480분 잔류 commit의 증가가 16MiB 이하**다. 필수 근거/작업을 유지한 채 배경 queue를 회수하는지 확인한다. 16MiB는 작은 page/cache fluctuation을 허용하는 진단 예산이고 product leak 0의 증명은 아니다. workload가 기능을 포기하고 더 적게 저장한 경우 정확성/지원 범위 손실과 함께 보고한다.

### 7.4 관측/계산 절차와 차이 기준

1. process/job tree와 helper inventory를 고정한다. 42B의 두 서비스, 44B window/pipe, 45B 생산/조회 상태를 빠뜨리지 않는다. source가 같은 원문을 보내도 소비자가 복사하면 실제 bytes로 센다.
2. Windows에서는 [GetProcessMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo)의 PrivateUsage를 **50ms 간격**으로 전체 process에서 수집한다. 공유 section은 생성/commit/decommit의 section ID/size 원장으로 추적한다. polling peak는 50ms 사이의 짧은 peak를 놓칠 수 있어 주요 allocate/free 직후 event sample과 allocator high-watermark를 병행한다.
3. 8시간 session을 3회 초기화해 수행하고 **세 session의 최대 중 가장 큰 값**을 대표 보고값으로 쓴다. 각 session의 peak와 시각/phase, idle 변화, sample 누락을 공개한다. process restart에서 peak 원장을 리셋하지 않는다.
4. 구현 전 PoC 계산은 allocation ID/owner/수명/bytes/동시 구간을 갖는 원장으로 같은 시각의 합과 peak를 산출한다. 역할마다 전체 1,792MiB를 복제하지 않고 공통 항목과 실제 추가 private heap/복사/공유 상태를 구별한다.
5. 후보 장애/미완료 workload로 조기 종료한 낮은 peak는 목표 달성으로 세지 않는다. cap 4,096MiB로 숫자를 잘라 결과를 맞추지 않는다. 관측 누락은 실제 관측 최대라는 하한과 누락 사실을 보고하며 전체 peak를 관측한 것처럼 등급을 부여하지 않는다.

**차이 기준: 128MiB 이상**, 목표 4GiB의 약 3.125%와 기본 상태/queue budget 한 묶음 크기다. polling 오차/allocator reserve 차이보다 구조의 동시 상태 차이를 보려는 작성자 기준이다. 계산에서는 추가 process heap, 중복 message copy, cache 크기를 절반/기준/두 배로 바꿔 확인한다. 41의 해석 Context/frame/부분 상태, 42의 추가 service/접수/outbox, 44의 continuation/window/buffer, 45의 원문 cache/게시 index/coverage/backlog가 참여한다. 어느 안도 무조건 작다고 확정하지 않는다.

## 8. 공통 PoC 환경과 A/B 비교 방법

공통 입력/원천 사건/후보/모델 조건은 여섯 QA에 공유하고, 각 QA의 분모/시간/금액/변경/메모리 경계는 §3~7의 완료 정의를 따른다. 공통 전사/장치 replay를 실제 ASR 정확도나 물리 장치 응답시간 실측으로 해석하지 않는다.

### 8.2 A/B 구성과 비교 근거의 범위

다른 DP 조건은 설명용 기준 구성 **41A/42A/44A/45A**로 고정한다. 기준 구성은 최종 선택이 아니다.

| 비교 | A 실행 구성 | B 실행 구성 |
| --- | --- | --- |
| 41 | 41A/42A/44A/45A | 41B/42A/44A/45A |
| 42 | 41A/42A/44A/45A | 41A/42B/44A/45A |
| 44 | 41A/42A/44A/45A | 41A/42A/44B/45A |
| 45 | 41A/42A/44A/45A | 41A/42A/44A/45B |

이번 검토 중 병행 상세화된 [42 §4.2~4.3](./04-42-lifecycle-ownership.md#42-b의-입력-hold업무-접수전송복구-프로토콜)와 [44 §3.1](./04-44-continuous-interaction.md#31-공통-소유와-허용-경계)을 확인했다. 42B의 Hold/HoldAck, CommandIntent, ReleaseAndReconcile, AcceptanceReceipt와 업무 로컬 transmission CAS가 44A/B의 후속 실행에 연결되는 문서 계약이 추가되어 있다. [04-40 §6](./04-40-common-execution-contract.md#6-네-dp가-실제-프로그램에서-결합되는-지점)의 이전 UNRESOLVED 표기만 보고 프로토콜 설명 자체가 없다고 복원하지 않는다. **문서 계약은 있으며 실제 구현/조합 검증은 아직 없다.** 대화/업무 저장소가 공동 transaction을 가진 것처럼 구현하지 않고 위 독립 접수/ACK/UNKNOWN 경로를 실행해야 한다. 구현/관측 준비 전 상태는 NOT_READY이며 A/B 수치가 아니다. 위 한 조건 비교는 다른 조합에서의 상호작용 우열을 입증하지 않는다.

모든 Task를 실제 외부 계정에 만들 필요가 없다. Agent 업무 품질은 stub으로 통제하고 VIA의 요청/상태/전달을 검사한다. **41/45의 의미 LLM까지 정답 mock으로 대체하면 실제 의미 정확성 비교가 되지 않는다.** model mock은 runner/판정의 검수에만 사용하고 공식 정확률은 실제 모델을 통과한 후보 실행에서 계산한다. mock 오류 확률로 A/B 차이를 만들어내지 않는다. 결과 evidence는 `MEASURED_REFERENCE_HARNESS`와 실제 모델 실행의 `MEASURED_MODEL`을 명시하며 이 장비/replay/stub 조건의 결과다. PC 제품/실제 Agent의 `PRODUCT_E2E`로 부르지 않는다.

### 8.3 실행 준비와 정의 완료의 구분

**현재 정확성 평가 설계에서 닫은 것:** 요청 처리 정확성 정의, S1~S6, 18개 초기 상황/Voice 입력/후속 답변/사건 순서/108개 항목별 통과 조건과 공통 판별 규칙, C1~C6 묶음별 이진 채점, Voice 단일 입력/사례별 조건/5회 반복과 분모, A/B 단일 변수 구성, 공통 환경/판정/관찰 절차, 목표/위반/차이 인정 기준.

**실행 때 해야 할 것:** 이 설계대로 원본/Voice replay/화면/사건 fixture를 제작하고 이미 정의한 18개 사례/108개 기대값/판별 규칙을 파일/검사기로 옮긴다. 원본 내용/답변/사건 순서를 다시 선택하는 작업이 아니다. 후보/harness/관측 adapter와 42B의 문서화된 독립 접수/hold 계약을 실제 구현하며, 모델/장비/설정과 각 파일 hash를 manifest에 넣고 검사기를 검수한 뒤 실행한다. 이는 확정 정의의 구현/검증이며 상황/분모/정답을 다시 선택하는 작업이 아니다. 이 요청에서는 후보나 모델을 실행하지 않았다.

추후 요구 범위를 바꿔야 할 때만 이유를 기록한 다음 버전으로 개정한다. 기존 계약과 생성된 실패/결과는 원래 버전으로 보존한다. 이전 v1/v2와 현재 v3에는 아직 실행 결과가 없다. 기존 QA-19/QA-09/QA-29/QA-39, 참조 Architecture, ADR와 과거 결과를 이번 새 지표로 소급 변경하지 않는다. 정확성 유형 수와 분모 논의를 처음부터 반복하지 않고, 완성된 여섯 QA의 허용 예산과 적용 범위를 함께 리뷰한다.

### 8.5 이 계획 단위의 확인과 게시 범위

정의 단위 2/3에서 여섯 QA의 정의/지표/수치 목표/근거/평가 방안을 모두 작성했다. 정확성/시간 모집단과 비용/변경/메모리 경계를 구별하며 외부 reference와 작성자 예산을 표시한다. 참조 계산은 [재현 입력](./03-02-poc-inputs.json), [검산 보고](./03-02-poc-calculation-report.md)와 [검산 코드](../../../../scripts/architecture/qa_poc_reference.py)로 연결한다. 발표자료는 이 원본의 요약표와 세부 평가 명세를 SHA-256으로 추적하며 별도 QA 정의를 만들지 않는다. 현재 reference를 찾았다는 이유로 ASR-QA-01~06의 실측 결과가 있다고 기록하지 않는다. 문서 로컬 링크/용어/기존 QA registry와 Git 공백 검사를 수행하고 이 작업의 파일만 commit/push한다.

| 06 | 같은 8시간/3session, 전체 allocation/process | 가장 큰 동시 peak, MiB | 128MiB 이상과 원장/오차 민감도 |

아래 `PRIMARY`는 실제 구조가 대표 지표를 직접 바꿀 경로가 있고 `REGRESSION_ONLY`는 같은 의미/호출 역할을 유지하며 회귀와 조건부 추가 비용을 확인한다는 뜻이다. 미참여를 좋은 점수로 바꾸지 않는다. 이번 여섯 축에서 네 DP 모두 적어도 관련 상태/경로의 회귀 또는 직접 영향을 가지며 모든 칸의 이유를 적었다.

| DP | 01 정확성 | 02 반응 | 03 사이클 | 04 비용 | 05 변경 | 06 메모리 |
| --- | --- | --- | --- | --- | --- | --- |
| 41 | PRIMARY: 모델 전체 판단/유한 frame 코드 결합과 지원 한계 | PRIMARY: 정정/확인/취소 해석 의존. local stop는 동일 | PRIMARY: 반복 read/부분 해석/재판단 | PRIMARY: 실제 semantic call/Context 길이 | PRIMARY: M-04의 의미/schema/Engine 확장 | PRIMARY: inference Context/항목 상태의 동시 수명 |
| 42 | REGRESSION_ONLY: owner 접수/현재성/hold/중복 일치. 분리 자체가 의미를 높이지 않음 | PRIMARY: 질문·결과 조회/반영/IPC | PRIMARY: 공동 확정/독립 접수의 전이 | REGRESSION_ONLY: 모델 역할 동일, 충돌 재해석만 실제 추가 | PRIMARY: M-05 token의 owner/접수/복원 | PRIMARY: 추가 process/outbox/projection/copy |
| 44 | REGRESSION_ONLY: 동일 의미 생산/채택, 늦은 후보와 실제 게시 | PRIMARY: 중앙 회수/Stage 활성화/차례 대기 | PRIMARY: 후속 진행/flow-control/join | REGRESSION_ONLY: 역할 동일, 실제 stale/retry 준비만 추가 | PRIMARY: 질문/제어 revision의 continuation/window 전파 | PRIMARY: 중앙 진행 상태 또는 windows/pipes/credit |
| 45 | PRIMARY: 원본 조합/공통 관계/coverage/원문 예외 | PRIMARY: 과거 질문/결과를 필요로 하는 반응 | PRIMARY: 관계 재해석/게시 query/backfill | PRIMARY: cache miss/배경 갱신/미사용 생산 | PRIMARY: M-06 철회와 파생 소비/생산 | PRIMARY: 원문 Context/cache 또는 resident index/coverage |

**영향이 있다는 것과 유의미한 차이가 난다는 것은 다르다.** 42의 정상 접수 왕복이나 44의 짧은 완료 회수만으로는 시간 차이 기준을 넘지 못할 수 있다. 41B의 부분 모델 호출이나 45A의 정상 cache로 차이가 줄어드는 것은 허용한다. 이 검수는 DP의 실제 구조/조건을 확인하며 major DP 자격이나 선택을 보장하지 않는다.

### 8.7 계산 가능한 작은 비교와 재현 입력

[계산 입력](./03-02-poc-inputs.json)과 [검산 보고](./03-02-poc-calculation-report.md)는 이 문서의 정의/단가/예시를 재현한다. [계산기](../../../../scripts/architecture/qa_poc_reference.py)는 API/후보를 호출하지 않는 산술/의존 그래프 검사다. 자료는 `CALCULATED_REFERENCE`이고 실제 Windows/모델/후보 실측으로 쓰지 않는다. source/가정/계산 수준을 매 행에 둔다. 공개 단가 확인일은 2026-10-11이다.

| DP의 설명용 조건 | 계산할 차이 | 그 조건에서의 해석 |
| --- | --- | --- |
| 41 충분한 typed 근거 | A의 추가 재판단 1회와 B의 코드 해결. 공통 read/음성/현재성 유지 | 가정한 call-plan에서 시간/비용 차이는 계산 가능. 실제 모델의 call 선택/정답률은 관측해야 함 |
| 41 모호한 frame 항목 | B 부분 해석 1회 추가, A도 같은 횟수일 수 있음 | 이름만으로 B를 한 번으로 고정하면 잘못된 계산 |
| 42 정상 hand-off 4회 | 공동 commit 4×0.010초와 독립 접수/반영 4×0.025초 | 0.060초는 03의 0.50초 차이 기준보다 작음. 이 값으로 큰 정상 이익/손실을 주장하지 않음 |
| 44 강한 양안의 짧은 전이 | A 6×0.010초, B 6×0.005초 + join 0.020초 | 0.010초 차이는 작음. 양안 같은 async/read 병렬성을 보존 |
| 44 교차 사건 burst | 중앙 queue 0.60초/연결 queue 0.20초라는 추가 가정 | 0.40초 잠재 차이. 실제 queue가 같거나 B join이 늘면 소멸. 이 가정이 실측되어야 조건부 주장을 강화할 수 있음 |
| 45 안정 과거/재사용 | A cache miss 40회와 B 관계 생산 20회 | 비용 차이 $0.032는 작은 차이. miss 32회가 손익분기이며 A miss 10회면 A가 더 쌈 |
| 45 첫/미게시 요청 | B query만이 아니라 생산/게시/backfill 대기 | 준비된 기억을 무료로 선주입하지 않음. N은 B가 느리고 W는 빨라질 수 있음 |

메모리 계산의 공통 동시 allocation 예시는 1,792MiB다. 41의 Context/frame 차이는 -32MiB, 42의 추가 service/receipt 상태는 +288MiB, 44의 추가 window/copy는 +48MiB, 45의 게시/생산 상태와 줄어든 원문 Context의 순차이는 +128MiB라는 **설명용 가정**을 둔다. prefix가 다른 process라고 전체 기본 메모리를 복제하지 않는다. ±절반/두 배로 바꿔 민감도를 확인한다. 이 수치는 후보의 실제 peak나 상주 상태가 해당 크기임을 주장하는 값이 아니다.

변경 용이성의 예시는 M-04에서 A의 3개/B의 4개 수정 집합이며 나머지 다섯 과제의 구체 patch 없이 여섯 과제 평균을 만들어내지 않는다. 정확성은 실제 model output 없이 가정 정답률을 만들지 않는다. **모든 QA의 정의/방법은 완성되어 있고, 아직 실행하지 않은 성능의 숫자는 가공해서 채우지 않는다.**

### 8.8 목표 판정, 번호순 선택과 tactic 기록

1. 모든 QA의 원값/분모/보호 조건/실패/근거 수준을 같은 행에 남긴다. 서로 다른 version, reference 계산과 실측을 한 우열 값으로 섞지 않는다.
2. 필수 위반을 발생시킨 후보도 여섯 축의 trade-off를 보고하되 위반이 보완되기 전 최종 적격으로 세지 않는다. 낮은 비용/메모리로 권한/오업무 효과를 상쇄하지 않는다.
3. **01부터 번호순으로 의미 있는 차이를 찾는다.** 양안 차이가 작거나 미입증인 축은 원값을 보고하고 다음 축으로 넘어간다. 상위 QA의 근거가 부족하면 하위 지표로 고른 안은 조건부 선호이며 상위 성능을 확인한 최종 선택이라고 하지 않는다.
4. 처음으로 의미 있는 상위 성능이 좋은 안을 구조 선호로 정하고 낮은 순위 목표 미달은 tactic의 보완 과제로 기록한다. 단순 목표 미달 때문에 그 축의 원값/장단점을 숨기거나 상위 축의 우위를 무시하지 않는다.
5. tactic별로 `원래 약점, 실제 변경, 비용/시간/상태 영향, 재평가할 상위 QA, 완료 기준`을 적는다. 모든 목표/필수 보호 조건의 충족 또는 사용자 리뷰로 명시적으로 개정한 계약을 확인한 뒤 최종 안이라고 기록한다.

| 약한 축 | 적용할 수 있는 tactic | 반드시 다시 확인할 것 |
| --- | --- | --- |
| 정확성 | source revision/조건 보존 검사, 필요한 확인 질문, 실제 전달/명령 idempotency | 정답 oracle 그대로, 질문 증가 시간/음성 비용 |
| 첫 반응 | local stop, 짧은 priority 전이, template, 준비와 게시 분리 | filler로 종료 대체 금지, 질문/current-check와 상태 정확성 |
| 전체 처리시간 | 독립 read 병렬, cache/부분 해석, 불필요한 재판단 제거 | 실제 의존/조건/금지 의미 보존, stale Context/권한 검사 |
| 비용 | 범위가 맞는 Context/출력 길이, 실제 hit cache, 선택적 관계 갱신 | 누락 조건/원문 예외, 폐기/배경 청구, 첫/미게시 시간 |
| 변경 | provider/source port 정규화, schema version, owner 책임 국소화 | 실제 계약 호환/이행/복원과 18개 원래 정답 |
| 메모리 | immutable 참조 공유, bounded queue/cache, 회수/압축 | 같은 근거 보존/질문/Task 기능, 압축/재조회 시간과 source gap |

아직 후보를 실행하지 않았으므로 현재 문서의 결과는 **선택 규칙/평가 계약/참조 계산 예시의 완성**이다. 이 정의를 완료했다는 이유로 A/B 승자, API 실측, Windows 실측 또는 제품 목표 달성을 선언하지 않는다.

### 8.9 발표용 등급과 원지표의 관계

제공한 레퍼런스의 `●●●, ●●◐, ●●○, ●◐○, ●○○, ◐○○, ○○○` 순서로 6~0점을 표시한다. 여섯 축 모두 개선 방향/단위가 달라 **QA 간 등급을 더하거나 평균/가중합으로 선택하지 않는다**. 등급은 각 축의 목표/개선 여유를 발표에서 읽기 쉽게 나타내는 작성자 규칙이다. 실제 선택은 §8.8의 번호순과 원지표 차이/보호 조건을 따른다.

| QA | 6점 상향 reference | 5 / 4 / 3 / 2 / 1점 경계 | 0점 |
| --- | --- | --- | --- |
| 01 높은 값이 좋음 | 정확히 100% | 각각 ≥99.6 / 99.2 / 98.8 / 98.4 / 98% | <98% |
| 02 낮은 값이 좋음 | ≤0.2초 | 각각 ≤0.36 / 0.52 / 0.68 / 0.84 / 1초 | >1초 |
| 03 낮은 값이 좋음 | ≤2초 | 각각 ≤3.6 / 5.2 / 6.8 / 8.4 / 10초 | >10초 |
| 04 낮은 값이 좋음 | ≤$0.50/8h | 각각 ≤0.70 / 0.90 / 1.10 / 1.30 / $1.50 | >$1.50 |
| 05 낮은 값이 좋음 | ≤1개 | 각각 ≤1.4 / 1.8 / 2.2 / 2.6 / 3개 | >3개 |
| 06 낮은 값이 좋음 | ≤1GiB | 각각 ≤1.6 / 2.2 / 2.8 / 3.4 / 4GiB | >4GiB |

경계는 낮은 값에서 먼저 해당하는 가장 높은 점수, 정확성은 높은 값에서 먼저 해당하는 가장 높은 점수다. 하위 구간의 반대 경계는 열려 있어 중복이 없다. 예: 02의 0.36초는 5점, `0.36 < t ≤ 0.52`는 4점이다. 반올림 전 Fraction/bytes로 판정한다. 목표를 통과한 1~6점이라도 보호 조건/필수 위반이 실패하면 **대표지표 등급 / 전체 목표 미달**을 함께 표시한다. 결과 미실시는 0점이 아니라 “실측 전”이며 숫자/기호를 넣지 않는다.

01의 100%는 오류 0의 상향 reference다. 다른 축의 상향 값은 예산을 충분히 개선한 발표용 참조이며 물리 최저값/SLA/논문이 입증한 달성값이 아니다. 6점 reference와 1점 목표 사이를 5등분했다. 05의 1개는 변화가 경계 하나에만 국소화되는 수준, 06의 1GiB는 4GiB 예산의 1/4, 시간은 기본 예산의 1/5, 비용은 $0.50의 경량 활동을 작성자 상향 reference로 정했다. 원래 요구/분모를 줄여 이 값을 맞추지 않는다.
