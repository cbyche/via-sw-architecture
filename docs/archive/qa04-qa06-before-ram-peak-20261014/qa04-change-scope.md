## 2. 왜 인력이나 개발시간 대신 모듈 수인가

사용자는 여러 개발자가 각자 AI 코딩을 사용할 때 수정 충돌과 통합 작업이 늘고 다른 담당 영역의 변경을 주저한 경험을 설명했다. 이는 **이 팀에서 나온 요구**이며 모든 조직에 대한 통계로 일반화하지 않는다.

개발시간에는 숙련도와 AI 모델 및 프롬프트 차이가 섞인다. 변경 모듈 수는 구조가 수정을 얼마나 넓게 전파하는지를 직접 보여준다. 다만 모듈 수가 충돌 수나 인력의 정확한 대체값은 아니다. 공통 모듈 한 개에 동시 수정이 집중될 수도 있다. 담당자 수와 실제 충돌 기록은 설명 자료로 남기되 주지표에 가중 합산하지 않는다.

## 3. Rust 모듈을 어떻게 세는가

Rust의 `mod`는 함수와 자료형 등의 item을 담고 공개 경계를 구성하는 단위다. 중첩할 수 있고 한 파일에 여러 모듈을 둘 수 있다. 파일을 분리해도 동일한 모듈 경로를 유지할 수 있다. [Rust Reference: Modules](https://doc.rust-lang.org/reference/items/modules.html)

`crate`는 컴파일 단위이며 그 안에 여러 모듈이 들어간다. `package`는 `Cargo.toml`로 관리하는 묶음이다. `src/lib.rs`와 `src/main.rs`가 함께 있으면 각각 다른 crate root다. 모듈 수와 crate 수 및 실행 프로세스 수는 다른 값이다. [Rust Book: Packages and Crates](https://doc.rust-lang.org/book/ch07-01-packages-and-crates.html)

평가 모듈의 고유 ID는 다음과 같다.

```text
package / crate-target / fully-qualified-module-path

예: via-core / lib / crate::interaction::dispatcher
예: via-app / bin:via / crate
```

모듈 registry에는 경로, 실제 소스 위치, 외부에 공개하는 함수와 자료형, 호출 의존성, 소유 prompt/schema/config를 기록한다. `crate` root도 자신이 직접 정의하는 항목이 바뀌면 한 개다. Windows 평가 build의 동일 feature profile을 사용하며 실제 제품에서 사용하는 대체 feature 경로도 변경 과제의 완료 조건에 포함한다. 사용하지 않는 테스트 전용 모듈은 운영 모듈 수에 넣지 않는다.

| 변경 상황 | 집계 규칙 |
| --- | --- |
| 모듈 내부 함수, 자료형, trait 구현, import, re-export, 연결 코드 수정 | 해당 모듈 1개 |
| 모듈 추가 또는 삭제 | 각각 고유 모듈 1개 |
| 하위 모듈만 수정 | 조상 모듈을 자동으로 더하지 않음 |
| 상위 모듈의 `mod` 선언이나 연결 코드도 수정 | 상위 모듈도 1개 |
| inline 모듈과 `mod.rs` 및 `#[path]` | 파일명이 아닌 해석된 모듈 경로로 집계 |
| 운영 prompt/schema/config만 수정 | 사전에 지정한 소유 모듈의 변경 1개. 공용 자산은 공용 소유 모듈로 등록 |
| `Cargo.toml` dependency/feature 또는 build 설정 수정 | 담당 crate root 또는 `build.rs` root를 사전에 소유 모듈로 지정. 설정 변경을 집계에서 숨기지 않음 |
| 같은 외부 자산을 여러 모듈이 읽음 | 읽는다는 이유로 전부 추가하지 않음. 이 데이터를 사용하는 코드나 자료형도 수정된 모듈은 별도 집계 |
| 자동 생성 코드 | 수정한 schema/generator의 소유 모듈을 셈. 결정적으로 재생성된 산출물만으로 수를 늘리지 않되 수동 어댑터 수정은 포함 |
| 테스트, 주석, 포맷만 수정 | 운영 모듈 수에서 제외. 회귀 검증은 완료 조건 |
| 경로 이동/이름 변경 | 필요한 변경이면 이전 경로와 새 경로를 대응한 논리 모듈 1개로 셈. 이동 중 실질 분할/병합은 변화한 모듈별로 기록 |

이는 `.rs` 파일 수나 기능 책임 수를 세는 방법이 아니다. 같은 책임 안에서도 실제 여러 모듈을 수정했다면 모두 센다. 반대로 모듈이 여러 책임을 담는다고 가상으로 나누어 세지 않는다.

### 모듈 포장으로 점수를 바꾸지 않는 조건

1. 양안의 모듈 registry와 기능 충족 기준을 변경 과제를 수행하기 전에 고정한다.
2. 한 안만 거대한 모듈로 합치거나 불필요한 얇은 모듈로 쪼개지 않았는지 독립 검토한다. 외부에 공개하는 함수와 자료형, 상태 소유, 의존성을 함께 본다.
3. 필요한 새 모듈은 허용하고 변경 수에 포함한다. 평가용으로 코드만 옮기는 리팩터링은 해당 기능 변경과 분리해 기록한다.
4. 검토 결과 적절한 모듈 경계가 양안에서 달라도 강제로 같은 수로 맞추지 않는다.
5. 코드가 없는 현 단계의 수는 `DESIGN_CHANGE_REVIEW`다. 이후 Rust diff로 확인한 값만 `IMPLEMENTED_CHANGE_REVIEW`라고 부른다.

## 4. 지표와 공통 변경 모집단

```text
M_i = 변경 과제 i를 완료하기 위해 수정 / 추가 / 삭제한 고유 모듈의 집합
X = (|M_1| + |M_2| + ... + |M_6|) / 6
```

각 과제는 변경 전의 같은 코드 버전에서 **독립적으로** 수행한다. C01을 적용한 뒤 그 이익을 C02에 누적시키지 않는다. 같은 모듈이 서로 다른 두 과제에서 바뀌면 각 과제에 한 번씩 들어간다. 수정 후 기능을 수행하지 못하거나 필수 회귀가 깨진 경우 작은 변경 수를 성공 점수로 인정하지 않는다. 미완료 과제는 분모에서 빼지 않고 전체 평가를 `INCOMPLETE`로 표시한다.

아래 6개는 새 비교용 변경 요구 제안이다. 기존 책임 단위 평가의 M01~06을 이름만 바꾼 결과가 아니다.

| ID | 실제로 바꿀 요구 | 완료 기준 |
| --- | --- | --- |
| C01 | 모델에 보내는 요청과 모델에서 받는 답변 및 사용량 데이터의 형식을 변경 | 형식이 달라져도 같은 요청을 보내고 같은 답과 취소 결과 및 사용량을 얻음 |
| C02 | Agent에 보내는 작업 요청과 취소 요청 및 접수 확인 데이터의 형식을 변경 | 같은 작업 ID를 사용하고 실제 접수 여부를 계속 구별함 |
| C03 | 화면과 과거 자료에서 읽는 좌표와 시각 및 버전 데이터의 형식을 변경 | 형식이 달라져도 같은 자료의 같은 위치와 시점을 가리킴 |
| C04 | Agent 답변 전체를 교체하던 기능에 지정 문단만 고치는 기능을 추가 | 해당 문단과 그 문단의 음성 대기 내용만 바꾸고 다른 문단과 다른 업무는 유지함. 문단은 `section_id`로 지정 |
| C05 | 과거 답변 조회에 해당 설명의 원본 위치와 버전을 함께 보여주는 기능을 추가 | 실제 전달한 설명마다 `source_id/revision/extent` 목록을 반환. 생성했지만 전달하지 않은 설명은 제외 |
| C06 | 문서 전체의 정보 사용 허용을 철회하던 기능에 지정 구간만 철회하는 기능을 추가 | `source_id + extent`에 해당하는 원본과 이를 사용한 대기 답변의 신규 사용을 막고 나머지 허용 구간은 유지 |

**C01~C03은 데이터 형식 변경 3건이고 C04~C06은 기능 확장 3건이다.** 앞의 세 건은 외부 데이터 형식을 바꾸어도 VIA가 제공하는 기능을 유지하는 변경이다. 뒤의 세 건은 부분 정정과 원본 조회 및 부분 허용 철회를 추가하는 변경이다.

각 DP를 비교할 때 나머지 부분은 같은 코드로 두고 해당 DP 부분만 A와 B로 바꾼다. 모든 DP에서 여섯 변경을 같은 비중으로 평가한다. 어떤 변경이 해당 DP의 구조 차이와 무관해도 전체 VIA에서 바꾼 모듈 수를 기록하며 결과에서 삭제하지 않는다.

현재성 검사와 전달 기록 및 허용 철회 자체는 이미 필요한 기능이다. C04~C06은 그 기능의 처리 범위를 넓히는 평가 과제다. 기존 안이 이미 추가 기능을 제공하면 0개 변경으로 기록한다. 평가 전에 여섯 변경의 적용 전후 동작과 완료 조건을 고정한다.

## 5. 목표 3개의 도출 근거와 한계

**제안하는 팀 개발 예산:** 데이터 형식 변경 C01~C03은 각 1개 모듈 안에서 처리하고 기능 확장 C04~C06은 각 5개 모듈 이내에서 처리하는 것을 목표로 한다. 대표 변경의 평균 목표는 다음과 같다.

```text
(데이터 형식 변경 3건 × 1개 + 기능 확장 3건 × 5개) / 6 = 3개/과제
```

이 수치는 Rust나 SW 공학 연구가 보장한 최적 모듈 수가 아니다. **팀의 협업 요구를 수치화하기 위한 작성자 예산 제안**이다. 단순 변경의 모듈 구성에 항상 root 수정이 필요한 경우 평균 예산을 3.5개로 재검토할 수 있지만 양안에 동일한 규칙을 적용하고 이전 기준을 보존한다. 기존의 “18개 책임 중 3개” 근거는 실제 Rust 모듈 지표에 사용하지 않는다.

평균이 목표를 충족해도 개별 과제에서 5개를 초과하면 원인과 수정 목록을 공개한다. 이것은 두 번째 가중 지표가 아니라 평균에 가려진 집중 파급의 검토 조건이다. 현재 3개와 5개는 팀 승인 완료값이 아니다.

## 6. 0~6점 구간 — CHG-v1 제안

| 점수 | 표시 | 평균 변경 모듈 수 X |
| --- | --- | --- |
| 6 | ●●● | 0 ≤ X ≤ 1.0 |
| 5 | ●●◐ | 1.0 < X ≤ 1.4 |
| 4 | ●●○ | 1.4 < X ≤ 1.8 |
| 3 | ●◐○ | 1.8 < X ≤ 2.2 |
| 2 | ●○○ | 2.2 < X ≤ 2.6 |
| 1 | ◐○○ | 2.6 < X ≤ 3.0 |
| 0 | ○○○ | X > 3.0 |

3개 이하가 목표 충족이다. 각 신규 변경이 한 모듈 안에서 끝나는 1개를 최상위 경계로 두고 1개와 3개 사이를 0.4개 간격으로 나눈 **평가 설계 규칙**이다. 모든 과제가 실제 신규 구현 변경을 필요로 하면 평균의 최솟값은 1개이며 이때 만점에 도달한다. 이미 지원한 과제의 0개를 숨기지는 않지만 만점 사례를 만들기 위해 불필요한 과제를 넣지 않는다. 미측정 / 미완료는 0점과 구별한다. 같은 점수 구간의 유의한 원값 차이는 원값으로 보존한다.

## 7. DP별 예상 결론과 발표 한 문장

**예측 기준은 C01~06 전체이며 아직 실제 모듈 diff를 만든 것은 아니다.** 아래 A/B 우열은 사전 가설이고 최종안 선택이 아니다.

| DP | 사전 예상 | 구조를 설명하는 한 문장 | 주요 확인 과제 |
| --- | --- | --- | --- |
| 44 | **A 우세 예상, 핵심 후보** | **“A는 여러 응답 경로의 진행 규칙을 중앙에서 바꾸므로 단계별 연결과 결합 규칙까지 수정할 범위를 줄인다.”** | C04/C06의 Dispatcher / 진행 상태 대 Stage / Join / 취소 계약 |
| 45 | **A 우세 예상, 핵심 후보** | **“A는 필요한 과거 관계를 조회할 때 구성하므로 새 관계를 추가할 때 생산 / 저장 / 재게시 계약까지 바꿀 필요가 적다.”** | C05/C06의 요청 조합과 cache 대 Publisher / schema / reader / 재생산 |
| 47 | **A 우세 예상, 보조 검토** | “A는 지칭 결과를 한 판단 계약으로 만들므로 근거 계약 변경을 여러 후보 생산자와 결합기에 전파할 범위가 적다.” | C03/C06; 국소 adapter 변경은 동점 예상 |
| 42 | **동점 예상, 핵심 커버리지 제외** | “모듈화한 통합 Core와 독립 서비스 모두 외부와 주고받는 데이터 형식 변경을 같은 경계에서 흡수할 수 있다.” | C02/C04/C06; 서비스 경계만으로 B의 모듈 수 감소를 주장하지 않음 |

강한 A도 handler, adapter, cache와 부분 갱신을 가진다. B도 공통 schema와 공통 제어 라이브러리로 변경을 국소화할 수 있다. 실제 최소 diff가 같으면 동점이다. **현재 QA4의 두 핵심 연결은 모듈 변경 실험에서 확인해야 하는 가설**이다.

### 이해 예시 — 측정값 아님

C04에서 A가 `notice_handler`, `dispatcher`, `publication_control`을 수정하고 B가 `notice_stage`, `event_schema`, `publication_join`, `flow_wiring`을 수정했다면 A는 3개이고 B는 4개다. “같은 기능 책임이니 양쪽 다 3개”로 합치지 않는다. 반대로 B가 기존 schema로 처리해 `notice_stage`만 바꾼다면 B는 1개로 기록하며 초기 예측을 수정한다.

## 8. 최소 PoC와 증거

모델 학습이나 전체 앱 구현은 필요 없다. 실제 구조의 Rust module skeleton, 공개 타입 / port, 상태 전이, prompt/schema 소유와 관련 회귀만 구현한 뒤 C01~06의 독립 patch를 만든다. 모델은 고정한 응답 fixture로 대체 가능하다. 기능적인 의미 해석 품질을 이 PoC로 검증했다고 주장하지 않는다.

필요한 결과는 `변경 전 모듈 목록`, 과제별 요구 diff, 실제 Git diff, 고유 변경 module 목록, 수정 이유, 해당 계약 회귀 결과다. reviewer는 A/B의 module 분해 수준과 빠진 변경을 먼저 확인하고 집계를 별도로 재현한다. AST와 자산 소유표로 집계한 뒤 사람이 최종 검토한다. 무관한 준비 리팩터링이나 테스트 변경을 섞어 수를 부풀리지 않는다.

**차이 인정 제안:** 전체 평균 0.5개 이상 차이이며 두 독립 검토자의 변경 집합 이견을 해소했을 때 주요 차이로 인정한다. 숫자는 실용 구분 규칙이며 통계 검정 결과가 아니다.
