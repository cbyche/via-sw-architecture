# Decision Point 선발 원칙

> 사용자의 최우선 요구: 중요한 VIA 문제를 푸는 다른 SW Architecture를 비교한다. Component의 존재·부재·대체가 그림에서 보여야 하며, 단순 분할·통합이나 설정 변경으로 끝나면 안 된다.

## 출발점

“어느 Component를 나눌까?”가 아니라 **“VIA가 이 기능을 성립시키려면 무엇을 지속적으로 알아야 하고, 무엇을 실행·저장·복원해야 하는가?”**를 묻는다. Target은 그 질문의 이미 선택된 한 답이다. 다른 답은 target의 Component 목록을 그대로 유지해야 할 이유가 없다.

## 필수 통과 기준

| 기준 | 채택할 설명 | 제외할 설명 |
| --- | --- | --- |
| 문제의 중요성 | 고정 UC의 구체적 실패가 정확한 대상·진행·응답·복구를 방해 | 범용 기술이 유행하거나 그림을 풍성하게 만들 수 있음 |
| 방안 1 충실성 | 실제 cache·transaction·outbox·동시 세션·삭제 gate를 보존 | target을 RAM-only·단순 호출·cache 없음으로 약화 |
| 실제 구조 차이 | 새 실행체·helper·파생 저장소 또는 책임/권위의 제거·대체 | 함수를 따로 박스로 그리거나 같은 책임에 새 이름 부여 |
| 메커니즘 차이 | 누가 무엇을 생산·소유하고 언제 확정·무효화·복원하는지 달라짐 | 화살표 방향·payload·threshold·프롬프트만 다름 |
| 충분한 대안 | 정상 기능·완료 조건 유지. 장애 시 공통 실패·보류 요구를 충족하고 달라지는 기능 손실·복구 범위 공개 | 이상적 정상 경로만 제시하거나 문제를 Agent에게 떠넘김 |
| 품질 인과 | 구조 → 추가/제거되는 작업·오류·변경 범위 → 해당 ASR | “분리했으니 성능·유지보수·신뢰성 모두 좋아짐” |
| 현실적인 선택 조건 | 비용을 감수할 만큼 반복되는 요구·규모·변화가 있음 | 모든 환경에서 target 또는 대안이 무조건 우월 |
| 독립성 | 한 구조 주장에 집중하고 나머지 기능·dependency 조건 고정 | workflow·event sourcing·새 모델·분산 배치 효과를 한꺼번에 합산 |

## 그림의 선발 시험

Component 이름과 화살표 라벨을 잠시 가려도 **어떤 생산체·실행체·저장 체계가 추가되거나 없어졌는지** 설명할 수 있어야 한다. 다음으로 라벨을 읽어 그 차이가 실제 기능·수명·상태 계약임을 확인한다. 외형만 다른 배치는 통과하지 않는다.

같은 Component의 확대도는 별도 배포 instance가 아님을 표시한다. 내부 책임을 설명하기 위한 모듈 이름은 target에 이미 존재하는 독립 Component인 것처럼 취급하지 않는다. 1안과 2안에 공통된 기능은 검정, 대체·추가·제거되는 책임은 양쪽 모두 파랑이다. 별도 process를 주장할 때만 점선 process 경계를 쓴다.

## Steelman과 반증

2안에도 가장 합리적인 cache·bounded queue·version 관리·오류 복구를 허용하되 비용을 생략하지 않는다. 1안에도 이미 있는 최적화와 내구성을 유지한다. 각 문서에 **2안을 선택할 조건**, **1안을 유지할 조건**, **현재 선택의 근거가 무너지는 관찰**, **대안의 도입 가치가 사라지는 관찰**을 적는다.

후보 수는 목표가 아니다. 이전 일곱 후보·VIA-DP의 번호를 새 후보에 배분하지 않는다. 알고리즘은 구조 안의 구현 수단일 수 있지만 그것만 다른 두 안을 이번 주력 후보로 선발하지 않는다.
