# 04-32. 화면 지칭의 정확성을 위한 대상 결합 — 통합 해석과 분리 생산 후 결합

> 발표용 구조 비교 / 2026-10-04 / [가이드](./04-30-comparison-guide.md) / 이전: [의미 구성](./04-31-semantic-construction.md) / 다음: [업무 대화](./04-33-dialogue-coordination.md)

**같은 “이 표와 저 표”를 A는 말과 화면을 함께 보는 모델이 연결하고, B는 화면 후보와 말의 지시 조건을 따로 생산한 뒤 코드가 연결한다.** A는 자유로운 표현을 함께 이해하기 좋고, B는 어느 시점의 어떤 근거끼리 연결했는지 명시하기 좋다. B는 후보나 관계 표현에 담기지 않은 뜻을 자동 해결하지 못한다.

읽는 순서는 **사용자 상황 → 구조도 → 같은 사례의 흐름 → 품질 손익 → 가장 싼 전환 반론**이다. 두 그림에도 이 상황, 생산 경로, 실패 처리와 선택 조건을 넣었다. 그림 없이 읽을 때에는 §3의 번호 흐름과 §4의 사건 표를 따른다.

## 1. 왜 VIA에서 중요한가

사용자는 첫 화면의 왼쪽 표를 가리키며 “이 표와”라고 말한다. 스크롤한 다음 오른쪽 표를 가리키며 “저 표를 비교해줘”라고 이어간다. VIA가 마지막 화면만 보고 두 표를 고르면 앞의 표를 잃는다. 두 포인터 위치만 저장해도 서로 다른 화면의 좌표를 같은 화면에 붙이면 틀린다.

UC-03/04의 화면 지칭과 UC-06의 보완을 다룬다. 말, 화면과 포인터를 한 대화에서 결합하는 능력은 VIA의 핵심 기능이다. 목표는 **사용자가 실제로 지시한 두 관측 대상을 올바르게 연결해 같은 비교 요청으로 넘기는 것**이다. 비교 업무의 분석 방법과 Tool 계획은 Downstream Agent가 결정한다.

## 2. SW Architecture에서 무엇이 어려운가

화면 인식, 발화 인식, 포인터 사건은 서로 다른 시점에 도착하고 나중에 수정될 수 있다. 화면의 왼쪽이라는 관계도 어떤 창의 어느 시점인지에 따라 바뀐다. SW는 무엇을 보존하고, 어떤 중간 표현을 생산하고, 누가 최종 대상 관계를 결정하며, 어느 결과를 다시 계산할지 정해야 한다.

**한 번의 공동 해석에 결합 판단을 맡길 것인가, 두 생산 경로와 명시적 결합 절차로 나눌 것인가**가 설계 질문이다. 전자는 해석의 유연성을 얻지만 잘못된 결합의 내부 원인을 분리하기 어렵다. 후자는 시간과 위치 조건을 검사 가능한 형태로 만들지만 중간 표현에서 정보가 빠질 수 있다.

이전의 “화면 이미지 vs 앱 객체 API”는 같은 참조에 함께 넣을 수 있어 주요 구조 비교로 부족했다. 그 철회 판단은 유지한다. 새 A/B 모두 이미지와 공개 객체 정보를 사용할 수 있다. **자료 제공자 종류가 아니라 대상 관계를 생산하는 구조**를 새로 비교한다. [이전 비교 보존본](../../../archive/decision-comparisons-before-presentation-2026-10-04/04-32-screen-grounding.md)은 현재 권고가 아니다.

## 3. 공통 조건과 두 구조

Interaction Manager는 동의한 화면, 포인터, 선택 사건을 기록하고 Speech Input Worker의 발화 구간/수정 버전을 연결한다. Context Manager는 창, 관측 시점과 자료 버전이 붙은 유한 근거 묶음을 제공한다. 양안의 같은 근거에는 공개 객체 ID가 있으면 포함하고, 없으면 당시 화면 영역을 쓴다. 현재 화면으로 없어진 과거 관측을 대신하지 않는다.

**관측 대상**은 특정 화면에서 확인한 영역이나 객체 후보다. **지시 조건**은 “첫 번째 ‘이 표’가 가리키는 것”, “같은 화면의 오른쪽 후보”처럼 대상을 고르는 조건이다. **결합**은 어느 지시 조건이 어느 관측 대상을 가리키는지 정하는 일이다. 관측 ID는 현재 문서를 수정할 권한이나 영구 객체 ID가 아니다.

Model Access가 같은 한 벌의 Omni를 사용한다. B의 두 생산자는 서로 다른 논리 호출이며 모델을 두 벌 로드하지 않는다. 별도 학습이나 새 시각 모델은 전제하지 않는다. 아래 표현을 모델에서 얻는 실제 성공률은 미측정이다.

### A. Joint Grounding Interpreter의 통합 해석

새 비교 책임 이름인 **Joint Grounding Interpreter**는 화면 지칭 전체를 해석하는 Component다. 기존 Request Interpreter 안에 구현할 수도 있으나 여기서는 비교할 책임을 펼쳐 그렸다.

1. Request Controller가 입력 구간을 지정하면 Context Manager가 당시 화면들과 포인터 궤적, 발화 시점 및 같은 범위의 대화 근거를 반환한다.
2. Joint Grounding Interpreter는 Model Access에 **말 + 화면 + 시간 연결**을 함께 보낸다. 모델이 `첫 지시 → 표 L@7`, `둘째 지시 → 표 R@8`, `관계=비교`라는 완성 대상 관계를 제안한다.
3. 내부 **대상 검증기**는 제안된 관측 ID가 실제 근거에 있고 창/시간 범위가 맞는지 확인한다. 잘못된 ID와 명백한 시간 모순은 A도 차단한다. 나머지 의미가 불분명하면 제한된 재해석이나 질문으로 돌린다.
4. Joint Grounding Interpreter는 검증한 관계 또는 미해결 지시를 Request Controller에 반환한다. Controller가 현재 의도/권한을 검사하고 Request Interpreter의 전체 요청 의미에 결합한다. 확인이 끝난 명령만 Task Manager와 Agent Gateway를 거친다.

A도 화면 전처리, 객체 힌트, 관측 cache와 일부 재시도를 사용할 수 있다. 그러나 **대상 간 대응 관계의 정상 생산자는 공동 해석 모델**이다. 과거 지칭 정정이 오면 관련 원문과 화면을 다시 모아 관계를 재제안한다.

### B. 두 종류의 근거를 생산하고 Grounding Join Engine이 결합

**Grounding Coordinator**는 한 지칭 입력의 버전과 두 생산 결과의 도착/수정 상태를 관리한다. 내부의 **근거 버전 관리기**가 입력, 관측, 두 결과가 같은 해석 시도를 가리키는지 확인한다. 영구적인 세계 모델을 새로 만들지 않는다.

1. Coordinator는 Context Manager에서 받은 **같은 근거 묶음**을 두 경로에 나눈다. **Scene Candidate Producer**에는 화면/공개 객체/포인터/시점을, **Deictic Anchor Producer**에는 발화/시점/허용된 이전 지칭 ID를 보낸다. 두 번째 생산자는 이번 화면 원본을 보지 않는다.
2. Scene Candidate Producer는 같은 Model Access 또는 신뢰할 수 있는 객체 읽기를 통해 `관측 ID, 창, 시점, 영역, 표 같은 확인 가능한 속성, 불확실성`의 후보를 반환한다. 말이 “첫 표”인지 “둘째 표”인지는 결정하지 않는다. 요청이 지정한 관측 구간에서만 생산하며 항상 화면 전체를 분석하지 않는다.
3. Deictic Anchor Producer는 같은 모델로 `지시 구간, 후보 종류, 시간/위치 조건, 이전 참조, 비교 관계`를 반환한다. 화면에서 실제 표 ID를 고르지 않는다. 말뜻이나 시간 정렬을 확신할 수 없으면 복수 조건 또는 미해결을 반환한다.
4. **Grounding Join Engine**은 두 결과를 받아 코드로 조건을 적용한다. 같은 창/관측 구간, 포인터 포함 또는 명시된 위치, 대상 종류를 만족하는 후보를 연결한다. 후보가 없거나 여러 개이거나 관계를 표현하지 못하면 해당 지시를 미해결로 반환한다. 자신이 자연어/픽셀을 다시 해석하거나 없는 후보를 만들지 않는다.
5. Coordinator는 결합 결과와 사용한 두 근거 버전을 Request Controller에 반환한다. 새 발화/관측 수정으로 영향을 받은 생산 결과와 결합만 무효화한다. 최종 의도/권한 검사와 요청 의미/Agent 인계는 A와 같다.

이 구조의 목적은 **서로 다른 관측 시점의 대상을 잘못 섞는 문제를 명시적 결합 계약으로 다루는 것**이다. B가 항상 더 정확하다는 주장은 아니다. 두 생산 단계 중 하나가 대상을 누락하거나 말을 잘못 조건화하면 결합 코드도 틀린 결과 또는 미해결을 낸다.

### 3.1 같은 값으로 보는 중간 자료

| 단계 | A | B |
| --- | --- | --- |
| 공통 관측 | 화면 7의 표 L, 화면 8의 표 R, 포인터 p1/p2와 발화 시점 | 동일. B에만 정답 영역을 제공하지 않음 |
| 대상 생산 | 모델이 원문/그림을 함께 보고 `d1=L@7, d2=R@8` 제안 | 화면 경로가 `L@7, R@8, …` 후보, 언어 경로가 `d1: t1의 표, d2: t2의 표` 조건 생산 |
| 결합 결정 | 모델이 선택한 대응을 검증 | Join Engine이 시점/포인터/종류 조건으로 후보 집합 계산 |
| 최종 결과 | 검증된 두 참조 + 비교 관계 | 결합된 두 참조 + 비교 관계 + 사용한 근거 버전 |
| 범위 밖 표현 | “붉은 선이 꺾이기 직전의 부분”을 공동 해석할 기회 | 장면 후보/관계 언어가 그 세부 영역을 표현하지 못하면 재지칭 필요 |

### 3.2 결합 코드가 실제로 하는 최소 판단

예를 들어 `d1`의 후보를 고르는 일은 다음처럼 나뉜다. 수치는 시험 전 임의로 정하지 않으며, 시간 구간과 불확실성은 실제 입력 계약으로 확보해야 한다.

1. 언어 생산자가 반환한 지시 구간과 포인터 사건이 어느 창/관측 구간에 속하는지 확인한다. 시간 근거가 없거나 여러 구간에 걸치면 그 사실을 유지한다.
2. 해당 관측의 후보 중 포인터/선택 영역과 관계가 있고, 요구한 종류/위치 조건을 만족하는 집합을 만든다. “오른쪽”의 기준 창/후보 집합도 명시되어야 한다.
3. 후보가 유일해도 관측 누락이나 불확실한 속성 때문에 다른 후보를 배제하지 못했다면 확정하지 않는다. 후보 없음은 자료가 없다는 확정 사실과 구별한다.
4. 확정 가능한 후보에는 원문 구간, 관측 ID, 화면/입력 버전과 적용 조건을 붙인다. 첫 지시 조건만 바뀌면 첫 결합을 다시 계산하되, 두 지시의 관계가 함께 바뀌면 전체 관계를 재검토한다.

A에도 시간/ID 검증을 넣을 수 있다. 차이는 A에서는 모델이 만든 완성 대응의 검증이고, B에서는 이 결합이 대응의 생산이라는 점이다. 이 작은 규칙으로 표현하지 못하는 “저 사람이 관심을 가질 부분” 같은 지칭을 처리한다고 주장하지 않는다.

| 사건 | A | B |
| --- | --- | --- |
| 1. 왼쪽 표를 가리키며 “이 표와” | Interaction Manager가 화면 7/p1/t1 기록 | 같은 기록 |
| 2. 스크롤 후 “저 표를 비교” | Context Manager가 화면 7/8과 p1/p2, 원문을 함께 반환 | Coordinator가 같은 기록을 화면 후보와 언어 조건 생산 경로에 전달 |
| 3. 두 대상 결정 | Joint Grounding Interpreter가 공동 모델 해석/검증 후 L@7/R@8 반환 | 두 Producer 결과를 받은 Join Engine이 조건 결합 후 L@7/R@8 반환 |
| 4. “첫 표는 왼쪽 말고 오른쪽” | 해당 장면/원문을 다시 해석해 첫 참조 재제안 | 언어 조건 수정, 기존 화면 후보에 해당 영역이 있으면 재결합. 없으면 필요한 장면만 재생산 |
| 5. 현재 검사 후 인계 | Request Controller가 수정 버전/허용 자료를 확인해 Task Manager/Agent Gateway에 전달 | 동일. 옛 결합 결과가 늦게 도착하면 버전 불일치로 채택하지 않음 |

단순 스크롤은 과거 관측 L@7을 현재 화면의 다른 표로 바꾸지 않는다. 현재 원문 조작이 필요한 업무라면 양안 모두 Context Manager로 현재 source를 재확인하고 Agent capability에 맞는 자료로 인계한다. 보이지 않는 과거 관측과 현재 문서의 일치를 무조건 보장하지 않는다.

## 5. 어떤 상황에서 각 안을 선택할 것인가

| 조건 | A의 선택 이유와 대가 | B의 선택 이유와 대가 |
| --- | --- | --- |
| 낯선 앱/복잡한 도형과 자유로운 말 | 원본을 함께 해석해 표현 폭을 유지. 모델 오결합의 원인을 분리하기 어려움 | 중간 후보/조건으로 표현하지 못하면 자동 지원 제한, 사용자 재지칭 증가 |
| 여러 시점의 표/목록을 순차 지칭 | 같은 모델이 전후 문맥을 연결. 관련 근거가 길어지고 재해석 비용 발생 | 명시된 시간/위치 결합과 국소 정정이 유리할 가능성. 두 생산자의 누락/오해 위험 |
| 짧은 단일 지칭 | 한 공동 해석과 검증으로 충분할 수 있음 | 후보 생산/동기화/결합의 비용이 이득보다 클 수 있음 |
| 반복해서 대상 조건만 수정 | 관련 관측 cache를 써도 대응 관계는 모델이 재제안 | 같은 후보 집합이 충분하면 조건 재해석/결합만 수행. 후보 최신성 관리 필요 |

B를 선택하려는 조직은 지원할 지시 관계와 후보 속성의 범위를 명시하고, 새 앱/표현을 추가할 때 두 생산 계약과 Join Engine을 함께 관리할 수 있어야 한다. 이런 범위를 제품 가치와 맞출 수 없다면 A가 합리적이다.

## 8. 가장 싼 확장과 역전환으로 반박하기

### 8.1 A에 화면 분석 helper를 붙이면 B인가

화면 후보를 만들어 원문/이미지와 함께 공동 모델에 넣는다면 **A의 보조 근거 확장**이다. 최종 대응은 여전히 모델이 만들며 B의 코드 결합이 없다. A의 강한 혼합안으로 인정하고 B와 비교할 수 있다. 모든 값에 시간/ID 검증을 붙이는 것도 A에 허용한다.

B의 성질은 보조 후보 존재가 아니라 **화면 후보와 언어 조건을 독립적으로 수정하고, 결합 코드가 최종 대응을 생산한다는 것**이다. 이를 얻으려면 다음 작업이 필요하다.

- 모델 출력 계약을 완성 대응 하나에서 서로 다른 두 자료로 분해하고, 어떤 뜻이 표현 가능한지와 미해결 규칙을 정의한다.
- 두 생산 결과의 버전 결합, 누락/복수 후보와 재생산 범위, 정정 시 의존성 무효화를 설계한다.
- 기존 공동 해석이 묵시적으로 처리하던 시각/언어 관계를 Join Engine의 지원 범위로 옮기거나 기능 손실로 남긴다.

이것은 대상 처리 서브시스템의 생산/정정 경로를 대체하는 재설계다. Task/Agent 계약이나 PC 전체를 바꿔야 하는 것은 아니다. **별도 Component로 구현했다는 사실이나 변경 파일 수를 근거로 삼지 않는다.** 이미 A가 같은 분리 생산/코드 결합을 가지고 있다면 그 부분은 B 계열이며 새 대안으로 중복 계산하지 않는다.

### 8.2 B에 공동 해석 fallback을 붙이면 해결되는가

가능하다. 표현 가능한 명확한 지칭은 B, 복잡한 표현은 A가 처리하는 혼합은 현실적인 세 번째 구성이다. 추가 공동 호출을 넣는 것은 B를 이미 구현했다면 작을 수 있다. 그러나 혼합은 두 생산 체계, 경로 선택, 같은 참조의 유효성/정정 및 시험을 유지한다. 어느 사례가 어느 경로를 썼는지 분리하지 않으면 B의 장점으로 A의 성공을 가져오게 된다.

혼합이 우세할 가능성도 남긴다. 이 가능성은 A/B의 생산 구조가 같다는 뜻은 아니며, 혼합이 항상 과도하게 비싸다는 주장도 하지 않는다. 최종 선정 전에 단순 A+검증 또는 이 혼합이 필요한 가치를 충분히 제공하는지 비교해야 한다.

| 비용 | A → B | B → A |
| --- | --- | --- |
| 기능 개발 | 두 Producer와 결합 규칙, 지원 관계 목록 | 공동 해석/검증 경로 구현. 기존 Model Access/관측을 재사용 |
| 상태 이행 | 진행 중 지칭을 끝내고 새 요청부터 적용 가능 | 동일. 과거 참조를 억지로 변환하지 않음 |
| 핵심 재설계 | 완성 대응 생산/전체 재해석을 독립 근거 생산/코드 결합/부분 무효화로 전환 | 두 생산 결과를 최종 판단에서 제거하고 공동 입력/재해석으로 변경. 더 단순한 역전환일 수 있음 |

## 9. 현재 판단과 반증 조건

**새 메커니즘으로 화면 지칭 주제를 발표 후보에 복귀시킨다.** 옛 이미지/객체 비교를 다시 합격시킨 것이 아니다. 후보 결합의 권한, 중간 표현, 실행 의존성과 정정 경로가 달라지는 제한된 서브시스템 선택으로 비교한다. 31은 여러 대화에 걸친 목표/금지 조건의 생성이고, 32는 말과 화면 사이의 대상 결합이다. 서로 강제하거나 같은 이익으로 중복 계산하지 않는다.

A는 표현 폭과 단순한 운영 경로를 우선할 때, B는 명시적 순차 지칭/반복 정정의 비중이 높고 지원 관계를 관리할 수 있을 때 선택 이유가 있다. B의 표현 손실이 VIA의 핵심 사용성을 크게 해치거나 A+시간/ID 검증만으로 필요한 정확성을 얻으면 B 채택 이유가 약해진다. 두 Producer를 같은 모델로 나눠 호출했을 때 오류/지연/자원 비용이 이익을 상쇄하는 경우도 반증이다.

이것은 작성자의 구조 설계 판정이다. 모델 출력 품질, 실제 입력 정렬, 표현별 지원률과 품질 우위는 구현/측정 전이다. 발표에서 확정 사실, 조건부 이익과 미확인을 구별한다.
