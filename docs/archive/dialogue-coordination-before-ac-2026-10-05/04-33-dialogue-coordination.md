# 04-33. 사용자 의도의 정확한 이해를 위한 판단 책임 — 통합, Task별, 기능별 판단

> 상태: **STAGE_4_ABC_EXPLORATION / 발표용 세 대안 비교 / 미선정 / 미측정** / 2026-10-05
> [비교 가이드](./04-30-comparison-guide.md) / [Agent 분해 지도](./04-50-agent-architecture-decision-map.md#area-02) / [현재 작업](./00-workplan.md)
> 사용자 요청에 따라 기존 A/B를 A/B/C로 재구성했다. 이전 B의 Task 없는 주제 actor는 현재 B에 자동 승계하지 않는다. [이전 세대](../../../archive/dialogue-coordination-before-abc-2026-10-05/README.md)는 검토 이력이다. 문서 작성과 게시 승인은 구조 채택이나 Stage 5/6 진행 승인이 아니다.

**같은 사용자 의도를 한 주체가 통합해서 이해할지, Task별 주체가 자기 맥락으로 이해할지, 기능별 주체가 부분 판단을 결합할지를 비교한다.** 판단 주체 수보다 누가 어떤 근거로 의미를 만들고 충돌 때 무엇을 다시 판단하는지가 핵심이다. VIA는 요청 이해와 대화 및 위임을 담당하고, 실제 보고서 작성과 메일 발송의 계획, 도구 선택과 실행은 Downstream Agent가 담당한다.

## 1. 발표용 메인 비교 — 이 그림 한 장으로 설명한다

![사용자 의도의 정확한 이해를 위한 A/B/C 판단 책임 비교](./diagrams/choice33-structure.svg)

[편집용 draw.io](./diagrams/choice33-structure.drawio) / [발표 삽입용 PNG](./diagrams/choice33-structure.png)

메인은 2560×1440의 16:9 그림이다. 위의 같은 입력과 정정을 읽고, 세 열에서 의미 생산자와 근거/상태, 요청과 반환을 따라간 뒤 공통 채택 경계와 아래의 손익을 설명한다. 세 안을 동시에 실행하는 시스템이 아니다. 공통 줄의 실제 전달 기록은 이후 해석의 근거로 돌아온다. 상단과 하단에 반복된 Request Controller는 각 안의 동일 Component를 서로 다른 단계에서 펼친 것이다. 네모에는 Component 이름만, 원통에는 상태 이름만 쓰며 동작은 연결과 바깥 설명에 둔다.

### 1.1 그림을 짚으며 설명하는 발표 대본

1. **같은 목표:** “보고서는 PDF, 메일에는 그 보고서 결론”을 이해하고, 나중에 “결론 대신 표만”이라고 바꾸면 PDF는 유지해야 한다. 새 질문과 결과가 교차해도 그 조건과 대상을 잃으면 안 된다.
2. **A의 파란 열:** 통합 요청 판단자가 관련 두 업무의 근거를 함께 읽고 목표, 대상과 관계를 생산한다. 모든 이력을 한꺼번에 넣는 구조가 아니며 Task별 검색과 부분 수정도 가능하다.
3. **B의 초록 열:** 보고서 담당과 메일 담당이 자기 조건과 질문으로 지역 변경을 생산한다. 조정자는 결론 참조를 메일 담당에게 전달하고 제안을 결합한다. Task가 없는 직접 대화와 Task 생성 전 요청은 공통 판단자가 담당한다. 담당은 앱별 직원이나 외부 업무 실행자가 아니다.
4. **C의 보라 열:** 대상 담당은 어떤 결론인지, 업무 연결 담당은 어느 Task의 수정인지, 관계 담당은 무엇을 유지하고 무엇을 교체할지 판단한다. 앞의 판단을 관계 담당이 몰래 덮어쓰지 않고 충돌한 생산자에게 재판단을 돌려보낸다.
5. **공통 하단과 선택 이유:** 코드가 현재 입력, 근거, 질문과 권한을 검사하고 채택한 변경만 기록하고 위임하거나 게시한다. 한 Omni를 공유하므로 역할별 호출과 Context/KV 비용은 남는다. A는 통합 관계와 적은 조정, B는 긴 Task의 연속성, C는 기능별 집중과 오류 분석의 이익 후보를 가진다. 추가 협력 비용보다 실제 기능 이익이 큰지는 아직 확인하지 않았다.

### 1.2 처음 보는 독자가 구별할 말

| 말 | 이 문서에서의 뜻 |
| --- | --- |
| 판단 주체 | 맡은 범위의 의미 산출물을 생산하고 근거 변경 때 재판단을 책임지는 논리적 주체. 호출 한 번과 같지 않다. |
| Component | 책임과 인터페이스의 SW 경계. 별도 AI Agent나 OS 프로세스를 뜻하지 않는다. |
| Actor | 상태와 메시지 수신함을 가진 논리 실행 단위. B의 Task 담당을 이런 방식으로 구현할 수 있지만 특정 framework는 선정하지 않는다. |
| AI Agent | 허용 범위에서 모델 판단으로 다음 조회나 해석 처리를 선택하는 주체. 코드가 정한 절차 안에서 모델만 호출하는 전문 Component를 모두 Agent라고 부르지 않는다. |
| 모델 세션 | 입력 맥락과 KV 등 계산 상태의 단위. 판단 주체와 일대일일 필요가 없으며 업무 원본이 아니다. |
| Task | Downstream Agent에 위임한 사용자 업무 목표의 VIA identity. 앱, 모델 세션, 외부 실행 ID와 다르다. |
| Request | 현재 처리할 논리적 요청. Direct Response는 새 Task 없이 Request와 Conversation에 남는다. 기존 Task 상태에 직접 답할 때는 그 Task를 참조할 수 있다. |
| 의미 제안 / 채택 | 생산자가 만든 임시 판단과, 현재 검사를 통과해 실제 처리 근거로 저장된 결과를 구분한다. |

## 2. 비교 질문과 범위

**관련 맥락을 한 판단 책임 아래 결합할 것인가, Task 또는 판단 기능을 기준으로 나눌 것인가? 나눈 뒤 전체 의도의 누락과 충돌은 누가 해결하는가?**

현재 33은 [04-50 영역 2](./04-50-agent-architecture-decision-map.md#area-02)를 중심으로 영역 1의 모델/코드 제어, 영역 4의 조정, 영역 5의 교환, 영역 7의 맥락과 영역 14의 채택을 구별한다. 분해 단위만으로 Supervisor/sub-agent 조직, 메시지 bus나 독립 프로세스를 선택하지 않는다. 본문에서는 분해의 효과를 보기 위해 코드 조정과 공통 채택 경계를 사용한다. 필요할 때의 의미 재판단은 명시적으로 모델에 요청하고 비용을 센다.

| 공통으로 유지 | 각 안에서 달라짐 |
| --- | --- |
| 같은 원문, 화면 시점 근거, 허용된 자료/Task/실제 게시 사실에 접근 가능 | 요청별로 누구에게 어떤 맥락을 구성해 제공하는가 |
| 같은 사용자 목표, 정정, 질문/결과 도착과 외부 Agent capability | 통합 의미, Task별 지역 의미, 기능별 부분 의미 중 무엇을 생산하는가 |
| 한 벌의 on-device Omni, 입력 capture/Streaming ASR 지속, 유한 자원 | 호출/Context 중복, 세션/KV 수명, 협력 대기와 재계산 |
| 현재 권한/버전, 중복 방지, 실제 결과 확인과 사용자 전달 | 임시 판단과 지속 대화 상태의 소유, 재판단/교환 경로 |
| 외부 업무 계획과 실행은 Downstream Agent | VIA 내부 요청 이해의 책임만 이동 |

세 안 모두 짧은 상태 전이와 모델 대기를 분리할 수 있다. A에도 비동기, 모듈화, Task별 검색, cache, 명시적 조건 보존과 부분 수정을 허용한다. 공유 가중치는 전문화된 독립 지식이나 독립 검증을 보장하지 않는다. 분해와 관련 없는 모델 성능 차이를 이익으로 가져오지 않는다. 참조 설계의 semantic 2회 정책은 기존 설계에 보존하며 새 세 안의 호출 수를 여기서 동결하지 않는다. repair, 참가자 판별, 관계 재판단과 재제안도 숨은 무료 호출이 아니다.

## 3. 세 구조의 생산자, 상태와 협력

### 3.1 A — 통합 판단과 기능별 지원 Component

Request Controller가 Context Manager와 각 원본 소유자의 읽기 계약으로 관련 근거를 확보하고 **통합 요청 판단자**에 전달한다. 이 이름은 비교용 책임 이름이며 참조 Architecture의 Request Interpreter를 개명한 것이 아니다. 통합 요청 판단자는 이번 입력의 목표, 대상, Task 연결, 정정 범위와 요청 관계를 함께 생산한다. 필요한 bounded read는 코드의 권한/예산 확인 뒤 수행하고 미해결이면 질문을 제안한다.

모델이 한 번에 모든 것을 맞혀야 하는 구조도, 중앙의 한 모듈이 모든 사건을 처리하는 구조도 아니다. Task별 일반 handler와 source adapter를 둘 수 있다. 결정적인 특징은 **관련 요청의 의미를 최종 생산하는 책임이 하나**라는 점이다. 대화/요청/질문은 Request Controller, 외부 Task 사실은 Task Manager, 자료 근거는 해당 원본 소유자가 유지한다. 의미 판단자는 영구 모델 세션 없이도 현재 상태를 읽어 판단한다.

메인 A의 1은 원문과 두 업무의 관련 맥락을 전달하는 경로, 2는 `보고서.format=PDF`, `메일.content=보고서@4의 결론`, 요청 간 관계를 반환하는 경로다. 다음 정정에서는 메일의 내용 조건만 변경한 제안을 반환한다. 공통 채택 경계가 Request Controller 소유 기록과 관련 명령 의도를 저장한다. 그림의 원통은 모델 내부 기억이 아니다.

### 3.2 B — 공통 대화 처리와 Task별 지속 판단

**Dialogue Coordinator**는 코드로 참가 후보와 버전을 관리하고 참조를 중개한다. **Common Dialogue Interpreter**는 Task 없는 직접 대화, 새 업무 위임 전의 요청 이해, 유일하게 라우팅할 수 없는 입력과 업무 간 연결 관계의 의미 제안을 담당한다. 명백히 기존 Task에 연결된 입력마다 이 판단자를 필수로 재호출하지 않는다. 후보 선정이 모호하면 관련 Task 후보와 원문을 주어 연결 판단을 요청하고, 불명확한 하나를 먼저 확정하지 않는다.

보고서 대화 처리자와 메일 대화 처리자는 같은 대화 처리 Component의 **Task별 논리 인스턴스**다. 해당 Task의 사용자 조건, 미해결 질문과 실제 제시 참조를 소유하며, 자신의 근거로 다음 의미/대화 변경을 제안한다. actor 방식의 수신함/사건 순서를 사용할 수 있지만 Task별 process, 모델 적재나 상주 KV를 요구하지 않는다. 실제 외부 질문/종료 사실은 Task Manager를 조회하며 복제 원본을 만들지 않는다.

| 시점/상황 | B에서의 처리 |
| --- | --- |
| 새 위임 요청, 아직 Task 없음 | 공통 판단자가 요청을 이해. Request Controller가 채택하고 Task Manager가 Task를 생성/연결하면 해당 대화 담당을 준비한다. 요청별 임시 상태는 대화 담당 생성 전에도 존재한다. |
| 독립 Direct Response | 공통 판단 경로와 Conversation/Request 기록을 사용. 이 목적만으로 Task나 새 주제 actor를 만들지 않는다. 좁은 S2S 직접 경로는 세 안 공통 별도 허용 조건을 따른다. |
| “보고서 어디까지 됐어?” | 기존 Task의 확인된 상태로 직접 답할 수 있다. Task 사실의 template 안내는 모델을 호출할 필요가 없고, 의미 해석이 필요하면 해당 담당에 요청한다. |
| 완료된 보고서의 후속 수정 | 같은 Task의 기록으로 담당을 재활성화. 완료가 모든 대화 근거의 즉시 삭제를 뜻하지 않는다. 새 외부 Execution 연결은 Task Manager 책임이다. |
| 무관한 앱으로 전환 | 앱 변경만으로 Task 담당을 바꾸지 않는다. 같은 앱에서도 다른 목표이면 다른 Task일 수 있다. |
| 삭제/장기 비활성 | 모델/KV와 실행 인스턴스는 회수 가능. 재구성에 필요한 허용된 내구 조건/질문은 보관 정책을 따르고 삭제/철회는 모든 파생 사용에 적용한다. |

메인 B의 1은 참가 Task에 같은 원문/입력 버전과 역할별 근거를 전달, 2는 각 지역 제안의 반환, 3은 Coordinator가 확인된 보고서 참조를 메일 담당에 전달하여 재제안을 받는 경로다. 4는 공통 검사/내구 채택에 성공한 뒤의 저장/통지이며 로컬 담당의 독자 commit이 아니다. 그림 아래 공통 판단자 가지는 Task 없는 요청과 생성 전 요청의 해석/반환을 표시한다.

참가 누락, 같은 절을 둘이 주장하는 경우, 여러 Task에 걸친 조건은 Coordinator가 원문 구간, 제안 ID와 의존 관계를 대조한다. **구간 coverage 검사는 문장의 의미 완전성을 증명하지 못한다.** 관계가 의미상 모호하면 공통 판단자에게 관계만 제안하도록 요청하고 각 Task 담당이 자기 지역 제안을 재확인한다. 공통 판단자가 모든 Task의 지역 내용을 다시 작성하는 방식은 A+B 혼합이며 순수 지역 생산의 이익으로 세지 않는다. 해결되지 않으면 최소 확인 질문을 공통 경로로 전달한다.

### 3.3 C — 기능별 전문 판단의 구성

**Semantic Coordinator**는 코드로 필요한 기능을 호출하고 같은 입력/근거 버전의 제안을 연결하며 누락, 상충, 무효화와 종료를 관리한다. 모든 요청에 세 담당을 무조건 호출하지 않는다. 결정적 ID나 기존 유효 제안으로 충분한 부분은 재사용할 수 있다. 코드가 의미를 알아서 완성한다고 가정하지 않는다.

| 생산자 | 입력 근거 | 독자적인 의미 책임과 반환 |
| --- | --- | --- |
| 대상 해석 담당 | 전체 원문, 관련 화면/시점/자료 후보, 실제 제시 참조. 필요하면 업무 연결 후보 | “그 보고서”, “결론”, “표”의 identity, 범위, 후보, 출처와 미해결 사항. Task 변경이나 관계를 독자 확정하지 않음 |
| 업무 연결 담당 | 전체 원문, Task 목표/질문/조건과 후보, 필요한 자료 참조 | 각 요청이 새 업무/기존 업무/Task 없는 요청 중 무엇인지, 어느 Task/질문에 연결되는지. 자료 내용이나 외부 업무 계획을 만들지 않음 |
| 관계 해석 담당 | 전체 원문, 대상/업무 제안 ID와 근거, 기존 유효 조건 | 목표, 변경 범위, 부정/조건, 요청 간 의존, 유지/교체할 조건과 처리 방향을 생산. 앞의 대상/Task 판단을 몰래 교체하지 않음 |
| Semantic Coordinator | 위 제안과 의존 버전, 원문 coverage, 현재 상태 | 제안 참조를 결합하고 관련 생산자에게 재판단 요청. 임의 대상 선택이나 자연어 의미의 코드 추측 금지 |

이 셋은 고정된 모든 자연어 의미의 완전한 분류라고 주장하지 않는다. 여기서는 목표/제약/처리 방향과 전체 문장 연결의 책임을 관계 해석 담당에 명시해 미소유 의미를 없앤다. 그 담당이 모든 원문/근거를 다시 해석해 앞의 두 결과를 대체하면 **통합 판단 + 보조**로 분류해야 한다. 대상과 Task는 서로 영향을 줄 수 있으므로 처음 후보를 강제 확정하는 일방향 pipeline으로 제한하지 않는다. 상충한 대상을 업무 담당의 새 근거로 좁히려면 대상 담당의 새 제안이 필요하다.

부분 판단은 `{producer, input_revision, source/read_set, value/candidates, unresolved, dependencies, proposal_revision}`을 가진 임시 자료다. 각 생산자가 자기 제안 내용을 소유하고 다른 담당은 참조만 한다. Semantic Coordinator는 호출/의존/조합 원장을 소유하며 임의의 값 수정 권한은 없다. 그림의 원통은 요청별 부분 제안과 의존 원장이다. Semantic Coordinator가 생산자의 제안을 기록/조회하되 각 의미 값의 변경은 해당 생산자의 새 제안으로만 가능하다. Task별 장기 조건을 소유하는 B의 원통과 수명이 다르다. 채택 전 상태를 장기 사용자 기억이나 권위 Task 원본으로 승격하지 않는다. 장기 질문 대기로 넘어갈 때는 Request Controller의 질문/요청 기록으로 필요한 참조를 채택해 보존한다.

메인 C의 1은 대상과 업무 담당에게 같은 원문과 적합한 근거를 제공, 2는 두 부분 제안 반환, 3은 원문과 그 제안을 관계 담당에게 제공, 4는 의존/정정 범위의 반환이다. 조정자가 결합한 의미도 공통 현재 검사 뒤에만 채택한다. 관계 산출물에 대상 또는 Task 충돌이 있으면 관련 생산자가 재판단한다. 현재 버전 검사는 의미상 정답의 검증이 아니다.

### 4.2 04-31과 함께 선택할 때의 소유 경계

31의 본문과 그림은 변경하지 않는다. 31은 요청별 의미 생성과 지속 의미 상태 생산, 여기의 33은 그 의미의 생산 책임을 나누는 기준이다. A는 중앙의 요청별 기록 또는 의미 Workspace, B는 각 Task 담당의 지역 기록/Workspace를 사용할 수 있다. B와 31 B를 조합하면 Workspace는 미채택 변경/질문을 반환하고 공동 채택 후 저장/게시하며 별도 전역 Workspace에 같은 지역 의미 원본을 복제하지 않는다. Task 없는 공통 대화의 의미는 공통 책임에 남는다.

C의 부분 제안 저장은 그 자체로 31 B의 지속 Meaning Workspace가 아니다. C와 31 B의 조합은 기능별 제안과 지속 제약 변경의 권한을 추가 설계해야 한다. 여기서 임의의 모든 조합을 해결했다고 주장하지 않으며 세 안의 기대 이익을 다른 비교의 이익에 단순 합산하지 않는다. 41의 모델/코드 해결 방식과 42의 독립 실행 수명도 별도 질문으로 유지한다.

| 모호함/추가 질문 | 관련 원문과 후보로 재판단 | 참가 확대/지역 재제안/공통 관계 판단 | 후보 교환/원 생산자 재판단 |
| 정정/철회/복구 | §5 계약 | §5 계약 + 지역 상태/교환 무효화 | §5 계약 + 부분 제안 의존 무효화 |

관계 표현이 부족하거나 필요한 참가자를 찾지 못한 사례를 빠른 성공으로 세지 않는다. 추가 질문으로 해결하면 사용자 수고를, 수동 재연결이 필요하면 기능 적절성/완전성 손실을 남긴다. 질문만 했다는 사실이 원래 사용자 목표 완료는 아니다. B의 공통 판단과 C의 필요한 기능 생략을 허용하되 어려운 사례를 A에 전부 넘긴 뒤 B/C의 단독 품질로 보고하지 않는다.

## 7. V-01~13으로 한 직관적 사고 실험

[03-00](./03-00-quality-scenarios.md)의 정의와 순위를 그대로 사용한다. 공동 1순위는 V-01/02/03, 공동 2순위는 V-04/05, 다음은 V-08, V-06, V-07이다. 나머지 V-09~13도 누락하지 않는다. **아래는 작성자의 조건부 예상이며 측정값, 실제 심사위원 평가나 A/B/C 선정이 아니다.** 동일 모델과 근거 접근에서 분해 때문에 생기는 경로만 설명한다. V-04/05는 VIA 귀속 시간이며 외부 Agent 업무 실행시간은 공통 외부 조건이다. 가중 총점이나 유리한 사례만의 평균은 만들지 않는다.

| 관점 | A의 예상 | B의 예상 | C의 예상 | 직관적 우열과 뒤집히는 조건 |
| --- | --- | --- | --- | --- |
| V-01 기능 정확성 | 전체 관계를 함께 해석. 검색 누락/맥락 혼입 위험 | 지역 조건에 집중. 참가 누락/교차 관계 오류 | 판단별 집중. 부분 결과 불일치/초기 오류 전파 | 교차 업무는 A 우세 예상. 긴 단일 Task는 B, 특정 어려운 해석은 C의 이익 가능. 전문화 자체의 효과는 미확인 |
| V-02 기능 적절성 | 한 문장으로 여러 목표를 연결하기 자연스러움 | 긴 Task의 재설명 감소 가능, 협력 부족 시 반복 질문 | 내부 해결이 잘되면 질문 감소, 불일치를 사용자에게 떠넘기면 증가 | 일반 대화 A, 장기 업무 B의 강점 후보. A도 조건 보존 가능하며 C는 실제 사용자 수고 감소가 필요 |
| V-03 기능 완전성 | Task 없는 대화와 자유로운 관계를 같은 판단에서 지원 | 공통/Task 경계를 모두 완성해야 함 | 기능 사이에 걸친 관계와 전체 누락 검사가 필요 | 전체 범위 구성은 A가 단순. B/C가 본질적 미지원은 아니지만 경계 누락/미확인 범위를 공개해야 함 |
| V-04 상호작용 반응성 | 짧은 입력은 적은 조정 경로 | 직접 대화는 A와 유사, 기존 Task의 좁은 맥락 이익/라우팅 비용 | 여러 판단/결합 대기. 필요한 기능만 호출 가능 | 짧은 요청 A≈B, C 불리 가능. 반복 Task에서 B가 앞서려면 실제 입력/대기 절약 필요 |
| V-05 VIA 귀속 요청 완료 시간 | 교차 관계를 한 경로에서 생산 | 참조 교환과 재제안이 추가됨 | 부분 판단과 결합의 반복/재사용이 모두 가능 | 교차 요청은 A 유리 예상. B/C의 선택적 재처리는 A의 부분 수정과 비교해야 함 |
| V-06 자원 활용성과 수용량 | 큰 통합 입력 가능, 조정/중복 입력은 적을 여지 | 담당 상태/수신함/Context와 호출, KV 상주 강제 없음 | 중복 원문/부분 근거/추론과 임시 판단 | 기본 A 유리 예상. B/C의 작은 입력/재계산 절약이 비용을 넘으면 역전. 자원량과 지원 부하 한계는 별도 확인 |
| V-07 결함 허용성과 복구성 | 중간 협력 상태가 적어 복구 단순 | 실패 Task 구별/지역 재구성, 참조 일관성 부담 | 실패 기능 구별, 필수 기능이 전체 경로를 막을 수 있음 | 복구 단순성 A. 동일 process/DB/Omni 장애의 격리 우열은 추론 불가. A도 Task별 실패 처리 가능 |
| V-08 변경 용이성과 모듈성 | 기능별 모듈화 가능, 통합 의미 계약 영향 | 다른 Task 대화 규칙이 있으면 국소화. 인스턴스 수만 늘리면 이익 작음 | 특정 해석 기능 개선을 국소화. 교환 의미 변경은 전파 | 판단 기능 변경 C, 실제 Task별 규칙 변경 B의 후보 이익. 일반 adapter 변경은 A도 가능 |
| V-09 분석 및 시험 용이성 | 전체 경로 시험 단순, 통합 의미 오류 분해 어려움 | Task별 원인 추적, 참가/협력 경합 시험 증가 | 오류 단계 분석 쉬울 여지, 부분 결과 조합 시험 증가 | 원인 분석 C, 전체 경로 시험 단순성 A. 분석과 시험을 한 점수로 합치지 않음 |
| V-10 기밀성 | 필요한 근거만 구성, 파생 사용 경로 적음 | Task별 맥락 제한 가능, 철회 전파 증가 | 기능별 최소 근거 가능, 자료 중복과 파생 경로 증가 | 고정 순위 없음. 맥락 제한은 B/C의 여지, 철회 관리 단순성은 A. 논리 경계는 강제 보안 격리가 아님 |
| V-11 상호운용성과 공존성 | 같은 외부 계약, 상대적으로 적은 추가 추론 가능 | 외부 계약 동일 가능, Task 판단의 경합 | 외부 계약 동일 가능, 전문 호출 경합 | 연동은 구조만으로 차이 없음. 다른 앱/음성과의 공존은 A 유리 예상이나 실제 자원 의존 |
| V-12 조작 용이성과 사용자 오류 방지 | 한 창구에서 자유롭게 전환. 오해하면 오대상 제어 위험 | Task별 질문/대상 관리, 내부 담당 선택을 사용자에게 강제하면 악화 | 판단 분리만으로 오조작 방지 보장 안 됨 | 같은 UI/검증이면 큰 차이 근거 부족. B의 Task 표시와 질문 결합은 A도 구현 가능 |
| V-13 설치 용이성 | 역할/중간 상태 계약이 비교적 적음 | Task 담당 상태와 버전 관리 | 전문 계약과 부분 상태 호환 | 같은 실행체/가중치면 설치 자체는 대체로 유사. 상태/계약 갱신 부담은 A가 작을 여지 |

A의 단순성 이익은 경로에서 직접 보이지만 B/C의 정확성/적절성 이익은 실제 정상 사례에서 더 구체화해야 한다. 이 비대칭을 숨기려고 A의 맥락 관리와 모듈화를 제거하지 않는다. 메인 그림의 V 표시는 위 조건부 경로를 요약한 것이며 순위 배지나 점수가 아니다.

## 8. 가장 싼 확장, 혼합과 양방향 전환

| 반론/혼합 | 실제로 얻는 것 | 작성자 판단 |
| --- | --- | --- |
| A에 Task별 상태/index/일반 handler 추가 | 조건 보존, 관련 검색, 비동기 사건과 부분 갱신 | 충분한 상황이 많다. 이 기능만으로 B의 주요 자격을 주장하지 않음 |
| A에 어려운 요청만 일시적 전문 보조 호출 | 별도 맥락의 후보/반대 근거를 참고해 통합 의미 생산 | 현실적인 강한 A. 독립적인 주요 구조가 자동 성립하지 않음. 보조 실패/폐기/호출 조건 비용도 포함 |
| A의 전문 보조가 자기 판단의 최종 부분 생산자로 바뀜 | 대상/Task/관계 생산과 의존 재판단을 분리 | 이름이나 호출 수가 아니라 실제 생산 권한/결합 계약이 이동하면 C 계열. 중앙이 모두 다시 해석하면 여전히 A+보조 |
| 일반 Task handler가 스스로 다음 의미 상태를 제안 | 입력/질문/결과/정정이 모두 해당 소유 계약을 따름 | actor framework 없이도 B가 될 수 있음. 새 process 도입비를 필수 전환비로 세지 않음 |
| B에 업무 간 관계 판단을 추가 | 지역 내용은 지역 담당, 교차 조건은 공통 판단 | 현재 B에 명시한 구성. 공통 판단이 모든 지역 의미를 재작성하면 다른 혼합이며 중복 비용을 공개 |
| 관계가 강한 Task들을 임시 한 판단 단위로 묶기 | 한 발화의 관련 맥락을 함께 판단 | 단순히 A의 관련 검색과 같으면 독립 대안 아님. 별도 상태/생산 권한 이동이 필요할 때 재검토 |
| C에 통합 fallback 추가 | 표현/협력 한계를 어려운 사례의 통합 해석으로 보완 | 가능하나 fallback 비중/추가 비용/이중 생산 책임을 기록. 순수 C의 정확성 증거로 사용하지 않음 |

| 전환 | 기능 개발 | 진행 상태 이행 | 반드시 바뀌는 핵심 처리 |
| --- | --- | --- | --- |
| A → B | 참가/지역 담당/참조 협력 | 대화 조건을 Task별로 연결. 진행 요청 drain으로 이행비 감소 가능 | 전체 의미 생산을 지역 의미 제안/공동 채택으로 이동. 비동기 질문/전달/정정도 같은 소유를 따름 |
| B → A | 통합 의미 생산/조회 | 지역 조건과 참조를 공통 읽기 구조로 노출 | 지역 재제안 협력을 통합 생산으로 대체. 저장소/Task identity는 유지 가능 |
| A → C | 부분 판단/결합/의존 재판단 | 기존 원문/채택 기록 재사용, 미채택 부분 상태는 종료 후 새로 생성 가능 | 하나의 완성 의미 생산을 부분 생산자와 결합으로 대체. 중앙의 중복 의미 작성 제거 |
| C → A | 통합 의미 생산, 부분 기능은 보조로 재사용 가능 | 채택 기록 유지, 진행 부분 판단 drain | 부분 의미 채택 권한을 통합 생산자에게 회수하고 협력 종료 조건 교체 |
| B ↔ C | 지역 업무 판단과 기능 판단 사이의 책임 재배정 | Task 기록은 유지 가능, 임시 제안/의존 원장 변환 또는 drain | 분할 기준이 목표별에서 기능별로 바뀜. 서로의 일부 helper는 재사용 가능하나 동일 의미의 이중 원본 금지 |

전환을 어렵게 만들려고 새 저장소/프로세스를 추가하지 않는다. 같은 외부 계약과 DB를 유지할 수 있다. 실제 이익이 작은 helper로 충족되면 그 차이는 주요 대안보다 세부 설계로 낮춰야 한다. 현재는 세 계열의 탐색 가치와 권한 차이를 구체화했으며 주요 DP 자격의 최종 판정은 남는다.

## 9. 선택 조건, 반증과 현재 결론

| 안 | 선택 이유가 강해지는 사용자 조건 | 그 이유를 약화시키는 반증 |
| --- | --- | --- |
| A | 짧은 직접 요청과 업무를 넘나드는 자유로운 표현, 적은 조정 비용이 중요 | 동일 예산의 관련 검색/부분 수정으로도 긴 조건을 반복 누락하고 B/C가 그 오류를 줄이며 추가 수고/자원 비용을 감당할 수 있음 |
| B | 오래 이어지는 Task에서 자기 조건/질문에 집중하는 판단이 반복적으로 중요 | A의 Task별 검색/handler로 같은 기능 이익을 얻거나, 교차 참조/참가 오류와 질문 비용이 지역 판단 이익을 상쇄 |
| C | 특정 의미 기능의 판단 오류/변경이 반복되고 부분 생산 책임 분리가 이를 줄임 | 역할 prompt만 나눈 것으로 정확성이 개선되지 않거나, 통합 재해석 없이는 결합을 마치지 못하고 지연/누락이 증가 |

**권고는 A/B/C 세 계열을 비교 대상으로 유지하는 것이며 승자는 정하지 않는다.** B는 Task별 대화 담당과 공통 대화 처리의 혼합으로 명확히 했고 C는 기능별 부분 의미 생산으로 추가했다. 일시적 보조와 통합 fallback은 현실적인 최소 확장/혼합 반론으로 남긴다. 상자 수, 문서 길이, 13개 행이나 렌더/CI 통과는 구조적 중요성 또는 우월성의 증거가 아니다.

이 문서와 그림은 31, 41, 42, 다른 비교 본문/그림, 32의 제외 상태, 참조 Architecture, QA/ADR를 변경하지 않는다. 새 구현, 모델 실행, 품질 측정, QA freeze나 최종 DP 선정은 없다.
