# 03-02. VIA 중요 품질속성 정의 — 공동 검토 초안

> 상태: **다섯 묶음 합의 / 요청 처리 정확성 평가 설계 v1 확정 / 나머지 QA 검토 예정** / 2026-10-10
> 사용자 지정: 정확성 1~2개, 응답속도 1~2개, 모델 사용 비용 1개, 변경 용이성 1개, 메모리 사용량 1개.
> 재개 시 **§9를 현재 정확성 평가 설계의 원본으로 읽는다.** 사용자 요청에 따라 상황 6개, 기본 사례 18개, 실행당 6개 이진 채점 항목, 공통 환경/절차, 분모와 목표를 확정했다. 세부 수치는 작성자가 위임 범위에서 정한 평가 목표다. 구현/실측/최종 DP 선택은 하지 않았고 실행 파일과 model build를 고정한 machine freeze도 아직 없다. §7~8은 정의 과정과 정답표 근거로 보존하며 충돌 시 §9가 우선한다.

## 1. 이 문서의 역할

VIA에서 중요한 품질속성의 의미, 범위, 우선순위와 평가 기준을 사용자와 함께 정의한다. 먼저 어떤 품질을 왜 중요하게 보는지 합의하고, 이후 지표와 측정 방법을 구체화한다. 새로운 정의 논의와 합의는 이 문서에 이어 기록한다.

[03-00 품질 시나리오](./03-00-quality-scenarios.md)는 기존에 검토한 13개 품질 관점과 충돌 상황의 근거다. [기존 Core ASR 계약](../../08-quality-attributes/core-asr-contract.md)은 QA-09, QA-19, QA-29, QA-39와 상세 QA의 현재 의미를 보존한다. 이번 초안은 이 자료를 바탕으로 재검토하며 기존 정의를 자동 대체하지 않는다.

최근 [04-40 공통 실행 계약](./04-40-common-execution-contract.md)은 로컬 VIA와 클라우드 음성/의미 모델을 전제로 한다. 이 조건에서 PC 자원과 모델 사용 비용, 네트워크 의존성이 품질에 미치는 영향을 다시 살핀다. 기존 on-device 참조 설계와 당시 QA 정의 및 결과는 원래 조건으로 보존한다.

### 1.1 합의한 목적과 DP/QA의 관계 — 재개 시 반드시 읽기

**VIA의 목적은 핵심 QA 성능을 우선순위에 따라 최대화하는 SW를 만드는 것이다.** 이 과제에서 중요한 기능과 구조를 다루면서 핵심 QA 성능에 영향을 미치는 설계 결정을 DP로 도출한다. 현재 유력 후보는 **DP-41, DP-42, DP-44, DP-45**다. 이 네 개가 최종 DP나 A/B 승자로 선정된 것은 아니다. 43과 별도 46 자료의 지위를 이번 논의로 변경하지 않는다.

정방향의 설계 논리는 다음과 같다.

1. 중요한 품질 목표와 우선순위를 정한다.
2. 그 품질에 영향을 주면서 과제 차원에서도 중요한 설계 결정을 도출한다.
3. 각 DP의 강한 방안 A/B에 대해 핵심 QA 전체의 trade-off를 확인한다.
4. 합의한 우선순위에서 더 좋은 QA 성능을 보이는 방안을 선택한다. 필수 규칙, 허용 한도, 동등 또는 불확실한 차이의 처리도 공통 선택 계약에서 정한다.
5. 선택한 방안의 낮은 우선순위 QA가 약하면 tactic으로 보완한다. 보완 후 높은 우선순위 QA의 회귀와 다른 비용을 함께 확인한다.

기본 구조와 적용한 tactic을 구별해 결과를 기록한다. 기본 구조 비교를 위해 필수 검사나 이미 허용한 정상 기능을 제거하거나, A 또는 B를 약한 구현으로 바꾸지 않는다. tactic으로 차이가 줄어드는 것은 정상적인 설계 과정이다. 여러 QA를 가중 총점으로 합쳐 trade-off를 숨기지 않는다.

### 1.2 이번에는 DP에서 QA 정의로 역으로 접근한다

사용자는 DP 후보가 이미 있는 상태에서 A/B 성능을 측정하거나 계산할 수 있도록, 다섯 품질 묶음의 정의, 세부항목, 대표 지표와 목표를 구체화하려 한다. **기존 QA 공식을 자동 적용하는 것으로 끝내지 않고, 실제 구조 차이의 중요한 품질 효과를 포착하는 공통 QA를 설계한다.** 다음 순서로 각 품질을 검토한다.

**A/B의 실제 작동 차이 → 품질이 달라지는 원인과 상황 → 사용자에게 중요한 QA 정의 → 공통 지표와 목표 → 측정/계산 → 우선순위에 따른 선택과 tactic 보완**

| 연결 | 확인할 질문 |
| --- | --- |
| 사용자 가치와 QA 정의 | 이 품질이 좋아지면 VIA 사용자가 무엇을 더 잘할 수 있는가? |
| 구조 차이와 품질 효과 | A/B의 어떤 판단, 근거 획득, 실행 의존성, 상태 또는 확정 차이가 품질을 바꾸는가? |
| 품질 효과와 지표 | 그 차이를 같은 입력과 조건에서 관찰하고 계산할 수 있는가? |

정의는 구조 차이에 민감하면서도 실제 사용자 가치에 근거해야 한다. 같은 조건에서 A/B 차이가 없거나 측정으로 구분되지 않는다면 그대로 남긴다. 모든 DP가 모든 QA에서 다른 값을 가져야 한다고 요구하지 않으며, 예상한 우열에 맞춰 사례나 분모를 고르지 않는다.

초기 측정/계산은 정의의 적합성을 확인하는 탐색에 사용할 수 있다. 이때 사용한 정의 version과 사례, 변경 이유를 남긴다. 최종 선택에 쓰는 비교는 검토를 마친 공통 계약을 결과 전에 고정한 뒤 수행한다. 탐색 결과를 개정된 계약의 최종 비교 결과로 재해석하지 않는다. 이번 합의는 정의와 평가 설계의 진행 방향이며 지금 구현, 모델 실행, 수치 freeze나 최종 선택을 시작하는 지시로 확대하지 않는다.

### 1.3 Compaction 또는 다른 세션에서 재개하는 순서

1. AGENTS.md와 00-workplan의 현재 QA 체크포인트를 읽고 실제 git 상태를 확인한다.
2. **이 문서 §1.1~1.3을 먼저 읽는다.** 현재 유력 DP 네 개, 역방향 정의 작업, 우선순위 선택과 tactic 보완의 관계를 복원한다.
3. §2의 다섯 묶음과 §6의 합의/미결정을 읽는다. 기존 7개 세부안은 작성자 제안이며 확정 목록으로 취급하지 않는다.
4. 정확성은 **§9의 평가 설계 v1로 확정했다.** §7~8의 집계/분모/목표 미정 문구는 이전 논의다. 다시 유형과 분모를 탐색하지 말고 §9의 테스트, 이진 채점, 반복과 목표를 구현용 fixture/manifest에 옮긴다. 구현/실측 착수는 별도 요청을 따른다.
5. 각 품질의 논의 결과를 이 파일에 반영하고 합의와 작성자 제안을 구별한다. 이전 QA 지표를 자동 복원하거나 DP 문서마다 다른 QA를 만들지 않는다.

## 2. 사용자가 정한 핵심 QA 구성

이번 정의 작업은 다음 다섯 묶음으로 진행한다. 정확성과 응답속도의 최종 항목 수에 따라 총 5~7개가 된다. 사용자가 제시한 나열 순서를 새로운 우선순위나 가중치로 해석하지 않는다.

| 묶음 | 항목 수 | 현재 세부 검토안 |
| --- | --- | --- |
| 정확성 | 1~2개 | 요청 처리 정확성을 공통 평가축으로 확정. C1~C6는 이 축의 채점/진단 항목이며 별도 핵심 QA로 나누지 않음. 추가 독립 정확성 QA는 아직 없음 |
| 응답속도 | 1~2개 | 상호작용 반응성, VIA 귀속 요청 완료 시간 |
| 모델 사용 비용 | 1개 | VIA 모델 사용 비용 |
| 변경 용이성 | 1개 | VIA 변경 용이성 |
| 메모리 사용량 | 1개 | 로컬 VIA 메모리 사용량 |

초기 검토에서는 정확성과 응답속도를 각각 두 항목으로 나눈 **7개 검토안**을 기록했다. 현재 정확성의 항목 수와 정의는 §7에서 재검토한다. 한 항목으로 합칠 필요가 있으면 평가 범위와 집계 의미를 함께 검토한다. 기존 QA 번호와 V 표식은 참조 자료로 사용하며 신규 QA ID를 아직 부여하지 않는다.

## 3. 일곱 세부 항목의 정의 초안

### 3.1 요청 해석 정확성

사용자의 입력과 허용된 근거에서 의도한 요청 의미를 올바르게 결정하는 능력이다. 의도, 지칭 대상, 대화 및 Task 연결, 복합 요청 관계, 정정 범위, 처리 방향과 확인 질문의 필요 여부를 살핀다. Task 연결은 해석의 결과이며 이미 결정된 입력으로 가정하지 않는다.

예를 들어 “보고서는 표로 바꾸고 메일은 그대로 보내줘”에서 수정할 요청과 보존할 요청을 구별하는지가 대상이다. 음성과 화면의 시간 대응이나 과거 정보 조회가 잘못된 해석으로 이어진 경우에도 최종 해석의 오류를 남긴다. 내부 검색 recall이나 전사 정확도는 원인 진단에 사용할 수 있지만 이 QA의 대표값을 대신하지 않는다.

### 3.2 상호작용 처리 정확성

해석하고 채택한 요청, 사용자 제어와 외부 Agent 사건을 올바른 대화 및 업무 상태에 적용하고, 확인 가능한 사실에 맞게 전달하는 능력이다. 질문 답변의 연결, 요청 관계와 정정의 적용, 취소 효력, 진행 상태, 결과 참조, 늦은 사건 처리와 실제 전달 기록을 살핀다.

예를 들어 취소 대상 Task를 올바르게 판단했는데 다른 실행에 취소를 전달하거나, 아직 재생하지 않은 설명을 사용자가 들었다고 기록하면 이 항목의 문제다. 요청 해석 정확성이 **의도한 Task를 결정했는가**를 본다면, 이 항목은 **그 결정을 올바른 실행과 상태에 적용했는가**를 본다.

두 정확성 항목은 판정하는 사실과 관측 경계를 구별해야 한다. 잘못된 해석이 처리 오류로 이어지는 같은 사건의 결과는 함께 남기되 독립 표본처럼 중복 합산하지 않는다. 해석과 처리 효과를 나누는 평가 단위 및 오류 귀속 규칙은 공통 계약에서 정한다. 기존 QA-19의 field와 QA-13~15의 회귀 진단을 그대로 두 항목으로 매핑하지 않는다. Downstream Agent 내부의 업무 계획, 도구 실행과 도메인 결과 품질은 VIA 평가 범위와 구별한다.

### 3.3 상호작용 반응성

사용자 입력이나 제어 사건에 대해 유효한 응답 또는 실제 제어 효과가 나타나기까지의 VIA 귀속 시간을 본다. 음성 출력 중단, 요청 정정과 Agent 업무 취소는 서로 다른 효과이므로 각각 필요한 사건을 정의한다. 일반적인 접수 멘트나 잘못된 빠른 응답은 해당 기능의 유효한 결과를 대신하지 않는다.

### 3.4 VIA 귀속 요청 완료 시간

요청 시작부터 필요한 최종 결과의 실제 전달까지 VIA가 만든 처리와 대기를 본다. 준비, 조회, 의미 판단, queue, 경합, 인계, 의존 요청의 해제, 검증, 재처리와 전달이 대상이다. Downstream Agent의 내부 대기, reasoning, 계획과 업무 실행은 동일한 외부 조건으로 두며 VIA 성능으로 평가하지 않는다.

상호작용 반응성과 일부 구간이 겹치더라도 두 값을 합산해 총점을 만들지 않는다. 병렬 실행에서는 외부 시간의 합을 전체 경과 시간에서 단순 차감하는 방식으로 귀속 시간을 확정하지 않는다. 클라우드 모델 왕복과 네트워크 지연을 포함한 시간 경계는 모든 DP에 공통으로 정의해야 한다.

### 3.5 VIA 모델 사용 비용

같은 사용자 활동과 평가 기간에서 VIA가 호출한 모델 사용량에 대해 발생하는 실제 금액이다. 음성 입력과 전사, 현재 의미 판단, 과거 의미 가공, 응답 준비와 음성 출력, 선택적 호출, 재시도와 폐기된 청구 작업을 포함한다. 요청 시점 밖의 배경 생산, 갱신과 사용되지 않은 생산 비용도 남긴다.

호출 수와 token 및 audio 사용량은 비용의 원인을 설명하는 보조값이다. 호출 수만으로 금액을 대신하지 않는다. 전체 기간 비용과 올바른 완료 수를 함께 보고, 실패나 보류의 청구 비용을 숨기지 않는다. 외부 Agent 내부 모델 비용은 별도 책임 경계로 보고한다. 비용 단위, 대표 집계, 단가 version과 workload는 아직 미정이다.

### 3.6 VIA 변경 용이성

모델, Agent, Context 정보원, 저장 형식과 기능 계약의 변화를 수용하면서 다른 사용자 기능을 유지하는 능력이다. 변경의 전파 범위, 책임 사이의 결합과 검증 부담을 살핀다. 파일이나 박스가 적다는 사실만으로 우위를 판정하지 않는다. 기존 QA-29의 changed Architecture Element 수를 대표 지표로 재사용할지는 검토 사항이다.

### 3.7 로컬 VIA 메모리 사용량

같은 사용자 활동과 동시 부하에서 VIA를 실행하기 위해 사용자 PC에 실제 사용하는 전체 메모리다. VIA process와 helper, 입력 근거 buffer, Context, queue, cache, 연동 client와 임시 모델 session 상태를 포함한다. 로컬 모델을 사용하는 비교 조건이라면 해당 weights, runtime과 KV cache도 포함한다. 클라우드 모델 서버와 외부 Agent 서버의 메모리는 로컬 PC 메모리와 구별한다.

배경 생산과 갱신, 반복 요청, 정정 및 장기 실행에 따른 축적을 포함해 관찰한다. 기능 제한이나 근거 보관 축소로 메모리를 줄인 경우 포기한 사용자 기능도 함께 설명한다. CPU, 에너지, 저장공간과 수용량을 이 항목의 대표값에 합치지 않는다.

이번 합의로 메모리 사용량을 새 핵심 QA 정의 작업의 독립 항목으로 둔다. 기존 QA-41의 peak committed memory 계약을 재사용할지, 대표 통계와 측정 범위 및 목표값을 어떻게 정할지는 후속 검토 사항이다. 기존 catalog의 QA-41 diagnostic 분류와 이전 결과의 의미는 아직 변경하지 않는다.

## 4. 다른 품질 관점과의 관계

기능 적절성, 기능 완전성과 결함 허용성 및 복구성은 이번 핵심 QA 목록의 독립 항목에서 제외한다. 기밀성, 분석 및 시험 용이성, 상호운용성과 공존성, 조작 용이성과 사용자 오류 방지, 설치 용이성 및 메모리 외 자원도 기존 자료에서 참고한다. 이 문서에 핵심 QA를 추가할 때는 사용자가 정한 다섯 묶음의 범위와 관계를 다시 논의한다.

[03-00](./03-00-quality-scenarios.md)의 13개 관점과 기존 구조 비교 기록은 보존한다. 기능 지원 차이와 수동 우회 부담은 비교 조건 및 한계로 남긴다. 미지원 안내를 원래 목표의 성공 완료로 세거나 권한 위반을 비용 절감으로 정당화하지 않는다. 장애 상황의 잘못된 상태나 중복 실행은 해당 정확성의 범위와 공통 시험 조건에서 어떻게 판정할지 정한다.

## 5. 모든 DP에 적용할 공통 정의 원칙

선정한 QA는 모든 DP와 모든 대안에서 동일한 정의, 대표 지표와 측정 방법을 사용한다. 평가 단위, 정답 판정, 시작/종료 사건, 시간 및 비용 경계, 집계, 모집단 적용, 분모와 제외 규칙, 실패 및 timeout 처리를 공통 원본에서 정한다. 각 DP는 구조의 인과적 참여와 내부 관측을 그 계약에 연결한다.

같은 QA를 특정 DP에서는 의미 field accuracy, 다른 DP에서는 검색 recall이나 업무 성공률로 바꾸어 사용하지 않는다. 추가 진단은 공통 QA를 대체하지 않는다. 미참여, 미지원과 미확인을 0점이나 동등으로 간주하지 않으며, 실패 사례를 조용히 제외하지 않는다.

QA의 개정 이유와 영향받는 문서를 함께 기록하고, 이전 정의 및 결과는 원래 계약으로 보존한다. 기존 자료의 재사용은 의미와 측정 방법이 맞는지 확인한 뒤 결정한다. 지표와 목표값을 확정하기 전에도 각 품질의 손익은 독립적으로 설명하며 가중 총점으로 합치지 않는다.

## 7. 정확성의 첫 공동 검토 — 작성자 제안

> 아래 §7~8은 정의 과정의 기록이다. **현재 평가 단위, 집계/분모, 반복과 목표는 §9로 확정했다.** 과거의 미정/검토안 문구를 재개 작업으로 복원하지 않는다. 실제 정확률은 아직 측정하지 않았다.

### 7.1 먼저 무엇의 정확성인지 정한다

**공통 정확성 후보: VIA가 사용자 입력과 관련 외부 사건을 의도 및 확인 가능한 사실에 맞는 요청 처리 결과로 연결하는 능력.** 해석뿐 아니라 올바른 대상/업무에 대한 적용, 요청 관계, 정정과 제어, 상태 및 실제 전달까지 포함한다. 외부 Agent가 만드는 보고서 내용이나 업무 도구의 내부 수행 품질은 VIA 정확성과 구별한다.

예를 들어 사용자가 보고서 형식을 표로 바꾸면서 메일은 유지하라고 정정한 경우, 보고서 변경과 메일 보존을 해석하고 올바른 Task에 적용하며 정정 전의 늦은 후보를 게시하거나 전송하지 않아야 한다. Agent 질문이 함께 도착했다면 실제 제시된 유효 질문에 답을 연결하고, 로컬 접수와 외부 접수 및 완료를 구별해 알리는지도 대상이다.

| DP | 실제 구조 차이 | 정확성에 영향을 줄 수 있는 상황 | 공통으로 판정할 사용자 결과와 한계 |
| --- | --- | --- | --- |

같은 품질을 내부 frame accuracy, join 오류율, 기억 검색 recall 등 서로 다른 대표 지표로 바꾸지 않는다. 그 값들은 원인 진단으로 두고 공통 사용자 결과에 연결한다. 네 DP 모두에서 정확성의 차이가 실제로 발생할지는 미확인이다. 공통 현재성 검사로 오류를 막고 차이가 재처리 시간/비용에만 남는다면 그 사실을 다른 QA에 기록한다.

### 7.3 한 개 또는 두 개로 구성하는 검토안

| 구성 | 정의와 장점 | 함께 해결할 문제 |
| --- | --- | --- |
| **1개: VIA 요청 처리 정확성** | 해석부터 상태 적용과 전달까지 같은 사용자 결과의 정확성을 평가. 네 DP를 동일한 품질 축으로 연결할 수 있음 | 어떤 단계의 오류인지 별도 진단 필요. 서로 다른 결과의 판정과 사례 구성을 공통으로 정해야 함 |
| **2개: 요청 해석 정확성 + 상호작용 처리 정확성** | 의미 결정과 결정의 적용/사실 전달을 각각 보여줌. §3.1/3.2의 기존 초안 | 잘못된 의미를 충실히 적용한 경우의 판정, downstream 오류 전파와 중복 집계 규칙 필요. 해석 오류를 처리 단계의 정답 입력으로 대체해 전체 성능을 높이지 않아야 함 |

작성자 권고는 **VIA 요청 처리 정확성을 공통 핵심 1개로 정의하고, 의미 해석과 상태/전달의 결과를 진단으로 나누는 안**을 먼저 검토하는 것이다. 별도 의미 정확성을 핵심 QA로 두어야 할 선택상의 이유가 확인되면 두 개로 발전시킨다. 기존 7개 초안을 이 권고로 자동 확정하거나 변경한 것은 아니다.

### 7.4 대표 지표 후보와 평가 상황

대표 지표의 첫 후보는 **사전에 정한 요청 처리 사례를 올바르게 처리한 비율**이다. 처음에는 입력과 후속 답변을 갖춘 유한한 interaction episode를 한 사례로 제안했다. 사용자가 분모 구성의 중요성을 지적한 뒤, 큰 대화 전체의 길이에 따른 영향을 줄이고 평가 단위를 명확히 하기 위해 §7.6의 짧은 처리 과제 단위로 구체화한다. 판정은 특정 내부 구조나 필드 수에 의존하지 않는 공통 사용자 결과 predicate로 한다.

```text
요청 처리 정확성 후보(%)
= 100 × 올바른 처리 결과를 충족한 scored 사례 수 / 전체 scored 사례 수
```

사례별 필수 의미, 적용 대상/관계, 제어 효력과 상태/전달 사실을 모두 만족하는지를 판정하는 안이다. 사례가 큰 만큼 같은 분모에 넣을 평가 단위와 난이도, 사례/반복 배분은 먼저 검토해야 한다. field micro-average는 일부 조건 누락을 세밀하게 보여주는 대안이지만 field 분할과 쉬운 field 수에 민감하므로 기존 QA-19 공식을 바로 채택하지 않는다. whole-case와 field 지표를 둘 다 대표 점수로 중복 사용하지 않는다.

| 공통 상황 후보 | 확인할 결과 |
| --- | --- |
| 명확한 단일 요청 | 의도, 대상과 처리 방향을 정확히 연결 |
| 생략/화면/과거 참조와 복합 관계 | 올바른 근거, Task, 조건과 요청 관계를 유지 |
| 반복 요청과 원본 변경 | 재사용한 관계가 현재 질문과 source version에 맞음 |
| 정정과 늦은 결과의 교차 | 바뀐 조건만 반영하고 기존 유효 조건 및 무관 업무를 보존 |
| 여러 Task 질문/결과와 채널 변경 | 유효 질문, 실행, 결과와 실제 제시 사실을 정확히 연결 |
| 사실 확인이 불가능하거나 근거가 모호한 경우 | 추측해 확정하지 않고 필요한 확인/보류 및 확인된 사실을 정확히 전달 |

이 목록은 workload의 확정이 아니다. 정답이 명확한 사례에서 질문만 반복한 결과를 성공으로 세지 않으며, 모호한 사례는 정해진 후속 답변을 포함해 해소 결과를 본다. 올바른 clarification이나 불명 안내 자체가 요구 결과인 사례는 그 요구로 판정하되, 완료가 필요한 요청의 성공과 구별한다. 미지원, 누락, timeout과 실패를 분모에서 숨기지 않는 공통 규칙을 정한다. 정확성의 유한 관찰 종료 조건과 응답속도 목표를 구별하여 두 QA의 관계도 명시한다.

평가자용 정답은 후보에 제공하지 않는다. 모델을 포함한 정확률은 실제 모델 실행 없이 구조 설명만으로 숫자를 계산할 수 없다. 코드의 유한 상태/사건 조합은 명시한 범위에서 계약의 성립 여부를 검토할 수 있지만, 가능한 오류 경로의 수를 제품 오류 확률로 바꾸지 않는다. 참고 수치나 가정으로 계산하면 조건부 추정으로 남기며 실제 정확률과 구별한다. 이번에는 이런 시험이나 모델 실행을 시작하지 않는다.

### 7.5 목표와 선택 차이를 정할 근거

목표값은 후보가 낼 것으로 예상하는 수치에서 역산하지 않는다. 지원해야 할 사용 상황, 오해석/오연결의 피해, 허용 가능한 사용자 정정 빈도와 사용량을 근거로 정한다. 다음 세 가지는 서로 다른 결정이다.

1. **목표 정확성:** 사용자가 수용할 수 있는 오류 빈도와 공통 사례 구성을 반영한 목표 성공률. 현재 수치 미정.
2. **필수 위반 조건:** 잘못된 대상의 외부 동작, 중복 실행, 유효하지 않은 승인과 무단 접근 등 기존 필수 규칙을 어떻게 판정할지. 높은 평균 정확성으로 상쇄하지 않음.
3. **선택에 의미 있는 차이:** A/B 차이가 표본 변동을 넘어 실질적인 사용자 이익인지 판정할 기준. 공통 paired 사례의 차이, 불확실성 및 효과 크기를 함께 검토하며 현재 수치 미정.

현재 공동 검토는 요청 처리 정확성의 **평가 단위, 정답 조건과 분모 구성**이다. 의미와 처리 단계의 별도 진단은 이 판정을 설명하도록 연결하며, 목표는 모집단의 의미를 정한 뒤 논의한다.

### 7.6 지표와 분모 구체화 — 사용자 검토안

**측정 모집단은 후보가 생성한 Request, 출력 field나 내부 실행 단계의 수가 아니라, 사전에 공통으로 정한 처리 과제와 정답 조건 목록으로 구성한다.** 아래 과제별 실행 수를 분모로 삼는 식은 하나의 집계 후보다. 조건별 집계에서는 같은 과제의 사전 정답 조건 수가 분모가 될 수 있다. 원시 측정/판정은 §7.7처럼 공유하고, 같은 집계 방식을 모든 DP의 A/B에 적용한다.

#### 평가 단위와 정답 조건

한 평가 단위에는 원본 상태/근거, 사용자 입력 또는 Agent 원천 사건, 공통 사건 순서, 필요한 사용자 답변, 기대 결과와 금지된 효과를 정의한다. 실제 표시/재생 및 외부 접수 등 판정에 필요한 관찰 종료 조건도 갖는다. 큰 대화는 준비 상태로 활용하거나 여러 평가 단위를 포함할 수 있지만, 후보의 내부 처리가 많다는 이유로 분모를 늘리지 않는다.

- 사용자가 한 번에 두 요청과 그 관계를 명시하면, 해당 입력의 복합 요청 처리를 한 과제로 두고 두 요청 및 관계를 모두 확인한다. 후보가 두 개 또는 세 개의 Request를 만들었다고 평가 단위 수가 바뀌지 않는다.
- 이후의 정정은 별도 입력에 대한 처리 과제다. 바뀐 조건, 보존할 조건과 무관 업무에 대한 효과를 함께 확인한다.
- Agent의 질문/결과 사건은 올바른 대화와 Task에 연결하고 처리 사실을 전달하는 과제다. 모델 호출이 없어도 평가 대상이 될 수 있다. 여러 중복 원천 event를 하나의 의미 있는 사건으로 묶는 규칙은 사전에 공통으로 정한다.
- 관계나 실제 전달과 같은 동일 정답 사실은 주 판정 과제에 귀속시켜 한 번만 센다. 다른 과제의 준비 상태나 회귀 확인에 재사용할 때는 원본 판정 ID를 참조한다. 이어진 과제는 같은 대화에서 상관될 수 있으므로 독립 표본으로 가정하지 않는다.

각 과제는 사전에 정한 필수 결과와 금지 효과를 모두 만족하면 PASS, 그렇지 않으면 FAIL로 판정하는 안이다. 의미, 대상/Task, 관계/제약과 처리/전달의 세부 판정은 원인 진단으로 보존한다. schema field가 많거나 일부 필드가 맞았다는 이유로 이 과제에 임의의 부분 정답을 부여하지 않는다.

#### 공통 모집단의 구성 후보

아래 표는 처음 제안한 상황 범위다. 현재 테스트 작성에는 이를 구체화한 **§8.1의 분류와 대표 상황군 지정 규칙**을 사용한다. 최초/반복, 여러 업무, 시간 경쟁 등은 §8.4의 공통 변형으로 함께 관리한다.

| 상황군 | 포함할 처리 과제 | 네 DP에서 확인할 영향 경로 |
| --- | --- | --- |
| 명확한 신규 요청 | 단일 목표, 명확한 대상과 처리 방향 | 일반 해석과 위임/응답 연결의 기준선 |
| 지칭과 근거 연결 | 화면/생략/과거 관계, 최초·반복 조회와 원본 변경 | 41의 의미 결합, 45의 근거 구성 및 생산/갱신 |
| 복합 요청 관계 | 독립, 순차, 조건, 결과 의존과 금지/보존 조건 | 41의 전체 관계 표현 및 결합, 관련 실행/상태 적용 |
| 정정과 시간 경쟁 | 새 입력과 오래된 의미/응답 반환, 전송 전 정정 | 41의 정정 범위, 42의 확정/접수, 44의 무효화와 후속 처리 |
| 여러 업무와 외부 사건 | 질문, 답변, 결과, 취소/완료와 실제 전달의 교차 | 42의 원본/접수 연결, 44의 후속 활성화/게시, 45의 이후 근거 재사용 |
| 모호함과 확인 불가 | 복수 후보, 원본 접근 불가, 확인되지 않은 상태 | 적절한 확인/보류와 사실 보존; 근거 없는 확정 방지 |

상황군은 DP별 전용 시험이나 제품 발생 빈도를 뜻하지 않는다. 과제의 난이도와 사건 조합을 설명하는 공통 분류다. 한 과제에 여러 특성이 있어도 대표 상황군은 하나로 등록하여 중복 집계를 막고 다른 특성은 tag로 남긴다. 같은 모델 조건과 원본/사용자 입력/외부 지원 및 사건 조건을 적용하되, 구조가 만드는 중간 근거나 실행 경로의 차이는 그대로 관찰한다.

제품 사용 빈도 자료가 없는 초기 비교에서는 상황군별 서로 다른 과제 수를 균등하게 두고 과제별 반복 수도 동일하게 두는 **균형 시험 모집단**을 출발점으로 제안한다. 세부 기능의 범위와 중요성에 따라 불균등 배분이 필요하면 이유와 결과의 의미를 함께 합의한다. 실제 제품 사용 빈도의 정확률이라고 부르지 않는다. 난이도와 정상/경쟁/미확인 조건의 비율, 과제 수와 반복 수는 아직 미정이며 균등 배분도 확정 계약은 아니다.

#### 대표값과 공통 분모

```text
N = 사전에 등록한 공통 평가 과제의 전체 scored 실행 수
C = 필수 결과와 금지 효과를 모두 만족한 PASS 실행 수
요청 처리 정확성 후보 = 100 × C / N
```

동일한 과제 목록, 초기 상태와 원천 사건 스케줄, 반복 조건을 모든 DP의 A/B에 적용한다. DP별 구조 인과/참여 여부는 결과의 분해와 원인 설명에 기록하며 그 이유만으로 분모에서 정상 사례를 빼지 않는다. 다른 DP의 선택 조건을 고정하는 구성과 가능한 조합의 미해결 계약은 평가 전에 구체화해야 한다. 네 DP의 절대값을 통합 구조의 정확률처럼 합산하지 않는다.

미지원, 필수 결과 누락, 관찰 종료까지의 미완료와 후보 실패도 분모에 남긴다. 공통 요구가 완료라면 미지원 안내는 PASS가 아니다. 공통 요구가 불명 사실의 정직한 안내라면 그 안내와 금지 효과 조건으로 판정한다. 확인이 필요한 과제는 공통 사용자 답변을 제공하고 요구 결과까지 확인한다. 모든 요청에 질문/보류만 반환해서 정확률을 높이지 못하도록 기대 disposition과 종료 조건을 미리 정한다.

예정된 외부 장애는 공통 과제 조건이다. 시험 장비/수집기의 결함으로 A/B 어느 쪽도 판정할 수 없는 실행은 별도 INVALID 상태와 이유를 보존하고 같은 과제를 복구 후 다시 수행하는 공통 절차를 정한다. 필수 trace를 후보가 생성하지 않아 판정이 불가능한 경우는 후보 실패로 남긴다. 성공 사례만 남겨 분모를 줄이지 않는다.

전체 `C/N`과 함께 상황군별 `C/N`, A만 PASS/B만 PASS한 같은 과제의 쌍, 오류 유형을 공개한다. 반복되는 모델 판단과 같은 대화의 이어진 과제에서 생기는 상관을 반영할 불확실성 계산은 후속 공통 계약에서 정한다. 한 상황군의 실패가 많은 쉬운 정상 과제로 희석되지 않는지 분해 결과를 확인한다.

#### 아직 합의할 사항

현재 제안은 공통 처리 과제와 균형 모집단이며, 과제별 PASS/FAIL은 그 원시 판정을 집계하는 후보 중 하나다. 먼저 §7.7의 공통 측정/정답 판정을 정하고, 그 뒤 집계, 상황군/난이도 배분과 목표를 합의한다. 정의 명칭을 승인한 것만으로 집계 방식이나 모집단을 확정한 것은 아니다.

### 7.7 원시 측정과 지표 집계의 구분 — 현재 검토 순서

사용자 지적대로 **동일한 정답 조건을 사용하면 전체 정답과 부분 정답에 필요한 원시 판정은 같다.** 전체 정답은 조건 판정들의 AND, 부분 정답은 맞은 조건 수와 전체 조건 수의 집계다. 어떤 지표를 택하더라도 같은 실제 사건과 기대 결과를 측정/판정해야 한다. 과제 완료 flag 하나만으로 의미, 대상, 조건과 전달의 정답을 대체하지 않는다.

예를 들어 정정 처리 과제의 네 필수 판정이 `[정답, 정답, 오답, 정답]`이면 전체 정답 집계는 해당 과제 FAIL, 조건별 집계는 3/4다. 이는 같은 자료를 가공한 예이며 실제 측정 결과나 채택된 집계가 아니다. 조건별 비율을 전체에 pooling할지 과제별 비율을 평균할지도 별도 집계 선택이며, 서로 다른 가중을 만들므로 공통 계약에서 정해야 한다.

따라서 다음 순서로 작업한다.

1. **공통 처리 과제와 조건의 coverage:** 고정 UC와 네 DP의 실제 영향 경로에서 어떤 사용자 요청, 근거 변화와 사건 조합을 넣을지 정한다.
2. **정답 조건:** 과제마다 의도한 의미, 대상/Task, 관계/제약, 정정/제어, 상태 및 전달에서 무엇이 맞아야 하는지 정한다. 각 조건은 검사 가능한 사실에 대응하며 내부 JSON 구조 때문에 잘게 쪼개지 않는다.
3. **관측과 정답 판정:** 채택 의미, Agent에 실제 전달한 요청/명령, VIA가 반영한 상태, UI/음성의 실제 전달을 어떤 근거로 확인할지 연결한다. 정답은 원래 입력과 source/사건의 의미에서 정하며 후보 출력 자체로 만들지 않는다.
4. **모집단 배분과 집계:** 조건 목록과 실제 관측이 정해진 뒤 과제/상황군 비율, 반복, 전체 또는 부분 정답의 분모와 실패 처리를 합의한다.
5. **목표와 선택 기준:** 이 모집단이 설명하는 품질의 의미에 맞춰 목표와 의미 있는 A/B 차이를 정한다.

| 각 원시 판정에 기록할 것 | 내용 |
| --- | --- |
| 과제 ID와 조건 ID | 구조와 무관하게 사전에 등록한 판정 사실. 같은 사실의 중복 검사와 재사용을 추적 |
| 입력/상태/사건 조건 | 원문, 허용 근거와 version, Task/질문/결과의 실제 상태와 관련 사건 순서 |
| 기대값 또는 허용 결과 | 단일 정답, 허용되는 복수 결과 또는 필요한 확인/보류, 발생하면 안 되는 효과 |
| 관측 근거 | 채택 결과, 실제 외부 전달, 상태 반영, 실제 표시/재생과 필요한 trace |
| 적용 규칙과 판정 | 사전 적용 범위, 정답/오답/미판정 이유. 누락과 후보 실패, 시험 장비 결함을 구별 |

이 공통 원시 판정 자료로 집계 후보들을 탐색할 수 있으나, 최종 대표 지표는 결과를 보고 유리한 방식으로 선택하지 않고 모든 DP의 A/B에 동일하게 고정한다. 기존 §7.6의 과제별 정답률 권고는 집계 후보로 유지하며, 지금 공동 검토의 첫 질문은 **무엇을 정답 조건으로 측정해야 네 DP의 중요한 품질 효과를 포착하는가**다.

## 8. 공통 테스트 상황과 정답 조건 — v1의 분류 근거

**테스트는 상황 6개 유형으로 분류하고, 정답은 조건 6개 유형으로 기술한다.** 상황 유형은 어떤 문제를 시험하는지, 조건 유형은 무엇이 맞아야 하는지를 나타낸다. 테스트마다 입력, 초기 상태, 사건 순서와 기대값을 바꾸되 조건의 의미와 판정 규칙은 재사용한다. 이 유형들은 새로운 QA 12개나 DP별 지표가 아니다.

기능 범위의 근거는 [고정 UC](../../05-representative-use-cases.md)이며, 네 DP의 영향 경로는 §7.2에 연결한다. 현재 네 비교에서 제외한 음성 모델의 자율 직접 응답은 [04-40](./04-40-common-execution-contract.md)의 경계를 따른다. UC-01의 기존 기능 요구 자체를 삭제하거나 Downstream Agent의 도메인 결과 품질을 VIA 판정으로 가져오지 않는다.

### 8.1 공통 상황 분류

| 유형 | 시험할 상황과 경계 | 공통으로 확인할 핵심 결과 | 주 UC 연결 |
| --- | --- | --- | --- |
| S1 명시적 기본 요청 | 목표와 대상이 입력에 명시된 새 요청. 특별한 과거 지칭, 복합 관계, 정정이나 확인이 필요하지 않음 | 명시된 목표/제약을 누락하지 않고 적절히 답변하거나 위임 | UC-02, 08, 17 |
| S2 지칭과 근거 연결 | 화면, 선택, 생략, 과거 설명이나 업무 결과에서 대상을 찾아야 하는 요청 | 해당 시점/범위/version의 올바른 근거와 대상을 사용 | UC-03, 04, 05, 07, 10 |
| S3 복합 요청과 관계 | 한 입력에 여러 목표가 있고 독립, 순서, 결과 의존 또는 조건 관계가 있음 | 각 목표 및 관계/제약을 보존하고 관계에 맞게 처리 | UC-09 |
| S4 정정과 제어 | 기존 요청/업무의 변경, 음성 중단, 특정 업무 취소 또는 사용자 설정 변경/삭제 | 지정 범위만 바꾸고 무관한 내용/업무를 보존. 효력과 실제 상태를 구별 | UC-10, 11, 12, 17 |
| S5 외부 업무 사건 | Agent의 질문, 진행, 접수, 결과, 실패 등 외부 사건을 VIA가 수신 | 올바른 업무/대화로 연결하고 확인된 사실과 필요한 후속 동작을 전달 | UC-13, 14, 15, 18 |
| S6 확인과 판단 유보 | 처음부터 정보/대상/허용 범위가 불충분한 요청 또는 기존 질문에 대한 사용자 답변 | 필요한 확인/유보를 하고 질문 유효성, 답변의 대상과 승인 범위를 보존. 근거 없는 확정 금지 | UC-06, 14, 16, 18 |

**대표 상황은 후보 실행 전에 원천 입력과 초기 상태로 하나만 지정한다.** 중복되는 경우 다음 순서로 정한다.

1. 평가할 입력이 Agent 원천 사건이면 S5다. 이후 그 질문에 대한 사용자 답변은 별도 과제로 등록하면 S6다.
2. 평가할 입력이 기존 질문의 답변이거나, 필요한 정보/허용이 불충분하도록 작성한 사례면 S6다. 철회/만료된 질문에 대한 답변도 이 유형에서 적용 금지를 확인한다.
3. 기존 내용을 바꾸거나 제어하는 입력이면 S4다.
4. 여러 목표의 관계를 시험하는 입력이면 S3다.
5. 지칭 대상과 근거를 찾아야 하는 입력이면 S2다.
6. 나머지 명시적 기본 요청은 S1이다.

예를 들어 “아까 보고서는 표로 바꾸고 메일은 그대로”는 S4이며 `과거 지칭`, `복수 업무`, `보존 조건`을 변형 tag로 붙인다. 후보가 명확한 S1 요청을 이해하지 못해 질문했다고 그 실행을 S6로 재분류하지 않는다. 복합 사례를 여러 상황군에 복제해 분모를 늘리지 않는다.

### 8.2 재사용할 정답 조건 유형

| 유형 | 정답으로 기술할 사실 | 대표 판정 예시와 관측 경계 |
| --- | --- | --- |
| C1 목표와 처리 방향 | 요청한 행위/산출물의 의미, 답변/위임/확인/유보 등 허용 처리 방향 | 보고서 형식 변경을 새 조사로 바꾸지 않음. 업무 실행은 Agent에 인계. 필요한 확인을 임의 완료로 대체하지 않음 |
| C2 대상과 근거 | 지칭한 자료/객체의 집합과 범위, 원본 시점/version, 실제 전달된 과거 설명이나 결과 참조 | 발화 당시 선택한 표와 당시 v1을 사용. 최신 v2 또는 아직 들려주지 않은 설명으로 바꾸지 않음 |
| C3 대화와 업무 연결 | 새 업무/기존 업무/업무 없음의 관계, 연결할 대화/Task/Execution/질문 | 보고서 변경은 보고서 업무에 적용. 메일 질문의 답을 보고서 업무로 보내지 않음 |
| C4 조건, 관계와 변경 범위 | 내용 제약, 금지/보존 조건, 요청 간 독립/순서/조건/결과 의존, 변경할 범위 | 요약 결과를 메일 입력으로 사용하고 먼저 보내지 않음. 표 형식만 바꾸고 기간/수신자/다른 요청을 보존 |
| C5 처리 효과와 상태 | 실제 요청/명령 적용, 중복 여부, 유효 revision, 접수/완료/실패/미확인 상태와 허용 전이 | 철회한 질문 답변을 적용하지 않음. 같은 command 재수신이 두 번 실행되지 않음. 로컬 접수만으로 외부 완료를 확정하지 않음 |
| C6 응답 내용과 실제 전달 | 사용자에게 알린 사실/결과 참조, Text/음성의 의미 일치, 실제 표시/재생과 전달 기록 | 미확인 취소를 완료라고 말하지 않음. 텍스트와 음성이 같은 업무 상태를 알림. 음성 중단 이후 미재생 범위를 들었다고 기록하지 않음 |

기대값은 사용자 입력과 공통 근거에서 정한다. Task가 아직 없다면 `새 업무에 연결`을 기대값으로 기록하고, 실제 생성 ID는 관측 후 대응시킨다. 특정 Task ID를 미리 확정한 것으로 모델에 주지 않는다. 기존 업무/질문은 fixture의 의미 ID와 실제 runtime ID를 대응시켜 검사한다.

정보 조회에서 허용되는 Core 직접 응답과 Agent 위임처럼 같은 요구를 만족하는 복수 결과는 사전에 허용 집합으로 기록한다. Component 배치, 모델 호출 횟수, 내부 frame 형식이나 의미 생산 순서는 이 QA의 정답 조건으로 강제하지 않는다. 실제로 채택된 의미, 외부로 전달한 요청/명령, 적용 상태와 사용자 전달에서 판정한다. 채택 전 틀린 임시 후보를 스스로 고친 것은 최종 오류와 구별하되, 이미 발생한 금지 효과는 마지막 상태가 맞아도 지우지 않는다.

#### 조건을 작성하는 공통 규칙

- 여섯 유형을 모든 테스트 양식에 둔다. 해당 사실이 있는 유형에는 조건을 쓰고 없는 유형은 **사전에** 적용 없음과 이유를 기록한다. 후보 출력에 field가 없다는 이유로 적용 없음으로 바꾸지 않는다.
- 조건 하나는 사용자에게 의미 있는 판정 사실 하나다. `수신자=민수`, `보고서 형식=표`, `메일 요청 보존`처럼 고정 의미 단위로 작성한다. 내부 JSON 속성 수나 Module 수에 따라 조건을 쪼개지 않는다.
- 같은 사실은 하나의 주 조건 ID에 귀속시킨다. 예를 들어 목표 업무 선택은 C3, 그 업무에 command가 한 번 적용된 사실은 C5, 그 처리 사실의 올바른 안내는 C6다. 같은 업무 선택 사실을 세 유형에서 세 정답으로 세지 않는다. 한 오선택이 실제 적용과 안내까지 오염시킨 경우 서로 다른 효과와 공통 원인은 함께 기록한다.
- 대상 집합이나 관계 graph의 판정 단위도 동일하다. 한 사례에서만 원소/간선을 별도 점수로 세지 않는다. 세부 누락/추가 항목은 진단으로 보존하고 집계 단위는 후속 계약에서 공통 결정한다.
- 명확한 사례에는 기대한 요청 처리를 요구한다. 근거가 부족한 사례에는 필요한 질문/유보와 공통 후속 답변 뒤의 처리까지 요구한다. 단순 접수 멘트나 모든 요청의 보류로 정답을 얻지 못한다.

### 8.3 구체적인 테스트 초안 18개

다음 18개는 **§9 v1의 기본 사례**로 채택했다. 각 사례의 6개 필수 채점 항목은 §9.4에 고정했다. 실제 원본 파일과 입력/사건 fixture는 이 계약대로 제작하고 실행 전에 hash를 고정한다. 표의 정답은 중심 사실이며 전체 필수 항목은 §9.4를 따른다. 18개가 제품의 모든 UC/필수 변형을 빠짐없이 검증한다는 뜻은 아니다.

| 사례 | 공통 초기 상태와 입력/사건 | 중심 정답 조건 |
| --- | --- | --- |
| S1-01 제한된 정보 조회 | 허용 문서 D1에 마감일 `10월 15일`이 명시됨. “D1에 적힌 마감일 알려줘” | C1: 범위 내 조회. C2: D1의 지정 version. C6: 10월 15일이라는 사실 전달. 허용되는 직접 응답/위임 경로 모두 인정 |
| S1-02 새 업무 위임 | 관련 기존 업무 없음. “올해 3분기 매출 보고서를 표 형식으로 작성해줘” | C1: 보고서 작성 위임. C3: 새 업무 연결. C4: 올해/3분기/표 조건. C5: 올바른 요청 전달. Agent가 실제 작성한 보고서의 품질은 제외 |
| S1-03 개인화 신규 등록 | 해당 선호의 기존 기록 없음. “앞으로 비교 결과는 표로 보여주는 걸 선호한다고 기억해줘” | C1: 선호 저장. C4: 비교 결과에 한정한 선호. C5: 허용된 저장 효과. C6: 저장한 범위를 사실대로 알림 |
| S2-01 발화 중 화면 지칭 | 발화 중 첫 “이 표”에는 표 A, 두 번째 “저 표”에는 표 B를 가리킴. 이후 화면은 C로 바뀜. “이 표와 저 표를 비교해줘” | C2: A/B와 각 당시 관측 범위. C1: 비교 목표. C4: 두 대상의 역할 보존. 현재 C로 치환 금지 |
| S2-02 과거 설명과 두 업무 결과 | 기준 설명 중 실제 들려준 범위 E1, 완료한 제품 비교 D2@v2와 견적 D3@v1이 있음. “아까 들은 기준과 두 업무 결과로 새 제안서를 만들어줘” | C2: 실제 전달 E1 및 D2/D3의 올바른 참조. C3: 과거 업무에 추가 지시하지 않고 새 업무 연결. C4: 기준/결과 사용 조건. 제안서 도메인 작성은 Agent 책임 |
| S2-03 원본 갱신과 과거 참조 | 과거 보여준 D1@v1의 값은 100, 현재 v2는 120. “그때 보여준 값으로 표를 만들어줘” | C2: v1/100을 선택. C4: 과거 기준 보존. v2/120을 최신이라는 이유로 사용하지 않음. v1 접근 불가 변형은 S6로 별도 사전 등록 |
| S3-01 독립된 두 요청 | “D1 요약해주고, 내일 일정도 알려줘.” D1과 일정 근거가 모두 허용됨 | C1: 두 목표 보존. C2: 각각의 근거. C4: 독립 관계. 한쪽 결과를 다른 쪽의 불필요한 선행 조건으로 만들지 않음 |
| S3-02 결과 의존 | “D1을 요약한 다음, 그 요약을 민수에게 메일로 보내줘.” 실행 허용과 수신자 정보 있음 | C4: 요약 산출물 참조를 메일 입력으로 사용. C5: 준비 전 메일 전송 없음. C2: D1/민수. 원본 문서 또는 다른 요약을 보내지 않음 |
| S3-03 조건 분기 | “금요일 3시가 비어 있으면 회의 잡고, 아니면 가능한 시간만 알려줘.” 공통 일정 fixture가 비어 있음/차 있음 두 변형 | C4: 같은 조건 관계 보존. C5: 빈 경우만 회의 생성 요청, 찬 경우 생성 없음. C6: 실제 조건/처리 사실에 맞는 안내 |
| S4-01 부분 정정과 늦은 후보 | 보고서/메일 요청을 준비 중이며 외부 전송 전. “보고서는 표로 바꾸고 메일은 그대로.” 정정 전 의미 후보가 늦게 반환 | C3: 보고서 업무. C4: 형식 변경과 메일/기타 조건 보존. C5: 정정 전 후보가 다시 적용되거나 전송되지 않음 |
| S4-02 음성 중단 | Agent 업무는 실행 중, VIA 설명은 일부만 재생. 사용자가 “잠깐, 그 수치부터 설명해줘”라고 끼어듦 | C1: 후속 설명 요청. C5: 음성 출력 중단, 업무 취소 없음. C6: 실제 들린 범위만 전달 기록. 중단 시간 수치는 응답속도에서 별도 정의 |
| S4-03 특정 업무 취소 | 보고서/메일 업무가 함께 실행 중. “메일 업무만 취소해줘.” fixture는 Agent의 취소 접수 뒤 종료 확인 또는 종료 미확인 변형 | C3: 메일 업무. C5: 해당 취소만 전달, 보고서 유지, 접수/종료/미확인 구별. C6: 확인된 단계만 안내. 이미 실행된 외부 효과를 없었다고 주장하지 않음 |
| S5-01 교차하는 질문 | 보고서 Task의 기간 질문과 메일 Task의 수신자 질문이 차례로 도착 | C3: 각 질문의 업무/질문 ID 유지. C5: 질문 유효성/제시 상태 반영. C6: 어떤 업무의 질문인지 제시하고 실제 제시 범위 기록. 사용자 답변은 S6의 후속 과제 |
| S5-02 결과 역전과 중복 | 두 Task의 결과가 시작 순서와 반대로 도착하고, 하나는 중복 수신. 정정 전 결과도 늦게 도착 | C3: 각각 올바른 업무 연결. C5: 중복 실행/새 완료 처리 없음, 오래된 결과의 현재 채택 금지. C6: 유효 결과/version 전달 |
| S5-03 음성 종료 중 결과 | 사용자가 음성을 종료했지만 업무는 유지. Agent 결과가 Text로 표시된 뒤 음성 재연결 | C5: 결과/업무 유지, 새 실행 없음. C6: Text 표시와 음성 전달 사실 구별. 필요한 재연결 안내를 하고 미재생 결과를 이미 들었다고 기록하지 않음 |
| S6-01 모호한 과거 대상 | 과거 보고서 두 개가 동일하게 유효함. “아까 보고서 수정해줘.” 이어서 사용자는 대상/수정 내용을 답함 | C1: 필요한 대상/내용 확인. C5: 답변 전 임의 변경 없음. C2/C3/C4: 답변 뒤 지정한 대상/업무/변경 적용. 질문 문구 자체는 일치 불필요 |
| S6-02 답변과 승인 범위 | 메일 Task의 유효 질문 Q1은 연락처 조회 동의이고, 별도 Q2는 전송 승인 대기. 실제 제시된 질문은 Q1. 사용자가 “응” | C3: Q1 답변 연결. C4/C5: 연락처 조회만 허용하고 전송 승인으로 확장하지 않음. 제시 대상이 확정되지 않는 변형은 재확인하며 임의 승인 금지 |
| S6-03 필요한 근거 접근 불가 | 필요한 D1의 접근이 거부되었으며 허용 대체 근거 없음. “D1의 계약 금액을 알려줘” | C1: 접근 불가 안내와 허용 대안/유보. C2: 임의 다른 문서로 대체 금지. C5: 권한 우회 조회 없음. C6: 금액을 추측하거나 조회 성공으로 알리지 않음 |

S1-03의 신규 저장 외에 기존 선호 변경/삭제는 S4로 분류한다. 삭제 후 재사용 금지는 같은 C2/C5 규칙으로 작성한다. 접근 거부, 누락, 접수 미확인 등은 fixture에 따라 정답이 달라질 수 있으나 판정 유형을 새로 만들지 않는다.

#### 한 사례의 정답표 작성 예 — S4-01

초기 상태는 보고서 업무 T보고서와 메일 업무 T메일이 각각 존재하고, 보고서 대상은 D1@v1, 기간은 올해 3분기, 형식은 문장이라고 둔다. 메일 대상/수신자와 지시는 이미 정해져 있다. 현재 준비 중인 변경 요청은 아직 외부에 전송되지 않았다. 사용자가 “보고서는 표로 바꾸고 메일은 그대로”라고 정정한 뒤 이전 입력을 기준으로 만든 의미 후보가 늦게 돌아온다. 공통 외부 Agent는 올바른 변경 요청의 접수만 확인하고 완료는 알리지 않는다.

| 공통 조건 유형 | 사전 기대값 | 확인할 근거 |
| --- | --- | --- |
| C1 목표와 처리 방향 | 기존 보고서의 형식 변경. 새 보고서 업무 생성이나 새로운 조사로 바꾸지 않음 | 채택 의미와 Agent에 전달한 요청의 목적 |
| C2 대상과 근거 | 보고서 대상 D1@v1 유지. 다른 자료나 최신 원본으로 교체하지 않음 | 실제 요청의 자료/version 참조 |
| C3 대화와 업무 연결 | T보고서에 변경 연결. T메일에 변경 연결하지 않음 | 실제 요청/명령의 업무 및 대화 연결 |
| C4 조건, 관계와 변경 범위 | 형식=표, 기간=올해 3분기 유지, 메일의 기존 대상/수신자/지시 보존 | 채택한 변경/보존 조건과 실제 인계 내용 |
| C5 처리 효과와 상태 | 유효 정정만 적용. 늦은 이전 후보의 재적용과 중복 변경 없음. 외부 접수 확인을 완료로 전이하지 않음 | 변경 적용/전송 trace, Agent receipt, 업무 상태 |
| C6 응답 내용과 실제 전달 | 보고서 변경 접수 사실을 알림. 완료라고 주장하지 않음. 실제 표시/재생 범위대로 기록 | 실제 Text/음성 내용과 전달 evidence |

이것은 **6개 조건 유형을 채운 예**다. §9 v1에서는 유형마다 필수 사실을 모두 만족해야 1점이 되는 여섯 이진 항목으로 집계한다. C4의 형식/기간/메일 보존처럼 여러 사실은 진단용 조건 ID로 등록하되 항목 내 부분 점수를 추가하지 않는다.

### 8.4 상황을 늘리지 않고 적용할 공통 변형

| 변형 축 | 정해진 값의 예 | 유지할 규칙 |
| --- | --- | --- |
| 입력 채널 | Voice, Text, Voice/Text 전환 | 같은 의도/목표를 유지하고 실제 입력 및 전달 차이는 남김. 의미 QA에서 음성 전사를 완벽한 것으로 자동 교체하지 않음 |
| 근거 출처 | 현재 화면/선택, 과거 실제 전달, 업무 결과, 허용 User Memory, 제한된 외부 자료 | 출처 종류로 새로운 정답 유형을 만들지 않고 C2의 대상/범위/version 검사 사용 |
| 업무 수와 관계 | 업무 없음, 하나, 여러 업무, 같은/다른 Agent | 기존 업무의 사실은 공통 제공하되 현재 요청의 Task 연결을 미리 정답 입력으로 제공하지 않음 |
| 근거 및 권한 상태 | 유일, 복수 후보, 누락, 변경/철회, 접근 거부, 승인 대기 | 예상 처리 방향과 금지 효과를 사전 설정. 모호함/불충분 사례는 S6 지정 규칙 적용 |
| 사건 순서 | 정상, 도착 순서 역전, 중복, 정정 후 늦은 반환, 질문 철회와 답변 경쟁 | 같은 원천 사실/외부 사건 조건을 적용. 내부 단계 수나 특정 구조의 반환 순서를 정답으로 강제하지 않음 |
| 과거 근거 사용 이력 | 첫 요청, 반복 요청, 원본 갱신 후 요청 | 양안에 같은 과거 활동과 준비 기간 제공. B에만 정답 파생 관계를 미리 넣지 않고 A의 허용 cache도 제거하지 않음 |
| 전달 상태 | Text 표시, 음성 전체/일부 재생, 음성 종료, receipt 미확인 | 생성/게시/실제 전달을 구별. 확인되지 않은 전달은 실제 전달로 간주하지 않음 |

모든 축의 전 조합을 만들지는 않는다. 고정 UC의 필수 변형과 §7.2의 실제 품질 효과를 드러내는 조합을 coverage 표로 관리한다. 여러 업무와 경쟁은 S4/S5만의 특성이 아니므로 S2/S3/S6에도 필요할 때 동일 변형을 적용한다. 각 DP를 설명하는 연결은 다음과 같으며 전용 분모를 만들지 않는다.

- **41:** S2/S3/S4/S6의 목표, 대상, 관계, 변경 범위와 확인 처리. 표현 가능한 관계뿐 아니라 공통 기능 범위 안의 새로운 관계도 포함한다.
- **42:** S4/S5/S6의 업무/질문 연결, 명령 접수와 반영, 취소/완료 사실. 정상 경로와 재접수/철회 경쟁을 구별한다.
- **44:** S4/S5/S6의 늦은 반환, 입력 중단, 실제 제시, 유효 답변과 후속 실행. 강한 A의 비동기/현재성 검사를 보존한다.
- **45:** S2 및 과거 근거 tag가 있는 다른 상황의 첫/반복/갱신 후 사용. 양안의 cache, 원본 확인, 오류 전파를 동일 사용자 결과로 판정한다.

### 8.5 공통 판정 방식과 관측

정답 조건은 다음 검사 방식으로 표현한다. **테스트마다 새로운 채점 알고리즘을 만들지 않고 조건 유형, 비교 연산과 기대값을 지정한다.** 아래는 평가 설계이며 실행 harness나 runtime schema를 구현한 것은 아니다.

| 공통 검사 방식 | 용도 | 예 |
| --- | --- | --- |
| 값/의미 일치 | ID, version, 상태, 의미가 정해진 목표/제약 | 대상 업무=메일, 기간=3분기, 기대 상태=접수됨 |
| 집합 일치 | 필수 대상/조건의 누락 및 원치 않은 추가 | 참조 대상={A, B}, 다른 C 포함 금지 |
| 허용 결과 집합 | 요구를 만족하는 복수 경로/표현 | 제한된 조회의 허용 직접 응답/위임, 의미가 같은 질문/안내 |
| 관계/전이 충족 | 조건/의존 graph, 실제 상태 변화와 인과 순서 | 요약 결과 준비 뒤 해당 참조로 메일 인계, 취소 접수와 종료 구별 |
| 금지 효과 없음 | 정해진 관찰 구간 전체의 부정 조건 | 답변 전 임의 실행 없음, 다른 Task 취소 없음, 중복 외부 명령 없음 |

자연어 결과는 정확한 문자열 일치로 채점하지 않는다. 사전 등록한 의미 사실/허용 표현 기준에 맞춰 목표, 조건과 주장 사실을 판정한다. 문장마다 임의의 “그럴듯함” 점수를 주지 않으며 자동 판정이 어려운 사실은 같은 rubric과 검토 절차로 기록한다. 자동/수동 판정과 평가자 불일치 처리는 §9.6으로 고정했다.

관측은 각 조건의 경계에 맞춘다. C1~C4는 채택 의미와 실제 처리에 사용한 대상/관계를, C5는 명령 전송/Agent receipt/상태 반영을, C6는 실제 Text 표시/음성 재생과 기록을 연결한다. 공통 의미로 정규화한 관측 record를 쓰되 A/B의 내부 저장 필드나 중간 Module을 같은 형식으로 바꾸도록 요구하지 않는다. 필요한 adapter와 필수 evidence는 측정 계약에서 별도 설계한다.

정답 조건별 record에는 `과제 ID, 조건 ID, C 유형, 검사 방식, 기대값, 실제값, evidence 참조, 판정, 오류 원인`을 둔다. 결과는 `정답/오답/적용 없음`으로 남긴다. 필수 결과/관측의 후보 귀속 누락은 오답으로 남기고, 시험 수집기 결함은 §7.6의 INVALID 절차를 따른다. 금지 효과가 없다는 판정에는 전체 관찰 구간의 필수 trace가 필요하다. 끝 상태만 보고 중간 오실행이 없었다고 추정하지 않는다.

기존 검사 방식으로 표현할 수 없는 중요한 사실을 발견하면 공통 조건/검사 정의를 개정하고 영향받는 사례 전체에 적용한다. 특정 DP나 실패 사례 하나에만 다른 판정법을 추가하지 않는다. 정답 파일은 평가자만 보며 후보에는 정상 사용자가 접근할 수 있는 입력/근거와 동일한 외부 지원만 제공한다.

### 8.6 모든 테스트에 사용할 작성 양식

```text
과제 ID / 대표 상황 S1~S6 / 고정 UC / 공통 변형 tag
초기 상태: 대화, 기존 업무/질문, 허용 정보/권한, 원본 version, 실제 전달 범위
입력과 사건: 원문 또는 음성, 화면/행동 근거, Agent 원천 사건, 공통 후속 사용자 답변
사건 순서: 공통 원천 사건의 순서/경쟁 조건과 외부 지원 응답
기대 조건:
  C1 목표와 처리 방향       → 조건 ID, 검사 방식, 기대값 또는 허용 집합
  C2 대상과 근거            → 동일 양식
  C3 대화와 업무 연결       → 동일 양식
  C4 조건, 관계와 변경 범위 → 동일 양식
  C5 처리 효과와 상태       → 동일 양식
  C6 응답 내용과 실제 전달  → 동일 양식
  적용 없음               → 유형/이유를 사전 기록
금지 효과: 조건 ID에 연결해 관찰 구간 전체에서 확인
관찰 종료: 요구 결과의 관측 경계, 지연 사건 포함 구간, 공통 최대 대기 규칙
관측 및 판정: 조건별 실제값/evidence/정답 여부/오류 원인
```

한 과제 안에 확인 질문과 공통 답변을 포함할 수 있다. 별도 과제로 나눌 경우 원래 질문/조건 ID를 연결하고 같은 사실을 중복 채점하지 않는다. 후보의 질문 문구/순서가 달라도 동일 의미의 답변을 제공한다. 답변 제공 규칙은 같은 질문 대상과 정보량을 유지하며 필요 없는 힌트를 추가하지 않는다.

사건 schedule은 공통 원천 사건과 외부 의미 경계에 맞춘다. 특정 안의 내부 Module 시작/완료를 기준으로 다른 안에 더 유리한 근거를 주지 않는다. 후보의 계산/조회/확정 순서는 구조가 만들도록 두고 경쟁 조건의 적용 방법을 계약에 명시한다. v1의 profile/관찰 종료/최대 대기는 §9.3/9.6을 따른다.

위 양식과 분류를 바탕으로 §9의 평가 설계 v1을 확정했다. 원본 fixture 제작과 관측 adapter는 §9의 실행 준비 단계이며, 상황 분류와 집계/분모/목표를 다시 결정하는 작업이 아니다.

## 9. 요청 처리 정확성 평가 설계 v1 — 2026-10-10 확정

**사용자가 이번에 평가 설계를 확정하도록 요청한 범위에서 다음 내용을 정한다.** 이 절의 분류, 채점, 모집단, 목표와 비교 규칙을 이후 실행의 기준으로 사용한다. 특정 A/B의 우열, 실제 목표 달성, 전체 제품 SLA나 나머지 QA의 정의를 확정한 것은 아니다. 실제 파일/모델/후보 build를 고정하는 machine freeze와 시험 실행은 별도 작업이다.

### 9.1 확정한 정의와 채점 단위

- **정의:** VIA가 사용자 입력과 외부 사건을 의도 및 확인 가능한 사실에 맞는 요청 처리 결과로 연결하는 능력. 의미, 근거/대상, 업무 연결, 관계/변경, 적용 상태와 실제 전달을 포함한다.
- **평가 상황:** §8.1의 S1~S6. 기본 사례는 §8.3의 상황군별 3개, 총 18개로 고정한다.
- **실행당 채점:** C1~C6를 각각 0 또는 1로 판정한다. 항목 안의 필수 사실을 모두 만족하면 1, 하나라도 틀리거나 필요한 결과/근거가 없으면 0이다. 세부 사실별 진단은 보존하지만 별도 점수로 더하지 않는다.
- **대표 지표:** 채점 항목 전체의 정답률. 여섯 항목은 같은 비중이며 비용/시간 등 다른 QA와 가중 합산하지 않는다.
- **완전 정답 처리율:** 한 실행의 여섯 항목이 모두 1인 비율. 같은 원시 판정에서 계산해 보조 품질 한도로 사용한다.

**기본 사례 18개를 한 조건에서 한 번 실행하면 18 × 6 = 108개 항목을 채점한다.** v1의 18개 사례에는 여섯 유형 모두에 의미 있는 필수 사실을 §9.4처럼 등록하므로 N/A 칸이 없다. 예를 들어 업무가 없는 경우의 C3은 `무관 Task에 연결하지 않음`, 상태 변경이 없는 조회의 C5는 `조회/응답을 처리하고 불필요한 외부 업무 효과를 만들지 않음`으로 검사한다. 빈 항목에 자동 1점을 주는 방식이 아니다.

기존 §8.2의 유형 안 세부 조건별 집계와 N/A 허용은 확장 평가를 설계할 때의 일반 원칙으로 남긴다. **이번 v1에서는 여섯 묶음의 이진 판정으로 집계한다.** 판정 후 N/A로 변경하거나 사례별 조건 수로 가중치를 바꾸지 않는다.

### 9.2 네 DP에서 차이를 포착할 수 있는가

| DP | 같은 QA에서 값이 달라질 수 있는 원인 | 주 관찰 사례/항목 | 강한 반대안과 같아질 조건 | 이번 결론 |
| --- | --- | --- | --- | --- |
| 41 | A의 조회 선택/전체 결합 오류 대 B의 frame 추출/유한 표현/코드 결합 오류. 생략, 부정, 예외와 부분 정정에서 다른 최종 의미를 만들 수 있음 | S2-01~03, S3-01~03, S4-01, S6-01/02의 C1~C4 및 실제 인계 | B가 필요한 표현을 포괄하고 A도 보존 검사/patch를 수행하면 동일 정답 가능 | 정확성에 직접 민감. 정형 표현과 자연스러운 교차 관계를 함께 시험 |
| 42 | A의 공동 로컬 확정 대 B의 별도 접수/대화 반영 사이에 질문 철회, 상태 변경, 접수 응답 유실이 끼면 적용/안내가 달라질 수 있음 | S4-01/03, S5-01~03, S6-02의 C3/C5/C6 | 동일 의미 모델과 올바른 재검사/중복 방지/사실 반영이면 양안 모두 정답. IPC 횟수 자체는 감점하지 않음 | 정확성의 주요 역할은 상태 처리 회귀 검사. 정상 의미 정확도 차이를 예상하지 않음 |
| 44 | A의 중앙 후속 전이 연결 대 B의 window/join/cancel 연결이 늦은 결과와 실제 제시를 처리할 때 다른 효과/전달을 만들 수 있음 | S4-01/02, S5-01~03, S6-02의 C3/C5/C6 | A의 비동기/priority/revision 검사와 B의 유효 join/최종 검사 모두 맞으면 동일 정답 | 교차 사건에 민감한 회귀 검사. 실행 조직만으로 B의 의미 정확성 이익을 부여하지 않음 |
| 45 | A의 현재 요청별 원본 결합 누락 대 B의 과거 관계 생산 손실/오류 공유/갱신 지연. 부정/예외와 실제 전달/원본 version에서 차이 가능 | S2-02/03, 과거 근거가 있는 S4-01/S6-01의 C2~C4 및 후속 인계 | A의 유효 cache와 B의 원문 확인/충분한 관계/부분 갱신으로 차이가 줄 수 있음 | 정확성에 직접 민감. 첫 사용/반복/갱신 직후와 원문 조건 보존을 함께 시험 |

**이 지표는 네 DP의 중요한 오류 경로를 관찰하지만 네 쌍 모두에 다른 값이 나오도록 보장하지 않는다.** 42/44가 같은 정확률이면 정상적인 결과다. 원래 품질 효과가 재처리 시간, 비용, 변경 범위나 메모리에만 남았다면 해당 QA에서 비교한다. 이를 정확률 차이로 만들기 위해 A의 검사를 제거하거나 B에 오류 확률을 미리 주입하지 않는다.

41B의 frame 또는 45B의 관계 종류가 같은 UC 요구를 표현하지 못하면 미지원과 원래 요구 손실을 기록하고 해당 필수 항목을 0으로 판정한다. 사용자 목표를 더 단순한 요청으로 바꾸어 성공으로 세지 않는다. 범용 의미 모델에게 전체 관계를 맡긴 B+는 별도 혼합 후보이며 순수 B의 점수로 보고하지 않는다.

### 9.3 공통 모집단과 실행 수

모든 DP A/B에 같은 **18개 기본 사례 × 입력 채널 2개 × 조건 profile 3개 × 반복 5회**를 적용한다.

| 축 | 고정한 구성 |
| --- | --- |
| 기본 사례 | S1~S6별 3개씩, §8.3의 18개. 후보가 생성한 Request/Task 수로 증가하지 않음 |
| 입력 채널 | Text와 Voice 각 1개. S5의 최초 사건은 Agent event이며 채널은 사용자 전달과 공통 후속 답변의 채널을 뜻함 |
| N 정상/첫 사용 | 보존된 원본/기존 상태에서 시작, 관련 신규 조회의 cache/게시 결과를 정답으로 선주입하지 않음. 추가 경쟁 없음 |
| W 반복/준비된 과거 | 같은 원본 활동 이력과 허용된 이전 조회를 실제 후보 경로로 처리한 뒤 현재 과제 실행. 양안 cache/생산/갱신 허용. 최대 120초의 동일 준비 창과 그 비용을 기록 |
| X 변경/교차 | 동일 초기 원본에서 관련 변경/철회, 중복/늦은 반환과 질문/결과의 교차를 사전 event script로 재생. source/hold/전송 경계를 trace로 확인 |
| 반복 | 각 기본 사례/채널/profile 조합에 5회. 매 반복은 초기 상태 복원 후 해당 준비 이력을 다시 처리. 실행 간 cache/Task/질문 누적을 섞지 않음 |

W는 B만 미리 완성된 기억을 받는 조건이 아니다. 준비 기간에는 양안이 같은 사용자 활동과 원본 사건을 실제 처리한다. 이전 조회는 과거 근거의 허용 read-only 조회로 한정하고 현재 채점할 신규 등록/업무/취소를 미리 실행하지 않는다. 기존 Task/질문/권한의 공통 준비 상태를 유지한다. A의 cache를 제거하지 않고 B의 관계 생산/게시를 evaluator가 대신하지 않는다. 준비 처리의 실제 비용/유실/지연도 기록한다. 현재 목표를 평가자 정답으로 알려주는 요청을 준비 이력에 넣지 않는다.

X의 공통 사건은 `관련 source 변경`, `질문/접수 사실 변경`, `이전 generation 반환`, `무관 업무 알림 5개`, `같은 외부 event 중복 1개`라는 재사용 유형으로 작성한다. 각 사례에서 존재하는 source/job/질문에 연결하며 없는 대상의 사건을 억지로 발명하지 않는다. 연결할 내부 job이 없으면 같은 외부 burst를 적용하고 job 관련 효과는 발생하지 않은 것으로 기록한다. 실제 모델 결과의 값은 바꾸지 않고 반환 전달 순서만 제어할 수 있다.

| 상황군 | X에서 집중할 사건과 공통 정답 규칙 |
| --- | --- |
| S1 | 다른 업무 결과/질문의 교차. 지정 목표/대상/제약과 전달을 오염시키지 않음 |
| S2 | source v1→v2와 오래된 파생 조회/생산 반환. 명시한 과거 snapshot과 현재 대상의 유효성을 구별하고 원문 부정/예외 보존 |
| S3 | 선행 결과의 늦은/중복 도착 또는 조건 근거 변경. 유효한 결과 참조/분기만 후속 처리에 사용 |
| S4 | 새 입력의 hold와 이전 후보/명령 경합. 정정 후 유효 변경만 적용하며 이미 외부로 나간 효과는 실제 사실대로 처리 |
| S5 | 질문 철회, 결과 version 변경, 역전/중복 수신. 각 원천 사실을 올바른 업무에 반영하고 stale/중복 효과 방지 |
| S6 | 실제 제시 receipt의 미확인 또는 질문/허용의 철회와 답변 교차. 필요하면 다시 확인하고 유효하지 않은 답변/승인 적용 금지 |

원문 표현도 고정한다. N은 §8.3의 대표 표현, W는 같은 의미의 자연스러운 바꿔 말하기, X는 원문에 명시된 부정/예외/보존 범위를 유지하는 표현을 사용한다. 목적/관계가 여러 개인 사례를 S1로 바꾸거나 모호한 사례를 명확한 것으로 바꾸지 않는다. S2-02의 과거 설명에는 `평가 기준 중 가격 제외`라는 명시 예외를 포함해 실제 전달 범위와 제외 조건을 확인한다. S3-03의 N은 빈 일정, W는 이미 일정 있음, X는 조회 후 일정이 차는 조건으로 고정해 두 분기와 변경 재확인을 검사한다.

```text
후보 1개: 18 × 2 × 3 × 5 = 540회 처리 과제 실행
후보 1개의 채점 분모: 540 × 6 = 3,240개 이진 항목
상황군 1개의 채점 분모: 3 × 2 × 3 × 5 × 6 = 540개
조건 유형 C 하나의 분모: 540개
DP 1개의 A/B: 1,080회 실행 / 6,480개 항목
네 DP를 모두 비교: 4,320회 실행 / 25,920개 항목
```

이는 상황/채널/profile을 균형 있게 시험하는 정확률이며 실제 제품 발생 빈도로 가중한 정확률이 아니다. 540회 또는 3,240개 항목을 모두 독립 표본으로 주장하지 않는다. 반복과 같은 대화의 후속 관측은 해당 기본 사례에 묶는다. 서로 다른 DP의 분자/분모를 합쳐 하나의 VIA 제품 정확률로 만들지 않는다.

### 9.5 시험 환경과 A/B 구성

| 영역 | 고정할 시험 환경과 역할 |
| --- | --- |
| 실행 장비 | 같은 로컬 시험 장비 한 대, AC 전원/전원 모드 동일. 기존 evaluation-profile의 MacBook Air/M5/24 GB는 재사용 장비 reference다. 이번 확인에서 OS는 macOS 26.5.1 (25F80), hardware sysctl은 sandbox 제한으로 재확인 못 했으므로 manifest에서 실제 CPU/메모리를 검증한다. 장비가 다르면 A/B 모두 같은 새 장비에서 전체 쌍 실행 |

이번 검토 중 병행 상세화된 [42 §4.2~4.3](./04-42-lifecycle-ownership.md#42-b에서-추가로-필요한-입력권한후속-요청-계약)와 [44 §3.1](./04-44-continuous-interaction.md#31-공통-소유와-허용-경계)을 확인했다. 42B의 Hold/HoldAck, CommandIntent, ReleaseAndReconcile, AcceptanceReceipt와 업무 로컬 transmission CAS가 44A/B의 후속 실행에 연결되는 문서 계약이 추가되어 있다. [04-40 §6](./04-40-common-execution-contract.md#6-네-dp가-실제-프로그램에서-결합되는-지점)의 이전 UNRESOLVED 표기만 보고 프로토콜 설명 자체가 없다고 복원하지 않는다. **문서 계약은 있으며 실제 구현/조합 검증은 아직 없다.** 대화/업무 저장소가 공동 transaction을 가진 것처럼 구현하지 않고 위 독립 접수/ACK/UNKNOWN 경로를 실행해야 한다. 구현/관측 준비 전 상태는 NOT_READY이며 A/B 수치가 아니다. 위 한 조건 비교는 다른 조합에서의 상호작용 우열을 입증하지 않는다.

모든 Task를 실제 외부 계정에 만들 필요가 없다. Agent 업무 품질은 stub으로 통제하고 VIA의 요청/상태/전달을 검사한다. **41/45의 의미 LLM까지 정답 mock으로 대체하면 실제 의미 정확성 비교가 되지 않는다.** model mock은 runner/판정의 검수에만 사용하고 공식 정확률은 실제 모델을 통과한 후보 실행에서 계산한다. mock 오류 확률로 A/B 차이를 만들어내지 않는다. 결과 evidence는 `MEASURED_REFERENCE_HARNESS`와 실제 모델 실행의 `MEASURED_MODEL`을 명시하며 이 장비/replay/stub 조건의 결과다. PC 제품/실제 Agent의 `PRODUCT_E2E`로 부르지 않는다.

### 9.6 실행과 관측 절차

1. **실행 자산 제작:** 18개 원본/정답표를 §9.4대로 만들고 Text/Voice 및 N/W/X를 전개한다. 파일 hash, source event script, fixture 의미 ID와 runtime ID 대응, audio/screen 시각, rubric을 고정한다. 후보에게 정답표를 제공하지 않는다.
2. **runner 검수:** 정답/누락/오선택/잘못된 상태/미전달 trace를 이용해 C1~C6와 위반 검출을 확인한다. 이는 검사기 검수이며 후보 정확성 점수에 넣지 않는다. critical Action은 stub 경계에서만 기록한다.
3. **모델/후보 binding:** 동일 build/설정과 실제 저장/인계/입력/표시/재생 경계의 관측을 확인한다. 구조별 prompt/운영 예산과 cache/생산의 version을 기록하고 준비 상태를 확인한다. 정답표를 보며 한쪽 prompt만 조정하지 않는다.
4. **동일 준비 상태 복원:** N/W/X의 동일 원본/외부 이력을 각각의 후보가 처리하게 한다. W에는 120초 준비 창, X에는 공통 변경/교차 script를 적용한다. 시험용 의미/파생 자료를 정답으로 선주입하지 않는다.
5. **쌍 실행:** 같은 사례/채널/profile/반복의 A/B를 가까운 시간에 연속 실행한다. 순서는 seed `20261010`으로 섞고 각 입력 조건의 5쌍에서는 A 선행/B 선행을 3/2 또는 2/3으로 배분한다. 같은 provider seed가 지원되면 대응시키되 동일 모델 응답을 강제하지 않는다.
6. **후속 사건/답변 제공:** 후보의 유효 질문에 정해진 의미의 사용자 답변을 준다. 허용하지 않은 임의 추가 정보는 주지 않는다. 계획된 확인은 필요한 정보가 모두 채워질 때까지, 후보가 추가한 불필요한 확인은 최대 2회 답변 기회까지 제공하고 그 수고/시간/비용도 남긴다. 미지원 관계를 다른 목표로 바꾸는 답변은 제공하지 않는다.
7. **관찰:** 마지막 원천 입력/필수 외부 사실 또는 제공한 사용자 답변부터 각 자동 처리 구간을 최대 60초 관찰한다. 준비/대기 중에도 금지 효과를 기록한다. 필수 후속 사건은 script의 60초 안에서 발생시키고, 마지막 처리 후 5초간 늦은 반환/중복/옛 음성의 재활성화를 확인한다. 처리 episode 총 상한은 10분이며 외부 Agent의 실제 장기 업무가 끝날 때까지 기다리는 테스트가 아니다.
8. **판정/보고:** C1~C6의 실제값/evidence/0·1, 세부 오류, 위반, 모델 사용량, 실제 완료/전달 시각을 저장한다. 같은 자료에서 §9.7의 전체/분해/완전 정답과 쌍 차이를 계산한다.

60초/10분은 미완료를 무한 대기로 숨기지 않기 위한 정확성 시험의 관찰 상한이다. 빠른 응답 목표나 정상적인 제품 응답시간 SLA를 이 숫자로 정의하지 않는다. 시간/비용/메모리 raw trace는 함께 수집할 수 있지만 그 QA의 대표 지표/목표는 이후 별도로 확정한다.

입력 onset→hold 수락→전송 시작의 경합에서는 **실제 순서**를 판정한다. 먼저 시작된 외부 효과는 확인/정정/취소의 대상으로 남기고, 이미 발생한 효과를 없었다고 표시하면 실패다. hold/권한 철회가 먼저 수락됐는데 이후 금지된 전송을 한 경우는 위반이다. 원천 사건과 software 인식 경계를 구별하는 원칙은 [event-boundary-contract](../../11-measurement/event-boundary-contract.md)를 따른다.

범위가 명확한 필수 사실을 자동 판정하고 자연어/audio는 목표/대상/조건/상태의 같은 사실 rubric으로 두 평가자가 독립 판정한다. 표현 차이는 허용하고 사실 추가/누락/모순은 허용하지 않는다. 불일치는 후보 이름을 가린 evidence와 원본으로 조정해 이유를 남긴다. 오답인 후보 출력을 정답으로 삼는 model judge를 단독 최종 판정자로 사용하지 않는다.

후보 누락/timeout이면 증명된 항목만 1로 남기고 나머지는 0이다. 예를 들어 의미는 맞았지만 Agent 인계/실제 전달이 없으면 C5/C6는 0이다. 이미 확인한 C1~C4를 무조건 모두 0으로 덮지는 않는다. 단, 후보 전체가 실패하여 근거가 없으면 여섯 항목 모두 0이다. 시험 수집기 결함이나 계획하지 않은 공통 provider 장애로 판정 자체가 불가능하면 A/B 쌍을 INVALID로 보존하고 복구 후 같은 쌍을 재실행한다. 후보의 잘못된 호출/예산 소진/필수 trace 미생성은 INVALID가 아니다. 원래 540개 유효 실행이 채워질 때까지 실패 사례를 유지하며 INVALID와 재실행도 공개한다.

### 9.7 측정식과 보고 항목

```text
y(i,c) ∈ {0,1}  # 실행 i의 채점 항목 c, c=1..6
요청 처리 정확성(%) = 100 × Σ_i Σ_c y(i,c) / 3,240
완전 정답 처리율(%) = 100 × count_i[모든 c에서 y(i,c)=1] / 540
상황군별 정답률(%) = 100 × 해당 상황군의 정답 항목 수 / 540
C 유형별 정답률(%) = 100 × 해당 C 유형의 정답 항목 수 / 540
A/B 차이(pp) = B의 요청 처리 정확성 − A의 요청 처리 정확성
```

전체 분자/분모와 함께 6개 상황군, 6개 C 유형, Text/Voice, N/W/X, 18개 사례 및 5개 반복의 분해 결과를 공개한다. 같은 항목에서 `둘 다 정답`, `A만 정답`, `B만 정답`, `둘 다 오답`을 기록하고 오답 원인 및 모든 위반 trace를 연결한다. 모델 전사/조회/생산/결합/채택/전송/게시/실제 전달 중 오류 발생 경로는 진단이며 점수를 추가하지 않는다.

작은 차이를 반복 수만으로 확실한 차이처럼 보이지 않게 한다. 불확실성은 **같은 기본 사례의 채널/profile/반복 전체를 하나의 묶음**으로 A/B 함께 재표집한다. S1~S6 각각에서 기본 사례 3개를 복원 추출해 균형을 유지하는 paired block bootstrap 10,000회, seed `20261010`, 차이의 2.5/97.5 percentile을 보고한다. 18개 사례 묶음만 있으므로 작은 차이의 검정력은 제한적이며 제품 모집단의 정확률 신뢰구간이라고 해석하지 않는다. 이 절의 구체적 묶음/횟수는 작성자 설계다. 의존된 음성 자료를 개별 독립 표본으로 재표집하지 않는 원칙은 [Liu와 Peng의 blockwise bootstrap 연구](https://arxiv.org/abs/1912.09508v2)를 참고했다.

### 9.8 목표값과 선택에 쓸 규칙

| 기준 | v1 목표 | 고정 분모에서 필요한 수 | 이유 |
| --- | --- | --- | --- |
| 대표 요청 처리 정확성 | **98% 이상** | 3,240개 중 3,176개 이상 정답, 오답 최대 64개 | 항목 오류 예산을 2% 이내로 제한 |
| 완전 정답 처리율 | **95% 이상** | 540회 중 513회 이상 여섯 항목 모두 정답 | 여러 칸의 높은 부분 점수로 요청 단위 실패를 숨기지 않음 |
| 각 S 상황군 정답률 | **각각 95% 이상** | 각 540개 중 513개 이상 정답 | 쉬운 정상 사례로 특정 중요한 상황의 실패를 희석하지 않음 |
| 각 C 조건 유형 정답률 | **각각 95% 이상** | 각 540개 중 513개 이상 정답 | 실제 적용/전달의 약점을 의미 항목 점수로 상쇄하지 않음 |
| 필수 위반 | **0건** | 전체 실행/관찰 trace에서 위반 없음 | 오업무/중복 외부 효과, 잘못된 질문/승인 적용, 무허용 접근/제공을 평균에 희석하지 않음 |

이 숫자는 제품 빈도나 실측에서 추정한 값, 산업 표준 또는 모델이 이미 달성한 성능이 아니다. 이번 과제의 **평가 목표**로 정한 설계 수치다. 두 후보 모두 미달하면 미달을 보고하고 원인을 보완한다. 목표를 결과 뒤에 낮추거나 실패 사례를 빼지 않는다. 필수 위반 0건은 이 시험에서의 관찰 결과이며 제품 전체에서 오류 확률이 0이라는 증명이 아니다.

필수 위반은 잘못된 Task/Execution의 외부 명령/제어, 같은 명령의 중복 외부 효과, 철회/다른 질문의 승인 사용, 허용하지 않은 정보 접근/제공, 다른 업무로 질문 답변/결과 적용이다. 일반 표현/설명 오류와 구별해 독립 원장을 남긴다. 위반 후보도 모든 적용 QA의 값과 손익을 측정/보고하며 최종 선택 적격성만 제한한다.

같은 DP의 A/B 차이가 **1 percentage point 이상이고 위 paired 95% 구간이 0을 포함하지 않을 때** 정확성의 의미 있는 우위로 인정한다. 1pp는 2% 항목 오류 예산의 절반에 해당하는 선택 차이로 정했으며 이 분모에서 순 정답 차이 최소 33개다. 필수 위반/목표 충족 여부와 함께 해석한다. 미달 후보가 더 높은 정확률을 보였다는 사실도 그대로 남긴다.

차이가 1pp 미만이면 선택상 작은 차이로 보고하고, 구간이 0을 포함하면 우열 미입증으로 보고한다. 미입증을 통계적 동등성으로 바꾸지 않는다. 정확성만으로 승자를 만들지 않고 합의할 다른 QA 우선순위와 손익을 사용한다. 현재 전체 QA 우선순위는 새 다섯 묶음에서 아직 정하지 않았으므로 이번 정확성 설계만으로 최종 A/B를 선택하지 않는다. 이 규칙은 각 DP의 쌍 비교용이며 네 비교 전체의 동시 95% 보장을 주장하지 않는다.

### 9.9 재개와 실행 준비의 경계

**이번에 닫은 것:** 요청 처리 정확성 정의, S1~S6, 18개 기본 사례, C1~C6 묶음별 이진 채점, 채널/profile/반복과 분모, A/B 단일 변수 구성, 공통 환경/판정/관찰 절차, 목표/위반/차이 인정 기준.

**실행 때 해야 할 것:** 이 설계대로 원본/음성/화면/사건 fixture를 제작하고 108개 입력 조건 조합의 정답값을 채운다. 후보/harness/관측 adapter와 42B의 문서화된 독립 접수/hold 계약을 실제 구현하며, 모델/장비/설정과 각 파일 hash를 manifest에 넣고 검사기를 검수한 뒤 실행한다. 이는 확정 정의의 구현/검증이며 상황/분모를 다시 선택하는 작업이 아니다. 이 요청에서는 후보나 모델을 실행하지 않았다.

추후 정말 요구 범위를 바꿔야 할 때만 이유를 기록한 v2로 개정한다. v1의 실패와 결과는 원래 계약으로 보존한다. 기존 QA-19/QA-09/QA-29/QA-39, 참조 Architecture, ADR와 과거 결과를 이번 새 지표로 소급 변경하지 않는다. 다음 QA 정의 작업은 응답속도이며, 정확성 유형 수와 분모 논의를 처음부터 반복하지 않는다.
