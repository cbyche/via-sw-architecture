# 문제 5. 적절한 Downstream Agent를 선택하고 전환하는 구조

## 1. VIA에서 풀어야 하는 문제

사용자는 VIA에서 ‘이 결과로 발표자료 만들어 줘’라고 말한다. VIA는 현재 자료와 수정 조건을 이해하고, 사용자가 연결한 Agent 중 이를 수행할 수 있는 대상을 정해야 한다. 이후 Agent가 추가되거나 성능 / 접근 권한이 달라져도 Conversation과 Task는 이어져야 한다. 이는 대표 UC의 업무 위임, 후속 수정, 외부 Agent 질문 재연결과 취소에 연결된다.

중요한 판단은 둘이다.

1. **지금 맡길 수 있는가:** 기능, 자료 접근, 출력 형식, 사용자 지정, 현재 연결과 실행 상태가 조건을 충족하는가.
2. **맡길 수 있는 후보 중 무엇이 적합한가:** 이번 업무와 사용자가 정한 품질 / 시간 / 비용 목적에 대해 어떤 근거가 있는가.

최신 모델 이름이나 Agent의 자기소개만으로 두 번째 판단을 검증할 수 없다. ‘그때그때 최고 성능 Agent로 교체’라는 제품 가치는 교체 가능성과 업무별 선택 근거를 갖추는 목표다. 매 요청에서 실제 최상의 결과를 보장하는 기능으로 단정하면 안 된다.

## 2. 구조와 무관한 완료 조건

- Task 식별자와 사용자 조건은 VIA에 남는다. Agent의 native session / Task ID는 연결 정보다. 다른 Agent로 같은 내부 실행 상태를 이식할 수 있다고 가정하지 않는다.
- 최초 선택 전에 후보의 필수 기능과 권한을 확인한다. 선택 제안 뒤에도 요청 / registry revision을 확인하여 오래된 제안의 실행을 막는다.
- 사용자의 명시적 Agent 지정과 허용 범위를 반영한다. 적합 후보가 없으면 보류 / 질문 / 가능한 범위 제안 중 적합한 처리를 한다. 등록된 첫 Agent를 무조건 실행하지 않는다.
- 외부 Agent는 결과와 확인 가능한 진행 사실을 제공한다. VIA가 업무 내부 tool 계획을 작성하여 orchestrator가 되는 것은 이 문제의 범위가 아니다.
- 전환은 새 execution attempt와 인계를 생성한다. 이전 실행이 종료되었는지 불명인 외부 Action은 새 Agent에서 중복 시작하지 않는다. 취소 요청 접수와 실제 종료를 구별한다.
- 카드 / 상태 조회, 캐시와 후보 축소는 양안 모두 사용할 수 있다. 허용된 후보가 하나이고 선택 여지가 없는 입력은 양안 모두 모델 선택 단계를 생략할 수 있다.
- 문제 4의 인계 구조와 독립적으로 조합한다. 후보를 고르는 능력과 필요한 업무 자료를 빠짐없이 전달하는 능력을 같은 점수로 섞지 않는다.

## 3. 구현 조사에서 남긴 두 가지 구조

| 구조 | 실제 근거 | VIA에서 바뀌는 것 |
| --- | --- | --- |
| A. 요청 판단에 선택을 결합 | Deep Agents의 task tool, OpenHands의 agent type catalog, CrewAI의 card 주입과 A2A 위임 응답 | 현재 요청 판단의 문맥과 모델 실행에서 Agent 선택을 함께 제안 |
| B. 요청 계약을 받아 별도 선택 판단 | AutoGen SelectorGroupChat의 별도 selector context, Magentic-One의 역할 / 진행 정보와 next-speaker 판단 | 요청과 별도로 후보 선택 실행과 상태를 유지. 선택 결과를 요청 revision에 다시 결합 |

둘 다 모델을 사용하며, 공통 code 검증도 사용한다. 이전 DP41의 ‘모델 대 code’ 질문을 재사용하지 않는다. 차이는 후보 정보가 **어느 의미 실행에 들어가고, 무엇을 다시 판단해야 하며, 선택 상태가 어떤 수명으로 남는가**다. 참고 구현의 domain plan은 VIA로 옮기지 않는다.

### 3.1 A. 요청 판단에 선택을 결합

1. 요청 해석이 최근 대화 / 화면 / 업무 근거와 허용 후보 요약을 읽는다. 필요할 때 상세 card와 확인 가능한 과거 결과 근거를 조회한다.
2. 같은 판단에서 대상, 업무 조건, 직접 응답 / 위임, Agent 후보와 선택 근거를 함께 제안한다.
3. 공통 채택 경계가 요청 revision, 필수 기능, 사용자 지정과 외부 실행 상태를 확인한다.
4. 인계 계약을 구성하여 Agent에 전달하고 receipt / Task 상태를 연결한다. 후속 정정이나 후보 변경은 영향받은 해석만 부분 갱신한다.

**상태:** 요청 판단 문맥과 선택 제안은 해당 요청 revision에 속한다. registry와 관측된 Agent 성과 기록은 공유 저장소에서 읽는다. 성과 기록 자체가 A에서 없거나 불가능하다고 가정하지 않는다.

**강한 보완:** 큰 catalog를 모두 prompt에 넣을 필요가 없다. 결정적인 필수 조건 필터, 설명 검색, 캐시, 선택 부분 재판단을 허용한다. 후보 변경 때문에 화면 지칭까지 전부 다시 읽도록 강제하지 않는다.

### 3.2 B. 별도의 선택 판단과 수명

1. 요청 해석이 업무 목적, 대상 자료, 완료 조건, 필수 기능, 사용자 선호와 불확실성으로 이루어진 요청 계약을 만든다. 이는 domain 실행 계획이 아니다.
2. 선택 판단은 해당 계약의 revision을 입력으로 받고 registry의 적격 후보, 업무별 품질 근거와 현재 연결 정보를 읽는다.
3. 선택 후보, 사용한 registry / 성과 자료 revision, 보류 이유를 반환한다. 요청 정보가 부족하면 보완을 요구하고 필요한 원본을 제한적으로 읽을 수 있다.
4. 공통 채택 경계가 현재 요청과 선택의 revision을 연결하고 인계 / 실행을 허가한다. registry 변경만으로 선택이 무효가 된 경우 선택 실행만 갱신할 수 있다.

**상태:** 선택 작업은 요청 본문과 분리된 실행 / context를 가진다. 사용자에게 전달할 진행 상황과 요청 조건은 VIA의 대화 상태에 남고, 후보 비교 근거와 갱신 상태는 선택 실행에 남는다. 새로운 후보, 접속 실패와 작업별 재선택을 다루는 책임도 명시된다.

**강한 보완:** 항상 full-history 복사나 두 개의 큰 모델 호출을 요구하지 않는다. 단일 후보 fast path, 최소 계약, 후보 캐시와 기존 선택의 유효성 검사를 허용한다. 원본 재조회가 가능하므로 축약된 계약의 누락을 복구할 수 있다. 그 재조회와 협의 비용은 B에 계산한다.

## 5. 선택과 실제 전환의 공통 상태 계약

| 상태 | 유지하는 사실 | 다음 처리 |
| --- | --- | --- |
| 선택 제안 | 요청 revision, 후보 집합 revision, 선택 근거와 불확실성 | 현재 적격성 / 사용자 조건 검사 |
| 위임 준비 | 허용 인계 자료, 대상 Agent, 새 attempt와 이전 attempt 연결 | 실행 상태 확인 후 전달 |
| 전달 / 접수 불명 | 시도한 명령과 알려진 receipt 범위 | 지원하는 상태 조회 / 동일 명령 확인 사용. 새 Agent로 임의 재실행 금지 |
| 기존 실행 종료 확인 | 관측된 완료 / 중지 사실과 실제 결과 revision | 문제 4 인계 구조로 다음 attempt 구성 |
| 늦은 이전 결과 | 이전 attempt와 요청 revision에 연결된 원본 | 이력 보존과 현재 결과 채택을 구별. 새 조건을 덮어쓰지 않음 |

이 상태 계약은 A/B 모두 필요하다. Agent Gateway의 edge 정규화와 Task 상태 소유 원칙을 유지한다. capability가 제공되지 않는 외부 Agent에 가상의 cancel / export / resume API를 붙이지 않는다.

## 7. 세 번째 대안으로 만들지 않은 것

- **catalog 축소와 최종 적격성 검사:** OpenClaw binding / allow list와 SelectorGroupChat의 prompt 후보 축소는 공통 보완의 근거다. SelectorGroupChat의 모델 반환 검사는 전체 participant 기준이므로 축소 후보 안의 선택을 강제하는 admission으로 인용하지 않는다. VIA의 결정적인 최종 적격성 검사는 별도 code 계약이다. 이 보완은 요청 적합성을 판단하는 전체 구조와 같은 수준의 경쟁안이 아니다.
- **worker의 다음 Agent 제안:** AutoGen Swarm에서 실제 구현된다. VIA에서는 현재 Agent가 제안한 target을 A 또는 B의 입력으로 받고 VIA가 허가할 수 있다. 이 정책만으로 새로운 선택 architecture를 만들 필요는 없다.
- **전 후보 시험 실행 / 입찰:** 정적인 card 조회와 다른 실행이다. 이번 확인 범위에서 이 기능을 다섯 harness의 공통 구현으로 제시할 근거를 확보하지 못했다. 별도 프로토콜과 실행 권한 / 비용 설계가 필요한 추가 탐색 후보다.
- **별도 selector를 함수로만 추출:** 호출과 상태 수명이 A와 같고 추가 선택 문맥도 없다면 B가 아니다. code 배치 변경으로 대안을 세지 않는다.

## 8. 대안 반증과 DP 권고

**A에 대한 반증:** candidate 검색 / cache / 부분 재판단을 충분히 적용했는데도 후보 변화가 지칭과 조건 해석을 반복적으로 흔들고, B는 같은 근거와 모델 조건에서 오류를 줄이는지 확인해야 한다. 복잡한 전체 history만 A에 강제한 결과는 반증이 아니다.

**B에 대한 반증:** A에서 선택 부분만 다시 판단하는 작은 보완으로 같은 정확도와 갱신 효과를 얻는다면 별도 실행과 상태의 필요성이 약해진다. 계약 축약과 보완 왕복이 더 큰 비용 / 오류를 낼 수도 있다. 별도 모듈이 있다는 이유로 높은 품질을 예상하지 않는다.

**권고:** VIA에 필수적인 문제이고 신규 QA의 필요성도 높다. 그러나 지금 두 구조만으로 주요 DP 자격을 확정하기에는 약하다. 실제 reference 기반의 비교안은 확보했으나, 강한 A의 선택적 조회 / 부분 재판단을 넘는 B의 정상 사용 이득과 3개 이상의 핵심 QA 차이가 아직 부족하다. 문제 4와 억지로 합쳐 그 빈칸을 채우지 않는다. 선택 / 인계는 서로 독립적으로 조합할 수 있다.

다음 검토에서 Agent 수 / 변경 빈도 / 연결 가능한 실제 capability와 사용자 선택 목적을 좁혀 구조적 차이가 남는지 판단한다. 남지 않으면 중요한 **선택 계약과 상세 설계**로 유지할 수 있다. 중요 기능이라는 사실과 강한 DP가 된다는 사실은 구별한다. 구현, 실제 Agent 연결, 선택 oracle 실험과 우열 측정은 수행하지 않았다.
