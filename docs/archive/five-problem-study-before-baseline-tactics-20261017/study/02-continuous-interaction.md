# 문제 2. 겹치는 입력을 어느 해석 실행에 반영할 것인가

2026-10-16 / 공식 구현 조사와 설계 사고 실험 / 대안과 품질 차이 미선정, 미측정

## 1. 결론과 VIA에서 중요한 이유

**주요 DP로 발전시킬 비교는 ‘하나의 대화 해석 실행을 계속 갱신할 것인가, 요청별 해석 실행을 분리하고 대화에서 다시 채택할 것인가’다.** 별도 질문만 제한적으로 처리하는 혼합안도 함께 남긴다. `steer`, `interrupt`, `followup` 설정 각각을 별도 Architecture로 세지는 않는다.

VIA가 긴 자료를 읽는 중에도 사용자는 짧은 질문을 하고 조건을 고친다. 다른 Agent는 자기 업무에 관한 질문과 결과를 보낸다. 사용자는 각각 다른 창으로 이동하거나 현재 처리가 끝날 때까지 기다리지 않고 VIA와 계속 대화하려고 한다. 이때 새로운 입력을 빨리 받는 것과 그 뜻을 빨리 반영하는 것은 다르다. 새 발화를 기록했더라도 현재 모델 호출이나 도구 묶음이 끝나야 해석할 수 있는 구조가 있다. 다른 실행에서 바로 해석하면 대기는 줄일 수 있지만, 이전 실행이 알고 있던 대상과 조건을 새 실행에 전달하고 서로 다른 revision의 결과를 다시 연결해야 한다.

이 문제는 [UC-01, 06, 09~15, 18](../../../../05-representative-use-cases.md)에 관련된다. [공동 조사 기준](./00-research-contract.md)의 QA01, QA03, QA05와 QA06에 직접적인 손익 경로가 있다. QA02와 QA04의 차이는 조건부이며 강제하지 않는다.

| 남긴 대안 | 새 입력이 들어가는 곳 | 정상 사용에서 선택할 이유 | 핵심 비용 |
| --- | --- | --- | --- |
| **A. 대화 해석 실행에 합류** | 다음 모델 판단 경계에서 현재 대화 실행의 문맥에 추가 | 같은 자료에 대한 연속 정정에서 이미 읽은 근거와 잠정 판단을 바로 활용 | 실행 중 호출의 경계까지 기다릴 수 있고 여러 요청의 임시 상태가 같은 문맥에 들어감 |
| **B. 요청별 해석 실행과 대화 채택 분리** | 공통 대화 해석에서 관계를 판단한 뒤 해당 요청 실행을 갱신하거나 별도 실행 생성 | 긴 자료 해석을 유지하면서 독립 질문이나 다른 업무의 질문을 처리 | 관계 판단, 실행별 문맥과 의존 추적, 결과 재연결 및 경합 비용 |
| **C. A에 제한된 별도 질문 경로 추가** | 짧고 독립적인 질문은 읽기 전용 snapshot 문맥, 나머지는 A | 도구 없는 옆 질문 때문에 원래 자료 해석을 멈추지 않음 | snapshot 준비와 별도 모델 호출. 자료 조회나 정정이 필요하면 A로 돌아가 대기 발생 |

C는 실용적인 혼합 후보이며 A에서의 저비용 보완이다. 따라서 **A와 C를 서로 독립적인 주요 DP로 세지 않는다. 최종 비교에서는 C까지 허용한 강한 A 계열을 B와 비교해야 한다.**

## 2. 같은 일을 수행하는 조건

### 2.1 공통 책임과 입력

모든 안에서 Interaction Manager는 입력과 화면 관측을 계속 수신하며 발화 시작에 음성을 즉시 멈춘다. 이 동작은 현재 의미 호출, Agent 취소 확인과 독립적이다. Request Controller는 입력 revision, 채택한 요청 관계와 질문 focus를 소유한다. Request Interpreter는 자연어의 의미와 새 요청, 정정, 답변, 취소 관계를 제안한다. Task Manager와 Agent Gateway는 확인된 외부 실행 사실을 보존한다. Response Manager는 게시 허용과 실제 전달 기록을 연결한다. Model Access의 동일한 cloud 모델과 전체 호출 예산을 사용한다.

대안에 들어오는 공통 자료는 다음과 같다. 아래 필드는 설계 설명용이며 신규 확정 API가 아니다.

- `InputRecord`: 원문, input ID와 revision, 발화와 화면 근거 참조. 정답 Task ID는 사전 부여하지 않는다.
- `ConversationSnapshot`: 실제 제시한 질문과 응답 범위, 최근 채택 조건, 미해결 요청의 식별자와 상태 revision. 요약에서 부족한 원본은 추가로 읽을 수 있다.
- `AgentEvent`: 원래 Task와 Execution 식별 정보, 확인된 사건 종류와 외부 상태. 자유문 내용의 의미는 필요할 때 해석한다.
- `InterpretationOutcome`: 사용한 입력과 근거 revision, 제안하는 대상과 관계, 남은 불확실성, 응답 또는 다음 처리의 제안.

대안의 차이는 Request Interpreter의 **임시 해석 문맥과 실행 수명**, Request Controller가 **새 입력과 완료를 연결하는 경로**다. 별도 process나 다른 모델을 사용해야 성립하는 비교가 아니다. Task마다 항상 별도 의미 소유자를 만드는 이전 33의 제외안도 아니다. B의 실행은 업무 종류나 앱에 고정되지 않는 요청 단위의 잠정 실행이며, 최종 의미와 Task 상태의 소유권은 공통으로 유지한다.

### 2.2 모두 충족해야 하는 조건

1. 독립 질문은 독립 요청으로 남기고, 이전의 유효한 목표를 취소하지 않는다.
2. 정정은 확인된 범위에 반영한다. ‘표는 T1/T3, 문단은 유지’에서 P2까지 지우지 않는다.
3. 사용자의 짧은 답은 실제로 제시한 질문에 연결한다. 마지막으로 도착한 Agent 질문을 자동 선택하지 않는다.
4. 음성 중단, VIA의 응답 준비 중단, 외부 업무 취소 요청, 외부 종료 확인을 구별한다.
5. 늦은 결과는 원래 실행의 확인 사실로 보존할 수 있으나 현재 수정 조건의 결과로 자동 채택하지 않는다. 의미상 재사용 가능 여부는 새 판단의 대상이다.
6. 완료와 미해결 요청을 보존하고 재접속 뒤 연결한다. 실행 ID가 있다는 이유만으로 crash 복구가 되는 것으로 취급하지 않는다.
7. 쉬운 질문은 불필요한 worker 생성이나 전체 이력 재조회 없이 바로 답할 수 있다. 모든 안에 cache, 병렬 read, 부분 갱신을 허용한다.

## 3. 공식 reference에서 확보한 메커니즘

고정 commit, 읽은 함수와 한계는 [소스 원장](../../../../../references/five-problem-study/continuous-interaction.md)에 있다. 아래 표는 제품 전체의 분류가 아니라 확인한 경로다.

| 구현에서 확인한 것 | VIA에 제공하는 선택 | 그대로 가져오지 않는 부분 |
| --- | --- | --- |
| OpenClaw의 같은 run steering, tool batch 뒤 입력 drain, 실패 시 followup | A의 현재 문맥 재사용과 협력적인 입력 반영 경계 | running tool의 즉시 종료, VIA의 부분 정정 의미와 실제 전달 정확성을 보장하지 않음 |
| OpenClaw의 subagent 완료 lease와 session writer 검사 | 완료 재연결, 이전 writer의 쓰기 방지 | writer가 현재라고 해서 내용이 정정 후에도 의미상 유효한 것은 아님 |
| OpenHands SDK의 메시지 기록과 실행 분리, I/O 중 state lock 해제 | 수신 지속과 의미 처리 지속을 구별 | background coroutine 자체가 독립 요청 처리나 내구 실행을 뜻하지 않음 |
| OpenHands Agent Server의 ACP prompt supersede와 재실행, run permit 보존 | 영향을 받은 실행의 새 입력 반영과 재시작 경로 | 이 ACP 경로를 모든 Agent와 모든 입력의 공통 동작으로 확대하지 않음 |
| Deep Agents의 별도 thread/run, update와 cancel 및 확인 도구 | B의 독립 실행 식별과 후속 수정 | 공개 구현의 child 승인 창은 VIA의 한 대화 답변 연결을 완성하지 않음 |
| Deep Agents Btw의 도구 없는 별도 질문과 읽기 전용 snapshot | C의 제한된 옆 질문 경로 | 원본에는 main checkpoint write가 없음. VIA는 실제 표시 내용을 공통 Conversation에 남겨야 함 |
| Magentic-One의 응답 후 progress ledger와 한 명의 다음 참여자 지정 | 결과를 모아 다음 의미 판단을 하는 A 계열의 참고 | 여러 참가자와 event가 있다는 이유로 자유로운 동시 사용자 개입을 주장하지 않음 |
| CrewAI의 conversational turn별 실행 초기화와 이력 보존, async Task의 join | 지속 대화 기록과 일시 실행 추적을 분리하는 근거 | 이 확인 범위에서 같은 Flow 인스턴스의 동시 사용자 turn 제어를 입증하지 못함 |

**탐색에서 별도 주안으로 남기지 않은 것:** 모든 입력을 현재 run 완료 뒤 처리하는 순수 followup은 기능적으로 가능하지만 긴 VIA 해석 중 독립 질문의 대기를 줄일 정상 이익이 없다. 호환 입력의 batching은 burst 비용을 줄일 공통 보완이다. 모든 새 입력마다 기존 실행을 취소하는 latest-only 방식은 독립 질문과 다른 업무의 유효 목표를 잃기 쉬우며, 보존과 재스케줄을 추가하면 아래 실행 변경 정책으로 수렴한다. 중앙 event bus와 Stage chain의 차이는 [기존 DP-44](../../04-44-continuous-interaction.md)의 별도 축이다.

## 4. 세 대안의 실제 처리와 상태

### 4.1 A: 하나의 대화 해석 실행에 합류

1. Request Controller가 새 입력을 기록하고, 대화의 현재 해석 실행 mailbox에 원문과 revision을 넣는다. 응답 후보의 미전송 부분은 공통 규칙으로 hold한다.
2. Request Interpreter는 진행 중인 model call이나 read batch가 끝나는 경계에서 pending 입력을 가져온다. 이미 완료한 read 결과와 새 입력을 같은 문맥에서 판단한다.
3. 독립 질문이면 기존 요청의 미해결 조건을 유지하면서 새 답을 만든다. 정정이면 관련 조건과 이후 읽기 계획을 부분 갱신한다. Task와 질문의 관계는 여기에서 제안한다.
4. Request Controller가 현재 revision과 사용 권한을 확인해 관계와 응답을 채택한다. Request Interpreter는 남은 원래 요청으로 돌아가거나 새 입력을 다시 읽는다.
5. Agent 사건은 먼저 Task Manager의 사실로 기록한다. 사용자에게 전달할 내용 해석이 필요하면 같은 대화 실행에 근거로 들어간다. 구조가 정해진 단순 상태 표시는 공통 코드 경로를 허용하며 매번 모델을 강제하지 않는다.

**상태:** Request Interpreter에 대화별 활성 문맥 하나, 요청별 미해결 조건과 read handle이 남는다. 하나의 문맥에 여러 요청의 잠정 상태가 있을 수 있다. Context Manager의 원본과 cache, Request Controller의 채택 사실은 별도다. 문맥을 덜어내더라도 유효 목표와 필요한 의존 참조를 원본에서 다시 얻을 수 있어야 한다.

**강한 A:** bounded read를 동시에 실행할 수 있고, 기다리는 read handle을 기록한 뒤 먼저 답할 수 있는 경계를 만들 수 있다. model streaming을 취소하고 동일 문맥에서 다시 판단하는 fallback도 허용한다. 따라서 ‘A는 모든 외부 업무가 끝날 때까지 대화를 잠근다’는 비교는 성립하지 않는다. 남는 제한은 **같은 대화의 긴 의미 판단 자체가 하나의 실행 문맥을 차지할 때**, 다음 입력이 그 판단의 경계를 기다리거나 기존 호출을 중단해야 한다는 점이다.

**유리한 정상 장면:** 동일한 문서와 조건을 계속 수정하며, 해석 경계가 짧고 옆 질문이 적다. 이미 읽은 원문과 잠정 관계를 별도 실행용 문맥으로 다시 정리하는 비용이 작다. **불리한 장면:** 취소하기 아까운 긴 의미 호출 중 독립적인 다른 자료 질문이 계속 들어온다.

### 4.2 B: 요청별 해석 실행과 대화 채택 분리

1. Request Controller가 새 입력을 기록한다. Request Interpreter의 공통 대화 해석은 원문, 최근 실제 전달과 활성 요청 snapshot으로 관계를 먼저 판단한다. 입력 전에 올바른 Task를 알고 있다고 전제하지 않는다.
2. 짧은 질문은 이 호출에서 답까지 제안한다. 더 긴 bounded read와 의미 판단이 필요한 요청은 `RequestContinuation`을 만든다. 이 기록은 요청 revision, 필요한 원본, 잠정 판단, 미해결 조건, 모델 호출과 read handle을 묶는다.
3. 각 요청의 continuation은 자기 문맥에서 실행한다. 공통 대화 해석은 그 완료를 기다리며 점유되지 않고 다음 입력을 처리할 수 있다. 실행 수와 전체 모델 동시 호출 수는 제한한다.
4. 정정은 해당 continuation에 원문과 채택된 변경 관계를 보낸다. 해당 실행은 다음 경계에서 steer를 받거나 새 revision으로 재개한다. 다른 요청의 continuation은 유지한다.
5. 완료는 현재 입력과 조건을 바로 덮어쓰지 않고 Request Controller로 돌아온다. 사용 근거의 revision과 변경 의존을 확인하고, 필요하면 Request Interpreter가 최신 대화와 결합해 재판단한다. 새 의미 판단이 필요 없는 현재 결과는 코드 확인 뒤 채택할 수 있다.

첫 공통 해석에서 관계를 확정하지 못하면 정답 Task를 추정해 worker를 보내지 않는다. 입력 ID와 복수 관련 후보를 가진 미해결 continuation에서 필요한 원본을 읽고, 관계 제안이 돌아온 뒤 채택한다. 첫 호출의 역할 분리가 ‘모든 Task 연관성이 먼저 해결된다’는 요구가 되지 않도록 한다.

**상태:** Request Controller는 입력과 continuation의 대응 및 최신 채택 revision을 보유한다. Request Interpreter는 실행별 문맥과 잠정 의미를 보유한다. 각 실행의 Context와 read 결과는 불변 참조와 공유 cache로 중복 복사를 줄일 수 있다. 클라우드 모델의 KV를 로컬 RAM으로 계산하지 않는다. 로컬에는 snapshot, 완료 대기, 문자열과 이미지 buffer, 작업 handle의 실제 메모리만 센다.

**강한 B:** 모든 입력을 추가 router 모델 호출과 worker 호출 두 번으로 강제하지 않는다. 쉬운 답은 공통 해석에서 완료하고, 긴 경우만 이어서 실행한다. 정정 후 처음부터 다시 읽지 않고 의존이 변한 부분만 갱신할 수 있다. 반대로 원래 실행의 잠정 추론 전체를 완벽히 가져오는 무료 snapshot을 가정하지 않는다. 부족한 원본, 질문 focus 또는 조건을 읽고 연결하는 비용은 남는다.

**유리한 정상 장면:** 길고 서로 독립적인 VIA 자료 해석과 짧은 대화가 반복적으로 교차한다. **불리한 장면:** 한 대상에 대한 촘촘한 정정이 많아 공통 해석과 요청 문맥 사이에 변경과 재판단을 자주 왕복한다. 한 개의 모델 호출만 허용되거나 provider가 실행 중 호출을 장시간 점유하면 독립 문맥만으로 빠른 반응을 보장하지 못한다.

### 4.3 C: A에 제한된 별도 질문 경로 추가

1. A의 해석 실행을 유지한다. 새 입력은 우선 원문과 작은 읽기 전용 대화 snapshot을 받는 별도 질문 경로에 들어갈 수 있다.
2. 이 경로는 이미 확보된 근거로 답할 수 있는 독립 질문만 응답 후보로 반환한다. 실행 중 업무를 수정하거나 취소하는 명령, 외부 Action, 새로운 자료 조회를 실행할 권한은 없다.
3. 관계가 불명확하거나 원본 조회와 기존 조건 변경이 필요하면 해당 사실과 원문을 A의 해석 실행에 넘긴다. 실패한 side call의 비용과 추가 대기를 보존한다.
4. 응답은 공통 채택과 게시 검사를 거친다. 실제 표시한 side answer와 지칭 anchor는 VIA Conversation에 남겨 이후 ‘방금 답’이 누락되지 않게 한다.

Deep Agents Btw는 명시적 side question 경로다. **자연어 입력을 자동으로 이 경로에 보낼 수 있는지와 독립성 판단의 정확도는 VIA가 추가로 해결할 문제**다. 첫 side call이 잘못 독립 질문으로 판단한 답을 현재 조건 검사만으로 의미적으로 고칠 수 있다고 전제하지 않는다.

**유리한 정상 장면:** ‘그 자료는 계속 읽고, TCP와 UDP 차이만 잠깐 알려줘’처럼 기존 문맥만으로 답할 옆 질문이 많다. **불리한 장면:** 옆 질문처럼 보이지만 다른 문서 조회나 정정이 필요해 A로 돌아가는 비율이 높다. C에서 도구와 지속 실행 권한을 늘리면 B에 가까워지므로 그 경계의 비용을 공개한다.

### 4.4 실행 변경 방식은 별도 선택 축이다

| 정책 | 실제 효과와 비용 | 적용 관계 |
| --- | --- | --- |
| 다음 경계에 입력 합류 | 완료된 read와 현재 문맥 재사용. 실행 중 model/tool 경계까지 기다릴 수 있음 | A의 기본, B의 해당 continuation에도 가능 |
| 영향 실행을 중단하고 새 revision으로 재개 | 오래 남은 호출의 결과를 기다리지 않을 수 있음. 취소 handshake, 폐기 토큰과 재구성 비용 | OpenHands ACP와 Deep Agents update의 근거. A/B 모두 가능 |
| 현재 실행 이후 followup | 현재 실행을 보존. 새 요청의 첫 응답이 지연될 수 있음 | 호환되지 않는 권한과 지원하지 않는 steer의 fallback |
| 독립 실행 또는 제한 side answer | 원래 실행의 진행을 유지하며 새 요청을 해석. 추가 문맥과 합류 비용 | B/C의 핵심 |

OpenClaw의 모든 queue mode를 각각 DP 대안으로 늘리면 이 조합 관계가 사라진다. 또한 VIA가 model call을 취소했다고 외부 Agent 업무까지 멈춘 것으로 취급하지 않는다.

공통 EX 목록의 구체화이며 새 측정 모집단이나 수치 freeze가 아니다. 각 장면에는 이미 요청한 목표, 실제 제공한 자료, 실행 중인 호출의 종류와 새 입력을 고정해야 한다. 아래 완료 조건은 대안마다 바꾸지 않는다.

| 장면과 같은 완료 조건 | A | B | C와 비교에서 확인할 점 |

**부하 변형:** EX05와 EX06에 동시 호출 여유가 있는 경우, 모든 slot이 이미 사용 중인 경우, 선행 호출이 취소에 응답하지 않는 경우를 각각 적용한다. B에만 추가 worker와 provider capacity를 주면 비교가 아니다. **반복 변형:** D2 재질문은 세 안 모두 cache와 기존 결과 재사용을 허용한다. 최신 요청이 아닌 결과의 반복은 정답 revision을 확인한다.

### 5.1 EX05b의 인과 경로

공통 시작 상태는 D1의 긴 의미 판단이 실행 중이고 새 D2 질문은 원본 read가 필요하다는 것이다. D1의 외부 업무 수행 시간이 아니라 **VIA가 수행하는 bounded 자료 이해**를 고정한다.

```text
A: D2 입력 저장
   → D1 의미 호출의 경계 또는 취소 정리
   → 같은 문맥에서 D2 관계와 필요 근거 판단
   → D2 원본 read와 답 준비 → 현재성 채택 → 실제 텍스트 표시
   → D1의 남은 유효 처리 재개

B: D2 입력 저장
   → 공통 대화 해석에서 독립 관계와 필요 근거 판단
   → D2 continuation의 read와 답 준비
   → 현재 대화와 조건 확인 → 실제 텍스트 표시
   D1 continuation은 별도 문맥에서 계속되며 동일 자원 예산을 공유

C: D2 입력 저장 → side 판단에서 자료 필요 확인
   → A의 입력 경계로 반환 → A의 D2 경로
```

D2의 구체적인 처리 의도가 자료 상세 읽기 전에 이미 확정돼 표시될 수 있으면 그 시점이 QA01이다. 위 read와 전체 답 준비 시간을 무조건 첫 응답에 넣지 않는다. B의 원래 D1 작업이 빨리 끝나는 것과 D2의 첫 응답이 빨라지는 것도 별개 관측이다.

## 6. 정정, 늦은 완료와 자원 한도의 계약

### 6.1 세 개의 경계를 구별한다

1. **입력 수신과 의미 반영:** 입력이 저장됐다는 사실, 현재 모델이 읽었다는 사실, 수정 관계가 채택됐다는 사실을 따로 남긴다.
2. **실행 취소와 결과 채택:** 취소 요청이 실패하거나 늦어도 옛 revision의 결과는 현재 게시를 통과하지 못한다. 취소된 호출도 실제 usage와 cleanup 시간을 가진다.
3. **Agent 사실과 현재 요청의 결과:** X1 완료 사실은 보존한다. 현재 R2 조건에 맞는 결과인지와 사용자에게 어떻게 설명할지는 별도 판단이다.

의미상 영향이 아직 불명확한 새 발화는 공통 규칙에 따라 관련 미전송 효과를 hold한다. 관계를 해석한 뒤 영향받은 revision만 바꾸고 무관한 결과는 해제한다. 모든 사건마다 대화 전체 epoch를 바꿔 모든 continuation을 재실행하면 B의 독립성 이익을 스스로 없애므로, 사용하는 조건과 실제 전달 근거를 명시적으로 추적해야 한다. 이 추적 비용은 B의 추가 계약이다. A도 부분 재사용을 주장하는 만큼 같은 종류의 근거 의존을 보존해야 한다.

### 6.2 실행 자원과 질문 대기

- Model Access의 총 동시 호출 한도와 provider 조건은 동일하다. B의 foreground 슬롯 예약은 무료 capacity가 아니며 배경 처리의 admission을 늦춘다. A/C도 같은 예약 정책을 사용할 수 있다.
- 독립 continuation, pending 입력과 완료 후보의 수는 제한한다. 포화 시 입력은 영속 보존과 명시적 대기 또는 거절로 처리한다. 사용자 정정과 취소를 overflow 요약만으로 대체하지 않는다.
- B는 사용자 답을 기다리는 continuation이 실행 slot을 계속 점유하지 않도록 상태와 실행을 분리한다. A도 pending 질문을 기록한 뒤 다른 요청을 처리할 수 있다.
- 원본 권한 철회와 질문 만료는 수신 시점과 채택 시점에 확인한다. 별도 질문 snapshot의 생성 시 권한만으로 나중의 사용을 허용하지 않는다.
- 외부 Agent 상태를 모르는 재접속에서 임의 재실행하지 않는다. 질문과 command identity를 대조하고 모르는 상태를 사용자에게 표시한다. 별도 process나 durable workflow engine은 이 비교의 필수 전제가 아니다.

| **QA03 VIA 처리시간** | B는 서로 독립적인 VIA 해석의 진행을 중첩할 수 있으나 관계 판단과 반환 채택, 재시도 비용 발생. A는 문맥 재구성과 중복 호출을 줄일 가능성 | 독립 목표와 반복 정정의 비율, model slot, cache가 방향을 바꿈. 외부 Agent 실행 시간은 제거한 실제 인과 경로로 계산 | **주요 차이 가설** |
| **QA04 변경 범위** | B는 continuation DTO, 질문 연결과 revision propagation이 추가됨. A는 혼합 문맥 처리 경계에 변경 영향이 모임 | C01/C02 wire 변화는 공통 adapter에서 끝나 동점일 수 있음. C04 응답 문단 수정은 partial publication 계약이 영향 범위를 결정 | **실제 Rust 소스 전 차이 미확보** |
| **QA05 모델 비용** | B/C의 별도 판단, snapshot 입력과 완료 재연결은 추가 청구. A는 복합 문맥 반복 입력과 중단 후 재생성 비용 가능 | 자주 끼어드는 독립 질문에서 B/C가 폐기 호출을 줄일 수 있음. 쉬운 연속 정정에서 A가 더 적은 호출로 완료할 수 있음 | **주요 차이 가설** |
| **QA06 최대 RAM** | B는 여러 요청 문맥과 완료 buffer를 동시에 보유. A도 pending read와 여러 잠정 요청, C도 side snapshot을 보유 | 참조 공유와 bounded 유지로 차이 감소. 512 MB 충족은 양쪽 필수이며 cloud KV를 로컬로 가산하지 않음 | **보조 차이 가설, 실제 크기 미확인** |

QA01과 QA03의 겹친 시간 구간을 독립적인 두 이익으로 합산하지 않는다. QA05는 관련 장면만 추린 비용으로 바꾸지 않고 공동 계약의 전체 COMMON-28 단위를 유지한다. 기존 QA07~09는 이번 핵심 비교를 채우기 위한 추가 축으로 사용하지 않는다.

### 7.1 신규 QA 제안: 요청 관계 연결 정확도

**의미:** 새 사용자 입력에 대해 VIA가 채택한 요청 관계가 독립적으로 정한 허용 관계와 일치하는가. 예를 들어 ‘새 독립 요청’, ‘R1 정정’, ‘실제로 제시된 Q2의 답변’, ‘T1 취소’를 구별한다. 판정 값은 관계 종류와 연결한 Request, Task 또는 질문 식별자의 집합이다. 정정할 개별 조건의 값이나 대상 문서와 화면 영역의 정확성을 이 지표에 추가하지 않는다. 후자는 QA02 또는 공통 기능 완료 조건으로 구별한다.

- 관측 단위는 입력 revision 하나의 최초 관계 채택이다. 여러 관계를 가진 복합 입력은 사전 정의한 관계 집합의 완전 일치로 판정한다.
- 분자는 허용 관계 집합과 일치한 입력 수, 분모는 관계 정답을 판정할 수 있는 적용 입력 수다. 이후 수정으로 첫 오연결을 지우지 않는다.
- 모호한 사례는 사전에 정한 확인 경로를 별도 표기한다. 모든 입력을 질문으로 돌리거나 연결을 끝없이 보류해 분모를 피하지 않도록 완료 조건과 관측 상한을 함께 정의해야 한다. 숫자와 점수는 제안하지 않는다.
- 문제 2의 동시 입력, 문제 4의 과거 결과를 잇는 후속 위임, 문제 5의 기존 Task 유지와 새 실행 전환에 같은 의미로 적용할 가능성이 있다. 문제 4와 5에서는 구조가 실제로 최초 관계 채택에 쓰는 입력이나 판단 경로를 바꾸는 경우에만 차이 가설을 등록한다. 이미 채택한 관계 뒤의 인계 문맥 구성이나 Agent 선택만 달라지면 이 지표의 trade-off로 세지 않는다.
- 관계 오연결 때문에 잘못된 업무 조건까지 인계했다면 요청 연결 오류와 인계 오류의 인과를 함께 기록한다. 두 지표를 별도로 관측할 수 있어도 동일한 한 오류를 독립적인 두 품질 개선으로 합산하지 않는다.
- A/B의 우열은 아직 없다. A의 풍부한 동일 문맥과 B의 명시적인 실행별 관계가 서로 다른 실패를 줄일 수 있지만 강한 보완 후 차이가 사라질 수 있다. 이 QA를 추가하면 DP 자격이 자동 확보되는 것은 아니다.

취소 후 오래된 결과의 무단 채택, 실제 종료 없는 완료 선언, 중복 외부 Action은 공통 기능 실패다. 이를 일부러 한 안에서 허용해 위 QA의 차이를 만들지 않는다.

## 8. 저비용 전환과 반증

| 보완 또는 전환 | 필요한 변화 | 판단 |
| --- | --- | --- |
| A에 짧은 read batch와 cancellation 추가 | 호출 경계, 재사용 가능한 완료 근거, provider cancel 처리 | 비교 전 허용할 기본 보완. 이 정도로 QA01 차이가 사라지면 B의 이익을 주장하지 않음 |
| A에 C 추가 | 읽기 전용 snapshot, side 결과의 범위 검사, 실제 전달 기록 | 실제 reference가 있는 비교적 작은 확장. B를 평가할 때 반드시 상대 안에 허용 |
| C에 새로운 read 도구 추가 | 권한 확인, source revision, pending read, late result 처리 | 단발 read 정도는 싸게 확장 가능. 모든 read가 B만의 이익은 아님 |
| C에 장기적인 독립 해석과 정정 허용 | 요청별 잠정 상태, 변경 전달, 실행 ID와 재개, dependency 추적, 완료 재연결 | B의 주요 계약에 접근. 이름만 바꾸는 전환은 아니지만 adapter와 공통 원장을 재사용할 수 있어 전체 재작성으로 과장하지 않음 |
| B를 거의 순차 실행하고 공통 문맥을 넓게 전달 | concurrency 제한과 input composition 변경 | A와의 실행 차이를 상당 부분 줄일 수 있음. 이미 저장한 continuation과 원래 질문의 대응을 해소하는 비용은 별도 |
| B에 긴 요청만 continuation 사용 | 임계 조건과 관계 판단, 공통 해석의 직접 답 경로 | 강한 B의 정상 구성. 모든 짧은 질문에 worker를 강제한 비용 우위 주장은 제외 |

**A 계열의 반증:** 완료 경계를 충분히 짧게 만들고 C를 붙여도, 서로 다른 자료를 이해하는 독립 입력이 정상적으로 겹치는 상황에서 첫 응답과 VIA 처리의 실용적 지연이 계속 커진다면 한 문맥 재사용의 이익만으로 A를 방어하기 어렵다.

**B의 반증:** 필요한 독립 입력 대부분을 C의 작은 확장으로 처리할 수 있거나, 동일 호출 예산에서 B도 foreground를 시작하지 못하거나, snapshot과 재판단 비용이 overlap 이익을 상쇄하면 별도 continuation 구조의 주요 DP 근거가 약해진다.

**C의 반증:** side 질문의 자동 분류 실패와 A로 돌아가는 비율이 높아 첫 응답과 비용 모두 악화되면 기본 적용 범위를 명시적 독립 질문으로 제한해야 한다. 제한 뒤 정상 사용 이익이 작다면 보조 기능으로 둔다.

## 9. DP 권고와 다른 문제와의 경계

**이 문제는 주요 DP 후보로 계속 발전시킬 가치가 있다.** 기존 44의 ‘다음 Stage를 누가 시작하는가’보다 **길게 진행 중인 의미 판단과 새 사용자 개입의 실행 관계**를 직접 바꾸므로, 정상 사용에서 QA01/03/05가 갈리는 인과를 더 명확하게 설명할 수 있다. 다만 세 축의 차이는 가설이며 QA01과 QA03의 중첩, C로의 저비용 보완을 검토한 뒤 실용적 크기가 남아야 한다.

발전시킬 단위는 A, B, C라는 세 이름보다 **A 계열의 현재 문맥 활용과 선택적 side 경로 대 B의 독립 요청 continuation**이다. C는 자료와 손익을 보존하며 비교에서 빼지 않는다. 여러 개입 정책은 각 계열의 내부 설계로 함께 명시한다. 기존 DP-44의 본문과 대안은 변경하지 않으며 새로운 DP 번호나 승자를 부여하지 않는다.

- **문제 1:** 각 실행에 어떤 근거를 공급하는가. 본 문제는 공급 전략을 공통으로 두고 실행 문맥과 대기 관계를 비교한다.
- **문제 3:** 발화와 관측에서 무엇을 보존하고 결합하는가. 본 문제는 그 원본을 동일하게 받으며 새 정정이 어느 실행을 바꾸는지 다룬다.
- **문제 4:** Agent 교체에 필요한 업무 기억과 인계 내용. 본 문제는 인계 내용 생산 구조를 정하지 않고 인계 요청과 결과가 대화 중 교차하는 실행을 다룬다.
- **문제 5:** Agent 선택의 적합성과 전환 결정. 본 문제는 선택된 Agent의 사실과 전환 입력을 올바른 요청 실행에 연결한다. 후보 선택 정확도 자체를 이 비교의 차이로 선점하지 않는다.

### 조사 범위와 남은 확인

공식 다섯 프로젝트의 관련 코드와 문서를 고정 commit으로 읽었다. OpenClaw의 실제 도구 경계와 steering custody, OpenHands의 SDK/Server 차이, Deep Agents의 thread/run/side 질문, Magentic-One의 순차 다음 참여자 선택, CrewAI의 turn과 Task join을 구별했다. 구현이 존재하는 메커니즘을 확보했으나 VIA의 자동 독립성 판단, 짧은 답의 질문 연결, provider 취소의 실제 지연, 전체 RAM과 QA 우열을 검증한 것은 아니다. 문서 작성과 정적 검토이며 harness 실행, 모델 실행과 성능 측정은 하지 않았다.
