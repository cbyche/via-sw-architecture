## 1. 이번 조사에서 유지한 원칙

사용자는 QA01~06을 출발점으로 삼되 새로운 중요 품질도 찾도록 허용했다. QA07~09는 이번 탐색의 상대적 우선도가 낮다. 이는 기존 정의를 삭제하거나 QA04 / QA06을 낮추라는 승인이 아니다. 이 문서의 신규 후보도 새 번호, 수치 목표와 점수 구간이 확정된 QA가 아니다.

QA01의 빠른 첫 표시와 QA03의 전체 VIA 처리시간은 같은 구간을 포함할 수 있다. 서로 다른 관찰 의미를 갖지만 두 개의 독립 이득이라고 합산하지 않는다. QA04는 실제 코드 변경이 있어야 모듈 수가 나온다. QA06은 로컬 최대 RAM이며 저장 파일 총량이나 cloud 모델 memory로 대신 평가하지 않는다.

## 2. 신규 후보 N-S. Downstream Agent 선택 정확도

### 2.1 단일 의미와 관찰 지점

**현재 요청 조건에서 VIA가 채택한 Agent 또는 보류 결정이 허용된 선택 집합에 속하는 비율**을 제안한다. 대상은 최초 위임과 재선택의 각 결정 revision이다. 선택 제안만 생성된 시점이 아니라 VIA가 실제 위임 대상으로 채택하는 지점에서 기록한다. 뒤에서 다른 Agent로 고쳤다는 이유로 처음의 잘못된 선택을 지우지 않는다.

사례 i의 사전 판정 집합을 `Acceptable(i)`라 하고 채택한 결과를 `Decision(i)`라 하면, 평가 가능한 사례에서 `Decision(i) ∈ Acceptable(i)`인 비율이다. 적합 후보가 없거나 독립 근거가 부족하여 보류해야 하는 사례에는 보류와 그 허용 이유를 집합에 명시한다. 충분한 근거로 선택할 수 있는 사례에서 무조건 보류하는 것은 성공이 아니다.

### 2.2 정답을 만드는 근거

1. 후보의 필수 capability, 사용 권한, 입출력 형식과 사용자 명시 지정을 판정한다. 연결 상태는 해당 revision에 관측 가능한 범위만 사용한다.
2. 남은 복수 후보 사이에 ‘가장 적합함’을 가를 필요가 있다면 **이번 요청에서 사용자가 정한 목적**과 독립적인 업무별 품질 근거를 사전에 정한다. Agent의 자기소개, 모델 이름, 선택기가 작성한 이유는 정답 근거가 아니다.
3. 여러 후보가 동등하게 조건을 만족하면 복수 정답을 허용한다. 속도 / 비용 / 품질을 임의 가중 합으로 합치지 않는다. 선택 목적이 지정되지 않아 갈릴 때는 확인 질문이나 허용 후보 집합으로 표현한다.
4. 독립적인 업무 품질 근거를 마련하지 못한 사례는 capability 적합성 검증으로 남긴다. 이를 ‘최고 성능 Agent 선택 정확도’라고 부르지 않는다. 평가 불가 사례 수와 이유도 보존한다.

미선택 / 시간 초과를 분모에서 조용히 제거하지 않는다. 사전 deadline 안에 필요한 채택이 없으면 실패로 기록하고, 정보상 판정 불가와 구별한다. 여러 결정 revision을 세는 규칙, deadline, 모집단과 수치 목표는 후속 공동 검토 대상이다.

### 2.3 적용 범위

문제 5가 직접 대상이다. 문제 1 / 4가 선택기에 공급하는 근거를 실제로 바꾸는 결합 설계라면 영향을 줄 수 있다. 그러나 **문제 4의 인계가 선택 이후에 일어나면 선택 정확도에는 영향이 없다.** 이 연결을 거꾸로 만들어 두 DP coverage를 채우지 않는다. 현재 독립된 핵심 QA로 선정할 경우 ‘최소 두 DP의 실제 차이’라는 과정 요건은 아직 충족하지 못한다.

## 3. 신규 후보 N-H. 업무 인계 정확도

### 3.1 단일 의미와 관찰 지점

**VIA가 외부 Agent에게 실행을 허가하며 확정한 인계 계약이, 현재 유효한 업무 조건과 필요한 근거를 정확하게 전달하는 비율**을 제안한다. 최초 위임, 후속 수정과 Agent 교체 모두 같은 경계를 사용한다. 준비 중인 요약이나 모델의 중간 입력을 관찰 지점으로 바꾸지 않는다.

평가 단위는 `(Task, request revision, execution attempt, delegation revision)`에 연결된 확정 계약이다. 정답 계약은 최소 다음을 구별한다.

- 사용자 목적, 완료 조건, 필수 제약, 유지 / 교체할 부분.
- 필요한 결과의 source / revision / 범위와 현재 유효한 접근 방식.
- 확인된 수행 범위, 아직 수행하면 안 되는 범위와 불명 상태.
- 철회된 조건 / 자료를 유효한 것으로 다시 넣지 않았는가.

표면 문구나 요약 길이가 같아야 하는 것은 아니다. 조건은 의미 동등성, 자료는 source identity / revision / 허용 범위와 적법한 접근 가능성을 사전 oracle로 판단한다. 필수 항목이 빠지거나 잘못 추가되면 해당 계약은 실패다. 항목별 누락 / 변형 / 금지 정보 재도입도 진단으로 보존한다. 목표 수치와 판정 도구는 미정이다.

### 3.2 push와 pull을 같은 조건으로 판단

문제 4의 참고 workspace를 읽는 안에서는 계약 안에 전체 본문이 들어갈 필요가 없다. **요구된 사실을 전달받을 수 있는 manifest, 유효 reference와 읽기 권한**이 계약에 포함되면 표현 방식으로 불이익을 주지 않는다. 확정 당시 이미 만료되었거나 필수 자료가 존재하지 않는 reference는 실패다.

외부 Agent가 유효 reference를 스스로 읽지 않았거나 domain 작업을 잘못 수행한 실패는 이 VIA 지표와 구별한다. 위임 뒤 자료가 철회되는 변형은 새로운 인계 revision에서 판정한다. 자료를 제공할 수 없어 올바르게 보류하는 장면은 사전에 명시한 보류 계약으로 평가하며, 필수 인계를 하지 않고 성공했다고 세지 않는다.

### 3.3 적용 범위와 제한

- 문제 4는 자료를 언제 만들고 누가 필요한 범위를 구성하는지 바꾸므로 직접 적용한다.
- 문제 2는 정정과 늦은 사건이 어떤 인계 revision에 반영되는지를 바꾸므로, **위임 장면**에서 직접 적용 가능하다.
- 문제 1은 조회 / 기억 누락이 최종 인계까지 남는 장면에서 인과 경로가 있다. 모델 입력의 충실도만 달라지고 인계 결과가 같으면 차이는 없다.
- 문제 3은 잘못된 대상 / 부분 정정이 인계 조건에 남는 경우 영향을 줄 수 있다. QA02와 중복되는 오류가 있으므로 서로 독립 이득으로 합치지 않는다.
- 문제 5는 동일한 인계기를 붙이면 구조만으로 차이가 약하다. 잘못된 Agent를 골랐다는 이유만으로 이 지표도 자동 실패시키지 않는다. 선택 정확도와 인계 내용은 구별한다.

이 후보는 **직접 응답만 하는 대화의 정정 정확도**를 평가하지 않는다. 현재 요청의 관계 / 변경 범위가 제대로 채택됐는지는 공통 기능 검증으로 별도 남긴다. 이를 인계 지표에 섞어 범위를 넓히지 않는다.

## 4. 신규 후보 N-R. 요청 관계 연결 정확도

문제 2에서 제안한 후보를 공통 검토 목록에 남긴다. **새 입력 revision에 대해 최초로 채택한 요청 관계 집합이 사전에 정한 허용 관계와 일치하는 비율**이다. 새 독립 요청, 특정 조건 정정, 실제 제시한 질문에 대한 답변, 특정 Task 취소 등을 구별한다. 복합 발화는 관계 집합 전체로 판정하며 대상 문서 / 화면 영역을 맞히는 QA02와 구별한다.

평가 단위와 최초 채택 지점은 모든 DP에서 동일하다. 이후 정정으로 최초 오연결을 지우지 않는다. 필요한 관계 채택이 없는 timeout / 무응답은 성공에서 제외하고 실패로 보존한다. 사전에 확인이 필요하다고 지정한 모호 입력은 허용 확인 경로로 평가하며, 명확한 입력을 무조건 질문으로 돌려 분모를 피하지 못하게 한다. 수치 상한, 모집단과 판정 도구는 미정이다.

문제 2는 임시 문맥과 relation 판단의 실행을 바꾸므로 직접 대상이다. 문제 1의 근거 공급은 관계를 판단하는 입력을 바꿀 때 영향을 줄 수 있다. 문제 3의 정정 범위 후보가 전체 요청 관계로 전달될 때도 경로가 있다. **문제 4 / 5의 비교가 관계 채택 이후의 인계 / 선택만 바꾸면 N-R 차이는 없다.** 같은 사례에서 relation 오류가 최종 인계에도 남으면 N-H와 중복 실패가 생긴다. 이를 두 개의 독립 품질 이득으로 합산하지 않는다.

N-R은 직접 응답과 외부 업무가 섞이는 VIA의 중요한 실패를 다룬다. N-H로 대체할 수 없고, 그렇다고 이번에 둘 다 core QA로 확정한 것도 아니다. 사용자 가치, 서로 다른 실패를 얼마나 설명하는지, 여러 구조에서 실제 차이가 남는지를 검토하여 core 또는 기능 진단으로 둘지 결정해야 한다.

## 5. 구조 차이가 남을 수 있는 범위

## 6. 지금 보이는 coverage의 빈칸

1. **첫 응답을 모든 문제의 주된 차이로 만들 수 없다.** 문제 4 / 5의 핵심 처리가 구체적 첫 내용 표시 뒤에 실행될 수 있다. 의도적으로 응답을 늦춰 QA01 이득을 만들어서는 안 된다.
2. **QA04는 단순한 모듈 분리로 이득을 주장할 수 없다.** 공통 edge와 안정 계약을 양안에 주면 차이가 사라질 수 있다. 지금 코드 변경 수를 추정 숫자로 채우지 않는다.
3. **강한 원본 재조회와 후보 확장은 정확도 차이를 줄일 수 있다.** 문제 1 / 3의 비용 차이와 최종 정확도 차이는 따로 검토해야 한다.
4. **N-S는 중요하지만 현재 한 문제에 집중된다.** 여러 DP에 관련 있다는 설명만으로 과정의 coverage 조건을 충족하지 않는다.
5. **N-H는 새로 드러난 VIA 가치를 직접 평가한다.** 문제 2 / 4에서 다른 구조의 실제 실패 경로가 있다. 그 차이가 일반적인 정상 사용에서도 충분한지는 후속 검토 대상이다.

따라서 이번 조사로 기존 6개에 신규 3개를 자동 추가해 9개 core QA로 확정하지 않는다. 새로운 후보들의 사용자 가치와 판정 가능성을 검토한 뒤 약 4~6개를 공동 선택해야 한다. 네 개의 최종 DP와 완성된 점수표를 확보했다고도 주장하지 않는다. **먼저 구조가 남는 문제를 고르고, 지표의 의미를 유지하면서 실제 차이가 나는 장면을 확인하는 것**이 다음 단계다.
