## 1. 문서 목적과 설계/평가 원칙

VIA에서 중요한 품질속성의 의미, 범위, 우선순위와 평가 기준을 사용자와 함께 정의한다. 먼저 어떤 품질을 왜 중요하게 보는지 합의하고, 이후 지표와 측정 방법을 구체화한다. 새로운 정의 논의와 합의는 이 문서에 이어 기록한다.

[03-00 품질 시나리오](./03-00-quality-scenarios.md)는 기존에 검토한 13개 품질 관점과 충돌 상황의 근거다. [기존 Core ASR 계약](../../08-quality-attributes/core-asr-contract.md)은 QA-09, QA-19, QA-29, QA-39와 상세 QA의 현재 의미를 보존한다. 이번 초안은 이 자료를 바탕으로 재검토하며 기존 정의를 자동 대체하지 않는다.

최근 [04-40 공통 실행 계약](./04-40-common-execution-contract.md)은 로컬 VIA와 클라우드 음성/의미 모델을 전제로 한다. 이 조건에서 PC 자원과 모델 사용 비용, 네트워크 의존성이 품질에 미치는 영향을 다시 살핀다. 기존 on-device 참조 설계와 당시 QA 정의 및 결과는 원래 조건으로 보존한다.

### 1.1 합의한 목적과 DP/QA의 관계 — 재개 시 반드시 읽기

**VIA의 목적은 핵심 QA 성능을 우선순위에 따라 최대화하는 SW를 만드는 것이다.** 이 과제에서 중요한 기능과 구조를 다루면서 핵심 QA 성능에 영향을 미치는 설계 결정을 DP로 도출한다. 현재 유력 후보는 **DP-41, DP-42, DP-44, DP-45**다. 이 네 개가 최종 DP나 A/B 승자로 선정된 것은 아니다. 43과 별도 46 자료의 지위를 이번 논의로 변경하지 않는다.

정방향의 설계 논리는 다음과 같다.

1. 중요한 품질 목표와 우선순위를 정한다.
2. 그 품질에 영향을 주면서 과제 차원에서도 중요한 설계 결정을 도출한다.
3. 각 DP의 강한 방안 A/B에 대해 핵심 QA 전체의 trade-off를 확인한다.
4. 합의한 우선순위에서 더 좋은 QA 성능을 보이는 방안을 선택한다. 필수 규칙, 허용 한도, 동등 또는 불확실한 차이의 처리도 공통 선택 계약에서 정한다.
5. 선택한 방안의 낮은 우선순위 QA가 약하면 tactic으로 보완한다. 보완 후 높은 우선순위 QA의 회귀와 다른 비용을 함께 확인한다.

기본 구조와 적용한 tactic을 구별해 결과를 기록한다. 기본 구조 비교를 위해 필수 검사나 이미 허용한 정상 기능을 제거하거나, A 또는 B를 약한 구현으로 바꾸지 않는다. tactic으로 차이가 줄어드는 것은 정상적인 설계 과정이다. 여러 QA를 가중 총점으로 합쳐 trade-off를 숨기지 않는다.

### 1.2 이번에는 DP에서 QA 정의로 역으로 접근한다

사용자는 DP 후보가 이미 있는 상태에서 A/B 성능을 측정하거나 계산할 수 있도록, 다섯 품질 묶음의 정의, 세부항목, 대표 지표와 목표를 구체화하려 한다. **기존 QA 공식을 자동 적용하는 것으로 끝내지 않고, 실제 구조 차이의 중요한 품질 효과를 포착하는 공통 QA를 설계한다.** 다음 순서로 각 품질을 검토한다.

**A/B의 실제 작동 차이 → 품질이 달라지는 원인과 상황 → 사용자에게 중요한 QA 정의 → 공통 지표와 목표 → 측정/계산 → 우선순위에 따른 선택과 tactic 보완**

| 연결 | 확인할 질문 |
| --- | --- |
| 사용자 가치와 QA 정의 | 이 품질이 좋아지면 VIA 사용자가 무엇을 더 잘할 수 있는가? |
| 구조 차이와 품질 효과 | A/B의 어떤 판단, 근거 획득, 실행 의존성, 상태 또는 확정 차이가 품질을 바꾸는가? |
| 품질 효과와 지표 | 그 차이를 같은 입력과 조건에서 관찰하고 계산할 수 있는가? |

정의는 구조 차이에 민감하면서도 실제 사용자 가치에 근거해야 한다. 같은 조건에서 A/B 차이가 없거나 측정으로 구분되지 않는다면 그대로 남긴다. 모든 DP가 모든 QA에서 다른 값을 가져야 한다고 요구하지 않으며, 예상한 우열에 맞춰 사례나 분모를 고르지 않는다.

초기 측정/계산은 정의의 적합성을 확인하는 탐색에 사용할 수 있다. 이때 사용한 정의 version과 사례, 변경 이유를 남긴다. 최종 선택에 쓰는 비교는 검토를 마친 공통 계약을 결과 전에 고정한 뒤 수행한다. 탐색 결과를 개정된 계약의 최종 비교 결과로 재해석하지 않는다. 이번 합의는 정의와 평가 설계의 진행 방향이며 지금 구현, 모델 실행, 수치 freeze나 최종 선택을 시작하는 지시로 확대하지 않는다.

### 1.3 Compaction 또는 다른 세션에서 재개하는 순서

1. AGENTS.md와 00-workplan의 현재 QA 체크포인트를 읽고 실제 git 상태를 확인한다.
2. **§1.1~1.2의 합의한 방향**을 읽는다. 유력 DP 네 개, 역방향 정의, 우선순위 선택과 tactic 보완의 관계를 복원한다.
3. §2의 목록/검토 상태와 §9의 최신 변경 이력을 읽는다. 정확성은 한 축으로 정의했고 다른 QA의 세부 지표/목표/새 우선순위는 아직 미정이다.
4. 정확성은 **§3의 Voice PoC v2**와 **§8의 공통 시험 환경**을 따른다. 이전 Text/Voice × 모든 조건 교차 시험이나 초기 7개 항목을 복원하지 않는다. 18개 대표 사례 × 5회, 실행당 6개 이진 항목을 유지한다.
5. 각 QA의 현재 내용은 해당 절에 갱신하고 변경 이유는 §9에 남긴다. 이전 QA 지표를 자동 복원하거나 DP별로 다른 QA를 만들지 않는다. 구현/실측 착수는 별도 요청을 따른다.

### 1.4 모든 DP에 적용할 공통 정의 원칙

선정한 QA는 모든 DP와 모든 대안에서 동일한 정의, 대표 지표와 측정 방법을 사용한다. 평가 단위, 정답 판정, 시작/종료 사건, 시간 및 비용 경계, 집계, 모집단 적용, 분모와 제외 규칙, 실패 및 timeout 처리를 공통 원본에서 정한다. 각 DP는 구조의 인과적 참여와 내부 관측을 그 계약에 연결한다.

같은 QA를 특정 DP에서는 의미 field accuracy, 다른 DP에서는 검색 recall이나 업무 성공률로 바꾸어 사용하지 않는다. 추가 진단은 공통 QA를 대체하지 않는다. 미참여, 미지원과 미확인을 0점이나 동등으로 간주하지 않으며, 실패 사례를 조용히 제외하지 않는다.

QA의 개정 이유와 영향받는 문서를 함께 기록하고, 이전 정의 및 결과는 원래 계약으로 보존한다. 기존 자료의 재사용은 의미와 측정 방법이 맞는지 확인한 뒤 결정한다. 지표와 목표값을 확정하기 전에도 각 품질의 손익은 독립적으로 설명하며 가중 총점으로 합치지 않는다.

### 1.5 다른 품질 관점과의 관계

기능 적절성, 기능 완전성과 결함 허용성 및 복구성은 이번 핵심 QA 목록의 독립 항목에서 제외한다. 기밀성, 분석 및 시험 용이성, 상호운용성과 공존성, 조작 용이성과 사용자 오류 방지, 설치 용이성 및 메모리 외 자원도 기존 자료에서 참고한다. 이 문서에 핵심 QA를 추가할 때는 사용자가 정한 다섯 묶음의 범위와 관계를 다시 논의한다.

[03-00](./03-00-quality-scenarios.md)의 13개 관점과 기존 구조 비교 기록은 보존한다. 기능 지원 차이와 수동 우회 부담은 비교 조건 및 한계로 남긴다. 미지원 안내를 원래 목표의 성공 완료로 세거나 권한 위반을 비용 절감으로 정당화하지 않는다. 장애 상황의 잘못된 상태나 중복 실행은 해당 정확성의 범위와 공통 시험 조건에서 어떻게 판정할지 정한다.

### 1.6 문서 관리 방식

각 QA의 현재 정의는 §3~7의 해당 절에 한 벌만 유지한다. 정의/범위, 지표/집계, 목표, 측정 방법, DP 영향 경로를 함께 관리한다. 응답속도 이하의 미확정 항목은 초안/검토 예정으로 표시하고 논의 후 그 절에서 갱신한다.

공통 시험 환경과 A/B 비교 조건은 §8에서 관리하고 각 QA는 필요한 공통 조건을 참조한다. 정확성의 90회/540개 분모나 목표를 아직 정의하지 않은 다른 QA에 자동 적용하지 않는다. 합의와 작성자 제안, 정의 완료와 실제 측정 완료를 구별한다.

이전 제안은 archive에 보존하고 변경 이유/범위를 §9에 기록한다. 목차 이동 시 본문 참조와 README/00-workplan의 재개 안내를 함께 갱신한다. 문서 정리는 QA 정의 개정이나 DP 선정으로 취급하지 않는다.

## 2. 핵심 QA 목록과 검토 상태

이번 정의 작업은 다음 다섯 묶음으로 진행한다. 정확성과 응답속도의 최종 항목 수에 따라 총 5~7개가 된다. 사용자가 제시한 나열 순서를 새로운 우선순위나 가중치로 해석하지 않는다.

| 묶음 | 항목 수 | 현재 세부 검토안 |
| --- | --- | --- |
| 정확성 | 1~2개 | 요청 처리 정확성을 공통 평가축으로 확정. C1~C6는 이 축의 채점/진단 항목이며 별도 핵심 QA로 나누지 않음. 추가 독립 정확성 QA는 아직 없음 |
| 응답속도 | 1~2개 | 상호작용 반응성, VIA 귀속 요청 완료 시간 |

현재 정확성은 요청 처리 정확성 한 축이다. 최초의 두 정확성 항목/총 7개 초안은 역사 기록에 보존한다. 응답속도는 두 초안을 계속 검토하며 기존 QA 번호와 V 표식은 참고 자료다. 신규 QA ID와 다섯 묶음의 우선순위는 아직 정하지 않았다.

## 3. 정확성

**현재 항목: 요청 처리 정확성 / Voice PoC 평가 설계 v2.** 정의/대표 지표/분모/목표/평가 방법을 아래에 모았다. 후보나 모델을 실행한 결과는 아직 없다. 공통 시험 환경과 A/B 구성은 §8을 따른다.

### 3.1 정의와 평가 범위

**사용자가 지정한 목적은 설계 방안 A/B의 품질 차이를 확인하는 작은 PoC다.** 모든 UC 변형/채널의 기능 완전성이나 제품 수준 음성 인식/장치 성능을 검증하는 캠페인이 아니다. 같은 대표 Voice 장면을 공통 경계까지 추상화하고 DP가 바꾸는 판단/결합/확정/후속 실행/근거 생산의 차이를 유지한다. Text 입력을 제외하고 모든 사례에 모든 조건을 곱하지 않는다. §3의 분류/채점/목표와 §8의 공통 환경을 실행 기준으로 사용하며 실제 파일/모델/후보 build의 machine freeze와 실행은 별도 작업이다. [이전 v1](../../../archive/qa-request-accuracy-before-voice-poc-20261010/README.md)은 변경 근거로 보존했고 실행 결과는 없었다.

- **정의:** VIA가 사용자 입력과 외부 사건을 의도 및 확인 가능한 사실에 맞는 요청 처리 결과로 연결하는 능력. 의미, 근거/대상, 업무 연결, 관계/변경, 적용 상태와 실제 전달을 포함한다.
- **평가 상황:** §3.2.1의 S1~S6. 기본 사례는 §3.2.2의 상황군별 3개, 총 18개로 고정한다.
- **실행당 채점:** C1~C6를 각각 0 또는 1로 판정한다. 항목 안의 필수 사실을 모두 만족하면 1, 하나라도 틀리거나 필요한 결과/근거가 없으면 0이다. 세부 사실별 진단은 보존하지만 별도 점수로 더하지 않는다.
- **대표 지표:** 채점 항목 전체의 정답률. 여섯 항목은 같은 비중이며 비용/시간 등 다른 QA와 가중 합산하지 않는다.
- **완전 정답 처리율:** 한 실행의 여섯 항목이 모두 1인 비율. 같은 원시 판정에서 계산해 보조 품질 한도로 사용한다.

**대표 사례 18개를 한 번씩 실행하면 18 × 6 = 108개 항목을 채점한다.** 18개 사례에는 여섯 유형 모두에 의미 있는 필수 사실을 §3.3.2처럼 등록하므로 N/A 칸이 없다. 예를 들어 업무가 없는 경우의 C3은 `무관 Task에 연결하지 않음`, 상태 변경이 없는 조회의 C5는 `조회/응답을 처리하고 불필요한 외부 업무 효과를 만들지 않음`으로 검사한다. 빈 항목에 자동 1점을 주는 방식이 아니다.

**이번 PoC에서는 여섯 묶음의 이진 판정으로 집계한다.** 판정 후 N/A로 변경하거나 사례별 조건 수로 가중치를 바꾸지 않는다.

### 3.2 테스트 상황 분류와 18개 대표 사례

**테스트는 상황 6개 유형으로 분류하고, 정답은 조건 6개 유형으로 기술한다.** 상황 유형은 어떤 문제를 시험하는지, 조건 유형은 무엇이 맞아야 하는지를 나타낸다. 테스트마다 입력, 초기 상태, 사건 순서와 기대값을 바꾸되 조건의 의미와 판정 규칙은 재사용한다. 이 유형들은 새로운 QA 12개나 DP별 지표가 아니다.

기능 범위의 근거는 [고정 UC](../../05-representative-use-cases.md)이며, 네 DP의 영향 경로는 §3.7에 연결한다. 현재 네 비교에서 제외한 음성 모델의 자율 직접 응답은 [04-40](./04-40-common-execution-contract.md)의 경계를 따른다. UC-01의 기존 기능 요구 자체를 삭제하거나 Downstream Agent의 도메인 결과 품질을 VIA 판정으로 가져오지 않는다.

#### 3.2.1 공통 상황 분류

| 유형 | 시험할 상황과 경계 | 공통으로 확인할 핵심 결과 | 주 UC 연결 |
| --- | --- | --- | --- |
| S1 명시적 기본 요청 | 목표와 대상이 입력에 명시된 새 요청. 특별한 과거 지칭, 복합 관계, 정정이나 확인이 필요하지 않음 | 명시된 목표/제약을 누락하지 않고 적절히 답변하거나 위임 | UC-02, 08, 17 |
| S2 지칭과 근거 연결 | 화면, 선택, 생략, 과거 설명이나 업무 결과에서 대상을 찾아야 하는 요청 | 해당 시점/범위/version의 올바른 근거와 대상을 사용 | UC-03, 04, 05, 07, 10 |
| S3 복합 요청과 관계 | 한 입력에 여러 목표가 있고 독립, 순서, 결과 의존 또는 조건 관계가 있음 | 각 목표 및 관계/제약을 보존하고 관계에 맞게 처리 | UC-09 |
| S4 정정과 제어 | 기존 요청/업무의 변경, 음성 중단, 특정 업무 취소 또는 사용자 설정 변경/삭제 | 지정 범위만 바꾸고 무관한 내용/업무를 보존. 효력과 실제 상태를 구별 | UC-10, 11, 12, 17 |
| S5 외부 업무 사건 | Agent의 질문, 진행, 접수, 결과, 실패 등 외부 사건을 VIA가 수신 | 올바른 업무/대화로 연결하고 확인된 사실과 필요한 후속 동작을 전달 | UC-13, 14, 15, 18 |
| S6 확인과 판단 유보 | 처음부터 정보/대상/허용 범위가 불충분한 요청 또는 기존 질문에 대한 사용자 답변 | 필요한 확인/유보를 하고 질문 유효성, 답변의 대상과 승인 범위를 보존. 근거 없는 확정 금지 | UC-06, 14, 16, 18 |

**대표 상황은 후보 실행 전에 원천 입력과 초기 상태로 하나만 지정한다.** 중복되는 경우 다음 순서로 정한다.

1. 평가할 입력이 Agent 원천 사건이면 S5다. 이후 그 질문에 대한 사용자 답변은 별도 과제로 등록하면 S6다.
2. 평가할 입력이 기존 질문의 답변이거나, 필요한 정보/허용이 불충분하도록 작성한 사례면 S6다. 철회/만료된 질문에 대한 답변도 이 유형에서 적용 금지를 확인한다.
3. 기존 내용을 바꾸거나 제어하는 입력이면 S4다.
4. 여러 목표의 관계를 시험하는 입력이면 S3다.
5. 지칭 대상과 근거를 찾아야 하는 입력이면 S2다.
6. 나머지 명시적 기본 요청은 S1이다.

예를 들어 “아까 보고서는 표로 바꾸고 메일은 그대로”는 S4이며 `과거 지칭`, `복수 업무`, `보존 조건`을 변형 tag로 붙인다. 후보가 명확한 S1 요청을 이해하지 못해 질문했다고 그 실행을 S6로 재분류하지 않는다. 복합 사례를 여러 상황군에 복제해 분모를 늘리지 않는다.

#### 3.2.2 대표 사례의 초기 상태와 입력

다음 18개는 **Voice PoC v2의 대표 사례**로 채택했다. 각 사례의 6개 필수 채점 항목은 §3.3.2에 고정했다. 실제 원본 파일과 입력/사건 fixture는 이 계약대로 제작하고 실행 전에 hash를 고정한다. 표의 정답은 중심 사실이며 전체 필수 항목은 §3.3.2를 따른다. 18개가 제품의 모든 UC/필수 변형을 빠짐없이 검증한다는 뜻은 아니다.

| S5-03 음성 종료 중 결과 | 사용자가 음성을 종료했지만 업무는 유지. Agent 결과가 Text로 표시된 뒤 음성 재연결 | C5: 결과/업무 유지, 새 실행 없음. C6: Text 표시와 음성 전달 사실 구별. 필요한 재연결 안내를 하고 미재생 결과를 이미 들었다고 기록하지 않음 |
| S6-01 모호한 과거 대상 | 과거 보고서 두 개가 동일하게 유효함. “아까 보고서 수정해줘.” 이어서 사용자는 대상/수정 내용을 답함 | C1: 필요한 대상/내용 확인. C5: 답변 전 임의 변경 없음. C2/C3/C4: 답변 뒤 지정한 대상/업무/변경 적용. 질문 문구 자체는 일치 불필요 |
| S6-02 답변과 승인 범위 | 메일 Task의 유효 질문 Q1은 연락처 조회 동의이고, 별도 Q2는 전송 승인 대기. 실제 제시된 질문은 Q1. 사용자가 “응” | C3: Q1 답변 연결. C4/C5: 연락처 조회만 허용하고 전송 승인으로 확장하지 않음. 제시 receipt가 미확인/철회되면 재확인하며 임의 승인 금지 |
| S6-03 필요한 근거 접근 불가 | 필요한 D1의 접근이 거부되었으며 허용 대체 근거 없음. “D1의 계약 금액을 알려줘” | C1: 접근 불가 안내와 허용 대안/유보. C2: 임의 다른 문서로 대체 금지. C5: 권한 우회 조회 없음. C6: 금액을 추측하거나 조회 성공으로 알리지 않음 |

S1-03의 신규 저장 외에 기존 선호 변경/삭제는 S4로 분류한다. 삭제 후 재사용 금지는 같은 C2/C5 규칙으로 작성한다. 접근 거부, 누락, 접수 미확인 등은 fixture에 따라 정답이 달라질 수 있으나 판정 유형을 새로 만들지 않는다.

#### 3.2.3 사례별 조건과 반복 수

모든 DP A/B에 같은 **18개 대표 Voice 사례 × 반복 5회**를 적용한다. N/W/X는 사례에 지정하는 조건 유형이며 별도 배수가 아니다. 각 사례는 아래에서 정한 조건 하나로만 실행한다.

| 축 | 고정한 구성 |
| --- | --- |
| 대표 사례 | S1~S6별 3개씩, §3.2.2의 18개. 후보가 생성한 Request/Task 수로 증가하지 않음 |
| 입력 | 사용자 요청/후속 답변은 Voice만 사용. S5의 최초 사건은 Agent event이며 사용자 답변이나 재연결이 필요한 경우 Voice로 제공. Text 출력 기록은 유지 |
| N 정상/첫 사용 | 보존된 원본/기존 상태에서 시작. 관련 신규 조회의 cache/게시 결과를 정답으로 선주입하지 않고 추가 경쟁을 넣지 않음 |
| W 반복/준비된 과거 | 같은 원본 활동 이력과 허용된 이전 조회를 실제 후보 경로로 처리한 뒤 현재 과제 실행. 양안 cache/생산/갱신 허용. 최대 120초의 동일 준비 창과 그 비용 기록 |
| X 변경/교차 | 해당 사례에 필요한 변경/철회, 중복/늦은 반환 또는 질문 교차만 사전 event script로 재생. 모든 경쟁 유형을 모든 사례에 넣지 않음 |
| 반복 | 각 사례의 지정 조건을 5회 실행. 매 반복은 초기 상태를 복원하고 필요한 준비 이력을 다시 처리. 실행 간 cache/Task/질문 누적을 섞지 않음 |

| 상황군 | 첫 사례의 조건 | 두 번째 사례의 조건 | 세 번째 사례의 조건 |
| --- | --- | --- | --- |
| S1 명시적 기본 요청 | S1-01 N: 자료 조회 | S1-02 N: 보고서 위임 | S1-03 N: 선호 저장 |
| S2 지칭/근거 연결 | S2-01 N: 발화 당시 두 표 | S2-02 W: 과거 설명/두 결과 재사용 | S2-03 X: 원본 갱신 뒤 과거 snapshot 지정 |
| S3 복합 관계 | S3-01 N: 독립 두 목표 | S3-02 X: 선행 결과의 늦은/중복 반환 | S3-03 X: 조회 뒤 일정이 차는 조건 변경 |

| S5 외부 Agent 사건 | S5-01 X: 두 질문/철회의 교차 | S5-02 X: 결과 역전/중복 수신 | S5-03 N: 음성 종료 중 결과와 재연결 |
| S6 확인/미해결/답변 | S6-01 N: 모호한 요청 확인 | S6-02 X: 제시 receipt/권한과 답변 경합 | S6-03 N: 원본 접근 거부 |

W는 B만 미리 완성된 기억을 받는 조건이 아니다. 양안이 같은 활동과 원본 사건을 처리한다. 이전 조회는 허용된 read-only 조회로 한정하고 현재 채점할 신규 등록/업무/취소를 미리 실행하지 않는다. A의 cache를 제거하지 않고 B의 관계 생산/게시를 evaluator가 대신하지 않는다. 준비 비용/유실/지연도 남기며 현재 목표나 정답 의미를 준비 이력에 넣지 않는다.

X는 공통 외부 원천 사건의 순서와 유효성 규칙으로 정의한다. 특정 안에만 있는 내부 Module의 완료를 다른 안의 시작 기준으로 삼지 않는다. 존재하지 않는 job/질문/source를 경쟁을 위해 발명하지 않고 실제 모델 반환값은 바꾸지 않는다. 늦은 결과를 시험할 때는 반환 전달 순서만 제어한다. 내부 job이 없으면 그 경합은 발생하지 않은 것으로 기록한다.

§3.2.2의 대표 발화/초기 상태를 사용한다. S2-02의 과거 설명에는 `평가 기준 중 가격 제외`라는 예외를 포함한다. S3-03은 최초 조회에서는 비어 있고 적용 전에 일정이 차는 조건 하나를 선택한다. 유효한 변경 근거로 생성하지 않고 안내하는지를 보며 두 분기를 전부 검증했다고 주장하지 않는다. 18개 사례의 108개 채점 항목은 그대로 유지한다.

```text
후보 1개: 18 × 5 = 90회 처리 과제 실행
후보 1개의 채점 분모: 90 × 6 = 540개 이진 항목
상황군 1개의 채점 분모: 3 × 5 × 6 = 90개
조건 유형 C 하나의 분모: 90개
DP 1개의 A/B: 180회 실행 / 1,080개 항목
네 DP를 모두 비교: 720회 실행 / 4,320개 항목
```

이는 선택한 대표 장면에서의 PoC 정확률이다. 상황군은 각각 3개지만 N/W/X는 8/1/9개이며 제품 빈도로 가중하거나 모든 조건을 균등하게 검증하지 않는다. 90회 또는 540개 항목을 모두 독립 표본으로 주장하지 않는다. 반복과 같은 대화의 후속 관측은 해당 사례에 묶는다. 서로 다른 DP의 분자/분모를 합쳐 하나의 VIA 제품 정확률로 만들지 않는다.

### 3.3 정답 조건과 6개 채점 항목

각 실행의 C1~C6에 같은 의미와 판정 규칙을 적용한다. 세부 사실은 진단을 위해 보존하되 여섯 이진 항목 이외의 점수를 추가하지 않는다.

#### 3.3.1 재사용할 정답 조건 유형

| 유형 | 정답으로 기술할 사실 | 대표 판정 예시와 관측 경계 |
| --- | --- | --- |
| C1 목표와 처리 방향 | 요청한 행위/산출물의 의미, 답변/위임/확인/유보 등 허용 처리 방향 | 보고서 형식 변경을 새 조사로 바꾸지 않음. 업무 실행은 Agent에 인계. 필요한 확인을 임의 완료로 대체하지 않음 |
| C2 대상과 근거 | 지칭한 자료/객체의 집합과 범위, 원본 시점/version, 실제 전달된 과거 설명이나 결과 참조 | 발화 당시 선택한 표와 당시 v1을 사용. 최신 v2 또는 아직 들려주지 않은 설명으로 바꾸지 않음 |
| C3 대화와 업무 연결 | 새 업무/기존 업무/업무 없음의 관계, 연결할 대화/Task/Execution/질문 | 보고서 변경은 보고서 업무에 적용. 메일 질문의 답을 보고서 업무로 보내지 않음 |
| C4 조건, 관계와 변경 범위 | 내용 제약, 금지/보존 조건, 요청 간 독립/순서/조건/결과 의존, 변경할 범위 | 요약 결과를 메일 입력으로 사용하고 먼저 보내지 않음. 표 형식만 바꾸고 기간/수신자/다른 요청을 보존 |
| C5 처리 효과와 상태 | 실제 요청/명령 적용, 중복 여부, 유효 revision, 접수/완료/실패/미확인 상태와 허용 전이 | 철회한 질문 답변을 적용하지 않음. 같은 command 재수신이 두 번 실행되지 않음. 로컬 접수만으로 외부 완료를 확정하지 않음 |
| C6 응답 내용과 실제 전달 | 사용자에게 알린 사실/결과 참조, Text/음성의 의미 일치, 실제 표시/재생과 전달 기록 | 미확인 취소를 완료라고 말하지 않음. 텍스트와 음성이 같은 업무 상태를 알림. 음성 중단 이후 미재생 범위를 들었다고 기록하지 않음 |

기대값은 사용자 입력과 공통 근거에서 정한다. Task가 아직 없다면 `새 업무에 연결`을 기대값으로 기록하고, 실제 생성 ID는 관측 후 대응시킨다. 특정 Task ID를 미리 확정한 것으로 모델에 주지 않는다. 기존 업무/질문은 fixture의 의미 ID와 실제 runtime ID를 대응시켜 검사한다.

정보 조회에서 허용되는 Core 직접 응답과 Agent 위임처럼 같은 요구를 만족하는 복수 결과는 사전에 허용 집합으로 기록한다. Component 배치, 모델 호출 횟수, 내부 frame 형식이나 의미 생산 순서는 이 QA의 정답 조건으로 강제하지 않는다. 실제로 채택된 의미, 외부로 전달한 요청/명령, 적용 상태와 사용자 전달에서 판정한다. 채택 전 틀린 임시 후보를 스스로 고친 것은 최종 오류와 구별하되, 이미 발생한 금지 효과는 마지막 상태가 맞아도 지우지 않는다.

##### 조건을 작성하는 공통 규칙

- 여섯 유형을 모든 테스트 양식에 둔다. 이번 18개 사례는 모든 유형에 필수 사실이 있으며 N/A를 사용하지 않는다. 업무가 없는 경우의 무관 업무 연결 금지처럼 의미 있는 사실을 검사한다. 후보 출력에 field가 없다는 이유로 적용 없음으로 바꾸지 않는다.
- 조건 하나는 사용자에게 의미 있는 판정 사실 하나다. `수신자=민수`, `보고서 형식=표`, `메일 요청 보존`처럼 고정 의미 단위로 작성한다. 내부 JSON 속성 수나 Module 수에 따라 조건을 쪼개지 않는다.
- 같은 사실은 하나의 주 조건 ID에 귀속시킨다. 예를 들어 목표 업무 선택은 C3, 그 업무에 command가 한 번 적용된 사실은 C5, 그 처리 사실의 올바른 안내는 C6다. 같은 업무 선택 사실을 세 유형에서 세 정답으로 세지 않는다. 한 오선택이 실제 적용과 안내까지 오염시킨 경우 서로 다른 효과와 공통 원인은 함께 기록한다.
- 대상 집합이나 관계 graph의 판정 단위도 동일하다. 한 사례에서만 원소/간선을 별도 점수로 세지 않는다. 세부 누락/추가 항목은 진단으로 보존하고 집계 단위는 §3.1의 여섯 묶음 이진 판정으로 고정한다.
- 명확한 사례에는 기대한 요청 처리를 요구한다. 근거가 부족한 사례에는 필요한 질문/유보와 공통 후속 답변 뒤의 처리까지 요구한다. 단순 접수 멘트나 모든 요청의 보류로 정답을 얻지 못한다.

#### 3.3.2 사례별 여섯 필수 채점 항목

각 칸은 하나의 이진 채점 항목이다. 세미콜론으로 구분한 사실도 모두 맞아야 해당 칸이 1이다. 사례에 지정한 조건의 source version/질문 유효성/실제 접수 차이는 사전 fixture 상태와 공통 전이 규칙으로 대입한다. 후보 결과를 보고 기대값을 바꾸지 않는다. §3.2.2의 원문/초기 상태와 아래 표를 함께 사용한다.

| 사례 | C1 목표/방향 | C2 대상/근거 | C3 대화/업무 | C4 조건/변경 | C5 효과/상태 | C6 내용/전달 |
| --- | --- | --- | --- | --- | --- | --- |
| S1-01 | D1 마감일 조회; 허용 직접 응답/위임 | D1 지정 version의 마감일 | 직접 응답이면 무관 Task 연결 없음; 위임이면 새 조회 업무 연결 | D1 안의 정보로 범위 제한 | 올바른 조회/응답 처리; 불필요한 외부 변경 없음 | fixture 마감일을 사실대로 전달; 실제 채널 전달 기록 |

#### 3.3.3 정답표 작성 예 — S4-01

초기 상태는 보고서 업무 T보고서와 메일 업무 T메일이 각각 존재하고, 보고서 대상은 D1@v1, 기간은 올해 3분기, 형식은 문장이라고 둔다. 메일 대상/수신자와 지시는 이미 정해져 있다. 현재 준비 중인 변경 요청은 아직 외부에 전송되지 않았다. 사용자가 “보고서는 표로 바꾸고 메일은 그대로”라고 정정한 뒤 이전 입력을 기준으로 만든 의미 후보가 늦게 돌아온다. 공통 외부 Agent는 올바른 변경 요청의 접수만 확인하고 완료는 알리지 않는다.

| 공통 조건 유형 | 사전 기대값 | 확인할 근거 |
| --- | --- | --- |
| C1 목표와 처리 방향 | 기존 보고서의 형식 변경. 새 보고서 업무 생성이나 새로운 조사로 바꾸지 않음 | 채택 의미와 Agent에 전달한 요청의 목적 |
| C2 대상과 근거 | 보고서 대상 D1@v1 유지. 다른 자료나 최신 원본으로 교체하지 않음 | 실제 요청의 자료/version 참조 |
| C3 대화와 업무 연결 | T보고서에 변경 연결. T메일에 변경 연결하지 않음 | 실제 요청/명령의 업무 및 대화 연결 |
| C4 조건, 관계와 변경 범위 | 형식=표, 기간=올해 3분기 유지, 메일의 기존 대상/수신자/지시 보존 | 채택한 변경/보존 조건과 실제 인계 내용 |
| C5 처리 효과와 상태 | 유효 정정만 적용. 늦은 이전 후보의 재적용과 중복 변경 없음. 외부 접수 확인을 완료로 전이하지 않음 | 변경 적용/전송 trace, Agent receipt, 업무 상태 |
| C6 응답 내용과 실제 전달 | 보고서 변경 접수 사실을 알림. 완료라고 주장하지 않음. 실제 표시/재생 범위대로 기록 | 실제 Text/음성 내용과 전달 evidence |

이것은 **6개 조건 유형을 채운 예**다. Voice PoC v2에서는 유형마다 필수 사실을 모두 만족해야 1점이 되는 여섯 이진 항목으로 집계한다. C4의 형식/기간/메일 보존처럼 여러 사실은 진단용 조건 ID로 등록하되 항목 내 부분 점수를 추가하지 않는다.

### 3.4 측정 지표와 분모

```text
y(i,c) ∈ {0,1}  # 실행 i의 채점 항목 c, c=1..6
요청 처리 정확성(%) = 100 × Σ_i Σ_c y(i,c) / 540
완전 정답 처리율(%) = 100 × count_i[모든 c에서 y(i,c)=1] / 90
상황군별 정답률(%) = 100 × 해당 상황군의 정답 항목 수 / 90
C 유형별 정답률(%) = 100 × 해당 C 유형의 정답 항목 수 / 90
A/B 차이(pp) = B의 요청 처리 정확성 − A의 요청 처리 정확성
```

전체 분자/분모와 함께 6개 상황군, 6개 C 유형, 지정된 N/W/X, 18개 사례 및 5개 반복의 분해 결과를 공개한다. 같은 항목에서 `둘 다 정답`, `A만 정답`, `B만 정답`, `둘 다 오답`을 기록하고 오답 원인 및 모든 위반 trace를 연결한다. 조회/생산/결합/채택/전송/게시/추상 장치 전달 중 오류 발생 경로는 진단이며 점수를 추가하지 않는다.

작은 차이를 반복 수만으로 확실한 차이처럼 보이지 않게 한다. 불확실성은 **같은 대표 사례의 5회 반복 전체를 하나의 묶음**으로 A/B 함께 재표집한다. S1~S6 각각에서 기본 사례 3개를 복원 추출해 균형을 유지하는 paired block bootstrap 10,000회, seed `20261010`, 차이의 2.5/97.5 percentile을 보고한다. 18개 사례 묶음만 있으므로 작은 차이의 검정력은 제한적이며 제품 모집단의 정확률 신뢰구간이라고 해석하지 않는다. 이 절의 구체적 묶음/횟수는 작성자 설계다. 의존된 음성 자료를 개별 독립 표본으로 재표집하지 않는 원칙은 [Liu와 Peng의 blockwise bootstrap 연구](https://arxiv.org/abs/1912.09508v2)를 참고했다.

### 3.5 목표와 A/B 차이 판단 기준

| 기준 | v2 PoC 목표 | 고정 분모에서 필요한 수 | 이유 |
| --- | --- | --- | --- |
| 대표 요청 처리 정확성 | **98% 이상** | 540개 중 530개 이상 정답, 오답 최대 10개 | 항목 오류 예산을 2% 이내로 제한 |
| 완전 정답 처리율 | **95% 이상** | 90회 중 86회 이상 여섯 항목 모두 정답 | 여러 칸의 높은 부분 점수로 요청 단위 실패를 숨기지 않음 |
| 각 S 상황군 정답률 | **각각 95% 이상** | 각 90개 중 86개 이상 정답 | 쉬운 정상 사례로 특정 중요한 상황의 실패를 희석하지 않음 |
| 각 C 조건 유형 정답률 | **각각 95% 이상** | 각 90개 중 86개 이상 정답 | 실제 적용/전달의 약점을 의미 항목 점수로 상쇄하지 않음 |
| 필수 위반 | **0건** | 전체 실행/관찰 trace에서 위반 없음 | 오업무/중복 외부 효과, 잘못된 질문/승인 적용, 무허용 접근/제공을 평균에 희석하지 않음 |

이 숫자는 제품 빈도나 실측에서 추정한 값, 산업 표준 또는 모델이 이미 달성한 성능이 아니다. 이번 과제의 **평가 목표**로 정한 설계 수치다. 두 후보 모두 미달하면 미달을 보고하고 원인을 보완한다. 목표를 결과 뒤에 낮추거나 실패 사례를 빼지 않는다. 필수 위반 0건은 이 시험에서의 관찰 결과이며 제품 전체에서 오류 확률이 0이라는 증명이 아니다.

필수 위반은 잘못된 Task/Execution의 외부 명령/제어, 같은 명령의 중복 외부 효과, 철회/다른 질문의 승인 사용, 허용하지 않은 정보 접근/제공, 다른 업무로 질문 답변/결과 적용이다. 일반 표현/설명 오류와 구별해 독립 원장을 남긴다. 위반 후보도 모든 적용 QA의 값과 손익을 측정/보고하며 최종 선택 적격성만 제한한다.

같은 DP의 A/B 차이가 **1 percentage point 이상이고 §3.4의 paired 95% 구간이 0을 포함하지 않을 때** 정확성의 의미 있는 우위로 인정한다. 1pp는 2% 항목 오류 예산의 절반에 해당하는 선택 차이로 정했으며 이 분모에서 순 정답 차이 최소 6개다. 필수 위반/목표 충족 여부와 함께 해석한다. 미달 후보가 더 높은 정확률을 보였다는 사실도 그대로 남긴다.

차이가 1pp 미만이면 선택상 작은 차이로 보고하고, 구간이 0을 포함하면 우열 미입증으로 보고한다. 미입증을 통계적 동등성으로 바꾸지 않는다. 정확성만으로 승자를 만들지 않고 합의할 다른 QA 우선순위와 손익을 사용한다. 현재 전체 QA 우선순위는 새 다섯 묶음에서 아직 정하지 않았으므로 이번 정확성 설계만으로 최종 A/B를 선택하지 않는다. 이 규칙은 각 DP의 쌍 비교용이며 네 비교 전체의 동시 95% 보장을 주장하지 않는다.

### 3.6 측정 절차와 관측 근거

공통 환경/후보 구성은 §8을 사용한다. 아래에서는 정확성의 기대값과 실제 처리 evidence를 어떻게 연결하고 채점하는지 정한다.

#### 3.6.1 공통 검사 방식과 관측

정답 조건은 다음 검사 방식으로 표현한다. **테스트마다 새로운 채점 알고리즘을 만들지 않고 조건 유형, 비교 연산과 기대값을 지정한다.** 아래는 평가 설계이며 실행 harness나 runtime schema를 구현한 것은 아니다.

| 공통 검사 방식 | 용도 | 예 |
| --- | --- | --- |
| 값/의미 일치 | ID, version, 상태, 의미가 정해진 목표/제약 | 대상 업무=메일, 기간=3분기, 기대 상태=접수됨 |
| 집합 일치 | 필수 대상/조건의 누락 및 원치 않은 추가 | 참조 대상={A, B}, 다른 C 포함 금지 |
| 허용 결과 집합 | 요구를 만족하는 복수 경로/표현 | 제한된 조회의 허용 직접 응답/위임, 의미가 같은 질문/안내 |
| 관계/전이 충족 | 조건/의존 graph, 실제 상태 변화와 인과 순서 | 요약 결과 준비 뒤 해당 참조로 메일 인계, 취소 접수와 종료 구별 |
| 금지 효과 없음 | 정해진 관찰 구간 전체의 부정 조건 | 답변 전 임의 실행 없음, 다른 Task 취소 없음, 중복 외부 명령 없음 |

자연어 결과는 정확한 문자열 일치로 채점하지 않는다. 사전 등록한 의미 사실/허용 표현 기준에 맞춰 목표, 조건과 주장 사실을 판정한다. 문장마다 임의의 “그럴듯함” 점수를 주지 않으며 자동 판정이 어려운 사실은 같은 rubric과 검토 절차로 기록한다. 자동/수동 판정과 평가자 불일치 처리는 §3.6.3으로 고정했다.

관측은 각 조건의 경계에 맞춘다. C1~C4는 채택 의미와 실제 처리에 사용한 대상/관계를, C5는 명령 전송/Agent receipt/상태 반영을, C6는 실제 Text 표시/음성 재생과 기록을 연결한다. 공통 의미로 정규화한 관측 record를 쓰되 A/B의 내부 저장 필드나 중간 Module을 같은 형식으로 바꾸도록 요구하지 않는다. 필요한 adapter와 필수 evidence는 측정 계약에서 별도 설계한다.

정답 조건별 record에는 `과제 ID, 조건 ID, C 유형, 검사 방식, 기대값, 실제값, evidence 참조, 판정, 오류 원인`을 둔다. 이번 여섯 항목의 결과는 `정답/오답`으로 남기며 N/A는 사용하지 않는다. 필수 결과/관측의 후보 귀속 누락은 오답으로 남기고, 시험 수집기 결함은 §3.6.3의 INVALID 절차를 따른다. 금지 효과가 없다는 판정에는 전체 관찰 구간의 필수 trace가 필요하다. 끝 상태만 보고 중간 오실행이 없었다고 추정하지 않는다.

기존 검사 방식으로 표현할 수 없는 중요한 사실을 발견하면 공통 조건/검사 정의를 개정하고 영향받는 사례 전체에 적용한다. 특정 DP나 실패 사례 하나에만 다른 판정법을 추가하지 않는다. 정답 파일은 평가자만 보며 후보에는 정상 사용자가 접근할 수 있는 입력/근거와 동일한 외부 지원만 제공한다.

#### 3.6.2 모든 테스트에 사용할 작성 양식

```text
과제 ID / 대표 상황 S1~S6 / 고정 UC / 공통 변형 tag
초기 상태: 대화, 기존 업무/질문, 허용 정보/권한, 원본 version, 실제 전달 범위
입력과 사건: Voice 발화의 공통 전사/시각, 화면/행동 근거, Agent 원천 사건, 공통 후속 사용자 답변
사건 순서: 공통 원천 사건의 순서/경쟁 조건과 외부 지원 응답
기대 조건:
  C1 목표와 처리 방향       → 조건 ID, 검사 방식, 기대값 또는 허용 집합
  C2 대상과 근거            → 동일 양식
  C3 대화와 업무 연결       → 동일 양식
  C4 조건, 관계와 변경 범위 → 동일 양식
  C5 처리 효과와 상태       → 동일 양식
  C6 응답 내용과 실제 전달  → 동일 양식
금지 효과: 조건 ID에 연결해 관찰 구간 전체에서 확인
관찰 종료: 요구 결과의 관측 경계, 지연 사건 포함 구간, 공통 최대 대기 규칙
관측 및 판정: 조건별 실제값/evidence/정답 여부/오류 원인
```

이번 18개 사례는 필요한 확인 질문과 공통 답변을 같은 과제 안에 포함한다. 후속 질문을 별도 과제로 추가해 분모를 늘리지 않는다. 후보의 질문 문구/순서가 달라도 동일 의미의 답변을 제공한다. 답변 제공 규칙은 같은 질문 대상과 정보량을 유지하며 필요 없는 힌트를 추가하지 않는다.

사건 schedule은 공통 원천 사건과 외부 의미 경계에 맞춘다. 특정 안의 내부 Module 시작/완료를 기준으로 다른 안에 더 유리한 근거를 주지 않는다. 후보의 계산/조회/확정 순서는 구조가 만들도록 두고 경쟁 조건의 적용 방법을 계약에 명시한다. v2의 사례별 조건/관찰 종료/최대 대기는 §3.2.3과 §3.6.3을 따른다.

원본 fixture 제작과 관측 adapter는 §8.3의 실행 준비 단계다. 상황 분류/분모/목표를 다시 결정하는 작업으로 복원하지 않는다.

#### 3.6.3 실행과 관측 절차

1. **실행 자산 제작:** 18개 원본/정답표를 §3.3.2대로 만들고 각 사례의 Voice 발화와 지정 조건 하나를 고정한다. 파일 hash, source event script, fixture 의미 ID와 runtime ID 대응, Voice/screen 시각, rubric을 고정한다. 후보에게 정답표를 제공하지 않는다.
2. **runner 검수:** 정답/누락/오선택/잘못된 상태/미전달 trace를 이용해 C1~C6와 위반 검출을 확인한다. 이는 검사기 검수이며 후보 정확성 점수에 넣지 않는다. critical Action은 stub 경계에서만 기록한다.
3. **모델/후보 binding:** 동일 build/설정과 실제 저장/인계/입력/표시/재생 경계의 관측을 확인한다. 구조별 prompt/운영 예산과 cache/생산의 version을 기록하고 준비 상태를 확인한다. 정답표를 보며 한쪽 prompt만 조정하지 않는다.
4. **동일 준비 상태 복원:** N/W/X의 동일 원본/외부 이력을 각각의 후보가 처리하게 한다. W에는 120초 준비 창, X에는 공통 변경/교차 script를 적용한다. 시험용 의미/파생 자료를 정답으로 선주입하지 않는다.
5. **쌍 실행:** 같은 사례/지정 조건/반복의 A/B를 가까운 시간에 연속 실행한다. 순서는 seed `20261010`으로 섞고 각 입력 조건의 5쌍에서는 A 선행/B 선행을 3/2 또는 2/3으로 배분한다. 같은 provider seed가 지원되면 대응시키되 동일 모델 응답을 강제하지 않는다.
6. **후속 사건/답변 제공:** 후보의 유효 질문에 정해진 의미의 Voice 답변을 공통 replay로 준다. 허용하지 않은 임의 추가 정보는 주지 않는다. 계획된 확인은 필요한 정보가 모두 채워질 때까지, 후보가 추가한 불필요한 확인은 최대 2회 답변 기회까지 제공하고 그 수고/시간/비용도 남긴다. 미지원 관계를 다른 목표로 바꾸는 답변은 제공하지 않는다.
7. **관찰:** 마지막 원천 입력/필수 외부 사실 또는 제공한 사용자 답변부터 각 자동 처리 구간을 최대 60초 관찰한다. 준비/대기 중에도 금지 효과를 기록한다. 필수 후속 사건은 script의 60초 안에서 발생시키고, 마지막 처리 후 5초간 늦은 반환/중복/옛 음성의 재활성화를 확인한다. 처리 episode 총 상한은 10분이며 외부 Agent의 실제 장기 업무가 끝날 때까지 기다리는 테스트가 아니다.
8. **판정/보고:** C1~C6의 실제값/evidence/0 또는 1, 세부 오류, 위반, 모델 사용량, 실제 완료/전달 시각을 저장한다. 같은 자료에서 §3.4의 전체/분해/완전 정답과 쌍 차이를 계산한다.

60초/10분은 미완료를 무한 대기로 숨기지 않기 위한 정확성 시험의 관찰 상한이다. 빠른 응답 목표나 정상적인 제품 응답시간 SLA를 이 숫자로 정의하지 않는다. 시간/비용/메모리 raw trace는 함께 수집할 수 있지만 그 QA의 대표 지표/목표는 이후 별도로 확정한다.

입력 onset→hold 수락→전송 시작의 경합에서는 **실제 순서**를 판정한다. 먼저 시작된 외부 효과는 확인/정정/취소의 대상으로 남기고, 이미 발생한 효과를 없었다고 표시하면 실패다. hold/권한 철회가 먼저 수락됐는데 이후 금지된 전송을 한 경우는 위반이다. 원천 사건과 software 인식 경계를 구별하는 원칙은 [event-boundary-contract](../../11-measurement/event-boundary-contract.md)를 따른다.

범위가 명확한 필수 사실을 자동 판정하고 자연어 출력/재생 구간은 목표/대상/조건/상태의 같은 사실 rubric으로 후보 이름을 가려 검토한다. 모호한 판정은 두 번째 평가자가 확인한다. 표현 차이는 허용하고 사실 추가/누락/모순은 허용하지 않는다. 불일치는 후보 이름을 가린 evidence와 원본으로 조정해 이유를 남긴다. 오답인 후보 출력을 정답으로 삼는 model judge를 단독 최종 판정자로 사용하지 않는다.

후보 누락/timeout이면 증명된 항목만 1로 남기고 나머지는 0이다. 예를 들어 의미는 맞았지만 Agent 인계/실제 전달이 없으면 C5/C6는 0이다. 이미 확인한 C1~C4를 무조건 모두 0으로 덮지는 않는다. 단, 후보 전체가 실패하여 근거가 없으면 여섯 항목 모두 0이다. 시험 수집기 결함이나 계획하지 않은 공통 provider 장애로 판정 자체가 불가능하면 A/B 쌍을 INVALID로 보존하고 복구 후 같은 쌍을 재실행한다. 후보의 잘못된 호출/예산 소진/필수 trace 미생성은 INVALID가 아니다. 원래 90개 유효 실행이 채워질 때까지 실패 사례를 유지하며 INVALID와 재실행도 공개한다.

## 4. 응답속도

**상태: 두 세부 항목의 정의 초안.** 정확성 다음의 공동 검토 대상이며 최종 항목 수/지표/목표는 아직 정하지 않았다.

### 4.1 정의와 평가 범위

#### 상호작용 반응성

사용자 입력이나 제어 사건에 대해 유효한 응답 또는 실제 제어 효과가 나타나기까지의 VIA 귀속 시간을 본다. 음성 출력 중단, 요청 정정과 Agent 업무 취소는 서로 다른 효과이므로 각각 필요한 사건을 정의한다. 일반적인 접수 멘트나 잘못된 빠른 응답은 해당 기능의 유효한 결과를 대신하지 않는다.

#### VIA 귀속 요청 완료 시간

요청 시작부터 필요한 최종 결과의 실제 전달까지 VIA가 만든 처리와 대기를 본다. 준비, 조회, 의미 판단, queue, 경합, 인계, 의존 요청의 해제, 검증, 재처리와 전달이 대상이다. Downstream Agent의 내부 대기, reasoning, 계획과 업무 실행은 동일한 외부 조건으로 두며 VIA 성능으로 평가하지 않는다.

상호작용 반응성과 일부 구간이 겹치더라도 두 값을 합산해 총점을 만들지 않는다. 병렬 실행에서는 외부 시간의 합을 전체 경과 시간에서 단순 차감하는 방식으로 귀속 시간을 확정하지 않는다. 클라우드 모델 왕복과 네트워크 지연을 포함한 시간 경계는 모든 DP에 공통으로 정의해야 한다.

## 8. 공통 PoC 환경과 A/B 비교 방법

현재 구체적인 실행 조건은 정확성 Voice PoC v2를 위해 정했다. 다른 QA를 정의할 때 공통 입력/원천 사건/후보/모델 조건은 함께 활용하되 시간/금액/변경/메모리의 지표와 관측 경계는 해당 QA 절에서 결정한다. 공통 전사/장치 replay를 실제 ASR 정확도나 물리 장치 응답시간 실측으로 해석하지 않는다.

### 8.1 공통 시험 환경

| 영역 | 고정할 시험 환경과 역할 |
| --- | --- |

| 44 | 41A/42A/44A/45A | 41A/42A/44B/45A |
| 45 | 41A/42A/44A/45A | 41A/42A/44A/45B |

이번 검토 중 병행 상세화된 [42 §4.2~4.3](./04-42-lifecycle-ownership.md#42-b의-입력-hold업무-접수전송복구-프로토콜)와 [44 §3.1](./04-44-continuous-interaction.md#31-공통-소유와-허용-경계)을 확인했다. 42B의 Hold/HoldAck, CommandIntent, ReleaseAndReconcile, AcceptanceReceipt와 업무 로컬 transmission CAS가 44A/B의 후속 실행에 연결되는 문서 계약이 추가되어 있다. [04-40 §6](./04-40-common-execution-contract.md#6-네-dp가-실제-프로그램에서-결합되는-지점)의 이전 UNRESOLVED 표기만 보고 프로토콜 설명 자체가 없다고 복원하지 않는다. **문서 계약은 있으며 실제 구현/조합 검증은 아직 없다.** 대화/업무 저장소가 공동 transaction을 가진 것처럼 구현하지 않고 위 독립 접수/ACK/UNKNOWN 경로를 실행해야 한다. 구현/관측 준비 전 상태는 NOT_READY이며 A/B 수치가 아니다. 위 한 조건 비교는 다른 조합에서의 상호작용 우열을 입증하지 않는다.

모든 Task를 실제 외부 계정에 만들 필요가 없다. Agent 업무 품질은 stub으로 통제하고 VIA의 요청/상태/전달을 검사한다. **41/45의 의미 LLM까지 정답 mock으로 대체하면 실제 의미 정확성 비교가 되지 않는다.** model mock은 runner/판정의 검수에만 사용하고 공식 정확률은 실제 모델을 통과한 후보 실행에서 계산한다. mock 오류 확률로 A/B 차이를 만들어내지 않는다. 결과 evidence는 `MEASURED_REFERENCE_HARNESS`와 실제 모델 실행의 `MEASURED_MODEL`을 명시하며 이 장비/replay/stub 조건의 결과다. PC 제품/실제 Agent의 `PRODUCT_E2E`로 부르지 않는다.

### 8.3 실행 준비와 정의 완료의 구분

**현재 정확성 평가 설계에서 닫은 것:** 요청 처리 정확성 정의, S1~S6, 18개 기본 사례, C1~C6 묶음별 이진 채점, Voice 단일 입력/사례별 조건/5회 반복과 분모, A/B 단일 변수 구성, 공통 환경/판정/관찰 절차, 목표/위반/차이 인정 기준.

**실행 때 해야 할 것:** 이 설계대로 원본/Voice replay/화면/사건 fixture를 제작하고 18개 사례의 108개 채점 칸에 정답값을 채운다. 후보/harness/관측 adapter와 42B의 문서화된 독립 접수/hold 계약을 실제 구현하며, 모델/장비/설정과 각 파일 hash를 manifest에 넣고 검사기를 검수한 뒤 실행한다. 이는 확정 정의의 구현/검증이며 상황/분모를 다시 선택하는 작업이 아니다. 이 요청에서는 후보나 모델을 실행하지 않았다.

추후 요구 범위를 바꿔야 할 때만 이유를 기록한 다음 버전으로 개정한다. 기존 계약과 생성된 실패/결과는 원래 버전으로 보존한다. v1과 현재 v2에는 아직 실행 결과가 없다. 기존 QA-19/QA-09/QA-29/QA-39, 참조 Architecture, ADR와 과거 결과를 이번 새 지표로 소급 변경하지 않는다. 다음 QA 정의 작업은 응답속도이며, 정확성 유형 수와 분모 논의를 처음부터 반복하지 않는다.
