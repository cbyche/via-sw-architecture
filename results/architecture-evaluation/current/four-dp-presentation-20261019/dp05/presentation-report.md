# DP05: C 선택과 조건 원문 보완의 실제 범위

## 기본 선택

이번 읽기 지원 수신자 조건의 목적 채택 QA01은 공통 함수를 사용하지만 실제 원문 입력이 달라 **구조적 동점이 아니라 우열 미확정**이다. A/B/C 원값 4.307/4.421/4.321초와 관측 20/21·21/21·21/21을 보존한다. QA02는 비적용이다. 이 불확실성을 공개한 조건부 권고는 QA03에서 VIA가 먼저 작업별 내용을 가공하지 않는 C의 4.329초가 A 11.019/B 12.439초보다 낮았다는 관측을 참고했다. 조건부 완료 평균과 같은 완료 목표 16개의 비교를 구별한다. C는 관측 QA04/05/06에서도 상대 열세가 없었다. 따라서 C1/C2를 입증되지 않은 상대 QA 열세의 해결로 만들지 않는다.

기존 최종 BASIC의 정상 첫 해석21호출/안 입력 token 합계는 A15,318/B41,002/C13,722, 출력은3,720/3,828/3,690이다. 단일 prompt 크기가 아니다. A의 이미 읽은 원문과 B의 valid record 원문 support가 prefix에 들어가며 C에는 그 보존 원문이 없다. 실제 요청 값은 A/C 15/21만 같고, A/B와 B/C는0/21이다. E3 후속 mail/meeting에서 A가 원문을 재사용하기 때문이다. 따라서 호출 위치만으로 영향이 없다고 판단할 수 없다. [첫 응답 입력 감사](basic-prefix-boundary-audit.json)는 원래 request bytes와 source를 보존한 읽기 전용 파생 분석이다. 새 API나 지연 재채점은 없다.

기본 N-H 구조계약 18/18과 실제 본문 C 12/18은 서로 다르다. B의 본문 15/18 이익도 QA02로 재명명하지 않는다. 상대적인 내용 취약점과 반복 읽기의 절대 부담을 별도 보완할 수 있다. 읽기 없는 Agent에 대한 A/B 연동 장점은 이번 공통 수신자 비교가 검증하지 않았다.

## C1: 이미 채택한 조건의 실제 원문을 최초 인계에 붙이기

고정 E3 × C/C1 × 3회, 각 9목표/인계다. 양쪽 모두 같은 `condition_source_refs`를 받는다. C1만 다음 위임 목적을 알기 전 해당 현재 원문 1–2행을 읽어 보존하고 최초 capsule에 붙인다. 평가용 추천 제품/정답은 넣지 않는다. 기존 조건 provenance가 이미 존재한다는 전제이며 그것을 새로 의미 추적해 생성하는 upstream 비용은 재지 않았다. 기존 BASIC 전체 C의 정확한 재실행으로 바꾸어 읽지 않는다.

## 무엇이 실제로 바뀌었는가

- C1은 입력 이전 3회 원문을 읽었다. 전체 파일 `read_to_string` 요청 1,848바이트, 해당 local read 구간 합계 0.200750ms, 첨부 상태 최대 직렬화 323바이트다. heap·물리 I/O 수치가 아니다. 미래 목적을 보고 선별한 요약은 없다.
- C의 receiver는 조건 원문을 2회 읽었고 7개 인계에서는 원문을 요청하지 않았다. C1은 9개 인계 모두에 원문 조건을 붙였고 receiver는 조건 원문을 추가 읽지 않았다. 공개 비교/견적은 각각 9회씩 같았다. receiver read 20→18이지만 prefetch를 합치면 **전체 원문 읽기 20→21**이다.
- 모든 인계가 양쪽 모두 receiver READ→result 경로였다. C1이 충분한 자료로 receiver 선택/결과 호출 자체를 생략한 것은 아니다. C는 목적 해석9+receiver선택9+결과9+복구1, C1은 목적 해석9+선택9+결과9였다.
- C1의 receiver 선택 입력 11,501token은 C 10,243보다 컸고 결과 입력도 14,345 vs 12,510이었다. 전체 비용 감소에는 C의 복구 1회 $0.0041768이 포함된다. 이를 제외하면 C $0.0365256, C1 $0.0376028이다. C1을 모델 호출/토큰의 일반 최적화라고 설명하지 않는다.
- C/C1의 **첫 해석 실제 API 요청 9쌍은 값이 동일**했다. 그럼에도 출력은 달랐다. 특히 C r2 mail 첫 안내는 `prioritize longer maintenance periods in any comparative statements`라며 가격 동률 전제를 강화했다. callback 9/9은 호스트 관측이지 ‘올바른 첫 구체내용 9/9’의 확정이 아니다. C1은 prefetch 원문을 이 prefix에 넣지 않는다. 그 뒤 품질 차이도 모두 prefetch 하나의 고립 인과라고 주장할 수 없다.

## 실패와 본문 판정

C r2 deck는 원문을 읽고 초안을 생성했지만 초기/복구가 모두 fact 15개를 반환하여 호스트 `facts.len()>14` 상한으로 게시되지 않았다. 에러 이름은 `missing_structured_facts_or_provenance`이나 실제로 모든 사실이 비어 있던 것은 아니다. frozen receiver 프롬프트에 숫자 14 상한은 명시되지 않았다. 의미 오답이나 미공급 원문으로 잘못 분류하지 않고, 이 계약 취약점과 비용을 그대로 보존했다. 사후 수정/재실행은 하지 않았다.

C r2 meeting은 가격차에도 긴 유지보수만으로 Aster 선호를 말했고, C r3 deck는 더 높은 가격에도 Aster preferred라고 명시해 원문의 ‘가격이 같을 때’ 조건을 위반했다. C r2/r3 mail은 동률 조건 명칭/마지막 단서와 현재 Aster 우위 문맥이 충돌하여 UNRESOLVED로 보존했다. C1 문안은 조건을 명시적으로 지키거나 현재 제품 추천을 하지 않았다. 휴면 조건을 매번 문자 그대로 반복하지 않는 것 자체를 실패로 추가하지 않았다.

저자는 실제 표시 17개와 미표시 1개를 고정 분모 18개로 대조했다. 독립 담당자는 저자 판정을 미리 받지 않고 mail6을 대조했고 C는 PASS1/UNRESOLVED2, C1은 PASS3으로 일치했다. 이는 일부 목적의 독립 확인이며 18개 전부의 독립 검토나 블라인드 사용자 연구가 아니다. [content-review.json](content-review.json)과 [독립 mail6](../dp04/independent-dp05-prefetch-mail-review.json), [prefix-review.json](prefix-review.json)을 보존했다. literal/동치/의미/호스트 종료를 섞지 않는다.

## C2는 기본 적용 보류

기존 C 12 episode × 기본/C2의 실제 응답 재생은 API 0회다. source/revision/정확 범위/access epoch/recipient 키와 매 hit 현재 권한 재검사로 읽기 선택·모델 payload·완료 본문이 모두 같았다. 실제 전체 파일 read 34→22, hit12, 최대 직렬화 cache14,790바이트였다. 그러나 전체 serving 합계는 7.601960→8.783749ms로 악화했다. E3만은 1.794333→1.491874ms로 줄었지만 전체 이득으로 바꾸지 않는다. 모델 호출/비용은 줄지 않았다. 현재 작은 로컬 원문에서는 기본 적용을 보류하고 비싼 반복 접근 조건에서 재검토한다.

## 조건부 결론과 정본

C 기본 선택은 QA01 우열이 미확정인 상태를 공개하고 이번 형식 QA의 VIA 처리·비용 이익을 참고한 조건부 권고다. QA 우선순위만으로 엄격한 전체 승자를 확정한 것은 아니다. C1은 **기존 조건 provenance가 있고 인계마다 조건을 잃을 위험을 줄일 필요가 있는 상황**에서 이번 E3의 의미 본문 이익을 관측한 보완이다. 모든 상황의 품질 개선·속도 개선·무상 provenance 추적을 입증하지 않았다. C2는 이번 전체 serving 결과로 기본 적용을 권하지 않는다.
