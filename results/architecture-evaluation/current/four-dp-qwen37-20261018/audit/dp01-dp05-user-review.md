## 1. 판단 요약

- **DP01:** A의 현재 이익은 같은 자료 후속 질문에서 추가 의미 모델 단계를 줄인 좁은 기제로 설명할 수 있다. QA02 100%를 요약 완성도 100%로 읽을 수 없다. 부족 근거를 발견한 뒤 실제 보완 없이 최종 결과를 채택하는 구현 결함과 요약 내용 미충족이 있으므로, A를 완결된 근거 공급 기능의 구조적 winner로 확정하는 것은 성급하다.
- **DP05:** C의 이번 총비용·전체 경과시간 이익은 실제 관측이다. 그러나 QA01 약 0.02ms와 C QA03 약 18ms는 이미 의미가 채택된 뒤의 국소 경로다. 원래 사용자 입력부터의 제품 응답시간으로 사용할 수 없다. A/B의 현재 호출 경로가 모든 강한 기본안을 대표한다고 확정할 근거도 부족하므로, C는 현재 구현과 읽기 지원 수신자 profile의 잠정 선택으로 한정한다.
- API 시간은 provider 요청 송신부터 반환까지의 관측 구간이다. 순수 모델 계산시간이나 로컬 Omni 지연이 아니다. [bridge.py:41](../../../../../benchmark/architecture/four_dp_poc/bridge.py#L41), [bridge.py:46](../../../../../benchmark/architecture/four_dp_poc/bridge.py#L46).

## 2. DP01: 실제 구조와 호출 차이

### 2.1 코드가 바꾸는 것

[dp01.rs:70](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L70)의 공통 첫 의미 호출에 A는 대화별 유지 근거를, B는 최소 최근 전달 이력을, C는 게시된 관계를 제공한다. 실제 근거가 충분하면 첫 호출에서 답할 수 있고, 그렇지 않으면 bounded source read와 추가 의미 호출을 수행한다. 직접 완료의 가용 근거·판본 관문은 [77행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L77), 실제 읽기는 [80행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L80), 추가 의미 호출은 [92행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L92)이다.

A의 view 갱신은 [97행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L97), 공통 최근 전달 이력은 [105행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L105)이다. B도 최근 답변을 이용할 수 있다. 새 대화에서는 A/B의 view·최근 이력이 초기화된다([67행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L67)). 현재 시험에서 view 압축 호출은 발생하지 않았다. 따라서 긴 대화 압축의 이익이나 오류를 측정한 것은 아니다.

C는 source activity마다 당시 허용된 원본 전체를 읽고 관계를 생산한다([52행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L52)). 이는 실제 생산 경로이지만 증분·배치·선택적 생산 구현은 아니다. 이 구현의 비용을 모든 게시 기억 구조의 고정 비용으로 일반화하지 않는다.

따라서 “문맥이 남아 같은 자료의 후속 질문에서 두 번째 모델 단계를 줄였다”는 설명은 코드와 trace로 지지된다. “파일 I/O가 줄어 전체 상황에서 A가 빠르다”는 설명은 지지되지 않는다. 현재 로컬 파일 읽기는 작으며 요청 시간 대부분은 API 호출이다. 요청 중 API 합계를 36으로 나누면 A 7,216.79ms, B 7,578.70ms, C 6,950.91ms이며, 표시 proxy 평균은 각각 7,226.13 / 7,589.08 / 6,957.52ms다. 모델의 출력량과 서비스 변동도 관측 차이에 포함된다.

C 비용은 A의 약 3.32배다. 관계 생산만 총 C 비용의 62.35%를 차지한다. 특히 생산 출력 41,513 token의 비용이 크다. 생산을 제외한 C 요청 경로도 $0.0460872로 A보다 약 25.07% 비싸다. 게시 records를 넓게 전달한 첫 호출 입력이 A 26,678 token보다 큰 C 62,385 token이기 때문이다. “생산만 빼면 C가 공짜로 재사용한다”는 해석은 틀리다.

source 파일 읽기 관측은 A 33회, B 39회, C 72회이며 C에는 생산을 위한 읽기가 포함된다. 이는 파일 API 실행 횟수이고 물리 디스크 I/O 측정이 아니다. C의 선생산은 다음 요청 이전에 모두 종료된다. 요청이 생산 도중 도착할 때의 대기나 자원 간섭은 이번 비교에 없다.

### 2.3 100 / 100 / 88.89%의 정확한 의미

QA02는 지칭 표현 36개의 **원본 source ID 집합**과 별도로 지정된 E3 판본의 최초 채택 일치율이다. 사실 요약이나 임의 문서 영역 식별의 완성도가 아니다. 판본·내용 조건은 [분리 oracle:81](../../../../../benchmark/architecture/four_dp_poc/oracles/dp01.json#L81), [분리 oracle:93](../../../../../benchmark/architecture/four_dp_poc/oracles/dp01.json#L93)에 있다.

C의 오답 4개는 E4에 있다.

- E4 q1 세 반복: 정답 `{old-research, old-price}`에 설명 자료 `old-explanation`을 추가했다.
- E4 q3 첫 반복: 정답 두 원본 대신 `old-explanation`만 채택했다.

이는 설명에 사용한 근거와 사용자가 지칭한 대상을 혼동한 실제 모델 출력이다. 원본 판본과 인용 범위가 유효하다는 host 검사는 이 semantic 구분을 보장하지 않는다. [원문 실패](../referent-failures.md)를 보존한다.

반대로 A/B의 100%도 올바른 요약을 의미하지 않는다. E3 q2 BASIC ABC 9개 답변과 A2 3개 답변은 사전 내용 조건의 금액 1,180,000원, 유지보수 36개월, 납기 11월 1일을 모두 누락했다. 표시된 것은 지칭 표현의 반복이었다. [내용 조건 보고](../semantic-conditions.md)는 원래 QA02 점수를 바꾸지 않는 별도 진단이다.

추가 원문 예시는 새 점수나 분모가 아니다. E3 첫 반복 q1에서도 A/B는 “실제로 설명한 기준과 받아둔 견적”만 출력했지만 C는 실제 기준·가격·유지보수·납기를 요약했다. E4 첫 반복 q1의 B도 요청문을 반복하면서 대상 ID는 맞췄다. 따라서 대상 점수만으로 C보다 A의 전체 근거 공급 품질이 좋다고 결론낼 수 없다.

### 2.4 부족 근거·완료 계약 결함

E3 q2 A/B에서 실제 관측된 경로는 다음과 같다.

1. 정정 source event가 유지 view와 관련 최근 답변을 무효화한다([48행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L48)).
2. 첫 모델은 catalog metadata만으로 `ANSWER`와 `reads: []`를 반환한다.
3. host는 실제 가용 근거가 없어 직접 완료를 거부한다([77행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L77)).
4. 그러나 reads가 빈 배열이므로 실제 원본 보완은 수행하지 않는다([80행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L80)).
5. 빈 `read_bundle`로 추가 모델을 호출하고, 그 결과의 source/version 선언을 최종 채택·표시한다([92행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L92), [93행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L93), [96행](../../../../../prototypes/candidates/four_dp_poc/src/dp01.rs#L96)).

이 경로는 부족 근거를 발견한 뒤 필요한 acquisition을 실제로 완료하도록 강제하지 않는다. 최종 경로에는 직접 완료 경로와 동등한 실제 근거 가용성 관문도 없다. 최종 prompt는 지칭 해석과 본문 응답의 계약을 충분히 분리하지 못했고, 출력 echo를 완결된 요약으로 차단하지 못했다. C는 같은 q2에서 v2 본문을 실제 읽었지만 최종 출력은 여전히 echo였으므로, 전체 실패를 A/B의 읽기 누락 하나만으로 설명할 수도 없다.

기존 시간은 “후보가 표시·완료 event를 낸 시간”으로 보존한다. 올바른 요약 전달 시각으로 바꾸어 설명하지 않는다. QA01/03의 오답 시간을 벌점으로 바꾸거나 QA02를 일반 답변 정확도로 확대하지 않는다. 다만 완결된 기능의 winner 선정은 공통 완료 계약 검증 전 유보해야 한다.

## 3. DP05: 이미 채택된 입력 뒤의 인계 비교

### 3.1 정확한 시작·끝과 역할 경계

실제 BASIC 코드는 [DP05 receiver v2](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs)를 사용했다. `adopt` 사건의 state와 delegate 목적·완료 조건·수신자는 fixture에 이미 주어져 있다. 현재 경로는 원래 자연어 사용자 입력을 해석하는 단계부터 시작하지 않는다.

- [v2:71](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L71): 공통 채택 state를 가져온다.
- [v2:84](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L84): delegate 사건의 목표를 가져온 직후 `STIMULUS`를 낸다.
- [v2:85](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L85): 이미 주어진 purpose로 처리 의도를 format하고 바로 `present`한다.
- [v2:125](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L125): 수신자 결과를 표시하고 `GOAL_COMPLETE`를 낸다.

정확한 stimulus/present 위치는 아래 소스 line anchor와 label을 함께 읽는다. QA01은 `STIMULUS → 첫 nonempty DISPLAY_PROXY`, QA03은 `STIMULUS → nonempty GOAL_COMPLETE`에서 receiver API 구간과 해당 사용자 대기를 제외한다([analyze.py:66](../../../../../benchmark/architecture/four_dp_poc/analyze.py#L66), [78행](../../../../../benchmark/architecture/four_dp_poc/analyze.py#L78), [85행](../../../../../benchmark/architecture/four_dp_poc/analyze.py#L85)).

따라서 약 0.02ms는 “채택 후 공통 처리 의도 callback”이다. 원래 사용자 요청에서 첫 의미 판단·응답까지의 공식 제품 지연을 측정한 값이 아니다. C QA03 18.246ms도 동일 후채택 경로에서 receiver API 송신·서비스·반환을 뺀 국소 VIA 처리다. DP01 약 7초와 직접 비교할 수 없다.

`role=RECEIVER`는 같은 실제 Qwen API를 사용하는 작은 수신자의 논리 책임 구분이다([v2:107](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L107)). 서로 다른 상용 Agent 제품, 별도 제품 설치, native session 이전이나 물리 process 경계를 검증한 것은 아니다. 역할별 비용 합계는 [analyze.py:131](../../../../../benchmark/architecture/four_dp_poc/analyze.py#L131), 실제 정가 계산은 [bridge.py:52](../../../../../benchmark/architecture/four_dp_poc/bridge.py#L52)다.

B는 실제로 work record를 생산하고 18번 모두 그 block을 선택했다. 그러나 실제 extract 모델 응답 18개 모두 original reads도 요청하여 원본 보완과 compose 호출을 추가했다. “B는 기록을 사용하지 않았다”는 설명은 틀리고, “기록을 재사용했으나 이번 표본에서 원본 읽기·목적별 구성 단계 제거로 이어지지 않았다”가 정확하다. B의 생산 API 구간 합계는 765.028초이며, 무위임 E1에만 미사용 생산 9호출/$0.0131528이 들었다.

### 3.3 실제 수신자 동작과 전체 시간

A/B/C 모두 같은 수신자 계약을 쓴다. 충분한 실제 capsule 근거가 있으면 첫 receiver 호출에서 완료하고, 부족하면 모델이 source/range를 선택한 후 실제 파일을 읽고 두 번째 결과 호출을 한다([v2:107](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L107), [119행](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L119), [122행](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L122)). manifest metadata 자체는 사실 근거로 인정하지 않는다.

A는 14/18, B는 17/18이 supplied capsule에서 바로 완료했다. C는 18/18에서 receiver 선택→실제 source read→결과 경로를 수행했고 source 범위 읽기는 35회였다. 이는 실제 읽기 지원 profile의 결과이며 수신자 자료 선택이 최소·최적이었다는 증거는 아니다. 예를 들어 E3 세 목적은 모두 같은 비교 1–4행과 견적 1–3행을 읽었다.

| 관측 | A | B | C |

| QA01 후채택 first-display proxy ms | 0.019 | 0.024 | 0.020 |

C의 receiver 비용은 A보다 28.72% 높지만 전체 모델 비용은 30.85% 낮고 전체 경과시간도 낮았다. 따라서 현재 관측 전체를 단순한 비용 외부 이전만으로 설명할 수는 없다. 다만 VIA $0/18ms만 떼어 구조 승리나 체감 완료시간으로 제시해서도 안 된다.

### 3.4 유효한 참조 경로에 관한 정정과 강한 기본안의 범위

**이 감사의 정정된 좁은 진술:** A/B에는 유효 artifact reference 표현이 있다. `passages`는 원문 전체가 아니라 source span과 explanation을 담고, `capsule_valid`는 그 참조의 판본·권한·범위를 검사한다([v2:15](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L15), [97행](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L97)). 따라서 “A는 reference-only 자료를 표현할 수 없다” 혹은 “A는 항상 원문 전체를 수신자에게 보낸다”는 주장은 틀리다.

실제 제약은 **A의 첫 선택 결과를 유효 참조 capsule로 직접 확정하는 분기가 없고, 선택한 reads를 즉시 실행한 뒤 A는 항상 별도 compose 호출을 추가한다**는 점이다([v2:93](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L93), [94행](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L94), [96행](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L96)).

처음에 metadata와 채택 조건만 있고 source-backed 설명을 새로 만들어야 하는 경우, 선택→읽기→구성의 두 의미 호출은 합리적 구현이다. 그러나 유효 참조나 이미 획득한 공통 근거만으로 그 목적의 인계를 충족하는 경우에도 같은 별도 구성 호출을 강제하는 현 경로가 모든 강한 A를 대표한다고 확정할 수는 없다. 그 앞의 의미 채택에서 실제로 얻은 근거가 있다면 A/B/C 모두 동등하게 사용할 수 있어야 한다. 존재하지 않는 공통 근거를 무료 완성 입력으로 제공하자는 뜻은 아니다.

B에는 이미 original reads가 필요 없을 때 유효 block과 추출 summary로 capsule을 확정하는 경로가 있다([v2:98](../../../../../prototypes/candidates/four_dp_poc/variants/dp05-receiver-v2.rs#L98)). 따라서 B의 compose가 코드상 항상 강제된다는 주장도 틀리다. 실제 모델이 18/18에서 원본 읽기를 택한 이유가 의미상 누락인지, 현재성 검사를 위해 불필요하게 재읽은 것인지, prompt 계약의 중복 유도인지 분리되지 않았다. 호스트는 이미 source 판본·권한을 확인하므로 이를 semantic 재요약 필요성과 구별해야 한다.

현재 C는 이 구현/profile의 잠정 선택으로 남길 수 있다. 다만 모든 A/B/C 구조를 대표한 일반 선택으로 격상하는 것은 성급하다. 강한 기본안의 필수 재사용 경로를 확인하는 일은 캐시·배치·부분 갱신 같은 선택 후 tactic을 무료로 선반영하라는 요구와 다르다.

### 3.5 N-H·권한 검증 범위

N-H는 필수 목표·조건·제외·허용 Action·현재 source revision·접근·capsule provenance의 계약 검증이다. 자유문 초안의 모든 사실이나 Agent 도메인 품질을 평가한 점수가 아니다. [score_dp05.py](../../../../../benchmark/architecture/four_dp_poc/score_dp05.py)를 참조한다.

본 비교의 실제 receiver read denial은 전 안 0건이고 private-annex 읽기 요청도 없었다. E4는 철회 이후 manifest 제외와 현재 허용 자료 제공을 관측했다. receiver가 금지 자료를 실제 요청한 뒤 거부당한 본 비교라고 설명하면 과장이다. 그 거부 경로는 별도 guard probe로 구별한다.

B E4 첫 반복에서 80행짜리 원본에 76–90행/91–105행을 인용한 생산 block 2개가 게시 전에 거절됐다. 유효 원본 보완 뒤 N-H는 통과했으며 폐기 생산 비용도 남아 있다. provenance 방어가 동작한 사실과 semantic 설명이 항상 맞다는 주장을 구별한다.

## 4. 최소 재검증 설계 — 새 실행 승인을 뜻하지 않음

1. **기존 결과 보존:** 기존 source/binary/freeze/oracle/raw와 공식 QA 결과를 덮어쓰지 않는다. 새 설계·버전의 계약과 결과를 별도로 기록한다.
2. **DP01의 공통 완료 계약:** 지칭 대상 필드와 사용자 요청에 대한 실제 응답을 분리하고, 직접 완료가 근거 부족으로 거절됐으면 원본 acquisition 또는 명시적 부족/보류 경로를 반드시 수행한다. 추가 호출의 최종 채택에도 실제 가용 근거·판본 관문을 적용한다. 기대 금액이나 정답 ID를 후보에 주지 않는다.
3. **기존 내용 조건의 소비:** 평가기는 이미 분리된 `semantic_checks`를 실제 집계한다. 각 후보는 원본과 실제 질문만으로 답하고 oracle는 평가기만 읽는다. 추가 내용 조건이 필요하면 결과 전에 공통으로 freeze하며 QA02를 일반 답변 정확도로 바꾸지 않는다. 오답의 원래 시간은 그대로 보존한다.
4. **DP05 clock 선택:** post-adoption 인계 기제만 비교한다면 지금 값의 명칭과 주장을 해당 slice로 한정하고 QA01은 이 구조 차이에 비적용/동점이라고 설명한다. 원래 사용자 입력부터의 동일 QA01/03을 주장하려면 새 계약에서 공통 실제 의미 채택 prefix를 포함하고, 기존 국소 측정과 구별한다.
5. **DP05 강한 A/B 확인:** 실제 공통 기확보 근거의 유무·생산 비용을 모든 안에 동일하게 공개한다. A는 그 목적에서 유효 참조만으로 충분할 때 별도 요약을 강제하지 않는 경로를, B는 유효 게시 block을 그대로 추출하고 필요한 누락에만 원본을 보완하는 경로를 명시한다. 둘 다 actual model 판단과 현재성/권한 검사를 유지하며 참조만의 기능 축소나 무료 완성 record를 사용하지 않는다. 캐시·배치 등 새 tactic의 자동 추가는 요구하지 않는다.
6. **동일 조건 재비교:** 수정이 필요한 DP의 같은 네 episode와 세 반복을 새 freeze에서 A/B/C 모두 비교한다. 비용은 준비·미소비·폐기와 receiver 사용량까지, 시간은 요청 전 준비·후채택 VIA·receiver API·전체 경과를 함께 공개한다. 함수/호출 수를 같게 강제하지 않고 정상/실패 결과를 모두 보존한다. 기존 선호 선택을 유지하려고 oracle·모집단·모델 설정을 사후 조정하지 않는다.

본 감사는 위 계획의 실행, 추가 API 지출, 제품 통합, QA 의미 변경이나 accepted ADR 변경을 승인하지 않는다.
