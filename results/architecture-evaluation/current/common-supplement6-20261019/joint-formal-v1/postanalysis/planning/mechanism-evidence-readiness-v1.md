## 2. Specific source-supported limits

1. **DP1:** `evidence.rs:352–445` always calls `evidence_select_ranges`. Available original passages can come from DP1 state **and** `handoff_prefix_originals`; attribute their owner from acquisition/producer provenance, not a configuration letter. `EVIDENCE_ORIGINAL_REUSED` records a selected source range copied from available material. It supports an observed reuse claim, not elimination of the common selector call, a counterfactual read count, or a token/time saving. Actual request inputs, selected spans, denials, preparation/eviction/repair and all stage costs must remain visible.
2. **DP4:** `HANDOFF_RECORD_COMMITTED` contains producer-backed records. A `record_id` alone is not a generation or revision key. A new commit/producer with the same ID is newly generated material. `HANDOFF_BUILD_BRANCH.record_ids` is a selection-plan field; use the actual built capsule, `AGENT_INGRESS.data.request.contract.capsule`, and the receiver chain to establish transfer and supply. A stale built contract that never reaches ingress is not consumption. Even repeated supply to a receiver does not prove which derived prose the model relied on internally.
3. **Endpoints and scope:** preserve actual source revision, request revision, goal association, read permission, external-share permission and action authority as separate facts. Join existing endpoint references; do not choose a new QA01 callback or credit later handoff work to an earlier response. Receiver acceptance and source support establish only the frozen bounded synthetic work. No physical file/send/product success follows.
4. **Cost/memory:** join existing call UUIDs and accepted accounting; do not compute avoided cost, reprice, drop unused preparation, or charge duplicate ledger copies. Logical serialized buffers are diagnostics, not RSS, actual heap residency, or an attribution of peak RSS to one record.
5. **Supplement:** contract 20 states that its six cases have no intended handoff. Keep every DP4 QA and producer cost there. This condition cannot validate handoff amortization; unexplained missing events in a truncated/failed trace must not be relabeled as a demonstrated inactive mechanism.

### Fixed resource bounds and failure handling

Prospective defaults, declared before execution: one run at a time, one trace up to 16 MiB, one linked model request up to 1 MiB, at most 100 selected request files per run, at most 16 GiB aggregate input, and at most 2 MiB projected output per run. Input numbers are operational caps, not population filters or claims about current file sizes. Use file metadata before reading, hash only bounded files, release each request before the next, and write incrementally. Do not retain full trace bodies across runs or recurse through directories. No image/base64 decoding, model/evaluator/parser execution, network or background workers.

An exceeded/missing/invalid source emits an explicit issue and planned row with unfilled linkage; it must not silently truncate, discard the row, or certify absence of events. Once the aggregate cap is reached, retain all remaining planned identities as not extracted due to that cap. Root may authorize a newly versioned cap plan from quiescent size metadata before an execution; never expand limits based on favorable/unfavorable results. Final receipt lists planned/attempted/complete/partial/unavailable/conflict counts, byte totals, input/output hashes and elapsed time. Preserve failed attempts and prior outputs. This proposal has not been implemented, tested or run.
