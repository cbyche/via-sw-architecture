# DP02 보완 BASIC 설명 — 현재 모델 step과 요청별 worker

## 범위와 구조적 직관

네 사례를 A/B 각각 세 번 실행한 실제 24개 비교다. 같은 Qwen snapshot, 입력, 출력 한도, source 검증, 제한된 복구를 사용했다. A는 대화의 현재 **모델 호출 step**이 끝나면 후속 입력을 처리한다. 긴 요청 전체가 끝날 때까지 기다리는 구조가 아니다. B는 요청별 worker를 유지하고 여유 슬롯에서 후속 판단을 겹친다. B도 현재 revision과 공통 채택 상태를 연결해야 한다.

예상 이익은 K=2에서 B의 후속 입력 판단을 먼저 시작하는 것이다. 반대 조건 K=1에서는 같은 슬롯을 기다려야 하므로 이익이 줄어든다. 실제 첫 안내와 상세 완료를 분리했으며, 짧은 질문의 답을 채택 call에서 이미 완성했다면 추가 call 없이 전달하는 fastpath를 두 안 모두 유지했다.

## 네 사례의 뜻과 실제 endpoint

- **E1 비겹침:** R1을 처리한 뒤 U2가 들어온다. A/B가 같은 코드·문맥 경로를 사용한다. 관측 차이를 구조 고유 재사용 이익으로 설명할 수 없다.
- **E2 K=2:** 긴 R1 처리 중 U2가 “그 일은 계속하고, 별도로 TCP/UDP를 설명해 달라”고 한다. 한 발화의 CONTINUE와 NEW를 모두 해석한다. B는 실제 API 구간을 겹칠 수 있다.
- **E3 K=1:** E2와 같은 입력을 한 슬롯으로 실행한다. enqueue 앞의 A step 대기와 enqueue 뒤의 B admission/slot 대기를 함께 본다.
- **E4 정정과 기존 Task:** U2가 R1 범위를 비용만으로 정정한다. Q-MAIL-1은 기존 T-MAIL의 Agent 질문 통지로 QA01만 측정한다. U3는 그 질문의 답변 전달/접수 하위목표다. 새 메일 Task나 기존 Task 전체 완료로 세지 않는다. R1은 최초 입력부터 마지막 revision2까지 한 목표다.

### E2: K=2에서 확인한 B의 이익

U2 first는 A13388.270/B6269.559ms, U2 완료는 A13389.138/B7285.259ms였다. 원래 R1 완료도 A42256.086/B35212.888ms였다. B의 실제 HTTP send→terminal 중첩은 반복별5569.270/6479.925/6732.828ms, 평균6260.674ms였고 A는0이었다. A의 U2 입력→현재 step 경계 대기는 평균7254.459ms였다.

B는 U2의 답이 준비돼도 아직 미해석된 R1 입력의 관계가 남으면 공통 publication gate를 기다렸다. 이 실제 추가 대기는 평균1014.929ms였다. 현재 코드는 pending 집합 전체를 기다리는 보수적 gate다. 더 세밀한 구현의 최소 필요 대기라고 일반화하지 않는다.

이 조건에서 B가 후속 입력 판단을 겹친다는 직관은 실제 전송 구간과 일치한다. 입력/출력 token 및 provider 서비스 차이도 함께 있으므로 차이 전부를 순수 병행 효과의 분리 추정치로 부르지 않는다.

### E3: K=1에서 병행 이익이 사라진 조건

양쪽 실제 HTTP 구간 중첩은0이었다. U2 first/완료는 A13427.624/13428.554ms, B13086.246/13087.101ms다. R1 완료는 A39462.504/B40337.797ms였다. 작은 차이를 강한 A 우위로 만들지 않는다.

실제 호출 순서는 R1 의도 채택→U2 의도 채택/직접 답변→R1 상세→인용 복구로 같았다. U2가120ms에 들어와 첫 R1 채택 call부터 기다렸기 때문이다. A는 실제 step 경계 앞에서 기다렸고, B는 이미 만든 U2 요청을 같은 슬롯 앞에 대기시켰다. **이 입력 시점에서는 B의 긴 상세 생성이 U2 앞을 선점했다고 설명하면 틀린다.**

첫 반복의 구체 증거: A step 대기7094.949ms; B U2 admission→send7198.553ms. 그 다음 R1 상세도 U2 뒤에 보내져 B admission→send6651.520ms를 기록했다. enqueue→send에는 직렬화·예산/기록·슬롯 대기가 함께 포함돼 순수 슬롯 대기만 분리할 수 없다. 실제 provider 시작/끝과 predecessor UUID를 함께 남겼다.

### E4: 정정과 Agent 질문 답변의 구분

Q-MAIL-1 질문 통지는 두 안 모두 약0.06ms의 callback이었다. 이 통지는 사용자 목표가 아니다. U2는 원래 R1의 revision2를 채택하고 비용 범위 안내를 했다. U3는 실제 T-MAIL/Q-MAIL-1에 답변을 전달하고 고정 acceptance shim receipt를 받은 뒤 끝났다. receipt의 외부 대기는0이므로 이 DP의 QA03과 실제 전체 경과는 같다.

B는 R1 채택/후속 입력을 겹쳤고 실제 HTTP 중첩 평균7391.523ms였다. A는0이었다. U2 first A10481.158/B3634.459ms, U3 first A14278.718/B7419.251ms, 전달 완료 A14279.497/B7421.861ms였다. 원래 R1은 A23493.583/B14549.796ms에 마지막 비용 범위 결과를 표시했다. 최초 R1 시각을 정정 시각으로 재설정하지 않았다.

B rep3 U2는 CORRECTION→R1 자체는 맞았지만 task_id=T-MAIL을 불필요하게 함께 붙였다. 고정 strict multiset에서는 오답1건이다. 실제 실행은 CORRECTION의 target_request_id=R1을 사용해 비용 정정과 U3 답변 전달을 완료했다. 이를 잘못된 메일 전송이나 완전한 관계 성공으로 바꿔 말하지 않는다.

## 실제 실패와 복구 비용

E1 A rep3의 R1은 initial/repair 두 상세 시도를 모두 거부한 뒤 실패했다. 첫 제안은 quote에'...'를 끼웠고 repair는 quote를 고쳤지만 required revision1에 applied_revision2를 냈다. 프로세스 rc0·stderr없음, 여섯 calls 모두 HTTP200/정상JSON이다. null/parse/provider/프로세스 오류가 아니다. 이후 U2도 첫 인용 거부 후 실제 복구에 성공했다.

R1의 첫 progress는 7257.262417ms였다. 원래 입력→실패 callback은 41758.671542ms다. 상세 성공 QA03은 미관측으로 남겼다. episode 전체 6calls의 가격은 $0.0143528다. 실패를 다시 실행하거나 성공 완료 시각으로 치환하지 않았다.

보조로 성공/실패 terminal을 구분한 실제 관측 종료시간을 모두 모으면 A24개 평균24827.906ms(성공23+실패1), B24개20982.021ms(성공24)다. **이 값은 QA03 성공 완료시간이 아니다.** 실패시간을 포함하는 별도의 실제 attempt 종료 진단이다.

## 메모리와 조건

A의 최대 동시표본은 Python42.090496+Rust3.260416=45.350912MB, 같은 run 초기값34.553856MB다. B는42.778624+3.391488=46.170112MB, 초기34.783232MB다. 해당 peak의 실험 기록 보관 논리크기는 A40043/B41148bytes, Rust 직렬화 상태는29077/29222bytes다.

B의 동시 worker/입력 buffer가 늘 수 있다는 직관은 있지만 이 RSS 차이819200bytes를 해당 상태만의 효과라고 분해하지 않는다. Python에는 HTTP/직렬화·TLS/allocator·실험용events/calls가 섞여 있고, 직렬화 bytes는 RSS 할당이 아니다. 실제 역할별 동시 peak·초기값·delta·논리 분류와 명목 50ms 대비 실제 gap을 원시와 CSV로 제공한다. shared page 중복 계수는 확인하지 않았고 UI와 cloud weights는 제외했다. 제품 전체 RAM이나 512MB 충족 주장이 아니다.

## 발표용 결론과 재현

- K=2 E2/E4에서는 B가 실제 입력 판단을 겹치며 첫 안내와 원래/후속 목표 완료가 빨라졌다.
- K=1 E3에서는 병행 구간이 없어졌고 같은 호출 순서로 수렴했다. 강한 반대 승리는 확인하지 못했다.
- E1은 같은 경로에서 발생한 모델 출력·복구·서비스 변동이다. A의 미완료를 빼고 전체 빠른 평균이라고 주장하지 않는다.
- B는 모든 예정 목표 terminal을 표시했지만 관계 metadata1건은 실패했다. A도 source/revision복구1건을 끝내지 못했다. 완전한 기능 성공이나 population 증명은 아니다.
